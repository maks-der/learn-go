# 21. Антипаттерны

## Описание

Эта тема показывает дизайны, которые падают по мере роста данных. Вы узнаёте, почему вредят **неограниченные массивы**. Почему вредят документы около **16 MB**. Почему вредит **ключ шарда низкой кардинальности**. Почему вредит **транзакция на каждую запись**. Почему MongoDB — **не подмена SQL один-в-один**. Сначала завершите моделирование, шардирование, транзакции и производительность.

Используйте один термин для каждого понятия. **Антипаттерн** — дизайн, который выглядит удобным, а затем падает. **Неограниченный** значит, что массив или документ могут расти без запланированного лимита. **Низкая кардинальность** значит мало различных значений. **Подмена один-в-один** — идея, что можно сохранить привычки SQL и только сменить драйвер.

Если антипаттерн уже используете, меняйте модель. Сначала не добавляйте больше железа.

## Неограниченные массивы, которые растут вечно

**Неограниченный массив** — поле, которое получает `push` на каждое событие без потолка. Примеры: все комментарии вирусного поста, все просмотры страниц, все строки журнала, все платежи на одном документе клиента.

Проблемы:

- Каждое обновление переписывает больший документ
- Документ приближается к 16 MB, затем записи падают
- Индексы по массиву становятся большими (мультиключ)
- Каждый читатель загружает весь массив, даже когда нужны последние пять элементов
- Одновременный `$push` и другие обновления конфликтуют на одном документе

Правило моделирования остаётся: данные, к которым обращаетесь вместе, могут жить вместе **если массив остаётся ограниченным**.

Ограниченные шаблоны:

- Держать последние N элементов (`$slice` на `$push`)
- Хранить потомков во второй коллекции с id родителя
- Использовать шаблон bucket или коллекцию временных рядов для событий
- Использовать шаблон outlier для одного популярного родителя

«Маленький» массив, который растёт на 1 элемент в день, через несколько лет становится большим. Запишите потолок в дизайне.

Не делайте `$push` события просмотра в документ пользователя на каждый клик.

Не опирайтесь на «потом заархивируем» без задачи и даты.

`explain` и `collStats` не всегда делают это очевидным, пока один документ не станет огромным. Запросите максимальную длину массива агрегацией (`$size`) на выборке.

## Огромные документы около 16 MB

Лимит размера документа BSON — **16 MB**. Документ, который «всего» 10 MB, уже проблема. Он использует кэш, канал и время блокировки на этом документе.

Причины:

- Неограниченные массивы
- Встроенные файлы (используйте GridFS или объектное хранилище)
- Огромные строки (дампы HTML, изображения base64)
- Вложенные копии тех же связанных данных

Эффекты:

- Вставка или обновление падает с ошибкой размера
- Каждый find этого документа двигает мегабайты
- Рабочий набор сжимается (несколько огромных документов заполняют ОЗУ)
- Репликация и резервные копии занимают дольше

Предотвращение:

- Хранить двоичные данные вне документа
- Ссылаться на большие связанные графы
- Использовать шаблон subset (хранить маленькое превью, остальное держать в другом месте)
- Валидировать максимальную длину в приложении

Если вы около лимита, вы опоздали. Разделите до ошибки в продакшене.

Не храните PDF как поле BinData 14 MB, потому что «это меньше 16 MB».

Не делайте `find` полного документа, когда API нужны три поля. Проекция помогает, но сервер всё равно может загрузить документ.

`Object.bsonsize` в `mongosh` (или помощник размера драйвера) измеряет документ. Смотрите размер `p99`, не только среднее.

## Ключи шарда низкой кардинальности

Ключ шарда **низкой кардинальности** имеет мало различных значений. Примеры: `country` с тремя значениями, `status` с четырьмя значениями, `isActive` с двумя значениями.

Эффекты:

- Чанки нельзя разделить дальше различных значений
- Эти чанки становятся **jumbo**
- Все документы с `status: "open"` живут на одном шарде
- Этот шард **горячий**
- Балансировщик вас не спасёт

Хеширование булева не создаёт кардинальность. У вас всё равно два хеша.

Составной ключ `{ status: 1, orderId: 1 }` может добавить кардинальность **если** `orderId` различен. Refine может добавить суффикс. Префикс `status` всё равно группирует открытые вместе. Записи новых заказов «open» всё ещё могут концентрироваться.

Высокая кардинальность необходима и недостаточна. Также нужны ровная частота и ключ, который используют запросы.

Не шардируйте по полю потому что «оно есть в каждом запросе», если у поля пять значений.

Не путайте уникальный `_id` (высокая кардинальность) с хорошим **диапазонным** ключом, если `_id` монотонен. Это другой антипаттерн (горячий последний чанк). Низкая кардинальность — проблема немногих значений.

Если уже шардировали по плохому ключу, используйте refine или reshard (тема 13). Это проект.

## Транзакции на каждую запись

У **мультидокументной транзакции** есть цена. Она держит снимок. Она может прерваться. У неё есть лимиты времени и размера. Она нужна для некоторых денежных перемещений между документами.

Антипаттерн — оборачивать **каждый** `insertOne` или `updateOne` в транзакцию «для безопасности».

Проблемы:

- Лишняя задержка
- Больше abort под нагрузкой
- Разработчики прячут плохую модель (два документа, которые принадлежат одному документу)
- Люди держат транзакцию, пока вызывают HTTP или ждут пользователя
- `bulkWrite` внутри транзакции — не причина транзакцировать каждую малую запись

Записи одного документа уже атомарны. Используйте это.

Используйте транзакцию, когда два документа должны измениться вместе и нельзя смоделировать их как один документ или как идемпотентную починку.

Не начинайте сессию и транзакцию в общем репозитории `save()`, который вызывает каждая возможность.

Не копируйте реляционную привычку «всегда BEGIN». MongoDB — не та среда выполнения.

Если транзакция нужна часто, сначала спросите, могут ли документы быть одним документом.

Write concern и уникальные индексы предотвращают многие баги без транзакции.

## Считать MongoDB подменой SQL один-в-один

**Подмена SQL один-в-один** — идея, что вы сохраняете таблицы, нормализуете каждую сущность, соединяете в каждом чтении и только меняете базу.

MongoDB не запускает SQL как основной язык. `$lookup` — не полный планировщик соединений SQL для каждого разового отчёта. Нет декларативных внешних ключей как основного инструмента целостности. Транзакции есть, но они не запись по умолчанию.

Если сопоставить каждую таблицу коллекции один-к-одному, часто получаете:

- Много обменов или много стадий `$lookup`
- Медленные отчёты, которые SQL делал лучше
- Схему, которая никогда не использует встраивание
- Ключи шарда, которые не совпадают с доступом
- Раздражение, что «MongoDB медленный»

MongoDB подходит, когда проектируете **документы под доступ**. Встраивайте то, что читаете вместе. Ссылайтесь на то, чем делите и обновляете независимо. Используйте хранилище или реляционную базу для тяжёлой разовой аналитики, если это нагрузка.

Мигрировать из SQL можно. Нужно **перепроектировать**. Недостаточно только мигрировать типы.

Не реализуйте эмулятор SQL на MongoDB для всего приложения.

Не запрещайте встраивание потому что «нормализация всегда права». Не встраивайте всё потому что «соединения запрещены». Оба крайности — антипаттерны.

ORM, которые прячут документы за таблицами, могут воссоздать этот антипаттерн. Читайте, какой SQL они генерируют или какие запросы испускают.

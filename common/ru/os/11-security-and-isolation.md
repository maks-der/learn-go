# 11. Безопасность и изоляция

## Описание

Ядро изолирует пользователей и процессы. Эта тема объясняет идентификаторы пользователей и наименьшие привилегии, возможности Linux и seccomp. Вы изучаете идею песочницы, разницу между эксплойтом ядра и эксплойтом пользовательского пространства и Secure Boot на высоком уровне.

Завершите эту тему после виртуализации. Завершите эту тему до сетевого стека (тема 12). Вы уже знаете биты прав, пространства имён и ядро против пользовательского пространства.

Используйте один термин для каждого понятия. Идентификатор пользователя (UID) — целое, которое ядро хранит для процесса и для владения файлом. Наименьшие привилегии — правило, что программа должна работать с наименьшими правами, которые всё ещё позволяют ей работать. Возможность — раскол старой власти root на именованные права. Seccomp — фильтр системных вызовов. Песочница — сочетание инструментов изоляции вокруг программы. Не смешивайте возможность с битом права файла. Не смешивайте Secure Boot с паролем входа.

## UID и наименьшие привилегии

Linux идентифицирует пользователя по UID. У процесса есть реальный UID, эффективный UID и сохранённый UID (и UID файловой системы). Ядро использует эффективный UID для большинства проверок прав. `id` печатает идентификаторы оболочки.

UID 0 — root. Root может пройти большинство проверок прав. Программа, которая работает как root, может читать частные файлы, привязывать низкие порты и загружать модули (если другие слои не останавливают).

Наименьшие привилегии значат:

1. Используйте обычную учётную запись пользователя для повседневной работы.
2. Дайте службе свой UID.
3. Не запускайте сетевой демон как root после bind, если можете сбросить привилегии.
4. Используйте `sudo` для одной команды, не оболочку root на весь сеанс.

Двоичные файлы `setuid` работают с эффективным UID владельца файла. `passwd` — классический пример. Ошибка в программе `setuid` — риск повышения привилегий. Дистрибутивы сводят к минимуму двоичные `setuid` root.

Пространство имён пользователя может отобразить UID 0 внутри пространства имён на ненулевой UID хоста. Внутри процесс выглядит как root. На хосте он не root. Эта карта — строительный блок контейнера (тема 10). Сама по себе она не полный продукт безопасности.

Биты прав файла (тема 6) всё равно применяются. Изоляция падает, если каждый файл читаем всем миром или если UID вашей службы может писать `/`.

Не практикуйтесь как root. Не отключайте проверки пользователей в ядре, которое вам нужно.

## Возможности и seccomp

Старый Unix считал root одним битом: UID 0 или нет. Возможности Linux делят эту власть на именованные флаги. Примеры:

- `CAP_NET_BIND_SERVICE`: привязывать порты ниже 1024
- `CAP_NET_ADMIN`: настройка сети
- `CAP_SYS_ADMIN`: большой набор операций администратора (всё ещё очень широкий)
- `CAP_SYS_MODULE`: загружать модули ядра

У процесса есть наборы возможностей: permitted, effective, inheritable и bounding (и ambient в современном Linux). Возможности файла могут дать подмножество двоичному файлу без полного setuid root. `getcap` и `setcap` управляют возможностями файла. `capsh` и `/proc/<pid>/status` (`Cap*`) показывают возможности процесса.

Сбрасывайте возможности, которые не нужны после старта. Веб-сервер может привязать порт 80, затем сбросить `CAP_NET_BIND_SERVICE`. `CAP_SYS_ADMIN` всё ещё близко к root. Не считайте «я использовал возможности» за «я в безопасности».

Seccomp (secure computing) — фильтр Linux на системные вызовы. Процесс ставит программу Berkeley Packet Filter (BPF). Каждый системный вызов попадает в фильтр. Фильтр может разрешить, отказать (`ENOSYS` или `EPERM`), убить поток или поймать.

`seccomp-bpf` — обычная форма. libseccomp помогает писать фильтры. Docker и systemd могут применять профили seccomp. Профиль, который разрешает только `read`, `write`, `exit` и `sigreturn`, — исторический строгий режим. Настоящим программам нужен больший список разрешения.

Seccomp сам по себе не проверяет пути файлов. Процесс, которому можно `open`, всё ещё может открыть много файлов. Сочетайте seccomp с UID, chroot или пространствами имён и правами файлов.

Плохой профиль seccomp ломает glibc (ей нужны неожиданные вызовы). Тестируйте. Не копируйте случайный список отказа из старого блога.

Не путайте возможности с битами режима файла. `r-x` — не `CAP_NET_ADMIN`.

## Песочница

Песочница — сочетание инструментов изоляции вокруг программы, которая не должна вредить остальной системе. Ни один инструмент не есть песочница. Продукт — сочетание плюс политика.

Типичные куски Linux:

- выделенный UID и GID
- пространство имён монтирования и минимальная корневая файловая система (chroot, pivot_root или образ)
- пространства имён пользователя, PID и сети (тема 10)
- пределы cgroup (ЦП, память, pids)
- сброшенные возможности
- профиль seccomp
- монтирования только для чтения и `noexec`, где можно
- Landlock или AppArmor или SELinux (MAC) в некоторых дистрибутивах

Браузеры и среды языков используют песочницы для ненадёжного кода (отрисовщик, плагин). Доверенный процесс маленький. У ненадёжного процесса почти нет прав. IPC (тема 9) их соединяет. Сокеты Unix и `SCM_RIGHTS` часты.

Песочница падает, если:

- в ядре ошибка (следующий раздел)
- политика разрешает опасный системный вызов или записываемое монтирование
- вы делите `/` или `/proc` без осторожности
- вы запускаете помощник как root хоста

`systemd-run` и `bwrap` (bubblewrap) — пользовательские инструменты, которые применяют некоторые из этих кусков. Контейнеры — стиль песочницы. Они сильны ровно настолько, насколько профиль.

Не скачивайте ненадёжные двоичные файлы и не «сажайте» их на основной ноутбук без ВМ. Не считайте chroot достаточным. chroot — не граница безопасности для root.

## Эксплойты ядра и пользовательские эксплойты

Пользовательский эксплойт использует ошибку в программе пользовательского пространства. Примеры: переполнение буфера в помощнике setuid, обход пути в веб-сервере, внедрение команды в скрипте. Атакующий начинает с прав этого процесса. Если процесс — UID 0 или имеет широкие возможности, атакующий становится root в пользовательском пространстве. Ядро всё ещё может быть целым.

Эксплойт ядра использует ошибку в ядре или в драйвере. Примеры: плохой `ioctl`, гонка в системном вызове, use-after-free в сетевом протоколе. Атакующий начинает в пользовательском режиме и достигает режима ядра. Затем атакующий может менять учётные данные, отключить seccomp или читать любую память. Песочницы, которые доверяют ядру, падают.

Защита в глубину:

- чинить и обновлять пользовательские программы
- наименьшие привилегии, чтобы пользовательский эксплойт был меньше
- песочница, чтобы у пользовательского эксплойта было мало системных вызовов
- обновлять ядро и сводить загруженные модули к минимуму
- аппаратные функции (NX, SMAP/SMEP, KASLR) поднимают цену некоторых атак на ядро
- ВМ добавляют слой гипервизора (тема 10). Эксплойт гостевого ядра — не автоматически эксплойт хоста, но ошибки гипервизора бывают

`/proc/kallsyms` и указатели ядра могут помочь атакующему. Дистрибутивы их ограничивают. Не считайте «я не могу читать kallsyms» достаточным.

Этот путь не учит писать эксплойты. Вы изучаете разделение, чтобы выбрать правильное обновление и правильный слой изоляции.

## Secure Boot (высокий уровень)

Secure Boot — функция прошивки (UEFI). Прошивка проверяет криптографическую подпись загрузчика (или shim) до того, как запускает этот код. Загрузчик затем может проверить ядро. Цель: атакующий, который пишет файл на диск, не должен заменить путь загрузки неподписанной вредоносной программой.

Ключи сидят в прошивке (db, dbx, ключ платформы). Дистрибутивы поставляют подписанные shim. Вы можете записать свои ключи на машине, которой владеете. Корпоративные машины могут запереть ключи.

Secure Boot — не:

- пароль входа
- полное шифрование диска (это LUKS или другой ключ диска; часто используют оба)
- гарантия против позднего эксплойта ядра
- гарантия, если у атакующего контроль прошивки или физическое устройство DMA

Measured Boot и TPM (Trusted Platform Module) могут записывать хеши пути загрузки. Удалённая аттестация — поздняя тема. Этот раздел только называет идею: TPM хранит измерения. Secure Boot — политика, которая отказывает неподписанному загрузчику.

Если Secure Boot выключен, прошивка всё равно загружается. Проверка пропускается. Двойная загрузка и некоторые учебные установки его выключают. Знайте компромисс.

Тема 1 назвала UEFI. Этот раздел добавляет проверку подписи. Не отключайте Secure Boot на ноутбуке, которым пользуетесь для банка, если не знаете зачем.

2. Выполните `id`, `grep Cap /proc/self/status` и `ls /proc/self/ns`. Напишите по одной строке.
3. Нарисуйте стек защиты: прошивка, ядро, UID службы, seccomp.
4. Добавьте в закладки `man 7 capabilities`, `man 7 credentials` и `man 2 seccomp`.

#### Средние практические задания

1. Напишите план укрепления из шести строк для игрушечного сетевого демона: bind, сбросить UID, сбросить возможности, seccomp, chroot или пространство имён.
2. Используйте `sudo -l`, если есть sudo. Запишите одну команду, которую ваш пользователь может запустить. Не повышайте ради забавы.
3. Документируйте список «нельзя»: повседневная оболочка root, `chmod 777`, отключать Secure Boot без причины, пустой список разрешения seccomp только `open`.

#### Сложные практические задания

1. Прочитайте страницу man песочницы systemd (`systemd.exec`). Напишите карту на одну страницу от директив к темам 10 и 11.
2. Спроектируйте (на бумаге) помощник из двух процессов: непривилегированный рабочий, привилегированный открыватель, сокет Unix, `SCM_RIGHTS`. Укажите угрозу, которую снижаете.

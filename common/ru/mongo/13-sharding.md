# 13. Шардирование

## Описание

Эта тема показывает, как MongoDB делит один набор данных между многими машинами. **Шардированный кластер** имеет **шарды**, маршрутизатор **mongos** и **config servers**. Сначала завершите репликацию, моделирование и индексы.

Используйте один термин для каждого понятия. **Шард** — replica set, который держит подмножество данных. **Ключ шарда** — список полей, который решает, какому шарду принадлежит документ. **Чанк** — диапазон значений ключа шарда, который балансировщик может переместить. **`mongos`** — процесс, который маршрутизирует запросы.

Шардирование увеличивает ёмкость. Шардирование также увеличивает операционную цену. Не шардируйте коллекцию, которая ещё помещается на одном replica set.

---

## Когда шардировать

Шардируйте, когда одного replica set недостаточно. Частые сигналы:

- Рабочий набор не помещается в ОЗУ одного replica set
- Пропускная способность записи насыщает primary
- Диск одного replica set полон или скоро будет полон
- Один replica set не может выдержать целевую задержку на пике

Не шардируйте потому что «большие системы шардируют». Многие приложения долго остаются на одном replica set. Atlas и современное железо держат большие наборы данных на одном replica set.

Цена шардирования:

- Нужно выбрать ключ шарда
- Некоторые запросы становятся scatter-gather (бьют по многим шардам)
- У транзакций и соединений (`$lookup`) есть дополнительные лимиты и цена
- Вы ведёте много replica set плюс config servers плюс `mongos`

Шардируют коллекцию, а не «всю базу» как одну единицу. Другие коллекции могут остаться нешардированными. Нешардированные коллекции живут на primary shard.

Сначала завершите моделирование. Плохая форма документа плюс шард — всё ещё плохая форма.

Для учёбы можно запустить шардированный кластер в Docker или использовать шардированный кластер Atlas. На бумаге можно спроектировать ключ шарда до оплаты лишних шардов.

## Выбор ключа шарда (трудная часть)

**Ключ шарда** — одно или несколько полей, которые есть в каждом документе. MongoDB хеширует или ранжирует эти значения, чтобы разместить документ.

Ключ шарда — трудная часть. Плохой ключ создаёт **горячий шард** (один шард получает большую часть записей или чтений) или **jumbo-чанки**, которые не двигаются.

Полезный ключ шарда:

- **Высокая кардинальность** — много различных значений
- **Ровная частота** — значения не сваливаются на одно значение
- **Не монотонный для записей**, если нужно ровное распределение записи (или используйте хешированный ключ)
- **Присутствует в фильтре запроса** для целевых чтений

Плохой ключ шарда:

- Булево или статус с тремя значениями
- Монотонно растущий `_id` или метка времени для диапазонного шардирования (все вставки идут в последний чанк)
- Поле, которое большинство запросов не включает

У значений ключа шарда в документе есть правила. Ключ шарда нельзя снять. Значение ключа шарда документа можно изменить в текущих версиях, но изменение дорогое. Планируйте ключ так, будто он останется.

Составные ключи шарда часты. Пример: `{ tenantId: 1, orderId: 1 }`. Первое поле целится в тенанта. Второе поле добавляет кардинальность.

Приложение должно отправлять ключ шарда в запросах, когда может. Find без ключа шарда может разлететься на все шарды.

Не выбирайте ключ только потому что он уникален. `_id` уникален и всё равно может быть плохим диапазонным ключом, если растёт со временем.

Читайте официальные страницы ключа шарда. Тестируйте с данными, похожими на продакшен, до шардирования живой коллекции.

## Хешированные и диапазонные ключи шарда

**Диапазонный** ключ шарда размещает документы по порядку значений ключа. Соседние значения могут жить в одном чанке. Диапазонные запросы по ключу шарда могут попасть в один шард или несколько шардов.

**Хешированный** ключ шарда считает хеш значения ключа. MongoDB размещает документы по хешу. Вставки распределяются ровно, даже если исходное поле растёт со временем.

Используйте диапазонный ключ, когда:

- Многие запросы используют диапазон по этому ключу
- Значения уже распределяют записи
- Хотите соседние ключи на одном шарде

Используйте хешированный ключ, когда:

- Естественный ключ монотонен (ObjectId, метка времени)
- Нужно ровное распределение записи
- Принимаете, что диапазонный запрос по исходному полю разлетится

Хешированные ключи не помогают диапазонному запросу по исходному полю. Пример: хешированный `_id` не делает `find({ _id: { $gt: ... } })` одношардовым диапазоном.

Хешированный индекс создают как ключ шарда:

```javascript
sh.shardCollection("shop.orders", { customerId: "hashed" })
```

Составные ключи могут смешивать диапазонный префикс и другие поля. Читайте текущие правила. У хешированных составных ключей есть ограничения, зависящие от версии.

Не хешируйте поле низкой кардинальности и не ждите чуда. У булева всё равно два хеша.

Atlas и помощники `mongosh` (`sh.status()`, `sh.shardCollection`) — обычные инструменты.

## Чанки и балансировщики

**Чанк** — непрерывный диапазон значений ключа шарда (или хешированных значений), который принадлежит одному шарду. Кластер делит чанки, когда они растут. **Балансировщик** перемещает чанки так, чтобы у шардов было похожее количество данных (и в текущих версиях похожая нагрузка по политике, которую настраиваете).

Config servers хранят карту чанков. `mongos` кэширует эту карту и маршрутизирует каждый запрос.

Типичные операции:

```javascript
sh.status()
sh.isBalancerRunning()
sh.startBalancer()
sh.stopBalancer()
```

Не останавливайте балансировщик надолго в продакшене без причины. Чанки растут неровно. Затем догоняющее перемещение велико.

Не запускайте тяжёлые смены схемы, некоторые резервные копии или некоторые обновления без процедуры в руководстве. Процедура может попросить остановить балансировщик на короткое окно.

У размера чанка есть значение по умолчанию (часто 128 MB во многих версиях). Большие документы дают меньше документов на чанк. Маленькие документы дают больше документов на чанк.

Запрос, который включает полный ключ шарда, может целиться в один чанк или один шард. Запрос без ключа шарда может попасть во все шарды.

Перемещение чанка использует ресурсы исходного шарда, целевого шарда и сети. Баланс в пик записи может добавить задержку. Atlas многое ведёт. Вы всё равно смотрите времена перемещения.

## Горячие шарды и jumbo-чанки

**Горячий шард** — шард, который получает гораздо больше трафика или данных, чем остальные. Причины:

- Монотонный диапазонный ключ (все вставки идут в последний чанк)
- Популярное значение ключа шарда (один тенант, одна страна)
- Шаблон запросов, который всегда целится в один префикс

**Jumbo-чанк** — чанк, который слишком велик, чтобы двигаться по правилам балансировщика. Причины:

- Слишком много документов с одним префиксом ключа шарда (чанк нельзя разделить)
- Очень большие документы
- Ключ почти без различных значений

Jumbo-чанки остаются на одном шарде. Балансировщик не может починить этот шард, переместив этот чанк. Нужно сменить ключ, уточнить ключ, разделить если версия позволяет, или перешардировать.

Обнаруживайте горячие шарды метриками: opcounters, CPU, диск и числа чанков, которые не совпадают с трафиком. У Atlas есть метрики шардов. `sh.status()` показывает флаги jumbo в некоторых версиях.

Сначала чините модель, когда один тенант огромен. Шаблон outlier из проектирования схемы может подойти. Шардирование не убирает горячий ключ.

Не игнорируйте предупреждения jumbo. Они растут.

Предотвращение легче починки. Выберите кардинальность и ровную частоту до шардирования.

## Уточнение / перешардирование (современные версии)

Старые версии MongoDB делали ключ шарда почти фиксированным после `shardCollection`. Текущие версии добавляют два важных инструмента.

**Уточнить ключ шарда** (`refineCollectionShardKey`) добавляет одно или несколько суффиксных полей к существующему ключу. Пример: `{ customerId: 1 }` становится `{ customerId: 1, orderId: 1 }`. Нужен поддерживающий индекс. Refine помогает кардинальности, когда старый префикс остаётся. Он не меняет существующее поле префикса.

**Перешардировать коллекцию** (`reshardCollection`) меняет ключ шарда на новый ключ. Кластер копирует данные в новое распределение. Операции нужны лишний диск и время. Читайте текущие лимиты (размер, запас диска, поведение блокировки).

Эти инструменты снижают цену ошибки первого ключа. Они не делают первый ключ дешёвым. Reshard большой коллекции — всё ещё проект.

Доступность возможностей зависит от основной версии и от Atlas. Используйте руководство, которое соответствует вашей версии.

Шаги по духу:

1. Создать нужный индекс для нового ключа.
2. Запустить refine или reshard, как показывает руководство.
3. Смотреть балансировщик и диск.
4. Сменить запросы приложения, чтобы включать новый ключ.

Не делайте refine вместо reshard, когда проблема — сам префикс (например префикс — булево).

Не запускайте reshard без плана диска и отката.

## Обзор темы

Эти вопросы не повторяют вопросы из разделов выше. Они охватывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Как ключ шарда, чанки и `mongos` решают, где живёт одна вставка?
2. Когда хешированные ключи, диапазонные ключи и составные ключи решают разные проблемы горячего шарда?
3. Почему jumbo-чанки и монотонный ключ оба могут сделать балансировщик «сломанным»?
4. Как refine и reshard меняют старое правило «ключ шарда нельзя изменить»?
5. Коллега шардирует по `{ status: 1 }`, потому что каждый запрос фильтрует статус. Какими фактами вы ответите на ревью?

#### Простые практические задания

1. Напишите шпаргалку: когда шардировать, тесты хорошего ключа, hashed vs ranged, чанк, балансировщик, jumbo, refine, reshard.
2. Нарисуйте полный кластер: три шарда, config replica set, два `mongos`, один целевой find, один scatter find.
3. Для одного реального имени коллекции запишите кандидата ключа и один запрос, который разлетится.
4. Откройте документацию `sh.status()`. Запишите два поля, которые прочитаете первыми в инциденте.

#### Средние практические задания

1. Спроектируйте ключи шарда для `users`, `orders` и `auditLog`. Обоснуйте hashed или ranged для каждого.
2. Напишите чек-лист до шардирования из десяти пунктов (метрики, ключ, индексы, окно балансировщика, откат).
3. На бумаге покажите, как горячий тенант плюс jumbo-чанки выглядели бы в `sh.status()` и на графиках CPU.

#### Сложные практические задания

1. Запустите или скриптуйте небольшой шардированный кластер. Шардируйте коллекцию, создайте перекос и запишите метрики. Затем предложите refine или reshard.
2. Напишите производственный стандарт: когда команда может шардировать, кто утверждает ключ, как нагрузочно тестируете и как смотрите jumbo-чанки.

# 20. Распределённые данные

## Описание

Эта тема показывает, как делить данные по узлам и как держать запись безопасной, когда задействовано больше одной службы. Вы изучаете шардирование, согласованное хеширование, почему распределённые транзакции дороги, шаблоны saga и outbox, eventual consistency, идемпотентные записи и проблемы часов.

Используйте один термин для каждого понятия. Шард — подмножество данных на одном узле (или одной паре). Saga — последовательность локальных транзакций с компенсирующими действиями. Завершите эту тему после того, как понимаете репликацию, транзакции и CAP практическими словами. Распределение добавляет режимы сбоя. Оно не убирает потребность в системе учёта.

Этот путь нейтрален к вендорам. Имена шаблонов стандартны. Синтаксис продукта отличается.

## Шардирование / секционирование

Шардирование (горизонтальное секционирование) делит строки набора данных по ключу шарда. Каждый шард держит непересекающееся подмножество ключей. Маршрутизатор или приложение шлёт запрос на шард, который владеет ключом.

```text
shard key = customer_id
customers 1..999    --> shard A
customers 1000..1999 --> shard B
```

Используйте шардирование, когда одна основная не может держать данные или скорость записи. Шардирование — операционная и проектная цена. Не шардируйте маленькую базу.

Хороший ключ шарда:

- появляется почти в каждом запросе
- распределяет запись (нет одного горячего ключа)
- держит связанные строки, которые соединяете, на одном шарде, когда можете

Плохой ключ шарда создаёт горячий шард (все новые заказы идут в «сегодня», если шардируете только по дате) или заставляет соединения между шардами.

Запросы между шардами должны расходиться веером. Они медленнее и труднее изолировать. Транзакции, которые касаются двух шардов, — распределённые транзакции (поздний раздел) или saga приложения.

Вертикальное секционирование (разделить столбцы на больше таблиц или складов) — другая идея. Этот раздел значит разделение строк по ключу.

Диапазонные шарды просты и могут разбалансироваться. Хеш-шарды распределяют лучше и затрудняют сканирования диапазона. Каталог (таблица поиска ключ-шард) гибок и это ещё одна система для запуска.

Перешардирование (перенести ключи на новые узлы) — запланированный проект. Проектируйте больше шардов, чем нужно в первый день, или используйте схему, которая может делиться (согласованное хеширование, следующий раздел).

Не шардируйте «ради высокой доступности». Репликация даёт копии. Шардирование даёт ёмкость. Часто нужны оба.

## Согласованное хеширование (идея)

Согласованное хеширование размещает ключи на кольце. Узлы занимают позиции на кольце. Ключ хешируется в точку. Ключ принадлежит следующему узлу вдоль кольца (или набору реплик на кольце).

Когда добавляете или убираете узел, двигаются только ключи, которые отображаются на изменённую дугу. В простой схеме по модулю (`hash(key) % N`) почти все ключи двигаются, когда N меняется.

```text
Ring:  0 ---- N1 ---- N2 ---- N3 ---- 0
Key k hashes to a point; owner is the next node clockwise
Add N4: only keys in N4's new arc change owner
```

Виртуальные узлы (много позиций на физический узел) распределяют нагрузку. Большая машина получает больше виртуальных узлов.

Клиенты или прокси считают хеш. Они должны использовать одну хеш-функцию и одно членство кольца. Смена членства должна распространиться. Во время смены некоторые ключи могут быть на старом узле и на новом узле. Нужен протокол переноса: копировать, переключить, удалить.

Согласованное хеширование — идея. Продукты добавляют корзины, vnode и диапазоны токенов. Цель одна: дешёвое изменение размера кластера и ровное распределение.

Не считайте хеш секретом. Не ставьте поле низкой кардинальности (булево) как единственный вход хеша. Получаете две кучи, не кольцо многих ключей.

Не предполагайте, что согласованное хеширование даёт транзакции. Оно только отвечает «какой узел владеет этим ключом».

## Распределённые транзакции и почему они дороги

Распределённая транзакция фиксирует изменения на более чем одном узле (или более чем одном продукте) как одну атомарную единицу. Обычный протокол — двухфазная фиксация (`2PC`): координатор просит участников подготовиться, затем просит их зафиксировать.

```text
1. Coordinator: PREPARE on A and B
2. A and B: flush enough state to commit or abort later; answer yes/no
3. Coordinator: COMMIT or ABORT on A and B
```

Цены:

- лишние круговые пути
- блокировки или подготовленное состояние держатся, пока координатор не закончит
- период блокировки, если координатор падает после prepare
- все участники должны реализовать протокол
- задержка — самый медленный участник плюс сеть

Если A фиксирует, а B прерывает без протокола, у вас частичная запись. Бизнес-данные неверны.

Многие команды избегают `2PC` между продуктами. Они используют одну локальную транзакцию в одной системе учёта, затем распространяют (saga, outbox).

Некоторые продукты предлагают распределённые транзакции внутри одного кластера. Они всё ещё стоят больше, чем транзакция одного шарда. Предпочитайте ключ шарда, который держит одно бизнес-событие на одном шарде.

Не начинайте `2PC` для строки журнала и инвалидации кэша. Используйте локальную транзакцию плюс повторяемый побочный эффект.

Не держите пользовательские подключения открытыми, пока координатор ждёт медленный второй склад.

## Шаблоны saga и outbox

Saga — последовательность локальных транзакций. У каждого шага есть компенсирующее действие, которое отменяет бизнес-эффект, если поздний шаг падает.

```text
1. Reserve inventory   (compensate: release)
2. Charge payment      (compensate: refund)
3. Create shipment     (compensate: cancel shipment)
```

Saga не изоляция `ACID` между шагами. Другие читатели могут видеть зарезервированный товар до завершения списания. Вы проектируете поля статуса (`reserved`, `paid`, `failed`).

Saga **оркестрации** имеет процесс-координатор, который вызывает каждый шаг. Saga **хореографии** даёт каждой службе реагировать на события. Оркестрацию легче видеть. Хореография избегает одного начальника и труднее отлаживать.

Шаблон **outbox** пишет бизнес-строку и строку «событие для отправки» в одной локальной транзакции. Издатель читает outbox и шлёт событие в шину или на другой склад. Затем помечает строку outbox как отправленную.

```text
BEGIN
  UPDATE orders SET status = 'paid'
  INSERT INTO outbox (event) VALUES ('OrderPaid')
COMMIT
-- publisher sends OrderPaid; at-least-once
```

Без outbox можете зафиксировать заказ и упасть до отправки события. Другая служба никогда не услышит. Двойная запись без транзакции — обычная ошибка.

Компенсации должны быть безопасны для повтора. Возврат, который выполняется дважды, — денежная ошибка, если возврат не идемпотентен (следующие разделы).

Не используйте saga, чтобы скрыть отсутствующее локальное ограничение. Не используйте outbox как журнал чата для людей. Это механизм доставки.

## Eventual consistency

Eventual consistency значит, что копии могут отличаться какое-то время. Если записи останавливаются, копии сходятся к одним значениям (по правилам продукта). Читатели могут видеть устаревшие данные во время задержки.

```text
Write on node A at t=0
Read on node B at t=50ms  -->  old value
Read on node B at t=2s    -->  new value (if replication caught up)
```

Эта модель появляется в:

- асинхронных репликах
- поисковых индексах после записи
- кэшах с TTL
- шагах saga, которые не закончились
- DNS и многих складах объектов

Используйте eventual consistency, когда бизнес может принять короткое устаревшее чтение. Пример: счётчик просмотров, результат поиска, рекомендация. Не используйте её как единственную историю для банковского баланса, если нет точного правила конфликта и журнала учёта.

Дайте пользователям истину, которую они могут понять: «Ваше изменение сохранено. Поиск может занять минуту». Молчаливое устаревшее чтение выглядит как потерянная запись.

**Читай свои записи** — более сильная потребность. После сохранения читайте основную или ждите версии. **Монотонные чтения** значат, что вы не идёте назад во времени в одной сессии.

Не говорите «eventual consistency», чтобы значить «мы не знаем». Пишите бюджет задержки и ремонт, если сходимость падает (застрявшая реплика).

Причинные истории важны: если комментарий B отвечает на комментарий A, читатель не должен видеть B без A. Это требование больше, чем «в конце концов оба существуют».

## Идемпотентные записи

Идемпотентная запись может выполниться больше одного раза и оставить то же конечное состояние, что один успешный запуск. Сети повторяют. Saga повторяют. Потребители outbox повторяют. Без идемпотентности повтор списывает карту дважды.

```text
POST /payments { idempotency_key: "ord-1001-pay" }
-- first call: charges
-- retry: returns the same payment id, no second charge
```

Методы:

1. Клиентский ключ идемпотентности, хранимый с результатом.
2. Натуральный уникальный ключ (`order_id` уникален на `payments`).
3. Конечный автомат: `pending` в `paid` только один раз.
4. Upsert с номером версии.

Доставка at-least-once (outbox, шина сообщений) требует идемпотентных потребителей. Доставка at-most-once теряет сообщения. Exactly-once — сочетание at-least-once плюс идемпотентность (и осторожные побочные эффекты).

`UPDATE balances SET n = n + 10` не идемпотентен. Два повтора добавляют 20. `UPDATE balances SET n = 90 WHERE account = 1 AND version = 3` может быть идемпотентен, если проверка версии падает на втором применении.

Не полагайтесь на «пользователь не нажмёт дважды». Повтор по тайм-ауту достаточен, чтобы применить дважды.

Журналируйте ключ. Отвергайте второе другое тело для того же ключа (конфликт).

## Проблемы часов и порядка

У каждой машины есть часы. Часы расходятся. NTP сдвигает часы. Виртуальная машина может приостановиться. Нельзя доверять `NOW()` на двух хостах как глобальному порядку.

```text
Host A thinks t=10:00:00.200  writes row
Host B thinks t=10:00:00.050  writes row
-- B's timestamp is earlier; B did not happen first
```

Проблемы:

- last-write-wins со стенными часами теряет более позднюю настоящую запись
- уникальный порядок `created_at` неверен между узлами
- TTL, посчитанный от будущих часов, истекает сразу
- сертификат или токен выглядит истёкшим, потому что часы прыгнули

Лучшие инструменты для порядка:

- последовательность или позиция журнала на одной основной
- логические часы или вектор версий для параллельных обновлений
- причинный id (id родительского события) в полезной нагрузке
- гибридные логические часы в некоторых продуктах (всё ещё не магия)

Не сортируйте глобальные события только по `timestamptz` от многих писателей. Используйте один секвенсор, если нужен полный порядок.

Не измеряйте отставание как `replica_now - primary_now` без осторожности. Предпочитайте разницу последовательности журнала.

В тестах подделывайте время. В продакшене оповещайте о расхождении часов между узлами.

Для людей показывайте локальное время. Для порядка храните UTC плюс монотонный источник, когда продукт его даёт.

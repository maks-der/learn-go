# 12. Модули и промышленное использование

## Описание

Модуль добавляет команды и типы, которые базовый Redis не поставляет. Промышленный Redis — набор политик, а не только работающий процесс. Эта тема обзорно разбирает RedisJSON, RediSearch, TimeSeries и Bloom, затем покрывает отдельные экземпляры кэша и долговечные экземпляры, бюджеты ключей, префиксы арендаторов, разрыв цепи и форки вроде Valkey.

Сначала завершите тему 5 (обзор модулей), тему 7 (персистентность), тему 9 (клиенты и шаблоны кэша) и тему 11 (безопасность).

Используйте один термин для каждого понятия. Модуль — плагин сервера, который регистрирует команды. Redis Stack — Redis плюс пакет модулей. Кэш-Redis — экземпляр, который можно потерять. Долговечный Redis — экземпляр, который является источником истины или хранилищем, которое нужно восстановить. Бюджет ключей — лимит на число или байты. Префикс арендатора — строка в начале ключа. Размыкатель цепи останавливает вызовы к Redis после ошибок. Альтернативная реализация — другой сервер, который говорит протоколами или командами Redis.

## RedisJSON, RediSearch, TimeSeries, Bloom

RedisJSON хранит документы JSON как полноценное значение. Вы адресуете пути. Не переписываете весь документ ради маленького изменения.

```text
JSON.SET lab:user:1 $ '{"name":"Ada","n":1}'
JSON.GET lab:user:1 $.name
JSON.NUMINCRBY lab:user:1 $.n 1
```

`$` — корень документа в JSONPath. Синтаксис путей на страницах команд RedisJSON. Проверьте версию модуля.

Почему не `SET` строки JSON? Строковый `SET` заменяет весь блоб. Конкурентные обновления двух полей нуждаются в блокировке или Lua read-modify-write. RedisJSON может обновить один путь.

`TYPE` на ключе JSON — не `string`. Команды вроде `GET` не применяются. Клиентам нужна поддержка RedisJSON или сырые вызовы команд.

Используйте RedisJSON, когда документы вложенные, обновления частичные и вы уже запускаете Redis Stack или хостинговую возможность JSON. Используйте хеш, когда модель — плоская карта маленьких полей.

RediSearch (Search) строит индекс на хешах или JSON. Вы запрашиваете индекс через `FT.SEARCH`. Это не SQL. Нужно создать схему.

```text
FT.CREATE idx:lab ON HASH PREFIX 1 lab:doc: SCHEMA title TEXT body TEXT score NUMERIC
FT.SEARCH idx:lab "hello"
```

`FT.CREATE` определяет поля и типы (`TEXT`, `TAG`, `NUMERIC`, `GEO` и другие по версии). Документы — обычные ключи Redis, которые совпадают с префиксом. Модуль поддерживает инвертированные индексы.

Поиск использует ОЗУ для индекса. Большие текстовые корпуса стоят памяти сверх документов. Агрегации (`FT.AGGREGATE`) есть. Они не хранилище данных.

Используйте Search, когда нужны полнотекстовые или фильтрующие запросы, которые хеши и `SCAN` не могут. Не используйте Search как замену PostgreSQL, когда нужны соединения, ограничения и произвольный SQL.

RedisTimeSeries хранит выборки с метками времени. Каждый ключ — один ряд.

```text
TS.CREATE lab:cpu
TS.ADD lab:cpu * 0.42
TS.RANGE lab:cpu - +
```

`TS.CREATERULE` даунсэмплит в другой ряд (avg, min, max и другие). Удержание (`RETENTION`) удаляет старые выборки.

Почему не упорядоченное множество? Упорядоченное множество может хранить `score=timestamp` и `member=value`. При большом объёме TimeSeries компактнее и имеет правила агрегации. Окна темы 4 хороши для маленьких случаев.

Метки позволяют запрашивать много рядов (`TS.MRANGE`). Метки высокой кардинальности (один ряд на id пользователя в огромном масштабе) взрывают память.

Используйте TimeSeries для инфраструктурных или продуктовых метрик, которые уже хотите в Redis. Используйте выделенную систему метрик, когда удержание и объём запросов превышают хранилище в памяти.

RedisBloom добавляет вероятностные структуры: фильтры Блума, фильтры Кукушки, эскизы Count-Min, Top-K и связанные типы.

Фильтр Блума отвечает «точно не в множестве» или «возможно в множестве». Он не хранит элементы. Ложные срабатывания есть. Ложных отрицаний нет (в стандартном фильтре Блума).

```text
BF.RESERVE lab:bf 0.01 10000
BF.ADD lab:bf user:42
BF.EXISTS lab:bf user:42
```

`0.01` — целевая частота ошибок. `10000` — подсказка ёмкости. После слишком многих вставок частота ошибок растёт, если не зарезервировали достаточно ёмкости.

HyperLogLog (тема 5) оценивает уникальные счёты. Фильтр Блума проверяет членство. Не смешивайте два.

Не используйте фильтр Блума как список контроля доступа. Ложное срабатывание может значить «возможно разрешено». Это неверный инструмент для безопасности.

Стройте сами (базовые типы + приложение), когда хеш, поток или упорядоченное множество уже совпадают с шаблоном доступа, или когда нужно запускать обычный Redis. Используйте модуль, когда модуль хорошо реализует известный алгоритм и ваша платформа уже его поставляет.

Команда модуля всё равно выполняется в основном потоке, если документация модуля не говорит иное. Огромный `FT.SEARCH` может застопорить.

Лицензирование и привязка к вендору — часть выбора. Читайте текущую лицензию до поставки. Не загружайте неподдерживаемый модуль на промышленный основной.

Модуль меняет историю эксплуатации. Версия Redis, версия модуля, тег образа Redis Stack и клиентская библиотека должны совпадать. Реплика без модуля не может загрузить данные. Проверьте `BGSAVE`, перезапуск и синхронизацию реплики с ключами модуля. Закрепите дайджест образа в продакшене. Не запускайте `latest` без закрепления.

`MODULE LOAD` — опасная команда (тема 11). Загружайте только подписанные или поддерживаемые вендором модули.

Используйте Redis Stack в Docker для обучения:

```text
docker run --name stack-learn -p 6379:6379 redis/redis-stack
```

## Отделить кэш-Redis от долговечного Redis

Один экземпляр, который и огромный кэш, и единственная копия заданий или сессий, создаёт конфликт.

Кэш хочет:

- Вытеснение (`allkeys-lru` или похожее)
- Короткие TTL
- Необязательную персистентность или никакую
- Терпимость к сбросу и перезапуску

Долговечное хранилище хочет:

- `noeviction` или осторожные только `volatile-*`
- Проверенную персистентность (тема 7)
- Репликацию и резервную копию (тема 8, тема 11)
- Нет `FLUSHALL` как шага выката

Если оба живут в одном процессе, штампед кэша или политика `maxmemory` могут вытеснить долговечные ключи. `FLUSHALL` стирает оба. Застой `KEYS` бьёт оба.

Шаблон: два экземпляра (или две вендорские базы). Разные хосты, разный `maxmemory`, разные ACL, разные резервные копии. Приложение использует двух клиентов.

Поток, который нельзя сбросить (тема 10), принадлежит долговечному экземпляру или Kafka. Кэш страницы продукта принадлежит экземпляру кэша.

Цена: два пула, два дашборда, два обновления. Эта цена ниже одного смешанного инцидента.

Не используйте логический `SELECT`, чтобы делить кэш и долговечные данные (тема 1, тема 8 Cluster).

Назовите экземпляры в конфигурации: `REDIS_CACHE_URL` и `REDIS_DURABLE_URL`. Не используйте один URL для обеих ролей.

Прогрев заполняет ключи кэша до того, как они горячие. Задача читает источник истины и делает `SET` ключей кэша с TTL и джиттером. Темпируйте задачу. Предпочитайте версионированные ключи (`cache:p:1001:v2`) и прогревайте `v2` до переключения. Не делайте `FLUSHALL`, чтобы «обновить кэш».

## Бюджеты ключей и префиксы нескольких арендаторов

Бюджет ключей — записанный лимит: максимум ключей на префикс, максимум байт на ключ, TTL по умолчанию, джиттер и владелец.

Без политики каждая возможность добавляет ключи навсегда. Redis растёт до вытеснения или OOM.

Строки политики выглядят так:

```text
prefix     role      ttl     jitter   max bytes   owner
cache:p:   cache     300s    0-60s    16KB        shop
sess:      session   1800s   0        4KB         iam
neg:       negative  30s     0-5s     16B         shop
```

Бюджеты используют тему 9 (TTL, джиттер, негативное) и тему 11 (большие ключи). Эксплуатация тревожит, когда `INFO keyspace` или оценка `SCAN` превышает бюджет.

`maxmemory` — жёсткий стоп. Политика — социальный стоп. Сначала бьёте политику.

Долговечным ключам всё равно нужен бюджет. Утечка ключей блокировок без TTL заполняет экземпляр `noeviction`, пока записи не упадут.

Каждому новому префиксу нужен разбор: TTL да/нет, кто удаляет, что происходит при выкате. Не изобретайте префикс в pull request без строки каталога.

Мерите: выборки `MEMORY USAGE`, `--bigkeys` на реплике, число ключей на префикс из темпового `SCAN` в задаче, не `KEYS`.

Несколько арендаторов (клиенты, магазины, коллективы) могут делить один Redis. Вы префиксируете ключи:

```text
t:acme:cache:product:1
t:globex:cache:product:1
```

Префикс избегает столкновений. Арендаторы всё равно делят ОЗУ, CPU основного потока, `connected_clients`, `FLUSHALL` если кто-то может его запустить, сеть и диск.

Префикс — не граница безопасности (тема 1, тема 11). Клиент, который может `GET t:acme:*`, всё ещё может `GET t:globex:...`, если ACL не ограничивают шаблоны ключей.

ACL могут ограничить пользователя арендатора `~t:acme:*`. Это настоящий контроль. Пользователь приложения, который обслуживает всех арендаторов, не должен иметь эту изоляцию, если не используете пользователей Redis на арендатора (редко) или экземпляры на арендатора (сильнее).

Шумный сосед: один арендатор может заполнить память или запустить большой `HGETALL`. Бюджеты на префикс арендатора, лимиты частоты (тема 10) и отдельные экземпляры для крупных арендаторов чинят это.

Хеш-теги Cluster: `{t:acme}` может привязать одного арендатора к диапазону слотов, если так спроектируете. Это также может сделать один слот горячей точкой. Предпочитайте теги для ключей, которые должны жить вместе, не для всех ключей арендатора, если не измерили.

Не кладите id арендатора только в значение и не используйте один ключ для всех арендаторов.

## Разрыв цепи, когда кэш лежит

Если Redis — кэш, отказ Redis не должен уронить продукт. Приложение читает источник истины и пропускает кэш.

Размыкатель цепи:

- Считает ошибки или таймауты к Redis
- Открывается после порога
- Быстро отказывает (не ждёт долгий таймаут на каждый запрос)
- Полуоткрывается, чтобы попробовать зонд (`PING` или один `GET`)
- Закрывается, когда Redis здоров

Таймауты темы 9 важны. Таймаут 5 секунд без размыкателя может исчерпать пул потоков приложения.

Если Redis долговечный (сессии, которые нельзя восстановить, поток заданий), размыкатель не изобретает данные. Приложение возвращает ошибку или деградированный режим, который вы спроектировали. Это другое продуктовое решение. Не притворяйтесь, что долговечное хранилище необязательно.

Cache-aside (тема 9) подходит размыкателю: считайте ошибки Redis промахами.

Журналы: когда размыкатель открывается, пишите журнал раз в интервал, не раз на запрос.

Метрики: состояние размыкателя, частота ошибок Redis, нагрузка SQL (SQL вырастет, когда кэш отсутствует).

Не повторяйте вечно внутри окна размыкателя (тема 9).

Проверьте: остановите Redis в лаборатории и подтвердите, что HTTP API всё ещё обслуживает маршруты, необязательные для кэша.

Двойная запись держит два хранилища в синхроне во время миграции или заполнения кэша. Приложение пишет SQL и Redis в одном запросе или пишет два кластера Redis. Если Redis падает, решите, падает ли запрос (долговечный) или продолжается (кэш). Двойная запись может разойтись. Нужна задача ремонта и TTL, чтобы расхождение умирало.

Холодный старт: пустой кэш после перезапуска вызывает штампед (тема 9). Прогрейте топ-N ключей, или используйте single-flight, или примите нагрузку SQL.

## Valkey и другие форки (осведомлённость)

Протокол и набор команд Redis вдохновили другие серверы.

Valkey — проект Linux Foundation, который форкнулся от Redis после смены лицензии проекта Redis. Многие команды остаются знакомыми. Это альтернатива, которую можно увидеть у вендоров и в дистрибутивах. Читайте документацию Valkey про Cluster, модули и лицензию. Не предполагайте, что каждый модуль Redis загрузится.

KeyDB — форк, который подчёркивает многопоточное выполнение команд. Модель конкурентности — не модель основного потока Redis. Предположения о гонках, верные на Redis (`INCR` атомарный в одном потоке), нуждаются в осторожном чтении документации KeyDB. Поведение модулей и Cluster может отличаться.

Существуют другие прокси и совместимые кэши (вендорские кэши, образы `redis-stack`, облачные движки). Совместимость — спектр: обычные `GET`/`SET` работают; `MODULE`, `FUNCTION` и точные поля `INFO` могут не работать.

Правила осведомлённости:

- Называйте сервер в runbook («Valkey 8», не «Redis», если это Valkey)
- Проверяйте клиент против этого сервера
- Читайте лицензию для вашего использования
- Не смешивайте реплики разных движков, если вендор это не поддерживает

Этот справочник остаётся путём обучения Redis. Команды здесь целят Redis. Когда используете альтернативу, проверяйте каждую команду на том движке.

Не считайте форк Redis для соответствия или договоров поддержки без проверки.

Официальная документация остаётся [https://redis.io/docs/](https://redis.io/docs/). Redis University — [https://university.redis.io/](https://university.redis.io/). Предлагаемый список практики в `redis.topics.md` — второй чеклист.

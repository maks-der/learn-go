# 9. Валидация и типы

## Описание

Эта тема показывает, как валидировать документы в MongoDB. Вы прикрепляете JSON Schema к коллекции. Задаёте `validationLevel` и `validationAction`. Сравниваете валидацию приложения с валидацией базы. Держите имена полей и типы стабильными. Сначала завершите документы, CRUD и моделирование.

Используйте один термин для каждого понятия. **Валидатор** — правило на коллекции. **JSON Schema** — обычный язык валидатора. **validationLevel** выбирает, какие документы проверяет сервер. **validationAction** выбирает ошибку или предупреждение. Приложение по-прежнему валидирует ввод пользователя.

## Валидация JSON Schema на коллекциях

Коллекцию можно создать или изменить через collMod с валидатором:

```javascript
db.createCollection("users", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["email", "createdAt"],
      properties: {
        email: { bsonType: "string", pattern: "^.+@.+$" },
        createdAt: { bsonType: "date" },
        age: { bsonType: "int", minimum: 0 }
      },
      additionalProperties: true
    }
  }
})
```

`$jsonSchema` описывает типы BSON через `bsonType`. Используйте `string`, `int`, `long`, `double`, `decimal`, `bool`, `date`, `objectId`, `array`, `object`, `null`, `binData`.

`required` перечисляет поля, которые должны существовать. `properties` описывает именованные поля. `additionalProperties: false` отклоняет неизвестные поля. Эта настройка строгая. Используйте её, когда схема стабильна.

Можно использовать `oneOf` для версий или вариантов. Массивы описывают через `items`.

Существующие коллекции: `db.runCommand({ collMod: "users", validator: { $jsonSchema: { ... } } })`.

Слишком строгий валидатор заблокирует записи. Тестируйте на копии. Вставляйте допустимые и недопустимые документы.

Схема — не полная модель приложения. Она не заменяет уникальные индексы. Она не заменяет авторизацию.

## `validationLevel` / `validationAction`

**validationLevel** управляет, какие документы сервер валидирует.

- `strict` — валидировать все вставки и все обновления. Это значение по умолчанию.
- `moderate` — валидировать вставки и валидировать обновления только если существующий документ уже совпадает со схемой. Документы, которые были недопустимы до валидатора, всё ещё можно обновлять, если в некоторых случаях они остаются недопустимыми. Читайте текущее руководство для точного правила moderate.

Используйте `strict` для новых коллекций. Используйте `moderate`, когда добавляете валидатор к коллекции со старыми недопустимыми документами и их всё ещё нужно обновлять.

**validationAction** управляет, что сервер делает при неудачной проверке.

- `error` — отклонить запись. Это значение по умолчанию.
- `warn` — принять запись и записать предупреждение.

Используйте `warn`, когда вводите схему и хотите найти нарушения без блокировки производственных записей. Смотрите логи. Исправьте приложение. Затем поставьте `error`.

```javascript
db.runCommand({
  collMod: "users",
  validator: { $jsonSchema: { /* ... */ } },
  validationLevel: "moderate",
  validationAction: "warn"
})
```

Не оставляйте `warn` навсегда. Недопустимые данные будут расти.

`strict` плюс `error` — обычное конечное состояние стабильной коллекции.

## Валидация приложения и валидация базы

**Валидация приложения** работает в клиенте или API. Примеры: библиотека JSON Schema, декодер типов, Mongoose, Bean Validation. Она проверяет ввод до записи. Она возвращает ясную ошибку пользователю.

**Валидация базы** работает в `mongod`. Она проверяет каждого писателя: API, скрипт, `mongosh`, миграцию. Это последний страж.

Используйте оба.

Приложение:

- Валидирует правила, обращённые к пользователю (сила пароля, подтверждение email)
- Даёт ошибки на уровне полей
- Может использовать более богатые типы, чем схема коллекции

База:

- Блокирует плохие записи из инструментов и забытых скриптов
- Обеспечивает тип и обязательные поля
- Не зависит от одного языка

Не опирайтесь только на приложение. Будущая задача напишет без этого кода.

Не опирайтесь только на базу. Пользователь увидит ошибку драйвера, а не ошибку формы. Схема не выражает каждое бизнес-правило.

Держите две схемы близко. Если `age` — `int` в MongoDB, API не должен отправлять float, который станет другим типом BSON.

Драйверы могут отправлять типы, которые проходят приложение, но падают на `bsonType`. Тестируйте настоящий BSON, а не только JSON.

## Стабильные имена полей и типы

Стабильные имена и типы держат запросы, индексы и валидаторы рабочими.

Правила:

- Выберите имя поля и держите его. Не смешивайте `user_id`, `userId` и `userID`.
- Выберите тип BSON и держите его. Не храните `qty` и как int, и как строку.
- Используйте один тип даты. Предпочитайте BSON Date, а не строку даты, если сортируете и индексируете по времени.
- Для денег используйте `Decimal128`. Не смешивайте decimal и double.
- Используйте один тип id для ссылки. Не смешивайте ObjectId и строку для одной цели.

Если нужно сменить имя или тип, используйте expand-contract и `schemaVersion`. Во время изменения запрашивайте обе формы. Дозаполните. Затем уберите старую форму.

Индексы не чинят смешанные типы. Запрос `{ qty: { $gt: 10 } }` пропускает `"11"`.

Валидация помогает после того, как вы её задали. Старые смешанные данные остаются, пока не почистите.

Стиль имён: команды часто используют camelCase в документах. Это соглашение. Согласованность важнее стиля.

Не используйте имя поля заново для нового смысла. Используйте новое имя или новую версию.

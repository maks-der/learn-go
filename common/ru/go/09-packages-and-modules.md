# 9. Пакеты и модули

## Описание

Модуль (`module`) — это набор пакетов Go с файлом `go.mod`. Пакет (`package`) — это один каталог файлов Go, которые используют одно и то же имя `package`. Эта тема показывает, как создать модуль, как добавить и привести в порядок зависимости и как версионировать модуль при ломающем изменении. Тема также показывает внутренние пакеты, небольшие API пакетов, теги сборки и встраивание файлов.

Сначала завершите тему 1. Тема 1 вводит `go.mod` и режим модулей. Эта тема даёт команды и правила проектирования. Используйте один термин для каждой идеи. Используйте *модуль* для версионируемой единицы. Используйте *пакет* для одного импортируемого каталога. Не смешивайте режим GOPATH с режимом модулей.

## Создание модуля через `go mod init`

Запустите `go mod init` в пустом корне проекта. Передайте путь модуля. Путь модуля — это префикс импорта для каждого пакета в модуле:

```text
go mod init example.com/app
```

Команда записывает `go.mod`. Новый файл выглядит так:

```text
module example.com/app

go 1.22.0
```

Строка `module` — это путь. Другие модули импортируют ваши пакеты с этим префиксом. Пример: пакет `internal/store` имеет путь импорта `example.com/app/internal/store`. Строка `go` — это версия языка, которую ожидает модуль.

Выберите путь модуля, который вы контролируете. Для публичного кода используйте URL репозитория без схемы: `github.com/user/app`. Для частных экспериментов достаточно домена, которым вы владеете: `example.com/learn/mod`. Не используйте случайное короткое имя вроде `app`, когда другие модули должны импортировать код.

`go mod init` не создаёт исходные файлы Go. Добавьте пакеты после команды. Поместите `go.mod` в корень. Не помещайте второй `go.mod` в подкаталог, если вы не намерены создать отдельный модуль.

Начиная с Go 1.21 набор инструментов может добавить строку `toolchain`. Эта строка выбирает версию набора инструментов Go. Версию языка можно задать позже:

```text
go mod edit -go=1.22.0
```

Запустите `go list -m`, чтобы напечатать путь модуля. Запустите `go env GOMOD`, чтобы напечатать путь активного файла `go.mod`.

## `go get`, `go mod tidy`, `go mod vendor`

`go get` добавляет или обновляет модуль в `go.mod`. Передайте путь модуля и версию:

```text
go get example.com/pkg@v1.2.3
go get example.com/pkg@latest
```

Используйте `@none`, чтобы удалить требование:

```text
go get example.com/pkg@none
```

Начиная с Go 1.16 `go get` меняет файл модуля. `go get` не устанавливает двоичный файл команды. Устанавливайте команду через `go install example.com/cmd/tool@version`.

`go get ./...` смотрит на импорты в текущем модуле и обновляет `go.mod` так, чтобы он им соответствовал. Для повседневной очистки предпочитайте `go mod tidy`.

`go mod tidy` добавляет недостающие модули, которые импортирует исходный код. `go mod tidy` удаляет модули, которые исходный код не импортирует. `go mod tidy` обновляет `go.sum`. Запускайте `go mod tidy` после добавления или удаления импортов.

`go.sum` хранит криптографические контрольные суммы. Команда `go` использует `go.sum`, чтобы обнаружить изменённый zip-архив модуля. Не редактируйте `go.sum` вручную. Восстанавливайте его через `go mod tidy`, когда он неверен.

`go mod vendor` копирует требуемые модули в `vendor/` в корне модуля. Файл `vendor/modules.txt` перечисляет скопированные модули. Собирайте в режиме vendor, когда нужна сборка без прокси модулей:

```text
go mod vendor
go build -mod=vendor ./...
```

Используйте `vendor/`, когда команде нужны офлайн-сборки или фиксированная копия исходного кода в репозитории. Не используйте `vendor/` как замену `go.mod`. Держите `go.mod` и `go.sum` в каждом модуле.

Команда `go` также записывает косвенные модули в `go.mod`. Косвенный модуль — это зависимость зависимости. Комментарий `// indirect` помечает эти строки. Не удаляйте эти строки вручную. Запускайте `go mod tidy`.

## Семантическое версионирование импорта (`/v2`)

Модули Go используют семантические версии: `vMAJOR.MINOR.PATCH`. Мажорная версия `v2` или выше — это другой модуль, чем `v1`. Путь импорта должен включать суффикс мажорной версии:

```text
module example.com/note/v2
```

Импортирующие пишут:

```go
import "example.com/note/v2"
```

Мажорные версии `v0` и `v1` суффикса не имеют. Эти пути модуля допустимы:

- `example.com/note` для `v0.x` и `v1.x`
- `example.com/note/v2` для `v2.x`
- `example.com/note/v3` для `v3.x`

Правило держит один путь импорта сопоставленным с одним мажорным API. Программа может импортировать `example.com/note` и `example.com/note/v2` в одной сборке, когда оба нужны во время миграции.

Ломающее изменение в помеченном модуле `v1` или выше требует новой мажорной версии. Ломающее изменение — это изменение, которое может сломать существующий импорт на этапе компиляции или несовместимо меняет задокументированное поведение. Добавление новой экспортированной функции не является ломающим изменением. Удаление экспортированной функции является ломающим изменением.

Не помещайте код `v2` в путь модуля `example.com/note` без суффикса `/v2`. Команда `go` отклоняет такую раскладку для модулей с файлом `go.mod`.

Версии `v0.x` не дают обещания совместимости. Импортирующие должны считать `v0` нестабильной.

В некоторых старых репозиториях есть теги вроде `v2.0.0` и нет `go.mod` того времени. Такие модули могут появляться с суффиксом `+incompatible`. Новые модули не должны опираться на этот шаблон. Добавляйте корректный `go.mod` с `/v2` для новых мажорных версий.

## Внутренние пакеты (`internal/`)

Каталог с именем `internal` ограничивает, кто может импортировать пакеты под ним. Импортировать эти пакеты могут только родитель `internal` и дерево под этим родителем.

Пример раскладки:

```text
example.com/app/go.mod
example.com/app/cmd/tool/main.go
example.com/app/internal/store/store.go
example.com/app/pkg/api/api.go
```

Пакет `example.com/app/cmd/tool` может импортировать `example.com/app/internal/store`. Пакет `example.com/app/pkg/api` может его импортировать. Другой модуль не может импортировать `example.com/app/internal/store`. Соседний путь модуля вроде `example.com/other` не может его импортировать.

Последний элемент `internal` в пути — это забор. В `example.com/app/internal/store/sql` пакет `sql` всё ещё внутренний для `example.com/app`.

Используйте `internal/` для кода, который не входит в публичный API. Помещайте туда общую реализацию. Помещайте небольшую публичную поверхность в пакет, который не находится под `internal/`.

Не используйте `internal/` как единственный инструмент проектирования. Ясный публичный пакет всё равно важен. `internal/` только блокирует импорты извне родительского дерева.

Команда `go` применяет правило на этапе компиляции. Ошибка упоминает `internal`.

## Проектирование пакетов: небольшие API, мало зависимостей

Пакет — это единица API и единица компиляции. Держите экспортированные имена немногочисленными. Экспортируйте тип или функцию только тогда, когда импортеру вне пакета это нужно. Скрывайте остальное именем в нижнем регистре или через `internal/`.

Дайте пакету одну задачу. Пакет `fmt` форматирует текст. Пакет `errors` обрабатывает ошибки. Не создавайте пакет с именем `util`, который смешивает файлы, HTTP и случайные помощники. Разделите этот код.

Держите список зависимостей коротким. Каждая строка `require` в `go.mod` — это контракт, который нужно обновлять и которому нужно доверять. Предпочитайте стандартную библиотеку, когда она решает задачу. Добавляйте модуль, когда стандартной библиотеки недостаточно и дополнительный модуль стабилен.

Избегайте циклов импорта. Пакет A не должен импортировать B, если B импортирует A. Циклы — это ошибки компиляции. Исправьте цикл меньшим третьим пакетом или интерфейсом, который разрывает цикл.

Принимайте интерфейсы и возвращайте конкретные типы, когда это правило подходит (тема 7). Не экспортируйте большой интерфейс, который реализует только один тип, если он не нужен для тестов.

Документируйте каждое экспортированное имя. Первое предложение — это краткое описание. Запустите `go doc` для своего пакета и прочитайте его как новый пользователь.

Называйте пакет по тому, что он предоставляет, а не по тому, что он содержит. Предпочитайте `package store`, а не `package storehelpers`. Путь импорта уже содержит префикс модуля.

## Теги сборки и суффиксы файлов (`_windows.go`, `//go:build`)

Команда `go` включает файл только тогда, когда файл соответствует текущему контексту сборки. Контекст включает `GOOS`, `GOARCH` и пользовательские теги.

Суффикс файла задаёт `GOOS` или `GOARCH` без комментария:

- `foo_windows.go` собирается только на Windows
- `foo_linux.go` собирается только на Linux
- `foo_amd64.go` собирается только на `amd64`
- `foo_windows_amd64.go` собирается только на Windows `amd64`

Не используйте суффикс, который не является известным `GOOS` или `GOARCH`. Суффикс `_test.go` помечает тестовый файл. Этот суффикс не является именем GOOS.

Ограничение сборки — это комментарий в начале файла. Используйте форму `//go:build`. Поставьте пустую строку после ограничения. Затем напишите строку `package`:

```go
//go:build windows

package pathx
```

Выражение может использовать `&&`, `||` и `!`:

```go
//go:build linux && amd64
```

```go
//go:build !windows
```

Старая форма `// +build` всё ещё работает. Новые файлы должны использовать `//go:build`. Команда `go` может записать обе формы, когда вы запускаете `gofmt` для файла, в котором есть только одна форма.

Передайте пользовательский тег через `-tags`:

```text
go test -tags=integration ./...
```

```go
//go:build integration

package store_test
```

Используйте теги для необязательных интеграционных тестов или для необязательных возможностей. Не используйте теги, чтобы скрыть сломанные файлы. Исправьте файлы.

`cgo` и `race` — особые теги. Вы не задаёте их как суффиксы файлов.

Два файла в одном пакете не должны объявлять одну и ту же функцию для одного и того же контекста сборки. Поместите общую сигнатуру в файл без тега. Поместите тело для операционной системы в `foo_windows.go` и `foo_unix.go`.

## Встраивание файлов через `embed`

Пакет `embed` включает файлы в двоичный файл на этапе компиляции. Компилятор читает файлы из каталога пакета. Вы не открываете эти файлы с диска во время выполнения.

Импортируйте пакет. Пустого импорта достаточно, когда вы встраиваете в `string` или `[]byte`:

```go
import _ "embed"
```

Импортируйте `"embed"`, когда используете `embed.FS`.

Поместите комментарий `//go:embed` на строку над переменной:

```go
//go:embed version.txt
var version string
```

```go
//go:embed logo.png
var logo []byte
```

```go
//go:embed static/*
var static embed.FS
```

Переменная должна иметь тип `string`, `[]byte` или `embed.FS`. Шаблон относителен к каталогу файла Go. Шаблон не должен содержать `..` и не должен начинаться с `/`.

Компилятор пропускает файлы, имена которых начинаются с `.` или `_`, если вы не используете префикс `all:` (Go 1.18 и новее):

```go
//go:embed all:templates
var templates embed.FS
```

Встраивание уместно для HTML-шаблонов, SQL-файлов и небольших статических ресурсов. Данные живут в двоичном файле. Большой ресурс увеличивает размер двоичного файла.

Файл должен существовать на этапе компиляции. Отсутствующий файл — это ошибка компиляции. Используйте `embed` для файлов, которые поставляются вместе с программой. Используйте `os.ReadFile` для файлов, которые предоставляет пользователь.

Нельзя встроить файл, который лежит вне каталога пакета. Переместите файл или поместите встраивание в пакет, которому принадлежит файл.

# 20. Продвинутый язык и среда выполнения

## Описание

Эта тема покрывает инструменты, которые лежат под обычным кодом приложения. Рефлексия, генерация кода, Cgo, ассемблер и модель планировщика сильны. Они также добавляют цену и риск. Используйте их, когда более простого дизайна на Go недостаточно.

Предпочитайте систему типов, интерфейсы и генераторы, которые можно прочитать. Не начинайте возможность с `reflect` или Cgo. Измеряйте и изолируйте эти инструменты, когда они нужны.

## Рефлексия (`reflect`) — используйте редко

Пакет `reflect` осматривает типы и значения во время выполнения. `reflect.TypeOf` возвращает `reflect.Type`. `reflect.ValueOf` возвращает `reflect.Value`. `Kind` сообщает нижележащий вид (`struct`, `slice`, `ptr` и другие).

`encoding/json` и похожие пакеты используют рефлексию. Это причина, почему кодирование и декодирование JSON медленнее ручного копирования полей. Код приложения, который использует `reflect` для бизнес-правил, часто медленнее и его сложнее проверять типами.

Обычные операции:

- `Value.NumField` и `Field` обходят экспортированные поля структуры.
- `Interface` возвращает значение как `any`.
- `Set` пишет значение, когда `CanSet` истинен.
- `Type.Implements` проверяет интерфейс.

`CanSet` ложен для неэкспортированных полей и для значений, к которым нельзя взять адрес. `ValueOf(x)` на не-указателе часто нельзя задать. Передавайте указатель, когда нужно задать поля.

Рефлексия пропускает проверки времени компиляции. Опечатка в имени поля становится ошибкой времени выполнения. Тесты должны покрывать эти пути.

Используйте рефлексию для:

- универсальных кодеков и форматтеров
- инструментов, которые должны принимать неизвестные структуры
- тонких адаптеров вокруг тегов вроде `json`

Не используйте рефлексию для:

- повседневного доступа к полям
- переключателя типов, который можно написать интерфейсами
- критичных по скорости внутренних циклов

Go 1.22 и новее по-прежнему считают `reflect` API последнего выбора. Дженерики убирают часть старых использований `any` плюс reflect. Предпочитайте дженерики или интерфейсы, когда они выражают дизайн.

`unsafe` плюс `reflect` — острая пара. Не смешивайте их, если не следуете текущим правилам `unsafe` и нет обзора.

## `go:generate` и инструменты AST

`go generate` запускает команды, которые вы пишете в особых комментариях. Форма комментария:

```text
//go:generate stringer -type=Color
```

Комментарий должен начинаться в начале строки. Запускайте `go generate ./...` из корня модуля. `go generate` не часть `go build`. Вы запускаете его, когда меняете вход генератора.

Обычные генераторы:

- `stringer` для методов `String` на целочисленных типах
- генераторы моков для интерфейсов
- компиляторы Protocol Buffer (см. тему 22)

Коммитьте сгенерированные файлы Go, когда команда согласна с этим правилом. CI должен падать, когда сгенерированные файлы устарели. Обычная проверка — запустить `go generate` и затем `git diff --exit-code`.

Пакеты `go/parser`, `go/ast` и `go/token` разбирают исходник Go в абстрактное синтаксическое дерево (AST). `parser.ParseFile` возвращает `*ast.File`. Вы обходите узлы через `ast.Inspect` или `ast.Walk`.

`go/types` проверяет типы пакетов. `golang.org/x/tools/go/packages` загружает пакеты с полной осведомлённостью о модулях. Используйте `go/packages` для инструментов, которые должны следовать импортам. Используйте один `go/parser` для эксперимента с одним файлом.

Инструменты AST — правильный уровень для линтеров и генераторов. Не разбирайте Go регулярными выражениями. Регулярные выражения пропускают комментарии, теги сборки и вложенный синтаксис.

Держите генераторы детерминированными. Вывод не должен включать локальное время или случайный id. Стабильный вывод держит обзоры маленькими.

`//go:generate` может вызывать `go run` генератора в вашем модуле. Этот шаблон держит версию генератора в `go.mod`.

## Cgo (цена и когда избегать)

Cgo позволяет файлу Go импортировать виртуальный пакет `C` и вызывать код C. Вы пишете C в комментариях над `import "C"`. Инструмент `cgo` генерирует клей.

У Cgo есть цена:

- Время сборки растёт.
- Кросс-компиляции нужен кросс-компилятор C.
- Каждый вызов из Go в C имеет накладные расходы. Тесный цикл маленьких вызовов C часто медленнее Go.
- Сборщик мусора Go должен отслеживать указатели, которые вы передаёте. Правила указателей cgo строгие. Нельзя хранить указатель Go в памяти C так, чтобы скрыть его от сборщика.
- `C.CString` выделяет память. Её нужно освободить через `C.free`, когда API C не берёт владение.
- Некоторые платформы и образы `scratch` становятся сложнее.

Задайте `CGO_ENABLED=0`, чтобы форсировать чистую сборку Go. Сборка падает, если пакету нужен Cgo. Это падение полезно. Многие команды держат `CGO_ENABLED=0` в релизных конвейерах.

Причины использовать Cgo:

- Нужно вызвать библиотеку C поставщика, у которой нет API на Go.
- Нужно использовать API операционной системы, который стандартная библиотека не открывает.

Причины избегать Cgo:

- Нужны простые сборки `GOOS`/`GOARCH`.
- Нужен статический бинарный файл в `scratch`.
- Можно использовать чистую библиотеку Go похожего качества.

Стандартная библиотека использует Cgo для некоторых сетевых поисков и поисков пользователя на некоторых платформах. Теги сборки `netgo` и `osusergo` запрашивают чистые реализации Go там, где они есть.

Не используйте Cgo ради скорости без бенчмарка, который включает накладные расходы вызова. Не оборачивайте каждую функцию C, если можно пакетно сделать работу на стороне C.

`CGO_CFLAGS` и `CGO_LDFLAGS` передают флаги компилятору C и компоновщику. Фиксируйте цепочки инструментов. Документируйте версию библиотеки C.

## Осведомлённость об ассемблере (`go tool objdump`, `//go:nosplit`)

Программы на Go компилируются в машинный код. Этот код можно осмотреть. Для приложения почти никогда не пишут ассемблер.

`go build -gcflags=-S` печатает ассемблер во время компиляции. `go tool objdump` дизассемблирует бинарный файл или архив пакета. `go tool objdump -s FuncName binary` ограничивает вывод одной функцией.

Ассемблер Go использует форму, похожую на ассемблер Plan 9. Это не тот же синтаксис, что GNU `as` для каждой платформы. Файлы архитектуры живут в `runtime` и `internal/bytealg` стандартной библиотеки.

`//go:nosplit` — директива компилятора. Она значит: функции не нужен split стека (проверка роста стека) на входе. Среда выполнения использует эту директиву в низкоуровневом коде. Если добавить `//go:nosplit` к функции, которой нужно больше стека, чем лимит, программа может упасть. Не добавляйте эту директиву в код приложения.

Другие директивы, которые можно увидеть:

- `//go:noescape` говорит компилятору, что аргументы-указатели не утекают через вызов.
- `//go:linkname` связывает локальное имя с другим символом. Это не публичный API. Команда Go может его сломать.

Используйте дампы объектов, чтобы учиться. Пример вопросов: встроил ли компилятор функцию, и осталась ли проверка границ?

Не копируйте ассемблер из блога в сервис, чтобы «сделать быстрее». Пишите ясный Go. Сначала используйте `go test -bench` и отчёт компилятора `-gcflags=-m`.

Этот раздел только для осведомлённости. Вам не нужно писать ассемблер, чтобы быть эффективным программистом на Go.

## Внутренности среды выполнения: модель G/M/P

Планировщик Go — планировщик M:N. Много горутин (G) работают на меньшем числе потоков операционной системы (M). Логический процессор (P) держит ресурсы, которые потоку нужны, чтобы выполнять код Go.

- G — горутина. У неё есть стек и состояние (выполняется, готова, ждёт).
- M — машина. Это поток операционной системы.
- P — процессор. Число значений P равно `GOMAXPROCS`. Поток должен держать P, чтобы выполнять код Go.

У P есть локальная очередь готовых горутин. Есть также глобальная очередь готовых. Простаивающие процессоры крадут работу у других процессоров. Это work stealing.

Когда горутина делает блокирующий системный вызов, M может отсоединиться от своего P. P может перейти к другому M, чтобы другие горутины продолжили. Когда системный вызов возвращается, M снова пытается получить P.

Сетевой поллер ждёт готовности сокета. Горутины, которые блокируются на сетевом I/O, паркуются. Им не нужен P, пока они ждут.

`GOMAXPROCS` по умолчанию равен числу ядер ЦП. Большее значение позволяет большему коду Go работать параллельно. Оно не повышает скорость, когда работа не параллельна. Слишком большое значение может добавить накладные расходы.

`runtime.Gosched` уступает ЦП. Большинству программ он не нужен. Каналы, мьютексы и I/O уже паркуют.

Вы не задаёте G, M или P в коде приложения. Вы наблюдаете их трассами и `GODEBUG=schedtrace`. Используйте эту модель, чтобы понять, почему заблокированный syscall не замораживает весь процесс, и почему тесный цикл ЦП без вызовов функций мог откладывать вытеснение в старых версиях Go. Текущие версии Go имеют асинхронное вытеснение (Go 1.14 и новее).

Не настраивайте `GOMAXPROCS` по слухам. Измеряйте.

## Финализаторы и почему они редко правильный инструмент

`runtime.SetFinalizer(obj, func)` регистрирует функцию, которую сборщик мусора может вызвать, когда `obj` становится недостижимым. Финализатор — не деструктор из C++.

Пределы:

- Среда выполнения не гарантирует, что финализатор выполнится в заданное время.
- Среда выполнения не гарантирует, что финализатор выполнится до выхода процесса.
- Финализатор может «воскресить» объект, когда снова сохраняет указатель. Это поведение удивляет.
- Финализаторы выполняются в отдельной горутине. Они могут взаимно заблокироваться, если берут блокировки в плохом порядке.
- Циклы объектов с финализаторами могут задержать или предотвратить сборку.

Используйте явную очистку. Дайте `Close() error`. Вызывайте `Close` с `defer`, когда открываете файл, соединение или дескриптор. Отслеживайте владение в типе, который создал ресурс.

`runtime.KeepAlive(x)` держит `x` достижимым до этой строки. Используйте его, когда финализатор или вызов cgo не должен выполниться, пока вы ещё используете память, которой владеет `x`. Это редкая нужда.

Go 1.24 добавляет `runtime.AddCleanup` как регистрацию очистки, которая избегает некоторых проблем воскрешения финализатора. Предпочитайте `AddCleanup` вместо `SetFinalizer`, когда вы на Go 1.24 или новее и всё ещё нужна очистка, привязанная к GC. Предпочитайте `Close` обоим.

Не используйте финализатор, чтобы сбросить лог или зафиксировать транзакцию. Эти действия должны выполняться в известное время. Не используйте финализатор, чтобы разблокировать мьютекс.

Финализатор — сеть последнего шанса для утечки, которую вы ещё не можете найти. Тест, который проверяет `Close`, — лучшая сеть.

## Ограничения пакета plugin

Пакет `plugin` загружает общий объект во время выполнения на некоторых платформах Unix. `plugin.Open` открывает файл `.so`. `Lookup` находит экспортированный символ.

Пределы суровы:

- Windows не поддерживается.
- Плагин и хост должны быть собраны одним набором инструментов Go и совместимыми флагами.
- Модель плагина плохо совпадает с модулями Go. Версии зависимостей должны совпадать.
- Нельзя выгрузить плагин безопасным общим способом.
- Падения и побочные эффекты `init` происходят в том же процессе. Плохой плагин может уронить хост.
- Кросс-компиляция плагинов мучительна.

Из-за этих пределов большинство команд не используют `plugin` в продакшене. Предпочитайте такие дизайны:

- Компилируйте возможности в бинарный файл тегами сборки.
- Запускайте расширения как отдельные процессы и используйте RPC или HTTP.
- Используйте хост скриптов только когда принимаете эту лишнюю среду выполнения.

Если всё же экспериментируете с `plugin`, держите его вне критического пути. Загружайте только подписанные артефакты из контролируемого пути. Считайте плагин частью того же домена доверия, что и хост.

Читайте `go doc plugin` для текущего списка платформ. Не предполагайте, что macOS, Linux и FreeBSD ведут себя одинаково в каждой версии Go.

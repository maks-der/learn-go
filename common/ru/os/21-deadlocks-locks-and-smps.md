# 21. Взаимные блокировки, блокировки и SMP (продвинуто)

## Описание

Тема 7 ввела мьютексы, взаимную блокировку и первый взгляд на видимость. Эта тема — следующий слой на многопроцессорной (SMP) системе Linux. Вы изучаете порядок блокировок, идею RCU, данные на ЦП, барьеры памяти на высоком уровне, футексы и условия прогресса без блокировок.

Завершите эту тему после внутренностей и трассировки. Завершите эту тему до практики (тема 22). Вы уже знаете критические секции и условия Коффмана. Теперь вы видите, как ядро и libc реализуют ожидания на многих ядрах.

Используйте один термин для каждого понятия. Порядок блокировок — глобальный ранг блокировок, которому должен следовать каждый поток. RCU — метод Linux read-copy-update для читателей, которые не берут писательский мьютекс. Данные на ЦП — копия переменной для каждого ЦП. Барьер памяти — ограничение на порядок операций с памятью. Футекс — очередь ожидания ядра, ключ которой — пользовательский адрес. Wait-free и lock-free — гарантии прогресса для параллельных алгоритмов. Не смешивайте барьер с мьютексом. Не смешивайте lock-free с «программой без блокировок в исходнике».

## Порядок блокировок

Взаимная блокировка среди блокировок нуждается в цикле (тема 7). Простое правило предотвращения — полный порядок. Каждый поток, которому нужно больше одной блокировки, берёт их в одном ранговом порядке. Цикл не может образоваться.

Как применить правило:

1. Перечислите каждую блокировку в подсистеме.
2. Дайте каждой блокировке ранг (число или задокументированный порядок имён).
3. Берите от низкого ранга к высокому (выберите одно направление и держите его).
4. Если держите высокую блокировку и нужна низкая, нужно отпустить и повторить или перепроектировать.

Ядро документирует классы блокировок и использует lockdep. Lockdep — проверка во время выполнения. Он записывает порядок взятия и сообщает о возможном цикле. Можно включить его в отладочном ядре. У пользовательских программ нет lockdep по умолчанию. Вы пишете порядок в комментариях и на ревью.

Порядок — на объект блокировки, не только на тип. Два мьютекса одного типа C всё равно нуждаются в правиле (например, по адресу или по номеру inode).

Один глобальный мьютекс избегает циклов и убивает масштабируемость (обзор темы 7). Порядок — средний путь: много блокировок, одна история рангов.

Инверсия (тема 7) — другая ошибка. Порядок её не чинит. Наследование или меньшая критическая секция могут.

Не берите блокировки в обработчике сигнала. Не изобретайте второй порядок «только когда установлен этот флаг», пока не напишете доказательство.

## Идея RCU (Linux)

Read-copy-update (RCU) — метод синхронизации Linux. Читатели не берут общий мьютекс. Читатель входит в критическую секцию стороны чтения RCU (`rcu_read_lock` в ядре). Затем читатель следует указателям, которые опубликовал писатель.

Писатель, который должен изменить структуру:

1. Копирует структуру (или выделяет новую).
2. Обновляет копию.
3. Публикует новый указатель упорядоченным сохранением.
4. Ждёт, пока каждый ЦП (или каждый читатель) покинет старые секции стороны чтения (период милости).
5. Освобождает старую структуру.

Период милости — сердце RCU. Писатель не освобождает память, которую читатель ещё может видеть.

В пользовательском пространстве есть библиотеки userspace RCU. Большинству прикладного кода всё равно стоит использовать мьютекс. RCU окупается, когда много читателей и мало писателей, как в таблицах маршрутизации и некоторых таблицах файловых дескрипторов.

RCU — не общая замена мьютекса. Писатели всё ещё сериализуются (часто блокировкой). Читатели не должны спать в некоторых вариантах RCU. Правила строгие.

Этот раздел — идея, не лицензия катить свой список в домашнем задании без библиотеки.

Не вызывайте `kfree` на узле, который только что отвязали, пока период милости не закончился.

## Данные на ЦП

Общий счётчик, который увеличивает каждый ЦП, нуждается в строке кэша, которая ездит между ядрами. Этот трафик дорогой. Данные на ЦП дают каждому ЦП свою копию. ЦП обновляет только свою копию. Читатель, которому нужна глобальная сумма, складывает копии (по правилам).

Linux использует переменные на ЦП для статистики, для некоторых аллокаторов и для учёта RCU. `this_cpu_inc` — идея: без блокировки на быстром пути, если ЦП не может мигрировать посреди обновления (или обновление атомарно на этом ЦП).

Пользовательское пространство может приблизить это локальным хранилищем потока (тема 5) или массивом с индексом ЦП (`sched_getcpu`). Миграция — трудная часть. Поток может начать увеличение на ЦП 0 и закончить на ЦП 1, если не осторожен. Ядро отключает вытеснение или использует атомарные операции для некоторых обновлений на ЦП.

Выгоды:

- меньше конкуренции за блокировки
- меньше ложного разделения (тема: одна строка кэша, две переменные)

Цены:

- больше памяти (одна копия на ЦП)
- сумма не мгновенно точная, пока не синхронизируете

Данные на ЦП — не IPC через общую память. Это раскладка для одного процесса или для ядра.

Не стройте массив на ЦП и затем не берите глобальный мьютекс на каждое увеличение. Вы потеряли смысл.

## Барьеры памяти (высокоуровнево)

Современные ЦП и компиляторы переупорядочивают операции с памятью ради скорости. Запись, которая в файле C появляется первой, может стать видимой другому ядру после более поздней записи. Тема 7 показала сломанный `data` плюс флаг `ready`.

Барьер памяти (fence) — аппаратная или компиляторная операция, которая ограничивает это переупорядочивание. Имена различаются:

- Store-release делает предыдущие сохранения в этом потоке видимыми до сохранения release.
- Load-acquire видит сохранение release и затем может прочитать данные, которые написал издатель.
- Полный барьер упорядочивает оба направления (сильнее, медленнее).

Атомики C11 (`memory_order_release`, `memory_order_acquire`, `memory_order_seq_cst`) выражают эти ограничения. Блокировка и разблокировка мьютекса POSIX включают достаточные барьеры. Если используете мьютекс, не добавляйте лишние fence для этих данных.

Код ядра Linux использует `smp_wmb`, `smp_rmb`, `smp_mb` и помощники acquire/release. Вы их видите, если читаете путь ядра (тема 20).

Правила для этого пути:

1. Предпочитайте мьютекс или атомики C11 с задокументированными порядками.
2. Не рассыпайте `asm volatile("" ::: "memory")` и не называйте это блокировкой.
3. `volatile` всё ещё не барьер для других ядер так, как надеются студенты (тема 7).
4. x86 сильнее ARM для некоторых порядков. Тест, который проходит на ноутбуке, может сбоить на телефоне.

Этот раздел не учит каждый litmus-тест слабой памяти ARM. Он учит, почему тема 7 сказала «блокировки публикуют».

## Футекс

Футекс (fast userspace mutex) — примитив Linux. Быстрый путь — атомарный compare-and-swap в пользовательском пространстве на целом. Если блокировка свободна, поток никогда не входит в ядро. Если блокировка занята, поток вызывает `futex`, чтобы спать на адресе. Сторона разблокировки пишет целое и вызывает `futex`, чтобы разбудить ждущих, если нужно.

POSIX `pthread_mutex` на Linux использует футексы. `FUTEX_WAIT` и `FUTEX_WAKE` — классические операции. Поздние операции добавляют requeue, pi (наследование приоритета) и ожидание значения.

Слово футекса должно оставаться по стабильному адресу. Оно может жить в общей памяти для мьютекса, общего для процессов (тема 15). Ядро хеширует адрес (и отображение) в очередь ожидания.

Ложные пробуждения существуют. Ждущий должен перечитать пользовательское целое в цикле. Это совпадает с циклом `while` переменной условия (тема 7).

Редко вызываете `futex` сами. Вызываете `pthread_mutex_lock`. Знание футексов объясняет строки `strace` и объясняет, почему неконкурирующий мьютекс дешёвый.

Не реализуйте мьютекс из `futex`, пока не прочитаете `man 2 futex` и известный хороший алгоритм. Потерянные пробуждения легки.

## Условия прогресса без блокировок (wait-free / lock-free)

Параллельные алгоритмы используют слова прогресса с точным смыслом.

Wait-free: каждый поток завершает операцию за ограниченное число своих шагов, даже если другие потоки останавливаются. Ни один поток не зависит от того, что другой поток выполняется.

Lock-free: какой-то поток завершает операцию за ограниченное число шагов. Система в целом делает прогресс. Один поток может голодать, если другие продолжают выигрывать compare-and-swap.

Obstruction-free: поток завершает, если достаточно долго выполняется один. Другие могут прервать его выполнением.

Алгоритм на мьютексах обычно блокирующий. Если владелец блокировки останавливается (или спит вечно), ждущие никогда не завершают. Это не lock-free.

«Lock-free» не значит «в исходнике нет мьютекса». Очередь lock-free использует атомики и циклы повтора. Она всё ещё может быть медленнее мьютекса. Её труднее доказать.

Структура wait-free ещё труднее. Многие студенческие списки «lock-free» ни корректны, ни lock-free.

Для этого пути:

1. Используйте слова только с определениями выше.
2. Предпочитайте мьютекс, пока измерение не скажет иное.
3. C11 `atomic_compare_exchange` — инструмент, не доказательство lock-freedom.
4. Прогресс алгоритма — не прогресс ввода-вывода. Очередь lock-free всё ещё может блокироваться на `write`.

Живая блокировка темы 7 родственна: потоки выполняются, но алгоритм не делает полезного прогресса. Плохой цикл CAS может дать живую блокировку.

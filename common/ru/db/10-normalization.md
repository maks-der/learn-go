# 10. Нормализация

## Описание

Нормализация — работа по разделению таблиц так, чтобы каждый факт жил в одном месте. Эта тема показывает аномалии обновления, функциональную зависимость, нормальные формы до `BCNF` и когда вы намеренно денормализуете. Пример заказов связывает идеи.

Используйте один термин для каждого понятия. Функциональная зависимость значит, что один набор атрибутов определяет другой. Нормальная форма — правило, которому таблица может удовлетворять. Завершите эту тему до добавления индексов. Грязная таблица тратит индексы.

Нормализуйте, чтобы убрать аномалии. Не делите таблицы только чтобы сделать больше объектов.

---

## Аномалии: вставка, обновление, удаление

Аномалия — плохой побочный эффект, когда пишете плохо спроектированную таблицу. Один и тот же факт сидит во многих строках. Запись может оставить факты в конфликте, или вы вообще не можете сохранить факт.

**Аномалия обновления.** Вы меняете факт в одной строке и забываете копии. Пример: таблица `order_rows` хранит `customer_name` на каждой строке. Ada меняет имя. Вы обновляете одну строку. Другие строки всё ещё показывают старое имя.

**Аномалия вставки.** Вы не можете сохранить факт, пока не существует несвязанный факт. Пример: нельзя сохранить нового клиента, пока у этого клиента нет заказа, потому что столбцы клиента живут только в таблице заказа.

**Аномалия удаления.** Вы удаляете строку и теряете факт, который ещё нужен. Пример: удаляете последний заказ клиента и теряете адрес клиента, потому что адрес жил только на строке заказа.

```text
Bad table order_rows
order_id  product  customer_name  customer_city
1         pen      Ada            London
1         ink      Ada            London
2         pen      Alan           Paris
```

Обновите город Ada только в одной строке. В таблице теперь два города для Ada. Это разделение — аномалия обновления.

Удалите заказ 2. Если у Alan нет другой строки, Alan и Paris исчезают. Эта потеря — аномалия удаления.

Нельзя вставить клиента Grace, у которого нет заказа. Этот пробел — аномалия вставки.

Нормализация переносит `customer_name` и `customer_city` в таблицу `customers`. Каждый факт клиента существует один раз. Заказы указывают на `customer_id`.

Не храните производные копии родительских атрибутов на дочерних строках, если не денормализуете намеренно (поздний раздел) и не контролируете путь обновления.

## Функциональная зависимость (простая идея)

Функциональная зависимость (`FD`) говорит: если две строки имеют одни значения атрибутов X, они должны иметь одни значения атрибутов Y. X определяет Y. Пишем `X → Y`.

Пример. В `customers` `customer_id → name`. У одного id одно имя. Две строки с одним id не могут иметь два имени. Первичный ключ определяет каждый столбец в таблице.

Пример. `isbn → title` в таблице книг, если ISBN идентифицирует книгу. `title → isbn` ложно. Две книги могут делить название.

Пример. В плохой таблице `order_rows` может держаться `order_id → customer_id`, и может держаться `customer_id → customer_city`. Тогда `order_id → customer_city` тоже держится по транзитивности. Город всё ещё принадлежит клиенту, не строке заказа.

Детерминант — левая сторона (X). Если X — кандидатный ключ, зависимость ожидаема. Если X не ключ, и Y не часть X, таблица хранит факт о чём-то другом, кроме ключа. Этот лишний факт — обычная причина разделить таблицу.

```text
order_id, product_id → qty          (line fact)
customer_id → customer_city         (customer fact)
order_id → customer_id              (order fact)
```

Не храните `customer_city` в таблице, чей ключ — `(order_id, product_id)`. Город не зависит от товара.

`FD` про смысл, не про текущий образец. Образец может выглядеть как `city → country`, если у вас одно имя города. Правило всё ещё ложно в мире (Paris существует больше чем в одной стране). Используйте настоящее правило.

## 1NF, 2NF, 3NF

Нормальные формы — тесты. Каждый тест сильнее предыдущего для обычного пути.

**Первая нормальная форма (`1NF`).** Каждый атрибут держит одно значение, не список и не вложенную таблицу. Каждая строка уникальна (ключ существует). У строк и столбцов нет скрытых повторяющихся групп.

Плохая `1NF`: `phones = '111,222'` или два столбца `phone1`, `phone2` как повторяющаяся группа. Хорошая `1NF`: таблица `customer_phones` с одним телефоном на строку.

**Вторая нормальная форма (`2NF`).** Таблица в `1NF`. Каждый неключевой атрибут зависит от всего первичного ключа, не от части составного ключа.

Плохая `2NF`: `order_lines` с ключом `(order_id, product_id)` и столбцом `customer_id`, который зависит только от `order_id`. Перенесите `customer_id` в `orders`.

**Третья нормальная форма (`3NF`).** Таблица в `2NF`. Никакой неключевой атрибут не зависит от другого неключевого атрибута. Неключевые атрибуты зависят только от ключа.

Плохая `3NF`: `orders` с `customer_id` и также `customer_city`. Город зависит от `customer_id`, не от `order_id`. Перенесите город в `customers`.

```text
1NF: atomic values, a key
2NF: no partial dependency on a composite key
3NF: no transitive dependency through a non-key
```

Таблица с одностолбцовым первичным ключом автоматически в `2NF`, если она в `1NF`. Частичные зависимости нуждаются в составном ключе.

`3NF` — обычная цель для операционных систем. Она убирает обычные аномалии. `BCNF` — следующий раздел.

Не гонитесь за нормальными формами как за счётом. Используйте их, чтобы найти неуместные факты.

## BCNF (высокий уровень)

Нормальная форма Бойса–Кодда (`BCNF`) — более строгая форма `3NF`. Правило простыми словами: каждый детерминант — кандидатный ключ.

`3NF` всё ещё допускает особый случай: неключевой детерминант, который указывает внутрь кандидатного ключа. Этот случай редок. `BCNF` его запрещает.

Пример (классическая форма). Таблица `offerings` курса:

- У курса много преподавателей.
- Преподаватель ведёт только один курс.
- Ключ — `(course, classroom)` или `(teacher, classroom)` в зависимости от правил.

Если `teacher → course` и `teacher` не кандидатный ключ таблицы, `BCNF` не проходит. Вы делите на `teacher_course(teacher, course)` и таблицу, которая назначает комнаты.

Для большинства схем новичка `3NF` и `BCNF` совпадают. Если каждый детерминант — ключ, вы в `BCNF`.

Не тратьте часы на головоломки `BCNF`, пока не умеете моделировать заказы и клиентов. Выучите лозунг: детерминанты должны быть ключами. Если находите детерминант, который не ключ, разделите таблицу.

`BCNF` может сделать некоторые ограничения труднее держать в одной таблице. Могут понадобиться две таблицы плюс приложение или ограничение СУБД, которое охватывает таблицы. Этот компромисс — почему некоторые тексты остаются на `3NF` для обучения.

```text
3NF:   non-key attributes depend only on keys
BCNF:  every determinant is a candidate key
```

Если у таблицы один кандидатный ключ и нет лишних `FD`, `BCNF` держится.

## Когда денормализовать намеренно

Денормализация — запланированная копия факта в другую таблицу. Вы делаете это после нормализованной модели. Вы принимаете лишнее хранение и лишнюю работу обновления ради более быстрого или более простого чтения.

Допустимые причины:

- отчёт, который не должен соединять десять таблиц на каждой загрузке страницы
- кэш отображаемого имени на строке события, которое никогда не меняется
- таблица фактов хранилища, которая хранит дату и метку ради скорости чтения
- поисковый индекс, который копирует поля из нескольких таблиц

Недопустимые причины:

- не хотели писать соединение
- скопировали столбцы «на всякий случай» без владельца обновлений
- хранили список в текстовом столбце, чтобы избежать дочерней таблицы, и всё ещё нужно запрашивать элементы

Правила, когда денормализуете:

- Назовите источник истины. Одна таблица остаётся владельцем.
- Спланируйте обновление: та же транзакция, триггер или пакетное задание.
- Документируйте задержку, если копия может устареть.
- Не денормализуйте до измерения настоящей проблемы чтения.

Пример. `orders` хранит `customer_id`. Для задания печати этикетки доставки вы копируете `ship_to_name` на заказ в момент оформления. Эта копия — снимок. Поздние смены имени не переписывают старые этикетки. Снимок — бизнес-выбор, не ошибка.

Пример. Столбец `customer_name` на каждой строке `order_lines`, который обновляете при смене клиента, — плохая денормализация. Цена обновления высока и легко пропустить.

Не путайте денормализацию с игнорированием `1NF`. Документный склад JSON — другая модель. В реляционной операционной базе начинайте с `3NF`.

## Пример: заказы и строки заказа

Этот пример — стандартное разделение.

**Факты.**

- Клиент оформляет много заказов.
- У заказа много строк.
- Строка — количество одного товара.
- Имя товара и прайс-лист живут с товаром. Строка может хранить продажную цену как снимок.

**Нормализованные таблицы.**

```sql
CREATE TABLE customers (
    customer_id INTEGER PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    city VARCHAR(100) NOT NULL
);

CREATE TABLE products (
    product_id INTEGER PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    list_price DECIMAL(10, 2) NOT NULL
);

CREATE TABLE orders (
    order_id INTEGER PRIMARY KEY,
    customer_id INTEGER NOT NULL,
    ordered_at TIMESTAMP NOT NULL,
    CONSTRAINT fk_orders_customers
        FOREIGN KEY (customer_id) REFERENCES customers (customer_id)
);

CREATE TABLE order_lines (
    order_id INTEGER NOT NULL,
    product_id INTEGER NOT NULL,
    qty INTEGER NOT NULL,
    unit_price DECIMAL(10, 2) NOT NULL,
    PRIMARY KEY (order_id, product_id),
    CONSTRAINT chk_ol_qty CHECK (qty > 0),
    CONSTRAINT fk_ol_orders FOREIGN KEY (order_id) REFERENCES orders (order_id),
    CONSTRAINT fk_ol_products FOREIGN KEY (product_id) REFERENCES products (product_id)
);
```

**Зависимости.**

- `customer_id → name, city`
- `product_id → name, list_price`
- `order_id → customer_id, ordered_at`
- `(order_id, product_id) → qty, unit_price`

`unit_price` на строке — снимок продажи. Он может позже отличаться от `list_price`. Эта копия намеренна.

**Плохая объединённая таблица (для контраста).**

```text
order_id, product_id, qty, product_name, list_price, customer_name, city
```

Эта таблица смешивает факты строки, товара и клиента. Она не проходит `2NF` и `3NF`. Появляются аномалии.

Запись нового заказа использует одну транзакцию: вставить `orders`, вставить `order_lines`. Тема 9 покрывает эту транзакцию.

### Вопросы

#### Теоретические вопросы

### Вопросы

#### Теоретические вопросы

1. Как `FD` говорят вам, что столбец в неверной таблице?

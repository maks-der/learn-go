# 10. Память: защита и разделение

## Описание

MMU не только переводит адреса. Он также обеспечивает разрешения. Эта тема объясняет биты чтения, записи и исполнения. Вы узнаете разделяемую память, страницы копирования при записи, рандомизацию раскладки адресного пространства (ASLR) и защитные страницы.

Завершите эту тему после адресных пространств и выделения. Вы уже знаете PTE и COW после `fork`. Эта тема использует эти идеи для безопасности и для разделения.

Используйте один термин для каждого понятия. Бит защиты — разрешение в записи таблицы страниц. Разделяемая память — кадр, который больше одного процесса отображает записываемым или читаемым нарочно. ASLR — случайный сдвиг баз отображений. Защитная страница — неотображённая или недоступная страница, которая ловит переполнение. Не смешивайте разделяемую память с частными отображениями COW. Не смешивайте ASLR со стековым канарейкой (другая защита).

## Биты защиты: R/W/X

У каждого отображения есть разрешения. Linux `mmap` и `mprotect` используют `PROT_READ`, `PROT_WRITE` и `PROT_EXEC`. `/proc/<pid>/maps` показывает `r`, `w`, `x`.

Типичные сочетания:

- `r-x`: текст, некоторые библиотеки
- `r--`: константы, некоторые отображения файлов
- `rw-`: куча, стек, записываемые данные
- `--x` или `r-x` без записи: вы не можете сохранять в страницу

ЦП и MMU обеспечивают биты. Запись в страницу только для чтения даёт отказ. Ядро может обработать отказ как COW или послать `SIGSEGV`. Исполнение неисполняемой страницы тоже даёт отказ (`SIGSEGV` или `SIGILL` в зависимости от пути).

W^X (write xor execute) — политика: страница не должна быть одновременно записываемой и исполняемой. Эта политика усложняет некоторые атаки внедрения кода. JIT-компиляторы сначала запрашивают `PROT_WRITE`, пишут код, затем делают `mprotect` в `PROT_READ|PROT_EXEC`.

Бит NX (no-execute) в PTE — аппаратный запрет исполнения. Современные пользовательские стеки Linux по умолчанию неисполняемы.

`PROT_NONE` отображает страницу без доступа. Защитные страницы используют это. Касание даёт отказ.

Пользовательские программы не могут обойти эти биты. Ошибка ядра или неверный `mprotect` в вашем процессе всё ещё может ослабить защиту. Не делайте `mprotect` стека исполняемым без сильной причины.

## Разделяемая память

Разделяемая память — дизайн, в котором два или более процессов отображают одни физические кадры и намерены видеть сохранения друг друга.

Способы в Linux:

1. `mmap` одного файла с `MAP_SHARED`.
2. POSIX разделяемая память: `shm_open`, затем `mmap`.
3. Разделяемая память System V: `shmget` и `shmat`.
4. Некоторые анонимные отображения с `MAP_SHARED` после `fork` (потомок наследует отображение).

Разделяемая память — быстрый IPC. Нет копии ядра на каждое сохранение. Процессы должны синхронизироваться. Используйте мьютекс в общей области (с `PTHREAD_PROCESS_SHARED`), семафор или атомики. Правила темы 7 всё ещё применимы. Гонка в разделяемой памяти всё ещё гонка.

Разделяемая память — не отображение данных `fork` по умолчанию. Частные отображения по умолчанию — COW. Записи не идут к соседу.

Разрешения всё равно применимы. Вы можете отобразить разделяемую память только для чтения в одном процессе и для чтения-записи в другом, если так настроите.

Очистка: сегменты System V могут остаться после выхода процесса, пока `shmctl` их не уберёт. Объекты POSIX shm живут в `/dev/shm`, пока вы не сделаете `shm_unlink`. Утечки заполняют эту файловую систему.

Не используйте разделяемую память для секретов без плана. Любой процесс с тем же доступом может читать байты.

## Страницы копирования при записи

Страницы копирования при записи — метод разделения, который становится частным при записи. Тема 9 объяснила COW после `fork`. Этот раздел ставит COW рядом с настоящей разделяемой памятью.

COW использует:

- общий кадр
- PTE только для чтения в каждом процессе
- отказ и копию при записи

Применения:

- `fork` без немедленной полной копии
- файловые отображения `MAP_PRIVATE`: чтения делят кэш страниц; записи получают частный кадр
- ядро может делить одинаковые страницы файлов между процессами, которые читают одну библиотеку

COW — разделение чистых страниц. Это не протокол для двух процессов, чтобы совместно работать над буфером. После записи процессы расходятся.

Ядро отслеживает, сколько PTE ссылаются на кадр (счётчик ссылок). Когда последнее отображение исчезает, ядро может освободить кадр. Когда происходит копия COW, писатель получает кадр со счётчиком 1.

Запись в отображение `MAP_PRIVATE` не меняет файл. Запись в отображение `MAP_SHARED` может изменить файл. Это практический тест.

Отказы COW могут сбоить при OOM. `fork` огромной грязной кучи — риск. Потомок или родитель могут умереть при первой записи в страницу COW, если кадра нет.

## ASLR

Рандомизация раскладки адресного пространства (ASLR) — защита. Ядро размещает стеки, кучи, библиотеки и (когда возможно) главный исполняемый файл по случайным смещениям на каждом запуске.

Цель: атакующий, который знает ошибку (например переполнение буфера), не должен знать фиксированный адрес гаджета или стека. Атакующий должен сначала утечь адрес.

Linux управляет ASLR через `kernel.randomize_va_space` (`sysctl`). Обычные значения:

- `0`: выкл
- `1`: консервативная рандомизация
- `2`: полная рандомизация (типичное значение по умолчанию)

Главная программа рандомизируется, когда она является позиционно-независимым исполняемым файлом (PIE). Большинство современных дистрибутивов собирают PIE по умолчанию. `cat /proc/self/maps` на двух запусках одной программы показывает разные старты, когда ASLR включён.

ASLR — не полная защита. Утечка одного адреса библиотеки может раскрыть остальную библиотеку. Частичные перезаписи и кучевые спреи всё ещё существуют. Сочетайте ASLR с NX, стековыми канарейками и безопасным кодом.

Не выключайте ASLR на производственном хосте, чтобы «отладить», если только не используете контролируемую среду. Для локальной сессии отладки существуют `gdb` и `set disable-randomization`. Предпочитайте журналировать адреса из `/proc/self/maps`, пока ASLR остаётся включённым.

`mmap` без подсказки всё равно получает адрес, выбранный ядром. Этот выбор может включать рандомизацию.

## Защитные страницы

Защитная страница — страница, к которой нельзя обращаться. Она сидит рядом с буфером или стеком. Переполнение, которое сходит с буфера, попадает в защиту и даёт отказ.

У стеков потоков Linux есть защитная область. Переполнение стека попадает в `PROT_NONE` или неотображённый промежуток. Процесс получает сигнал вместо тихого повреждения кучи или стека другого потока.

Вы можете добавить свою защиту:

```c
/* allocate 3 pages, make the first PROT_NONE, use the middle page */
```

Сделайте `mmap` большей области и `mprotect` краёв в `PROT_NONE`. Ваш объект сидит посередине.

Аппаратное переполнение стека и программное переполнение кучи различаются. `malloc` не ставит защитную страницу после каждого объекта 16 байт. Переполнение кучи всё ещё может разбить метаданные следующего куска. Инструменты вроде AddressSanitizer добавляют красные зоны. Эти красные зоны — возможность отладочного распределителя, не защита стека ядра.

У `MAP_GROWSDOWN` и расширения стека особые правила. Большой пропуск стека может промахнуться мимо защиты и всё равно дать отказ, или его могут счесть атакой. Не выделяйте огромные массивы на стеке.

Защитные страницы используют гранулярность страницы. Переполнение на 1 байт маленького объекта кучи не попадает в защитную страницу, если вы не выровняли объект в конце страницы и не поставили защиту рядом.

2. Задокументируйте, как бы вы делили кольцевой буфер между двумя процессами: тип отображения, место мьютекса и почему COW неверен.
3. Используйте `readelf -l` и `maps`, чтобы показать PIE и NX-стек для одного двоичного файла.

#### Сложные практические задания

1. Прочитайте Linux `Documentation/admin-guide/sysctl/kernel.rst` про `randomize_va_space` и обзор pkeys. Напишите одну страницу «защиты в глубину» для памяти процесса.
2. Реализуйте POSIX shm с мьютексом, общим для процессов, и защитной страницей на каждом конце буфера. Задокументируйте отказы, если соседний обход уходит слишком далеко.

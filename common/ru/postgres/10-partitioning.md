# 10. Секционирование

## Описание

Эта тема показывает декларативное секционирование в PostgreSQL 16 и PostgreSQL 17. Вы узнаёте секции range, list и hash, отсечение секций, индексы на секционированных таблицах и как архивировать старые секции.

Сначала завершите тему 9. Вы умеете создавать таблицы и функции. Завершите эту тему до изучения бэкапов и реплик.

Используйте один термин для каждого понятия. Секционированная таблица — родитель. Секция — дочерняя таблица, которая держит срез строк. Ключ секции — список столбцов, который выбирает срез. Отсечение секций пропускает секции, которые не могут совпасть с запросом. Декларативное секционирование — `PARTITION BY` на `CREATE TABLE`. Наследование — другая, более старая возможность. Для новых больших таблиц предпочитайте декларативное секционирование. Этот справочник рассчитан на PostgreSQL 16 и PostgreSQL 17.

## Декларативные секции range, list и hash

Декларативное секционирование режет одну таблицу на секции. `INSERT` делаете в родителя. Сервер направляет строку в одну секцию. `SELECT` на родителе может читать много секций.

Три метода:

- **RANGE** — смежные границы (`FOR VALUES FROM ... TO ...`). Обычно для `date` и `timestamptz`.
- **LIST** — дискретные значения (`FOR VALUES IN (...)`). Обычно для id тенанта или статуса, который режете намеренно.
- **HASH** — корзины по модулю (`FOR VALUES WITH (MODULUS n, REMAINDER r)`). Обычно когда нужен ровный размер и всегда фильтруете по ключу хеша.

```sql
CREATE TABLE shop.orders (
    id bigint GENERATED ALWAYS AS IDENTITY,
    created_on date NOT NULL,
    tenant_id bigint NOT NULL,
    total numeric(12, 2) NOT NULL,
    PRIMARY KEY (id, created_on)
) PARTITION BY RANGE (created_on);

CREATE TABLE shop.orders_2026_01
    PARTITION OF shop.orders
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');

CREATE TABLE shop.orders_2026_02
    PARTITION OF shop.orders
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
```

Верхняя граница исключительная. Строка с `created_on = '2026-02-01'` идёт в `orders_2026_02`.

Секция по умолчанию ловит значения, которые не заявляет ни одна другая секция:

```sql
CREATE TABLE shop.orders_default
    PARTITION OF shop.orders DEFAULT;
```

Секцию по умолчанию используйте осторожно. Она может расти без предела, если забудете новые месяцы.

Пример hash:

```sql
CREATE TABLE shop.sessions (
    sid uuid NOT NULL,
    user_id bigint NOT NULL,
    PRIMARY KEY (sid)
) PARTITION BY HASH (sid);

CREATE TABLE shop.sessions_p0 PARTITION OF shop.sessions
    FOR VALUES WITH (MODULUS 4, REMAINDER 0);
```

Уникальные ключи и первичные ключи на секционированной таблице должны включать ключ секции. Глобальный уникальный `id` один на родителе в PostgreSQL 16 и 17 недопустим.

Не секционируйте маленькую таблицу. Секционирование добавляет стоимость планирования. Не вставляйте строку, которая не совпадает ни с одной секцией и нет default; оператор падает. Не используйте наследование таблиц, чтобы резать новую таблицу фактов (тема 2).

Официально: [https://www.postgresql.org/docs/17/ddl-partitioning.html](https://www.postgresql.org/docs/17/ddl-partitioning.html).

## Отсечение секций

Отсечение секций пропускает секции, которые не могут содержать совпадающие строки. Планировщику нужно ограничение на ключ секции (или значение, которое он может доказать).

```sql
EXPLAIN (ANALYZE, COSTS OFF)
SELECT id, total
FROM shop.orders
WHERE created_on >= DATE '2026-02-01'
  AND created_on <  DATE '2026-03-01';
```

План должен перечислить `orders_2026_02` и не должен сканировать `orders_2026_01`, когда границы — константы.

Отсечение может быть на этапе плана или на этапе выполнения. Отсечение во время выполнения применяется, когда значение — параметр, который исполнитель узнаёт позже (`PREPARE` / bind или соединение). `EXPLAIN (ANALYZE)` показывает удалённые секции яснее, чем `EXPLAIN` без analyze.

Фильтр по столбцу, который не ключ секции, не отсекает. `WHERE total > 100` всё равно может сканировать каждый месяц.

`SET enable_partition_pruning = off` — отладочный переключатель. В продакшене оставляйте включённым.

Функции на ключе секции могут блокировать отсечение. Предпочитайте `created_on >= $1` вместо `date_trunc('month', created_on) = $1`, когда `created_on` — ключ.

Не прячьте ключ секции внутри выражения, которое планировщик не может доказать. Не ждите отсечения от поля `jsonb`, если это поле не ключ секции.

## Индексы на секционированных таблицах

Индекс на родителе — секционированный индекс. PostgreSQL создаёт соответствующий индекс на каждой секции. Новые секции получают индекс при присоединении, если индекс создали на родителе.

```sql
CREATE INDEX orders_tenant_idx ON shop.orders (tenant_id);
```

У каждой секции своё B-дерево. Одного кластерного B-дерева на все месяцы нет. Уникальный индекс на родителе должен включать ключ секции — то же правило, что у первичного ключа.

Индекс можно создать только на одной секции:

```sql
CREATE INDEX orders_2026_01_total_idx ON shop.orders_2026_01 (total);
```

Локальный индекс используйте, когда одному срезу нужна другая форма. Предпочитайте родительские индексы, чтобы не забыть новые месяцы.

`CREATE INDEX CONCURRENTLY` на секционированном родителе в PostgreSQL 16 и 17 имеет дополнительные правила. Часто создаёте индекс на родителе без `CONCURRENTLY` или строите по секции concurrently и присоединяете. Прочитайте текущую страницу `CREATE INDEX`, прежде чем запускать это на продакшене.

`REINDEX` может целиться в родителя или одну секцию. Тема 5 разбирала `REINDEX` и `CONCURRENTLY`.

Внешний ключ из обычной таблицы на секционированную поддерживается, когда существует ссылаемый уникальный ключ. Кросс-секционных уникальных ключей, которые опускают ключ секции, нет.

Не ждите одного уникального `email` по всем list-секциям, если `email` не в ключе секции. Не создавайте пятьдесят разных определений индексов вручную без родительского индекса.

## Архивирование старых секций

Секция — таблица. Её можно отсоединить, сдампить, переместить или удалить. Это главный операционный выигрыш range-секционирования.

Отсоединить без долгого ожидания в PostgreSQL 14 и новее (16 и 17 включены):

```sql
ALTER TABLE shop.orders DETACH PARTITION shop.orders_2025_01 CONCURRENTLY;
```

`CONCURRENTLY` нельзя запускать в блоке транзакции. После успешного отсоединения таблица — обычная таблица. Её можно `pg_dump`, перенести в архивную схему или `DROP TABLE`, когда бэкап безопасен.

Присоединить старую таблицу, у которой уже есть нужные строки и границы:

```sql
ALTER TABLE shop.orders ATTACH PARTITION shop.orders_2025_01
    FOR VALUES FROM ('2025-01-01') TO ('2025-02-01');
```

Присоединение проверяет границы. Проверка может взять блокировку и сканировать. Подготовьте таблицу подходящим ограничением `CHECK`, чтобы ускорить attach, когда документация говорит, что это помогает.

Поток архива, который используют многие команды:

1. Создайте секции следующего месяца до начала месяца.
2. Отсоедините месяцы, которые приложение не должно запрашивать онлайн.
3. Сдампите или скопируйте отсоединённую таблицу в холодное хранилище.
4. Удалите отсоединённую таблицу после проверки дампа.

Секцию по умолчанию, которая собрала «забытые» месяцы, сложнее разрезать. Держите календарное задание, которое создаёт секции.

Не `DELETE` миллионы старых строк из несекционированной таблицы, если можно секционировать по дате и удалить срез. Не удаляйте секцию до бэкапа, который проверили. Тема 11 разбирает `pg_dump` одной таблицы.

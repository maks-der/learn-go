# 7. Схема, типы и ограничения

## Описание

Эта тема показывает, как создавать таблицы, выбирать типы и обеспечивать правила. Вы изучаете `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`, обычные типы, ловушки денег и часовых поясов, ограничения, действия внешних ключей и именование.

Используйте один термин для каждого понятия. Оператор определения схемы меняет объекты, не значения строк. `CREATE`, `ALTER` и `DROP` — язык определения данных (DDL). Тип ограничивает значения в столбце. Ограничение — правило, которое СУБД проверяет при записи.

Практикуйтесь на одноразовой базе. Не удаляйте таблицу, которой пользуются другие люди.

## `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`

`CREATE TABLE` определяет базовую таблицу. Вы называете таблицу. Вы называете каждый столбец. Вы даёте каждому столбцу тип. Вы добавляете ограничения.

```sql
CREATE TABLE products (
    product_id INTEGER PRIMARY KEY,
    sku VARCHAR(32) NOT NULL UNIQUE,
    name VARCHAR(200) NOT NULL,
    price DECIMAL(10, 2) NOT NULL,
    active BOOLEAN NOT NULL,
    created_at TIMESTAMP NOT NULL
);
```

`CREATE TABLE` падает, когда имя уже существует. Используйте новое имя или удалите старую таблицу только если это безопасно.

`ALTER TABLE` меняет существующую таблицу. Вы добавляете столбец, удаляете столбец, меняете тип или добавляете ограничение. Точные предложения отличаются по вендору. Изучайте идеи, затем читайте синтаксис продукта.

Добавить столбец:

```sql
ALTER TABLE customers
    ADD email_verified BOOLEAN NOT NULL DEFAULT FALSE;
```

Новому столбцу `NOT NULL` нужно значение по умолчанию, если строки уже есть. СУБД должна заполнить новый столбец для каждой старой строки.

Удалить столбец:

```sql
ALTER TABLE customers
    DROP COLUMN email_verified;
```

Удаление столбца уничтожает эти данные. Другие объекты (представления, индексы) могут блокировать удаление.

Добавить ограничение после того, как таблица существует:

```sql
ALTER TABLE products
    ADD CONSTRAINT chk_products_price CHECK (price >= 0);
```

Добавление падает, если текущая строка ломает проверку. Сначала очистите данные или исправьте правило.

Меняйте тип, когда существующие значения чисто преобразуются. Смена с `VARCHAR(200)` на `VARCHAR(50)` падает, если значение длиннее 50.

Не используйте `ALTER TABLE` как ежедневный инструмент правки данных. Для значений используйте `UPDATE`. Для структуры используйте `ALTER`.

DDL может заблокировать таблицу. Долгий alter может блокировать писателей. В продакшене большие изменения запускайте в окне обслуживания. Этому пути нужны только маленькие учебные таблицы.

`DROP TABLE` удаляет объект таблицы и её данные. Имя исчезает. Индексы этой таблицы исчезают. Действие — не пустая таблица. Чтобы оставить таблицу и удалить строки, используйте `DELETE` или `TRUNCATE`.

```sql
DROP TABLE scratch_items;
```

Если другие таблицы ссылаются на таблицу внешним ключом, СУБД по умолчанию отклоняет удаление. Это правило безопасности.

Некоторые продукты позволяют `DROP TABLE customers CASCADE`. `CASCADE` удаляет зависимые объекты или внешние ключи, которые указывают на таблицу. Точный список отличается по вендору. `CASCADE` может удалить больше, чем вы ожидаете.

Не путайте `DROP TABLE ... CASCADE` (удалить объекты) с `ON DELETE CASCADE` (удалить дочерние строки при удалении родительской). Следующие разделы покрывают действия внешних ключей.

У некоторых продуктов есть `DROP TABLE IF EXISTS`. Эта форма избегает ошибки, когда таблицы уже нет. Используйте её в скриптах, которые перезапускаете.

## Целые, десятичные, текст, даты, булевы

Доменный тип ограничивает, что столбец может хранить. СУБД отклоняет значение, которое не совпадает с типом. Типы — первое правило целостности.

**Целое.** Целое — целое число. Используйте целое для счётчиков, идентификаторов, которые являются числами, и количеств без дроби. Пример: `quantity` на строке заказа. Не используйте целое для денег, если не храните центы.

**Десятичное.** Десятичное хранит число с фиксированной шкалой. Шкала — число цифр после точки. Точность — общее число цифр. Пример: `DECIMAL(12, 2)` может хранить значения вроде `1999.50` с двумя дробными цифрами. Используйте десятичное, когда дробь должна быть точной.

**Текст.** Текст хранит символы. Используйте ограниченный тип, когда продукт даёт его (`VARCHAR(n)`). Используйте неограниченный тип только когда длина не имеет полезного предела. Храните коды в стабильном алфавите. Не храните дату или число как текст, если нужно сортировать или считать по этому значению.

**Дата и время.** Тип даты хранит календарный день. Тип метки времени хранит день и время часов. Тип времени хранит время часов без дня. Используйте эти типы для значений времени. Не храните дату как текст, если нужно сравнивать даты.

**Булево.** Булево хранит истину или ложь. Некоторые продукты также допускают неизвестное (`NULL`). Используйте булево для факта да/нет. Пример: `is_active`. Не используйте целые `0` и `1`, если у продукта нет булева типа.

Обычные семейства типов (имена отличаются по продукту):

| Семейство | Типичное имя в стиле стандарта | Применение |
| --- | --- | --- |
| Целое | `INTEGER` | Счётчики, id, количества |
| Десятичное | `DECIMAL(p, s)` | Деньги и точные дроби |
| Плавающее | `DOUBLE PRECISION` | Научные меры, не деньги |
| Текст | `VARCHAR(n)` | Строки; предпочитайте `VARCHAR` |
| Дата | `DATE` | Календарный день |
| Время | `TIMESTAMP` | День плюс время |
| Булево | `BOOLEAN` | Истина или ложь |

Выбирайте самый узкий тип, который подходит домену. Узкий тип занимает меньше места. Узкий тип также отклоняет больше плохих записей.

`NULL` — не тип. `NULL` значит, что значение отсутствует. Тип плюс `NOT NULL` сильнее, чем тип один.

Не смешивайте единицы в одном столбце. Пример: не храните килограммы и граммы в одном числовом столбце без столбца единицы. Тип не видит единицу.

Не изобретайте тип на продукт на этом пути, когда существует тип в стиле стандарта. Пишите `INTEGER` и `DECIMAL`. Подстройте под продукт при реализации.

## Деньги и ловушки плавающей точки

Деньги — счёт единицы валюты. Счёт должен быть точным. Тип с плавающей точкой (`REAL`, `FLOAT`, `DOUBLE PRECISION`) — двоичное приближение. У многих десятичных дробей нет точной двоичной формы. Пример: `0.1` плюс `0.2` может провалить проверку равенства в плавающей точке.

Не храните деньги в столбце с плавающей точкой. Используйте десятичный тип с фиксированной шкалой или храните целое число наименьшей единицы (центы). Оба метода держат точные суммы.

```sql
-- Prefer a decimal with a known scale
unit_price DECIMAL(12, 2) NOT NULL

-- Or an integer count of cents
unit_price_cents INTEGER NOT NULL
```

Выберите один метод для всей схемы. Не смешивайте доллары как float и центы как целое в одной базе без письменного правила.

Округление — бизнес-правило. Деньги с двумя знаками часто используют банковское округление или округление половины вверх. Десятичный тип СУБД хранит цифры. Приложение или задокументированная функция SQL должны применять правило округления на одном и том же шаге каждый раз.

Валюта — не только число. Цена `10.00` неполная, если не знаете валюту. Используйте столбец кода валюты (`USD`, `EUR`), когда существует больше одной валюты. Не складывайте суммы в разных валютах.

Налоги и скидки создают больше точек округления. Считайте из одного источника истины (цена единицы и количество). Храните итог строки, который вы взяли. Не пересчитывайте исторический счёт по живым таблицам налогов, если продукт этого не требует.

Типы с плавающей точкой остаются полезны для измерений и научных значений. Они неверный тип для журналов учёта.

## Часовые пояса и UTC

Метка времени без часового пояса — чтение местных часов. СУБД не знает пояс. Метка времени с часовым поясом (или мгновение, сохранённое в UTC) называет одну точку на шкале времени.

UTC — стандартная шкала времени. Многие системы хранят мгновения в UTC. Приложение переводит в местный пояс только когда показывает значение человеку.

Используйте одно правило для всех мгновений:

1. Примите время от клиента с явным поясом или как UTC.
2. Переведите значение в UTC.
3. Храните UTC.
4. Переводите в пояс пользователя только в слое представления.

Календарная дата (`DATE`) не имеет времени часов и не имеет пояса. День рождения — дата. Начало встречи — мгновение. Не храните начало встречи только как дату.

«Местное гражданское время» — другая потребность. Пример: магазин, который открывается в 09:00 в каждом городе. Это значение — время плюс имя пояса, не одно мгновение UTC, пока не выберете день.

```sql
-- Instant: prefer UTC in the column or a timestamptz type
created_at TIMESTAMP NOT NULL  -- store UTC; document the rule

-- Civil date: no zone
birth_date DATE NOT NULL
```

Не дописывайте аббревиатуру пояса вроде `EST` как свободный текст. Аббревиатуры сталкиваются. Когда нужно хранить пояс, используйте имя зоны IANA (`America/New_York`).

Переход на летнее время меняет смещение. Сохранённое мгновение UTC не двигается. Сохранённое местное время без пояса может стать неоднозначным в час перекрытия.

Не сравнивайте метки времени, которые смешивают UTC и неизвестный местный пояс. Сначала переведите.

## `NOT NULL`, `UNIQUE`, `CHECK`, `DEFAULT`

Ограничения — правила на таблице. СУБД отклоняет изменение, которое ломает ограничение.

**`NOT NULL`.** Столбец должен иметь значение в каждой строке.

**`UNIQUE`.** Никакие две строки не делят одно значение (для `NULL` продукты отличаются: многие допускают несколько `NULL` в уникальном столбце). Уникальное ограничение может покрывать больше одного столбца.

**`CHECK`.** Выражение должно быть истинным или неизвестным для каждой строки. `CHECK (price >= 0)` отклоняет отрицательные цены. Цена `NULL` делает проверку неизвестной, поэтому допускающая `NULL` цена всё ещё может быть `NULL`, если не добавить также `NOT NULL`.

**`DEFAULT`.** Когда вставка опускает столбец, СУБД хранит это значение. Значение по умолчанию — не ограничение в том же смысле, но принадлежит определению столбца.

```sql
CREATE TABLE products (
    product_id INTEGER PRIMARY KEY,
    sku VARCHAR(32) NOT NULL UNIQUE,
    name VARCHAR(200) NOT NULL,
    price DECIMAL(10, 2) NOT NULL DEFAULT 0,
    active BOOLEAN NOT NULL DEFAULT TRUE,
    CONSTRAINT chk_products_price CHECK (price >= 0)
);
```

`PRIMARY KEY` подразумевает `UNIQUE` и `NOT NULL`. Не нужно писать эти два снова на тех же столбцах.

Именуйте ограничения (`chk_products_price`). Имя появляется в сообщениях об ошибках. Безымянные ограничения получают сгенерированное имя, которое трудно читать.

Можно прикрепить `UNIQUE`, `CHECK` и внешние ключи как ограничения таблицы. Можно прикрепить `NOT NULL` и `DEFAULT` как атрибуты столбца.

Не используйте `CHECK` для правил, которым нужна другая таблица. Используйте внешний ключ. Некоторые продукты допускают подзапросы в `CHECK`. Эта возможность не переносима.

Не полагайтесь на `DEFAULT`, чтобы спрятать отсутствующее бизнес-значение. Если приложение должно слать `active`, требуйте его в приложении, даже если у столбца есть значение по умолчанию.

## Действия внешних ключей, мягкое удаление и столбцы аудита

Внешний ключ говорит, что дочернее значение должно совпадать с родительским ключом. СУБД также может определить, что происходит, когда родительская строка меняется.

`ON DELETE` задаёт действие, когда удаляете родительскую строку.

| Действие | Эффект на дочерние строки |
| --- | --- |
| `NO ACTION` / `RESTRICT` | Удаление родителя падает, пока дети существуют |
| `CASCADE` | СУБД удаляет совпадающие дочерние строки |
| `SET NULL` | СУБД ставит внешний ключ в `NULL` (столбец должен допускать `NULL`) |
| `SET DEFAULT` | СУБД ставит внешний ключ в значение по умолчанию |

`ON UPDATE` задаёт действие, когда значение родительского ключа меняется. Суррогатные ключи редко меняются. Предпочитайте стабильные ключи, чтобы `ON UPDATE` оставался редким.

```sql
CREATE TABLE orders (
    order_id INTEGER PRIMARY KEY,
    customer_id INTEGER NOT NULL,
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id) REFERENCES customers (customer_id)
        ON DELETE RESTRICT
        ON UPDATE CASCADE
);
```

`CASCADE` при удалении удобен и опасен. Удаление одного клиента может убрать все заказы и, если эти таблицы тоже каскадируют, все строки заказов. Используйте `RESTRICT` (или `NO ACTION`), когда история должна остаться. Используйте `CASCADE` для принадлежащих частей, которые не имеют смысла без родителя. Пример: строки заказа принадлежат заказу.

Жёсткое удаление убирает строку. После `COMMIT` строки нет в таблице. Связанные строки следуют действиям внешнего ключа.

Мягкое удаление оставляет строку и помечает её удалённой. Типичные метки: булево `is_deleted` или метка времени `deleted_at`, которая `NULL` для живых строк.

```sql
UPDATE customers
SET deleted_at = CURRENT_TIMESTAMP
WHERE customer_id = 42;

SELECT *
FROM customers
WHERE deleted_at IS NULL;
```

Используйте жёсткое удаление, когда у строки нет юридической или бизнес-ценности после удаления. Используйте мягкое удаление, когда нужно спрятать строку от обычных запросов, но сохранить её для аудита, отмены или истории уникального ключа.

У мягкого удаления есть цена. Каждый запрос, который значит «живые строки», должен фильтровать метку. Уникальные ключи всё ещё видят удалённую строку, если не спроектировать частичный уникальный индекс. «Удалённый» клиент может всё ещё блокировать нового клиента с тем же email.

Не используйте мягкое удаление как резерв. Резерв — копия базы. Мягко удалённая строка всё ещё в живой базе.

Столбцы аудита записывают, когда строка была создана и когда строка последний раз менялась. Это факты о строке, не времена бизнес-событий.

Типичные столбцы: `created_at` (мгновение первой вставки), `updated_at` (мгновение последнего обновления), необязательные `created_by` и `updated_by`.

Храните эти мгновения в UTC. Ставьте `created_at` при вставке. Не меняйте `created_at` при обновлении. Ставьте `updated_at` при вставке и при каждом позже обновлении. Значение столбца по умолчанию «сейчас» помогает `created_at`. Триггер или код приложения должен поддерживать `updated_at`. Одно значение по умолчанию не меняется при `UPDATE`.

Столбцы аудита — не полный журнал аудита. `updated_at` хранит только время последней записи. У заказа есть `placed_at`, `shipped_at` и `cancelled_at` как бизнес-времена. У этих столбцов есть смысл. `updated_at` только говорит, что какой-то столбец изменился.

Не доверяйте часам клиента как единственному источнику, если пользователи могут поставить свои часы. Предпочитайте `CURRENT_TIMESTAMP` (или эквивалент вендора) в СУБД.

## Соглашения об именах

Соглашение об именах — правило команды для имён объектов. СУБД принимает много имён. Читателям нужен один стиль.

Рекомендуемые привычки для этого пути:

- Используйте строчные буквы, цифры и `_`.
- Используйте стиль таблиц в единственном или множественном числе. Выберите один. Этот путь часто использует множественные имена таблиц (`customers`) и речь о сущности в единственном числе (`customer`).
- Называйте первичные ключи `table_id` или `id`. Выберите одно. `customer_id` ясно в соединениях.
- Называйте внешние ключи по ссылочному ключу (`customer_id` в `orders`).
- Называйте индексы `idx_table_columns`.
- Называйте уникальные ограничения `uq_table_columns`.
- Называйте проверки `chk_table_rule`.
- Называйте внешние ключи `fk_table_ref`.

Примеры:

```text
customers.customer_id
orders.customer_id
idx_orders_customer_id
fk_orders_customers
chk_products_price
```

Не используйте пробелы в именах. Не используйте зарезервированные слова (`order`, `user`, `table`) как сырые имена. Если нужно, заключайте имя в кавычки. Имена в кавычках на многих продуктах чувствительны к регистру. Избегайте необходимости кавычек.

Не смешивайте `camelCase` и `snake_case` в одной схеме. Читатели SQL во многих экосистемах ожидают `snake_case`.

Держите имена на английском, если язык команды для кода — английский. Держите имена стабильными. Переименование ломает программы.

Не кодируйте тип в имени (`name_varchar`). Тип живёт в каталоге. Не префиксируйте каждую таблицу именем схемы (`sales_sales_orders`). Схема уже даёт пространство имён таблице.

Задокументируйте соглашение на короткой странице. Следуйте ему в каждом операторе `CREATE`.

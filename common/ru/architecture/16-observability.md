# 16. Наблюдаемость

## Описание

Наблюдаемость — способность объяснить текущее поведение системы по её выходам. Эта тема разбирает журналы, метрики и трассировки; идентификаторы корреляции; методы RED и USE; OpenTelemetry на высоком уровне; панели против оповещений; и усталость от оповещений.

Тема 2 определила наблюдаемость как атрибут качества. Теме 15 нужны меры для SLI. Эта тема показывает сигналы и привычки. Завершите темы 1–15 до этой темы. Проектируйте сигналы вместе с функцией. Не добавляйте их только после первого инцидента.

Используйте один термин для каждого понятия. Журнал — запись события. Метрика — число во времени. Трассировка — путь spans. Идентификатор корреляции соединяет записи. Панель — для людей, которые исследуют. Оповещение — страница, которая требует действия. OpenTelemetry — стандарт телеметрии, не продукт поставщика.

## Журналы, метрики, трассировки

Журналы, метрики и трассировки — три обычных типа сигналов.

Журнал — структурированное событие. Полезный журнал имеет время, уровень, сообщение, имя сервиса и идентификаторы. Предпочитайте структурированные поля (JSON или ключ-значение) свободному тексту. Ограничивайте размер. Не пишите секреты в журналы (тема 14). Не пишите целые тела запросов, если они могут держать персональные данные.

Метрика — число во временном ряду: число запросов, число ошибок, гистограмма задержки, глубина очереди и CPU. Метрики дёшево агрегировать. Они плохо рассказывают уникальную историю. Высокая кардинальность (новый ряд на идентификатор пользователя) может сломать систему метрик (тема 2).

Трассировка — дерево spans для одного запроса через процессы. У каждого span есть имя, времена и атрибуты. Трассировки объясняют, куда ушло время. Вы сэмплируете трассировки, если объём высок. Сэмплирование всё равно должно ловить ошибки.

Используйте все три. Метрики говорят, что доля ошибок выросла. Журналы говорят сообщение ошибки. Трассировки говорят, какой hop был медленным.

Пишите журналы на границе: начало запроса, конец запроса и обработанные отказы. Журналы отладки в горячем цикле заполняют диски и скрывают события.

Хранение — выбор проектирования. Правовые правила могут заставить минимум или максимум (тема 1). Стоимость растёт с объёмом (тема 2).

Не считайте снимки stdout производственной стратегией. Отправляйте журналы в хранилище, которое можете искать.

## Идентификаторы корреляции

Идентификатор корреляции — значение, которое соединяет записи одной единицы работы. Обычные имена: идентификатор запроса, идентификатор трассировки и идентификатор причинности.

Идентификатор запроса помечает один входящий HTTP-вызов. Каждая строка журнала этого вызова повторяет значение. Если API запускает задачу worker, журнал задачи повторяет то же значение или дочернее значение, которое указывает на родителя.

Идентификатор трассировки помечает распределённую трассировку. Идентификаторы span помечают каждый hop. Распространение контекста копирует эти значения через заголовки HTTP или заголовки сообщений (тема 10).

Правила:

- Создайте идентификатор на краю, если клиент не отправил один.
- Принимайте идентификатор клиента только после проверки формата и размера.
- Никогда не кладите секреты в идентификатор.
- Показывайте идентификатор на страницах ошибок, которые операторы могут спросить.
- Кладите идентификатор в сообщения и исходящие вызовы.

Без корреляции нельзя доказать, что почтовый worker обработал тот же заказ, который API принял. Отладка dual write и саги становится угадыванием (темы 10 и 12).

Операторам в 03:00 нужно одно значение для вставки. Обучите команду сначала спрашивать это значение.

Не изобретайте новое имя заголовка, если стандарт, который вы уже используете, определяет одно. OpenTelemetry и многие шлюзы уже определяют заголовки (следующий раздел). Выберите одно соглашение и запишите его.

## Методы RED / USE

RED и USE — два простых метода выбрать метрики.

RED подходит сервисам, ведомым запросами:

- Rate: запросов в секунду
- Errors: неудачных запросов в секунду или доля ошибок
- Duration: распределение задержки

USE подходит ресурсам (CPU, диск, очередь, пул потоков):

- Utilization: доля времени, когда ресурс занят
- Saturation: лишняя работа, которая ждёт (глубина очереди)
- Errors: ошибки устройства или пула

Используйте RED на пути SLI (тема 15). Используйте USE, когда отлаживаете тесный ресурс. Высокая duration при низкой utilization может значить удалённое ожидание. Высокая utilization с растущей saturation означает, что ёмкости нет.

Не собирайте каждую метрику ядра в первый день. Начинайте с RED для пользовательского пути и USE для базы и брокера.

Называйте метрики так, чтобы новый оператор мог угадать смысл. `http_requests_total` с метками `route` и `status` яснее, чем `x1`.

Метки осторожно. Маршрут, метод и статус обычны. Идентификатор пользователя как метка обычно слишком большая кардинальность.

Методы не заменяют трассировки. Они говорят, где открыть трассировку.

## OpenTelemetry (высокий уровень)

OpenTelemetry — набор стандартов и библиотек для трассировок, метрик и журналов. Проект живёт на [https://opentelemetry.io/](https://opentelemetry.io/). Этот раздел на высоком уровне. Это не учебник SDK.

Полезные идеи:

- Общая модель данных для spans, метрик и журналов
- Распространение контекста через границы процессов
- Collector, который может принимать телеметрию и экспортировать её в бэкенд
- Библиотеки инструментирования, которые оборачивают HTTP, gRPC и обычные хранилища

Выборы архитектуры:

- Что вы инструментируете (ваш код и ваш край)
- Что вы сэмплируете
- Где работает collector
- Какой бэкенд хранит трассировки и метрики
- Сколько вы тратите (тема 2)

OpenTelemetry не заменяет нужду в вопросах. Вы всё равно называете вопросы 03:00 (тема 2). Стандарт снижает привязку к поставщику API инструментирования. Поставщик хранения всё равно может привязать данные (тема 19).

Не включайте каждое автоинструментирование на огромном монолите в первый день. Вы утонете в spans. Начинайте со входящего HTTP span и исходящего HTTP или SQL span.

Держите атрибуты ограниченными. Не прикрепляйте полные полезные нагрузки.

Идентификатор корреляции, который совпадает с идентификатором трассировки, упрощает поиск. Выравнивайте поле журнала с контекстом трассировки, когда можете.

Если команда не может запустить collector, более простой стек (структурированные журналы плюс один агент метрик) всё ещё наблюдаемость. Принимайте OpenTelemetry, когда лишние hop оправдывают общий API.

## Панели против оповещений

Панель — экран графиков и таблиц, который читает человек. Оповещение — условие, которое уведомляет человека, когда остаётся истинным.

Панели отвечают «что происходит?» во время обзора или инцидента. Оповещения отвечают «должен ли человек действовать сейчас?»

Хорошие привычки панелей:

- Начинайте с RED для пользовательского пути
- Показывайте долю ошибок, задержку и насыщение
- Связывайте с журналами и трассировками с тем же диапазоном времени
- Держите один экран для основного пути

Хорошие привычки оповещений:

- Оповещайте о симптомах, которые чувствуют пользователи, или о границе, которая предсказывает боль пользователя
- Требуйте длительность (не один всплеск)
- Назовите следующий шаг в тексте оповещения
- Вызывайте человека только когда этот человек может действовать

График без владельца — украшение. Оповещение без runbook — шум.

Не оповещайте на каждой линии панели. Этот путь вызывает усталость от оповещений (следующий раздел).

Оповещения сжигания SLO (тема 15) часто лучше сырых оповещений CPU. CPU может быть высоким, пока пользователям хорошо. Пользователи могут быть в боли, пока CPU низкий.

Статическим порогам нужен обзор, когда нагрузка меняется. Фиксированное оповещение «100 запросов в секунду» может срабатывать каждую экзаменационную неделю и молчать летом.

## Усталость от оповещений

Усталость от оповещений — состояние, когда люди игнорируют оповещения, потому что слишком много оповещений бесполезны. Система всё равно вызывает. Люди перестают доверять вызову.

Причины:

- Оповещения на шумных метриках
- Нет длительности
- Дублирующие оповещения на один отказ
- Оповещения, которые сбрасываются и срабатывают в цикле
- Оповещения, на которые никто не может действовать
- Отсутствующее владение

Эффекты:

- Медленный ответ на настоящий инцидент
- Тихое отключение оповещений
- Потеря цикла бюджета ошибок (тема 15)

Ремонты:

- Удаляйте или понижайте оповещения, которым не нужен был человек за последние N недель
- Группируйте оповещения, которые делят одну причину
- Используйте каналы предупреждений для медленных трендов и вызовы для видимых пользователю разрывов
- Настраивайте пороги после смены сезона
- Напишите привычку еженедельного обзора оповещений

Маленькая команда может поддерживать маленький набор вызовов. Запишите максимум. Пример: пять вызывающих оповещений для студенческого магазина. Всё остальное — панель или тикет.

Ночные вызовы нуждаются в более высокой планке, чем будничные тикеты. Защищайте сон. Усталые операторы вызывают дефекты.

Не добавляйте оповещение как сувенир инцидента без условия остановки. Многие команды добавляют оповещения после боли и никогда не убирают их.

Измеряйте усталость: вызовы в неделю, процент, который привёл к действию, и время до подтверждения. Эти числа — качество эксплуатации.

### Вопросы

#### Теоретические вопросы

1. Как журналы, метрики, трассировки и идентификаторы корреляции вместе отвечают на один вопрос 03:00?
2. Как RED и USE выбирают метрики без случайного списка покупок?
3. Что стандартизирует OpenTelemetry, и что вы всё равно должны решить?
4. Как панели, оповещения и усталость контролируют ту же телеметрию разными способами?
5. Почему этот путь ставит наблюдаемость после SLO, а не только после атрибутов качества?

#### Простые практические задания

1. Напишите одностраничную шпаргалку всех терминов этой темы.
2. Для API списка дел напишите пять полей журнала, три метрики RED, одну метрику USE и одно оповещение словами.
3. Нарисуйте путь запроса с идентификатором корреляции через API и worker.
4. Добавьте в закладки [https://opentelemetry.io/](https://opentelemetry.io/). Напишите одно предложение о том, когда вы его открываете.

#### Средние практические задания

1. Напишите двухстраничное резюме наблюдаемости для кампусного магазина: сигналы, идентификаторы, панели, оповещения и потолок усталости.
2. Возьмите проект товарища по команде, который только говорит «мы добавим ELK и Grafana». Перепишите его как вопросы, сигналы и владельцев.
3. Сопоставьте темы 2, 12 и 15 с одним путём оформления. Напишите SLI и три сигнала, которые его доказывают.

#### Сложные практические задания

1. Напишите tabletop (60 минут), который использует только телеметрию, чтобы найти медленный hop платежа. Включите идентификаторы и графики RED.
2. Прочитайте публичный обзор наблюдаемости OpenTelemetry или SRE. Напишите десять предложений, которые вы добавили бы в командный стандарт. Не копируйте длинные отрывки.

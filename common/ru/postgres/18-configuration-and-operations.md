# 18. Конфигурация и эксплуатация

## Описание

Эта тема показывает ежедневную эксплуатацию PostgreSQL 16 и PostgreSQL 17. Вы узнаёте настройки памяти, checkpoint, журналирование операторов, представления активности и блокировок, обновления мажорной версии и инциденты полного диска.

Сначала завершите тему 17. Вы умеете именовать сессии через `application_name`. Завершите эту тему до применения шаблонов производительности.

Используйте один термин для каждого понятия. Настройка — имя, которое используют `SHOW` и `postgresql.conf`. `shared_buffers` — кэш страниц сервера внутри PostgreSQL. `work_mem` — память на один шаг сортировки или хеша. Checkpoint — сброс грязных страниц и позиция WAL. `pg_stat_activity` — представление живых сессий. Мажорное обновление меняет первое число версии. Этот справочник рассчитан на PostgreSQL 16 и PostgreSQL 17.

## Память: `shared_buffers`, `work_mem`, `maintenance_work_mem`, `effective_cache_size`

PostgreSQL использует несколько настроек памяти. Это не одна ручка «процент RAM».

**`shared_buffers`** — общий кэш страниц таблиц и индексов. Частый старт — около 25 процентов RAM машины на выделенном хосте, с верхней границей, которую измеряете. Кэш операционной системы всё равно держит страницы. Не ставьте `shared_buffers` почти на всю RAM.

**`work_mem`** — лимит на одну операцию сортировки или хеша в одном шаге запроса. Запрос может использовать несколько шагов. Много сессий могут сортировать одновременно. Хост с `max_connections = 200` и `work_mem = 100MB` может запросить больше RAM, чем есть у машины. Начинайте низко (например `8MB` или `16MB`). Поднимайте для известного тяжёлого запроса в этой сессии: `SET work_mem = '64MB';`.

**`maintenance_work_mem`** — для `VACUUM`, `CREATE INDEX` и `ALTER TABLE`. Одна команда обслуживания использует этот бюджет. Можно задать выше `work_mem` (например `256MB` или больше на большом хосте), потому что мало заданий обслуживания идут сразу.

**`effective_cache_size`** — подсказка планировщику. Это не выделение. Задайте примерно RAM, которую ждёте для кэша ОС плюс `shared_buffers` (часто 50–75 процентов RAM на выделенном хосте). Неверное значение не выделяет RAM. Может сменить, выберет ли планировщик индекс.

```sql
SHOW shared_buffers;
SHOW work_mem;
SHOW maintenance_work_mem;
SHOW effective_cache_size;
```

Тема 9 представила `work_mem` для сортировок и хешей. Этот раздел — взгляд эксплуатации.

Не копируйте блог, который ставит `shared_buffers = 80%` и `work_mem = 1GB` на общем ноутбуке. Не поднимайте `work_mem` глобально, чтобы исправить один отчёт. Не считайте `effective_cache_size` резервом памяти.

Официально: [https://www.postgresql.org/docs/17/runtime-config-resource.html](https://www.postgresql.org/docs/17/runtime-config-resource.html).

## Checkpoint и `max_wal_size`

Checkpoint сбрасывает грязные буферы и записывает позицию. Восстановление стартует с последнего checkpoint и затем воспроизводит WAL. Слишком частые checkpoint дают лишние записи. Слишком долгие checkpoint дают рост WAL и более долгое восстановление после сбоя.

**`max_wal_size`** — цель роста WAL между checkpoint. Когда WAL растёт к этому размеру, сервер начинает checkpoint. **`min_wal_size`** — пол для переработанных файлов WAL.

**`checkpoint_timeout`** — лимит времени между checkpoint (по умолчанию часто 5 минут). Сервер делает checkpoint раньше из лимита времени и триггера размера WAL.

```sql
SHOW max_wal_size;
SHOW min_wal_size;
SHOW checkpoint_timeout;
SELECT * FROM pg_stat_bgwriter;
```

`pg_stat_bgwriter` и в PostgreSQL 17 смежные представления I/O помогают видеть активность checkpoint. У PostgreSQL 16 также есть `pg_stat_io` для статистики I/O. Используйте представления, которые поставляет ваша мажорная версия.

`CHECKPOINT` запускает checkpoint сейчас. Используйте в лабораториях. Не запускайте в цикле в продакшене.

Реплика и `archive_command` должны успевать. Большой `max_wal_size` может быть нормален, если диски быстрые и время восстановления приемлемо.

Не ставьте `max_wal_size` крошечным, чтобы «быть в безопасности». Увеличиваете усиление записи. Не игнорируйте всплески checkpoint после массового `COPY`. Массовые загрузки темы 17 создают грязные страницы.

Официально: [https://www.postgresql.org/docs/17/wal-configuration.html](https://www.postgresql.org/docs/17/wal-configuration.html).

## Журналирование: `log_min_duration_statement`

PostgreSQL может писать строку журнала для каждого оператора, который работает не меньше N миллисекунд.

```sql
SHOW log_min_duration_statement;
-- session test
SET log_min_duration_statement = 200;
```

`0` журналирует каждый оператор. `-1` выключает возможность (частое умолчание). Глобальный `0` на занятом сервере заполняет диск и стоит I/O.

Смежные настройки (обзор):

- `logging_collector` — собирать журналы в файлы
- `log_directory` и `log_filename` — куда идут файлы
- `log_line_prefix` — добавить время, пользователя, `application_name`, pid
- `log_checkpoints` — журналировать старт и стоп checkpoint
- `log_lock_waits` — журналировать ожидания дольше `deadlock_timeout`
- `log_connections` / `log_disconnections` — полезно в лабораториях; шумно в продакшене

`SET` в сессии достаточно, чтобы учиться. `ALTER SYSTEM` плюс `SELECT pg_reload_conf();` меняет работающий сервер, когда настройка перезагружаемая.

Читайте журналы, чтобы найти медленный SQL. Затем используйте `EXPLAIN ANALYZE` (тема 9) и `pg_stat_statements` (ниже). Не гадайте.

Не оставляйте `log_min_duration_statement = 0` в продакшене. Не журналируйте пароли. Клиентские операторы `SET` могут появиться в журналах; держите секреты вне текста SQL.

Официально: [https://www.postgresql.org/docs/17/runtime-config-logging.html](https://www.postgresql.org/docs/17/runtime-config-logging.html).

## `pg_stat_activity`, блокировки, `pg_stat_statements`

**`pg_stat_activity`** показывает одну строку на backend. Полезные столбцы: `pid`, `usename`, `application_name`, `client_addr`, `state`, `wait_event_type`, `wait_event`, `query`, `backend_xid`, `xact_start`, `query_start`.

```sql
SELECT pid, usename, application_name, state, wait_event, left(query, 80)
FROM pg_stat_activity
WHERE datname = current_database()
  AND pid <> pg_backend_pid();
```

Значения `state` включают `active` и `idle in transaction`. Долгий `idle in transaction` блокирует vacuum (тема 11).

**Блокировки:** `pg_locks`, соединённый с `pg_stat_activity`, показывает, кто ждёт. `log_lock_waits` пишет строку журнала. `pg_blocking_pids(pid)` перечисляет блокирующих.

```sql
SELECT * FROM pg_blocking_pids(12345);
```

**`pg_stat_statements`** (тема 9 и тема 13) агрегирует время по нормализованному запросу. Нужны `shared_preload_libraries` и `CREATE EXTENSION`.

```sql
SELECT calls, round(total_exec_time::numeric, 1) AS total_ms, left(query, 80)
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

`pg_stat_statements_reset()` очищает итоги. Используйте после теста, не случайно в продакшене.

`pg_cancel_backend(pid)` просит запрос остановиться. `pg_terminate_backend(pid)` завершает сессию. Сначала предпочитайте отмену. Не завершайте нужного рабочего autovacuum без причины (wraparound темы 11).

Не запускайте `SELECT * FROM pg_stat_activity` в тесном цикле в приложении. Не выдавайте эти представления всем, если они раскрывают текст SQL с секретами.

Официально: [https://www.postgresql.org/docs/17/monitoring-stats.html](https://www.postgresql.org/docs/17/monitoring-stats.html).

## Обновление мажорных версий (`pg_upgrade`, дамп/восстановление, логическая)

Мажорное обновление (16 на 17) меняет каталоги. Нельзя запустить бинарники 17 на каталоге данных 16.

Три поддерживаемых пути:

1. **`pg_upgrade`** — преобразует каталог данных на месте или со ссылками. Быстро. Нужны оба набора бинарников. Сначала запускайте `--check`. Читайте страницу `pg_upgrade` 17 про `--link`, `--clone` и `--copy`.
2. **дамп и восстановление** — `pg_dumpall` или `pg_dump` каждой базы, новый `initdb`, восстановление. Медленно. Просто. Хорошо, когда меняете машины или кодировку.
3. **логическая репликация** — новый кластер 17 как подписчик, затем переключение записей. Больше движущихся частей. Полезно для малого простоя. Ограничения темы 16 всё равно применяются.

Минорные обновления (16.x на 16.y) не используют `pg_upgrade`. Устанавливаете новые бинарники и перезапускаете. Тема 1 это покрыла.

После любого мажорного обновления:

- `ANALYZE` нового кластера (или используйте `vacuumdb --analyze-in-stages`)
- запустите `REINDEX`, если заметки говорят (изменения collation или glibc)
- проверьте расширения
- обновите `shared_preload_libraries` и `postgresql.conf` для новых имён
- проверьте приложение на 17 до удаления 16

У PostgreSQL 16 и 17 есть раздел «Migration» в заметках о выпуске. Читайте его.

Не пропускайте `--check`. Не обновляйте продакшен до теста восстановления. Не разрабатывайте на 17 и не выкатывайте на 16 без списка возможностей.

Официально: [https://www.postgresql.org/docs/17/pgupgrade.html](https://www.postgresql.org/docs/17/pgupgrade.html), [https://www.postgresql.org/docs/17/upgrading.html](https://www.postgresql.org/docs/17/upgrading.html).

## Инциденты заполнения диска

Когда диск, который держит `PGDATA` или `pg_wal`, полон, PostgreSQL может остановить записи, запаниковать или не стартовать. Это продакшен-авария. Тема 21 просит runbook. Этот раздел — техническая картина.

Частые наполнители:

- рост WAL: падающий archive_command, слот репликации, держащий WAL, `max_wal_size` плюс застрявший checkpoint
- раздутие: тема 11
- журналы: `log_min_duration_statement = 0`
- `COPY` или `CREATE INDEX` на том же томе
- забытое назначение `pg_basebackup` на том же диске

Первые взгляды (если сервер ещё принимает подключение суперпользователя):

```sql
SELECT pg_size_pretty(pg_database_size(current_database()));
SELECT slot_name, slot_type, active, pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) AS retained
FROM pg_replication_slots;
SELECT * FROM pg_stat_archiver;
```

На хосте найдите, какой каталог полон (`du` на `pg_wal`, `log`, base). Освобождайте место так, чтобы не уничтожить единственную копию WAL, которая нужна реплике.

Безопасные идеи (обзор):

- переместить или сжать старые файлы журнала, если ими владеет `logging_collector`
- удалить одноразовую базу или таблицу только если принимаете потерю данных
- удалить устаревший слот репликации, который доказали неиспользуемым
- исправить `archive_command`, чтобы WAL мог перерабатываться

Небезопасные идеи:

- удалять случайные файлы в `pg_wal`
- `rm` каталога данных
- `VACUUM FULL`, когда нет дополнительного места (нужна копия)

Если сервер лежит, освободите место на уровне ОС, затем запустите PostgreSQL и следуйте журналам. Восстанавливайте из резервной копии, если файлы пропали.

Не ждите 100 процентов диска в продакшене без алерта. Не удаляйте WAL потому что вики сказала «старые файлы». Тема 16 объяснила, почему WAL важен.

#### Средние практические задания

## Обзор темы

Эти вопросы не повторяют вопросы разделов выше. Они покрывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Как `work_mem`, checkpoint и массовый `COPY` взаимодействуют на занятом хосте?
2. Как журналы, `pg_stat_activity` и `pg_stat_statements` образуют один путь отладки?
3. Почему мажорное обновление — также обзор памяти и расширений?
4. Как упавший архив и высокий `max_wal_size` могут закончиться инцидентом диска?
5. Коллега ставит `shared_buffers` на 90 процентов RAM и `log_min_duration_statement` в `0`. Какие факты из этой темы вы используете в ответе?

#### Простые практические задания

1. `SHOW` восемь настроек из этой темы (память, WAL, журналирование). Сохраните список.
2. Напишите шпаргалку: четыре имени памяти, пара checkpoint, медленный журнал, три представления, три пути обновления, наполнители диска.
3. Выберите `pg_stat_activity` и `pg_database_size`.
4. Откройте страницы runtime-config 16 и 17. Добавьте в закладки resource, WAL и logging.

#### Средние практические задания

1. Напишите еженедельный операционный чеклист: `SHOW` памяти, статистика checkpoint, образец медленного журнала, верх `pg_stat_statements`, размеры слотов, свободный диск.
2. Сымитируйте ожидание блокировки и медленный оператор. Найдите оба в представлениях или журналах.
3. Набросайте план обновления 16-на-17, который включает `shared_preload_libraries` и `ANALYZE`.

#### Сложные практические задания

1. Соберите лабораторный скрипт, который печатает: версию, четыре настройки памяти, `max_wal_size`, слоты репликации, пять верхних операторов, размер базы.
2. Сопоставьте эту тему с официальными главами: конфигурация ресурсов, WAL, журналирование, мониторинг, обновление. Добавьте один факт `pg_stat_io` для 16 или 17, которого в этой теме не было.

# 11. Производительность

## Описание

Эта тема показывает, как измерять и улучшать скорость MongoDB. Вы читаете `explain`. Сравниваете `COLLSCAN` и `IXSCAN`. Держите рабочий набор в ОЗУ. Режете нагрузку проекцией. Используете покрытые запросы. Используете профайлер и Atlas Performance Advisor.

Сначала завершите индексы, агрегацию и запросы.

Используйте один термин для каждого понятия. **Сканирование коллекции** (`COLLSCAN`) читает каждый документ. **Сканирование индекса** (`IXSCAN`) читает индекс. **Рабочий набор** — данные и индексы, которые приложение часто использует. **Покрытый запрос** — запрос, на который сервер отвечает только из индекса.

Не настраивайте наугад. Измеряйте через `explain` и на реальной нагрузке.

## `explain("executionStats")`

`explain` показывает, как сервер планирует выполнить find или агрегацию. Режим `executionStats` выполняет план и сообщает счётчики и время.

```javascript
db.orders.find({ userId: "u1" }).explain("executionStats")
```

Полезные поля:

- `queryPlanner.winningPlan` — выбранный план
- `executionStats.nReturned` — возвращённые документы
- `executionStats.totalDocsExamined` — прочитанные документы
- `executionStats.totalKeysExamined` — прочитанные ключи индекса
- `executionStats.executionTimeMillis` — время этого запуска

Режимы:

- `queryPlanner` — только план, без счётчиков выполнения
- `executionStats` — план плюс счётчики этого выполнения
- `allPlansExecution` — также показывает отклонённые планы

Используйте `executionStats`, когда учитесь. Запуск делает настоящую работу. Не запускайте тяжёлый `explain("executionStats")` на огромной коллекции в промышленности без осторожности.

Хороший знак: `nReturned` близко к `totalDocsExamined` для избирательного фильтра. Плохой знак: просматриваете 1 000 000 документов, чтобы вернуть 10.

Агрегация использует `db.orders.explain("executionStats").aggregate([ ... ])` или помощник, который документирует ваша версия.

`explain` — не нагрузочный тест. Один вызов на тёплом кэше — не ваш пик. Используйте его, чтобы увидеть форму плана.

Читайте страницу explain для вашей основной версии. Имена полей могут меняться.

## COLLSCAN против IXSCAN

`COLLSCAN` значит, что сервер читает коллекцию. Он не использует индекс для этого фильтра (или выбирает не использовать).

`IXSCAN` значит, что сервер читает индекс. Этап **`FETCH`** затем загружает полные документы, когда индекс не держит все нужные поля.

Типичный победивший план хорошего find:

```text
IXSCAN → FETCH → PROJECTION (optional)
```

Типичный плохой план:

```text
COLLSCAN
```

`COLLSCAN` приемлем на крошечной коллекции. `COLLSCAN` на миллионах документов — проблема для пути API.

Существующего индекса недостаточно. Фильтр должен совпадать с индексом (включая правило префикса составного индекса из темы индексов). Функция на поле, плохой `$or` или ведущий `$not` могут заблокировать индекс.

Сортировка может использовать индекс или добавить блокирующий `SORT`. Большой `SORT`, который не помещается в память, падает, пока не разрешите диск (чаще в агрегации).

`explain` показывает `stage: "COLLSCAN"` или `stage: "IXSCAN"` в победившем плане. Начните оттуда.

Не добавляйте десять индексов, чтобы убрать один `COLLSCAN`, без проверки стоимости записи. Сначала чините форму запроса.

Нагрузка с **тяжёлой записью** вставляет или обновляет много документов. Лишние индексы замедляют записи. Нагрузка с **тяжёлым чтением** запускает много find. Индексы, проекция и рабочий набор в ОЗУ важнее. Измерьте, затем меняйте одно.

## Рабочий набор, проекция и покрытые запросы

**Рабочий набор** — документы и страницы индексов, которые приложение часто читает и пишет. MongoDB (WiredTiger) держит столько, сколько может, в **кэше WiredTiger**. Операционная система тоже кэширует страницы файлов.

Если рабочий набор помещается в ОЗУ, большинство чтений избегает медленного диска. Если рабочий набор больше ОЗУ, сервер подгружает данные туда-сюда. Задержка растёт. Растут **page fault** и вытеснение кэша.

Вместить рабочий набор:

- Держите документы маленькими
- Индексируйте только то, что запрашиваете
- Архивируйте холодные данные
- Добавьте ОЗУ или шарды, когда горячие данные действительно велики

У размера кэша есть значение по умолчанию на самостоятельно управляемом `mongod` (большая доля ОЗУ с зарезервированным объёмом). Atlas задаёт кэш от уровня кластера. Не ставьте кэш на 100% ОЗУ. Операционной системе и соединениям нужна память.

Рабочий набор — не то же самое, что полный размер данных. Коллекция 2 ТБ может иметь горячий набор 20 ГБ.

Не покупайте шард только потому что полный диск велик. Сначала измерьте горячий набор.

**Проекция** выбирает поля в find или в `$project`. Меньший документ в сети быстрее. Приложение также разбирает меньше данных.

```javascript
db.orders.find({ userId: "u1" }, { total: 1, status: 1 })
```

Включайте поля, которые нужны вызывающему. Исключайте большие неиспользуемые поля. Проекция не всегда избегает `FETCH`. Сервер может всё равно загрузить полный документ из хранилища, затем отбросить поля. Проекция всё равно помогает сети и клиенту.

Не возвращайте полный документ в API списка «на потом». Добавьте конечную точку деталей.

`find({}, {})` без лимита всё равно неограничен. Проекция не заменяет `limit`.

Ставьте `$match` первым в агрегации. Проецируйте рано, когда отбрасываете большие поля до `$group` или `$lookup`.

**Покрытый запрос** использует индекс, который содержит каждое поле фильтра, сортировки и проекции. Сервер не делает `FETCH` полного документа.

`explain` показывает `IXSCAN`, затем проекцию или счёт, без `FETCH`. `totalDocsExamined` во многих покрытых планах равен `0`.

Требования (типичные):

- Все поля фильтра в индексе
- Все проецируемые поля в индексе
- Проекция исключает поля, которых нет в индексе
- Поля вне индекса не нужны

Пример:

```javascript
db.orders.createIndex({ userId: 1, status: 1 })
db.orders.find({ userId: "u1" }, { _id: 0, userId: 1, status: 1 })
```

`_id` есть в документе и включён по умолчанию. Если `_id` нет в индексе, исключите `_id` в проекции или добавьте `_id` в индекс.

Покрытые запросы помогают горячим путям чтения с малым набором полей. Они не помогают, когда нужен весь документ.

Мультиключевые индексы (массивы) часто не покрывают так, как ожидаете. Читайте текущие лимиты.

Не добавляйте огромный составной индекс только чтобы покрыть редкий запрос.

## Профайлер и Atlas Performance Advisor

**Профайлер базы** записывает медленные операции в `system.profile`. Задаёте уровень и порог slow-ms.

```javascript
db.setProfilingLevel(1, { slowms: 100 })
```

Уровень `0` — выкл. Уровень `1` записывает медленные операции. Уровень `2` записывает все операции (тяжело). Не оставляйте уровень `2` на занятой промышленной базе.

Читать записи:

```javascript
db.system.profile.find().sort({ ts: -1 }).limit(5)
```

Каждая запись показывает команду, миллисекунды и резюме плана. Используйте, чтобы найти `COLLSCAN` и долгие блокировки.

**Atlas Performance Advisor** читает медленные логи и предлагает индексы. Это помощник. Всё равно проверяйте через `explain`. Предложенный индекс может быть дубликатом или вредить записям.

Atlas также показывает:

- Логи медленных запросов
- Производительность в реальном времени
- Query Insights на некоторых уровнях

`serverStatus` и `currentOp` помогают на самостоятельно управляемых серверах. `db.currentOp()` показывает операции, которые идут сейчас.

Логируйте медленные операции даже когда профайлер выключен (`operationProfiling.slowOpThresholdMs` или значение Atlas по умолчанию). Лога многим командам достаточно.

Не добавляйте каждый индекс Advisor в один день. Добавьте один. Измерьте. Оставьте или удалите.

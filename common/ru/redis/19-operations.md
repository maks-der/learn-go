# 19. Эксплуатация

## Описание

Эксплуатация держит Redis верным и доступным после того, как приложение работает. Эта тема покрывает конфигурацию времени выполнения, заполнение диска, всплеск памяти `BGSAVE`, обновления, живые метрики и файловые резервные копии.

Сначала завершите тему 9 (персистентность), тему 10 (репликация), тему 16 (память) и тему 17 (безопасность).

Используйте один термин для каждого понятия. Конфигурация времени выполнения — настройка, которую `CONFIG SET` меняет в живом процессе. Заполнение диска — полный том для RDB или AOF. Copy-on-write (COW) — лишнее ОЗУ во время fork. Наблюдаемость — набор метрик, которые говорят, здоров ли Redis. Резервная копия — копия RDB или AOF, которая живёт вне хоста Redis.

## `CONFIG GET` / `SET` (осторожно)

`CONFIG GET pattern` читает живые настройки. `CONFIG SET name value` меняет настройку до перезапуска, если не сохраните.

```text
CONFIG GET maxmemory
CONFIG SET maxmemory 256mb
CONFIG REWRITE
```

`CONFIG REWRITE` пишет текущие настройки в `redis.conf` (или файл конфигурации, который загрузил Redis). Без перезаписи или правки файла перезапуск может восстановить старые значения.

Некоторые настройки не применяются через `CONFIG SET`. Им нужен перезапуск. Страница команды и комментарии `CONFIG GET` говорят. Примеры часто включают адреса bind, daemonize и некоторые пути файлов TLS. Проверьте версию.

Риски:

- `CONFIG SET` — класс опасных команд (тема 17). Ограничьте ACL.
- Опечатка в `dir` или `dbfilename` может писать файлы не туда.
- Слишком низкий `maxmemory` начинает вытеснение или ошибки записи.
- Смены `appendonly` и `save` меняют окно потери (тема 9).
- Смены `protected-mode` и `requirepass` могут запереть вас или открыть экземпляр.

Предпочитайте тикет изменения, лабораторный тест и `CONFIG GET` до и после. Скопируйте старое значение.

`redis.conf` остаётся источником истины для нового процесса. Документируйте каждый `CONFIG SET`, который не перезаписываете.

Не экспериментируйте с `CONFIG SET` на долговечном промышленном primary.

## Заполнение диска персистентности

RDB и AOF пишут файлы под `dir`. Если том полон, `BGSAVE` падает, добавление AOF падает или перезапись падает. Redis может остановить записи (`stop-writes-on-bgsave-error`, поведение ошибки AOF). Кэш тогда может отклонять `SET`. Долговечный Redis может отказаться терять данные.

```text
CONFIG GET dir
INFO persistence
```

Смотрите использованный диск, число inode и строки журнала Redis про ошибки записи.

Перезапись AOF и запись RDB нуждаются в лишнем месте. Перезаписи может понадобиться место для нового файла рядом со старым. Том на 95 процентах может упасть даже если финальный файл поместился бы.

Поля `INFO persistence` вроде `rdb_last_bgsave_status` и `aof_last_write_status` (имена варьируются) говорят последний результат.

Если диск полон:

- Освободите место (старые дампы, журналы) в лаборатории или с известной политикой резервных копий
- Не удаляйте единственный живой AOF без плана
- Исправьте размер тома до повышения трафика

Репликация не заменяет полный диск на primary. Primary всё равно должен писать, если персистентность включена.

Не кладите `dir` на крошечный overlay-диск контейнера без монтирования.

## Fork / copy-on-write во время `BGSAVE` (всплеск памяти)

Тема 9 объяснила `BGSAVE`. Родитель делает fork дочернего. Дочерний пишет RDB. Операционная система делит страницы, пока родитель не пишет страницу. Затем COW копирует эту страницу. Много записей во время долгого сохранения могут поднять RSS почти до двух копий набора.

Эффекты:

- Хост может уйти в swap или Linux OOM killer может остановить Redis
- Задержка может вырасти во время fork на некоторых ядрах
- Перезапись AOF (`BGREWRITEAOF`) тоже делает fork

Оставьте свободное ОЗУ для пика. Частое правило планирования — держать запас на полную лишнюю копию, если скорость записи высока. Измеряйте RSS во время сохранения. Не угадывайте только из `used_memory`.

```text
INFO memory
INFO persistence
```

Смотрите `used_memory_rss`, пока `rdb_bgsave_in_progress` равен `1`.

Заметки Linux `overcommit_memory` и `vm.overcommit_memory` появляются в предупреждениях Redis. Ошибка `fork` в журнале значит ядро отказало дочернему. Исправьте ОЗУ, overcommit или размер набора.

`SAVE` не делает fork. `SAVE` блокирует основной поток. Не используйте `SAVE` в промышленной среде.

Не планируйте тяжёлую нагрузку записи и ручной `BGSAVE` в одно время на тесном хосте.

## Обновления

Обновление меняет двоичный файл или образ Redis. Планируйте его.

Типичный путь сначала-реплика для primary плюс реплики:

1. Обновите реплику. Проверьте репликацию и `INFO`.
2. Обновите остальные реплики.
3. Переключите (Sentinel или Cluster), чтобы обновлённая реплика стала primary.
4. Обновите старый primary (теперь реплика).
5. Проверьте приложение против нового поведения команд.

Читайте заметки о выпуске. Некоторые версии меняют значения по умолчанию (ACL, AOF, имена реплик). Некоторые команды меняются.

Модули: обновляйте Redis Stack как пакет. Проверяйте совместимость модулей (тема 18).

Конфигурация: новые версии добавляют настройки. Делайте diff `redis.conf`. Не копируйте старый файл вслепую, если новый образ ждёт новые включения.

Клиенты: обновляйте клиентов после того, как знаете версию сервера, или оставайтесь совместимыми. Проверяйте конвейеры, Cluster и AUTH.

Откат: держите предыдущий образ и резервную копию до обновления. Смена формата данных может усложнить откат. Читайте заметки.

Не обновляйте единственный primary на месте во время пика без реплики и резервной копии.

У Kubernetes и облачных вендоров свои процедуры прокрутки. Следуйте им плюс заметки Redis.

## Наблюдаемость: доля попаданий, вытеснения, подключённые клиенты, заблокированные клиенты

Нельзя эксплуатировать Redis только из `PING`. Собирайте `INFO` (или панель вендора) с интервалом.

Доля попаданий (кэш):

```text
# conceptual
hit_rate = keyspace_hits / (keyspace_hits + keyspace_misses)
```

Низкая доля попаданий значит кэш не окупается, или TTL слишком короткие, или ключи не совпадают. Высокой доли попаданий недостаточно, если значение устарело (проблема приложения).

Вытеснения: рост `evicted_keys` значит `maxmemory` и политика сбрасывают ключи (тема 4). Для кэша некоторое вытеснение может быть нормальным. Для долговечного Redis вытеснение — инцидент.

Подключённые клиенты: `connected_clients` против `maxclients`. Утечка в пуле приложения (тема 12) видна здесь. Внезапное падение может значить обрыв сети или перезапуск.

Заблокированные клиенты: `blocked_clients` считает клиентов в блокирующих командах (`BRPOP`, `XREAD BLOCK`, `BZPOPMIN`). Число выше нуля может быть нормальным. Число, равное всем работникам, может значить, что они ждут пустую очередь.

Другие полезные поля:

- `instantaneous_ops_per_sec`
- `rejected_connections`
- `expired_keys` против `evicted_keys`
- `connected_slaves` / число реплик
- `rdb_last_bgsave_status`
- `used_memory` против `maxmemory`
- `latest_fork_usec`

Оповещайте о: вытеснении на долговечном экземпляре, неудачных сохранениях, `rejected_connections`, памяти около `maxmemory`, лаге репликации (тема 10), истечении сертификата (тема 17).

Не оповещайте о каждом `blocked_clients` > 0, если используете блокирующие чтения.

## Резервная копия RDB/AOF

Реплика — не резервная копия. Реплика может удалить данные, если primary удаляет. Резервная копия — копия файла, которую можно восстановить после плохого `FLUSHALL`, плохого деплоя или потерянного хоста.

Шаги (форма):

1. Убедитесь, что персистентность включена, если нужна история.
2. Вызовите `BGSAVE` или ждите запланированного сохранения. Ждите, пока `rdb_bgsave_in_progress` станет `0` и статус OK.
3. Скопируйте файл RDB с хоста (объектное хранилище, другой диск).
4. Сделайте контрольную сумму копии.
5. Если AOF — источник истины, скопируйте AOF после перезаписи или следуйте официальным заметкам на момент времени для вашей версии.
6. Проверьте восстановление на лабораторном экземпляре.

```text
CONFIG GET dir
CONFIG GET dbfilename
CONFIG GET appendfilename
```

Шифруйте резервные копии, если они содержат персональные данные. Ограничьте, кто может читать корзину.

Расписание: почасовое или ежедневное зависит от окна потери. Кэшу может не нужна резервная копия. Хранилищу сессий может нужно короткое окно. Долговечному Redis нужно проверенное восстановление.

Cluster: резервируйте каждый primary (или используйте снимок вендора). Слоты живут на разных узлах.

Не копируйте файлы только пока идёт `BGSAVE`, если не знаете, что файл согласован. Предпочитайте ждать завершения.

`DEBUG RELOAD` и похожие — лабораторные инструменты. Восстанавливайте запуском Redis со скопированным файлом в `dir` на пустой лаборатории.

## Обзор темы

Эти вопросы не повторяют вопросы из разделов выше. Они охватывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Как `CONFIG SET`, заполнение диска и COW взаимодействуют во время одного `BGSAVE` на маленьком хосте?
2. Какие метрики говорят «кэш в порядке» против «долговечный Redis теряет данные»?
3. Почему порядок обновления и резервная копия существуют в одном окне изменения?
4. Что должно быть верно до того, как считать файл RDB восстанавливаемым?
5. Какие задачи эксплуатации требуют прав ACL ops, которых у приложения не должно быть?

#### Простые практические задания

1. Напишите шпаргалку: `CONFIG GET/SET/REWRITE`, `INFO persistence`, `INFO memory`, `INFO stats`, `BGSAVE`, копирование RDB.
2. Экспортируйте `INFO` и выделите счётчики попаданий, вытеснения, клиенты, статус последнего сохранения, RSS.
3. Нарисуйте ОЗУ (использованное + запас COW) и диск (RDB + место перезаписи).
4. Напишите пять правил эксплуатации для лаборатории.

#### Средние практические задания

1. Запустите мини-учение: смените безвредную конфигурацию, `BGSAVE`, скопируйте RDB, восстановите на другом порту, прочитайте ключ. Запишите времена.
2. Напишите одностраничник дежурства: первые 10 минут для высокой памяти, полного диска, неудачного сохранения, слишком многих клиентов.
3. Сопоставьте лаг темы 10 и slow log темы 16 с панелью этой темы.

#### Сложные практические задания

1. Напишите полный runbook эксплуатации Redis: конфигурация, диск, COW, обновление, метрики, резервная копия, контакты безопасности.
2. Сравните автоматическую резервную копию вендора с вашей процедурой копирования файлов. Запишите, что всё ещё проверяете сами (восстановление).

# 13. Эволюция и практика

## Описание

Эта тема превращает путь в привычку. Вы обзорно изучаете backend-for-frontend (BFF) и серверный рендеринг против одностраничных приложений. Вы узнаёте, почему порождение событий и CRDT редко значение по умолчанию. Вы пишете ADR и контекстную диаграмму C4. Вы делите монолит только после настоящей боли границы. Вы читаете *Designing Data-Intensive Applications* (DDIA) и пишете один разбор инцидента в неделю.

Файл `architecture.topics.md` также перечисляет предложенный порядок практики из десяти шагов. Используйте этот список после завершения этих разделов. Завершите темы 1–12 до того, как считать эту тему сделанной. Сочетайте этот путь с `db.topics.md`, `net.topics.md` и языковым путём. Архитектура остаётся компромиссами (тема 1).

Используйте один термин для каждого понятия. BFF — бэкенд, который обслуживает один тип клиента. SSR рендерит HTML на сервере. SPA рендерит в браузере после загрузки скрипта. Порождение событий — не «мы используем события». CRDT — не общее слияние для каждой формы. Разбор инцидента — документ обучения после инцидента.

## BFF, SSR против SPA (обзор)

Этот раздел — обзор. Клиенты — часть системы (тема 1). Они держат состояние, кэшируют и падают на плохих сетях (`net.topics.md`).

BFF (бэкенд для фронтенда) — процесс на стороне сервера, который существует, чтобы обслуживать один тип клиента. Веб-BFF формирует данные для браузера. Мобильный BFF формирует данные для мобильного приложения. Каждый BFF говорит с сервисами-владельцами или с модульным монолитом (темы 3 и 9).

BFF может агрегировать два или три чтения в один вызов клиента, скрыть внутренние имена сервисов, применить детали аутентификации конкретного клиента и обрезать поля, которые клиенту не нужны (тема 10).

BFF не должен стать домом доменных правил. Цена и политика выдачи остаются у владельца (темы 3 и 4). Если каждое новое бизнес-правило попадает в BFF, вы построили второй монолит на краю.

BFF — родственник шлюза API (тема 9). Шлюз применяет общую краевую политику. BFF применяет форму одного клиента. Не добавляйте BFF для одностраничного студенческого приложения, которое уже говорит с одним API.

Серверный рендеринг (SSR) производит HTML на сервере для запроса. Браузер показывает содержимое без большого клиентского рендера сначала. SSR может помочь первой отрисовке, простым кэшам и клиентам с малым JavaScript.

Одностраничное приложение (SPA) загружает скрипт и затем рендерит в браузере. Позже навигация может остаться на клиенте. SPA может подойти богатым интерактивным инструментам. Оно добавляет публичный пакет JavaScript, более трудную первую отрисовку и более длинное окно совместимости с API (тема 5).

Многие продукты смешивают два: SSR для первой страницы, затем клиентский рендер для следующих действий. Пишите смесь. Согласованность UX — то, что видит человек. Согласованность сервиса — то, в чём согласны хранилища (тема 4). Спиннер, который скрывает отстающего подписчика, — ложь UX, если запись уже провалилась.

Не считайте браузер тонким украшением перед микросервисами. Болтливое SPA против десяти сервисов нуждается в BFF или агрегации шлюза. Модульного монолита с одним JSON API достаточно для многих кампусных приложений.

## Порождение событий и CRDT (редко значение по умолчанию)

Порождение событий хранит источник истины как последовательность событий. Вы перестраиваете состояние воспроизведением. Текущий баланс — проекция. Журнал событий — источник истины (тема 6).

Это не то же, что «публиковать события после записи строки». Этот шаблон — управляемая событиями интеграция (тема 7). Порождение событий меняет модель записи.

Цены порождения событий:

- Нужно версионировать события вечно.
- Нужно проектировать правила повышения версии.
- Удаление и исправление персональных данных становятся трудными (закон, тема 1).
- Проекции отстают. UX должен говорить правду.
- Растут стоимость воспроизведения и хранения.
- Людям нужно обучение.

Когда порождение событий может подойти: жёсткий аудит каждого изменения — продукт, вы уже эксплуатируете журнал событий и можете сформулировать правила удаления и исправления. Когда не подходит: обычное CRUD-приложение кампуса, молодой единый язык (тема 4) или команда из двух человек.

CQRS часто появляется с порождением событий (тема 6). CQRS без порождения событий достаточно для многих разделений чтения/записи. Не начинайте побочный проект на порождении событий, чтобы выглядеть продвинуто. Начните со строки и исходящего ящика (тема 7).

CRDT (бесконфликтный реплицируемый тип данных) — структура данных, которую реплики могут обновлять без блокировки. Слияние определено так, что реплики сходятся. Нужно использовать типы, у которых есть эта математика слияния.

CRDT помогают некоторым совместным редакторам и некоторым краевым репликам. Они не сливают произвольные бизнес-объекты. Банковский баланс — не случайная задача CRDT. Деньгам обычно нужен один писатель или тщательно спроектированный тип и аудит.

Большинство кампусных приложений используют «сервер побеждает» плюс подсказку пользователю, когда мобильный клиент был офлайн. Этого достаточно. Не добавляйте библиотеку CRDT потому, что доклад использовал аббревиатуру.

Если вы изучаете эти идеи, напишите ADR, который называет ограничение закона и значение по умолчанию, которое вы держите. Не копируйте лозунги поставщиков.

## Пишите ADR и контекстную диаграмму C4

Выберите систему, которой вы владеете или которую можете менять. Инструмента задач, сайта кампусного клуба или библиотеки заметок достаточно. Проект должен работать. Колода слайдов — не побочный проект.

Пишите ADR в репозитории (тема 1). См. [https://adr.github.io/](https://adr.github.io/). Начните с трёх:

1. Источник истины (основное хранилище)
2. Идентичность (как принципал аутентифицируется)
3. Единица развёртывания (один процесс или больше)

Добавляйте ADR, когда решение дорого отменить: стиль публичного API, очередь, регион, хранилище секретов (темы 5, 7, 10 и 12).

Правила из этого пути:

- Одно решение на ADR
- Контекст включает ограничения (команда, время, закон, существующие системы)
- Последствия включают качество, которое вы ослабляете
- Статус может меняться. Не удаляйте заменённый ADR (тема 12)

Не пишите двадцать ADR в первый день. Три хороших ADR лучше папки лозунгов. Ревьюйте ADR после поставки. Если код не согласен, исправьте код или замените ADR.

Модель C4 — маленький набор уровней диаграмм. Сайт [https://c4model.com/](https://c4model.com/). Этот путь сначала использует контекст. Добавляйте вид контейнера, когда больше чем один процесс или хранилище.

Контекстная диаграмма показывает людей, вашу систему как одну коробку и внешние системы. У каждой связи есть глагол. Диаграмма контейнеров показывает единицы развёртывания и хранилища внутри вашей системы: веб-приложение, API, рабочий, база и брокер.

Правила для диаграмм:

- Одна работа на диаграмму
- Имена совпадают с кодом и ADR
- Границы доверия можно наложить позже (тема 10)
- Не рисуйте двадцать коробок, которых нет в коде

Контекстная диаграмма плюс три ADR — полный первый пакет архитектуры для студенческой системы.

## Делите монолит только после настоящей боли границы

Модульный монолит — значение по умолчанию (тема 3). Разделение — дорогое решение (тема 1). Вы делите только после настоящей боли границы.

Настоящая боль выглядит так:

- Две команды блокируют друг друга на одних часах выпуска, и границы пакетов уже существуют.
- Измеренная нагрузка нуждается в другом пути масштаба для одного модуля-владельца (тема 12).
- Отказ в одном модуле роняет процесс, который закон или контракт требует оставить доступным.
- Поставщик или закон заставляет отдельную систему.

Не боль:

- Пост в блоге про микросервисы
- Цель по числу строк
- Возможная будущая нужда в масштабе без меры
- Желание использовать брокер в первый день

До разделения у модуля уже должны быть язык, свои таблицы, контракт и тесты (темы 4, 5 и 6). Извлечение — перенос существующей границы на новую единицу развёртывания (тема 9). Если нельзя нарисовать границу на доменной диаграмме, не рисуйте её на диаграмме развёртывания.

После разделения вы платите стоимость сети, стоимость саги и стоимость эксплуатации (темы 8 и 9). Пишите эти цены в ADR. Назовите качество, которое вы ослабляете.

Если боль исчезает после улучшения модульного монолита (яснее пакеты, реплика, очередь для одного задания), оставьте монолит. Этот результат — успех.

Предложенный порядок практики в `architecture.topics.md` ставит «разделить сервис только если граница настоящая» последним. Следуйте этому порядку.

## DDIA и один разбор инцидента в неделю

*Designing Data-Intensive Applications* (Kleppmann) — книга, которая покрывает модели данных, хранение, репликацию, разделы и производные данные. Сайт [https://dataintensive.net/](https://dataintensive.net/). Читайте её после поставки модульного монолита с одной базой. Сочетайте главы с темами 6–8 и с `db.topics.md`. Не используйте книгу как причину начать с глобального плана шардов.

Разбор инцидента (также называется обзор обучения) — короткий документ после инцидента или после лабораторного отказа. Он утверждает, что произошло, что вы ожидали, чему научились и что измените. Он не винит человека.

Пишите один разбор инцидента в неделю, пока практикуете:

- Тест, который упал неожиданным способом
- Тайм-аут, который вы забыли
- Развёртывание, которое сломало контракт
- Заметку игрового дня из темы 11

Правила:

- Сначала факты. Время, симптом, влияние и идентификатор корреляции, если есть.
- Одно или два действия с владельцем и датой.
- Делитесь с командой. Держите секреты вне (тема 10).
- Неделя без производственного инцидента всё равно имеет вто лабораторный разбор.

Официальные и стандартные ресурсы этого пути также включают модель C4, ADR, двенадцать факторов, Enterprise Integration Patterns и книги Google SRE (`architecture.topics.md`). Выберите одну следующую книгу после DDIA. Закончите её. Не начинайте четыре книги за одну неделю.

Практикуйте в порядке, который перечисляет `architecture.topics.md`, если можете: модульный монолит, структурированные журналы, тайм-ауты, три ADR, кэш или реплика, одно асинхронное задание, SLO, расширить-сжать, режимы отказа, затем разделение только если граница настоящая.

Не кладите решения лабораторных курса в эту папку справочника. Держите практику в своём репозитории.

# 16. Внутренности и следующие шаги

## Описание

Эта тема объясняет, как Go хранит значения, как сборщик мусора освобождает память и как срезы и карты работают внутри. Вы также узнаете, когда избегать reflection и cgo. Последние разделы указывают на Effective Go, стандартную библиотеку, роутеры, gRPC и дальнейшее чтение.

Используйте один термин для каждого понятия. Выделение — акт резервирования памяти. Escape-анализ — проход компилятора, который решает стек против кучи. Сборщик мусора (GC) освобождает объекты кучи, которые программа больше не может достичь. Не считайте микробенчмарки доказательством без `testing.B` и ясной гипотезы.

Сначала завершите темы 1–15. Эта тема — карта, не полное руководство по среде выполнения.

## Стек, куча и escape-анализ

У каждой горутины есть стек. Стек держит локальные переменные, которые не убегают. Выделение на стеке дёшево. Среда растит и сжимает стек, когда горутине нужно больше места.

Куча держит объекты, которые живут после возврата функции, или которые компилятор не может держать на стеке. Сборщик мусора управляет кучей. Выделение в куче дороже, чем выделение на стеке. Объекты кучи добавляют работу GC.

Escape-анализ — проход компилятора, который решает расположение. Компилятор не следует простому правилу «new значит куча». Значение, которое создаёте через `&T{}`, может остаться на стеке, если ничего не удерживает указатель. Локальная переменная может переехать в кучу, если вы возвращаете её адрес.

Частые причины, почему значение убегает в кучу:

- вы возвращаете указатель на значение
- вы сохраняете значение в значении интерфейса (интерфейсу может понадобиться объект кучи)
- вы отправляете значение в канал, который переживает функцию
- вы сохраняете указатель в структуре или срезе, который уже живёт в куче
- вы замыкаете переменную в горутине, которая выполняется после возврата функции

Просматривайте escape-анализ так:

```text
go build -gcflags=-m
```

Добавьте `-m` дважды для большей детализации: `-gcflags="-m -m"`. Компилятор печатает строки вроде `moved to heap` и `escapes to heap`. Читайте эти строки как подсказки. Они не стабильный публичный API. Формулировки могут меняться между версиями Go.

```go
func makeInt() *int {
	x := 42
	return &x // x escapes
}

func sum(a, b int) int {
	return a + b // a and b stay on the stack
}
```

Не принуждайте выделение в куче без причины. Пишите ясный код. Сначала профилируйте. Затем меняйте выделение только когда профиль показывает стоимость.

Большой локальный массив может быть дорог на стеке. Для больших буферов используйте `make([]byte, n)` и примите срез кучи или переиспользуйте буфер.

Стек не разделяется между горутинами. Не скрывайте указатели от среды через `unsafe`, если не знаете правила.

## Сборщик мусора (обзор)

Сборщик мусора находит объекты кучи, которые программа не может достичь. Он освобождает эту память. В Go не вызывают `free`.

Go использует конкурентный трёхцветный сборщик mark-and-sweep в текущих версиях. Сборщик работает вместе с вашей программой. Он останавливает все горутины только на короткое время. Эти остановки — паузы stop-the-world (STW). Современный Go держит STW короткими.

Простая картина:

1. Mark: сборщик трассирует указатели от корней (стеки, глобальные, регистры).
2. Объекты, которые он не пометил, — мусор.
3. Sweep: сборщик освобождает непомеченные объекты.

Сборщик — не система реального времени. Огромная куча или огромное число указателей всё равно могут стоить CPU. Важна скорость выделения. Много короткоживущих объектов создают работу.

`GOGC` задаёт целевой процент роста кучи. По умолчанию — `100`. Это значение означает, что сборщик стремится запуститься после того, как куча вырастет примерно на 100% от живого размера. `GOGC=off` отключает GC. Не отключайте GC в продакшене.

`GOMEMLIMIT` (Go 1.19 и новее) задаёт мягкий предел памяти. Сборщик работает усерднее около этого предела. Используйте его, когда у контейнера есть потолок памяти.

`runtime.GC()` запускает сборку. Используйте в тестах или инструментах. Не вызывайте на горячем пути запроса.

`runtime.ReadMemStats` и профили кучи `pprof` показывают выделение. Тема 11 покрывает `pprof`.

Сначала не настраивайте GC. Исправьте утечки (горутины, неограниченные срезы, глобальные кэши). Затем профилируйте. Затем меняйте `GOGC` или `GOMEMLIMIT` с измерением.

## Внутренности срезов и карт

Заголовок среза — три слова: указатель на массив, длина и ёмкость. Тема 5 покрывает взгляд программиста. Этот раздел добавляет внутренний взгляд.

`append` растит backing-массив, когда `len` равна `cap`. Среда выбирает новую ёмкость. Коэффициент роста — не обещание в вашем коде. Старые массивы становятся мусором, когда ни один срез на них больше не указывает. Маленький срез, который всё ещё указывает на огромный массив, держит огромный массив живым. Скопируйте маленькую часть наружу.

Срез указателей или срез интерфейсов держит указатели. GC должен сканировать эти указатели. Срез чисел дешевле сканировать.

Строка — заголовок: указатель и длина. Байты неизменяемы. Срез строки делит backing-байты. Преобразования `string` и `[]byte` могут копировать. Go 1.22 и новее оптимизируют некоторые преобразования. Не полагайтесь на копию или разделение без нужды.

Карта — хеш-таблица. Среда хранит корзины. Значение карты — указатель на эту таблицу. Присваивание делит таблицу. Тема 5 покрывает это правило.

Рост карты выделяет новые корзины и вытесняет overflow. Порядок итерации случаен намеренно. Среда рандомизирует старт, чтобы программы не зависели от порядка.

У пустой карты всё равно есть заголовок. У карты `nil` нет таблицы. Запись в карту `nil` паникует.

Параллельная запись в карту фатальна. Среда обнаруживает многие гонки и падает с `concurrent map writes`. Детектор гонок тоже сообщает гонки.

Не используйте `unsafe`, чтобы обходить корзины карты. Используйте `range` и API.

`clear(s)` для среза задаёт элементам ноль и в недавних версиях Go сохраняет длину. `clear(m)` удаляет все ключи. Прочитайте текущую спецификацию правила `clear` для среза в вашей версии Go.

## Reflection и cgo (когда их избегать)

Пакет `reflect` проверяет типы и значения во время выполнения. `encoding/json` использует reflection, чтобы читать поля структур и теги. Можно написать `reflect.ValueOf(x).Kind()`.

Reflection медленнее сгенерированного или типизированного кода. Reflection может паниковать на неверном виде. Reflection ломает некоторые проверки компилятора. Вы теряете автодополнение и безопасность типов.

Используйте reflection, когда пишете обобщённый кодировщик, тестовый помощник, который печатает любое значение, или реестр в стиле плагинов. Не используйте reflection, чтобы прочитать поле, которое можете назвать в исходниках. Не используйте reflection на горячем пути запроса без измерения.

```go
v := reflect.ValueOf(p)
fmt.Println(v.Kind(), v.Type())
```

`unsafe` позволяет сломать систему типов. `unsafe.Pointer` может указывать на любой адрес. Злоупотребление вызывает порчу памяти. Сборщик мусора может не увидеть скрытый указатель. Не используйте `unsafe` в прикладных сервисах. Стандартная библиотека использует `unsafe` в нескольких местах со строгим ревью.

cgo вызывает C из Go. Вы пишете `import "C"` и исходный код C в комментариях. cgo полезен для библиотеки поставщика, у которой нет API Go. Стоимости:

- более медленные сборки
- более сложная кросс-компиляция
- дополнительные потоки и стоимость соглашения вызова
- сборки `CGO_ENABLED=0` падают
- труднее образы Docker scratch

Не используйте cgo, чтобы вызвать крошечную функцию C, которую можете написать на Go. Предпочитайте чистый драйвер Go (например `modernc.org/sqlite` или `pgx`), когда можете.

Если нужно использовать cgo, изолируйте его в одном пакете. Задавайте `CGO_ENABLED=1` только для этой сборки. Задокументируйте инструментарий C.

## Роутеры, gRPC и дальнейшее чтение

`ServeMux` Go 1.22 покрывает многие HTTP API. Вы всё равно можете выбрать роутер для дополнительных возможностей: стеки middleware, автоматический OpenAPI или старые версии Go. Популярные роутеры включают `chi` и `echo`. Оценивайте модуль до добавления. Предпочитайте стандартный mux, пока не почувствуете настоящий предел.

gRPC — система RPC поверх HTTP/2. Она использует Protocol Buffers. Реализация Go — `google.golang.org/grpc`. Используйте gRPC, когда многим внутренним сервисам нужны типизированные контракты и стриминг. Используйте JSON HTTP, когда важны браузеры и простые клиенты. Не добавляйте gRPC к одному публичному CRUD API без причины.

Дальнейшие навыки после этого пути:

- пулы воркеров и `errgroup` (`golang.org/x/sync/errgroup`)
- `sqlc` или аккуратное использование ORM (тема 14)
- OpenTelemetry для трасс
- больше `pprof` и бенчмарков (тема 11)
- ревью безопасности: TLS, секреты, проверка (тема 15)
- чтение предложений Go и заметок о выпуске

Предлагаемый порядок практики из пути обучения:

1. Tour of Go плюс крошечные программы CLI
2. Структуры, срезы, карты: список в памяти
3. HTTP JSON API через `net/http`
4. Тесты, табличные случаи и `-race`
5. Таймауты context и корректное завершение
6. `database/sql`
7. Пул воркеров
8. Dockerize и кросс-компиляция
9. Профилируйте один медленный путь через `pprof`
10. Пересоберите маленький инструмент, которым реально пользуетесь

Официальные ресурсы остаются источником истины: go.dev, спецификация, Effective Go и pkg.go.dev.

Не учите каждый лишний модуль сразу. Поставьте маленький сервис стандартной библиотекой. Добавляйте одну зависимость, когда стандартной библиотеки недостаточно.

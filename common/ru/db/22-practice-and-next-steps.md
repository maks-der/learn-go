# 22. Практика и следующие шаги

## Описание

Эта тема — практическое закрытие общего пути по базам. Вы проектируете маленькую схему, пишете SQL руками, читаете план запроса, снимаете резерв и восстанавливаете его, затем выбираете продукт для следующего изучения (PostgreSQL, MongoDB или Redis).

Используйте один термин для каждого понятия. Практика значит, что выполняете команды на локальной СУБД. Специализация — путь вендора после этого нейтрального к вендорам пути. Завершите эту тему после того, как умеете использовать ограничения, транзакции, индексы и резервы. Эта тема не учит эти идеи снова. Она просит их сочетать.

Не пропускайте шаг SQL руками. Поздний ORM будет выдавать SQL, который должны читать.

## Спроектируйте схему для маленькой предметной области (библиотека, магазин, билеты)

Выберите одну предметную область. Спроектируйте таблицы до кода приложения. Напишите проект на бумаге или в коротком документе. Затем реализуйте его в SQL.

**Библиотека.** Читатели, экземпляры произведений, выдачи. У произведения есть название. У экземпляра есть штрихкод. Выдача связывает читателя и экземпляр с `loaned_at` и `due_at`. Экземпляр не может быть на двух открытых выдачах.

**Магазин.** Клиенты, товары, заказы, строки заказа. У строки есть количество и цена единицы как точные деньги. У заказа есть клиент и статус. У товара есть уникальный `sku`.

**Билеты.** События, места или типы билетов, клиенты, брони. Место нельзя продать дважды на одно событие. Используйте уникальное ограничение и транзакцию, когда бронируете.

Минимальное содержание проекта:

1. Сущности и связи (один-ко-многим, многие-ко-многим).
2. Первичные ключи и внешние ключи с действиями `ON DELETE`.
3. Типы: деньги, даты, мгновения UTC, булевы.
4. Уникальные ограничения, которые совпадают с бизнес-правилами.
5. Столбцы аудита, если нужны.
6. Какие удаления жёсткие, а какие мягкие.

```text
Example shop grain
customers 1--* orders 1--* order_lines *--1 products
```

Нормализуйте до `3NF` для этого упражнения. Не денормализуйте ради скорости, пока нет запроса и плана.

Напишите два или три запроса, на которые система должна ответить. Спроектируйте ключи и индексы для этих запросов после того, как таблицы существуют. Не придумывайте десять индексов в первый день.

Не моделируйте весь мир. Библиотеке не нужна полная кадровая система. Остановитесь на названной предметной области.

## Пишите SQL руками до ORM

Пишите операторы в CLI. Не начинайте с ORM для этого упражнения. Нужно видеть текст, который выполняет СУБД.

Покройте этот набор на схеме своей предметной области:

1. `INSERT` родителя и потомков в одной транзакции.
2. `UPDATE` с `WHERE`, который использует ключ.
3. `DELETE` или `UPDATE` мягкого удаления, который совпадает с вашей политикой.
4. `SELECT` с соединением и `WHERE`.
5. Отчёт `GROUP BY` (подсчёты или суммы).
6. Подзапрос или `EXISTS`, если отчёту это нужно.
7. `LIMIT` со страницей keyset, не только `OFFSET 0`.

```sql
BEGIN;
INSERT INTO orders (order_id, customer_id, placed_at, status)
VALUES (1, 1, CURRENT_TIMESTAMP, 'placed');
INSERT INTO order_lines (order_id, product_id, quantity, unit_price)
VALUES (1, 10, 2, 19.99);
COMMIT;
```

Сохраните скрипты в файлах. Выполняйте их больше одного раза только если они идемпотентны, или сначала сбросьте данные.

Читайте ошибки. Ошибка внешнего ключа значит, что порядок вставок неверен или родителя нет. Уникальная ошибка значит, что бизнес-правило сработало.

После того как скрипты работают, можете попробовать ORM. Сравните SQL, который выдаёт ORM, со своими скриптами. Если не можете объяснить SQL ORM, не выпускайте его.

Не склеивайте пользовательский ввод в этих скриптах. Позже используйте параметры в приложении. В CLI можете использовать литералы, которые написали сами.

#### Сложные практические задания

## Прочитайте план запроса

План запроса — путь доступа, который выбрал оптимизатор. Читаете его до добавления индексов и после них.

Шаги:

1. Напишите SQL.
2. Выполните `EXPLAIN` (или имя вендора) без побочного эффекта записи.
3. Найдите сканирование или поиск на каждой таблице.
4. Найдите тип соединения.
5. Сравните оценочные строки с фактическими, если продукт показывает оба.
6. Смените одно (индекс или перепись). Объясните снова.

```text
Tokens to search for (names differ)
Seq Scan / Table Scan
Index Scan / Index Seek
Nested Loop / Hash Join / Merge Join
Sort / Aggregate
```

Используйте таблицу, достаточно большую, чтобы это имело значение. План на 10 строках учит мало. Загрузите тысячи строк, если нужно.

Не выполняйте `EXPLAIN ANALYZE` на `DELETE` в продакшене. Форма, которая выполняет оператор, удалит.

Проверьте, что ключ соединения имеет индекс на большой стороне. Проверьте, что ожидаемый фильтр не спрятан в сканировании всей таблицы.

Напишите план в заметках четырьмя строками: доступ на A, доступ на B, соединение, цена или время. Не нужно запоминать каждый тип узла.

Если оценка далека от факта, обновите статистику и объясните снова (тема 17).

#### Сложные практические задания

## Снимите резерв и восстановите его

Резерв, который восстановили, — единственный резерв, который доказали. Используйте учебную базу.

Шаги:

1. Запишите доказательное значение (`COUNT(*)` главной таблицы или конкретная строка).
2. Снимите логический дамп или физический резерв официальным инструментом.
3. Храните файл вне живого каталога данных, если можете.
4. Измените живые данные (вставьте строку или обновите имя).
5. Восстановите в новое имя базы или на новый экземпляр. Не перезаписывайте единственную копию, пока не уверены.
6. Выполните доказательный запрос. Подтвердите, что лишнее изменение отсутствует, если восстановили более старую копию.
7. Запишите длительность. Эта длительность — нижняя граница `RTO` для этого метода.

```text
learn  -->  dump file  -->  learn_restored
proof: COUNT(*) = 17
```

Если есть только инструмент дампа, используйте его. Если можете сделать PITR на одноразовом экземпляре, сделайте это как вторую лабораторную.

Не называйте реплику резервом в этом упражнении. Снимите файл. Восстановите файл.

После того как восстановление работает, напишите runbook из пяти строк: команда, путь файла, команда восстановления, доказательный запрос, кого звать (себя).

Шифрование учебного дампа необязательно. Не кладите дамп с настоящими персональными данными в публичную папку.

4. Напишите runbook из пяти строк.

2. Засеките дамп и восстановление. Напишите `RTO` как «не меньше столько» для этого размера.
3. Провалите восстановление (неверный путь). Запишите ошибку. Восстановите правильно.

#### Сложные практические задания

## Затем специализируйтесь: PostgreSQL, MongoDB, Redis

Этот путь был нейтрален к вендорам. Дальше выбираете один продукт и изучаете его имена, инструменты и пределы.

**PostgreSQL.** Реляционная СУБД. Выберите её, чтобы глубже изучить SQL, типы, `WAL`, `EXPLAIN`, роли и логическую репликацию. Она совпадает с большей частью этого пути один к одному.

**MongoDB.** Документная СУБД. Выберите её, чтобы изучить коллекции, документы, индексы на JSON, наборы реплик и когда документный агрегат — единица работы. Держите реляционную систему учёта в уме для денег, если она всё ещё нужна.

**Redis.** Склад ключ-значение (и структур данных). Выберите его, чтобы изучить ключи, `TTL`, варианты персистентности и доступ в памяти. Используйте его как кэш, склад сессий или блокировку, не как единственный журнал заказов.

```text
After this path
  --> PostgreSQL  if you need SQL and a general record store
  --> MongoDB     if you need document aggregates
  --> Redis       if you need fast key access and TTL
```

Можете изучить больше одного. Изучите один достаточно, чтобы установить, снять резерв и объяснить план или эквивалент.

Не начинайте три пути вендоров в одну неделю. Завершите первую установку, первый резерв и первую настоящую схему или проект ключей.

Официальные документы — источник истины для команд. Этот справочник намеренно остаётся нейтральным к вендорам.

Когда специализируетесь, берите идеи с собой: типы, транзакции, индексы, резервы, наименьшие привилегии, сначала измеряйте. Меняются только синтаксис и имена внутренностей.

#### Сложные практические задания

1. Упакуйте предметную область: миграции или файлы SQL, семя, отчёт, команда резерва, команда восстановления, снимок плана или текст. Другая машина должна это воспроизвести.
2. Напишите закрытие общего пути: чему можете учить, что изучите на пути вендора, и один риск, который ещё не покрываете (HA, `CDC` или шардирование).

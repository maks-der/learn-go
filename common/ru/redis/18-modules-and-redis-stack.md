# 18. Модули и Redis Stack

## Описание

Модуль добавляет команды и типы, которые базовый Redis не поставляет. Redis Stack — дистрибутив, который загружает общий набор модулей. Эта тема обзорно покрывает RedisJSON, RediSearch, RedisTimeSeries и RedisBloom, затем когда модуль — лучший путь и какую стоимость эксплуатации вы платите.

Сначала завершите тему 7 (обзор модулей). Та тема ввела префиксы команд. Эта тема — взгляд выбора и эксплуатации.

Используйте один термин для каждого понятия. Модуль — плагин сервера, который регистрирует команды. Redis Stack — Redis плюс пакет модулей. Схема — определение индекса для Search. Фильтр — вероятностная структура (Bloom и связанные). Совместимость — могут ли ваша версия Redis, Cluster, персистентность и клиент запускать модуль.

## RedisJSON

RedisJSON хранит документы JSON как полноценное значение. Вы адресуете пути. Не переписываете весь документ ради маленькой смены.

```text
JSON.SET lab:user:1 $ '{"name":"Ada","n":1}'
JSON.GET lab:user:1 $.name
JSON.NUMINCRBY lab:user:1 $.n 1
```

`$` — корень документа в JSONPath. Синтаксис путей на страницах команд RedisJSON. Проверьте версию модуля.

Почему не `SET` строки JSON? Строковый `SET` заменяет весь блоб. Параллельные обновления двух полей нуждаются в блокировке или Lua read-modify-write. RedisJSON может обновить один путь. Раскладка памяти для документов, не для сырой строки.

`TYPE` на ключе JSON не `string`. Команды вроде `GET` не применяются. Клиентам нужна поддержка RedisJSON или сырые вызовы команд.

Search может индексировать документы JSON (следующий раздел), когда запускаете оба модуля.

Cluster: ключ JSON всё ещё один ключ в одном слоте. Огромный документ — большой ключ (тема 16).

Персистентность и репликация включают данные модуля, когда модуль это поддерживает. Проверяйте перезапуск (тема 9).

Используйте RedisJSON, когда документы вложенные, обновления частичные и вы уже запускаете Redis Stack или хостинговую возможность JSON. Используйте хеш, когда модель — плоская карта маленьких полей. Используйте строку JSON, когда документ маленький и вы всегда заменяете его.

## RediSearch

RediSearch (Search) строит индекс на хешах или JSON. Вы запрашиваете индекс через `FT.SEARCH`. Это не SQL. Нужно создать схему.

```text
FT.CREATE idx:lab ON HASH PREFIX 1 lab:doc: SCHEMA title TEXT body TEXT score NUMERIC
FT.SEARCH idx:lab "hello"
```

`FT.CREATE` определяет поля и типы (`TEXT`, `TAG`, `NUMERIC`, `GEO` и другие по версии). Документы — обычные ключи Redis, которые совпадают с префиксом. Модуль поддерживает инвертированные индексы.

Нужно держать индекс в синхроне. Записи в хеши (или JSON), которые совпадают с префиксом, обновляют индекс. Если обходите ожидаемый тип, документ может не индексироваться.

`FT.DROPINDEX` удаляет индекс. Читайте опцию `DD` до удаления. Можно удалить только индекс или также документы.

Search использует ОЗУ для индекса. Большие текстовые корпуса стоят памяти сверх документов.

Агрегации (`FT.AGGREGATE`) есть. Это не склад. Тяжёлая аналитика всё ещё принадлежит системе, построенной для сканирований.

У Cluster и Search есть особые правила развёртывания. Читайте заметки модуля Cluster. Некоторые схемы используют выделенную раскладку шардов Search.

Используйте Search, когда нужны полнотекстовые или фильтровые запросы, которые хеши и `SCAN` не могут сделать. Не используйте Search как замену PostgreSQL, когда нужны соединения, ограничения и произвольный SQL.

## RedisTimeSeries

RedisTimeSeries хранит выборки с метками времени. Каждый ключ — один ряд (одна метрика, один помеченный поток точек).

```text
TS.CREATE lab:cpu
TS.ADD lab:cpu * 0.42
TS.RANGE lab:cpu - +
```

`*` использует время сервера. Можно передать явную метку.

`TS.CREATERULE` даунсэмплирует в другой ряд (avg, min, max и другие). Удержание (`RETENTION`) удаляет старые выборки. Уплотнение держит грубую историю.

Почему не упорядоченное множество? Упорядоченное множество может хранить `score=timestamp` и `member=value`. При большом объёме TimeSeries компактнее и имеет правила агрегации. Окна темы 6 хороши для маленьких случаев.

Метки (`TS.ADD` с `LABELS`) позволяют запрашивать многие ряды (`TS.MRANGE`). Мощность меток должна оставаться ограниченной. Метки высокой мощности (один ряд на id пользователя в огромном масштабе) взрывают память.

Используйте TimeSeries для инфраструктурных или продуктовых метрик, которые уже хотите в Redis. Используйте выделенную систему метрик (Prometheus, склад), когда удержание и объём запросов превышают хранилище в памяти.

Не пишите одну выборку TimeSeries на клик пользователя в интернет-масштабе без плана.

## RedisBloom

RedisBloom добавляет вероятностные структуры: фильтры Блума, фильтры Кукушки, эскизы Count-Min, Top-K и связанные типы. Точные имена зависят от версии модуля.

Фильтр Блума отвечает «точно не в множестве» или «возможно в множестве». Он не хранит элементы. Ложные срабатывания есть. Ложных отрицаний нет (в стандартном фильтре Блума).

```text
BF.RESERVE lab:bf 0.01 10000
BF.ADD lab:bf user:42
BF.EXISTS lab:bf user:42
```

`0.01` — целевая доля ошибки. `10000` — подсказка ёмкости. После слишком многих вставок доля ошибки растёт, если не зарезервировали достаточно ёмкости.

Используйте фильтр Блума, чтобы пропустить более медленную проверку (поиск SQL, диск), когда ответ «точно нет». Тема 13 негативное кэширование хранит ключ. Фильтр Блума использует меньше памяти для огромных пространств id, с ошибкой.

HyperLogLog (тема 7) оценивает уникальные счёты. Фильтр Блума проверяет членство. Не смешивайте два.

Эскиз Count-Min оценивает частоты. Top-K оценивает тяжёлых хиттеров. Читайте страницы команд до того, как считать числа точными.

Не используйте фильтр Блума как список контроля доступа. Ложное срабатывание может значить «возможно разрешено». Это неверный инструмент для безопасности.

## Когда модуль лучше, чем строить самим

Стройте сами (базовые типы + приложение), когда:

- Хеш, поток или упорядоченное множество уже совпадает с шаблоном доступа
- Лишняя зависимость не стоит стоимости эксплуатации
- Нужно запускать ванильный Redis на ограниченной платформе
- Логика маленькая (один скрипт Lua)

Используйте модуль, когда:

- Модуль хорошо реализует известный алгоритм (инвертированный индекс, компактные временные ряды, Bloom)
- Частичные обновления JSON частые и большие
- Платформа уже поставляет Redis Stack или модуль
- Корректность самодельного индекса была бы хуже модуля

Самодельный поиск через `SCAN` и совпадение строк — ловушка в масштабе. Самодельные временные ряды с безграничными упорядоченными множествами — ловушка памяти. Самодельный Bloom на битовых картах возможен (тема 7), но легко ошибиться на огромных смещениях.

Модуль не всегда быстрее. Команда модуля всё ещё выполняется в основном потоке (если документация модуля не говорит иное). Огромный `FT.SEARCH` может остановить.

Лицензирование и привязка к вендору — часть выбора. Redis Stack, модули и форки (тема 20) имеют разные лицензии. Читайте текущую лицензию до поставки.

Не загружайте несопровождаемый модуль на промышленный primary.

## Совместимость и стоимость эксплуатации

Модуль меняет историю эксплуатации.

Матрица версий: версия Redis, версия модуля, тег образа Redis Stack и клиентская библиотека должны совпадать. Команда, которая есть в Stack 7, может отсутствовать на старом сервере.

Персистентность: RDB и AOF должны восстанавливать значения модуля. Проверяйте `BGSAVE`, перезапуск и синхронизацию реплики с ключами модуля. Реплика без модуля не может загрузить данные.

Cluster: у некоторых модулей есть пределы команд с несколькими ключами и того, как шардируются индексы. Читайте страницу модуля Cluster. Не предполагайте, что каждый модуль безопасен для Cluster.

Резервная копия: дамп данных модуля — не текстовый экспорт JSON, если не построите. Резервируйте RDB/AOF как обычно (тема 19). Проверяйте восстановление на машине с теми же модулями.

Память: индексы и фильтры — дополнительно. Помогают `INFO modules` и разделы `INFO` модуля. `MEMORY USAGE` может не показать полную стоимость индекса на другом ключе.

Безопасность: `MODULE LOAD` — опасная команда (тема 17). Загружайте только подписанные или поддерживаемые вендором модули. Ограничьте, кто может загружать.

Клиенты: приложение должно отправлять команды модуля. Старые клиенты всё ещё могут использовать общие API команд.

Наблюдаемость: добавьте метрики модуля (размер индекса, ёмкость фильтра) на панель Redis.

Стоимость: больше ОЗУ, больше шагов обновления, больше режимов отказа, меньше людей, которые видели этот класс инцидентов.

Используйте Redis Stack в Docker для обучения:

```text
docker run --name stack-learn -p 6379:6379 redis/redis-stack
```

Закрепите дайджест образа в промышленной среде. Не запускайте `latest` без закрепления.

### Вопросы

#### Теоретические вопросы

1. Как RedisJSON, Search, TimeSeries и Bloom отображаются на «документ», «запрос», «метрика» и «возможно видели»?
2. Какие стоимости модуля тяжелы по ОЗУ даже когда число ключей выглядит маленьким?
3. Когда отказываться от модуля даже если возможность подходит?
4. Как базовые типы темы 7 (битовая карта, HLL, упорядоченное множество) всё ещё заменяют модуль в маленьких дизайнах?
5. Что должно быть верно о персистентности, репликах и клиентах до поставки модуля?

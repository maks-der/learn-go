# 14. Продакшен и экосистема

## Описание

Эта тема показывает, как запускать PostgreSQL 16 и PostgreSQL 17 в продакшене и куда идти дальше после этого пути. Вы узнаёте роль приложения с наименьшими привилегиями, сетевые правила, миграции, изменения схемы expand-contract, мониторинг, короткий обзор оконных функций, обёрток внешних данных и PostGIS, плюс официальную документацию, облачные продукты и отчёты об ошибках.

Сначала завершите тему 13. Вы умеете читать представления активности и настройки памяти. После этой темы используйте настоящую базу и продолжайте читать.

Используйте один термин для каждого понятия. Наименьшие привилегии значат, что у роли только права, которые нужны программе. Миграция — версионированное изменение схемы. Expand-contract — совместимое изменение мелкими шагами. Оконная функция вычисляет значение из связанного набора строк, не схлопывая результат. Обёртка внешних данных (FDW) читает удалённый источник как таблицу. Официальная документация — страницы на postgresql.org для мажорной версии. Этот справочник рассчитан на PostgreSQL 16 и PostgreSQL 17.

## Роль приложения с наименьшими привилегиями и сетевая экспозиция

Тема 8 представила роли и `GRANT`. В продакшене это default, не дополнение.

Роль приложения (`shop_app`):

- имеет `LOGIN`
- имеет `CONNECT` на базе приложения
- имеет `USAGE` на схеме приложения
- имеет DML на таблицах приложения (`SELECT`, `INSERT`, `UPDATE`, `DELETE` по необходимости)
- имеет `USAGE` последовательности для вставок identity
- имеет `EXECUTE` только на функциях, которые приложение должно вызывать
- не имеет `SUPERUSER`, `BYPASSRLS`, `CREATEDB`, `CREATEROLE` или `REPLICATION`
- не владеет таблицами, если ими владеет роль migrator

Роль migrator запускает DDL. CI использует секрет migrator. Приложение этот секрет никогда не видит.

```sql
CREATE ROLE shop_migrator LOGIN PASSWORD 'migrator-secret';
CREATE ROLE shop_app LOGIN PASSWORD 'app-secret';

GRANT CONNECT ON DATABASE shop TO shop_migrator, shop_app;
GRANT USAGE, CREATE ON SCHEMA shop TO shop_migrator;
GRANT USAGE ON SCHEMA shop TO shop_app;
```

Безопасность на уровне строк остаётся включённой, если вы мультиарендные. Роль приложения не должна обходить RLS.

PostgreSQL по умолчанию слушает TCP-порт `5432`. Если этот порт достижим из публичного интернета, атакующие его сканируют. SSL не делает публичный `5432` хорошей идеей.

Безопасный шаблон:

- `listen_addresses` привязывает только интерфейсы, которым это нужно
- файрвол или security group разрешает `5432` только из подсети приложения, PgBouncer или bastion
- `pg_hba.conf` совпадает с этими источниками и требует `scram-sha-256` (и `hostssl`, когда используете TLS)
- клиенты используют `sslmode=verify-full`, когда контролируете сертификаты
- администраторы используют VPN, bastion или вендорский private link, не открытое правило `0.0.0.0/0`

Docker `-p 5432:5432` на ноутбуке — привычка лаборатории. На облачной VM опубликованный `5432` на `0.0.0.0` — инцидент.

Не отлаживайте продакшен-аварию, выдавая `SUPERUSER` `shop_app`. Не ставьте PostgreSQL в публичный интернет на хосте с настоящими данными. Не используйте `trust` ни для одной удалённой строки.

## Миграции и изменения схемы expand-contract

Миграция — версионированное изменение SQL (или кода), которое применяете по порядку. Продакшен-схема не должна быть «чем кто-то запустил в `psql`».

Частые инструменты:

- **Flyway** — файлы версий вроде `V3__add_orders.sql`; отслеживает `flyway_schema_history`
- **golang-migrate** — `0003_add_orders.up.sql` и файл down; часто в сервисах Go
- **Sqitch** — планы с именами и зависимостями; силён для ревью

Всем трём нужно:

- одна таблица истории
- роль migrator
- шаг CI, который применяет ожидающие файлы
- правило, что файл, который дошёл до продакшена, не меняется

```text
-- 0004_items_qty.up.sql
ALTER TABLE shop.items ADD COLUMN qty int NOT NULL DEFAULT 0;
```

Down-миграции в части команд необязательны. Если держите их, тестируйте. Down, который удаляет столбец, уничтожает данные.

Блокировка, которая переписывает большую таблицу, может остановить приложение. Проверьте текущую страницу `ALTER TABLE`: часть изменений — только обновление каталога; часть сканирует таблицу; часть переписывает.

**Expand-contract** (расширить, мигрировать, сузить):

1. Expand: добавить новый столбец или таблицу, которые старое приложение игнорирует
2. Двойная запись или backfill: приложение или задание заполняет новый объект
3. Переключить чтения на новый объект
4. Contract: удалить старый столбец или таблицу в позднем релизе

Пример: переименовать `name` в `title` без долгой перезаписи:

1. Добавить `title text`
2. Выкатить приложение, которое пишет оба
3. Backfill `title` из `name`
4. Выкатить приложение, которое читает `title`
5. Удалить `name`

`CREATE INDEX CONCURRENTLY` (тема 5) — шаг expand. `DETACH PARTITION` (тема 10) может удалить старые данные без огромного `DELETE`.

Не смешивайте два инструмента миграции на одной базе. Не редактируйте применённый файл после того, как продакшен его применил. Не запускайте DDL как `shop_app`. Не добавляйте `NOT NULL` без default или предварительного backfill.

Официальный `ALTER TABLE`: [https://www.postgresql.org/docs/17/sql-altertable.html](https://www.postgresql.org/docs/17/sql-altertable.html).

## Мониторинг: подключения, лаг, раздутие, wraparound

Продакшену нужны измерения, не ощущения. Тема 13 показала представления. Этот раздел — минимальный набор.

**Подключения**

```sql
SELECT count(*) FROM pg_stat_activity;
SHOW max_connections;
SELECT usename, state, count(*)
FROM pg_stat_activity
GROUP BY 1, 2;
```

Алертите, когда использованные подключения остаются высокими, когда много сессий `idle in transaction` или когда приложение не может подключиться.

**Лаг репликации** (тема 11)

```sql
SELECT client_addr, state, replay_lsn, sent_lsn
FROM pg_stat_replication;
```

На реплике используйте функцию времени лага, если есть replay. Алертите, когда лаг превышает SLA отчётов.

**Раздутие** (тема 7)

```sql
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 20;
```

Алертите на долю мёртвых кортежей и на рост размера, который числа строк не объясняют.

**Wraparound** (тема 7)

```sql
SELECT datname, age(datfrozenxid)
FROM pg_database
ORDER BY 2 DESC;
```

Алертите задолго до предела wraparound. Autovacuum должен успевать. Неудачный freeze — авария.

Также смотрите: свободный диск, WAL, удержанный слотом репликации, выбросы `pg_stat_statements`, всплески checkpoint, журналы ошибок.

Не алертите на каждый `n_dead_tup > 0`. Не игнорируйте wraparound, потому что «autovacuum включён». Не собирайте текст SQL, который содержит секреты.

## Оконные функции, FDW, PostGIS (обзор)

Этот раздел — обзор. Не каждая возможность нужна первому продакшен-приложению. Нужно знать имена и когда открывать документацию.

**Оконная функция** использует `OVER (...)`. Набор результата держит одну строку на входную строку. `GROUP BY` схлопывает строки.

```sql
SELECT
    id,
    customer_id,
    total,
    sum(total) OVER (PARTITION BY customer_id) AS customer_sum,
    rank() OVER (PARTITION BY customer_id ORDER BY total DESC) AS rnk,
    lag(total) OVER (PARTITION BY customer_id ORDER BY id) AS prev_total
FROM shop.orders;
```

`PARTITION BY` сбрасывает окно. `ORDER BY` внутри `OVER` обязателен для `rank` и `lag`. Тема 3 `DISTINCT ON` может заменить простой фильтр `row_number()`. Официально: [https://www.postgresql.org/docs/17/tutorial-window.html](https://www.postgresql.org/docs/17/tutorial-window.html).

**Обёртка внешних данных (FDW)** позволяет запрашивать удалённый источник как внешнюю таблицу. `postgres_fdw` — частая обёртка для другого сервера PostgreSQL.

```sql
CREATE EXTENSION postgres_fdw;

CREATE SERVER remote_shop
    FOREIGN DATA WRAPPER postgres_fdw
    OPTIONS (host 'remote.example', dbname 'shop', port '5432');
```

Затем создаёте сопоставление пользователя и внешние таблицы. Проталкивание предложений `WHERE` ограничено. FDW не замена реплики или логической репликации. Официально: [https://www.postgresql.org/docs/17/postgres-fdw.html](https://www.postgresql.org/docs/17/postgres-fdw.html).

**PostGIS** — необязательное расширение для типов geometry и geography, пространственных индексов GiST и функций вроде `ST_DWithin`. Многие установки его не загружают.

```sql
CREATE EXTENSION IF NOT EXISTS postgis;
SELECT PostGIS_Version();
```

Если `CREATE EXTENSION postgis` падает, напишите, что пакета нет. Пространственный поиск — не пара `numeric` плюс B-дерево. Официально: [https://postgis.net/documentation/](https://postgis.net/documentation/).

Не храните каждый отчёт как окно, если соединение с сгруппированным подзапросом яснее. Не направляйте FDW на продакшен-primary из недоверенной сети. Не считайте PostGIS обязательным для остального пути.

## Официальная документация, облачные продукты и отчёты об ошибках

Официальный учебник: [https://www.postgresql.org/docs/current/tutorial.html](https://www.postgresql.org/docs/current/tutorial.html). Слово `current` — новейшая стабильная мажорная версия. Эта версия может быть новее 17. Также откройте учебник, который совпадает с вашим сервером:

- [https://www.postgresql.org/docs/16/tutorial.html](https://www.postgresql.org/docs/16/tutorial.html)
- [https://www.postgresql.org/docs/17/tutorial.html](https://www.postgresql.org/docs/17/tutorial.html)

Заметки о выпуске важны при каждом мажорном обновлении. Прочитайте раздел «Migration», прежде чем переносить данные.

Вики: [https://wiki.postgresql.org/](https://wiki.postgresql.org/). Когда вики и официальная документация расходятся, побеждает официальная документация. **Postgres Weekly** ([https://postgresweekly.com/](https://postgresweekly.com/)) ссылается на статьи. Это не замена документации.

Управляемый PostgreSQL снижает работу ОС. Вы всё равно владеете схемой, выдачами, RLS, планами, миграциями, размером пула и тестом бэкапа.

| Продукт | Вендор | Заметка на высоком уровне |
| --- | --- | --- |
| Amazon RDS for PostgreSQL | AWS | управляемый экземпляр, группы параметров, опция Multi-AZ |
| Amazon Aurora PostgreSQL | AWS | совместимый движок, вендорское хранилище и HA |
| Cloud SQL for PostgreSQL | Google Cloud | управляемый экземпляр, опция HA |
| AlloyDB | Google Cloud | совместим с PostgreSQL, вендорская HA и возможности |
| Crunchy | Crunchy Data | эксперты PostgreSQL; Crunchy Bridge — управляемое облако |
| Supabase | Supabase | PostgreSQL плюс платформа приложения (auth, API) |

Aurora и AlloyDB — совместимые продукты. Это не обещание drop-in для каждого расширения. Тестируйте `pg_dump` из сервиса, если нужно уйти.

Когда PostgreSQL ведёт себя так, как документация запрещает, можно сообщить. Официальное руководство: [https://www.postgresql.org/docs/current/bug-report.html](https://www.postgresql.org/docs/current/bug-report.html).

Полезный отчёт включает `SELECT version();`, точные шаги, результат, который получили, результат, который ждали, со ссылкой на документацию, и маленькую схему. Воспроизводите на community PostgreSQL 16 или 17, когда можете. Не прикладывайте секреты или дамп клиента.

Не учите продакшен-поведение из случайного поста, когда есть официальная страница. Не пропускайте тесты `pg_dump`, потому что есть снимки. Не требуйте дату исправления в отчёте об ошибке.

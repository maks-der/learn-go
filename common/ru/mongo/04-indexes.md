# 4. Индексы

## Описание

Индекс — структура данных, которая помогает серверу находить документы без полного сканирования коллекции. Эта тема показывает однополевые индексы, составные индексы, уникальные индексы и мультиключевые индексы. Вы также изучаете TTL, текстовые, геопространственные и хешированные индексы на высоком уровне. Скрываете индексы и читаете `explain`.

Сначала завершите запросы. Завершите эту тему до изучения агрегации и производительности.

Используйте один термин для каждого понятия. **Индекс** — отсортированная структура по одному или нескольким полям. **Сканирование коллекции** (`COLLSCAN`) читает каждый документ. **Сканирование индекса** (`IXSCAN`) читает индекс, затем при необходимости загружает документы. **Префикс** составного индекса — список полей слева.

Индексы ускоряют чтения. Индексы замедляют записи. Каждая вставка, обновление и удаление должны обновлять индексы. Не добавляйте индекс на каждое поле.

## Однополевые и составные индексы (правило префикса)

Однополевый индекс использует одно поле. У MongoDB уже есть уникальный индекс по `_id`.

Создать индекс в `mongosh`:

```javascript
db.orders.createIndex({ userId: 1 })
```

`1` — по возрастанию. `-1` — по убыванию. Для одного поля направление редко меняет поиск по равенству. Направление важнее для сортировки.

Используйте однополевый индекс, когда многие запросы фильтруют или сортируют только по этому полю.

Список индексов:

```javascript
db.orders.getIndexes()
```

Удалить индекс по имени:

```javascript
db.orders.dropIndex("userId_1")
```

У индекса есть имя. MongoDB может сгенерировать имя. Можно задать `name` в опциях `createIndex`.

Запрос использует индекс, когда фильтр или сортировка совпадают с индексом. `explain` показывает план. Если на большой коллекции видите `COLLSCAN`, скорее всего нужен индекс или лучший фильтр.

**Составной индекс** использует два или больше полей в фиксированном порядке.

```javascript
db.orders.createIndex({ userId: 1, createdAt: -1 })
```

Руководство **ESR** (Equality, Sort, Range) помогает упорядочить ключи: поля равенства, затем поля сортировки, затем поля диапазона.

**Правило префикса**: составной индекс `{ a: 1, b: 1, c: 1 }` может поддержать запросы по:

- `{ a }`
- `{ a, b }`
- `{ a, b, c }`

Он не поддерживает запрос только по `{ b }` или `{ c }` как префикс индекса. Сервер иногда может использовать более поздний ключ в некоторых планах, но на это нельзя опираться. Ставьте первое поле фильтра первым, когда можете.

Сортировка: индекс может удовлетворить сортировку, если ключи сортировки совпадают с порядком индекса (или обратным, с правилами). Несовпадение может заставить сортировку в памяти.

Один составной индекс может заменить два однополевых, когда запросы всегда включают левый префикс. Не создавайте и `{ a: 1, b: 1 }`, и `{ a: 1 }` без причины. Префикс покрывает `{ a }`.

Порядок — часть индекса. `{ a: 1, b: 1 }` — не `{ b: 1, a: 1 }`.

Не создавайте дублирующий индекс с тем же шаблоном ключей.

## Уникальные и мультиключевые индексы

**Уникальный индекс** отклоняет второй документ с тем же ключом.

```javascript
db.users.createIndex({ email: 1 }, { unique: true })
```

Индекс `_id` уникален.

Уникальные индексы обеспечивают уникальность, которую хочет и приложение. База — последняя защита. Две одновременные вставки не могут обе пройти с одним email.

Уникальный индекс считает отсутствующие поля как `null` (с правилами). Два документа без `email` могут конфликтовать на уникальном индексе `email`. Используйте **частичный уникальный индекс**, когда уникальность нужна только при наличии поля:

```javascript
db.users.createIndex(
  { email: 1 },
  { unique: true, partialFilterExpression: { email: { $exists: true, $type: "string" } } }
)
```

Уникальный составной индекс уникален по комбинации полей.

Не используйте уникальный индекс как единственную проверку формата. Уникальность — про равенство ключа, не про синтаксис email.

Если дубликат уже есть, `createIndex` падает. Сначала почистите данные.

Когда индексируют поле-массив, MongoDB создаёт **мультиключевой** индекс. Каждый элемент массива становится ключом в индексе.

```javascript
db.posts.createIndex({ tags: 1 })
```

Запрос `{ tags: "mongo" }` может использовать этот индекс.

У мультиключевых индексов есть ограничения. Обычно нельзя создать составной индекс с **более чем одним** полем-массивом. Индекс `{ tags: 1, scores: 1 }` падает, если оба поля — массивы.

Составной индекс может включать одно поле-массив и другие скалярные поля: `{ authorId: 1, tags: 1 }`.

Встроенные документы в массиве: можно индексировать `"lines.sku"`. Индекс мультиключевой.

Мультиключевые индексы могут быть большими. Каждый элемент — ключ. Документ с 10 000 тегов создаёт много записей индекса. Держите массивы ограниченными.

`explain` может показать `isMultiKey: true`.

## TTL, текстовые, геопространственные и хешированные индексы (обзор)

**TTL-индекс** (Time To Live) удаляет документы после задержки. Его создают по полю **даты**.

```javascript
db.sessions.createIndex({ expiresAt: 1 }, { expireAfterSeconds: 0 })
```

Если `expireAfterSeconds` равен `0`, MongoDB удаляет документ, когда `expiresAt` в прошлом. Если задать положительное число, MongoDB прибавляет столько секунд к значению поля.

Монитор TTL работает в фоне. Удаления не мгновенны в ту же секунду. Не используйте TTL как блокировку, которая должна истечь в точный момент.

Поле должно быть Date (или массивом Date). Строковая дата не истекает.

Используйте TTL для сессий, логов и временных токенов. Не используйте TTL как единственную политику юридического хранения, если данные нужно хранить.

Эти другие типы индексов решают особые запросы. Выучите идею. Перед промышленным использованием прочитайте полные страницы.

**Текстовый индекс.** Текстовый индекс поддерживает поиск `$text` по строковым полям. Он токенизирует слова. Это не полноценный поисковый движок. Atlas Search (Lucene) сильнее для поиска товаров. Во многих версиях у коллекции может быть не больше одного текстового индекса. Проверьте для своей версии.

**Геопространственный индекс.** `2dsphere` индексирует точки и фигуры GeoJSON. Запрашиваете `$near` и `$geoWithin`. Используйте для «найти места рядом с этой точкой». Храните координаты в форме GeoJSON, которую показывает руководство.

**Хешированный индекс.** Хешированный индекс хранит хеш поля. MongoDB использует хешированные индексы для хеш-шардирования. Запросы равенства могут использовать хешированный индекс. Диапазонные запросы плохо используют хешированный индекс.

Не создавайте текстовый индекс вместо простого индекса равенства по `email`. Не создавайте геопространственный индекс по обычному числовому полю. Не создавайте хешированный индекс для диапазонной сортировки.

## Скрытые индексы и `explain`

**Скрытый индекс** существует и сервер его обновляет, но планировщик запросов его не использует.

```javascript
db.orders.createIndex({ status: 1 }, { hidden: true })
db.orders.hideIndex("status_1")
db.orders.unhideIndex("status_1")
```

Скройте индекс перед удалением. Если нагрузка в порядке — удалите. Если запрос стал медленным — покажите снова. Так безопаснее, чем сразу удалять.

`explain` показывает, как сервер выполняет запрос.

```javascript
db.orders.find({ userId: "u1" }).explain("executionStats")
```

Подробность:

- `queryPlanner` — выбранный план
- `executionStats` — просмотренные документы и время
- `allPlansExecution` — больше одного плана

Читайте эти поля:

- `stage` — `COLLSCAN`, `IXSCAN`, `FETCH`, `SORT`
- `nReturned` — возвращённые документы
- `totalDocsExamined` — прочитанные документы
- `totalKeysExamined` — прочитанные ключи индекса

Хороший план просматривает примерно столько документов, сколько возвращает, или меньше при покрытом запросе. Плохой план просматривает намного больше документов, чем возвращает.

Не гадайте. Запускайте `explain` на реалистичном размере данных.

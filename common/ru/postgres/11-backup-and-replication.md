# 11. Бэкап и репликация

## Описание

Эта тема показывает бэкап и копии кластера в PostgreSQL 16 и PostgreSQL 17. Вы узнаёте `pg_dump`, `pg_restore`, `pg_dumpall`, `pg_basebackup`, архивирование WAL, восстановление на точку во времени, потоковую репликацию, hot standby, логическую репликацию и инструменты failover на высоком уровне.

Сначала завершите тему 10. Вы умеете отсоединять секцию и дампить таблицу. Завершите эту тему до настройки клиентских пулов.

Используйте один термин для каждого понятия. Логический дамп — SQL или архив объектов. Физический бэкап — копия каталога данных плюс WAL. WAL — журнал упреждающей записи. PITR — восстановление на выбранное время. Потоковая реплика — физический стендбай, который проигрывает WAL. Логическая репликация копирует набор таблиц через публикации и подписки. Этот справочник рассчитан на PostgreSQL 16 и PostgreSQL 17.

## `pg_dump`, `pg_restore`, `pg_dumpall`

`pg_dump` копирует одну базу. Не копирует роли или табличные пространства. `pg_dumpall` копирует все базы плюс объекты всего кластера (роли, табличные пространства). `pg_restore` загружает не-plain архив из `pg_dump`.

Форматы `pg_dump`:

- plain (`-Fp`) — SQL-скрипт; загрузка через `psql`
- custom (`-Fc`) — сжатый архив; загрузка через `pg_restore`; можно выбирать объекты
- directory (`-Fd`) — одна папка; параллельный дамп и восстановление (`-j`)
- tar (`-Ft`) — tar-архив; загрузка через `pg_restore`

```text
pg_dump -h localhost -U postgres -d shop -Fc -f shop.dump
pg_restore -h localhost -U postgres -d shop_copy --clean --if-exists shop.dump
```

Только схема или только данные:

```text
pg_dump -s -d shop -f shop_schema.sql
pg_dump -a -d shop -Fc -f shop_data.dump
```

Одна таблица:

```text
pg_dump -d shop -t shop.orders_2025_01 -Fc -f orders_2025_01.dump
```

`pg_dump` делает согласованный снимок этой базы. Других баз кластера в файле нет. Открытые транзакции, которые держат старые снимки, могут задержать дамп (темы 6 и 7).

```text
pg_dumpall -g -f roles.sql
```

`-g` дампит только глобальные объекты. Восстановите глобальные объекты до восстановления базы, которая зависит от этих ролей.

По возможности совпадайте мажорные версии клиента и сервера. Более новый `pg_dump` часто может дампить более старый сервер. Восстановление дампа 17 на 16 может упасть на новых возможностях.

Не считайте копию файловой системы работающего каталога данных бэкапом. Эта копия несогласованна. Используйте `pg_dump` или `pg_basebackup`. Не коммитьте файлы дампа с живыми данными в git.

Официально: [https://www.postgresql.org/docs/17/app-pgdump.html](https://www.postgresql.org/docs/17/app-pgdump.html).

## `pg_basebackup`, архивирование WAL и PITR

`pg_basebackup` берёт физический бэкап всего кластера. Копирует каталог данных через протокол репликации. Бэкап — точка старта для реплики или для PITR.

```text
pg_basebackup -h primary.example -U replicator -D /var/lib/postgresql/17/backup -Fp -X stream -R
```

Полезные флаги:

- `-D` — каталог назначения
- `-Fp` или `-Ft` — обычные файлы или tar
- `-X stream` — включить WAL, который приходит во время копирования
- `-R` — записать `standby.signal` и настройки подключения для реплики
- `-c fast` — быстрый checkpoint перед копией

Роли нужен `REPLICATION` (или суперпользователь). В `pg_hba.conf` нужна строка `replication`.

PostgreSQL 17 добавляет инкрементальный физический бэкап. Берёте полный `pg_basebackup`, затем позже `pg_basebackup --incremental` против прежнего манифеста. `pg_combinebackup` собирает пригодный каталог из полного бэкапа плюс инкрементов. У PostgreSQL 16 этого набора инкрементальных инструментов нет.

Физический бэкап — на весь кластер. Одну базу из `pg_basebackup` без дополнительной работы не восстановить. Когда нужна одна база, используйте `pg_dump`.

Сервер пишет WAL до записи страниц данных. Если храните каждый сегмент WAL от базового бэкапа дальше, можно проиграть до целевого времени. Этот процесс — восстановление на точку во времени (PITR).

Основные настройки (обзор):

- `wal_level = replica` (или `logical`, если также нужно логическое декодирование)
- `archive_mode = on`
- `archive_command` — команда оболочки, которая копирует `%p` в безопасное хранилище, или `archive_library` в текущих установках 16/17

```text
archive_command = 'test ! -f /archive/%f && cp %p /archive/%f'
```

`%p` — путь файла. `%f` — имя файла. Команда должна возвращать успех только когда копия устойчива.

Восстановление в PostgreSQL 16 и 17 использует конфигурацию плюс файл сигнала:

- положите `restore_command` в конфигурацию
- создайте пустой `recovery.signal` для восстановления, которое станет primary
- создайте пустой `standby.signal`, чтобы остаться стендбаем

В этих версиях нет `recovery.conf`.

```text
recovery_target_time = '2026-09-13 16:00:00+00'
recovery_target_action = 'promote'
```

Восстанавливаете базовый бэкап, добавляете WAL из архива, задаёте цель и запускаете сервер.

Не запускайте два primary из копий одного бэкапа без плана восстановления. Не задавайте `archive_command` командой, которая может успеть без настоящей копии. Не тестируйте PITR только в голове.

Официально: [https://www.postgresql.org/docs/17/app-pgbasebackup.html](https://www.postgresql.org/docs/17/app-pgbasebackup.html), [https://www.postgresql.org/docs/17/continuous-archiving.html](https://www.postgresql.org/docs/17/continuous-archiving.html).

## Потоковая репликация и hot standby

Потоковая репликация отправляет WAL с primary на стендбай по подключению репликации. Стендбай пишет WAL и проигрывает его. Копия физическая. Мажорная версия должна совпадать. Стендбай только для чтения для обычного SQL.

Шаги на высоком уровне:

1. Создайте роль `REPLICATION` на primary.
2. Разрешите `replication` в `pg_hba.conf`.
3. Задайте `wal_level` не ниже `replica`.
4. Возьмите `pg_basebackup -R` в каталог данных стендбая.
5. Запустите стендбай.

Стендбай использует `primary_conninfo` (часто пишет `-R`) и `standby.signal`.

Смотреть лаг:

```sql
-- на primary
SELECT client_addr, state, sent_lsn, replay_lsn
FROM pg_stat_replication;

-- на стендбае
SELECT pg_is_in_recovery(), pg_last_wal_replay_lsn();
```

Синхронная репликация ждёт, пока стендбай сбросит WAL (`synchronous_commit` и `synchronous_standby_names`). Эта настройка снижает потерю данных и увеличивает задержку записи. Новички начинают с асинхронного потока.

Слоты (`pg_create_physical_replication_slot`) держат WAL на primary, пока реплика его не потребит. Слот, который никто не потребляет, заполняет диск.

Hot stand-by — реплика, которая принимает SQL только для чтения, пока восстанавливается. `hot_standby` по умолчанию `on` в PostgreSQL 16 и 17.

```sql
SHOW hot_standby;
SELECT pg_is_in_recovery();
```

На hot stand-by можно `SELECT`. Нельзя `INSERT`, `UPDATE`, `DELETE` или DDL, который пишет.

Конфликты: primary может vacuum или обновить строку, которая всё ещё нужна долгому запросу стендбая. Стендбай может отменить запрос (`max_standby_streaming_delay`). `hot_standby_feedback` сообщает primary о снимках стендбая. Это снижает отмены запросов. Может задержать vacuum на primary (больше раздутия).

Не пишите на стендбае. Не используйте поток как единственный бэкап. Не смешивайте primary PostgreSQL 16 со стендбаем 17. Не задавайте `hot_standby = off` на реплике, которую приложения должны запрашивать.

Официально: [https://www.postgresql.org/docs/17/warm-standby.html](https://www.postgresql.org/docs/17/warm-standby.html).

## Логическая репликация

Логическая репликация копирует изменения строк для набора таблиц. Издатель и подписчик во многих поддерживаемых парах могут быть разных мажорных версий. Таблица подписчика записываемая. Конфликты — ваша проблема, если обе стороны пишут один ключ.

На издателе:

```sql
CREATE PUBLICATION shop_pub FOR TABLE shop.items;
```

На подписчике:

```sql
CREATE SUBSCRIPTION shop_sub
    CONNECTION 'host=primary port=5432 dbname=shop user=replicator'
    PUBLICATION shop_pub;
```

`wal_level` на издателе должен быть `logical`. PostgreSQL 15 и новее (значит 16 и 17) могут добавлять списки столбцов и фильтры строк на публикациях.

Начальная синхронизация копирует существующие строки, затем применяет изменения. Слот репликации на издателе держит WAL для подписчика. Мёртвый подписчик заполняет диск.

PostgreSQL 16 может выполнять логическое декодирование со стендбая в поддерживаемых схемах. PostgreSQL 17 добавляет больше помощников failover для логических слотов (`pg_createsubscriber` и связанные инструменты). Считайте их возможностями оператора. Сначала учите `PUBLICATION` и `SUBSCRIPTION`.

Логическая репликация копирует не всё. Типичные пробелы: последовательности (проверьте заметки версии 16/17), большие объекты, DDL (изменения схемы применяете сами) и некоторые типы.

Не используйте логическую репликацию как единственный бэкап. Не подписывайте таблицу на саму себя. Не забывайте DDL: новый столбец на издателе может сломать подписчика, пока не добавите его.

Официально: [https://www.postgresql.org/docs/17/logical-replication.html](https://www.postgresql.org/docs/17/logical-replication.html).

## Инструменты failover (обзор)

Потоковая репликация сама не продвигает реплику, когда primary умирает. Человек или инструмент должен продвинуть (`pg_ctl promote` или `SELECT pg_promote();`) и перевести клиентов на новый primary.

**Patroni** — частый агент с открытым кодом. Использует etcd, Consul или ZooKeeper, чтобы выбрать лидера. Управляет `postgres` и виртуальным IP или прокси. Бэкапы всё равно нужны. Patroni не замена PITR.

**HA облачного вендора** (Amazon RDS Multi-AZ, Google Cloud SQL HA, Azure, AlloyDB, Aurora PostgreSQL, Crunchy-managed) запускает вендорский путь failover. Учите вендорский runbook: кто продвигает, что делает имя DNS и какой RPO/RTO заявляет продукт. Тема 14 перечисляет эти продукты.

Что новичок должен помнить:

- failover — процесс, не файл дампа
- клиентам нужно одно стабильное имя (прокси, DNS или вендорская точка)
- реплику, которую продвигаете, нельзя делить со старым primary без fencing
- тестируйте failover по расписанию
- держите `pg_dump` или базовые бэкапы даже когда HA включена

Не пишите свой выборщик, если команда может использовать Patroni или вендорский продукт HA. Не продвигайте два primary. Не пропускайте бэкапы, потому что «есть реплика».

## Обзор темы

Эти вопросы не повторяют вопросы разделов выше. Они покрывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Когда для одной задачи выбираете `pg_dump`, `pg_basebackup`, PITR, поток или логическую репликацию?
2. Как архивы WAL, слоты и забытые реплики связаны с риском полного диска?
3. Почему hot stand-by — не тот же объект, что логический подписчик?
4. Как инкрементальный бэкап PostgreSQL 17 меняет политику бэкапа эпохи 16?
5. Коллега говорит, что реплики хватает, а дампы необязательны. Какие факты из этой темы вы используете в ответе?

#### Простые практические задания

1. Сдампите учебную базу через `pg_dump -Fc` и восстановите под новым именем. Выполните `SELECT count(*)` на одной таблице в обеих базах.
2. Напишите шпаргалку: форматы дампа, базовый бэкап, архив, поток, hot stand-by, публикация, Patroni.
3. `SHOW wal_level;` `SHOW archive_mode;` `SELECT pg_is_in_recovery();`.
4. Добавьте в закладки документацию `pg_dump`, `pg_basebackup` и логической репликации для вашей мажорной версии.

#### Средние практические задания

1. Нарисуйте конвейер: ночной `pg_dump`, недельный `pg_basebackup`, непрерывный архив, одна потоковая реплика. Напишите, для чего каждая копия.
2. Создайте публикацию и подписку на двух учебных базах для одной таблицы. Затем возьмите `pg_dump` подписчика. Напишите, почему существуют оба.
3. Напишите план теста восстановления с целевым временем и проверкой успеха (строка есть / строки нет).

#### Сложные практические задания

1. Соберите Docker Compose с primary и репликой. Уроните primary в лаборатории. Продвиньте. Направьте `psql` на новый primary. Держите дамп от до теста.
2. Сопоставьте эту тему с официальными главами: бэкап, непрерывное архивирование, высокая доступность, логическая репликация. Добавьте одно ограничение 16-или-17, которого в теме не было.

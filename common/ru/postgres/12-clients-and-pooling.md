# 12. Клиенты и пулинг

## Описание

Эта тема показывает, как программы подключаются к PostgreSQL 16 и PostgreSQL 17. Вы узнаёте строки подключения libpq, режимы пула PgBouncer, драйверы (`psycopg`, `pgx`, JDBC), подготовленные операторы, `LISTEN` / `NOTIFY` и `COPY`.

Сначала завершите тему 11. Вы знаете, что реплика только для чтения. Завершите эту тему до смены настроек памяти.

Используйте один термин для каждого понятия. libpq — официальная клиентская библиотека C. Строка подключения — URI или список ключ-значение, который понимает libpq. Пул повторно использует сессии сервера. PgBouncer — частый пулер. Драйвер — привязка языка. Подготовленный оператор — разобранный оператор, который выполняете с параметрами. `COPY` — команда массовой передачи. Этот справочник рассчитан на PostgreSQL 16 и PostgreSQL 17.

## Параметры подключения `libpq`

Тема 1 показала URI. libpq также принимает строки ключевых слов:

```text
host=localhost port=5432 dbname=shop user=shop_app sslmode=verify-full
```

Форма URI:

```text
postgresql://shop_app@localhost:5432/shop?sslmode=verify-full&connect_timeout=5
```

Частые параметры:

| Имя | Роль |
| --- | --- |
| `host` | имя хоста или путь к Unix-сокету |
| `port` | по умолчанию `5432` |
| `dbname` | база |
| `user` | роль входа |
| `password` | предпочитайте `.pgpass` или хранилище секретов |
| `sslmode` | тема 8 |
| `connect_timeout` | секунды ожидания TCP-подключения |
| `application_name` | видно в `pg_stat_activity` |
| `options` | опции в стиле командной строки сервера |

Переменные окружения: `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`, `PGSSLMODE`, `PGAPPNAME`. Параметр в строке перекрывает окружение.

`application_name` помогает операциям:

```text
postgresql://shop_app@localhost:5432/shop?application_name=shop-api
```

```sql
SELECT application_name, state, query
FROM pg_stat_activity
WHERE datname = current_database();
```

libpq — основа для `psql`, многих драйверов и `pg_dump`. Если драйвер документирует «параметры libpq», таблица выше применяется.

Не кладите пароль в списки процессов или логи CI. Не используйте `sslmode=disable` в сети, которой не доверяете. Не делите одно `application_name` на каждый микросервис, если нужно отлаживать подключения.

Официально: [https://www.postgresql.org/docs/17/libpq-connect.html](https://www.postgresql.org/docs/17/libpq-connect.html).

## PgBouncer: транзакционный против сессионного пулинга

Каждая сессия PostgreSQL использует память и процесс (или слот backend). Веб-приложение, которое открывает одну сессию на HTTP-запрос, исчерпает `max_connections`. Пул держит меньший набор сессий сервера и выдаёт их клиентам.

**PgBouncer** — популярный пулер. Стоит между приложением и PostgreSQL. Три режима пула:

- **session** — одно серверное подключение на всё клиентское подключение. Все возможности работают. Выигрыш пулинга мал, если клиенты остаются подключёнными.
- **transaction** — серверное подключение возвращается в пул на `COMMIT` или `ROLLBACK`. Высокое повторное использование. Многие сессионные возможности ломаются.
- **statement** — возврат после каждого оператора. Редко. Ломает многооператорные транзакции.

Возможности, которым нужен режим **session** (или прямое подключение):

- `LISTEN` / `NOTIFY`
- временные таблицы, которые переживают транзакции
- `SET`, который должен жить на сессию клиента
- консультативные блокировки, держащиеся через транзакции
- подготовленные операторы на сессии сервера, если PgBouncer не настроен их отслеживать

Транзакционный режим — обычный выбор для stateless HTTP API с короткими транзакциями. Сессионный режим — обычный выбор для воркера, который `LISTEN` или держит состояние.

PgBouncer аутентифицирует клиентов и открывает серверные подключения как настроено. Всё равно используйте роль с наименьшими привилегиями (тема 8). Всё равно ограничивайте `max_connections` на PostgreSQL (тема 13).

Не задавайте `max_connections` 1000 и не пропускайте пул. Не используйте транзакционный пулинг и затем зависьте от `LISTEN`. Не запускайте PgBouncer как публичный интернет-прокси без TLS и аутентификации.

Официально: [https://www.pgbouncer.org/](https://www.pgbouncer.org/).

## Драйверы: `psycopg`, `pgx`, JDBC

Драйвер отправляет старт, запросы и `COPY` через протокол PostgreSQL. Многие драйверы используют libpq. Некоторые говорят на протоколе на языке.

**`psycopg`** — обычный драйвер Python (psycopg 3). Поддерживает строки подключения, параметры и `COPY`. Используйте bind-параметры. Не собирайте SQL через f-строки.

**`pgx`** — частый драйвер Go. Может использовать протокол без libpq. Строки подключения всё равно выглядят как URI libpq. Предпочитайте `pgx` с пулом (`pgxpool`) в приложении плюс PgBouncer, когда много хостов приложения делят один кластер.

**JDBC** (`org.postgresql.Driver`) — обычный драйвер Java. Форма URL — `jdbc:postgresql://host:5432/shop`. У JDBC свои продукты пула (HikariCP). Те же правила сессия-против-транзакции применяются, если второй пулер стоит впереди.

Все три должны:

- использовать параметры (`$1` или `?` как документирует драйвер)
- задавать `application_name`
- закрывать или возвращать подключения
- запрашивать `sslmode`, который совпадает с темой 8
- обрабатывать ошибки и повторы без двойного `INSERT`, если фиксация неясна

```python
# Python idea (psycopg 3)
# conn.execute("SELECT id FROM shop.items WHERE name = %s", ("nail",))
```

```go
// Go idea (pgx)
// conn.Query(ctx, "SELECT id FROM shop.items WHERE name = $1", "nail")
```

Не логируйте полные строки подключения. Не отключайте TLS в продакшене, чтобы «заставить драйвер работать». Не смешивайте два пула в одном процессе без плана размера (пул драйвера умножить на PgBouncer умножить на `max_connections`).

## Подготовленные операторы

Подготовленный оператор — разбор и анализ, который сессия держит. Затем `EXECUTE` с параметрами. Протокол делает ту же работу без SQL `PREPARE`, когда драйвер отправляет сообщение parse.

```sql
PREPARE item_by_name (text) AS
    SELECT id, qty FROM shop.items WHERE name = $1;

EXECUTE item_by_name('nail');
DEALLOCATE item_by_name;
```

Выгоды:

- параметры остаются вне текста SQL (безопаснее склейки)
- сервер может пропустить повторный разбор
- `pg_stat_statements` видит нормализованную форму

Цены:

- план может остаться общим; разовый план может быть лучше для редкого значения
- prepare живёт в сессии; транзакционный пулинг может сломать безымянные или привязанные к сессии prepare
- `PREPARE` на сессию, не на весь кластер

Драйверы часто готовят неявно после нескольких повторов. Это можно выключить, когда планы становятся плохими (настройки драйвера вроде «prepare threshold»).

`EXPLAIN EXECUTE item_by_name('nail');` показывает план execute.

Не склеивайте пользовательский текст в `PREPARE`. Не считайте подготовленный оператор кэшем через транзакционный режим PgBouncer. Не держите тысячи именованных prepare в долгой сессии без `DEALLOCATE`.

Официально: [https://www.postgresql.org/docs/17/sql-prepare.html](https://www.postgresql.org/docs/17/sql-prepare.html).

## `LISTEN` / `NOTIFY` и `COPY`

`NOTIFY` отправляет полезную нагрузку всем сессиям, которые `LISTEN` на том же канале в той же базе. Notify виден после фиксации. Откат не уведомляет.

```sql
-- session A
LISTEN shop_jobs;

-- session B
NOTIFY shop_jobs, 'order:42';
```

В `psql` сессия A печатает асинхронное уведомление после фиксации сессии B. В драйвере нужно опрашивать или использовать API драйвера для уведомлений.

Правила:

- имена каналов — идентификаторы
- полезная нагрузка — `text` (держите маленькой; кладите ключ, не документ)
- слушатели должны использовать сессию, которая остаётся подключённой
- транзакционный режим PgBouncer — неверный пул для слушателей
- `NOTIFY` — не очередь заданий с повтором и персистентностью

Используйте `LISTEN` для «проснись и затем `SELECT` таблицу работ». Работу храните в таблице. Notify — только сигнал.

`COPY` перемещает строки между таблицей и файлом или потоком. Это быстрый путь массовой загрузки и выгрузки.

```sql
COPY shop.items (name, qty) FROM STDIN WITH (FORMAT csv, HEADER true);
```

В `psql` `\copy` — вариант на стороне клиента. `\copy` читает файл на хосте клиента. SQL `COPY` по пути файла выполняется на сервере и нуждается в суперпользователе (или выданной роли на настроенной программе). Для прикладных загрузок предпочитайте `\copy` или API `COPY` драйвера.

```text
\copy shop.items (name, qty) FROM 'items.csv' WITH (FORMAT csv, HEADER true)
\copy shop.items TO 'items_out.csv' WITH (FORMAT csv, HEADER true)
```

Двоичный формат быстрее для больших числовых таблиц. CSV проще отлаживать. Строковые триггеры всё равно выполняются. Ограничения всё равно действуют.

Не используйте `NOTIFY` как единственное хранилище заказа. Не `LISTEN` на новом подключении на каждый HTTP-запрос. Не стройте 100000 однострочных `INSERT`, если доступен `COPY`.

Официально: [https://www.postgresql.org/docs/17/sql-notify.html](https://www.postgresql.org/docs/17/sql-notify.html), [https://www.postgresql.org/docs/17/sql-copy.html](https://www.postgresql.org/docs/17/sql-copy.html).

2. Загрузите CSV через `\copy`. Затем `NOTIFY` канала, который слушает вторая сессия.
3. Размерьте пул драйвера и пул PgBouncer так, чтобы произведение оставалось ниже `max_connections`. Покажите арифметику.

#### Сложные практические задания

1. Соберите маленькую программу, которая использует параметры, `RETURNING` и `COPY` или пакетную вставку. Задокументируйте режим пула и почему `LISTEN` нет.
2. Сопоставьте эту тему с официальными страницами libpq, `PREPARE`, `NOTIFY` и `COPY`. Добавьте одну настройку конкретного драйвера, которую тема не называла.

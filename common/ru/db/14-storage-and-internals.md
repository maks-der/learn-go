# 14. Хранение и внутренности

## Описание

Эта тема показывает, как СУБД хранит данные на диске и в памяти. Вы изучаете страницы, таблицы-кучи, кластерные и индекс-организованные таблицы, журнал упреждающей записи (`WAL`), буферный кэш, контрольные точки и вакуум (сборку мусора).

Используйте один термин для каждого понятия. Страница — блок байтов фиксированного размера. Буферный кэш — набор страниц в памяти. `WAL` — долговечный журнал изменений. Завершите эту тему после того, как понимаете транзакции и индексы. Внутренности объясняют, почему существуют фиксация, восстановление после сбоя и вакуум.

Этот путь нейтрален к вендорам. Имена продуктов для одной идеи отличаются (`WAL`, redo, journal). Работы — нет.

## Страницы / блоки

Страница (также блок) — единица, которую СУБД читает с диска и пишет на диск. Типичные размеры — 4 КиБ, 8 КиБ или 16 КиБ. Продукт задаёт размер. Вы не храните одну строку как один файл.

Таблица — набор страниц. Каждая страница держит заголовок и некоторое число версий строк (или слотов строк). Большая строка может занимать больше одной страницы. Маленькая строка делит страницу с другими строками.

СУБД адресует строку идентификатором страницы плюс слот (или эквивалентным указателем строки). Лист индекса хранит этот указатель или хранит строку в кластерной структуре (следующий раздел).

```text
Page 0   : header + rows
Page 1   : header + rows
Page 2   : header + rows
...
```

Цена ввода-вывода — в страницах, не в строках. Запрос, которому нужна одна строка, всё равно читает хотя бы одну страницу. Последовательное сканирование читает много страниц по порядку. Случайные чтения прыгают между страницами. Последовательные чтения часто дешевле на том же диске.

Когда обновляете строку, СУБД часто пишет новую версию на странице и оставляет старую версию, пока вакуум или отмена больше не нуждаются в ней. Эта деталь отличается по продукту. Страница всё ещё контейнер.

Не путайте страницу с блоком файловой системы, хотя размеры могут совпадать. Страница СУБД — структура, которую понимает движок хранения. Операционная система может делить или сливать ввод-вывод вокруг неё.

Выбирайте размер страницы только когда продукт позволяет и когда есть измеренная причина. Для обучения держите значение по умолчанию.

## Куча и кластерные / индекс-организованные таблицы (отличия вендоров)

Таблица-куча хранит строки на страницах без обязательного порядка по первичному ключу. Новая строка идёт на страницу со свободным местом. Первичный ключ — отдельный уникальный индекс. Индекс указывает на место в куче.

Кластерная таблица (или индекс-организованная таблица) хранит строку в порядке первичного ключа. Первичный ключ — организация таблицы. Вторичные индексы указывают на первичный ключ (или на ключ кластеризации), не на стабильный слот кучи.

| Организация | Порядок строк | Первичный ключ | Цель вторичного индекса |
| --- | --- | --- | --- |
| Куча | Нет порядка ключа | Отдельный уникальный индекс | Страница/слот (или эквивалент) |
| Кластерная / IOT | Порядок первичного ключа | Сама таблица | Обычно первичный ключ |

Примеры продуктов (только категория): многие пользовательские таблицы PostgreSQL — кучи. Некоторые другие продукты кластеризуют по первичному ключу по умолчанию. Имена «кластерный индекс» и «индекс-организованная таблица» приходят из этих продуктов. Изучите идею. Затем читайте свой продукт.

Польза кучи: вставки просты. Обновления могут оставить новую версию в новом слоте. Вакуум должен возвращать старые версии.

Польза кластера: сканирование диапазона по первичному ключу читает строки по порядку. Точечный поиск по первичному ключу может избежать второго чтения кучи.

Цена кластера: поиск по вторичному индексу часто нуждается во втором шаге к первичному ключу. Смена ключа кластеризации может переместить строку.

Не предполагайте, что `ORDER BY primary_key` бесплатен на куче. Без индекса СУБД всё равно сортирует. На кластерной таблице диапазон первичного ключа может совпадать с порядком хранения.

Не выбирайте продукт только из-за этого отличия. Оба проекта работают. Ваши индексы и запросы важнее для новичка.

## Идея WAL / журнала redo

`WAL` значит журнал упреждающей записи. СУБД пишет изменение в журнал на стабильном хранилище до того, как считает изменение долговечным. Некоторые продукты говорят redo log или journal. Работа одна: восстановиться после сбоя.

Транзакция меняет страницы в памяти. Эти страницы могут остаться грязными (ещё не записаны в файлы данных). На `COMMIT` СУБД не должна потерять зафиксированное изменение. Она сбрасывает записи `WAL` этой транзакции. Ей не нужно сбрасывать каждую грязную страницу данных в момент фиксации.

```text
1. Change pages in the buffer cache
2. Append WAL records
3. Flush WAL to disk on COMMIT
4. Later: write dirty pages to data files
```

Восстановление использует `WAL`. После сбоя СУБД воспроизводит записи журнала, которые не достигли файлов данных. Она отменяет незафиксированную работу, если проект этого требует. Вы получаете долговечность зафиксированных транзакций и атомарность незавершённых.

`WAL` также питает реплики и инструменты резерва во многих продуктах. Физические резервы и восстановление на момент времени зависят от непрерывного журнала. Более поздняя тема покрывает это использование.

Synchronous_commit (имя продукта отличается) контролирует, ждёт ли `COMMIT` сброса журнала. Если выключите это ожидание, можете потерять последние фиксации после сбоя. Эта настройка — компромисс долговечности, не бесплатный выигрыш скорости.

Не удаляйте файлы `WAL` руками. СУБД перерабатывает их после контрольной точки и после того, как реплики или задания архива больше в них не нуждаются.

Не считайте копию каталога данных без совпадающего журнала безопасным резервом.

## Буферный кэш / общие буферы

Буферный кэш (общие буферы) — набор страниц, которые СУБД держит в памяти. Попадание в кэш значит, что страница уже в памяти. Промах кэша значит, что СУБД читает страницу с диска (или из кэша операционной системы).

Все бэкенды серверной СУБД делят один кэш (детали продукта отличаются). У кэша есть политика замены. Обычная идея — держать горячие страницы и вытеснять холодные.

```text
Query needs page P
  P in cache  -->  read memory
  P not in cache  -->  read disk, put P in cache, maybe evict Q
```

Грязные страницы сидят в кэше, пока контрольная точка или фоновый писатель не запишет их. `WAL` всё ещё защищает зафиксированные данные.

Больший кэш может снизить чтения с диска. Слишком большой кэш может голодать операционную систему или другие процессы. Операционная система также кэширует файлы. Некоторые продукты больше полагаются на этот кэш ОС, чем другие.

Не ставьте буферный кэш на всю ОЗУ. Оставьте память для подключений, сортировок, ОС и приложения.

Не используйте кэш как кэш приложения результатов запросов. Буферный кэш держит страницы. Кэш результатов — другой слой (более поздняя тема производительности).

Полное сканирование таблицы больше кэша вытеснит полезные страницы. Этот эффект — загрязнение кэша. Большие аналитические сканирования и маленькие поиски OLTP конкурируют в одном кэше, если не разделяете системы.

## Контрольные точки

Контрольная точка — момент, когда СУБД пишет грязные страницы так, чтобы восстановление могло начаться с известного места. После контрольной точки более старый `WAL` не нужен для восстановления после сбоя этих сброшенных страниц (реплики и архив всё ещё могут нуждаться в этом `WAL`).

СУБД выполняет контрольные точки по расписанию, по триггеру объёма `WAL` или когда вы запрашиваете одну. Контрольная точка не то же самое, что `COMMIT`. Между контрольными точками происходит много фиксаций.

```text
WAL  ----c--------c--------c---->
         ^        ^        ^
      checkpoint
```

Долгое время между контрольными точками значит более длинное воспроизведение после сбоя. Очень частая контрольная точка значит больше записи ввода-вывода в обычной работе.

Во время контрольной точки трафик записи в файлы данных растёт. Пользователи могут увидеть паузу, если продукт пишет всплеском. Многие продукты распределяют запись (цель завершения контрольной точки).

Не выполняйте ручную контрольную точку как замену `COMMIT`. Не выполняйте частые ручные контрольные точки, чтобы «сделать безопаснее», без измерения. `WAL` уже делает фиксацию долговечной.

Инструменты резерва часто создают контрольную точку или ждут её, чтобы файлы данных и линия журнала совпали. Следуйте процедуре резерва продукта.

Если восстановление медленное после сбоя, одна причина — большое расстояние от последней контрольной точки до сбоя. Другая причина — большой `WAL` для воспроизведения. Измеряйте. Затем меняйте интервал контрольной точки с письменной причиной.

## Идея вакуума / сборки мусора (позже специфично для вендора)

Многие проекты СУБД держат старые версии строк, пока ни одна транзакция не может их видеть. Обновление и удаление не всегда сразу освобождают место. Вакуум (сборка мусора, purge, очистка undo) возвращает это место и поддерживает связанные структуры.

В куче с версионированием (пример категории: кучи `MVCC`) `UPDATE` делает новую версию строки. Старая версия остаётся до вакуума. Мёртвые версии увеличивают размер таблицы (вздутие). Сканирование читает больше страниц, чем требуют живые данные.

Вакуум также обновляет информацию видимости и может замораживать старые идентификаторы транзакций (специфично для продукта). Autovacuum или эквивалентное фоновое задание выполняет эту работу. Можно также выполнить ручной вакуум в окнах обслуживания.

```text
UPDATE row  -->  new version + old version
COMMIT
...
VACUUM     -->  reclaim old version if no reader needs it
```

Другие продукты используют журналы undo. Идея сборки мусора всё ещё существует: что-то должно убрать данные, которые ни одной транзакции не нужны.

Вакуум не резерв. Вакуум не `TRUNCATE`. `VACUUM FULL` или перестройка (имена отличаются) может уплотнить таблицу и держать сильную блокировку. Читайте правила блокировок до полной перезаписи в продакшене.

Не выключайте autovacuum (или эквивалент), чтобы «идти быстрее», если не заменяете его проверенным заданием. Мёртвые версии накапливаются. Запросы замедляются. Диск растёт.

Большое удаление без вакуума оставляет мёртвое место. Поздняя вставка может переиспользовать это место после вакуума. До тех пор таблица может оставаться большой.

Изучите главу продукта после этого пути. Здесь идеи достаточно: запись создаёт мусор; чистильщик должен работать; вы следите за вздутием и здоровьем чистильщика.

### Вопросы

# 12. Несколько кластеров и экосистема

## Описание

Один кластер Kafka живёт в одном домене сбоя даже когда используете стойки (тема 10). Второй кластер в другом регионе или другом аккаунте — другая система. Экосистема Kafka — набор продуктов, которые говорят на протоколе Kafka или сидят рядом с кластером Kafka.

Эта тема показывает MirrorMaker 2, аварийное восстановление, Confluent, Redpanda, управляемую Kafka, Schema Registry, REST Proxy, UI и порядок учёбы: produce и consume на вашем языке, затем добавить задачу Streams. Завершите эту тему после тем 1, 4, 7, 8 и 9. Каждый новый кластер использует KRaft. Не добавляйте ZooKeeper. Инструменты репликации говорят с каждым кластером через `bootstrap.servers`.

Используйте один термин для каждого понятия. Исходный кластер — кластер, у которого уже есть записи. Целевой кластер — кластер, который принимает копию. MirrorMaker 2 (MM2) — репликатор Apache на базе Connect. Аварийное восстановление (DR) — план продолжить после сбоя кластера или региона. Apache Kafka — проект ASF. Система, совместимая с API Kafka, принимает клиенты Kafka. Управляемый сервис запускает брокеров за вас.

## MirrorMaker 2 и аварийное восстановление

**MirrorMaker 2** — репликатор Apache Kafka. Он работает как коннекторы Kafka Connect. Он копирует топики из исходного кластера в целевой кластер. Он может копировать офсеты групп консьюмеров (с отображением). Он может создавать топики на цели с шаблоном имени (часто префикс или суффикс).

MM2 использует коннекторы source и checkpoint. Воркерам нужен сетевой доступ к обоим кластерам. Настройте два значения `bootstrap.servers`. Оба кластера могут быть KRaft. MM2 не нужен ZooKeeper.

Копия асинхронна. Цель отстаёт от источника. Этот лаг — ваша задержка репликации. Измеряйте её.

MM2 не транзакция, которая охватывает два кластера. Exactly-once внутри одного кластера (тема 5) не делает два кластера одним атомарным журналом.

Типичный шаблон имени: исходный топик `orders.placed` становится `sourceCluster.orders.placed` на цели. Консьюмеры должны использовать имя цели.

**Отображение офсетов** отображает зафиксированный офсет группы на источнике на офсет на цели. Офсет 1000 на кластере A — не та же запись, что офсет 1000 на кластере B. Без отображения частая ошибка — стартовать группу на цели с latest (потерять данные) или с earliest (обработать всё заново). Предпочитайте одно число партиций на обоих кластерах.

**Active-passive** значит, что один кластер принимает все отправки топика (активный). Другой кластер — копия (пассивный). При аварии переключаете клиентов на пассивный кластер после шага promote.

**Active-active** значит, что два кластера принимают отправки в «тот же» бизнес-топик одновременно. Получаете конфликты. Большинство проектов DR начинают как active-passive. Не запускайте два цикла MM2 на одном топике в обоих направлениях без фильтра, иначе создадите петлю.

**Cluster Linking** — продукт Confluent, который связывает топики. Он не часть обычного архива Apache. Если есть только Apache Kafka, используйте MM2.

**Аварийное восстановление** — задокументированный путь, когда кластер или регион падает. Вы определяете **RPO** (сколько недавних данных можно потерять, связано с лагом) и **RTO** (сколько до того, как клиенты снова пишут и читают).

Шаги failover (active-passive, только форма):

1. Остановите продюсеров к упавшему источнику (или подтвердите, что они падают).
2. Подтвердите лаг цели и что принимаете как RPO.
3. Promote цели (promote MM2 или Cluster Linking, или сделайте её писателем).
4. Примените отображение офсетов для групп, которые должны продолжить.
5. Направьте клиентов на bootstrap цели. Используйте TLS и SASL для этого кластера (тема 10).
6. Когда старый регион вернётся, не запускайте двух активных без плана failback.

Rack awareness одного кластера (тема 10) не DR для потери региона. Тестируйте DR. Непротестированный runbook падает. Используйте KRaft на обеих сторонах, чтобы в runbook не было шага восстановления ZooKeeper.

```text
# Conceptual MM2 keys (names follow current MM2 docs)
source.cluster.bootstrap.servers=...
target.cluster.bootstrap.servers=...
topics=orders.placed
```

## Confluent, Redpanda и управляемая Kafka

**Apache Kafka** — проект на [https://kafka.apache.org/](https://kafka.apache.org/). Вы скачиваете брокеров, клиентские библиотеки, Kafka Streams и Kafka Connect. Вы их эксплуатируете. Новые кластеры используют KRaft.

**Confluent Platform** — дистрибутив от Confluent. Он включает Apache Kafka (или совместимый брокер) плюс дополнительные компоненты: Schema Registry, ksqlDB, Control Center, коннекторы и коммерческие возможности. **Confluent Cloud** — хостируемая форма.

Протокол Kafka — та же идея. Продюсер, который использует клиент Apache, может говорить с Confluent Cloud, если задать bootstrap, безопасность и иногда пакет клиента, который документирует Confluent.

Документы Apache Kafka — источник ключей брокера и KRaft. Учебники Confluent часто запускают дополнительные контейнеры. Они не обязательны, чтобы учить темы 1–6. Читайте лицензии дополнительных коннекторов.

**Redpanda** — система потоков, которая говорит на API Kafka. Многие клиенты Kafka работают. Движок не JVM-брокер Kafka. Эксплуатация, раскладка диска и дополнительные возможности отличаются. Этот справочник учит Apache Kafka. Используйте Redpanda, когда команда выбирает этот продукт и принимает отличия.

**Apache Pulsar** — другая система pub/sub. По умолчанию она использует отдельный протокол. Pulsar не «Kafka под другим именем». Не запускайте учебник Pulsar и не думайте, что выучили партиции Kafka и KRaft.

**Amazon MSK** — Kafka как управляемый сервис на AWS. Новые кластеры MSK могут использовать KRaft. Вы всё равно используете топики, ACL и клиентов.

**Confluent Cloud**, **Aiven** и похожие продукты дают bootstrap и проект. **WarpStream** хранит данные в объектном хранилище. Модель эксплуатации отличается от классического `log.dirs`. Клиенты всё равно используют протокол Kafka. Тестируйте совместимость ваших возможностей.

Общие факты управляемых сервисов:

- Вы не запускаете `kafka-server-start` на ноутбуке для продакшена.
- Выбирайте KRaft, когда поставщик ещё перечисляет старые версии на ZooKeeper.
- Сеть (private link, VPC) — часть проекта.
- Не предполагайте, что транзакции, Connect или Streams работают внутри поставщика без страницы поставщика.

Если поставщик говорит «совместим с Kafka», тестируйте: produce, consume, группы, транзакции (если нужен EOS) и admin.

KRaft — режим метаданных Apache Kafka. У Redpanda и Pulsar свои метаданные.

## Schema Registry, REST Proxy и UI

**Schema Registry** (Confluent или Karapace, тема 7) хранит схемы и правила совместимости. Это HTTP-сервис. Это не брокер. Он часто использует компактируемый топик `_schemas` на Kafka.

**REST Proxy** (Confluent REST Proxy и похожие проекты) открывает HTTP для produce, consume и некоторого admin. Используйте его, когда у языка нет хорошего клиента или когда устаревшая система может только вызывать HTTP. Предпочитайте родной клиент Kafka, когда можете. Прокси — ещё один процесс, который нужно защитить (тема 10).

**Control Center** — UI Confluent для топиков, Connect, ksql и метрик. Он не часть Apache Kafka.

**AKHQ** и **Kafdrop** — открытые браузерные UI. Они перечисляют топики, просматривают записи и осматривают группы. Им нужны bootstrap и учётные данные. UI, который потребляет топик, — консьюмер. Он может менять лаг или использовать группу, если так настроить. Используйте выделенный group id. Не цепляйте UI к продакшен-группе приложения.

UI не заменяют `kafka-topics` и метрики. Они помогают новичкам видеть партиции и офсеты.

Все они говорят с кластером Kafka. Этот кластер должен быть KRaft для новой работы. Ни один не требует устанавливать ZooKeeper.

Фиксируйте версии UI. Не открывайте UI в публичный интернет без auth.

## Produce и consume на вашем языке; затем добавьте задачу Streams

Учите в этом порядке. Не начинайте с кластера потоков до того, как умеете писать и читать.

1. Запустите локальную Kafka **KRaft** (тема 1). Создайте топик с тремя партициями (тема 2).
2. Используйте **консольный продюсер и консьюмер**. Подтвердите записи и `--from-beginning`.
3. Напишите **продюсера** на языке, который знаете (Java, Go, Python или другой официальный клиент). Задайте `bootstrap.servers`, сериализаторы, `acks=all` и идемпотентный продюсер (тема 3).
4. Напишите **консьюмера** на том же языке. Задайте `group.id`, десериализаторы, автофиксацию выключенной и цикл poll (тема 4). Фиксируйте после завершения работы.
5. Запустите **двух консьюмеров в одной группе**. Остановите одного. Подтвердите, что партиции двигаются. Смотрите лаг.
6. Добавьте **event id** и идемпотентный сток или маленькую транзакцию, если нужен EOS (тема 5).
7. Сначала используйте **JSON**. Затем добавьте Schema Registry и Avro или JSON Schema, если команде нужен контракт (тема 7).
8. Необязательно: добавьте **Connect** (JDBC или Debezium), когда нужно копировать базу (тема 8).
9. Затем добавьте **задачу Streams**: топологию Java Kafka Streams, постоянный запрос ksqlDB или маленькую задачу Flink (тема 9). Начните с фильтра. Затем добавьте счёт на ключ. Затем добавьте окно, если нужны корзины времени.
10. Необязательно: добавьте **TLS и SASL** на локальном стеке compose (тема 10).

Задача Streams — второй клиент. Ей нужен свой `application.id` (или id задачи Flink). Она создаёт внутренние топики. Не используйте повторно `group.id` консьюмера из шага 4 для другой топологии.

Официальные ресурсы остаются теми же:

- [Apache Kafka Documentation](https://kafka.apache.org/documentation/)
- [Introduction](https://kafka.apache.org/intro)
- [Confluent Developer](https://developer.confluent.io/)

Практикуйтесь на KRaft. Не запускайте ZooKeeper для этого пути.

2. Напишите стандарт экосистемы и DR для вашей компании: ядро протокола на KRaft, разрешённые дополнения, MM2 или связь поставщика, запрещённый ZooKeeper, ревью для каждого нового UI.

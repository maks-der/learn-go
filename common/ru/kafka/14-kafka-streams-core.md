# 14. Kafka Streams (ядро)

## Описание

Kafka Streams — библиотека Java, которая читает топики, обрабатывает записи и пишет топики. Вы определяете топологию. Библиотека запускает топологию в вашем процессе. Экземпляры, которые делят `application.id`, делят работу.

Эта тема покрывает топологию, KStream, KTable, Processor API против DSL, join, exactly-once в Streams, интерактивные запросы и тесты. Завершите эту тему после тем 5, 6, 7, 8 и 13. Запускайте Streams против кластера Kafka KRaft. Не добавляйте ZooKeeper.

Используйте один термин для каждого понятия. Топология — граф source, процессоров и sink. KStream — поток событий. KTable — changelog последнего значения на ключ. DSL — API высокого уровня. Processor API — API низкого уровня. Интерактивные запросы читают хранилище состояния у работающих экземпляров.

## Топология, KStream, KTable

**Топология** — направленный граф. Source читают топики Kafka. Процессоры трансформируют записи. Sink пишут топики Kafka. Kafka Streams строит задачу на поток из этого графа. Каждая задача владеет подмножеством партиций.

**KStream** — поток записей. Каждая запись — событие. Две записи с одним ключом — два события. Пример: заказ 1, затем заказ 2 для одного пользователя.

**KTable** — табличный вид changelog. Для каждого ключа таблица хранит последнее значение. Значение null — томбстоун и удаляет ключ (тема 8). Пример: пользователь 9 теперь живёт в городе A, затем в городе B. Таблица показывает город B.

KStream можно превратить в KTable (агрегат или latest-per-key). KTable можно превратить в KStream (каждое изменение становится событием).

Входные топики для таблиц часто компактируемые. Входные топики для потоков часто используют ретеншн delete. Согласуйте `cleanup.policy` со смыслом топика (тема 8).

`application.id` называет группу консьюмеров и префиксирует внутренние топики (repartition, changelog). Не используйте повторно `application.id` для другой топологии без плана сброса.

```text
StreamsBuilder builder = new StreamsBuilder();
KStream<String, String> orders = builder.stream("orders.placed");
KTable<String, String> customers = builder.table("customers");
```

Кластер — KRaft. Streams использует `bootstrap.servers`. В текущих Streams нет настройки ZooKeeper.

## Processor API против DSL

**DSL** (domain-specific language) — API высокого уровня: `stream`, `table`, `filter`, `map`, `groupByKey`, `aggregate`, `join`. Большинство задач используют DSL. DSL строит топологию за вас.

**Processor API** позволяет реализовать узел процессора. Вы получаете записи в `process`. Можно планировать `punctuate` (callback по времени). Вы читаете и пишете хранилища состояния напрямую. Вы присоединяете процессоры через `Topology.addSource`, `addProcessor` и `addSink`.

Используйте DSL, когда операция существует. Используйте Processor API, когда нужны своё время, свой доступ к store или граф, который DSL не выражает.

Их можно смешивать. DSL может добавить свой процессор. Processor API может остаться в маленькой части большей топологии DSL.

Processor API не снимает нужду в корректных ключах, партиционировании и восстановлении состояния. Вы всё равно используете changelog-store, когда процессор stateful.

Не пишите задачу Processor API, чтобы избежать изучения KStream и KTable. Сначала выучите DSL.

Оба API работают в одном рантайме Streams. Оба используют Kafka KRaft как журнал.

## Join

Join в Streams сочетает записи, которые делят ключ. Партиционирование должно использовать один ключ и одно число партиций на обеих сторонах (или Streams должен сделать repartition).

**Stream-stream join** соединяет два KStream. Join оконный. Запись на одной стороне находит записи на другой стороне внутри окна join. Без окна задача не знает, как долго ждать.

**Stream-table join** соединяет KStream с KTable. Каждое событие потока ищет текущее значение таблицы для этого ключа. Это обогащение факта. Пример: событие заказа плюс текущий профиль клиента.

**Table-table join** соединяет две KTable. Результат — KTable. Когда любая таблица меняется, результат join для этого ключа обновляется.

Foreign-key join существуют для таблиц, когда ключ join не является ключом записи. Прочитайте текущую документацию Streams для этого случая.

Ключи null не соединяются. Томбстоуны на таблице удаляют результат join для этого ключа.

Если ключи на неверной партиции, Streams пишет repartition-топик. Этот топик внутренний. Он добавляет стоимость produce и consume.

Join stateful. Они используют store и changelog (тема 13).

## Exactly-once в Streams

Exactly-once в Streams означает, что обработка входной записи имеет один видимый эффект на выходные топики и на внутреннее состояние, которым управляет Streams. Он использует транзакционный протокол Kafka (тема 7).

Вы задаёте `processing.guarantee` в `exactly_once_v2` (текущее имя; старые версии использовали `exactly_once`). Streams оборачивает consume, обновление состояния и produce в транзакцию. Перезапуск не применяет тот же вход дважды к выходу.

`exactly_once_v2` нужны брокеры, которые это поддерживают. Текущая Apache Kafka на KRaft это поддерживает. Прочитайте матрицу версий в официальных документах.

EOS не покрывает побочные эффекты, которые вы добавляете в процессоре (вызовы HTTP, дополнительные записи в базу). Эти побочные эффекты могут выполниться дважды. Ставьте внешние записи за идемпотентным консьюмером или outbox (тема 19).

`at_least_once` — другая обычная гарантия. Она проще и может писать дубликаты в sink.

Идемпотентные продюсеры — часть пути EOS. Вам всё ещё нужно понять тему 7.

Изоляция: транзакционные консьюмеры sink должны использовать `isolation.level=read_committed`, если не должны видеть прерванные записи (тема 7).

Не включайте EOS только на продюсере sink, пока приложение Streams использует at-least-once. Задайте гарантию Streams.

## Интерактивные запросы (высокий уровень)

Интерактивные запросы позволяют читать хранилище состояния, пока экземпляры Streams работают. Store — тот же store, который обновляет топология. Для простого поиска по ключу этого состояния отдельная база данных не нужна.

Каждый экземпляр держит только партиции, которыми владеет. Запрос ключа должен идти к экземпляру, который владеет этим ключом. Kafka Streams открывает метаданные: какой экземпляр хостит какую партицию store. Вы добавляете RPC (HTTP или другой протокол) между экземплярами.

Если запросить неверный экземпляр, ключа нет или нужно переслать запрос. Постройте тонкий API запросов перед экземплярами.

Интерактивные запросы eventually consistent с входным журналом. Запись, которая ещё не обработана, не в store. EOS и восстановление влияют на то, когда ключ появляется.

Не используйте интерактивные запросы как базу данных общего назначения. Нет богатого языка произвольных запросов. Доступность зависит от экземпляров Streams. Если все экземпляры остановятся, запросы останавливаются.

Этот раздел — высокий уровень. Прочитайте `ReadOnlyKeyValueStore` и `StreamsMetadata` в официальных документах, когда реализуете.

KRaft не хостит API запросов. Брокеры хостят changelog. Ваш процесс хостит store и эндпоинт запросов.

## Тестирование топологий

Топологию можно тестировать без кластера Kafka. `TopologyTestDriver` (тестовая зависимость Java) подаёт входные записи и читает выходные записи. Вы управляете временем для окон.

Модульные тесты проверяют логику map, filter, join и агрегации. Вы подаёте список записей во имя исходного топика и утверждаете записи sink.

Интеграционные тесты используют настоящий кластер (EmbeddedKafka, Testcontainers или локальный брокер KRaft). Эти тесты проверяют Serdes, EOS и восстановление. Не пропускайте интеграционные тесты, если используете EOS или свои Serdes.

Тестируйте класс топологии, не только бизнес-функцию. Неверные Serdes или неверные окна join падают в рантайме.

Не используйте продакшен `application.id` и продакшен-топики в тестах. Используйте тестовые имена.

Тестовый драйвер не заменяет нагрузочный тест (тема 16). Он не заменяет эксплуатационный тест rolling restart (тема 15).

Пример формы теста:

```text
TopologyTestDriver driver = new TopologyTestDriver(topology, props);
TestInputTopic<...> input = driver.createInputTopic(...);
TestOutputTopic<...> output = driver.createOutputTopic(...);
input.pipeInput(key, value);
assert output.readKeyValue() ...
```

1. Напишите шпаргалку на одну страницу: топология, KStream, KTable, DSL, Processor API, три join, ключ EOS, IQ, тестовый драйвер.
2. Нарисуйте полную схему: два исходных топика, join, store, changelog, sink, стрелка запроса.
3. Добавьте в закладки официальные страницы DSL Streams, EOS и тестирования.
4. Назовите каждый топик, который нужна этой образцовой задаче: `orders.placed`, `customers`, sink плюс два внутренних вида.

#### Средние практические задания

1. Соберите одну задачу, которая использует filter, stream-table join и sink. Протестируйте топологию модульно. Запустите на KRaft. Сохраните конфиги (`application.id`, гарантия).
2. Сопоставьте каждый подраздел с одним официальным URL.
3. Сбросьте или замените `application.id` в лаборатории после изменения топологии. Запишите шаги очистки топиков, которые использовали.

#### Сложные практические задания

1. Добавьте интерактивные запросы и EOS к задаче. Уроните один экземпляр. Запросите ключ и прочитайте sink. Запишите, что осталось корректным.
2. Напишите продакшен-стандарт Streams: версия Java, bootstrap KRaft, `processing.guarantee`, слои тестов, без ZooKeeper, именование `application.id`.

# 2. Многоуровневые модели

## Описание

Многоуровневая модель делит сетевую работу на уровни. У каждого уровня своя задача. Каждый уровень использует уровень ниже и обслуживает уровень выше. Эта тема показывает карту семи уровней OSI и карту четырёх уровней TCP/IP. Вы также узнаете инкапсуляцию, заголовки и принцип сквозной передачи.

Используйте один термин для каждого понятия. Уровень — ступень с ясной задачей. Заголовок — дополнительные байты, которые добавляет уровень. Инкапсуляция — обёртывание данных заголовком. Завершите эту тему до изучения физического уровня и канального уровня.

Модели — карты. Они помогают говорить и отлаживать. Они не закон. Реальные системы могут делить или сливать задачи.

## Семь уровней OSI (карта, не закон)

Модель OSI имеет семь уровней. Модель — учебная карта. Поставщики и RFC не следуют каждому имени OSI в повседневной работе. Вы всё равно используете карту, чтобы разместить проблему.

Семь уровней снизу:

1. Physical: биты на среде (напряжение, свет, радио)
2. Data link: кадры на одном канале, локальные адреса
3. Network: пакеты через много хопов, логические адреса
4. Transport: сквозной поток байтов или датаграммы, порты
5. Session: диалоги и контрольные точки (редко отдельный ящик в IP-сетях)
6. Presentation: синтаксис и кодирование (часто часть приложения)
7. Application: протокол пользователя (HTTP, DNS, SMTP)

Используйте карту, когда спрашиваете: плохой кабель, неверный MAC, неверный IP, закрытый порт или неверный запрос HTTP? Этот список вопросов идёт по уровням снизу.

Не делайте из OSI религию. Session и presentation часто живут в программе приложения. Ethernet и IP не используют пакеты сессии OSI. Ценность OSI — общий словарь.

Когда человек говорит «Layer 2», часто имеют в виду канал. Когда говорят «Layer 3», часто имеют в виду IP. Когда говорят «Layer 4», часто имеют в виду TCP или UDP. Когда говорят «Layer 7», часто имеют в виду протокол приложения.

## Четыре уровня TCP/IP: link, internet, transport, application

Модель TCP/IP, которую использует этот справочник, имеет четыре уровня:

1. Link: сетевой интерфейс, Ethernet, Wi-Fi, кадры, MAC-адреса
2. Internet: IP, маршрутизация, ICMP
3. Transport: TCP, UDP, порты
4. Application: HTTP, DNS, TLS как его используют приложения, и другие протоколы пользователя

Некоторые тексты добавляют физический уровень под канальным. Этот справочник держит биты на среде в теме физического и канального уровней. Список из четырёх уровней всё равно совпадает с тем, как вы читаете пакет: кадр, IP, TCP или UDP, затем байты приложения.

Интернет-уровень доставляет пакеты на IP-адрес назначения. Транспортный уровень доставляет данные на порт на этом хосте. Уровень приложения задаёт смысл байтов.

IP может работать на многих типах каналов. TCP и UDP могут работать на IPv4 и IPv6. HTTP может работать на TCP (и позже на QUIC). Эта независимость — смысл уровней.

В лабораторных заметках используйте имена TCP/IP. Номера OSI используйте только когда их использует собеседник. Не смешивайте «Layer 3» и «internet layer» в одном предложении без карты.

Ядро и сетевая карта реализуют нижние уровни. Программа реализует уровень приложения. Сокеты — API между программой и транспортным уровнем.

## Инкапсуляция и декапсуляция

Инкапсуляция — шаг обёртки. Приложение отправителя даёт байты TCP или UDP. Транспортный уровень добавляет транспортный заголовок. IP добавляет заголовок IP. Канальный уровень добавляет заголовок кадра и часто трейлер (FCS). Физический уровень отправляет биты.

Декапсуляция — шаг развёртки. Канальный уровень приёмника проверяет кадр. IP проверяет заголовок IP и передаёт полезную нагрузку TCP или UDP. Транспортный уровень проверяет порт и передаёт полезную нагрузку приложению.

Каждый уровень считает байты с уровня выше полезной нагрузкой. В этой нагрузке могут быть ещё заголовки. Инструмент захвата показывает вложенные заголовки.

На обратном пути тот же процесс идёт на другом хосте. Промежуточные хопы часто декапсулируют только до интернет-уровня. Маршрутизатор читает заголовок IP, затем инкапсулирует пакет в новый кадр для следующего канала. Маршрутизатору не нужны байты HTTP.

Не добавляйте новый заголовок, который следующий хоп не сможет разобрать. Не считайте, что каждый хоп видит полезную нагрузку приложения. Многие хопы видят только внешние заголовки.

Туннелирование — инкапсуляция пакета внутри другого пакета. VPN может положить IP внутрь UDP внутрь IP. Идея та же обёртка. Поздние темы могут использовать эту идею. Этой теме нужны только базовая обёртка и развёртка.

## Что добавляет каждый уровень (заголовок)

Заголовок — структурированный набор полей в начале единицы данных протокола. Трейлер — дополнительные байты в конце. У Ethernet часто есть контрольная последовательность кадра как трейлер.

Типичные добавления:

- Link (Ethernet): destination MAC, source MAC, Ethertype, затем полезная нагрузка, затем FCS
- Internet (IPv4): version, header length, total length, TTL, protocol, header checksum, source IP, destination IP
- Internet (IPv6): version, payload length, next header, hop limit, source IP, destination IP
- Transport (UDP): source port, destination port, length, checksum
- Transport (TCP): source port, destination port, sequence number, acknowledgment number, flags, window, checksum
- Application: method, URL path, headers, body (HTTP) или сообщение запроса DNS

Каждый заголовок отвечает на вопрос. Ethernet: какая NIC на этом канале. IP: какой хост в интернете. TCP или UDP: какой сокет. HTTP: какой ресурс и какой метод.

Поле protocol в IPv4 (или поле next-header в IPv6) называет тип полезной нагрузки. Ethertype называет тип полезной нагрузки кадра. Порты называют сокет приложения, а не синтаксис нагрузки. Заголовок приложения называет смысл остального.

Размер заголовка имеет цену. Маленькая полезная нагрузка с большим заголовком тратит ёмкость. Поздние темы покрывают MTU и сегментацию.

Не выдумывайте имена полей. Используйте имена, которые используют инструмент захвата и RFC. Не пропускайте заголовок при отладке. Неверный MAC и неверный IP — разные неисправности.

## Принцип сквозной передачи (обзор)

Принцип сквозной передачи говорит: ставьте функцию на концы, когда функции нужны знания приложения. Сеть посередине должна оставаться простой. Надёжность, шифрование и смысл приложения часто принадлежат хостам.

Пример: IP не повторяет ваш файл. TCP на двух хостах может повторить. Маршрутизаторы посередине пересылают пакеты. Они не хранят весь файл.

Пример: сеть не может знать полный смысл банковского перевода. Приложение и TLS на концах защищают смысл.

Принцип — обзорный. Реальные сети добавляют промежуточные устройства: NAT, межсетевые экраны, балансировщики нагрузки. Эти ящики ломают простую картину. Поздние темы покрывают NAT и middlebox. Вы всё равно используете принцип, чтобы спросить: эта функция должна сидеть в каждом маршрутизаторе или только в двух программах?

Функции, которые нужны каждому хопу, могут сидеть в сети. Пример: контрольная сумма на одном канале или TTL, чтобы петля умерла. Функции, которые понимают только два приложения, должны сидеть на концах.

Не ждите, что Internet сохранит порядок ваших байтов и ваши повторы, если это не делает транспорт или приложение. Не кладите политику приложения в каждый коммутатор.

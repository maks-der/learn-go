# 10. Транзакции и конкурентный доступ

## Описание

Эта тема показывает транзакции и конкурентный доступ в PostgreSQL 16 и PostgreSQL 17. Вы узнаёте MVCC, уровни изоляции, блокировки строк, консультативные блокировки, взаимные блокировки и снимки. При MVCC читатели не блокируют писателей для обычного `SELECT`.

Сначала завершите тему 9. Вы умеете читать планы. Завершите эту тему до изучения vacuum.

Используйте один термин для каждого понятия. Транзакция — группа операторов, которые фиксируются или откатываются вместе. Изоляция — насколько одна транзакция видит другую. Снимок — набор транзакций, которые видны. Блокировка ждёт или падает, когда другая сессия держит конфликтующую блокировку. MVCC значит Multi-Version Concurrency Control.

## MVCC в PostgreSQL (читатели не блокируют писателей)

PostgreSQL хранит больше одной версии строки. `UPDATE` пишет новый кортеж и помечает старый как мёртвый. `DELETE` помечает кортеж как мёртвый. `SELECT` использует снимок. `SELECT` читает версию, видимую этому снимку. Он не ждёт писателя, который меняет другую версию.

Правила, которые новичок должен помнить:

- Обычный `SELECT` не берёт блокировку строки.
- Обычный `SELECT` не ждёт `UPDATE` или `DELETE` той же строки.
- `UPDATE` ждёт другой `UPDATE` (или `SELECT FOR UPDATE`) той же строки.
- Мёртвые кортежи остаются до `VACUUM` (тема 11).

У каждого кортежа есть скрытые системные столбцы. Часть можно выбрать:

```sql
SELECT xmin, xmax, ctid, * FROM items WHERE id = 1;
```

`xmin` — id вставляющей транзакции (отображение 32-битного xid). `ctid` — физическое расположение `(page, offset)`. После `UPDATE` `ctid` меняется. Логический `id` остаётся тем же.

Поскольку читатели не блокируют писателей, PostgreSQL может обслуживать много чтений во время записей. Писатели всё равно конфликтуют с писателями той же строки.

`INSERT` нового ключа не ждёт `SELECT`. Уникальные индексы всё равно заставляют двух вставщиков одного ключа сериализоваться.

MVCC — не то же самое, что «без блокировок». DDL берёт более сильные блокировки. `SELECT FOR UPDATE` берёт блокировки строк. Внешние ключи берут блокировки. Поздние разделы темы это разбирают.

Не используйте `SELECT` как блокировку. Если нужно остановить другого писателя, используйте `SELECT ... FOR UPDATE` или `UPDATE`.

## Уровни изоляции; по умолчанию read committed

SQL определяет уровни изоляции. PostgreSQL реализует:

| Уровень | Поведение PostgreSQL |
| --- | --- |
| `READ UNCOMMITTED` | То же, что `READ COMMITTED`. Грязных чтений нет. |
| `READ COMMITTED` | По умолчанию. Каждый оператор видит строки, зафиксированные до старта этого оператора. |
| `REPEATABLE READ` | Снимок с первого оператора. Поздние операторы той же транзакции видят тот же снимок. |
| `SERIALIZABLE` | Повторяемое чтение плюс проверки, которые предотвращают больше аномалий. Транзакция может упасть с ошибкой сериализации. |

Задать уровень:

```sql
BEGIN TRANSACTION ISOLATION LEVEL READ COMMITTED;
-- statements
COMMIT;

BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

`default_transaction_isolation` — `read committed`, если не сменить.

Факты **read committed**:

- Оператор 1 может видеть версию строки V1. После того как другая сессия зафиксирует обновление, оператор 2 в той же транзакции может видеть V2.
- Неповторяемые чтения возможны. Фантомные строки возможны.
- `UPDATE` находит последнюю зафиксированную версию и ждёт при необходимости. Затем заново оценивает `WHERE` на этой версии.

Большинство транзакционных приложений используют read committed. Это правильное значение по умолчанию.

Незафиксированные данные другой транзакции читать нельзя. Грязного чтения нет.

Показать текущий уровень:

```sql
SHOW transaction_isolation;
SELECT current_setting('transaction_isolation');
```

Не поднимайте глобальное значение по умолчанию до `serializable` без плана повторов. Не считайте, что `READ UNCOMMITTED` даёт грязные чтения. Не даёт.

## `REPEATABLE READ` и `SERIALIZABLE`

**Повторяемое чтение** берёт снимок на первом запросе (или первом операторе, которому нужны данные). Все поздние операторы `SELECT` видят этот снимок. Если вы `UPDATE` строку, которую другая транзакция зафиксировала после вашего снимка, PostgreSQL может выдать:

```text
ERROR:  could not serialize access due to concurrent update
```

Эта ошибка — сбой сериализации. Откатываете и повторяете транзакцию.

Повторяемое чтение в PostgreSQL использует изоляцию снимков. Некоторые аномалии write-skew всё ещё возможны. Две транзакции могут писать разные строки, которые вместе ломают правило, которого ни одна транзакция не видела.

**Serializable** использует Serializable Snapshot Isolation (SSI). Сервер отслеживает зависимости чтение/запись. Если появляется опасный шаблон, одна транзакция падает с ошибкой сериализации. Когда все транзакции, которые касаются тех же данных, используют `SERIALIZABLE` и повторяют при сбое, результат совпадает с одним последовательным порядком.

```sql
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
-- reads and writes
COMMIT;
```

Правила:

- Приложение должно повторять при сбое сериализации (`SQLSTATE 40001`).
- Все сессии, которым нужна гарантия, должны использовать `SERIALIZABLE`.
- У serializable больше накладных расходов, чем у read committed.
- Транзакции serializable только на чтение могут использовать более безопасный режим снимка.

Используйте повторяемое чтение для согласованных отчётов из многих операторов. Используйте serializable, когда бизнес-правило не может принять write skew и вы напишете цикл повтора. Используйте read committed для большей части транзакционной работы.

Не игнорируйте ошибки сериализации. Не повторяйте бесконечно без паузы и лимита.

## Блокировки строк: `SELECT ... FOR UPDATE`

`SELECT ... FOR UPDATE` блокирует выбранные строки. Другая сессия, которая хочет `UPDATE`, `DELETE` или `SELECT FOR UPDATE` этих строк, ждёт (или падает с `NOWAIT`).

```sql
BEGIN;
SELECT * FROM items WHERE id = 1 FOR UPDATE;
-- other statements
COMMIT;
```

Силы блокировки (среди этих четырёх самая сильная последняя):

- `FOR KEY SHARE` — допускает обновления, которые не меняют ключ; используют внешние ключи
- `FOR SHARE` — разделяемая блокировка; блокирует `FOR UPDATE`
- `FOR NO KEY UPDATE` — как обновление, но не блокирует `KEY SHARE`
- `FOR UPDATE` — блокирует другие исключительные блокировки строк и обновления

Опции:

- `NOWAIT` — ошибка вместо ожидания
- `SKIP LOCKED` — пропустить уже заблокированные строки (очереди работ)
- `OF table` — блокировать строки одной таблицы в соединении

```sql
SELECT id FROM jobs
WHERE status = 'new'
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT 1;
```

Блокировка длится до конца транзакции. `COMMIT` или `ROLLBACK` её освобождает.

`FOR UPDATE` не блокирует всю таблицу. Другие строки остаются доступны.

Используйте блокировки строк, когда читаете значение и затем пишете решение (проверка баланса, захват задания). Не держите транзакцию открытой, пока ждёте пользователя в браузере.

Посмотреть блокировки:

```sql
SELECT * FROM pg_locks;
SELECT * FROM pg_stat_activity WHERE wait_event_type = 'Lock';
```

## Консультативные блокировки

Консультативные блокировки — блокировки, которые определяет приложение. PostgreSQL не привязывает их к строке таблицы. Передаёте целочисленные ключи.

Блокировки уровня сессии остаются, пока не снимете или сессия не закончится:

```sql
SELECT pg_advisory_lock(42);
-- work
SELECT pg_advisory_unlock(42);
```

Блокировки уровня транзакции остаются до `COMMIT` или `ROLLBACK`:

```sql
BEGIN;
SELECT pg_advisory_xact_lock(42);
COMMIT;  -- lock released
```

Формы с двумя аргументами используют пару ключей `int4`: `pg_advisory_lock(1, 2)`.

`pg_try_advisory_lock` возвращает `false` вместо ожидания.

Применения:

- одиночный cron: ключ блокировки 1001 в начале; пропустить, если блокировка занята
- мигрировать ресурс, у которого ещё нет строки
- сериализовать работу, которая охватывает больше одной таблицы

Правила:

- Выберите карту ключей и запишите её. Избегайте столкновений.
- Предпочитайте транзакционные блокировки, когда работа — одна транзакция.
- У блокировок сессии должно быть парное снятие на каждом пути. Забытое снятие блокирует других до отключения.
- Консультативные блокировки не переживают сбой как данные. Они не ограничения.

Смотрите удерживаемые консультативные блокировки в `pg_locks`, где `locktype = 'advisory'`.

Не используйте консультативные блокировки вместо ограничения уникальности. Не используйте их вместо `FOR UPDATE`, когда строка есть.

## Взаимные блокировки в журналах

Взаимная блокировка случается, когда сессия A ждёт сессию B, а сессия B ждёт сессию A. PostgreSQL обнаруживает цикл. Он прерывает одну транзакцию:

```text
ERROR:  deadlock detected
```

Другая транзакция продолжается. Прерванная сессия должна повторить.

Типичная причина: две транзакции обновляют те же две строки в противоположном порядке.

```text
Session A: UPDATE t SET ... WHERE id = 1;
Session B: UPDATE t SET ... WHERE id = 2;
Session A: UPDATE t SET ... WHERE id = 2;  -- waits
Session B: UPDATE t SET ... WHERE id = 1;  -- deadlock
```

Профилактика:

- Всегда обновляйте строки в одном порядке (пример: по `id`)
- Держите транзакции короткими
- Не держите блокировки, пока ждёте сеть

PostgreSQL пишет строку деталей, которая показывает два процесса. `log_lock_waits` и `deadlock_timeout` управляют журналированием ожиданий. `deadlock_timeout` — как долго длится ожидание, прежде чем сервер проверит взаимную блокировку (по умолчанию `1s`).

```sql
SHOW deadlock_timeout;
SHOW log_lock_waits;
```

Журнал сервера (или `stderr` в Docker) содержит отчёт о взаимной блокировке. `psql` показывает ошибку клиенту, который проиграл.

Взаимная блокировка — не сбой. Это обычная ошибка при конкурентном доступе. Приложение повторяет.

Не поднимайте `deadlock_timeout`, чтобы скрыть ошибку порядка блокировок. Исправьте порядок.

## `txid` / снимки (осведомлённость)

Снимок говорит, какие id транзакций видны. В обычном SQL снимок вручную не задаёте. Его задают уровни изоляции.

Старые функции используют префикс `txid_`. В текущем PostgreSQL также есть функции `xid8`:

```sql
SELECT pg_current_xact_id();           -- xid8, assigns an xid if needed
SELECT pg_current_xact_id_if_assigned();
SELECT pg_current_snapshot();
SELECT pg_snapshot_xmin(pg_current_snapshot());
SELECT pg_snapshot_xmax(pg_current_snapshot());
```

Старые псевдонимы всё ещё есть (`txid_current()`, `txid_current_snapshot()`). В новой работе на PostgreSQL 16 и 17 предпочитайте имена `pg_current_*`.

`pg_current_xact_id()` назначает id транзакции, если у транзакции его ещё нет. Транзакция только на чтение может обойтись без xid, пока не пишет. Используйте `pg_current_xact_id_if_assigned()`, когда назначать нельзя.

У снимка есть `xmin`, `xmax` и список xid в процессе. Правила видимости используют эти значения. Полные правила не нужны, чтобы писать прикладной SQL. Нужно знать:

- Vacuum и wraparound используют xid (тема 11)
- `xmin` на кортеже — вставляющий xid
- Повторяемое чтение и serializable замораживают видимость на одном снимке

```sql
SELECT xmin, xmax FROM items;
```

Не используйте xid как прикладные ключи. Xid заворачиваются (тема 11). Не сравнивайте xid как целые в коде приложения.

Этот раздел — осведомлённость. Xid снова встретите, когда будете изучать freeze и wraparound.

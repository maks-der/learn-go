# 12. Схемы, роли и безопасность

## Описание

Эта тема показывает роли, привилегии и безопасность подключений в PostgreSQL 16 и PostgreSQL 17. Вы узнаёте роли входа, `GRANT` и `REVOKE`, привилегии по умолчанию, безопасность на уровне строк, функции `SECURITY DEFINER`, SSL и почему приложение не должно использовать суперпользователя.

Сначала завершите тему 11. Вы умеете обслуживать кластер. Завершите эту тему до написания функций и триггеров.

Используйте один термин для каждого понятия. Роль — учётная запись кластера. Пользователь — роль с `LOGIN`. Привилегия — именованное право на объект. Политика — фильтр строк для безопасности на уровне строк. Прикладная роль — вход, который использует программа. Суперпользователь — роль с `SUPERUSER`. Этот справочник рассчитан на PostgreSQL 16 и PostgreSQL 17.

## Роли против пользователей (пользователь — роль с входом)

PostgreSQL хранит учётные записи как роли. Роль с `LOGIN` может открыть сессию. Роль без `LOGIN` — группа. В старых текстах «пользователь» — роль входа. `CREATE USER name` это `CREATE ROLE name LOGIN`. В новых скриптах предпочитайте `CREATE ROLE`, чтобы атрибуты были видны.

```sql
CREATE ROLE shop_read NOLOGIN;
CREATE ROLE shop_app LOGIN PASSWORD 'secret';
GRANT shop_read TO shop_app;
```

`shop_app` может использовать привилегии `shop_read`, когда `shop_app` наследует членство. PostgreSQL 16 и 17 позволяют задать `INHERIT` и `SET` на каждом членстве. `INHERIT true` добавляет привилегии группы члену. `SET true` позволяет члену выполнить `SET ROLE` на эту группу.

Полезные атрибуты роли:

- `LOGIN` / `NOLOGIN` — сессия или группа
- `INHERIT` / `NOINHERIT` — наследование привилегий группы по умолчанию (умолчание уровня роли)
- `CREATEDB` — создавать базы
- `CREATEROLE` — создавать роли
- `REPLICATION` — подключения репликации
- `BYPASSRLS` — пропускать безопасность на уровне строк
- `SUPERUSER` — почти все проверки выключены

Роль принадлежит кластеру. Роль не создают внутри одной базы. Привилегии на объекты всё равно действуют внутри каждой базы.

`PUBLIC` — особая неявная цель grant. Каждая роль — член `PUBLIC`. В PostgreSQL 15 и новее у `PUBLIC` нет `CREATE` на схеме `public`. PostgreSQL 16 и 17 сохраняют это правило.

Просмотреть роли:

```sql
SELECT rolname, rolsuper, rolcanlogin, rolbypassrls
FROM pg_roles
ORDER BY rolname;
```

`\du` в `psql` перечисляет роли. Тема 1 представила `createuser`. Используйте SQL, когда нужны все атрибуты.

Не делите одну роль входа между несвязанными программами. Не кладите продакшен-пароль в справочник или коммит git.

## `GRANT` / `REVOKE` на таблицы, схемы, последовательности

Привилегия — право, которое выдаёте на объект. Владелец объекта имеет все привилегии. Другим ролям нужен `GRANT`. `REVOKE` снимает привилегию.

Привилегии схемы:

- `USAGE` — искать объекты в схеме
- `CREATE` — создавать объекты в схеме

Привилегии таблицы включают `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES` и `TRIGGER`. Привилегии последовательности включают `USAGE`, `SELECT` и `UPDATE`. Столбцы identity используют последовательность. `INSERT`, который использует identity, нуждается в `USAGE` последовательности.

```sql
CREATE SCHEMA shop;
CREATE TABLE shop.items (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name text NOT NULL
);

GRANT USAGE ON SCHEMA shop TO shop_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON TABLE shop.items TO shop_app;
GRANT USAGE, SELECT ON SEQUENCE shop.items_id_seq TO shop_app;
```

Можно выдать на каждую текущую таблицу в схеме:

```sql
GRANT SELECT ON ALL TABLES IN SCHEMA shop TO shop_read;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA shop TO shop_app;
```

`ALL TABLES` применяется к таблицам, которые есть сейчас. Не применяется к таблицам, которые создадите позже. Привилегии по умолчанию покрывают поздние объекты.

`CONNECT` — привилегия базы. Без `CONNECT` роль не может открыть сессию на этой базе.

```sql
GRANT CONNECT ON DATABASE shop TO shop_app;
REVOKE CONNECT ON DATABASE shop FROM PUBLIC;
```

`REVOKE` у `PUBLIC` — частый шаг укрепления после выдачи `CONNECT` именованным ролям.

`psql` показывает привилегии через `\dp` (таблицы) и `\dn+` (схемы). Представления каталога `information_schema.role_table_grants` и `pg_class.relacl` тоже хранят grant.

Не выдавайте `ALL` на каждый объект прикладной роли, когда программе нужны только `SELECT` и `INSERT`. Не выдавайте привилегии таблицы без `USAGE` на схеме. Без `USAGE` схемы роль не увидит таблицу.

Официальный справочник: [https://www.postgresql.org/docs/17/sql-grant.html](https://www.postgresql.org/docs/17/sql-grant.html) и тот же путь под `/docs/16/`.

## Привилегии по умолчанию

`ALTER DEFAULT PRIVILEGES` задаёт grant для объектов, которые роль создаст позже. Объекты, которые уже есть, не меняет.

```sql
ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA shop
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO shop_app;

ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA shop
    GRANT USAGE, SELECT ON SEQUENCES TO shop_app;

ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA shop
    GRANT SELECT ON TABLES TO shop_read;
```

`FOR ROLE migrator` значит: когда `migrator` создаёт таблицу в `shop`, применить эти grant. Если таблицу создаёт `shop_app`, эти умолчания не применяются, пока не добавите второй `ALTER DEFAULT PRIVILEGES FOR ROLE shop_app`.

Привилегии по умолчанию — на базу. Оператор нужно выполнять, пока подключены к целевой базе.

Показать умолчания:

```sql
SELECT defaclrole::regrole, defaclnamespace::regnamespace, defaclobjtype, defaclacl
FROM pg_default_acl;
```

`psql` `\ddp` перечисляет привилегии по умолчанию.

Типичное разделение:

- `migrator` владеет таблицами и запускает `CREATE TABLE`
- у `shop_app` только DML
- привилегии по умолчанию выдают DML от `migrator` к `shop_app`

Не считайте, что `GRANT ON ALL TABLES` хватает после добавления таблиц. Снова запустите `ALL TABLES` или сначала задайте привилегии по умолчанию.

Не задавайте привилегии по умолчанию в `template1`, если не хотите, чтобы каждая новая база их наследовала.

## Безопасность на уровне строк (RLS)

Безопасность на уровне строк (RLS) добавляет политику на таблицу. После включения RLS обычная роль видит только строки, которые проходят `USING`. Вставки и обновления должны проходить `WITH CHECK`.

```sql
ALTER TABLE shop.orders ENABLE ROW LEVEL SECURITY;

CREATE POLICY orders_by_tenant ON shop.orders
    FOR ALL
    TO shop_app
    USING (tenant_id = current_setting('app.tenant_id')::bigint)
    WITH CHECK (tenant_id = current_setting('app.tenant_id')::bigint);
```

Сессия задаёт параметр, затем запрашивает:

```sql
SET app.tenant_id = '42';
SELECT * FROM shop.orders;
```

`current_setting('app.tenant_id')` падает, если параметра нет и вы не используете `missing_ok`. Используйте помощник `SECURITY DEFINER` или задайте параметр в контролируемом месте. Тема 13 разбирает риск функций. Держите выражение политики простым.

Владелец таблицы обходит RLS, пока не принудите:

```sql
ALTER TABLE shop.orders FORCE ROW LEVEL SECURITY;
```

Роль с `BYPASSRLS` или `SUPERUSER` тоже пропускает RLS. У прикладной роли не должно быть этих атрибутов.

Политики могут быть `FOR SELECT`, `FOR INSERT`, `FOR UPDATE`, `FOR DELETE` или `FOR ALL`. Можно прикрепить больше одной политики. Для одной команды PostgreSQL комбинирует разрешающие политики через `OR` (по умолчанию). Ограничивающие политики используют `AND`. Начинайте с одной разрешающей политики на таблицу.

`EXPLAIN` может показать фильтр политики как квалификатор. Тестируйте прикладной ролью, не владельцем.

Не считайте RLS единственным контролем. Всё равно нужен `GRANT`. Роль без `SELECT` не видит строк. Роль с `BYPASSRLS` видит все строки, которые позволяет `GRANT`.

Не включайте RLS и не забывайте `FORCE`, если владелец — также прикладная роль.

Официальный обзор: [https://www.postgresql.org/docs/17/ddl-rowsecurity.html](https://www.postgresql.org/docs/17/ddl-rowsecurity.html).

## Функции `SECURITY DEFINER` (опасность)

Функция по умолчанию выполняется с привилегиями вызывающего (`SECURITY INVOKER`). `SECURITY DEFINER` выполняется с привилегиями владельца. Используйте только когда вызывающему нельзя иметь эти привилегии, а тело функции — узкая проверенная операция.

Опасность: функция может трогать объекты, которые вызывающий трогать не может. Если функция использует неквалифицированные имена, `search_path` может указать на схему, которую контролирует вызывающий. Тогда функция может вызвать не ту функцию или использовать не ту таблицу.

Безопасный шаблон для PostgreSQL 16 и 17:

```sql
CREATE FUNCTION shop.touch_item(p_id bigint)
RETURNS void
LANGUAGE sql
SECURITY DEFINER
SET search_path = pg_catalog, shop
AS $$
    UPDATE shop.items SET name = name WHERE id = p_id;
$$;
```

`SET search_path` на функции фиксирует путь на время вызова. Включите `pg_catalog`. Включайте только схемы, которым доверяете. Некоторые команды используют `SET search_path = ''` и квалифицируют каждое имя.

Также:

- выдавайте `EXECUTE` только ролям, которым нужна функция
- отзывайте `EXECUTE` у `PUBLIC`, когда можете
- держите тело коротким
- предпочитайте `SECURITY INVOKER`, когда хватает `GRANT`
- не собирайте динамический SQL вместе с недоверенным текстом

`SECURITY DEFINER` плюс RLS легко ошибиться. Владелец функции может обойти RLS. Тестируйте настоящим вызывающим.

Не копируйте пример `SECURITY DEFINER` из интернета без фиксированного `search_path`. Не используйте `SECURITY DEFINER`, чтобы спрятать суперпользователя от приложения. Владелец функции не должен быть суперпользователем, если у задачи нет другого дизайна.

Официальное предупреждение: [https://www.postgresql.org/docs/17/sql-createfunction.html](https://www.postgresql.org/docs/17/sql-createfunction.html) (см. `SECURITY`).

## Подключения SSL

SSL шифрует TCP-сессию между клиентом и сервером. PostgreSQL 16 и 17 используют TLS. В старых текстах всё ещё говорят SSL. Имена настроек сохраняют `ssl`.

Сторона сервера (`postgresql.conf`):

- `ssl = on`
- `ssl_cert_file` и `ssl_key_file` — сертификат и ключ сервера
- необязательный `ssl_ca_file` — когда проверяете клиентские сертификаты

`pg_hba.conf` может требовать SSL:

```text
hostssl shop shop_app 10.0.0.0/8 scram-sha-256
```

`hostssl` совпадает только с SSL-подключениями. `hostnossl` совпадает только с не-SSL. `host` совпадает с обоими.

Клиентский `sslmode` (libpq):

| Значение | Смысл |
| --- | --- |
| `disable` | без SSL |
| `allow` / `prefer` | пробовать оба; `prefer` — умолчание libpq |
| `require` | SSL обязателен; проверка сертификата нет |
| `verify-ca` | SSL плюс сертификат сервера, подписанный вашим CA |
| `verify-full` | `verify-ca` плюс совпадение имени хоста |

Продакшен-клиенты используют `verify-full`, когда контролируете CA и имя хоста. `require` останавливает открытый текст. Не останавливает неверный сервер.

URI подключения:

```text
postgresql://shop_app@db.example:5432/shop?sslmode=verify-full
```

`psql` показывает SSL после подключения, когда выполняете `\conninfo`.

Не открывайте `5432` в публичный интернет и не полагайтесь только на SSL. Тема 21 разбирает сетевые правила. SSL не заменяет пароли или `pg_hba.conf`.

Не кладите закрытые ключи в образ приложения без хранилища секретов.

Официальная страница SSL: [https://www.postgresql.org/docs/17/ssl-tcp.html](https://www.postgresql.org/docs/17/ssl-tcp.html).

## Суперпользователь: почти никогда для прикладной роли

Суперпользователь обходит большинство проверок привилегий. Суперпользователь может читать и писать файлы, которые может читать пользователь ОС, запускать `COPY` из файлов, менять роли и пропускать RLS. Роль по умолчанию `postgres` — суперпользователь.

Прикладная роль должна быть обычным входом:

```sql
CREATE ROLE shop_app LOGIN PASSWORD 'secret';
-- no SUPERUSER, no BYPASSRLS, no REPLICATION
```

Используйте суперпользователя (или узкую админскую роль) для:

- `CREATE EXTENSION` в некоторых установках
- полного `pg_dumpall` ролей
- восстановления после сбоя и ремонта каталога
- первой установки

Используйте роль мигратора с `CREATE` на прикладной схеме для `CREATE TABLE`. Эта роль всё равно не суперпользователь.

Проверить текущую роль:

```sql
SELECT current_user, session_user;
SELECT rolsuper FROM pg_roles WHERE rolname = current_user;
```

Если программа подключается как `postgres`, каждая SQL-инъекция или украденный пароль — полный компромисс кластера.

Облачные вендоры часто прячут настоящего суперпользователя и дают мощную админскую роль. Относитесь к этой админской роли так же: «не для приложения».

Не выдавайте `SUPERUSER`, чтобы отладить ошибку привилегии. Выдайте недостающую привилегию. Не оставляйте личный пароль суперпользователя в пуле подключений.

Тема 21 повторяет наименьшие привилегии для продакшена.

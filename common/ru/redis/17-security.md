# 17. Безопасность

## Описание

Redis не стартует как публичный интернет-сервис. Эта тема покрывает пароли, ACL, адреса привязки, защищённый режим, TLS и команды, которые могут уничтожить данные или остановить экземпляр.

Завершите эту тему до размещения Redis в общей сети. Используйте лабораторный экземпляр для каждого практического задания, которое меняет аутентификацию или имена команд. Не практикуйте на общем промышленном экземпляре.

Используйте один термин для каждого понятия. Аутентификация — доказательство личности Redis. Пользователь ACL — именованная учётная запись со списком команд и шаблоном ключей. Защищённый режим — безопасность по умолчанию, когда у Redis нет привязки и нет пароля. TLS шифрует соединение. Опасная команда — команда, которая может стереть данные, остановить сервер или сменить настройки безопасности.

Эта тема — укрепление. Она не описывает атаки.

## `requirepass` / ACL (Redis 6+)

Старый Redis использовал один пароль на весь экземпляр:

```text
CONFIG SET requirepass labpass
AUTH labpass
```

`requirepass` — один общий секрет. Каждый клиент, который его знает, имеет полную власть. Redis 6 добавляет списки контроля доступа (ACL). Предпочитайте ACL на Redis 6 и новее.

Идеи ACL:

- Есть пользователь default. Можно задать ему пароль или отключить.
- `ACL SETUSER` создаёт или меняет пользователя.
- У пользователя есть правила: команды (`+GET`, `-FLUSHALL`), категории (`+@read`) и шаблоны ключей (`~cache:*`).
- `AUTH username password` выбирает пользователя.

```text
ACL LIST
ACL WHOAMI
ACL SETUSER app on >apppass ~cache:* +@read +SET +DEL -@dangerous
```

Детали синтаксиса на страницах команд `ACL`. Проверьте версию. Префикс `>` в `SETUSER` задаёт пароль. `on` включает пользователя.

Клиенты приложения используют пользователя с наименьшими привилегиями. Человек-оператор использует более сильного пользователя для работы `CONFIG` и `ACL`. Не давайте приложению `FLUSHALL`, `DEBUG` или `KEYS`.

Храните пароли вне репозитория. Используйте менеджер секретов или окружение. Не кладите промышленные пароли в историю оболочки, если можете использовать запрос или файл с жёсткими правами.

`ACL SAVE` пишет файл ACL, когда используете файл ACL. `CONFIG REWRITE` может сохранить изменения `redis.conf`. Пароль `CONFIG SET`, который не сохраняете, может исчезнуть после перезапуска. Проверяйте перезапуск.

Хостинговый Redis часто требует пользователя и TLS. Следуйте документации вендора.

## Адрес привязки и защищённый режим

`bind` задаёт адреса, на которых Redis слушает.

```text
CONFIG GET bind
```

`bind 127.0.0.1` (и `::1` для IPv6 localhost) принимает только локальных клиентов. Это верный режим по умолчанию для лабораторного ноутбука.

`bind 0.0.0.0` слушает на всех адресах IPv4. Любой хост, который может достичь порта, может попытаться подключиться. Сочетайте это с отсутствием аутентификации — и у вас открытое хранилище данных в сети.

Защищённый режим: когда у Redis нет задуманной конфигурации bind и нет пароля, Redis может отказать удалённым командам. Клиент видит ошибку, которая говорит привязать или задать пароль.

```text
CONFIG GET protected-mode
```

Защищённый режим — страховочная сеть. Он не замена файрвола и ACL.

В Docker публикация `-p 6379:6379` может открыть Redis на хосте. Привязывайте внутри контейнера и публикуйте только на `127.0.0.1:6379` на хосте, когда учитесь:

```text
docker run --name redis-learn -p 127.0.0.1:6379:6379 redis
```

Группа безопасности облака или файрвол должны разрешать только подсети приложения. Не полагайтесь на «никто не знает IP».

`protected-mode no` плюс `bind 0.0.0.0` плюс нет ACL — неверная конфигурация. Не запускайте это в маршрутизируемой сети.

## TLS

TLS шифрует байты в сети. Без TLS перехват пакетов на пути может показать команды и значения. Пароли аутентификации тоже идут открытым текстом без TLS (RESP `AUTH`).

Redis может слушать с TLS (`tls-port`, сертификаты и связанные настройки `tls-*`). Точные имена файлов и флаги зависят от версии. Официальная документация: ищите «Redis TLS» на redis.io.

Типичные части:

- Серверный сертификат и закрытый ключ
- Сертификат CA, которому доверяют клиенты
- Необязательные клиентские сертификаты (взаимный TLS)
- `redis-cli --tls` и опции TLS клиентской библиотеки

Хостинговый Redis часто требует TLS. Вендор даёт пакет CA или URL «rediss://».

TLS не заменяет ACL. TLS защищает путь. ACL решают, что клиент может делать после подключения.

Сертификаты истекают. Перезапуск или отказ клиента после истечения — событие эксплуатации (тема 19). Календарите истечение.

Не отключайте проверку сертификата в промышленной среде, чтобы «заработало». Исправьте CA и имя хоста.

Локальная лаборатория Docker на `127.0.0.1` может пропустить TLS. Хост Redis в общей сети не должен пропускать TLS, если сеть уже не доверенная зашифрованная ткань, которую команда безопасности назвала эквивалентной.

## Опасные команды: `FLUSHALL`, `KEYS`, `DEBUG`, `CONFIG`

Некоторые команды верны в лаборатории и вредны на общем экземпляре.

`FLUSHALL` удаляет все ключи на экземпляре (все логические БД). `FLUSHDB` удаляет текущую логическую БД. Отката нет.

`KEYS` обходит пространство ключей в основном потоке. На большом экземпляре может остановить Redis (тема 12, тема 16).

`DEBUG` включает подкоманды, которые могут уронить процесс или заблокировать его (`DEBUG SEGFAULT`, `DEBUG SLEEP`). Это инструменты разработчика. Это не команды приложения.

`CONFIG GET` может раскрыть настройки. `CONFIG SET` может сменить bind, персистентность и каталоги. Клиент, который может `CONFIG SET`, может ослабить безопасность или сломать персистентность.

Другие команды того же класса: `SHUTDOWN`, `REPLICAOF` / `SLAVEOF`, `MODULE LOAD`, `SCRIPT DEBUG`. Категория ACL `@dangerous` группирует многие из них. Проверьте `ACL CAT dangerous` на вашей версии.

У пользователя приложения не должно быть этих команд. Оператор использует их в контролируемом окне с тикетом изменения.

Не запускайте `FLUSHALL` как шаг деплоя на долговечном Redis. Тема 13 и тема 21 объясняют прогрев кэша вместо этого.

## Переименование или отключение команд

Старые схемы переименовывали опасные команды в `redis.conf`:

```text
rename-command FLUSHALL ""
rename-command KEYS ""
rename-command CONFIG ""
```

Пустое новое имя отключает команду. Секретное имя скрывает команду от случайного использования. Секретное имя — слабый контроль. Имя может утечь. Предпочитайте ACL.

Redis 7+ устаревает `rename-command` в пользу ACL. Читайте комментарии в `redis.conf`. Если `rename-command` игнорируется или предупреждается, используйте `ACL SETUSER`, чтобы убрать команды.

Отключение значит сервер отклоняет команду для всех, включая вас, пока не смените конфигурацию и не перезапустите (или не держите одного пользователя-админа с командой). Планируйте, как ops всё ещё запустят контролируемый `CONFIG`, если отключите его глобально.

`COMMAND` перечисляет команды. После отключения имя исчезает или падает.

Не переименовывайте `AUTH` или `ACL` так, чтобы запереть себя на удалённом экземпляре. Держите путь локальной консоли (localhost, container exec), который проверили.

Код приложения должен использовать `SCAN`, а не переименованный `KEYS`. Если отключите `KEYS`, учебники, которые всё ещё показывают `KEYS *`, упадут. Это то, что нужно в промышленной среде.

## Не открывайте Redis в публичный интернет

Redis на публичном адресе без ACL и без TLS — риск утечки данных и стирания. Боты сканируют порт `6379`. Это частый класс инцидентов.

Нужные контроли (используйте все применимые):

- Привязка только к частным адресам
- Файрвол или группа безопасности: только подсети приложения
- Пользователи ACL с наименьшими привилегиями
- TLS на любом пути, который покидает доверенный хост
- Защищённый режим оставлен включённым, если bind и аутентификация не заданы намеренно
- Опасные команды запрещены пользователям приложения
- Нет публичного входящего `6379` / `tls-port`

«Временный тест» на `0.0.0.0` в облачной ВМ всё ещё публичный, если группа безопасности открыта.

Управляемый Redis в VPC всё ещё не публичный, если следуете модели частной конечной точки вендора. Публичные конечные точки нуждаются в дополнительном обзоре (TLS, сильная аутентификация, списки разрешённых IP).

Kubernetes: `Service` типа `LoadBalancer` на Redis может опубликовать его. Предпочитайте ClusterIP и сетевую политику.

Не кладите Redis в публичный интернет, чтобы «сэкономить время». Используйте туннель SSH, VPN или бастион, чтобы достичь лаборатории в облаке.

Если уже открыли лабораторию, считайте все ключи скомпрометированными. Смените пароли. Снимите экземпляр с публичного адреса. Запустите новый экземпляр для обучения, если не уверены.

3. Напишите команду туннеля, которую использовали бы, чтобы достичь удалённой лаборатории (локальный форвард SSH) без открытия `6379` миру. Не сканируйте чужие хосты.

#### Сложные практические задания

1. Напишите стандарт команды: bind, ACL, TLS, файрвол, запреты команд и ежеквартальный обзор.
2. Разберите существующий compose-файл или Helm-чарт для Redis. Отметьте публичные порты, отсутствующие пароли и отсутствующие пределы ресурсов. Запишите находки.

## Обзор темы

Эти вопросы не повторяют вопросы из разделов выше. Они охватывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Как bind, файрвол, TLS и ACL каждый останавливают разный отказ (достичь, подслушать, действовать)?
2. Почему одного `requirepass` недостаточно как промышленной истории на Redis 6+?
3. Какие опасные команды бьют доступность (`KEYS`, `DEBUG SLEEP`) против долговечности (`FLUSHALL`)?
4. Когда всё ещё использовать `rename-command` и когда отказываться?
5. Какой самый короткий верный ответ на «просто открой 6379, чтобы я отладил из дома»?

#### Простые практические задания

1. Напишите шпаргалку: `ACL LIST`, `AUTH`, `bind`, `protected-mode`, `--tls`, `FLUSHALL`, `rename-command`.
2. Экспортируйте `CONFIG GET bind`, `protected-mode` и `aclfile` (или связанное). Выделите их.
3. Нарисуйте атакующего в интернете и три закрытые двери (файрвол, TLS+аутентификация, ACL).
4. Напишите лабораторные правила: локальная привязка, одноразовые пароли, нет промышленного `FLUSHALL`.

#### Средние практические задания

1. Укрепите одноразовую лабораторию: пользователь ACL app, bind localhost, `FLUSHALL` запрещён. Подключитесь как app и как ops. Запишите обе сессии.
2. Напишите чеклист инцидента «Redis был привязан к 0.0.0.0 день»: сменить, аудит, пересобрать, обзор файрвола.
3. Сопоставьте каждую настройку клиента темы 12 (таймауты, пароль, TLS) с контролем безопасности этой темы.

#### Сложные практические задания

1. Сделайте одностраничный базовый уровень безопасности Redis для команды. Включите версии (ACL, TLS), сеть, команды и секреты.
2. Сравните базовый уровень с официальной страницей безопасности Redis. Добавьте любой контроль, который пропустили. Запишите URL.

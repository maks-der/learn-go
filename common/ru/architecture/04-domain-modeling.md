# 4. Моделирование предметной области

## Описание

Моделирование предметной области — работа по именованию бизнеса и по проведению границ вокруг смысла. Эта тема покрывает единый язык, ограниченные контексты, агрегаты, сущности, объекты-значения, доменные события и выборы согласованности внутри домена.

Домен — предметная область продукта (выдача книг, приём заказов, оценка экзаменов). Модель — набор типов, правил и имён, которые ПО использует для этого предмета. Слабая модель использует только технические имена (`table1`, `manager`, `data`). Сильная модель использует слова людей, которые делают работу.

Завершите темы 1–3 до этой темы. Держите модели маленькими. Этот справочник использует предметно-ориентированное проектирование (DDD) в практической форме. Большая церемония DDD не нужна.

Используйте один термин для каждого понятия. Сущность — не объект-значение. Ограниченный контекст — не разворачиваемый сервис. Доменное событие — не команда. Транзакционная согласованность — не итоговая согласованность.

## Единый язык и ограниченные контексты

Единый язык — общий набор имён, который команда и эксперты домена используют в речи, в документах и в коде. Одно понятие имеет одно имя. Это имя появляется в типах, именах таблиц, журналах и ADR.

Если эксперт говорит «выдача», а код говорит «contract_x», люди переводят вечно. Перевод порождает дефекты. Правило, которое формулирует эксперт, не совпадает с функцией, которую пишет разработчик.

Стройте язык из разговоров. Напишите короткий глоссарий. Включите:

- Имя
- Смысл в одном предложении
- Пример
- Отвергнутый синоним

Не изобретайте имена, которые звучат «более технически». Не используйте пустые имена (`Manager`, `Processor`, `Item2`). Предпочитайте `Loan`, `Hold`, `Fine`.

Ограниченный контекст — граница, внутри которой модель и язык согласованы. Внутри границы каждое имя имеет один смысл. Вне границы то же слово может значить другое.

Пример: «Order» в контексте покупок — покупка. «Order» в контексте склада — лист комплектации. Эти две модели не должны делить один тип, который пытается быть обоими.

Язык локален для ограниченного контекста. Слово «клиент» может значить два разных в двух контекстах. Не навязывайте одно глобальное имя, когда эксперты не согласны.

Ограниченный контекст — граница дизайна. Он может жить в модульном монолите как модуль. Позже он может стать сервисом. Контекст не автоматически сервис. Тема 3: не делите единицу развёртывания, пока не должны.

Между контекстами вы переводите. Опубликованное событие или DTO несёт данные, которые нужны другому контексту. Вы не делитесь внутренними сущностями. Антикоррупционный слой (тема 9) — переводчик, который защищает вашу модель от внешней модели.

Как найти первую карту контекстов:

- Слушайте одно слово с разными правилами.
- Ищите разных владельцев (команда биллинга против команды каталога).
- Ищите разные нужды согласованности.
- Ищите документ или экран, который сам по себе мир.

Держите первую карту маленькой. Двух или трёх контекстов достаточно для студенческой системы (каталог, выдача, идентичность). Карта с пятнадцатью контекстами для одного человека — чрезмерное проектирование (тема 3).

Когда язык меняется, модель должна меняться. Переименование в бизнесе — сигнал архитектуры. Обновляйте глоссарий и типы вместе.

Используйте язык в тестах. Тест с именем `cannot_return_loan_if_fine_is_open` учит правило. Тест с именем `test1` — нет.

## Агрегаты и границы согласованности

Агрегат — кластер доменных объектов, которые вы меняете как одну единицу. У агрегата есть корень. Все изменения идут через корень. Корень защищает инварианты.

Граница согласованности — край агрегата. Внутри границы можно использовать одну транзакцию и держать инварианты истинными вместе. Между агрегатами вы не используете одну большую транзакцию по умолчанию. Вы используете процесс, событие или более позднюю проверку.

Пример: агрегат `Loan` может включать заголовок выдачи и строки выдачи. Корень проверяет, что срок возврата и список предметов остаются допустимыми. `CatalogBook` — другой агрегат. Действие выдачи может нуждаться в обоих. Вы всё равно решаете, какой агрегат фиксируется первым и как другая сторона узнаёт.

Правила:

- Маленькие агрегаты. Гигантский агрегат блокирует слишком много данных и его трудно понять.
- Одна транзакция на агрегат по умолчанию (позже в разделе).
- Идентичность корня — то, как другие агрегаты на него ссылаются (идентификатор, не общий изменяемый объект).
- Не держите живой граф объектов между контекстами.

Если каждая запись должна блокировать половину базы, агрегат слишком большой. Если каждая запись нуждается в трёх удалённых вызовах, чтобы остаться согласованной, граница слишком маленькая или разделение развёртывания слишком раннее.

Агрегат — идея дизайна. В модульном монолите это может быть пакет плюс свои таблицы. Сам по себе это не микросервис.

## Сущности против объектов-значений

Сущность — доменный объект с идентичностью, которая остаётся той же, когда атрибуты меняются. `Loan` с идентификатором `L-42` всё ещё та же выдача после смены срока возврата.

Объект-значение — доменный объект, который вы определяете по атрибутам. У него нет собственной идентичности. Два значения `Money` с той же суммой и той же валютой равны. Вы заменяете объект-значение. Вы не меняете его на месте как именованного человека в модели.

Примеры объектов-значений: деньги, адрес почты, диапазон дат, адрес, цвет. Примеры сущностей: клиент, выдача, экземпляр книги, счёт.

Правила:

- Кладите инварианты на тип, которому они принадлежат. `Money` отвергает отрицательную сумму, если таково правило.
- Объекты-значения в модели часто неизменяемы. Изменение даёт новое значение.
- Не давайте объекту-значению суррогатный ключ базы, если только хранилище этого не требует. Модель всё равно считает его значением.
- Не считайте каждую строку таблицы сущностью. Строка соединения может быть значением или частью агрегата.

Идентичность — не «у него есть UUID». Идентичность — «бизнес отслеживает эту вещь через изменения». UUID на строке адреса не делает Address сущностью, если бизнесу важны только поля.

Используйте объекты-значения, чтобы убрать одержимость примитивами. `string` с именем `email` не проверяет формат. Тип `Email` может.

## Доменные события

Доменное событие — факт, что в домене что-то произошло. Имя в прошедшем времени: `LoanReturned`, `FineOpened`, `OrderPlaced`. Событие — часть модели. Это не только строка журнала.

Команда просит систему сделать работу (`ReturnLoan`). После того как агрегат принимает команду, агрегат может записать доменное событие. Другие модули в том же ограниченном контексте могут реагировать. Другие ограниченные контексты могут получить опубликованную форму события (тема 7).

Доменное событие — не команда. Команда может провалиться. Событие утверждает, что изменение уже произошло в модели.

Доменное событие — не технический хук «строка обновлена». Назовите бизнес-факт. `TableLoansUpdated` ничему не учит. `LoanReturned` учит правило.

Используйте события, чтобы избегать циклов. Модуль выдачи не импортирует почтовый модуль. Модуль выдачи записывает `LoanReturned`. Почтовый адаптер подписывается.

В модульном монолите можно публиковать в процессе. Между процессами нужен инструмент сообщений (тема 7). Имя и смысл остаются теми же. Транспорт меняется.

Включайте время, идентификатор агрегата и идентификатор корреляции, когда публикуете. Тема 11 использует эти поля в журналах.

Не используйте события, чтобы скрыть отсутствующую границу модуля. Если два модуля должны измениться за один щелчок пользователя и у вас нет имени для факта, модель неполная.

## Транзакционная против итоговой согласованности

Транзакционная согласованность значит, что одна транзакция делает набор изменений видимым вместе. Все изменения фиксируются или не фиксируется ни одно. Внутри одного агрегата и одной базы это значение по умолчанию. Тема 6 и `db.topics.md` покрывают транзакции.

Итоговая согласованность значит, что копии или другие агрегаты становятся правильными через некоторое время. Читатели могут видеть старое значение в течение периода. Вы используете итоговую согласованность, когда нельзя или нельзя блокировать все данные в одной транзакции.

Используйте транзакционную согласованность, когда:

- Инвариант в одном агрегате.
- Хранилище — одна база, которой вы владеете.
- Действие пользователя должно увидеть новое состояние в том же ответе.

Используйте итоговую согласованность, когда:

- У двух ограниченных контекстов разные владельцы.
- Второй процесс должен сделать работу (почта, поиск, отчёт).
- Распределённая запись нуждалась бы в долгой блокировке или хрупком двухфазном коммите.

Итоговая согласованность — не «мы надеемся». Вы должны определить:

- Как другая сторона узнаёт (событие, опрос или файл).
- Что видит пользователь, пока копия старая.
- Как вы чините пропущенное обновление.
- Как вы избегаете двойного эффекта (идемпотентность, тема 2).

Модульный монолит всё ещё может использовать итоговую согласованность для почты и поиска. Он может использовать одну транзакцию для строки выдачи и строки исходящего ящика (тема 7). Этот шаблон держит запись согласованной и позволяет подписчику отставать.

Не скрывайте отсутствующий инвариант за «итоговой». Если бизнес говорит, что два факта должны быть истинны вместе сейчас, нужен один агрегат или явный процесс, который пользователь может видеть.

## Обзор темы

Эти вопросы не повторяют вопросы разделов выше. Они покрывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Как единый язык, ограниченный контекст и агрегат вкладываются в одну модель?
2. Почему одно слово может нуждаться в двух моделях и как это влияет на сущности, которыми вы делитесь?
3. Когда доменное событие — лучший инструмент, чем прямой импорт другого модуля?
4. Как объекты-значения и агрегаты делят работу защиты инвариантов?
5. Какие атрибуты качества из темы 1 меняются, когда вы выбираете итоговую согласованность для подписчика?

#### Простые практические задания

1. Напишите шпаргалку на одну страницу: глоссарий, контекст, агрегат, сущность, объект-значение, событие, два типа согласованности.
2. Для приложения задач напишите четыре термина глоссария, один контекст, один агрегат, два события и одного итогового подписчика (почта).
3. Нарисуйте карту контекстов с двумя коробками и одним переведённым идентификатором.
4. Добавьте в закладки короткий открытый глоссарий DDD. Напишите три термина, которые совпадают с этой темой, и один термин, который эта тема опустила.

#### Средние практические задания

1. Напишите краткое доменное описание кампусного бюро находок: язык, два контекста, агрегаты и согласованность для уведомления почтой.
2. Возьмите схему с именами `tbl_x`. Переименуйте её в единый язык на бумаге. Покажите до и после.
3. Напишите план моделирования на двенадцать недель: сначала глоссарий, затем агрегаты, затем события.

#### Сложные практические задания

1. Напишите чек-лист ревью модели на одну страницу, которым коллега пользуется на запросе на слияние (имена, границы, согласованность).
2. Сравните это практическое подмножество DDD с оглавлением большой книги DDD. Сопоставьте пять тем книги с этим файлом и пометьте церемонию, которую вы пропускаете.

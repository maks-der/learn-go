# 3. Продюсеры

## Описание

Продюсер — клиент, который добавляет записи в партиции топика. Продюсер выбирает партицию, собирает записи в пакеты, отправляет их лидеру партиции и обрабатывает успех или ошибку.

Эта тема показывает API продюсера, подтверждения, идемпотентный продюсер, повторы, таймаут доставки, пакеты, сжатие, сериализацию и ядовитые сообщения. Завершите эту тему после темы 2. Завершите эту тему до темы 4.

Используйте один термин для каждого понятия. Подтверждение (`acks`) — ответ брокера, которого ждёт продюсер. Идемпотентный продюсер — режим продюсера, который предотвращает дубликаты от повторов. Ядовитое сообщение — запись, которую продюсер или консьюмер не может обработать. Для всей новой работы используйте кластеры KRaft. Продюсер говорит с брокерами. Продюсер не говорит с ZooKeeper.

## API продюсера

API продюсера — клиентский интерфейс, который отправляет записи. В Java тип — `KafkaProducer`. В других языках есть тип продюсера с той же идеей: настроить, отправить, flush или close.

Типичная последовательность:

1. Соберите конфигурацию. Задайте `bootstrap.servers`. Задайте сериализаторы для ключа и значения.
2. Создайте продюсера.
3. Соберите запись (топик, необязательный ключ, значение, необязательные заголовки и партиция).
4. Вызовите `send`. `send` часто асинхронный. Клиент возвращает future или вызывает callback.
5. Вызовите `flush`, когда нужно дождаться записей в полёте. Вызовите `close`, когда процесс заканчивается.

`bootstrap.servers` — список брокеров. Продюсер получает метаданные. Затем продюсер отправляет каждый пакет текущему лидеру целевой партиции.

Не создавайте нового продюсера на каждую запись. Продюсер держит соединения и буферы. Делите одного продюсера на процесс, когда конфигурация та же.

Обрабатывайте результат `send`. Игнор callback — частая причина тихой потери данных.

Консольный продюсер — маленький продюсер для тестов. Используйте его, чтобы учиться. Для приложений используйте API клиента.

## Acks: `0`, `1`, `all`

`acks` контролирует, когда продюсер считает отправку успешной.

- `acks=0`. Продюсер не ждёт ответа брокера. Брокер может отбросить запись. Продюсер также может потерять запись при сетевой ошибке. Пропускная способность может быть высокой. Устойчивость низкая.
- `acks=1`. Лидер пишет запись в свой локальный журнал и отвечает. У фолловеров записи ещё может не быть. Если лидер падает до того, как фолловеры скопируют запись, запись можно потерять.
- `acks=all` (или `acks=-1`). Лидер ждёт, пока синхронные реплики (ISR) удовлетворят `min.insync.replicas`. Тема 6 определяет ISR. Эта настройка — устойчивый выбор для важных данных.

Идемпотентный продюсер требует `acks=all`. Текущие клиенты Java включают идемпотентность по умолчанию и задают `acks=all`.

Не используйте `acks=0` для заказов, платежей или других данных, которые нельзя потерять. Используйте `acks=0` только когда потеря приемлема (некоторые метрики).

`acks` — настройка продюсера. `min.insync.replicas` — настройка брокера или топика. Для `acks=all` важны обе.

## Идемпотентный продюсер, повторы и таймаут доставки

**Идемпотентный продюсер** предотвращает дубликаты, которые повторы создали бы на той же партиции. Брокер хранит идентификатор продюсера и номер последовательности. Повтор того же пакета не добавляет вторую копию.

Текущие клиенты Java включают идемпотентность по умолчанию. Идемпотентность требует `acks=all` и ограниченный `max.in.flight.requests.per.connection` (клиент задаёт безопасное значение). Не выключайте идемпотентность без письменной причины.

**Повторы** происходят, когда продюсер получает повторяемую ошибку (сеть, смена лидера, недостаточно реплик). Продюсер отправляет пакет снова. Без идемпотентности повтор после потерянного ack может создать дубликат в журнале.

`retries` и `delivery.timeout.ms` ограничивают, сколько продюсер пытается. `delivery.timeout.ms` — максимальное время от send до успеха или сбоя. `request.timeout.ms` — время одного запроса. `linger.ms` — время в пакете до первой отправки. Эти времена должны сходиться. Официальные документы показывают связь.

`retry.backoff.ms` ждёт между повторами. Очень маленький backoff может перегрузить восстанавливающийся брокер.

Идемпотентность не делает всё приложение exactly-once. Новый `send` того же бизнес-события с новой последовательностью — новая запись. Используйте идентификатор события в полезной нагрузке или транзакцию (тема 5), когда приложение повторяет новый send.

`transactional.id` — дальнейший режим. Тема 5 покрывает транзакции. Для этого раздела транзакции не нужны.

## Пакеты и сжатие

Продюсер группирует записи в **пакеты** на партицию. `batch.size` — максимальный размер пакета в байтах. `linger.ms` — дополнительное ожидание, чтобы добавить больше записей до отправки.

Когда пакет полон, продюсер отправляет, даже если время linger не кончилось. Когда время linger кончилось, продюсер отправляет, даже если пакет не полон.

Больший пакет повышает пропускную способность. Первая запись в пакете ждёт. Это ожидание повышает задержку. Тема 10 снова покрывает этот компромисс.

`buffer.memory` ограничивает, сколько продюсер может держать до отправки. Если буфер полон, `send` блокируется или падает по конфигурации.

**Сжатие** работает на пакете. Частые типы: `none`, `lz4`, `snappy`, `gzip`, `zstd`. Больший пакет часто сжимается лучше. Сжатие использует CPU на клиенте. Брокер хранит сжатый пакет. Консьюмеры распаковывают.

Не задавайте `batch.size` больше, чем принимает брокер. Брокерный `message.max.bytes` и топиковый `max.message.bytes` ограничивают пакет записей.

Для низкой задержки держите linger маленьким. Для высокой пропускной способности поднимайте linger и размер пакета, пока пределом не станет брокер или сеть. Измеряйте после каждого изменения.

KRaft не меняет эти ключи продюсера.

## Сериализация

**Сериализатор** пишет ключ или значение как байты. **Десериализатор** на консьюмере читает эти байты. Пара должна совпадать. Тема 7 покрывает схемы и Schema Registry.

Брокеры Kafka не разбирают поля. Они хранят байты. Если вы пишете JSON-текст и читаете десериализатором Avro, консьюмер падает или печатает мусор.

Частые сериализаторы клиента:

- строка (UTF-8)
- integer или long (фиксированная двоичная раскладка)
- массив байтов (вы собираете байты)
- JSON (как текст или через библиотеку)
- Avro, Protobuf или JSON Schema (часто с реестром)

Задайте `key.serializer` и `value.serializer` (имена Java). Другие языки используют ту же идею.

Не меняйте формат живого топика без плана. Старые записи остаются в старом формате, пока ретеншн их не удалит.

Заголовки могут называть тип содержимого. Десериализатор всё равно должен понимать байты. Заголовок не замена совпадающей паре сериализаторов.

Ключ null и значение null допустимы. Значение null — томбстоун на компактируемом топике (тема 6). Сериализатор должен разрешать null, когда вы отправляете томбстоун.

## Ядовитые сообщения

**Ядовитое сообщение** — запись, которую клиент не может обработать. На пути отправки сериализация может упасть, запись может превысить `max.message.bytes`, или брокер может отклонить produce. На пути чтения десериализация может упасть, или бизнес-логика может отклонить полезную нагрузку.

Если игнорировать ошибки отправки, вы теряете данные и можете не увидеть яд. Если консьюмер останавливается на первой плохой записи, партиция не движется вперёд. Тема 4 покрывает цикл poll. Тема 8 покрывает очередь недоставленных в Connect.

Обрабатывайте сбои отправки в callback или future. Логируйте топик, партицию и ошибку. Не повторяйте вечно без границы (`delivery.timeout.ms`).

Для слишком большой записи разделите полезную нагрузку, храните blob вне Kafka или поднимите предел размера с планом. Не поднимайте `max.message.bytes` на каждом топике без плана диска и fetch.

Для полезной нагрузки, которую консьюмеры не могут разобрать, исправьте контракт продюсера. Топик недоставленных — прикладной шаблон: напишите плохую запись во второй топик и зафиксируйте исходный офсет. Тема 5 и тема 11 покрывают дубликаты и обработку яда в приложениях.

Не используйте `acks=0`, чтобы «пропустить» ошибки яда. Вы только прячете сбой.

## Повторение темы

Эти вопросы не повторяют вопросы разделов выше. Они покрывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Опишите устойчивую отправку от `send` до ack. Назовите bootstrap, партиционер, пакет, `acks=all` и идемпотентность.
2. Как linger, размер пакета и сжатие меняют и скорость, и задержку?
3. Почему «продюсер повторил» не то же самое, что «приложение отправило событие дважды»?
4. Что должно оставаться тем же между сериализатором продюсера и десериализатором консьюмера?
5. Коллега задаёт `acks=0` и игнорирует callback, чтобы «идти быстрее». Какие факты вы используете в коротком ответе?

#### Простые практические задания

1. Напишите продюсера, который отправляет три записи с ключами с `acks=all`, затем делает flush и close. Напечатайте партицию и офсет.
2. Напишите шпаргалку на одну страницу: шаги API, три значения `acks`, идемпотентность, таймаут доставки, ключи пакета, сжатие, сериализаторы, яд.
3. Из значений по умолчанию вашего клиента запишите `acks`, идемпотентность и linger.
4. Нарисуйте путь: запись → сериализатор → пакет → лидер → ack.

#### Средние практические задания

1. Измените только `linger.ms` на отправке 1000 записей. Запишите длительность и успешны ли все callback.
2. Сопоставьте каждый подраздел с одним официальным ключом конфигурации или типом API.
3. Отправьте в отсутствующий топик с выключенным auto-create. Запишите ошибку. Создайте топик. Повторите.

#### Сложные практические задания

1. Соберите маленького продюсера, который считает ошибки callback, повторяет на уровне приложения с повторно используемым заголовком event-id и останавливается после бюджета в стиле `delivery.timeout.ms`.
2. Напишите продакшен-стандарт продюсера: только bootstrap KRaft, `acks=all`, идемпотентность, контракт сериализатора и политика callback.

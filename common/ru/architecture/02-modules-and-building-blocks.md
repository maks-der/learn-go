# 2. Модули и строительные блоки

## Описание

Модуль — часть системы с границей и ответственностью. Классические строительные блоки — базовые части сетевых систем: клиенты, серверы, синхронные и асинхронные вызовы, состояние, идемпотентность и тайм-ауты. Эта тема покрывает связность, связанность, инкапсуляцию, направление зависимостей и пакеты как границы.

Хорошие модули позволяют менять одну часть без переписи других. Плохие модули разносят одно изменение по всей системе. Тема 1 назвала этот эффект сопровождаемостью.

Завершите тему 1 до этой темы. Сначала пишите маленькие модули. Не начинайте с многих сетевых сервисов. Модуль может жить в одном процессе. Идеи процесса и потока читайте в `os.topics.md`, если эти термины новые.

Используйте один термин для каждого понятия. Модуль — граница дизайна. Пакет — языковая граница. Процесс — не поток. Синхронный вызов не всегда то же, что блокирующий вызов ОС в каждом языке. Этот справочник использует «синхронный» для «вызывающий ждёт результат этой операции».

## Связность, связанность, инкапсуляция

Связность — насколько сильно элементы внутри модуля принадлежат друг другу. Модуль с высокой связностью делает одну работу. Примеры: «оценить заказ», «хешировать пароль», «записать строку аудита». Модуль с низкой связностью смешивает несвязанные работы. Пример: «цены, письма и вёрстка PDF в одном файле».

Связанность — насколько сильно один модуль зависит от другого. Модуль с высокой связанностью нельзя менять без изменений во многих других модулях. Модуль с низкой связанностью зависит от маленького стабильного интерфейса.

Стремитесь к высокой связности и низкой связанности. Эти две цели работают вместе. Когда модуль делает одну работу, другим модулям нужно меньше знания о его внутренностях.

Некоторая связанность необходима. Модуль оформления заказа должен вызывать модуль цен. Эта связанность приемлема, когда интерфейс цен маленький и стабильный.

Скрытая связанность хуже видимой. Скрытая связанность включает общую глобальную переменную, общую таблицу базы без владельца и скрытое предположение о формате файла. Видимая связанность — импорт или задокументированный интерфейс.

Инкапсуляция — правило, что модуль скрывает внутренности и показывает только маленький интерфейс. Внутренности включают структуры данных, SQL и вспомогательные функции. Вызывающие не должны зависеть от этих внутренностей.

Инкапсуляция защищает инварианты. Инвариант — правило, которое должно оставаться истинным. Пример: «итог заказа равен сумме итогов строк.» Если каждый вызывающий пишет в те же таблицы, инвариант ломается.

Инкапсуляция — не то же, что «сделать каждое поле закрытым и добавить геттеры». Геттер, который открывает всю внутреннюю структуру, — утечка. Скрывайте структуру. Открывайте операции, которые соответствуют работе: `placeOrder`, не `getOrderMap`.

Запрос на изменение — проверка дизайна. Если маленькое бизнес-изменение трогает много модулей, связность низкая или связанность высокая.

## Направление зависимостей

Направление зависимостей — правило, которое говорит, какой модуль может импортировать или вызывать какой другой модуль. Здоровый граф имеет ясное направление. Цикл — путь, который возвращается к началу. Циклы делают изменение трудным. Нельзя понять или тестировать один модуль отдельно, когда он зависит от цикла.

Направляйте зависимости к стабильным модулям. Доменное правило стабильнее HTTP-обработчика. Адаптер хранилища менее стабилен, чем доменный интерфейс, который он реализует. Тема 3 использует это правило в слоях и шестиугольном дизайне.

Разрешённые примеры:

- Модуль представления может вызывать доменный модуль.
- Доменный модуль не должен импортировать драйвер SQL.
- Утилита, которую импортируют многие модули, должна оставаться маленькой и без бизнес-правил.

Запрещённые примеры:

- Два модуля, которые импортируют друг друга.
- Доменный модуль, который импортирует тип веб-фреймворка.
- Пакет `utils`, который импортирует каждый другой пакет.

Цикл может скрываться в данных. Два модуля, которые делят таблицу без владельца, образуют цикл данных. Граф импортов может выглядеть чистым. Цена изменения всё равно высокая.

Рисуйте граф. Инструменты могут перечислить импорты. Можно также нарисовать четыре коробки и стрелки на бумаге. Если граф нарисовать нельзя, направление неясно.

Когда нужен обратный вызов от стабильного модуля к нестабильному, используйте интерфейс, которым владеет стабильный модуль. Нестабильный модуль реализует интерфейс. Это инверсия зависимости.

## Клиент/сервер, синхронный против асинхронного, с состоянием против без состояния

Клиент — программа, которая начинает запрос. Сервер — программа, которая ждёт запрос и затем отвечает. Один процесс может быть клиентом одной системы и сервером для другой.

Отношение — о том, кто начинает вызов. Браузер — клиент HTTP-сервера. Этот HTTP-сервер может быть клиентом сервера базы. База не вызывает браузер.

Контракт связывает клиента и сервер. Контракт включает протокол, операции, формы данных и правила ошибок. Сервер не должен доверять клиенту. Клиент может отправить неверные данные. Сервер проверяет вход.

Синхронный вызов — вызов, где вызывающий ждёт результат этой операции. Асинхронный вызов — вызов, где вызывающий не ждёт полного результата в том же ожидании. Вызывающий может продолжить и получить результат позже (сообщение, опрос или обратный вызов).

Синхронные вызовы просто читать. Они держат ресурс, пока ждут. Асинхронные вызовы могут поглотить всплеск. Им нужно место для хранения работы и правило отказа.

Сервис с состоянием хранит данные конкретного клиента в памяти процесса (или на локальном диске этого экземпляра). Следующий запрос должен попасть на тот же экземпляр, или данные должны быть общими. Сервис без состояния хранит данные конкретного клиента вне экземпляра (база или кэш). Любой здоровый экземпляр может обработать следующий запрос.

Экземпляры без состояния легче клонировать за балансировщиком нагрузки. Липкие сессии усложняют масштаб. Некоторое состояние необходимо (база). Цель — держать локальное состояние сессии экземпляра маленьким.

Процесс — экземпляр программы, который запускает ОС. Поток — единица выполнения внутри процесса. Потоки в одном процессе делят память. Если один процесс останавливается, все потоки в этом процессе останавливаются. См. `os.topics.md`.

Не проектируйте двадцать процессов для студенческого проекта. Начните с одного процесса и ясных модулей. Добавляйте процесс, когда нужен другой жизненный цикл, другой лимит ресурсов или другой домен отказа.

## Идемпотентность и тайм-ауты

Идемпотентность — свойство, что повторный запрос имеет тот же эффект, что один запрос. Второй `PUT` того же ресурса не должен создать второй ресурс. Второй «списать этот платёжный ключ» не должен списать дважды.

Сети повторяют. Пользователи делают двойной щелчок. Рабочие повторяют сообщения. Если обработчик не идемпотентен, повтор создаёт дефект хуже тайм-аута.

Ключ идемпотентности — идентификатор клиента для одного задуманного действия. Сервер хранит ключ и результат. Повтор с тем же ключом возвращает сохранённый результат и не выполняет побочный эффект снова.

`GET` обычно идемпотентен. `PUT` и `DELETE` могут быть идемпотентными, если вы так спроектируете. Голый `POST`, который всегда создаёт новую строку, не идемпотентен, пока вы не добавите ключ или естественное уникальное правило.

Тайм-аут ограничивает ожидание. Каждый удалённый вызов нуждается в тайм-ауте. Вызов без тайм-аута может ждать вечно. Вечные ожидания заполняют потоки и скрывают отказ.

Правила для тайм-аутов:

- Ставьте тайм-аут на каждый исходящий вызов (HTTP, база, брокер).
- Держите общее ожидание внутри бюджета пользователя.
- Тайм-аут — локальное решение. Удалённая работа всё ещё может завершиться.
- После тайм-аута не считайте, что работа не выполнилась. Для повтора используйте идемпотентность.

Тайм-аут — не повтор. Повтор повторяет вызов. Повторяйте только идемпотентные операции или операции, которые вы защищаете ключом. Тема 8 покрывает повторы в распределённой системе.

Не используйте `sleep` как дизайн тайм-аута. Не ждите без границы «пока сервер ответит».

## Пакеты как границы

Пакет — языковая граница. Во многих языках пакет (или модуль, или пространство имён) группирует типы и функции. Компилятор или среда выполнения может скрыть неэкспортируемые имена. Это скрытие — инструмент инкапсуляции. Оно не заменяет дизайн.

Используйте пакеты как первую границу модуля в монолите. Один пакет делает одну работу. Другие пакеты импортируют только публичные имена. Они не должны импортировать внутренности. Они не должны делить мешок с именем `utils`, который растёт без владельца.

Правила, которые держат границы пакетов полезными:

- Одна работа на пакет.
- Маленькая публичная поверхность.
- Нет циклов импорта.
- Таблицы и файлы, которыми владеет пакет, имеют ясное имя владельца.
- Тесты могут импортировать пакет без загрузки всего мира, когда это возможно.

Папка — не граница, если каждый файл публичный и каждый пакет импортирует каждый другой пакет. Имена на папках без правил — украшение.

Библиотека — распространяемый пакет (или набор пакетов). Библиотека не владеет производственным хранилищем данных. Сервис владеет. Тема 9 определяет сервис.

Языковые средства помогают: закрытые имена, пакеты и модули. Публичный пакет, который экспортирует двадцать типов, имеет большую поверхность. Большая поверхность — слабая инкапсуляция.

Когда вы меняете внутренности и не меняете публичные имена, вызывающие продолжают работать. Это практическая проверка границы пакета.

Начинайте с пакетов. Процессы и сети добавляйте позже. Тема 3 держит эти пакеты внутри одной единицы развёртывания.

#### Простые практические задания

1. Нарисуйте монолит с четырьмя пакетами и только разрешёнными импортами.
2. Составьте таблицу: «Имя» и «Работа». Добавьте шесть имён пакетов для блога.
3. Перечислите пять имён, которые должны остаться неэкспортируемыми в пакете `pricing`.

#### Средние практические задания

#### Сложные практические задания

2. Просмотрите открытый репозиторий монолита. Пометьте пакеты, которые существуют как настоящие границы, и папки, которые только имена. Напишите доказательства.

## Обзор темы

### Вопросы

#### Теоретические вопросы

1. Как связность, связанность и инкапсуляция работают вместе в одном модуле?
2. Почему чистый граф импортов всё ещё может иметь высокую связанность через общую таблицу?
3. Когда вы оставляете вызов синхронным и когда делаете его асинхронным?
4. Как тайм-ауты и идемпотентность защищают клиента, который повторяет запрос?
5. Почему пакеты — первая граница, до процессов и сервисов?

#### Простые практические задания

1. Напишите шпаргалку на одну страницу: связность, связанность, инкапсуляция, направление, клиент/сервер, синхронный/асинхронный, состояние, идемпотентность, тайм-аут, правила пакетов.
2. Для API задач назовите четыре пакета, два синхронных вызова, один тайм-аут и одну идемпотентную запись.
3. Нарисуйте клиента, сервер и базу. Пометьте, кто ждёт и кто хранит состояние сессии.
4. Добавьте в закладки `os.topics.md`. Напишите три термина, которые эта тема берёт из того пути.

#### Средние практические задания

1. Напишите короткий дизайн API выдачи книг в библиотеке в одном процессе: пакеты, одно хранилище с состоянием и тайм-ауты на хранилище.
2. Возьмите дизайн коллеги, который использует глобальные переменные для корзины. Перепишите его как пакет с интерфейсом и хранилищем.
3. Составьте таблицу запросов на изменение: пять маленьких бизнес-изменений и пакеты, которые каждое изменение должно тронуть.

#### Сложные практические задания

1. Напишите обзор на одну страницу небольшого открытого клиента API: связанность, тайм-ауты и идемпотентность повторов. Оставайтесь в защите.
2. Спроектируйте карту модулей кампусного магазина, из которой позже можно извлечь один пакет. Напишите, чем нельзя делиться через будущий разрез.

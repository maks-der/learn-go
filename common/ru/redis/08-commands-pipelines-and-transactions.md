# 8. Команды, конвейеры и транзакции

## Описание

Клиент Redis отправляет команды и читает ответы. Эта тема объясняет одну команду за раз против конвейера, транзакции Redis (`MULTI`, `EXEC`, `WATCH`) и скрипты на сервере. Вы узнаёте, что значит «атомарный» в Redis и чем это отличается от отката SQL.

Завершите эту тему до изучения персистентности и репликации.

Используйте один термин для каждого понятия. Круг — одна сетевая отправка и одно ожидание ответа. Конвейер — много команд в одной отправке, ответы позже. Транзакция — очередь блока, который `EXEC` выполняет без вставки других команд. Скрипт — Lua или Redis Function, который выполняется на сервере.

---

## Запрос/ответ против конвейера

Режим по умолчанию — запрос/ответ. Клиент отправляет `GET k`. Клиент ждёт. Redis отвечает. Клиент отправляет следующую команду. Каждая команда платит сетевую задержку (RTT).

Конвейер отправляет много команд без ожидания после каждой. Клиент затем читает все ответы по порядку. Redis всё равно выполняет команды по одной в основном потоке. Выигрыш — меньше времени ожидания сети.

```text
# conceptual, not a special Redis command
INCR views
INCR views
INCR views
```

В конвейере эти три `INCR` могут лежать в одной записи TCP. Ответы — `1`, `2`, `3`, если ключ изначально отсутствовал.

`redis-cli` может конвейерить из файла:

```text
redis-cli --pipe < commands.txt
```

Клиентские библиотеки имеют API конвейера. Используйте его для многих независимых команд (тысячи `SET`, много `HGET`).

Конвейер — не транзакция. Другие клиенты могут выполнять команды между вашими конвейерными командами. Отката нет. Если соединение оборвётся, вы можете не знать, какие команды выполнились.

Держите пакеты конвейера ограниченными (например сотни или несколько тысяч команд). Огромный конвейер использует буферы клиента и сервера.

Не конвейерьте команды, которые должны видеть предыдущий ответ (если не принимаете, что нельзя ветвиться в середине). Для «прочитать, затем записать если» используйте `WATCH`, скрипт Lua или Function.

## `MULTI` / `EXEC` / `DISCARD`

`MULTI` начинает транзакцию. Redis ставит следующие команды в очередь на этом соединении. Redis ещё не выполняет их. Немедленный ответ — `QUEUED`.

`EXEC` выполняет очередь команд по порядку как одну единицу в основном потоке. Никакое другое соединение не выполняет команду в середине этого `EXEC`. Ответ — массив ответов, по одному на очередь команд.

`DISCARD` сбрасывает очередь и заканчивает транзакцию без `EXEC`.

```text
MULTI
INCR acct:1
INCR acct:2
EXEC
```

Если у очереди команды ошибка синтаксиса, Redis может отклонить `EXEC` и ничего не выполнить (зависит от того, когда Redis обнаруживает ошибку). Если команда падает при выполнении (`WRONGTYPE`, отсутствующий ключ для типа), более поздние команды в том же `EXEC` всё равно выполняются. Redis не откатывает более ранние команды.

`EXEC` может вернуть ошибку или null-ответ, когда ключ под `WATCH` изменился (следующий раздел).

У транзакций нет уровней изоляции как в SQL. Нет точек сохранения. Они сами не ждут диск.

Используйте `MULTI` / `EXEC`, когда нужно выполнить несколько команд без вставки и не нужно читать значение в середине. Нельзя сделать `GET` внутри `MULTI` и полезно использовать это значение в следующей очереди команде на клиенте. `GET` в очереди. Клиент не видит значение до `EXEC`.

Для логики, которая читает и затем пишет, используйте `WATCH` или Lua.

## Оптимистичная блокировка: `WATCH`

`WATCH key [key ...]` помечает ключи на текущем соединении. Если любой наблюдаемый ключ меняется до `EXEC`, Redis прерывает транзакцию. `EXEC` возвращает null-ответ. Клиент затем повторяет: снова `WATCH`, чтение, `MULTI`, запись, `EXEC`.

Это оптимистичная блокировка. Вы предполагаете, что конфликт редок. Вы обнаруживаете конфликт на `EXEC`.

```text
WATCH acct:1
GET acct:1
MULTI
SET acct:1 40
EXEC
```

Если другой клиент пишет `acct:1` после `WATCH` и до `EXEC`, `EXEC` падает. Ваш `SET` не выполняется.

`UNWATCH` снимает наблюдения. `EXEC` и `DISCARD` тоже снимают наблюдения.

`WATCH` на соединение. Нужно делать `GET` на том же соединении после `WATCH` и использовать это соединение для `MULTI` / `EXEC`. Пул соединений не должен смешивать эти шаги между соединениями.

`WATCH` не блокирует других клиентов. Они всё ещё могут писать. Вместо этого падает ваш `EXEC`.

Не делайте `WATCH` огромного набора ключей. Не используйте `WATCH` как распределённую блокировку. Используйте `SET NX EX` для превью блокировки или скрипт для обновлений нескольких ключей.

`WATCH` плюс `MULTI` достаточно для «прочитать баланс, записать если всё ещё тот же» на одном экземпляре. В Cluster все ключи транзакции должны жить в одном слоте (тема 11).

## Транзакции — не SQL с откатом

Транзакции SQL могут сделать `ROLLBACK`. Движок отменяет записи, когда вы прерываете, или когда падает ограничение (зависит от движка и оператора).

`EXEC` Redis не отменяет. Если команда 1 в транзакции проходит, а команда 2 падает, команда 1 остаётся применённой. Redis — не реляционный движок. Нет блокировок строк, нет отката WAL транзакции и нет команды `ROLLBACK`, которая восстанавливает значения.

Транзакции Redis дают:

- нет вставки других команд во время `EXEC`
- необязательное прерывание всего `EXEC`, когда `WATCH` обнаруживает изменение
- выполнение очереди на одном соединении

Транзакции Redis не дают:

- откат неудачной команды внутри `EXEC`
- интерактивное чтение своих записей внутри очереди
- атомарный коммит на нескольких экземплярах (нет двухфазного коммита в базовом Redis)

Если нужно «все ключи обновляются или ни один» с логикой, положите логику в скрипт Lua или Function. Скрипт выполняется как одна команда. Если вы сделали `redis.call` записи и затем попали в ошибку, записи, которые уже выполнились в этом скрипте, остаются применёнными, если не проверяете ошибки до записи. Пишите скрипты так, чтобы проверки шли сначала.

Компенсация на уровне приложения (записать обратное) возможна, но легко ошибиться. Предпочитайте один атомарный скрипт для обновлений вроде денег на одном экземпляре Redis.

Не называйте Redis `MULTI` «транзакцией SQL» на обзоре дизайна. Говорите «очередь атомарного пакета» или «транзакция Redis».

## Скрипты Lua: `EVAL`, `EVALSHA`, атомарные обновления нескольких ключей

`EVAL script numkeys key [key ...] arg [arg ...]` выполняет скрипт Lua на сервере. Скрипт использует `KEYS[]` и `ARGV[]`. Redis выполняет скрипт как одну команду. Другие команды ждут.

```text
EVAL "return redis.call('INCR', KEYS[1])" 1 lab:c
```

`redis.call` поднимает ошибку при ошибке Redis. `redis.pcall` возвращает значение ошибки.

`EVALSHA sha1 numkeys ...` выполняет скрипт, который сервер уже закэшировал. `SCRIPT LOAD` возвращает SHA1. `EVALSHA` экономит полосу. Если сервер перезапустился и кэш пуст, клиент получает `NOSCRIPT` и должен снова сделать `EVAL` или `SCRIPT LOAD`.

Используйте скрипт, когда нужно читать и писать несколько ключей с логикой и без вставки. Пример: увеличить счётчик и задать `EXPIRE` только когда новое значение `1`. Пример: снять блокировку, если `GET` равен вашему токену.

Правила:

- Передавайте каждый ключ, к которому обращаетесь, в списке `KEYS`. Не стройте имена ключей из `ARGV` в скриптах, безопасных для Cluster.
- Держите скрипты короткими. Длинный скрипт блокирует экземпляр.
- Не используйте Lua как общий сервер приложений. Нет длинных циклов. Нет случайных пауз.
- Скрипты должны быть детерминированными для репликации. Избегайте `TIME` в старых режимах, если не следуете документированному шаблону (`redis.replicate_commands` / эффекты в текущих версиях). Читайте документацию скриптов для вашей версии.

Redis реплицирует скрипт или его эффекты на реплики. Ошибка в скрипте тоже может реплицироваться.

Предпочитайте `EVALSHA` плюс шаг загрузки при старте приложения.

## Functions (Redis 7+)

Redis 7 добавляет Functions. Function — зарегистрированная библиотека, которая живёт на сервере. Клиенты вызывают `FCALL name numkeys key [key ...] arg ...`.

Вы загружаете библиотеку через `FUNCTION LOAD` и полезный груз, который задаёт документация (синтаксис библиотеки Lua). `FUNCTION LIST` показывает библиотеки. `FUNCTION DELETE` удаляет библиотеку. `FUNCTION FLUSH` удаляет все (только лаборатория).

Functions решают эксплуатационные задачи сырых строк `EVAL` в каждом клиенте:

- Сервер хранит код
- Можно обновить библиотеку в одном месте
- `FCALL` использует стабильное имя

Functions всё ещё выполняются в основном потоке. Они всё ещё атомарны. Они всё ещё блокируют, если медленные. Правила ключей Cluster всё ещё действуют.

`EVAL` всё ещё работает. Многие приложения держат скрипты Lua. Новые дизайны на Redis 7+ могут предпочитать Functions, когда команда хочет версионирование на сервере.

Нужно сохранять functions как другие данные, если они нужны после перезапуска. Проверьте, восстанавливает ли ваш режим персистентности и репликация functions. Официальная страница Functions описывает персистентность и репликацию.

Не смешивайте десять копий одного Lua в клиентах и библиотеку Function без одного источника истины.

AOF и RDB могут включать определения functions, чтобы реплика или перезапуск всё ещё имели цели `FCALL`. Проверьте это в лаборатории до промышленной среды.

### Вопросы

#### Теоретические вопросы

1. Ранжируйте конвейер, `MULTI`/`EXEC`, `WATCH` и Lua по «нет другой команды в середине» и по «можно использовать результат чтения в более поздней логике».

#### Простые практические задания

#### Сложные практические задания

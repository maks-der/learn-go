# 14. HTTP/2, HTTP/3, QUIC

## Описание

HTTP/2 и HTTP/3 — более новые отображения HTTP. HTTP/2 использует TLS на TCP в обычном веб-случае. HTTP/3 использует QUIC на UDP. Эта тема показывает мультиплексирование, сжатие заголовков на уровне осведомлённости, QUIC на UDP, почему существует HTTP/3, и ALPN.

Используйте один термин для каждого понятия. Поток — один разговор запрос-ответ внутри одного соединения. Мультиплексирование значит, что много потоков делят одно соединение. Завершите эту тему после TLS и HTTP/1.1.

Практикуйтесь с `curl -v` и видом разработчика браузера, который показывает версию HTTP. Захват HTTP/2 или HTTP/3 двоичный. Сначала назовите версию. Не ждите текст HTTP/1.1 на проводе.

## Мультиплексирование

Keep-alive HTTP/1.1 повторно использует одно соединение TCP. Обычный клиент всё равно ждёт одного ответа, прежде чем отправить следующий запрос на этом соединении. Браузеры открывают несколько соединений TCP, чтобы снизить ожидание.

HTTP/2 мультиплексирует много потоков на одном соединении. У каждого потока есть идентификатор. Кадры несут данные потока. Один потерянный сегмент TCP всё равно застопоривает всё соединение на уровне TCP. Мультиплексирование не снимает блокировку начала очереди TCP. Тема TCP уже назвала этот предел.

HTTP/3 мультиплексирует потоки на QUIC. Потеря на одном потоке не блокирует другие потоки на транспортном уровне в проекте QUIC. Это причина существования HTTP/3. Поздний раздел повторяет это с потерями.

Сервер может толкать в HTTP/2 в старом проекте. Многие браузеры ограничивают или игнорируют push. Не стройте новую службу на server push. Используйте обычный запрос.

Не открывайте сотни соединений HTTP/2, чтобы «ехать быстрее», без измерения. Одно соединение на origin — учебное значение по умолчанию. Не путайте поток с соединением TCP.

Приоритет и управление потоком существуют на поток. Этой теме нужно только: много запросов могут быть в полёте на одном соединении.

## HPACK / QPACK (осведомлённость)

HTTP/1.1 повторяет заголовки как текст на каждом запросе. `Cookie`, `User-Agent` и `Authorization` могут быть большими. HTTP/2 использует HPACK для сжатия заголовков. HTTP/3 использует QPACK.

Обе схемы используют таблицы полей заголовков. Две стороны соглашаются на имена и значения, которые уже отправили. Провод тогда несёт компактную форму. Раскладка бит Huffman для этого пути не нужна.

Факты осведомлённости:

- сжатие снижает повторные байты заголовков
- HPACK предполагает упорядоченную доставку (TCP)
- QPACK построен для потоков QUIC, которые могут прийти не по порядку
- сжатые заголовки всё ещё внутри крипто TLS или QUIC в публичном вебе

Сжатие заголовков имело истории безопасности, когда смешивало секреты с полями, которые контролирует злоумышленник. Современные стеки следуют текущим правилам RFC. Не выдумывайте своё сжатие заголовков.

Не смотрите на двоичный захват и не ждите прочитать `Host:` как ASCII. Декодер в Wireshark может показать заголовки после разбора HPACK. Зашифрованной нагрузке всё равно нужны ключи, которыми владеете.

Этот раздел — осведомлённость. Нужно знать имена HPACK и QPACK и зачем они существуют. Здесь вы их не реализуете.

## QUIC поверх UDP

QUIC — транспортный протокол, который работает поверх UDP. HTTP/3 использует QUIC. QUIC включает TLS 1.3 для ключей. QUIC — не «сырой UDP без надёжности». QUIC может повторять данные потока. QUIC также может поддерживать ненадёжные датаграммы в поздних расширениях. Эта тема использует надёжные потоки HTTP/3.

Почему UDP: эволюция в пространстве пользователя, один круговой обход для крипто и транспорта в обычном случае 1-RTT и нет начала очереди TCP между потоками. NAT и межсетевые экраны уже пропускают UDP для многих пользователей. Некоторые сети всё ещё блокируют UDP. Тогда клиент падает на HTTP/2 или HTTP/1.1 на TCP.

Соединение QUIC использует идентификаторы соединения. Смена IP или порта клиента (повторная привязка NAT, телефон в новой сети) может сохранить соединение, когда идентификаторы совпадают с проектом. TCP жёстче привязывает соединение к 4-tuple.

Не пишите свой «QUIC» сырым UDP в производстве. Используйте библиотеку. Не считайте, что UDP-порт 443 всегда открыт. Измеряйте.

`curl` может использовать HTTP/3, когда сборка это поддерживает. Подробный вывод тогда говорит `HTTP/3`. Захват показывает UDP, не TCP, для этой сессии.

У QUIC всё ещё есть управление перегрузкой. Потеря всё равно замедляет отправителя. QUIC не делает тонкий канал толстым.

## Почему существует HTTP/3 (потеря + HOL)

TCP доставляет упорядоченный поток байтов. Потерянный сегмент задерживает все поздние байты для приложения. HTTP/2 кладёт много потоков на этот один поток. Одна потеря задерживает все потоки HTTP/2. Это блокировка начала очереди TCP. Тема 9 заявила этот факт.

HTTP/3 существует, чтобы сохранить семантику HTTP (методы, статус, заголовки, тело) и избежать этой цены HOL TCP. QUIC восстанавливает каждый поток своими номерами пакетов. Потерянный пакет для потока 1 не держит поток 2 в очереди приёма транспорта.

HTTP/3 также целится в более быстрое рукопожатие: TLS и транспорт объединяются. Первому запросу может понадобиться меньше круговых обходов, чем TCP плюс TLS 1.2 на холодном соединении. Реальный выигрыш зависит от пути и от возобновления.

HTTP/3 не снимает потери. Потеря всё равно задерживает этот поток и всё равно сигналит перегрузку. HTTP/3 не чинит плохое приложение. Один огромный ответ на одном потоке всё равно занимает время.

Не включайте HTTP/3 только потому, что номер версии больше. Измеряйте страницу или API. Не вините HTTP/3, когда сначала упали DNS или проверка TLS.

Некоторые CDN и браузеры уже используют HTTP/3. Ваша сборка `curl` может не уметь. Это несовпадение нормально.

## ALPN

ALPN — Application-Layer Protocol Negotiation. Клиент и сервер используют ALPN во время рукопожатия TLS (или QUIC). Они выбирают протокол приложения. Обычные ID: `http/1.1`, `h2`, `h3`.

Без ALPN сервер на порту 443 не знал бы, хочет ли клиент HTTP/1.1 или HTTP/2 после TLS. Старый танец обновления на открытом тексте HTTP — не значение HTTPS по умолчанию.

Клиент предлагает список. Сервер выбирает один ID, который поддерживает. Если списки не встречаются, рукопожатие или следующий шаг падает. `curl -v` может напечатать согласованный протокол ALPN.

ALPN — не DNS. ALPN — не схема URL. `https` всё ещё схема для HTTP/2 и HTTP/3 в вебе. Версия — результат рукопожатия.

Не выдумывайте ID ALPN для частного протокола без плана реестра, если нужна совместимость. Не считайте, что успешное рукопожатие TLS значит HTTP/2. Читайте согласованный протокол.

QUIC использует ALPN для `h3`. TCP плюс TLS использует ALPN для `h2` или `http/1.1`.

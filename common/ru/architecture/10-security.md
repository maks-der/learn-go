# 10. Безопасность

## Описание

Архитектура безопасности — набор границ доверия, правил идентичности, правил доступа и правил работы с секретами, которые структура должна поддерживать. Эта тема покрывает границы доверия, аутентификацию против авторизации, роли OAuth 2.0 и OpenID Connect, секреты и наименьшие привилегии, моделирование угроз и риск цепочки поставок от зависимостей.

Эта тема защитная. Используйте её, чтобы снизить случайности и злоупотребления. Не используйте её, чтобы планировать атаки или обходить контроли. Следуйте закону и правилам школы или работодателя. Завершите темы 1–9 до этой темы. Тема 1 определяет безопасность как атрибут качества. Эта тема показывает структуру, которая поддерживает это качество.

Используйте один термин для каждого понятия. Аутентификация — не авторизация. Клиент — не сервер ресурсов. Секрет — не публичный идентификатор. STRIDE — чек-лист ревью. Это не продукт.

## Границы доверия

Граница доверия — линия, где уровень доверия меняется. Данные и вызовы, которые пересекают линию, нуждаются в дополнительных проверках.

Типичные зоны:

- Публичный интернет и браузеры
- Край (балансировщик нагрузки или шлюз API, тема 9)
- Процессы приложения
- Хранилища данных
- Пути оператора и администратора
- API третьих сторон

Запрос из «внутренней» сети не автоматически доверен. Внутренние сети сканируют. Случаются ошибки конфигурации. Аутентифицируйте принципалов. Авторизуйте действия. Шифруйте в пути через враждебные или общие сети.

Рисуйте границу на диаграмме контейнеров C4. Пометьте каждую стрелку, которая пересекает линию. Для каждой стрелки пишите:

- Какая идентичность путешествует
- Какая классификация данных путешествует (публичные, внутренние, персональные)
- Что происходит, если вызывающий поддельный или повторён

У монолита всё равно есть границы доверия: браузер к процессу, процесс к базе, процесс к поставщику почты. Микросервисы добавляют больше линий. Больше линий значит больше политики и больше шанса пропущенной проверки (тема 9).

Не изобретайте «безопасную зону», которая пропускает аутентификацию потому, что есть межсетевой экран. Межсетевой экран — один контроль. Идентичность — другой контроль.

Интерфейсам администратора нужна более строгая граница. Используйте отдельное имя хоста, более сильную идентичность и более короткую сессию. Журналируйте действия администратора.

## Аутентификация против авторизации

Аутентификация отвечает «кто этот принципал?». Авторизация отвечает «что этому принципалу можно делать?». Смешение двух слов вызывает дефекты.

Принципал — пользователь, учётная запись сервиса или идентичность машины. Аутентификация связывает запрос с принципалом с помощью учётных данных или токена. Сессии и токены — доказательство более ранней аутентификации.

Авторизация использует роли, разрешения или политики. «Пользователь вошёл» недостаточно. Студент, который аутентифицирован, не должен писать оценки.

Пишите авторизацию рядом с владельцем данных. Сервис, который владеет записью оценки, должен проверить права преподавателя. Шлюз может отвергнуть отсутствующий токен. Шлюз не должен быть единственным местом, которое знает «этот преподаватель может менять этот курс», если другие пути могут достичь сервиса (тема 9).

Отказывайте при сомнении. Если идентичность отсутствует или хранилище политик недоступно, запретите чувствительное действие. Запишите отказ. Не открывайтесь при отказе на путях администратора.

Не кладите учётные данные в URL (тема 5). Не журналируйте токены. Используйте HTTPS в публичных сетях (`net.topics.md`).

Дизайн сессии — архитектура. Сессия на стороне сервера в хранилище поддерживает выход. Долгоживущий токен в браузере имеет риск кражи. Пишите компромисс (тема 1).

Вызовам сервис-сервис тоже нужна идентичность. Сетевого имени недостаточно. Используйте идентичность машины, которую можно отозвать.

## Роли OAuth2 / OIDC

OAuth 2.0 — рамка делегированной авторизации. Пользователь может разрешить клиентскому приложению доступ к ресурсу без передачи пароля пользователя этому клиенту. OpenID Connect (OIDC) — слой идентичности поверх OAuth 2.0. OIDC добавляет ID-токен, который утверждает, кто пользователь.

Изучите роли. Не смешивайте имена.

- Владелец ресурса: пользователь (или владелец данных).
- Клиент: приложение, которое запрашивает доступ.
- Сервер авторизации: сервер, который аутентифицирует пользователя и выдаёт токены.
- Сервер ресурсов: API, который принимает токен и обслуживает данные.

OIDC добавляет роль поставщика идентичности (часто тот же процесс, что сервер авторизации). Клиент получает ID-токен для аутентификации и токен доступа для API.

Типичный веб-поток на высоком уровне: пользователь входит на сервере авторизации. Клиент получает токены. Клиент вызывает сервер ресурсов с токеном доступа. Сервер ресурсов проверяет токен и авторизует действие.

Правила:

- Клиент — не сервер авторизации.
- Ваш API часто сервер ресурсов. Проверяйте токены. Не изобретайте частный OAuth, если есть кампусный поставщик.
- Выберите поток, который соответствует прототипу клиента. Публичный браузерный клиент — не конфиденциальный серверный клиент. Следуйте текущим официальным рекомендациям для потока, который поддерживает ваш поставщик.
- Области грубые. Они не полная модель авторизации. Всё равно проверяйте права на уровне объекта у владельца.

Не используйте этот раздел, чтобы обойти страницу входа или украсть токены. Используйте его, чтобы разместить роли на диаграмме и избежать самодельного танца паролей с поставщиком.

Храните токены как секреты (следующий раздел). Предпочитайте короткое время жизни токена доступа и путь обновления, который документирует поставщик.

## Секреты и наименьшие привилегии

Секрет — значение, которое доказывает идентичность или расшифровывает данные: пароли, ключи API, закрытые ключи и ключи подписи сессий. Публичный идентификатор — не секрет. Идентификатор клиента может быть публичным. Секрет клиента не должен быть публичным.

Правила для секретов:

- Не кладите секреты в систему контроля версий.
- Не кладите секреты в URL, журналы или страницы ошибок.
- Используйте хранилище секретов или среду платформы, которую контролируют операторы (тема 12).
- Ротируйте секреты. Пишите, кто может их ротировать.
- Ограничивайте время жизни. Утёкший долгоживущий ключ хуже утёкшего короткоживущего токена.

Наименьшие привилегии — правило, что принципал получает только права, которые нужны работе. Процесс API не должен использовать роль базы, которая может удалить все схемы, если ему нужно только читать и писать свои таблицы. Роль студента не должна включать API администратора.

Применяйте наименьшие привилегии к:

- Людям (роли в продукте)
- Процессам (пользователь ОС, роль облака, роль базы)
- Сетям (какой хост может достичь какого порта)
- Полям данных (не возвращайте лишние персональные поля, тема 5)

Общий производственный пароль — провал владения (тема 6) и наименьших привилегий.

Шифруйте в пути в публичных и общих сетях. Шифруйте чувствительные данные в покое, когда модель угроз этого требует (следующий раздел). Шифрование не заменяет контроль доступа. Процесс, который может прочитать ключ, может прочитать данные.

## Моделирование угроз и цепочка поставок

Моделирование угроз — структурированное ревью того, как система может отказать в смысле безопасности. Простой метод — STRIDE как чек-лист:

- Подмена: поддельная идентичность
- Подделка: изменение данных
- Отрицание: отрицать действие потому, что журналы слабы
- Раскрытие информации: утечка данных
- Отказ в обслуживании: сделать сервис непригодным
- Повышение привилегий: получить лишние права

Пройдите каждую стрелку границы доверия. Спросите, какие пункты STRIDE применимы. Напишите смягчение, которое у вас уже есть или которое вы добавите. Оставайтесь в защите. Не пишите шаги эксплуатации.

Цепочка поставок — набор зависимостей, которые вы не писали: библиотеки, базовые образы контейнеров, инструменты сборки и поставщики. Злонамеренная или дефектная зависимость становится вашим дефектом.

Правила для цепочки поставок:

- Фиксируйте версии. Записывайте контрольные суммы, когда набор инструментов это поддерживает.
- Запускайте известное сканирование, которое команда может эксплуатировать.
- Не добавляйте библиотеку ради десяти строк (стоимость и поверхность).
- Конвейер — единственный поддерживаемый путь в продакшен (тема 12). Копия с ноутбука — риск цепочки поставок.
- Проверяйте, кто может публиковать в ваш реестр пакетов.

Моделирование угроз без владельца — плакат. Назначьте владельца. Ревьюйте снова, когда добавляете границу (новый поставщик, новый путь администратора).

Закон и класс данных принадлежат модели. Персональные данные на новом приёмнике журналов — новый риск раскрытия.

### Вопросы

#### Теоретические вопросы

1. Как границы доверия, аутентификация и авторизация складываются на одном запросе?
2. Почему правильная диаграмма ролей OAuth всё ещё может провалиться, если сервер ресурсов пропускает проверки на уровне объекта?
3. Как секреты и наименьшие привилегии поддерживают один атрибут качества?
4. Почему больше микросервисов увеличивают и линии доверия, и поверхность цепочки поставок?
5. Как STRIDE использует стрелки C4, которые ввела тема 1?

#### Простые практические задания

1. Напишите шпаргалку на одну страницу: граница, аутентификация/авторизация, роли OAuth, секреты, наименьшие привилегии, STRIDE, цепочка поставок.
2. Для API задач нарисуйте две границы, один вход, одну проверку владельца и нет секретов в git.
3. Добавьте в закладки обзор кампусного или открытого OIDC. Напишите четыре роли OAuth на одной диаграмме.
4. Напишите список запретов: секреты в репозитории, токены в журналах, `GET` с паролем в запросе.

#### Средние практические задания

1. Напишите краткое описание безопасности кампусного бюро находок: границы, идентичность, класс данных и один ACL поставщика (тема 9).
2. Возьмите дизайн коллеги, который доверяет внутренней сети. Добавьте идентичность и наименьшие привилегии на бумаге.
3. Напишите план на двенадцать недель: недели для входа и проверок владельца и ревью, которое добавляет STRIDE.

#### Сложные практические задания

1. Напишите чек-лист ревью безопасности, которым коллега пользуется на запросе на слияние (границы, место авторизации, секреты, зависимости).
2. Сопоставьте эту тему с темой 5 (публичный API) и темой 6 (владение данными) в таблице на одну страницу: контроль и владелец.

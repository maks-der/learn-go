# 2. Моделирование данных

## Описание

Моделирование данных — работа по именованию вещей, которые вы храните, и связей между ними. Эта тема показывает сущности, атрибуты, ключи, типы связей и `NULL`.

Используйте один термин для каждого понятия. Сущность — вещь, которую вы храните. Атрибут — факт об этой вещи. Связь — звено между сущностями. Первичный ключ идентифицирует одну строку. Внешний ключ указывает на другую строку. Завершите эту тему до написания SQL-запросов.

Сначала нарисуйте модель. Пишите SQL после того, как модель ясна.

## Сущности, атрибуты и связи

Сущность — тип вещи, которую хранит база. Примеры: клиент, товар, заказ, аудитория. В реляционном проекте одна сущность обычно становится одной таблицей.

Атрибут — факт об одной сущности. Примеры: email клиента, цена товара, дата заказа. В таблице один атрибут обычно становится одним столбцом.

Связь — звено между двумя сущностями. Пример: клиент оформляет заказ. У связи есть имя и направление, которое читается как предложение.

Называйте сущности существительными. Называйте связи глаголами. Держите имена в единственном числе в модели (`customer`, не `customers`), если команда так договорилась. Затем выбирайте имена таблиц по соглашению команды.

Пример. Библиотека:

- сущности: `member`, `book`, `loan`
- атрибуты `book`: `isbn`, `title`, `year_published`
- связи: читатель берёт книгу через выдачу

Не храните две сущности в одной куче столбцов без причины. Таблица с именем `stuff` со смешанными людьми и товарами — не модель. Разделите сущности. Добавьте связи.

У связи могут быть атрибуты. У выдачи есть `loaned_on` и `due_on`. Эти факты принадлежат выдаче, а не только читателю или книге.

## Строки и столбцы

Таблица имеет форму сетки. Столбец — именованный атрибут. Все значения в одном столбце имеют один смысл. Строка — один экземпляр сущности. Пример: одна строка в `customers` — один клиент.

Слова *запись* и *поле* в многих инструментах означают те же идеи. Запись — строка. Поле — столбец. В работе с SQL используйте *строка* и *столбец*. Используйте *запись* и *поле*, когда документ или форма так говорят. Не смешивайте пары в одном предложении без карты.

```text
customers
+----+--------+------------------+
| id | name   | email            |
+----+--------+------------------+
|  1 | Ada    | ada@example.com  |
|  2 | Alan   | alan@example.com |
+----+--------+------------------+
```

В этой сетке `name` — столбец. Пара `Ada` плюс `ada@example.com` сидит в одной строке. Эта строка — один клиент.

У каждого столбца есть тип данных. Тип ограничивает значения. Пример: `email` — текст. `id` — целое. Позже тема покрывает типы подробнее.

Не кладите два факта в один столбец, если их нужно искать отдельно. Пример: не храните `"Ada <ada@example.com>"` в одном столбце, если нужно искать по email. Используйте два столбца.

Результат запроса тоже имеет строки и столбцы. Эта сетка не всегда сохранённая таблица. Это вывод оператора.

## Первичные и внешние ключи

Первичный ключ — столбец или набор столбцов, который идентифицирует одну строку. Никакие две строки не делят одно значение первичного ключа. Первичный ключ не должен быть `NULL`.

СУБД обеспечивает уникальность. Вставка с дубликатом первичного ключа падает. Это правило держит каждый экземпляр сущности отдельным.

Выбирайте стабильный первичный ключ. Не используйте значение, которое пользователи часто меняют. Человек может сменить email. Email — слабый первичный ключ, если такая смена обычна.

```sql
CREATE TABLE customers (
    customer_id INTEGER PRIMARY KEY,
    email VARCHAR(255) NOT NULL,
    name VARCHAR(100) NOT NULL
);
```

`customer_id` идентифицирует клиента. Два клиента могут делить имя. Они не должны делить `customer_id`.

Первичный ключ может иметь больше одного столбца. Такой ключ — составной первичный ключ. Пример: `order_id` плюс `line_no` в `order_lines`. Вместе они идентифицируют одну строку.

Каждая таблица, которую вы считаете сущностью, должна иметь первичный ключ. Таблица без первичного ключа допускает дубликаты строк. На одну строку нельзя безопасно указать внешним ключом.

Внешний ключ — столбец или набор столбцов, который указывает на первичный ключ (или уникальный ключ) в другой таблице. Указанная строка должна существовать. Это правило — ссылочная целостность.

Пример. `orders.customer_id` указывает на `customers.customer_id`. Нельзя хранить заказ для клиента, которого нет.

```sql
CREATE TABLE orders (
    order_id INTEGER PRIMARY KEY,
    customer_id INTEGER NOT NULL,
    ordered_at TIMESTAMP NOT NULL,
    CONSTRAINT fk_orders_customers
        FOREIGN KEY (customer_id) REFERENCES customers (customer_id)
);
```

СУБД отклоняет вставку в `orders`, когда `customer_id` нет в `customers`. СУБД также отклоняет удаление клиента, пока заказы указывают на него, если вы не задали правило каскада. Безопасное действие по умолчанию — отклонить удаление.

Ссылочная целостность держит связи валидными. Без неё отчёты показывают заказы с отсутствующими клиентами. Такие строки — сироты.

Внешний ключ может быть `NULL`, когда связь необязательна. Пример: `orders.coupon_id` может быть `NULL`, когда у заказа нет купона. Не используйте `NULL` в смысле «неизвестный клиент», если у каждого заказа должен быть клиент. Поставьте `NOT NULL` на этот внешний ключ.

Столбцы внешнего ключа должны совпадать со ссылочным ключом по числу и по типу. Один целочисленный ключ требует один целочисленный внешний ключ.

Не используйте значение первичного ключа для новой сущности после удаления старой строки, если другие системы всё ещё держат старый id. Предпочитайте новые значения.

## Один-к-одному, один-ко-многим и многие-ко-многим

У связи есть кардинальность. Кардинальность говорит, сколько строк с каждой стороны могут связаться.

**Один-к-одному.** Одна строка в A связана не более чем с одной строкой в B. Пример: у сотрудника один шкафчик. Поставьте уникальный внешний ключ в одну таблицу. Пример: `lockers.employee_id` уникален. Каждый шкафчик указывает на одного сотрудника. Каждый сотрудник появляется не более одного раза.

**Один-ко-многим.** Одна строка в A связана со многими строками в B. Одна строка в B связана с одной строкой в A. Пример: у клиента много заказов. Поставьте внешний ключ на стороне «многие». `orders.customer_id` указывает на `customers`.

**Многие-ко-многим.** Одна строка в A связана со многими строками в B. Одна строка в B связана со многими строками в A. Пример: студенты и курсы. Студент берёт много курсов. У курса много студентов. Нельзя поставить один внешний ключ в `students` или в `courses`. Вы добавляете таблицу связи. Следующий раздел покрывает эту таблицу.

Читайте каждую связь в обоих направлениях. «У клиента много заказов» — тот же проект, что «у каждого заказа один клиент».

Не кладите список id через запятую в столбец, чтобы имитировать многие-ко-многим. Такой проект ломает запросы и внешние ключи. Используйте таблицу связи.

```text
One-to-many:   customers (1) ----< orders (many)
One-to-one:    employees (1) ----- lockers (1)
Many-to-many:  students (many) >----< courses (many)
```

## Справочные таблицы и таблицы связи

Справочная таблица — маленькая таблица с контролируемым списком. Примеры: `countries`, `order_statuses`, `currencies`. Другие таблицы указывают на неё внешним ключом. Справочная таблица держит список в одном месте. Вы не повторяете слово `shipped` с разными написаниями во многих строках.

```sql
CREATE TABLE order_statuses (
    status_code VARCHAR(20) PRIMARY KEY,
    label VARCHAR(50) NOT NULL
);

CREATE TABLE orders (
    order_id INTEGER PRIMARY KEY,
    status_code VARCHAR(20) NOT NULL,
    CONSTRAINT fk_orders_status
        FOREIGN KEY (status_code) REFERENCES order_statuses (status_code)
);
```

Таблица связи реализует многие-ко-многим. Она держит внешние ключи на обе стороны. Часто у неё есть свои атрибуты, например `enrolled_on`.

```sql
CREATE TABLE student_courses (
    student_id INTEGER NOT NULL,
    course_id INTEGER NOT NULL,
    enrolled_on DATE NOT NULL,
    PRIMARY KEY (student_id, course_id),
    CONSTRAINT fk_sc_students FOREIGN KEY (student_id) REFERENCES students (student_id),
    CONSTRAINT fk_sc_courses FOREIGN KEY (course_id) REFERENCES courses (course_id)
);
```

Каждая пара `(student_id, course_id)` появляется один раз. Этот первичный ключ предотвращает дубликат записи.

Имена таблицы связи часто сочетают два имени сущностей: `student_courses`, `order_items`. Некоторые команды используют имя роли: `enrollments`. Выберите один стиль и держите его.

Не храните один и тот же справочный текст в каждой родительской строке, когда список общий и должен оставаться согласованным. Используйте справочную таблицу. Не добавляйте таблицу связи для настоящего один-ко-многим. Достаточно одного внешнего ключа.

## Суррогатные ключи и натуральные ключи

Натуральный ключ — уникальный ключ, который существует в бизнесе. Примеры: ISBN книги, код страны ISO, номер счёта, который уже использует финансы.

Суррогатный ключ — уникальное значение, которое база генерирует для идентичности. Примеры: целое `id`, UUID. У значения нет бизнес-смысла. Пользователи не вводят его как бизнес-факт.

Оба вида могут быть первичным ключом. Натуральный ключ полезен, когда он уникален, стабилен и всегда известен в момент вставки. Суррогатный ключ полезен, когда натуральный ключ длинный, составной или может меняться.

Пример. `countries.country_code` (`SE`, `UA`) — стабильный натуральный ключ. `orders.order_id` как целое — обычный суррогат. `customers.email` уникален во многих системах, но может меняться, поэтому многие команды добавляют `customer_id` и держат email уникальным как отдельное ограничение.

Не используйте суррогатный ключ как оправдание пропустить уникальность бизнес-ключа. Если ISBN должен быть уникальным, добавьте ограничение `UNIQUE` на `isbn`, даже когда `book_id` — первичный ключ.

```sql
CREATE TABLE books (
    book_id INTEGER PRIMARY KEY,
    isbn VARCHAR(13) NOT NULL UNIQUE,
    title VARCHAR(200) NOT NULL
);
```

Не меняйте первичный ключ как обычную бизнес-правку. Если бизнес-значение может меняться, предпочитайте суррогатный первичный ключ и уникальный натуральный ключ.

## NULL: отсутствующее значение, не ноль и не пустая строка

`NULL` значит, что значение отсутствует. `NULL` — не число `0`. `NULL` — не пустая строка. `NULL` — не текст `N/A`. Эти значения — присутствующие значения.

Используйте `NULL`, когда атрибут не применим или неизвестен. Пример: `employees.middle_name` может быть `NULL`, когда у человека нет отчества. Пример: `orders.shipped_at` может быть `NULL`, когда заказ не отгружен.

Не храните `0` в смысле «цены ещё нет», если `0` также валидная цена. Не храните `''` в смысле «неизвестный email», если вы также ищете email. Используйте `NULL` для отсутствия. Используйте реальное значение только когда это значение верно.

SQL обрабатывает `NULL` особым способом. Сравнение с `NULL` не даёт истину. `price = NULL` неизвестно. Вы проверяете отсутствие через `IS NULL` и `IS NOT NULL`. Позже тема покрывает эти предикаты.

```sql
SELECT order_id
FROM orders
WHERE shipped_at IS NULL;
```

Агрегатные функции в общем игнорируют `NULL`. `SUM` от `{10, NULL, 5}` равен `15`. `COUNT(column)` не считает `NULL` в этом столбце. Позже тема покрывает это поведение.

Первичный ключ не должен быть `NULL`. Столбец `NOT NULL` должен иметь значение при каждой вставке.

Будьте последовательны. Если `shipped_at` равен `NULL` до момента отгрузки, не храните также текст статуса `not shipped` без причины. Два источника одного факта могут разъехаться.

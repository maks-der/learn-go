# 13. Обзор обработки потоков

## Описание

Обработка потоков читает записи из Kafka, вычисляет результат и пишет записи или запрашиваемое состояние. Эта тема — обзор. Она называет обычные инструменты и общие идеи. Тема 14 подробнее покрывает Kafka Streams.

Эта тема покрывает Kafka Streams, KSQL / ksqlDB, Apache Flink, stateless против stateful обработки, типы окон, changelog-топики и хранилища состояния. Завершите эту тему после тем 2, 5, 7 и 8. Потоковые задачи используют кластер Kafka. Используйте KRaft для новых кластеров. Обработчикам потоков не нужен ZooKeeper.

Используйте один термин для каждого понятия. Потоковая задача — программа, которая обрабатывает записи непрерывно. Stateless-обработка использует только текущую запись. Stateful-обработка хранит store. Окно группирует записи по времени. Changelog-топик — компактируемый топик Kafka, который записывает обновления store. Хранилище состояния — локальное (или запрашиваемое) состояние задачи.

## Kafka Streams

Kafka Streams — библиотека Java. Вы запускаете её внутри процесса приложения. Это не отдельный кластер. Каждый экземпляр — консьюмер Kafka и продюсер Kafka (и больше). Экземпляры, которые делят `application.id`, образуют группу. Kafka назначает партиции этим экземплярам.

Вы строите топологию: граф исходных топиков, процессоров и sink-топиков. Тема 14 объясняет KStream, KTable, DSL и Processor API.

Kafka Streams хранит локальное состояние на диске (часто RocksDB) и подкрепляет это состояние changelog-топиками на кластере Kafka. После перезапуска или ребаланса экземпляр может восстановить состояние из changelog.

Обработка exactly-once доступна через транзакционный протокол Kafka (тема 7 и тема 14). Вы задаёте гарантию обработки в конфигурации Streams.

Используйте Kafka Streams, когда команда пишет Java (или язык JVM), задача умещается в приложение и вы хотите эксплуатировать задачу как обычный сервис. Не используйте Kafka Streams, если нужен первоклассный API не-JVM как единственный вариант.

Kafka Streams говорит с брокерами. Для новой работы используйте брокеры KRaft. В текущих Streams нет клиента ZooKeeper.

## KSQL / ksqlDB

ksqlDB (в старых материалах также KSQL) — система обработки потоков, которая использует операторы в стиле SQL. Вы запускаете сервер ksqlDB. Клиенты отправляют операторы: создать поток, создать таблицу, filter, join, aggregate.

**Поток** в ksqlDB — последовательность событий (как KStream). **Таблица** — последнее значение на ключ (как KTable). Тема 14 определяет эти идеи в Kafka Streams. Имена похожи намеренно.

ksqlDB использует Kafka как журнал и во многих развёртываниях использует Kafka Streams внутри. Кластер Kafka всё равно нужен. Используйте KRaft для этого кластера. ksqlDB не часть брокера Apache Kafka. Это отдельный продукт (Confluent и связанные дистрибутивы).

Используйте ksqlDB, когда аналитики или платформенные команды хотят SQL и сервер, а не топологию Java в каждом сервисе. Не ожидайте каждую функцию Streams или каждый свой процессор в SQL.

Примеры операторов (только форма; следуйте текущему синтаксису ksqlDB):

```text
CREATE STREAM orders (... ) WITH (KAFKA_TOPIC='orders.placed', VALUE_FORMAT='JSON');
CREATE STREAM large_orders AS SELECT * FROM orders WHERE amount > 100;
```

Форматы и Schema Registry следуют теме 11. Постоянные запросы пишут результаты в топики Kafka.

## Apache Flink (часто с Kafka)

Apache Flink — движок обработки потоков. Вы запускаете кластер Flink (JobManager и TaskManagers) или управляемый сервис Flink. Задача Flink — DAG операторов. Flink может использовать Kafka как source и как sink.

Flink по умолчанию не библиотека Kafka внутри маленького сервиса. Это вычислительный кластер. У него своя модель checkpoint и savepoint. Офсеты Kafka — часть этого состояния, когда используете Kafka source.

Используйте Flink, когда нужны крупномасштабные stateful-задачи, сложное event time или команда, которая уже эксплуатирует Flink. Используйте Kafka Streams, когда задача принадлежит микросервису и язык — JVM. Оба могут делить один кластер Kafka KRaft как журнал.

У Flink также есть объединение batch и stream. Этому справочнику нужна только идея: Flink читает Kafka, вычисляет, пишет Kafka или другой sink.

Коннекторы Kafka во Flink должны совпадать с версией протокола Kafka. Они не запускают ZooKeeper. Направляйте их на `bootstrap.servers`.

Не считайте Flink заменой Kafka Connect один в один. Connect копирует и трансформирует записи. Flink вычисляет окна, join и большое состояние. Некоторые команды используют оба.

## Stateless map/filter против stateful-агрегаций

**Stateless**-обработка использует только текущую запись (и константы). `map` меняет запись. `filter` оставляет или отбрасывает запись. Задача может потерять локальную память и всё же быть корректной, если снова читает топик с последнего зафиксированного офсета.

**Stateful**-обработка хранит store, ключом которого является ключ записи (и иногда окно). Примеры: count, sum, join, уникальный пользователь в день. Задача должна восстановить этот store после падения. Для этого существуют changelog-топики и checkpoint.

Filter, который отбрасывает маленькие заказы, — stateless. Count заказов на клиента — stateful. Join заказов и клиентов — stateful.

Состояние растёт с ключами и с окнами. Неограниченные наборы ключей заполняют диск. Планируйте компакцию, ретеншн и томбстоуны на changelog-топиках (тема 8).

Exactly-once и at-least-once (тема 7) важнее, когда у задачи есть состояние. Дубликат обработки stateless map всё ещё может написать дубликат выходной записи. Дубликат обработки count может удвоить count, если фреймворк не использует транзакции или идемпотентные обновления.

Не прячьте запись в базу внутри «stateless» map без плана. Эта запись — внешнее состояние.

## Окна: tumbling, hopping, session

Окно группирует записи, которые делят ключ и попадают в диапазон времени. Окна — для stateful-агрегации. Время может быть event time (метка времени записи) или processing time (часы на задаче). Event time — обычный выбор, когда записи могут прийти поздно.

**Tumbling**-окна имеют фиксированный размер и не перекрываются. Пример: 5-минутные окна в 10:00, 10:05, 10:10. Каждая запись принадлежит одному tumbling-окну.

**Hopping**-окна имеют фиксированный размер и интервал hop. Hop меньше размера, когда нужно перекрытие. Пример: размер 5 минут, hop 1 минута. Одна запись может принадлежать больше чем одному hopping-окну.

**Session**-окна используют разрыв. Если для этого ключа не приходит запись в течение времени разрыва, сессия закрывается. Следующая запись начинает новую сессию. Длина сессии не фиксирована.

Поздним записям нужен grace period или разрешённая опоздание в некоторых движках. После закрытия окна поздняя запись может быть проигнорирована или может обновить поздний результат. Читайте документацию движка.

Окна создают больше состояния, чем простой count-по-ключу. Каждый ключ окна — `(key, window-start)` или идентификатор сессии. Ретеншн состояния окна — конфигурация.

Kafka Streams, ksqlDB и Flink все реализуют эти типы окон. Имена почти те же. Ключи конфигурации отличаются.

## Changelog-топики и хранилища состояния

**Хранилище состояния** держит текущую агрегацию или состояние join. Kafka Streams часто использует RocksDB на диске экземпляра. Flink использует свои бэкенды состояния. ksqlDB использует store Streams под слоем SQL.

**Changelog-топик** — топик Kafka, который записывает каждое обновление store как запись (ключ = ключ store, значение = новое значение store). Топик обычно компактируемый (тема 8). После сбоя экземпляр читает changelog и пересобирает store.

Томбстоуны в changelog удаляют ключ из store (тема 8). Ретеншн должен хранить компактированную историю, которая нужна восстановлению. Не задавайте короткий delete-ретеншн на changelog, если не принимаете неверное восстановление.

Changelog-топики внутренние. Kafka Streams называет их из `application.id` и имени store. Не пишите в них из консольного продюсера.

Интерактивные запросы (тема 14) читают хранилище состояния. Changelog — устойчивая копия на кластере.

KRaft хранит метаданные кластера. KRaft не заменяет changelog-топики. Данные партиций и changelog по-прежнему живут в `log.dirs` на брокерах.

Если удалить `application.id` или задачу Flink без плана, можно оставить сиротские внутренние топики. Используйте процедуры admin.

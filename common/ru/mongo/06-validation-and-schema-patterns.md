# 6. Валидация и шаблоны схемы

## Описание

Эта тема показывает, как проверять документы в MongoDB и как применять частые шаблоны схемы. Вы прикрепляете JSON Schema к коллекции. Задаёте `validationLevel` и `validationAction`. Сравниваете валидацию в приложении и в базе. Изучаете шаблоны attribute, bucket, outlier, computed, subset и extended-reference. Добавляете поле версии схемы.

Сначала завершите моделирование данных. Завершите эту тему до изучения драйверов и промышленных изменений схемы.

Используйте один термин для каждого понятия. **Валидатор** — правило на коллекции. **JSON Schema** — обычный язык валидатора. **Шаблон** — дизайн, который применяют намеренно. Не применяйте каждый шаблон к каждой коллекции.

## Валидация JSON Schema, `validationLevel`, `validationAction`

Коллекцию можно создать или изменить через collMod с валидатором:

```javascript
db.createCollection("users", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["email", "createdAt"],
      properties: {
        email: { bsonType: "string", pattern: "^.+@.+$" },
        createdAt: { bsonType: "date" },
        age: { bsonType: "int", minimum: 0 }
      },
      additionalProperties: true
    }
  }
})
```

`$jsonSchema` описывает типы BSON через `bsonType`. Используйте `string`, `int`, `long`, `double`, `decimal`, `bool`, `date`, `objectId`, `array`, `object`, `null`, `binData`.

`required` перечисляет поля, которые должны быть. `properties` описывает именованные поля. `additionalProperties: false` отклоняет неизвестные поля. Эта настройка строгая. Используйте её, когда схема стабильна.

Можно использовать `oneOf` для версий или вариантов. Массивы описывают через `items`.

Существующие коллекции: `db.runCommand({ collMod: "users", validator: { $jsonSchema: { ... } } })`.

Слишком строгий валидатор заблокирует записи. Тестируйте на копии. Вставляйте допустимые и недопустимые документы.

Схема — не полная модель приложения. Она не заменяет уникальные индексы. Не заменяет авторизацию.

**validationLevel** управляет, какие документы сервер проверяет.

- `strict` — проверять все вставки и все обновления. Это значение по умолчанию.
- `moderate` — проверять вставки и проверять обновления только если существующий документ уже соответствует схеме. Документы, которые были недопустимы до валидатора, в некоторых случаях всё ещё можно обновить. Прочитайте текущее руководство про точное правило moderate.

Используйте `strict` для новых коллекций. Используйте `moderate`, когда добавляете валидатор к коллекции со старыми недопустимыми документами и их всё ещё нужно обновлять.

**validationAction** управляет, что сервер делает при неудачной проверке.

- `error` — отклонить запись. Это значение по умолчанию.
- `warn` — принять запись и записать предупреждение в лог.

Используйте `warn`, когда вводите схему и хотите найти нарушения без блокировки промышленных записей. Смотрите логи. Исправьте приложение. Затем поставьте `error`.

```javascript
db.runCommand({
  collMod: "users",
  validator: { $jsonSchema: { /* ... */ } },
  validationLevel: "moderate",
  validationAction: "warn"
})
```

Не оставляйте `warn` навсегда. Недопустимые данные будут расти.

`strict` плюс `error` — обычное конечное состояние для стабильной коллекции.

## Валидация в приложении против валидации в базе

**Валидация в приложении** работает в клиенте или API. Примеры: библиотека JSON Schema, декодер типов, Mongoose, Bean Validation. Она проверяет ввод до записи. Возвращает ясную ошибку пользователю.

**Валидация в базе** работает в `mongod`. Она проверяет каждого писателя: API, скрипт, `mongosh`, миграцию. Это последняя защита.

Используйте оба.

Приложение:

- Проверяет правила, обращённые к пользователю (сила пароля, подтверждение email)
- Даёт ошибки по полям
- Может использовать более богатые типы, чем схема коллекции

База:

- Блокирует плохие записи из инструментов и забытых скриптов
- Обеспечивает тип и обязательные поля
- Не зависит от одного языка

Не полагайтесь только на приложение. Будущее задание напишет без этого кода.

Не полагайтесь только на базу. Пользователь увидит ошибку драйвера, а не ошибку формы. Схема не выразит каждое бизнес-правило.

Держите две схемы близко. Если `age` — `int` в MongoDB, API не должен слать float, который станет другим типом BSON.

Драйверы могут слать типы, которые проходят приложение, но падают на `bsonType`. Тестируйте настоящий BSON, а не только JSON.

Стабильные имена и типы держат запросы, индексы и валидаторы рабочими. Выберите имя поля и держите его. Выберите тип BSON и держите его. Если нужно сменить имя или тип, используйте expand-contract и `schemaVersion`.

## Шаблоны attribute, bucket, outlier, computed, subset и extended-reference

**Шаблон** — известный способ формы документов. Официальные имена шаблонов приходят из документации и докладов MongoDB. Используйте эти имена, чтобы команда говорила одним словарём. Именуйте шаблон в заметках, когда применяете его.

**Шаблон атрибутов (attribute).** Храните много необязательных предикатов как массив документов ключ–значение.

```javascript
{
  attrs: [
    { k: "color", v: "red" },
    { k: "size", v: "M" }
  ]
}
```

Индексируйте `{ "attrs.k": 1, "attrs.v": 1 }`. Запрос красного цвета использует `$elemMatch` по `k` и `v`. Используйте этот шаблон, когда у многих документов разные необязательные поля и эти поля нужно индексировать. Не используйте его для малого стабильного набора полей.

**Шаблон корзины (bucket).** Группируйте много мелких событий в один документ. Документ — **корзина** на диапазон времени или лимит размера.

```javascript
{
  deviceId: "d1",
  start: ISODate("2026-01-15T10:00:00Z"),
  n: 3,
  readings: [
    { t: ISODate("2026-01-15T10:01:00Z"), c: 21.1 },
    { t: ISODate("2026-01-15T10:02:00Z"), c: 21.2 }
  ]
}
```

Плюсы: меньше документов, меньше индекс `_id`, одно чтение окна. Корзину нужно ограничить. Закрывайте корзину, когда `n` достигает максимума или когда окно времени кончается. Коллекции временных рядов MongoDB используют родственную идею внутри сервера.

**Шаблон выброса (outlier).** Держите обычный случай в основном документе. Редкий огромный случай перенесите в другую коллекцию. Пример: у большинства книг меньше 20 соавторов. У нескольких книг 500 участников. Встраивайте авторов до 20. Ставьте `hasExtraAuthors: true` и храните остальных в `book_authors`. Большинству чтений лишний запрос не нужен. Измерьте процентили. Если 99-й процентиль всё ещё огромен, встраивание — неверный выбор по умолчанию.

**Вычисленный шаблон (computed).** Храните значение, которое можно посчитать из других полей. Обновляйте хранимое значение, когда источник меняется. Пример: хранить `commentCount` на посте. Увеличивать его при вставке комментария. Не делайте `$count` всех комментариев на каждый просмотр страницы. Цена — записи должны держать значение верным. Ошибка может сделать хранимое значение устаревшим. Может понадобиться задание починки.

**Шаблон подмножества (subset).** Храните **маленькую копию** связанных данных для частого чтения. Полный документ живёт в другой коллекции. Пример: список товаров хранит `{ productId, name, thumbUrl, price }`. Коллекция `products` хранит длинное описание. Обновления исходного поля, которое есть в подмножестве, должны обновлять копии, либо вы принимаете устаревание. Не дублируйте весь документ.

**Расширенная ссылка (extended reference).** Храните id **и** несколько полей из ссылаемого документа.

```javascript
{
  productId: ObjectId("..."),
  name: "Nail",
  price: NumberDecimal("1.50")
}
```

Id — живая связь. Лишние поля — снимок или кэш для частого чтения. Этот шаблон стоит между голой ссылкой и полным встраиванием. Решите, лишние поля — **снимок** (история заказа) или **кэш** (можно обновить). Не расширяйте ссылку двадцатью полями.

Не применяйте все шесть шаблонов к одной коллекции.

## Поле версии схемы

**Поле версии схемы** записывает форму документа. Частое имя — `schemaVersion` или `v`.

```javascript
{ schemaVersion: 2, name: "Ann", displayName: "Ann" }
```

Приложение читает версию. Оно запускает **читателя**, который понимает версию 1 и версию 2. **Писатель** пишет только текущую версию или пишет оба поля во время перехода.

Это идея expand-contract:

1. Выложить код, который читает старое и новое.
2. Писать новые поля (expand).
3. Дозаполнить старые документы.
4. Убрать чтения старых полей (contract).

Поле версии делает форму явной. Можно запросить `{ schemaVersion: 1 }` для дозаполнения.

Не увеличивайте версию на каждое мелкое добавление, если читатель может считать отсутствующее поле значением по умолчанию. Увеличивайте, когда меняется смысл поля или когда форму трудно обнаружить.

Не храните два полностью несовместимых смысла в одном поле без версии или нового имени.

Валидация может разрешить больше одной версии через `oneOf`.

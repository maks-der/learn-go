# 17. Безопасность и изоляция

## Описание

Ядро изолирует пользователей и процессы. Эта тема объясняет идентификаторы пользователей и наименьшие привилегии, capabilities Linux и seccomp. Вы узнаете идею песочницы, разницу между эксплуатацией ядра и эксплуатацией пользовательского пространства и Secure Boot на высоком уровне.

Завершите эту тему после виртуализации. Завершите эту тему до сетевого стека (тема 18). Вы уже знаете биты разрешений, пространства имён и ядро против пользовательского пространства. Теперь вы узнаёте, как Linux ограничивает, что процесс может делать.

Используйте один термин для каждого понятия. Идентификатор пользователя (UID) — целое, которое ядро хранит для процесса и для владения файлом. Наименьшие привилегии — правило, что программа должна работать с наименьшими правами, которые всё ещё позволяют ей работать. Capability — раскол старой силы root на именованные права. Seccomp — фильтр системных вызовов. Песочница — сочетание инструментов изоляции вокруг программы. Не смешивайте capability с битом разрешения файла. Не смешивайте Secure Boot с паролем входа.

## Идентификаторы пользователей и наименьшие привилегии

Linux идентифицирует пользователя по UID. У процесса есть реальный UID, эффективный UID и сохранённый UID (и UID файловой системы). Ядро использует эффективный UID для большинства проверок разрешений. `id` печатает ID оболочки.

UID 0 — root. Root может пройти большинство проверок разрешений. Программа, которая работает как root, может читать частные файлы, привязывать низкие порты и загружать модули (если другие слои не останавливают).

Наименьшие привилегии означают:

1. Используйте обычную учётную запись пользователя для ежедневной работы (тема 1).
2. Дайте службе свой UID.
3. Не запускайте сетевой демон как root после bind, если можете сбросить привилегии.
4. Используйте `sudo` для одной команды, не оболочку root на всю сессию.

Двоичные файлы `setuid` работают с эффективным UID владельца файла. `passwd` — классический пример. Ошибка в программе `setuid` — риск повышения привилегий. Дистрибутивы сводят к минимуму двоичные файлы `setuid` root.

Пользовательское пространство имён может отобразить UID 0 внутри пространства имён на ненулевой UID хоста. Внутри процесс выглядит как root. На хосте он не root. Эта карта — строительный блок контейнера (тема 16). Сама по себе это не полный продукт безопасности.

Биты разрешений файлов (тема 11) всё ещё применимы. Изоляция сбоит, если каждый файл читаем всеми или если UID вашей службы может писать `/`.

Не практикуйтесь как root. Не отключайте проверки пользователей в ядре, которое вам нужно.

## Capabilities (Linux)

Старый Unix считал root одним битом: UID 0 или нет. Capabilities Linux раскалывают эту силу на именованные флаги. Примеры:

- `CAP_NET_BIND_SERVICE`: привязывать порты ниже 1024
- `CAP_NET_ADMIN`: конфигурация сети
- `CAP_SYS_ADMIN`: большой набор операций администратора (всё ещё очень широкий)
- `CAP_SYS_MODULE`: загружать модули ядра
- `CAP_DAC_OVERRIDE`: обходить проверки разрешений файлов

У процесса есть набор capabilities. Файловые capabilities могут давать биты, когда вы делаете `exec` двоичного файла (`setcap`). Это более тонкий инструмент, чем `setuid` root, но широкая capability всё ещё почти root.

`capsh`, `getpcaps` и `/proc/self/status` (поля Cap*) показывают наборы. `man 7 capabilities` — справочник.

Ambient и inheritable наборы управляют тем, что сохраняют потомки. Рантаймы контейнеров сбрасывают большинство capabilities. Файлы юнитов systemd могут использовать `CapabilityBoundingSet`.

`CAP_SYS_ADMIN` — знак предупреждения. Он покрывает многие операции. Сбросить «всё кроме `CAP_SYS_ADMIN`» — не наименьшие привилегии.

Capabilities не заменяют UID. Процесс может быть UID 1000 и всё равно иметь `CAP_NET_BIND_SERVICE`. Процесс может быть UID 0 и иметь пустой bounding set в тесной песочнице.

Не делайте `setcap` случайных двоичных файлов на машине, которая вам нужна.

## Seccomp

Seccomp (secure computing) — фильтр Linux на системные вызовы. После того как процесс устанавливает фильтр, ядро проверяет каждый системный вызов против фильтра. Фильтр может разрешить, запретить, вернуть ошибку или убить поток.

Исходный режим разрешал только крошечный набор вызовов (`read`, `write`, `exit` и несколько других). Этот режим слишком строг для обычной программы libc.

Seccomp-BPF позволяет написать программу Berkeley Packet Filter на номер системного вызова и значения аргументов (с пределами). libseccomp — обычная библиотека-помощник. Рантаймы контейнеров ставят профиль по умолчанию. Chrome и другие песочницы используют seccomp.

Фильтр — чёрный список или белый список. Белый список нужных вызовов теснее. Чёрный список известных плохих вызовов слабее. Могут появиться новые системные вызовы. Список «запретить по умолчанию» стареет лучше, если вы его поддерживаете.

Seccomp сам по себе не фильтрует пути файлов. Процесс, который может вызвать `open`, всё ещё может открыть многие файлы. Сочетайте seccomp с chroot, пространствами имён и разрешениями файлов.

`prctl(PR_SET_SECCOMP, ...)` и `seccomp()` устанавливают фильтры. После установки типичный процесс не может ослабить фильтр. Привилегированный помощник может быть вторым процессом.

Не копируйте случайный фильтр BPF из интернета на производственный хост. Тестируйте в VM. Неверный фильтр ломает `exec` или DNS и выглядит как загадочный `EPERM`.

## Идея песочницы

Песочница — связка ограничений вокруг программы. Программа всё ещё работает. Она видит меньше объектов и меньше вызовов.

Типичные ингредиенты Linux:

1. UID и GID (наименьшие привилегии)
2. Разрешения файлов и выделенный корень или overlay
3. Пространства имён (тема 16)
4. Cgroups (тема 16)
5. Capabilities
6. Seccomp
7. Landlock или политики LSM (SELinux, AppArmor) на некоторых системах
8. VM, когда само ядро ненадёжно (тема 16)

Идея — защита в глубину. У одного слоя есть ошибки. Второй слой всё равно должен остановить класс вреда.

Песочница — не доказательство безопасности. Ошибка ядра может сбежать из контейнера. Побег из VM реже и всё ещё существует. Ошибка приложения всё ещё может утечь данные, которые песочница позволяет процессу читать.

Браузеры сажают процессы отрисовщика в песочницу. Отрисовщик разбирает враждебный HTML. Браузер предполагает, что отрисовщик — цель атаки. Инструменты ОС ограничивают, что скомпрометированный отрисовщик может открыть.

Для этого пути песочница — дизайн: перечислите, что процессу нужно, затем запретите остальное. Начните с обычного UID. Добавляйте слои, когда угроза растёт.

Не стройте песочницу только из `chroot`. Тема 12 уже утверждала, что `chroot` слаб.

## Эксплуатации ядра и пользовательские эксплуатации

Эксплуатация — использование ошибки, чтобы сломать правило безопасности. Этот раздел называет классы. Он не учит, как писать эксплуатацию.

Пользовательская эксплуатация атакует пользовательскую программу. Примеры: переполнение буфера в помощнике setuid, обход пути в веб-сервере, вредоносный документ, который роняет разборщик. Атакующий получает права этого процесса (и, возможно, больше, если процесс привилегирован). ASLR, NX и W^X (тема 10) повышают цену. Они не убирают ошибки.

Эксплуатация ядра атакует ядро. Успешная эксплуатация ядра может дать кольцо 0 на хосте. Тогда идентификаторы пользователей, seccomp и контейнеры на этом ядре не являются границей. Поэтому вы обновляете ядро и не загружаете случайные модули (тема 20).

Эксплуатация гостевого ядра в VM захватывает гостя. Эксплуатация гипервизора или ядра хоста хуже. Цели изоляции различаются (тема 16).

Повышение привилегий — любой прыжок от меньших прав к большим. Оно может остаться в пользовательском пространстве (UID 1000 к UID 0) или войти в ядро.

Защита в этом курсе:

1. Запускайте меньше кода как root.
2. Держите ядро и libc обновлёнными.
3. Не отключайте смягчения ради маленького бенчмарка на машине, которая вам нужна.
4. Считайте исходники драйверов и модулей доверенным кодом.

Этот справочник никогда не просит вас писать эксплуатацию, атаку доказательства концепции или обход.

## Secure Boot (высокий уровень)

Secure Boot — возможность прошивки. При включении прошивка проверяет криптографическую подпись загрузчика (и цепочка может продолжиться до ядра). Если подпись не доверенная, прошивка может отказаться грузиться.

Якорь доверия — ключи в прошивке (ключ платформы, ключ обмена ключами и списки разрешённых или запрещённых в модели UEFI). Производитель или пользователь регистрирует ключи. Тема 3 назвала UEFI. Этот раздел называет проверку.

Цели:

- Остановить неза подписанный загрузчик от работы до ОС.
- Усложнить класс постоянных буткитов.

Пределы:

- Secure Boot не шифрует ваши файлы. Шифрование диска — отдельная возможность (LUKS в Linux).
- Secure Boot не останавливает подписанный, но ошибочный загрузчик или ядро.
- Если у атакующего контроль прошивки или ваш зарегистрированный ключ, цепочка не помогает.
- Некоторой аппаратуре и некоторым драйверам нужен подписанный shim. Дистрибутивы это документируют.

Linux часто использует подписанный shim и GRUB или подписанный UKI (unified kernel image). Переменные EFI видны в `/sys/firmware/efi`, когда система загрузилась в режиме UEFI.

Secure Boot — не вход. Это не песочница. Это проверка подлинности во время загрузки.

Не выключайте Secure Boot на машине, которая вам нужна, если не знаете зачем (лаборатория неза подписанных ядер). Не регистрируйте случайные ключи.

### Вопросы

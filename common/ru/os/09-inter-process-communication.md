# 9. Межпроцессное взаимодействие

## Описание

Процессы по умолчанию не делят адресное пространство. Им всё равно нужно обмениваться данными и событиями. Эта тема объясняет главные инструменты межпроцессного взаимодействия (IPC) Unix: каналы и FIFO, сокеты домена Unix, сигналы и общую память с синхронизацией. Последний раздел говорит, когда использовать каждый инструмент.

Завершите эту тему после устройств и ввода-вывода. Завершите эту тему до виртуализации (тема 10). Вы уже знаете дескрипторы файлов, `fork` и мьютексы.

Используйте один термин для каждого понятия. Канал — безымянный буфер ядра с концом чтения и концом записи. FIFO — именованный канал, который живёт в пространстве имён файловой системы. Сокет Unix — сокет, который использует путь файловой системы или абстрактное имя на одной машине. Сигнал — асинхронное уведомление процессу или потоку. Общая память — отображение, которое могут видеть больше одного процесса. Не смешивайте канал с сокетом Unix. Не смешивайте сигнал с возвращаемым значением `wait`.

## Каналы и FIFO

Канал — однонаправленный поток байтов внутри ядра. `pipe` создаёт два дескриптора файлов: конец чтения и конец записи. После `fork` родитель и потомок закрывают концы, которые им не нужны. Данные, которые писатель пишет, становятся данными, которые читатель читает.

Оператор оболочки `|` — канал. Левый процесс пишет stdout в канал. Правый процесс читает stdin из канала.

Правила канала:

1. Записи малых размеров (до `PIPE_BUF` байт) атомарны. Два писателя не перемежают эти записи.
2. Если все концы записи закрыты, читатель получает конец файла (`read` возвращает 0).
3. Если все концы чтения закрыты, `write` вызывает `SIGPIPE` и ошибку `EPIPE`.
4. У канала ограниченный буфер. Полный канал блокирует блокирующий `write`.

У FIFO (именованного канала) есть путь. `mkfifo` его создаёт. Несвязанные процессы открывают путь. Один процесс открывает на чтение. Другой открывает на запись. Ядро всё равно реализует буфер канала. Запись каталога — только точка встречи.

Открытие FIFO блокируется, пока не существуют и читатель, и писатель (обычная семантика). `O_NONBLOCK` меняет это правило. Читайте `man 7 fifo`.

Каналы не сохраняют границы сообщений. Два вызова `write` могут стать одним `read`. Если нужны сообщения, определите префикс длины или используйте другой тип IPC.

Не используйте FIFO как файл блокировки. Используйте `flock` или другую документированную блокировку.

## Сокеты Unix

Сокет домена Unix (локальный сокет) использует семейство адресов `AF_UNIX`. Оба конца живут на одной машине. Нет стека TCP и нет номера порта в смысле интернета.

Формы:

1. Сокет с путём: путь в файловой системе (`bind` на `/tmp/app.sock`). Другие процессы делают `connect` к этому пути.
2. Абстрактный сокет (Linux): имя, которое начинается с нулевого байта. Оно не использует запись каталога. Оно исчезает, когда ни один процесс его не держит.

Потоковые сокеты Unix (`SOCK_STREAM`) ведут себя как локальный канал TCP: `listen`, `accept`, двунаправленный поток байтов. Дейтаграммные сокеты Unix (`SOCK_DGRAM`) шлют сообщения. `SOCK_SEQPACKET` сохраняет границы сообщений на соединённом сокете.

Сокеты Unix могут передавать дескрипторы файлов через `SCM_RIGHTS` и учётные данные через `SCM_CREDENTIALS` (Linux). Привилегированный помощник может открыть файл и передать FD непривилегированному процессу. Тема 11 использует эту идею в песочницах.

`connect` к сокету с путём нуждается в праве на путь. Удалите протухший файл сокета перед `bind`, если ваш сервер владеет этим путём. `unlink` путь при чистом выходе.

Сокеты Unix часто быстрее TCP localhost, потому что пропускают IP и маршрутизацию. Они не работают между машинами. Тема 12 покрывает интернет-сокеты.

Не смешивайте `AF_UNIX` с `AF_INET`. Поле `sun_path` — не IP-адрес.

## Сигналы

Сигнал — асинхронное уведомление. Его шлёт ядро или другой процесс. Примеры: `SIGINT` (Control-C), `SIGTERM` (вежливая остановка), `SIGKILL` (нельзя поймать), `SIGCHLD` (изменение состояния потомка), `SIGPIPE` (запись в закрытый канал), `SIGSEGV` (плохое обращение к памяти).

Процесс может:

- принять действие по умолчанию (выход, игнор, дамп ядра, остановка)
- игнорировать сигнал (не `SIGKILL` или `SIGSTOP`)
- поставить обработчик через `sigaction`

Обработчик работает в процессе (на потоке). Он должен вызывать только функции, безопасные для асинхронных сигналов. `printf` и `malloc` в обработчике небезопасны. Частый шаблон: обработчик ставит флаг `volatile sig_atomic_t`. Главный цикл читает флаг.

`kill` шлёт сигнал процессу. `kill -9` — это `SIGKILL`. Сначала предпочитайте `SIGTERM`. `raise` шлёт сигнал вызывающему.

Сигналы — не канал данных. Вы не шлёте файл через сигнал. Можно использовать `sigqueue` и `siginfo` для маленького целого. Для байтов используйте канал или сокет.

`fork` наследует обработчики. `exec` сбрасывает обработчики к умолчанию, кроме игнорируемых сигналов, которые остаются игнорируемыми (с правилами). Читайте `man 7 signal`.

Не используйте сигналы как единственный протокол между двумя занятыми серверами. Гонки и пределы обработчиков делают этот проект хрупким. Self-pipe или `signalfd` в Linux могут превратить сигнал в FD для `epoll` (тема 8).

## Общая память плюс синхронизация

Общая память — область, которую отображают два или больше процессов. Сохранение в одном процессе может быть загрузкой в другом. Нет копии ядра на каждое сохранение. Тема 5 назвала `MAP_SHARED`, `shm_open` и `shmget`. Этот раздел добавляет правило: общая память без синхронизации — гонка данных.

Вы должны спарить общую память с блокировкой или с атомиками, у которых определённый порядок памяти (тема 4). Варианты:

1. Мьютекс POSIX в общей области с `PTHREAD_PROCESS_SHARED`.
2. Семафор POSIX (`sem_open` или общий `sem_t`).
3. Фьютекс на общем слове (тема 14). Сложнее.
4. Канал или eventfd только как пробуждение, пока полезная нагрузка сидит в отображении.

Протокол должен определить, кто пишет какое поле и когда данные действительны. Номер последовательности плюс мьютекс — простой шаблон. Кольцевому буферу нужны индексы головы и хвоста и видимость памяти.

Общая память быстра для больших полезных нагрузок (кадр, очередь записей). Настройка сложнее канала. Время жизни и уборка важны: `shm_unlink` удаляет имя. Отображение может жить, пока последний процесс не снимет отображение.

Не кладите указатель, действительный только в одном адресном пространстве, в общую область, если оба процесса не отображают по одной базе (редко и хрупко). Используйте смещения от начала отображения.

Безопасность: любой процесс, который может отобразить объект, может его читать. Используйте строгий режим на `shm_open` и частный каталог. Тема 11 покрывает учётные данные.

## Когда что использовать

Выбирайте самый маленький инструмент, который подходит задаче.

Используйте канал или FIFO, когда:

- у вас поток байтов
- процессы — родитель и потомок или они могут встретиться на пути
- вам не нужен произвольный доступ или второй читатель тех же байтов
- подходит модель оболочки `|`

Используйте сокет Unix, когда:

- нужен сервер, который принимает много клиентов на одной машине
- нужны дейтаграммы или сообщения `SOCK_SEQPACKET`
- нужно передавать дескрипторы файлов или учётные данные
- нужен путь в `/run` как у многих системных служб

Используйте сигнал, когда:

- нужно маленькое событие: стоп, перезагрузка, потомок умер
- не нужна полезная нагрузка (или нужна только `siginfo`)
- вы принимаете правила обработчика

Используйте общую память плюс синхронизацию, когда:

- полезная нагрузка большая или очень частая
- вы можете написать правильный протокол
- вы принимаете работу уборки и прав

Используйте интернет-сокеты (тема 12), когда другой конец может быть другой машиной. Используйте файл плюс `flock`, когда задача — блокировка ресурса, не поток.

Можно сочетать инструменты. Частый шаблон: общая память для данных, eventfd или сокет для пробуждения. Другой шаблон: канал для байтов, `SIGCHLD` для смерти.

Не начинайте с общей памяти для первой лаборатории. Начните с канала. Не шлите большие данные через сигналы.

Очереди сообщений (`mq_open`, очереди System V) существуют. Этот путь их не требует. Если нужны сообщения, дейтаграммный сокет Unix или канал с префиксом длины достаточно для лабораторий.

#### Простые практические задания

1. Напишите шпаргалку: `pipe`, `PIPE_BUF`, FIFO, `AF_UNIX`, `SCM_RIGHTS`, `sigaction`, `SIGKILL`, `shm_open`, мьютекс, общий для процессов.
2. Выполните `echo a | wc -c` и `ss -x | head`. Запишите по одному факту с каждой команды.
3. Нарисуйте четыре прямоугольника: канал, сокет Unix, сигнал, общая память. Добавьте одну стрелку данных или события.
4. Добавьте в закладки `man 7 pipe`, `man 7 unix` и `man 7 signal`.

#### Средние практические задания

1. Соберите конвейер двух потомков от одного родителя (стиль `ls`, затем `wc`) с двумя `pipe` или одним каналом. Напишите отчёт из шести строк.
2. Используйте `strace -f -e pipe,socket,connect,kill` на `sh -c 'echo hi | cat'`. Запишите IPC, который видите.
3. Документируйте чеклист отладки IPC: неиспользуемые концы канала, протухший `.sock`, `EPIPE`, отсутствующий `shm_unlink`, безопасность обработчика.

#### Сложные практические задания

1. Объедините сокет Unix для управления и область общей памяти для нагрузки. Напишите протокол на одной странице. Реализуйте крошечное демо, если есть время.
2. Прочитайте главы OSTEP об IPC или параллелизме, которые соответствуют каналам и общей памяти. Напишите карту на одну страницу к именам POSIX.

# 11. Кластеризация

## Описание

Redis Cluster делит ключи на многие экземпляры primary. Каждый primary владеет подмножеством хеш-слотов. Эта тема покрывает 16384 слота, хеш-теги, пределы команд с несколькими ключами, перешардирование на высоком уровне и что клиент должен делать в режиме кластера.

Сначала завершите более ранние темы. Cluster — не Sentinel. Cluster шардирует данные. Sentinel переключает один primary при отказе.

Используйте один термин для каждого понятия. Слот — целое от `0` до `16383`. Шард — primary (и его реплики), который владеет некоторыми слотами. Хеш-тег — часть `{...}` ключа, которую Redis использует для расчёта слота. Перенаправление — ответ `MOVED` или `ASK`, который говорит клиенту другой узел.

## Хеш-слоты Redis Cluster (16384)

Redis Cluster делит пространство ключей на 16384 слота. Каждый ключ отображается на один слот. Redis считает `CRC16(key) mod 16384` (с правилами хеш-тегов). Результат — слот.

Каждый primary владеет непрерывным или не непрерывным набором слотов. Вместе primary владеют всеми 16384 слотами. Если у слота нет владельца, кластер нездоров для этого слота.

Запись ключа идёт на primary, который владеет слотом ключа. Другие primary не хранят этот ключ. Это шардирование. Память и CPU масштабируются наружу. Один ключ всё ещё живёт на одном primary. Огромный ключ не делится.

```text
CLUSTER KEYSLOT user:42
CLUSTER SLOTS
CLUSTER NODES
```

`CLUSTER KEYSLOT` работает на узле кластера и показывает слот ключа. Используйте в лаборатории, чтобы доказать, что два ключа делят слот или нет.

Шина кластера (второй порт, часто `16379`, когда клиентский порт `6379`) несёт gossip и сообщения переключения между узлами. Клиенты используют клиентский порт. Не отправляйте `GET` на порт шины.

Логических БД в Cluster нет. `SELECT` недоступен. Используйте префиксы ключей.

Кластеру нужно несколько primary (три — частый минимум для промышленной среды). У каждого primary могут быть реплики для переключения внутри кластера. Это переключение — не Sentinel. Узлы кластера голосуют.

Не запускайте режим Cluster для крошечного кэша, который помещается на одном экземпляре, если не нужна эксплуатационная практика. Cluster добавляет перенаправления, пределы слотов и больше узлов.

`INFO cluster` и `CLUSTER INFO` показывают `cluster_state`. `ok` значит слоты покрыты. `fail` значит кластер не готов.

## Хеш-теги ключей `{user:42}`

Если ключ содержит подстроку `{...}`, Redis использует только символы между первой `{` и соответствующей `}` для расчёта слота. Эта подстрока — хеш-тег.

```text
{user:42}:profile
{user:42}:cart
{user:42}:orders
```

Эти три ключа отображаются на один слот. Они могут жить на одном primary. Команды с несколькими ключами, которые требуют один слот, могут на них выполняться.

Правила:

- Первая `{` начинает тег
- Первая `}` после этого заканчивает тег
- Если `{}` пуст, Redis игнорирует тег и хеширует полный ключ
- Если `{` нет, Redis хеширует полный ключ

```text
user:{42}:profile
```

Здесь тег — `42`. Все ключи с `{42}` делят слот. Это может положить ключи многих пользователей в один слот, если тегировать только id в стиле `{42}`, которые сталкиваются. Предпочитайте тег, который включает уникальный id пользователя: `{user:42}`.

Хеш-теги — намеренный инструмент горячей точки. Если все ключи используют `{global}`, один слот и один primary берут весь трафик. Это ломает шардирование.

Используйте хеш-теги, когда транзакция, скрипт Lua или `MGET` должны коснуться нескольких ключей. Не тегируйте всё.

`CLUSTER KEYSLOT` доказывает правило. Два имени с одним тегом должны показать один слот.

Lua, безопасный для Cluster, должен обращаться только к ключам в `KEYS[]`, и эти ключи должны делить слот (на практике один тег).

## Команды с несколькими ключами, которые падают через слоты

Многие команды принимают больше одного ключа: `MGET`, `MSET`, `DEL key1 key2`, `SUNION`, `SINTER`, `RENAME`, `ZUNIONSTORE`, `BITOP` и Lua с несколькими `KEYS`.

В Cluster все ключи в одной команде должны хешироваться в один слот. Если нет, Redis возвращает ошибку вроде `CROSSSLOT Keys in request don't hash to the same slot`.

```text
MGET {u:1}:name {u:1}:city
MGET u:1:name u:2:name
```

Первый `MGET` может работать (один тег). Второй падает, если слоты отличаются.

`RENAME` требует источник и назначение в одном слоте. Чтобы переименовать через слоты, приложение делает `GET`, `SET` нового ключа и `DEL` старого. Этот путь не атомарный.

Транзакции (`MULTI`/`EXEC`) и `WATCH` тоже требуют все ключи на одном узле и правила слотов. Нельзя охватить два primary в одной транзакции Redis.

Конвейеры могут включать команды для разных слотов только если клиент делит конвейер по узлу. Наивный конвейер на один узел падает или перенаправляет.

Команды одного ключа (`GET`, `HGET`, `INCR`) всегда целят один слот. Это лёгкий случай. Клиент следует `MOVED` на верный узел.

Когда проектируете схему, кладите ключи, которые нужно читать вместе, под один хеш-тег, либо избегайте команд с несколькими ключами и делайте несколько вызовов одного ключа.

`SCAN` на узел. Полное сканирование кластера должно запрашивать каждый primary.

## Перешардирование (на высоком уровне)

Перешардирование переносит слоты с одного primary на другой. Вы делаете это, чтобы добавить primary, убрать primary или сбалансировать память и CPU.

Оператор (или управляемый сервис) запускает перешардирование. `redis-cli --cluster reshard` — частый инструмент для самостоятельно управляемого кластера. Облачные консоли скрывают ту же идею.

На высоком уровне:

1. Выберите исходный primary, целевой primary и список слотов
2. Для каждого слота мигрируйте ключи пакетами (`MIGRATE` / состояния cluster setslot)
3. Обновите владение слотом, чтобы клиенты делали `MOVED` на новый primary
4. Повторяйте, пока план не закончен

Во время миграции слот может быть в переходном состоянии. Клиенты могут получать перенаправления `ASK`. `ASK` значит «попробуй тот узел один раз для этого ключа, не обновляй карту слотов навсегда». `MOVED` значит «обнови карту слотов; тот узел владеет слотом».

Перешардирование использует лишний CPU, сеть и память. Делайте это в окне. Смотрите задержку и `CLUSTER INFO`.

Перешардирование не делит один большой ключ. Если один ключ слишком большой, нужно сменить модель данных.

Добавление реплики — не перешардирование. Реплика копирует один primary. Она не берёт слоты, пока вы её не повысите или не перебалансируете.

Удаление primary требует сначала унести его слоты. Не убивайте primary, который всё ещё владеет слотами.

Управляемый Redis Cluster часто перешардирует за вас, когда меняете число шардов. Читайте runbook вендора.

## Поддержка клиента для режима кластера

Клиент, осведомлённый о кластере:

- Подключается хотя бы к одному узлу
- Загружает карту слотов (`CLUSTER SLOTS`)
- Отправляет каждую команду на узел, который владеет слотом
- Следует `MOVED` и обновляет карту
- Следует `ASK` с `ASKING`, когда слот мигрирует
- Делит конвейеры и команды с несколькими ключами по слоту, когда библиотека может

Клиент, не осведомлённый о кластере, говорит с одним узлом как с автономным Redis. Этот узел возвращает `MOVED` для ключей, которыми не владеет. Неосведомлённый клиент считает `MOVED` ошибкой. Не используйте клиент только для автономного режима против Cluster.

`redis-cli -c` включает режим кластера. CLI тогда следует перенаправлениям.

```text
redis-cli -c -h 127.0.0.1 -p 7000
```

Пулы соединений должны хранить карту слотов и соединение на узел (или подмножество). После переключения или перешардирования карта меняется. Хорошие клиенты обновляют по `MOVED`.

Таймауты и повторы требуют осторожности. Повтор записи после сетевой ошибки может дважды применить `INCR`. Используйте идемпотентные записи или примите риск.

Библиотеки: многие официальные и популярные клиенты имеют опцию кластера (кластерный клиент или флаг). Читайте ту страницу. Не задавайте только список хостов для Sentinel, когда сервер — Cluster. Sentinel и Cluster — разные топологии.

Вывод `CLUSTER SLOTS` включает адреса узлов и диапазоны слотов. Файрволы должны позволять клиенту достичь каждого primary (и реплик, если читаете с реплик). Один VIP, который скрывает все узлы, не работает, если это не умный прокси.

Проверяйте клиент в лаборатории с `MOVED` (перезапуск узла, перешардирование одного слота) до промышленной среды.

1. Соберите кластер из трёх primary в Docker (или Redis Stack / официальный create). Сделайте `SET` ключей, уроните одну реплику (не единственную копию слотов) и задокументируйте `CLUSTER INFO`.
2. Напишите руководство по дизайну ключей для Cluster на одну страницу для приложения магазина (пользователь, корзина, sku, таблица лидеров).
3. Задокументируйте настройки клиента: начальные узлы, таймауты, повторы и делит ли библиотека `MGET`.

#### Сложные практические задания

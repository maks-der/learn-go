# 4. Срок жизни и вытеснение

## Описание

Redis может удалить ключ через время. Redis также может удалять ключи, когда память заполнена. Эта тема покрывает команды срока, политики вытеснения и `maxmemory`. Вы узнаёте, что происходит, когда экземпляр не может сохранить новую запись.

Завершите эту тему до того, как опираться на Redis как кэш в более поздних дизайнах.

Используйте один термин для каждого понятия. Срок — таймер на ключе. TTL — оставшееся время. Вытеснение — удаление под давлением памяти. `maxmemory` — предел памяти. Политика — правило, которое выбирает ключи для вытеснения. Не смешивайте `expired_keys` и `evicted_keys`.

## `EXPIRE`, `PEXPIRE`, `TTL`, `PTTL`

`EXPIRE key seconds` задаёт время жизни в целых секундах. Redis удаляет ключ, когда время кончается. Ответ — `1`, если Redis задал срок, или `0`, если ключа нет.

`PEXPIRE key milliseconds` использует миллисекунды. Используйте `PEXPIRE`, когда шаги в одну секунду слишком грубые.

`TTL key` возвращает оставшиеся секунды. Ответ:

- неотрицательное целое — секунды осталось
- `-1` — ключ есть и срока нет
- `-2` — ключа нет (или уже истёк)

`PTTL key` возвращает оставшиеся миллисекунды или те же правила `-1` и `-2`.

```text
SET session:abc data
EXPIRE session:abc 300
TTL session:abc
```

`PERSIST key` снимает срок и оставляет значение. Тогда `TTL` возвращает `-1`.

`EXPIRE` на отсутствующем ключе ничего полезного не делает (`0`). Сначала задайте значение или используйте `SET key value EX seconds` одной командой.

Redis 7 добавляет опции `EXPIRE` вроде `NX`, `XX`, `GT` и `LT` в некоторых версиях. Эти опции задают срок только когда условие верно. Читайте страницу команды для вашей версии.

Срок использует время сервера. Большой скачок системных часов может изменить момент истечения ключей. Не полагайтесь на миллисекундную точность для критичных юридических сроков. Используйте срок для кэшей, сессий и временных удержаний.

Чтение истёкшего ключа выглядит как отсутствующий ключ. Приложение должно обрабатывать null.

## `EXPIREAT`

`EXPIREAT key unix-seconds` задаёт срок в абсолютном времени Unix в секундах. Redis удаляет ключ, когда часы сервера достигают этого времени.

`PEXPIREAT key unix-milliseconds` использует миллисекунды с эпохи Unix.

```text
EXPIREAT session:abc 1893456000
```

Используйте `EXPIREAT`, когда много ключей должны умереть в одно настенное время (конец дня, конец распродажи). Используйте `EXPIRE`, когда нужно «жить 15 минут от сейчас».

Аргумент — время Unix в UTC, не локальная строка даты. Считайте метку в приложении. Подтвердите часовой пояс этого расчёта.

Если метка в прошлом, Redis удаляет ключ (или команда ведёт себя как немедленное истечение). Проверьте точный ответ на вашей версии. Не храните прошлые времена по ошибке.

`SET key value EXAT timestamp` — форма одной команды в версиях, которые поддерживают `EXAT`. Предпочитайте одну команду, когда создаёте ключ и срок вместе.

`TTL` после `EXPIREAT` всё ещё показывает оставшиеся секунды. `TTL` относительный. `EXPIREAT` абсолютный.

Реплика использует время срока, которое сохранил primary. Рассинхрон часов между хостами всё ещё может удивить в эксплуатации. Держите NTP здоровым на хостах Redis.

## Политики вытеснения: `noeviction`, `allkeys-lru`, `volatile-lru`, LFU, random

Когда задан `maxmemory` и Redis нужна ещё ОЗУ для записи, Redis применяет политику вытеснения. Политика — значение `CONFIG`: `maxmemory-policy`.

Частые политики:

- `noeviction` — Redis не вытесняет. Записи, которым нужна память, возвращают ошибку. Чтения всё ещё работают.
- `allkeys-lru` — Redis вытесняет любой ключ, сначала давно не использованный (приблизительный LRU).
- `volatile-lru` — Redis вытесняет только ключи со сроком, LRU среди этих ключей.
- `allkeys-lfu` — Redis вытесняет любой ключ, сначала редко используемый (приблизительный LFU).
- `volatile-lfu` — LFU среди ключей со сроком.
- `allkeys-random` — Redis вытесняет случайный ключ.
- `volatile-random` — случайный среди ключей со сроком.
- `volatile-ttl` — среди ключей со сроком вытесняет ключ с самым коротким TTL сначала.

LRU значит «least recently used». Ключ, которого давно не касался клиент, лучший кандидат на вытеснение, чем горячий ключ. Redis использует приближение, а не идеальный список LRU для каждого ключа.

LFU значит «least frequently used». Ключ с малым числом чтений лучший кандидат, чем ключ с многими чтениями. Redis хранит счётчик с затуханием.

Политики `volatile-*` ничего полезного не делают, если ни у одного ключа нет срока и память заполнена. Записи тогда падают как при `noeviction`. Если выбираете `volatile-lru`, дайте ключам кэша TTL.

`allkeys-lru` — частая политика кэша. Redis может вытеснить ключи без TTL. Долговечные ключи без TTL могут исчезнуть. Не храните данные, которые должны остаться, на экземпляре с `allkeys-*`, если не принимаете потерю.

Читайте `CONFIG GET maxmemory-policy`. Меняйте лабораторный экземпляр через `CONFIG SET maxmemory-policy allkeys-lru`. Сохраните настройку в `redis.conf` для настоящего сервиса.

## `maxmemory`

`maxmemory` — верхняя граница памяти, которую Redis должен использовать. Значение в байтах. `CONFIG GET maxmemory` показывает его. `0` на 64-битной сборке значит без предела. Redis тогда растёт, пока ОС не откажет в ОЗУ.

Задайте `maxmemory` в промышленной среде. Выберите значение ниже ОЗУ хоста, чтобы ОС, перезапись AOF и copy-on-write `BGSAVE` имели место. Частый шаблон — 50–70 процентов ОЗУ для хоста, который также сохраняет. Тема 9 и темы эксплуатации покрывают fork.

```text
CONFIG SET maxmemory 64mb
```

`CONFIG SET` меняет работающий экземпляр. Запишите то же значение в `redis.conf` (`maxmemory 64mb`), чтобы перезапуск сохранил предел.

`INFO memory` показывает `used_memory`, `used_memory_rss` и `maxmemory`. `used_memory` — взгляд аллокатора на данные. `used_memory_rss` — размер процесса, который видит ОС. Они отличаются.

Реплики и клиенты тоже используют память. Буферы могут расти. `maxmemory` — не только «сумма размеров ключей».

У реплики может быть другой `maxmemory`, чем у primary. Если вытеснять на реплике, реплика может разойтись. Многие коллективы настраивают реплики так, чтобы они не вытесняли, или держат запас ОЗУ.

Не задавайте `maxmemory` ниже текущего `used_memory` без плана. Redis может сразу вытеснять или отклонять записи в зависимости от политики.

## Что происходит, когда Redis заполнен

«Заполнен» значит `used_memory` достиг `maxmemory` и команде нужна ещё память.

Если политика `noeviction`, Redis возвращает ошибку командам записи, которые увеличивают память. Типичный текст включает `OOM command not allowed when used memory > 'maxmemory'`. Команды чтения всё ещё работают. `DEL` может освободить память.

Если политика вытесняет ключи, Redis удаляет один или несколько ключей, затем повторяет запись. Вы теряете эти ключи. Запись может пройти. `INFO stats` увеличивает `evicted_keys`.

Если Redis не может вытеснить достаточно (например `volatile-lru` и нет volatile-ключей), запись падает с ошибкой OOM.

Приложение должно обрабатывать ошибки записи. Приложение cache-aside может пропустить кэш и использовать основную базу. Приложение, которое считает Redis единственным хранилищем, может провалить запрос пользователя. Спроектируйте этот путь намеренно.

Клиенты, которые конвейерят много записей, могут увидеть всплеск ошибок. Монитор должен оповещать о скорости `evicted_keys` и об ошибках OOM в журналах.

Redis не останавливается навсегда, чтобы уплотнить память. Фрагментация может держать RSS высоким после удалений. `MEMORY PURGE` или перезапуск могут помочь в некоторых схемах аллокатора. Не полагайтесь на это в приложении.

Не ждите OOM killer ОС. Задайте `maxmemory` и политику. Killer ОС труднее контролировать, чем ошибка Redis.

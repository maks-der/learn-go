# 12. Администрирование и безопасность

## Описание

Эта тема показывает, как запускать и защищать развёртывание MongoDB. Вы настраиваете `mongod`. Изучаете движок хранения WiredTiger. Делаете резервные копии, практикуете восстановление и планируете обновления. Аутентифицируете пользователей и назначаете роли. Ограничиваете сетевой доступ, включаете TLS и используете типизированные API драйверов. Изучаете шифрование на уровне поля на высоком уровне.

Сначала завершите драйверы и идеи replica set. Не запускайте команды администрирования на общем кластере без роли и окна изменений.

Используйте один термин для каждого понятия. **`mongod`** — процесс базы. **WiredTiger** — движок хранения по умолчанию. **Аутентификация** доказывает, кто клиент. **Авторизация** (RBAC) решает, что этот пользователь может делать. **TLS** шифрует сеть.

Учебной базе на localhost всё равно нужен пароль, прежде чем открывать порт. Atlas нужны пользователь базы и список IP-доступа (или частная сеть), прежде чем открывать кластер приложению.

## `mongod` и WiredTiger

`mongod` читает файл конфигурации YAML. Путь по умолчанию зависит от операционной системы. Можно также передавать флаги. Предпочитайте файл для всего, что должно пережить перезапуск.

Частые настройки (имена — примеры; читайте свою версию):

- `storage.dbPath` — файлы данных
- `systemLog.path` — файл лога
- `net.port` — порт прослушивания (`27017` по умолчанию)
- `net.bindIp` — интерфейсы
- `replication.replSetName` — имя replica set
- `security.authorization` — доступ пользователей вкл или выкл

Форма примера:

```yaml
storage:
  dbPath: /var/lib/mongo
systemLog:
  destination: file
  path: /var/log/mongodb/mongod.log
net:
  port: 27017
  bindIp: 127.0.0.1
```

Запуск:

```text
mongod --config /etc/mongod.conf
```

`mongosh` — клиент. `mongod` — сервер. Не путайте два процесса.

На Windows MongoDB часто работает как служба. В Docker те же идеи задают флаги или файл env. Atlas скрывает `mongod.conf`. Эквивалентные идеи задаёте в интерфейсе Atlas (уровень кластера, список IP, резервная копия).

Проверяйте изменение на тестовом хосте. Неверный `dbPath` или `bindIp` может запустить пустой экземпляр или открыть порт.

Не включайте публичный `bindIp` без аутентификации и TLS.

**WiredTiger** — движок хранения по умолчанию. Он хранит документы и индексы на диске. Использует кэш в ОЗУ. Поддерживает конкурентность на уровне документа. Два обновления двух документов могут идти одновременно.

WiredTiger сжимает данные. Сжатие уменьшает диск. Сжатие использует CPU. Значение по умолчанию подходит большинству учебных систем.

WiredTiger — не MMAPv1. MMAPv1 ушёл из текущей MongoDB. Старые посты блогов про выравнивание записей и блокировки на уровне коллекции к WiredTiger не относятся.

Контрольные точки пишут согласованный снимок в файлы данных. Между контрольными точками **журнал** держит недавние записи. Журналирование включено по умолчанию. После сбоя WiredTiger воспроизводит журнал и возвращается к согласованному состоянию. Не выключайте журнал на системе, которая вам важна.

Write concern `j: true` ждёт, пока запись не окажется в журнале. Журнал — не пользовательская резервная копия.

Не удаляйте файлы под `dbPath`, чтобы «освободить место», пока работает `mongod`.

`db.serverStatus().wiredTiger` показывает кэш и другие счётчики. Atlas показывает графики хранения.

## Резервная копия, восстановление и обновления

**Резервная копия** — копия, которую можно восстановить. Secondary — не резервная копия. Отложенный член — не полная резервная копия.

Частые методы:

**`mongodump` / `mongorestore`.** Логический экспорт BSON. Хорош для малых данных и выбранных коллекций. Медленный и тяжёлый на больших кластерах. Можно дампить со скрытого secondary.

**Снимки файловой системы или тома.** Снимите диск (или облачный том) согласованным методом. Для самостоятельно управляемых replica set руководство описывает снимок плюс журнал или снимок на secondary с процедурами сброса.

**Резервная копия Atlas.** Atlas предлагает облачные снимки и на некоторых уровнях более частые копии и восстановление на момент времени. Используйте резервную копию Atlas для кластеров Atlas, если нет письменного исключения.

Выберите метод, который соответствует размеру и RPO (сколько данных можно потерять). Ночной `mongodump` 2 ТБ часто неверный инструмент.

Шифруйте резервные копии. Контролируйте, кто может их скачать. В копии все данные.

Не запускайте `mongodump` против primary на пике без плана. Предпочитайте скрытый secondary.

Не копируйте `dbPath` через `cp` или zip, пока `mongod` пишет, если официальная процедура не разрешает именно этот метод.

**Учение восстановления** — практика восстановления. Восстанавливаете на безопасную цель. Измеряете время. Проверяете данные. Записываете, что не вышло.

Учение отвечает:

- Сколько восстанавливать (RTO)
- У кого пароли и роли
- Полная ли копия
- Могут ли приложения указать на восстановленные данные

Шаги по духу:

1. Выбрать копию (дамп, снимок или снимок Atlas).
2. Восстановить на новый кластер или новое имя базы. Не перезаписывайте промышленность на первом учении.
3. Запустить проверки: счёт документов, пример find, дымовой тест приложения.
4. Записать часы и проблемы.
5. Повторять по расписанию (например каждые 90 дней).

`mongorestore` может удалить коллекции, если передать флаги drop. Читайте флаги. Неверное восстановление может удалить данные.

WiredTiger может оставлять свободное место внутри файлов после удалений. Файл на диске не всегда сжимается. **Compact** переписывает данные, чтобы освободить место (поведение зависит от версии). Compact может занять долго. Не запускайте compact на primary на пике. Compact не чинит плохую модель.

**Основная версия** — первое число (например 7 к 8). MongoDB поддерживает путь обновления. Не перепрыгивайте неподдерживаемые разрывы. Читайте **Upgrade** для вашей from-версии и to-версии.

Типичные идеи:

- Сначала обновить двоичные файлы на secondary, затем primary (катящееся)
- Задавать **feature compatibility version** (`setFeatureCompatibilityVersion`) только когда документы говорят так
- Читать совместимость драйверов и Atlas
- Тестировать на копии данных
- Читать устаревшие команды и удалённые опции

Atlas: версию выбираете в интерфейсе. Atlas всё равно нуждается в окне изменений и тесте приложения.

Откат может быть трудным или невозможным после включения новых возможностей FCV. Не задавайте FCV в промышленности в тот же день, что обновление двоичных файлов, если процедура не говорит, что должны.

Не обновляйте промышленность в пятницу без команды и плана отката, который руководство ещё разрешает.

## Аутентификация и доступ на основе ролей

**Аутентификация** проверяет учётные данные. MongoDB поддерживает несколько механизмов. Частые для приложений — **SCRAM** и **x.509**.

**SCRAM** (Salted Challenge Response Authentication Mechanism) использует имя пользователя и пароль. Текущие серверы предпочитают **SCRAM-SHA-256**. Клиент и сервер доказывают пароль, не отправляя пароль открытым текстом (TLS в сети всё равно нужен).

Создайте пользователя на самостоятельно управляемом сервере после включения авторизации:

```javascript
use admin
db.createUser({
  user: "app",
  pwd: "use-a-secret-store",
  roles: [ { role: "readWrite", db: "shop" } ]
})
```

Кладите пользователя и пароль в URI или пусть драйвер спросит. Не коммитьте пароль.

**x.509** использует сертификаты. Приложение предъявляет сертификат. Сервер сопоставляет субъект сертификата пользователю. Члены replica set также могут использовать x.509, чтобы аутентифицироваться друг другу.

Atlas: пользователя базы создаёте в интерфейсе. Atlas по умолчанию использует SCRAM для этих пользователей. Можно добавить другие методы, которые документирует Atlas.

Включите авторизацию на Community Server (`security.authorization: enabled`). Без неё клиент, который достигает порта, может делать всё.

`localhost exception` позволяет создать первого пользователя на свежем самостоятельно управляемом сервере. Прочитайте эту страницу, прежде чем запереть себя снаружи.

Не создавайте пользователя с ролью `root` для приложения.

**Контроль доступа на основе ролей (RBAC)** даёт привилегии через **роли**. Привилегия — действие над ресурсом (база, коллекция или кластер).

Встроенные роли (примеры):

- `read` — find на базе
- `readWrite` — find и запись
- `dbAdmin` — индексы и часть администрирования базы
- `userAdmin` / `userAdminAnyDatabase` — управлять пользователями
- `clusterMonitor` — много статистики кластера только на чтение
- `backup` / `restore` — действия, связанные с дампом и восстановлением
- `root` — все действия (только операторы и только когда нужно)

Назначайте наименьшую роль, которая работает. Приложению нужен `readWrite` на своей базе, не `root`.

Можно создать пользовательскую роль, когда встроенные роли слишком широки:

```javascript
db.createRole({
  role: "orderWriter",
  privileges: [
    { resource: { db: "shop", collection: "orders" }, actions: [ "find", "insert", "update" ] }
  ],
  roles: []
})
```

У Atlas есть встроенные роли в интерфейсе. Пользовательские роли есть и на Atlas. Используйте их.

Не делите одного пользователя между многими приложениями. Утечка тогда имеет большой радиус поражения.

Не давайте `dropCollection` веб-приложению, если приложение никогда не удаляет коллекции.

## Bind IP, TLS и типизированные API (без запросов из строк)

Порт MongoDB в публичном интернете без контроля — частый инцидент. Ограничьте, кто может открыть TCP-соединение.

**Самостоятельно управляемый `bindIp`.** Привяжите к `127.0.0.1` для только локальной лаборатории. Привяжите к частному интерфейсу для VPC. Не привязывайте к `0.0.0.0` без аутентификации, TLS и межсетевого экрана.

**Межсетевой экран.** Разрешите порт `27017` (или свой порт) только из подсетей приложения. Остальное запретите.

**Список IP Atlas.** Atlas отказывает клиентам, которых нет в списке (если не используете частную конечную точку и соответствующий режим). Добавьте исходящие IP приложения. Не добавляйте `0.0.0.0/0`, кроме короткоживущего учебного кластера без настоящих данных, и уберите после.

**VPC и частная сеть.** Кладите `mongod` в частную подсеть. На Atlas используйте VPC peering или частную конечную точку, чтобы трафик не шёл через публичный интернет.

Сетевой контроль — не аутентификация. Нужны оба. Украденный пароль с ноутбука в списке всё равно работает. Публичный порт с сильным паролем всё равно цель сканирования.

Не держите личный домашний IP в списке Atlas после ухода из проекта.

**TLS** (Transport Layer Security) шифрует байты в сети. Клиенты и серверы аутентифицируют сертификат. Без TLS наблюдатель сети может читать запросы и документы.

Atlas требует TLS для клиентских соединений. Официальный URI включает `tls=true` (или старый `ssl=true`). Драйвер проверяет сертификат Atlas.

Самостоятельно управляемый:

- Задайте `net.tls.mode` (например `requireTLS`)
- Укажите сертификат PEM и ключ
- Раздайте файл CA клиентам
- Используйте TLS и для трафика членов replica set

Не используйте самоподписанный сертификат в промышленности без настоящего плана CA. Не отключайте проверку сертификата (`tlsInsecure`, `sslAllowInvalidCertificates`) кроме короткой лаборатории и никогда с настоящими данными.

Сертификаты истекают. Поставьте обновление в календарь. Истёкший сертификат останавливает приложение.

`mongodb+srv` на Atlas уже подразумевает TLS. URI `mongodb://` к самостоятельно управляемому хосту может не подразумевать. Будьте явны.

TLS — не шифрование на уровне поля. Сервер всё равно видит открытые документы после окончания TLS.

Инъекция запросов MongoDB случается, когда собираете запрос из **строк** или сырого JSON пользователя и передаёте его драйверу без контроля.

Классическая ошибка — взять HTTP JSON и передать его как фильтр:

```javascript
// unsafe if body is the whole filter
collection.find(req.body)
```

Клиент может послать `{ "role": "admin" }` или операторы вроде `$gt` и `$ne`. Фильтр тогда — фильтр атакующего.

Другая ошибка — склеивать строки в `$where` или во фрагмент JavaScript. Не используйте `$where` для фильтров приложения.

Безопасные привычки:

- Собирайте объект фильтра в коде. Задавайте каждое поле из **типизированного** значения (строка, число, ObjectId).
- Разрешайте только поля, по которым клиент может фильтровать.
- Преобразуйте id типом драйвера `ObjectId`. Не принимайте объект оператора там, где ждёте id.
- Используйте официальный API драйвера, не строку JavaScript, которую `eval`.

Это тот же класс бага, что SQL-инъекция. Язык — BSON, не SQL. Правило то же: ввод пользователя — данные, не структура запроса.

Не логируйте полные запросы, которые содержат пароли или токены.

## Шифрование на уровне поля (обзор)

**Шифрование полей на стороне клиента (CSFLE)** шифрует выбранные поля в драйвере, прежде чем документ достигнет сервера. Сервер хранит шифротекст. Операторы, которые читают коллекцию без ключей, не видят открытый текст.

**Queryable Encryption** — более поздний продукт, который позволяет шифровать поля и всё равно выполнять некоторые запросы равенства (и в текущих версиях больше) по этим полям. Сервер использует зашифрованные индексы. Читайте текущее руководство. Точные типы запросов растут с версиями.

Части высокого уровня:

- Сервис **управления ключами** (KMIP, облачный KMS или локальный ключ только для лабораторий)
- **Ключ шифрования данных** на поле или хранилище, обёрнутый мастер-ключом
- Достаточно новый драйвер
- Схема или карта автоматического шифрования, которая именует поля

Используйте эти инструменты для полей высокой чувствительности (национальный id, некоторые медицинские данные, некоторые платёжные токены), когда политика требует, чтобы администратор базы не видел открытый текст.

Лимиты:

- Не каждый оператор работает на шифротексте
- Случайное шифрование (CSFLE) блокирует запросы равенства, если не используете queryable-продукт правильно
- Потеря ключа значит потерю данных
- Растут CPU и размер

Эта тема остаётся обзорной. Не изобретайте самодельное XOR-«шифрование» в приложении.

TLS плюс RBAC плюс CSFLE решают разные задачи. Могут понадобиться все три.

У Atlas есть страницы продукта и помощники. Возможности Enterprise и лицензирование применяются в некоторых схемах. Читайте, что включает ваша редакция.

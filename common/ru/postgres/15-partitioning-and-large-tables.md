# 15. Секционирование и большие таблицы

## Описание

Эта тема показывает декларативное секционирование в PostgreSQL 16 и PostgreSQL 17. Вы узнаёте секции range, list и hash, отсечение секций, индексы на секционированных таблицах, почему наследование — старый путь, и как архивировать старые секции.

Сначала завершите тему 14. Вы умеете моделировать широкие строки. Завершите эту тему до изучения резервных копий и реплик.

Используйте один термин для каждого понятия. Секционированная таблица — родитель. Секция — дочерняя таблица, которая держит срез строк. Ключ секции — список столбцов, который выбирает срез. Отсечение секций пропускает секции, которые не могут совпасть с запросом. Декларативное секционирование — `PARTITION BY` на `CREATE TABLE`. Наследование — другая, более старая возможность. Этот справочник рассчитан на PostgreSQL 16 и PostgreSQL 17.

## Декларативное секционирование (range, list, hash)

Декларативное секционирование разбивает одну таблицу на секции. `INSERT` идёт в родителя. Сервер направляет строку в одну секцию. `SELECT` на родителе может читать много секций.

Три метода:

- **RANGE** — непрерывные границы (`FOR VALUES FROM ... TO ...`). Обычно для `date` и `timestamptz`.
- **LIST** — дискретные значения (`FOR VALUES IN (...)`). Обычно для id тенанта или статуса, который намеренно разбиваете.
- **HASH** — корзины по модулю (`FOR VALUES WITH (MODULUS n, REMAINDER r)`). Обычно когда нужен ровный размер и всегда фильтруете по ключу хеша.

```sql
CREATE TABLE shop.orders (
    id bigint GENERATED ALWAYS AS IDENTITY,
    created_on date NOT NULL,
    tenant_id bigint NOT NULL,
    total numeric(12, 2) NOT NULL,
    PRIMARY KEY (id, created_on)
) PARTITION BY RANGE (created_on);

CREATE TABLE shop.orders_2026_01
    PARTITION OF shop.orders
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');

CREATE TABLE shop.orders_2026_02
    PARTITION OF shop.orders
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
```

Верхняя граница исключительная. Строка с `created_on = '2026-02-01'` идёт в `orders_2026_02`.

Секция по умолчанию ловит значения, которые никакая другая секция не претендует:

```sql
CREATE TABLE shop.orders_default
    PARTITION OF shop.orders DEFAULT;
```

Секцию по умолчанию используйте осторожно. Она может расти без предела, если забудете новые месяцы.

Пример hash:

```sql
CREATE TABLE shop.sessions (
    sid uuid NOT NULL,
    user_id bigint NOT NULL,
    PRIMARY KEY (sid)
) PARTITION BY HASH (sid);

CREATE TABLE shop.sessions_p0 PARTITION OF shop.sessions
    FOR VALUES WITH (MODULUS 4, REMAINDER 0);
-- p1, p2, p3 in the same way
```

Уникальные ключи и первичные ключи на секционированной таблице должны включать ключ секции. Поэтому выше появляется `PRIMARY KEY (id, created_on)`. Один глобальный уникальный `id` на родителе в PostgreSQL 16 и 17 невалиден.

Не секционируйте маленькую таблицу. Секционирование добавляет стоимость планирования. Не смешивайте месяцы range с несвязанными ключами list на одном родителе без задокументированного дизайна. Не вставляйте строку, которая не совпадает ни с одной секцией и без умолчания; оператор падает.

Официальная глава: [https://www.postgresql.org/docs/17/ddl-partitioning.html](https://www.postgresql.org/docs/17/ddl-partitioning.html).

## Отсечение секций

Отсечение секций пропускает секции, которые не могут содержать совпадающие строки. Планировщику нужно ограничение на ключ секции (или значение, которое он может доказать).

```sql
EXPLAIN (ANALYZE, COSTS OFF)
SELECT id, total
FROM shop.orders
WHERE created_on >= DATE '2026-02-01'
  AND created_on <  DATE '2026-03-01';
```

План должен перечислить `orders_2026_02` и не должен сканировать `orders_2026_01`, когда границы — константы.

Отсечение может быть в момент плана или в момент выполнения. Отсечение во время выполнения применяется, когда значение — параметр, который исполнитель узнаёт позже (`PREPARE` / bind или соединение). `EXPLAIN (ANALYZE)` яснее показывает удалённые секции, чем `EXPLAIN` без analyze.

Фильтр по столбцу, который не ключ секции, не отсекает. `WHERE total > 100` всё равно может сканировать каждый месяц.

`SET enable_partition_pruning = off` — отладочный переключатель. В продакшене оставьте включённым.

Функции на ключе секции могут блокировать отсечение. Предпочитайте `created_on >= $1` вместо `date_trunc('month', created_on) = $1`, когда ключ — `created_on`.

Не прячьте ключ секции внутри выражения, которое планировщик не может доказать. Не ждите отсечения от поля `jsonb`, если это поле не ключ секции.

## Индексы на секционированных таблицах

Индекс на родителе — секционированный индекс. PostgreSQL создаёт совпадающий индекс на каждой секции. Новые секции получают индекс при присоединении, если создали индекс на родителе.

```sql
CREATE INDEX orders_tenant_idx ON shop.orders (tenant_id);
```

У каждой секции свой B-tree. Одного кластерного B-tree на все месяцы нет. Уникальный индекс на родителе должен включать ключ секции — то же правило, что у первичного ключа.

Можно создать индекс только на одной секции:

```sql
CREATE INDEX orders_2026_01_total_idx ON shop.orders_2026_01 (total);
```

Используйте локальный индекс, когда одному срезу нужна другая форма. Предпочитайте родительские индексы, чтобы не забыть новые месяцы.

У `CREATE INDEX CONCURRENTLY` на секционированном родителе в PostgreSQL 16 и 17 есть дополнительные правила. Часто создаёте индекс на родителе без `CONCURRENTLY` или строите на секцию конкурентно и присоединяете. Читайте текущую страницу `CREATE INDEX` до запуска в продакшене.

`REINDEX` может целиться в родителя или одну секцию. Тема 8 разбирала `REINDEX` и `CONCURRENTLY`.

У первичных ключей, ограничений уникальности и внешних ключей есть пределы между секциями. Внешний ключ из обычной таблицы на секционированную поддерживается, когда существует ссылаемый уникальный ключ. Внешний ключ из секционированной таблицы на другую таблицу тоже обычен. Кросс-секционных уникальных ключей, которые опускают ключ секции, нет.

Не ждите одного уникального `email` по всем list-секциям, если `email` не в ключе секции. Не создавайте пятьдесят разных определений индекса вручную без родительского индекса.

## Наследование против декларативного секционирования

Наследование таблиц позволяет дочерней таблице получить столбцы от родителя. Тема 5 сказала предпочитать композицию. Наследование также служило старым ручным методом секций: дети с ограничениями `CHECK`, триггеры `INSERT` и `constraint_exclusion`.

Декларативное секционирование — поддерживаемый метод для новых больших таблиц в PostgreSQL 16 и 17.

| Задача | Наследование | Декларативное |
| --- | --- | --- |
| Направить `INSERT` на родителя | триггер или приложение | встроено |
| Отсечь неиспользуемых детей | `constraint_exclusion` | отсечение секций |
| Уникальный ключ по срезам | легко ошибиться | ключ должен включать ключ секции |
| Присоединить / отсоединить | `INHERIT` / `NO INHERIT` | `ATTACH` / `DETACH` |
| Новая работа | не использовать для шардов | использовать это |

```sql
-- old pattern (do not use for new shards)
CREATE TABLE logs_all (t timestamptz, msg text);
CREATE TABLE logs_2026 () INHERITS (logs_all);
```

`SELECT` из родителя может включать детей. `SELECT ... ONLY` пропускает детей. Это поведение наследования, не декларативного секционирования.

Декларативный родитель — не обычная куча ваших строк. Строки живут в секциях. Родители наследования могут держать строки, и дети могут держать строки. Эта смесь удивляет новичков.

Знайте наследование, чтобы читать старые схемы. Мигрируйте старые шарды inherit-и-триггер на `PARTITION BY`, когда можете спланировать перенос.

Не создавайте новое дерево наследования, чтобы разбить таблицу фактов. Не смешивайте `INHERITS` и `PARTITION BY` на одной таблице.

## Архивирование старых секций

Секция — таблица. Её можно отсоединить, снять дамп, переместить или удалить. Это главный операционный выигрыш секционирования range.

Отсоединить без долгого ожидания в PostgreSQL 14 и новее (16 и 17 включены):

```sql
ALTER TABLE shop.orders DETACH PARTITION shop.orders_2025_01 CONCURRENTLY;
```

`CONCURRENTLY` нельзя запускать в блоке транзакции. После успешного отсоединения таблица обычная. Можно сделать `pg_dump`, переместить в архивную схему или `DROP TABLE`, когда резервная копия безопасна.

Присоединить старую таблицу, у которой уже есть нужные строки и границы:

```sql
ALTER TABLE shop.orders ATTACH PARTITION shop.orders_2025_01
    FOR VALUES FROM ('2025-01-01') TO ('2025-02-01');
```

Attach проверяет границы. Проверка может взять блокировку и сканировать. Подготовьте таблицу совпадающим ограничением `CHECK`, чтобы ускорить attach, когда документация говорит, что это помогает.

Поток архива, который используют многие команды:

1. Создайте секции следующего месяца до начала месяца.
2. Отсоедините месяцы, которые приложение не должно запрашивать онлайн.
3. Снимите дамп или скопируйте отсоединённую таблицу в холодное хранилище.
4. Удалите отсоединённую таблицу после проверки дампа.

Секцию по умолчанию, которая собрала «забытые» месяцы, труднее разбить. Держите календарное задание, которое создаёт секции.

Не `DELETE` миллионы старых строк из несекционированной таблицы, если можно секционировать по дате и удалить срез. Не удаляйте секцию до проверенной резервной копии. Тема 16 разбирает `pg_dump` одной таблицы.

1. Соберите двухмесячного родителя `orders`. Вставьте строки. `EXPLAIN` запрос одного месяца. Отсоедините более старый месяц.
2. Напишите шпаргалку: RANGE, LIST, HASH, отсечение, родительский индекс, наследование, detach.
3. Запросите `pg_partition_tree('shop.orders');`, если функция есть в вашей версии. Сохраните результат.
4. Вставьте одну строку и выберите её из родителя и по имени таблицы секции.

#### Средние практические задания

1. Добавьте родительский индекс на `tenant_id`. Добавьте третий месяц. Докажите, что индекс есть на новой секции. Выполните отсечённый запрос.
2. Сравните `pg_relation_size` каждой секции после неровной нагрузки.
3. Задокументируйте календарь: когда создаёте следующие секции и когда отсоединяете.

#### Сложные практические задания

1. Загрузите 100000 строк по четырём месяцам. Сравните `EXPLAIN ANALYZE` для фильтра месяца против фильтра, который не может отсечь. Запишите числа буферов, если используете `BUFFERS`.
2. Сопоставьте эту тему с официальной главой секционирования. Добавьте один предел (внешние ключи, identity или уникальность), который эта тема не детализировала.

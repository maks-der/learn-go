# 11. Память, безопасность и эксплуатация

## Описание

Redis быстр, когда данные помещаются в ОЗУ и команды остаются маленькими. Redis не стартует как публичный интернет-сервис. Эксплуатация держит Redis верным после того, как приложение работает. Эта тема показывает, как читать память, как находить большие ключи, как работает медленный журнал, как ужесточать доступ и как обрабатывать `BGSAVE`, заполнение диска и обновления.

Сначала завершите тему 2 (`maxmemory`), тему 7 (персистентность) и тему 8 (репликация). Используйте лабораторный экземпляр для каждого практического задания, которое меняет аутентификацию или имена команд. Не практикуйте на общем промышленном экземпляре.

Используйте один термин для каждого понятия. Используемая память — байты, которые Redis сообщает для данных и накладных расходов. RSS — размер процесса, который видит операционная система. Большой ключ — одно значение, большое в байтах или в числе элементов. Медленный журнал — список команд, которые превысили порог времени. Пользователь ACL — именованная учётная запись со списком команд и шаблоном ключей. TLS шифрует соединение. Copy-on-write (COW) — дополнительная ОЗУ во время fork.

Эта тема — ужесточение и эксплуатация. Она не описывает атаки.

## `INFO memory`, `MEMORY USAGE`, большие ключи

`INFO memory` печатает поля памяти как строки `key:value`. Полезные поля (имена могут чуть отличаться по версии):

- `used_memory` / `used_memory_human` — взгляд аллокатора на данные Redis
- `used_memory_rss` / `used_memory_rss_human` — резидентный размер операционной системы
- `used_memory_peak_human` — пик с старта
- `maxmemory` — настроенный лимит (`0` часто значит без лимита на 64-бит)
- `mem_fragmentation_ratio` — RSS, делённый на используемую память (приблизительно)

```text
INFO memory
```

`used_memory` и RSS — не одно и то же. Фрагментация, отображения файлов и copy-on-write во время `BGSAVE` поднимают RSS.

Отношение сильно выше `1` может значить фрагментацию или недавний fork. Отношение ниже `1` может появиться с общими страницами или странностями аллокатора. Не считайте одно число приговором. Используйте `MEMORY DOCTOR` и документацию для вашей версии.

`INFO stats` добавляет `expired_keys`, `evicted_keys`, `keyspace_hits` и `keyspace_misses`. Смотрите `used_memory` против `maxmemory`. Когда они встречаются, начинаются вытеснение или ошибки `OOM` (тема 2).

`MEMORY USAGE key` оценивает байты одного ключа, включая накладные расходы. Это оценка. Её достаточно, чтобы найти выбросы.

```text
MEMORY USAGE lab:big
```

Ответ — целое (байты) или null, если ключа нет.

`MEMORY DOCTOR` возвращает текстовый совет об экземпляре. Считайте его подсказкой. `MEMORY STATS` возвращает карту чисел аллокатора и набора данных.

`MEMORY PURGE` просит аллокатор отдать свободные страницы операционной системе, когда аллокатор это поддерживает. Эффект разный. Сначала используйте в лаборатории.

Не запускайте `MEMORY USAGE` на каждом ключе в продакшене в тесном цикле без темпа `SCAN`. Каждый вызов — команда в основном потоке.

Большой ключ — ключ с большим размером в байтах или большим числом элементов. Примеры: строка 50 MB, список из 10 миллионов элементов, хеш с 1 миллионом полей.

Риски:

- `GET`, `HGETALL`, `LRANGE 0 -1`, `SMEMBERS` копируют или обходят всё значение в основном потоке
- Репликация и RDB растут
- Сетевые буферы растут
- Cluster не может делить один ключ по слотам (тема 8)

Найти большие ключи:

```text
redis-cli --bigkeys
redis-cli --memkeys
```

Эти инструменты используют `SCAN`. Они сэмплируют. Они могут пропустить ключ. Они всё равно добавляют нагрузку. Запускайте их на реплике, когда можете (тема 8). Примите устаревшие чтения.

Исправления:

- Разделите одну огромную коллекцию на много ключей (шарды, ведра времени)
- Храните блобы в объектном хранилище; держите указатель в Redis
- Используйте `HSCAN`, страницы `LRANGE`, `SSCAN` вместо полных дампов
- `UNLINK` вместо `DEL` для больших значений (ленивое освобождение)

Не игнорируйте большой ключ, потому что у `used_memory` ещё есть запас. Следующий `HGETALL` может застопорить экземпляр.

`--bigkeys` — инструмент лаборатории и реплики. Не планируйте его на основном каждую минуту.

`OBJECT ENCODING key` показывает текущую раскладку в памяти (`listpack`, `hashtable`, `int`, `embstr` и другие). Redis превращает маленькие коллекции в более крупные структуры, когда они растут. Бенчмарки на 10 полях не предсказывают 100 000 полей.

## Медленный журнал

Медленный журнал записывает команды, которые превысили порог. Он живёт в памяти на экземпляре.

```text
SLOWLOG GET 10
SLOWLOG LEN
SLOWLOG RESET
```

Конфигурация:

- `slowlog-log-slower-than` — микросекунды (1000 микросекунд = 1 миллисекунда). Отрицательное значение может отключить журнал (проверьте версию).
- `slowlog-max-len` — максимум записей

```text
CONFIG GET slowlog-log-slower-than
CONFIG GET slowlog-max-len
```

Каждая запись включает id, метку времени, время выполнения и аргументы команды (обрезаны). Используйте его, чтобы найти `KEYS`, большой `HGETALL`, тяжёлый `SORT` или медленный скрипт Lua.

Время — выполнение команды на сервере. Оно не включает RTT клиента.

`SLOWLOG RESET` очищает журнал. Используйте после копирования записей. Не сбрасывайте на общем промышленном экземпляре без причины.

Команда может быть медленной, потому что ключ большой, потому что скрипт крутится или потому что хост перегружен. Сочетайте медленный журнал с `MEMORY USAGE` и `INFO`.

Не задавайте порог `0` на занятом промышленном экземпляре надолго. Журнал заполнится обычными командами.

Монитор задержки (`LATENCY DOCTOR`, `LATENCY LATEST`) — связанный инструмент для скачков. Используйте, когда медленного журнала недостаточно.

## ACL, адрес bind, TLS

Старый Redis использовал один пароль на весь экземпляр:

```text
CONFIG SET requirepass labpass
AUTH labpass
```

`requirepass` — один общий секрет. Каждый клиент, который его знает, имеет полную власть. Redis 6 добавляет списки контроля доступа (ACL). Предпочитайте ACL на Redis 6 и новее.

Идеи ACL:

- Есть пользователь по умолчанию. Можно задать ему пароль или отключить его.
- `ACL SETUSER` создаёт или меняет пользователя.
- У пользователя есть правила: команды (`+GET`, `-FLUSHALL`), категории (`+@read`) и шаблоны ключей (`~cache:*`).
- `AUTH username password` выбирает пользователя.

```text
ACL LIST
ACL WHOAMI
ACL SETUSER app on >apppass ~cache:* +@read +SET +DEL -@dangerous
```

Детали синтаксиса на страницах команд `ACL`. Проверьте версию. Префикс `>` в `SETUSER` задаёт пароль. `on` включает пользователя.

Клиенты приложения используют пользователя с наименьшими привилегиями. Человек-оператор использует более сильного пользователя для работы `CONFIG` и `ACL`. Не давайте приложению `FLUSHALL`, `DEBUG` или `KEYS`.

Храните пароли вне репозитория. Используйте менеджер секретов или окружение. Не кладите промышленные пароли в историю оболочки, если можете использовать запрос или файл с жёсткими правами.

`ACL SAVE` пишет файл ACL, когда используете файл ACL. `CONFIG REWRITE` может сохранить изменения `redis.conf`. Пароль `CONFIG SET`, который не сохраните, может исчезнуть после перезапуска. Проверьте перезапуск.

`bind` задаёт адреса, на которых Redis слушает.

```text
CONFIG GET bind
```

`bind 127.0.0.1` (и `::1` для localhost IPv6) принимает только локальных клиентов. Это верный режим по умолчанию для лабораторного ноутбука.

`bind 0.0.0.0` слушает на всех адресах IPv4. Любой хост, который может достичь порта, может попытаться соединиться. Сочетайте это с отсутствием аутентификации — и у вас открытое хранилище данных в сети.

Защищённый режим: когда у Redis нет задуманной конфигурации bind и нет пароля, Redis может отказать удалённым командам. Защищённый режим — страховочная сеть. Он не заменяет межсетевой экран и ACL.

В Docker публикация `-p 6379:6379` может открыть Redis на хосте. Привяжите внутри контейнера и публикуйте только на `127.0.0.1:6379` на хосте, когда учитесь:

```text
docker run --name redis-learn -p 127.0.0.1:6379:6379 redis
```

Группа безопасности облака или межсетевой экран должны разрешать только подсети приложения. Не полагайтесь на «никто не знает IP».

TLS шифрует байты в сети. Без TLS захват пакетов на пути может показать команды и значения. Пароли аутентификации тоже идут открытым текстом без TLS (RESP `AUTH`).

Redis может слушать с TLS (`tls-port`, сертификаты и связанные настройки `tls-*`). Хостинговый Redis часто требует TLS. Используйте `redis-cli --tls` и опции TLS клиентской библиотеки.

TLS не заменяет ACL. TLS защищает путь. ACL решают, что клиент может делать после подключения.

Сертификаты истекают. Календарите истечение. Не отключайте проверку сертификатов в продакшене, чтобы «заработало». Исправьте ЦС и имя хоста.

Не открывайте Redis в публичный интернет. Боты сканируют порт `6379`. Привязывайте к частным адресам. Используйте межсетевой экран. Используйте пользователей ACL. Используйте TLS на любом пути, который покидает доверенный хост.

Если вы уже открыли лабораторию, считайте все ключи скомпрометированными. Смените пароли. Снимите экземпляр с публичного адреса.

## Опасные команды (`FLUSHALL`, `KEYS`, `DEBUG`)

Некоторые команды верны в лаборатории и вредны на общем экземпляре.

`FLUSHALL` удаляет все ключи на экземпляре (все логические БД). `FLUSHDB` удаляет текущую логическую БД. Отмены нет.

`KEYS` обходит пространство ключей в основном потоке. На большом экземпляре может застопорить Redis (тема 9).

`DEBUG` включает подкоманды, которые могут уронить процесс или заблокировать его (`DEBUG SEGFAULT`, `DEBUG SLEEP`). Это инструменты разработчика. Они не команды приложения.

`CONFIG GET` может раскрыть настройки. `CONFIG SET` может сменить bind, персистентность и каталоги. Клиент, который может `CONFIG SET`, может ослабить безопасность или сломать персистентность.

Другие команды того же класса: `SHUTDOWN`, `REPLICAOF` / `SLAVEOF`, `MODULE LOAD`, `SCRIPT DEBUG`. Категория ACL `@dangerous` группирует многие из них. Проверьте `ACL CAT dangerous` на вашей версии.

Пользователь приложения не должен иметь эти команды. Оператор использует их в контролируемом окне с заявкой на изменение.

Не запускайте `FLUSHALL` как шаг выката на долговечном Redis. Тема 9 и тема 12 объясняют прогрев кэша вместо этого.

Старые схемы переименовывали опасные команды в `redis.conf`:

```text
rename-command FLUSHALL ""
rename-command KEYS ""
```

Пустое новое имя отключает команду. Redis 7+ устаревает `rename-command` в пользу ACL. Предпочитайте ACL. Секретное переименование — слабый контроль. Имя может утечь.

Не переименовывайте `AUTH` или `ACL` так, чтобы запереть себя на удалённом экземпляре. Держите путь локальной консоли, который проверили.

Код приложения должен использовать `SCAN`, не `KEYS`. Если отключите `KEYS`, учебники, которые всё ещё показывают `KEYS *`, упадут. Это то, что нужно в продакшене.

## Fork/COW во время `BGSAVE`, заполнение диска, обновления

Тема 7 объяснила `BGSAVE`. Родитель делает fork потомка. Потомок пишет RDB. Операционная система делит страницы, пока родитель не пишет страницу. Затем COW копирует эту страницу. Много записей во время долгого сохранения могут поднять RSS почти до двух копий набора данных.

Эффекты:

- Хост может уйти в swap или убийца OOM Linux может остановить Redis
- Задержка может вырасти во время fork на некоторых ядрах
- Перезапись AOF (`BGREWRITEAOF`) тоже делает fork

Оставьте свободную ОЗУ для пика. Частое правило планирования — держать запас на полную дополнительную копию, если скорость записи высока. Мерите RSS во время сохранения. Не угадывайте только по `used_memory`.

Смотрите `used_memory_rss`, пока `rdb_bgsave_in_progress` равен `1`.

Заметки Linux `overcommit_memory` появляются в предупреждениях Redis. Ошибка `fork` в журнале значит, ядро отказало потомку. Исправьте ОЗУ, overcommit или размер набора.

`SAVE` не делает fork. `SAVE` блокирует основной поток. Не используйте `SAVE` в продакшене.

RDB и AOF пишут файлы под `dir`. Если том полон, `BGSAVE` падает, добавление AOF падает или перезапись падает. Redis может остановить записи (`stop-writes-on-bgsave-error`, поведение ошибки AOF).

Перезапись AOF и запись RDB нуждаются в дополнительном месте. Перезапись может нуждаться в комнате для нового файла рядом со старым. Том на 95 процентах может упасть, даже если финальный файл поместился бы.

Поля `INFO persistence` вроде `rdb_last_bgsave_status` и `aof_last_write_status` говорят последний результат.

Если диск полон:

- Освободите место (старые дампы, журналы) в лаборатории или с известной политикой резервного копирования
- Не удаляйте единственный живой AOF без плана
- Исправьте размер тома до повышения трафика

Репликация не заменяет полный диск на основном. Не кладите `dir` на крошечный overlay-диск контейнера без монтирования.

Обновление меняет двоичный файл или образ Redis. Планируйте его.

Типичный путь «сначала реплика» для основного плюс реплики:

1. Обновите реплику. Проверьте репликацию и `INFO`.
2. Обновите остальные реплики.
3. Переключите (Sentinel или Cluster), чтобы обновлённая реплика стала основным.
4. Обновите старый основной (теперь реплика).
5. Проверьте приложение против нового поведения команд.

Читайте заметки о выпуске. Некоторые версии меняют значения по умолчанию (ACL, AOF, имена реплик). Модули: обновляйте Redis Stack как пакет.

Откат: держите предыдущий образ и резервную копию до обновления. Смена формата данных может усложнить откат.

Не обновляйте единственный основной на месте во время пика без реплики и резервной копии.

`CONFIG GET` / `CONFIG SET` меняют живые настройки. `CONFIG REWRITE` пишет их в `redis.conf`. Без перезаписи перезапуск может восстановить старые значения. Ограничьте `CONFIG SET` через ACL. Не экспериментируйте на долговечном промышленном основном.

Реплика — не резервная копия. Резервная копия — копия файла, которую можно восстановить после плохого `FLUSHALL` или потерянного хоста. Запустите `BGSAVE`, дождитесь завершения, скопируйте RDB с хоста, проверьте контрольную сумму копии и проверьте восстановление на лабораторном экземпляре.

Смотрите `INFO` на долю попаданий, `evicted_keys`, `connected_clients`, `blocked_clients`, `instantaneous_ops_per_sec` и статус последнего сохранения. Тревожьте по вытеснению на долговечном экземпляре, упавшим сохранениям, `rejected_connections` и памяти около `maxmemory`.

### Вопросы

#### Теоретические вопросы

1. Почему RSS растёт во время `BGSAVE`, если родитель пишет много ключей?
2. Почему том на 95 процентах всё ещё может провалить перезапись?
3. Почему обновлять реплику до основного?
4. Почему реплика не резервная копия?
5. Что часто значит ошибка `fork` в журнале?

#### Простые практические задания

1. Выполните `BGSAVE`. Смотрите `rdb_bgsave_in_progress`. Запишите `LASTSAVE` после.
2. Выполните `CONFIG GET dir`. Сохраните путь.
3. Запишите `redis_version` из `INFO server`.
4. Напишите четыре предложения: fork против `SAVE` в основном потоке.

#### Средние практические задания

1. Во время `BGSAVE` перепишите большой набор ключей в лаборатории. Запишите пик RSS против простоя.
2. На одноразовом томе заполните диск, пока `BGSAVE` не упадёт (или задайте крошечную квоту). Запишите ошибку и `rdb_last_bgsave_status`. Затем освободите место.
3. `BGSAVE`. Подождите. Скопируйте RDB в лабораторную папку. Восстановите на втором порту Docker. Подтвердите известный ключ.

#### Сложные практические задания

1. Размерьте хост для 8 GB `used_memory` и высокой скорости записи. Запишите числа ОЗУ и диска с оговоркой COW.
2. Составьте матрицу обновления: сервер, модули Stack, ваш клиент, ОС. Заполните текущее и целевое. Включите резервную копию и откат.

## Обзор темы

Эти вопросы не повторяют вопросы из разделов выше. Они охватывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Как `INFO memory`, `MEMORY USAGE` и `--bigkeys` отвечают на три разных вопроса?
2. Как bind, межсетевой экран, TLS и ACL каждый останавливают разный отказ (достичь, сниффить, действовать)?
3. Какие опасные команды бьют доступность (`KEYS`, `DEBUG SLEEP`) против долговечности (`FLUSHALL`)?
4. Как `CONFIG SET`, заполнение диска и COW взаимодействуют во время одного `BGSAVE` на маленьком хосте?
5. Почему порядок обновления и резервная копия существуют в одном окне изменения?

#### Простые практические задания

1. Напишите шпаргалку: `INFO memory`, `MEMORY USAGE`, `--bigkeys`, `SLOWLOG GET`, `ACL LIST`, `bind`, `--tls`, `FLUSHALL`, `BGSAVE`.
2. Экспортируйте `INFO memory` и выделите `used_memory_human`, `used_memory_rss_human`, `maxmemory`.
3. Нарисуйте ОЗУ (используемая + запас COW) и диск (RDB + место перезаписи).
4. Напишите пять лабораторных правил: локальный bind, нет `FLUSHALL` в продакшене, нет `KEYS`, нет `SAVE` в продакшене, копировать файлы до ремонта.

#### Средние практические задания

1. Создайте лабораторный набор с одним большим хешем и 1000 маленьких ключей. Найдите большой хеш через `--bigkeys` и через `SCAN`+`HLEN`. Запишите оба пути.
2. Ужесточите одноразовую лабораторию: пользователь ACL приложения, bind localhost, `FLUSHALL` запрещён. Подключитесь как app и как ops. Запишите обе сессии.
3. Запустите мини-учение: смените безвредную настройку, `BGSAVE`, скопируйте RDB, восстановите на другом порту, прочитайте ключ. Запишите времена.

#### Сложные практические задания

1. Напишите контур ежемесячного скрипта здоровья Redis: память, большие ключи на реплике, снимок медленного журнала, доля попаданий. Нет `KEYS` в продакшене.
2. Сделайте базовую линию безопасности и эксплуатации Redis на одну страницу для коллектива. Включите версии (ACL, TLS), сеть, команды, запас COW и восстановление резервной копии.

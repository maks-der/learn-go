# 9. Микросервисы и интеграция

## Описание

Микросервис — единица развёртывания, которая владеет своими данными и открывает контракт. Интеграция — способ, которым две системы обмениваются данными или начинают работу. Эта тема покрывает сервис как разворачиваемую единицу со своими данными, стоимость сети и эксплуатации, когда не делить, саги, хореографию, оркестрацию, шлюз API, передачу файлов, общую базу, RPC, обмен сообщениями и антикоррупционный слой.

Микросервисы — не значение по умолчанию. Модульный монолит — обычное начало (тема 3). Вы добавляете вторую единицу развёртывания только после настоящей боли. Завершите темы 1–8 до этой темы. Владение данными сочетайте с темой 6. Удалённый отказ сочетайте с темой 8. Сообщения сочетайте с темой 7.

Используйте один термин для каждого понятия. Сервис — единица развёртывания с контрактом и владельцем данных. Модуль — граница дизайна внутри одной единицы развёртывания. Размер в строках кода — не определение. Сага — не распределённая транзакция базы.

## Сервис как разворачиваемая единица со своими данными

Сервис в этом справочнике — единица, которую вы собираете, запускаете, останавливаете и поставляете по своим часам. У единицы есть процесс (или маленький набор процессов, которые вы всегда поставляете вместе). Единица владеет хранилищем данных. Другие сервисы не пишут таблицы этого хранилища.

Владение — правило. Владелец принимает записи, которые меняют источник истины. Другие сервисы читают через API или через события (темы 5, 6 и 7). Общая таблица между двумя единицами развёртывания — скрытый контракт. Тема 6 называет эту форму антипаттерном интеграционной базы.

Сервис также владеет своими отказами. Если процесс недоступен, владелец этого процесса — команда, которая его поставляет. Если смена схемы неверна, та же команда откатывает её. Сервис без владельца — не полный сервис.

Контракт — часть сервиса. HTTP JSON, gRPC или события — публичное лицо (тема 5). Можно менять внутренности. Нельзя менять контракт без окна совместимости.

Библиотека, которую импортируют многие процессы, — не сервис. Пакет в монолите — не сервис. Эти единицы не разворачиваются отдельно и не владеют хранилищем.

Слово «микро» намекает на маленький размер. Размер в строках кода — не правило дизайна. Правило дизайна — граница. Полезная граница совпадает с ограниченным контекстом или ясной линией владения (тема 4).

Плохое разделение следует техническим слоям: один «сервис API», один «сервис логики» и один «сервис базы». Эти единицы нельзя менять отдельно. Каждая функция пересекает сеть. Эта форма копирует слоистый монолит и добавляет задержку (тема 3).

Не делите хранилище в первый день «для микросервисов». Одна база с таблицами владельцев модулей — значение по умолчанию в модульном монолите (темы 3 и 6).

## Стоимость сети и эксплуатации; когда не делить

Каждая лишняя единица развёртывания добавляет сетевой прыжок и счёт эксплуатации. Сеть ненадёжна, задержка не ноль, путь не бесплатен (тема 8). Стоимость эксплуатации включает конвейеры, дежурство, панели, секреты и миграции схемы.

Когда не делить:

- Одна команда владеет всем продуктом и может поставлять по одним часам.
- Нельзя нарисовать стабильный ограниченный контекст (тема 4).
- Нужна одна транзакция для действия пользователя и нет истории саги.
- Нет меры, что модуль — узкое место (тема 1).
- Нельзя укомплектовать дежурство для другого процесса.
- Разделение следовало бы слоям (API / логика / база) вместо владения.

Когда разделение может быть допустимым:

- Две команды должны выпускать по независимым часам, и модульный монолит уже не выполняет эту нужду.
- Измеренная нагрузка нуждается в другом пути масштаба для одной части (тема 12).
- Закон или поставщик заставляет отдельную систему.
- Жёсткое правило изоляции (отказ в одной части не должен уронить другой процесс).

Пишите причину в ADR с мерой или ограничением. «Нам может понадобиться масштабировать» недостаточно.

Монолит всё ещё может запускать много экземпляров той же единицы. Это масштаб, не разделение сервиса (тема 12).

Если вы уже разделили слишком рано, слияние обратно в модульный монолит может быть правильной архитектурой. Запишите это в ADR. Мода — не атрибут качества.

## Сага, хореография, оркестрация, шлюз API

Сага — последовательность локальных транзакций, которые вместе реализуют бизнес-действие между больше чем одним владельцем. У каждого шага есть компенсирующее действие, если более поздний шаг падает. Сага — не распределённая транзакция ACID. Вы принимаете итоговую согласованность (тема 4).

Пример: зарезервировать запас, затем списать платёж, затем создать отгрузку. Если платёж падает, компенсация освобождает запас.

Хореография — стиль, где каждый сервис реагирует на события. Нет центрального директора. `OrderPlaced` ведёт к `PaymentCaptured` ведёт к `ShipmentCreated`. Поток живёт в подписчиках.

Оркестрация — стиль, где координатор отправляет команды и ждёт результатов. Поток живёт в оркестраторе.

Выбирайте хореографию, когда поток простой и владельцы должны оставаться развязанными. Выбирайте оркестрацию, когда поток длинный, когда компенсаций много или когда нужно одно место, чтобы видеть состояние действия.

Шлюз API — краевой процесс, который принимает вызовы клиентов и пересылает их сервисам. Он может применять общую политику: завершение TLS, проверка аутентификации, лимит частоты и маршрутизация. Он не должен стать домом доменных правил (тема 3). Цена и политика выдачи остаются у владельца.

Шлюз — домен отказа. Если шлюз недоступен, публичные клиенты падают, даже если сервисы доступны. Дайте ему избыточность (тема 11).

Не используйте шлюз как скрытую интеграционную базу. Не кладите все соединения в шлюз, если это делает его вторым монолитом. BFF — родственник шлюза для одного типа клиента (тема 13).

Пишите, кто владеет состоянием саги. Отсутствующий владелец порождает потерянные заказы и двойные списания.

## Файл, общая БД, RPC, обмен сообщениями

Хопе и Вульф описывают четыре классических стиля интеграции. Этот справочник использует те же четыре имени. См. [https://www.enterpriseintegrationpatterns.com/](https://www.enterpriseintegrationpatterns.com/).

Передача файлов — интеграция через файл, который одна система пишет, а другая читает. Файл может лежать на диске, в объектном хранилище или на хосте SFTP. Производителю и потребителю не нужно работать в одно время. Стиль подходит пакетной работе и обмену с партнёрами. Он плохо подходит щелчку пользователя, которому нужен ответ за 200 мс. Вы должны определить формат, версию, сигнал полноты, хранение и идемпотентную загрузку.

Общая база — хранилище, которое больше чем одна система использует как общую схему. Обе системы выполняют SQL против тех же таблиц. Этот справочник считает этот стиль высокой связанностью (тема 6). Используйте его только если унаследовали. Остановите новых писателей. Планируйте выход.

RPC — запрос и ответ (тема 5). Вызывающий ждёт. Используйте RPC, когда действию пользователя нужен ответ сейчас и обе стороны могут делить контракт. Применяйте тайм-ауты, повторы и выключатели (тема 8).

Обмен сообщениями — асинхронное сообщение (тема 7). Вызывающий не ждёт всех подписчиков. Используйте обмен сообщениями, когда нужен разрыв по времени, буфер или много независимых потребителей.

Выбирайте стиль из ограничения:

- Одно время, нужен ответ: RPC.
- Разное время, пакет, файл партнёра: передача файлов.
- Разное время, много подписчиков, задания: обмен сообщениями.
- Общие таблицы: отвергнуть для новой работы.

Можно смешивать стили. Публичный HTTP API может принять заказ. Событие может уведомить поиск. Ночной файл может кормить склад.

Безопасность — часть каждого стиля. Аутентифицируйте отправителя. Ограничивайте размер. Не кладите секреты в имена файлов или URL (тема 10).

## Антикоррупционный слой

Антикоррупционный слой (ACL) — граница перевода. Он защищает вашу модель от внешней модели. Входящие и исходящие данные проходят через типы, которыми вы владеете. Внешние имена, идентификаторы и правила не утекают в ваш домен (тема 4).

Используйте ACL, когда интегрируетесь с поставщиком, устаревшей системой или другим ограниченным контекстом, которым вы не управляете.

ACL может быть:

- Пакетом в модульном монолите
- Маленьким сервисом-адаптером
- Набором функций сопоставления на краю модуля

ACL не должен стать вторым домом ваших бизнес-правил. Он переводит. Домен всё равно решает, что выдача может делать.

Без ACL имя поля поставщика появляется в ваших таблицах, вашем API и вашем UI. Смена версии поставщика затем переписывает вашу систему. Это скрытая связанность (тема 2).

Переводите идентификаторы. Их `customerCode` — не ваш `PatronId`, пока вы не напишете карту. Храните внешний идентификатор как значение на вашей сущности, если нужен круговой путь. Не принимайте весь их тип.

ACL — не общее представление базы, которое обе стороны пишут. Это представление всё ещё общая модель.

Тестируйте ACL фикстурами, которые выглядят как внешняя полезная нагрузка. Не бейте поставщика из каждого модульного теста.

## Обзор темы

Эти вопросы не повторяют вопросы разделов выше. Они покрывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Как сервис, граница и владение данными образуют одно определение?
2. Почему стоимость сети и сложность саги аргументируют сначала модульный монолит?
3. Когда вы выбираете хореографию и когда оркестрацию для одного магазина?
4. Как четыре стиля интеграции связаны с темами 5, 6 и 7?
5. Как ACL защищает единый язык через границу поставщика?

#### Простые практические задания

1. Напишите шпаргалку на одну страницу: определение сервиса, когда не делить, пара саги, четыре стиля, ACL.
2. Для приложения задач напишите «один сервис», четыре модуля, только HTTP, нет саги, нет ACL.
3. Нарисуйте шлюз, два сервиса и два хранилища. Пометьте, кто может писать каждое хранилище.
4. Добавьте в закладки сайт EIP и `architecture.topics.md`. Напишите одно предложение, когда вы открываете каждый.

#### Средние практические задания

1. Напишите краткое описание интеграции кампусного магазина: публичный HTTP, один файл поставщика, одно событие и отвергнутая общая БД.
2. Возьмите дизайн коллеги, который делит API / логику / базу на три сервиса. Перепишите его как модульный монолит или как два сервиса владения.
3. Напишите план на двенадцать недель: недели в монолите и боль, которая снова откроет разделение.

#### Сложные практические задания

1. Напишите чек-лист извлечения сервиса: язык, свои таблицы, контракт, сага, ACL, дежурство. Заполните его для одного модуля.
2. Сравните слияние обратно в монолит с дальнейшим разделением. Напишите атрибуты качества, которые каждый ход улучшает или ослабляет.

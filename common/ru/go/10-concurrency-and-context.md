# 10. Параллельность и context

## Описание

Go запускает много функций одновременно. Горутина — функция, которую планирует среда выполнения Go. Канал перемещает значения между горутинами. Пакет `sync` защищает общие данные, когда канал — не простой выбор. `context.Context` несёт сигнал отмены, таймаут и дедлайн через границы API.

Завершите эту тему до того, как строить серверы, воркеры или другие параллельные программы. Используйте один термин для каждого понятия. Горутина — не поток операционной системы. Отправка в канал — не вызов функции. Гонка данных — не то же, что взаимная блокировка. Context — не мешок необязательных параметров.

## Горутины

Ключевое слово `go` запускает горутину. Новая горутина выполняет `f`, пока текущая горутина продолжает.

```go
go f()
go f(a, b)
go func() {
	doWork()
}()
```

Аргументы `f` вычисляются в текущей горутине. Вызов `f` выполняется в новой горутине.

Процесс стартует с одной горутины. Эта горутина выполняет `main`. Когда `main` возвращает управление, процесс завершается. Остальные горутины останавливаются в этот момент. Нужно ждать, если эти горутины должны закончиться. Используйте `sync.WaitGroup` или канал для этого ожидания.

У горутины в начале маленький стек. Стек растёт и сжимается, когда функции нужна память. Можно запустить много горутин. Всё равно нужно ограничивать число, когда каждая горутина держит ресурс (файл, соединение или большой буфер).

С Go 1.22 у каждой итерации цикла `for` свои переменные цикла. Этот код безопасен в Go 1.22 и новее:

```go
for _, item := range items {
	go func() {
		process(item)
	}()
}
```

До Go 1.22 каждая горутина могла прочитать последний `item`. Если поддерживаете старые компиляторы, копируйте переменную внутри цикла: `item := item`.

Планировщик Go запускает много горутин на меньшем числе потоков операционной системы. Эта модель — планировщик M:N. `GOMAXPROCS` — максимальное число логических процессоров, которые могут выполнять код Go одновременно. По умолчанию — число логических CPU.

Не запускайте горутину и не игнорируйте её ошибку. Верните ошибку по каналу или соберите её через `WaitGroup` и мьютекс.

## Каналы, close и `select`

Канал — типизированный канал передачи. Создаёте канал через `make`.

```go
ch := make(chan int)    // unbuffered
ch := make(chan int, 4) // buffered, capacity 4
```

Отправляйте значение через `ch <- v`. Принимайте значение через `v := <-ch`. Форма comma-ok сообщает, открыт ли канал:

```go
v, ok := <-ch
```

`ok` — `false`, когда `ch` закрыт и пуст. `v` в этом случае — нулевое значение типа элемента.

`close(ch)` помечает канал как закрытый. Приёмники опустошают оставшиеся буферизованные значения, затем видят закрытое состояние.

Правила каналов:

- Отправка в закрытый канал паникует.
- Закрытие закрытого канала паникует.
- Закрытие канала nil паникует.
- Отправка в канал nil блокируется навсегда.
- Приём из канала nil блокируется навсегда.

Отправитель закрывает канал. Приёмник не закрывает канал, когда отправителей больше одного.

Небуферизованный канал имеет ёмкость 0. Отправка ждёт, пока другая горутина примет. Буферизованный канал хранит значения, пока буфер не полон. Не используйте `len(ch)`, чтобы решить, что отправка безопасна.

Инструкция `select` ждёт набор операций канала. `select` выполняет одну готовую ветку. Если готовы несколько веток, `select` выбирает одну случайно.

```go
select {
case v := <-in:
	handle(v)
case out <- v:
	// sent
case <-time.After(2 * time.Second):
	return errTimeout
}
```

Ветка `default` выполняется, когда никакая другая ветка не готова. Используйте `default` для неблокирующей попытки.

`for v := range ch` принимает, пока канал не закрыт и буфер не пуст. Если никто не закрывает канал, цикл ждёт вечно.

## `sync.WaitGroup` и `sync.Mutex`

`sync.WaitGroup` ждёт набор горутин. Вызывайте `Add` до запуска каждой горутины. Вызывайте `Done`, когда горутина заканчивается. Вызывайте `Wait` в ожидающем коде.

```go
var wg sync.WaitGroup
for i := range 3 {
	wg.Add(1)
	go func(n int) {
		defer wg.Done()
		work(n)
	}(i)
}
wg.Wait()
```

`Add` не должен выполняться внутри новой горутины, когда `Wait` может выполниться первым. Этот порядок — гонка. Вызывайте `Add` в запускающем коде. Предпочитайте `defer wg.Done()`, чтобы `Done` выполнился на каждом пути.

Не копируйте `WaitGroup` после использования. Передавайте указатель.

`sync.Mutex` — блокировка взаимного исключения. Вызывайте `Lock` до касания общих данных. Вызывайте `Unlock` после. Предпочитайте `defer mu.Unlock()` после успешной блокировки.

```go
var mu sync.Mutex
var count int

func inc() {
	mu.Lock()
	defer mu.Unlock()
	count++
}
```

Мьютекс сам по себе не защищает данные. Нужно блокировать каждое чтение и каждую запись этих данных. Задокументируйте, какие поля защищает мьютекс.

`sync.RWMutex` разрешает многих читателей или одного писателя. Используйте его, когда чтения частые, а записи редкие. Не держите `RLock` и затем берите `Lock` в той же горутине. Этот порядок взаимно блокирует.

`sync.Once` выполняет функцию один раз. `sync.Pool` переиспользует временные объекты. Начинайте с `Mutex` и `WaitGroup`. Добавляйте остальные типы, когда измерите нужду.

Карты небезопасны для параллельной записи. Защищайте общую карту мьютексом. Параллельное чтение без записей безопасно.

## Детектор гонок и утечки горутин

Гонка данных возникает, когда две горутины обращаются к одной памяти и хотя бы одно обращение — запись, и обращения не синхронизированы.

Собирайте и тестируйте с детектором гонок:

```text
go test -race ./...
go run -race .
```

Детектор печатает отчёт, когда видит гонку. Отчёт показывает два стека. Исправьте гонку мьютексом, каналом или без общей записи. Не используйте `time.Sleep`, чтобы скрыть гонку.

Детектор гонок использует дополнительную память и CPU. Используйте его в тестах и на staging. Он ловит не каждую гонку. Успешный запуск `-race` — не доказательство безопасности.

Утечка горутины — горутина, которая никогда не возвращает управление. Частые причины:

- Приём из канала, который никто не закрывает и в который никто не отправляет
- Отправка в канал, из которого никто не принимает
- `Wait`, которому никто не делает `Done`
- `select`, который никогда не становится готовым
- Работа, которая игнорирует отмену context

Утёкшие горутины держат стеки и любые значения, которые захватывают. В сервере они растут, пока процесс не станет медленным или не умрёт.

Ищите утечки через `runtime.NumGoroutine` в тестах, через профили горутин `pprof` и через аккуратный `select` на `ctx.Done()`. Тема 11 покрывает `pprof`.

У каждой горутины, которую запускаете, должно быть правило остановки. Задокументируйте, кто закрывает канал. Задокументируйте, кто отменяет context.

## Отмена `context`, таймаут и дедлайн

`context.Context` несёт дедлайн, сигнал отмены и необязательные значения запроса. Вы передаёте context как первый параметр функции. Вызываемый код останавливает работу, когда context завершён.

```go
type Context interface {
	Deadline() (deadline time.Time, ok bool)
	Done() <-chan struct{}
	Err() error
	Value(key any) any
}
```

`Done` закрывается, когда работу нужно остановить. `Err` объясняет почему. `Deadline` сообщает время, если дедлайн есть.

`context.Background` возвращает пустой корневой context. Этот context никогда не отменяется. Используйте `Background` вверху `main` и в тестах, когда начинаете дерево. `context.TODO` тоже возвращает пустой context. Используйте `TODO` только как метку. Замените его, когда цепочка вызовов ясна.

Context образует дерево. Дочерние создают через `WithCancel`, `WithTimeout` или `WithDeadline`. Когда родитель завершён, дочерние завершены. Отмена дочернего не отменяет родителя.

```go
ctx, cancel := context.WithCancel(parent)
defer cancel()

ctx, cancel := context.WithTimeout(parent, 2*time.Second)
defer cancel()

ctx, cancel := context.WithDeadline(parent, time.Now().Add(2*time.Second))
defer cancel()
```

Нужно вызывать `cancel`, когда создаёте производный context. `cancel` освобождает ресурсы. `defer cancel()` — частая форма. После таймаута `ctx.Err()` — `context.DeadlineExceeded`. После отмены `ctx.Err()` — `context.Canceled`.

Проверяйте `ctx.Done()` в `select`. Возвращайте `ctx.Err()` вызывающему коду. Передавайте тот же context вниз в `http.NewRequestWithContext` и в вызовы базы данных.

Не храните context в долгоживущем поле структуры, если структура — не работа, которую контролирует context. Передавайте context вниз по цепочке вызовов.

## Почему избегать `WithValue` для необязательных параметров

`context.WithValue` сохраняет ключ и значение в производном context.

```go
type key struct{}

ctx := context.WithValue(parent, key{}, userID)
id, ok := ctx.Value(key{}).(string)
```

Используйте закрытый тип ключа, чтобы другие пакеты не сталкивались. API значений нетипизирован. Вызывающий код должен делать assertion.

`WithValue` — для данных области запроса, которые должны пересечь API, который вы не контролируете. Типичные случаи: id трассировки, id запроса и иногда принципал пользователя, который уже сохранил middleware.

Не используйте `WithValue` для необязательных параметров своих функций. Не скрывайте логгер, дескриптор базы данных или структуру конфигурации в context. Эти значения принадлежат структуре, которую передаёте как обычный параметр, или полю типа сервера.

Проблемы значений в context:

- Вызывающий код не видит обязательные входы в сигнатуре функции.
- Тестам нужно строить context вместо ясного списка аргументов.
- Отсутствующий ключ — тихое нулевое значение после неудачного assertion.
- Один context может нести скрытые зависимости, которые позже создают циклы импорта.

Передавайте context для отмены и дедлайна. Передавайте данные как параметры. Если сторонняя функция принимает только `context.Context`, храните наименьшее значение, которое документирует эта библиотека.

Не храните context внутри значения, которое затем кладёте обратно в то же дерево context. Этот цикл трудно отменить.

#### Простые практические задания

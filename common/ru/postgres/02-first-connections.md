# 2. Первые подключения

## Описание

Эта тема показывает, как клиент достигает сервера PostgreSQL 16 или 17. Вы узнаете два главных файла конфигурации, поля подключения и первые метакоманды `psql`. Также узнаете `search_path` и как читать настройки сессии.

Сначала завершите тему 1. Нужен работающий сервер и рабочий `psql`. Завершите эту тему до прикладного SQL.

Используйте один термин для каждого понятия. `postgresql.conf` задаёт параметры сервера. `pg_hba.conf` задаёт, кто может подключаться и как сервер аутентифицирует клиента. Сессия — одно подключение. `search_path` — список схем, которые используют неквалифицированные имена.

## `postgresql.conf` и `pg_hba.conf` (обзор)

`postgresql.conf` — главный файл конфигурации сервера. По умолчанию он лежит в каталоге данных. Он задаёт адрес прослушивания, порт, память, журналирование и многие другие параметры. Примеры строк:

```text
listen_addresses = 'localhost'
port = 5432
max_connections = 100
```

Переопределения можно класть в `postgresql.auto.conf`. `ALTER SYSTEM` пишет этот файл. Не редактируйте `postgresql.auto.conf` вручную.

`pg_hba.conf` — файл аутентификации по хосту. Каждая строка — правило. Сервер берёт первое подходящее правило. В правиле есть тип подключения, база, роль, адрес клиента и метод.

Примеры правил (не копируйте в продакшен без проверки):

```text
# TYPE  DATABASE  USER  ADDRESS      METHOD
local   all       all                scram-sha-256
host    all       all   127.0.0.1/32 scram-sha-256
host    all       all   ::1/128      scram-sha-256
```

Частые методы:

- `scram-sha-256` — пароль через SCRAM (метод пароля по умолчанию в текущих версиях)
- `md5` — старый метод пароля; не используйте для новой работы
- `trust` — без пароля; только для закрытого локального теста
- `peer` — локальный сокет; имя пользователя ОС должно совпадать с ролью
- `reject` — отклонить совпадение

`postgresql.conf` отвечает на вопрос «как сервер работает». `pg_hba.conf` отвечает на вопрос «кто может подключаться». Неверный адрес прослушивания блокирует сеть. Неверное правило `pg_hba.conf` отклоняет вход после TCP-подключения.

Многие настройки перезагружаются через `SELECT pg_reload_conf();` или `pg_ctl reload`. Некоторые параметры требуют перезапуска. Документация помечает каждый параметр как `SIGHUP` или postmaster.

Не ставьте вместе `listen_addresses = '*'` и `trust`. Тема 21 разбирает сетевые правила продакшена.

## Хост, порт `5432`, база, пользователь, пароль

Клиенту нужны эти поля:

- **host** — имя или IP сервера (`localhost`, `127.0.0.1` или имя контейнера)
- **port** — TCP-порт; по умолчанию `5432`
- **database** — имя базы; не имя кластера
- **user** — роль с `LOGIN`
- **password** — пароль роли, когда метод `pg_hba.conf` его требует

Флаги `psql`:

```text
psql -h localhost -p 5432 -U postgres -d postgres
```

Переменные окружения libpq:

- `PGHOST`
- `PGPORT`
- `PGUSER`
- `PGDATABASE`
- `PGPASSWORD` (избегайте в общих оболочках; предпочитайте `.pgpass`)

Unix-domain сокет — локальное подключение без TCP. В Linux `psql` без `-h` часто использует сокет. Применяется тип `pg_hba.conf` `local`. В Windows клиенты обычно используют TCP.

Хост должен совпадать с `listen_addresses`. Порт должен совпадать с `port`. База должна существовать. Роль должна существовать и иметь `CONNECT` на эту базу. Пароль должен удовлетворять методу `pg_hba.conf`.

Сообщения об ошибках:

- connection refused — на этом хосте и порте никто не слушает
- no `pg_hba.conf` entry — TCP сработал; правила аутентификации отклонили клиента
- password authentication failed — правило совпало; пароль неверный
- database does not exist — имя неверное или вы подключились к другому кластеру

Не путайте пользователя ОС с ролью PostgreSQL. Имена могут совпадать. Это разные учётные записи.

## Метакоманды `psql`: `\l`, `\c`, `\dt`, `\d`, `\dn`, `\du`

Метакоманды начинаются с обратной косой черты. Это команды `psql`. Сервер не получает строку с обратной косой как SQL. `psql` отправляет SQL за вас.

| Команда | Назначение |
| --- | --- |
| `\l` | список баз |
| `\c dbname` | подключиться к другой базе |
| `\dt` | список таблиц в текущем `search_path` |
| `\d name` | описать таблицу или другой объект |
| `\dn` | список схем |
| `\du` | список ролей |

Полезные варианты:

- `\l+` — базы с размером и комментарием
- `\dt *.*` — таблицы во всех схемах
- `\dt schema.*` — таблицы в одной схеме
- `\d+ name` — дополнительные детали (индексы, комментарии о размере)
- `\du+` — роли с описанием
- `\x` — переключить расширенный вывод
- `\q` — выход
- `\conninfo` — показать текущее подключение

Примеры:

```text
\l
\c learn
\dn
\dt
\d public.items
\du
```

`\c` меняет базу. Базу нельзя сменить SQL-командой `USE`. В PostgreSQL нет `USE`. Вы переподключаетесь.

`\dt` без шаблона скрывает таблицы, которых нет в `search_path`. Таблица в схеме `app` не появится, пока не зададите путь или не выполните `\dt app.*`.

`\d` без имени перечисляет больше типов объектов, чем `\dt`. Предпочитайте `\dt`, когда нужны только таблицы.

Эти команды помогают подтвердить, что вы в нужной базе и что роль видит объекты.

## `search_path` и схема `public`

`search_path` — список схем. PostgreSQL использует этот список, чтобы находить неквалифицированные имена. Неквалифицированное имя — `items`. Квалифицированное имя — `app.items`.

`search_path` по умолчанию — `"$user", public`. `"$user"` означает схему с тем же именем, что текущая роль. Если такой схемы нет, PostgreSQL её пропускает. Затем использует `public`.

Показать путь:

```sql
SHOW search_path;
SELECT current_schemas(true);
```

`current_schemas(true)` включает неявные схемы, например `pg_catalog`. Системные функции разрешаются, даже если вы не пишете `pg_catalog`.

Задать путь для сессии:

```sql
SET search_path TO app, public;
```

Задать значение по умолчанию для роли:

```sql
ALTER ROLE shop_app SET search_path TO app, public;
```

Новые объекты попадают в первую существующую схему в `search_path`. Если в `CREATE TABLE items` схему не указать, PostgreSQL создаст `public.items`, когда `public` — первая существующая схема.

Схема `public` есть в новых базах. В PostgreSQL 15 и новее роль `PUBLIC` по умолчанию не имеет `CREATE` на `public`. Обычной роли входа нужен `GRANT CREATE ON SCHEMA public` или своя схема. PostgreSQL 16 и 17 сохраняют это более безопасное значение по умолчанию.

Не кладите прикладные таблицы в `pg_catalog`. Не полагайтесь на `public` как на единственную границу безопасности. Тема 12 разбирает привилегии.

Две таблицы с одним именем могут жить в двух схемах. `search_path` выбирает первое совпадение. В скриптах квалифицируйте имена, если путь может меняться.

## `SHOW` и `current_database()`

`SHOW` читает параметр конфигурации текущей сессии:

```sql
SHOW port;
SHOW listen_addresses;
SHOW server_version;
SHOW search_path;
SHOW TimeZone;
SHOW work_mem;
```

`SHOW ALL` перечисляет каждый параметр. Список длинный. Фильтруйте в `psql` или запрашивайте `pg_settings`:

```sql
SELECT name, setting, unit, context
FROM pg_settings
WHERE name IN ('port', 'work_mem', 'search_path');
```

`context` говорит, можно ли менять значение в сессии, перезагрузкой или только при старте.

Функции сессии:

```sql
SELECT current_database();
SELECT current_user;
SELECT session_user;
SELECT current_schema();
SELECT inet_server_addr(), inet_server_port();
SELECT inet_client_addr(), inet_client_port();
```

`current_database()` — база этого подключения. `current_user` — роль для проверки привилегий. `session_user` — исходная роль входа. `SET ROLE` может сменить `current_user`.

`current_schema()` — первая записываемая схема в `search_path`. Это не то же самое, что `current_database()`.

Эти функции подтверждают, что вы подключились к нужному серверу. Выполняйте их до `DELETE`.

`SET` меняет параметр сессии, если параметр это позволяет:

```sql
SET TimeZone TO 'UTC';
SHOW TimeZone;
RESET TimeZone;
```

Не путайте `SHOW` с `SELECT` по таблице. `SHOW` — для параметров.

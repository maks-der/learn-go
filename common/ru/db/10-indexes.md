# 10. Индексы

## Описание

Эта тема показывает, как СУБД находит строки. Вы изучаете, почему полное сканирование медленное, как работает индекс B-tree на высоком уровне, уникальные индексы, составные индексы, покрывающие индексы, селективность, цену записи и как читать план запроса.

Используйте один термин для каждого понятия. Путь доступа — метод, который выбирает оптимизатор. Полное сканирование таблицы читает каждую строку. Поиск по индексу использует индекс, чтобы найти маленький набор строк. Завершите эту тему после того, как умеете писать соединения и `GROUP BY`. Индексы существуют для этих запросов.

Не добавляйте индексы, пока нет запроса. Измеряйте планом.

## Почему полное сканирование таблицы медленное

Полное сканирование таблицы читает каждую строку таблицы (точнее: каждую страницу, которая держит таблицу). Затем СУБД применяет `WHERE`. Если нужен один клиент по id из миллиона строк, сканирование всё равно читает миллион строк.

Цена растёт с размером таблицы. Вдвое больше строк значит примерно вдвое больше работы для сканирования. Пределом становятся пропускная способность диска и памяти.

Сканирование не всегда неверно. Если нужны большинство строк, сканирование может быть дешевле многих поисков по индексу. Пример: `SELECT * FROM products` без фильтра. Пример: фильтр, который совпадает с 80 процентами строк.

Сканирование неверно, когда нужны немногие строки и на столбце фильтра есть индекс. Пример: `WHERE customer_id = 42` на большой таблице `orders`.

```sql
SELECT *
FROM orders
WHERE customer_id = 42;
```

Без индекса на `customer_id` СУБД читает все заказы. С полезным индексом она прыгает к совпадающим записям.

`COUNT(*)` большой таблицы тоже может сканировать (или сканировать индекс). Не запускайте тяжёлые сканирования в продакшене как зонд. Используйте план. Используйте образец.

Не угадывайте. Таблица из 20 строк мала. Сканирование нормально. Таблица из 20 миллионов строк не мала. Тот же текст SQL имеет другую цену.

Соединения могут сканировать обе стороны, если ключи не проиндексированы. Вложенный цикл со сканированием внутренней стороны — частый медленный шаблон. Индексируйте ключ соединения (обычно внешний ключ).

## Идея B-tree

Индекс B-tree — сбалансированное дерево ключей. Листовые узлы держат ключи по порядку и указатели на строки (или включают строку в кластерном индексе). Верхние узлы направляют поиск.

Чтобы найти `customer_id = 42`, СУБД идёт от корня к листу. Число шагов растёт медленно с числом ключей (логарифмически). Затем она следует указателям к совпадающим строкам.

Поскольку листья упорядочены, B-tree также поддерживает диапазоны:

```sql
WHERE customer_id = 42
WHERE ordered_at >= DATE '2026-01-01' AND ordered_at < DATE '2026-02-01'
WHERE name >= 'A' AND name < 'B'
```

B-tree помогает не каждому выражению. `WHERE YEAR(ordered_at) = 2026` может спрятать столбец от простого индекса на `ordered_at`. Предпочитайте диапазон по столбцу.

```text
Root
  ├─ ... 40
  └─ 41 ...
Leaf: 41, 42, 42, 43  → row pointers
```

Большинство реляционных продуктов используют B-tree (или B+ tree) как индекс по умолчанию. Существуют другие виды (hash, bitmap, GIN). Сначала изучайте B-tree. Этот путь нейтрален к вендорам: думайте «упорядоченный поиск по ключу».

Индекс первичного ключа обычно B-tree. Вторичные индексы — дополнительные B-tree на других столбцах.

Не представляйте индекс как копию полной таблицы. Он хранит ключ и указатель (или подмножество столбцов). Оптимизатор выбирает, использовать ли B-tree. Вы создаёте индекс. Вы не выбираете путь в тексте `SELECT` в стандартном SQL.

## Уникальный индекс и первичный ключ

Первичный ключ — логическое правило: идентифицировать строку, не `NULL`, уникально. СУБД почти в каждом продукте реализует его уникальным индексом.

Уникальный индекс — физический объект, который запрещает дубликаты ключей. Можно создать уникальный индекс на столбце, который не первичный ключ. Этот индекс поддерживает ключ-кандидат (`email`, `isbn`).

```sql
CREATE TABLE customers (
    customer_id INTEGER PRIMARY KEY,
    email VARCHAR(255) NOT NULL UNIQUE
);
```

`PRIMARY KEY` создаёт уникальный индекс на `customer_id`. `UNIQUE` создаёт уникальный индекс на `email`.

Можно также написать:

```sql
CREATE UNIQUE INDEX idx_customers_email
    ON customers (email);
```

Не создавайте второй уникальный индекс на тех же столбцах, что первичный ключ. Вы тратите записи и место.

Отличия:

| Пункт | Первичный ключ | Уникальный индекс / уникальное ограничение |
| --- | --- | --- |
| `NULL` | Не допускается | Часто допускается (правила продукта отличаются) |
| Число на таблицу | Один | Много |
| Цель внешнего ключа | Обычная цель | Допускается, если уникален |
| Смысл | Идентификатор | Дополнительный ключ-кандидат |

Неуникальный индекс допускает дубликаты ключей. Используйте его для внешних ключей (`orders.customer_id`), где много заказов делят одного клиента.

Поиски по уникальному индексу возвращают не больше одной строки (кроме случая `NULL` в некоторых продуктах). Оптимизатор может использовать этот факт.

Не используйте уникальный индекс вместо отсутствующего первичного ключа. Дайте каждой таблице сущности первичный ключ. Добавляйте уникальные индексы для других ключей-кандидатов.

## Составные индексы и левый префикс

Составной индекс (многостолбцовый индекс) хранит больше одного столбца в ключе.

```sql
CREATE INDEX idx_orders_cust_date
    ON orders (customer_id, ordered_at);
```

B-tree упорядочивает строки сначала по `customer_id`, затем по `ordered_at`.

**Левый префикс.** Запрос может использовать индекс, когда ограничивает префикс списка столбцов слева.

Полезно:

```sql
WHERE customer_id = 42
WHERE customer_id = 42 AND ordered_at >= DATE '2026-01-01'
```

Не полезно как простой поиск (индекс всё ещё могут сканировать, но первый столбец не используется):

```sql
WHERE ordered_at >= DATE '2026-01-01'
```

Индекс на `(customer_id, ordered_at)` не заменяет индекс на `(ordered_at)`, если часто фильтруете только по дате.

Равенство по первому столбцу плюс диапазон по второму — классический хороший шаблон. Диапазон по первому столбцу может помешать плотному использованию второго столбца.

Порядок столбцов важен. Ставьте столбец равенства первым, когда один столбец — равенство, а другой — диапазон. Ставьте самый селективный столбец равенства первым, когда оба равенства, если другое правило (соединение, покрытие) не побеждает.

Не создавайте и `(a, b)`, и `(a)` без причины. `(a, b)` уже поддерживает поиски по `a`. Лишний индекс на `a` дублирует работу. Индекс на `(b, a)` другой: он поддерживает `b` как левый префикс.

Составной уникальный индекс обеспечивает уникальность пары, не каждого столбца.

```sql
CREATE UNIQUE INDEX idx_enroll_pair
    ON enrollments (student_id, course_id);
```

Один студент может появиться много раз. Одна пара не может.

## Селективность и покрывающие индексы

Селективность — доля строк, которые оставляет предикат. Высокоселективный предикат оставляет мало строк. Низкоселективный оставляет много строк.

```text
WHERE customer_id = 42          -- often highly selective
WHERE country = 'US'            -- can be low selectivity
WHERE active = TRUE             -- often low selectivity
WHERE 1 = 1                     -- no selectivity
```

Оптимизатор использует статистику, чтобы оценить селективность. Высокая селективность благоприятствует поиску по индексу. Низкая селективность благоприятствует сканированию.

Индекс на булевом столбце часто трата, если половина строк истинна. Индекс на уникальном id высокоселективен.

Селективность зависит от значения. `country = 'VA'` (Ватикан) может быть селективным. `country = 'US'` может не быть. У одного столбца разная селективность для разных литералов.

Составные индексы могут быть селективнее одного столбца. `status = 'open' AND warehouse_id = 7` может быть селективным, даже если каждый столбец нет.

Не индексируйте столбец только потому, что он появляется в `WHERE`. Проверьте, сколько строк обычно совпадает. Используйте план и числа строк.

Покрывающий индекс содержит каждый столбец, который нужен запросу. СУБД может ответить на запрос из одного индекса. Она не посещает кучу таблицы (или базовую строку).

```sql
CREATE INDEX idx_orders_cust_date
    ON orders (customer_id, ordered_at);

SELECT customer_id, ordered_at
FROM orders
WHERE customer_id = 42;
```

Если индекс — `(customer_id, ordered_at)`, этот запрос может быть покрывающим. Если запрос также выбирает `status_code`, индекс не покрывает, пока этот столбец не в индексе или в списке include.

Некоторые продукты допускают включённые (неключевые) столбцы:

```sql
-- product-specific idea
CREATE INDEX idx_orders_cust
    ON orders (customer_id) INCLUDE (ordered_at, status_code);
```

`INCLUDE` не стандартный SQL. Идея переносима: дополнительные столбцы в листе индекса, чтобы избежать поисков таблицы.

Покрывающий индекс помогает частым узким запросам. Он стоит больше места и больше работы записи. Не покрывайте `SELECT *`.

Читайте план. План, который говорит «index only» или «covering» (слова отличаются), значит, строка таблицы не требовалась.

Не добавляйте десять включённых столбцов. Вы перестраиваете широкий индекс на каждой записи. Покрывайте столбцы одного-двух горячих запросов.

`DISTINCT` и `GROUP BY` также заботятся о числе различных значений (кардинальность). Запомните: мало совпадений → индекс; большинство строк совпадает → сканирование.

## Когда индекс вредит записям

Каждый индекс — лишняя работа на `INSERT`, `UPDATE` проиндексированных столбцов и `DELETE`. СУБД должна поддерживать каждое B-tree.

Цены:

- больше места на диске
- больше трафика журнала
- больше CPU, чтобы найти позицию вставки и разделить страницы
- более длинные транзакции и более длинные блокировки страниц индекса

Таблица с двенадцатью индексами пишет как двенадцать дополнительных структур. Массовая загрузка гораздо медленнее.

Обновления, которые не меняют проиндексированные столбцы, дешевле обновлений, которые меняют ключ. Смена проиндексированного ключа — удаление плюс вставка в индексе.

Индексы также замедляют `COPY` / массовую вставку. Некоторые команды удаляют неуникальные индексы, загружают и создают заново. Эта тактика — операционный выбор. Пересоздавайте уникальные индексы только когда всё ещё можете обеспечить уникальность.

Не добавляйте индекс для запроса, который запускаете раз в месяц на таблице, в которую пишете тысячу раз в секунду. Налог записи постоянен. Экономия запроса редка.

Не держите неиспользуемые индексы. Неиспользуемые индексы всё ещё стоят записи. Перечислите индексы и сравните их с реальными запросами.

Проверки внешних ключей используют индексы на ссылочном ключе и, для удалений родителя, на столбце внешнего ключа ребёнка. У этого индекса есть цена записи и польза корректности. Держите его.

```text
Writes per insert ≈ 1 table + N indexes
```

Измерьте время записи с кандидатным индексом и без на черновой таблице. Затем решите.

## Чтение плана запроса

План запроса — путь доступа, который выбрал оптимизатор. `EXPLAIN` (слово отличается: `EXPLAIN`, `EXPLAIN ANALYZE`, `SHOW PLAN`) печатает этот путь. Вы читаете его. Вы не угадываете.

Типичные вещи для чтения:

- сканирование против поиска по индексу (или сканирования индекса)
- тип соединения (вложенный цикл, hash, merge)
- оценённые строки против фактических (когда продукт показывает оба)
- шаги сортировки и агрегации
- был ли индекс покрывающим

```sql
EXPLAIN
SELECT o.order_id, c.name
FROM orders AS o
INNER JOIN customers AS c
    ON c.customer_id = o.customer_id
WHERE o.customer_id = 42;
```

Вывод — текст или JSON, специфичный для продукта. Изучите токены своей СУБД. Ищите имя таблицы, имя индекса и фильтр.

`EXPLAIN` без выполнения показывает оценки. `EXPLAIN ANALYZE` (если есть) выполняет запрос и показывает фактические времена. Не запускайте `ANALYZE` на тяжёлом операторе записи в продакшене без осторожности. На некоторых продуктах он выполняет оператор. Читайте руководство.

Навык чтения:

1. Найдите лист, который читает `orders`.
2. Посмотрите, использует ли он `idx_orders_customer_id` или seq scan.
3. Найдите соединение с `customers`.
4. Посмотрите, является ли `customers` поиском по первичному ключу.
5. Сравните оценённые строки с тем, что ожидаете.

Плохой план — подсказка. Причины: нет индекса, спрятанное выражение, устаревшая статистика, неверная селективность, слишком широкий `SELECT`.

Не форсируйте подсказку индекса как первую привычку. Подсказки специфичны для вендора и могут устареть. Исправьте SQL и индексы. Обновите статистику, если продукт требует.

Сохраняйте планы в заметках для запросов, которые настраиваете. План — доказательство.

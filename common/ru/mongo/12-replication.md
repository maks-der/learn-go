# 12. Репликация

## Описание

Эта тема показывает, как MongoDB копирует данные между членами. **Replica set** — группа процессов `mongod`, которые держат один набор данных. Один член — **primary**. Остальные члены с данными — **secondary**. Сначала завершите CRUD, драйверы и транзакции.

Используйте один термин для каждого понятия. **Primary** принимает записи клиента. **Secondary** применяет те же записи из **oplog**. **Выборы** выбирают новый primary, когда текущий primary недоступен. **Устаревшее чтение** — чтение, которое ещё не включает недавнюю запись.

Репликация даёт высокую доступность. Репликация сама по себе — не резервная копия. Всё равно нужна копия, которую хранят вне replica set.

## Replica set: primary и secondary

У replica set в типичной производственной раскладке нечётное число голосующих членов. Три голосующих члена — частый минимум. Набор выбирает один primary. Остальные члены с данными — secondary.

Записи идут на primary. Primary записывает каждую запись в oplog. Каждый secondary тянет эти записи oplog и применяет их. После применения у secondary те же документы, что у primary, с возможной задержкой.

Replica set может включать:

- Членов с данными (`mongod` с полной копией)
- **Arbiter** (голосует, данных приложения не держит)

Arbiter — особый случай. Atlas и текущие рекомендации предпочитают членов с данными. Не добавляйте arbiter, пока не понимаете компромисс write concern и хранения.

Члены общаются по портам replica set. Клиенты используют строку соединения со списком семян и `replicaSet=Name` или SRV URI Atlas.

Полезные команды:

```javascript
rs.status()
rs.conf()
db.hello()
```

`rs.status()` показывает здоровье, состояние и optime. `db.hello()` показывает, является ли текущий член primary, и перечисляет хосты.

Одиночный `mongod` — не replica set. Мультидокументным транзакциям и change streams нужен replica set (или шардированный кластер). Для учёбы можно запустить replica set из одного члена.

Primary может смениться. Драйвер должен обнаружить новый primary. Официальные драйверы это делают. Не прошивайте один хост как «всегда primary».

Не пишите на secondary. Secondary отклоняют обычные записи приложения.

## Выборы

**Выборы** выбирают новый primary. Голосующие члены начинают выборы, когда не могут достичь primary или когда primary уходит.

Член может стать primary, только если выиграет **большинство голосов**. В наборе из трёх членов два голоса — большинство. Если два члена лежат, последний член не может выбрать себя. У набора нет primary. Записи падают.

Primary **уходит** (step down), когда:

- Вы запускаете `rs.stepDown()`
- Появляется более подходящий член
- Primary не видит большинства (становится secondary, чтобы избежать записи split-brain)

**Приоритет** влияет на то, кто побеждает. Член с приоритетом `0` не может стать primary. Используйте это для hidden или delayed члена.

Выборы занимают время. Во время выборов у набора нет primary. Записи ждут или падают. Официальные драйверы повторяют некоторые записи. Проектируйте приложение на короткий простой записи.

Не запускайте два независимых replica set, которые думают, что владеют одним каталогом данных. Это не поддерживаемый метод failover.

Версия протокола и настройки выборов принадлежат конфигурации replica set. Читайте руководство своей основной версии до изменения.

Atlas проводит выборы за вас. Вы всё равно должны знать, что failover может случиться и что запись с `w: 1` может откатиться.

## Oplog

**Oplog** — особая capped-коллекция. Имя по умолчанию — `local.oplog.rs`. Primary пишет запись для каждой операции, которую secondary должны применить.

Secondary читают хвост oplog. Они применяют записи по порядку. Применение — то, как работает репликация.

Oplog **ограничен**. Старые записи исчезают, когда коллекция полна. Временной охват оставшихся записей — **окно oplog**.

Если secondary лежит дольше окна oplog, он не может догнать из oplog. Ему нужна начальная синхронизация (полная копия). Это дорого.

Размер oplog настраивается. Atlas позволяет увеличить oplog. На Community Server размер oplog задают в конфигурации или командой, которую руководство перечисляет для вашей версии.

Oplog — не общая шина событий для приложения. Change streams используют oplog внутри. Приложение должно использовать change streams или другой одобренный API, а не сырой хвост `local.oplog.rs`, если вы не оператор, который знает риски.

Не храните данные приложения в базе `local`.

`db.printReplicationInfo()` и `rs.printReplicationInfo()` показывают оценки окна oplog во многих версиях. Atlas показывает метрики oplog в UI.

## Чтение с secondary и устаревшие чтения

**Устаревшее чтение** — чтение, которое пропускает запись, уже прошедшую на primary. Репликация асинхронна, пока не подождёте write concern и правилами чтения.

Read preference по умолчанию — `primary`. Эти чтения не устаревшие чтения secondary.

Если задать read preference `secondary`, `secondaryPreferred` или `nearest`, драйвер может читать secondary. Этот secondary может отставать.

Отставание вызывает:

- Пользователь не видит документ, который только что создал
- Проверка уникальности на secondary пропускает новый ключ
- Отчёты, которые не совпадают с primary

Используйте чтения secondary, когда приложение принимает отставание. Примеры: некоторые панели, некоторые превью поиска, некоторые отчёты по всей коллекции.

Не используйте чтение secondary, чтобы подтвердить запись, которую только что отправили. Используйте primary или сессию с причинной согласованностью и concerns из темы транзакций.

Write concern `majority` не убирает устаревшие чтения на secondary. Majority значит, что запись прочна на большинстве. Конкретный secondary всё ещё может отставать.

Измеряйте отставание. Atlas показывает отставание репликации. `rs.status()` показывает даты optime. Сигнализируйте, когда отставание растёт.

## Hidden и delayed члены

**Hidden** член — secondary, который клиентские драйверы не используют для чтений. Задают `hidden: true`. Hidden член должен иметь приоритет `0`. Он всё ещё может голосовать. Он всё ещё реплицирует.

Используйте hidden член для резервных копий или задач, которые не должны брать трафик чтения приложения.

**Delayed** член применяет записи oplog после фиксированной задержки. Задержка — `secondaryDelaySecs` (старые документы использовали `slaveDelay`). Delayed член должен быть hidden и должен иметь приоритет `0`.

Используйте delayed член как короткое окно «ой». Пример: задержка 3600 секунд держит копию часовой давности. Плохой drop можно починить с этого члена, если действовать внутри задержки. Это не полная стратегия резервного копирования.

Не направляйте приложение на delayed член. Данные намеренно старые.

Не скрывайте единственные secondary, которые нужны для большинства, если не понимаете голоса. Hidden члены часто всё ещё голосуют. Планируйте большинство.

Atlas предлагает родственные типы узлов (например analytics) на некоторых тарифах. Читайте страницу Atlas своего кластера. Идея та же: держать особые члены вне пути чтения по умолчанию.

## Replica set в Atlas

**Atlas** создаёт replica set (или шардированный кластер из replica set), когда вы создаёте кластер. Вы не запускаете `mongod` вручную. Вы не правите `rs.conf()` для обычного failover.

Типичный replica set Atlas имеет три члена с данными. Atlas размещает их для высокой доступности. Atlas ведёт выборы, хранение и мониторинг.

Подключаетесь SRV URI:

```text
mongodb+srv://cluster0.example.mongodb.net
```

Драйвер разрешает хосты. Хосты могут меняться. Не привязывайте один IP Atlas как единственный хост.

Возможности Atlas, связанные с этой темой:

- Автоматический failover
- Настраиваемый размер oplog на многих тарифах
- Резервные копии отдельно от живого replica set
- Необязательные дополнительные узлы для аналитики на некоторых тарифах

Вы всё равно выбираете write concern, read preference и принимает ли приложение устаревшие чтения. Значения Atlas по умолчанию часто majority write concern. Читайте настройки кластера.

Бесплатного тарифа Atlas достаточно, чтобы выучить поведение replica set со стороны клиента. Не каждую деталь `rs.status()` видно с каждой ролью пользователя. Используйте метрики UI Atlas, когда оболочка ограничена.

Не открывайте кластер на `0.0.0.0/0` ради удобства. Используйте список IP-доступа или частную сеть.

Самоуправляемые replica set Community всё ещё полезны. Они учат `rs.initiate()`, выборы, которые вы запускаете, и hidden члены. Atlas учит производственную форму.

#### Средние практические задания

1. Соберите локальный набор из трёх членов. Сделайте step down primary. Подтвердите, что драйвер или `mongosh` находит новый primary и тестовый документ остаётся.
2. Напишите сравнение на одну страницу: задача резервной копии hidden члена, снимок Atlas, delayed член. Включите по одному ограничению.
3. Измерьте отставание во время пакетной вставки. Запишите пик отставания и было бы чтение secondary безопасным для вашего API.

#### Сложные практические задания

1. Подготовьте стандарт replica set для команды: число членов, приоритеты, политика hidden/delayed, write concern, read preference, размер oplog, Atlas vs самоуправление.

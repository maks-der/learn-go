# 11. Прикладные шаблоны

## Описание

Прикладные шаблоны — способы использовать Kafka в проекте системы. Брокер не выбирает шаблон. Вы выбираете, что значит запись и как сервис её пишет и читает.

Эта тема показывает уведомление о событии против события с состоянием против event sourcing, outbox, CQRS, порядок, дубликаты, ядовитые сообщения и правило цикла poll. Завершите эту тему после тем 3, 4, 5 и 7. Используйте кластер KRaft. Этим шаблонам не нужен ZooKeeper.

Используйте один термин для каждого понятия. Уведомление о событии — маленький сигнал, что что-то изменилось. Event-carried state transfer — событие, которое несёт данные, нужные читателю. Event sourcing хранит каждое изменение как событие и строит состояние из этого журнала. Outbox — таблица (или эквивалент) в той же транзакции базы, что и бизнес-запись. CQRS разделяет модели записи и модели чтения. Backpressure — как вы замедляете вход, когда консьюмер не успевает.

## Уведомление о событии против события с состоянием против event sourcing

**Уведомление о событии** говорит, что факт произошёл, и даёт указатель. Пример: `{ "orderId": "55" }`. Консьюмер должен вызвать API или прочитать базу, чтобы получить заказ. Много консьюмеров создают нагрузку на источник. Если источник лежит, события недостаточно.

**Event-carried state transfer (ECST)** кладёт нужные поля в событие. Пример: id заказа, позиции, итоги, id клиента. Консьюмеры могут обновить своё хранилище без обратного вызова. Событие больше. Эволюция схемы важна (тема 7).

**Event sourcing** использует журнал событий как источник истины для потока изменений. Текущее состояние — свёртка событий. Вы не перезаписываете одну «текущую строку» как единственную истину. Kafka может хранить этот журнал. Всё равно нужен способ снимка и определения типов событий. Event sourcing — проект, не переключатель Kafka.

Не смешивайте три без имени. Топик, который иногда имеет указатель, а иногда полный документ, сломает консьюмеров.

Уведомление годится, когда полезная нагрузка огромна или частная, а читателей мало. ECST — частый шаблон интеграции. Event sourcing — для ограниченного контекста, который принимает повтор как модель.

Ретеншн должен совпадать с шаблоном. Event sourcing нужен длинный или осторожно компактируемый история. Топики уведомлений могут использовать короткий ретеншн по времени, если указатель только подсказка.

KRaft не меняет смысл события. Он только хостит журнал.

## Outbox и CQRS

**Шаблон outbox** решает этот сбой: сервис пишет строку базы и затем падает до отправки в Kafka (или наоборот). Два хранилища расходятся.

Сервис пишет бизнес-строку и **строку outbox** в **одной транзакции базы**. Отдельный издатель читает outbox и производит в Kafka. После успешной отправки (и устойчивости, которую требуете, тема 3 и тема 5) издатель помечает строку outbox как отправленную или удаляет её.

Если процесс останавливается после фиксации и до отправки, издатель повторяет. Kafka может увидеть дубликат, если отправка успела, а пометка нет. Используйте идемпотентный продюсер и ключ дедупликации (тема 5).

Debezium может захватить таблицу outbox как CDC (тема 8). Тогда приложение не запускает цикл poll на таблице. Журнал транзакций становится издателем.

Не пишите сначала в Kafka и потом в базу без компенсирующего плана. Не используйте двухфазную фиксацию между Kafka и SQL-базой по умолчанию.

Кластер Kafka — KRaft. Outbox живёт в вашей базе. Connect или воркер его читает.

**CQRS** (command query responsibility segregation) разделяет модель записи от модели чтения. Команды меняют сторону записи. Запросы читают модель, сформированную под запрос.

Kafka часто труба между ними. Сервис записи фиксирует (база и/или события). События идут в Kafka (outbox или event sourcing). Консьюмер строит хранилище чтения: индекс поиска, кэш или SQL-вид. API чтения не запрашивает базу записи.

Модель чтения **eventually consistent**. Запрос может пропустить команду, которая ещё в журнале или у консьюмера. Скажите продуктовой команде. Не прячьте это.

Можно иметь больше одной модели чтения из одного топика. Это причина использовать Kafka вместо одной общей базы для всех запросов.

Не кладите каждый запрос на consume-from-beginning Kafka. Используйте сохранённую модель чтения. Ретеншн Kafka не ваш API запросов.

**Запрос-ответ через Kafka** обычно плохой выбор по умолчанию. HTTP и RPC подходят вызову, который ждёт один ответ. Если всё равно используете два топика и correlation id, задайте короткие таймауты и не блокируйте поток poll (следующий раздел).

## Порядок, дубликаты и ядовитые сообщения

**Порядок** в Kafka — на партицию (тема 2). Записи в одной партиции имеют полный порядок. Записи в двух партициях — нет.

Если нужна отношение happens-before между двумя событиями, кладите их в одну партицию (один ключ) или кладите причинный токен в полезную нагрузку (например версия на сущность).

Меток времени часов недостаточно. У двух продюсеров могут быть рассинхронные часы. Не сортируйте глобальные события по метке времени и не называйте это причинностью.

Группы консьюмеров не меняют порядок партиции. Ребалансы могут поставить партицию на паузу. Они не переставляют журнал. Unclean leader election может отбросить записи (тема 6). Держите unclean election выключенным.

**Дубликаты** нормальны в проектах at-least-once (тема 5). Причины: повтор продюсера без идемпотентности, process-then-crash-before-commit, прикладной повтор нового send, ребаланс в середине пакета.

Обрабатывайте дубликаты идемпотентным консьюмером, ключом дедупликации или транзакциями Kafka для путей Kafka-в-Kafka. Не считайте дубликат дефектом Kafka, когда выбрали at-least-once.

**Ядовитые сообщения** — записи, которые ваше приложение не может обработать (тема 3). Ядовитая запись может остановить партицию, если падает весь цикл poll. Шаблоны:

- написать запись в топик недоставленных, затем зафиксировать исходный офсет
- пропустить после ограниченного числа повторов и алертить
- исправить контракт продюсера так, чтобы яд прекратился

Топик недоставленных — обычный топик Kafka. Задайте ретеншн. Читайте его операторским процессом. У Connect есть возможность DLQ (тема 8). Приложения могут использовать ту же идею.

Не используйте `acks=0`, чтобы спрятать сбои отправки. Не отбрасывайте ядовитые записи без лога.

Запрос-ответ через Kafka добавляет больше дубликатов на таймауте и повторе. Предпочитайте HTTP для пользовательских вызовов.

## Не блокируйте цикл poll

**Цикл poll** консьюмера (тема 4) должен вызывать poll достаточно часто. `max.poll.interval.ms` ограничивает, сколько можно работать между poll. Если блокируете поток на медленном вызове HTTP или полной базе, координатор группы может убрать участника. Начинается ребаланс. Другие партиции паузятся.

**Backpressure** значит, что вы замедляете вход, когда выход не успевает. Правильные инструменты:

- ставить партиции на паузу (`pause` / `resume`), пока сливаете локальный буфер
- использовать ограниченную очередь и ставить на паузу, когда очередь полна
- понизить `max.poll.records`, чтобы каждый poll был меньше
- масштабировать консьюмеров или исправить медленный сток
- использовать квоты на других шумных клиентов (тема 10), не как единственное исправление

Неправильные инструменты:

- sleep в цикле без poll
- ждать запрос-ответ Kafka в том же потоке
- обработать тысячи записей, затем poll

У Connect и Streams свои потоки задач. Та же идея: не блокируйте задачу на неограниченном внешнем I/O без таймаута и стратегии паузы.

Медленный poll выглядит как простой Kafka. Часто это ваш код (тема 10).

KRaft не меняет правила poll. Координатор группы всё равно живёт на брокере.

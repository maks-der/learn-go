# 16. Память и производительность

## Описание

Redis быстр, когда данные помещаются в ОЗУ и команды остаются маленькими. Эта тема показывает, как читать память, как находить большие ключи, как Redis кодирует маленькие значения, как конвейеры сокращают ожидание и как slow log записывает дорогие команды.

Сначала завершите тему 2 (однопоточное выполнение), тему 4 (`maxmemory`) и тему 8 (конвейеры).

Используйте один термин для каждого понятия. Использованная память — байты, которые Redis сообщает для данных и оверхеда. RSS — размер процесса, который видит операционная система. Большой ключ — одно значение, большое в байтах или в числе элементов. Кодирование — раскладка значения в памяти. Slow log — список команд, которые превысили порог времени.

## `INFO memory`

`INFO memory` печатает поля памяти как строки `key:value`. Полезные поля (имена могут чуть варьироваться по версии):

- `used_memory` / `used_memory_human` — взгляд аллокатора на данные Redis
- `used_memory_rss` / `used_memory_rss_human` — резидентный размер операционной системы
- `used_memory_peak_human` — пик с старта
- `maxmemory` — настроенный предел (`0` часто значит без предела на 64-бит)
- `mem_fragmentation_ratio` — RSS делённый на использованную память (приблизительно)
- `allocator_*` — детали аллокатора в некоторых сборках

```text
INFO memory
```

`used_memory` и RSS не одно и то же. Фрагментация, отображения файлов и copy-on-write во время `BGSAVE` (тема 9, тема 19) поднимают RSS.

Отношение сильно выше `1` может значить фрагментацию или недавний fork. Отношение ниже `1` может появиться с общими страницами или странностями аллокатора. Не считайте одно число приговором. Используйте `MEMORY DOCTOR` и документацию вашей версии.

`INFO stats` добавляет `expired_keys`, `evicted_keys`, `keyspace_hits` и `keyspace_misses`. Доля попаданий — производное число (тема 19).

Смотрите `used_memory` против `maxmemory`. Когда они встречаются, начинаются вытеснение или ошибки `OOM` (тема 4).

Не сэмплируйте `INFO` в тесном цикле в основном потоке огромного экземпляра без нужды. Команда обычно дешёвая. Привычка собирать каждые 10 секунд нормальна.

## `MEMORY USAGE`, `MEMORY DOCTOR`

`MEMORY USAGE key` оценивает байты одного ключа, включая оверхед. Это оценка. Её достаточно, чтобы найти выбросы.

```text
MEMORY USAGE lab:big
```

Ответ — целое (байты) или null, если ключа нет.

`MEMORY DOCTOR` возвращает текстовый совет об экземпляре (фрагментация, пик, аллокатор). Считайте подсказкой, а не тикетом, который закрываете вслепую.

`MEMORY STATS` возвращает карту чисел аллокатора и набора. Используйте, когда `INFO memory` недостаточно.

`MEMORY PURGE` просит аллокатор отдать свободные страницы операционной системе, когда аллокатор это поддерживает. Эффект варьируется. Сначала используйте в лаборатории. Не ждите, что это сожмёт полный набор.

`MEMORY MALLOC-SIZE` есть в некоторых сборках для отладки аллокатора. Для работы приложения не нужен.

Не запускайте `MEMORY USAGE` на каждом ключе в промышленной среде в тесном цикле без темпа `SCAN`. Каждый вызов — команда в основном потоке. Пакетируйте расследование.

Маленький `MEMORY USAGE` с огромным `HLEN` всё ещё может быть проблемой в момент `HGETALL`. Размер в байтах и размер в числе элементов оба «большие» (следующий раздел).

## Большие ключи (`--bigkeys`, `SCAN`)

Большой ключ — ключ с большим размером в байтах или большим числом элементов. Примеры: строка 50 МБ, список из 10 миллионов элементов, хеш с 1 миллионом полей.

Риски:

- `GET`, `HGETALL`, `LRANGE 0 -1`, `SMEMBERS` копируют или обходят всё значение в основном потоке
- Репликация и RDB растут
- Сетевые буферы растут
- Cluster не может разделить один ключ по слотам (тема 11)

Найдите большие ключи:

```text
redis-cli --bigkeys
redis-cli --memkeys
```

Эти инструменты используют `SCAN`. Они сэмплируют. Могут пропустить ключ. Всё равно добавляют нагрузку. Запускайте на реплике, когда можете (тема 10). Примите устаревшие чтения.

Можно также делать `SCAN` и вызывать `MEMORY USAGE`, `STRLEN`, `HLEN`, `LLEN`, `SCARD`, `ZCARD`, `XLEN` на ключ. Темпируйте цикл.

Исправления:

- Разделить одну огромную коллекцию на много ключей (шарды, корзины времени)
- Хранить блобы в объектном хранилище; держать указатель в Redis
- Использовать `HSCAN`, страницы `LRANGE`, `SSCAN` вместо полных дампов
- `UNLINK` вместо `DEL` для больших значений (ленивое освобождение)

Не игнорируйте большой ключ, потому что у `used_memory` ещё есть запас. Следующий `HGETALL` может остановить экземпляр.

`--bigkeys` — инструмент лаборатории и реплики. Не планируйте его на primary каждую минуту.

## Внутренности кодирования: ziplist / listpack / hashtable (осведомлённость)

Redis хранит маленькие коллекции в компактных кодированиях, чтобы экономить ОЗУ. Когда коллекция растёт за пороги, Redis превращает значение в более крупную структуру.

Исторические и текущие имена (осведомлённость):

- ziplist — старый компактный список записей (многие версии использовали для маленьких хешей, списков, zset)
- listpack — более новое компактное кодирование, которое заменяет ziplist в текущем Redis
- quicklist — список компактных узлов (реализация списка)
- hashtable (dict) — хеш-таблица для более крупных хешей и множеств
- intset — маленькое множество целых
- skiplist плюс dict — более крупные упорядоченные множества

Вы не выбираете кодирование в приложении. Redis превращает, когда пересекаются пределы в `redis.conf` (`hash-max-listpack-entries`, `hash-max-ziplist-entries` в старых версиях и похожие ключи).

`OBJECT ENCODING key` показывает текущее кодирование:

```text
OBJECT ENCODING lab:h
```

Ответы выглядят как `listpack`, `hashtable`, `int`, `embstr`, `raw`, `quicklist`, `intset`, `skiplist`.

Почему это важно:

- Маленький хеш может использовать гораздо меньше ОЗУ, чем ждёте от наивной модели указателей
- После преобразования память прыгает
- Бенчмарки на 10 полях не предсказывают 100 000 полей

Не настраивайте пределы listpack в промышленной среде без теста памяти. Более высокий предел держит компактное кодирование дольше и может сделать одну команду, которая переписывает весь компактный блоб, дороже.

Этот раздел — осведомлённость. Вы не пишете ziplist руками.

## Конвейеры против многих кругов

Тема 8 объяснила конвейеры. Этот раздел — взгляд производительности.

Каждый запрос/ответ платит один сетевой круг (RTT). На RTT 0,5 мс 10 000 `GET` ждут около 5 секунд только сеть. Конвейер из 10 000 `GET` платит несколько RTT за весь пакет (плюс время сервера).

```text
redis-cli --pipe < commands.txt
```

Правила:

- Конвейерьте независимые команды
- Ограничивайте пакет (сотни до нескольких тысяч)
- Не предполагайте атомарность (другие клиенты вставляются)
- Кластерные клиенты делят пакеты по слоту (тема 11, тема 12)
- Конвейер огромных `GET` всё ещё может остановить основной поток и заполнить буферы

`MGET` и `MSET` сокращают RTT для строк на одном слоте. Они не полная замена конвейера смешанных команд.

Измеряйте:

- Астрономическое время цикла против конвейера
- `INFO stats` `instantaneous_ops_per_sec`
- Память клиента во время огромного конвейера

Не конвейерьте команду, которая должна видеть предыдущий ответ до выбора следующей команды.

## Slow log

Slow log записывает команды, которые превышают порог. Он живёт в памяти на экземпляре.

```text
SLOWLOG GET 10
SLOWLOG LEN
SLOWLOG RESET
```

Конфигурация:

- `slowlog-log-slower-than` — микросекунды (1000 микросекунд = 1 миллисекунда). Отрицательное значение может отключить журнал (проверьте версию).
- `slowlog-max-len` — максимум записей

```text
CONFIG GET slowlog-log-slower-than
CONFIG GET slowlog-max-len
```

Каждая запись включает id, метку времени, время выполнения и аргументы команды (обрезанные). Используйте, чтобы найти `KEYS`, большой `HGETALL`, тяжёлый `SORT` или медленный скрипт Lua.

Время — выполнение команды на сервере. Оно не включает RTT клиента.

`SLOWLOG RESET` очищает журнал. Используйте после копирования записей. Не сбрасывайте на общем промышленном экземпляре без причины.

Команда может быть медленной, потому что ключ большой, потому что скрипт крутится или потому что хост перегружен. Сочетайте slow log с `MEMORY USAGE` и `INFO`.

Не задавайте порог `0` на занятом промышленном экземпляре надолго. Журнал заполняется обычными командами.

Монитор задержки (`LATENCY DOCTOR`, `LATENCY LATEST`) — связанный инструмент для всплесков. Используйте, когда slow log недостаточно.

5. Когда предпочитать реплику для расследования памяти?

#### Простые практические задания

1. Напишите шпаргалку: `INFO memory`, `MEMORY USAGE`, `OBJECT ENCODING`, `--bigkeys`, `--pipe`, `SLOWLOG GET`.
2. Экспортируйте `INFO memory` и выделите `used_memory_human`, `used_memory_rss_human`, `maxmemory`.
3. Перечислите три команды, которые не запустите на огромной коллекции в промышленной среде.
4. Нарисуйте использованную память против RSS во время простоя, нагрузки и `BGSAVE`.

#### Средние практические задания

1. Создайте лабораторный набор с одним большим хешем и 1000 маленьких ключей. Найдите большой хеш через `--bigkeys` и через `SCAN`+`HLEN`. Запишите оба пути.
2. Конвейерьте 10 000 `PING`. Сравните время с 10 000 последовательных `PING`. Добавьте один `SLOWLOG GET`.
3. Задокументируйте кодирование хеша, пока он растёт через точку преобразования. Включите `MEMORY USAGE`.

#### Сложные практические задания

1. Набросайте ежемесячный скрипт здоровья Redis: память, большие ключи на реплике, снимок slow log, доля попаданий. Нет промышленного `KEYS`.
2. Воспроизведите остановку в лаборатории (большой `HGETALL`). Покажите запись slow log и исправление (HSCAN или разделение). Запишите времена.

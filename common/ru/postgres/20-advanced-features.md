# 20. Продвинутые возможности

## Описание

Эта тема показывает продвинутый SQL и расширения в PostgreSQL 16 и PostgreSQL 17. Вы узнаёте оконные функции, `FILTER` на агрегатах, диапазонные типы и ограничения исключения, необязательный PostGIS, обёртки внешних данных, параллельный запрос и логическое декодирование для захвата изменений.

Сначала завершите тему 19. Вы умеете читать планы и индексы. Завершите эту тему до укрепления продакшен-кластера.

Используйте один термин для каждого понятия. Оконная функция считает значение по связанному набору строк, не сворачивая результат. `FILTER` ограничивает, какие строки входят в один агрегат. Диапазонный тип хранит нижнюю и верхнюю границу. Ограничение исключения запрещает пересекающиеся диапазоны. Обёртка внешних данных (FDW) читает удалённый источник как таблицу. Логическое декодирование превращает WAL в поток изменений. Этот справочник рассчитан на PostgreSQL 16 и PostgreSQL 17.

## Оконные функции

Оконная функция использует `OVER (...)`. Набор результата держит одну строку на входную строку. `GROUP BY` сворачивает строки. Окно используют, когда нужны ранг, нарастающая сумма или соседняя строка.

```sql
SELECT
    id,
    customer_id,
    total,
    sum(total) OVER (PARTITION BY customer_id) AS customer_sum,
    rank() OVER (PARTITION BY customer_id ORDER BY total DESC) AS rnk,
    lag(total) OVER (PARTITION BY customer_id ORDER BY id) AS prev_total
FROM shop.orders;
```

Предложения внутри `OVER`:

- `PARTITION BY` — сбросить окно
- `ORDER BY` — порядок внутри раздела (нужен для `rank`, `lag`, нарастающих сумм)
- рамка (`ROWS BETWEEN ...` или `RANGE BETWEEN ...`) — какие соседи считаются

Умолчательная рамка для многих агрегатов с `ORDER BY` — `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. Это нарастающий агрегат. Если нужна сумма всего раздела, используйте `sum(total) OVER (PARTITION BY customer_id)` без `ORDER BY` или задайте рамку `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`.

Частые функции: `row_number()`, `rank()`, `dense_rank()`, `lag()`, `lead()`, `first_value()`, `sum()`, `avg()`, `count()`.

Тема 6 покрыла `GROUP BY` и CTE. Окно можно положить в CTE и затем фильтровать `WHERE rnk = 1`. `DISTINCT ON` (тема 6) может заменить фильтр `row_number()` в простых случаях «первая строка в группе». Предпочитайте форму, которую можете проверить.

Не используйте окно, когда соединение с сгруппированным подзапросом яснее и планировщик проще. Не забывайте `ORDER BY` внутри `OVER` для `lag` и `rank`.

Официально: [https://www.postgresql.org/docs/17/tutorial-window.html](https://www.postgresql.org/docs/17/tutorial-window.html), [https://www.postgresql.org/docs/17/functions-window.html](https://www.postgresql.org/docs/17/functions-window.html).

## `FILTER` на агрегатах

`FILTER` ограничивает строки, которые видит один агрегат. Другие столбцы в том же `SELECT` могут использовать другой фильтр.

```sql
SELECT
    customer_id,
    count(*) AS orders,
    count(*) FILTER (WHERE total >= 100) AS large_orders,
    sum(total) FILTER (WHERE created_on >= DATE '2026-01-01') AS ytd
FROM shop.orders
GROUP BY customer_id;
```

Без `FILTER` пишут `sum(CASE WHEN total >= 100 THEN 1 ELSE 0 END)`. `FILTER` короче и говорит о намерении.

`FILTER` работает с `GROUP BY` и с оконными агрегатами:

```sql
SELECT
    id,
    count(*) FILTER (WHERE total > 0)
        OVER (PARTITION BY customer_id) AS positive_count
FROM shop.orders;
```

`FILTER` — не `WHERE` для всего запроса. Строки, которые не прошли фильтр, всё равно существуют для других агрегатов в той же строке.

Не заменяйте избирательный `WHERE`, который убирает большинство строк, на `FILTER` по огромному сканированию. `WHERE` всё равно сначала сужает входной набор. Не смешивайте `FILTER` с `DISTINCT` внутри агрегата, пока не прочитаете документацию этой комбинации.

Официально: [https://www.postgresql.org/docs/17/sql-expressions.html#SYNTAX-AGGREGATES](https://www.postgresql.org/docs/17/sql-expressions.html#SYNTAX-AGGREGATES).

## Диапазонные типы и ограничения исключения

Диапазонный тип хранит нижнюю и верхнюю границу. Встроенные типы: `int4range`, `int8range`, `numrange`, `tsrange`, `tstzrange` и `daterange`. Границы могут быть включительными или исключительными. Диапазон может быть пустым. Диапазон может быть безграничным.

```sql
SELECT daterange('2026-01-01', '2026-02-01', '[)');
SELECT tstzrange('2026-01-01 00:00+00', '2026-01-01 12:00+00')
       && tstzrange('2026-01-01 11:00+00', '2026-01-01 18:00+00');
```

`&&` значит пересекается. `@>` значит содержит. Тема 5 показала `EXCLUDE` на высоком уровне. Обычное ограничение бронирования:

```sql
CREATE TABLE shop.room_bookings (
    room_id bigint NOT NULL,
    during tstzrange NOT NULL,
    EXCLUDE USING gist (room_id WITH =, during WITH &&)
);
```

Две строки с одним `room_id` не должны иметь пересекающиеся `during`. Ограничению исключения нужен индекс GiST. PostgreSQL создаёт этот индекс для ограничения.

Установите `btree_gist`, когда нужен `=` на скаляре рядом с `&&` на диапазоне в одном `EXCLUDE`:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;
```

Тема 5 сказала знать `EXCLUDE`. Этот раздел — рабочий шаблон. Предпочитайте столбец диапазона плюс `EXCLUDE` двум столбцам времени плюс клубок предложений `CHECK`.

Не храните пересекающиеся бронирования и не фильтруйте их только в приложении. Не используйте `tsrange`, если нужны часовые пояса; используйте `tstzrange`. Не забывайте `btree_gist`, когда документация его требует.

Официально: [https://www.postgresql.org/docs/17/rangetypes.html](https://www.postgresql.org/docs/17/rangetypes.html), [https://www.postgresql.org/docs/17/btree-gist.html](https://www.postgresql.org/docs/17/btree-gist.html).

## PostGIS (геопространственное, необязательно)

PostGIS — расширение, которое добавляет типы geometry и geography, пространственные индексы (GiST) и пространственные функции. Оно необязательно. Многие установки PostgreSQL 16 и 17 его не загружают. Облачные поставщики часто предлагают его как именованное расширение.

```sql
CREATE EXTENSION IF NOT EXISTS postgis;
SELECT PostGIS_Version();
```

Типичные объекты:

- `geometry` — плоские координаты в системе пространственной привязки
- `geography` — измерения на сфероиде (метры)
- `ST_DWithin`, `ST_Contains`, `ST_Distance`
- индекс `GIST` на столбце geometry

```sql
CREATE TABLE shop.stores (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name text NOT NULL,
    loc geography(Point, 4326) NOT NULL
);

CREATE INDEX stores_loc_gix ON shop.stores USING gist (loc);

SELECT name
FROM shop.stores
WHERE ST_DWithin(loc, ST_MakePoint(-0.12, 51.50)::geography, 1000);
```

Если `CREATE EXTENSION postgis` падает, пропустите практические задания, которым оно нужно. Напишите, что пакета нет. Вы всё равно должны знать, что пространственный поиск — не пара `numeric` плюс B-дерево.

Не храните широту и долготу как `text`. Не запускайте `ST_Distance` по каждой строке без индекса GiST, когда таблица большая. Не считайте PostGIS обязательным для остального пути.

Официально: [https://postgis.net/documentation/](https://postgis.net/documentation/). Сопоставьте версию PostGIS с вашим PostgreSQL 16 или 17.

## Обёртки внешних данных

Обёртка внешних данных (FDW) позволяет запрашивать удалённый источник как внешнюю таблицу. `postgres_fdw` — частая обёртка для другого сервера PostgreSQL. Другие обёртки существуют для файлов и других баз. Качество разное.

```sql
CREATE EXTENSION postgres_fdw;

CREATE SERVER remote_shop
    FOREIGN DATA WRAPPER postgres_fdw
    OPTIONS (host 'remote.example', dbname 'shop', port '5432');

CREATE USER MAPPING FOR shop_app
    SERVER remote_shop
    OPTIONS (user 'remote_read', password 'secret');

CREATE FOREIGN TABLE shop.remote_items (
    id bigint,
    name text,
    qty int
)
SERVER remote_shop
OPTIONS (schema_name 'shop', table_name 'items');
```

`IMPORT FOREIGN SCHEMA` может создать много внешних таблиц сразу.

Планировщик может протолкнуть часть предложений `WHERE` на удалённый сервер. Соединение локальной и удалённой таблиц может вытянуть много строк. `EXPLAIN` показывает `Foreign Scan`.

FDW не замена репликации, когда нужна локальная копия. Это путь живого запроса. Сбой сети — сбой запроса. Транзакции между локальным и удалённым имеют пределы. Читайте документацию `postgres_fdw` про текущее поведение изоляции 16/17.

Не кладите пароль в `USER MAPPING` в общем скрипте. Не запрашивайте огромную удалённую таблицу через `SELECT *` с ноутбука. Не используйте FDW как единственную резервную копию удалённых данных.

Официально: [https://www.postgresql.org/docs/17/postgres-fdw.html](https://www.postgresql.org/docs/17/postgres-fdw.html).

## Параллельный запрос

PostgreSQL может использовать больше одного worker для одного запроса. В `EXPLAIN` видны `Gather`, `Parallel Seq Scan` или `Parallel Hash`. Тема 9 сказала, что перед узлом может быть `Parallel`.

Настройки (обзор):

- `max_parallel_workers_per_gather` — worker на узел gather
- `max_parallel_workers` — потолок кластера
- `max_worker_processes` — слоты процессов
- `min_parallel_table_scan_size` / `min_parallel_index_scan_size` — пороги размера

```sql
SHOW max_parallel_workers_per_gather;
EXPLAIN (ANALYZE)
SELECT count(*) FROM shop.events;
```

Параллельный запрос помогает большим сканированиям и большим хешам. Он может вредить маленьким поискам OLTP (стоимость старта). Планировщик отключает параллелизм, когда так говорит модель стоимости, когда запрос в контексте только serial, или когда вы `SET max_parallel_workers_per_gather = 0`.

Некоторые операции не параллелятся. Функция, которая не `PARALLEL SAFE`, может блокировать worker. Помечайте функции верно (`PARALLEL SAFE`, `RESTRICTED`, `UNSAFE`).

Не поднимайте `max_parallel_workers_per_gather` до 8 на занятом 4-ядерном хосте OLTP без измерения. Не форсируйте параллель на таблице из 10 строк. Не забывайте, что каждый worker использует `work_mem` (тема 18).

Официально: [https://www.postgresql.org/docs/17/parallel-query.html](https://www.postgresql.org/docs/17/parallel-query.html).

## Логическое декодирование / CDC

Логическое декодирование читает WAL и выдаёт поток изменений (insert, update, delete) для таблиц. Инструменты захвата изменений (CDC) используют этот поток. `wal_level` должен быть `logical`. Слот репликации удерживает WAL для потребителя.

Встроенный плагин вывода: `pgoutput` (использует логическая репликация). Существуют contrib и внешние плагины (`test_decoding` для лабораторий). Инструменты вроде Debezium сидят вне PostgreSQL и потребляют слот.

```sql
SELECT * FROM pg_create_logical_replication_slot('cdc_lab', 'test_decoding');
-- make changes, then:
SELECT * FROM pg_logical_slot_get_changes('cdc_lab', NULL, NULL);
SELECT pg_drop_replication_slot('cdc_lab');
```

`test_decoding` может нуждаться в пакете contrib. Если плагина нет, прочитайте документацию и пропустите шаг потребления.

CDC не резервная копия. CDC не замена `LISTEN`. Потребители CDC должны обрабатывать смены схемы, снимки и сбои. Застрявший слот заполняет диск (тема 16 и тема 18).

PostgreSQL 16 может декодировать со стендбая в поддерживаемых схемах. PostgreSQL 17 улучшает failover для логических слотов. Сначала изучите слоты и `wal_level`.

Не создавайте слот для теста и не оставляйте его. Не разбирайте файлы WAL вручную. Не отправляйте поток в недоверенную сеть без TLS и аутентификации.

Официально: [https://www.postgresql.org/docs/17/logicaldecoding.html](https://www.postgresql.org/docs/17/logicaldecoding.html).

# 6. Множества и отображения

## Описание

Множество хранит уникальные ключи. Отображение хранит значение для каждого ключа. Эта тема объясняет неупорядоченные хеш-реализации, упорядоченные древовидные реализации, мультимножества, инвалидацию итераторов и как выбирать хеш против дерева.

Завершите эту тему после хеш-таблиц. Завершите двоичные деревья поиска в теме 8 после того, как узнаете, зачем существует упорядоченное отображение.

Используйте один термин для каждого понятия. **Множество** отвечает «есть ли этот ключ?». **Отображение** (также словарь) отвечает «какое значение сидит у этого ключа?». **Неупорядоченное** значит, что порядок обхода — не сортировка ключей. **Упорядоченное** значит, что обход посещает ключи в отсортированном порядке. **Мультимножество** хранит один ключ больше одного раза. **Итератор** — курсор, который обходит элементы. **Инвалидация** значит, что курсор больше не безопасно использовать.

## Неупорядоченное множество/отображение (хеш) против упорядоченного множества/отображения (дерево)

**Неупорядоченное множество** — хеш-таблица ключей. **Неупорядоченное отображение** — хеш-таблица пар ключ–значение. Поиск, вставка и удаление в среднем Θ(1) при хорошем хеше и ограниченном коэффициенте заполнения. Порядок обхода не задан. Два обхода могут дать два порядка после resize.

**Упорядоченное множество** — сбалансированное дерево поиска ключей. **Упорядоченное отображение** хранит значение в каждом узле. Поиск, вставка и удаление есть Θ(log n) в худшем случае, если дерево остаётся сбалансированным. Обход in-order посещает ключи от малого к большому.

```text
unordered map (hash)
  "cat" → 1
  "eel" → 3
  "dog" → 2
  walk can be: eel, cat, dog

ordered map (tree)
  same three pairs
  walk is: cat, dog, eel
```

Оба ADT поддерживают get, put, delete и «contains» для ключа. Упорядоченный ADT также поддерживает:

- первый и последний ключ
- следующий ключ после k
- обход диапазона от L до R

Хеш-ADT не поддерживает эти операции дёшево. Пришлось бы просмотреть все ключи.

Память: хеш-таблица хранит массив корзин плюс записи. Дерево хранит указатели в каждом узле. Константы различаются. Классы — обычная причина выбора.

Не используйте хеш-отображение, когда нужны отсортированные ключи. Не используйте дерево-отображение, когда нужны только get и put и вы хотите среднее константное время.

Тема 5 указала худший случай Θ(n) для деградировавшей хеш-таблицы. Сбалансированное дерево даёт строгую логарифмическую оценку. Эта оценка — причина выбрать дерево, даже если порядок не нужен.

## Мультимножество

**Мультимножество** (мешок) хранит ключи и разрешает дубликаты. Ключ 7 может появиться три раза. Множество хранило бы 7 один раз.

**Мультимножество со счётчиком** хранит каждый различный ключ один раз и хранит целое-счётчик. Вставка существующего ключа добавляет 1 к счётчику. Удаление вычитает 1. Когда счётчик достигает 0, вы убираете ключ.

```text
multiset of integers:  2, 2, 5, 5, 5, 9
count form:            2 → 2,  5 → 3,  9 → 1
size (elements):       6
size (distinct):       3
```

Пишите, какой размер вы имеете в виду. **Полный размер** считает элементы. **Размер различных** считает ключи.

Хеш-отображение из ключа в счётчик реализует неупорядоченное мультимножество. Дерево-отображение из ключа в счётчик реализует упорядоченное мультимножество. Обход упорядоченного мультимножества может выдавать каждый ключ `count` раз или выдавать каждый различный ключ один раз.

Список значений тоже мультимножество, если вы не убираете дубликаты. Поиск одного значения тогда Θ(n). Форма отображения-счётчиков находит ключ в классе внутреннего отображения.

Не используйте множество, когда задача считает копии (например, голоса или инвентарь). Не используйте мультимножество, когда правило — уникальность.

Отображение ключа в список записей — другой дизайн. Этот дизайн хранит лишние данные на копию. Счётчика достаточно, когда копии одинаковы.

## Инвалидация итератора (концептуально)

**Итератор** — курсор. Он называет позицию в коллекции. Next двигает курсор. Некоторые итераторы также разрешают удаление текущего элемента.

**Инвалидация** значит, что курсор больше не безопасен. Поздний next или чтение — дефект. Коллекция изменилась так, что курсор этого не понимает.

Типичные причины:

- resize хеш-таблицы (перехеширование двигает записи)
- вставка, которая растит динамический массив (адрес буфера может измениться)
- удаление узла, который держит курсор
- удаление более ранней ячейки массива (поздние индексы двигаются)

```text
walk a hash map
  mid-walk: insert many keys, table resizes
  old cursor points at a stale bucket
  next is invalid
```

Правила различаются по реализации. Эта тема учит идее, а не одному языку. Безопасный шаблон:

1. Не вставляйте и не удаляйте во время обхода, кроме определённой операции «удалить текущий».
2. Если нужно изменить коллекцию, сначала соберите ключи, затем меняйте после обхода.
3. После resize или перестройки создайте новый итератор.

Целочисленный индекс в массив тоже может устареть. После вставки в начало старый индекс i называет другой элемент.

Указатель на узел списка может остаться действительным, когда вы вставляете в другом месте, потому что адреса узлов не двигаются. Удаление этого узла всё равно инвалидирует этот указатель.

Не предполагайте, что обход безопасен при конкурентных записях. Тема 15 покрывает конкурентные отображения на высоком уровне.

## Как выбирать хеш против дерева

Выбирайте **хеш-множество или хеш-отображение**, когда:

- нужны get, put, delete и contains
- не нужен отсортированный порядок или ближайший ключ
- вы принимаете среднее Θ(1) и возможный худший случай Θ(n)
- ключи хешируемые и стабильные

Выбирайте **дерево-множество или дерево-отображение**, когда:

- нужен отсортированный обход, first, last, next или диапазон
- нужна оценка Θ(log n) на каждый вызов
- у ключей полный порядок (их можно сравнивать)
- вы можете заплатить лишние указатели и большую константу

```text
need "all names from K to M"     → ordered tree
need "value for this id"          → hash (usual)
need "never pause for Θ(n) chain" → balanced tree (or a hash with extra care)
need "most frequent key"          → neither alone; add a count or a heap
```

Если ключи нельзя хешировать, нельзя использовать хеш-таблицу. Если ключи нельзя сравнивать, нельзя использовать дерево поиска.

Отсортированный массив плюс двоичный поиск — третий выбор. Поиск есть Θ(log n). Вставка в середину есть Θ(n). Используйте его, когда коллекция почти статична.

Список пар — четвёртый выбор. Поиск есть Θ(n). Используйте его только для очень малого n.

Измеряйте, если n умеренное и константы важны. Запись выбирает семейство. Измерение выбирает победителя на машине.

Не выбирайте дерево, потому что оно выглядит более формальным. Не выбирайте хеш, потому что он выглядит быстрее в лозунге.

Тема 9 объясняет сбалансированные деревья. Тема 8 объясняет свойство BST, которое использует упорядоченное отображение.

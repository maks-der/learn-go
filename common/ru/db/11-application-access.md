# 11. Доступ из приложения

## Описание

Эта тема показывает, как программа говорит с СУБД. Вы изучаете драйверы, строки подключения, пул подключений, подготовленные операторы, SQL-инъекцию, объектно-реляционные отображатели (ORM), построители запросов, сырой SQL, проблему N+1 запросов, миграции, сиды и фикстуры.

Используйте один термин для каждого понятия. Драйвер — библиотека, которая шлёт сообщения протокола СУБД. Сессия — одно подключение. Миграция — версионированное изменение схемы. Завершите эту тему после того, как умеете писать SQL и использовать транзакции. Приложение должно использовать эти навыки без небезопасной конкатенации строк.

Путь нейтрален к вендорам. Имена драйверов и ORM отличаются. Риски — нет.

## Драйверы и строки подключения

Драйвер — библиотека на языке приложения. Драйвер реализует клиентский протокол СУБД. Ваш код вызывает драйвер. Драйвер шлёт SQL и параметры. Драйвер возвращает строки и ошибки.

Вы не открываете файлы данных. Вы подключаетесь. Строка подключения (также URI или DSN) — одно текстовое значение, которое называет, как подключиться. Типичные поля:

- хост
- порт
- пользователь
- пароль
- имя базы
- дополнительные опции (TLS, таймаут, путь поиска схемы)

```text
# URI shape (product prefixes differ)
postgresql://learn:SECRET@127.0.0.1:5432/learn?sslmode=disable

# Key-value shape
host=127.0.0.1 port=5432 user=learn password=SECRET dbname=learn
```

Используйте официальный драйвер для своего языка и продукта. Общий драйвер ODBC или JDBC валиден, когда платформа требует. Читайте документацию драйвера по типам: как десятичное, метка времени и булево становятся значениями языка.

Подключение — сессия. У сессии есть пользователь, текущая база и состояние транзакции. Закрывайте подключение, когда работа сделана, или возвращайте его в пул (следующий раздел).

Не кладите продакшен-пароль в исходный код. Не коммитьте строку подключения, которая содержит секрет. Используйте переменную окружения или хранилище секретов. Позже тема безопасности покрывает секреты подробнее.

Не используйте пользователя-администратора из приложения в продакшене. Создайте пользователя приложения с правами, которые нужны программе.

Если драйвер не подключается, читайте ошибку. Типичные причины: неверный хост, неверный порт, сервер не запущен, несовпадение TLS или отклонённый пользователь.

## Пул подключений

Пул подключений — набор открытых подключений, которые приложение переиспользует. Открытие и закрытие TCP-сессии и сессии СУБД имеет цену. Пул платит эту цену один раз, затем даёт подключение на одну единицу работы.

Типичные настройки пула:

| Настройка | Смысл |
| --- | --- |
| Максимальный размер | Больше всего подключений, которые пул может открыть |
| Минимальный размер | Подключения, которые держать открытыми в простое |
| Таймаут простоя | Когда пул закрывает неиспользуемое подключение |
| Таймаут получения | Как долго запрос ждёт свободное подключение |

Приложение берёт подключение, выполняет операторы, фиксирует или откатывает и возвращает подключение. «Вернуть» значит, что пул снова владеет подключением. Приложение не должно держать взятое подключение через ожидание HTTP или время размышления пользователя.

Размер пула — не «как можно больше». Каждое подключение использует память на СУБД. Слишком много подключений замедляет сервер. Веб-процессу с 50 воркерами не нужно 50 простаивающих подключений, если большинство воркеров ждёт сеть.

```text
Client requests  -->  application pool  -->  few DBMS connections
```

Не открывайте новое подключение на каждый оператор SQL на горячем пути. Не используйте одно глобальное подключение из многих потоков, если драйвер не документирует такое использование. Предпочитайте одно подключение на параллельную единицу работы.

Пул в приложении и пул в прокси (пример: пулер подключений перед СУБД) могут умножать подключения. Считайте произведение: максимум приложения умножить на число экземпляров приложения.

Когда пул пуст, новая работа ждёт. Это ожидание лучше, чем безграничный шторм новых подключений.

## Подготовленные операторы и SQL-инъекция

Подготовленный оператор — SQL с заполнителями. Приложение шлёт текст оператора один раз (или это делает драйвер). Приложение шлёт значения параметров отдельно. СУБД не считает значения параметров синтаксисом SQL.

```sql
-- Placeholder shape differs by product: $1, ?, :name
SELECT *
FROM customers
WHERE email = $1;
```

SQL-инъекция — атака. Злоумышленник кладёт синтаксис SQL в значение. Если приложение конкатенирует это значение в строку оператора, СУБД выполняет SQL злоумышленника.

```text
-- Unsafe shape (do not use)
"SELECT * FROM users WHERE name = '" + userInput + "'"

-- If userInput is:  ' OR '1' = '1
-- the statement changes meaning
```

Правила:

1. Используйте связанные параметры для каждого значения, которое приходит извне оператора.
2. Не собирайте SQL склейкой строк с пользовательским вводом.
3. Идентификаторы (имена таблиц, имена столбцов) не могут использовать параметры значений в стандартном SQL. Если нужно выбрать идентификатор, используйте фиксированный белый список, не сырой ввод.

Подготовленные операторы также помогают СУБД переиспользовать план. Эта польза вторична. Безопасность — первая причина.

ORM или построитель запросов, который использует параметры, безопасен для значений. ORM, который позволяет передать сырую строку, не автоматически безопасен. Читайте запасной люк.

Числа `LIMIT` и `OFFSET` — значения. Связывайте их. Не конкатенируйте их.

## ORM против построителя запросов против сырого SQL

Три обычных способа слать SQL из приложения:

**Сырой SQL.** Вы пишете оператор. Драйвер выполняет его с параметрами. Вы контролируете текст. Вам принадлежат каждое соединение и каждый список столбцов.

**Построитель запросов.** Вы вызываете функции, которые строят SQL. Построитель добавляет параметры. Вы всё ещё думаете таблицами и столбцами. Построитель уменьшает ошибки строк. Он не прячет реляционную модель.

**ORM.** Объектно-реляционный отображатель сопоставляет строки объектам (или структурам). Вы загружаете `Customer`. ORM пишет `SELECT` и `INSERT`. ORM может прятать соединения и загружать графы объектов.

| Метод | Контроль SQL | Типичный риск |
| --- | --- | --- |
| Сырой SQL | Полный | Дублирование; инъекция, если конкатенируете |
| Построитель запросов | Высокий | Сложные запросы становятся трудны читать |
| ORM | Переменный | Загрузки N+1; скрытые операторы; дырявые отображения |

Используйте сырой SQL или построитель, когда запрос — отчёт, чтение с тяжёлыми соединениями или пакетная запись. Используйте ORM, когда много простых операций над строками и команда принимает правила отображения.

ORM — не вторая СУБД. Ограничения, типы и транзакции всё ещё живут в базе. Если модель ORM и схема не согласны, во время выполнения побеждает схема.

Не считайте «мы используем ORM» заявлением о безопасности. ORM всё равно должен параметризовать. Не считайте «мы используем сырой SQL» заявлением о производительности. Плохой сырой запрос всё равно плох.

Сначала изучите SQL. Затем используйте ORM как инструмент. Если не можете прочитать SQL, который испускает ORM, не можете его настроить.

## Проблема N+1 запросов

Проблема N+1 — форма запроса. Вы запускаете один запрос, чтобы загрузить N родителей. Затем запускаете один запрос на родителя, чтобы загрузить детей. Всего запросов: `1 + N`.

Пример. Загружаете 50 заказов. Затем загружаете клиента для каждого заказа в цикле. Запускаете 51 запрос. Одно соединение или одно `WHERE order_id IN (...)` может загрузить те же данные в одном или двух запросах.

```text
-- N+1 shape
SELECT * FROM orders;                 -- 1 query
SELECT * FROM customers WHERE id = ?; -- repeated N times

-- Set-based shape
SELECT o.*, c.name
FROM orders AS o
JOIN customers AS c ON c.customer_id = o.customer_id;
```

ORM вызывают эту форму, когда лениво загружаете связь внутри цикла. Код выглядит как доступ к полю. Каждый доступ — запрос.

Исправления:

1. Соединение в SQL.
2. Жадная загрузка связи в ORM (один лишний запрос с `IN` или соединение).
3. Загрузить id, затем загрузить детей одним запросом, затем прикрепить их в памяти.

N+1 — проблема корректности для задержки и для использования пула. Каждый лишний запрос использует круговой путь. Под нагрузкой 1 + N становится застоем.

Не «исправляйте» N+1 открытием большего числа подключений. Исправьте форму запроса. Не предзагружайте всю базу, чтобы избежать N+1. Загружайте столбцы, которые нужны странице.

Считайте запросы в разработке. Если страница списка запускает один запрос на строку, вы нашли N+1.

## Миграции, сиды и фикстуры

Миграция — скрипт (или пара скриптов), который меняет схему. У каждой миграции есть номер версии или метка времени. Приложение или инструмент хранит, какие версии уже выполнены.

Вы не меняете продакшен-таблицы руками в незадокументированной сессии. Вы добавляете миграцию. Вы её ревьюите. Вы запускаете её в каждой среде в одном порядке.

Типичные операции в миграции:

- `CREATE TABLE` / `ALTER TABLE` / `DROP TABLE`
- создать или удалить индексы и ограничения
- заполнение данных, которое требует новая схема

```text
versions
  001_create_customers.sql
  002_create_orders.sql
  003_add_orders_status.sql
```

Скрипт «up» применяет изменение. Скрипт «down» обращает его, когда инструмент поддерживает безопасный откат. Не у каждого изменения есть безопасный откат. `DROP COLUMN`, который удалил данные, не восстанавливает эти значения.

Правила:

1. Одно логическое изменение на миграцию, когда можете.
2. Миграции должны быть повторяемы по порядку на пустой базе и в продакшене.
3. Не правьте миграцию, которая уже выполнилась в общих средах. Добавьте новую миграцию.
4. Сочетайте изменение схемы с изменением приложения. Расширяйте, мигрируйте, сжимайте, когда нужен нулевой простой (добавить столбец, выкатить код, затем позже удалить старый столбец).

Сид загружает известные данные в базу для разработки или демо. Фикстура — фиксированный набор строк для теста. Оба — данные, не схема.

```text
Development: migrations first, then seeds
Test:       migrations (or a test schema), then fixtures
Production: migrations only, unless you have a controlled reference-data job
```

Правила для сидов:

1. Сиды должны выполняться после миграций.
2. Сиды должны быть безопасны для запуска больше одного раза, или инструмент должен заменять данные задокументированным способом.
3. Не сидьте продакшен фейковыми пользователями, если это не намеренное, проверенное задание.
4. Не кладите реальные персональные данные из продакшена в сид разработки.

Фикстуры должны быть маленькими. Тест, который загружает полный дамп продакшена, медленный и неясный. Назовите факты, которые нужны тесту. Пример: один клиент, два заказа, один отменённый заказ.

Предпочитайте стабильные ключи в фикстурах (`customer_id = 1`), чтобы утверждения оставались читаемыми. Сбрасывайте данные фикстуры в начале теста или используйте транзакцию, которая откатывается.

Не используйте сид вместо миграции обязательных справочных строк, если эти строки нужны каждой среде. Обязательные справочные данные принадлежат миграции или контролируемому заданию данных. Необязательные демо-данные принадлежат сиду.

Не кладите специфичные для среды имена хостов в миграцию. Не запускайте разрушительный `DROP` в продакшене без резерва и ревью.

### Вопросы

#### Теоретические вопросы

1. Что записывает версия миграции и почему нельзя править миграцию, которая уже выполнилась в общей среде?
2. В чём разница между скриптом «up» и скриптом «down»?
3. В чём разница между сидом и фикстурой и в каком порядке запускают миграции и сиды?
4. Почему нельзя копировать продакшен-персональные данные в сид разработки?
5. Когда справочные данные принадлежат миграции вместо сида и что значит expand-then-contract для смены столбца?

#### Простые практические задания

1. Назовите инструмент миграций, который использует ваш язык или фреймворк, или соглашение SQL-файлов. Напишите последовательность из двух файлов: создать `customers`, затем добавить `email`.
2. Напишите сид из трёх строк `products` для учебной схемы. Напишите фикстуру одного клиента и двух заказов для теста «список заказов».
3. Перечислите три оператора, которые принадлежат миграции, и два, которые принадлежат сиду. Пометьте четыре файла в образце проекта как миграцию, сид, фикстуру или код приложения.
4. Напишите два правила из этого раздела, которые защищают продакшен. Напишите одну причину отказать в `DROP TABLE` в продакшен-миграции без резерва.

#### Средние практические задания

1. Запустите миграции на пустой базе. Подтвердите таблицу версий. Добавьте новую миграцию. Запустите снова. Попробуйте запустить ту же миграцию дважды. Напишите, как инструмент предотвращает двойное применение.
2. Запустите миграции и сид на одноразовой базе. Удалите базу. Повторите. Подтвердите, что процесс повторяем.
3. Напишите план expand-contract для переименования `name` в `display_name` в трёх выкладках. Отделите демо-пользователей от обязательных справочных строк (пример: статусы заказов). Положите каждое в верное место.

#### Сложные практические задания

1. Напишите стандарт миграций на одну страницу: именование, ревью, резерв и запрещённые правки. Включите один небезопасный пример. Практикуйте падающую миграцию (плохой SQL) на одноразовой базе. Запишите, как чините вперёд новой миграцией.
2. Спроектируйте сид, который идемпотентен (запуск дважды, одно конечное состояние). Реализуйте его через `MERGE` / upsert или правило очистить-и-вставить. Напишите политику данных на одну страницу: что разработчики могут сидить, что тесты могут загружать и как анонимизируете образец продакшена, если команде он нужен.

## Обзор темы

Эти вопросы не повторяют вопросы разделов выше. Они покрывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Как драйвер, пул и параметризованный SQL работают вместе на одном веб-запросе?
2. Когда выбирают сырой SQL вместо ORM, если на одной странице есть и N+1, и запрос отчёта?
3. Чем миграции, сиды и фикстуры отличаются по цели, среде и риску?
4. Какие сбои доступа из приложения выглядят как «СУБД медленная», но начинаются в клиенте?
5. Коллега конкатенирует имя таблицы и открывает новое подключение на строку. Какие факты вы используете в ответе?

#### Простые практические задания

1. Напишите шпаргалку: поля URI, правило возврата в пул, связывание параметров, ORM против SQL, форма N+1, порядок миграций, сид против фикстуры.
2. Подключитесь драйвером. Выполните один параметризованный `SELECT`. Верните подключение в пул или закройте его.
3. Добавьте миграцию, которая создаёт таблицу. Добавьте сид из двух строк. Запросите строки.
4. Посчитайте запросы для списка двух таблиц в журналах. Напишите число.

#### Средние практические задания

1. Постройте маленькую программу: пул из двух подключений, параметризованное соединение, без N+1, схема из миграций, данные из сида.
2. Сломайте программу инъецированной кавычкой в конкатенированном запросе (одноразовая база). Затем исправьте параметрами. Запишите оба исхода.
3. Напишите план миграции expand-contract плюс фикстуру, которая тестирует новый столбец.

#### Сложные практические задания

1. Просмотрите маленькое приложение (своё) против этой темы: секреты в URI, размер пула, инъекция, N+1, история миграций, безопасность сида. Напишите находки и исправления.
2. Добавьте ORM и сырой SQL-отчёт рядом. Захватите SQL, число запросов и рекомендацию на одну страницу для этого приложения.

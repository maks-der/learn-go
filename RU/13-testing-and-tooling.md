# 13. Тесты и инструменты

## Описание

Тесты Go живут рядом с кодом. Пакет `testing` и команда `go test` запускают тесты, бенчмарки, примеры и цели фаззинга. Покрытие, линтеры и `pprof` дополняют ежедневный набор инструментов.

Эта тема учит каждому инструменту как отдельному навыку. Завершите тему 1 до этой темы. Нужно знать `go test`, пакеты и модули. Тема 11 и тема 12 помогают, когда тест запускает `goroutine` или использует контекст.

Для каждого понятия используйте одно слово. Тестовая функция — не бенчмарк. Пример — не цель фаззинга. `fake` — не `mock`. `go generate` не выполняется, когда запускаете `go build`.

## Файлы `*_test.go`

Тестовый файл — файл Go, имя которого заканчивается на `_test.go`. Команда `go test` компилирует эти файлы вместе с тестируемым пакетом. Команда `go build` игнорирует их, когда собираете библиотеку или команду.

Положите тестовый файл в тот же каталог, что и пакет. Файл может использовать одно из двух имён пакета:

- `package foo` — тест внутренний. Файл может использовать неэкспортированные имена.
- `package foo_test` — тест внешний. Файл импортирует `foo` как клиент. Файл может использовать только экспортированные имена.

Используйте внешний тест, когда хотите тестировать открытый API. Используйте внешний тест, когда внутренний тест создал бы цикл импорта. Используйте внутренний тест, когда нужно проверить неэкспортированные помощники.

Правила для тестовых файлов:

- Имя файла должно заканчиваться на `_test.go`.
- Компилятор игнорирует тестовый файл во время `go build` нетестового пакета.
- Каталог с именем `testdata` не является пакетом Go для `go list`. Кладите фикстуры в `testdata`.
- Теги сборки на тестовых файлах работают так же, как на других файлах.

Не кладите производственный код в файл `_test.go`. Не кладите тесты в файл без суффикса `_test.go`. `go test` не запустит эти тесты.

`go test` компилирует пакет плюс тестовые файлы в тестовый двоичный файл. Затем запускает этот двоичный файл. `go test ./...` запускает тесты в каждом пакете под текущим каталогом.

## `TestXxx(t *testing.T)`

Тестовая функция имеет такую форму:

```go
func TestAdd(t *testing.T) {
    got := Add(1, 2)
    if got != 3 {
        t.Fatalf("Add(1, 2) = %d, want 3", got)
    }
}
```

Имя должно начинаться с `Test`. Следующая руна не должна быть строчной буквой. `Testadd` — не тест. `TestAdd` — тест. Единственный параметр — `*testing.T`.

`go test` запускает каждую функцию `TestXxx`. Тест падает, когда код вызывает `t.Fail`, `t.Error`, `t.Errorf`, `t.Fatal`, `t.Fatalf` или `t.FailNow`. Тест пропускается, когда код вызывает `t.Skip`, `t.Skipf` или `t.SkipNow`.

`t.Fatal` и `t.Fatalf` останавливают эту тестовую функцию. `t.Error` и `t.Errorf` записывают сбой и продолжают. Используйте `Fatal`, когда последующие строки небезопасны. Используйте `Error`, когда хотите больше проверок в той же функции.

Другие полезные методы:

- `t.Log` и `t.Logf` пишут журнал. `go test` показывает их с `-v` или когда тест падает.
- `t.Cleanup(fn)` запускает `fn` после теста (и после подтестов) в порядке последний вошёл — первый вышел.
- `t.TempDir()` создаёт временный каталог. Тест удаляет его в конце.
- `t.Setenv` задаёт переменную окружения для теста.
- `t.Parallel()` помечает тест как параллельный с другими параллельными тестами.
- Начиная с Go 1.24, `t.Context()` возвращает контекст, который отменяется, когда тест заканчивается. Начиная с Go 1.24, `t.Chdir` меняет рабочий каталог для теста.

Не вызывайте `t.Parallel`, если тест делит несинхронизированное состояние пакета с другими тестами. Запускайте `go test -race`, когда тесты идут параллельно.

Флаги `go test`, которые часто используете: `-v`, `-count=1` (отключить кэш результатов), `-run TestAdd`, `-timeout`, `-race`.

## Табличные тесты

Табличный тест хранит случаи в `slice`. Тест обходит `slice` и выполняет те же проверки.

```go
func TestAdd(t *testing.T) {
    tests := []struct {
        name string
        a, b int
        want int
    }{
        {name: "zeros", a: 0, b: 0, want: 0},
        {name: "positive", a: 2, b: 3, want: 5},
        {name: "negative", a: -1, b: 1, want: 0},
    }
    for _, tc := range tests {
        t.Run(tc.name, func(t *testing.T) {
            got := Add(tc.a, tc.b)
            if got != tc.want {
                t.Fatalf("Add(%d, %d) = %d, want %d", tc.a, tc.b, got, tc.want)
            }
        })
    }
}
```

У каждого случая есть `name`. Имя появляется в выводе `go test`. Используйте `t.Run`, чтобы можно было запустить один случай через `-run TestAdd/positive`.

Начиная с Go 1.22, у каждой итерации цикла свой `tc`. Замыкание может использовать `tc` без ручной копии. До Go 1.22 писали `tc := tc` внутри цикла.

Кладите неверные входы и случаи ошибок в ту же таблицу, когда API возвращает ошибку. Добавьте поле `wantErr`. Не прячьте случай в комментарии. Добавьте строку.

Держите структуру случая маленькой. Вынесите настройку, одинаковую для каждой строки, за цикл. Кладите уникальную настройку в строку.

Не генерируйте случайные строки как единственные тесты. Случайные строки принадлежат цели фаззинга. Таблица — список случаев, которые вы понимаете.

## Подтесты: `t.Run`

`t.Run` запускает подтест. Родительский тест ждёт подтест. Первый аргумент — имя. Второй аргумент — функция.

```go
func TestSplit(t *testing.T) {
    t.Run("empty", func(t *testing.T) {
        // ...
    })
    t.Run("comma", func(t *testing.T) {
        // ...
    })
}
```

Полное имя — `TestSplit/empty`. Пробелы в имени становятся подчёркиваниями в фильтре запуска. Держите имена короткими и уникальными.

`t.Run` возвращает `false`, когда подтест упал или родитель должен остановиться. Можно использовать возвращаемое значение. Большинство тестов его игнорируют.

Сбой в подтесте роняет родителя. `t.Fatalf` в подтесте останавливает этот подтест. Он не останавливает другие подтесты, которые родитель ещё запускает. Если нужно остановить родителя, проверьте возвращаемое значение `t.Run` или вызовите `t.FailNow` в родителе.

Можно вкладывать `t.Run`. Группируйте случаи по классу входа. Не вкладывайте без причины.

`t.Parallel` в подтесте запускает этот подтест параллельно с другими параллельными подтестами того же родителя. Родитель не заканчивается, пока эти подтесты не закончатся. Начиная с Go 1.22, переменные цикла безопасны в параллельных подтестах, которые замыкают `tc`.

Используйте подтесты для строк таблицы. Используйте подтесты для двух реализаций одного интерфейса. Используйте подтесты, когда настройка дорогая и хотите разделить её в родителе (осторожно с изменением).

## `t.Helper()`, `t.Fatalf`, `t.Error`

`t.Helper` помечает вызывающую функцию как помощник. Следующая строка сбоя в выводе `go test` — вызывающий, не помощник.

```go
func assertEq[T comparable](t *testing.T, got, want T) {
    t.Helper()
    if got != want {
        t.Fatalf("got %v, want %v", got, want)
    }
}
```

Вызывайте `t.Helper` в начале каждого помощника, который может упасть. Если опустите `t.Helper`, сбой указывает на файл помощника. Затем тратите время не там.

`t.Fatalf(format, args...)` пишет сообщение и останавливает тестовую функцию (или подтест). Это `Logf` плюс `FailNow`.

`t.Error(args...)` пишет сообщение и помечает тест как упавший. Тестовая функция продолжает. `t.Errorf` — форма с форматом.

Выбирайте так:

- Используйте `t.Fatalf`, когда тест не может продолжаться (`nil` указатель, настройка упала, неверный тип).
- Используйте `t.Error` или `t.Errorf`, когда поздние проверки всё ещё имеют смысл.
- Используйте помощник с `t.Helper`, когда одному и тому же проверке нужны больше одного теста.

Не вызывайте `panic` в тесте, чтобы сигнализировать сбой. Используйте `t.Fatal`. `panic` роняет тест, но вывод труднее читать.

`t.Fail` помечает сбой и продолжает без сообщения. `t.FailNow` останавливает без нового сообщения. Предпочитайте `Error` и `Fatal`, чтобы в выводе была причина.

`t.Fatal` не выполняет остаток функции. `defer` и `t.Cleanup` всё равно выполняются.

## Бенчмарки: `BenchmarkXxx`

Функция бенчмарка имеет такую форму:

```go
func BenchmarkAdd(b *testing.B) {
    for i := 0; i < b.N; i++ {
        Add(1, 2)
    }
}
```

Имя должно начинаться с `Benchmark`. Следующая руна не должна быть строчной буквой. Параметр — `*testing.B`.

`b.N` — число итераций. Пакет `testing` выбирает `N` так, чтобы бенчмарк шёл стабильное время. Нужно поместить проверяемую работу внутрь цикла.

Начиная с Go 1.24, можно писать `for b.Loop() { ... }`. `Loop` сообщает таймер более безопасным способом. В Go 1.22 и 1.23 используйте цикл `b.N`.

Запускайте бенчмарки:

```text
go test -bench=BenchmarkAdd -benchmem
go test -bench=. -count=5
```

`-bench` — регулярное выражение. `-benchmem` печатает выделения. `-count` повторяет бенчмарк.

Управление таймером:

- `b.ResetTimer()` после настройки.
- `b.StopTimer()` и `b.StartTimer()` вокруг кода, который не проверяете.
- `b.ReportAllocs()`, чтобы всегда сообщать выделения.

`b.Run` запускает подбенчмарк. `b.RunParallel` выполняет тело на нескольких `goroutine`. `b.SetBytes` сообщает пропускную способность.

Не используйте методы `testing.T` на `b`. У `B` есть `Error`, `Fatal`, `Helper` и `Cleanup`, которые соответствуют тестовым версиям.

Не дайте компилятору убрать работу. Присвойте результат переменной уровня пакета, если компилятор видит, что результат не используется, а функция простая. Читайте результаты бенчмарка осторожно. Микробенчмарк — не полная программа.

## Примеры: `ExampleXxx` (и комментарии `Output:`)

Пример — функция, имя которой начинается с `Example`. Примеры появляются в документации на pkg.go.dev и в `go doc`. `go test` компилирует примеры. `go test` запускает пример, когда у функции есть комментарий вывода.

```go
func ExampleAdd() {
    fmt.Println(Add(1, 2))
    // Output:
    // 3
}
```

Комментарий должен использовать точную форму. Текст после `Output:` сравнивается со стандартным выводом примера. Ведущие пробелы в комментарии следуют правилам `go test`. Держите вывод простым.

`// Unordered output:` сравнивает строки без порядка.

Правила имён:

- `Example()` — пример пакета.
- `ExampleAdd` документирует функцию `Add`.
- `ExampleT` документирует тип `T`.
- `ExampleT_M` документирует метод `M` у `T`.
- `ExampleAdd_second` — второй пример для `Add`. Суффикс начинается со строчной буквы.

Если опустите `Output:` и `Unordered output:`, `go test` компилирует пример и не выполняет его как тест.

Не кладите утверждения с `testing.T` в пример. Вывод — это проверка. Печатайте через `fmt`. Держите пример коротким. Читатель его копирует.

Примеры живут в файлах `_test.go`. Можно поместить их в тот же файл, что и тесты.

## Фаззинг: `FuzzXxx`

Цель фаззинга имеет такую форму:

```go
func FuzzParse(f *testing.F) {
    f.Add("hello")
    f.Add("")
    f.Fuzz(func(t *testing.T, s string) {
        _, err := Parse(s)
        if err != nil {
            return
        }
    })
}
```

Имя должно начинаться с `Fuzz`. Следующая руна не должна быть строчной буквой. `f.Add` загружает семенные значения. `f.Fuzz` регистрирует функцию, которую вызывает фаззер. Функция фаззинга принимает `*testing.T` и аргументы. Допустимые типы аргументов включают `string`, `[]byte`, фиксированные целые, `bool`, `rune`, `float32` и `float64`. Проверьте текущую документацию `testing` для полного списка.

`go test` без `-fuzz` запускает только семенной корпус. Этот прогон похож на таблицу семян.

Запускайте фаззер:

```text
go test -fuzz=FuzzParse -fuzztime=10s
```

Фаззер пишет интересные входы в `testdata/fuzz`. Падающий вход сохраняется. `go test` без `-fuzz` воспроизводит этот вход. Фиксируйте полезные падающие случаи. Исправьте код. Оставьте случай, если это верный регрессионный тест.

Пишите функцию фаззинга, которая ищет свойство. Пример: разбор, затем формат возвращает те же байты. Не только игнорируйте каждую ошибку. Ошибка может быть верной. `panic` или неверный круговой путь — ошибка.

Не запускайте фаззинг функции, которая удаляет файлы или вызывает сеть. Держите цель в памяти. Используйте `t.Skip` для входов вне области, когда это верное правило.

Флаг `-fuzz` принимает один пакет. Не передавайте `./...` с `-fuzz`.

#### Теоретические вопросы

1. В чём разница между `f.Add` и функцией, которую регистрирует `f.Fuzz`?

#### Простые практические задания

## Покрытие тестами: `go test -cover`

Покрытие измеряет, какие операторы выполнили тесты.

```text
go test -cover
go test -coverprofile=cover.out
go tool cover -func=cover.out
go tool cover -html=cover.out
```

`-cover` печатает процент для пакета. `-coverprofile` пишет файл. `go tool cover -func` печатает функции. `go tool cover -html` открывает страницу, которая раскрашивает выполненные строки.

Режимы покрытия:

- `set` — оператор выполнился или нет.
- `count` — сколько раз оператор выполнился.
- `atomic` — как `count`, безопасен для конкурентных тестов. Используйте `atomic` с `-race`.

```text
go test -covermode=atomic -coverprofile=cover.out
```

`-coverpkg` задаёт, какие пакеты считаются. Используйте его, когда тест в одном пакете упражняет другой пакет. Покрытие по умолчанию — тестируемый пакет.

Высокий процент не значит, что тесты хорошие. Покрытие не проверяет, что утверждение существует. Тест может выполнить строку и не проверить результат.

Нацельте покрытие на пакеты, которые меняете. Не гонитесь за 100 процентами, когда последние строки — `panic("unreachable")` или сгенерированный код. Исключайте сгенерированные файлы в инструменте отчётов, когда команда согласна.

`go test -cover` достаточно для локальной проверки. Храните профиль в непрерывной интеграции, когда команда хочет отчёт. Не роняйте сборку из-за небольшого падения без правила команды.

## `mock` против `fake` против `stub`; интерфейсы для тестируемости

Тестам нужно заменить зависимость. Три обычные замены — разные инструменты.

`stub` возвращает фиксированный результат. `stub` не реализует настоящее поведение. Пример: `Get` всегда возвращает одного и того же пользователя.

`fake` — рабочая маленькая реализация. Пример: `map`, которая хранит пользователей в памяти. `fake` следует тем же правилам, что и настоящее хранилище, для случаев, которые важны.

`mock` записывает вызовы и проверяет ожидания. Пример: тест падает, если `Save` не вызвали с этим ID. `mock` часто генерируют. Тест может стать списком вызовов вместо списка поведений.

Предпочитайте `fake`, когда зависимость — хранилище, часы или очередь. Предпочитайте `stub`, когда результат — одно готовое значение. Используйте `mock`, когда сам вызов — поведение (отправитель почты должен быть вызван один раз). Не мокайте каждый интерфейс. Тогда тест копирует граф вызовов производства.

Проектируйте производственный код с интерфейсами на границе:

```go
type UserStore interface {
    Find(ctx context.Context, id string) (User, error)
}

type Service struct {
    Store UserStore
}
```

Производственная функция `main` внедряет настоящее хранилище. Тест внедряет `fake`-хранилище. Тип `Service` не импортирует пакет базы данных.

Держите интерфейсы маленькими. Определяйте интерфейс в пакете, который его использует, не в пакете, который его реализует, когда такое разделение помогает. Это правило «принимайте интерфейсы, возвращайте структуры» из темы 7.

Не добавляйте интерфейс только для `mock`, когда хватает `fake` конкретного типа. Не используйте пустой интерфейс для `fake`.

## `httptest` для HTTP-обработчиков

Пакет `net/http/httptest` тестирует HTTP-серверы и клиенты без настоящего сетевого порта в простом случае и с локальным сервером, когда он нужен.

Модульно тестируйте обработчик запросом и записывающим устройством:

```go
func TestHealth(t *testing.T) {
    req := httptest.NewRequest(http.MethodGet, "/health", nil)
    rec := httptest.NewRecorder()
    handler.ServeHTTP(rec, req)
    if rec.Code != http.StatusOK {
        t.Fatalf("status = %d, want %d", rec.Code, http.StatusOK)
    }
}
```

`httptest.NewRequest` строит входящий запрос. Предпочитайте `httptest.NewRequestWithContext`, когда обработчик использует `r.Context()`. `httptest.ResponseRecorder` реализует `http.ResponseWriter`. Читайте `rec.Code`, `rec.Body` и `rec.Header()`.

Интеграционно тестируйте с сервером:

```go
srv := httptest.NewServer(handler)
defer srv.Close()
resp, err := srv.Client().Get(srv.URL + "/health")
```

`NewServer` слушает на локальной машине. `srv.URL` — базовый URL. Нужно вызвать `Close`. `NewTLSServer` запускает TLS. `NewUnstartedServer` позволяет задать поля до `Start`.

Начиная с Go 1.22, можно зарегистрировать `GET /health` на `http.NewServeMux` и протестировать этот шаблон. Используйте `req := httptest.NewRequest(http.MethodGet, "/health", nil)` и `mux.ServeHTTP`.

Тесты отмены: создайте контекст, передайте его через `NewRequestWithContext`, отмените его и проверьте, что обработчик возвращает управление. Для `NewServer` используйте клиентский запрос с `NewRequestWithContext` и `client.Do`.

Не слушайте на фиксированном порту в тестах, когда `httptest` может выбрать порт. Не утекайте сервер. Используйте `t.Cleanup(srv.Close)`.

## `go generate`

`go generate` запускает команды, которые пишете в специальных комментариях. Компилятор не запускает эти команды. Вы запускаете `go generate` намеренно.

```go
//go:generate stringer -type=Status
```

Комментарий должен начинаться в начале строки. Форма — `//go:generate` плюс команда. Команда выполняется в каталоге пакета.

```text
go generate .
go generate ./...
```

Обычные использования:

- `stringer` для методов `String` на целочисленных типах.
- Код для protocol buffers.
- Генератор `mock`, когда команда принимает сгенерированные `mock`.
- Помощники, связанные с встраиванием, когда `embed` недостаточно.

Сгенерированный файл — обычный исходник Go. Фиксируйте файл, если команда хочет сборки без генератора. Или генерируйте в непрерывной интеграции, если команда хочет такое правило. Выберите одно правило.

Не используйте `go generate` для самой сборки. `go build` должен работать после того, как файлы существуют. Не прячьте обязательные шаги только в комментарии generate без README или скрипта.

`go generate` не запускает тесты. Он не форматирует файлы, если команда этого не делает. Запускайте `go fmt` на сгенерированных файлах, если генератор их не форматирует.

В команде доступны переменные вроде `$GOFILE` и `$GOPACKAGE`. Прочитайте `go help generate` для списка.

## Линтеры: `staticcheck`, `golangci-lint`

Линтер сообщает проблемы, которые компилятор принимает. `go vet` — первый линтер. Он поставляется с Go. Запускайте `go vet ./...` на каждое изменение.

`staticcheck` — широко используемый линтер. Он находит мёртвый код, неверное использование `errors.Is`, неиспользуемые значения и многие другие проблемы. Проверки имеют имена вроде `SA4006`. Установите официальный двоичный файл `staticcheck`. Запускайте:

```text
staticcheck ./...
```

`golangci-lint` запускает много линтеров одной командой. Он может запускать `govet`, `staticcheck`, `gofmt` и другие. Установите официальный выпуск. Запускайте:

```text
golangci-lint run
```

Файл конфигурации (`.golangci.yml` или текущее имя в документации `golangci-lint`) выбирает линтеры. Начните с небольшого набора. Включите `staticcheck` и `govet`. Добавляйте больше линтеров, когда команда согласна.

Правила для новичка:

- Сначала исправьте `go vet`.
- Затем запустите `staticcheck` или `golangci-lint`.
- Не отключайте проверку без причины.
- Не оформляйте спор о конфигурации. Официальный формат Go остаётся `gofmt`.

Версия `golangci-lint` и версия Go должны работать вместе. Прочитайте страницу установки для вашей версии Go.

Линтеры — не тесты. Чистый прогон линтера не доказывает поведение. Тесты доказывают поведение. Линтеры снижают ошибки.

Непрерывная интеграция должна запускать `go test` и хотя бы один линтер. Тема 1 уже использует `go vet`. Эта тема добавляет `staticcheck` и `golangci-lint`.

## Профилирование: `pprof` (CPU, куча, горутины)

`pprof` записывает, где программа тратит время и память. Пакет `runtime/pprof` пишет профили. Пакет `net/http/pprof` отдаёт профили по HTTP. Команда `go tool pprof` читает профиль.

Профиль CPU. Сэмплер отмечает стек вызовов с частотой. Используйте его, когда программа медленная.

Профиль кучи. Профиль показывает выделения. Используйте его, когда растёт память или когда высока частота выделений.

Профиль `goroutine`. Профиль перечисляет `goroutine` и их стеки. Используйте его, когда подозреваете утечку или взаимную блокировку, которая не глобальная.

Для тестов и бенчмарков:

```text
go test -cpuprofile=cpu.out -bench=BenchmarkAdd
go test -memprofile=mem.out -bench=BenchmarkAdd
go tool pprof cpu.out
```

Для сервера импортируйте обработчики pprof:

```go
import _ "net/http/pprof"
```

Зарегистрируйте их на mux, которым управляете, или используйте `http.DefaultServeMux` на порту отладки. Пути выглядят как `/debug/pprof/profile` (CPU), `/debug/pprof/heap` и `/debug/pprof/goroutine`. Не открывайте этот порт в публичной сети без защиты.

```text
go tool pprof http://127.0.0.1:6060/debug/pprof/profile?seconds=30
go tool pprof http://127.0.0.1:6060/debug/pprof/heap
go tool pprof http://127.0.0.1:6060/debug/pprof/goroutine
```

`go tool pprof` может открыть локальную страницу с `-http`. Используйте `top`, `list` и `web` в приглашении pprof.

Также можно написать профиль из кода через `pprof.StartCPUProfile` и `pprof.WriteHeapProfile`. Останавливайте профиль CPU через `pprof.StopCPUProfile`.

Читайте время CPU как подсказку, не как доказательство. Измеряйте до изменения кода. Измеряйте после. Тема 15 разбирает выделения и анализ побега.

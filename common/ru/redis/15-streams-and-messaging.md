# 15. Потоки и обмен сообщениями

## Описание

Поток Redis — журнал записей только для добавления. Эта тема покрывает id записей, группы потребителей, отложенные записи, когда выбирать Kafka вместо и почему Pub/Sub может терять сообщения.

Сначала завершите тему 7 (введение в потоки) и тему 14 (Pub/Sub против потоков). Тема 7 показала `XADD`, `XREAD` и первую группу. Эта тема — модель эксплуатации.

Используйте один термин для каждого понятия. Запись — один элемент в потоке. Id — адрес записи (`milliseconds-sequence`). Группа потребителей — именованный курсор плюс список отложенных. Потребитель — имя внутри группы. PEL — список отложенных записей. `XACK` убирает запись из PEL. At-most-once значит доставка может потеряться. At-least-once значит доставка может случиться дважды, если не сделать работу идемпотентной.

## Записи потока и ID

`XADD key id field value [field value ...]` добавляет запись. Обычный id — `*`. Redis создаёт id из времени и порядкового номера.

```text
XADD lab:orders * item book qty 1
```

Ответ — id вроде `1726248000000-0`. Часть до `-` — миллисекунды. Часть после `-` — последовательность в этой миллисекунде.

Можно передать явный id. Новый id должен быть больше последнего id в потоке. Явные id — для импорта и тестов. Предпочитайте `*` в новых производителях.

Особые id при чтении:

- `0-0` или `-` — с начала (зависит от команды)
- `+` — конец (в `XRANGE`)
- `$` — только новые записи после текущего конца (`XREAD`)
- `>` — новые записи для группы (`XREADGROUP`)

```text
XRANGE lab:orders - +
XLEN lab:orders
XREAD COUNT 10 STREAMS lab:orders 0-0
```

`XREAD BLOCK milliseconds STREAMS lab:orders $` ждёт новую запись. Соединение заблокировано. `INFO clients` может показать заблокированных клиентов (тема 19).

Каждое поле — строка. Кладите JSON в поле, если нужен документ. Держите поле `type` для маршрутизации.

Безграничный поток заполняет ОЗУ. Используйте `MAXLEN` на `XADD` или `XTRIM`, чтобы ограничить длину. Приблизительный `MAXLEN` (`~`) быстрее. Можно потерять более старые записи. Это политика, а не сюрприз.

## Группы потребителей, `XREADGROUP`, `XACK`

Группа потребителей позволяет многим работникам делить поток. Каждая запись идёт одному потребителю в группе (конкурирующие потребители). Redis хранит последний доставленный id для группы и PEL.

Создайте группу:

```text
XGROUP CREATE lab:orders grpA 0 MKSTREAM
```

`0` значит «начать с начала». `$` значит «начинать только с новых записей». `MKSTREAM` создаёт поток, если его нет.

Читайте как потребитель:

```text
XREADGROUP GROUP grpA worker1 COUNT 1 STREAMS lab:orders >
```

`>` значит «дай записи, которые группа ещё не доставила». Имя потребителя — `worker1`. Два работника используют два имени.

После успеха подтвердите:

```text
XACK lab:orders grpA 1726248000000-0
```

`XACK` убирает запись из PEL. Запись может остаться в потоке до обрезки. `XACK` — не `XDEL`.

Если процесс умрёт до `XACK`, запись остаётся отложенной. Другой работник может её заявить (следующий раздел).

`XINFO GROUPS lab:orders` и `XINFO CONSUMERS lab:orders grpA` показывают поля в стиле лага и счёты отложенных.

`XGROUP DESTROY` и `XGROUP DELCONSUMER` — эксплуатационные команды. Используйте их в лаборатории или в runbook, не на горячем пути.

Один поток может иметь много групп. У каждой группы свой курсор. Одна запись может быть доставлена каждой группе. Это fan-out через группы и конкурирующие потребители внутри группы.

## Отложенные записи (`XPENDING`, `XCLAIM`)

PEL держит записи, которые группа доставила и которые ни один потребитель не подтвердил.

```text
XPENDING lab:orders grpA
XPENDING lab:orders grpA - + 10
XPENDING lab:orders grpA - + 10 worker1
```

Короткая форма возвращает счёт и диапазон простоя. Длинная форма перечисляет id, потребителя, время простоя и счёт доставок.

Мёртвый потребитель оставляет отложенные записи. Другой потребитель заявляет их:

```text
XCLAIM lab:orders grpA worker2 60000 1726248000000-0
```

Число `60000` — минимальное время простоя в миллисекундах. Redis не заявляет запись моложе этого времени простоя (если не форсируете). Это избегает кражи у медленного, но живого работника.

`XAUTOCLAIM` (Redis 6.2+) обходит PEL и заявляет пакет. Предпочитайте в новых работниках.

После `XCLAIM` новый потребитель владеет записями PEL. Обработайте их. Затем `XACK`.

Счёт доставок растёт, когда Redis доставляет снова. Ядовитое сообщение (всегда падает) может зациклиться. После N доставок пишите ключ мёртвых писем или журнал, затем `XACK`, чтобы PEL не рос вечно.

`XPENDING` — проверка здоровья группы. Растущий PEL значит потребители медленные, упали или не делают `XACK`.

Не делайте `XACK` до того, как побочный эффект долговечен, если нужна обработка at-least-once. Не пропускайте `XACK`, если уже завершили побочный эффект, иначе PEL растёт и другой работник сделает работу снова. Сделайте побочный эффект идемпотентным (тема 14).

## Когда использовать Redis Streams против Kafka

Redis Streams и Apache Kafka оба журналы. Они не один продукт.

Redis Streams подходят, когда:

- Вы уже запускаете Redis
- Журнал достаточно мал для ОЗУ (или жёстко обрезаете)
- Удержание короткое
- Группы потребителей простые
- Эксплуатационная команда — команда Redis
- Нужна низкая задержка на одном кластере, который уже знаете

Kafka подходит, когда:

- Удержание большое (часы-дни высокого объёма на диске)
- Много независимых групп потребителей читают длинный журнал
- Нужен большой кластер брокеров, разделы и экосистема (Connect, реестр схем)
- Повтор огромной истории — обычная операция
- Изоляция от кэш-Redis обязательна (тема 21)

Redis держит данные потока в памяти (плюс персистентность, если включите). Многодневный пожарный шланг событий заполнит Redis. Kafka пишет журнал на диск и масштабирует разделы по брокерам.

Смещения потребителей Kafka живут в Kafka. Состояние группы Redis живёт в Redis. Режимы отказа следуют остальной системе (переключение Redis против ISR реплик Kafka).

Можно использовать оба: Redis для кэша и коротких очередей работы, Kafka для корпоративной шины событий.

Не выбирайте Streams только потому, что имена команд короче. Измеряйте объём, удержание и кто будет эксплуатировать систему.

## Природа Pub/Sub at-most-once

Тема 14 показала `PUBLISH` и `SUBSCRIBE`. Этот раздел фиксирует слово доставки.

At-most-once: Redis пытается отправить сообщение текущим подписчикам. Если подписчик отключён, медленный или ещё не подписан, этот подписчик не получает более поздний повтор от Redis. Redis не хранит сообщение.

Медленные подписчики: Redis может отключить клиента, который не читает достаточно быстро (`client-output-buffer-limit` для pubsub). Этот клиент теряет сообщения.

`SUBSCRIBE` после `PUBLISH` не получает старое сообщение.

Нет `ACK`. Издатель не знает, что данный подписчик обработал полезный груз.

Используйте Pub/Sub для подсказок. Пример: «товар 1001 изменился». Подписчик делает `DEL` ключа кэша или перезагружает флаги. Если подсказка потеряна, TTL всё ещё чинит кэш.

Не используйте Pub/Sub для «списать эту карту» или «отправить это письмо один раз». Используйте поток (или Kafka) и идемпотентных работников.

Pub/Sub Cluster всё ещё не добавляет журнал. Шина кластера разносит по узлам. Доставка подписчику остаётся at-most-once.

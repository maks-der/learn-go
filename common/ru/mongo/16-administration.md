# 16. Администрирование

## Описание

Эта тема показывает, как вести сервер MongoDB. Вы настраиваете `mongod`. Изучаете движок хранения **WiredTiger**. Изучаете **журналирование**. Делаете **резервные копии** и практикуете **восстановление**. Узнаёте, когда помогает **compact**. Планируете **обновления основных версий**. Параллельно завершите репликацию и основы безопасности. Не запускайте команды администрирования на общем кластере без роли и окна изменений.

Используйте один термин для каждого понятия. **`mongod`** — процесс базы. **WiredTiger** — движок хранения по умолчанию. **Журнал** — журнал упреждающей записи, который WiredTiger использует для восстановления после сбоя. **Учение восстановления** — практическое восстановление, которое засекаете и проверяете.

Администрирование — операционная работа. Разработчик приложения всё равно должен знать риск резервной копии и обновления.

## Конфигурация `mongod`

`mongod` читает файл конфигурации YAML. Путь по умолчанию зависит от операционной системы. Можно также передавать флаги. Предпочитайте файл для всего, что должно пережить перезапуск.

Частые настройки (имена — примеры; читайте свою версию):

- `storage.dbPath` — файлы данных
- `systemLog.path` — файл журнала
- `net.port` — порт прослушивания (`27017` по умолчанию)
- `net.bindIp` — интерфейсы
- `replication.replSetName` — имя replica set
- `security.authorization` — доступ пользователей включён или выключен
- `processManagement.fork` — режим демона на Unix (когда используете)

Форма примера:

```yaml
storage:
  dbPath: /var/lib/mongo
systemLog:
  destination: file
  path: /var/log/mongodb/mongod.log
net:
  port: 27017
  bindIp: 127.0.0.1
```

Запуск:

```text
mongod --config /etc/mongod.conf
```

`mongosh` — клиент. `mongod` — сервер. Не путайте два процесса.

В Windows MongoDB часто работает как служба. В Docker те же идеи задают флаги или файл env. Atlas скрывает `mongod.conf`. Эквивалентные идеи задаёте в UI Atlas (тариф кластера, список IP, резервная копия).

Проверяйте изменение на тестовом хосте. Неверный `dbPath` или `bindIp` может запустить пустой экземпляр или открыть порт.

Не включайте публичный `bindIp` без аутентификации и TLS.

Храните конфигурацию в контроле версий без секретов. Ключи и пароли кладите в хранилище секретов.

## Движок хранения: WiredTiger

**WiredTiger** — движок хранения по умолчанию. Он хранит документы и индексы на диске. Использует кэш в ОЗУ. Поддерживает конкурентность на уровне документа. Два обновления двух документов могут идти одновременно.

WiredTiger сжимает данные. Сжатие уменьшает диск. Сжатие использует CPU. Значение по умолчанию подходит большинству учебных систем.

У каждой коллекции и каждого индекса могут быть опции WiredTiger. В начале их редко меняют.

WiredTiger — не MMAPv1. MMAPv1 ушёл из текущего MongoDB. Старые посты блогов о выравнивании записей и блокировках на уровне коллекции не относятся к WiredTiger.

`db.serverStatus().wiredTiger` показывает кэш и другие счётчики. Atlas показывает графики хранения.

Контрольные точки пишут согласованный снимок в файлы данных. Между контрольными точками журнал держит недавние записи. Следующий раздел покрывает журнал.

Не удаляйте файлы под `dbPath`, чтобы «освободить место», пока работает `mongod`.

Не смешивайте файлы данных двух движков или двух основных версий без официальной процедуры обновления.

Если в старом обучении видите «storage engine», подтвердите, что страница про WiredTiger и вашу версию.

## Журналирование

**Журналирование** пишет задуманные изменения в журнал до того, как (или как часть того, как) сделать их прочными. После сбоя WiredTiger воспроизводит журнал и возвращается к согласованному состоянию.

Журналирование включено по умолчанию для WiredTiger. Не выключайте его на системе, которая вам важна.

Write concern `j: true` ждёт, пока запись будет в журнале (и следует правилам этого concern). `w: "majority"` взаимодействует с журналом и подтверждением реплик. Снова прочитайте страницу write-concern с журналированием в уме.

Журнал живёт под `dbPath`. Это не пользовательская резервная копия. Нельзя отправить только журнал и игнорировать файлы данных.

Потеря питания с включённым журналированием не портит метаданные WiredTiger, если диск соблюдает сброс. Дешёвые USB-диски и некоторые виртуальные диски врут о сбросе. Используйте хранилище, безопасное для баз.

Atlas ведёт журналирование. Вы всё равно выбираете write concern.

Не отключайте журнал, чтобы «ускориться» в продакшене.

Не копируйте файлы данных для резервной копии, пока идут записи, если не используете поддерживаемый метод снимка (следующие разделы).

## Резервная копия: `mongodump`, снимки, резервная копия Atlas

**Резервная копия** — копия, которую можно восстановить. Secondary — не резервная копия. Delayed член — не полная резервная копия.

Частые методы:

**`mongodump` / `mongorestore`.** Логический экспорт BSON. Хорош для малых данных и выбранных коллекций. Медленный и тяжёлый на больших кластерах. Можно дампить с hidden secondary.

**Снимки файловой системы или тома.** Снять диск (или облачный том) согласованным методом. Для самоуправляемых replica set руководство описывает снимок плюс журнал или снимок на secondary с процедурами сброса. У облачных дисков (EBS, Azure disks, GCP disks) есть продукты снимков.

**Резервная копия Atlas.** Atlas предлагает облачные снимки и на некоторых тарифах более частые копии и восстановление на точку во времени. Используйте резервную копию Atlas для кластеров Atlas, если нет письменного исключения.

Выберите метод, который соответствует размеру и RPO (сколько данных можно потерять). Ночной `mongodump` 2 TB часто неверный инструмент.

Шифруйте резервные копии. Контролируйте, кто может их скачать. В копии все данные.

Тестируйте копию. Копия, которую никогда не восстанавливали, — надежда, не план. Следующий раздел — учение.

Не запускайте `mongodump` против primary на пике без плана. Предпочитайте hidden secondary.

Не копируйте `dbPath` через `cp` или zip, пока `mongod` пишет, если официальная процедура не разрешает именно этот метод.

## Учения восстановления

**Учение восстановления** — практическое восстановление. Восстанавливаете на безопасную цель. Измеряете время. Проверяете данные. Записываете, что упало.

Учение отвечает:

- Сколько восстанавливать (RTO)
- У кого пароли и роли
- Полная ли копия
- Могут ли приложения указать на восстановленные данные

Шаги по духу:

1. Выбрать копию (dump, снимок или снимок Atlas).
2. Восстановить на новый кластер или новое имя базы. Не перезаписывать продакшен на первом учении.
3. Запустить проверки: счета документов, пример find, дымовой тест приложения.
4. Записать часы и проблемы.
5. Повторять по расписанию (например каждые 90 дней).

Atlas: при учёбе используйте восстановление на новый кластер. Производственное восстановление на точку во времени — именованная процедура. Практикуйте её в непромышленном проекте.

`mongorestore` может удалить коллекции, если передать флаги drop. Читайте флаги. Неверное восстановление может удалить данные.

После восстановления идентичность replica set и учётные данные пользователей могут удивить. Следуйте руководству по восстановлению в replica set.

Не ждите первого настоящего инцидента, чтобы выучить UI.

Не храните единственные инструкции восстановления в голове одного человека.

## Compact / осведомлённость о уплотнении

WiredTiger может оставлять свободное место внутри файлов после удалений. Файл на диске не всегда сжимается. **Compact** — операция, которая переписывает данные, чтобы отдать место файловой системе (с лимитами и поведением, зависящим от версии).

```javascript
db.runCommand({ compact: "orders" })
```

Compact может занять много времени. Compact использует лишний диск, пока работает. Compact может влиять на задержку. Текущие версии улучшили compact, но это всё ещё событие администрирования, не еженедельная привычка.

Осведомлённость:

- Удаления не всегда возвращают диск ОС
- Удалите коллекцию, если можете её заменить (это возвращает место)
- Удаления TTL всё ещё могут нуждаться в compact или drop-and-recreate в некоторых случаях, если файлы остаются большими
- Графики диска Atlas могут показывать used vs allocated

Не запускайте compact на primary на пике. Предпочитайте окно обслуживания. На replica set некоторые команды сначала уплотняют secondary. Читайте текущую процедуру.

Не уплотняйте, чтобы починить плохую модель (неограниченные массивы, огромные документы). Чините модель.

`compact` — не `repairDatabase`. Старые советы о repair могут быть вредны. Используйте официальные страницы своей версии.

Atlas может ограничить или скрыть compact. Идея всё равно нужна, когда диск не падает после большого удаления.

## Обновления основных версий

**Основная версия** — первое число (например 6 на 7 или 7 на 8). MongoDB поддерживает путь обновления. Не перепрыгивайте неподдерживаемые разрывы. Читайте **Upgrade** для вашей from-версии и to-версии.

Типичные идеи:

- Сначала обновить двоичные файлы на secondary, затем primary (катящееся)
- Задавать **feature compatibility version** (`setFeatureCompatibilityVersion`) только когда документы так говорят
- Читать совместимость драйверов и Atlas
- Тестировать на копии данных
- Читать устаревшие команды и удалённые опции

Atlas: версию выбираете в UI. Atlas всё равно нуждается в окне изменений и тесте приложения. Читайте заметки обновления Atlas.

Community Server: скачайте новые пакеты. Следуйте странице катящегося обновления replica set. Не обновляйте только primary первым.

Драйверы: старый драйвер может упасть на новом сервере. Читайте матрицу совместимости.

Feature compatibility version (FCV) управляет, какие новые возможности на диске включены. Откат может быть трудным или невозможным после включения новых возможностей FCV. Не задавайте FCV в продакшене в тот же день, что обновление двоичных файлов, если процедура не говорит, что должны.

Ведите заметки: предыдущая версия, новая версия, FCV, дата, кто, ссылка на процедуру.

Не обновляйте продакшен в пятницу без команды и плана отката, который руководство ещё разрешает.

### Вопросы

#### Теоретические вопросы

1. Что такое основная версия в MongoDB?
2. Почему secondary обновляют до primary?
3. Что такое feature compatibility version?
4. Почему драйвер может упасть после обновления сервера?
5. Почему откат может упасть после смены FCV?

#### Простые практические задания

1. Запишите основную версию сервера (`db.version()`).
2. Откройте страницу обновления следующей основной версии. Запишите URL.
3. Откройте матрицу совместимости драйвера. Запишите, указана ли основная версия вашего драйвера.
4. Составьте таблицу: шаг, почему. Добавьте резервную копию, обновить secondary, обновить primary, FCV.

#### Средние практические задания

1. Прочитайте удалённые возможности между вашей версией и следующей. Запишите два пункта, которые могли бы сломать приложение.
2. Напишите план теста: CRUD, построение индекса, транзакция, change stream после обновления.
3. Если используете Atlas, запишите путь UI, чтобы запланировать смену версии. Не применяйте её на общем проекте.

#### Сложные практические задания

1. Выполните обновление основной версии на локальном replica set в Docker. Запишите команды, FCV и одну неудачную запись, если была.
2. Напишите стандарт обновления команды: окно заморозки, канареечное приложение, лимиты отката, кто задаёт FCV.

## Обзор темы

Эти вопросы не повторяют вопросы из разделов выше. Они охватывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Как конфигурация `mongod`, WiredTiger и журнал работают вместе на одной подтверждённой записи?
2. Когда выбирать `mongodump`, снимок или резервную копию Atlas для одного размера данных?
3. Почему учения восстановления и compact оба нуждаются в окне обслуживания, но решают разные задачи?
4. Как обновление основной версии меняет риск, если резервных копий и FCV нет в плане?
5. Коллега отключает журнал, копирует `dbPath` zip во время записей и запускает compact на primary в полдень. Какими фактами вы ответите на ревью?

#### Простые практические задания

1. Напишите шпаргалку: ключи конфигурации, WiredTiger, журнал, dump vs снимок vs Atlas, учение, compact, катящееся обновление, FCV.
2. Запишите среду: Community, Docker или Atlas, версия, метод резервной копии, дата последнего учения или «никогда».
3. Нарисуйте восстановление после сбоя: запись, журнал, контрольная точка, перезапуск, воспроизведение.
4. Перечислите пять действий администрирования, которые нельзя запускать в продакшене без тикета.

#### Средние практические задания

1. Запустите одно учение dump/restore на лабораторной базе. Заполните шаблон отчёта из раздела учений.
2. Напишите страницу операционного runbook: перезапуск `mongod`, где живут логи, как увидеть здоровье реплик, у кого админ Atlas.
3. Сравните диск `storageSize` после большого удаления и после drop тестовой коллекции. Запишите урок для compact.

#### Сложные практические задания

1. Подготовьте стандарт администрирования: базовая конфигурация, RPO/RTO резервной копии, календарь учений, правила compact, путь обновления, разделение Atlas vs самоуправление.
2. Попрактикуйте катящийся перезапуск лабораторного набора из трёх членов. Подтвердите отсутствие потери данных и запишите write concern, который использовали во время перезапуска.

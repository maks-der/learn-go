# 8. Хранение и ретеншн

## Описание

Kafka хранит каждую партицию как журнал на диске. Журнал — последовательность файлов сегментов. Правила ретеншна удаляют старые данные. Компакция хранит последнее значение на ключ. Томбстоуны помечают ключ как удалённый.

Эта тема покрывает сегменты журнала, ретеншн по времени и по размеру, компакцию, compact-plus-delete, томбстоуны и `log.dirs`. Завершите эту тему после темы 2. Тема 9 покрывает копии этих данных между брокерами.

Используйте один термин для каждого понятия. Сегмент — один файл (плюс индексные файлы) в журнале партиции. Ретеншн — правило, которое удаляет старые записи. Компакция — правило, которое хранит последнюю запись на ключ. Томбстоун — запись со значением null. Используйте KRaft для метаданных. KRaft не заменяет журналы партиций. Данные партиций по-прежнему живут в `log.dirs`.

## Сегменты журнала

Журнал партиции — не один бесконечный файл. Kafka делит журнал на сегменты. Активный сегмент принимает новые добавления. Когда активный сегмент достигает предела размера или времени, Kafka закрывает его и начинает новый активный сегмент.

У каждого сегмента есть базовый офсет. Имя файла использует этот офсет. Kafka также пишет индексные файлы. Индекс офсетов отображает офсет на позицию в файле `.log`. Индекс времени отображает метку времени на офсет. Эти файлы не правят вручную.

Ретеншн и компакция работают на закрытых сегментах. Активный сегмент не кандидат на удаление тем же способом. Очень длинные активные сегменты задерживают очистку. Конфигурация вроде `log.segment.bytes` и `log.roll.ms` управляет, когда начинается новый сегмент.

Маленькие сегменты создают много файлов. Большие сегменты задерживают удаление и делают восстановление тяжелее. Используйте значения по умолчанию, пока нет измеренной причины.

Не удаляйте файлы сегментов в файловой системе, чтобы «освободить диск». Используйте ретеншн или удалите топик через admin API. Ручное удаление портит партицию.

## Ретеншн по времени и по размеру

Политика очистки по умолчанию — `delete`. Kafka удаляет старые записи из закрытых сегментов, когда срабатывает предел ретеншна.

**Время.** `retention.ms` (или `log.retention.hours` на уровне брокера) — максимальный возраст записи. Когда предел времени истекает, Kafka может удалить сегмент.

**Размер.** `retention.bytes` — максимальный размер журнала партиции. Когда журнал больше, Kafka удаляет самые старые сегменты.

Если задать оба предела, Kafka может удалять, когда применяется любой предел (проверьте точное правило в документах вашей версии; обычная идея — оба предела существуют и удаление может произойти от любого).

Ретеншн — на партицию, не на топик как один блоб. Горячая партиция первой упирается в предел размера.

`retention.ms=-1` и отключённый предел размера могут хранить данные вечно. Диск заполнится. Используйте бесконечный ретеншн только когда есть план диска.

У консьюмеров с зафиксированным офсетом, который теперь удалён, проблема. Применяется `auto.offset.reset`. Можно потерять логическую позицию. Следите за лагом и диском.

## Компакция (`cleanup.policy=compact`)

Компакция хранит последнюю запись для каждого ключа в партиции. Более старые записи с тем же ключом могут быть удалены. Записи с разными ключами остаются.

Используйте компакцию для changelog: текущее состояние сущности — последнее значение для этого ключа. Примеры: профиль пользователя, статус счёта, состояние таблицы потока.

Компакции нужны ключи. Ключи null не компактируются как changelog сущности. Используйте стабильный ключ.

Компакция не мгновенна. Поток cleaner читает закрытые сегменты и пишет компактированные сегменты. Последнее значение может существовать больше одного раза, пока cleaner не отработает.

Компакция не делает топик базой данных. Нельзя запросить по ключу через протокол Kafka, как запрашиваете SQL. Консьюмер всё равно читает журнал. Kafka Streams и компактируемые топики вместе могут построить таблицу (тема 14).

Задайте `cleanup.policy=compact` на топике. Не предполагайте, что значение брокера по умолчанию — compact. Обычное значение по умолчанию — `delete`.

## Compact + delete

Топик может использовать обе политики: `cleanup.policy=compact,delete`. Kafka компактирует ключи и также удаляет записи старше времени ретеншна (или превышающие размер, в зависимости от конфигурации).

Используйте compact+delete, когда нужен changelog, который не растёт вечно. Старые ключи, которые никто не обновляет, всё равно оставляют запись в топике только compact. Часть delete может удалить эти старые записи после `retention.ms`.

Поймите правило продукта: компакция хранит последнее значение на ключ. Delete удаляет данные по возрасту или размеру. Вместе они ограничивают диск и всё же схлопывают дубликаты горячего ключа.

Эта комбинация обычна для changelog-топиков, которые не должны хранить неиспользуемые ключи годами.

Тестируйте политику на непродакшен-топике. Подтвердите, что тихий ключ исчезает после времени ретеншна. Подтвердите, что горячий ключ всё ещё схлопывается до одного недавнего значения.

Не задавайте время ретеншна короче времени, которое консьюмеру нужно, чтобы пересобрать состояние, если консьюмер не может принять отсутствующий ключ.

## Томбстоуны

Томбстоун — запись с ключом и значением null. На компактируемом топике томбстоун означает «этот ключ удалён». Cleaner может удалить более ранние значения для этого ключа. После времени ретеншна томбстоуна сам томбстоун может исчезнуть.

Продюсеры отправляют томбстоун, когда сущность исчезла. Пример: пользователь удалён. Консьюмеры, которые строят таблицу, удаляют ключ из таблицы, когда видят значение null.

Если только перестать отправлять обновления, компакция хранит последнее ненулевое значение. Ключ остаётся. Нужно отправить томбстоун, чтобы удалить ключ из compact changelog.

Значение null на топике только `delete` — просто запись со значением null. У него нет того же смысла очистки, что у compact-томбстоуна.

Не используйте томбстоун как обычную нагрузку. Используйте структурированное событие «удалено» на топике с политикой delete, если консьюмеры должны хранить историю удаления. Используйте томбстоун, когда changelog должен сбросить ключ.

`delete.retention.ms` управляет, как долго остаются томбстоуны (официальное имя). Читателям нужно это окно, чтобы увидеть удаление.

## Диск и `log.dirs`

`log.dirs` (или `log.dir`) — конфигурация брокера, которая называет каталоги для журналов партиций. Можно задать больше одного каталога. Kafka назначает партиции каталогам. Это не менеджер RAID. Используйте правильную установку диска под каталогами.

Полный диск — серьёзный сбой. Брокер может остановить запись. Следите за диском. Ретеншн — ваш главный инструмент освобождения места. Компакция может уменьшить место для changelog. Удаление топика освобождает место после завершения процесса удаления.

Копии умножают диск. Фактор репликации 3 хранит примерно в три раза больше данных. Включайте реплики в планы диска.

Важен page cache. Чтения Kafka часто идут из кэша операционной системы. Не запускайте другие дискоёмкие задачи на тех же дисках без плана. Тема 15 пути покрывает эксплуатацию.

У метаданных KRaft свой каталог хранения в конфигурации контроллера. Не путайте журнал метаданных с `log.dirs` для партиций топиков. Обоим нужен диск. Форматируйте оба при создании кластера (официальная команда format).

Никогда не направляйте `log.dirs` на сетевую файловую систему, которая не соответствует требованиям Kafka. Следуйте официальным рекомендациям по диску.

3. Из describe топика выделите cleanup.policy и ключи ретеншна.
4. Нарисуйте compact+delete на оси времени для одного неиспользуемого ключа и одного горячего ключа.

#### Средние практические задания

1. Напишите скрипт, который создаёт компактируемый топик, отправляет ключи, отправляет томбстоун и читает с начала.
2. Сравните размер диска JSON changelog до и после многих обновлений тех же ключей (после компакции, если она отработала).
3. Сопоставьте каждый подраздел с официальным ключом конфигурации.

#### Сложные практические задания

1. Соберите маленькую программу «таблица из компактируемого топика». Перезапустите её. Подтвердите, что она пересобирается из журнала. Затем отправьте томбстоун и подтвердите, что ключ исчез.
2. Напишите продакшен-стандарт хранения: значения по умолчанию для потоков событий против changelog, формула диска с репликами и запрет ручного удаления файлов.

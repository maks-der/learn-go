# 19. Прикладные шаблоны

## Описание

Прикладные шаблоны — способы использовать Kafka в дизайне системы. Брокер не выбирает шаблон. Вы выбираете, что означает запись и как сервис её пишет и читает.

Эта тема покрывает уведомление о событии против передачи состояния в событии против event sourcing, шаблон outbox, CQRS с Kafka, request-reply поверх Kafka, порядок и причинность и backpressure на цикле poll. Завершите эту тему после тем 4, 5, 7, 8 и 11. Используйте кластер KRaft. Этим шаблонам не нужен ZooKeeper.

Используйте один термин для каждого понятия. Уведомление о событии — маленький сигнал, что что-то изменилось. Передача состояния в событии — событие, которое несёт данные, нужные читателю. Event sourcing хранит каждое изменение как событие и строит состояние из этого журнала. Outbox — таблица (или эквивалент) в той же транзакции базы данных, что и бизнес-запись. CQRS разделяет модели записи и модели чтения. Backpressure — как вы замедляете вход, когда консьюмер не успевает.

## Уведомление о событии против передачи состояния в событии против event sourcing

**Уведомление о событии** говорит, что факт произошёл, и даёт указатель. Пример: `{ "orderId": "55" }`. Консьюмер должен вызвать API или прочитать базу данных, чтобы получить заказ. Многие консьюмеры создают нагрузку на источник. Если источник недоступен, события недостаточно.

**Передача состояния в событии (ECST)** кладёт нужные поля в событие. Пример: идентификатор заказа, позиции, итоги, идентификатор клиента. Консьюмеры могут обновить своё хранилище без обратного вызова. Событие больше. Важна эволюция схемы (тема 11).

**Event sourcing** использует журнал событий как источник истины для потока изменений. Текущее состояние — свёртка событий. Вы не перезаписываете одну «текущую строку» как единственную истину. Kafka может хранить этот журнал. Вам всё равно нужен способ снимка и определение типов событий. Event sourcing — дизайн, не переключатель Kafka.

Не смешивайте три без имени. Топик, в котором иногда указатель, а иногда полный документ, сломает консьюмеров.

Уведомление подходит, когда нагрузка огромна или приватна и читателей мало. ECST — обычный шаблон интеграции. Event sourcing — для ограниченного контекста, который принимает воспроизведение как модель.

Ретеншн должен совпадать с шаблоном. Event sourcing нуждается в длинной или осторожно компактируемой истории. Топики уведомлений могут использовать короткий ретеншн по времени, если указатель — только подсказка.

KRaft не меняет смысл события. Он только хостит журнал.

## Шаблон outbox

**Шаблон outbox** решает этот сбой: сервис пишет строку базы данных и затем падает до produce в Kafka (или наоборот). Два хранилища расходятся.

Сервис пишет бизнес-строку и **строку outbox** в **одной транзакции базы данных**. Отдельный издатель читает outbox и производит в Kafka. После успешного produce (и устойчивости, которую требуете, темы 4 и 7) издатель помечает строку outbox как отправленную или удаляет её.

Если процесс останавливается после фиксации и до produce, издатель повторяет. Kafka может увидеть дубликат, если produce успел, а пометка нет. Используйте идемпотентный продюсер и ключ дедупликации (тема 7).

Debezium может захватывать таблицу outbox (или выделенную схему outbox) как CDC (тема 12). Тогда приложение не запускает цикл poll по таблице. Журнал транзакций становится издателем.

Не пишите сначала в Kafka и во вторую очередь в базу без компенсирующего плана. Не используйте двухфазную фиксацию между Kafka и базой SQL по умолчанию.

Кластер Kafka — KRaft. Outbox живёт в вашей базе данных. Connect или воркер его читает.

## CQRS с Kafka

**CQRS** (command query responsibility segregation) разделяет модель записи от модели чтения. Команды меняют сторону записи. Запросы читают модель, сформированную для запроса.

Kafka часто — труба между ними. Сервис записи фиксирует (база данных и/или события). События идут в Kafka (outbox или event sourcing). Консьюмер строит хранилище чтения: поисковый индекс, кэш или представление SQL. API чтения не запрашивает базу записи.

Модель чтения **eventually consistent**. Запрос может пропустить команду, которая ещё в журнале или в консьюмере. Скажите продуктовой команде. Не прячьте это.

Можно иметь больше одной модели чтения из одного топика. Это причина использовать Kafka вместо одной общей базы для всех запросов.

Интерактивные запросы в Kafka Streams (тема 14) — чтение состояния потока в стиле CQRS. Модель чтения базы данных — другая обычная форма.

Не ставьте каждый запрос на consume-from-beginning Kafka. Используйте сохранённую модель чтения. Ретеншн Kafka — не ваш API запросов.

KRaft хостит топики событий. База чтения отдельна.

## Request-reply поверх Kafka (обычно избегать)

**Request-reply** означает, что клиент отправляет запрос и ждёт ответа, который совпадает с этим запросом. HTTP и RPC делают это хорошо. Kafka — журнал. Она не даёт сокет на вызов.

Люди реализуют request-reply двумя топиками: запросы и ответы. Запрос несёт correlation id. Клиент ждёт ответа с этим идентификатором, часто на временной партиции или выделенном топике ответов.

Проблемы:

- Тайм-аут и повтор создают дубликаты. Нужна идемпотентность.
- Порядок ответов не равен времени жизни соединения HTTP.
- Застрявший консьюмер выглядит как медленный API (цикл poll, тема 5).
- Вы строите хранилище корреляции.

**Обычно избегайте** этого шаблона для request-reply лицом к пользователю. Используйте HTTP или gRPC к сервису. Используйте Kafka для событий, которым не нужен синхронный ответ.

Если всё же делаете (например интеграция бэкенда, которая уже только Kafka), задайте короткие тайм-ауты, ограничьте ожидание и не блокируйте общий поток poll, пока ждёте ответа (следующий раздел).

KRaft не делает request-reply хорошим выбором по умолчанию.

## Порядок и причинность

**Порядок** в Kafka — на партицию (тема 3). Записи в одной партиции имеют полный порядок. Записи в двух партициях — нет.

Если нужна отношение happens-before между двумя событиями, положите их в одну партицию (один ключ) или положите причинный токен в нагрузку (например версия на сущность).

**Причинность** — правило: если событие A вызвало событие B, читатели должны уметь увидеть A до того, как считают B полным. Партиционирование по одному ключу даёт это для одной сущности. Причинность между сущностями нуждается в дизайне (саги, версии или один писатель).

Метки времени часов недостаточно. У двух продюсеров могут быть сдвинутые часы. Метки времени записей Kafka могут быть временем брокера или временем создания. Не сортируйте глобальные события по метке времени и не называйте это причинностью.

Группы консьюмеров не меняют порядок партиции. Две группы могут читать на разных офсетах. Одна группа всё равно читает одну партицию по порядку на одном консьюмере.

Ребалансы могут поставить партицию на паузу. Они не переупорядочивают журнал.

Геокопии (тема 18) могут задержать партицию. Читатель цели не должен предполагать, что догнал источник.

Выборы лидера KRaft не переупорядочивают зафиксированный журнал. Unclean leader election может (тема 9). Держите unclean election выключенным.

## Backpressure: не блокируйте цикл poll

**Цикл poll** консьюмера (тема 5) должен вызывать poll достаточно часто. `max.poll.interval.ms` ограничивает, как долго можно работать между poll. Если блокируете поток на медленном вызове HTTP или полной базе данных, координатор группы может исключить участника. Начинается ребаланс. Другие партиции паузятся.

**Backpressure** означает, что вы замедляете вход, когда выход не успевает. Корректные инструменты:

- ставить партиции на паузу (`pause` / `resume`), пока опустошаете локальный буфер
- использовать ограниченную очередь и ставить на паузу, когда очередь полна
- понизить `max.poll.records`, чтобы каждый poll был меньше
- масштабировать консьюмеров или чинить медленный сток
- использовать квоты на других шумных клиентах (тема 17), не как единственное исправление

Некорректные инструменты:

- sleep в цикле без poll
- ждать request-reply Kafka в том же потоке
- обработать тысячи записей, затем poll

У Connect и Streams свои потоки задач. Та же идея держится: не блокируйте задачу на безграничном внешнем I/O без тайм-аута и стратегии паузы.

Медленный poll выглядит как простой Kafka. Часто это ваш код (тема 16).

KRaft не меняет правила poll. Координатор группы всё равно живёт на брокере.

Эти вопросы не повторяют вопросы разделов выше. Они покрывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Как ECST, outbox и CQRS образуют один путь интеграции от команды до запроса?
2. Почему этот справочник отвергает request-reply Kafka как значение по умолчанию, но принимает Kafka как журнал событий?
3. Как ключи порядка и цикл poll оба защищают корректность под нагрузкой?
4. Какому шаблону тема 7 (идемпотентность) нужна больше всего и почему?
5. Что остаётся тем же, когда эти шаблоны работают на KRaft вместо старого кластера?

#### Простые практические задания

1. Напишите шпаргалку на одну страницу: три стиля событий, outbox, CQRS, избегать RPC, порядок, пауза.
2. Нарисуйте полный путь магазина: HTTP-команда, outbox, Kafka, чтение CQRS, HTTP запроса. Без топика ответов.
3. Добавьте в закладки одно объяснение outbox и одно CQRS, которым доверяете. Запишите URL.
4. Пометьте шесть реальных функций продукта, который знаете, шаблоном из этой темы.

#### Средние практические задания

1. Реализуйте тонкий путь: outbox или прямой produce ECST, модель чтения консьюмера, без request-reply. Используйте KRaft.
2. Сопоставьте каждый подраздел с одним официальным или классическим URL шаблона.
3. Напишите чеклист ревью для pull request, который добавляет топик Kafka (шаблон, ключ, poll, схема).

#### Сложные практические задания

1. Добавьте медленный сток и backpressure на паузе к консьюмеру CQRS. Покажите лаг без ребаланса.
2. Напишите стандарт прикладных шаблонов для команды: ECST+outbox+CQRS по умолчанию, запреты двойной записи и RPC Kafka, только KRaft.

# 13. TLS и основы безопасности

## Описание

TLS защищает поток байтов между двумя программами. Эта тема показывает конфиденциальность, целостность, подлинность, сертификаты, PKI, рукопожатие на высоком уровне, HTTPS как HTTP поверх TLS, обычные сбои сертификатов и SSH как отдельный защищённый канал.

Используйте один термин для каждого понятия. Конфиденциальность значит, что наблюдатель не может прочитать полезную нагрузку. Целостность значит, что изменение обнаружимо. Подлинность значит, что вы говорите с задуманным узлом. Завершите эту тему после DNS и превью HTTPS в HTTP.

Практикуйтесь с `curl -v` и видом сертификата браузера. Захватывайте записи TLS. Вы видите версии и сообщения рукопожатия. Вы не видите пути HTTP в обычной сессии HTTPS.

## Конфиденциальность, целостность, подлинность

Конфиденциальность скрывает полезную нагрузку от наблюдателя пути. TLS шифрует байты приложения после рукопожатия. Адреса и порты остаются видимыми. Имя Server Name Indication (SNI) часто всё ещё видно в старом TLS. TLS 1.3 может шифровать больше рукопожатия. Этому разделу нужна идея: шифрование — не невидимость соединения.

Целостность позволяет приёмнику обнаружить изменение шифротекста или записей. Middlebox, который переворачивает биты, должен вызвать сбой, а не тихую неверную страницу. TLS использует MAC или AEAD для этой задачи. Математика не нужна. Нужно свойство.

Подлинность связывает сессию с личностью узла. Для HTTPS личность — имя DNS на сертификате. Шифрования без проверки имени недостаточно. Злоумышленник на пути может завершить TLS другим сертификатом, если клиент не проверяет.

Три слова работают вместе. Конфиденциальность без подлинности может скрыть данные от третьей стороны и всё равно отдать данные неверному узлу. Подлинность без целостности — не полный канал. Целостность без конфиденциальности всё ещё может утечь секреты.

Не говорите «безопасно», не называя, которое из трёх имеете в виду. Не считайте VPN заменой TLS к публичному API, если не спроектировали эту модель доверия.

SSH использует те же три идеи с другим протоколом и другой моделью личности (ключи хоста и ключи пользователя).

## Сертификаты и PKI

Сертификат связывает открытый ключ с именем (и иногда с другими именами). Центр сертификации (CA) подписывает эту связь. У клиента есть хранилище доверенных корневых сертификатов CA. Операционная система и браузер поставляют эти корни.

PKI — инфраструктура открытых ключей. PKI — набор CA, сертификатов, данных отзыва и политик, которые делают связь usable. Вам не нужно запускать публичный CA для этой темы. Нужно знать цепочку доверия: сертификат сервера, необязательные промежуточные и корень, которому клиент уже доверяет.

Клиент проверяет:

- имя в URL совпадает с именем на сертификате
- текущее время внутри интервала действия
- цепочка ведёт к доверенному корню
- подпись на каждом звене верна
- статус отзыва, когда клиент реализует эту проверку

Самоподписанный сертификат подписан своим ключом. Браузер не доверяет ему, пока не добавите исключение или не установите локальный CA вроде mkcert. Используйте самоподписанный или mkcert только на машинах, которыми владеете.

Не отправляйте закрытый ключ в чат или в репозиторий. Не отключайте проверку, чтобы «заработало» на реальном пути пользователя. Не считайте значок замка на фишинговом имени безопасностью. Замок говорит только, что TLS к этому имени успешен.

Сертификат клиента необязателен. Некоторые API используют взаимный TLS. Этой теме нужно только: обычный веб-случай подлинности сервера.

## Рукопожатие (обзор)

Рукопожатие TLS идёт после рукопожатия TCP для TLS на TCP. Две стороны согласуют версию TLS и алгоритмы. Сервер отправляет сертификат (обычный веб-случай). Клиент проверяет сертификат. Две стороны выводят ключи. Затем они отправляют зашифрованные данные приложения.

TLS 1.3 — текущая обычная версия в публичном вебе. Сообщения на проводе отличаются от TLS 1.2. Учебная история та же: подлинность сервера, затем защита байтов.

ALPN может идти внутри рукопожатия. ALPN выбирает протокол приложения (HTTP/1.1, HTTP/2 или другие). Следующая тема покрывает ALPN с HTTP/2 и HTTP/3.

Рукопожатие может упасть до любого запроса HTTP. `curl -v` тогда печатает ошибку TLS, не статус HTTP. Захват показывает предупреждение или закрытие. Вы снова отладите этот шаблон в теме наблюдаемости.

Не выдумывайте своё «шифрование» заголовков HTTP на порту 80 и не называйте это TLS. Не пропускайте проверку. Не вставляйте полный дамп рукопожатия, в котором есть секреты из лаборатории с билетами сессии, которые нужно держать в тайне.

Возобновление может пропустить полное рукопожатие на позднем соединении. Идея — скорость. Безопасность всё равно зависит от первого решения доверия.

QUIC включает TLS 1.3 в своё рукопожатие UDP. Это тема HTTP/3. Этот раздел — TLS на TCP, если не читаете вперёд.

## HTTPS = HTTP поверх TLS

HTTPS — HTTP на сессии TLS. Порт по умолчанию — 443. Схема URL — `https`. Клиент разбирает URL, разрешает имя, соединяется TCP, завершает TLS, затем отправляет запрос HTTP по защищённому потоку.

Методы HTTP, коды состояния и заголовки — те же идеи, что тема 11. TLS не заменяет `Host`. Клиент всё равно отправляет `Host`. Наблюдатель пути не видит этот заголовок, когда TLS работает.

Обратный прокси часто завершает TLS. Прокси говорит HTTPS с клиентом и HTTP или HTTPS с приложением. Приложение должно знать, был ли исходный запрос HTTPS (`X-Forwarded-Proto` или эквивалент). Доверяйте этому заголовку только от своего прокси.

HSTS говорит браузеру использовать HTTPS для имени на время. Смешанное содержимое — ресурсы HTTP на странице HTTPS. Браузеры блокируют или предупреждают. Исправьте URL ресурсов.

Не кладите секреты в URL HTTP и затем «добавьте TLS позже» без проверки. Старые ссылки и журналы всё ещё могут утечь. Не называйте сайт HTTPS, если проверка TLS выключена.

`curl` использует HTTPS, когда URL говорит `https`. `curl -k` всё ещё HTTP поверх TLS с выключенной проверкой. Это не то же самое, что безопасный HTTPS.

## Обычные сбои: истёкший сертификат, неверный хост, MITM в публичном Wi-Fi

Истёкший сертификат: время конца действия в прошлом (или время начала в будущем). Клиент должен упасть. Причина: оператор не продлил. Ваши часы тоже могут быть неверны. Неверные часы выглядят как неисправность истечения.

Неверный хост: имена сертификата не включают хост URL. Причина: неверный vhost, сертификат по умолчанию или сырой IP в URL. Клиент должен упасть.

Недоверенный издатель: цепочка не достигает корня, которому этот клиент доверяет. Причина: корпоративный CA перехвата не установлен, самоподписанный сервер или отсутствующий промежуточный.

MITM в публичном Wi-Fi: captive portal или злоумышленник предъявляет другой сертификат. Верный клиент показывает предупреждение. Не игнорируйте предупреждение. Портал также может перехватывать HTTP и перенаправлять вас. Используйте HTTPS и имя, которое набрали или сохранили в закладках.

Другие обычные сбои: отозванный сертификат, слабый старый TLS, который клиент отвергает, и имя, которое не разрешается. Читайте точную ошибку. `curl` и браузеры используют разные слова для одной проверки.

Не кликайте предупреждение сертификата на банке, почте или рабочем сайте. Не используйте публичный Wi-Fi для секретов без TLS, который проверяет. Не ставьте системные часы назад, чтобы «починить» истечение.

Корпоративный перехватчик TLS — поздняя тема укрепления. Этому разделу нужно: клиент видит неожиданного издателя.

## SSH как защищённый канал

SSH — протокол защищённого канала, обычно на TCP-порту 22. Обычные применения: удалённая оболочка, копирование файлов (`scp`, `sftp`) и проброс портов. SSH — не HTTP. SSH — не TLS. Цели совпадают: конфиденциальность, целостность, подлинность.

У сервера есть ключ хоста. Клиент хранит отпечаток в `known_hosts` после первого успеха (или вы фиксируете отпечаток). Сменённый ключ хоста — предупреждение. Это может значить новый сервер или злоумышленника. Не игнорируйте предупреждение сменённого ключа на хосте, который должен быть стабильным.

Пользователь проходит подлинность паролем или, лучше, парой открытого ключа. Держите закрытый ключ закрытым. Используйте парольную фразу на файле ключа.

SSH может туннелировать другие порты TCP. Этот туннель — инструмент, не полный проект сети. Тема 21 покрывает VPN на высоком уровне.

Не отключайте проверки ключа хоста, чтобы сэкономить время. Не используйте один пользовательский ключ на публичной вставке. Не выставляйте SSH в Internet без плана (ключи, обновления и ограниченные пользователи).

`ssh -v` печатает шаги рукопожатия. Используйте его, чтобы учиться. Используйте его на хостах, к которым можно подключаться.

1. Прочитайте `man ssh` или страницу SSH поставщика про `-L` или `-D` на высоком уровне. Напишите четыре предложения STE. Не открывайте туннель в сеть, которой нельзя пользоваться.
2. Напишите шесть предложений: подлинность паролем против подлинности открытым ключом.
3. Если есть лабораторная VM, которой владеете, подключитесь по SSH один раз. Запишите, как выглядел запрос ключа хоста. Пропустите, если VM нет.

#### Сложные практические задания

1. Напишите список укрепления SSH на одну страницу для лабораторной VM: ключи, нет неиспользуемых учётных записей, обновления. Без шагов атаки.
2. Сравните `sftp` и загрузку файлов HTTPS в короткой заметке: канал, личность и типичное использование.

## Обзор темы

Эти вопросы не повторяют вопросы в разделах выше. Они покрывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Опишите сессию HTTPS от поиска имени до HTTP. Используйте три свойства безопасности и одну проверку сертификата.
2. Как PKI, рукопожатие и обратный прокси, который завершает TLS, стыкуются на одном публичном имени?
3. Почему SSH и TLS оба могут быть «безопасными» и всё равно не заменять друг друга?
4. Когда `curl -k` — неверный инструмент, а когда верное исправление — локальное хранилище доверия?
5. Напарник говорит: «пароль Wi-Fi шифрует мой HTTPS». Какие факты вы используете в ответе?

#### Простые практические задания

1. Напишите шпаргалку на одну страницу: три свойства, цепочка сертификата, порядок рукопожатия, уровни HTTPS, три сбоя, ключ хоста SSH.
2. Запустите `curl -v https://example.com` и откройте тот же сайт в виде сертификата браузера. Запишите два факта, которые совпадают.
3. Нарисуйте одну картинку: клиент, публичный Wi-Fi, сервер. Подпишите, где TLS должен проверять.
4. Перечислите порты по умолчанию: HTTPS и SSH.

#### Средние практические задания

1. Напишите лабораторию: локальный сервер TLS, несовпадение имени, затем исправление. Запишите команды. Используйте только свою машину.
2. Постройте поток устранения неполадок: ошибка рукопожатия, HTTP 403, сменённый ключ хоста SSH. По одному блоку.
3. Сравните строки TLS `curl -v` со сводкой TLS Wireshark для одной загрузки. Запишите три поля, которые показывают оба.

#### Сложные практические задания

1. Напишите маленький клиент HTTPS на Go или Python, который проверяет TLS и печатает имена сертификата узла. Проверьте на `example.com`.
2. Соберите глоссарий из 14 терминов этой темы. Каждая запись: термин, одно предложение, один инструмент, который его показывает.

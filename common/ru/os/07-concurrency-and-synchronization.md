# 7. Параллельность и синхронизация

## Описание

Параллельные потоки делят данные. Без правил они гоняют. Эта тема объясняет критическую секцию и главные блокировки: мьютекс, семафор и условную переменную. Вы узнаете взаимную блокировку и четыре условия Коффмана, живую блокировку, голодание, инверсию приоритета и первый взгляд на видимость памяти.

Завершите эту тему после потоков и планирования. Завершите эту тему до того, как делить буферы между потоками в поздних проектах.

Используйте один термин для каждого понятия. Мьютекс — блокировка, которой владеет один поток. Семафор — счётчик, на котором потоки ждут. Условная переменная — очередь ожидания, которую поток использует вместе с мьютексом. Взаимная блокировка — постоянный цикл ожидания. Не смешивайте взаимную блокировку с живой блокировкой. Не смешивайте мьютекс с семафором. Не считайте sleep блокировкой.

## Критическая секция

Критическая секция — область кода, которая не должна выполняться больше чем на одном потоке одновременно, когда потоки используют одни и те же общие данные.

Общие данные — причина секции. Два потока могут выполнять одну функцию. Они не могут оба выполнять увеличение одного счётчика одновременно.

Свойства, которые должен дать правильный протокол блокировки:

1. Взаимное исключение: в критической секции для этих данных находится не больше одного потока.
2. Прогресс: если секция свободна и потоки хотят войти, решение, кто входит, не должно вечно ждать поток, который вне секции.
3. Ограниченное ожидание (цель справедливости): поток не должен ждать вечно, пока другие входят снова и снова.

Критическая секция должна быть маленькой. Не делайте файловый ввод-вывод или долгий цикл ЦП внутри секции, если ввод-вывод не является общим объектом, который вы защищаете. Большая секция снижает параллелизм.

Вход и выход должны быть парными. Если вы забудете разблокировать, другие потоки блокируются навсегда. Используйте один путь выхода, когда можете. В C проверяйте каждый ранний `return`.

Не каждая строка программы — критическая секция. Локальным переменным на частном стеке блокировка не нужна. Неизменяемым данным, которые никто не пишет, блокировка не нужна. Гонка есть только когда хотя бы одно обращение — запись, а обращения одновременны и несинхронизированы.

## Мьютекс, семафор, условная переменная

У мьютекса (блокировки взаимного исключения) две операции: захватить и освободить. Поток, который захватывает мьютекс, владеет им. Только этот поток может его освободить. Мьютекс — инструмент по умолчанию для критической секции. POSIX: `pthread_mutex_lock`, `pthread_mutex_unlock`. Фьютексы Linux реализуют ожидание (тема 21). Сначала используйте API POSIX.

Семафор — счётчик с wait (P, down) и post (V, up). Двоичный семафор может выглядеть как блокировка, но у него нет владельца в модели POSIX `sem_t`. Любой поток может сделать post. Считающий семафор может пустить N потоков в пул (например, N слотов буфера). POSIX: `sem_wait`, `sem_post`.

Условная переменная позволяет потоку ждать булево условие. Поток должен держать мьютекс, когда ждёт. `pthread_cond_wait` освобождает мьютекс, ждёт и снова захватывает мьютекс до возврата. Другой поток меняет условие, затем вызывает `pthread_cond_signal` или `pthread_cond_broadcast`, пока держит мьютекс (или по задокументированным правилам). Всегда ждите в цикле: `while (!ready) pthread_cond_wait(...)`. Пробуждение может быть ложным, и другой поток может потребить условие.

Типичные роли:

- мьютекс: защитить структуру данных
- семафор: считать разрешения или элементы
- условная переменная: ждать, пока предикат истинен (очередь не пуста, фаза закончилась)

Мьютекс по умолчанию не рекурсивный. Поток, который дважды захватывает один нерекурсивный мьютекс, блокирует сам себя. Рекурсивный мьютекс существует. Предпочитайте один путь владельца блокировки.

Не используйте условную переменную без мьютекса. Не используйте `sleep`, чтобы ждать другой поток.

## Взаимная блокировка: четыре условия Коффмана

Взаимная блокировка — состояние, в котором набор потоков ждёт вечно. Каждый поток держит ресурс и ждёт ресурс, который держит другой поток в наборе.

Коффман, Элфик и Шошани назвали четыре условия. Все четыре должны выполняться для этого вида взаимной блокировки:

1. Взаимное исключение: хотя бы один ресурс нельзя делить. Мьютекс — такой ресурс.
2. Удержание и ожидание: поток держит ресурс и ждёт другой ресурс.
3. Нет вытеснения: ядро или сосед не могут забрать блокировку. Владелец должен освободить.
4. Циклическое ожидание: есть цикл. A ждёт блокировку B, B ждёт блокировку A.

Если вы сломаете любое одно условие, такая взаимная блокировка не сможет образоваться.

Обычные методы слома:

- порядок блокировок: все потоки захватывают мьютекс A, затем мьютекс B, никогда B, затем A (ломает циклическое ожидание)
- try-lock и отступление (может ввести живую блокировку, если вы неосторожны)
- не ждать, пока держите блокировку (ломает удержание и ожидание; не всегда возможно)
- безблокировочные дизайны (продвинуто)

Двух мьютексов и двух потоков достаточно:

```text
Thread 1: lock(A); lock(B);
Thread 2: lock(B); lock(A);
```

Взаимная блокировка — не гонка на счётчике. Программа перестаёт делать прогресс. ЦП может простаивать.

Обнаружение: сторож, таймаут или граф ждущих. Linux волшебно не ломает взаимные блокировки пользовательских мьютексов. Ваш процесс зависает.

## Живая блокировка и голодание

Живая блокировка — состояние, в котором потоки продолжают менять состояние, но не делают полезного прогресса. Они не застряли в цикле ожидания блокировки. Они заняты. Пример: два потока обнаруживают конфликт, оба отступают, оба повторяют одновременно, вечно. Пример: два человека в коридоре отступают в одну сторону.

Голодание — состояние, в котором один поток никогда не получает ресурс, который другие продолжают получать. Система в целом всё ещё может делать прогресс. Пример: SJF всегда запускает короткие работы; долгая работа ждёт вечно. Пример: политика пробуждения мьютекса всегда предпочитает последнего ждущего.

Различия:

- взаимная блокировка: нет прогресса, часто спят в цикле
- живая блокировка: активность, нет полезного прогресса
- голодание: некоторые потоки прогрессируют, один поток нет
- гонка: неверный результат, программа обычно продолжается

Исправления живой блокировки: случайное отступление, предел повторов, полный порядок, чтобы одна сторона всегда побеждала.

Исправления голодания: справедливые блокировки, старение (приоритет растёт со временем ожидания), справедливость в стиле CFS у планировщика, не использовать строгий SJF для планирования.

Спинлок, который всегда сбоит и повторяет без справедливой очереди, может морить поток на занятой блокировке. Поток `SCHED_FIFO` может морить потоки `SCHED_OTHER` (тема 6).

## Инверсия приоритета (высокий уровень)

Инверсия приоритета возникает, когда поток с высоким приоритетом ждёт блокировку, которую держит поток с низким приоритетом, а поток со средним приоритетом работает вместо потока с низким приоритетом.

Последовательность:

1. Низкий L захватывает мьютекс M.
2. Высокому H нужен M, и он блокируется.
3. Средний M-pri становится готов и вытесняет L (L не закончил критическую секцию).
4. H ждёт, пока работает M-pri. H инвертирован: он ждёт поток с более низким приоритетом, который не может работать.

Планировщик делает правильное с приоритетами, но блокировка создала скрытую зависимость.

Наследование приоритета — обычное исправление. Пока H ждёт M, L временно, работает с приоритетом H. Средний не может вытеснить L. L освобождает. H работает. L возвращается к старому приоритету.

Потолок приоритета — другое исправление. У мьютекса есть потолок приоритета. Поток, который его захватывает, поднимается до этого потолка. Этому методу нужен статический анализ приоритетов.

Мьютексы pthread Linux могут использовать `PTHREAD_PRIO_INHERIT`, когда поток использует политику реального времени. Рабочий стол по умолчанию `SCHED_OTHER` не показывает ту же историю инверсии, что жёсткая система реального времени, но инверсия всё равно может задержать поток.

Не давайте долгую критическую секцию потоку с низким приоритетом, если потоку с высоким приоритетом нужна та же блокировка. Держите секцию короткой. Это снижает время инверсии даже без наследования.

## Видимость памяти и блокировки (превью модели памяти)

Блокировка делает больше, чем взаимное исключение. Правильный мьютекс также упорядочивает память.

Без блокировки или атомика с правильным порядком запись в потоке A может быть ещё не видна потоку B. Компилятор может держать значение в регистре. ЦП может переупорядочить записи и чтения. Другое ядро может видеть старую строку кэша.

Пример сломанного флага:

```c
/* thread A */
data = 42;
ready = 1;

/* thread B */
while (ready == 0) { }
use(data);   /* may see data != 42 */
```

На настоящей машине это может сбоить. Мьютекс вокруг обеих сторон или атомарная запись-release `ready` и атомарное чтение-acquire в B делают запись `data` видимой до того, как `ready` увидят как 1.

Правила для этого пути:

1. Если вы делите неатомарный объект, используйте мьютекс (или другой задокументированный примитив) для всех чтений и записей этого объекта.
2. Не используйте обычный флаг `int`, чтобы опубликовать структуру без истории порядка памяти.
3. `volatile` в C — не мьютекс. `volatile` не делает увеличение атомарным. Не используйте `volatile` как блокировку.

Тема 21 возвращается к барьерам и безблокировочному прогрессу. Этот раздел только утверждает: блокировки исключают и публикуют.

Атомики C11 (`<stdatomic.h>`) дают другой путь. Используйте их, когда измерили нужду. Для новичка мьютекс — значение по умолчанию.

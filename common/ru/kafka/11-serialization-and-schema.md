# 11. Сериализация и схема

## Описание

Kafka хранит ключи и значения как байты. Сериализатор пишет эти байты. Десериализатор их читает. Схема описывает форму данных. Schema Registry хранит схемы и может принуждать совместимость.

Эта тема покрывает байты на проводе, Schema Registry (Confluent или Karapace), Avro, Protobuf, JSON Schema, режимы совместимости и стратегии имён subject. Завершите эту тему после темы 4. ZooKeeper не нужен. Schema Registry — отдельный сервис. Kafka на KRaft и Schema Registry работают вместе через протокол Kafka и HTTP.

Используйте один термин для каждого понятия. Байты на проводе — нагрузки ключа и значения в записи. Схема — контракт для этих байтов. Subject — имя в реестре, которое держит последовательность версий схемы. Совместимость — правило, которое разрешает или отклоняет новую версию схемы.

## Байты на проводе

Ключ записи Kafka — последовательность байтов или null. Значение записи Kafka — последовательность байтов или null. Брокеры не разбирают JSON или Avro. Брокеры не проверяют ваши поля.

Сериализатор продюсера создаёт байты. Десериализатор консьюмера должен понимать тот же формат. Если пара не совпадает, консьюмер бросает исключение или печатает мусор.

Простые форматы:

- строка (текст UTF-8)
- сырой текст JSON
- integer или long в фиксированной двоичной раскладке (сериализаторы клиента)

Со Schema Registry в стиле Confluent значение часто использует эту раскладку:

1. magic byte
2. 4-байтовый идентификатор схемы
3. нагрузка Avro, Protobuf или JSON

Брокер всё равно видит байты. Реестр отображает идентификатор на схему. Десериализатор получает схему (и кэширует её), затем декодирует нагрузку.

Не смешивайте сырой JSON-продюсер и Avro-консьюмер реестра на одном топике. Создайте ясный контракт на топик.

Заголовки могут нести тип содержимого. Заголовки необязательны. Не полагайтесь на заголовок, если десериализатор его не читает.

## Schema Registry (Confluent или Karapace)

Schema Registry — HTTP-сервис, который хранит схемы. Продюсеры регистрируют схему (или используют известный идентификатор). Консьюмеры загружают схему по идентификатору.

**Confluent Schema Registry** — обычный продукт в Confluent Platform и Confluent Cloud. **Karapace** — открытый реестр, который говорит на совместимом API. Существуют другие реестры. Этот справочник использует «реестр» для роли сервиса.

Реестр — не Kafka. Вы запускаете его рядом с кластером. Он часто хранит свои данные в топике Kafka (например `_schemas`). Этот топик — компактируемый changelog. Не считайте его прикладным топиком.

Клиентам нужен `schema.registry.url` (имя может отличаться). Аутентификация на реестре отдельна от SASL Kafka. Тема 17 покрывает безопасность.

Без реестра всё ещё можно использовать файлы Avro или Protobuf в репозитории. Тогда у каждого консьюмера должен быть файл схемы. Реестр помогает, когда многие команды делят топики и когда схемы эволюционируют.

Не запускайте продакшен-реестр как один процесс без бэкапа без плана. Следуйте руководству эксплуатации продукта.

Темы Kafka 1–10 можно учить без реестра. Используйте реестр, когда нужен общий контракт.

## Avro / Protobuf / JSON Schema

Эти три системы схем обычны с реестром.

**Avro.** Компактная двоичная кодировка. Схема — JSON. Avro обычен в Kafka и системах в стиле Hadoop. Читателям нужна схема писателя. Реестр её хранит. У Avro простая модель эволюции, которая хорошо совпадает с совместимостью реестра.

**Protobuf.** Компактная двоичная кодировка. Вы пишете файлы `.proto`. Многие сервисы уже используют Protobuf для RPC. Клиенты Kafka могут использовать Protobuf с реестром. Правила эволюции отличаются от Avro. Важны номера полей.

**JSON Schema.** Нагрузка может остаться текстом JSON (или двоичной формой, в зависимости от сериализатора). JSON Schema описывает поля и типы. Отладка проще. Размер больше, чем у Avro или Protobuf. Проверка может происходить в сериализаторе.

Выберите один формат на топик. Не меняйте формат на месте. Используйте новый топик, если нужно сменить семейство (Avro на Protobuf).

JSON без схемы — не JSON Schema. У сырого JSON нет проверки реестра.

Генерация кода обычна. Avro и Protobuf генерируют типы. Сгенерированные типы уменьшают ошибки имён полей. Коммитьте исходник схемы (`.avsc` или `.proto`) в репозиторий, который владеет топиком.

## Совместимость: backward, forward, full

Реестр может отклонить новую схему, если она ломает режим совместимости subject.

**Backward.** Новая схема может читать данные, которые писатели произвели предыдущей схемой. Новые консьюмеры могут читать старые записи. Это обычное значение по умолчанию. Пример: вы добавляете необязательное поле со значением по умолчанию.

**Forward.** Старая схема может читать данные, которые производит новый писатель. Старые консьюмеры могут читать новые записи. Пример: вы удаляете поле, которое старые читатели никогда не требовали.

**Full.** Держится и backward, и forward.

**None.** Реестр принимает любую схему. Консьюмеры могут сломаться. Избегайте этого на общих топиках.

Транзитивные режимы (`BACKWARD_TRANSITIVE`, `FORWARD_TRANSITIVE`, `FULL_TRANSITIVE`) проверяют новую схему против всех сохранённых версий, не только последней. Используйте транзитивные режимы, когда консьюмеры могут сильно отставать.

Совместимость не заменяет тесты. Тестируйте новую схему со старым двоичным файлом консьюмера и со старыми файлами из продакшена (анонимизированными).

Ломающее изменение нуждается в новом subject или новом топике и плане миграции. Не форсируйте `NONE`, чтобы «разблокировать» конвейер.

## Стратегии имён subject

Subject — ключ реестра для последовательности версий. Стратегия имён отображает запись Kafka на subject.

Обычные стратегии Confluent:

- **TopicNameStrategy.** Subject — `{topic}-value` или `{topic}-key`. Одно семейство схем на топик для значения. Это обычное значение по умолчанию.
- **RecordNameStrategy.** Subject — полностью квалифицированное имя записи (имя Avro или сообщение Protobuf). Несколько топиков могут делить одну схему записи. Один топик может содержать больше одного типа записи.
- **TopicRecordNameStrategy.** Subject — `{topic}-{record name}`. Схема специфична для топика и типа записи.

Используйте TopicNameStrategy, когда у одного топика один тип события. Этот случай самый простой.

Используйте стратегию на основе записи, когда один топик — поток нескольких типов. Тогда консьюмеры должны обрабатывать больше одной схемы. Это сложнее.

Не изобретайте случайные имена subject в каждом продюсере. Задайте стратегию в клиенте. Выровняйте всех продюсеров топика.

Неверная стратегия создаёт новый subject и выглядит как «схема отсутствует» у консьюмера.

Ключи часто используют строковый идентификатор и без реестра. Если ключ — Avro, subject — `{topic}-key` при TopicNameStrategy.

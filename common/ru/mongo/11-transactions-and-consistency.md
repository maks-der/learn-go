# 11. Транзакции и согласованность

## Описание

Эта тема показывает, как MongoDB держит записи корректными. Запись одного документа всегда атомарна. Мультидокументные транзакции **ACID** есть на replica set и на шардированных кластерах. Вы узнаёте, когда транзакция не нужна. Задаёте read concern, write concern и read preference. Изучаете причинную согласованность на высоком уровне. Сначала завершите CRUD, моделирование и драйверы.

Используйте один термин для каждого понятия. **Атомарный** значит, что запись в один документ полностью происходит или не происходит. **Транзакция** группирует чтения и записи по документам так, что они фиксируются или прерываются вместе. **Write concern** — насколько прочной и насколько широко реплицированной должна быть запись, прежде чем сервер подтвердит её. **Read concern** — насколько актуальным и зафиксированным большинством должно быть чтение. **Read preference** выбирает, с какой реплики читать.

## Атомарность одного документа (всегда)

Запись в **один документ** атомарна. Сервер не оставляет на диске половину полей этой записи. `$set` двух полей в одном `updateOne` применяет оба или ни одного.

Это верно без мультидокументной транзакции. Это первый инструмент согласованности в MongoDB.

Проектируйте под это. Кладите данные, которые должны меняться вместе, в один документ, когда модель позволяет. Заказ со строками в одном документе может обновить `status` и `lines` одной записью.

Атомарность — не изоляция между документами. Два документа могут измениться в порядке, который второй клиент видит как смешанный.

Атомарность сама по себе — не прочность. Запись может быть атомарной в памяти и всё равно пропасть, если узел упадёт до журнала или большинства реплик, в зависимости от write concern.

`updateOne` одного совпадения, `insertOne` и `replaceOne` — однодокументные. `updateMany` атомарна **на документ**, а не как один пакет всё-или-ничего, если нет транзакции.

Не используйте транзакцию только чтобы изменить два поля в том же документе. Одного обновления достаточно.

## Мультидокументные транзакции ACID (replica set / шардированные)

**Мультидокументная транзакция** позволяет читать и писать больше одного документа как одну фиксацию.

Требования:

- **Replica set** (даже один член для учёбы) или **шардированный кластер**
- API драйвера: `startSession`, `startTransaction`, операции, `commitTransaction` или `abortTransaction`
- Одиночный `mongod` без replica set эти транзакции **не** поддерживает

ACID в этом контексте:

- **Atomic** — все записи фиксации появляются или не появляется ни одна
- **Consistency** — согласованность приложения всё равно определяете вы; сервер обеспечивает ограничения, которые вы настроили
- **Isolation** — изоляция снимка для транзакции (читайте текущее руководство)
- **Durability** — зависит от write concern при фиксации

Форма примера в `mongosh`:

```javascript
session = db.getMongo().startSession()
session.startTransaction()
const orders = session.getDatabase("shop").orders
const stock = session.getDatabase("shop").stock
orders.insertOne({ _id: 1, sku: "nail", qty: 1 })
stock.updateOne({ sku: "nail" }, { $inc: { qty: -1 } })
session.commitTransaction()
session.endSession()
```

Если запись падает, прервите. Повторите всю транзакцию при временных ошибках (драйвер может помочь).

У транзакций есть лимиты: время, размер и число операций. Не держите транзакцию, пока ждёте пользователя.

Шардированные транзакции поддерживаются в текущих версиях. Они дороже. Держите их короткими.

## Когда мультидокументная транзакция не нужна

Мультидокументная транзакция не нужна, когда:

- Хватает записи одного документа (встраивание, вычисленное поле в том же документе)
- Бизнес принимает **конечную** согласованность и задачу повтора (например строка журнала, которая может прийти поздно)
- Запись можно сделать **идемпотентной** и можно починить (outbox, повтор)
- Нужен только уникальный индекс, чтобы предотвратить дубликат
- Читаете после записи так, что сессия и majority concern уже покрывают (см. следующие разделы)

У транзакций есть цена. Они держат блокировки или снимок. Они могут прерваться. Они усложняют код.

Предпочитайте смену модели транзакциям. Если всегда транзакционно обновляете пользователя и счётчик, храните счётчик на пользователе или примите ночную починку.

Не оборачивайте каждый `insertOne` в транзакцию.

Не используйте транзакцию, чтобы спрятать проблему неограниченного массива.

Один `bulkWrite` без транзакции — **не** всё-или-ничего между документами.

Когда транзакция всё же нужна: деньги между двумя счетами в двух документах, остаток плюс заказ если они разделены, две коллекции, которые не должны показывать смешанное состояние любому читателю.

## Read и write concerns

**Write concern** — правило подтверждения записи.

Частые значения:

- `w: 1` — подтверждает primary. Быстро. Падение primary может потерять запись, если она не реплицировалась.
- `w: "majority"` — большинство голосующих членов replica set сохраняет запись. Безопаснее.
- `j: true` — запись в журнале.

Atlas часто по умолчанию использует majority. Задавайте majority для денег и для данных, которые нельзя восстановить.

**Read concern** — правило снимка для чтения.

Частые значения:

- `local` — данные на выбранном узле, даже если они не зафиксированы большинством
- `majority` — данные, которые большинство зафиксировало
- `snapshot` — согласованный снимок, используется в транзакциях

Чтение с `local` на primary всё ещё может увидеть запись, которая позже откатится в редких случаях failover, если запись не была зафиксирована большинством.

Не смешивайте записи `w: 1` с верой, что каждый другой узел уже имеет данные.

Concerns можно задать в URI, на клиенте, на коллекции или на одной операции. Для важных записей будьте явны.

`w: 0` (без подтверждения) — для особых случаев. Не используйте в API, который должен знать, что запись сработала.

## Read preference

**Read preference** выбирает, какой член replica set выполняет чтение.

Частые режимы:

- `primary` — всегда primary. По умолчанию. Самая сильная свежесть на этом узле.
- `primaryPreferred` — primary если доступен, иначе secondary
- `secondary` — secondary
- `secondaryPreferred` — secondary если доступен, иначе primary
- `nearest` — член с низкой задержкой, который совпадает с тегами

Чтения с **secondary** могут быть **устаревшими**. Репликация не мгновенна. Приложение может не увидеть запись, которую только что отправило на primary.

Используйте `primary` для чтений, которые должны видеть последнюю запись этого приложения (или используйте сессию с причинной согласованностью, следующий раздел).

Используйте secondary для отчётов, которые принимают отставание, или чтобы снять нагрузку чтения. Измеряйте отставание. Не гадайте.

`nearest` всё равно может попасть на secondary. Не используйте `nearest` для «самых свежих» чтений.

Наборы тегов выбирают членов (например delayed-член). Delayed-члены — для практики катастроф, не для обычных пользовательских чтений.

Read preference — не read concern. Preference выбирает узел. Concern выбирает, насколько зафиксированными должны быть данные на этом узле.

## Причинная согласованность (обзор)

**Причинная согласованность** значит: если операция B зависит от операции A, каждый читатель с теми же правилами видит A до B.

Пример: клиент пишет пост, затем читает список постов. Без осторожности чтение на устаревшем secondary может пропустить пост.

**Сессии** MongoDB могут давать причинную согласованность. После записи сессия хранит cluster time. Следующее чтение в этой сессии ждёт, пока выбранные члены будут хотя бы так далеко.

По умолчанию: многие драйверы включают причинную согласованность на сессии. Читайте страницу драйвера.

Причинная согласованность — не полная линеаризуемость всей базы для всех клиентов. Другой клиент без сессии в крайних случаях всё ещё может увидеть другой порядок, в зависимости от concerns и preference.

Вы всё равно выбираете write concern и read concern. Причинная согласованность плюс majority concerns — частая пара для «прочитать свои записи» в сессии приложения.

Не путайте причинную согласованность с мультидокументной транзакцией. Транзакция — другой инструмент. Можно использовать оба.

Правило на высоком уровне: используйте одну сессию для цепочки запросов пользователя, когда следующее чтение должно видеть предыдущую запись, особенно если читаете с secondary.

### Вопросы

#### Теоретические вопросы

1. Как атомарность одного документа, мультидокументные транзакции и write concern решают разные задачи?
2. Когда read concern и read preference оба важны для бага «прочитать после записи»?
3. Почему replica set — требование транзакций, но также место, где появляются устаревшие чтения secondary?
4. Чем причинная согласованность в сессии отличается от изоляции снимка в транзакции?
5. Коллега оборачивает каждую запись в транзакцию и читает с `nearest`. Какими фактами вы ответите на ревью?

#### Простые практические задания

1. Напишите шпаргалку: атомарность одного документа, API транзакции, когда не использовать, `w`/`readConcern`, режимы read preference, причинность сессии.
2. На replica set зафиксируйте одну транзакцию и одну запись majority. Найдите оба документа.
3. Нарисуйте шкалу времени: запись клиента, primary, secondary, устаревшее чтение, чтение majority.
4. Отметьте три записи магазина как: один документ, транзакция или асинхронная починка.

#### Средние практические задания

1. Реализуйте перевод двух счетов транзакцией и `w: "majority"`. Прервите при недостатке средств. Напишите тесты.
2. Реализуйте тот же перевод как события в одной коллекции журнала (однодокументное добавление). Сравните код и режимы отказа.
3. Настройте одно чтение API как `primary` + `majority` и один отчёт как `secondary` + `local`. Объясните, почему каждая пара подходит.

#### Сложные практические задания

1. Измерьте долю abort и длительность конфликтующей транзакции (два клиента обновляют те же два документа). Запишите числа и смену модели, которая снижает конфликт.
2. Прочитайте текущую документацию согласованности для вашей основной версии. Напишите политику на одну страницу: значения по умолчанию для write concern, read concern, read preference и сессий.

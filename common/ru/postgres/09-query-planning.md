# 9. Планирование запросов

## Описание

Эта тема показывает, как PostgreSQL 16 и PostgreSQL 17 планируют и выполняют SQL. Вы узнаёте `EXPLAIN` и `EXPLAIN ANALYZE`. Узнаёте последовательные сканирования, индексные сканирования и bitmap-сканирования. Также узнаёте методы соединения, статистику, `work_mem` и почему `SELECT *` вредит горячим путям.

Сначала завершите тему 8. Нужны индексы, чтобы сравнивать планы. Завершите эту тему до глубокого изучения транзакций.

Используйте один термин для каждого понятия. Планировщик выбирает план. Исполнитель выполняет план. Сканирование читает таблицу или индекс. Метод соединения объединяет два источника строк. Статистика — оценки, которые хранит `ANALYZE`. Горячий путь — запрос, который выполняется часто или должен оставаться быстрым.

## `EXPLAIN` и `EXPLAIN ANALYZE`

`EXPLAIN` печатает план. Он не выполняет запрос (кроме некоторых форм, которые всё равно готовят работу). `EXPLAIN ANALYZE` выполняет запрос и печатает фактические времена и числа строк.

```sql
EXPLAIN
SELECT * FROM items WHERE name = 'nail';

EXPLAIN ANALYZE
SELECT * FROM items WHERE name = 'nail';
```

Полезные опции:

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT * FROM items WHERE qty > 10;

EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)
SELECT * FROM items WHERE qty > 10;
```

Частые опции в PostgreSQL 16 и 17:

- `ANALYZE` — выполнить запрос
- `BUFFERS` — показать shared и read буферы
- `WAL` — показать записи WAL (полезно на записях)
- `SETTINGS` — показать настройки планировщика, которые отличаются от умолчания
- `VERBOSE` — дополнительные детали
- `COSTS` — показать стоимости (по умолчанию вкл.)
- `TIMING` — таймер на узел (по умолчанию вкл. с `ANALYZE`)
- `SUMMARY` — итоговая сводка времени

`EXPLAIN ANALYZE` на `INSERT`, `UPDATE` или `DELETE` **выполняет** изменение. Когда нужен только план, используйте транзакцию и `ROLLBACK`:

```sql
BEGIN;
EXPLAIN ANALYZE UPDATE items SET qty = qty + 1;
ROLLBACK;
```

Читайте текстовый план сверху. Первый узел — корень. Отступ показывает детей. PostgreSQL сначала выполняет детей.

Два числа на каждом узле: оценочная стоимость (`cost=startup..total`) и оценочные строки (`rows=`). После `ANALYZE` также видите `actual time` и `actual rows`. Большой разрыв между оценочными и фактическими строками значит плохую статистику или плохую оценку предиката.

Не настраивайте запрос только по числам стоимости. Используйте фактическое время из `ANALYZE`. Не запускайте `EXPLAIN ANALYZE` на тяжёлой записи в продакшене без плана.

`EXPLAIN` не включает сетевое время до клиента. Не включает циклы приложения.

## Seq scan против index scan против bitmap scan

**Последовательное сканирование** (Seq Scan) читает кучу с начала до конца. Фильтр применяется к каждой строке. Оно дёшево, когда таблица маленькая или фильтр совпадает с большой долей строк.

**Индексное сканирование** идёт по B-tree (или другому индексу) и выбирает совпавшие кортежи кучи. Оно дёшево, когда фильтр избирательный и индекс совпадает с предикатом.

**Сканирование только по индексу** читает индекс и не ходит в кучу, когда карта видимости говорит, что страница целиком видима. `VACUUM` помогает сканированиям только по индексу (тема 11). Столбцы `INCLUDE` помогают сканированиям только по индексу (тема 19).

**Bitmap index scan** строит битовую карту совпавших страниц кучи. Затем **bitmap heap scan** читает эти страницы. PostgreSQL может комбинировать битовые карты через `AND` и `OR` (BitmapAnd, BitmapOr). Bitmap-сканирования хорошо работают, когда совпадает много строк, но не вся таблица, и когда комбинируются два индекса.

```sql
EXPLAIN ANALYZE
SELECT * FROM items WHERE qty > 10 AND name = 'nail';
```

Можно увидеть:

- Seq Scan
- Index Scan using items_pkey
- Index Only Scan
- Bitmap Heap Scan + Bitmap Index Scan

Выбирает планировщик. Тип сканирования в SQL не пишете. Меняете SQL, индексы и статистику.

`SELECT *` часто блокирует сканирование только по индексу, потому что индекс держит не каждый столбец.

Случайный `id = $1` на большой таблице должен использовать индексное сканирование по первичному ключу. Если видите seq scan, проверьте, что таблица не крошечная, что `enable_seqscan` включён (оставьте включённым) и что статистика есть.

Не ставьте `enable_seqscan = off` в продакшене, чтобы принудить индекс. Эта настройка — инструмент отладки.

## Nested loop, hash join, merge join

Когда соединяются два источника строк, планировщик выбирает метод соединения.

**Nested loop**: для каждой строки внешней стороны найти совпадения на внутренней. Индекс на внутреннем ключе соединения делает это быстрым. Nested loop хорош, когда внешняя сторона маленькая.

**Hash join**: построить хеш-таблицу из меньшей стороны (сторона построения), затем зондировать другой стороной. Hash join хорош для больших соединений по равенству без полезного внутреннего индекса. Hash join нужна память (`work_mem`). Если хеш-таблица не умещается, PostgreSQL сбрасывает на диск.

**Merge join**: отсортировать обе стороны по ключу соединения (или использовать отсортированный индекс) и слить. Merge join хорош, когда обе стороны уже упорядочены или когда соединение — большое равенство и сортировка достаточно дешёвая.

```sql
EXPLAIN ANALYZE
SELECT c.email, o.id
FROM customers AS c
JOIN orders AS o ON o.customer_id = c.id;
```

В плане ищите Nested Loop, Hash Join или Merge Join.

Внешние соединения ограничивают некоторые методы. У планировщика всё равно есть варианты. Декартово соединение огромных таблиц — nested loop катастрофы. Сначала фильтруйте.

Метод соединения в SQL не выбираете. Можно:

- добавить индекс на ключ соединения (помогает nested loop)
- переписать запрос так, чтобы одна сторона оставалась маленькой
- поднять `work_mem` для сессии, которая хеширует или сортирует большой набор (следующий раздел)
- выполнить `ANALYZE`, чтобы оценки строк были верными

Не отключайте типы соединений в продакшене (`enable_hashjoin = off`), кроме короткого теста.

PostgreSQL также может использовать параллельные варианты (Parallel Hash Join). Тема 20 разбирает параллельный запрос. Знайте, что перед узлом можете увидеть `Parallel`.

## Статистика: `ANALYZE`, `pg_stat_statements`

Планировщик использует статистику: числа строк, наиболее частые значения, гистограммы и доли NULL. `ANALYZE` (и analyze автоочистки) их собирает.

```sql
ANALYZE items;
ANALYZE;
```

`ANALYZE items` обновляет одну таблицу. `ANALYZE` без имени обновляет базу (все таблицы, которые роль может анализировать).

Посмотреть хранимые числа:

```sql
SELECT relname, reltuples, relpages
FROM pg_class
WHERE relname = 'items';

SELECT * FROM pg_stats
WHERE tablename = 'items';
```

`reltuples` — оценка. После большой загрузки выполните `ANALYZE`. Плохие оценки дают плохие планы (seq scan вместо индекса или неверное соединение).

`default_statistics_target` управляет, сколько деталей хранит `ANALYZE` (по умолчанию 100). Можно поднять на столбец:

```sql
ALTER TABLE items ALTER COLUMN name SET STATISTICS 200;
ANALYZE items;
```

`pg_stat_statements` — расширение. Оно записывает, как часто выполняется каждый текст запроса и сколько времени занимает.

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
```

Модуль должен быть в `shared_preload_libraries`. Многие упакованные серверы его уже включают. Если `CREATE EXTENSION` падает, читайте документацию сервера.

```sql
SELECT query, calls, total_exec_time, mean_exec_time, rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```

Используйте это представление, чтобы найти горячие пути. Затем `EXPLAIN ANALYZE` этих запросов.

`pg_stat_statements` нормализует литералы. Два оператора `SELECT`, которые отличаются только константой, могут делить одну строку.

Не путайте SQL-команду `ANALYZE` с `EXPLAIN ANALYZE`. Первая обновляет статистику. Вторая выполняет запрос для замера.

## Work_mem и сортировки / хеши (обзор)

`work_mem` — объём памяти, который одна операция запроса может использовать для сортировки или хеш-таблицы. Единица — размер памяти. По умолчанию часто `4MB`. Можно задать в `postgresql.conf` или в сессии:

```sql
SHOW work_mem;
SET work_mem = '32MB';
```

Запрос может использовать несколько сортировок и хешей. Каждая операция может использовать до `work_mem`. Сессия с многими операциями может использовать больше одного `work_mem`. `max_connections` умножить на много операций может исчерпать RAM. Не ставьте огромный глобальный `work_mem`.

Когда сортировка не умещается, PostgreSQL сбрасывает на диск (внешняя сортировка слиянием). Когда хеш не умещается, сбрасывает пакетами. Диск медленнее памяти.

Планы показывают это:

- `Sort Method: quicksort Memory: ...`
- `Sort Method: external merge Disk: ...`
- `Hash Batches` больше 1 значит сброс

Используйте `EXPLAIN (ANALYZE, BUFFERS)`, чтобы видеть временные чтения и записи.

`maintenance_work_mem` — отдельная настройка для `VACUUM`, `CREATE INDEX` и `ALTER TABLE`. Не путайте с `work_mem`. Тема 18 глубже разбирает настройки памяти.

Поднимите `work_mem` для одной тяжёлой сессии отчёта, когда видите дисковые сортировки. Затем сбросьте. Глобальное значение держите скромным.

`hash_mem_multiplier` (PostgreSQL 13+) может дать хеш-операциям больше одного `work_mem`. Знайте имя. Читайте документацию до изменения.

Не поднимайте `work_mem`, чтобы скрыть отсутствующий индекс. Сначала исправьте запрос.

## Избегать `SELECT *` на горячих путях

`SELECT *` возвращает каждый столбец. В `psql` при изучении это нормально. На горячих путях это проблема.

Почему вредит:

- Исполнитель читает столбцы, которые приложение не использует.
- Сканирования только по индексу становятся менее вероятными. Индекс содержит не каждый столбец.
- Больше данных идёт по сети.
- `CREATE TABLE` плюс новый столбец меняет форму результата. Клиентский код, который сопоставляет по позиции, может сломаться.
- Столбцы `json` / `text` / `bytea` могут быть большими. `SELECT *` всегда их тянет.

Пишите список столбцов:

```sql
SELECT id, email, created_at
FROM customers
WHERE id = 1;
```

Исключения:

- Админские сессии `psql`
- `RETURNING *` на узкой таблице, когда нужна полная строка
- Быстрое исследование

Для полезных нагрузок `jsonb` выбирайте `id` и нужные ключи (`payload->>'type'`), не весь документ, когда документ большой.

`SELECT t.*` в соединении всё равно тянет каждый столбец `t`. Называйте столбцы.

Широкие таблицы (много столбцов или большой текст) требуют дополнительной осторожности. Вынесите холодные столбцы в другую таблицу, если измерили проблему (поздняя работа над дизайном).

Не используйте `SELECT *` в представлении, которое приложения вызывают на горячем пути. Представления, которые скрывают `*`, всё равно раскрываются во все столбцы.

### Вопросы

#### Теоретические вопросы

1. Почему `SELECT *` блокирует часть сканирований только по индексу?
2. Как `SELECT *` влияет на сеть?
3. Почему новый столбец может сломать клиентов, которые используют `SELECT *`?
4. Когда `SELECT *` приемлем?
5. Что такое горячий путь в этой теме?

#### Простые практические задания

1. Перепишите `SELECT *` как список из трёх столбцов.
2. `EXPLAIN` `SELECT *` против `SELECT id` на таблице с первичным ключом. Запишите оба типа сканирования, если различаются.
3. Добавьте столбец `text`. Покажите, что `SELECT *` теперь его включает.
4. Напишите четыре предложения: столбцы, только индекс, сеть, стабильность.

#### Средние практические задания

1. Сравните размер результата: `psql` с `\a` и широкий `SELECT *` против двух столбцов. Используйте большое значение `text`.
2. Создайте представление как `SELECT * FROM items`. Добавьте столбец в `items`. Выберите из представления. Запишите, что произошло (`*` в представлениях в PostgreSQL раскрывается в момент создания — проверьте и запишите факт).
3. Найдите три прикладных запроса (или напишите три) и отметьте любой `*`.

#### Сложные практические задания

1. Измерьте байты и время для `SELECT *` против узкого списка на 10000 строк со столбцом `text` 1 КБ. Запишите оба замера.
2. Прочитайте, как PostgreSQL хранит представления (`pg_get_viewdef`). Подтвердите, раскрылся ли `*` в момент создания. Запишите результат.

## Обзор темы

Эти вопросы не повторяют вопросы разделов выше. Они покрывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Опишите путь от строки SQL к плану: разбор, перепись, план, выполнение. По одному предложению.
2. Как статистика, индексы и `work_mem` меняют одно и то же соединение?
3. Когда доверять `EXPLAIN` без `ANALYZE`, и когда нужно запускать `ANALYZE`?
4. Почему bitmap-сканирования и hash join оба появляются на больших фильтрах или больших соединениях?
5. Как `pg_stat_statements` говорит, какой запрос объяснять первым?

#### Простые практические задания

1. Выберите один запрос соединения. Выполните `EXPLAIN (ANALYZE, BUFFERS)`. Пометьте тип сканирования и тип соединения.
2. Напишите шпаргалку: опции `EXPLAIN`, три типа сканирования, три типа соединения, `ANALYZE`, `work_mem`, `SELECT *`.
3. Выполните `ANALYZE` на своей схеме. Затем объясните один горячий `SELECT`.
4. Перепишите два горячих запроса, чтобы убрать `SELECT *`.

#### Средние практические задания

1. Создайте отчёт с пятью самыми медленными операторами из `pg_stat_statements` (или пять замеренных вручную запросов, если расширение выключено).
2. Покажите дисковую сортировку, затем исправьте индексом или `work_mem` сессии. Запишите, какое исправление выбрали и почему.
3. Задокументируйте правило команды: у каждого нового API-запроса должен быть сохранённый `EXPLAIN (ANALYZE, BUFFERS)` на данных продакшен-размера.

#### Сложные практические задания

1. Смените `random_page_cost` в сессии и переобъясните один запрос. Запишите, сменился ли тип сканирования. `RESET` настройки.
2. Прочитайте главу «Using EXPLAIN». Напишите разбор одного своего плана на одну страницу только официальными терминами.

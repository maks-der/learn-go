# 20. Архитектура фронтенда / клиента (обзор)

## Описание

Архитектура клиента — структура программ, которыми пользуются люди: браузеры, мобильные приложения и похожие клиенты. Эта тема — обзор. Она разбирает шаблон backend-for-frontend (BFF), офлайн-поведение mobile, server-side rendering против single-page applications в вебе и разницу между согласованностью пользовательского опыта и согласованностью сервиса.

Клиенты — часть системы (тема 1). Они держат состояние, кэшируют и падают на плохих сетях (`net.topics.md`). Завершите темы 1–19 до этой темы. Не считайте браузер тонким украшением перед микросервисами. Сочетайте API с темой 8. Сочетайте идентичность с темой 14.

Используйте один термин для каждого понятия. BFF — бэкенд, который служит одному типу клиента. Офлайн — режим первого класса, не дефект. SSR отрисовывает HTML на сервере. SPA отрисовывает в браузере после загрузки скрипта. Согласованность UX — то, что видит человек. Согласованность сервиса — то, в чём согласны хранилища (тема 7).

## BFF (backend for frontend)

BFF (backend for frontend) — серверный процесс, который существует, чтобы служить одному типу клиента. Веб-BFF формирует данные для браузера. Мобильный BFF формирует данные для мобильного приложения. Каждый BFF говорит с сервисами-владельцами или с модульным монолитом (темы 5 и 12).

BFF может:

- Агрегировать два или три чтения в один вызов клиента
- Скрывать внутренние имена сервисов
- Применять детали аутентификации, специфичные для клиента
- Обрезать поля, которые клиенту не нужны (тема 14, least privilege на данных)

BFF не должен становиться домом доменных правил. Цена и политика выдачи остаются у владельца (темы 6 и 7). Если каждое новое бизнес-правило приземляется в BFF, вы построили второй монолит на краю.

BFF — родственник API gateway (тема 12). Шлюз применяет общую политику края. BFF применяет одну форму клиента. Некоторые команды сочетают их. Запишите правило. Огромный список плагинов — риск.

Не добавляйте BFF для одностраничного студенческого приложения, которое уже говорит с одним API. Добавляйте BFF, когда двум клиентам нужны разные полезные нагрузки или разные часы выпуска (тема 18).

BFF — домен отказа. Если мобильный BFF лежит, мобильное приложение падает, даже если сервисы-владельцы работают. Дайте ему SLO и избыточность (тема 15).

Версионируйте контракт BFF с той же заботой, что любой публичный API (тема 8). Мобильные клиенты заставляют длинные окна совместимости.

## Офлайн на mobile

Мобильные клиенты теряют сеть. Офлайн — нормальный режим. Архитектура должна определить, что человек может делать без сети и что происходит, когда сеть возвращается.

Типичная офлайн-работа:

- Читать локальный кэш недавних данных
- Ставить записи в очередь (запрос выдачи, заметка)
- Показывать ясную метку офлайн
- Переигрывать очередь с ключами идемпотентности (темы 4 и 8)

Конфликт — трудная часть. Сервер может измениться, пока клиент офлайн. Нужно правило: побеждает сервер, побеждает клиент или слияние. CRDT — более поздняя тема осведомлённости (тема 21). Большинство кампусных приложений используют победу сервера плюс запрос пользователю.

Безопасность не исчезает офлайн. Токены живут на устройстве. Используйте хранилище платформы для токенов. Не пишите токены в журналы (тема 14). У шифрованных локальных хранилищ всё равно есть риск кражи устройства. Запишите класс данных, который может сидеть на диске.

Синхронизация — стиль интеграции (тема 13). Она может использовать RPC когда онлайн и файл или очередь сообщений локальных операций. Dual write на устройстве всё равно проблема dual write. Используйте один локальный outbox.

Окна совместимости растут. Пользователи пропускают обновления (тема 18). Сервер должен принимать старых клиентов на окно.

Не обещайте «полное офлайн-оформление», если платежам нужен живой поставщик. Обещайте подмножество, которое можете протестировать.

Измеряйте отставание синхронизации и долю конфликтов (тема 16). Эти числа — атрибуты качества (тема 2).

## Веб: SSR против SPA

SSR (server-side rendering) означает, что первый HTML страницы производится на сервере. Браузер показывает содержимое до или без большой клиентской отрисовки. SPA (single-page application) означает, что сервер отправляет оболочку и скрипты. Браузер строит страницу и говорит с API.

Выгоды SSR:

- Более быстрое первое содержимое для многих документов
- Более простой обмен ссылками и некоторая индексация поиска
- Меньше нужды в большой клиентской среде выполнения на первой отрисовке

Цены SSR:

- CPU сервера на запрос
- Правила кэша для HTML (тема 17)
- Смесь серверных шаблонов и клиентских скриптов, если вы добавляете интерактивность

Выгоды SPA:

- Богатое взаимодействие на странице после загрузки
- Ясный раскол между командами API и UI

Цены SPA:

- Медленная или пустая первая отрисовка, если скрипты большие
- Дополнительная забота об истории, доступности и поиске
- Хранение токенов и поверхность XSS (тема 14). Оставайтесь в защите.

Многие продукты смешивают: SSR для первого документа, затем клиентская отрисовка для виджетов. Эта смесь — структура. Назовите, кто отрисовывает каждую часть.

Выбор архитектурный, когда вы меняете бюджет задержки, проект кэша и форму BFF. Выбор не архитектурный, когда это только слоган фреймворка (тема 1).

Не запускайте SPA, которое болтает с двадцатью внутренними сервисами из браузера. Это утекает топологию и доверие (темы 12 и 14). Используйте один API или BFF.

Измеряйте Largest Contentful Paint или похожий SLI первого содержимого, если веб — продукт. Сочетайте с темой 15.

## Согласованность UX против согласованности сервиса

Согласованность сервиса — согласие хранилищ и процессов о фактах (тема 7). Транзакционная согласованность и eventual consistency — термины сервиса.

Согласованность UX — то, во что человек верит на экране. UI может выглядеть согласованным, пока сервисы ещё догоняют. UI может выглядеть сломанным, пока сервисы правильны.

Примеры:

- Клиент показывает «бронь поставлена» из локального оптимистичного обновления. Сервер позже отвергает бронь. UX и сервис не согласны, пока вы не почините экран.
- Страница каталога устарела 30 секунд из-за кэша. Истина сервиса в порядке. UX старый.
- Две вкладки показывают две цены. У сервиса одна цена. UX несогласован.

Проектируйте UX под согласованность, которая у вас реально есть. Если почта асинхронна (тема 17), не показывайте «почта отправлена» до успеха worker. Показывайте «почта в очереди».

Оптимистичный UI — выбор. Ему нужен видимый путь отказа и идемпотентные записи. Тихий откат — дефект доверия.

Между устройствами один пользователь может видеть два состояния во время синхронизации. Запишите правило. Спиннер или время «последнее обновление» — часть архитектуры, не украшение.

Не заставляйте распределённую транзакцию, чтобы спиннер исчез (темы 11 и 12). Смените предложение на кнопке вместо этого.

Доступность и язык принадлежат сюда. Ошибка, которая появляется только как красная коробка без текста, — несогласованный UX для многих пользователей.

SLI могут включать факты UX: «доля запросов брони, которые показывают окончательный успех или отказ за 10 секунд». Это строже, чем «API 200».

# 9. Клиенты и кэширование

## Описание

Приложение говорит с Redis через клиентскую библиотеку. Кэш хранит результат, чтобы более позднее чтение избежало медленного пути. Эта тема покрывает популярные клиенты, пулы соединений, таймауты, повторы, сериализацию, безопасный обход ключей и шаблоны записи кэша.

Сначала завершите тему 2 (срок и вытеснение) и тему 8 (клиенты Cluster). Эта тема предполагает, что Redis — кэш, а не единственный источник истины, если задание не говорит иное.

Используйте один термин для каждого понятия. Клиент — библиотека или инструмент, который отправляет команды Redis. Соединение — одна сессия TCP (или TLS) к экземпляру. Пул — набор повторно используемых соединений. Таймаут — предел времени ожидания. Повтор — вторая отправка той же логической команды. Сериализация — преобразование объекта приложения в байты, которые хранит Redis. Источник истины — долговечное хранилище (часто SQL или документная база). Попадание — чтение, которое находит пригодное значение в Redis. Промах — чтение, которое не находит. Штампед — много промахов одного ключа одновременно. Негативное кэширование хранит маркер «отсутствует». Джиттер — случайный дополнительный TTL.

## Популярные клиенты и пул соединений

Redis говорит текстовым протоколом (RESP, затем RESP3). Можно отправлять команды через `redis-cli`. Промышленные приложения используют библиотеку на языке приложения.

Частые библиотеки:

- Go: `go-redis` (`github.com/redis/go-redis`)
- Python: `redis-py` (пакет `redis`)
- Node.js: `ioredis` и `node-redis`
- Java: Jedis (синхронный) и Lettuce (асинхронный, реактивный)

Эти имена меняются. Подтвердите текущий официальный или рекомендуемый клиент на [https://redis.io/docs/clients/](https://redis.io/docs/clients/).

Хороший клиент делает больше, чем `SET` и `GET`. Он управляет соединениями. Он разбирает ответы. Он поддерживает конвейеры, Pub/Sub и Cluster или Sentinel, когда нужны эти режимы. Тема 8 объяснила, почему клиент Cluster должен следовать `MOVED`.

Выберите один клиент на язык для нового проекта. Читайте документацию этого клиента про:

- Конструкторы автономного режима, Sentinel и Cluster
- Настройки пула
- Настройки таймаута
- API конвейера и транзакций
- Как клиент отображает ошибки Redis в ошибки языка

Не смешивайте два клиента в одном процессе без причины. Два пула удваивают число соединений.

`redis-cli` остаётся лабораторным инструментом. Когда библиотека падает, воспроизведите ту же команду в `redis-cli`. Это разделение показывает, проблема на сервере или в клиенте.

Версия клиента и версия сервера должны совпадать для новых команд (ACL, Functions, `GEOSEARCH`). Проверьте обе.

Каждая команда Redis нуждается в соединении. Новое рукопожатие TCP на каждый `GET` медленное. Пул держит открытые соединения и выдаёт одно соединение на команду (или на конвейер).

Типичные настройки пула:

- Максимум открытых соединений
- Минимум простаивающих соединений
- Таймаут простоя
- Максимальное время жизни одного соединения

Задайте максимум от конкурентности приложения и от `maxclients` на сервере (`INFO clients`, `CONFIG GET maxclients`). Если 50 процессов приложения каждый открывают 100 соединений, Redis должен принять 5000 клиентов. Это число часто слишком велико.

Одно соединение последовательно. Две горутины или потока не должны делить одно соединение без мьютекса. Пул даёт каждому конкурентному вызывающему своё соединение.

Режим Cluster нуждается в соединениях ко многим узлам. Пул — на узел или общая карта пулов. Sentinel нуждается в соединениях к процессам Sentinel и к текущему основному.

Pub/Sub часто нуждается в выделенном соединении. Соединение в режиме `SUBSCRIBE` не выполняет обычные команды `GET`. Тема 10 покрывает Pub/Sub.

Закройте пул, когда процесс останавливается. Утёкшие соединения остаются в `connected_clients`, пока не истекут.

Не создавайте новый объект клиента внутри горячего обработчика запроса. Создайте один клиент (один пул) при старте процесса.

## Таймауты, повторы, сериализация

Таймаут останавливает бесконечное ожидание. У клиента обычно есть:

- Таймаут соединения — ждать рукопожатие TCP (или TLS)
- Таймаут чтения — ждать ответ
- Таймаут записи — ждать, пока буфер отправки примет команду
- Таймаут пула — ждать свободное соединение

Задавайте таймауты. Отсутствующий таймаут чтения может повесить поток запроса навсегда, если Redis или сеть застопорятся.

Повтор повторяет команду после таймаута, разрыва или `MOVED` (Cluster). Повторы помогают после короткого сетевого сбоя. Повторы также создают риск.

Безопасно повторять без дополнительного дизайна: `GET`, `EXISTS`, `SET` того же полного значения, `PING`.

Небезопасно повторять вслепую: `INCR`, `DECR`, `LPUSH`, `RPOP`, `XADD` без явного id. Первая отправка могла пройти. Повтор тогда применяет команду дважды.

Идемпотентный дизайн (тема 10) использует ключ id запроса, чтобы второе применение было пустой операцией.

Backoff: подождите короткое время, затем повторите. Ограничьте число повторов (например 2 или 3). Не повторяйте в тесном цикле. Этот цикл может усилить нагрузку во время отказа.

Клиенты Cluster повторяют на `MOVED` и `ASK`. Этот повтор — перенаправление, не политика дублирования записи. Вам всё ещё нужна идемпотентность для записей после ошибки TCP.

Не задавайте таймаут чтения короче самой медленной законной команды (большой `LRANGE`, тяжёлый скрипт Lua). Используйте медленный журнал (тема 11), чтобы узнать реальные времена команд.

Redis хранит байты (bulk-строки) и типизированные структуры (хеши, списки, потоки). Redis не знает объекты вашего языка. Вы кодируете. Вы декодируете.

Частые кодировки:

- Простая строка или целое — счётчики, флаги, id
- JSON — читаемый, широкая поддержка инструментов, больше двоичного
- MessagePack — компактные двоичные карты и массивы
- Protocol Buffers (protobuf) — схема, меньшие полезные грузы, генерация кода

Хеш Redis может хранить одно поле на атрибут (`HSET user:42 name Ada`). Эта раскладка позволяет обновить одно поле. JSON в одной строке (`SET user:42 '{"name":"Ada"}'`) обновляется целиком, если не использовать RedisJSON (тема 12).

Выбирайте этими вопросами:

- Нужно ли читать или обновлять одно поле?
- Должны ли люди отлаживать значения в `redis-cli`?
- Размер полезного груза — проблема памяти?
- Многие языки читают один ключ?

JSON в `redis-cli` легко читать. Protobuf в `redis-cli` выглядит как двоичные данные. Нужен шаг декодирования.

Не смешивайте кодировки на одном ключе. `GET` JSON, декодированный как protobuf, падает. Положите кодировку в каталог ключей.

Большие значения стоят ОЗУ и сеть. Сжимайте только когда измерите выигрыш. Сжатие усложняет `redis-cli` и может спрятать полезную структуру.

## `SCAN` вместо `KEYS *`

`KEYS pattern` обходит пространство ключей в основном потоке и возвращает все совпадения. На большом экземпляре `KEYS *` может застопорить Redis надолго. Другие клиенты ждут. В продакшене считайте `KEYS` опасной командой (тема 11).

`SCAN cursor [MATCH pattern] [COUNT hint] [TYPE type]` возвращает новый курсор и пакет ключей. Повторяйте, пока курсор не станет `0`.

```text
SCAN 0 MATCH lab:* COUNT 20
```

`COUNT` — подсказка, не точный размер страницы. Redis может вернуть больше или меньше ключей.

`SCAN` — не снимок. Если ключи появляются или исчезают во время обхода, можно увидеть ключ дважды или пропустить ключ. Это приемлемо для метрик и задач очистки. Это неприемлемо как один согласованный экспорт, если не принимаете предел.

Сканирования коллекций:

- `HSCAN` — большие хеши
- `SSCAN` — большие множества
- `ZSCAN` — большие упорядоченные множества

`HGETALL`, `SMEMBERS` и полный `ZRANGE` имеют тот же класс риска, что и `KEYS`, когда коллекция огромная. Используйте семейство `*SCAN`.

Cluster: `SCAN` — на узел. Нужно сканировать каждый основной (тема 8).

`redis-cli --scan --pattern 'lab:*'` использует `SCAN` за вас.

Не запускайте `KEYS *` на общем или промышленном экземпляре. Используйте `SCAN` в лаборатории, когда практикуете. Отключите или запретите `KEYS` через ACL в продакшене (тема 11).

## Cache-aside, write-through, write-behind

Cache-aside (ленивая загрузка) кладёт логику кэша в приложение:

1. Приложение делает `GET` ключа кэша.
2. При попадании приложение использует значение.
3. При промахе приложение читает источник истины.
4. Приложение делает `SET` ключа кэша (часто с TTL).
5. Приложение возвращает значение.

```text
GET cache:product:1001
# miss
# ... read SQL ...
SET cache:product:1001 <bytes> EX 300
```

Приложение владеет политикой. Redis не вызывает базу. Redis не знает SQL.

При записи в источник истины приложение обновляет или удаляет ключ кэша. Два частых выбора:

- Удалить (`DEL`) ключ кэша. Следующее чтение перезагружает. Это просто.
- Записать новое значение в кэш. Следующее чтение попадает. Нужна та же кодировка, что и путь чтения.

Удаление может гоняться: процесс A читает SQL (старое), процесс B пишет SQL и удаляет кэш, процесс A затем делает `SET` старого значения. Короткие TTL ограничивают окно устаревания. Некоторые коллективы используют поле версии или шаг сравнения.

Если Redis лежит, приложение должно читать источник истины и пропускать кэш (разрыв цепи в теме 12). Cache-aside делает этот путь естественным: промах и ошибка Redis оба могут упасть обратно в SQL.

Не считайте попадание в кэш доказательством, что источник истины всё ещё имеет эту строку. Кэш может быть устаревшим до TTL или инвалидации.

Read-through и write-through переносят шаги загрузки и сохранения в модуль кэша, который приложение вызывает так, будто это база.

Read-through: приложение спрашивает модуль ключ. Модуль делает `GET` Redis. При промахе модуль читает источник истины, делает `SET` Redis и возвращает значение. Обработчик не содержит ветку промаха.

Write-through: приложение пишет через модуль. Модуль пишет источник истины и пишет Redis в том же запросе приложения (два хранилища, один вызов). Запрос пользователя ждёт оба.

В Redis вы всё равно реализуете это в приложении или в библиотеке. Redis сам не загружает SQL.

Read-through прячет путь промаха. Это может быть чище. Это также может прятать стоимость: «простой get» может запустить медленный запрос.

Write-through держит Redis и источник истины ближе в момент записи. Запрос медленнее, чем запись, которая трогает только SQL. Если Redis падает, нужно решить: провалить запрос или писать SQL и принять промах кэша позже.

Не путайте write-through с базой только Redis. Источник истины остаётся долговечным хранилищем, если не проектируете иначе.

Write-behind (write-back) пишет Redis первым (или только Redis в запросе). Фоновый работник пишет источник истины позже.

Запрос пользователя быстрый. Долговечное хранилище отстаёт. Если Redis потеряет ключ до запуска работника (вытеснение, перезапуск без персистентности, ошибка), долговечное хранилище никогда не увидит запись.

Используйте write-behind только когда принимаете этот риск, или когда Redis персистентен и есть очередь повтора (потоки, тема 10), которую потребляет работник.

Не используйте write-behind для денег или юридических записей, если нет долговечного журнала вне летучего кэша.

Cache-aside плюс `DEL` проще, когда источник истины должен побеждать каждый раз.

## Штампед, негативное кэширование, джиттер TTL

Штампед (громовое стадо) случается, когда много клиентов промахивают один ключ сразу. Каждый клиент загружает источник истины. База получает вспышку. Кэш затем получает вспышку `SET`.

Типичные причины:

- Ключ истекает (`TTL` достигает 0), пока трафик высок
- Вытеснение снимает горячий ключ
- Выкат сбрасывает кэш
- Процесс стартует с пустым кэшем (холодный старт)

Эффекты: высокая нагрузка SQL, высокий CPU Redis, более медленные запросы пользователей.

Смягчения:

- Single-flight: только один загрузчик на ключ; другие вызывающие ждут этого загрузчика
- Блокировка (`SET NX EX`) вокруг загрузки (тема 10)
- Мягкий TTL плюс раннее обновление
- Джиттер TTL, чтобы много ключей не истекали в одну секунду
- Прогрев кэша до выката (тема 12)
- Негативное кэширование, чтобы отсутствующая строка не била SQL на каждый запрос

Штампед — задача координации. Redis может держать блокировку или флаг «загружается». Приложение должно его использовать.

Не сбрасывайте все ключи при выкате, если набор большой и горячий. Предпочитайте версионированные ключи или постепенный прогрев.

Промах может значить «в источнике истины нет строки». Если ничего не хранить, каждый запрос плохого id бьёт SQL.

Негативное кэширование хранит маркер на короткий TTL:

```text
SET cache:product:9999:neg 1 EX 30
```

Или вы храните пустой объект JSON с полем типа `{ "missing": true }`. Приложение должно отличать «отсутствует» от «продукт с пустым именем».

Используйте короткий TTL. Негативная запись, которая живёт слишком долго, прячет строку, которую вы только что вставили.

При успешном создании в SQL удалите негативный ключ. Иначе следующее чтение всё ещё может показать «отсутствует».

Не кэшируйте негативно ошибки вроде «SQL лежит». Этот маркер спрятал бы восстановление. Кэшируйте «не найдено», не «нельзя говорить с SQL».

Джиттер TTL добавляет случайное дополнительное время жизни каждому ключу. Если 10 000 ключей продуктов все получают `EX 300`, они могут истечь в одну секунду после массовой загрузки. Следующая секунда — штампед.

```text
# conceptual: 300 seconds plus a random 0–60
SET cache:product:1001 <bytes> EX 347
```

Каждый ключ истекает в разное время. Перезагрузки распределяются по минуте.

Джиттер — не блокировка. Джиттер не помогает одному горячему ключу, который делят все клиенты. Джиттер помогает многим ключам, которые делят один TTL и одно время загрузки.

Выберите диапазон джиттера от базового TTL. TTL 300 секунд плюс 0–30 секунд — часто. Джиттер больше базового TTL делает истечение трудным для рассуждения.

Вытеснение всё ещё может снять много ключей сразу, если память полна. Джиттер не заменяет планирование `maxmemory` (тема 2).

Вероятностное раннее истечение обновляет горячий ключ до того, как TTL станет нулём, с вероятностью, которая растёт по мере сокращения оставшегося времени. Redis не считает вероятность. Это делает приложение. Сочетайте с блокировкой или single-flight, чтобы два ранних обновления не били SQL оба.

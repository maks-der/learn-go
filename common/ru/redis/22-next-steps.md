# 22. Следующие шаги

## Описание

Эта тема превращает справочник в практику. Вы завершаете официальные учения команд, строите слой cache-aside, реализуете ограничитель частоты, запускаете реплику и сравниваете блокировку с опубликованной критикой.

Сначала завершите темы 1–21. Используйте локальную лабораторию. Не используйте общий промышленный экземпляр.

Используйте один термин для каждого понятия. Учение — короткое официальное упражнение. Слой — маленькая библиотека на вашем языке. Реплика — второй Redis, который копирует primary (тема 10). Критика — открытый разбор алгоритмов блокировки (тема 14). Официальная документация остаётся [https://redis.io/docs/](https://redis.io/docs/).

Откройте каждую страницу команды. Запишите сложность и тип возврата. Проверьте `redis_version`, если флага нет.

Redis University ([https://university.redis.io/](https://university.redis.io/)) необязателен. Он не заменяет этот путь.

Предложенный список практики в `redis.topics.md` — второй чеклист. Завершите эти десять пунктов, если ещё нет.

Не пропускайте `SCAN` и всё ещё используйте `KEYS *` на любом экземпляре, который не одноразовая лаборатория.

Добавьте в закладки индекс типов данных: [https://redis.io/docs/data-types/](https://redis.io/docs/data-types/).

## Постройте слой cache-aside на вашем языке

Напишите маленький модуль, не фреймворк.

Требуемое поведение (тема 13, тема 12, тема 21):

- `Get(key)` — `GET` Redis; при промахе загрузить из функции источника; `SET` с TTL и джиттером
- `Invalidate(key)` — `DEL`
- Ошибки Redis — считать промахом, если Redis — кэш; необязательный разрыв цепи
- Один клиент при старте процесса (пул)
- Нет `KEYS`
- Документированный префикс ключей (`cache:`)
- Тесты: попадание, промах, инвалидация, Redis недоступен

Держите источник истины как функцию или интерфейс (`LoadProduct(id)`). Не кладите драйверы SQL в первую версию, если макета достаточно.

Добавляйте негативное кэширование только после того, как простой путь работает.

Сериализация: начните со строк JSON. Отметьте кодирование в комментарии (тема 12).

Не добавляйте write-behind.

Положите модуль в обычную раскладку языка (пакет, класс). Держите меньше нескольких сотен строк.

## Реализуйте ограничитель частоты

Постройте один ограничитель, который могут делить многие процессы (тема 14).

Выберите один алгоритм и задокументируйте почему:

- Фиксированное окно — `INCR` + `EXPIRE` (Lua задаёт срок на первом увеличении)
- Скользящее окно — упорядоченное множество меток
- Token bucket — Lua на одном ключе

Требуемое поведение:

- `Allow(subject) -> yes/no` (и необязательный оставшийся счёт)
- Ключ, безопасный для Cluster, с хеш-тегом, если тестируете Cluster (`{user:42}`)
- TTL или дозаправка, чтобы ключи умирали
- Тесты: под лимитом, на лимите, после сброса окна
- Нет `KEYS`

Используйте долговечный или выделенный Redis, не экземпляр кэша, если нельзя потерять лимиты во время сброса кэша (тема 21). Для лаборатории одного экземпляра достаточно.

Не утверждайте идеальный глобальный ограничитель для дизайна active-active нескольких регионов. Укажите экземпляр как область.

## Запустите реплику локально

Практикуйте тему 10 на своей машине.

Форма:

1. Запустите primary на порту `6379`.
2. Запустите реплику на порту `6380`.
3. `REPLICAOF 127.0.0.1 6379` на реплике.
4. `SET` на primary. `GET` на реплике.
5. `INFO replication` на обоих.

Пример Docker (подстройте имена):

```text
docker run --name redis-p -p 6379:6379 redis
docker run --name redis-r -p 6380:6379 redis
```

Затем `REPLICAOF`, используя хост, который контейнер реплики может достичь (`host.docker.internal` на Docker Desktop или пользовательская сеть и имя контейнера primary). Задокументируйте точные команды, которые сработали.

Подтвердите:

- Реплика только для чтения по умолчанию
- Запись на реплике падает
- После `REPLICAOF NO ONE` старая реплика — автономная копия

Необязательно: включите AOF на реплике и перезапустите. Тема 9.

Не открывайте ни один порт дальше localhost.

Это учение — не Sentinel и не Cluster. Те — дополнительно, если хотите (тема 10, тема 11).

## Сравните реализацию блокировки со статьёй или критикой Redlock

Тема 3 и тема 14 дали `SET NX EX`, снятие Lua, fencing и спор Redlock.

Теперь сделайте письменное сравнение. Реализовывать Redlock не нужно.

Читайте:

- Страницу документации Redis про распределённые блокировки
- Критику вроде эссе Мартина Клеппманна про Redlock (или другую серьёзную открытую критику)
- Необязательно: ответ авторов Redis

Напишите таблицу:

```text
Issue              Simple SET NX EX     Redlock (as described)    Your notes
Pause / GC
Clock / TTL
Failover loss
Fencing token
What it is for
```

Затем реализуйте или повторно используйте простую блокировку на вашем языке:

- Уникальный id держателя
- `SET NX EX`
- Снятие Lua
- Необязательный fence `INCR`

Перечислите, чего ваша блокировка не гарантирует. Укажите применение, которое приемлемо (пересборка кэша одного экземпляра), и применение, которое нет (перевод денег без долговечного fence или ограничения SQL).

Не поставляйте Redlock в промышленную среду только потому, что блог его хвалил. Не запрещайте все блокировки Redis потому, что есть критика. Сопоставляйте инструмент с риском.

Держите записку в одну-две страницы.

# 9. DNS

## Описание

DNS сопоставляет имя с данными. Обычный случай — имя с IP-адресом. Эта тема показывает рекурсивный резолвер против авторитетного. Вы узнаете A, AAAA, CNAME, MX, NS и TXT. Вы узнаете TTL. Вы узнаете `dig`. Вы узнаете DNS over HTTPS и DNS over TLS на уровне осведомлённости.

Завершите эту тему после HTTP. Вы уже используете имена в URL.

Используйте один термин для каждого понятия. Имя — доменное имя вроде `example.com`. Резолвер — программа, которая задаёт вопросы DNS. Авторитетный сервер отвечает из зоны, которую держит. TTL — время, которое кэш может хранить ответ. Не смешивайте рекурсивный резолвер с авторитетным сервером. Не считайте имя одним хостом.

Практикуйтесь с `dig` или `nslookup`. Захватывайте UDP-порт 53, когда запрос открытый. Зашифрованный DNS скрывает запрос от пути. Вы всё равно видите адрес резолвера.

## Рекурсивный резолвер против авторитетного

В операционной системе есть stub-резолвер. Stub отправляет запрос рекурсивному резолверу. Рекурсивный резолвер часто — домашний маршрутизатор, резолвер ISP или публичный резолвер.

Рекурсивный резолвер принимает запрос от stub. Он находит ответ. Он может использовать свой кэш. Если в кэше нет действительных данных, он спрашивает другие серверы. Он начинает с подсказки корня, затем сервер TLD, затем авторитетный сервер зоны. Затем возвращает ответ stub.

Авторитетный сервер отвечает из данных зоны, которые положил администратор или реестр. Ему не нужно рекурсировать для имён в этой зоне. Сервер может быть авторитетным для одних зон и рекурсивным для других запросов. Многие публичные резолверы рекурсируют и не авторитетны для `example.com`.

Цепочка авторитета использует записи NS. Родительская зона перечисляет серверы имён потомка. Вы идёте по NS от корня до зоны.

Stub в обычной настройке ОС не обходит дерево. Stub спрашивает один настроенный резолвер. Дерево можно обойти самому через `dig +trace`, когда инструмент это умеет.

Не открывайте рекурсивный резолвер в публичный Internet на хосте, который не задуман как публичная служба. Открытый резолвер можно злоупотребить. Не меняйте продакшен-DNS без плана отката.

## A, AAAA, CNAME, MX, NS, TXT

Типы записей называют данные, которые возвращает DNS.

- A: адрес IPv4
- AAAA: адрес IPv6
- CNAME: другое имя (псевдоним). Затем клиент ищет это имя
- MX: хост почтового обменника и число предпочтения
- NS: сервер имён зоны
- TXT: текст. Люди используют его для SPF, проверки домена и других утверждений

У имени могут быть A, AAAA, оба или ни одного. Dual stack использует оба, когда оба есть. Happy Eyeballs может пробовать оба семейства.

У CNAME есть правила. Имя, у которого есть CNAME, в обычных правилах зоны не должно иметь других данных. Не ставьте CNAME на вершину зоны, если хост DNS это запрещает. Некоторые хосты используют ANAME или ALIAS как обход поставщика.

Значения MX — имена хостов, не IP-адреса. Для обменника всё равно нужны A или AAAA.

NS у родителя и NS у потомка должны согласиться, иначе получите lame delegation.

TXT может быть длинным. Проверяющий ищет конкретную строку. TXT — не шифрование.

Не кэшируйте адрес в долгоживущей программе без плана TTL. Не считайте заголовок From доказанным, потому что есть MX. MX — путь доставки, не доказательство отправителя.

## TTL

TTL — time to live ответа DNS в кэше. Значение в секундах. Рекурсивный резолвер не должен отдавать кэшированный ответ после конца TTL. Stub и ОС тоже кэшируют.

Длинный TTL снижает запросы и может скрыть смену. Короткий TTL позволяет быстрее перенести адрес. Он увеличивает нагрузку запросов. Некоторые резолверы зажимают очень короткие или очень длинные TTL.

Когда меняете запись A, старые кэши всё ещё держат старый адрес, пока не кончится старый TTL. Планируйте смену до того, как выключите старый сервер. Этот сюрприз — частый отказ.

Отрицательные ответы (NXDOMAIN) тоже имеют TTL из параметров SOA. Неверное «не существует» может закэшироваться.

Приложения, которые хранят IP навсегда, игнорируют DNS. Мобильные клиенты и долгоживущие серверы должны обновлять.

Не ставьте TTL в 0 по привычке. Некоторые кэши всё равно держат минимум. Не снижайте TTL только после начала отказа. Снижайте его до смены.

Тема 13 возвращается к сюрпризам TTL DNS в отладке.

## `dig`

`dig` — инструмент запросов DNS из BIND. Он печатает вопрос, ответ, authority и extra. Он печатает резолвер, который использовал, и время.

Полезные формы:

- `dig example.com A`
- `dig example.com AAAA`
- `dig example.com MX`
- `dig example.com NS`
- `dig example.com TXT`
- `dig @1.1.1.1 example.com A` (спросить конкретный резолвер)
- `dig +short example.com A` (короткий вывод)
- `dig +trace example.com` (обойти дерево)

`nslookup` обычен в Windows. Он может задать тип и сервер. `Resolve-DnsName` — командлет PowerShell. Выучите один инструмент хорошо.

`dig` говорит с резолвером. Это не доказывает, что браузер использует тот же резолвер или тот же кэш. Зашифрованный DNS в браузере может обойти резолвер ОС.

Не заливайте публичный резолвер скриптом. Не запрашивайте имена, которые нет причины запрашивать в цикле. Не считайте SERVFAIL `dig` «сайт лежит» без второго резолвера.

Читайте статус: NOERROR, NXDOMAIN, SERVFAIL, REFUSED.

## DoH / DoT (осведомлённость)

DNS over TLS (DoT) отправляет DNS в сессии TLS, часто на порту 853. DNS over HTTPS (DoH) отправляет DNS в HTTPS, часто на URL резолвера.

Оба скрывают имя запроса от наблюдателя пути, который не резолвер. Резолвер всё равно видит запрос. IP-адреса резолвера всё равно видны на пути.

Факты осведомлённости:

- ОС, браузер или приложение могут выбрать DoH или DoT
- захват домашнего маршрутизатора на UDP 53 может затихнуть
- корпоративным фильтрам, которые опираются на вид UDP 53, нужен новый план
- DoH использует идеи HTTP и TLS из тем 8 и 10

DoH и DoT не заменяют авторитетные серверы. Они защищают хоп stub-рекурсивный. Они не шифруют поздний обход, если рекурсивный резолвер всё ещё использует открытый DNS к авторитету (некоторые резолверы шифруют больше хопов; эта деталь не нужна).

Этот раздел — осведомлённость. Нужно знать имена и что они скрывают. Запускать сервер DoH не нужно.

Не считайте, что зашифрованный DNS делает назначение HTTPS невидимым. SNI и адреса всё равно утекают, пока нет других контролей. Не отключайте политику DoH компании на рабочей машине.

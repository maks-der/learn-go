# 5. Tables and Constraints

## Description

This topic shows how you create tables in PostgreSQL 16 and PostgreSQL 17. You learn `CREATE TABLE`, identity columns, and constraints. You also learn foreign keys, default values, and table inheritance.

Complete topic 4 first. You must know types and `NULL`. Complete this topic before you write joins.

Use one term for each concept. A table is a named set of rows. A constraint is a rule that a row must satisfy. An identity column is a column that PostgreSQL fills from a sequence. Inheritance copies column definitions from a parent table. Prefer composition (foreign keys) over inheritance for new designs.

---

## `CREATE TABLE`

`CREATE TABLE` defines a table name, columns, and table constraints.

```sql
CREATE TABLE customers (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email      text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);
```

Column order is the order that `SELECT *` uses. Name columns explicitly in application SQL.

Useful clauses:

- `IF NOT EXISTS` — do not fail when the table exists
- `TEMPORARY` / `TEMP` — session table; drop at end of session (or transaction)
- `UNLOGGED` — skip WAL; faster; not crash-safe; not replicated
- `INHERITS` — see the inheritance section
- `PARTITION BY` — topic 15

```sql
CREATE TEMP TABLE scratch (id int);
CREATE UNLOGGED TABLE cache_keys (k text PRIMARY KEY, v text);
```

Use `TEMP` for session scratch data. Use `UNLOGGED` only when you can lose the data.

`CREATE TABLE ... AS SELECT` builds a table from a query:

```sql
CREATE TABLE customer_copy AS
SELECT id, email FROM customers;
```

`CREATE TABLE AS` does not copy constraints. Add constraints after, or use `CREATE TABLE` plus `INSERT ... SELECT`.

`ALTER TABLE` adds columns and constraints later. Some `ALTER TABLE` forms rewrite the table. Test on a copy.

`DROP TABLE name;` removes the table. `DROP TABLE name CASCADE;` also drops dependent objects. Use `CASCADE` only when you intend that result.

Name tables in the singular or plural form that your team picks. Use one form. Use `snake_case`.

## `GENERATED ALWAYS AS IDENTITY` (prefer over `serial` for new work)

An identity column uses a sequence. PostgreSQL owns the sequence and ties it to the column.

```sql
CREATE TABLE orders (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    note text
);

INSERT INTO orders (note) VALUES ('first') RETURNING id;
```

Two modes:

- `GENERATED ALWAYS AS IDENTITY` — you must not write the column in `INSERT` unless you use `OVERRIDING SYSTEM VALUE`
- `GENERATED BY DEFAULT AS IDENTITY` — you may supply a value; the sequence fills the rest

```sql
INSERT INTO orders (id, note) OVERRIDING SYSTEM VALUE
VALUES (1000, 'manual');
```

`serial`, `bigserial`, and `smallserial` are old macros. They create a sequence, set `DEFAULT nextval(...)`, and set `NOT NULL`. They do not mark the column as identity. Privileges and dump behavior differ. For new tables, use identity.

```sql
-- old style; do not use for new work
id serial PRIMARY KEY
```

Identity is in the SQL standard. `serial` is not.

View identity:

```sql
SELECT column_name, is_identity, identity_generation
FROM information_schema.columns
WHERE table_name = 'orders';
```

`\d orders` shows `generated always as identity`.

You can add identity to an existing column with `ALTER TABLE ... ADD GENERATED`. You can change the sequence with `ALTER TABLE ... ALTER COLUMN ... SET GENERATED` and `RESTART`.

Do not use `uuid` and identity on the same column. Pick one key style.

## Primary key, unique, check, exclude (high-level)

A **primary key** identifies one row. It is `UNIQUE` and `NOT NULL`. One table has at most one primary key. The primary key can use one column or many columns (composite).

```sql
CREATE TABLE products (
    sku  text PRIMARY KEY,
    name text NOT NULL
);
```

A **unique** constraint forbids duplicate values in the column set. `NULL` handling: many `NULL` values are allowed unless you write `UNIQUE NULLS NOT DISTINCT` (PostgreSQL 15+).

```sql
CREATE TABLE users (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email text NOT NULL UNIQUE
);
```

A **check** constraint is a boolean expression. The row is valid when the expression is `true` or `NULL` (unknown). Write `IS NOT NULL` inside the check when you must reject `NULL`.

```sql
CREATE TABLE prices (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    cents integer CHECK (cents >= 0)
);
```

An **exclusion** constraint (`EXCLUDE`) forbids two rows that match a specified operator. The common case is overlapping ranges with GiST:

```sql
CREATE TABLE reservations (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room  int NOT NULL,
    during tstzrange NOT NULL,
    EXCLUDE USING gist (room WITH =, during WITH &&)
);
```

This example says: two rows must not have the same `room` and overlapping `during`. Topic 20 covers range types in more depth. Know that `EXCLUDE` exists. Use it when `UNIQUE` cannot express the rule.

Constraints can be named:

```sql
CONSTRAINT prices_cents_nonneg CHECK (cents >= 0)
```

Name constraints. Error texts then show a stable name.

`PRIMARY KEY` and `UNIQUE` create an index. `CHECK` does not. `EXCLUDE` creates an index of the stated type.

## Foreign keys and `ON DELETE` actions

A foreign key says that a value must match a primary key or unique key in another table (or the same table).

```sql
CREATE TABLE orders (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL REFERENCES customers (id)
);
```

`REFERENCES customers (id)` is a column foreign key. A table constraint can list several columns.

`ON DELETE` sets what happens when the parent row is deleted:

| Action | Effect |
| --- | --- |
| `NO ACTION` | default; error if child rows exist; check can wait until end of statement |
| `RESTRICT` | error if child rows exist; check is immediate |
| `CASCADE` | delete child rows |
| `SET NULL` | set the foreign column to `NULL` (column must be nullable) |
| `SET DEFAULT` | set the foreign column to its default |

```sql
CREATE TABLE order_lines (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id   bigint NOT NULL REFERENCES orders (id) ON DELETE CASCADE,
    product_sku text NOT NULL REFERENCES products (sku) ON DELETE RESTRICT
);
```

`ON UPDATE` has the same action names. `ON UPDATE CASCADE` updates child keys when the parent key changes. Prefer stable keys so that you rarely need `ON UPDATE`.

A foreign key requires an index on the parent key (the primary key or unique constraint already has one). PostgreSQL does not create an index on the child column. Add an index on `order_id` when you delete parents or join often.

Both tables must be in the same database. A foreign key cannot point at another database.

`NOT VALID` and `VALIDATE CONSTRAINT` allow a two-step add on large tables. Learn that pattern before you lock a large production table.

## Default values and `now()`

A default fills a column when `INSERT` omits that column.

```sql
CREATE TABLE audit_notes (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    body       text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now()
);
```

`DEFAULT now()` uses `now()`. `now()` is the timestamp of the start of the current transaction. All rows inserted in the same transaction get the same `now()` value. That behavior is usually what you want for `created_at`.

Other time functions:

- `CURRENT_TIMESTAMP` — same as `now()`
- `CURRENT_DATE` — date of the transaction start
- `clock_timestamp()` — wall clock; changes inside the transaction
- `statement_timestamp()` — start of the current statement

Use `now()` for defaults. Use `clock_timestamp()` only when you need a different time per statement or per call inside one transaction.

Defaults can be expressions:

```sql
DEFAULT 0
DEFAULT gen_random_uuid()
DEFAULT CURRENT_DATE
```

The default runs when the column is missing from `INSERT`. An explicit `NULL` does not use the default. You must omit the column or use `DEFAULT`:

```sql
INSERT INTO audit_notes (body) VALUES ('hi');
INSERT INTO audit_notes (body, created_at) VALUES ('hi', DEFAULT);
```

`updated_at` defaults do not change on `UPDATE`. Use a trigger (topic 13) or set the column in the `UPDATE` statement.

`ALTER TABLE ... ALTER COLUMN ... SET DEFAULT` changes the default for new rows. It does not rewrite old rows.

## Table inheritance (know it exists; prefer composition)

Table inheritance lets a child table receive columns from a parent table.

```sql
CREATE TABLE vehicles (
    id    bigint,
    label text NOT NULL
);

CREATE TABLE cars (
    doors int NOT NULL
) INHERITS (vehicles);
```

`cars` has `id`, `label`, and `doors`. `INSERT` into `cars` also makes the row visible in `SELECT` from `vehicles` unless you use `ONLY`:

```sql
SELECT * FROM vehicles;
SELECT * FROM ONLY vehicles;
```

Problems:

- Indexes and unique constraints do not cover the whole inheritance tree in the way beginners expect.
- Foreign keys to the parent do not see child rows as the parent key in a reliable way.
- Identity and unique keys on the parent do not give a single sequence across children in a simple way.
- Declarative partitioning (topic 15) is the supported path for splitting large tables.

Prefer **composition**: a `vehicles` table and a `cars` table with `vehicle_id` as a foreign key. Share columns only when a real subtype table needs extra columns, and still prefer a single table plus nullable columns or JSON when the model is simple.

Know inheritance so that you can read old schemas. Do not use inheritance for new application tables. Do not use inheritance as a substitute for partitioning.

`ALTER TABLE parent ADD COLUMN` can cascade to children. Test this on a copy.

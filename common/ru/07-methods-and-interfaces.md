# 7. Методы и интерфейсы

## Описание

Метод — это функция с получателем (`receiver`). Получатель связывает метод с типом. Вы вызываете метод на значении или на указателе этого типа.

Интерфейс — это набор сигнатур методов. Тип удовлетворяет интерфейсу, когда у типа есть эти методы. Вы не пишете ключевое слово implements. Соответствие неявное.

Эта тема показывает value-получатели, pointer-получатели и набор методов каждой формы. Она показывает пустой интерфейс `any`. Она показывает type assertion и type switch. Она показывает частые интерфейсы стандартной библиотеки.

Используйте методы, чтобы дать типу поведение. Используйте интерфейсы, чтобы описать поведение, которое могут предоставить многие типы. Принимайте интерфейсы в параметрах. Возвращайте конкретные `struct` из конструкторов, когда можете.

## Получатели методов: значение и указатель

В объявлении метода получатель стоит в круглых скобках перед именем.

```go
type Point struct {
	X int
	Y int
}

func (p Point) Sum() int {
	return p.X + p.Y
}

func (p *Point) Scale(k int) {
	p.X *= k
	p.Y *= k
}
```

Получатель `(p Point)` — value-получатель. Метод получает копию `struct`. Изменение `p` не меняет значение вызывающего кода.

Получатель `(p *Point)` — pointer-получатель. Метод получает указатель. Изменение `p.X` меняет хранилище вызывающего кода.

Можно вызвать метод с value-получателем на значении или на указателе. Компилятор копирует значение или разыменовывает указатель.

Можно вызвать метод с pointer-получателем на указателе. Можно также вызвать его на адресуемом значении. Компилятор берёт адрес. Значение адресуемо, когда это переменная. Временное значение не адресуемо.

```go
p := Point{X: 1, Y: 2}
p.Scale(2)
(&p).Scale(2)
```

`Point{1, 2}.Scale(2)` не компилируется. Литерал не адресуем.

Набор методов `T` — это набор методов с получателем `T`. Набор методов `*T` — это набор методов с получателем `T` или `*T`. Интерфейсы используют наборы методов. Поздний раздел разбирает соответствие.

Держите одно имя получателя для типа. Короткие имена обычны. Пример: `p` для `Point`.

## Когда выбирать pointer-получатель

Используйте pointer-получатель, когда метод должен менять получатель. Value-получатель не может сохранить изменение.

Используйте pointer-получатель, когда `struct` большой. Value-получатель копирует каждое поле на каждый вызов. Pointer-получатель копирует один указатель.

Используйте pointer-получатель, когда некоторые методы типа уже используют pointer-получатель. Держите один стиль для типа. Смешанные стили путают набор методов.

Используйте pointer-получатель, когда вы объявляете методы интерфейса с pointer-получателями. Только `*T` имеет эти методы в своём наборе методов. `T` не удовлетворяет этому интерфейсу.

Используйте value-получатель, когда тип — маленькое неизменяемое значение. Примеры: методы `time.Time` часто используют value-получатель. Маленький `struct` из чисел может использовать value-получатель для методов только для чтения.

Используйте value-получатель, когда тип — маленький `struct`, который вы считаете значением. Именованный тип `slice` может использовать value-получатель. Именованный тип `map` может использовать value-получатель. Не заменяйте заголовок в этом методе. Value-получатель всё равно делит заголовок `map` или заголовок `slice`. Запись в `map` через value-получатель видна вызывающему коду. Заголовок — копия. Таблица — нет.

Не выбирайте pointer-получатель только потому, что он выглядит обычным. Выбирайте его из-за изменения, размера, согласованности или интерфейсов.

Конструктор, который возвращает `*T`, хорошо сочетается с pointer-методами. Конструктор, который возвращает `T`, хорошо сочетается с value-методами. Можно всё равно вернуть `T` и брать адреса в месте вызова.

Получатели `nil` возможны. Метод с pointer-получателем может получить `nil`. Проверяйте `nil`, когда это состояние допустимо. Пример: метод узла связного списка.

## Интерфейсы: неявное соответствие

Тип интерфейса перечисляет методы. Тип удовлетворяет интерфейсу, когда набор методов этого типа содержит каждый перечисленный метод. Вы не объявляете связь.

```go
type Speaker interface {
	Speak() string
}

type Dog struct {
	Name string
}

func (d Dog) Speak() string {
	return d.Name
}

func say(s Speaker) {
	fmt.Println(s.Speak())
}
```

`Dog` удовлетворяет `Speaker`. `say(Dog{Name: "Rex"})` допустим. Дополнительное ключевое слово не нужно.

Имена методов и сигнатуры должны совпадать. `Speak() string` не равно `Speak() int`. Дополнительные методы у `Dog` допустимы. Отсутствующие методы означают, что тип не удовлетворяет интерфейсу.

Если у `Speak` pointer-получатель, `Dog` не удовлетворяет `Speaker`. `*Dog` удовлетворяет `Speaker`. Присвойте `&Dog{}` переменной `Speaker`.

Значение интерфейса имеет две части: динамический тип и динамическое значение. Нулевое значение интерфейса — `nil`. Обе части не заданы.

```go
var s Speaker
fmt.Println(s == nil)
s = Dog{Name: "Rex"}
```

Типизированный указатель `nil` в интерфейсе — не интерфейс `nil`. `var d *Dog; var s Speaker = d` делает `s == nil` ложным. Эта ошибка появляется в возвратах ошибок. Проверяйте конкретный указатель до сохранения его в интерфейс.

Держите интерфейсы маленькими. Один или два метода — хороший размер. Стандартная библиотека использует маленькие интерфейсы.

Называйте интерфейсы глаголом или суффиксом `-er`, когда у них один метод. Примеры: `Speaker`, `Reader`, `error`.

## Пустой интерфейс `any` / `interface{}`

У пустого интерфейса нет методов. Каждый тип ему удовлетворяет. Предобъявленное имя `any` — псевдоним `interface{}`. Используйте `any` в новом коде. Go 1.18 добавил `any`. Оба имени — один тип.

```go
var x any
x = 3
x = "hi"
x = Point{X: 1}
```

`x` может хранить любое значение. Нельзя вызывать методы на `x` без type assertion. Нельзя использовать `x` как `int` без шага преобразования.

`fmt.Println` принимает `...any`. Многие API используют `any`, когда хранят неизвестные значения. Пример: `map[string]any` для свободного объекта JSON.

Предпочитайте настоящий интерфейс, когда знаете методы. `any` прячет тип. Вызывающий код должен делать assertion. Тесты становятся труднее.

Значение `any` равное `nil` — интерфейс `nil`. У `var x any` проверка `x == nil` истинна. После `x = (*int)(nil)` проверка `x == nil` ложна.

Не используйте `any`, чтобы избежать проектирования. Используйте `struct`, параметр обобщённого типа или маленький интерфейс, когда можете.

`any` — не особый тип среды выполнения сверх `interface{}`. Инструменты и документы могут всё равно показывать `interface{}`.

## Type assertion и type switch

Type assertion читает динамический тип значения интерфейса.

```go
var s Speaker = Dog{Name: "Rex"}
d := s.(Dog)
```

`s.(Dog)` успешен, когда динамический тип — `Dog`. Результат — значение `Dog`. Assertion вызывает `panic`, когда тип не совпадает.

Форма comma-ok не вызывает `panic`.

```go
d, ok := s.(Dog)
if !ok {
	fmt.Println("not a Dog")
}
```

Можно сделать assertion к типу интерфейса. Динамическое значение должно удовлетворять этому интерфейсу.

Type switch выбирает ветку по динамическому типу.

```go
switch v := s.(type) {
case Dog:
	fmt.Println(v.Name)
case *Dog:
	fmt.Println(v.Name)
default:
	fmt.Println("other")
}
```

У `v` тип совпавшей ветки. В `default` у `v` тот же тип, что у `s`.

Не используйте type switch как первый проект. Предпочитайте методы на интерфейсе. Используйте type switch на границе. Примеры: декодировать значение, обработать несколько известных типов или адаптировать старые API.

Assertion к типу указателя не совпадает с типом значения. `*Dog` не равен `Dog`. Включите ветку, которую вы сохраняете.

Assertion на интерфейсе `nil` вызывает `panic` в форме с одним значением. Форма comma-ok возвращает `ok == false`.

## Частые интерфейсы: `error`, `fmt.Stringer`, `io.Reader`, `io.Writer`

У интерфейса `error` один метод.

```go
type error interface {
	Error() string
}
```

`error` предобъявлен. Функции возвращают `error` как последний результат. Ошибка `nil` означает успех. Любой тип с `Error() string` может быть ошибкой. Используйте `errors.New` и `fmt.Errorf` в обычном коде. Следующая тема подробно разбирает обработку ошибок.

У `fmt.Stringer` один метод.

```go
type Stringer interface {
	String() string
}
```

`fmt` вызывает `String` для глаголов вроде `%s` и `%v`. Реализуйте `String` для ясной формы печати. Не вызывайте `panic` в `String`.

У `io.Reader` один метод.

```go
type Reader interface {
	Read(p []byte) (n int, err error)
}
```

`Read` заполняет `p` байтами. Он возвращает число и ошибку. `io.EOF` отмечает конец. Многие типы — читатели: файлы, буферы, тела HTTP.

У `io.Writer` один метод.

```go
type Writer interface {
	Write(p []byte) (n int, err error)
}
```

`Write` пишет байты из `p`. `fmt.Fprint` пишет в любой `io.Writer`. `os.Stdout` — писатель. `bytes.Buffer` — читатель и писатель.

```go
var buf bytes.Buffer
fmt.Fprint(&buf, "hello")
```

Эти четыре интерфейса маленькие. Можно удовлетворить им одним методом каждый. Можно тестировать через `bytes.Buffer` и `strings.NewReader`.

Не пишите `Read` или `Write`, если вы не даёте документированный смысл. Неверные правила `io.EOF` ломают вызывающий код.

## Композиция интерфейсов

Можно встраивать интерфейсы в интерфейс. Новый интерфейс включает все методы.

```go
type ReadWriter interface {
	io.Reader
	io.Writer
}
```

`ReadWriter` требует `Read` и `Write`. Тип, у которого уже есть оба метода, удовлетворяет `ReadWriter`. `*bytes.Buffer` — пример.

Стандартная библиотека использует эту форму. `io.ReadCloser` встраивает `Reader` и `Closer`. `io.ReadWriteCloser` встраивает больше.

```go
type Closer interface {
	Close() error
}

type ReadCloser interface {
	io.Reader
	Closer
}
```

Композиция держит интерфейсы маленькими. Вы добавляете имена без нового списка методов. Вызывающий код, которому нужен только `Read`, всё равно принимает `ReadCloser`.

Тип не встраивает интерфейс, пока вы не напишете это в типе. Соответствие остаётся неявным. `*os.File` удовлетворяет `ReadWriter`, потому что у него есть методы.

Не компонуйте большие интерфейсы. Большой интерфейс трудно удовлетворить и трудно имитировать. Компонуйте два или три маленьких интерфейса.

Можно встроить интерфейс в `struct`. Тогда `struct` продвигает эти методы. Встроенное поле не должно быть `nil`, когда вы вызываете продвинутый метод. Этот шаблон — обёртка, не подкласс.

Называйте составной интерфейс по совместной работе. Не изобретайте новый метод, который только пересылает вызов без причины.

## Правило «принимайте интерфейсы, возвращайте структуры»

Это правило проектирования. Параметры функций принимают типы интерфейсов. Конструкторы и вспомогательные функции возвращают конкретные типы `struct`.

```go
type Store struct {
	path string
}

func NewStore(path string) *Store {
	return &Store{path: path}
}

func Save(w io.Writer, data []byte) error {
	_, err := w.Write(data)
	return err
}
```

`NewStore` возвращает `*Store`. Вызывающий код видит все методы `Store`. Можно добавить методы позже без нового интерфейса.

`Save` принимает `io.Writer`. Вызывающий код передаёт файл, буфер или тестовый писатель. `Save` не зависит от `*os.File`.

Если `NewStore` возвращал интерфейс, вызывающий код не мог бы вызывать дополнительные методы. Тестам нужен был бы более широкий интерфейс. Новые методы ломали бы интерфейс или оставались скрытыми.

Возвращайте интерфейс, когда нужно скрыть тип. Примеры: вы возвращаете один из нескольких типов, или нужно держать конкретный тип неэкспортируемым и маленьким. Эти случаи — исключение.

Принимайте конкретный тип, когда функции нужен именно этот тип и другой тип не имеет смысла. Не изобретайте интерфейс для одной реализации в том же пакете без нужды в тесте.

Параметр типа `any` — плохая замена маленькому интерфейсу. Укажите методы, которые вам нужны.

Это правило работает с неявным соответствием. Вам не нужно менять конкретный тип, чтобы добавить `io.Writer` в список параметров. Нужны только методы.

## Ограничение `comparable` (обзор)

`comparable` — предобъявленный интерфейс. Вы используете его как ограничение параметра типа. Аргумент типа должен поддерживать `==` и `!=`.

```go
func Contains[T comparable](s []T, v T) bool {
	for i := range s {
		if s[i] == v {
			return true
		}
	}
	return false
}
```

`Contains` работает для `int`, `string` и других сравнимых типов. `Contains` не работает для `[]int` как `T`. `slice` не сравнимы. `map` и функции не сравнимы.

Сравнимые типы включают булевы значения, числа, строки, указатели, каналы, массивы сравнимых элементов и `struct` сравнимых полей. Значения интерфейсов сравнимы. Сравнение двух интерфейсов вызывает `panic`, когда динамические типы не сравнимы.

Go 1.20 позволяет обычным типам интерфейсов удовлетворять `comparable` как ограничению. Можно писать `map[K]V` с `K`, ограниченным `comparable`. Это правило для ключей `map`.

`comparable` — не обычный интерфейс для переменных. Вы не пишете `var x comparable` в обычном коде. Вы используете `comparable` в списке параметров типа.

Не используйте `comparable`, чтобы принудительно получить `==` у типов, которым нужен свой метод равенства. Напишите метод `Equal` или передайте функцию, когда равенство — не встроенный оператор.

Этот раздел — обзор. Поздняя тема подробно разбирает обобщения. Помните, что ключам `map` и `==` нужны сравнимые типы.

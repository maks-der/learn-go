# 3. Зачем существуют партиции

## Описание

Топик — набор партиций. Партиции существуют, чтобы Kafka могла писать и читать параллельно. Партиции также задают единицу порядка. Эта тема объясняет параллельную работу, правила порядка, записи с ключом, ключи null и как выбрать число партиций.

Завершите эту тему после темы 2. Завершите эту тему до настройки продюсеров. Используйте один термин для каждого понятия. Порядок в Kafka — на партицию. Партиционер — логика продюсера, которая выбирает партицию. Партиционер по умолчанию использует ключ, когда ключ не null.

Партиции можно добавить в топик. Число партиций в Apache Kafka уменьшить нельзя. Выбирайте число осторожно.

## Параллельная запись и чтение

Одна партиция — один упорядоченный журнал на одном брокере-лидере. Лидер обрабатывает все записи в эту партицию. Лидер обрабатывает обычные чтения этой партиции. У одной партиции есть предел пропускной способности: диск, сеть и CPU на этом лидере.

Много партиций позволяют многим лидерам работать одновременно. Партиция 0 может жить на брокере 1. Партиция 1 может жить на брокере 2. Продюсеры могут писать в обе партиции одновременно. Консьюмеры в одной группе могут читать обе партиции одновременно.

Параллельная запись не означает, что один процесс продюсера всегда быстрее. Один продюсер всё равно собирает пакеты и отправляет в несколько партиций. Кластер может принять большую суммарную нагрузку, когда нагрузка распределена.

Параллельное чтение в одной группе ограничено числом партиций. Нельзя иметь больше активных читателей, чем партиций в этой группе. Тема 6 снова покрывает это правило.

Не создавайте тысячи партиций без причины. Каждая партиция использует память и файлы на брокере. Каждая партиция добавляет работу контроллеру и ребалансам консьюмеров.

## Порядок на партицию, не на топик

Kafka гарантирует порядок только внутри одной партиции. Если запись A добавлена до записи B в той же партиции, консьюмер этой партиции видит A до B.

Kafka не гарантирует порядок между партициями. Запись A в партиции 0 и запись B в партиции 1 могут прийти к консьюмерам в любом чередовании.

Если нужен полный порядок для потока, используйте одну партицию. Этот выбор убирает параллельных консьюмеров в одной группе. Если нужен порядок на сущность, используйте ключ, чтобы все записи этой сущности шли в одну партицию.

Не предполагайте, что «топик упорядочен», потому что вы отправили последовательность из одного потока. Партиционер по умолчанию может отправить соседние записи с разными ключами в разные партиции.

Время на машине продюсера — не порядок. Порядок — порядок добавления на лидере этой партиции.

## Записи с ключом и партиционер по умолчанию

Партиционер выбирает партицию для записи. Продюсер запускает партиционер до отправки записи.

Партиционер по умолчанию использует эту идею: если у записи есть ключ, хешировать ключ, затем отобразить хеш на партицию. Все записи с одним ключом идут в одну партицию, пока число партиций не меняется.

Хеш — не то, что вы считаете вручную в ежедневной работе. Вы выбираете ключ, который идентифицирует сущность, которая должна оставаться упорядоченной.

Если позже добавить партиции, хеш отображается на новый номер партиции для некоторых ключей. Записи с тем же ключом могут пойти в новую партицию после изменения. Старые записи остаются на старой партиции. Порядок на ключ может сломаться через изменение. Планируйте число партиций до того, как долго полагаться на порядок по ключу.

В некоторых клиентах можно написать свой партиционер. Делайте это только когда хеша ключа по умолчанию недостаточно. Задокументируйте правило. Протестируйте его.

## Ключ null и sticky / round-robin партиционеры

У записи может быть ключ null. Поведение по умолчанию для ключа null — не «хешировать ключ». Современные Java-клиенты используют sticky-партиционер для ключей null. Продюсер отправляет пакет в одну партицию, затем переходит к другой, когда пакет полон или истекает время linger. Эта схема улучшает пакетирование.

Старые клиенты и некоторые инструменты используют round-robin для ключей null. Round-robin отправляет соседние записи в соседние партиции. Пакеты остаются маленькими.

Консольные продюсеры часто отправляют строки без ключа. Эти записи распределяются по партициям. Не используйте консоль с пустыми ключами, когда тестируете порядок по ключу.

Если нужно распределение и не нужен порядок по ключу, ключ null допустим. Если нужен порядок на сущность, задайте ключ. Не смешивайте «порядок на сущность» с ключами null.

Некоторые клиенты позволяют задать поле партиции на записи. Этот выбор пропускает партиционер. Используйте его только когда есть ясное правило назначения.

## Выбор числа партиций (трудно уменьшить)

Выбирайте число партиций при создании топика. Используйте эти вопросы:

- Какую нагрузку записи примет этот топик?
- Сколько консьюмеров вы хотите в одной группе на пике?
- Сколько у вас брокеров?
- Нужен ли полный порядок? Если да, используйте одну партицию.

Обычное учебное значение по умолчанию — 3 партиции на ноутбуке. Обычный старт в продакшене — небольшое число, которое всё ещё позволяет добавить консьюмеров, затем вы добавляете партиции, если нагрузка растёт.

Число партиций можно увеличить. В Apache Kafka его нельзя уменьшить. Лишние пустые партиции всё равно стоят память и файлы. Лишние партиции меняют отображение хеша ключа.

Фактор репликации — отдельный выбор. Число партиций — про параллельность и порядок. Фактор репликации — про копии. Не повышайте партиции, когда нужны только дополнительные копии. Вместо этого добавляйте брокеров и реплики.

Просматривайте число с командой, которая потребляет топик. У коннектора или потоковой задачи могут быть свои пределы на партицию.

# 17. Клиентские приложения

## Описание

Эта тема показывает, как программы подключаются к PostgreSQL 16 и PostgreSQL 17. Вы узнаёте строки подключения libpq, режимы пула PgBouncer, драйверы (`psycopg`, `pgx`, JDBC), подготовленные операторы, `LISTEN` / `NOTIFY` и `COPY`.

Сначала завершите тему 16. Вы знаете, что реплика только на чтение. Завершите эту тему до смены настроек памяти.

Используйте один термин для каждого понятия. libpq — официальная клиентская библиотека C. Строка подключения — URI или список ключ-значение, который понимает libpq. Пул переиспользует сессии сервера. PgBouncer — частый пулер. Драйвер — привязка языка. Подготовленный оператор — разобранный оператор, который выполняете с параметрами. `COPY` — команда массовой передачи. Этот справочник рассчитан на PostgreSQL 16 и PostgreSQL 17.

## Строки подключения и параметры `libpq`

Тема 1 показала URI. libpq также принимает строки ключевых слов:

```text
host=localhost port=5432 dbname=shop user=shop_app sslmode=verify-full
```

Форма URI:

```text
postgresql://shop_app@localhost:5432/shop?sslmode=verify-full&connect_timeout=5
```

Частые параметры:

| Имя | Роль |
| --- | --- |
| `host` | имя хоста или путь к Unix-сокету |
| `port` | по умолчанию `5432` |
| `dbname` | база |
| `user` | роль входа |
| `password` | предпочитайте `.pgpass` или хранилище секретов |
| `sslmode` | тема 12 |
| `connect_timeout` | секунды ожидания TCP-подключения |
| `application_name` | видно в `pg_stat_activity` |
| `options` | опции в стиле командной строки сервера |

Переменные окружения: `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`, `PGSSLMODE`, `PGAPPNAME`. Параметр в строке перекрывает окружение.

`application_name` помогает эксплуатации:

```text
postgresql://shop_app@localhost:5432/shop?application_name=shop-api
```

```sql
SELECT application_name, state, query
FROM pg_stat_activity
WHERE datname = current_database();
```

libpq — основа для `psql`, многих драйверов и `pg_dump`. Если драйвер документирует «параметры libpq», таблица выше применяется.

Не кладите пароль в списки процессов или журналы CI. Не используйте `sslmode=disable` в сети, которой не доверяете. Не делите один `application_name` на каждый микросервис, если нужно отлаживать подключения.

Официально: [https://www.postgresql.org/docs/17/libpq-connect.html](https://www.postgresql.org/docs/17/libpq-connect.html).

## Пулы: PgBouncer (транзакция против сессии)

Каждая сессия PostgreSQL использует память и процесс (или слот backend). Веб-приложение, которое открывает одну сессию на HTTP-запрос, исчерпает `max_connections`. Пул держит меньший набор сессий сервера и выдаёт их клиентам.

**PgBouncer** — популярный пулер. Стоит между приложением и PostgreSQL. Три режима пула:

- **session** — одно подключение сервера на всё клиентское подключение. Все возможности работают. Выигрыш пула мал, если клиенты остаются подключёнными.
- **transaction** — подключение сервера возвращается в пул на `COMMIT` или `ROLLBACK`. Высокое переиспользование. Многие возможности сессии ломаются.
- **statement** — возврат после каждого оператора. Редко. Ломает многооператорные транзакции.

Возможности, которым нужен режим **session** (или прямое подключение):

- `LISTEN` / `NOTIFY`
- временные таблицы, которые переживают транзакции
- `SET`, который должен длиться сессию клиента
- консультативные блокировки, удерживаемые между транзакциями
- подготовленные операторы на сессии сервера, если PgBouncer не настроен их отслеживать

Режим транзакции — обычный выбор для stateless HTTP API с короткими транзакциями. Режим сессии — обычный выбор для работника, который делает `LISTEN` или держит состояние.

PgBouncer аутентифицирует клиентов и открывает подключения сервера по конфигурации. Всё равно используете роль с наименьшими привилегиями (тема 12). Всё равно ограничиваете `max_connections` на PostgreSQL (тема 18 и тема 19).

Не ставьте `max_connections` в 1000 и не пропускайте пул. Не используйте пул транзакций и затем полагайтесь на `LISTEN`. Не запускайте PgBouncer как публичный интернет-прокси без TLS и аутентификации.

Официальный сайт: [https://www.pgbouncer.org/](https://www.pgbouncer.org/).

## Драйверы: `psycopg`, `pgx`, JDBC

Драйвер отправляет старт, запросы и `COPY` через протокол PostgreSQL. Многие драйверы используют libpq. Некоторые говорят протоколом на языке.

**`psycopg`** — обычный драйвер Python (psycopg 3). Поддерживает строки подключения, параметры и `COPY`. Используйте bind-параметры. Не собирайте SQL через f-строки.

**`pgx`** — частый драйвер Go. Может использовать протокол без libpq. Строки подключения всё равно похожи на URI libpq. Пути тем в этом репозитории, которые используют Go, должны предпочитать `pgx` с пулом (`pgxpool`) в приложении плюс PgBouncer, когда много хостов приложения делят один кластер.

**JDBC** (`org.postgresql.Driver`) — обычный драйвер Java. Форма URL — `jdbc:postgresql://host:5432/shop`. У JDBC свои продукты пула (HikariCP). Те же правила сессия-против-транзакции применяются, если второй пулер стоит впереди.

Все три должны:

- использовать параметры (`$1` или `?` как документирует драйвер)
- задавать `application_name`
- закрывать или возвращать подключения
- запрашивать `sslmode`, который совпадает с темой 12
- обрабатывать ошибки и повторы без двойного `INSERT`, если фиксация неопределённа

```python
# Python idea (psycopg 3)
# conn.execute("SELECT id FROM shop.items WHERE name = %s", ("nail",))
```

```go
// Go idea (pgx)
// conn.Query(ctx, "SELECT id FROM shop.items WHERE name = $1", "nail")
```

Не журналируйте полные строки подключения. Не отключайте TLS в продакшене, чтобы «заставить драйвер работать». Не смешивайте два пула в одном процессе без плана размера (пул драйвера умножить на PgBouncer умножить на `max_connections`).

## Подготовленные операторы и `PREPARE`

Подготовленный оператор — разбор и анализ, который сессия хранит. Затем `EXECUTE` с параметрами. Протокол делает ту же работу без SQL `PREPARE`, когда драйвер отправляет сообщение parse.

Форма SQL:

```sql
PREPARE item_by_name (text) AS
    SELECT id, qty FROM shop.items WHERE name = $1;

EXECUTE item_by_name('nail');
DEALLOCATE item_by_name;
```

Выгоды:

- параметры остаются вне текста SQL (безопаснее склейки)
- сервер может пропустить повторный разбор
- `pg_stat_statements` видит нормализованную форму

Цены:

- план может остаться общим; разовый план может быть лучше для редкого значения
- prepare живёт в сессии; пул транзакций может сломать безымянные или привязанные к сессии prepare
- `PREPARE` на сессию, не на кластер

Драйверы часто готовят неявно после нескольких повторов. Можно выключить, когда планы становятся плохими (настройки драйвера вроде «prepare threshold»).

`EXPLAIN EXECUTE item_by_name('nail');` показывает план execute.

Не склеивайте пользовательский текст в `PREPARE` (это мимо цели). Не считайте подготовленный оператор кэшем через режим транзакции PgBouncer. Не держите тысячи именованных prepare в долгой сессии без `DEALLOCATE`.

Официально: [https://www.postgresql.org/docs/17/sql-prepare.html](https://www.postgresql.org/docs/17/sql-prepare.html).

## Listen / notify

`NOTIFY` отправляет полезную нагрузку всем сессиям, которые делают `LISTEN` на том же канале в той же базе. Notify виден после фиксации. Откат не уведомляет.

```sql
-- session A
LISTEN shop_jobs;

-- session B
NOTIFY shop_jobs, 'order:42';
```

В `psql` сессия A печатает асинхронное уведомление после фиксации сессии B (простой `NOTIFY` автофиксируется). В драйвере нужно опрашивать или использовать API драйвера для уведомлений.

Правила:

- имена каналов — идентификаторы
- полезная нагрузка — `text` (есть лимит длины; держите маленькой; кладите ключ, не документ)
- слушатели должны использовать сессию, которая остаётся подключённой
- режим транзакции PgBouncer — неверный пул для слушателей
- `NOTIFY` — не очередь заданий с повтором и постоянством

Используйте `LISTEN` для «проснись и затем `SELECT` таблицу работ». Храните работу в таблице. Notify — только сигнал.

Не используйте `NOTIFY` как единственное хранилище заказа. Не отправляйте мегабайты в полезной нагрузке. Не делайте `LISTEN` на новом подключении на каждый HTTP-запрос.

Официально: [https://www.postgresql.org/docs/17/sql-notify.html](https://www.postgresql.org/docs/17/sql-notify.html), [https://www.postgresql.org/docs/17/sql-listen.html](https://www.postgresql.org/docs/17/sql-listen.html).

## COPY для массовой загрузки

`COPY` перемещает строки между таблицей и файлом или потоком. Это быстрый путь массовой загрузки и выгрузки. Это одна транзакция, если не разбить файлы.

```sql
COPY shop.items (name, qty) FROM STDIN WITH (FORMAT csv, HEADER true);
```

В `psql` `\copy` — вариант на стороне клиента. `\copy` читает файл на хосте клиента. SQL `COPY` по пути файла выполняется на сервере и нуждается в суперпользователе (или выданной роли на настроенной программе). Для загрузок приложения предпочитайте `\copy` или API `COPY` драйвера.

```text
\copy shop.items (name, qty) FROM 'items.csv' WITH (FORMAT csv, HEADER true)
```

Выгрузка:

```text
\copy shop.items TO 'items_out.csv' WITH (FORMAT csv, HEADER true)
```

Двоичный формат быстрее для больших числовых таблиц. CSV проще отлаживать. Представление `NULL` должно совпадать с файлом.

`COPY` не запускает построчные триггеры `BEFORE INSERT` более дешёвым способом, который их пропускает; строковые триггеры всё равно выполняются. Операторные триггеры и ограничения всё равно применяются. Отключайте индексы или ограничения только с письменным планом.

Не собирайте 100000 однострочных операторов `INSERT`, если доступен `COPY`. Не запускайте серверный `COPY` из пути, который пользователь ОС `postgres` не должен читать. Не загружайте CSV без правила заголовка и списка столбцов.

Официально: [https://www.postgresql.org/docs/17/sql-copy.html](https://www.postgresql.org/docs/17/sql-copy.html).

## Обзор темы

Эти вопросы не повторяют вопросы разделов выше. Они покрывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Как `application_name`, пул и `pg_stat_activity` помогают отладить застрявший API?
2. Какие возможности этой темы принуждают пул сессии или прямое подключение?
3. Как bind-параметры, `PREPARE` и `COPY` каждый перемещают данные без SQL, склеенного строками?
4. Почему `NOTIFY` — сигнал, а `COPY` — массовый путь, не продукт очереди?
5. Коллега открывает новую сессию PostgreSQL на каждый HTTP-запрос и склеивает SQL. Какие факты из этой темы вы используете в ответе?

#### Простые практические задания

1. Подключитесь URI, который задаёт `application_name`. Выполните `SELECT 1`. Выполните `\copy` одной таблицы.
2. Напишите шпаргалку: ключи libpq, три режима пула, три драйвера, `PREPARE`, `LISTEN`, `COPY` против `\copy`.
3. `PREPARE` и `EXECUTE` одного `SELECT`. `DEALLOCATE`.
4. Откройте две сессии и завершите один круговой путь `LISTEN` / `NOTIFY`.

#### Средние практические задания

1. Напишите политику подключения приложения: поля URI, режим пула, драйвер, макс. размер пула против `max_connections`.
2. Загрузите 5000 строк CSV через `\copy`. Затем `LISTEN` не требуется. Запишите времена и `pg_stat_activity` во время загрузки.
3. Нарисуйте два хоста API Go, режим транзакции PgBouncer и PostgreSQL. Посчитайте подключения на каждом переходе для 50 одновременных запросов.

#### Сложные практические задания

1. Соберите маленькую программу, которая использует параметры, `COPY` внутрь и `RETURNING` на однострочной вставке. Откажите URI с паролем.
2. Сопоставьте эту тему с официальными страницами libpq, `PREPARE`, `NOTIFY` и `COPY`. Добавьте один параметр libpq, которого эта тема не перечислила.

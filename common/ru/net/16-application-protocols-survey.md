# 16. Протоколы приложения (обзор)

## Описание

Многие приложения говорят протоколом выше TCP или UDP. Эта тема — обзор: почта (SMTP и IMAP), FTP против SFTP, WebSockets, gRPC на HTTP/2, MQTT и краткий вид проводных протоколов Redis и Postgres.

Используйте один термин для каждого понятия. Обзор называет задачу каждого протокола. Он не заменяет полный справочник почты или баз данных. Завершите эту тему после HTTP, TLS и сокетов.

Практикуйтесь с публичной документацией и с инструментами, которые уже есть (`curl`, почтовый клиент, клиент базы данных). Не атакуйте почтовый сервер или базу данных, которыми не владеете.

## SMTP / IMAP (почта)

SMTP — протокол, который двигает сообщение к почтовому ящику. Почтовый клиент или почтовый сервер использует SMTP для отправки или ретрансляции. Обычный порт отправки в Internet сегодня — 587 с TLS или 465 для неявного TLS. Порт 25 всё ещё хоп между почтовыми серверами. Многие провайдеры блокируют порт 25 из домов.

IMAP — протокол, который клиент использует, чтобы читать и управлять сообщениями на сервере. Обычный порт — 993 с TLS. POP3 — более старый протокол выборки. Этот обзор использует IMAP.

У сообщения есть заголовки и тело. MIME может добавить части. SPF, DKIM и DMARC — проверки DNS и крипто на домене отправителя. Это не команды SMTP. Вы уже встречали записи TXT в теме DNS.

Не отправляйте SMTP без TLS на публичном пути. Не считайте «почта пришла» доказательством, что заголовок From верен. Не запускайте открытый релей.

Почта — store-and-forward. Задержка может быть минутами. Это не запрос-ответ HTTP. Отлаживайте журналами и `dig` на MX, не только `curl`.

## FTP против SFTP

FTP — старый протокол передачи файлов. Классический FTP использует управляющее соединение и отдельное соединение данных. NAT и межсетевые экраны ломают активный FTP. Пассивный FTP — обычный обход. FTP часто отправляет пароли и файлы открытым текстом. FTPS добавляет TLS. Два соединения всё равно добавляют боль.

SFTP — передача файлов на канале SSH. SFTP — не FTP и не FTPS. Одно соединение TCP (SSH) несёт команды и данные. Межсетевые экраны видят порт 22 в обычном случае. Тема 13 уже представила SSH.

Выбирайте SFTP или другое копирование на SSH (`scp`), когда контролируете оба конца и хотите простое безопасное перемещение файлов. Выбирайте загрузку HTTPS или хранилище подписанных объектов для многих веб-приложений. Выбирайте FTPS только когда поставщик всё ещё требует команды вроде FTP.

Не включайте FTP открытым текстом в Internet. Не путайте SFTP с FTPS в runbook. Не открывайте широкий диапазон портов данных для FTP, если не должны и не владеете межсетевым экраном.

Захват пакетов FTP показывает строки USER. Захват SFTP показывает SSH. Эта разница — учебный инструмент.

## WebSockets

WebSocket — долгоживущий двунаправленный канал сообщений, который начинается как HTTP. Клиент отправляет запрос HTTP с `Upgrade: websocket`. Сервер отвечает `101`, если принимает. Затем обе стороны отправляют кадры. Транспорт всё ещё TCP (или путь прокси). TLS использует `wss://`. Открытый текст использует `ws://`.

WebSockets подходят чату, живым видам и играм, которым нужен server-push без нового запроса HTTP каждый раз. Они не заменяют REST для простого CRUD. Они сами не заменяют QUIC. HTTP/2 и SSE — другие стили push.

Прокси должны разрешать обновление и не считать сессию коротким запросом HTTP. Таймауты простоя закрывают тихие сокеты. Heartbeat держат путь живым.

Не отправляйте секреты по `ws://` в публичной LAN. Не игнорируйте проверки `Origin` на сервере, который пишете. Не считайте WebSocket полной mesh-сетью.

Захват после обновления — не текст HTTP/1.1. Wireshark может декодировать кадры WebSocket, когда сессия открытый текст или когда есть ключи.

## gRPC / HTTP/2

gRPC — каркас RPC. Отображение по умолчанию использует HTTP/2. Каждый вызов может быть потоком. Protobuf — обычный формат полезной нагрузки. Клиент вызывает метод на stub. Сервер реализует метод.

gRPC нуждается в HTTP/2 (или отображении HTTP/3 в более новых стеках). Прокси, который понимает только текст HTTP/1.1, может сломать gRPC. Нужен балансировщик нагрузки, который понимает HTTP/2, или пропуск HTTP/2.

TLS и ALPN (`h2`) применяются как в теме 14. Многие службы gRPC используют TLS. Некоторые лабораторные настройки используют HTTP/2 открытым текстом (`h2c`). Не используйте открытый текст на публичном пути.

gRPC хорошо подходит вызовам служба-служба с типизированными контрактами. Он слабее подходит простому публичному API браузера, если не генерируете клиенты и не контролируете браузеры.

Не отлаживайте gRPC так, будто это текст `curl` HTTP/1.1. Используйте `grpcurl` или клиент языка. Некоторые сборки `curl` могут говорить HTTP/2 с двоичным телом. Читайте документы инструмента.

Сроки и коды состояния в gRPC — не те же числа, что статус HTTP, но шлюз может их сопоставить.

## MQTT (IoT)

MQTT — протокол публикации-подписки. Брокер сидит посередине. Издатели отправляют сообщения в темы. Подписчики получают сообщения для тем, которые выбрали. Клиенты часто датчики и телефоны. Транспорт обычно TCP. TLS — защищённый вариант. Порт 1883 обычен для открытого текста. Порт 8883 обычен для TLS.

Уровни QoS управляют подтверждениями. QoS 0 — не больше одного раза. QoS 1 — хотя бы один раз. QoS 2 — ровно один раз в смысле MQTT. Выше QoS — больше болтовни. Ограниченное радио может остаться на QoS 0.

MQTT хорошо подходит телеметрии многие-ко-многим. Он плохо подходит большой передаче файлов. Он не замена HTTP в браузере без дополнительных библиотек.

Не выставляйте брокер MQTT в Internet без подлинности и TLS. Не используйте угадываемые имена тем как единственный контроль доступа. Не затопляйте брокер скриптом в общей лаборатории.

Retained-сообщение — хранилище последнего значения на теме. Will-сообщение — последнее слово, когда клиент умирает. Эти функции — часть обзора, не полный курс IoT.

## Проводные протоколы Redis / Postgres (осведомлённость)

Redis и PostgreSQL — не HTTP. У каждого есть проводной протокол на TCP. Клиентская библиотека говорит этим протоколом. Вы уже используете сокеты. Этот раздел — осведомлённость, чтобы захват не удивил.

Redis использует простой текстово-ориентированный протокол (RESP). Команды выглядят как `*2\r\n$3\r\nGET\r\n$3\r\nkey\r\n` на проводе в классической форме. AUTH может отправить пароль. Не выставляйте Redis в Internet. Используйте пароль или лучшую подлинность, привязывайте к localhost или частной сети и используйте TLS, когда путь не частный.

PostgreSQL начинается с сообщения запуска, затем подлинность, затем сообщения запросов. Протокол двоичный после запуска в современных версиях. `sslmode` управляет TLS. Не кладите порт Postgres на `0.0.0.0` без межсетевого экрана и подлинности.

Факты осведомлённости:

- номера портов общеизвестны (6379, 5432), но их можно сменить
- прокси или пулер может сидеть впереди (PgBouncer, реплика Redis)
- журналы приложения плюс `ss` говорят больше, чем догадка о полезной нагрузке
- ORM всё равно используют эти протоколы под HTTP API вашего приложения

Не вставляйте рабочий захват, в котором есть запросы или ключи. Не считайте «порт отфильтрован» доказательством, что данные безопасны, если клиент в LAN может подключиться.

Здесь вы эти протоколы не реализуете. Вы их называете и держите их вне публичных интерфейсов.

# 7. Администрирование и схемы

## Описание

Админ-работа создаёт и меняет топики, задаёт конфигурацию и осматривает группы. Kafka хранит ключи и значения как байты. Схема описывает форму этих байтов. Schema Registry хранит схемы и может требовать совместимость.

Эта тема показывает создание, описание и удаление топиков, внутренние топики, байты на проводе, Schema Registry, Avro, Protobuf, JSON Schema и уровни совместимости. Завершите эту тему после тем 2, 3 и 6. ZooKeeper не нужен. Инструменты admin используют `--bootstrap-server`. Schema Registry — отдельный сервис. Kafka на KRaft и Schema Registry работают вместе через протокол Kafka и HTTP.

Используйте один термин для каждого понятия. Админ-операция меняет метаданные кластера или конфигурацию топика. Внутренний топик — топик, который Kafka использует для своего состояния. Байты на проводе — полезные нагрузки ключа и значения в записи. Схема — контракт этих байтов. Subject — имя в реестре, которое держит последовательность версий схемы. Совместимость — правило, которое разрешает или отклоняет новую версию схемы.

## Создание, описание и удаление топиков

Вы создаёте топик с именем, числом партиций и фактором репликации. Пример формы команды:

```text
kafka-topics --bootstrap-server localhost:9092 --create --topic orders.placed --partitions 3 --replication-factor 1
```

На Windows используйте файл `.bat`. На macOS и Linux используйте файл `.sh`. Некоторые установки кладут инструменты в `PATH` без суффикса.

`--describe` показывает партиции, лидеров, реплики, ISR и конфигурацию, когда вы просите конфиги.

`--list` показывает имена топиков.

`--delete` удаляет топик. Кластер должен разрешать удаление (`delete.topic.enable` или текущий эквивалент). Удаление не мгновенно. Данные уходят с диска после процесса удаления. Не удаляйте топик в продакшене без процесса изменения.

Автосоздание может существовать на брокере (`auto.create.topics.enable`). Не полагайтесь на автосоздание в продакшене. Создавайте топики с явным числом партиций и фактором репликации.

У имён топиков есть правила. Используйте буквы, цифры, `.`, `_` и `-`. Избегайте пробелов. Избегайте имён, которые сталкиваются с внутренними префиксами.

Значения брокера по умолчанию применяются ко всем топикам. Можно переопределить ключи на одном топике. Примеры: `retention.ms`, `cleanup.policy`, `min.insync.replicas`, `max.message.bytes`. Задавайте переопределения при создании (`--config`) или позже через `kafka-configs`.

Описывайте с конфигами, чтобы видеть эффективные значения и является ли значение значением по умолчанию или переопределением топика. Используйте переопределения для особых топиков. Не создавайте уникальный конфиг для каждого топика без причины.

Admin API вашего языка делает те же операции из программы или конвейера.

Не используйте старые флаги ZooKeeper на новых кластерах KRaft.

## Внутренние топики

Kafka создаёт **внутренние топики** для своего состояния.

`__consumer_offsets` хранит зафиксированные офсеты групп консьюмеров. Не пишите прикладные события в этот топик. Не удаляйте его. Координатор группы его использует (тема 4).

Состояние транзакций использует внутренние топики (имена включают состояние транзакций в официальных документах, например `__transaction_state`). EOS-продюсерам они нужны (тема 5). Не удаляйте их.

Могут появиться другие внутренние имена. Метаданные кластера в KRaft используют журнал метаданных на контроллерах. Этот журнал не обычный прикладной топик. Connect и Streams могут добавить больше топиков, когда вы используете эти продукты (темы 8 и 9).

`--list` может показать внутренние топики. Некоторые инструменты скрывают их, пока не попросите. Считайте каждое имя, которое начинается с `__`, зарезервированным, если документация не говорит иное.

Внутренние топики всё равно используют партиции, реплики и ретеншн. Им нужен диск и правильный фактор репликации. На одноброкерной лаборатории они используют фактор репликации 1. В продакшене им нужен продакшен RF.

Не компактируйте и не удаляйте внутренние топики как эксперимент. Можно сломать группы и транзакции.

## Байты на проводе

Ключ записи Kafka — последовательность байтов или null. Значение записи Kafka — последовательность байтов или null. Брокеры не разбирают JSON или Avro. Брокеры не проверяют ваши поля.

Сериализатор продюсера создаёт байты (тема 3). Десериализатор консьюмера должен понимать тот же формат. Если пара не совпадает, консьюмер бросает исключение или печатает мусор.

Простые форматы:

- строка (текст UTF-8)
- сырой текст JSON
- integer или long в фиксированной двоичной раскладке (сериализаторы клиента)

Со Schema Registry в стиле Confluent значение часто использует эту раскладку:

1. magic byte
2. 4-байтовый идентификатор схемы
3. полезная нагрузка Avro, Protobuf или JSON

Брокер всё равно видит байты. Реестр отображает id на схему. Десериализатор получает схему (и кэширует её), затем декодирует полезную нагрузку.

Не смешивайте сырой JSON-продюсер и Avro-консьюмер реестра на одном топике. Создайте ясный контракт на топик.

Заголовки могут нести тип содержимого. Заголовки необязательны. Не полагайтесь на заголовок, если десериализатор его не читает.

## Schema Registry, Avro / Protobuf / JSON Schema

**Schema Registry** — HTTP-сервис, который хранит схемы. Продюсеры регистрируют схему (или используют известный id). Консьюмеры загружают схему по id.

**Confluent Schema Registry** — частый продукт в Confluent Platform и Confluent Cloud. **Karapace** — открытый реестр, который говорит на совместимом API. Существуют другие реестры. Этот справочник использует «реестр» для роли сервиса.

Реестр — не Kafka. Вы запускаете его рядом с кластером. Он часто хранит свои данные в топике Kafka (например `_schemas`). Этот топик — компактируемый changelog. Не считайте его прикладным топиком.

Клиентам нужен `schema.registry.url` (имя может отличаться). Аутентификация на реестре отдельна от Kafka SASL. Тема 10 покрывает безопасность.

Без реестра всё равно можно использовать файлы Avro или Protobuf в репозитории. Тогда у каждого консьюмера должен быть файл схемы. Реестр помогает, когда многие команды делят топики и когда схемы эволюционируют.

Можно учить темы Kafka 1–6 без реестра. Используйте реестр, когда нужен общий контракт.

**Avro.** Компактная двоичная кодировка. Схема — JSON. Avro часто встречается в Kafka и системах в стиле Hadoop. Читателям нужна схема писателя. Реестр её хранит. У Avro простая модель эволюции, которая хорошо совпадает с совместимостью реестра.

**Protobuf.** Компактная двоичная кодировка. Вы пишете файлы `.proto`. Многие сервисы уже используют Protobuf для RPC. Клиенты Kafka могут использовать Protobuf с реестром. Правила эволюции отличаются от Avro. Номера полей важны.

**JSON Schema.** Схема для документов JSON. Полезные нагрузки остаются читаемыми как текст (плюс обёртка реестра, если используете реестр). Правила эволюции и проверки следуют JSON Schema и режиму реестра.

Выберите один формат на топик. Не смешивайте Avro и JSON на одном subject без плана.

Не запускайте продакшен-реестр как один процесс без бэкапа и без плана. Следуйте руководству эксплуатации продукта.

## Уровни совместимости

**Совместимость** — правило, которое реестр использует, когда вы регистрируете новую версию схемы для subject. Реестр принимает или отклоняет новую версию.

Частые уровни (имена следуют реестрам в стиле Confluent; подтвердите на вашем продукте):

- **BACKWARD.** Новая схема может читать данные, записанные предыдущей схемой. Добавляйте необязательные поля. Не удаляйте поля, которые старые писатели ещё отправляют, если правила не разрешают. Это частое значение по умолчанию.
- **FORWARD.** Старые читатели могут читать данные, записанные новой схемой. Новая схема осторожнее с обязательными полями.
- **FULL.** И backward, и forward для пары версий, которую определяет режим.
- **NONE.** Реестр не проверяет. Можно сломать читателей.

Некоторые продукты добавляют режимы `*_TRANSITIVE`. Эти режимы проверяют новую схему против всех предыдущих версий, не только последней.

**Именование subject** — как реестр называет последовательность версий. Частые стратегии: имя топика плюс `-value` или `-key`, или имя записи. Все продюсеры одного топика должны согласовать.

Отклонённая регистрация — успех для безопасности. Не задавайте `NONE` в продакшене, чтобы «разблокировать» деплой. Исправьте схему или добавьте новый топик.

Консьюмеры, которые кэшируют схемы, должны обработать новый id. Формат провода несёт id. Консьюмер получает новую схему.

Совместимость не заменяет тесты. Напишите тест консьюмера со старой полезной нагрузкой и новой полезной нагрузкой.

3. Перечислите топики. Отметьте внутренние имена. Отметьте ваши прикладные имена.
4. Добавьте в закладки официальные документы admin и главную одного Schema Registry.

#### Средние практические задания

1. Измените ретеншн на лабораторном топике. Зарегистрируйте схему, если есть реестр. Запишите оба процедуры изменения.
2. Сопоставьте каждый подраздел с одним официальным URL.
3. Сравните `kafka-topics` с Admin API для create и describe. Запишите пять эквивалентных операций.

#### Сложные практические задания

1. Соберите маленький конвейер: Admin API создаёт топик, продюсер пишет Avro или JSON Schema через реестр, консьюмер декодирует. Запишите subject, id и режим совместимости.
2. Напишите платформенный стандарт: чеклист создания топика, запрещённые удаления, продукт реестра, совместимость по умолчанию, только bootstrap KRaft, без флагов ZooKeeper.

# 14. Базы данных

## Описание

Эта тема показывает, как программы Go хранят данные. Стандартный пакет `database/sql` — интерфейс. Драйвер реализует низкоуровневые вызовы. Вы пишете SQL, управляете транзакциями и передаёте `context.Context` в запросы.

Используйте один термин для каждого понятия. Драйвер говорит с одним продуктом базы данных. Пул (`sql.DB`) держит соединения. Транзакция группирует инструкции так, чтобы они зафиксировались или откатились вместе. ORM генерирует или сопоставляет SQL за вас. Не храните секреты в исходных файлах. Не склеивайте ввод пользователя в SQL. Используйте параметры.

## `database/sql`

Пакет `database/sql` не содержит клиент PostgreSQL или MySQL. Он определяет типы, которые реализуют драйверы. Приложение импортирует драйвер ради побочного эффекта и затем использует `sql.DB`.

```go
import (
	"database/sql"
	_ "github.com/jackc/pgx/v5/stdlib"
)

db, err := sql.Open("pgx", os.Getenv("DATABASE_URL"))
if err != nil {
	return err
}
defer db.Close()

if err := db.PingContext(ctx); err != nil {
	return err
}
```

Пустой импорт регистрирует драйвер. `sql.Open` проверяет имя драйвера и конфигурацию. Он не всегда открывает настоящее сетевое соединение. `Ping` или `PingContext` доказывают, что соединение работает.

`sql.DB` безопасен для параллельного использования. Не открывайте новый `sql.DB` на каждый запрос. Откройте один пул при старте процесса. Закройте его при остановке процесса.

Частые методы:

- `Exec` / `ExecContext` — INSERT, UPDATE, DELETE, DDL
- `Query` / `QueryContext` — много строк
- `QueryRow` / `QueryRowContext` — одна строка

Сканируйте строки в переменные:

```go
rows, err := db.QueryContext(ctx, `SELECT id, name FROM items WHERE qty > $1`, min)
if err != nil {
	return err
}
defer rows.Close()
for rows.Next() {
	var id int
	var name string
	if err := rows.Scan(&id, &name); err != nil {
		return err
	}
}
if err := rows.Err(); err != nil {
	return err
}
```

Всегда делайте `Close` для `rows`. Всегда проверяйте `rows.Err()` после цикла. `QueryRow` возвращает `sql.ErrNoRows`, когда строки нет. Обнаруживайте её через `errors.Is`.

Используйте `sql.NullString` и другие типы `Null*`, когда столбец может быть NULL. Обычное сканирование `string` падает на NULL.

## Драйверы, подготовленные инструкции и транзакции

Драйвер — отдельный модуль. Примеры: `pgx` для PostgreSQL, `modernc.org/sqlite` или `github.com/mattn/go-sqlite3` для SQLite, драйвер MySQL для MySQL. Первый аргумент `sql.Open` — имя драйвера, которое драйвер регистрирует.

Плейсхолдеры зависят от базы данных. PostgreSQL использует `$1`, `$2`. SQLite и MySQL часто используют `?`. Не копируйте запрос `$1` в драйвер `?` без изменения.

Подготовленная инструкция — SQL, который база данных разбирает один раз. Затем вы выполняете её с параметрами.

```go
stmt, err := db.PrepareContext(ctx, `SELECT name FROM items WHERE id = $1`)
if err != nil {
	return err
}
defer stmt.Close()
row := stmt.QueryRowContext(ctx, id)
```

`QueryContext` с параметрами тоже подготавливает или использует инструкцию внутри пула. Явный `Prepare` помогает, когда выполняете один SQL много раз в одной функции. Всегда делайте `Close` инструкции.

Транзакция группирует инструкции.

```go
tx, err := db.BeginTx(ctx, &sql.TxOptions{Isolation: sql.LevelSerializable})
if err != nil {
	return err
}
defer tx.Rollback()

if _, err := tx.ExecContext(ctx, `UPDATE accounts SET n = n - 1 WHERE id = $1`, from); err != nil {
	return err
}
if _, err := tx.ExecContext(ctx, `UPDATE accounts SET n = n + 1 WHERE id = $1`, to); err != nil {
	return err
}
return tx.Commit()
```

`defer tx.Rollback()` безопасен. Rollback после Commit ничего не делает. Если вернётесь до Commit, Rollback отменит работу.

Не склеивайте ввод пользователя в SQL. Это SQL-инъекция. Всегда передавайте значения как параметры.

```go
// wrong
q := "SELECT * FROM items WHERE name = '" + name + "'"
// correct
db.QueryContext(ctx, `SELECT * FROM items WHERE name = $1`, name)
```

`sql.Tx` небезопасен для параллельного использования. Используйте одну горутину на транзакцию.

## Пул соединений и context

`sql.DB` — пул. Пул открывает соединения по необходимости. Он переиспользует простаивающие соединения.

Задайте пределы пула:

```go
db.SetMaxOpenConns(10)
db.SetMaxIdleConns(5)
db.SetConnMaxLifetime(time.Hour)
db.SetConnMaxIdleTime(10 * time.Minute)
```

`MaxOpenConns` ограничивает открытые соединения к базе данных. Слишком высокое значение может перегрузить базу. Слишком низкое заставляет запросы ждать. Начните с небольшого числа. Измеряйте.

`MaxIdleConns` держит неиспользуемые соединения готовыми. `ConnMaxLifetime` закрывает старые соединения, чтобы балансировщики нагрузки и таймауты простоя на стороне сервера не удивляли.

У каждого метода запроса есть форма `Context`. Предпочитайте `QueryContext`, `ExecContext`, `QueryRowContext`, `BeginTx` и `PingContext`. Когда context завершён, драйвер отменяет запрос, если база поддерживает отмену.

```go
ctx, cancel := context.WithTimeout(r.Context(), 3*time.Second)
defer cancel()
row := db.QueryRowContext(ctx, `SELECT name FROM items WHERE id = $1`, id)
```

В сервере передавайте context запроса. Добавьте таймаут, если у context запроса нет дедлайна. Не используйте `context.Background()` в обработчике.

`db.Stats()` сообщает счётчики пула. Используйте их, когда отлаживаете время ожидания.

Закрывайте строки и инструкции, чтобы соединение вернулось в пул. Утёкшие `Rows` держат соединение. Эта утечка может исчерпать `MaxOpenConns`.

Не храните `*sql.Tx` на долгоживущей структуре между запросами. Транзакция принадлежит одной единице работы.

## ORM против сырого SQL

Сырой SQL означает, что вы пишете инструкции. `database/sql` и драйвер выполняют их. Вы контролируете индексы, соединения и точный SQL, который запускаете в продакшене.

ORM (object-relational mapper) сопоставляет структуры таблицам. Некоторые инструменты генерируют SQL. Некоторые инструменты только сканируют строки в структуры. Примеры в экосистеме Go включают GORM и sqlc. sqlc генерирует Go из SQL. Этот стиль — не полный ORM.

Плюсы сырого SQL:

- Инструкция видна.
- SQL можно скопировать в консоль базы данных.
- Вы избегаете скрытых запросов.

Минусы сырого SQL:

- Вы пишете код сканирования.
- Повторяете списки столбцов.

Плюсы ORM или маппера:

- Меньше кода сканирования.
- Общий шаблон для простого CRUD.

Минусы ORM:

- Скрытые запросы и загрузки N+1
- Более трудная настройка
- Большая зависимость

Предпочитайте сырой SQL или sqlc, когда команда знает SQL. Используйте ORM для простого CRUD только когда команда уже знает этот инструмент. Не смешивайте два ORM в одном сервисе.

Держите SQL в одном пакете, например `internal/store`. Не разбрасывайте запросы по HTTP-обработчикам.

`database/sql` всё равно лежит под многими ORM. Вам всё равно нужны пул, context и правила транзакций.

## Миграции

Миграция — изменение схемы базы данных. Вы храните миграции как файлы. Применяете их по порядку. У каждого файла есть версия.

Типичные задачи:

- создать таблицу
- добавить столбец
- добавить индекс
- заполнить данные отдельным шагом

Инструменты включают `golang-migrate`, `goose` и `atlas`. Некоторые команды применяют файлы SQL небольшой командой Go. Выберите один инструмент. Не редактируйте миграцию, которая уже выполнилась в продакшене. Добавьте новую версию.

```text
migrations/0001_init.up.sql
migrations/0001_init.down.sql
```

Файл `up` применяет изменение. Файл `down` откатывает его. Многие команды перестают писать `down` для продакшена и восстанавливают из резервной копии. Если пишете `down`, тестируйте его.

Запускайте миграции до того, как новая версия приложения нуждается в новых столбцах. Expand-contract:

1. Добавьте допускающий NULL столбец.
2. Разверните код, который пишет и старую, и новую формы.
3. Заполните данные.
4. Разверните код, который читает только новую форму.
5. Удалите старый столбец в более поздней миграции.

Не удаляйте столбец в том же релизе, который его всё ещё читает.

Применяйте миграции из контролируемой задачи. Не гоняйте несколько реплик, которые все мигрируют. Используйте блокировку, которую даёт инструмент.

Держите файлы миграций в репозитории. Встраивайте их через `embed`, если команда migrate живёт в том же модуле.

Никогда не кладите дампы пользовательских данных в файлы миграций.

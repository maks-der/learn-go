# 8. Шаблоны проектирования схемы

## Описание

Эта тема показывает частые шаблоны схемы MongoDB. Шаблон — известный способ формировать документы. Вы изучите шаблоны attribute, bucket, outlier, computed, subset и extended-reference, а также поле версии схемы. Сначала завершите моделирование данных.

Используйте один термин для каждого понятия. **Шаблон** — дизайн, который применяете намеренно. Не применяйте каждый шаблон к каждой коллекции. Именуйте шаблон в заметках, когда используете его.

Официальные имена шаблонов приходят из документации MongoDB и докладов. Используйте эти имена, чтобы команда говорила одним словарём.

## Шаблон attribute

**Шаблон attribute** хранит много необязательных предикатов как массив документов ключ–значение.

Вместо многих разреженных полей:

```javascript
{ color: "red", size: "M", material: null, season: null }
```

вы храните:

```javascript
{
  attrs: [
    { k: "color", v: "red" },
    { k: "size", v: "M" }
  ]
}
```

Индексируете `{ "attrs.k": 1, "attrs.v": 1 }`. Запрос красного цвета использует `$elemMatch` по `k` и `v`.

Используйте этот шаблон, когда:

- У многих документов разные необязательные поля
- Эти поля нужно индексировать
- Широкий набор имён полей создал бы много разреженных индексов

Не используйте этот шаблон для малого стабильного набора полей. Обычные поля проще читать и валидировать.

Приложение по-прежнему владеет разрешёнными ключами. Массив — не свалка случайного JSON без списка ключей.

Чтения, которым нужна форма документа с именованными полями, могут `$project` или перестроить форму в приложении.

## Шаблон bucket

**Шаблон bucket** группирует много маленьких событий в один документ. Документ — **корзина** для диапазона времени или лимита размера.

Пример: показания датчика для одного устройства и одного часа:

```javascript
{
  deviceId: "d1",
  start: ISODate("2026-01-15T10:00:00Z"),
  n: 3,
  readings: [
    { t: ISODate("2026-01-15T10:01:00Z"), c: 21.1 },
    { t: ISODate("2026-01-15T10:02:00Z"), c: 21.2 },
    { t: ISODate("2026-01-15T10:03:00Z"), c: 21.0 }
  ]
}
```

Плюсы:

- Меньше документов
- Меньший индекс `_id`
- Одно чтение окна

Корзину нужно ограничивать. Закрывайте корзину, когда `n` достигает максимума или когда окно времени кончается. Начинайте новый документ.

Коллекции временных рядов MongoDB используют родственную идею внутри сервера. Корзину на уровне приложения всё равно можно использовать для других данных (логи, метрики).

Не кладите неограниченный месяц событий в одну корзину. Это неограниченный массив.

Записи используют `$push` и `$inc` на `n`. Одновременные записи в одну корзину требуют осторожности (повтор или уникальный ключ корзины).

## Шаблон outlier

**Шаблон outlier** держит обычный случай в основном документе. Редкий огромный случай уводит в другую коллекцию.

Пример: у большинства книг меньше 20 соавторов. У немногих книг 500 участников. Вы встраиваете авторов до 20. Ставите `hasExtraAuthors: true` и храните остальное в `book_authors`.

Приложение:

1. Читает книгу.
2. Если флаг истинен, читает дополнительную коллекцию.

Большинству чтений дополнительный запрос не нужен.

Используйте этот шаблон, когда:

- У распределения длинный хвост
- Обычный случай должен оставаться маленьким и быстрым
- Хвост всё равно нужно хранить

Не используйте этот шаблон, если каждый документ велик. Тогда основная модель неверна.

Граница должна быть реальной. Измерьте перцентили. Если 99-й перцентиль всё ещё огромен, встраивание — неверный выбор по умолчанию.

Записи, которые добавляют автора, должны переносить данные, когда граница пересечена.

## Шаблон computed

**Шаблон computed** хранит значение, которое можно вычислить из других полей. Хранимое значение обновляют, когда меняется источник.

Пример: хранить `commentCount` на посте. Увеличивать его при вставке комментария. Не делать `$count` всех комментариев на каждый просмотр страницы.

Пример: хранить `lineTotal` и `orderTotal`, когда меняете строку.

Плюсы:

- Быстрые чтения
- Простой `find`

Минусы:

- Записи должны держать значение верным
- Ошибка может сделать хранимое значение устаревшим
- Может понадобиться задача починки

Используйте этот шаблон, когда чтения вычисленного значения часты, а формула стабильна.

Не храните вычисленное значение, которое меняется при каждом чтении по другой причине (текущее время), если не храните также `computedAt` и не принимаете устаревание.

Можно пересчитать задачей агрегации. Задача — путь починки, не горячий путь.

Вычисления в одном документе могут использовать конвейер обновления агрегации. Счета по нескольким документам нуждаются в аккуратном увеличении или транзакции.

## Шаблон subset

**Шаблон subset** хранит **маленькую копию** связанных данных для обычного чтения. Полный документ живёт в другой коллекции.

Пример: список товаров хранит `{ productId, name, thumbUrl, price }`. Коллекция `products` хранит длинное описание, все изображения и складские поля.

Страница списка не загружает 50 KB описания на строку.

Этот шаблон — денормализация с целью размера. Копируете подмножество, не весь товар.

Обновления исходного поля, которое есть в subset, должны обновлять копии, или вы принимаете устаревание. Цена в списке часто достаточно живая, чтобы обновлять в фоне, или цену читают живой и всё равно выносят тяжёлые поля в subset.

Не делайте subset полей, которые меняются каждую секунду, без плана обновления.

Не дублируйте весь документ. Тогда у вас два источника истины для всего.

## Extended reference

**Extended reference** хранит id **и** несколько полей из ссылаемого документа.

```javascript
{
  productId: ObjectId("..."),
  name: "Nail",
  price: NumberDecimal("1.50")
}
```

Id — живая связь. Дополнительные поля — снимок или кэш для обычного чтения.

Этот шаблон стоит между голой ссылкой и полным встраиванием.

Используйте его, когда:

- Нужно соединять или переходить по id
- Нужно показать метку без lookup
- Дополнительных полей мало и у них известное правило свежести

Решите, дополнительные поля — **снимок** (история заказа) или **кэш** (можно обновить).

Не расширяйте ссылку двадцатью полями. Тогда получите слишком большой subset или скрытое встраивание.

Держите имена полей ясными. `name` в строке заказа — имя снимка. Не притворяйтесь, что это всегда имя каталога.

## Поле версии схемы

Поле **версии схемы** записывает форму документа. Частое имя — `schemaVersion` или `v`.

```javascript
{ schemaVersion: 2, name: "Ann", displayName: "Ann" }
```

Приложение читает версию. Оно запускает **читателя**, который понимает версию 1 и версию 2. **Писатель** пишет только текущую версию или пишет оба поля во время перехода.

Это идея expand-contract:

1. Выкатите код, который читает старое и новое.
2. Пишите новые поля (expand).
3. Дозаполните старые документы.
4. Уберите чтения старых полей (contract).

Поле версии делает форму явной. Можно запросить `{ schemaVersion: 1 }` для дозаполнения.

Не увеличивайте версию на каждое мелкое добавление, если читатель может считать отсутствующее поле значением по умолчанию. Увеличивайте, когда меняется смысл поля или форму трудно обнаружить.

Не храните два полностью несовместимых смысла в одном поле без версии или нового имени.

Валидация может разрешить больше одной версии через `oneOf` (следующая тема).

5. Коллега применяет все семь шаблонов к одной коллекции. Какими фактами вы это остановите?

#### Простые практические задания

1. Назовите шаблон для: последние 100 метрик в документе одного часа; `likeCount` на посте; id товара плюс имя в строке.
2. Напишите шпаргалку: семь имён шаблонов, по одному предложению.
3. Добавьте `schemaVersion: 1` к одному примеру документа для каждой из двух коллекций, которые используете.
4. Нарисуйте магазин, который использует только extended reference и вычисленный `orderTotal`. Других шаблонов нет.

#### Средние практические задания

1. Возьмите реальный или выдуманный каталог товаров. Примените attribute или нет. Примените subset для списков. Запишите почему.
2. Спроектируйте корзины для событий кликов и выбросы для комментариев вирусного поста. Запишите границы и флаги.
3. Напишите изменение, которому нужен `schemaVersion` с 1 на 2 и починка вычисленного поля. Перечислите порядок выката.

#### Сложные практические задания

1. Прочитайте официальную серию building-with-patterns. Сопоставьте каждый официальный шаблон этой темы с URL и одним лишним фактом.
2. Просмотрите модель из темы 5. Добавьте не больше трёх шаблонов. Запишите, какие задачи они решают и какие пути записи вы добавили.

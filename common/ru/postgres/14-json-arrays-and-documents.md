# 14. JSON, массивы и документы

## Описание

Эта тема показывает JSON и массивы в PostgreSQL 16 и PostgreSQL 17. Вы узнаёте `json` против `jsonb`, индексы GIN на `jsonb`, массивы и `unnest`, когда JSON уместен в PostgreSQL, и ограниченные check-ограничения на форму JSON.

Сначала завершите тему 13. Вы умеете создавать расширения и функции. Завершите эту тему до секционирования больших таблиц.

Используйте один термин для каждого понятия. `json` — текстовый тип JSON. `jsonb` — двоичный тип JSON. Документ — одно значение JSON в столбце. Массив — типизированный список (`text[]`, `int[]`, `jsonb[]`). `unnest` превращает массив в множество строк. Индекс GIN на `jsonb` поддерживает операторы включения и существования ключа. Этот справочник рассчитан на PostgreSQL 16 и PostgreSQL 17.

## `json` против `jsonb`

Тема 4 представила два типа. Этот раздел — рабочее правило.

`json` хранит входной текст. Сохраняет порядок ключей. Сохраняет дубликаты ключей. Сохраняет незначимые пробелы. Каждая операция должна разбирать текст.

`jsonb` хранит разобранное дерево. Отбрасывает незначимые пробелы. Если ключ повторяется, побеждает последний. Порядок ключей — не контракт данных. Операторы и индексы работают с `jsonb`.

```sql
SELECT '{"b": 1, "a": 2}'::json;
SELECT '{"b": 1, "a": 2}'::jsonb;
SELECT pg_typeof('{"a":1}'::jsonb);
```

Предпочитайте `jsonb` для столбцов, которые фильтруете, индексируете или обновляете на месте. Предпочитайте `json` только когда нужно хранить точный текст, который прислал клиент.

Тема 7 перечислила операторы. Повтор:

| Оператор | Результат |
| --- | --- |
| `->` | поле или элемент; тип остаётся `json` / `jsonb` |
| `->>` | поле или элемент как `text` |
| `@>` | включение `jsonb` |
| `?` | ключ верхнего уровня `jsonb` существует |

```sql
CREATE TABLE shop.events (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    payload jsonb NOT NULL
);

INSERT INTO shop.events (payload)
VALUES ('{"type": "click", "n": 3}');

SELECT payload ->> 'type' AS type,
       payload -> 'n'     AS n_jsonb,
       payload @> '{"type":"click"}' AS is_click
FROM shop.events;
```

PostgreSQL 16 добавляет больше предикатов SQL/JSON (`IS JSON` и смежные проверки). PostgreSQL 17 добавляет помощники запросов SQL/JSON вроде `JSON_TABLE` для превращения JSON в строки. Ежедневную работу всё равно можно делать через `->`, `->>`, `@>` и `jsonb_set`.

Обновить ключ:

```sql
UPDATE shop.events
SET payload = jsonb_set(payload, '{n}', '4', true)
WHERE id = 1;
```

Не храните JSON как `text`, если нужно, чтобы парсер отклонял невалидный JSON. Не используйте `json` потому что имя короче. Не сравнивайте `jsonb` через `=`, когда имели в виду включение (`@>`).

Официальная глава: [https://www.postgresql.org/docs/17/datatype-json.html](https://www.postgresql.org/docs/17/datatype-json.html).

## Индексирование `jsonb` через GIN

B-tree на `(payload->>'type')` помогает равенству по одному извлечённому ключу. Индекс GIN на столбце `jsonb` помогает включению и существованию ключа по многим ключам.

```sql
CREATE INDEX events_payload_gin ON shop.events USING gin (payload);
```

Класс операторов по умолчанию — `jsonb_ops`. Он поддерживает `@>`, `?`, `?|`, `?&` и смежные поиски. Индексирует ключи и значения. Он больше.

`jsonb_path_ops` поддерживает только `@>`. Он меньше и может быть быстрее для включения. Не поддерживает `?`.

```sql
CREATE INDEX events_payload_path_gin
    ON shop.events USING gin (payload jsonb_path_ops);
```

Проверить план:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id
FROM shop.events
WHERE payload @> '{"type":"click"}';
```

Хотите bitmap index scan или index scan, который называет индекс GIN. Последовательное сканирование на большой таблице значит, что индекс не совпадает с предикатом. `@>` совпадает с GIN. `payload->>'type' = 'click'` совпадает с B-tree на этом выражении, не с путём включения GIN по умолчанию.

GIN по выражению тоже допустим:

```sql
CREATE INDEX events_tags_gin ON shop.events USING gin ((payload -> 'tags'));
```

Тема 8 разбирала GIN как класс. Этот раздел — шаблон `jsonb`. `CREATE INDEX CONCURRENTLY` на занятой таблице всё равно применяется.

Не создавайте и `jsonb_ops`, и `jsonb_path_ops` на одном столбце без измерения. Не ждите, что GIN ускорит `ORDER BY payload`. Не индексируйте огромные документы, если фильтруете только один маленький ключ; B-tree на выражении может хватить.

Официальные классы операторов: [https://www.postgresql.org/docs/17/datatype-json.html#JSON-INDEXING](https://www.postgresql.org/docs/17/datatype-json.html#JSON-INDEXING).

## Массивы и `unnest`

Массив — один столбец, который держит список значений одного типа. Синтаксис использует `{` в литералах и `[]` в конструкторах.

```sql
CREATE TABLE shop.posts (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tags text[] NOT NULL DEFAULT '{}'
);

INSERT INTO shop.posts (tags) VALUES (ARRAY['sql', 'gin']);
INSERT INTO shop.posts (tags) VALUES ('{sql,json}');
```

Операторы и функции:

- `tags @> ARRAY['sql']` — содержит все перечисленные элементы
- `tags && ARRAY['gin', 'fts']` — пересекается
- `tags[1]` — первый элемент (массивы с индекса 1)
- `array_length(tags, 1)` — длина первого измерения
- `unnest(tags)` — одна строка на элемент

```sql
SELECT p.id, u.tag
FROM shop.posts AS p
CROSS JOIN LATERAL unnest(p.tags) AS u(tag);
```

Тема 6 разбирала `LATERAL`. `unnest` — частый боковой партнёр.

Индекс GIN на `text[]` поддерживает `@>` и `&&`:

```sql
CREATE INDEX posts_tags_gin ON shop.posts USING gin (tags);
```

Можно хранить `jsonb[]`, но массив `jsonb` внутри одного документа (`{"tags":[...]}`) часто яснее. Не смешивайте оба стиля без правила.

Массив — не дочерняя таблица. Нельзя поставить внешний ключ на один элемент. Нельзя прикрепить ограничение уникальности к одному элементу без дополнительной работы. Тема 4 сказала использовать массивы для маленьких множеств. Этот раздел добавляет `unnest` и GIN.

Не заменяйте `orders` и `order_lines` на `line_ids bigint[]`, когда нужны итоги строк, ограничения и соединения. Не используйте индексацию с 0 в SQL; первый элемент — `[1]`.

Официальная глава: [https://www.postgresql.org/docs/17/arrays.html](https://www.postgresql.org/docs/17/arrays.html).

## Когда JSON уместен в PostgreSQL против документной БД

PostgreSQL может хранить документы. Документная база может хранить документы. Выбор — выбор модели, не моды.

JSON уместен в PostgreSQL, когда:

- большая часть данных уже имеет таблицы, ключи и транзакции
- нужны соединения документа с реляционной строкой в одной транзакции
- документ — полезная нагрузка, мешок настроек или разреженный набор атрибутов
- всё равно хотите резервные копии PostgreSQL, роли и ограничения на типизированных столбцах

JSON не уместен как единственная модель, когда:

- каждый запрос — глубокий путь в меняющийся документ и вы никогда не соединяете
- нужен документный API и управляемый документный продукт уже есть
- храните большие непрозрачные блобы, которые никогда не фильтруете (используйте `bytea` или объектное хранилище и держите ключ)

Правила, которые держат гибридный дизайн безопасным:

- типизированные столбцы для значений, которые фильтруете, сортируете, соединяете или ограничиваете
- `jsonb` для значений, которые меняются от строки к строке или меняют форму
- индекс GIN или по выражению только для путей, которые измерили
- ограничение check, когда форма маленькая и стабильная (следующий раздел)

PostgreSQL — не «MongoDB с SQL», когда пропускаете ключи. Тема 1 сказала, что таблицы остаются основной моделью. Документная база — не «неверно». Это другой продукт с другой операционной моделью.

Не кладите всё состояние приложения в один столбец `jsonb` с именем `data`. Не дублируйте один атрибут как столбец и как JSON без правила записи. Не выбирайте JSON, чтобы избежать миграции. Тема 21 разбирает миграции.

## Ограничения check на форму JSON (ограниченно)

Столбец `jsonb` принимает любой валидный JSON, пока не добавите ограничение. PostgreSQL 16 и 17 не поставляют полный валидатор JSON Schema как ограничение ядра. Типы, ключи и маленькие формы можно проверять SQL.

```sql
ALTER TABLE shop.events
    ADD CONSTRAINT events_payload_is_object
    CHECK (jsonb_typeof(payload) = 'object');

ALTER TABLE shop.events
    ADD CONSTRAINT events_payload_has_type
    CHECK (payload ? 'type');

ALTER TABLE shop.events
    ADD CONSTRAINT events_type_is_text
    CHECK (jsonb_typeof(payload -> 'type') = 'string');
```

`IS JSON` (PostgreSQL 16 и 17) проверяет текст или синтаксис JSON в выражениях. Столбец `jsonb` уже отклонил невалидный JSON на вводе. Полезные проверки — форма и типы полей.

Ограничения:

- каждый `CHECK` — булево SQL-выражение
- глубокие необязательные деревья трудно выразить
- сообщения об ошибках — не ошибки схемы уровня поля
- ограничение, которое вызывает функцию `STABLE`, должно оставаться дешёвым на каждой записи

Можно обернуть проверки в `IMMUTABLE` SQL-функцию и вызывать её из `CHECK`. Функция должна оставаться `IMMUTABLE`, чтобы ограничение было валидным.

Для большой схемы валидируйте в приложении и держите несколько проверок базы для инвариантов, которые никогда не должны падать (type присутствует, id — число).

Не копируйте полную JSON Schema в пятьдесят предложений `CHECK`. Не используйте функцию `VOLATILE` в `CHECK`. Не считайте, что `@>` доказывает полную схему; оно доказывает только включение образца, который написали.

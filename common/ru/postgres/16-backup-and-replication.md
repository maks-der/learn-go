# 16. Резервное копирование и репликация

## Описание

Эта тема показывает резервные копии и копии кластера в PostgreSQL 16 и PostgreSQL 17. Вы узнаёте `pg_dump`, `pg_restore`, `pg_dumpall`, `pg_basebackup`, архивирование WAL, восстановление на точку во времени, потоковую репликацию, hot standby, логическую репликацию и инструменты failover на высоком уровне.

Сначала завершите тему 15. Вы умеете отсоединить секцию и снять дамп таблицы. Завершите эту тему до настройки клиентских пулов.

Используйте один термин для каждого понятия. Логический дамп — SQL или архив объектов. Физическая резервная копия — копия каталога данных плюс WAL. WAL — журнал упреждающей записи. PITR — восстановление на выбранное время. Потоковая реплика — физический стендбай, который воспроизводит WAL. Логическая репликация копирует набор таблиц через публикации и подписки. Этот справочник рассчитан на PostgreSQL 16 и PostgreSQL 17.

## `pg_dump` / `pg_restore` / `pg_dumpall`

`pg_dump` копирует одну базу. Не копирует роли или табличные пространства. `pg_dumpall` копирует все базы плюс кластерные объекты (роли, табличные пространства). `pg_restore` загружает не-plain архив из `pg_dump`.

Форматы `pg_dump`:

- plain (`-Fp`) — SQL-скрипт; загрузка через `psql`
- custom (`-Fc`) — сжатый архив; загрузка через `pg_restore`; можно выбирать объекты
- directory (`-Fd`) — одна папка; параллельный дамп и восстановление (`-j`)
- tar (`-Ft`) — tar-архив; загрузка через `pg_restore`

```text
pg_dump -h localhost -U postgres -d shop -Fc -f shop.dump
pg_restore -h localhost -U postgres -d shop_copy --clean --if-exists shop.dump
```

Только схема или только данные:

```text
pg_dump -s -d shop -f shop_schema.sql
pg_dump -a -d shop -Fc -f shop_data.dump
```

Одна таблица (архив темы 15):

```text
pg_dump -d shop -t shop.orders_2025_01 -Fc -f orders_2025_01.dump
```

`pg_dump` выполняет согласованный снимок этой базы. Других баз кластера в файле нет. Открытые транзакции, которые держат старые снимки, могут задержать дамп (тема 10 и тема 11).

```text
pg_dumpall -g -f roles.sql
```

`-g` снимает только глобальные объекты. Восстанавливайте глобальные объекты до восстановления базы, которая зависит от этих ролей.

По возможности совпадайте мажорные версии клиента и сервера. Более новый `pg_dump` часто может снимать дамп более старого сервера. Восстановление дампа 17 на 16 может упасть на новых возможностях.

Не считайте копию файловой системы работающего каталога данных резервной копией. Эта копия не согласована. Используйте `pg_dump` или `pg_basebackup`. Не коммитьте файлы дампа с живыми данными в git.

Официально: [https://www.postgresql.org/docs/17/app-pgdump.html](https://www.postgresql.org/docs/17/app-pgdump.html), [https://www.postgresql.org/docs/17/app-pgrestore.html](https://www.postgresql.org/docs/17/app-pgrestore.html), [https://www.postgresql.org/docs/17/app-pg-dumpall.html](https://www.postgresql.org/docs/17/app-pg-dumpall.html).

## `pg_basebackup`

`pg_basebackup` берёт физическую резервную копию всего кластера. Копирует каталог данных через протокол репликации. Копия — стартовая точка для реплики или для PITR.

```text
pg_basebackup -h primary.example -U replicator -D /var/lib/postgresql/17/backup -Fp -X stream -R
```

Полезные флаги:

- `-D` — каталог назначения
- `-Fp` или `-Ft` — обычные файлы или tar
- `-X stream` — включить WAL, который приходит во время копирования
- `-R` — записать `standby.signal` и настройки подключения для реплики
- `-c fast` — быстрый checkpoint до копирования (больше WAL, короче ожидание старта)

Роли нужен `REPLICATION` (или суперпользователь). В `pg_hba.conf` нужна строка `replication`.

PostgreSQL 17 добавляет инкрементальную физическую резервную копию. Берёте полный `pg_basebackup`, затем позже `pg_basebackup --incremental` против предыдущего манифеста. `pg_combinebackup` собирает пригодный каталог из полной копии плюс инкрементов. У PostgreSQL 16 этого набора инкрементальных инструментов нет. На 16 используйте полный `pg_basebackup` или файловый инкрементальный инструмент, который понимает PostgreSQL.

Физическая резервная копия — на весь кластер. Одну базу из `pg_basebackup` без дополнительной работы восстановить нельзя. Когда нужна одна база, используйте `pg_dump`.

Не запускайте два первичных из копий одной резервной копии без плана восстановления. Они разойдутся и сломают реплики. Не кладите каталог резервной копии внутрь живого каталога данных.

Официально: [https://www.postgresql.org/docs/17/app-pgbasebackup.html](https://www.postgresql.org/docs/17/app-pgbasebackup.html). PostgreSQL 17 также документирует [https://www.postgresql.org/docs/17/app-pgcombinebackup.html](https://www.postgresql.org/docs/17/app-pgcombinebackup.html).

## Архивирование WAL и PITR

Сервер пишет WAL до записи страниц данных. Если храните каждый сегмент WAL от base backup дальше, можете воспроизвести до целевого времени. Этот процесс — восстановление на точку во времени (PITR).

Основные настройки (обзор):

- `wal_level = replica` (или `logical`, если также нужно логическое декодирование)
- `archive_mode = on`
- `archive_command` — команда оболочки, которая копирует `%p` в безопасное хранилище, или `archive_library` в текущих установках 16/17

Идея примера (правьте пути; не копируйте сломанную команду в продакшен):

```text
archive_command = 'test ! -f /archive/%f && cp %p /archive/%f'
```

`%p` — путь файла. `%f` — имя файла. Команда должна возвращать успех только когда копия долговечна.

Восстановление в PostgreSQL 16 и 17 использует `postgresql.conf` (или `postgresql.auto.conf`) плюс файл сигнала:

- положите `restore_command` в конфигурацию
- создайте пустой `recovery.signal` для восстановления, которое станет первичным
- создайте пустой `standby.signal`, чтобы остаться стендбаем

В этих версиях нет `recovery.conf`. Этот файл — старый шаблон.

Примеры цели:

```text
recovery_target_time = '2026-09-13 16:00:00+00'
recovery_target_action = 'promote'
```

Восстанавливаете base backup, добавляете WAL из архива, задаёте цель и запускаете сервер.

Не задавайте `archive_command` командой, которая может успешно завершиться без настоящей копии. Не удаляйте WAL из архива, пока не истекла каждая base backup, которой эти файлы ещё нужны. Не тестируйте PITR только в голове. Восстанавливайте в пустой каталог.

Официально: [https://www.postgresql.org/docs/17/continuous-archiving.html](https://www.postgresql.org/docs/17/continuous-archiving.html).

## Потоковая репликация

Потоковая репликация отправляет WAL с первичного на стендбай по подключению репликации. Стендбай пишет WAL и воспроизводит его. Копия физическая. Мажорная версия должна совпадать. Стендбай только для чтения для обычного SQL.

Шаги на высоком уровне:

1. Создайте роль `REPLICATION` на первичном.
2. Разрешите `replication` в `pg_hba.conf`.
3. Задайте `wal_level` не ниже `replica`.
4. Возьмите `pg_basebackup -R` в каталог данных стендбая.
5. Запустите стендбай.

Стендбай использует `primary_conninfo` (часто пишет `-R`) и `standby.signal`.

Следить за лагом:

```sql
-- on primary
SELECT client_addr, state, sent_lsn, replay_lsn
FROM pg_stat_replication;

-- on stand-by
SELECT pg_is_in_recovery(), pg_last_wal_replay_lsn();
```

Синхронная репликация ждёт, пока стендбай сбросит WAL (`synchronous_commit` и `synchronous_standby_names`). Эта настройка снижает потерю данных и увеличивает задержку записи. Новички начинают с асинхронного потока.

Слоты (`pg_create_physical_replication_slot`) держат WAL на первичном, пока реплика его не потребит. Слот, который никто не потребляет, заполняет диск. Тема 18 разбирает инциденты полного диска.

Не пишите на стендбае. Не используйте поток как единственную резервную копию; всё равно нужна base backup и часто архив. Не смешивайте первичный PostgreSQL 16 со стендбаем 17.

Официально: [https://www.postgresql.org/docs/17/warm-standby.html](https://www.postgresql.org/docs/17/warm-standby.html).

## Hot standby и `hot_standby`

Hot stand-by — реплика, которая принимает SQL только на чтение, пока восстанавливается. `hot_standby` по умолчанию `on` в PostgreSQL 16 и 17.

```sql
SHOW hot_standby;
SELECT pg_is_in_recovery();
```

На hot stand-by можно `SELECT`. Нельзя `INSERT`, `UPDATE`, `DELETE` или DDL, который пишет.

Конфликты: первичный может сделать vacuum или обновить строку, которая всё ещё нужна долгому запросу стендбая. Стендбай может отменить запрос (`max_standby_streaming_delay`). Отчётный запрос, который работает долго, может упасть на занятой реплике.

`hot_standby_feedback` сообщает первичному о снимках стендбая. Снижает отмены запросов. Может задержать vacuum на первичном (больше раздутия). Тема 11 объяснила мёртвые кортежи.

Используйте реплику для отчётов, которые терпят лаг и отмену. Тема 19 разбирает этот шаблон.

Не ставьте `hot_standby = off` на реплике, которую приложения должны запрашивать. Не направляйте API записи на стендбай.

## Логическая репликация и публикации / подписки

Логическая репликация копирует изменения строк для набора таблиц. Издатель и подписчик во многих поддерживаемых парах могут быть разных мажорных версий. Таблица подписчика записываемая. Конфликты — ваша проблема, если обе стороны пишут один ключ.

На издателе:

```sql
CREATE PUBLICATION shop_pub FOR TABLE shop.items;
-- or FOR ALL TABLES
```

На подписчике:

```sql
CREATE SUBSCRIPTION shop_sub
    CONNECTION 'host=primary port=5432 dbname=shop user=replicator'
    PUBLICATION shop_pub;
```

`wal_level` на издателе должен быть `logical`. Публикация может перечислить таблицы или все таблицы. PostgreSQL 15 и новее (значит 16 и 17) может добавлять списки столбцов и фильтры строк на публикациях. Читайте страницу `CREATE PUBLICATION` до того, как полагаться на фильтр.

Начальная синхронизация копирует существующие строки, затем применяет изменения. Слот репликации на издателе удерживает WAL для подписчика. Мёртвый подписчик заполняет диск.

PostgreSQL 16 может выполнять логическое декодирование со стендбая в поддерживаемых установках. PostgreSQL 17 добавляет больше помощников failover для логических слотов (`pg_createsubscriber` и смежные инструменты). Относитесь к ним как к операторским возможностям. Сначала выучите `PUBLICATION` и `SUBSCRIPTION`.

Логическая репликация копирует не всё. Типичные пробелы: последовательности (проверьте заметки версии 16/17), большие объекты, DDL (изменения схемы применяете сами) и некоторые типы. Всегда читайте текущую страницу ограничений.

Не используйте логическую репликацию как единственную резервную копию. Не подписывайте таблицу на саму себя. Не забывайте DDL: новый столбец на издателе может сломать подписчика, пока не добавите его.

Официально: [https://www.postgresql.org/docs/17/logical-replication.html](https://www.postgresql.org/docs/17/logical-replication.html).

## Инструменты failover (обзор: Patroni, HA облачного вендора)

Потоковая репликация сама не повышает реплику, когда первичный умирает. Человек или инструмент должен повысить (`pg_ctl promote` или `SELECT pg_promote();`) и перевести клиентов на новый первичный.

**Patroni** — частый агент с открытым кодом. Использует etcd, Consul или ZooKeeper, чтобы выбрать лидера. Управляет `postgres` и виртуальным IP или прокси. Резервные копии всё равно нужны. Patroni — не замена PITR.

**HA облачного вендора** (Amazon RDS Multi-AZ, Google Cloud SQL HA, Azure, AlloyDB, Aurora PostgreSQL, Crunchy-managed) запускает путь failover вендора. Учите runbook вендора: кто повышает, что делает DNS-имя и какой RPO/RTO заявляет продукт. Тема 22 перечисляет эти продукты. Тема 21 просит письменный runbook.

Что новичок должен помнить:

- failover — процесс, не файл дампа
- клиентам нужно одно стабильное имя (прокси, DNS или эндпоинт вендора)
- реплика, которую повышаете, не должна делить старый первичный без fencing
- тестируйте failover по расписанию
- держите `pg_dump` или base backup даже когда HA включён

Не пишите свой выборщик, если команда может использовать Patroni или продукт HA вендора. Не повышайте два первичных. Не пропускайте резервные копии потому что «есть реплика».

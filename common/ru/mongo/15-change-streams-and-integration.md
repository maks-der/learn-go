# 15. Change streams и интеграция

## Описание

Эта тема показывает, как MongoDB толкает изменения данных слушателям. **Change stream** — официальный курсор событий изменения. **Resume token** позволяет продолжить после разрыва. Команды используют change streams для **CDC** (change data capture) в поиск или хранилище. **Atlas Triggers** запускают код, когда данные меняются. Сначала завершите репликацию, драйверы и CRUD.

Используйте один термин для каждого понятия. **Событие изменения** — один документ, который описывает вставку, обновление, замену, удаление или некоторые события кластера. **Resume token** — `_id` события. **CDC** — практика копирования этих изменений в другую систему.

Change streams нужен replica set или шардированный кластер. Одиночного `mongod` недостаточно.

## Change streams

Change stream — долгоживущий курсор. Сервер отправляет новое событие, когда совпавшая запись фиксируется.

Откройте поток на коллекции в `mongosh`:

```javascript
const cs = db.orders.watch()
cs.tryNext()
```

Драйверы используют `watch` или эквивалентный помощник. Можно наблюдать:

- Одну коллекцию
- Одну базу
- Всё развёртывание (с нужным API и правами)

Типичное событие включает:

- `_id` — resume token
- `operationType` — `insert`, `update`, `replace`, `delete` и другие
- `fullDocument` — документ после изменения, когда вы его запрашиваете
- `documentKey` — `_id` и поля ключа шарда
- `updateDescription` — поля, которые изменились, для некоторых обновлений
- `clusterTime` — когда изменение произошло в кластере

По умолчанию событие обновления может опустить полный документ. Откройте поток с `fullDocument: "updateLookup"`, когда нужен документ после обновления. Этот lookup имеет цену и может гоняться. Читайте текущие опции (`whenAvailable`, `required` в более новых версиях).

Поток следует oplog. Если слушатель лежит дольше окна oplog, поток нельзя возобновить. Нужна полная повторная синхронизация нижестоящей системы.

Фильтруйте в `watch` конвейером агрегации (`$match` по `operationType` или по полям). Не тяните каждое событие, если нужны только вставки.

Не считайте change stream очередью с бесконечным хранением. Это не Kafka. Хранение — окно oplog, пока не добавите другое хранилище.

Не запускайте воркер change stream, который делает медленную работу внутри цикла приёма без противодавления. Можно выпасть из oplog.

## Resume tokens

**Resume token** — `_id` события изменения. Его передают в `watch`, чтобы следующий курсор продолжился после этого события.

```javascript
const token = event._id
const cs2 = db.orders.watch([], { resumeAfter: token })
```

Родственные опции (имена зависят от версии):

- `resumeAfter` — продолжить после этого токена
- `startAfter` — начать после invalidate в некоторых случаях
- `startAtOperationTime` — начать с метки времени кластера

Сохраняйте токен только после завершения нижестоящей работы для этого события. Если сохранить токен сначала и затем упасть, можно пропустить событие. Если токен никогда не сохранять, события повторяются. Предпочитайте доставку **at-least-once** и делайте потребителя **идемпотентным**.

Токены непрозрачны. Не собирайте их вручную. Не храните случайный ObjectId как токен.

Если токен вне oplog, `watch` падает. Нужен снимок исходной коллекции, затем новый поток с известного времени.

На шардированном кластере токены всё равно работают, но нужно использовать API драйвера. Не открывайте сырой поток только на одном шарде.

После `invalidate` (drop, rename, drop database) многие курсоры умирают. Может понадобиться `startAfter` или новая полная синхронизация. Читайте страницу своей версии.

Atlas и драйверы могут помочь с возобновлением. Токен всё равно сохраняете в хранилище приложения.

## CDC в поиск или хранилище

**CDC** копирует изменения базы в другую систему. Частые цели:

- Поисковый движок или индекс Atlas Search, который ведёте сами
- Хранилище данных или озеро
- Кэш или модель чтения
- Другой микросервис

Change streams — один источник CDC. Atlas также предлагает другие инструменты конвейера на некоторых тарифах. Есть Kafka Connect и похожие инструменты. Выберите один конвейер. Не запускайте три независимых слушателя, которые пишут в один приёмник.

Типичный поток:

1. Снять начальный снимок коллекции (или запроса).
2. Записать cluster time или токен.
3. Применить снимок к приёмнику.
4. Запустить change stream с этого времени или токена.
5. Применять события по порядку на документ. Делать каждое применение идемпотентным.

CDC поиска: сопоставить каждую вставку/обновление/замену с upsert в индексе. Сопоставить удаление с удалением в индексе. Если пропустить события, индекс неверен, пока не перестроите.

CDC хранилища: многие команды пишут события в файлы или в очередь, затем загружают пакетами. Не выпускайте крошечный оператор хранилища на каждое событие, если хранилище медленное.

Порядок: события одного документа упорядочены. События двух документов могут переплетаться. Приёмник должен это терпеть.

Не используйте CDC, чтобы заменить транзакцию между MongoDB и приёмником. Приёмник асинхронен. Приложению, которому нужен хит поиска «сейчас», нужно принять задержку или писать в поиск на пути запроса (с другой историей согласованности).

Защитите слушателя. Change stream может читать все поля. Используйте роль только с нужными правами. Не логируйте полные документы, если в них секреты.

## Triggers (Atlas)

**Atlas Triggers** запускают функцию, когда происходит событие. Триггер базы может сработать на insert, update, replace или delete в связанном кластере Atlas. Плановые триггеры срабатывают по таймеру. Триггеры аутентификации срабатывают на событиях пользователя в Atlas App Services.

Триггер базы получает событие изменения. Функция может вызвать API, записать в другую коллекцию или вызвать сервис Atlas.

Триггеры полезны для:

- Небольшого fan-out (отправить уведомление)
- Лёгкой денормализации
- Первого шага CDC в сервис Atlas

Триггеры не полезны для:

- Долгой работы CPU
- Неограниченных циклов
- Единственного журнала аудита, если нужна жёсткая гарантия без мониторинга

Есть лимиты: время выполнения, вычислительные ресурсы и объём событий. Читайте страницу Atlas Triggers своего проекта. Занятая коллекция может превысить бюджет триггера. Тогда нужен самоуправляемый воркер или очередь.

Триггер настраивают в UI Atlas или инфраструктурой как код, которую поддерживает Atlas. Выбираете коллекцию, типы операций и нужен ли полный документ.

Отказы повторяются по правилам Atlas. Делайте функцию идемпотентной. Повтор может запустить побочный эффект дважды.

Не кладите секреты в исходник триггера, который коммитите в публичный репозиторий. Используйте хранилище секретов Atlas.

Если Atlas не используете, Atlas Triggers нет. Используйте воркер change stream на своём хосте.

# 17. Безопасность

## Описание

Эта тема показывает, как защитить развёртывание MongoDB. Вы аутентифицируете пользователей. Назначаете **роли**. Ограничиваете **сетевой** доступ. Включаете **TLS**. Изучаете шифрование на уровне полей на высоком уровне. Используете типизированные API драйвера, чтобы не собирать запросы из сырых строк. Сначала завершите драйверы и идеи администрирования.

Используйте один термин для каждого понятия. **Аутентификация** доказывает, кто клиент. **Авторизация** (RBAC) решает, что этот пользователь может делать. **TLS** шифрует сеть. **Queryable Encryption** и **client-side field-level encryption** защищают значения полей так, что сервер может хранить шифротекст.

Учебной базе на localhost всё равно нужен пароль, прежде чем открывать порт. Atlas нуждается в пользователе базы и списке IP-доступа (или частной сети), прежде чем открыть кластер приложению.

## Аутентификация (SCRAM, x.509)

**Аутентификация** проверяет учётные данные. MongoDB поддерживает несколько механизмов. Частые для приложений — **SCRAM** и **x.509**.

**SCRAM** (Salted Challenge Response Authentication Mechanism) использует имя пользователя и пароль. Текущие серверы предпочитают **SCRAM-SHA-256**. Клиент и сервер доказывают пароль, не отправляя пароль открытым текстом (TLS на сети всё равно нужен).

Создайте пользователя на самоуправляемом сервере после включения авторизации:

```javascript
use admin
db.createUser({
  user: "app",
  pwd: "use-a-secret-store",
  roles: [ { role: "readWrite", db: "shop" } ]
})
```

Положите пользователя и пароль в URI или дайте драйверу спросить. Не коммитьте пароль.

**x.509** использует сертификаты. Клиент предъявляет сертификат. Сервер сопоставляет субъект сертификата с пользователем. Члены replica set также могут использовать x.509, чтобы аутентифицироваться друг к другу.

Atlas: пользователя базы создаёте в UI. Atlas по умолчанию использует SCRAM для этих пользователей. Можно добавить другие методы, которые документирует Atlas (LDAP, AWS IAM, OIDC на некоторых тарифах). Флаги `mongod` вручную не запускаете.

Включите авторизацию на Community Server (`security.authorization: enabled`). Без неё клиент, который достигает порта, может делать что угодно.

`localhost exception` позволяет создать первого пользователя на свежем самоуправляемом сервере. Прочитайте эту страницу, прежде чем запереть себя.

Не используйте один пароль в Atlas и в публичном gist.

Не создавайте пользователя с ролью `root` для приложения.

## Управление доступом на основе ролей

**Управление доступом на основе ролей (RBAC)** выдаёт привилегии через **роли**. Привилегия — действие над ресурсом (база, коллекция или кластер).

Встроенные роли (примеры):

- `read` — find на базе
- `readWrite` — find и запись
- `dbAdmin` — индексы и часть администрирования базы
- `userAdmin` / `userAdminAnyDatabase` — управлять пользователями
- `clusterMonitor` — многие статистик кластера только для чтения
- `backup` / `restore` — действия, связанные с dump и restore
- `root` — все действия (только операторам и только когда нужно)

Назначайте наименьшую роль, которая работает. Приложению нужен `readWrite` на своей базе, не `root`.

Можно создать свою роль, когда встроенные роли слишком широки:

```javascript
db.createRole({
  role: "orderWriter",
  privileges: [
    { resource: { db: "shop", collection: "orders" }, actions: [ "find", "insert", "update" ] }
  ],
  roles: []
})
```

У Atlas есть встроенные роли в UI. Свои роли в Atlas тоже есть. Используйте их.

Не делите одного пользователя между многими приложениями. Утечка тогда имеет большой радиус поражения.

Не выдавайте `dropCollection` веб-приложению, если приложение никогда не удаляет коллекции.

Аудит (Enterprise / Atlas) может записывать события auth. Прочитайте, включает ли это ваша редакция.

Список привилегий — через `rolesInfo` и UI Atlas.

## Сетевая открытость: bind IP, VPC, списки IP

Порт MongoDB в публичном интернете без контроля — частый инцидент. Ограничьте, кто может открыть TCP-соединение.

**Самоуправляемый `bindIp`.** Привяжите к `127.0.0.1` для лаборатории только локально. Привяжите к частному интерфейсу для VPC. Не привязывайте к `0.0.0.0` без аутентификации, TLS и файрвола.

**Файрвол.** Разрешите порт `27017` (или свой порт) только из подсетей приложения. Остальное запретите.

**Список IP-доступа Atlas.** Atlas отказывает клиентам, которых нет в списке (если не используете private endpoint и соответствующий режим). Добавьте исходящие IP приложения. Не добавляйте `0.0.0.0/0`, кроме недолгого учебного кластера без реальных данных, и уберите после.

**VPC и частная сеть.** Поместите `mongod` в частную подсеть. В Atlas используйте VPC peering или private endpoint, чтобы трафик не шёл через публичный интернет.

**SRV и DNS.** Клиенты разрешают хосты Atlas. Всё равно ограничивайте IP или частную связность. DNS — не контроль доступа.

Сетевой контроль — не аутентификация. Нужны оба. Украденный пароль с ноутбука в списке всё равно работает. Публичный порт с сильным паролем всё равно цель сканирования.

Не публикуйте `mongod` на облачной VM с группой безопасности вендора «разрешить всем».

Не держите личный домашний IP в списке Atlas после ухода из проекта.

## TLS

**TLS** (Transport Layer Security) шифрует байты в сети. Клиенты и серверы аутентифицируют сертификат. Без TLS наблюдатель сети может читать запросы и документы.

Atlas требует TLS для клиентских соединений. Официальный URI включает `tls=true` (или старый `ssl=true`). Драйвер проверяет сертификат Atlas.

Самоуправление:

- Задать `net.tls.mode` (например `requireTLS`)
- Указать PEM-сертификат и ключ
- Раздать файл CA клиентам
- Использовать TLS и для трафика членов replica set

Не используйте самоподписанный сертификат в продакшене без настоящего плана CA. Не отключайте проверку сертификата (`tlsInsecure`, `sslAllowInvalidCertificates`) кроме короткой лаборатории и никогда с реальными данными.

Сертификаты истекают. Занесите обновление в календарь. Истёкший сертификат останавливает приложение.

`mongodb+srv` в Atlas уже подразумевает TLS. URI `mongodb://` к самоуправляемому хосту может не подразумевать. Будьте явные.

TLS — не шифрование на уровне полей. Сервер всё равно видит документы открытым текстом после окончания TLS.

Не смешивайте «TLS к базе» с «HTTPS к пользователю» и не думайте, что закончили. Пути от сервера приложения к `mongod` тоже нужен TLS.

## Шифрование на уровне полей / Queryable Encryption (обзор)

**Client-side field-level encryption (CSFLE)** шифрует выбранные поля в драйвере, прежде чем документ достигнет сервера. Сервер хранит шифротекст. Операторы, которые читают коллекцию без ключей, не видят открытый текст.

**Queryable Encryption** — более поздний продукт, который позволяет шифровать поля и всё равно выполнять некоторые запросы равенства (и в текущих версиях больше) по этим полям. Сервер использует зашифрованные индексы. Читайте текущее руководство. Точные типы запросов растут с версиями.

Части на высоком уровне:

- Сервис **управления ключами** (KMIP, облачный KMS или локальный ключ только для лабораторий)
- **Ключ шифрования данных** на поле или хранилище, обёрнутый мастер-ключом
- Достаточно новый драйвер
- Схема или карта автоматического шифрования, которая именует поля

Используйте эти инструменты для полей высокой чувствительности (национальный id, некоторые данные здоровья, некоторые платёжные токены), когда политика требует, чтобы администратор базы не видел открытый текст.

Лимиты:

- Не каждый оператор работает на шифротексте
- Случайное шифрование (CSFLE) блокирует запросы равенства, если не использовать queryable-продукт правильно
- Потеря ключа значит потерю данных
- Растут CPU и размер

Эта тема остаётся обзорной. Не выдумывайте самодельное XOR-«шифрование» в приложении.

TLS плюс RBAC плюс CSFLE решают разные задачи. Могут понадобиться все три.

У Atlas есть продуктовые страницы и помощники. В некоторых установках применяются возможности Enterprise и лицензирование. Читайте, что включает ваша редакция.

## Без инъекции через запросы из строк (используйте типизированные API)

Инъекция запросов MongoDB случается, когда собираете запрос из **строк** или сырого пользовательского JSON и передаёте его драйверу без контроля.

Классическая ошибка — взять HTTP JSON и передать его как фильтр:

```javascript
// unsafe if body is the whole filter
collection.find(req.body)
```

Клиент может отправить `{ "role": "admin" }` или операторы вроде `$gt` и `$ne`. Фильтр тогда — фильтр атакующего.

Другая ошибка — склеивать строки в `$where` или в фрагмент JavaScript. Не используйте `$where` для фильтров приложения.

Безопасные привычки:

- Собирать объект фильтра в коде. Задавать каждое поле из **типизированного** значения (строка, число, ObjectId).
- Разрешать только поля, по которым клиент может фильтровать.
- Преобразовывать id типом `ObjectId` драйвера. Не принимать объект оператора там, где ждёте id.
- Использовать официальный API драйвера, не строку JavaScript, которую `eval`.
- Для библиотек в стиле SQL поверх MongoDB всё равно привязывать параметры. Предпочитать официальный драйвер.

Библиотеки ODM могут помочь, если считают ввод пользователя значениями, а не полными документами запроса. Они также могут спрятать `$where`. Читайте документацию.

Это тот же класс бага, что SQL-инъекция. Язык — BSON, не SQL. Правило то же: ввод пользователя — данные, не структура запроса.

Не логируйте полные запросы, которые содержат пароли или токены.

## Обзор темы

Эти вопросы не повторяют вопросы из разделов выше. Они охватывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Как аутентификация, RBAC и сетевые списки останавливают разных атакующих?
2. Когда TLS и шифрование на уровне полей оба применяются на одном соединении?
3. Почему пользователь с наименьшими привилегиями всё равно может утечь данные, если обработчик передаёт `req.body` в `find`?
4. Как пользователи SCRAM, члены x.509 и пользователи UI Atlas складываются в одну производственную картину?
5. Коллега привязывает `0.0.0.0`, отключает проверку TLS и использует `root` в API. Какими фактами вы ответите на ревью?

#### Простые практические задания

3. Нарисуйте слои защиты: сеть, TLS, auth, RBAC, шифрование полей, безопасный API.
4. Перечислите пять секретов, которых не должно быть в git (пароль URI, ключ PEM, ключ KMS, секрет триггера, файл дампа).

#### Сложные практические задания

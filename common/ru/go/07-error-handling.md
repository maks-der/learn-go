# 7. Обработка ошибок

## Описание

Go считает ошибку обычным значением. Функция возвращает `error`, когда операция может завершиться неудачей. Вызывающий код проверяет значение и выбирает следующий шаг. Эта тема показывает интерфейс `error`, как создавать и оборачивать ошибки и как просматривать цепочку ошибок. Тема также показывает, когда `panic` уместен.

Сначала завершите тему 4. Тема 4 вводит `panic` и `recover`. Эта тема даёт правила для рабочего кода. Используйте один термин для каждой идеи. Используйте `error` для значения, которое реализует интерфейс `error`. Используйте `panic` только для сбоя, после которого программа не должна продолжаться.

## Интерфейс `error`

Предопределённый интерфейс `error` имеет один метод:

```go
type error interface {
	Error() string
}
```

Любой тип с методом `Error() string` является `error`. Метод возвращает сообщение для людей и для логов. Не разбирайте эту строку в логике. Просматривайте типизированное значение или цепочку.

Нулевое значение интерфейса `error` — `nil`. Ошибка `nil` означает успех. Ненулевая ошибка означает сбой. Проверяйте ошибку сразу после возврата функции:

```go
n, err := w.Write(p)
if err != nil {
	return err
}
```

По соглашению `error` — последний результат. Типичная сигнатура — `func Open(name string) (*File, error)`. Когда `err != nil`, не используйте остальные результаты, если пакет не документирует особый случай.

Значение интерфейса равно `nil` только когда тип и данные оба не заданы. Функция, которая возвращает `error`, должна вернуть интерфейс `nil`, а не указатель nil, сохранённый в интерфейсе. Эта ошибка частая:

```go
var p *MyError = nil
return p // the error is not nil
```

Возвращайте `nil` напрямую. Не возвращайте указатель nil как `error`.

## `errors.New`, `fmt.Errorf` и `%w`

Пакет `errors` создаёт простую ошибку:

```go
err := errors.New("not found")
```

`errors.New` сохраняет строку. Строка позже не меняется. Используйте `errors.New` для фиксированного сообщения без дополнительных данных.

`fmt.Errorf` форматирует сообщение как `fmt.Sprintf` и возвращает `error`:

```go
err := fmt.Errorf("user %d not found", id)
```

Глагол `%w` оборачивает другую ошибку. Новая ошибка держит исходную ошибку в цепочке:

```go
err := fmt.Errorf("load config: %w", fileErr)
```

Используйте `%w`, когда вызывающий код всё ещё должен обнаружить исходную ошибку через `errors.Is` или `errors.As`. Используйте `%v` или `%s`, когда нужен только текст и цепочку не сохраняете. Строка формата должна использовать `%w` только с операндом `error`.

С Go 1.20 можно обернуть больше одной ошибки в одном вызове:

```go
err := fmt.Errorf("copy %s to %s: %w; %w", src, dst, errRead, errWrite)
```

`errors.Join` тоже объединяет ошибки. `errors.Join` возвращает `nil`, когда каждый вход — `nil`. Используйте `errors.Join`, когда два или больше независимых шага не удались и нужно сообщить обо всех.

Не оборачивайте одну ошибку много раз без причины. Каждое оборачивание добавляет кадр контекста. Держите сообщение коротким. Не начинайте сообщение с заглавной буквы. Не заканчивайте сообщение точкой. Это стиль стандартной библиотеки.

Добавляйте контекст на слое, у которого есть данные. Оборачивайте в точке, где вызываете другую функцию. Не кладите секреты в сообщение. Не оборачивайте на каждой строке внутри одной функции, когда нового факта нет.

## `errors.Is` и `errors.As`

После оборачивания ошибок `==` не находит внутреннее значение. Type assertion на внешней ошибке не находит внутренний тип. Используйте функции пакета `errors`.

`errors.Is(err, target)` обходит цепочку. Возвращает true, когда значение в цепочке совпадает с `target`. Совпадение использует `==` или метод `Is(error) bool` на типе в цепочке. Используйте `errors.Is` для сентинел-ошибок:

```go
if errors.Is(err, os.ErrNotExist) {
	// the file is missing
}
```

`errors.As(err, &target)` обходит цепочку. Находит первое значение, которое совпадает с типом `target`. `target` должен быть ненулевым указателем на тип, который реализует `error`, или указателем на интерфейс. При успехе `errors.As` записывает значение в `target` и возвращает true:

```go
var pe *os.PathError
if errors.As(err, &pe) {
	fmt.Println(pe.Path)
}
```

`errors.Unwrap(err)` возвращает следующую одну ошибку в цепочке. Возвращает `nil`, когда следующей ошибки нет. `errors.Unwrap` не обходит объединение многих ошибок. `errors.Is` и `errors.As` обходят объединение.

Не пишите `err == os.ErrNotExist` после оборачивания. Не пишите `err.(*os.PathError)` после оборачивания. Используйте `errors.Is` и `errors.As`.

Когда `err` — `nil`, `errors.Is(err, target)` истинно только когда `target` тоже `nil`.

## Сентинел-ошибки против пользовательских типов ошибок

Сентинел-ошибка — переменная уровня пакета, которую вызывающий код сравнивает через `errors.Is`:

```go
var ErrNotFound = errors.New("not found")
```

Стандартная библиотека использует сентинелы. Примеры: `io.EOF`, `os.ErrNotExist`, `sql.ErrNoRows`. Сентинел верен, когда сбой — один известный случай и вызывающему коду не нужны лишние поля.

Пользовательский тип ошибки — структура (или другой именованный тип) с методом `Error() string`. Добавьте поля для данных, которые вызывающий код должен прочитать:

```go
type QueryError struct {
	Query string
	Err   error
}

func (e *QueryError) Error() string {
	return e.Query + ": " + e.Err.Error()
}

func (e *QueryError) Unwrap() error {
	return e.Err
}
```

Добавьте `Unwrap`, когда тип оборачивает другую ошибку. Тогда `errors.Is` и `errors.As` проходят через тип.

Используйте сентинел, когда случай стабилен и нет дополнительных данных. Используйте пользовательский тип, когда вызывающий код должен прочитать путь, код статуса или другое поле. Не экспортируйте большой набор сентинелов, которые никогда не появляются в коде вызывающего. Не используйте пользовательский тип, когда достаточно сентинела.

Сравнивайте сентинелы через `errors.Is`, не через `==`, когда возможно любое оборачивание. Обнаруживайте пользовательские типы через `errors.As`, не через type assertion, когда возможно любое оборачивание.

## Когда уместен panic

`error` — для сбоя, который вызывающий код может обработать. `panic` останавливает текущую горутину. Если никто не вызывает `recover`, процесс печатает стек и завершается.

Используйте `panic` только когда программа не может продолжаться безопасным способом. Типичные случаи:

- Инвариант программиста ложен. Пример: switch пропускает ветку, которую система типов не может исключить, и вы считаете это ошибкой.
- Инициализация не может завершиться и полезной программы не остаётся. Пример: обязательный упакованный ресурс отсутствует в двоичном файле.
- Вы достигли состояния, которое означает порчу памяти или невозможный контракт.

Не используйте `panic` для ожидаемых сбоев. Отсутствующие файлы, плохой ввод пользователя, сетевые таймауты и случаи HTTP 4xx — ошибки. Вызывающий код должен получить `error`.

Не используйте `panic` как второй путь возврата в библиотеке. Библиотечный код, который паникует на обычном вводе, заставляет каждого вызывающего использовать `recover`. Такой дизайн трудно тестировать и трудно составлять.

`recover` принадлежит определённой границе. HTTP-сервер в стандартной библиотеке восстанавливается после panic в обработчике, чтобы один запрос не остановил процесс. Не разбрасывайте `recover` в каждой функции. Восстанавливайтесь на границе и логируйте panic.

Разыменование указателя nil, индекс вне диапазона и отправка в закрытый канал тоже паникуют. Эти panic — ошибки. Исправьте код. Не скрывайте их широким `recover`, если вы не на границе процесса.

Помощник `Must*` вызывает функцию, которая возвращает `(T, error)`, и паникует, когда ошибка не `nil`. Используйте `Must*`, когда вход — фиксированный литерал или встроенный файл и сбой означает, что двоичный файл неверен. Примеры: `regexp.MustCompile` и `template.Must`. Не используйте `Must*` на вводе пользователя.

#### Теоретические вопросы

1. Опишите путь от низкоуровневой ошибки `os` до вызывающего кода, который использует `errors.Is` после двух оборачиваний.
2. Как выбирать среди `errors.New`, `fmt.Errorf` с `%w`, сентинела и пользовательского типа?
3. Почему существуют `errors.Is` и `errors.As`, когда уже есть `==` и type assertion?
4. Когда публичный API должен скрыть внутреннюю ошибку вместо оборачивания через `%w`?
5. Как решать между возвращённой ошибкой, panic `Must*` при init и recover на границе сервера?

#### Простые практические задания

1. Напишите `func load(path string) ([]byte, error)`, которая оборачивает `os.ReadFile` через `%w` и путь. Вызовите её для отсутствующего файла и напечатайте ошибку.
2. Обнаружьте `os.ErrNotExist` через `errors.Is` на этой обёрнутой ошибке. Напечатайте `true` или `false`.
3. Объявите `ErrEmpty` как сентинел. Верните её, когда путь — `""`. Обнаружьте её через `errors.Is`.
4. Нарисуйте таблицу: Создать ошибку, Обернуть ошибку, Проверить сентинел, Проверить тип, Panic. Добавьте одно имя функции или форму в каждую ячейку.

#### Средние практические задания

1. Постройте три пакета: `store`, `service`, `cmd`. Каждый слой оборачивает через `%w` и одно новое слово. Напечатайте итоговую ошибку. Покажите `errors.Is` для корневого сентинела.
2. Напишите пользовательский `*PathError` с `Unwrap`. Используйте `errors.As` в `main`, чтобы напечатать путь после оборачивания.
3. Просмотрите пять строк `return err` в небольшой программе. Оставляйте оборачивание только на границах пакетов. Запишите, какие строки меняете.

#### Сложные практические задания

1. Напишите помощник `func wrap(op, name string, err error) error`, который возвращает `nil`, когда `err` — `nil`. Используйте его в трёх местах вызова. Докажите, что вход nil остаётся nil.
2. Спроектируйте политику ошибок для библиотеки: какие ошибки остаются в цепочке, какие становятся сентинелами и какие теряют причину. Напишите политику на одну страницу и реализуйте одну функцию, которая ей следует.

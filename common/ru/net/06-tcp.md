# 6. TCP

## Описание

TCP — транспортный протокол, который даёт надёжный поток байтов. TCP строит соединение, нумерует байты, повторяет потерянные данные и управляет скоростью отправки. Эта тема показывает тройное рукопожатие. Вы узнаете номера последовательности, повтор передачи и окно. Вы узнаете управление перегрузкой: slow start и AIMD. Вы узнаете закрытие и `TIME_WAIT`. Вы узнаете блокировку начала очереди.

Завершите эту тему после UDP. Завершите эту тему до программ на сокетах, которые считают поток данным.

Используйте один термин для каждого понятия. Сегмент — единица TCP на проводе. Соединение — состояние, которое держат два хоста. Окно приёма защищает приёмника. Окно перегрузки защищает сеть. Не смешивайте управление потоком с управлением перегрузкой. Не считайте TCP протоколом сообщений.

TCP не сохраняет границы сообщений. Приложение должно разбирать поток.

## Тройное рукопожатие

TCP-соединение начинается с тройного рукопожатия. Клиент отправляет сегмент с флагом SYN и начальным номером последовательности. Сервер отвечает SYN и ACK и своим начальным номером последовательности. Клиент отправляет ACK. После этого обе стороны могут слать данные.

Рукопожатие согласует начальные номера последовательности и опции вроде максимального размера сегмента (MSS). Рукопожатие также доказывает, что обе стороны могут принимать пакеты в обычном случае.

Сокет сервера в состоянии listen принимает новые SYN. Ядро держит очередь соединений, которые закончили рукопожатие. `accept` в следующей теме берёт одно соединение из этой очереди.

Рукопожатие может не удаться. Межсетевой экран может отбросить SYN. Сервер может отправить RST, если никто не слушает. Клиент может истечь по таймауту. SYN flood — поздняя тема безопасности. Этому разделу нужно только: SYN использует память ядра.

Первый байт данных в некоторых стеках может ехать с третьим ACK. Три флага SYN, SYN-ACK, ACK — учебная последовательность.

Не отправляйте данные приложения так, будто соединение есть до завершения рукопожатия (пока не изучите TCP Fast Open позже). Не называйте рукопожатие похожим на UDP. У UDP нет рукопожатия.

## Номера последовательности, повтор передачи и окно

TCP нумерует поток байтов. Номер последовательности в сегменте — номер первого байта в этом сегменте (после того как рукопожатие тратит один номер последовательности на SYN). Номер подтверждения — следующий байт, который отправитель ACK ожидает.

Накопительный ACK говорит: у меня все байты до этого номера. Selective ACK (SACK) — опция, которая называет дополнительные блоки. Этой теме сначала нужен накопительный ACK.

Номера последовательности 32-битные и заворачиваются. Относительные номера в Wireshark для отображения начинаются с 0. На проводе абсолютное значение. У каждой стороны своё пространство последовательности. Не складывайте их.

Отправитель держит копию неподтверждённых байтов. Если ACK не приходит вовремя, отправитель повторяет передачу. Обнаружение потери использует таймаут повтора (RTO) и быстрый повтор (часто после нескольких дубликатов ACK).

Надёжность — не Bound на задержку. Ужасный путь может повторять долго. Приложениям всё равно нужны таймауты. Успешный `write` значит, что локальный стек принял байты. Это не доказывает, что сосед их прочитал. RST заканчивает поток.

Управление потоком защищает приёмника. Приёмник объявляет окно: сколько ещё байтов может принять. Отправитель не должен слать больше неподтверждённых данных, чем позволяет окно. Окно ноль значит, что отправитель должен остановиться, кроме зондов окна.

Управление потоком — не управление перегрузкой. Управление потоком — про буфер приёма. Управление перегрузкой — про путь сети.

Не считайте номер последовательности счётчиком пакетов. Большой сегмент прыгает последовательность на много байт. Не задавайте крошечный буфер приёма сокета без причины.

## Управление перегрузкой (slow start, AIMD)

Управление перегрузкой защищает сеть. Слишком много отправителей могут заполнить очередь и отбросить пакеты. TCP считает потерю (а в современных стеках — сигналы задержки) знаком замедлиться.

Slow start: окно перегрузки (`cwnd`) начинается малым и растёт быстро (часто экспоненциально), пока приходят ACK. Отправитель может держать больше данных в полёте.

AIMD: additive increase, multiplicative decrease. После slow start окно растёт медленно. После потери окно падает на большой коэффициент (классический Reno делит пополам). Детали различаются по алгоритму (Cubic, BBR). Этой теме нужна идея, а не формулы каждого варианта.

Отправитель использует минимум `cwnd` и окна приёма. Путь и приёмник оба могут ограничить скорость.

Управление перегрузкой — причина, почему один поток TCP не остаётся на полной скорости линии после отбрасывания. Это также причина, почему много потоков могут грубо делить канал.

Новое соединение платит slow start. Keep-alive HTTP (тема 8) и HTTP/2 (тема 11) переиспользуют соединение, чтобы поздние запросы пропускали новый slow start.

Не отключайте управление перегрузкой, чтобы ехать быстрее в публичном Internet. Не считайте каждую потерю перегрузкой на Wi-Fi. Потеря может быть шумом. Современные стеки пытаются различить. Идея всё равно начинается с «потеря может значить замедлиться».

## Закрытие и `TIME_WAIT`

Чистое закрытие TCP использует сегменты FIN. Каждая сторона закрывает своё направление отправки. Обычная учебная последовательность — закрытие из четырёх сегментов: FIN, ACK, FIN, ACK. Некоторые стеки совмещают FIN и ACK. Идея — полузакрытие: одна сторона всё ещё может принимать после того, как перестала слать.

RST обрывает соединение. Данные в полёте могут пропасть с точки зрения приложения. Предпочитайте чистое закрытие, когда можете.

`TIME_WAIT` — состояние на стороне, которая сделала активное закрытие. Этот хост держит 5-кортеж занятым короткое время (часто две максимальные жизни сегмента). Ожидание отбрасывает задержанные сегменты старого соединения, чтобы новое соединение с тем же кортежем не получило старые данные.

Много коротких клиентских соединений могут заполнить `TIME_WAIT` на клиенте. Это причина переиспользовать соединения. Серверы, которые активно закрывают много соединений, тоже могут видеть `TIME_WAIT`. `SO_REUSEADDR` (тема 7) помогает привязаться во время некоторых ожиданий. Это не удаляет нужду в состоянии.

Не убивайте `TIME_WAIT` твиком ядра на публичном сервере без причины. Не считайте `TIME_WAIT` утечкой. Это таймер безопасности.

Приложение видит чтение нуля байт при чистом закрытии. Это не UDP.

## Блокировка начала очереди

Блокировка начала очереди (HOL) значит, что потеря или простой в начале очереди задерживает всё позади.

В TCP один потерянный сегмент задерживает доставку поздних байт приложению, пока щель не заполнится. TCP должен представить упорядоченный поток. HTTP/2 мультиплексирует много запросов на одном TCP-соединении. Потерянный сегмент TCP всё равно останавливает все потоки на уровне TCP. Это причина, почему HTTP/3 использует QUIC на UDP (тема 11).

HOL также появляется на других уровнях. HTTP/1.1 на одном соединении в обычном клиенте ждёт один ответ перед следующим запросом. Очередь коммутатора может задержать большой поток и маленький поток, которые делят порт. Называйте уровень, когда говорите HOL.

HOL TCP — не ошибка спецификации. Это цена упорядоченного надёжного потока.

Не открывайте сотни TCP-соединений, чтобы избежать HOL, без измерения. Каждое соединение платит рукопожатие и slow start. Не вините заголовки HTTP за простой потери TCP на HTTP/2.

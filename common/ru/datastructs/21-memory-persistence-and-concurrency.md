# 21. Память, персистентность и параллельность

## Описание

Эта тема объясняет, как структуры разделяют память, как они сохраняют старые версии, как больше одного потока их использует и как они ведут себя, когда данные не помещаются в ОЗУ. Вы изучаете структурное разделение, копирование при записи, конкурентные очереди и отображения, идеи cache-oblivious и внешнюю сортировку. Завершите эту тему после массивов, деревьев и предварительного взгляда на персистентное дерево отрезков.

Используйте один термин для каждого понятия. **Персистентная** структура сохраняет старые версии после обновления. **Структурное разделение** переиспользует неизменённые узлы. **Копирование при записи** копирует страницу или узел только когда писатель меняет его. **Блокировка** позволяет одному потоку войти в критическую секцию. **Прогресс без блокировок** использует атомарные операции без мьютекса (точное определение — более поздний курс).

## Персистентные / неизменяемые структуры данных (структурное разделение)

**Неизменяемая** структура не меняется на месте. «Обновление» возвращает **новый корень**. Старый корень всё ещё показывает старое значение.

**Структурное разделение** означает, что новая версия переиспользует узлы, которые не изменились. Push персистентного списка копирует новую голову и указывает на старый список. Обновление персистентного дерева копирует путь от корня к изменённому листу. Неизменённые поддеревья остаются общими.

```text
old list:  a → b → c
push d:    d → a → b → c
           a, b, c are the same nodes
```

```text
old tree root0
update one leaf
new path of O(height) nodes
side children still point into the old tree
```

Память одного обновления — O(высота) для дерева, не O(n), если вы разделяете. Время — тот же класс, что изменяемое обновление плюс выделение пути.

Применения: отмена, несколько версий, более безопасное разделение между потоками, если версии неизменяемы (читатели держат старый корень).

Персистентная структура не автоматически хранится на диске. Персистентность здесь означает **версии в памяти**. Долговечность диска — другое слово в базах данных. Этот справочник говорит **версионная** или **структурно персистентная**, когда путаница высока. Заголовок темы использует смысл структуры CS.

Не мутируйте общий узел. Мутация меняет каждую версию, которая указывает на этот узел.

Функциональные языки часто используют персистентные отображения и векторы (битово-разделённые боры). Прочитайте одну картинку после того, как поймёте копирование пути.

Персистентное дерево отрезков в теме 18 — один пример. Персистентный стек — более простая первая реализация.

## Копирование при записи

**Копирование при записи (COW)** откладывает копию, пока писатель не изменит общий объект. Читатели разделяют одну физическую страницу или узел. Первая запись копирует страницу, затем меняет копию.

Операционные системы используют COW для `fork`: родитель и ребёнок разделяют страницы, пока один процесс не пишет. Файловые системы и некоторые базы данных используют COW для снимков страниц.

```text
two users share page P
user A writes
system copies P to P'
A writes into P'
user B still reads P
```

COW — родственник структурного разделения. Разделение — выбор по умолчанию. Копия происходит при записи. Зерно может быть страницей памяти (ОС) или узлом дерева (персистентное дерево).

**Массив COW** (простой): две структуры держат указатель на один backing-массив и счётчик ссылок. Запись, которая не должна задеть другого пользователя, сначала копирует массив. Это дорого, если вы копируете весь массив. Персистентный вектор копирует только путь блоков.

Не путайте COW с глубокой копией при каждом присваивании. Глубокая копия всегда копирует. COW копирует только при записи и только ту часть, которую называет дизайн.

Счётчики ссылок или сборка мусора должны освободить страницу или узел, когда ни одна версия его не использует.

В однопоточном редакторе отмена может быть снимками COW буферов. Копия полного буфера проста и медленна. Верёвка или персистентное дерево — лучшее разделение.

Когда вы вызываете `fork` в Unix, адресное пространство ребёнка — COW. Этот факт — пример ОС, не домашнее задание по структурам данных.

## Конкурентные очереди и отображения (концептуально: блокировка против без блокировок)

Два потока не должны писать один изменяемый узел без правила. **Гонка** — ошибка, когда результат зависит от небезопасного чередования.

**Мьютекс** (блокировка) вокруг всей структуры — простое правило. Один поток держит блокировку, делает операцию, затем отпускает блокировку. ADT остаётся верным. Потоки ждут. Большая критическая секция может быть медленной.

**Более мелкая блокировка** (одна блокировка на корзину хеш-отображения) позволяет потокам касаться разных корзин одновременно. Вы всё равно должны блокировать в фиксированном порядке, если нужны две блокировки.

Структуры **без блокировок** используют атомарное сравнение с обменом (CAS) на указателях или индексах. Неудачный CAS повторяет. Цель — что некоторый поток завершает операцию, даже если другие потоки останавливаются (точные термины прогресса: lock-free, wait-free). Эти термины принадлежат курсу параллельности. Этому справочнику нужна идея: нет мьютекса, атомики, циклы повтора, трудно доказать.

```text
locked queue
  lock
  enqueue
  unlock

lock-free queue (idea)
  CAS tail next from null to node
  CAS tail to node
  retry if CAS fails
```

**Конкурентная очередь** — частая нужда (перехват работы, конвейеры). **Конкурентное отображение** — частая нужда (кэши). Многие языки дают хорошо протестированный тип. Предпочитайте языковой тип в продакшене.

Не изобретайте отображение без блокировок как первый проект. Реализуйте отображение, защищённое мьютексом. Затем прочитайте одну стандартную очередь без блокировок (Майкл–Скотт) как учёбу, не как первую запись.

Неизменяемые персистентные корни могут позволить многим читателям работать без блокировки. Один писатель может опубликовать новый корень атомарным сохранением указателя. Это полезный шаблон. Это не полное отображение без блокировок.

Порядок памяти (acquire, release) — более поздняя тема. Не игнорируйте его, если пишете атомики. Сначала используйте языковую очередь.

## Идея cache-oblivious (ознакомление)

**Cache-aware** алгоритм использует размер строки кэша или размер блока B как параметр. Вы настраиваете код под B.

**Cache-oblivious** алгоритм написан без B. Тот же код эффективен для каждого уровня кэша, если модель выполняется. Анализ использует идеальный кэш, который программа не называет.

```text
cache-aware:   tile size = B, you write B in the code
cache-oblivious: recurse on halves, no B in the code
```

Классические примеры (ознакомление): расположение van Emde Boas завершённого дерева, cache-oblivious сортировка, cache-oblivious аналог B-дерева. Вы не реализуете их в этой теме.

Идея, которую вы уже используете: **просмотр массива** имеет хорошую локальность. **Преследование указателей** на связном списке имеет плохую локальность. Куча в массиве более кэш-дружественна, чем куча указателей. B+-дерево cache-aware (или disk-aware): размер узла — страница.

Расположение cache-oblivious пытается получить выигрыш многоуровневого кэша без константы страницы в исходнике.

Этот раздел — **только ознакомление**. Не переписывайте свои библиотеки в порядке van Emde Boas сейчас.

```text
you implement now:  array-friendly layouts that you already know
you only name:      cache-oblivious, van Emde Boas layout
```

Когда текст говорит «cache-oblivious», читайте «нет B в коде, анализ всё равно использует B».

## Алгоритмы внешней памяти (сортировка, которая не помещается в ОЗУ)

**Внешняя память** означает, что данные живут на диске или SSD. ОЗУ держит только часть. Дорогой шаг — **передача блока** между диском и ОЗУ, не сравнение CPU.

**Блок** имеет размер B. ОЗУ держит M слов. Вход имеет N записей. Число передач — главная стоимость.

**Внешняя сортировка слиянием** (идея):

1. Читайте куски около M / size(record) записей. Сортируйте каждый кусок в ОЗУ. Пишите каждый отсортированный **прогон** на диск.
2. Сливайте k прогонов за раз. k ограничен тем, сколько блоков размера B помещается в ОЗУ (k-путевое слияние).
3. Повторяйте проходы слияния, пока не останется один отсортированный файл.

```text
pass 0:  many sorted runs of length ~ M
pass 1:  merge groups of k runs
...
last:    one run of length N
```

Это та же идея слияния, что у сортировки слиянием в памяти. Разница — явные прогоны и блоковый ввод-вывод.

Не загружайте все N записей в ОЗУ, если N не помещается. Программа будет страничить случайно и станет очень медленной или упадёт.

B+-дерево — структура **поиска** внешней памяти. Внешняя сортировка — **сортировка** внешней памяти. Базы данных используют оба.

Replacement selection может сделать прогоны длиннее M. Это необязательное улучшение.

Считайте вводы-выводы в модели: просмотр N записей стоит около N / B передач. Хорошая внешняя сортировка стоит около (N / B) log_{M/B}(N / B) передач. Запомните форму формулы. Вам не нужно доказательство здесь.

Реализуйте крошечную симуляцию: файлы как файлы прогонов, малое M, целые записи. Не утверждайте производственную сортировку.

Эти вопросы не повторяют вопросы разделов выше. Они покрывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Опишите путь от изменяемого массива к версионному дереву, затем к дисковым прогонам, которые не помещаются в ОЗУ.
2. Как структурное разделение и COW оба избегают полной копии, но на разном зерне?
3. Напарник говорит «без блокировок всегда быстрее». Какие факты вы используете в аккуратном ответе?
4. Что cache-oblivious отказывается класть в исходник и что внешняя сортировка называет намеренно?
5. Почему многие читатели могут разделять неизменяемый корень, пока писатель публикует новый корень?

#### Простые практические задания

1. Напишите шпаргалку на одну страницу: разделение, COW, мьютекс против CAS, ознакомление cache-oblivious, прогоны внешней сортировки.
2. Нарисуйте один общий список, одну страницу COW и одно дисковое слияние двух прогонов.
3. Составьте таблицу: «Задача», «Инструмент». Пять строк.
4. Напишите N, M, B и «новый корень» по памяти в одном предложении каждое.

#### Средние практические задания

1. Реализуйте персистентный стек и очередь с мьютексом. Напишите тесты для версий и для двух потоков.
2. Реализуйте малое внешнее слияние файлов прогонов. Проверьте вывод против сортировки в памяти тех же целых.
3. Замерьте просмотр массива против обхода указателей. Напишите оба времени и причину локальности.

#### Сложные практические задания

1. Напишите дизайн крошечного версионного хранилища ключ-значение в ОЗУ (персистентное дерево) плюс заметку о том, когда вы сбросили бы прогоны на диск. Не стройте базу данных.
2. Прочитайте последнюю тему (практика). Напишите пять структур из этого пути, которые вы реализуете снова по памяти.

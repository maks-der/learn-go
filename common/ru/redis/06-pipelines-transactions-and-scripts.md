# 6. Конвейеры, транзакции и скрипты

## Описание

Клиент Redis отправляет команды и читает ответы. Эта тема объясняет одну команду за раз против конвейера, транзакции Redis (`MULTI`, `EXEC`, `WATCH`) и скрипты на стороне сервера. Вы узнаете, что значит «атомарно» в Redis и чем это отличается от отката SQL.

Завершите эту тему до изучения персистентности и репликации.

Используйте один термин для каждого понятия. Круг — одна сетевая отправка и одно ожидание ответа. Конвейер — много команд в одной отправке, ответы позже. Транзакция — очередь блока, который `EXEC` выполняет без чередования других команд. Скрипт — Lua или Redis Function, который выполняется на сервере.

---

## Конвейер против одной команды за раз

Режим по умолчанию — запрос/ответ. Клиент отправляет `GET k`. Клиент ждёт. Redis отвечает. Клиент отправляет следующую команду. Каждая команда платит сетевую задержку (RTT).

Конвейер отправляет много команд без ожидания после каждой команды. Клиент затем читает все ответы по порядку. Redis всё равно выполняет команды по одной в основном потоке. Выигрыш — меньше времени на ожидание сети.

```text
# conceptual, not a special Redis command
INCR views
INCR views
INCR views
```

В конвейере эти три `INCR` могут лежать в одной записи TCP. Ответы — `1`, `2`, `3`, если ключ начинался отсутствующим.

`redis-cli` может конвейерить из файла:

```text
redis-cli --pipe < commands.txt
```

Клиентские библиотеки имеют API конвейера. Используйте его для многих независимых команд (тысячи `SET`, много `HGET`).

Конвейер — не транзакция. Другие клиенты могут выполнять команды между вашими конвейерными командами. Отката нет. Если соединение оборвётся, вы можете не знать, какие команды выполнились.

Держите пакеты конвейера ограниченными (например сотни или несколько тысяч команд). Огромный конвейер использует буферы клиента и сервера.

Не конвейерьте команды, которые должны видеть предыдущий ответ (если не принимаете, что нельзя ветвиться посередине). Для «прочитать, затем записать если» используйте `WATCH`, скрипт Lua или Function.

При RTT 0,5 мс 10 000 `GET` ждут около 5 секунд только сети. Конвейер из 10 000 `GET` платит несколько RTT за весь пакет плюс время сервера.

`MGET` и `MSET` сокращают RTT для строк на одном слоте. Они не полная замена конвейера смешанных команд.

Клиенты Cluster делят пакеты по слотам (тема 8). Конвейер огромных `GET` всё ещё может застопорить основной поток и заполнить буферы.

## `MULTI` / `EXEC` / `WATCH`

`MULTI` начинает транзакцию. Redis ставит следующие команды в очередь на этом соединении. Redis ещё не выполняет их. Немедленный ответ — `QUEUED`.

`EXEC` выполняет очередные команды по порядку как одну единицу в основном потоке. Никакое другое соединение не выполняет команду посередине этого `EXEC`. Ответ — массив ответов, по одному на очередную команду.

`DISCARD` сбрасывает очередь и завершает транзакцию без `EXEC`.

```text
MULTI
INCR acct:1
INCR acct:2
EXEC
```

Если у очередной команды синтаксическая ошибка, Redis может отклонить `EXEC` и ничего не выполнить (зависит от того, когда Redis обнаружит ошибку). Если команда падает при выполнении (`WRONGTYPE`, отсутствующий ключ для типа), более поздние команды в том же `EXEC` всё равно выполняются. Redis не откатывает более ранние команды.

`WATCH key [key ...]` помечает ключи на текущем соединении. Если любой наблюдаемый ключ меняется до `EXEC`, Redis прерывает транзакцию. `EXEC` возвращает null. Клиент затем повторяет: снова `WATCH`, прочитать, `MULTI`, записать, `EXEC`.

Это оптимистичная блокировка. Вы предполагаете, что конфликт редок. Вы обнаруживаете конфликт на `EXEC`.

```text
WATCH acct:1
GET acct:1
MULTI
SET acct:1 40
EXEC
```

Если другой клиент пишет `acct:1` после `WATCH` и до `EXEC`, `EXEC` падает. Ваш `SET` не выполняется.

`UNWATCH` снимает наблюдения. `EXEC` и `DISCARD` тоже снимают наблюдения.

`WATCH` привязан к соединению. Нужно делать `GET` на том же соединении после `WATCH` и использовать это соединение для `MULTI` / `EXEC`. Пул соединений не должен смешивать эти шаги между соединениями.

`WATCH` не блокирует других клиентов. Они всё ещё могут писать. Вместо этого падает ваш `EXEC`.

Не делайте `WATCH` огромного набора ключей. Не используйте `WATCH` как распределённую блокировку. Используйте `SET NX EX` для обзора блокировки или скрипт для обновлений нескольких ключей.

`WATCH` плюс `MULTI` достаточно для «прочитать баланс, записать если всё ещё тот же» на одном экземпляре. В Cluster все ключи транзакции должны жить в одном слоте (тема 8).

Используйте `MULTI` / `EXEC`, когда нужно, чтобы несколько команд выполнились без чередования, и не нужно читать значение посередине. Нельзя сделать `GET` внутри `MULTI` и полезно использовать это значение в следующей очередной команде на клиенте. `GET` стоит в очереди. Клиент не видит значение до `EXEC`.

Для логики, которая читает и затем пишет, используйте `WATCH` или Lua.

У транзакций нет уровней изоляции как в SQL. Нет точек сохранения. Они сами по себе не ждут диск.

## Почему транзакции Redis — не откат SQL

Транзакции SQL могут сделать `ROLLBACK`. Движок отменяет записи, когда вы прерываете, или когда падает ограничение (зависит от движка и оператора).

`EXEC` Redis не отменяет. Если команда 1 в транзакции проходит, а команда 2 падает, команда 1 остаётся применённой. Redis — не реляционный движок. Нет блокировок строк, нет отката WAL транзакции и нет команды `ROLLBACK`, которая восстанавливает значения.

Транзакции Redis дают:

- нет чередования других команд во время `EXEC`
- необязательное прерывание всего `EXEC`, когда `WATCH` обнаруживает изменение
- очередное выполнение на одном соединении

Транзакции Redis не дают:

- откат упавшей команды внутри `EXEC`
- интерактивное чтение своих записей внутри очереди
- атомарный коммит на нескольких экземплярах (нет двухфазного коммита в базовом Redis)

Если нужно «все ключи обновить или ни один» с логикой, положите логику в скрипт Lua или Function. Скрипт выполняется как одна команда. Если вы сделаете `redis.call` записи и затем попадёте в ошибку, записи, которые уже выполнились в этом скрипте, остаются применёнными, если не проверите ошибки до записи. Пишите скрипты так, чтобы проверки шли первыми.

Компенсация на уровне приложения (записать обратное) возможна, но её легко испортить. Предпочитайте один атомарный скрипт для обновлений вроде денег на одном экземпляре Redis.

Не называйте `MULTI` Redis «транзакцией SQL» на разборе дизайна. Говорите «очередной атомарный пакет» или «транзакция Redis».

## Lua: `EVAL`, `EVALSHA`

`EVAL script numkeys key [key ...] arg [arg ...]` выполняет скрипт Lua на сервере. Скрипт использует `KEYS[]` и `ARGV[]`. Redis выполняет скрипт как одну команду. Другие команды ждут.

```text
EVAL "return redis.call('INCR', KEYS[1])" 1 lab:c
```

`redis.call` поднимает ошибку при ошибке Redis. `redis.pcall` возвращает значение ошибки.

`EVALSHA sha1 numkeys ...` выполняет скрипт, который сервер уже закэшировал. `SCRIPT LOAD` возвращает SHA1. `EVALSHA` экономит полосу. Если сервер перезапустился и кэш пуст, клиент получает `NOSCRIPT` и должен снова сделать `EVAL` или `SCRIPT LOAD`.

Используйте скрипт, когда нужно читать и писать несколько ключей с логикой и без чередования. Пример: инкремент счётчика и `EXPIRE` только когда новое значение — `1`. Пример: снять блокировку, если `GET` равен вашему токену.

Правила:

- Передавайте каждый ключ, к которому обращаетесь, в списке `KEYS`. Не стройте имена ключей из `ARGV` в скриптах, безопасных для Cluster.
- Держите скрипты короткими. Длинный скрипт блокирует экземпляр.
- Не используйте Lua как общий сервер приложений. Нет длинных циклов. Нет случайных пауз.
- Скрипты должны быть детерминированными для репликации. Избегайте `TIME` в старых режимах, если не следуете документированному шаблону. Читайте документацию скриптов для вашей версии.

Redis реплицирует скрипт или его эффекты на реплики. Ошибка в скрипте тоже может реплицироваться.

Предпочитайте `EVALSHA` плюс шаг загрузки при старте приложения.

## Functions (Redis 7+)

Redis 7 добавляет Functions. Function — зарегистрированная библиотека, которая живёт на сервере. Клиенты вызывают `FCALL name numkeys key [key ...] arg ...`.

Вы загружаете библиотеку через `FUNCTION LOAD` и полезный груз, который задаёт документация (синтаксис библиотеки Lua). `FUNCTION LIST` показывает библиотеки. `FUNCTION DELETE` удаляет библиотеку. `FUNCTION FLUSH` удаляет все (только лаборатория).

Functions решают эксплуатационные проблемы сырых строк `EVAL` в каждом клиенте:

- Сервер хранит код
- Можно обновить библиотеку в одном месте
- `FCALL` использует стабильное имя

Functions всё равно выполняются в основном потоке. Они всё равно атомарны. Они всё равно блокируют, если медленные. Правила ключей Cluster всё равно применяются.

`EVAL` всё ещё работает. Многие приложения оставляют скрипты Lua. Новые дизайны на Redis 7+ могут предпочитать Functions, когда коллектив хочет версионирование на стороне сервера.

Нужно персистировать functions как другие данные, если они нужны после перезапуска. Проверьте, восстанавливают ли ваш режим персистентности и репликация functions. Официальная страница Functions описывает персистентность и репликацию.

Не смешивайте десять копий одного Lua в клиентах и библиотеку Function без одного источника истины.

AOF и RDB могут включать определения functions, чтобы у реплики или перезапуска всё ещё были цели `FCALL`. Проверьте это в лаборатории до продакшена.

### Вопросы

#### Теоретические вопросы

1. Ранжируйте конвейер, `MULTI`/`EXEC`, `WATCH` и Lua по «нет другой команды посередине» и по «можно использовать результат чтения в дальнейшей логике».
2. Что ломается через пулы соединений, если использовать `WATCH`?
3. Чем атомарность Redis отличается от отката SQL?
4. Когда выбирать `EVALSHA` или `FCALL` вместо конвейера на стороне клиента?
5. Какой общий риск есть у длинных конвейеров, длинных транзакций и длинных скриптов на однопоточном Redis?

#### Простые практические задания

1. Запустите один конвейер `PING`, один `MULTI`/`EXEC` из `PING` и один `EVAL`, который возвращает `PONG`. Сохраните формы трёх ответов.
2. Напишите шпаргалку: `--pipe`, `MULTI`, `EXEC`, `DISCARD`, `WATCH`, `EVAL`, `EVALSHA`, `FCALL`.
3. Нарисуйте блок-схему: независимые записи → конвейер; пакет всё-или-ничего без чтений → `MULTI`; чтение-затем-запись → `WATCH` или Lua.
4. Перечислите три команды, которые никогда не положите в горячий скрипт (`KEYS`, огромный `LRANGE`, `DEBUG SLEEP`).

#### Средние практические задания

1. Напишите скрипт, который конвейерит 5000 `SET`, затем запускает Lua `INCR`+`EXPIRE` на одном ключе лимита частоты. Напечатайте времена.
2. Опишите правило пула соединений для транзакций и скриптов (одно соединение, таймаут, повтор).
3. Реализуйте инкремент-если-меньше-N тремя способами (`WATCH`, Lua, Function если доступен). Составьте таблицу гонок и повторов.

#### Сложные практические задания

1. Под параллельными клиентами сравните потерянные обновления для `GET`+`SET` против `INCR` против Lua compare-and-set. Сообщите итоговые значения.
2. Прочитайте `SCRIPT KILL` и `FUNCTION KILL` (занятый скрипт). Запишите, когда можно убить скрипт и когда нельзя (записи уже начались).

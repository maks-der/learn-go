# 8. Роли и безопасность

## Описание

Эта тема показывает роли, привилегии и безопасность подключений в PostgreSQL 16 и PostgreSQL 17. Вы узнаёте роли входа, `GRANT` и `REVOKE`, привилегии по умолчанию, безопасность на уровне строк, функции `SECURITY DEFINER`, SSL и почему приложение не должно использовать суперпользователя.

Сначала завершите тему 7. Вы умеете обслуживать кластер. Завершите эту тему до написания функций и триггеров.

Используйте один термин для каждого понятия. Роль — учётная запись кластера. Пользователь — роль с `LOGIN`. Привилегия — именованное право на объект. Политика — фильтр строк для безопасности на уровне строк. Роль приложения — вход, который использует программа. Суперпользователь — роль с `SUPERUSER`. Этот справочник рассчитан на PostgreSQL 16 и PostgreSQL 17.

## Роли против пользователей

PostgreSQL хранит учётные записи как роли. Роль с `LOGIN` может открыть сессию. Роль без `LOGIN` — группа. В старых текстах «пользователь» — роль входа. `CREATE USER name` — это `CREATE ROLE name LOGIN`. В новых скриптах предпочитайте `CREATE ROLE`, чтобы атрибуты были видны.

```sql
CREATE ROLE shop_read NOLOGIN;
CREATE ROLE shop_app LOGIN PASSWORD 'secret';
GRANT shop_read TO shop_app;
```

`shop_app` может использовать привилегии `shop_read`, когда `shop_app` наследует членство. PostgreSQL 16 и 17 позволяют задать `INHERIT` и `SET` на каждом членстве. `INHERIT true` добавляет привилегии группы члену. `SET true` позволяет члену выполнить `SET ROLE` на эту группу.

Полезные атрибуты роли:

- `LOGIN` / `NOLOGIN` — сессия или группа
- `INHERIT` / `NOINHERIT` — наследование привилегий группы по умолчанию (default уровня роли)
- `CREATEDB` — создавать базы
- `CREATEROLE` — создавать роли
- `REPLICATION` — подключения репликации
- `BYPASSRLS` — пропускать безопасность на уровне строк
- `SUPERUSER` — почти все проверки выключены

Роль принадлежит кластеру. Роль не создаёте внутри одной базы. Привилегии на объекты всё равно действуют внутри каждой базы.

`PUBLIC` — особая неявная цель выдачи. Каждая роль — член `PUBLIC`. В PostgreSQL 15 и новее у `PUBLIC` нет `CREATE` на схеме `public`. PostgreSQL 16 и 17 это правило сохраняют.

Осмотреть роли:

```sql
SELECT rolname, rolsuper, rolcanlogin, rolbypassrls
FROM pg_roles
ORDER BY rolname;
```

`\du` в `psql` перечисляет роли.

Не делите одну роль входа между несвязанными программами. Не кладите продакшен-пароль в справочник или коммит git.

## `GRANT` / `REVOKE` и привилегии по умолчанию

Привилегия — право, которое выдаёте на объект. Владелец объекта имеет все привилегии. Другим ролям нужен `GRANT`. `REVOKE` снимает привилегию.

Привилегии схемы:

- `USAGE` — искать объекты в схеме
- `CREATE` — создавать объекты в схеме

Привилегии таблицы включают `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES` и `TRIGGER`. Привилегии последовательности включают `USAGE`, `SELECT` и `UPDATE`. Столбцы identity используют последовательность. `INSERT`, который использует identity, нуждается в `USAGE` последовательности.

```sql
CREATE SCHEMA shop;
CREATE TABLE shop.items (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name text NOT NULL
);

GRANT USAGE ON SCHEMA shop TO shop_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON TABLE shop.items TO shop_app;
GRANT USAGE, SELECT ON SEQUENCE shop.items_id_seq TO shop_app;
```

Можно выдать на каждую текущую таблицу в схеме:

```sql
GRANT SELECT ON ALL TABLES IN SCHEMA shop TO shop_read;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA shop TO shop_app;
```

`ALL TABLES` действует на таблицы, которые есть сейчас. Не действует на таблицы, которые создадите позже. Привилегии по умолчанию покрывают поздние объекты.

`CONNECT` — привилегия базы. Без `CONNECT` роль не может открыть сессию на этой базе.

```sql
GRANT CONNECT ON DATABASE shop TO shop_app;
REVOKE CONNECT ON DATABASE shop FROM PUBLIC;
```

`psql` показывает привилегии через `\dp` (таблицы) и `\dn+` (схемы).

`ALTER DEFAULT PRIVILEGES` задаёт выдачи для объектов, которые роль создаст позже. Уже существующие объекты не меняет.

```sql
ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA shop
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO shop_app;

ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA shop
    GRANT USAGE, SELECT ON SEQUENCES TO shop_app;
```

`FOR ROLE migrator` значит: когда `migrator` создаёт таблицу в `shop`, применить эти выдачи. Привилегии по умолчанию — на базу. `psql` `\ddp` их перечисляет.

Типичное разделение:

- `migrator` владеет таблицами и запускает `CREATE TABLE`
- у `shop_app` только DML
- привилегии по умолчанию выдают DML от `migrator` к `shop_app`

Не выдавайте `ALL` на каждый объект роли приложения, когда программе нужны только `SELECT` и `INSERT`. Не выдавайте привилегии таблицы без `USAGE` на схему. Не считайте, что `GRANT ON ALL TABLES` хватает после добавления таблиц.

Официально: [https://www.postgresql.org/docs/17/sql-grant.html](https://www.postgresql.org/docs/17/sql-grant.html).

## Безопасность на уровне строк

Безопасность на уровне строк (RLS) добавляет политику на таблицу. После включения RLS обычная роль видит только строки, которые проходят `USING`. Вставки и обновления должны проходить `WITH CHECK`.

```sql
ALTER TABLE shop.orders ENABLE ROW LEVEL SECURITY;

CREATE POLICY orders_by_tenant ON shop.orders
    FOR ALL
    TO shop_app
    USING (tenant_id = current_setting('app.tenant_id')::bigint)
    WITH CHECK (tenant_id = current_setting('app.tenant_id')::bigint);
```

Сессия задаёт параметр, затем запрашивает:

```sql
SET app.tenant_id = '42';
SELECT * FROM shop.orders;
```

`current_setting('app.tenant_id')` падает, если параметра нет и вы не используете `missing_ok`. Держите выражение политики простым.

Владелец таблицы обходит RLS, если не форсировать:

```sql
ALTER TABLE shop.orders FORCE ROW LEVEL SECURITY;
```

Роль с `BYPASSRLS` или `SUPERUSER` тоже пропускает RLS. У роли приложения не должно быть этих атрибутов.

Политики могут быть `FOR SELECT`, `FOR INSERT`, `FOR UPDATE`, `FOR DELETE` или `FOR ALL`. Можно прикрепить больше одной политики. Для одной команды PostgreSQL сочетает разрешающие политики через `OR` (по умолчанию). Ограничивающие политики используют `AND`. Начинайте с одной разрешающей политики на таблицу.

`EXPLAIN` может показать фильтр политики как квалификатор. Тестируйте ролью приложения, не владельцем.

Не считайте RLS единственным контролем. Всё равно нужен `GRANT`. Роль без `SELECT` не видит строк. Не включайте RLS и не забывайте `FORCE`, если владелец — также роль приложения.

Официально: [https://www.postgresql.org/docs/17/ddl-rowsecurity.html](https://www.postgresql.org/docs/17/ddl-rowsecurity.html).

## Опасность `SECURITY DEFINER`

Функция по умолчанию выполняется с привилегиями вызывающего (`SECURITY INVOKER`). `SECURITY DEFINER` выполняется с привилегиями владельца. Используйте только когда вызывающему нельзя иметь эти привилегии, а тело функции — узкая проверенная операция.

Опасность: функция может трогать объекты, которые вызывающий трогать не может. Если функция использует неквалифицированные имена, `search_path` может указать на схему, которую контролирует вызывающий. Тогда функция может вызвать неверную функцию или использовать неверную таблицу.

Безопасный шаблон для PostgreSQL 16 и 17:

```sql
CREATE FUNCTION shop.touch_item(p_id bigint)
RETURNS void
LANGUAGE sql
SECURITY DEFINER
SET search_path = pg_catalog, shop
AS $$
    UPDATE shop.items SET name = name WHERE id = p_id;
$$;
```

`SET search_path` на функции фиксирует путь на вызов. Включите `pg_catalog`. Включите только схемы, которым доверяете. Часть команд использует `SET search_path = ''` и квалифицирует каждое имя.

Также:

- выдавайте `EXECUTE` только ролям, которым нужна функция
- отзывайте `EXECUTE` у `PUBLIC`, когда можете
- держите тело коротким
- предпочитайте `SECURITY INVOKER`, когда хватает `GRANT`
- не собирайте динамический SQL вместе с недоверенным текстом

`SECURITY DEFINER` плюс RLS легко сделать неверно. Владелец функции может обойти RLS. Тестируйте настоящим вызывающим.

Не копируйте пример `SECURITY DEFINER` из интернета без фиксированного `search_path`. Не используйте `SECURITY DEFINER`, чтобы спрятать суперпользователя от приложения. Владелец функции не должен быть суперпользователем, если у задачи нет другого дизайна.

Официальное предупреждение: [https://www.postgresql.org/docs/17/sql-createfunction.html](https://www.postgresql.org/docs/17/sql-createfunction.html) (см. `SECURITY`).

## SSL и почему роль приложения не суперпользователь

SSL шифрует TCP-сессию между клиентом и сервером. PostgreSQL 16 и 17 используют TLS. В старых текстах всё ещё говорят SSL. Имена настроек сохраняют `ssl`.

Сторона сервера (`postgresql.conf`):

- `ssl = on`
- `ssl_cert_file` и `ssl_key_file` — сертификат и ключ сервера
- необязательный `ssl_ca_file` — когда проверяете клиентские сертификаты

`pg_hba.conf` может требовать SSL:

```text
hostssl shop shop_app 10.0.0.0/8 scram-sha-256
```

`hostssl` совпадает только с SSL-подключениями. `hostnossl` совпадает только с не-SSL. `host` совпадает с обоими.

Клиентский `sslmode` (libpq):

| Значение | Смысл |
| --- | --- |
| `disable` | без SSL |
| `allow` / `prefer` | пробовать оба; `prefer` — default libpq |
| `require` | SSL обязателен; проверки сертификата нет |
| `verify-ca` | SSL плюс сертификат сервера, подписанный вашим CA |
| `verify-full` | `verify-ca` плюс совпадение имени хоста |

Продакшен-клиенты используют `verify-full`, когда контролируете CA и имя хоста. `require` останавливает открытый текст. Неверный сервер не останавливает.

```text
postgresql://shop_app@db.example:5432/shop?sslmode=verify-full
```

`psql` показывает SSL после подключения, когда выполняете `\conninfo`.

Суперпользователь обходит большинство проверок привилегий. Суперпользователь может читать и писать файлы, которые может читать пользователь ОС, запускать `COPY` из файлов, менять роли и пропускать RLS. Роль `postgres` по умолчанию — суперпользователь.

Роль приложения должна быть обычным входом:

```sql
CREATE ROLE shop_app LOGIN PASSWORD 'secret';
-- без SUPERUSER, без BYPASSRLS, без REPLICATION
```

Используйте суперпользователя (или узкую админскую роль) для установки, части работы `CREATE EXTENSION`, полного `pg_dumpall` ролей и восстановления после сбоя. Используйте роль migrator с `CREATE` на прикладной схеме для `CREATE TABLE`. Эта роль всё равно не суперпользователь.

```sql
SELECT current_user, session_user;
SELECT rolsuper FROM pg_roles WHERE rolname = current_user;
```

Если программа подключается как `postgres`, каждая SQL-инъекция или украденный пароль — полный компромисс кластера. Облачные вендоры часто прячут настоящего суперпользователя и дают мощную админскую роль. Эту админскую роль считайте «не для приложения».

SSL не заменяет пароли или `pg_hba.conf`. Не открывайте `5432` в публичный интернет и затем полагайтесь только на SSL. Тема 14 разбирает сетевые правила. Не выдавайте `SUPERUSER`, чтобы отладить ошибку привилегии. Выдайте недостающую привилегию.

Официальный SSL: [https://www.postgresql.org/docs/17/ssl-tcp.html](https://www.postgresql.org/docs/17/ssl-tcp.html).

4. Почему у роли приложения не должно быть `SUPERUSER`?
5. Заменяет ли SSL пароль?

#### Простые практические задания

1. Подключитесь через `psql` и выполните `\conninfo`. Запишите, использует ли сессия SSL.
2. Напишите URI, который задаёт `sslmode=require` для локального теста.
3. Выполните `SELECT rolsuper FROM pg_roles WHERE rolname = current_user;` как роль приложения, если она есть.
4. Найдите `ssl` через `SHOW ssl;`, если есть разрешение.

#### Средние практические задания

1. Сравните строку `host` и строку `hostssl`. Напишите, какие клиенты могут совпасть с каждой строкой.
2. Задайте `sslmode=disable` против сервера, который требует SSL (лаборатория). Запишите ошибку.
3. Создайте вход не-суперпользователя. Докажите, что `CREATE ROLE` или `CREATE EXTENSION` падает. Выдайте недостающую привилегию вместо `SUPERUSER`.

#### Сложные практические задания

1. Включите SSL на учебном сервере (самоподписанный допустим). Подключитесь с `sslmode=require`. Сохраните `\conninfo`.
2. Напишите политику на одну страницу: атрибуты роли приложения, роль migrator, SSL `sslmode` и `pg_hba.conf` `hostssl`.

## Обзор темы

Эти вопросы не повторяют вопросы разделов выше. Они покрывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Как групповая роль, `GRANT` на таблицы и привилегии по умолчанию работают вместе, когда migrator добавляет таблицу?
2. Почему RLS — второй фильтр после `GRANT`, а не замена?
3. Какие две ошибки превращают `SECURITY DEFINER` в утечку привилегий?
4. Почему `sslmode=require` мало для продакшена, если контролируете DNS?
5. Какой радиус поражения у украденного пароля `shop_app`, если эта роль не суперпользователь?

#### Простые практические задания

1. Создайте `shop_app` и `shop_read`. Выдайте `USAGE` схемы и `SELECT` таблицы `shop_read`. Подключитесь каждой ролью. Выполните `SELECT current_user, rolsuper FROM pg_roles WHERE rolname = current_user`.
2. Напишите шпаргалку: роль, `GRANT`, default, RLS, definer, SSL, суперпользователь.
3. Перечислите роли через `\du` и привилегии таблиц через `\dp`.
4. Напишите URI подключения с `sslmode=verify-full` и без пароля в строке.

#### Средние практические задания

1. Включите RLS на таблице тенанта. Задайте привилегии по умолчанию для новых таблиц. Проверьте вставку как `shop_app` с параметром тенанта.
2. Отзовите `CONNECT` у `PUBLIC`. Докажите, что подключаются только выданные роли. Сначала восстановите доступ к лаборатории, если работаете на общем кластере.
3. Создайте функцию definer с фиксированным `search_path`. Вызовите её как `shop_app`. Покажите состояние SSL `\conninfo` в тех же заметках.

#### Сложные практические задания

1. Напишите скрипт магазина с наименьшими привилегиями: migrator владеет объектами, у app есть DML, у читателя есть `SELECT`, RLS на `tenant_id`, без суперпользователя, комментарий `hostssl` в образце `pg_hba.conf`.
2. Прочитайте «Database Roles», «Privileges», «Row Security» и «SSL» в документации 17. Добавьте одно официальное предупреждение, которое эта тема не цитировала.

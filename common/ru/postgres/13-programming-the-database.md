# 13. Программирование базы

## Описание

Эта тема показывает, как класть логику в PostgreSQL 16 и PostgreSQL 17. Вы узнаёте SQL-функции, PL/pgSQL, триггеры, генерируемые столбцы и расширения. Также узнаёте частые расширения: `pgcrypto`, `uuid-ossp`, `citext`, `pg_trgm` и `pg_stat_statements`.

Сначала завершите тему 12. Вы умеете выдавать `EXECUTE` и знаете риск `SECURITY DEFINER`. Завершите эту тему до хранения JSON-документов как основной модели.

Используйте один термин для каждого понятия. Функция — именованная подпрограмма, которая возвращает значение или множество. Процедура — подпрограмма, которую вызываете через `CALL` и которая может фиксировать. Триггер — функция, которую сервер запускает на событие таблицы. Генерируемый столбец хранит значение, которое сервер вычисляет. Расширение — упакованный набор объектов, который устанавливаете через `CREATE EXTENSION`. Этот справочник рассчитан на PostgreSQL 16 и PostgreSQL 17.

## SQL-функции

Тело SQL-функции — один SQL-оператор или список операторов в PostgreSQL 16 и 17. Имя языка — `sql`. Функция выполняется в той же транзакции, что вызывающий.

```sql
CREATE FUNCTION shop.item_label(p_name text, p_qty int)
RETURNS text
LANGUAGE sql
STABLE
AS $$
    SELECT p_name || ' (' || p_qty::text || ')';
$$;

SELECT shop.item_label('nail', 10);
```

Метки волатильности помогают планировщику:

- `VOLATILE` — по умолчанию; может менять данные или возвращать разные значения
- `STABLE` — тот же результат внутри одного сканирования для тех же аргументов; может читать таблицы
- `IMMUTABLE` — тот же результат навсегда для тех же аргументов; без чтения таблиц

Используйте `IMMUTABLE` только когда это правда. Неверная метка `IMMUTABLE` может заставить индекс или генерируемый столбец хранить устаревший результат.

SQL-функции могут возвращать таблицу:

```sql
CREATE FUNCTION shop.low_stock(p_min int)
RETURNS TABLE (id bigint, name text, qty int)
LANGUAGE sql
STABLE
AS $$
    SELECT i.id, i.name, i.qty
    FROM shop.items AS i
    WHERE i.qty < p_min;
$$;
```

Предпочитайте SQL-функции, когда тело — запрос. Планировщик часто может встроить простую SQL-функцию. Предпочитайте PL/pgSQL, когда нужны переменные, циклы или `EXCEPTION`.

`CREATE OR REPLACE FUNCTION` меняет тело. Некоторые смены сигнатуры требуют сначала `DROP FUNCTION`.

Выдавайте `EXECUTE` ролям, которые должны вызывать функцию. Отзывайте `EXECUTE` у `PUBLIC`, когда функция не публичный помощник.

Не прячьте длинный бизнес-поток во вложенных SQL-функциях, которые никто не может протестировать. Не помечайте функцию `IMMUTABLE`, если она вызывает `now()` или читает таблицу.

Официальный справочник: [https://www.postgresql.org/docs/17/xfunc-sql.html](https://www.postgresql.org/docs/17/xfunc-sql.html).

## PL/pgSQL: `$$`, `BEGIN`, исключения

PL/pgSQL — процедурный язык, который поставляется с PostgreSQL. Пишете блоки `BEGIN` ... `END`. Доллар-квотирование (`$$` или `$tag$`) держит тело, чтобы внутренние кавычки не ломали оператор `CREATE`. Тема 3 представила доллар-квотирование.

```sql
CREATE FUNCTION shop.clamp_qty(p_qty int)
RETURNS int
LANGUAGE plpgsql
IMMUTABLE
AS $fn$
BEGIN
    IF p_qty IS NULL THEN
        RETURN 0;
    END IF;
    IF p_qty < 0 THEN
        RETURN 0;
    END IF;
    RETURN p_qty;
END;
$fn$;
```

Блок может объявлять переменные:

```sql
CREATE FUNCTION shop.next_label(p_id bigint)
RETURNS text
LANGUAGE plpgsql
STABLE
AS $$
DECLARE
    v_name text;
BEGIN
    SELECT name INTO STRICT v_name
    FROM shop.items
    WHERE id = p_id;
    RETURN v_name;
EXCEPTION
    WHEN NO_DATA_FOUND THEN
        RETURN 'missing';
    WHEN TOO_MANY_ROWS THEN
        RAISE EXCEPTION 'duplicate id %', p_id;
END;
$$;
```

`INTO STRICT` требует ровно одну строку. `EXCEPTION` обрабатывает именованные условия. `RAISE` сообщает ошибку или сообщение. `RAISE NOTICE` — для отладки. Убирайте notices из продакшен-функций.

PL/pgSQL по умолчанию `VOLATILE`. Задавайте `STABLE` или `IMMUTABLE`, когда правила позволяют.

Процедуры используют `CREATE PROCEDURE` и `CALL`. Процедура в некоторых случаях может `COMMIT`. Предпочитайте функцию, которая возвращает значение, когда поведение фиксации процедуры не нужно.

Не ставьте пустой `EXCEPTION WHEN OTHERS`, который прячет каждую ошибку. Не обходите строку за строкой, когда одну SQL-команду может сделать работа.

Официальная глава: [https://www.postgresql.org/docs/17/plpgsql.html](https://www.postgresql.org/docs/17/plpgsql.html).

## Триггеры: `BEFORE` / `AFTER`, строка против оператора

Триггер запускает функцию, когда происходит событие таблицы. Сначала создаёте функцию. Функция возвращает `trigger` и использует переменные `TG_`. Затем прикрепляете её через `CREATE TRIGGER`.

Момент:

- `BEFORE` — выполняется до записи строки; можно менять `NEW`; можно вернуть `NULL`, чтобы пропустить строку
- `AFTER` — выполняется после записи; используйте для побочных эффектов, которые должны видеть итоговую строку
- `INSTEAD OF` — для представлений

Гранулярность:

- `FOR EACH ROW` — один раз на строку
- `FOR EACH STATEMENT` — один раз на оператор

```sql
CREATE FUNCTION shop.set_updated_at()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    NEW.updated_at := clock_timestamp();
    RETURN NEW;
END;
$$;

CREATE TRIGGER items_set_updated_at
    BEFORE UPDATE ON shop.items
    FOR EACH ROW
    EXECUTE FUNCTION shop.set_updated_at();
```

В PostgreSQL 16 и 17 ключевое слово — `EXECUTE FUNCTION` (в старых текстах `EXECUTE PROCEDURE`). Обе формы есть для совместимости. Предпочитайте `EXECUTE FUNCTION`.

`NEW` — новая версия строки на `INSERT` и `UPDATE`. `OLD` — старая версия строки на `UPDATE` и `DELETE`. У операторных триггеров нет записей строк `NEW` и `OLD`. Они могут использовать таблицы перехода (`REFERENCING NEW TABLE AS ...`), когда нужен набор строк.

Используйте триггер `BEFORE ROW`, чтобы заполнять столбцы. Используйте триггер `AFTER`, чтобы писать в таблицу аудита. Триггер `AFTER`, который обновляет ту же строку, может зациклиться. Избегайте такого дизайна.

Значения по умолчанию `updated_at` не меняются при `UPDATE`. Тема 5 сказала использовать триггер или задать столбец в операторе. Этот раздел — тот триггер.

Не используйте триггеры вместо внешнего ключа или ограничения check. Не складывайте много триггеров без задокументированного порядка (`WHEN`, имена, `pg_trigger.tgenabled`).

Официальная глава: [https://www.postgresql.org/docs/17/triggers.html](https://www.postgresql.org/docs/17/triggers.html).

## Генерируемые столбцы

Генерируемый столбец — столбец, который сервер вычисляет из других столбцов. В PostgreSQL 16 и PostgreSQL 17 обязательна хранимая форма. Ключевое слово — `STORED`. Сервер пишет значение на `INSERT` и `UPDATE`. Столбец можно индексировать. Генерируемый столбец нельзя `UPDATE` напрямую.

```sql
CREATE TABLE shop.products (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    price_net numeric(12, 2) NOT NULL,
    tax_rate numeric(4, 3) NOT NULL,
    price_gross numeric(12, 2)
        GENERATED ALWAYS AS (price_net * (1 + tax_rate)) STORED
);
```

PostgreSQL 16 и 17 не предлагают виртуальные генерируемые столбцы. Поздняя мажорная версия может добавить эту возможность. Не пишите `VIRTUAL` в скриптах 16 или 17.

Выражение должно быть `IMMUTABLE`. Оно может использовать другие базовые столбцы той же строки. Не может использовать подзапрос. Не может использовать волатильную функцию.

Генерируемый столбец — не триггер. Планировщик видит настоящий столбец. `SELECT *` его включает. Тема 8 сказала, что хранимый генерируемый столбец плюс B-tree может заменить длинный индекс по выражению, когда значение также выбираете.

```sql
CREATE INDEX products_price_gross_idx ON shop.products (price_gross);
```

Не копируйте генерируемое значение во второй записываемый столбец. Не кладите бизнес-правила, которым нужны другие таблицы, в генерируемый столбец. Используйте запрос, представление или функцию.

Официальный справочник: [https://www.postgresql.org/docs/17/ddl-generated-columns.html](https://www.postgresql.org/docs/17/ddl-generated-columns.html).

## Расширения: `CREATE EXTENSION`

Расширение — именованный пакет. `CREATE EXTENSION` создаёт его объекты и записывает имя в `pg_extension`. Файлы лежат в каталоге share PostgreSQL. Не копируйте SQL из блога как замену, когда расширение есть.

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
```

Многим расширениям нужен суперпользователь или роль с `CREATE` на базе плюс пакет на диске. Облачные вендоры часто разрешают список расширений и блокируют другие.

Перечислить, что сервер может загрузить:

```sql
SELECT name, default_version, installed_version
FROM pg_available_extensions
ORDER BY name;
```

Перечислить, что есть в этой базе:

```sql
SELECT extname, extversion FROM pg_extension ORDER BY 1;
```

`CREATE EXTENSION ... SCHEMA shop` кладёт объекты в эту схему, когда расширение позволяет. Некоторые расширения должны жить в `public` или в фиксированной схеме.

`DROP EXTENSION` удаляет объекты. `CASCADE` удаляет зависимые объекты. Используйте `CASCADE` только когда принимаете эту потерю.

`ALTER EXTENSION ... UPDATE` переходит на более новую версию расширения, которую даёт пакет.

Не включайте каждое расширение «на всякий случай». Каждое расширение добавляет объекты, работу обновления и поверхность атаки. Не создавайте те же функции вручную, когда поддерживаемый путь — `CREATE EXTENSION`.

Официальная глава: [https://www.postgresql.org/docs/17/extend-extensions.html](https://www.postgresql.org/docs/17/extend-extensions.html).

## Частые расширения: `pgcrypto`, `uuid-ossp` / gen `pgcrypto`, `citext`, `pg_trgm`, `pg_stat_statements`

Эти расширения contrib встречаются во многих приложениях PostgreSQL 16 и 17.

**`gen_random_uuid()`** встроен с PostgreSQL 13. Для UUID версии 4 в новой работе расширение не нужно:

```sql
SELECT gen_random_uuid();
```

**`uuid-ossp`** всё ещё даёт другие версии UUID (`uuid_generate_v1`, `uuid_generate_v5` и смежные функции). Создавайте только когда нужны эти функции.

**`pgcrypto`** даёт `crypt`, `gen_salt`, `digest`, `hmac` и функции шифрования. В старых текстах `pgcrypto` использовали для `gen_random_uuid()`. Для id предпочитайте встроенный `gen_random_uuid()`. Используйте `pgcrypto` для хешей паролей и работы digest. Не изобретайте свой протокол хеша.

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;
SELECT crypt('demo', gen_salt('bf'));
```

**`citext`** — текстовый тип без учёта регистра. `WHERE email = 'A@B.com'` совпадает с `a@b.com`. Уникальный индекс на `citext` без учёта регистра. Предпочитайте `citext` вместо `lower(email)` в каждом запросе, когда столбец всегда без учёта регистра. Можно также использовать `LOWER` плюс уникальный индекс на `lower(email)` без `citext`.

**`pg_trgm`** добавляет сходство триграмм и может индексировать `LIKE '%x%'` через GIN или GiST. Тема 7 это превьюила. Тема 8 разбирала GIN.

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX items_name_trgm ON shop.items USING gin (name gin_trgm_ops);
SELECT name FROM shop.items WHERE name LIKE '%nail%';
```

**`pg_stat_statements`** записывает нормализованный запрос и его суммарное время. Тема 9 его представила. Библиотеку нужно загрузить в `postgresql.conf`:

```text
shared_preload_libraries = 'pg_stat_statements'
```

Перезапустите сервер. Затем `CREATE EXTENSION pg_stat_statements` в каждой базе, которая должна запрашивать представление. Тема 18 разбирает операции вокруг этого представления.

Не храните обратимые ключи шифрования в той же таблице, что шифротекст, без плана ключей. Не включайте `pg_stat_statements` и затем игнорируйте `pg_stat_statements.track`. Не используйте `uuid-ossp` только чтобы генерировать UUID v4 на 16 или 17.

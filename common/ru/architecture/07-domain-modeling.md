# 7. Моделирование предметной области

## Описание

Моделирование предметной области — это работа по именованию бизнеса и по рисованию границ вокруг смысла. Эта тема разбирает ubiquitous language, bounded contexts, агрегаты, сущности, объекты-значения, доменные события и выборы согласованности внутри домена.

Предметная область — это предметная зона продукта (выдача книг, приём заказов, оценка экзаменов). Модель — это набор типов, правил и имён, которые ПО использует для этого предмета. Слабая модель использует только технические имена (`table1`, `manager`, `data`). Сильная модель использует слова людей, которые делают работу.

Завершите темы 1–6 до этой темы. Держите модели маленькими. Этот справочник использует Domain-Driven Design (DDD) в практической форме. Большая церемония DDD не нужна.

Используйте один термин для каждого понятия. Сущность — не объект-значение. Bounded context — не развёртываемый сервис. Доменное событие — не команда.

## Ubiquitous language

Ubiquitous language — это общий набор имён, который команда и эксперты предметной области используют в речи, в документах и в коде. У одного понятия одно имя. Это имя появляется в типах, именах таблиц, журналах и ADR.

Если эксперт говорит «loan», а код говорит «contract_x», люди переводят вечно. Перевод производит дефекты. Правило, которое формулирует эксперт, не совпадает с функцией, которую пишет разработчик.

Стройте язык из разговоров. Напишите короткий глоссарий. Включите:

- Имя
- Смысл одним предложением
- Пример
- Отвергнутый синоним

Не изобретайте имена, которые звучат «более технически». Не используйте пустые имена (`Manager`, `Processor`, `Item2`). Предпочитайте `Loan`, `Hold`, `Fine`.

Язык локален для bounded context (следующий раздел). Слово «customer» может значить две вещи в двух контекстах. Не навязывайте одно глобальное имя, когда эксперты не согласны.

Когда язык меняется, модель должна меняться. Переименование в бизнесе — архитектурный сигнал. Обновляйте глоссарий и типы вместе.

Используйте язык в тестах. Тест с именем `cannot_return_loan_if_fine_is_open` учит правило. Тест с именем `test1` не учит.

## Bounded context (DDD, практический)

Bounded context — это граница, внутри которой модель и язык согласованы. Внутри границы у каждого имени один смысл. Вне границы то же слово может значить другое.

Пример: «Order» в контексте покупок — покупка. «Order» в контексте склада — лист комплектации. Эти две модели не должны разделять один тип, который пытается быть обоими.

Bounded context — это граница проектирования. Он может жить в модульном монолите как модуль. Позже он может стать сервисом. Контекст не автоматически сервис. Тема 5: не дробите единицу развёртывания, пока не должны.

Между контекстами вы переводите. Опубликованное событие или DTO несёт данные, которые нужны другому контексту. Вы не разделяете внутренние сущности. Anti-corruption layer (позже в пути) — переводчик, который защищает вашу модель от внешней модели.

Как найти первую карту контекстов:

- Слушайте одно слово с разными правилами.
- Ищите разных владельцев (команда биллинга против команды каталога).
- Ищите разные нужды согласованности.
- Ищите документ или экран, который является миром сам по себе.

Держите первую карту маленькой. Двух или трёх контекстов достаточно для студенческой системы (catalog, loan, identity). Карта с пятнадцатью контекстами для одного человека — чрезмерное усложнение (тема 6).

Нарисуйте карту контекстов: имена, связи (upstream/downstream или «этот контекст публикует X») и владелец каждого контекста.

## Агрегаты и границы согласованности

Агрегат — это кластер доменных объектов, которые вы меняете как одну единицу. У агрегата есть корень. Все изменения идут через корень. Корень защищает инварианты.

Граница согласованности — это граница, внутри которой вы требуете немедленное согласованное обновление (часто одна транзакция). Агрегат — обычная граница согласованности в этом справочнике.

Пример: корень `Order` плюс объекты `OrderLine`. Инвариант «сумма строк равна итогу» проверяется на корне. Вы не обновляете строку снаружи корня.

Не делайте большой агрегат. Большой агрегат блокирует больше данных и создаёт конкуренцию. Если два пользователя могут менять две части независимо, эти части скорее два агрегата.

Ссылки между агрегатами используют идентификаторы, не графы объектов, которые вы сохраняете в одной транзакции. `Order` может хранить `CustomerID`. `Order` не хранит полный граф `Customer`, если customer — другой агрегат.

Одно действие пользователя может затронуть больше одного агрегата. Тогда нельзя иметь один простой инвариант через оба, если не использовать одну транзакцию через оба (жёсткое зацепление) или не принять eventual consistency (поздний раздел). Предпочитайте маленькие агрегаты и явные процессы.

Сохранение часто хранит один агрегат на транзакцию. Это правило держит границу настоящей. Если каждый сценарий использования обновляет десять агрегатов в одной транзакции, у вас нет десяти агрегатов. У вас один скрытый ком.

## Сущности против объектов-значений

Сущность — это объект со стабильной идентичностью. Две сущности могут иметь одинаковые атрибуты и всё равно быть разными. Пример: два пользователя с именем Ada с разными id. Вы отслеживаете сущность во времени.

Объект-значение — это объект, который вы определяете по атрибутам. Два объекта-значения с одинаковыми атрибутами — одно и то же. Пример: денежная сумма `10 EUR`, диапазон дат, адрес (если вы не даёте адресу собственную идентичность). Можно заменить объект-значение. Вы не обновляете его на месте как отслеживаемую идентичность.

Используйте сущности для вещей, которые бизнес отслеживает: `Loan`, `Customer`, `Invoice`. Используйте объекты-значения для мер, кодов и малых соединений: `Money`, `ISBN`, `EmailAddress`.

Объекты-значения часто неизменяемы. Смена адреса у человека — замена значения, не тихая мутация общего объекта.

Не давайте id строки базы каждому значению. Id не делает сущность. Делает бизнес. Id строки `Money` обычно утечка хранения в модель.

Равенство различается:

- Сущности: равны, если идентичность равна.
- Объекты-значения: равны, если атрибуты равны.

Проверка принадлежит обоим. Значение `EmailAddress` может отвергнуть плохую строку. Сущность может отвергнуть запрещённую смену состояния.

## Доменные события

Доменное событие — это запись, что в домене произошло что-то значимое. Имя в прошедшем времени: `LoanReturned`, `PaymentCaptured`, `SeatReserved`. Событие — факт. Вы не отменяете факт. Можно записать более поздний компенсирующий факт.

Доменные события помогают общению внутри модели и между контекстами. Другие модули могут реагировать. Событие `LoanReturned` может начать расчёт штрафа в другом модуле без прямого цикла импорта.

Событие — не команда. Команда — это запрос (`ReturnLoan`). Команда может провалиться. Событие — результат после успешного изменения (`LoanReturned`). Тема 10 разбирает команды против событий против запросов в обмене сообщениями.

Держите полезную нагрузку маленькой. Включите идентификаторы, время и данные, которые нужны подписчику. Не прикрепляйте полный граф агрегата, если подписчику нужны только id и дата возврата.

Сначала можно использовать события в процессе (вызовы функций к слушателям). Брокер не нужен, чтобы иметь доменное событие. Добавляйте брокер, когда процесс или граница команды требует его (тема 10).

Пишите события на ubiquitous language. `RowUpdated` — не доменное событие. `HoldExpired` — доменное событие.

Храните события, когда другие системы не должны их пропустить. Шаблон outbox (тема 10) — один метод. В маленьком монолите таблицы событий или диспетчера в процессе может хватить.

## Транзакционная и eventual consistency внутри домена

Транзакционная согласованность означает, что набор изменений фиксируется как одна единица. После фиксации все эти изменения видимы. Если фиксация падает, ни одно из изменений не видимо. Транзакция базы — обычный инструмент.

Eventual consistency означает, что система может показать временное разногласие. Более поздний процесс, сообщение или повтор приводит виды к согласию. Пользователь может видеть короткую задержку.

Внутри одного агрегата предпочитайте транзакционную согласованность. Инвариант корня должен держаться после транзакции.

Между агрегатами или между контекстами eventual consistency часто честная модель. Захваченный платёж и добавленная точка лояльности — два факта. Они могут использовать две транзакции и событие `PaymentCaptured`.

Не притворяйтесь, что распределённая система транзакционно согласована, если это не так. Сетевой вызов внутри транзакции базы — обычный дефект. Удалённая работа может пройти, а локальная фиксация упасть, или наоборот.

Выбирайте согласованность из бизнеса. «Число на полке и запись выдачи должны совпасть в ту же секунду» может заставить одну транзакцию или один агрегат. «Еженедельный отчёт может отставать на 5 минут» не должен заставлять распределённую транзакцию.

Меры помогают. Запишите максимальное отставание, которое принимает заинтересованная сторона. Это отставание — атрибут качества (тема 2).

Компенсирующие действия обрабатывают отказ в eventual-проектах: факт `PaymentFailed` после зарезервированного места или таймаут, который освобождает место. Тема 12 позже разбирает саги. Можно начать с простого повтора и списка ручного ремонта.

1. Спроектируйте выдачу книги с одним агрегатом и одной транзакцией. Затем напишите, что происходит, если штрафы живут в другом агрегате.
2. Нарисуйте временную шкалу eventual consistency для «заказ оформлен» и «запас зарезервирован». Покажите окно разногласия.
3. Напишите ADR, который отвергает распределённую транзакцию для письма после заказа.

#### Сложные практические задания

1. Напишите одностраничный лист решений: инвариант, максимальное отставание, владелец и стиль (транзакционный или eventual). Заполните пять строк.
2. Изучите публичное объяснение саг на высоком уровне. Сопоставьте его с компенсирующими событиями в этом разделе. Не копируйте длинный текст.

## Обзор темы

Эти вопросы не повторяют вопросы в разделах выше. Они покрывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Как ubiquitous language и bounded context останавливают один тип «User» от поглощения всего продукта?
2. Как агрегаты и выборы согласованности защищают инварианты без большой блокировки?
3. Когда доменное событие — правильный инструмент держать модули ациклическими (тема 3)?
4. Как сущности и объекты-значения меняют способ проектирования равенства и сохранения?
5. Почему эта тема остаётся полезной внутри модульного монолита?

#### Простые практические задания

1. Напишите одностраничную шпаргалку всех терминов с одним библиотечным примером каждого.
2. Постройте мини-модель: глоссарий (шесть терминов), два контекста, два агрегата, четыре события.
3. Нарисуйте карту контекстов и одну диаграмму агрегата для проката велосипедов.
4. Перечислите десять имён из вашего последнего проекта и пометьте язык, сущность/значение и контекст.

#### Средние практические задания

1. Напишите двухстраничный доменный проект для карты столовой: язык, контексты, агрегаты, события и таблица согласованности.
2. Напишите два ADR: границы агрегатов и события в процессе (без брокера).
3. Возьмите CRUD-схему (пять таблиц). Предложите модель, которая не только строки. Покажите инварианты.

#### Сложные практические задания

1. Напишите бумажный проект событий и агрегатов, который можно реализовать в одном процессе с одной базой.
2. Сравните обзорную главу DDD (публичную) с этим практическим подмножеством. Напишите, что вы сознательно пропускаете для маленькой команды.

# 9. Replica set

## Описание

Эта тема показывает, как MongoDB копирует данные между членами. **Replica set** — группа процессов `mongod`, которые держат один набор данных. Один член — **primary**. Остальные члены с данными — **secondary**. Вы изучаете выборы, oplog, устаревшие чтения и скрытые или отложенные члены.

Сначала завершите CRUD, драйверы и транзакции. Завершите эту тему до изучения шардирования.

Используйте один термин для каждого понятия. **Primary** принимает записи клиента. **Secondary** применяет те же записи из **oplog**. **Выборы** выбирают новый primary, когда текущий primary недоступен. **Устаревшее чтение** — чтение, которое ещё не включает недавнюю запись.

Репликация даёт высокую доступность. Репликация сама по себе — не резервная копия. Всё равно нужна копия, которую хранят вне replica set.

## Primary, secondary и выборы

У replica set в типичной производственной раскладке нечётное число голосующих членов. Три голосующих члена — частый минимум. Набор выбирает один primary. Остальные члены с данными — secondary.

Записи идут на primary. Primary записывает каждую запись в oplog. Каждый secondary тянет эти записи oplog и применяет их. После применения у secondary те же документы, что у primary, с возможной задержкой.

Replica set может включать:

- Членов с данными (`mongod` с полной копией)
- **Arbiter** (голосует, данных приложения не держит)

Arbiter — особый случай. Atlas и текущие рекомендации предпочитают членов с данными. Не добавляйте arbiter, пока не понимаете компромисс write concern и хранения.

Члены общаются по портам replica set. Клиенты используют строку соединения со списком семян и `replicaSet=Name` или SRV URI Atlas.

Полезные команды:

```javascript
rs.status()
rs.conf()
db.hello()
```

`rs.status()` показывает здоровье, состояние и optime. `db.hello()` показывает, является ли текущий член primary, и перечисляет хосты.

Одиночный `mongod` — не replica set. Мультидокументным транзакциям и change streams нужен replica set (или шардированный кластер). Для учёбы можно запустить replica set из одного члена.

Primary может смениться. Драйвер должен обнаружить новый primary. Официальные драйверы это делают. Не прошивайте один хост как «всегда primary».

Не пишите на secondary. Secondary отклоняют обычные записи приложения.

**Выборы** выбирают новый primary. Голосующие члены начинают выборы, когда не могут достичь primary или когда primary уходит.

Член может стать primary, только если может выиграть **большинство голосов**. В наборе из трёх членов два голоса — большинство. Если два члена недоступны, последний член не может выбрать себя. У набора нет primary. Записи падают.

Primary **уходит** (step down), когда:

- Вы запускаете `rs.stepDown()`
- Появляется более подходящий член
- Primary не видит большинство (он становится secondary, чтобы избежать записи split-brain)

**Priority** влияет на то, кто побеждает. Член с priority `0` не может стать primary. Используйте это для скрытого или отложенного члена.

Выборы занимают время. Во время выборов у набора нет primary. Записи ждут или падают. Официальные драйверы повторяют некоторые записи. Проектируйте приложение на короткую недоступность записи.

Atlas создаёт replica set, когда вы создаёте кластер. `mongod` вручную не запускаете. Всё равно нужно знать, что отказ возможен и что запись с `w: 1` может откатиться.

## Oplog

**Oplog** — особая capped-коллекция. Имя по умолчанию — `local.oplog.rs`. Primary пишет запись для каждой операции, которую secondary должны применить.

Secondary читают хвост oplog. Они применяют записи по порядку. Применение — как работает репликация.

Oplog **ограничен по размеру** (capped). Старые записи исчезают, когда коллекция полна. Интервал времени оставшихся записей — **окно oplog**.

Если secondary недоступен дольше окна oplog, он не может догнать из oplog. Ему нужна начальная синхронизация (полная копия). Это дорого.

Размер oplog настраивается. Atlas позволяет увеличить oplog. На Community Server размер oplog задают в конфигурации или командой, которую руководство указывает для вашей версии.

Oplog — не общая шина событий для приложения. Change streams используют oplog внутри. Приложение должно использовать change streams или другой одобренный API, а не сырой хвост `local.oplog.rs`, если вы не оператор, который знает риски.

Не храните данные приложения в базе `local`.

`db.printReplicationInfo()` и `rs.printReplicationInfo()` на многих версиях показывают оценки окна oplog. Atlas показывает метрики oplog в интерфейсе.

## Устаревшие чтения со secondary

**Устаревшее чтение** — чтение, которое пропускает запись, уже прошедшую на primary. Репликация асинхронна, пока не подождёте write concern и правилами чтения.

Read preference по умолчанию — `primary`. Эти чтения — не устаревшие чтения со secondary.

Если задать read preference `secondary`, `secondaryPreferred` или `nearest`, драйвер может читать со secondary. Этот secondary может отставать.

Отставание вызывает:

- Пользователь не видит документ, который только что создал
- Проверка уникальности на secondary пропускает новый ключ
- Отчёты, которые не совпадают с primary

Используйте чтения со secondary, когда приложение принимает отставание. Примеры: некоторые дашборды, некоторые превью поиска, некоторые отчёты по всей коллекции.

Не используйте чтение со secondary, чтобы подтвердить запись, которую только что отправили. Используйте primary или сессию с причинной согласованностью и concern из темы транзакций.

Write concern `majority` не убирает устаревшие чтения на secondary. Majority значит, что запись прочна на большинстве. Конкретный secondary всё ещё может отставать.

Измерьте отставание. Atlas показывает отставание репликации. `rs.status()` показывает даты optime. Алерт, когда отставание растёт.

## Скрытые и отложенные члены

**Скрытый** член — secondary, которого клиентские драйверы не используют для чтений. Задайте `hidden: true`. Скрытый член должен иметь priority `0`. Он всё ещё может голосовать. Он всё ещё реплицирует.

Используйте скрытый член для резервных копий или для заданий, которые не должны брать трафик чтения приложения.

**Отложенный** член применяет записи oplog после фиксированной задержки. Задержка — `secondaryDelaySecs` (в старых документах — `slaveDelay`). Отложенный член должен быть скрытым и должен иметь priority `0`.

Используйте отложенный член как короткое окно «ой». Пример: задержка 3600 секунд держит копию часовой давности. Плохой drop можно починить с этого члена, если успеете внутри задержки. Это не полная стратегия резервного копирования.

Не направляйте приложение на отложенный член. Данные намеренно старые.

Не скрывайте единственные secondary, которые нужны для большинства, если не понимаете голоса. Скрытые члены часто всё ещё голосуют. Планируйте большинство.

Atlas предлагает родственные типы узлов (например аналитические) на некоторых уровнях. Читайте страницу Atlas для своего кластера. Идея та же: держать особые члены вне пути чтения по умолчанию.

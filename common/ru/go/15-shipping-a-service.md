# 15. Поставка сервиса

## Описание

Настоящая программа Go — больше, чем одна функция `main`. Нужно организовать пакеты, загрузить конфигурацию, писать логи, остановить процесс безопасным способом и поставить двоичный файл. Эта тема показывает, как поставить сервис.

Команда Go не определяет одно официальное дерево папок для приложений. Команды всё равно делят общие шаблоны. Используйте эти шаблоны, когда они помогают. Не копируйте большую раскладку для маленького инструмента.

Используйте один термин для каждого понятия. Конфигурация — данные, которые загружаете при старте. Корректное завершение — остановка, которая заканчивает текущую работу. Секрет — пароль или ключ. Не храните секреты в исходных файлах.

## Раскладка `cmd/` и `internal/`

Официальные заметки о раскладке модуля — на [https://go.dev/doc/modules/layout](https://go.dev/doc/modules/layout). Этот документ — руководство. Это не обязательный стандарт.

Типичный модуль приложения выглядит так:

- `go.mod` в корне модуля
- `cmd/appname/` для `package main`, который собираете и запускаете
- `internal/` для пакетов, которые другие модули не должны импортировать
- необязательный `pkg/` для пакетов, которые другие модули могут импортировать
- `api/`, `migrations/` или `docs/` для файлов, которые не являются пакетами Go

`cmd/` держит команды. Каждый подкаталог — одна программа. Пример: `cmd/api` и `cmd/worker`. Имя каталога часто — имя двоичного файла. Держите `main` маленькой. Вызывайте `run()` из `internal` или из того же пакета.

`internal/` — правило компилятора. Пакет вне родителя `internal` не может импортировать пакет под этим деревом `internal`. Используйте `internal/` для доступа к базе данных, конфигурации и другого закрытого кода. Тема 8 покрывает забор импорта.

`pkg/` — только соглашение. Компилятор не считает `pkg/` особым.

Держите первую версию модуля маленькой. Одного пакета `main` в корне достаточно для крошечного инструмента. Добавляйте `cmd/`, когда есть две команды. Добавляйте `internal/`, когда нужен закрытый пакет. Не создавайте пустые слои вроде `models/`, `utils/` и `helpers/` без ясной задачи для каждого пакета.

Именуйте пакеты по тому, что они дают. Предпочитайте `store` вместо `storepkg`. Предпочитайте `httpapi` вместо `helpers`.

```text
example.com/shop/
  go.mod
  cmd/api/main.go
  cmd/worker/main.go
  internal/store/store.go
  internal/httpapi/server.go
```

## Конфигурация и структурированные логи

Конфигурация — данные, которые процесс читает при старте. Источники включают флаги, переменные окружения и файлы.

Используйте `flag` для маленького CLI. Используйте переменные окружения для сервиса в контейнере. Пример: `PORT`, `DATABASE_URL`, `LOG_LEVEL`. Читайте их в одной функции. Возвращайте структуру `Config`.

```go
type Config struct {
	Addr string
	DSN  string
}

func Load() (Config, error) {
	addr := os.Getenv("PORT")
	if addr == "" {
		addr = "8080"
	}
	dsn := os.Getenv("DATABASE_URL")
	if dsn == "" {
		return Config{}, errors.New("DATABASE_URL is required")
	}
	return Config{Addr: ":" + addr, DSN: dsn}, nil
}
```

Не читайте `os.Getenv` в каждом пакете. Загружайте один раз в `main` или в `internal/config`. Передавайте `Config` вниз.

Проверяйте обязательные поля при старте. Падайте быстро. Не запускайте HTTP-сервер, когда DSN пуст.

Структурированные логи используют `log/slog`. Тема 9 вводит `slog`. Установите JSON-обработчик в продакшене. Используйте текст в локальной разработке, если предпочитаете.

```go
h := slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: level})
slog.SetDefault(slog.New(h))
slog.Info("listen", "addr", cfg.Addr)
```

Логируйте id запроса, если он есть. Логируйте ошибки через `"err", err`. Не логируйте секреты. Не логируйте полные тела запросов, которые могут содержать пароли.

Задавайте уровень лога из конфигурации. `DEBUG` — для разработки. `INFO` — умолчание для продакшена.

## Корректное завершение

Корректное завершение останавливает приём новой работы. Оно ждёт текущие запросы. Затем выходит.

`http.Server.Shutdown` — стандартный метод. Он закрывает слушатель. Он ждёт, пока обработчики вернут управление или context завершится.

```go
s := &http.Server{Addr: cfg.Addr, Handler: mux}

go func() {
	if err := s.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
		slog.Error("listen", "err", err)
	}
}()

ch := make(chan os.Signal, 1)
signal.Notify(ch, os.Interrupt, syscall.SIGTERM)
<-ch

ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()
if err := s.Shutdown(ctx); err != nil {
	return err
}
```

`signal.Notify` должен использовать буферизованный канал. `SIGTERM` обычен в контейнерах. `SIGINT` — Ctrl+C.

После завершения HTTP закройте пул базы данных. Отмените context воркеров. Подождите `WaitGroup` воркеров. Порядок остановки: сначала остановите приём, затем закончите работу, затем закройте зависимости.

`os.Exit` пропускает отложенные закрытия. Предпочитайте `return` из `run`, чтобы `defer db.Close()` выполнился.

`Shutdown` не останавливает обработчик, который игнорирует context запроса. Обработчики должны следить за `r.Context()`. Тема 10 покрывает context.

Задайте таймауты `http.Server`, чтобы застрявший клиент не блокировал завершение навсегда. Context завершения — последняя граница.

## Docker и кросс-компиляция

Go компилируется в статический двоичный файл для многих операционных систем. Вы задаёте `GOOS` и `GOARCH`.

```text
set GOOS=linux
set GOARCH=amd64
go build -o api ./cmd/api
```

На Unix:

```text
GOOS=linux GOARCH=amd64 go build -o api ./cmd/api
```

Для большинства сервисов CGO не нужен. Задайте `CGO_ENABLED=0` для статического двоичного файла, который копируется в маленький образ.

Типичный Dockerfile использует этап сборки и этап выполнения:

```text
FROM golang:1.22 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o /api ./cmd/api

FROM gcr.io/distroless/static:nonroot
COPY --from=build /api /api
USER nonroot
ENTRYPOINT ["/api"]
```

Сначала копируйте `go.mod`, чтобы загрузка зависимостей кэшировалась. Не запускайтесь от root в итоговом образе. Образы Distroless и scratch не имеют оболочки. Передавайте конфигурацию переменными окружения.

Фиксируйте версии базовых образов. Сканируйте образы в CI, когда можете.

Кросс-компилируйте на своей машине для удалённой ОС. Docker не нужен только чтобы получить двоичный файл Linux. Docker — для повторяемого окружения выполнения.

`go build -trimpath` убирает локальные пути из двоичного файла. `-ldflags="-s -w"` уменьшает размер. Используйте их, когда знаете компромисс (труднее отлаживать).

## Таймауты, повторы и секреты

Сервис должен ограничивать время. Задайте таймауты HTTP-сервера. Задайте таймауты HTTP-клиента. Задайте таймауты context на исходящих вызовах и запросах к базе данных.

```go
client := &http.Client{Timeout: 5 * time.Second}
ctx, cancel := context.WithTimeout(r.Context(), 3*time.Second)
defer cancel()
```

Таймаут клиента включает соединение, редиректы и чтение тела. Таймаут context отменяет запрос. Используйте оба, когда нужна отмена всего дерева.

Повтор повторяет вызов после сбоя. Повторяйте только когда операция идемпотентна или когда знаете, что повтор безопасен. GET часто безопасен. POST, который создаёт ресурс, небезопасен без ключа идемпотентности.

Используйте экспоненциальный backoff и максимальное число попыток. Добавляйте jitter, чтобы многие клиенты не повторяли в одно время. Не повторяйте на `400` или `401`. Повторяйте на таймауте и на `503`, когда API это документирует.

```go
for attempt := 0; attempt < 3; attempt++ {
	err := call(ctx)
	if err == nil {
		return nil
	}
	if !retryable(err) {
		return err
	}
	time.Sleep(backoff(attempt))
}
```

Уважайте `ctx.Done()` в sleep. Повтор не должен игнорировать отмену.

Секрет — пароль, токен или закрытый ключ. Загружайте секреты из окружения или из хранилища секретов. Не коммитьте файлы `.env`, которые содержат настоящие секреты. Не кладите секреты в логи, в сообщения об ошибках или в JSON для клиента.

Ротируйте секреты без изменения кода, когда можете. Используйте новое значение окружения и перезапуск.

Файлы TLS — секреты. Права файлов не должны быть world-readable.

## Проверка ввода

Проверяйте ввод на границе. HTTP-обработчик или CLI — граница. Не доверяйте параметрам запроса, полям JSON или заголовкам.

Проверяйте:

- обязательные поля
- пределы длины
- формат (email, UUID, enum)
- диапазоны (размер страницы, id)
- неожиданные поля, когда API строгий

```go
if in.Name == "" || len(in.Name) > 100 {
	http.Error(w, "bad name", http.StatusBadRequest)
	return
}
```

Возвращайте `400` для ввода, который клиент может исправить. Возвращайте `404`, когда id хорошо сформирован, но отсутствует. Не используйте `500` для проверки.

Проверяйте до разговора с базой данных. Неудачная проверка не должна открывать транзакцию.

Ограничивайте списки. Отклоняйте `page_size=1000000`. Задайте максимум.

Используйте `http.MaxBytesReader` для тел JSON. Тема 13 покрывает этот предел. Используйте `DisallowUnknownFields`, когда лишние ключи — ошибка.

Для HTML-форм кодируйте вывод через `html/template`, чтобы скрипты не выполнялись. Для JSON API всё равно ограничивайте строки.

Не проверяйте только в базе данных. Ограничение базы — последняя остановка. Обработчик всё равно возвращает ясную ошибку.

Держите функции проверки чистыми, когда можете. Их легко тестировать. Тема 11 покрывает табличные тесты.

### Вопросы

#### Теоретические вопросы

1. Как `cmd/`, `internal/` и маленький `main` работают вместе в поставляемом модуле?
2. Что должен делать `run` от загрузки конфигурации до прослушивания, завершения и закрытия базы данных?
3. Как структурированные логи, редакция и конфигурация окружения защищают эксплуатацию?
4. Почему таймауты, повторы и проверка все принадлежат границе процесса?
5. Что добавляет образ контейнера, чего одна кросс-компиляция не добавляет?

#### Простые практические задания

1. Создайте `cmd/api` с `/health`, `slog` и `PORT`. Соберите двоичный файл Linux.
2. Напишите шпаргалку: раскладка, config, slog, Shutdown, GOOS, таймаут, секрет, проверка.
3. Нарисуйте жизненный цикл: старт, загрузка, миграция, прослушивание, сигнал, завершение, выход.
4. Замаскируйте DSN в строке лога. Покажите печатный текст.

#### Средние практические задания

1. Реализуйте `run() error` с конфигурацией, mux, корректным завершением и `db.Close` (используйте SQLite, если есть тема 14).
2. Добавьте один повторяющийся исходящий GET с таймаутом клиента и границей context.
3. Напишите Dockerfile и `.dockerignore`. Перечислите, что исключаете.

#### Сложные практические задания

1. Поставьте крошечный сервис: раскладка, JSON API с проверкой, slog, завершение и многоэтапная сборка Docker. Задокументируйте переменные окружения.
2. Запустите `-race` на тесте завершения, который стартует сервер и отправляет SIGINT в процессе или вызывает `Shutdown` напрямую.

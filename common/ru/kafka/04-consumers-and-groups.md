# 4. Консьюмеры и группы

## Описание

Консьюмер — клиент, который читает записи из партиций топика. Обычный путь — группа, подписка и цикл poll. Консьюмер фиксирует офсеты, чтобы продолжить после перезапуска.

Эта тема показывает subscribe против assign, цикл poll, режимы фиксации, таймауты poll и сессии, группы консьюмеров, ребаланс, статическое членство, cooperative assignor и seek. Завершите эту тему после темы 3. Тема 5 покрывает семантику доставки.

Используйте один термин для каждого понятия. Poll — вызов, который получает записи и ведёт консьюмера. Фиксация хранит офсет для группы и партиции. Группа консьюмеров — набор консьюмеров, которые делят один `group.id`. Участник — один процесс консьюмера в группе. Subscribe даёт группе назначать партиции. Assign задаёт партиции в клиенте. Используйте кластеры KRaft. Консьюмер говорит с брокерами, не с ZooKeeper.

## Subscribe против assign и цикл poll

API консьюмера — клиентский интерфейс, который читает записи. В Java тип — `KafkaConsumer`. В других языках есть тип консьюмера с той же идеей: настроить, subscribe или assign, poll, commit, close.

Типичная последовательность:

1. Соберите конфигурацию. Задайте `bootstrap.servers`. Задайте `group.id` для пути группы. Задайте десериализаторы для ключа и значения.
2. Создайте консьюмера.
3. Подпишитесь на имена топиков или назначьте объекты партиций.
4. Цикл: вызовите `poll` с таймаутом. Обработайте записи. Фиксируйте, когда требует ваша политика.
5. Вызовите `close`, когда процесс заканчивается. `close` может вызвать выход из группы и ребаланс.

`subscribe` регистрирует имена топиков (или шаблон). Координатор группы и assignor выбирают партиции. Когда участники входят или выходят, Kafka переназначает партиции. Это обычный прикладной путь.

`assign` задаёт явный список партиций топика на консьюмере. Консьюмер не входит в ребаланс группы для этого назначения. Список ваш. Если запустить два процесса, которые назначают одну партицию, оба читают те же записи. Автоматического деления нет.

Используйте `subscribe`, когда работники должны делить топик. Используйте `assign` для инструментов, задач повтора и тестов, которые должны закрепить партицию. Не вызывайте `subscribe` и `assign` конфликтующим способом на одном консьюмере. Выберите один режим.

**Цикл poll** — главный цикл консьюмера. Каждый вызов `poll` входит в группу и отправляет heartbeat, как требует клиент, получает записи из назначенных партиций и возвращает пакет записей вашему коду.

Вы должны вызывать `poll` достаточно часто. Если нет, группа может считать участника мёртвым. Обработайте записи, которые вернул `poll`, до следующего `poll`. `max.poll.records` ограничивает, сколько записей возвращает один `poll`.

Пустой poll нормален. Таймаут на `poll` — максимальное ожидание записей, не ошибка.

`auto.offset.reset` применяется, когда у группы нет зафиксированного офсета для партиции. `earliest` начинает с самой старой сохранённой записи. `latest` начинает с конца журнала. `none` падает, если офсета нет.

Не делите один объект консьюмера между потоками, если клиент не документирует такое использование. Обычный Java-консьюмер не потокобезопасен. Тема 11 повторяет: не блокируйте цикл poll.

## Автофиксация против ручной фиксации

Фиксация пишет офсет группы для партиции в Kafka (топик `__consumer_offsets`). После перезапуска консьюмер продолжает с зафиксированной позиции.

**Автофиксация.** Клиент фиксирует по таймеру, когда `enable.auto.commit` истинно. Таймер — `auto.commit.interval.ms`. Клиент фиксирует офсеты, которые консьюмер вернул из `poll`, а не офсеты, которые ваша бизнес-логика закончила, если вы не закончите работу до следующей точки фиксации.

**Ручная фиксация.** Ваш код вызывает `commitSync` или `commitAsync` (имена Java) после того, как закончите работу. Синхронная фиксация ждёт брокера. Асинхронная фиксация не ждёт. Сочетайте их с ясной политикой.

Ручная фиксация даёт контроль. Можно фиксировать после записи в базу. Можно фиксировать каждую запись или каждый пакет.

At-least-once обработка — обычный результат: если упасть после работы и до фиксации, обработаете снова. Тема 5 покрывает этот случай.

Автофиксацию легко сделать неправильно. Можно обработать запись после того, как клиент её уже зафиксировал. Сбой тогда пропускает запись. Это at-most-once. Дополнительные потоки, которые держат записи, повышают этот риск.

Для учёбы выключите автофиксацию. Фиксируйте в коде после завершения работы. Если оставляете автофиксацию включённой, закончите всю работу по записям poll до следующего `poll` и не передавайте записи другим потокам.

Не смешивайте политики в одной команде без письменного правила.

## `max.poll.interval.ms` и таймаут сессии

У консьюмера два важных таймера.

`session.timeout.ms` (вместе с интервалом heartbeat) контролирует живость процесса в группе. Если heartbeat останавливаются, координатор убирает участника. Heartbeat могут идти в фоновом потоке в текущих клиентах Java.

`max.poll.interval.ms` контролирует, сколько группа разрешает между двумя вызовами `poll`. Если обработка длится дольше этого интервала, координатор убирает участника, даже если heartbeat ещё идут. Партиция назначается другому участнику. Ваш старый участник может затем фиксировать или обрабатывать записи, которыми больше не владеет. Это серьёзный дефект.

Задайте `max.poll.interval.ms` выше худшего времени обработки одного пакета poll. Или уменьшите `max.poll.records`, чтобы каждый пакет был меньше.

`heartbeat.interval.ms` должен быть ниже `session.timeout.ms`. Официальные документы дают отношение. Не задавайте случайные значения.

Эти таймеры не то же самое, что `delivery.timeout.ms` у продюсера.

Лаг — разница между концом журнала и зафиксированным офсетом. Если поднимать `max.poll.interval.ms` только чтобы спрятать медленную работу, лаг всё равно растёт. Исправьте сток или ставьте партиции на паузу (тема 11).

## Группы консьюмеров: один активный консьюмер на партицию

**Группа консьюмеров** — набор консьюмеров, которые делят один `group.id`. Группа делит партиции подписанных топиков. Kafka назначает каждую партицию не более чем одному активному участнику группы.

Это правило держит одного читателя на партицию. Порядок в партиции остаётся простым. Участник не делит партицию с коллегой в той же группе.

Если в группе больше участников, чем партиций, лишние участники простаивают. Они не получают партиций. Они всё равно входят в группу. Они становятся полезны, когда участник уходит или когда вы добавляете партиции.

Если в группе меньше участников, чем партиций, некоторые участники получают больше одной партиции.

Две группы не следуют этому правилу друг с другом. Одна партиция может иметь одного активного читателя в группе A и одного активного читателя в группе B одновременно.

**Координатор группы** — брокер. Kafka отображает каждый идентификатор группы на координатора. Участники отправляют join, heartbeat и commit этому координатору. Координатора не выбирают вручную. Задаёте `bootstrap.servers` и `group.id`.

Масштабируете группу, добавляя участников. Пропускная способность может расти, пока число участников не сравняется с числом партиций. После этого лишние участники не увеличивают параллелизм для этого топика в этой группе. Масштабируйте независимую работу новой группой. Сервис биллинга и сервис почты не должны делить `group.id`.

Неравномерные ключи создают горячую партицию. Лишние участники не помогают горячей партиции. Смотрите лаг.

Не создавайте огромное число неиспользуемых идентификаторов групп. Каждая группа использует хранилище в `__consumer_offsets`, пока офсеты не истекут.

`kafka-consumer-groups` говорит с кластером и показывает состояние: участники, назначение, лаг. Используйте его, когда отлаживаете группу.

## Ребаланс, статическое членство и cooperative assignor

**Ребаланс** — смена назначения партиций в группе. Участники входят, выходят или падают. Assignor считает новое назначение.

**Eager-ребаланс** (старый протокол). Все участники сначала отзывают все партиции. Чтение останавливается. Затем участники получают новое назначение. Это пауза для всей группы.

**Cooperative-ребаланс** (инкрементальный). Участники отзывают только партиции, которые должны отдать. Остальные оставляют. Чтение продолжается на партициях, которые не двигаются.

**Assignor** отображает партиции на участников. Частые имена Java: `RangeAssignor`, `RoundRobinAssignor`, `StickyAssignor`, `CooperativeStickyAssignor`.

**Sticky** значит, что assignor старается оставить партицию на том же участнике, когда может. **Cooperative** значит, что протокол ребаланса инкрементальный. `CooperativeStickyAssignor` сочетает обе идеи. Это обычный выбор для новых приложений.

Все участники группы должны использовать совместимые assignor. Задайте один список стратегий на каждом участнике.

**Статическое членство** даёт консьюмеру стабильную идентичность. Задаёте `group.instance.id` уникальной строкой на экземпляр процесса (например имя пода). Без статического членства перезапуск — выход и вход. Группа ребалансируется. Со статическим членством координатор может сохранить назначение во время короткого перезапуска, если участник вернётся до таймаута сессии.

`group.instance.id` должен быть уникален в группе. Два процесса с одним instance id — серьёзная ошибка конфигурации. Статическое членство не заменяет cooperative assignor. Используйте оба.

Во время ребаланса фиксируйте офсеты партиций, которые отзываете. У текущих клиентов есть callback отзыва. Фиксируйте в callback отзыва, когда используете ручную фиксацию. Не берите длинную блокировку в callback ребаланса.

Причины частых ребалансов: участники перезапускаются без статического членства, истекает `max.poll.interval.ms`, истекает таймаут сессии, вы часто добавляете или убираете участников.

Этот справочник не использует координацию групп ZooKeeper. Текущие группы консьюмеров Kafka живут на брокерах.

## Seek

Seek двигает позицию консьюмера в партиции. Следующий `poll` читает с этого офсета.

- Seek к офсету. Нужно назначить партицию (или дождаться назначения). Некоторые клиенты требуют poll до seek.
- Seek к началу. Следующее чтение — самый ранний сохранённый офсет.
- Seek к концу. Следующее чтение — конец журнала. Вы пропускаете существующие записи.

Seek не всегда фиксирует. Если сделать seek и затем упасть до фиксации, группа может перезапуститься на старом зафиксированном офсете. Если хотите, чтобы seek пережил перезапуск, фиксируйте после seek (или используйте инструмент admin reset).

Инструмент consumer-groups может сбросить офсеты для простаивающей группы. Используйте этот инструмент для эксплуатации. Используйте seek в работающем консьюмере для повтора в процессе.

Не делайте seek на партиции, которой не владеете в группе subscribe. Назначение может измениться.

`--from-beginning` у консольного консьюмера — seek к началу для этого старта, часто с новой группой.

Некоторые клиенты поддерживают seek по метке времени (`offsetsForTimes`). Брокер отображает время на офсет через индекс времени (тема 6).

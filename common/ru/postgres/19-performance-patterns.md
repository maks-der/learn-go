# 19. Шаблоны производительности

## Описание

Эта тема показывает частые шаблоны производительности в PostgreSQL 16 и PostgreSQL 17. Вы узнаёте пагинацию по ключу, частичные индексы, покрывающие индексы с `INCLUDE`, обновления heap-only tuple (HOT), почему высокий `max_connections` приводит к пробуксовке, и как использовать реплики чтения для отчётов.

Сначала завершите тему 18. Вы умеете читать `EXPLAIN` и настройки памяти. Завершите эту тему до изучения оконных функций и другого продвинутого SQL.

Используйте один термин для каждого понятия. Пагинация по ключу — поиск по последнему увиденному ключу сортировки. Частичный индекс — индекс с предложением `WHERE`. Покрывающий индекс включает дополнительные столбцы, чтобы index-only scan мог обойтись без кучи. HOT — обновление кортежа только в куче. Пробуксовка здесь — слишком много backend для RAM и CPU. Реплика чтения — горячий стендбай, который используют для чтения. Этот справочник рассчитан на PostgreSQL 16 и PostgreSQL 17.

## Пагинация по ключу

`LIMIT` плюс `OFFSET` каждый раз пропускает строки. Страница 100 с `OFFSET 1000` всё равно читает и отбрасывает 1000 строк. Стоимость растёт с номером страницы.

Пагинация по ключу (ещё называют seek method) фильтрует по последней строке, которую клиент уже видел:

```sql
SELECT id, created_at, title
FROM shop.posts
WHERE (created_at, id) < ('2026-09-01 12:00:00+00', 8400)
ORDER BY created_at DESC, id DESC
LIMIT 21;
```

Клиент использует последние `created_at` и `id` предыдущей страницы. Нужен уникальный разрыв ничьей (`id`). Без него две строки с одним временем можно пропустить или повторить.

Подходящее B-дерево:

```sql
CREATE INDEX posts_created_id_idx ON shop.posts (created_at DESC, id DESC);
```

`EXPLAIN` должен показать сканирование индекса, которое останавливается после `LIMIT`, а не полную сортировку таблицы.

`OFFSET` приемлем для маленьких админских страниц. Это неверное умолчание для бесконечной прокрутки по большой таблице.

Не смешивайте `OFFSET` с ключом так, что клиент не сможет объяснить поведение. Не пагинируйте только по неуникальному столбцу. Не используйте `LIMIT` / `OFFSET`, чтобы скрыть отсутствие индекса.

Тема 3 представила `LIMIT`, `OFFSET` и `FETCH`. Этот раздел — шаблон для большой таблицы.

## Частичные индексы для горячих фильтров

Частичный индекс хранит только строки, которые совпадают с предикатом. Он меньше. Он полезен, когда предикат совпадает с запросом.

```sql
CREATE INDEX orders_open_idx
    ON shop.orders (customer_id)
    WHERE status = 'open';
```

Запрос, который использует индекс:

```sql
SELECT id, total
FROM shop.orders
WHERE status = 'open' AND customer_id = 42;
```

Запрос с `status = 'closed'` не может использовать `orders_open_idx`. Запрос без `status` тоже не может, пока планировщик не докажет предикат.

Частичные индексы подходят:

- маленький горячий срез (`status = 'open'`, `deleted_at IS NULL`)
- редкий флаг, по которому ищут (`is_error = true`)
- тенант или регион, который часто запрашивают

Тема 8 представила частичные индексы. Этот раздел — правило «горячего фильтра»: индексируйте срез, который продакшен реально фильтрует.

`EXPLAIN` должен упоминать частичный индекс. Если планировщик использует последовательное сканирование, предикат не совпадает или таблица крошечная.

Не создавайте частичный индекс для каждого значения статуса без измерения. Не используйте частичный уникальный индекс вместо настоящего бизнес-правила, если только правило не «уникально среди живых строк»:

```sql
CREATE UNIQUE INDEX users_email_live_uidx
    ON shop.users (email)
    WHERE deleted_at IS NULL;
```

## Покрывающие индексы (`INCLUDE`)

Покрывающий индекс — B-дерево, чей лист может удовлетворить запрос без чтения кучи. PostgreSQL называет дополнительные столбцы **included columns**. Это не ключи сортировки.

```sql
CREATE INDEX items_name_cover_idx
    ON shop.items (name)
    INCLUDE (qty, price);
```

Запрос, который может стать index-only scan:

```sql
SELECT name, qty, price
FROM shop.items
WHERE name = 'nail';
```

`name` — ключ поиска. `qty` и `price` — полезная нагрузка. `WHERE` и `ORDER BY` всё равно используют только ключевые столбцы (и их порядок).

Тема 8 и тема 9 предварительно показали `INCLUDE` и index-only scan. Index-only scan также нужна карта видимости, которая говорит, что страница полностью видима. Помогает `VACUUM` (тема 11). Если `EXPLAIN` показывает «Heap Fetches» больше нуля, покрывающего индекса недостаточно или vacuum отстаёт.

Включённые столбцы делают индекс больше. Они замедляют записи. Они могут сломать HOT, если включить столбец, который часто обновляют (следующий раздел).

Не делайте `INCLUDE` каждого столбца, чтобы скопировать таблицу в индекс. Не ждите, что `INCLUDE` поможет `SELECT *` по широкой строке. Не добавляйте `INCLUDE`, пока не увидите heap fetches в `EXPLAIN (ANALYZE)`.

Официально: [https://www.postgresql.org/docs/17/indexes-index-only-scans.html](https://www.postgresql.org/docs/17/indexes-index-only-scans.html).

## Обновления heap-only tuples (HOT) (осведомлённость)

Обычный `UPDATE` пишет новый кортеж кучи и новые записи индекса для каждого индекса, который включает изменённый столбец. Обновление **HOT** пишет новый кортеж на ту же страницу кучи и пропускает обновления индекса, когда:

1. ни один индексированный столбец не меняется (ключевые столбцы и столбцы `INCLUDE` считаются индексированными)
2. новый кортеж умещается на той же странице (свободное место; помогает `fillfactor`)

HOT снижает раздутие индексов. Тема 11 представила HOT и fillfactor. Этот раздел — правило приложения: не индексируйте столбцы, которые обновляете на каждый запрос, если можно избежать.

```sql
-- last_seen changes often; a B-tree on last_seen blocks HOT for that update
UPDATE shop.users SET last_seen = now() WHERE id = 1;
```

Если у `last_seen` есть индекс, эти обновления не HOT. Если `last_seen` фильтруете только в редком отчёте, удалите индекс или используйте частичный индекс, который исключает горячий путь.

`SELECT n_tup_hot_upd, n_tup_upd FROM pg_stat_user_tables WHERE relname = 'users';` показывает HOT против всех обновлений (имена могут чуть различаться; читайте столбцы `pg_stat_all_tables` на своей версии).

`EXPLAIN` не говорит «HOT». HOT выводят из статистики и из дизайна индексов.

Не добавляйте покрывающие столбцы, которые обновляете так же часто, как читаете. Не ставьте `fillfactor = 50` на каждую таблицу. Сначала измерьте горячую таблицу.

Официальная страница: [https://www.postgresql.org/docs/17/storage-hot.html](https://www.postgresql.org/docs/17/storage-hot.html) (тот же путь под `/docs/16/`).

## Избежание пробуксовки из-за слишком высокого `max_connections`

`max_connections` — потолок backend сервера. Каждый backend использует память (`work_mem` на шаг плюс накладные расходы на backend). Операционная система тратит больше времени на переключение контекста, когда активны сотни backend.

Пробуксовка здесь значит: слишком много backend, слишком мало RAM, тяжёлый swap или вытеснение кэша, и каждый запрос медленнее, чем при меньшем пуле.

Тема 17 сказала использовать PgBouncer. Тема 18 сказала, что `work_mem` умножить на соединения может превысить RAM. Шаблон:

1. задайте `max_connections` числом, которое хост может выполнить (часто 100–200 на среднем хосте, не 2000)
2. поставьте впереди PgBouncer или пул драйвера
3. размер пула — несколько десятков серверных соединений для OLTP
4. отдельный маленький пул для админки и миграций

```sql
SHOW max_connections;
SELECT count(*) FROM pg_stat_activity;
```

Облачные экземпляры часто задают `max_connections` по классу RAM. Не поднимайте умолчание, чтобы «убрать ошибки too many connections», без пула. Эта ошибка — сигнал пулить, а не размножать backend.

Не ставьте `max_connections` в 1000 на хосте с 4 ГБ. Не открывайте сессию на каждый HTTP-запрос (тема 17). Не забывайте, что у реплик свой `max_connections`.

## Реплики чтения для отчётов

Отчётный запрос, который сортирует большую таблицу, может конкурировать с OLTP на первичном. Горячий стендбай (тема 16) может выполнять SQL только на чтение. Отчёт направляют на реплику.

Правила:

- отчёт должен принимать отставание (секунды или больше)
- отчёт должен принимать отмену запроса из-за конфликтов восстановления
- отчёт не должен писать
- индексы всё равно нужны на первичном (они реплицируются физически)
- `hot_standby_feedback` может защитить отчёт и задержать vacuum на первичном

```sql
-- on replica
SELECT pg_is_in_recovery();
SELECT now() - pg_last_xact_replay_timestamp() AS replica_lag;
```

`pg_last_xact_replay_timestamp()` может быть null, когда воспроизведения ещё нет. Считайте отставание отображением, а не гарантией транзакции.

Логические подписчики (тема 16) тоже могут обслуживать отчёты, если публикация включает таблицы. У них могут быть другие индексы. Это другой продуктовый путь.

Не запускайте ночной `VACUUM FULL` на реплике вместо обслуживания первичного. Не используйте реплику для следующего ключа номера заказа. Не игнорируйте отставание на дашборде, который выглядит «живым».

Тема 21 мониторит отставание репликации. Этот раздел — причина производительности иметь реплику.

### Вопросы

#### Теоретические вопросы

1. Как пагинация по ключу и покрывающий индекс работают вместе на запросе ленты?
2. Как частичный индекс и HOT конфликтуют или сотрудничают на таблице со `status` плюс `updated_at`?
3. Почему высокий `max_connections` — ошибка производительности даже когда SQL проиндексирован?
4. Когда добавляют реплику вместо ещё одного индекса на первичном?
5. Коллега пагинирует с `OFFSET 50000`, индексирует каждый столбец и ставит `max_connections = 2000`. Какие факты из этой темы вы используете в ответе?

#### Простые практические задания

1. На одной таблице создайте составной индекс сортировки и частичный индекс. Выполните один запрос по ключу и один горячий фильтр. Сохраните `EXPLAIN`.

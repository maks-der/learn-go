# 20. Продвинутые темы и внутреннее устройство

## Описание

Эта тема — осведомлённость о том, как Redis работает внутри одного процесса и как к нему относятся альтернативные серверы. Вы изучаете цикл событий, потоки ввода-вывода, активное истечение, шину Cluster, Functions против Lua и имена вроде Valkey и KeyDB.

Сначала завершите темы 2, 8, 11 и 16. Не нужно читать исходники Redis на C, чтобы закончить эту тему. Официальной документации и полей `INFO` достаточно.

Используйте один термин для каждого понятия. Цикл событий — цикл ожидания и диспетчеризации, который обрабатывает сокеты и события времени. Потоки ввода-вывода читают и пишут сокеты; они не выполняют логику команд. Цикл активного истечения — фоновая задача, которая удаляет истёкшие ключи. Шина Cluster — канал узел-к-узлу. Function — именованная библиотека на сервере. Альтернативная реализация — другой сервер, который говорит протоколами или командами Redis.

## Осведомлённость о цикле событий (ae)

Redis использует цикл событий (исторически библиотека `ae`). Процесс ждёт готовый сокет, затем читает команду, затем выполняет её в основном потоке, затем пишет ответ, когда сокет готов.

События времени сидят в том же цикле: работа в стиле cron вроде выборки истечения, обслуживания репликации и статистики.

Одна команда выполняется до конца. Медленная команда задерживает следующий сокет и следующее событие времени. Поэтому `KEYS` и огромный `HGETALL` останавливают клиентов (тема 2, тема 16).

Цикл — не обещание, что Redis использует только одно ядро для всей работы. Дочерние процессы после fork пишут файлы RDB. Потоки ввода-вывода могут переносить чтение/запись сокетов. Модули могут добавлять работу. Выполнение команд движка по умолчанию остаётся одним основным потоком.

Вы не настраиваете `ae` по имени в `redis.conf`. Эффект виден в задержке, slow log и `INFO`.

Блокирующие команды (`BRPOP`, `XREAD BLOCK`) паркуют этого клиента. Цикл продолжает обслуживать других клиентов. `blocked_clients` (тема 19) считает этих ждущих.

Не проектируйте команду приложения, которой нужно 100 мс CPU в основном потоке. Дробите работу.

## Потоки ввода-вывода

С Redis 6 можно включить потоки ввода-вывода. Эти потоки читают входящие байты и пишут исходящие. Основной поток по-прежнему разбирает и выполняет команды.

```text
CONFIG GET io-threads
CONFIG GET io-threads-do-reads
```

По умолчанию часто выключены или `1` (нет лишних потоков ввода-вывода). Маленький экземпляр на локальном сокете может не выиграть. Нагрузка с многими соединениями и маленькими командами на многоядерном хосте может выиграть в пропускной способности.

Потоки ввода-вывода не делают `INCR` параллельным на одном ключе. Они не убирают проблему большого ключа.

Настройка:

- Задайте `io-threads` маленьким числом ядер, не «все ядра»
- Измеряйте `INFO` и p99 приложения
- Читайте заметки версии; поведение менялось между выпусками

Не включайте потоки ввода-вывода и затем не предполагайте, что Cluster не нужен. Масштаб CPU команд всё ещё нуждается в шардах, когда одно ядро — предел.

Потоки для ввода-вывода — не многопоточное выполнение команд в стиле KeyDB (следующий раздел).

Оставляйте потоки ввода-вывода выключенными, пока нет измерения, которое показывает выигрыш.

## Цикл активного истечения

Ключи с TTL должны исчезнуть. Redis не только ждёт следующий `GET`.

Два механизма:

- Ленивое истечение: когда команда касается ключа, Redis удаляет его, если TTL в прошлом
- Активное истечение: цикл сэмплирует ключи с TTL и удаляет истёкшие

Активный цикл выполняется как событие времени в цикле. Он использует долю времени, чтобы истечение не монополизировало основной поток. Если много ключей истекают сразу (давка темы 13, тема 4), цикл может взять больше работы. Растёт `expired_keys`.

`INFO` может показывать поля, связанные с истечением (`expired_stale_perc` и другие по версии). Высокий процент устаревших значит многие ключи в наборе истечения уже мертвы, но ещё не удалены. Память остаётся высокой, пока цикл не догонит.

Огромная буря истечения после массовой загрузки с одним TTL — событие эксплуатации. Джиттер (тема 13) разносит эту бурю.

`EXPIRE` миллионов ключей за одну секунду тоже создаёт будущую работу.

Не путайте `expired_keys` с `evicted_keys`. Вытеснение — `maxmemory` (тема 4).

## Шина Cluster

Тема 11 упоминала шину Cluster. Каждый узел Cluster слушает второй порт для сообщений узел-к-узлу. По умолчанию это клиентский порт плюс `10000` (клиент `6379` → шина `16379`).

Шина несёт:

- Gossip (какие узлы есть, какими слотами владеют, флаги)
- Голоса переключения
- Fan-out Pub/Sub через узлы
- Сообщения миграции, связанные со слотами

Клиенты не отправляют `GET` на порт шины. Файрволы должны разрешать трафик шины между узлами, не из публичного интернета.

```text
CLUSTER INFO
CONFIG GET cluster-port
```

Если шина заблокирована, узлы помечают друг друга недостижимыми. Кластер может уйти в `fail` даже если клиенты могут достичь каждого клиентского порта.

Протокол шины — не команды приложения RESP. Не направляйте `redis-cli` на порт шины и не ждите, что обычное приглашение будет полезным.

Безопасность: защищайте шину как клиентский порт (частная сеть, нет публичной привязки). Чужой на шине — проблема члена кластера.

Не публикуйте порт шины на LoadBalancer.

## Redis Functions против Lua

Тема 8 покрыла `EVAL` / `EVALSHA` и Redis 7 Functions (`FUNCTION LOAD`, `FCALL`).

Скрипты Lua:

- Путешествуют с клиента (или из `SCRIPT LOAD`)
- Используют кэш SHA1, который пустеет при перезапуске, если не перезагрузите
- Легко копировать в каждый сервис
- Создают дрейф версий (три SHA1 «одного» скрипта блокировки)

Functions:

- Живут как именованные библиотеки на сервере
- Обновляются в одном месте
- Сохраняются с RDB/AOF, когда настроено (проверьте)
- Всё ещё выполняются в основном потоке и всё ещё блокируют, если медленные
- Всё ещё должны перечислять ключи для безопасности Cluster

Оба атомарны относительно других команд. Оба должны быть достаточно детерминированными для репликации. Оба не общий сервер приложений.

Выбирайте Functions для Redis 7+, когда многие клиенты должны делить одну серверную версию. Выбирайте `EVALSHA` плюс `SCRIPT LOAD` во время деплоя, когда на старом Redis или когда у команды уже есть этот конвейер.

Не сопровождайте и Function, и копию Lua одной блокировки без одного источника истины.

`FUNCTION KILL` и `SCRIPT KILL` есть для сбежавшего скрипта, который сервер позволяет убить (читайте правила; некоторые скрипты нельзя убить, пока они выполняют определённые команды).

## Альтернативные реализации (Valkey, KeyDB) — осведомлённость

Протокол и набор команд Redis вдохновили другие серверы.

Valkey — проект Linux Foundation, который форкнулся от Redis после смены лицензии проекта Redis. Многие команды остаются знакомыми. Это альтернатива, которую можете увидеть у вендоров и в дистрибутивах. Читайте документацию Valkey про Cluster, модули и лицензию. Не предполагайте, что каждый модуль Redis загружается.

KeyDB — форк, который подчёркивает многопоточное выполнение команд. Модель параллелизма — не модель основного потока Redis. Предположения о гонках, верные на Redis (`INCR` атомарный в одном потоке), нуждаются в внимательном чтении документации KeyDB. Поведение модулей и Cluster может отличаться.

Есть другие прокси и совместимые кэши (кэши вендоров, образы `redis-stack`, облачные движки). Совместимость — спектр: обычные `GET`/`SET` работают; `MODULE`, `FUNCTION` и точные поля `INFO` могут нет.

Правила осведомлённости:

- Называйте сервер в runbook («Valkey 8», не «Redis», если это Valkey)
- Проверяйте клиент против этого сервера
- Читайте лицензию для вашего применения
- Не смешивайте реплики разных движков, если вендор это не поддерживает

Этот справочник остаётся путём обучения Redis. Команды здесь целят Redis. Когда используете альтернативу, проверяйте каждую команду на том движке.

Не считайте форк Redis для соответствия или контрактов поддержки без проверки.

# 10. Шардирование

## Описание

Эта тема показывает, как MongoDB делит один набор данных на много машин. **Шардированный кластер** имеет **шарды**, маршрутизатор **mongos** и **config-серверы**. Вы узнаёте, когда шардировать, как выбрать ключ шарда, хешированные и диапазонные ключи, чанки, балансировщик, горячие шарды и решардирование.

Сначала завершите репликацию, моделирование и индексы.

Используйте один термин для каждого понятия. **Шард** — replica set, который держит подмножество данных. **Ключ шарда** — список полей, который решает, какому шарду принадлежит документ. **Чанк** — диапазон значений ключа шарда, который балансировщик может переместить. **`mongos`** — процесс, который маршрутизирует запросы.

Шардирование увеличивает ёмкость. Шардирование также увеличивает стоимость эксплуатации. Не шардируйте коллекцию, которая ещё помещается на одном replica set.

---

## Когда шардировать

Шардируйте, когда одного replica set недостаточно. Частые сигналы:

- Рабочий набор не помещается в ОЗУ одного replica set
- Пропускная способность записи насыщает primary
- Диск одного replica set полон или скоро будет полон
- Один replica set не может удержать целевую задержку при пиковой нагрузке

Не шардируйте потому что «большие системы шардируют». Многие приложения долго живут на одном replica set. Atlas и современное железо держат большие наборы данных на одном replica set.

Стоимость шардирования:

- Нужно выбрать ключ шарда
- Некоторые запросы становятся scatter-gather (бьют по многим шардам)
- У транзакций и соединений (`$lookup`) есть лишние лимиты и стоимость
- Вы эксплуатируете много replica set плюс config-серверы плюс `mongos`

Шардируют коллекцию, а не «всю базу» как одну единицу. Другие коллекции могут остаться нешардированными. Нешардированные коллекции живут на primary-шарде.

Сначала завершите моделирование. Плохая форма документа плюс шард — всё ещё плохая форма.

Для учёбы можно запустить шардированный кластер в Docker или использовать шардированный кластер Atlas. На бумаге можно спроектировать ключ шарда до оплаты лишних шардов.

## Выбор ключа шарда

**Ключ шарда** — одно или несколько полей, которые есть в каждом документе. MongoDB хеширует или ранжирует эти значения, чтобы разместить документ.

Ключ шарда — трудная часть. Плохой ключ создаёт **горячий шард** (один шард получает большинство записей или чтений) или **jumbo-чанки**, которые не двигаются.

Полезный ключ шарда:

- **Высокая кардинальность** — много различных значений
- **Ровная частота** — значения не сваливаются в одно
- **Не монотонный для записей**, если нужно ровное распределение записи (или используйте хешированный ключ)
- **Присутствует в фильтре запроса** для целевых чтений

Плохой ключ шарда:

- Булево значение или статус с тремя значениями
- Монотонно растущий `_id` или метка времени для диапазонного шардирования (все вставки идут в последний чанк)
- Поле, которое большинство запросов не включает

У значений ключа шарда в документе есть правила. Ключ шарда нельзя снять. Значение ключа шарда документа в текущих версиях можно сменить, но смена дорогая. Планируйте ключ так, будто он останется.

Составные ключи шарда часты. Пример: `{ tenantId: 1, orderId: 1 }`. Первое поле целится в арендатора. Второе поле добавляет кардинальность.

Приложение должно слать ключ шарда в запросах, когда может. Find без ключа шарда может разлететься на все шарды.

Не выбирайте ключ только потому что он уникален. `_id` уникален и всё равно может быть плохим диапазонным ключом, если растёт со временем.

Читайте официальные страницы ключа шарда. Тестируйте на данных, похожих на промышленные, до шардирования живой коллекции.

## Хешированные и диапазонные ключи

**Диапазонный** ключ шарда размещает документы по порядку значений ключа. Соседние значения могут жить в одном чанке. Диапазонные запросы по ключу шарда могут попасть в один шард или в несколько шардов.

**Хешированный** ключ шарда считает хеш значения ключа. MongoDB размещает документы по хешу. Вставки распределяются ровно, даже если исходное поле растёт со временем.

Используйте диапазонный ключ, когда:

- Многие запросы используют диапазон по этому ключу
- Значения уже распределяют записи
- Хотите соседние ключи на одном шарде

Используйте хешированный ключ, когда:

- Натуральный ключ монотонен (ObjectId, метка времени)
- Нужно ровное распределение записи
- Принимаете, что диапазонный запрос по исходному полю разлетится

Хешированные ключи не помогают диапазонному запросу по исходному полю. Пример: хешированный `_id` не делает `find({ _id: { $gt: ... } })` диапазоном одного шарда.

Хешированный индекс как ключ шарда создают так:

```javascript
sh.shardCollection("shop.orders", { customerId: "hashed" })
```

Составные ключи могут смешивать диапазонный префикс и другие поля. Читайте текущие правила. У хешированных составных ключей есть ограничения, зависящие от версии.

Не хешируйте поле низкой кардинальности и не ждите чуда. У булева значения всё равно два хеша.

Atlas и помощники `mongosh` (`sh.status()`, `sh.shardCollection`) — обычные инструменты.

## Чанки, балансировщик, горячие шарды

**Чанк** — непрерывный диапазон значений ключа шарда (или хешей), который принадлежит одному шарду. Кластер делит чанки, когда они растут. **Балансировщик** перемещает чанки так, чтобы у шардов было похожее количество данных (и в текущих версиях похожая нагрузка по политике, которую настраиваете).

Config-серверы хранят карту чанков. `mongos` кэширует эту карту и маршрутизирует каждый запрос.

Типичные операции:

```javascript
sh.status()
sh.isBalancerRunning()
sh.startBalancer()
sh.stopBalancer()
```

Не останавливайте балансировщик надолго в промышленности без причины. Чанки растут неровно. Затем догоняющее перемещение велико.

Не запускайте тяжёлые смены схемы, некоторые резервные копии или некоторые обновления без процедуры из руководства. Процедура может попросить остановить балансировщик на короткое окно.

У размера чанка есть значение по умолчанию (часто 128 МБ во многих версиях). Большие документы дают меньше документов на чанк. Маленькие документы дают больше документов на чанк.

Запрос, который включает полный ключ шарда, может попасть в один чанк или один шард. Запрос без ключа шарда может ударить по всем шардам.

Перемещение чанка использует ресурсы исходного шарда, целевого шарда и сети. Балансировка во время пиковой записи может добавить задержку.

**Горячий шард** — шард, который получает гораздо больше трафика или данных, чем остальные. Причины:

- Монотонный диапазонный ключ (все вставки идут в последний чанк)
- Популярное значение ключа шарда (один арендатор, одна страна)
- Шаблон запросов, который всегда целится в один префикс

**Jumbo-чанк** — чанк, слишком большой, чтобы балансировщик мог его переместить по правилам. Причины:

- Слишком много документов с одним префиксом ключа шарда (чанк нельзя разделить)
- Очень большие документы
- Ключ почти без различных значений

Jumbo-чанки остаются на одном шарде. Балансировщик не может починить этот шард, переместив этот чанк. Нужно сменить ключ, уточнить ключ, разделить, если версия позволяет, или решардировать.

Обнаруживайте горячие шарды метриками: opcounters, CPU, диск и числа чанков, которые не совпадают с трафиком. У Atlas есть метрики шардов. `sh.status()` на некоторых версиях показывает флаги jumbo.

Сначала чините модель, когда один арендатор огромен. Шаблон выброса из дизайна схемы может подойти. Шардирование не убирает горячий ключ.

Не игнорируйте предупреждения jumbo. Они растут. Профилактика легче ремонта. Выберите кардинальность и ровную частоту до шардирования.

## Решардирование (современные версии)

В старых версиях MongoDB ключ шарда после `shardCollection` был почти фиксирован. Текущие версии добавляют два важных инструмента.

**Уточнить ключ шарда** (`refineCollectionShardKey`) добавляет одно или несколько суффиксных полей к существующему ключу. Пример: `{ customerId: 1 }` становится `{ customerId: 1, orderId: 1 }`. Нужен поддерживающий индекс. Уточнение помогает кардинальности, когда старый префикс остаётся. Оно не меняет существующее поле префикса.

**Решардировать коллекцию** (`reshardCollection`) меняет ключ шарда на новый ключ. Кластер копирует данные в новое распределение. Операции нужны лишний диск и время. Читайте текущие лимиты (размер, запас диска, блокирующее поведение).

Эти инструменты снижают цену ошибки первого ключа. Они не делают первый ключ дешёвым. Решардирование большой коллекции всё равно проект.

Доступность возможности зависит от основной версии и от Atlas. Используйте руководство, которое соответствует вашей версии.

Шаги по духу:

1. Создать нужный индекс для нового ключа.
2. Запустить refine или reshard, как показывает руководство.
3. Смотреть балансировщик и диск.
4. Сменить запросы приложения, чтобы включать новый ключ.

Не уточняйте вместо решардирования, когда проблема — сам префикс (например префикс булев).

Не запускайте решардирование без плана диска и отката.

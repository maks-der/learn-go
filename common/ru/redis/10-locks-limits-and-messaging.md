# 10. Блокировки, лимиты и обмен сообщениями

## Описание

Приложения используют Redis как общее место для блокировок, лимитов, id запросов и сессий. Redis также доставляет сообщения через Pub/Sub и потоки. Эта тема покрывает эти шаблоны, группы потребителей и когда выбирать Kafka.

Сначала завершите тему 2 (строковые блокировки), тему 5 (введение в потоки), тему 6 (Lua) и тему 9 (клиенты). Считайте каждый шаблон дизайном приложения плюс команды Redis, а не продуктом консенсуса.

Используйте один термин для каждого понятия. Блокировка — ключ, который может держать только один работник. Лимит частоты — потолок событий в окне времени. Ключ идемпотентности — сохранённый id запроса, который делает второе применение пустой операцией. Сессия — состояние на пользователя с TTL. Pub/Sub — широковещательная рассылка fire-and-forget. Поток — журнал с id. Группа потребителей — именованный курсор плюс список ожидающих. PEL — список ожидающих записей. `XACK` снимает запись с PEL.

## Распределённая блокировка (`SET NX EX`) и спор Redlock

Тема 2 ввела простую блокировку:

```text
SET lock:resource holder-id NX EX 30
```

`OK` значит, этот работник держит блокировку. Null значит, её держит другой работник. TTL освобождает ключ, если работник умрёт.

Снятие должно удалить только вашу блокировку. Скрипт Lua (тема 6) делает `GET`, затем `DEL`, если значение равно `holder-id`. Двухшаговый `GET` плюс `DEL` из клиента может снять блокировку другого работника после истечения.

Пределы блокировок на одном экземпляре:

- Пауза Redis, вытеснение или долгий GC в работнике могут истечь блокировку, пока работник ещё работает.
- Второй работник тогда приобретает блокировку. Два работника выполняют критическую секцию.
- Один экземпляр Redis — не система консенсуса на нескольких узлах. Переключение может потерять блокировку, которая не была персистирована.

Redlock — алгоритм, который использует несколько независимых экземпляров Redis. Документация Redis его описывала. Мартин Клеппманн и другие опубликовали критику. Спор покрывает часы, паузы, fencing и безопасен ли Redlock для работы, критичной к корректности.

Этот справочник не разрешает спор. Для обучения:

- Используйте один экземпляр, уникальный id держателя, TTL и атомарное снятие.
- Для работы, критичной к корректности (деньги, уникальные побочные эффекты), добавьте fencing-токен (монотонное число из `INCR`), который проверяет ресурс, или используйте систему, спроектированную для консенсуса.
- Не считайте `SET NX EX` полной распределённой транзакцией базы.

Не блокируйте, когда одна команда Redis уже делает обновление безопасным (`INCR`, обновление Lua данных только Redis).

## Лимит частоты

Лимит частоты отклоняет или задерживает события, когда клиент превышает бюджет.

Фиксированное окно:

```text
INCR rl:user:42:202609131857
EXPIRE rl:user:42:202609131857 60
```

Используйте текущую минуту (или секунду) в ключе. Если счёт выше N, отклоните. `EXPIRE` на первом инкременте (Lua может задать срок только когда значение — `1`).

Лимит сбрасывается на границе окна. Пользователь может отправить N событий в конце одной минуты и N в начале следующей (2N за две секунды).

Скользящее окно: храните метки времени событий в упорядоченном множестве. `ZREMRANGEBYSCORE` сбрасывает старых членов. `ZCARD` — счёт. `ZADD` нового события, если ниже лимита. Тема 4 покрыла команды. Память растёт с событиями в окне.

Token bucket: ключ хранит токены (или время последней доливки плюс токены). Каждый запрос берёт один токен. Токены доливаются со временем до потолка. Скрипт Lua обновляет ключ атомарно. Вспышки разрешены до размера ведра.

Выбирайте:

- Фиксированное окно — простое, дешёвое, вспышка на границах
- Скользящее окно — глаже, больше CPU и памяти
- Token bucket — контроль вспышки со стабильной доливкой

Cluster: держите все ключи одного лимита на одном слоте (`{user:42}`).

Не лимитируйте частоту только в процессе приложения. Многие процессы делят один бюджет Redis.

## Ключи идемпотентности и хранилище сессий

Клиент может отправить один запрос дважды (повтор, двойной клик, таймаут). Ключ идемпотентности делает второе применение возвращающим первый результат (или зарезервированную ошибку) без второго побочного эффекта.

Шаблон:

```text
SET idem:pay:req-9f3a 1 NX EX 86400
```

Если ответ — `OK`, это первый запрос. Сделайте работу. Затем `SET` сохранённого результата (или хеша) на том же ключе или на соседнем ключе.

Если ответ — null, ключ есть. Верните сохранённый результат. Не списывайте снова.

Используйте TTL достаточно длинный для повторов (часы для платежей часто). Документируйте TTL.

Сама работа всё ещё должна быть безопасной, если процесс умрёт после `SET NX` и до завершения побочного эффекта. Некоторые дизайны хранят `pending`, затем `done` плюс результат. Согласователь завершает ключи `pending`.

Redis — координатор. Запись банка или SQL всё ещё нуждается в собственной идемпотентности, когда можете её использовать.

Не используйте короткий TTL для id платежа, который клиент может повторить через 10 минут.

Cluster: `{pay:req-9f3a}` и на ключе блокировки, и на ключе результата, если используете два ключа.

Сессия — данные, которые принадлежат браузеру или устройству после входа. Redis — частое хранилище сессий: низкая задержка, TTL и общее хранилище для многих процессов приложения.

Типичная раскладка:

```text
HSET sess:a1b2 user 42 role staff
EXPIRE sess:a1b2 1800
```

Или одна строка JSON: `SET sess:a1b2 '{"user":42}' EX 1800`.

Приложение задаёт cookie с id сессии (случайное значение). Cookie — не id пользователя. Redis держит отображение.

Скользящая сессия: на каждый запрос снова `EXPIRE` (или `SET` с новым TTL). Абсолютная сессия: держите поле `created` и отказывайте после максимального возраста, даже если `EXPIRE` скользит.

Выход: `DEL` ключа сессии.

Не храните пароли в сессии. Храните id пользователя и небольшой набор утверждений. Подписывайте или шифруйте cookie, если id должен быть неугадываемым; ключу Redis всё равно нужен длинный случайный id.

Многие процессы делят один Redis. В этом смысл. Локальная карта сессий процесса падает, когда балансировщик меняет процесс.

Персистентность: сессии могут быть кэшем. Потеря разлогинивает всех. Если это неприемлемо, включите персистентность или примите риск (тема 7, тема 12).

## Pub/Sub против потоков

Pub/Sub:

```text
SUBSCRIBE news
PUBLISH news hello
```

Redis доставляет `hello` текущим подписчикам. Если ни один подписчик не подключён, сообщение пропало. Нет журнала, нет `ACK` и нет группы потребителей.

`PSUBSCRIBE news*` совпадает с шаблонами. `UNSUBSCRIBE` покидает канал.

Соединение в режиме подписки не выполняет обычные команды. Используйте выделенное соединение (тема 9).

At-most-once: Redis старается отправить сообщение текущим подписчикам. Если подписчик отключён, медленный или ещё не подписан, этот подписчик не получит более поздний повтор из Redis. Redis не хранит сообщение.

Медленные подписчики: Redis может отключить клиента, который читает недостаточно быстро (`client-output-buffer-limit` для pubsub). Этот клиент теряет сообщения.

`SUBSCRIBE` после `PUBLISH` не получает старое сообщение.

`ACK` нет. Издатель не знает, что данный подписчик обработал полезный груз.

Потоки (введение в теме 5):

- У записей есть id
- Потребитель может прочитать позже
- Группы и `XACK` отслеживают работу
- `XTRIM` / `MAXLEN` ограничивают память

Используйте Pub/Sub для живых сигналов, когда потеря приемлема (подсказки инвалидации кэша, «флаги перезагрузки», присутствие). Используйте потоки, когда работник должен обработать каждое событие хотя бы раз и нужен список ожидающих.

Pub/Sub в Cluster использует шину кластера для веера. Доставка всё ещё at-most-once для каждого подписчика.

Не используйте Pub/Sub как долговечную очередь заданий. Не используйте Pub/Sub для «списать эту карту» или «отправить это письмо один раз».

Используйте Pub/Sub для подсказок. Пример: «продукт 1001 изменился». Подписчик делает `DEL` ключа кэша. Если подсказка потеряна, TTL всё равно чинит кэш.

## Группы потребителей, `XACK`, ожидающие записи

Группа потребителей позволяет многим работникам делить поток. Каждая запись идёт одному потребителю в группе (конкурирующие потребители). Redis хранит последний доставленный id для группы и PEL.

Создайте группу:

```text
XGROUP CREATE lab:orders grpA 0 MKSTREAM
```

`0` значит «начать с начала». `$` значит «начать только с новых записей». `MKSTREAM` создаёт поток, если его нет.

Читайте как потребитель:

```text
XREADGROUP GROUP grpA worker1 COUNT 1 STREAMS lab:orders >
```

`>` значит «дай мне записи, которые группа ещё не доставила». Имя потребителя — `worker1`. Два работника используют два имени.

После успеха подтвердите:

```text
XACK lab:orders grpA 1726248000000-0
```

`XACK` снимает запись с PEL. Запись может остаться в потоке до обрезки. `XACK` — не `XDEL`.

Если процесс умрёт до `XACK`, запись остаётся ожидающей. Другой работник может её заявить.

`XINFO GROUPS lab:orders` и `XINFO CONSUMERS lab:orders grpA` показывают поля в стиле отставания и счёты ожидающих.

У одного потока может быть много групп. У каждой группы свой курсор. Одна запись может быть доставлена каждой группе. Это веер между группами и конкурирующие потребители внутри группы.

PEL держит записи, которые группа доставила и которые ни один потребитель не подтвердил.

```text
XPENDING lab:orders grpA
XPENDING lab:orders grpA - + 10
```

Короткая форма возвращает счёт и диапазон простоя. Длинная форма перечисляет id, потребителя, время простоя и счёт доставок.

Мёртвый потребитель оставляет ожидающие записи. Другой потребитель заявляет их:

```text
XCLAIM lab:orders grpA worker2 60000 1726248000000-0
```

Число `60000` — минимальное время простоя в миллисекундах. Redis не заявляет запись моложе этого времени простоя (если не форсировать). Это избегает кражи у медленного, но живого работника.

`XAUTOCLAIM` (Redis 6.2+) обходит PEL и заявляет пакет. Предпочитайте его в новых работниках.

После `XCLAIM` новый потребитель владеет записями PEL. Обработайте их. Затем `XACK`.

Счёт доставок растёт, когда Redis доставляет снова. Ядовитое сообщение (всегда падает) может зациклиться. После N доставок напишите ключ мёртвых писем или журнал, затем `XACK`, чтобы PEL не рос вечно.

`XPENDING` — проверка здоровья группы. Растущий PEL значит, потребители медленные, упали или не делают `XACK`.

Не делайте `XACK` до того, как побочный эффект долговечен, если нужно обработка at-least-once. Не пропускайте `XACK`, если уже завершили побочный эффект, иначе PEL растёт и другой работник сделает работу снова. Делайте побочный эффект идемпотентным.

`XADD key * field value` добавляет запись. Неограниченный поток заполняет ОЗУ. Используйте `MAXLEN` на `XADD` или `XTRIM`, чтобы ограничить длину.

## Когда использовать потоки Redis против Kafka

Потоки Redis и Apache Kafka оба журналы. Они не один продукт.

Потоки Redis подходят, когда:

- Вы уже запускаете Redis
- Журнал достаточно мал для ОЗУ (или вы жёстко обрезаете)
- Удержание короткое
- Группы потребителей простые
- Эксплуатационная команда — команда Redis
- Нужна низкая задержка на одном кластере, который вы уже знаете

Kafka подходит, когда:

- Удержание большое (часы или дни высокого объёма на диске)
- Много независимых групп потребителей читают длинный журнал
- Нужен большой кластер брокеров, разделы и экосистема (Connect, реестр схем)
- Повтор огромной истории — обычная операция
- Изоляция от кэш-Redis обязательна (тема 12)

Redis держит данные потока в памяти (плюс персистентность, если включите). Многодневный пожарный шланг событий заполнит Redis. Kafka пишет дисковый журнал и масштабирует разделы по брокерам.

Смещения потребителей Kafka живут в Kafka. Состояние группы Redis живёт в Redis. Режимы отказа следуют остальной системе (переключение Redis против ISR реплик Kafka).

Можно использовать оба: Redis для кэша и коротких очередей работы, Kafka для корпоративной шины событий.

Не выбирайте потоки только потому, что имена команд короче. Мерите объём, удержание и кто будет эксплуатировать систему.

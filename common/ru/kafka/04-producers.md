# 4. Продюсеры

## Описание

Продюсер — клиент, который добавляет записи в партиции топика. Продюсер выбирает партицию, собирает записи в пакеты, отправляет их лидеру партиции и обрабатывает успех или ошибку.

Эта тема покрывает API продюсера, подтверждения, идемпотентный продюсер, повторы, пакетирование, сжатие, сериализацию и ядовитые сообщения. Завершите эту тему после темы 3. Завершите эту тему до темы 5.

Используйте один термин для каждого понятия. Подтверждение (`acks`) — ответ брокера, которого ждёт продюсер. Идемпотентный продюсер — режим продюсера, который предотвращает дубликаты от повторов. Ядовитое сообщение — запись, которую продюсер или консьюмер не может обработать. Для всей новой работы используйте кластеры KRaft. Продюсер говорит с брокерами. Продюсер не говорит с ZooKeeper.

## API продюсера

API продюсера — клиентский интерфейс, который отправляет записи. В Java тип — `KafkaProducer`. В других языках есть тип продюсера с той же идеей: настроить, отправить, flush или close.

Типичная последовательность:

1. Соберите конфигурацию. Задайте `bootstrap.servers`. Задайте сериализаторы для ключа и значения.
2. Создайте продюсера.
3. Соберите запись (`topic`, необязательный `key`, `value`, необязательные заголовки и партиция).
4. Вызовите `send`. `send` часто асинхронный. Клиент возвращает future или вызывает callback.
5. Вызовите `flush`, когда нужно дождаться записей в полёте. Вызовите `close`, когда процесс заканчивается.

`bootstrap.servers` — список брокеров. Продюсер получает метаданные. Затем продюсер отправляет каждый пакет текущему лидеру целевой партиции.

Не создавайте нового продюсера на каждую запись. Продюсер держит соединения и буферы. Делите одного продюсера на процесс, когда конфигурация одна.

Обрабатывайте результат `send`. Игнор callback — частая причина тихой потери данных.

Консольный продюсер — маленький продюсер для тестов. Используйте его, чтобы учиться. Для приложений используйте клиентский API.

## Acks: `0`, `1`, `all`

`acks` управляет, когда продюсер считает отправку успешной.

- `acks=0`. Продюсер не ждёт ответа брокера. Брокер может отбросить запись. Продюсер также может потерять запись при сетевой ошибке. Пропускная способность может быть высокой. Устойчивость низкая.
- `acks=1`. Лидер пишет запись в свой локальный журнал и отвечает. У фолловеров записи может ещё не быть. Если лидер падает до того, как фолловеры скопировали запись, запись может быть потеряна.
- `acks=all` (или `acks=-1`). Лидер ждёт, пока in-sync реплики (ISR) удовлетворят `min.insync.replicas`. Тема 9 определяет ISR. Эта настройка — устойчивый выбор для важных данных.

Идемпотентный продюсер требует `acks=all`. Текущие Java-клиенты включают идемпотентность по умолчанию и задают `acks=all`.

Не используйте `acks=0` для заказов, платежей или других данных, которые нельзя потерять. Используйте `acks=0` только когда потеря приемлема (некоторые метрики).

`acks` — настройка продюсера. `min.insync.replicas` — настройка брокера или топика. Оба важны для `acks=all`.

## Идемпотентный продюсер

Идемпотентный продюсер предотвращает дубликаты, которые создают повторы. Без идемпотентности продюсер может отправить запись, потерять подтверждение, повторить и добавить ту же запись дважды.

С идемпотентностью у продюсера есть идентификатор продюсера (PID) и порядковый номер на партицию. Брокер отклоняет дубликат последовательности. Журнал хранит одну копию.

Включите функцию через `enable.idempotence=true`. Текущие Java-клиенты задают это по умолчанию. Идемпотентность требует `acks=all` и ограниченный набор запросов в полёте на соединение.

Идемпотентность не делает всю бизнес-операцию ровно один раз. Она убирает дубликаты повторов продюсера. Тема 7 покрывает семантику exactly-once и транзакции.

Не отключайте идемпотентность, чтобы «сделать проще». Простой устойчивый режим по умолчанию — идемпотентность включена.

Идемпотентный продюсер — не то же самое, что консьюмер, который игнорирует дубликаты бизнес-ключей. Оба могут существовать в одной системе.

## Повторы и `delivery.timeout.ms`

Сети падают. Лидеры перемещаются. Продюсер повторяет неудачную отправку, когда ошибка временная. `retries` (или эквивалент) задаёт, сколько раз клиент повторяет. Современные клиенты используют большое число повторов и вместо этого ограничивают время.

`delivery.timeout.ms` — общий бюджет времени для записи. Бюджет включает время linger, время отправки и повторы. Когда бюджет заканчивается, продюсер считает отправку неудачной. Вы обрабатываете эту ошибку.

`request.timeout.ms` — тайм-аут одного запроса. `linger.ms` — ожидание до ухода пакета. Тайм-аут доставки должен быть больше linger плюс тайм-аут запроса.

Повтор неидемпотентного продюсера может создать дубликаты. Повтор идемпотентного продюсера эти дубликаты не создаёт.

Не повторяйте бесконечно в прикладном коде вокруг `send` без границы. Используйте тайм-аут клиента. Логируйте неудачный ключ и значение (или безопасное резюме), чтобы можно было починить.

Некоторые ошибки не временные. Примеры: запись слишком большая, неизвестный топик (когда автосоздание выключено), ошибка сериализации. Повторы эти ошибки не исправляют.

## Пакетирование: `linger.ms`, `batch.size`

Продюсер группирует записи, которые идут в одну партицию, в пакет. Пакет — полезная нагрузка одного запроса produce для этой партиции.

`batch.size` — максимальный размер пакета в байтах. Продюсер отправляет раньше, когда пакет полон.

`linger.ms` — дополнительное ожидание новых записей. `linger.ms=0` отправляет как можно скорее. Небольшой linger (например 5–20 мс) часто повышает пропускную способность, потому что каждый запрос несёт больше записей.

Пакетирование увеличивает задержку до времени linger. Пакетирование уменьшает число запросов. Выбирайте linger из бюджета задержки приложения.

Sticky-партиционер для ключей null существует, чтобы заполнять пакеты. Тема 3 покрывает это поведение.

`buffer.memory` — суммарная память, которую продюсер может использовать для ещё не отправленных записей. Когда буфер полон, `send` блокируется или бросает исключение в зависимости от `max.block.ms`.

## Сжатие

Продюсер может сжать пакет. Обычные кодеки — `gzip`, `snappy`, `lz4` и `zstd`. Вы задаёте `compression.type` на продюсере (или на топике).

Сжатие уменьшает размер сети и диска. Сжатие использует CPU. `lz4` и `zstd` — обычные значения по умолчанию для новых систем. `gzip` медленнее. `snappy` обычен в старых установках.

Брокер хранит сжатый пакет. Консьюмеры распаковывают. Все клиенты, которые читают топик, должны понимать кодек. Текущие клиенты Kafka поддерживают обычные кодеки.

Не сжимайте дважды без причины. Если значение уже сжатый блоб, сжатие продюсера может не помочь.

Измеряйте. Пакет JSON часто сжимается хорошо. Пакет случайных байтов — нет.

## Сериализация (JSON, Avro, Protobuf)

Продюсер должен преобразовать ключ и значение в байты. Сериализатор делает эту работу. Консьюмер использует согласованный десериализатор.

JSON — текстовые байты. JSON легко отлаживать. У JSON нет встроенной проверки схемы на брокере. Продюсеры могут писать разные формы. Консьюмеры ломаются.

Avro и Protobuf — двоичные кодировки со схемой. Команды часто хранят схему в Schema Registry. Тема 11 покрывает реестр и совместимость.

Задайте `key.serializer` и `value.serializer` (имена Java) или эквивалент. Обычная учебная пара — строка или JSON для ключа и значения. Не используйте JSON-сериализатор для ключа, который хотите хешировать как стабильный идентификатор, если не контролируете порядок полей JSON. Строковый идентификатор — более простой ключ.

Kafka не проверяет ваш JSON. Успех produce означает, что байты в журнале, а не что значение — корректное бизнес-событие.

## Обработка ошибок и ядовитые сообщения

Ядовитое сообщение — запись, которая блокирует прогресс. На стороне produce ядовитая запись может быть значением, которое не сериализуется, записью больше `max.request.size` или `max.message.bytes` топика, или записью, которую брокер отклоняет.

На стороне consume (тема 5) ядовитая запись может быть байтами, которые не десериализуются, или значением, которое не проходит бизнес-правило. Этот раздел фокусируется на продюсере.

Обрабатывайте ошибки сериализатора до `send`. Не повторяйте запись, которую нельзя сериализовать. Исправьте приложение или направьте событие на путь ремонта.

Обрабатывайте ошибки брокера в callback. Временные ошибки принадлежат бюджету повторов клиента. Постоянные ошибки принадлежат метрикам, логам и плану dead-letter.

Dead-letter топик — топик, который хранит записи, которые не удались. Пишите исходный топик, ошибку и достаточно нагрузки для ремонта. Не создавайте бесконечный цикл между основным топиком и dead-letter топиком.

Ограничивайте размер записи. Большие записи вредят брокерам и консьюмерам. Храните большие блобы в объектном хранилище. Положите указатель в значение Kafka.

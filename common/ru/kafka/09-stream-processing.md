# 9. Обработка потоков

## Описание

Обработка потоков читает записи из Kafka, считает результат и пишет записи или запрашиваемое состояние. Эта тема называет частые инструменты и базовые идеи Kafka Streams.

Эта тема показывает Kafka Streams против ksqlDB против Flink, KStream, KTable, топологию, stateless против stateful обработки, окна и exactly-once в Streams. Завершите эту тему после тем 4, 5, 6 и 8. Потоковые задачи используют кластер Kafka. Используйте KRaft для новых кластеров. Процессорам потоков не нужен ZooKeeper.

Используйте один термин для каждого понятия. Потоковая задача — программа, которая обрабатывает записи непрерывно. Топология — граф источников, процессоров и стоков. KStream — поток событий. KTable — changelog последнего значения на ключ. Stateless-обработка использует только текущую запись. Stateful-обработка держит хранилище. Окно группирует записи по времени.

## Kafka Streams против ksqlDB против Flink

**Kafka Streams** — библиотека Java. Вы запускаете её внутри процесса приложения. Это не отдельный кластер. Каждый экземпляр — консьюмер Kafka и продюсер Kafka (и больше). Экземпляры, которые делят `application.id`, образуют группу. Kafka назначает партиции этим экземплярам.

Kafka Streams хранит локальное состояние на диске (часто RocksDB) и подпирает это состояние changelog-топиками на кластере Kafka. После перезапуска или ребаланса экземпляр может восстановить состояние из changelog.

Используйте Kafka Streams, когда команда пишет Java (или язык JVM), задача умещается в приложении и вы хотите эксплуатировать задачу как обычный сервис. Не используйте Kafka Streams, если нужен first-class API не-JVM как единственный вариант.

**ksqlDB** (в старых материалах также KSQL) — система обработки потоков, которая использует операторы в стиле SQL. Вы запускаете сервер ksqlDB. Клиенты отправляют операторы: создать поток, создать таблицу, фильтр, join, агрегация.

Поток в ksqlDB — последовательность событий (как KStream). Таблица — последнее значение на ключ (как KTable). ksqlDB использует Kafka как журнал и во многих развёртываниях использует Kafka Streams внутри. Кластер Kafka всё равно нужен. ksqlDB не часть брокера Apache Kafka. Это отдельный продукт (Confluent и связанные дистрибутивы).

Используйте ksqlDB, когда аналитики или платформенные команды хотят SQL и сервер, а не Java-топологию в каждом сервисе. Не ждите каждую возможность Streams или каждый свой процессор в SQL.

**Apache Flink** — движок обработки потоков. Вы запускаете кластер Flink (JobManager и TaskManagers) или управляемый сервис Flink. Задача Flink — DAG операторов. Flink может использовать Kafka как источник и как сток.

Flink по умолчанию не библиотека Kafka внутри маленького сервиса. Это вычислительный кластер. У него своя модель checkpoint и savepoint. Офсеты Kafka — часть этого состояния, когда используете источник Kafka.

Используйте Flink, когда нужны крупномасштабные stateful-задачи, сложное event time или команда, которая уже эксплуатирует Flink. Используйте Kafka Streams, когда задача принадлежит микросервису и язык — JVM. Оба могут делить один кластер Kafka KRaft как журнал.

Connect копирует и преобразует записи (тема 8). Streams, ksqlDB и Flink считают. Некоторые команды используют Connect и потоковую задачу вместе.

Все эти инструменты говорят с брокерами через `bootstrap.servers`. Они не запускают ZooKeeper. Используйте KRaft для новых кластеров Kafka.

## KStream, KTable и топология

**Топология** — направленный граф. Источники читают топики Kafka. Процессоры преобразуют записи. Стоки пишут топики Kafka. Kafka Streams строит задачу на поток из этого графа. Каждая задача владеет подмножеством партиций.

**KStream** — поток записей. Каждая запись — событие. Две записи с одним ключом — два события. Пример: заказ 1, затем заказ 2 для того же пользователя.

**KTable** — табличный вид changelog. Для каждого ключа таблица хранит последнее значение. Значение null — томбстоун и удаляет ключ (тема 6). Пример: пользователь 9 теперь живёт в городе A, затем в городе B. Таблица показывает город B.

Можно превратить KStream в KTable (агрегация или последнее-на-ключ). Можно превратить KTable в KStream (каждое изменение становится событием).

Входные топики для таблиц часто компактируемые. Входные топики для потоков часто используют ретеншн delete. Совмещайте `cleanup.policy` со смыслом топика (тема 6).

`application.id` называет группу консьюмеров и префиксирует внутренние топики (repartition, changelog). Не используйте повторно `application.id` для другой топологии без плана сброса.

```text
StreamsBuilder builder = new StreamsBuilder();
KStream<String, String> orders = builder.stream("orders.placed");
KTable<String, String> customers = builder.table("customers");
```

**DSL** — API высокого уровня: `stream`, `table`, `filter`, `map`, `groupByKey`, `aggregate`, `join`. Большинство задач используют DSL. **Processor API** позволяет реализовать узел процессора. Сначала учите DSL.

Join сочетают записи, которые делят ключ. Join поток-поток оконные. Join поток-таблица смотрит текущее значение таблицы. Join таблица-таблица производит таблицу. Ключи null не join. Если ключи на неправильной партиции, Streams пишет топик repartition.

Кластер — KRaft. Streams использует `bootstrap.servers`. В текущем Streams нет настройки ZooKeeper.

## Stateless map/filter против stateful-агрегаций

**Stateless**-обработка использует только текущую запись (и константы). `map` меняет запись. `filter` оставляет или отбрасывает запись. Задача может потерять локальную память и всё равно быть правильной, если снова читает топик с последнего зафиксированного офсета.

**Stateful**-обработка держит хранилище с ключом записи (и иногда окном). Примеры: счёт, сумма, join, уникальный пользователь за день. Задача должна восстановить это хранилище после сбоя. Changelog-топики существуют для этого.

Фильтр, который отбрасывает маленькие заказы, stateless. Счёт заказов на клиента stateful. Join заказов и клиентов stateful.

**State store** держит текущую агрегацию или состояние join. Kafka Streams часто использует RocksDB на диске экземпляра. **Changelog-топик** — топик Kafka, который записывает каждое обновление хранилища. Топик обычно компактируемый (тема 6). После сбоя экземпляр читает changelog и перестраивает хранилище.

Томбстоуны в changelog убирают ключ из хранилища. Не пишите в changelog-топики консольным продюсером. Не задавайте короткий ретеншн delete на changelog, если не принимаете неверное восстановление.

Состояние растёт с ключами и с окнами. Неограниченные наборы ключей заполняют диск.

Exactly-once и at-least-once (тема 5) важнее, когда у задачи есть состояние. Дубликат обработки счёта может удвоить счёт, если фреймворк не использует транзакции или идемпотентные обновления.

Не прячьте запись в базу внутри «stateless» map без плана. Эта запись — внешнее состояние.

KRaft хранит метаданные кластера. KRaft не заменяет changelog-топики. Данные партиций и changelog по-прежнему живут в `log.dirs` на брокерах.

## Окна

**Окно** группирует записи, которые делят ключ и попадают в диапазон времени. Окна — для stateful-агрегации. Время может быть event time (метка времени записи) или processing time (часы на задаче). Event time — обычный выбор, когда записи могут прийти поздно.

**Tumbling**-окна имеют фиксированный размер и не перекрываются. Пример: 5-минутные окна в 10:00, 10:05, 10:10. Каждая запись принадлежит одному tumbling-окну.

**Hopping**-окна имеют фиксированный размер и интервал hop. Hop меньше размера, когда нужно перекрытие. Пример: размер 5 минут, hop 1 минута. Одна запись может принадлежать больше чем одному hopping-окну.

**Session**-окна используют разрыв. Если для ключа не приходит запись в течение времени разрыва, сессия закрывается. Следующая запись начинает новую сессию. Длина сессии не фиксирована.

Поздним записям нужен grace period или разрешённая опоздание в некоторых движках. После закрытия окна поздняя запись может быть проигнорирована или обновить поздний результат. Читайте документацию движка.

Окна создают больше состояния, чем простой счёт-на-ключ. Каждый ключ окна — `(key, window-start)` или id сессии. Ретеншн состояния окна — конфигурация.

Kafka Streams, ksqlDB и Flink все реализуют эти типы окон. Имена почти те же. Ключи конфигурации отличаются.

Join поток-поток тоже оконные. Запись на одной стороне находит записи на другой стороне внутри окна join.

## Exactly-once в Streams

Exactly-once в Streams значит, что обработка входной записи имеет один видимый эффект на выходных топиках и на внутреннем состоянии, которым управляет Streams. Он использует транзакционный протокол Kafka (тема 5).

Вы задаёте `processing.guarantee` в `exactly_once_v2` (текущее имя; старые версии использовали `exactly_once`). Streams оборачивает consume, обновление состояния и produce в транзакцию. Перезапуск не применяет тот же вход дважды к выходу.

`exactly_once_v2` нужны брокеры, которые это поддерживают. Текущая Apache Kafka на KRaft поддерживает. Прочитайте матрицу версий в официальных документах.

EOS не покрывает побочные эффекты, которые вы добавляете в процессоре (вызовы HTTP, дополнительные записи в базу). Эти побочные эффекты могут выполниться дважды. Кладите внешние записи за идемпотентным консьюмером или outbox (тема 11).

`at_least_once` — другая частая гарантия. Она проще и может писать дубликаты в сток.

Изоляция: транзакционные консьюмеры стока должны использовать `isolation.level=read_committed`, если не должны видеть прерванные записи (тема 5).

Не включайте EOS только на продюсере стока, пока приложение Streams использует at-least-once. Задайте гарантию Streams.

Можно тестировать топологию без кластера через `TopologyTestDriver` (Java). Интеграционным тестам всё равно нужен настоящий кластер KRaft для Serdes, EOS и восстановления.

#### Простые практические задания

1. Напишите шпаргалку на одну страницу: три инструмента, KStream против KTable, stateless против stateful, три типа окон, EOS Streams.
2. Нарисуйте одну схему, которая включает кластер KRaft и два из трёх инструментов, которые делят топики.
3. Добавьте в закладки официальные страницы Streams, ksqlDB и коннектора Flink Kafka.
4. Пометьте пять реальных правил магазина как stateless, stateful или windowed-stateful.

#### Средние практические задания

1. Напишите решение для трёх задач: (a) замаскировать поле в S3, (b) текущий баланс на счёт, (c) уникальные пользователи за 15 минут. Выберите Connect, Streams, ksqlDB или Flink для каждой. Дайте одну причину.
2. Сопоставьте каждый подраздел с одним официальным URL.
3. Перечислите типы внутренних топиков, названные в этой теме и в теме 8. Запишите, кто их создаёт.

#### Сложные практические задания

1. Спроектируйте один конвейер, который использует Connect (source), Kafka Streams или ksqlDB (агрегация) и sink. Назовите топики, ключи, окно и роль changelog. Используйте только KRaft.
2. Напишите сравнение на две страницы для вашей команды: когда добавляете Flink, когда остаётесь на Streams и как оба используют одну Kafka KRaft.

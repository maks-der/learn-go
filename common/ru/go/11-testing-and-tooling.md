# 11. Тесты и инструменты

## Описание

Тесты Go живут рядом с кодом. Пакет `testing` и команда `go test` запускают тесты, бенчмарки, примеры и цели фаззинга. Покрытие, линтеры и `pprof` дополняют ежедневный набор инструментов.

Эта тема учит каждый инструмент как отдельный навык. Сначала завершите тему 1. Нужно знать `go test`, пакеты и модули. Тема 10 помогает, когда тест запускает горутины или использует context.

Используйте один термин для каждого понятия. Тестовая функция — не бенчмарк. Пример — не цель фаззинга. Fake — не mock.

## `*_test.go` и табличные тесты

Тестовый файл — файл Go, имя которого заканчивается на `_test.go`. Команда `go test` компилирует эти файлы вместе с тестируемым пакетом. Команда `go build` игнорирует их, когда собираете библиотеку или команду.

Кладите тестовый файл в тот же каталог, что и пакет. Файл может использовать одно из двух имён пакетов:

- `package foo` — тест внутренний. Файл может использовать неэкспортируемые имена.
- `package foo_test` — тест внешний. Файл импортирует `foo` как клиент. Файл может использовать только экспортируемые имена.

Используйте внешний тест, когда хотите тестировать публичный API. Используйте внутренний тест, когда нужно проверить неэкспортируемые помощники. Фикстуры кладите в папку с именем `testdata`. Эта папка не является пакетом Go для `go list`.

Тестовая функция имеет такую форму:

```go
func TestAdd(t *testing.T) {
	got := Add(1, 2)
	if got != 3 {
		t.Fatalf("Add(1, 2) = %d, want 3", got)
	}
}
```

Имя должно начинаться с `Test`. Следующая руна не должна быть строчной буквой. Единственный параметр — `*testing.T`.

Тест падает, когда код вызывает `t.Fail`, `t.Error`, `t.Errorf`, `t.Fatal` или `t.Fatalf`. `Fatal` останавливает текущую тестовую функцию. `Error` записывает неудачу и продолжает.

Табличный тест хранит случаи в срезе. Один цикл запускает каждый случай.

```go
func TestAbs(t *testing.T) {
	tests := []struct {
		name string
		in   int
		want int
	}{
		{name: "positive", in: 2, want: 2},
		{name: "negative", in: -2, want: 2},
		{name: "zero", in: 0, want: 0},
	}
	for _, tc := range tests {
		got := Abs(tc.in)
		if got != tc.want {
			t.Fatalf("%s: Abs(%d) = %d, want %d", tc.name, tc.in, got, tc.want)
		}
	}
}
```

Дайте каждому случаю `name`. Кладите в таблицу интересные случаи: ноль, пусто, ошибка и одно обычное значение. Не копируйте один блок `if` много раз.

## Подтесты и помощники

`t.Run` запускает подтест. У каждого подтеста есть имя. `go test` может запустить один подтест через `-run`.

```go
func TestAbs(t *testing.T) {
	tests := []struct {
		name string
		in   int
		want int
	}{
		{name: "negative", in: -2, want: 2},
	}
	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			got := Abs(tc.in)
			if got != tc.want {
				t.Fatalf("got %d, want %d", got, tc.want)
			}
		})
	}
}
```

Неудача в одном подтесте не останавливает остальные подтесты. `Fatal` в подтесте останавливает только этот подтест.

Запустите один подтест:

```text
go test -run TestAbs/negative
```

Функция-помощник вызывает `t.Helper()`. Тогда строки неудачи указывают на тест, не на помощник.

```go
func assertEq[T comparable](t *testing.T, got, want T) {
	t.Helper()
	if got != want {
		t.Fatalf("got %v, want %v", got, want)
	}
}
```

`t.Cleanup` регистрирует функцию, которая выполняется после окончания теста (или подтеста). Используйте `Cleanup` для временных файлов и для `cancel` context.

`t.Parallel` позволяет тесту выполняться параллельно с другими параллельными тестами. Вызывайте `t.Parallel` в начале теста или подтеста. Не делите записываемое состояние между параллельными тестами. Захватывайте строку таблицы в новой переменной на старых версиях Go. Go 1.22 даёт каждой итерации цикла свой `tc`.

`t.TempDir` создаёт временный каталог. Фреймворк тестов удаляет его после теста.

## Бенчмарки, примеры и фазз-тесты

Функция бенчмарка имеет форму `func BenchmarkXxx(b *testing.B)`. Тело выполняет работу `b.N` раз. Инструмент выбирает `N`.

```go
func BenchmarkAbs(b *testing.B) {
	for i := 0; i < b.N; i++ {
		Abs(-1)
	}
}
```

Запускайте бенчмарки через `go test -bench=. -benchmem`. Не используйте `t` в бенчмарке. Вызывайте `b.ResetTimer` после настройки, если настройка дорогая. Останавливайте таймер вокруг настройки через `b.StopTimer` и `b.StartTimer`, когда нужно.

Функция примера имеет форму `func ExampleXxx()`. Комментарий после функции может содержать `Output:`. `go test` проверяет, что печатный текст совпадает.

```go
func ExampleAbs() {
	fmt.Println(Abs(-2))
	// Output:
	// 2
}
```

Примеры появляются в `go doc` и на pkg.go.dev. Пишите примеры для публичного API.

Фазз-тест имеет форму `func FuzzXxx(f *testing.F)`. Добавляйте seed-значения через `f.Add`. Функция фаззинга получает `*testing.T` и типизированные входы.

```go
func FuzzAbs(f *testing.F) {
	f.Add(-2)
	f.Fuzz(func(t *testing.T, n int) {
		got := Abs(n)
		if got < 0 {
			t.Fatalf("Abs(%d) = %d", n, got)
		}
	})
}
```

Запускайте фаззинг через `go test -fuzz=FuzzAbs -fuzztime=5s`. Инструмент пишет неудачные входы в `testdata/fuzz`. Коммитьте эти файлы. Они становятся seed регрессии.

Не фаззьте функцию, которая говорит с сетью, без границы. Держите тело фаззинга быстрым и детерминированным.

## `httptest` и покрытие

Пакет `net/http/httptest` строит HTTP-сервер или recorder для тестов.

`httptest.NewRecorder` реализует `http.ResponseWriter` и хранит ответ.

```go
req := httptest.NewRequest(http.MethodGet, "/health", nil)
rec := httptest.NewRecorder()
Health(rec, req)
if rec.Code != http.StatusOK {
	t.Fatalf("status %d", rec.Code)
}
```

`httptest.NewServer` запускает локальный сервер. Закрывайте его через `server.Close` или `t.Cleanup(server.Close)`.

```go
srv := httptest.NewServer(http.HandlerFunc(Health))
defer srv.Close()
resp, err := http.Get(srv.URL + "/health")
```

Используйте `NewRequest` или `NewRequestWithContext` для входящего запроса. Задайте метод, путь и тело. С recorder вы не слушаете настоящий порт.

Покрытие измеряет, какие инструкции выполнил `go test`.

```text
go test -cover ./...
go test -coverprofile=cover.out ./...
go tool cover -html=cover.out
```

`-cover` печатает процент. `-coverprofile` пишет файл. `go tool cover -html` открывает отчёт. Стремитесь покрыть пути ошибок, не только счастливый путь.

Покрытие — не качество. Тест может выполнить строку и всё равно не проверить результат. Пишите утверждения.

Используйте `-coverpkg`, когда нужно покрытие пакетов, которые тест импортирует, но в которых не сидит. Начинайте с тестируемого пакета.

## Линтеры и `pprof`

`go vet` — первая статическая проверка. Запускайте `go vet ./...` на каждое изменение. Тема 1 вводит `vet`.

Линтер находит больше шаблонов стиля и ошибок. `staticcheck` и `golangci-lint` — частые инструменты. Устанавливайте их как отдельные команды. Запускайте их в CI. Не отключайте проверку без причины.

```text
go vet ./...
staticcheck ./...
```

`golangci-lint` запускает много линтеров в одном процессе. Фиксируйте версию в CI. Начинайте с набора по умолчанию. Добавляйте `errcheck`, `govet` и `staticcheck`, если настраиваете вручную.

`pprof` профилирует CPU, кучу, горутины и блокировки. Пакет `net/http/pprof` монтирует конечные точки на сервере. Пакет `runtime/pprof` пишет профили в файл.

```text
go test -cpuprofile=cpu.out -bench=Abs
go tool pprof cpu.out
```

В `pprof` команда `top` показывает самые горячие функции. `list FuncName` показывает строки. `web` открывает граф, когда установлен Graphviz.

Используйте профили, чтобы объяснить медленность, которую измерили. Не оптимизируйте по догадке. Сравнивайте два профиля после изменения.

Детектор гонок тоже инструмент. Запускайте `go test -race ./...` в CI. Тема 10 объясняет гонки.

`go generate` выполняет комментарии `//go:generate`. Он не выполняется во время `go build`. Коммитьте сгенерированные файлы или генерируйте их в CI. Задокументируйте команду.

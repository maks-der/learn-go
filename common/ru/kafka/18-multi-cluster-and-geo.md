# 18. Мультикластер и гео

## Описание

Один кластер Kafka живёт в одном домене отказа даже когда используете стойки (тема 15). Второй кластер в другом регионе или другом аккаунте — другая система. Вы копируете топики между кластерами, когда нужны аварийное восстановление, локальность геочтения или разделение команд.

Эта тема покрывает MirrorMaker 2, Cluster Linking (Confluent), active-passive против active-active, отображение офсетов и аварийное восстановление. Завершите эту тему после тем 5, 6, 9, 12 и 15. Каждый кластер использует KRaft. Не добавляйте ZooKeeper. Инструменты репликации говорят с каждым кластером через `bootstrap.servers`.

Используйте один термин для каждого понятия. Исходный кластер — кластер, в котором уже есть записи. Целевой кластер — кластер, который принимает копию. MirrorMaker 2 (MM2) — репликатор Apache на базе Connect. Cluster Linking — продукт Confluent, который связывает топики. Отображение офсетов отображает позицию группы консьюмеров с одного кластера на другой. Аварийное восстановление (DR) — план продолжить после падения кластера или региона.

## MirrorMaker 2

MirrorMaker 2 — репликатор Apache Kafka. Он работает как коннекторы Kafka Connect. Он копирует топики из исходного кластера в целевой кластер. Он может копировать офсеты групп консьюмеров (с отображением). Он может создавать топики на цели с шаблоном имени (часто префикс или суффикс).

MM2 использует source- и checkpoint-коннекторы. Воркерам нужен сетевой доступ к обоим кластерам. Настройте два значения `bootstrap.servers`. Оба кластера могут быть KRaft. MM2 не нужен ZooKeeper.

Копия асинхронна. Цель отстаёт от источника. Этот лаг — ваша задержка репликации. Измеряйте её.

MM2 не транзакция, которая охватывает два кластера. Exactly-once внутри одного кластера (тема 7) не делает два кластера одним атомарным журналом.

Не запускайте два неконтролируемых потока MM2, которые пишут в один целевой топик из двух источников без дизайна. Получите дубликаты или конфликты.

Идентичность и ACL (тема 17) применяются на обоих кластерах. Принципалу MM2 нужно чтение на источнике и запись на цели.

Типичный шаблон имени: исходный топик `orders.placed` становится `sourceCluster.orders.placed` на цели. Меняйте шаблон только с планом. Консьюмеры должны использовать имя цели.

```text
# Концептуальные ключи воркера / коннектора (имена следуют текущим документам MM2)
source.cluster.bootstrap.servers=...
target.cluster.bootstrap.servers=...
topics=orders.placed
```

## Cluster Linking (Confluent)

**Cluster Linking** — функция Confluent Platform и Confluent Cloud. Она создаёт связь от исходного кластера к кластеру назначения. **Mirror-топик** на назначении следует исходному топику.

Cluster Linking не часть tarball только Apache Kafka. Вы используете его, когда запускаете продукты Confluent, которые его включают. Этот справочник считает его точкой сравнения.

Отличия, которые документирует Confluent (высокий уровень; подтвердите на текущей странице продукта):

- Назначение может сохранить то же имя топика (без префикса) во многих установках.
- Сохранение офсетов может быть ближе к источнику, чем наивная копия consume-produce.
- Связь — первоклассный объект кластера, не только задача Connect, которую вы написали.

У вас всё равно два кластера. У вас всё равно асинхронная копия и лаг. Вам всё равно нужны ACL и TLS с обеих сторон. Назначение и источник могут быть KRaft.

Не предполагайте, что Cluster Linking существует на Amazon MSK или на простой установке Apache. Если есть только Apache Kafka, используйте MM2 или другой репликатор, который поддерживаете.

Cluster Linking не снимает нужду в runbook DR (поздний раздел). Связь может остановиться. Вы должны знать, как повысить mirror или как сделать failover.

## Active-passive против active-active

**Active-passive** означает, что один кластер принимает все produce для топика (активный). Другой кластер — копия (пассивный). При катастрофе вы переключаете клиентов на пассивный кластер после шага promote. Есть один писатель. Конфликт редок.

**Active-active** означает, что два (или больше) кластера принимают produce на «один» бизнес-топик одновременно. Каждый кластер реплицирует в другой. Один ключ может измениться в двух местах. Вы получаете конфликты. Нужно спроектировать правила слияния или партиционировать записи по региону (пользователи региона A пишут только в кластер A).

Active-active — не «вдвое доступность бесплатно». Это проблема дизайна данных. Last-write-wins по метке времени может потерять запись. Event sourcing (тема 19) может помочь, если каждая запись — событие с уникальным идентификатором, но порядок на ключ всё равно нужен.

Большинство дизайнов DR начинают как active-passive. Active-active — для записей с низкой задержкой в двух регионах, когда бизнес может изолировать ключи или слить.

Консьюмеры в пассивном регионе могут читать локальную копию, если принимаете лаг. Это шаблон read-local, write-home.

Не запускайте два цикла MM2 на одном топике в обоих направлениях без фильтра (например исключить реплицированный префикс), иначе создадите цикл.

Оба кластера используют KRaft. Failover — смена bootstrap клиента и ACL, не миграция ZooKeeper.

## Отображение офсетов

Офсет группы консьюмеров — позиция в **конкретном кластере** (темы 5 и 6). Офсет 1000 на кластере A — не та же запись, что офсет 1000 на кластере B. Целевой журнал может иметь другое число партиций, другие начальные офсеты и дополнительные контрольные записи.

**Отображение офсетов** отображает зафиксированный офсет группы на источнике на офсет на цели, чтобы консьюмер, который делает failover, не пропустил большой разрыв и не повторил весь топик.

Checkpoint-коннекторы MM2 пишут отображённые офсеты в топики на цели. Затем вы применяете эти офсеты к группе на цели (процедура зависит от версии). У Cluster Linking свои функции офсетов. Читайте продукт, который используете.

Без отображения обычная ошибка — стартовать группу на цели с latest (потерять данные) или с earliest (переобработать всё).

Отображение — на партицию. Если у цели другое число партиций, отображение сложнее или невозможно для простого номера офсета. Предпочитайте одно число партиций и один партиционер ключа на обоих кластерах.

Компактируемые топики и усечённые журналы усложняют отображение. Тестируйте failover группы в лаборатории.

KRaft не хранит офсеты вашей прикладной группы в особой геотаблице. `__consumer_offsets` — на кластер.

## Аварийное восстановление

**Аварийное восстановление** — задокументированный путь, когда падает кластер или регион. Вы определяете:

- **RPO** (recovery point objective): сколько недавних данных можно потерять (связано с лагом репликации).
- **RTO** (recovery time objective): как долго до того, как клиенты снова пишут и читают.

Мультикластерная копия необходима, но недостаточна. Также нужны смена DNS или bootstrap, ACL на цели, доступность schema registry (тема 11), поведение `application.id` Connect и Streams и лицо, принимающее решение.

Шаги failover (active-passive, только форма):

1. Остановить продюсеров к упавшему источнику (или подтвердить, что они падают).
2. Подтвердить лаг цели и что принимаете как RPO.
3. Повысить цель (promote MM2 или Cluster Linking или сделать её писателем).
4. Применить отображение офсетов для групп, которые должны продолжить.
5. Направить клиентов на bootstrap цели. Используйте TLS и SASL для этого кластера (тема 17).
6. Когда старый регион вернётся, не запускайте двух активных без плана failback.

Failback — второй проект. Нужно скопировать или догнать старый кластер и переключить снова.

Тестируйте DR. Непротестированный runbook падает. Используйте KRaft с обеих сторон, чтобы в runbook не было шага восстановления ZooKeeper.

Rack awareness одного кластера (тема 15) — не DR для потери региона.

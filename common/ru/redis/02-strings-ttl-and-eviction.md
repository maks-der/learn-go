# 2. Строки, TTL и вытеснение

## Описание

Строковый тип — базовое значение Redis. Строка — бинарно-безопасный блоб. Можно хранить текст, JSON, число или сырые байты. Эта тема показывает команды записи и чтения, опции `SET`, целочисленные счётчики, команды срока жизни, политики вытеснения и `maxmemory`. Вы узнаете, что происходит, когда экземпляр не может сохранить новую запись.

Завершите эту тему до изучения хешей, списков и множеств.

Используйте один термин для каждого понятия. Строковый ключ держит один блоб. `SET` пишет блоб. `GET` читает блоб. `INCR` считает блоб целым числом в базе 10. Срок жизни — таймер на ключе. TTL — оставшееся время. Вытеснение — удаление при нехватке памяти. `maxmemory` — лимит памяти. Политика — правило выбора ключей для вытеснения. Не смешивайте `expired_keys` и `evicted_keys`.

## `SET`, `GET`, `MSET`, `MGET`, опции `SET` (`EX`, `NX`, `XX`)

`SET key value` пишет строку. Redis создаёт ключ или заменяет старое значение. Тип становится строкой. Ответ — `OK`.

`GET key` читает строку. Отсутствующий ключ возвращает null. Ключ другого типа возвращает `WRONGTYPE`.

```text
SET user:1:name Ada
GET user:1:name
```

`MSET` пишет много строковых ключей одной командой. Все пары применяются как одна атомарная команда. Другие клиенты не видят частичный `MSET`.

```text
MSET user:1:name Ada user:1:city London
```

`MGET` читает много строковых ключей одной командой. Ответ — массив. Каждый слот — значение или null. Порядок совпадает с порядком аргументов.

```text
MGET user:1:name user:1:city user:1:missing
```

Используйте `MGET` и `MSET`, чтобы сократить круги. Ключи должны существовать как строки или отсутствовать. Один неверный тип в `MGET` может провалить команду.

Максимальный размер строки — 512 MB. Не храните большие файлы в Redis. Держите значения маленькими. Несколько килобайт — частый размер кэша. Замеряйте `MEMORY USAGE`, если не уверены.

`GET` сам по себе не меняет TTL. `SET` без опций TTL снимает любой старый TTL с этого ключа.

`SET key value NX` пишет только когда ключа нет. Ответ — `OK` при успехе или null, когда ключ есть. `SETNX` — та же идея.

`SET key value XX` пишет только когда ключ уже есть. Ответ — `OK` или null.

`SET key value EX seconds` задаёт значение и TTL в секундах. `PX` использует миллисекунды. `EXAT` и `PXAT` используют время Unix, если ваша версия их поддерживает.

Опции можно комбинировать:

```text
SET lock:order:9 worker1 NX EX 30
```

Эта команда пишет `worker1` только если `lock:order:9` отсутствует, и истекает через 30 секунд.

`GETSET key value` возвращает старую строку и затем пишет новую. Redis 6.2 и новее также позволяют `SET key value GET`, что можно комбинировать с `NX` или `XX`. На новых серверах предпочитайте `SET ... GET`.

`KEEPTTL` сохраняет текущий TTL, когда вы заменяете значение. Обычный `SET` снял бы TTL.

Читайте страницу команды `SET` для вашей версии. Список опций рос со временем. Не угадывайте. Проверьте `redis_version`.

## `INCR` и связанные команды

`INCR key` читает строку как целое в базе 10, добавляет `1` и пишет новое целое. Ответ — новое значение. Если ключа нет, Redis считает старое значение `0`.

`DECR` вычитает `1`. `INCRBY key n` добавляет целое `n`. `n` может быть отрицательным. `DECRBY` вычитает `n`. `INCRBYFLOAT` добавляет число с плавающей точкой.

Значение должно выглядеть как целое (или как float для `INCRBYFLOAT`). Строка вроде `hello` вызывает ошибку. Хеш-ключ вызывает `WRONGTYPE`.

```text
INCR views:post:10
INCR views:post:10
INCRBY views:post:10 5
```

Каждая команда атомарна. Два клиента могут сделать `INCR` одного ключа. Redis не теряет счёт из-за чередования двух одиночных команд.

`INCR` не задаёт TTL. Если нужен счётчик со сбросом, задайте TTL на первом инкременте (Lua в теме 6 может сделать это за один шаг). Частый шаблон — ключ на окно времени: `views:post:10:2026-09-13`.

У целых есть пределы. Redis использует 64-битные знаковые целые для `INCR`. Переполнение возвращает ошибку.

Не используйте `GET`, прибавление единицы в клиенте и `SET`. Этот путь не атомарный. Два клиента могут записать одно и то же число. Используйте `INCR`.

`APPEND key value` добавляет байты в конец строки. Если ключа нет, `APPEND` создаёт его. `STRLEN key` возвращает длину в байтах. `GETRANGE` и `SETRANGE` правят подстроку. Эти команды полезны для записей фиксированной ширины. Они плохо подходят для JSON, который вы разбираете в клиенте.

## `EXPIRE`, `TTL`, `EXPIREAT`

`EXPIRE key seconds` задаёт время жизни в целых секундах. Redis удаляет ключ, когда время кончается. Ответ — `1`, если Redis задал срок, или `0`, если ключа нет.

`PEXPIRE key milliseconds` использует миллисекунды. Используйте `PEXPIRE`, когда шаг в одну секунду слишком грубый.

`TTL key` возвращает оставшиеся секунды. Ответ:

- неотрицательное целое — секунды осталось
- `-1` — ключ есть и срока нет
- `-2` — ключа нет (или он уже истёк)

`PTTL key` возвращает оставшиеся миллисекунды или те же правила `-1` и `-2`.

```text
SET session:abc data
EXPIRE session:abc 300
TTL session:abc
```

`PERSIST key` снимает срок и сохраняет значение. `TTL` затем возвращает `-1`.

`EXPIRE` на отсутствующем ключе ничего полезного не делает (`0`). Сначала задайте значение или используйте `SET key value EX seconds` одной командой.

`EXPIREAT key unix-seconds` задаёт срок на абсолютное время Unix в секундах. Redis удаляет ключ, когда часы сервера достигают этого времени. `PEXPIREAT` использует миллисекунды с эпохи Unix.

Используйте `EXPIREAT`, когда много ключей должны умереть в одно настенное время (конец дня, конец распродажи). Используйте `EXPIRE`, когда нужно «жить 15 минут от сейчас».

Аргумент — время Unix в UTC, не локальная строка даты. Считайте метку времени в приложении.

Если метка в прошлом, Redis удаляет ключ (или команда ведёт себя как немедленный срок). Проверьте точный ответ на вашей версии.

`SET key value EXAT timestamp` — форма одной команды на версиях, которые поддерживают `EXAT`. Предпочитайте одну команду, когда создаёте ключ и дедлайн вместе.

`TTL` после `EXPIREAT` всё равно показывает оставшиеся секунды. `TTL` относительный. `EXPIREAT` абсолютный.

Redis 7 добавляет опции `EXPIRE` вроде `NX`, `XX`, `GT` и `LT` на некоторых версиях. Эти опции задают срок только когда условие выполняется. Читайте страницу команды для вашей версии.

Срок использует время сервера. Большой скачок системных часов может изменить момент истечения ключей. Не полагайтесь на миллисекундную точность для юридически критичных дедлайнов. Используйте срок для кэшей, сессий и временных удержаний.

Чтение истёкшего ключа выглядит как отсутствующий ключ. Приложение должно обрабатывать null.

Ключ без срока живёт, пока вы его не удалите или пока вытеснение его не снимет. Вытеснение отличается от TTL. Счётчики темы `expired_keys` и `evicted_keys` в `INFO stats` — не одно и то же.

Активное истечение — фоновый цикл. Redis не ждёт чтения, чтобы удалить каждый истёкший ключ. Redis также проверяет срок при доступе.

## Политики вытеснения и `maxmemory`

Когда задан `maxmemory` и Redis нужна дополнительная ОЗУ для записи, Redis применяет политику вытеснения. Политика — значение `CONFIG`: `maxmemory-policy`.

Частые политики:

- `noeviction` — Redis не вытесняет. Записи, которым нужна память, возвращают ошибку. Чтения всё ещё работают.
- `allkeys-lru` — Redis вытесняет любой ключ, сначала давно не использованный (приблизительный LRU).
- `volatile-lru` — Redis вытесняет только ключи со сроком, LRU среди этих ключей.
- `allkeys-lfu` — Redis вытесняет любой ключ, сначала редко используемый (приблизительный LFU).
- `volatile-lfu` — LFU среди ключей со сроком.
- `allkeys-random` — Redis вытесняет случайный ключ.
- `volatile-random` — случайный среди ключей со сроком.
- `volatile-ttl` — среди ключей со сроком сначала вытесняет ключ с самым коротким TTL.

LRU значит «давно не использованный». Ключ, который давно никто не трогал, лучший кандидат на вытеснение, чем горячий ключ. Redis использует приближение, а не идеальный список LRU для каждого ключа.

LFU значит «редко используемый». Ключ с малым числом чтений лучший кандидат, чем ключ с многими чтениями.

Политики `volatile-*` ничего полезного не делают, если ни у одного ключа нет срока и память полна. Записи тогда падают как при `noeviction`. Если выбираете `volatile-lru`, дайте кэш-ключам TTL.

`allkeys-lru` — частая политика кэша. Redis может вытеснить ключи без TTL. Долговечные ключи без TTL могут исчезнуть. Не храните данные, которые обязаны остаться, на экземпляре с `allkeys-*`, если не принимаете потерю.

`maxmemory` — верхняя граница памяти, которую Redis должен использовать. Значение в байтах. `CONFIG GET maxmemory` показывает его. `0` на 64-битной сборке значит «без лимита». Redis тогда растёт, пока ОС не откажет в ОЗУ.

Задавайте `maxmemory` в продакшене. Выберите значение ниже ОЗУ хоста, чтобы ОС, перезапись AOF и copy-on-write `BGSAVE` имели запас. Частый шаблон — 50–70 процентов ОЗУ для хоста, который ещё и персистирует.

```text
CONFIG SET maxmemory 64mb
```

`CONFIG SET` меняет работающий экземпляр. Запишите то же значение в `redis.conf` (`maxmemory 64mb`), чтобы перезапуск сохранил лимит.

`INFO memory` показывает `used_memory`, `used_memory_rss` и `maxmemory`. `used_memory` — взгляд аллокатора на данные. `used_memory_rss` — размер процесса, который видит ОС. Они отличаются.

Реплики и клиенты тоже используют память. Буферы могут расти. `maxmemory` — не только «сумма размеров ключей».

У реплики может быть другой `maxmemory`, чем у основного. Если вытеснять на реплике, реплика может разойтись. Многие команды настраивают реплики так, чтобы они не вытесняли, или оставляют запас ОЗУ.

Прочитайте `CONFIG GET maxmemory-policy`. Смените лабораторный экземпляр через `CONFIG SET maxmemory-policy allkeys-lru`. Сохраните настройку в `redis.conf` для реального сервиса.

TTL — таймер на ключ. Вытеснение — механизм давления памяти. Кэш часто использует оба: TTL, чтобы данные не устаревали навсегда, и политику вытеснения, чтобы Redis мог сбрасывать ключи, когда ОЗУ полна.

## Что происходит, когда Redis полон

«Полон» значит, что `used_memory` достиг `maxmemory` и команде нужна дополнительная память.

Если политика — `noeviction`, Redis возвращает ошибку командам записи, которые увеличивают память. Типичный текст включает `OOM command not allowed when used memory > 'maxmemory'`. Команды чтения всё ещё выполняются. `DEL` может освободить память.

Если политика вытесняет ключи, Redis удаляет один или несколько ключей, затем повторяет запись. Эти ключи вы теряете. Запись может пройти. `INFO stats` увеличивает `evicted_keys`.

Если Redis не может вытеснить достаточно (например `volatile-lru` и нет volatile-ключей), запись падает с ошибкой OOM.

Приложение должно обрабатывать ошибки записи. Приложение cache-aside может пропустить кэш и использовать основную базу. Приложение, которое считает Redis единственным хранилищем, может провалить запрос пользователя. Проектируйте этот путь сознательно.

Клиенты, которые конвейерят много записей, могут увидеть вспышку ошибок. Монитор должен тревожить по скорости `evicted_keys` и по ошибкам OOM в журналах.

Redis не останавливается навсегда, чтобы уплотнить память. Фрагментация может держать RSS высоким после удалений. `MEMORY PURGE` или перезапуск могут помочь в некоторых настройках аллокатора. Не полагайтесь на это в приложении.

Не ждите убийцу OOM операционной системы. Задайте `maxmemory` и политику. Убийца ОС контролировать труднее, чем ошибка Redis.

# 14. Производительность

## Описание

Эта тема показывает, как измерять и улучшать скорость MongoDB. Вы читаете `explain`. Сравниваете `COLLSCAN` и `IXSCAN`. Держите рабочий набор в ОЗУ. Режете нагрузку проекцией. Используете покрытые запросы. Проектируете под нагрузку с тяжёлой записью или тяжёлым чтением. Используете профайлер и Atlas Performance Advisor. Сначала завершите индексы, агрегацию и запросы.

Используйте один термин для каждого понятия. **Сканирование коллекции** (`COLLSCAN`) читает каждый документ. **Сканирование индекса** (`IXSCAN`) читает индекс. **Рабочий набор** — данные и индексы, которые приложение часто использует. **Покрытый запрос** — запрос, на который сервер отвечает только из индекса.

Не настраивайте по догадке. Измеряйте через `explain` и реальную нагрузку.

## `explain("executionStats")`

`explain` показывает, как сервер планирует выполнить find или агрегацию. Режим `executionStats` выполняет план и сообщает счета и время.

```javascript
db.orders.find({ userId: "u1" }).explain("executionStats")
```

Полезные поля:

- `queryPlanner.winningPlan` — выбранный план
- `executionStats.nReturned` — возвращённые документы
- `executionStats.totalDocsExamined` — прочитанные документы
- `executionStats.totalKeysExamined` — прочитанные ключи индекса
- `executionStats.executionTimeMillis` — время этого запуска

Режимы:

- `queryPlanner` — только план, без счетов выполнения
- `executionStats` — план плюс счета этого выполнения
- `allPlansExecution` — также показывает отвергнутые планы

Используйте `executionStats`, когда учитесь. Запуск делает реальную работу. Не запускайте тяжёлый `explain("executionStats")` на огромной коллекции в продакшене без осторожности.

Хороший знак: `nReturned` близко к `totalDocsExamined` для избирательного фильтра. Плохой знак: просмотрели 1 000 000 документов, чтобы вернуть 10.

Агрегация использует `db.orders.explain("executionStats").aggregate([ ... ])` или помощник, который документирует ваша версия.

`explain` — не нагрузочный тест. Один вызов на тёплом кэше — не ваш пик. Используйте его, чтобы увидеть форму плана.

Читайте страницу explain своей основной версии. Имена полей могут меняться.

## COLLSCAN vs IXSCAN

`COLLSCAN` значит, что сервер читает коллекцию. Он не использует индекс для этого фильтра (или выбирает не использовать).

`IXSCAN` значит, что сервер читает индекс. Стадия **`FETCH`** затем загружает полные документы, когда индекс не держит все нужные поля.

Типичный победивший план хорошего find:

```text
IXSCAN → FETCH → PROJECTION (optional)
```

Типичный плохой план:

```text
COLLSCAN
```

`COLLSCAN` приемлем на крошечной коллекции. `COLLSCAN` на миллионах документов — проблема для пути API.

Существующего индекса недостаточно. Фильтр должен совпадать с индексом (включая правило префикса составного индекса из темы индексов). Функция на поле, плохой `$or` или ведущий `$not` могут заблокировать индекс.

Сортировка может использовать индекс или добавить блокирующий `SORT`. Большой `SORT`, который не помещается в память, падает, пока не разрешите использование диска (чаще в агрегации).

`explain` показывает `stage: "COLLSCAN"` или `stage: "IXSCAN"` в победившем плане. Начните оттуда.

Не добавляйте десять индексов, чтобы убрать один `COLLSCAN`, без проверки цены записи. Сначала чините форму запроса.

## Рабочий набор в ОЗУ

**Рабочий набор** — документы и страницы индекса, которые приложение часто читает и пишет. MongoDB (WiredTiger) держит столько, сколько может, в **кэше WiredTiger**. Операционная система тоже кэширует страницы файлов.

Если рабочий набор помещается в ОЗУ, большинство чтений избегает медленного диска. Если рабочий набор больше ОЗУ, сервер подкачивает данные туда-сюда. Задержка растёт. Растут **ошибки страниц** и вытеснение кэша.

Поместить рабочий набор:

- Держите документы маленькими
- Индексируйте только то, что запрашиваете
- Архивируйте холодные данные
- Добавьте ОЗУ или шарды, когда горячие данные действительно велики

У размера кэша есть значение по умолчанию на самоуправляемом `mongod` (большая доля ОЗУ с зарезервированным объёмом). Atlas задаёт кэш от тарифа кластера. Не ставьте кэш на 100% ОЗУ. Операционной системе и соединениям нужна память.

Рабочий набор — не то же самое, что полный размер данных. Коллекция 2 TB может иметь горячий набор 20 GB.

Измеряйте:

- Задержку под нагрузкой
- Доли dirty и used кэша WiredTiger
- Ошибки страниц (заметнее на некоторых ОС)
- Графики кэша и IOPS диска Atlas

Не покупайте шард только потому что полный диск велик. Сначала измерьте горячий набор.

## Проекция, чтобы резать нагрузку

**Проекция** выбирает поля в find или в `$project`. Меньший документ по сети быстрее. Приложение также разбирает меньше данных.

```javascript
db.orders.find({ userId: "u1" }, { total: 1, status: 1 })
```

Включайте поля, которые нужны вызывающему. Исключайте большие неиспользуемые поля (например большой встроенный журнал).

Проекция не всегда избегает `FETCH`. Сервер всё равно может загрузить полный документ из хранилища, затем отбросить поля. Проекция всё равно помогает сети и клиенту.

Проекция плюс покрывающий индекс может избежать `FETCH`. Это следующий раздел.

Не возвращайте полный документ в API списка «на потом». Потом не наступает. Добавьте конечную точку деталей.

`find({}, {})` без лимита всё равно неограничен. Проекция не заменяет `limit`.

`$project` и `$set` агрегации тоже режут или добавляют поля. Ставьте `$match` первым. Проецируйте рано, когда отбрасываете большие поля до `$group` или `$lookup`.

## Покрытые запросы

**Покрытый запрос** использует индекс, который содержит каждое поле фильтра, сортировки и проекции. Сервер не делает `FETCH` полного документа.

`explain` показывает `IXSCAN` и затем проекцию или счёт, без `FETCH`. `totalDocsExamined` равен `0` во многих покрытых планах.

Требования (типичные):

- Все поля фильтра в индексе
- Все проецируемые поля в индексе
- Проекция исключает поля, которых нет в индексе
- Поля вне индекса не нужны

Пример:

```javascript
db.orders.createIndex({ userId: 1, status: 1 })
db.orders.find({ userId: "u1" }, { _id: 0, userId: 1, status: 1 })
```

`_id` есть в документе и включён по умолчанию. Если `_id` нет в индексе, исключите `_id` в проекции или добавьте `_id` в индекс.

Покрытые запросы помогают горячим путям чтения с малым набором полей. Они не помогают, когда нужен весь документ.

Мультиключевые индексы (массивы) часто не могут покрыть так, как ожидаете. Читайте текущие лимиты.

Не добавляйте огромный составной индекс только чтобы покрыть редкий запрос.

## Шаблоны тяжёлой записи и тяжёлого чтения

Нагрузка с **тяжёлой записью** вставляет или обновляет много документов. Каждая запись должна обновлять каждый индекс коллекции. Лишние индексы замедляют записи. Большие документы замедляют записи. Транзакции и высокий write concern добавляют задержку.

Привычки тяжёлой записи:

- Мало индексов (только те, что нужны чтениям)
- Ограниченные документы
- Пакетные записи (`insertMany`, `bulkWrite`) вместо одного обмена на документ
- Избегать read-modify-write на клиенте, когда хватает `$inc` или `$set`
- Majority write concern только там, где нужно

Нагрузка с **тяжёлым чтением** запускает много find или агрегаций. Важнее индексы, проекция, покрытые запросы и рабочий набор в ОЗУ. Чтения secondary могут помочь, если устаревшие данные приемлемы.

Привычки тяжёлого чтения:

- Составные индексы, которые совпадают с фильтрами и сортировками
- Проекция на путях списка
- Агрегация, которая рано делает `$match`
- Кэш только если измерили нужду (см. тему поиска)

Многие системы смешанные. Оформление чувствительно к записи. Просмотр каталога — тяжёлое чтение. Используйте разные коллекции или разные индексы на путь.

Не копируйте реляционную привычку «индексировать каждый внешний ключ». Не копируйте привычку «ноль индексов».

Измеряйте через `explain`, профайлер и графики Atlas. Затем меняйте одно.

## Профайлер и Atlas Performance Advisor

**Профайлер базы** записывает медленные операции в `system.profile`. Задают уровень и порог slow-ms.

```javascript
db.setProfilingLevel(1, { slowms: 100 })
```

Уровень `0` выключен. Уровень `1` записывает медленные операции. Уровень `2` записывает все операции (тяжело). Не оставляйте уровень `2` на занятой производственной базе.

Читать записи:

```javascript
db.system.profile.find().sort({ ts: -1 }).limit(5)
```

Каждая запись показывает команду, миллисекунды и краткий план. Используйте, чтобы найти `COLLSCAN` и долгие блокировки.

**Atlas Performance Advisor** читает медленные логи и предлагает индексы. Это помощник. Вы всё равно проверяете через `explain`. Предложенный индекс может быть дубликатом или вредить записям.

Atlas также показывает:

- Логи медленных запросов
- Производительность в реальном времени
- Query Insights на некоторых тарифах

`serverStatus` и `currentOp` помогают на самоуправляемых серверах. `db.currentOp()` показывает операции, которые идут сейчас.

Логируйте медленные операции даже когда профайлер выключен (`operationProfiling.slowOpThresholdMs` или значение Atlas по умолчанию). Лога многим командам достаточно.

Не добавляйте каждый индекс Advisor в один день. Добавьте один. Измерьте. Оставьте или удалите.

### Вопросы

#### Простые практические задания

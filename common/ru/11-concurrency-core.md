# 11. Конкурентность (ядро)

## Описание

Go запускает много функций одновременно. `goroutine` — это функция, которую планирует среда выполнения Go. `channel` передаёт значения между `goroutine`. Пакет `sync` защищает общие данные, когда `channel` — не простой выбор.

Эта тема учит базовым инструментам. Завершите эту тему до серверов, воркеров и других конкурентных программ. Тема 12 подробнее разбирает `context.Context`. Тема 19 разбирает продвинутую конкурентность.

Для каждого понятия используйте одно слово. `goroutine` — не поток операционной системы. Отправка в `channel` — не вызов функции. Гонка данных — не то же самое, что взаимная блокировка.

## Горутины: `go f()`

Ключевое слово `go` запускает `goroutine`. Новая `goroutine` выполняет `f`, а текущая `goroutine` продолжает работу.

```go
go f()
go f(a, b)
go func() {
    doWork()
}()
```

Аргументы `f` вычисляются в текущей `goroutine`. Вызов `f` выполняется в новой `goroutine`.

Процесс начинается с одной `goroutine`. Эта `goroutine` выполняет `main`. Когда `main` возвращает управление, процесс завершается. Остальные `goroutine` в этот момент останавливаются. Нужно ждать, если эти `goroutine` должны закончить работу. Для ожидания используйте `sync.WaitGroup` или `channel`.

У `goroutine` в начале маленький стек. Стек растёт и сжимается по мере нужды функции в памяти. Можно запустить много `goroutine`. Нужно ограничивать число, когда каждая `goroutine` держит ресурс (файл, соединение или большой буфер).

Начиная с Go 1.22, у каждой итерации цикла `for` свои переменные цикла. Этот код безопасен в Go 1.22 и новее:

```go
for _, item := range items {
    go func() {
        process(item)
    }()
}
```

До Go 1.22 каждая `goroutine` могла прочитать последний `item`. Если нужна поддержка старых компиляторов, скопируйте переменную внутри цикла: `item := item`.

Не запускайте `goroutine` и не игнорируйте её ошибку. Верните ошибку через `channel`, или соберите её через `WaitGroup` и мьютекс, или используйте помощник вроде `errgroup` в более поздней теме.

## Планировщик Go (обзор: M:N, `GOMAXPROCS`)

Планировщик Go выполняет много `goroutine` на меньшем числе потоков операционной системы. Это модель планировщика M:N. M `goroutine` выполняются на N потоках.

Простая схема использует три имени:

- G — это `goroutine`.
- M — это поток операционной системы.
- P — это логический процессор. P хранит очередь запуска и другое состояние планировщика.

`GOMAXPROCS` — максимальное число P, которые могут одновременно выполнять код Go. Начиная с Go 1.5, значение по умолчанию — число логических CPU. Читайте значение через `runtime.GOMAXPROCS(0)`. Задавайте значение через `runtime.GOMAXPROCS(n)` или через переменную окружения `GOMAXPROCS`.

`goroutine`, которая выполняет блокирующий системный вызов, может отсоединиться от своего P. Планировщик может создать или повторно использовать другой поток, чтобы остальные `goroutine` продолжили работу. `goroutine`, которая ждёт на `channel` или мьютексе, не занимает поток операционной системы, пока ждёт.

Планировщик кооперативный и вытесняющий. Длинный цикл без вызовов функций всё равно может быть вытеснен в современном Go. Не вставляйте ручные вызовы уступки для обычного кода.

Не считайте `GOMAXPROCS` ручкой пропускной способности, которую крутят без измерения. Для работы, ограниченной CPU, обычный старт — значение около числа логических CPU. Для работы, ограниченной вводом-выводом, много `goroutine` могут ждать, пока работают немногие потоки.

Этот раздел остаётся на обзорном уровне. Тема 20 глубже разбирает модель G, M и P.

## Каналы: отправка, приём, закрытие

`channel` — типизированный канал передачи. Создайте `channel` через `make`.

```go
ch := make(chan int)        // unbuffered
ch := make(chan int, 4)     // buffered, capacity 4
```

Отправьте значение через `ch <- v`. Примите значение через `v := <-ch`. Оператор приёма может стоять справа от короткого объявления или присваивания.

Форма comma-ok сообщает, открыт ли `channel`:

```go
v, ok := <-ch
```

`ok` равен `false`, когда `ch` закрыт и пуст. В этом случае `v` — нулевое значение типа элемента.

`close(ch)` помечает `channel` как закрытый. Приёмники забирают оставшиеся буферизованные значения, затем видят закрытое состояние. После этого каждый приём возвращает нулевое значение.

Правила `channel`:

- Отправка в закрытый `channel` вызывает `panic`.
- Закрытие уже закрытого `channel` вызывает `panic`.
- Закрытие `nil` `channel` вызывает `panic`.
- Отправка в `nil` `channel` блокируется навсегда.
- Приём из `nil` `channel` блокируется навсегда.

Отправитель закрывает `channel`. Приёмник не закрывает `channel`, когда отправителей больше одного. Не закрывайте `channel`, если ни один код не использует `range` или comma-ok, чтобы обнаружить конец.

Значение `channel` — ссылка. Копия переменной `channel` всё равно ссылается на тот же `channel`. Нулевое значение типа `channel` — `nil`.

## Небуферизованные и буферизованные каналы

У небуферизованного `channel` ёмкость 0. Отправка в небуферизованный `channel` ждёт, пока другая `goroutine` примет. Приём ждёт, пока другая `goroutine` отправит. Две `goroutine` встречаются. Эта встреча — рукопожатие. Значение передаётся, и обе стороны продолжают работу.

У буферизованного `channel` ёмкость `n`, где `n` больше 0. Отправка кладёт значение в буфер и продолжает работу, пока буфер не полон. Приём забирает значение из буфера и продолжает работу, пока буфер не пуст. Отправка блокируется, когда буфер полон. Приём блокируется, когда буфер пуст.

```go
unbuf := make(chan int)     // capacity 0
buf := make(chan int, 8)    // capacity 8
```

`cap(ch)` — ёмкость. `len(ch)` — число значений в буфере в этот момент. Не используйте `len`, чтобы решить, что отправка или приём безопасны. Другая `goroutine` может изменить буфер до вашей следующей операции.

Используйте небуферизованный `channel`, когда отправитель должен ждать, пока приёмник заберёт значение. Используйте небольшой буфер, когда нужно развязать всплески работы. Не берите большой буфер наугад ради скорости. Большой буфер может скрыть медленного потребителя. Большой буфер может занять много памяти.

Буфер не заменяет ожидание завершения. Если `main` возвращает управление, буферизованные значения, которые никто не принял, теряются.

## `select` и тайм-ауты

Оператор `select` ждёт набор операций с `channel`. Каждый `case` — отправка или приём. `select` выполняет один готовый `case`. Если готовы несколько `case`, `select` выбирает один случайно. Если ни один `case` не готов, `select` блокируется, пока один `case` не станет готов.

```go
select {
case v := <-in:
    handle(v)
case out <- v:
    // sent
case <-ctx.Done():
    return ctx.Err()
}
```

Ветка `default` выполняется, когда ни один другой `case` не готов. Используйте `default` для неблокирующей попытки. Не добавляйте `default`, когда хотите ждать.

Тайм-аут — это приём из `channel`, который становится готов через заданную длительность:

```go
select {
case v := <-ch:
    use(v)
case <-time.After(2 * time.Second):
    return errTimeout
}
```

`time.After` возвращает `channel`. Среда выполнения отправляет текущее время в этот `channel` после длительности. Если `select` сначала берёт другой `case`, таймер всё равно работает, пока не сработает. Это приемлемо для редких тайм-аутов. Для плотного цикла используйте `time.NewTimer`, примите или остановите таймер и сбросьте его. Таймер, который никогда не останавливают, может держать `goroutine` и `channel` живыми до конца длительности.

`time.Tick` в цикле `select` — частая утечка. Предпочитайте `time.NewTicker` и вызывайте `Stop`, когда цикл заканчивается.

`select` с одним `case` допустим. `select` без веток блокируется навсегда.

## Обход каналов через `range`

`for` `range` по `channel` принимает значения, пока `channel` не закрыт и буфер не пуст.

```go
for v := range ch {
    handle(v)
}
```

Цикл заканчивается только после `close(ch)` и после приёма всех буферизованных значений. Если никто не закрывает `channel`, цикл ждёт вечно. Это ожидание — утечка `goroutine`, когда остальная программа продолжает работу.

Форма `range` не даёт флаг comma-ok. Этот флаг не нужен, когда нужны только значения.

Можно принимать в обычном цикле `for`, когда нужен `ok` или когда нужен `select` для отмены:

```go
for {
    select {
    case v, ok := <-ch:
        if !ok {
            return
        }
        handle(v)
    case <-ctx.Done():
        return
    }
}
```

Не закрывайте `channel` в цикле `range`, который из него принимает. Отправитель закрывает `channel`.

`range` по `nil` `channel` блокируется навсегда. `range` по закрытому пустому `channel` не входит в тело цикла.

Начиная с Go 1.22, `for i := range n` обходит целые числа. Эта форма — не обход `channel`. Используйте `range ch` только когда `ch` — `channel`.

## Направленные каналы (`chan<-`, `<-chan`)

Тип `channel` может ограничивать направление.

- `chan T` — двунаправленный. Можно отправлять и принимать.
- `chan<- T` — только отправка.
- `<-chan T` — только приём.

Стрелка показывает путь данных. `chan<- T` — `channel`, который принимает `T`. `<-chan T` — `channel`, который выдаёт `T`.

Двунаправленный `channel` преобразуют в направленный. Направленный `channel` нельзя преобразовать обратно в двунаправленный.

```go
func produce(out chan<- int) {
    out <- 1
    close(out)
}

func consume(in <-chan int) {
    for v := range in {
        fmt.Println(v)
    }
}

func main() {
    ch := make(chan int)
    go produce(ch)
    consume(ch)
}
```

Направленные типы документируют API. Компилятор отклоняет отправку в `<-chan T`. Компилятор отклоняет приём из `chan<- T`. Компилятор отклоняет `close` на `channel` только для приёма.

Используйте направленные типы в параметрах функций. Результат `make` оставляйте как `chan T` у владельца.

Тип возврата `<-chan T` говорит вызывающему, что функция владеет стороной отправки. Вызывающий только принимает.

## Типичные шаблоны

Эти четыре шаблона встречаются во многих программах Go. Считайте их одним набором инструментов. Комбинируйте их. Не копируйте шаблон, когда хватает одной `goroutine`.

**Пул воркеров.** Один `channel` несёт задания. Фиксированное число рабочих `goroutine` принимает задания. Каждый воркер отправляет результат во второй `channel` или пишет в безопасный сборщик. `WaitGroup` ждёт воркеров. Затем закрываете `channel` результатов. Пул ограничивает конкурентность. Граница — число воркеров.

**`Fan-out`.** Один источник отправляет работу многим `goroutine`. Источник может быть `channel`, который делят многие воркеры (пул воркеров — это `fan-out`). `Fan-out` повышает пропускную способность, когда работа независима.

**`Fan-in`.** Многие производители отправляют в один `channel` результатов. Вы сливаете потоки. Закрывайте `channel` результатов только после завершения каждого производителя. `WaitGroup` в `goroutine` слияния — обычное правило закрытия: каждый производитель вызывает `Done`, `goroutine` слияния ждёт, затем закрывает `channel` результатов.

**Конвейер (`pipeline`).** Каждый этап — `goroutine`. Этап 1 принимает вход и отправляет на этап 2. Этап 2 отправляет на этап 3. `channel` соединяют этапы. Закрывайте выход этапа, когда этот этап заканчивается. Следующий этап обходит через `range` до этого закрытия.

**Отмена через `context.Context`.** Передавайте `context.Context` в производители, воркеры и этапы. Когда вызывающий отменяет, каждая `goroutine` возвращает управление. Проверяйте `ctx.Done()` в `select` рядом с операциями `channel`. Тема 12 полностью объясняет `context`. В этой теме используйте `context.WithCancel` или `context.WithTimeout`, чтобы медленный этап не работал вечно.

Безопасный пул или конвейер следует этим правилам:

1. Владелец создаёт `channel`.
2. Отправитель закрывает `channel`.
3. Каждая `goroutine` может выйти, когда контекст отменён.
4. `WaitGroup.Add` происходит до `go`.
5. Не отправляйте в закрытый `channel`.

## `sync.WaitGroup`, `sync.Mutex`, `sync.RWMutex`

`sync.WaitGroup` ждёт набор `goroutine`.

```go
var wg sync.WaitGroup
wg.Add(1)
go func() {
    defer wg.Done()
    work()
}()
wg.Wait()
```

Вызывайте `Add` до `go`. Вызывайте `Add` с числом `goroutine` или вызывайте `Add(1)` по разу на каждую `goroutine`. `Done` вычитает единицу. `Wait` блокируется, пока счётчик не станет нулём. Отрицательный счётчик вызывает `panic`. Не копируйте `WaitGroup` после использования. Начиная с Go 1.25, `wg.Go(func() { ... })` вызывает `Add(1)`, запускает функцию и вызывает `Done`. В Go 1.22–1.24 используйте `Add` и `Done`.

`sync.Mutex` — блокировка взаимного исключения. `Lock` захватывает блокировку. `Unlock` освобождает блокировку. Используйте `defer mu.Unlock()` сразу после `Lock`, когда критическая секция — остаток функции. Защищайте каждое чтение и каждую запись общих данных.

```go
var mu sync.Mutex
var count int

mu.Lock()
count++
mu.Unlock()
```

`sync.RWMutex` допускает многих читателей или одного писателя. `RLock` и `RUnlock` — для читателей. `Lock` и `Unlock` — для писателей. Писатель ждёт, пока все читатели не снимут блокировку. Используйте `RWMutex`, когда чтения часты, а записи редки. Измеряйте, прежде чем заменять `Mutex`. `RWMutex` не всегда быстрее.

Не держите блокировку на медленном вызове ввода-вывода или на операции `channel`, которая может ждать. Держите блокировку только пока читаете или пишете общие данные.

Нулевое значение `WaitGroup`, `Mutex` и `RWMutex` готово к использованию. Не копируйте эти значения. Передавайте их указателями, когда передаёте в функции.

## `sync.Once`, `sync.Map`, `sync.Pool`

`sync.Once` выполняет функцию один раз. Конкурентные вызывающие ждут, пока этот запуск закончится.

```go
var once sync.Once

func setup() {
    once.Do(func() {
        loadConfig()
    })
}
```

`Do` выполняет функцию при первом вызове. Последующие вызовы возвращают управление без запуска. Если функция вызывает `panic`, `Once` считает запуск выполненным. Поздний `Do` не повторяет попытку. Не копируйте `Once` после первого использования.

`sync.Map` — конкурентная `map`. Используйте её, когда многие `goroutine` читают и пишут ключи, а блокировка обычной `map` — измеренная проблема. API использует ключи и значения `any`: `Load`, `Store`, `LoadOrStore`, `LoadAndDelete`, `Delete`, `Swap`, `CompareAndSwap` и `Range`. Обычная `map` плюс `Mutex` или `RWMutex` проще для большинства программ. Не копируйте `sync.Map` после первого использования.

`sync.Pool` — кэш временных объектов. `Get` возвращает значение типа `any`. Сделайте приведение типа результата. `Put` возвращает объект в пул. Сборщик мусора может отбросить объекты пула в любой момент. Пул — не надёжное хранилище. Используйте пул, чтобы снизить выделения короткоживущих объектов, которые можно переиспользовать (например, `bytes.Buffer`). Не кладите в пул грязный объект без сброса.

```go
var bufPool = sync.Pool{
    New: func() any {
        return new(bytes.Buffer)
    },
}

b := bufPool.Get().(*bytes.Buffer)
b.Reset()
// use b
bufPool.Put(b)
```

`New` выполняется, когда `Get` не находит кэшированный объект. `New` может быть `nil`. Тогда `Get` возвращает `nil`, когда пул пуст.

## Детектор гонок: `go test -race`

Гонка данных возникает, когда две `goroutine` обращаются к одной памяти, хотя бы одно обращение — запись, и обращения не синхронизированы. Детектор гонок находит многие гонки данных во время выполнения.

Запускайте тесты с детектором гонок:

```text
go test -race ./...
```

Запускайте программу `main` с детектором гонок:

```text
go run -race .
go build -race -o app .
```

Детектор инструментирует программу. Программа использует больше CPU и больше памяти. Используйте `-race` в разработке и в непрерывной интеграции. Не включайте `-race` в каждый производственный двоичный файл, если нет особой нужды и вы не измерили стоимость.

Детектор сообщает два стека, которые участвовали в гонке. Исправьте гонку через `channel`, мьютекс или атомарную операцию. Не добавляйте `time.Sleep`, чтобы скрыть гонку. Сон не синхронизирует память.

Детектору гонок на некоторых платформах нужен CGO. В Windows официальный набор инструментов поддерживает `-race` на `amd64`. Если `-race` не собирается, прочитайте ошибку. Установите нужный компилятор C, когда сообщение об этом просит.

`go test -race` и `go test -covermode=atomic` работают вместе, когда нужны покрытие и детекция гонок.

Чистый прогон `-race` не доказывает, что в программе нет гонок. Детектор видит гонки, которые выполняет прогон тестов. Пишите тесты, которые запускают конкурентные пути.

## Взаимные блокировки и утечки горутин

Взаимная блокировка (`deadlock`) возникает, когда каждая `goroutine` ждёт и ни одна `goroutine` не может продвинуться. Среда выполнения Go обнаруживает глобальную взаимную блокировку и останавливает процесс с фатальной ошибкой. Сообщение перечисляет `goroutine` и точки ожидания.

Типичные причины взаимной блокировки:

- Отправка в небуферизованный `channel` без приёмника в единственной оставшейся `goroutine`.
- Две `goroutine` ждут друг друга (A ждёт B, B ждёт A).
- `WaitGroup.Wait`, который никогда не видит достаточно вызовов `Done`.
- Два мьютекса, захваченные в противоположном порядке.
- `select` без готового `case` и без `default`, когда никакая другая `goroutine` не отправит.

Утечка `goroutine` — другое. Процесс продолжает работу. Одна или несколько `goroutine` остаются заблокированными или остаются в цикле. Они держат память и другие ресурсы. Среда выполнения не останавливает процесс.

Типичные причины утечки:

- Приём из `channel`, в который никто не отправит и который никто не закроет.
- `for range ch`, когда `ch` никогда не закрывают.
- `time.After` или `time.Tick`, которые создаёте в цикле и никогда не останавливаете.
- `goroutine`, которая ждёт `ctx.Done()`, когда вы никогда не отменяете и никогда не задаёте крайний срок.
- Воркер, которого запустили, но потеряли единственную функцию отмены.

Обнаруживайте утечки в тестах. Считайте `goroutine` до и после работы. Используйте `runtime.NumGoroutine` осторожно (другие пакеты запускают `goroutine`). Предпочитайте тест, который ждёт сигнал выхода с тайм-аутом. Тема 13 разбирает тесты. Тема 19 разбирает трассировки.

Исправляйте взаимную блокировку или утечку ясным временем жизни: кто запускает `goroutine`, кто закрывает `channel`, кто вызывает отмену и кто ждёт.

## Предпочитайте обмен сообщениями общей памяти

Пословица Go: не общайтесь, разделяя память; разделяйте память, общаясь. Идея такая: передавайте данные через `channel`. Приём передаёт владение. После приёма значение использует одна `goroutine`. Для этого значения мьютекс не нужен.

`channel` делают поток видимым. Конвейер, пул воркеров и обработчик запроса, который отправляет результат в `channel`, следуют этой идее.

Мьютекс проще, когда данные — одна структура в одном месте. Примеры:

- Кэш-`map`, которую обновляют многие обработчики.
- Счётчик или набор счётчиков (или используйте `sync/atomic` для одного счётчика).
- Граф объектов, который многие методы должны обновлять на месте.

Мьютекс — неверный инструмент, когда копируете блокировку, когда забываете блокировать чтение или когда держите блокировку во время медленного вызова. `channel` — неверный инструмент, когда создаёте много `channel` только чтобы защитить несколько полей одной структуры.

Выбирайте инструмент, который соответствует владению:

- Один владелец за раз: отправьте значение в `channel` или отправьте сообщение в один цикл (`goroutine`, которая владеет данными).
- Много читателей и редкие писатели на одной `map`: `RWMutex` или копия `map` под блокировкой.
- Однократная инициализация: `sync.Once`.
- Короткая критическая секция на одном целом: `sync/atomic` (тема 19).

Запишите владение в комментарии, когда код неочевиден. Тесты с `-race` — часть дизайна.

# 8. Модули и пакеты

## Описание

Модуль — набор пакетов Go с файлом `go.mod`. Пакет — один каталог файлов Go, которые используют одно имя `package`. Эта тема показывает, как создать модуль, как добавить и привести в порядок зависимости и как версионировать модуль для ломающего изменения. Тема также показывает внутренние пакеты, теги сборки и встраивание файлов.

Сначала завершите тему 1. Тема 1 вводит `go.mod` и режим модулей. Эта тема даёт команды и правила проектирования. Используйте один термин для каждой идеи. Используйте модуль для версионируемой единицы. Используйте пакет для одного импортируемого каталога. Не смешивайте режим GOPATH с режимом модулей.

## `go mod init`, `go get` и `go mod tidy`

Запустите `go mod init` в пустом корне проекта. Передайте путь модуля. Путь модуля — префикс импорта для каждого пакета в модуле:

```text
go mod init example.com/app
```

Команда пишет `go.mod`. Новый файл выглядит так:

```text
module example.com/app

go 1.22.0
```

Строка `module` — путь. Другие модули импортируют ваши пакеты с этим префиксом. Строка `go` — версия языка, которую модуль ожидает.

Выберите путь модуля, который вы контролируете. Для публичного кода используйте URL репозитория без схемы: `github.com/user/app`. Не используйте случайное короткое имя вроде `app`, когда другие модули должны импортировать код.

`go get` добавляет или обновляет модуль в `go.mod`. Передайте путь модуля и версию:

```text
go get example.com/pkg@v1.2.3
go get example.com/pkg@latest
go get example.com/pkg@none
```

С Go 1.16 `go get` меняет файл модуля. `go get` не устанавливает двоичный файл команды. Устанавливайте команду через `go install example.com/cmd/tool@version`.

`go mod tidy` добавляет отсутствующие модули, которые импортирует исходный код. `go mod tidy` удаляет модули, которые исходный код не импортирует. `go mod tidy` обновляет `go.sum`. Запускайте `go mod tidy` после добавления или удаления импортов.

`go.sum` хранит криптографические контрольные суммы. Команда go использует `go.sum`, чтобы обнаружить изменённый zip модуля. Не редактируйте `go.sum` вручную. Восстанавливайте его через `go mod tidy`, когда он неверен.

`go mod vendor` копирует требуемые модули в `vendor/` в корне модуля. Используйте `vendor/`, когда команде нужны офлайн-сборки. Не используйте `vendor/` как замену `go.mod`.

Команда go также записывает косвенные модули в `go.mod`. Косвенный модуль — зависимость зависимости. Комментарий `// indirect` помечает эти строки. Не удаляйте эти строки вручную. Запускайте `go mod tidy`.

Держите экспортируемые имена каждого пакета немногочисленными. Дайте пакету одну задачу. Предпочитайте стандартную библиотеку, когда она решает задачу. Избегайте циклов импорта.

## Семантическое версионирование импорта (`/v2`)

Модули Go используют семантические версии: `vMAJOR.MINOR.PATCH`. Основная версия `v2` или выше — другой модуль, чем `v1`. Путь импорта должен включать суффикс основной версии:

```text
module example.com/note/v2
```

Импортирующие пишут:

```go
import "example.com/note/v2"
```

Основные версии `v0` и `v1` не имеют суффикса. Эти пути модулей допустимы:

- `example.com/note` для `v0.x` и `v1.x`
- `example.com/note/v2` для `v2.x`
- `example.com/note/v3` для `v3.x`

Правило держит один путь импорта сопоставленным с одним основным API. Программа может импортировать `example.com/note` и `example.com/note/v2` в одной сборке, когда оба нужны во время миграции.

Ломающее изменение в помеченном модуле `v1` или выше требует новой основной версии. Ломающее изменение — изменение, которое может сломать существующий импорт при компиляции или которое меняет задокументированное поведение несовместимым способом. Добавление новой экспортируемой функции — не ломающее изменение. Удаление экспортируемой функции — ломающее изменение.

Не кладите код `v2` в путь модуля `example.com/note` без суффикса `/v2`. Команда go отклоняет такую раскладку для модулей с файлом `go.mod`.

Версии `v0.x` не дают обещания совместимости. Импортирующие должны считать `v0` нестабильным.

В некоторых старых репозиториях есть теги вроде `v2.0.0` и нет `go.mod` того времени. Эти модули могут появиться с суффиксом `+incompatible`. Новые модули не должны полагаться на этот шаблон.

## Пакеты `internal`

Каталог с именем `internal` ограничивает, кто может импортировать пакеты под ним. Только родитель `internal` и дерево под этим родителем могут импортировать эти пакеты.

Пример раскладки:

```text
example.com/app/go.mod
example.com/app/cmd/tool/main.go
example.com/app/internal/store/store.go
example.com/app/pkg/api/api.go
```

Пакет `example.com/app/cmd/tool` может импортировать `example.com/app/internal/store`. Пакет `example.com/app/pkg/api` может импортировать его. Другой модуль не может импортировать `example.com/app/internal/store`. Соседний путь модуля вроде `example.com/other` не может его импортировать.

Последний элемент `internal` в пути — забор. В `example.com/app/internal/store/sql` пакет `sql` всё ещё внутренний для `example.com/app`.

Используйте `internal/` для кода, который не входит в публичный API. Кладите туда общую реализацию. Маленькую публичную поверхность кладите в пакет, который не под `internal/`.

Не используйте `internal/` как единственный инструмент проектирования. Ясный публичный пакет всё равно важен. `internal/` только блокирует импорты извне родительского дерева.

Команда go применяет правило во время компиляции. Ошибка упоминает `internal`.

## Теги сборки и суффиксы файлов

Команда go включает файл только когда файл совпадает с текущим контекстом сборки. Контекст включает `GOOS`, `GOARCH` и пользовательские теги.

Суффикс файла задаёт `GOOS` или `GOARCH` без комментария:

- `foo_windows.go` собирается только в Windows
- `foo_linux.go` собирается только в Linux
- `foo_amd64.go` собирается только на `amd64`
- `foo_windows_amd64.go` собирается только в Windows `amd64`

Не используйте суффикс, который не является известным `GOOS` или `GOARCH`. Суффикс `_test.go` помечает тестовый файл. Этот суффикс — не имя GOOS.

Ограничение сборки — комментарий в начале файла. Используйте форму `//go:build`. Поставьте пустую строку после ограничения. Затем напишите строку `package`:

```go
//go:build windows

package pathx
```

Выражение может использовать `&&`, `||` и `!`:

```go
//go:build linux && amd64
```

```go
//go:build !windows
```

Старая форма `// +build` всё ещё работает. Новые файлы должны использовать `//go:build`.

Передайте пользовательский тег через `-tags`:

```text
go test -tags=integration ./...
```

```go
//go:build integration

package store_test
```

Используйте теги для необязательных интеграционных тестов или необязательных возможностей. Не используйте теги, чтобы скрыть сломанные файлы. Исправьте файлы.

Два файла в одном пакете не должны объявлять одну функцию для одного контекста сборки. Общую сигнатуру кладите в файл без тега. Тело для операционной системы кладите в `foo_windows.go` и `foo_unix.go`.

## Встраивание файлов через `embed`

Пакет `embed` включает файлы в двоичный файл во время компиляции. Компилятор читает файлы из каталога пакета. Вы не открываете эти файлы с диска во время выполнения.

Импортируйте пакет. Пустого импорта достаточно, когда встраиваете в `string` или `[]byte`:

```go
import _ "embed"

//go:embed version.txt
var version string
```

Импортируйте `"embed"`, когда используете `embed.FS`. Поставьте комментарий `//go:embed` на строке над переменной:

```go
import "embed"

//go:embed static/*
var staticFS embed.FS
```

Тип переменной должен быть `string`, `[]byte` или `embed.FS`. Путь относителен каталогу пакета. Путь не должен содержать `.` или `..` как элемент пути. Можно перечислить несколько шаблонов в одной директиве или в нескольких строках `//go:embed` над одной переменной `embed.FS`.

`embed.FS` реализует `fs.FS`. Файлы можно открыть через `staticFS.Open("static/app.css")`. Можно передать `embed.FS` в `http.FileServer` через `http.FS`.

Встраивание происходит во время компиляции. Изменение файла на диске не меняет работающий двоичный файл. Пересоберите после правки встроенного файла.

Используйте embed для HTML-шаблонов, SQL-файлов, маленьких статических ресурсов и строки версии. Не встраивайте огромные наборы данных без причины. Двоичный файл растёт на размер файла.

Все файлы в шаблоне должны существовать во время компиляции. Отсутствующий файл — ошибка компиляции. Не встраивайте секреты, которые нужно ротировать без пересборки.

### Вопросы

#### Теоретические вопросы

1. Как путь модуля, путь импорта пакета и забор `internal` работают вместе в одном репозитории?
2. Когда запускать `go mod init`, `go get` и `go mod tidy` в новом проекте, который позже добавляет зависимость?
3. Почему ломающее изменение API нуждается в `/v2` в пути модуля?
4. Как суффиксы файлов и `//go:build` выбирают исходники для одного `GOOS`?
5. Что принадлежит `embed`, а что принадлежит диску рядом с процессом?

#### Простые практические задания

1. Создайте модуль `example.com/pack`. Добавьте `internal/store` и `cmd/app`. Встройте строку `help.txt`. Соберите и запустите.
2. Напишите шпаргалку: `go mod init`, `go get`, `go mod tidy`, `go list -m`, `//go:build`, `//go:embed`.
3. Нарисуйте дерево с `go.mod`, `internal/`, одним файлом `*_windows.go` и одним встроенным файлом.
4. Запустите `go list -m` и `go env GOMOD`. Запишите оба вывода.

#### Средние практические задания

1. Добавьте публичный модуль с `replace`, затем позже `go get` настоящей версии. Запишите `go.mod` до и после.
2. Разделите одну команду на публичный пакет и реализацию `internal`. Добавьте файл, специфичный для GOOS, для помощника путей.
3. Напишите интеграционный тест с `//go:build integration`, который читает встроенный fixture-файл.

#### Сложные практические задания

1. Спроектируйте v1 и v2 одной библиотеки на диске. Импортируйте оба из одной команды двумя строками `replace`. Вызовите оба API.
2. Кросс-компилируйте команду для двух операционных систем. Покажите, какие файлы Go каждая сборка включает, и подтвердите, что встроенный файл есть в обоих двоичных файлах.

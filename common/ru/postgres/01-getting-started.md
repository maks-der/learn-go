# 1. Начало работы

## Описание

PostgreSQL — объектно-реляционная СУБД с открытым исходным кодом. Эта тема показывает, что такое PostgreSQL, зачем важна мажорная версия и как установить сервер. Вы также узнаёте кластеры, базы, схемы, роли и как клиент подключается.

Сначала изучите общие идеи баз (`db.topics.md`). Затем завершите эту тему. Завершите эту тему до изучения типов, таблиц и SQL.

Используйте один термин для каждого понятия. Кластер — один каталог данных с одним работающим сервером. База живёт в кластере. Схема группирует объекты внутри базы. Роль — имя входа или имя группы. `postgresql.conf` задаёт параметры сервера. `pg_hba.conf` задаёт, кто может подключаться. `search_path` — список схем, которые используют неквалифицированные имена. Этот справочник рассчитан на PostgreSQL 16 и PostgreSQL 17.

## Что такое PostgreSQL

PostgreSQL — реляционная база. Данные хранят в таблицах. Запросы пишут на SQL. PostgreSQL также объектно-реляционная. Можно определять типы, операторы и функции. Таблицы могут наследовать столбцы от других таблиц. Большая часть новой работы использует обычные таблицы, типы и ограничения. Не считайте наследование дизайном по умолчанию.

Проект поддерживает PostgreSQL Global Development Group. Лицензия — PostgreSQL License. Можно использовать, менять и распространять ПО. Это не продукт одного вендора.

PostgreSQL работает на Linux, macOS и Windows. Клиенты подключаются по TCP. Порт по умолчанию — `5432`. Процесс сервера — `postgres`. В старых текстах главный процесс иногда называют `postmaster`.

PostgreSQL следует стандартам SQL для многих возможностей. Есть и свои расширения. Примеры: `RETURNING`, `ILIKE`, `DISTINCT ON` и `jsonb`. Позже в этом пути эти возможности разбирают отдельно.

PostgreSQL — не хранилище только документов. JSON хранить можно. Таблицы, типы и ограничения остаются основной моделью. PostgreSQL — не маленький встроенный файл вроде SQLite. Вы запускаете сервер. Клиенты подключаются к этому серверу.

## Мажорные версии

PostgreSQL использует номер major.minor. Примеры: `16.15` и `17.11`. Первое число — мажорная версия. Остальное — минорная.

Минорный выпуск исправляет дефекты и проблемы безопасности. Его можно применить без дампа и восстановления каталога данных. Остановите сервер. Установите новые бинарники. Запустите сервер.

Мажорный выпуск может менять каталоги, формат на диске и поведение SQL. Нельзя направить бинарник PostgreSQL 17 на каталог данных PostgreSQL 16. Нужно обновление через `pg_upgrade`, дамп и восстановление или логическую репликацию. Тема 11 разбирает физический бэкап. Тема 14 разбирает практику обновления.

Мажорная версия определяет набор возможностей. URL документации включают мажорную версию. Пример: [https://www.postgresql.org/docs/17/](https://www.postgresql.org/docs/17/). Слово `current` в URL документации указывает на новейшую стабильную мажорную версию. Она может быть новее 17.

Используйте одну и ту же мажорную версию в разработке, тестах и продакшене. Не разрабатывайте на 17 и не выкатывайте на 16 без проверки возможностей. Не пропускайте минорные обновления надолго.

Покажите версию сервера после подключения:

```sql
SELECT version();
SHOW server_version;
SHOW server_version_num;
```

`server_version_num` — целое число. Пример: PostgreSQL 17.11 сообщает `170011`. В скриптах сравнивайте версии по этому числу.

## Установка PostgreSQL или официальный образ Docker

PostgreSQL можно установить официальным установщиком, менеджером пакетов или Docker.

Официальные установщики для Windows и macOS: [https://www.postgresql.org/download/](https://www.postgresql.org/download/). Дистрибутивы Linux дают пакеты. PostgreSQL Global Development Group также публикует репозитории PGDG apt и yum. Предпочитайте репозиторий, который называет мажорную версию. Пример: `postgresql-17`.

Официальный образ Docker — `postgres` на Docker Hub. Фиксируйте мажорный тег. Примеры: `postgres:16` и `postgres:17`. Не используйте `postgres:latest` для настоящей работы. Тег latest может сменить мажорную версию.

Минимальный запуск Docker:

```text
docker run --name pg17 -e POSTGRES_PASSWORD=secret -p 5432:5432 postgres:17
```

Полезные переменные окружения:

- `POSTGRES_PASSWORD` — пароль суперпользователя (обязательна)
- `POSTGRES_USER` — имя суперпользователя (по умолчанию `postgres`)
- `POSTGRES_DB` — первая база (по умолчанию имя пользователя)

Образ запускает `initdb` при первом старте, если том данных пуст. Данные внутри контейнера лежат в `/var/lib/postgresql/data`. Смонтируйте том, если данные должны остаться после удаления контейнера.

После установки убедитесь, что сервер слушает. На хосте имя службы часто `postgresql` или `postgresql-17`. В Docker используйте `docker logs pg17` и ищите «ready to accept connections».

`psql` — официальный терминальный клиент. Он входит в клиентский пакет PostgreSQL. Подключение с хостом, портом, пользователем и базой:

```text
psql -h localhost -p 5432 -U postgres -d postgres
```

Более новый `psql` часто может подключаться к более старому серверу для многих задач. Сильно старый `psql` может не знать новый SQL. По возможности совпадайте мажорные версии клиента и сервера.

Не открывайте порт `5432` в публичный интернет. Тема 14 разбирает сетевые правила продакшена.

## Кластеры, базы, схемы и роли

**Кластер** — один каталог данных, инициализированный `initdb`. У одного кластера один работающий сервер. Один сервер может содержать много баз.

**База** — именованный каталог внутри кластера. Объекты одной базы не видны в другой базе того же кластера. Подключаетесь к одной базе за раз.

**Схема** — пространство имён внутри базы. У таблиц, представлений и функций есть имя схемы. Схема по умолчанию для новых объектов часто `public`.

**Роль** — учётная запись в кластере. Роль может входить, если у неё есть `LOGIN`. Роль без `LOGIN` — группа. В старых текстах «пользователь» — роль с входом. PostgreSQL хранит и то и другое как роли. `CREATE USER` — это `CREATE ROLE` с `LOGIN`.

Системные базы после `initdb`:

- `postgres` — база по умолчанию для админской работы
- `template1` — источник для новых баз
- `template0` — чистый шаблон; не кладите сюда объекты

Системные схемы включают `pg_catalog` (системные каталоги) и `information_schema` (представления стандарта SQL). Не кладите прикладные таблицы в `pg_catalog`.

Иерархия: кластер → база → схема → таблица. Роль принадлежит кластеру. Привилегии действуют на объекты внутри базы. Тема 8 подробно разбирает `GRANT`.

`createdb` и `createuser` — клиентские программы. Они отправляют SQL на сервер. Ту же работу можно сделать в `psql`:

```sql
CREATE DATABASE shop;
CREATE ROLE shop_app LOGIN PASSWORD 'secret';
GRANT CONNECT ON DATABASE shop TO shop_app;
```

## URI подключения, `pg_hba.conf` и `postgresql.conf` (обзор)

`postgresql.conf` — главный файл конфигурации сервера. По умолчанию он лежит в каталоге данных. Задаёт адрес прослушивания, порт, память, журналирование и много других параметров. Примеры строк:

```text
listen_addresses = 'localhost'
port = 5432
max_connections = 100
```

Переопределения можно класть в `postgresql.auto.conf`. `ALTER SYSTEM` пишет этот файл. Не редактируйте `postgresql.auto.conf` вручную.

`pg_hba.conf` — файл аутентификации по хосту. Каждая строка — правило. Сервер берёт первое подходящее правило. В правиле есть тип подключения, база, роль, адрес клиента и метод.

Примеры правил (не копируйте в продакшен без проверки):

```text
# TYPE  DATABASE  USER  ADDRESS      METHOD
local   all       all                scram-sha-256
host    all       all   127.0.0.1/32 scram-sha-256
host    all       all   ::1/128      scram-sha-256
```

Частые методы:

- `scram-sha-256` — пароль со SCRAM (метод пароля по умолчанию в текущих версиях)
- `md5` — старый метод пароля; для новой работы не используйте
- `trust` — без пароля; только на закрытом локальном тесте
- `peer` — локальный сокет; имя пользователя ОС должно совпасть с ролью
- `reject` — отказать при совпадении

`postgresql.conf` отвечает на вопрос «как работает сервер». `pg_hba.conf` отвечает на вопрос «кто может подключаться». Неверный адрес прослушивания блокирует сеть. Неверное правило `pg_hba.conf` отвергает вход после TCP-подключения.

Многие настройки перечитываются через `SELECT pg_reload_conf();` или `pg_ctl reload`. Часть параметров требует перезапуска. Документация помечает каждый параметр как `SIGHUP` или postmaster.

URI подключения (также connection URL) — одна строка:

```text
postgresql://shop_app:secret@localhost:5432/shop
```

Части URI:

- схема: `postgresql://` или `postgres://`
- пользователь и необязательный пароль
- хост и необязательный порт (по умолчанию `5432`)
- имя базы
- необязательные параметры запроса (`sslmode`, `connect_timeout`)

`psql` принимает URI:

```text
psql "postgresql://shop_app@localhost:5432/shop"
```

Libpq также читает переменные окружения: `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`. Тема 12 подробнее разбирает параметры клиента.

Не ставьте вместе `listen_addresses = '*'` и `trust`. Не коммитьте URI с паролем.

## Метакоманды `psql`: `\l`, `\c`, `\dt`, `\d`, `\dn`, `\du`

Метакоманды начинаются с обратной косой черты. Это команды `psql`. Сервер не получает строку с обратной косой чертой как SQL. `psql` отправляет SQL за вас.

| Команда | Назначение |
| --- | --- |
| `\l` | список баз |
| `\c dbname` | подключиться к другой базе |
| `\dt` | список таблиц в текущем `search_path` |
| `\d name` | описать таблицу или другой объект |
| `\dn` | список схем |
| `\du` | список ролей |

Полезные варианты:

- `\l+` — базы с размером и комментарием
- `\dt *.*` — таблицы во всех схемах
- `\dt schema.*` — таблицы в одной схеме
- `\d+ name` — больше деталей (индексы, комментарии о размере)
- `\du+` — роли с описанием
- `\x` — переключить расширенный вывод
- `\q` — выход
- `\conninfo` — показать текущее подключение
- `\h CREATE TABLE` — справка по синтаксису SQL
- `\?` — справка по метакомандам `psql`

Примеры:

```text
\l
\c learn
\dn
\dt
\d public.items
\du
```

`\c` меняет базу. Базу нельзя сменить SQL-командой `USE`. В PostgreSQL нет `USE`. Вы переподключаетесь.

`\dt` без шаблона скрывает таблицы, которых нет в `search_path`. Таблица в схеме `app` не появится, пока не зададите путь или не выполните `\dt app.*`.

`\d` без имени перечисляет больше типов объектов, чем `\dt`. Предпочитайте `\dt`, когда нужны только таблицы.

Эти команды помогают убедиться, что вы в нужной базе и что роль видит объекты.

## `search_path` и схема `public`

`search_path` — список схем. PostgreSQL использует этот список, чтобы найти неквалифицированные имена. Неквалифицированное имя — `items`. Квалифицированное имя — `app.items`.

`search_path` по умолчанию — `"$user", public`. `"$user"` значит схему с тем же именем, что у текущей роли. Если такой схемы нет, PostgreSQL её пропускает. Затем использует `public`.

Показать путь:

```sql
SHOW search_path;
SELECT current_schemas(true);
```

`current_schemas(true)` включает неявные схемы вроде `pg_catalog`. Системные функции разрешаются, даже если вы не пишете `pg_catalog`.

Задать путь для сессии:

```sql
SET search_path TO app, public;
```

Задать значение по умолчанию для роли:

```sql
ALTER ROLE shop_app SET search_path TO app, public;
```

Новые объекты попадают в первую существующую схему из `search_path`. Если в `CREATE TABLE items` схему не указать, PostgreSQL создаёт `public.items`, когда `public` — первая существующая схема.

Схема `public` есть в новых базах. В PostgreSQL 15 и новее роль `PUBLIC` по умолчанию не имеет `CREATE` на `public`. Обычной роли входа нужен `GRANT CREATE ON SCHEMA public` или своя схема. PostgreSQL 16 и 17 сохраняют этот более безопасный default.

Для новой работы предпочитайте прикладную схему (`app` или `shop`). Квалифицируйте имена в скриптах, когда две схемы могут держать одно и то же имя объекта.

Не кладите прикладные таблицы в `pg_catalog`. Не рассчитывайте на `CREATE` в `public` для каждой роли. Не оставляйте две таблицы с одним именем в `search_path` без плана. Побеждает первое совпадение.

### Вопросы

#### Теоретические вопросы

1. Что такое неквалифицированное имя?
2. Что значит `"$user"` в `search_path`?
3. Куда `CREATE TABLE items` кладёт таблицу?
4. Есть ли у `PUBLIC` по умолчанию `CREATE` на `public` в PostgreSQL 16 и 17?

#### Простые практические задания

1. Выполните `SHOW search_path;` и `SELECT current_schemas(true);`. Сохраните оба результата.
2. Создайте схему `app`. `SET search_path TO app, public;`. Создайте таблицу `items`. Подтвердите схему через `\d app.items`.
3. Напишите квалифицированное и неквалифицированное имя одной таблицы.
4. Выдайте `USAGE` на `app` роли входа. Подключитесь этой ролью. Попробуйте `SELECT` из `app.items` после выдачи прав на таблицу.

#### Средние практические задания

1. Создайте одно и то же имя таблицы в `public` и в `app`. Смените `search_path`. Покажите, какую таблицу читает `SELECT * FROM items`.
2. Через `ALTER ROLE` задайте учебной роли `search_path` = `app, public`. Переподключитесь этой ролью. Подтвердите через `SHOW`.
3. От имени не-суперпользователя попробуйте `CREATE TABLE` в `public` без дополнительных прав. Запишите ошибку. Затем создайте в `app`.

#### Сложные практические задания

1. Прочитайте документацию 16 или 17 по `search_path` и привилегиям схем. Напишите политику из четырёх шагов для новой базы, которая не использует `public` для прикладных таблиц.
2. Найдите, какие объекты игнорируют `search_path` (пример: часть системных каталогов). Запишите два примера из документации.

## Обзор темы

Эти вопросы не повторяют вопросы разделов выше. Они покрывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Опишите путь от пустой машины до `SELECT 1` в `psql`. Назовите установку, запуск и подключение.
2. Почему кластер — не тот же объект, что база?
3. Как URI подключения и `pg_hba.conf` работают вместе, когда вход не удаётся?
4. Какой риск, если `docs/current` и мажорная версия вашего сервера не совпадают?
5. Коллега хочет хранить только JSON и обойтись без таблиц. Какие факты из этой темы вы используете в ответе?

#### Простые практические задания

1. Запустите PostgreSQL 16 или 17. Подключитесь через `psql`. Выполните `SELECT version();` и `SELECT current_database();`. Сохраните оба результата.
2. Напишите шпаргалку на одну страницу: кластер, база, схема, роль, метакоманды `psql`, URI, `search_path`, мажор против минора.
3. Создайте базу `learn` и роль входа `learn_app`. Подключитесь как `learn_app` к `learn`, если привилегий хватает, либо задокументируйте нужный дополнительный `GRANT`.
4. Откройте официальную страницу загрузки и страницу Docker Hub `postgres`. Напишите по одной команде установки для каждого метода.

#### Средние практические задания

1. Напишите короткий скрипт (PowerShell или bash), который ждёт, пока порт `5432` примет подключения, затем запускает `psql -c "SELECT 1"`.
2. Создайте две базы и две роли. Нарисуйте, кто куда может подключаться. Проверьте каждую пару через `psql`.
3. Задокументируйте установку в десять шагов так, чтобы другой новичок мог повторить. Включите номера версий и пути `postgresql.conf` и `pg_hba.conf`.

#### Сложные практические задания

1. Запустите две мажорные версии одновременно (16 и 17) на разных портах. Подключитесь к каждой. Сохраните `SHOW server_version` для обеих.
2. Прочитайте справочник `initdb`. Перечислите пять опций, которые меняют новый кластер. Укажите значение по умолчанию для каждой опции, у которой оно есть.

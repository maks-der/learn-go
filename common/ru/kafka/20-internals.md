# 20. Внутренности (продвинутое)

## Описание

Внутренности объясняют, как Kafka хранит позиции и как клиенты говорят с брокерами. Эта тема не нужна, чтобы писать и читать. Она нужна, когда отлаживаете лаг, репликацию или фиксацию, которая не двигается.

Эта тема покрывает log end offset против high watermark, протокол produce и fetch, кворум контроллера KRaft, индексные файлы и протокол фиксации офсетов консьюмера. Завершите эту тему после тем 2, 5, 6, 8 и 9. Используйте KRaft. Эта тема упоминает ZooKeeper только как старую историю, которую не устанавливаете.

Используйте один термин для каждого понятия. Log end offset (LEO) — следующий офсет, который реплика запишет. High watermark (HW) — офсет, который полностью реплицирован в ISR. Кворум контроллера — группа Raft KRaft, которая хранит метаданные кластера. Индексный файл отображает офсеты или времена на позиции в сегменте. Фиксация — запись офсета группы в `__consumer_offsets`.

## Log end offset против high watermark

У каждой реплики партиции есть **log end offset (LEO)**. LEO — офсет следующей записи, которую эта реплика добавит. Если последняя сохранённая запись — офсет 41, LEO — 42. У разных реплик могут быть разные значения LEO, когда фолловер отстаёт.

**High watermark (HW)** — наибольший офсет, который лидер записал и который все реплики в текущем ISR тоже записали (точное определение следует текущему дизайну репликации Kafka: HW продвигается, когда запись есть у ISR). Консьюмеры, которые используют обычный путь чтения, могут получать записи **ниже HW**. Они не могут читать записи, которые есть только у лидера и ещё нет у ISR (эти офсеты выше HW).

`acks=all` ждёт ISR (и `min.insync.replicas`, тема 9). После успеха этого produce эти записи могут стать видимыми, когда HW двигается.

Фолловер делает fetch у лидера и поднимает свой LEO. Когда ISR догнал, лидер поднимает HW.

Если сравнить LEO на лидере с HW, разница — данные, которые ещё не полностью реплицированы (или ещё не помечены). Большой разрыв означает лаг (тема 9).

Не используйте LEO как «latest» консьюмера в разговоре об эксплуатации, не сказав HW. «Конец журнала» в API консьюмера — конец журнала, который клиенту разрешено видеть (HW для обычного консьюмера).

KRaft не меняет LEO и HW. Эти числа принадлежат журналу партиции, не кворуму метаданных.

## Протокол fetch и produce

Клиенты и брокеры говорят на **протоколе Kafka** по TCP. Протокол — набор типов запросов с версиями. Обычные типы плоскости данных:

- **Produce**: продюсер отправляет пакеты записей для партиций. Брокер отвечает ошибками и базовыми офсетами (и другими полями в текущих версиях).
- **Fetch**: консьюмер (или фолловер) просит записи из партиций с офсетом fetch, min bytes и max wait (тема 16). Брокер отвечает пакетами записей до HW для консьюмеров.

Фолловеры также используют Fetch для репликации. Офсет fetch фолловера — LEO этой реплики. Это путь репликации, не группа консьюмеров.

Существуют другие типы запросов: Metadata, FindCoordinator, JoinGroup, OffsetCommit, OffsetFetch, запросы Txn. Вы не запоминаете каждое поле. Вы должны знать, что клиент — не «просто HTTP».

Клиент использует `bootstrap.servers`, чтобы получить **метаданные** (лидеры, эпохи). Затем produce и fetch идут к **лидеру** каждой партиции (fetch у фолловера — необязательный путь).

Версии протокола согласуются. Старый клиент на новом брокере использует более старую версию. Слишком старый клиент может упасть.

KRaft меняет, как хранятся метаданные. Запрос Metadata всё ещё существует. Клиенты всё ещё делают bootstrap к брокерам. Нет протокола ZooKeeper для клиентов.

Не реализуйте сырой разбор протокола как первое упражнение. Используйте поддерживаемый клиент. Читайте руководство протокола, когда отлаживаете инструментом пакетов или логами брокера.

## Кворум контроллера (KRaft)

**KRaft** — Kafka Raft. **Кворум контроллера** — набор процессов Kafka с ролью контроллера. Они реплицируют **журнал метаданных** через Raft. Один узел — активный контроллер. Остальные — голосующие (и наблюдатели в некоторых установках).

Журнал метаданных хранит топики, партиции, реплики, ACL (текущие версии) и другое состояние кластера. Он не хранит прикладные записи. Прикладные записи остаются в журналах партиций в `log.dirs` (тема 8).

`process.roles` может быть `broker`, `controller` или оба. Совмещённый режим обычен в маленьких лабораториях. Продакшен может разделить контроллеры и брокеров.

**Большинство** Raft должно быть поднято, чтобы принимать изменения метаданных (создать топик, переместить лидера). Если большинство контроллеров останавливается, кластер не может избирать лидеров или менять топики. Существующие лидеры партиций всё ещё могут обслуживать produce и fetch какое-то время, но операции деградируют. Не останавливайте большинство (тема 15).

Клиенты не подключаются к ZooKeeper. Инструменты используют `--bootstrap-server`. `kafka-storage format` пишет идентификатор кластера для KRaft (тема 1).

Этот справочник упоминает ZooKeeper только чтобы сказать: не устанавливайте его для новых кластеров. Старая Kafka хранила метаданные в ZooKeeper. Этот путь здесь не учат.

Эпоха контроллера и эпоха лидера партиции защищают устаревших лидеров. Устаревший брокер не должен добавлять как лидер после новой эпохи.

## Индексные файлы (.index, .timeindex)

Сегмент партиции — файл `.log` плюс индексные файлы (тема 8). Два обычных индекса:

- **`.index`** (индекс офсетов): отображает офсет записи на байтовую позицию в файле `.log`. Брокер использует его, чтобы начать fetch с офсета без полного скана сегмента.
- **`.timeindex`** (индекс времени): отображает метку времени на офсет. Брокер использует его для ретеншна по времени и для fetch по метке времени (`offsetsForTimes` в клиенте).

Индексы разреженные. Они не хранят каждую запись. Kafka находит ближайшую запись, затем сканирует небольшой диапазон в файле `.log`.

Могут быть дополнительные файлы (например индекс транзакций в некоторых версиях). Не правьте ни один из них вручную. Плохой индекс может сделать партицию нечитаемой до восстановления.

Восстановление пересобирает индексы из `.log`, если они отсутствуют или повреждены. Это занимает время на больших сегментах. Это одна причина, почему огромные сегменты вредят перезапуску (темы 8 и 15).

Сегменты метаданных KRaft — другой журнал. Не смешивайте эти файлы с индексами прикладных партиций.

Не удаляйте индексы, чтобы «сэкономить диск», пока брокер работает.

## Протокол фиксации офсетов консьюмера

Группа консьюмеров хранит зафиксированные офсеты во внутреннем топике `__consumer_offsets` (темы 6 и 10). **Протокол фиксации офсетов** — путь запроса:

1. Клиент находит **координатора группы** (FindCoordinator).
2. Клиент отправляет **OffsetCommit** с идентификатором группы, участником (или поколением), партициями и офсетами (плюс метаданные).
3. Координатор добавляет запись фиксации в `__consumer_offsets` и отвечает успехом или ошибкой.

**OffsetFetch** читает последние зафиксированные офсеты, когда участник стартует или ребалансируется.

Автофиксация и ручная фиксация (тема 5) обе используют этот протокол. Разница — когда клиент его вызывает.

Транзакционная фиксация (тема 7) может отправлять офсеты внутри транзакции (`sendOffsetsToTransaction`). Тогда фиксация транзакции и офсетов — одна атомарная единица с produce. Изоляция и `__consumer_offsets` всё равно применяются.

Фиксация — не consume. Фиксация — produce во внутренний компактируемый топик. У этого топика есть партиции. Координатор владеет группой.

Если координатор перемещается, клиент находит его снова. Фиксации могут упасть с повторяемой ошибкой. Клиент должен повторить. Потерянная фиксация после падения процесса вызывает повтор (at-least-once).

KRaft не заменяет `__consumer_offsets`. Данные группы всё ещё в этом топике на брокерах. В текущей Kafka офсеты не фиксируют в ZooKeeper.

2. Напишите стандарт внутренностей для дежурного: какие метрики (HW, LEO, URP, контроллер), кворум KRaft, никогда не править индексы, никогда не использовать ZooKeeper.

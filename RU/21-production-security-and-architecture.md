# 21. Продакшен, безопасность и архитектура

## Описание

Сервис, который работает на ноутбуке, всё равно нуждается в продакшен-дизайне. Нужно версионировать API, наблюдать процесс, ограничивать время, проверять ввод и защищать секреты. Также нужно держать раскладку пакетов достаточно маленькой, чтобы новый коллега мог её прочитать.

Эта тема защитная. Используйте её, чтобы снижать случайности и злоупотребления. Не используйте её, чтобы планировать атаки. Следуйте закону и правилам работодателя.

## Версионирование API и совместимость

API — контракт. Клиенты зависят от URL, полей, кодов статуса и форм ошибок. Ломающее изменение заставляет каждого клиента меняться в одно время. Эта цена высока.

Совместимое изменение добавляет поле или эндпоинт. Старый клиент игнорирует новое поле. Ломающее изменение убирает поле, переименовывает поле, меняет смысл или превращает успех в ошибку для того же запроса.

Обычные методы версий:

- Версия в пути: `/v1/items` и `/v2/items`.
- Версия в заголовке: `Accept: application/vnd.myapp.v1+json`.
- Один URL с аддитивной эволюцией и без номера версии для маленького внутреннего API.

Версии в пути легко видеть в логах. Версии в заголовке держат URL стабильными. Выберите один метод и документируйте его.

Правила, которые держат v1 стабильным:

- Не удаляйте и не переименовывайте поля JSON.
- Не меняйте тип поля.
- Не переиспользуйте имя поля для нового смысла.
- Добавляйте новые поля как необязательные.
- Добавляйте новые эндпоинты вместо перегрузки старого новым смыслом.

Когда контракт нужно сломать, опубликуйте v2. Держите v1, пока клиенты не переедут. Задайте дату заката. Логируйте версию, которую использует каждый клиент.

Пишите тесты совместимости. Храните файлы примеров запросов и ответов. Проигрывайте их в CI. Контракты, ведомые потребителем, помогают, когда API делят многие команды.

Теги структур Go должны оставаться стабильными. Изменение `json:"name,omitempty"` может скрыть поле. Считайте изменения тегов изменениями API.

## Наблюдаемость: метрики, трассировка и OpenTelemetry

Наблюдаемость — способность объяснить текущее поведение системы по её выходам. Три обычных сигнала: логи, метрики и трассы.

Логи — события. Тема 18 покрывает `slog`. Метрики — числа во времени: число запросов, число ошибок, задержка, глубина очереди. Трассы следуют за одним запросом через сервисы. У трассы есть id трассы. Каждый шаг — span.

OpenTelemetry — набор API и экспортёров, независимый от поставщика. Модули Go живут под `go.opentelemetry.io/otel`. Вы создаёте `Tracer` и `Meter`. Вы стартуете span в обработчике. Вы передаёте `context.Context`, чтобы дочерние span оставались в одной трассе.

Распространение контекста шлёт id трассы следующему сервису. HTTP использует заголовки вроде W3C `traceparent`. Инструментируйте клиент и сервер. Если инструментирована только одна сторона, трасса рвётся.

Prometheus — обычная система метрик. Многие сервисы на Go открывают `/metrics` для сбора Prometheus. Пакет `expvar` и `runtime/metrics` открывают факты процесса. Используйте `runtime/metrics` для GC и памяти. Не изобретайте свой формат сбора, когда стандарт команды — Prometheus.

Кардинальность — число уникальных комбинаций меток. Не кладите id пользователя или сырой путь URL с id в метку метрики. Высокая кардинальность может перегрузить систему метрик.

Сэмплируйте трассы в продакшене, когда трафик высок. Держите все трассы ошибок, если можете. Выравнивайте поля логов с `trace_id`, чтобы переходить от строки лога к трассе.

Не открывайте метрики или pprof на публичном слушателе. Привяжите отладочные эндпоинты к внутреннему порту или частной сети.

## Таймауты, повторы и автоматические выключатели

Таймаут ограничивает, как долго операция может работать. Повтор повторяет неудачную операцию. Автоматический выключатель (`circuit breaker`) останавливает вызовы зависимости, которая уже падает. Вместе они защищают потоки, горутины и время пользователя.

Используйте `context.WithTimeout` или `WithDeadline` для исходящих вызовов и для бюджетов обработчика. Задайте `http.Client.Timeout` или, лучше, таймауты на транспорте и контекст на запрос. Задайте серверные `ReadTimeout`, `WriteTimeout` и `IdleTimeout` на `http.Server`.

Повторы безопасны, когда операция идемпотентна. GET, который читает данные, часто безопасно повторять. POST, который создаёт заказ, может создать два заказа, если повторить. Используйте ключи идемпотентности, когда клиент может повторить запись.

Backoff должен расти. Ждите короткое время, затем более длинное. Добавляйте jitter (случайную задержку), чтобы многие клиенты не повторяли на одном такте. Ограничьте число повторов. Уважайте `Retry-After`, когда сервер его шлёт.

Автоматический выключатель держит три идеи: closed (вызовы проходят), open (вызовы сразу падают), half-open (пробный вызов проверяет зависимость). Открывайте цепь после порога ошибок. Закрывайте её после успешных проб. Библиотеки вроде `sony/gobreaker` реализуют этот шаблон. Можно также реализовать маленькую версию с атомарным состоянием и часами.

Не повторяйте ошибку класса 400, которая упадёт снова. Повторяйте таймаут или 503, когда протокол говорит, что сервер перегружен. Логируйте номер попытки.

Каждый повтор умножает нагрузку. Шторм повторов может уронить сервис. Автоматические выключатели и лимиты частоты снижают этот риск.

## Проверка ввода и риски внедрения

Считайте весь ввод недоверенным. Ввод включает пути URL, строки запроса, заголовки, тела JSON, cookie и имена файлов. Сначала проверяйте. Затем используйте значения.

Внедрение случается, когда вы строите команду, запрос или путь, склеивая строки с данными пользователя. Данные пользователя могут изменить смысл команды.

SQL: используйте параметризованные запросы через `database/sql`. Не склеивайте строку пользователя в оператор SQL. Тема 17 покрывает это правило. То же правило относится к построителям запросов NoSQL, которые принимают сырые строки.

Команды операционной системы: не передавайте пользовательский ввод в оболочку. Если нужно запустить процесс, используйте `os/exec` с фиксированным путём исполняемого файла и списком аргументов. Не используйте `bash -c` со склеенной строкой.

Пути файлов: не открывайте `filepath.Join(root, userPath)` без проверки. Путь, который содержит `..`, может выйти из корневого каталога. Очистите путь. Проверьте, что результат остаётся под корнем.

HTML: если генерируете HTML, кодируйте текст пользователя. Используйте `html/template`. Не пишите сырые строки пользователя в HTML.

Заголовки и логи: отклоняйте новые строки в значениях, которые пишете в заголовки или в строки лога, которые разбирают другие системы.

Возвращайте ясную ошибку 400 для неверного ввода. Не возвращайте стеки и текст SQL клиенту. Логируйте детали на сервере.

Библиотеки проверки помогают. Можно также писать маленькие проверки: лимиты длины, допустимые наборы символов и перечислимые значения. Предпочитайте списки разрешения спискам запрета.

Этот раздел учит защите. Не практикуйте внедрение против систем, которыми не владеете.

## Управление секретами

Секрет — значение, которое даёт доступ: пароль, токен API, закрытый ключ или URL базы, который содержит пароль. Не коммитьте секреты в git. Не кладите секреты в слой образа Docker. Не логируйте секреты.

Храните секреты вне дерева исходников. Обычные места:

- переменные окружения, которые внедряет хост
- облачный менеджер секретов
- файл, который хост монтирует со строгими правами

Переменные окружения просты и легко утекают в отладочных дампах. Менеджеры секретов добавляют ротацию, журналы доступа и короткоживущие учётные данные. Предпочитайте менеджер секретов в продакшене.

Используйте файл `.env` только на ноутбуке, если команда это разрешает. Добавьте `.env` в `.gitignore`. Коммитьте файл `.env.example` с пустыми или поддельными значениями.

Сканируйте репозиторий сканером секретов в CI. Если секрет попал в git, ротируйте секрет. Предполагайте, что у каждого клона и каждого форка есть копия. Переписывание истории не достигает каждой копии.

Разделяйте секреты по окружениям. Ключ разработки не должен открывать продакшен-данные. Дайте каждому сервису свои учётные данные. Ротируйте по расписанию и после ухода человека из команды.

В Go загружайте секреты при старте в структуру. Не печатайте структуру через `%+v`, если она содержит секреты. Реализуйте `String` или `slog.LogValuer`, чтобы скрывать.

Закрытые ключи TLS и ключи подписи JWT — секреты. Храните их так же, как пароли.

## Наименьшие привилегии для ОС и сети

Наименьшие привилегии значат: у процесса есть только те права, которые ему нужны. Украденный процесс тогда наносит меньше вреда.

Операционная система:

- Запускайте процесс от пользователя не-root в контейнере и на хосте.
- Дайте рабочему каталогу и порту прослушивания только нужные права файлов.
- Не монтируйте сокет Docker в контейнер приложения.
- Сбрасывайте возможности Linux, которые не нужны.
- Используйте корневые файловые системы только для чтения, когда приложение не пишет на диск.

Сеть:

- Слушайте на интерфейсе, который нужен. Внутренний порт администратора не должен привязываться к `0.0.0.0` на публичном хосте без межсетевого экрана.
- Разрешайте исходящий трафик только к базам и API, которые сервис должен вызывать.
- Используйте TLS для данных в пути.
- Отделяйте публичный слушатель от отладочного слушателя.

В Go `http.Server` может отдавать два mux на двух адресах: публичный и внутренний. `net.Listen` может использовать сокет Unix для доступа только локально.

Роли IAM в облаке не должны использовать подстановку, когда достаточно одного бакета или топика. Пользователи базы не должны быть администраторами. Давайте `SELECT` и `INSERT` только на таблицы, которые сервис использует.

Пересматривайте привилегии, когда добавляете возможность. Новый исходящий URL — новое решение о доверии.

## Флаги возможностей и горячая перезагрузка конфигурации

Флаг возможности — переключатель, который меняет поведение без нового развёртывания. Флаги могут быть булевыми или маленькими перечислениями. Используйте флаги, чтобы скрыть неготовый путь или выкатить изменение на долю трафика.

Загружайте флаги из конфигурации или из сервиса флагов. Передавайте снимок в путь запроса. Не читайте изменяемую глобальную переменную без определённой политики конкурентности.

Горячая перезагрузка значит: процесс читает новый файл конфигурации или новый набор флагов, пока работает. Горячая перезагрузка полезна. Она также источник гонок и частичных обновлений.

Правила безопасной горячей перезагрузки:

- Сначала проверьте новую конфигурацию. Держите старый снимок, если проверка падает.
- Меняйте указатель на неизменяемый снимок через `atomic.Pointer`.
- Не меняйте половину полей, пока работают обработчики.
- Решите, что нельзя перезагружать (адрес прослушивания, URL базы). Для этих значений перезапускайте.

Опасные идеи горячей перезагрузки:

- Перезагружать ключи TLS без ясного пути ошибки.
- Перезагружать только часть реплик, так что флот не согласен.
- Разбирать файл на каждом запросе.

Флагам возможностей нужны владелец и дата удаления. Старый флаг — лишний код. Тестируйте оба значения каждого флага, который держите.

Не используйте флаги, чтобы скрыть проверки безопасности. Флаг, который отключает аутентификацию, — контроль высокого риска. Защищайте его как изменение секрета.

## Предметно-ориентированное проектирование в Go (пакеты как границы)

Предметно-ориентированное проектирование (DDD) — способ структурировать ПО вокруг языка бизнеса. Ограниченный контекст — граница, где слово имеет один смысл. В Go естественная граница — пакет.

Не копируйте дерево папок Java (`entities`, `repositories`, `services`, `usecases`) в каждый модуль. Это дерево часто создаёт циклические импорты и пустые типы. Называйте пакеты по предметной области: `checkout`, `catalog`, `account`.

Кладите основные типы и правила в пакет, который не импортирует `net/http` или драйвер базы. HTTP-адаптеры и SQL-адаптеры импортируют пакет предметной области. Пакет предметной области не импортирует адаптеры.

Используйте в коде те же слова, что и продуктовая команда. Если команда говорит «счёт», не называйте тип `BillDoc`.

Держите агрегаты маленькими. Агрегат — кластер объектов, которые вы меняете как одно. В Go это часто одна структура плюс методы и интерфейс хранилища.

Не вводите шину событий предметной области в первой версии. Начните с функций и типов. Добавляйте события, когда несколько контекстов должны реагировать.

Пакет `internal/` держит предметную область закрытой для модуля, когда никакой другой модуль не должен её импортировать. Экспортируйте только типы, которые нужны адаптерам.

Циклические импорты — сигнал. Если `checkout` и `catalog` импортируют друг друга, выделите маленький пакет `money` или `sku` либо перенесите функцию.

## Гексагональная и чистая архитектура в Go (держите маленькой)

Гексагональная архитектура (порты и адаптеры) ставит приложение в центр. Порты — интерфейсы. Адаптеры говорят с HTTP, базами и очередями. Чистая архитектура — родственная идея с внутренними и внешними кольцами.

В Go порт часто — маленький интерфейс:

```text
type OrderStore interface {
    Save(ctx context.Context, o Order) error
}
```

HTTP-обработчик и SQL-хранилище оба зависят от центра. Центр не зависит от драйвера SQL.

Держите это маленьким. Модуля с двумя интерфейсами и тремя пакетами достаточно для многих сервисов. Модуль с двадцатью слоями не более профессионален. Лишние слои прячут поток.

Правила, которые остаются полезными:

- `main` связывает адаптеры с приложением.
- Интерфейсы маленькие и определены рядом с пользователем, когда это естественно.
- Тесты заменяют адаптеры подделками.
- Можно сменить PostgreSQL на поддельное хранилище без изменения функций предметной области.

Правила, которые разрастаются слишком сильно:

- Тип `UseCase` на каждую функцию.
- DTO на каждое копирование поля между одинаковыми структурами.
- Интерфейсы с одной реализацией и одной тестовой подделкой, которые всё равно живут в отдельном пакете `ports` слишком рано.

Начните с одного пакета `internal/app` и одного пакета `internal/httpapi`. Делите, когда файл трудно назвать или когда импорты зацикливаются.

Внедрение через конструктор из темы 18 — обычный способ связывания. Фреймворк не нужен, чтобы быть гексагональным.

## Системы, ведомые событиями, и очереди сообщений

Система, ведомая событиями, реагирует на события. Очередь сообщений или журнал несёт эти события. Обычные системы — Apache Kafka, NATS и RabbitMQ.

Kafka — устойчивый распределённый журнал. Потребители читают по смещению. Многие команды используют Kafka для потоков событий высокого объёма и для повторного проигрывания.

NATS — лёгкая система обмена сообщениями. NATS Core — для pub/sub. JetStream добавляет устойчивость. Многие команды используют NATS для внутреннего разброса и для более простой эксплуатации, чем у Kafka.

RabbitMQ — брокер с очередями, обменами и ключами маршрутизации. Многие команды используют RabbitMQ для очередей работ и для маршрутизации по ключу.

Термины доставки:

- At-most-once: сообщение может исчезнуть. Нет дубликата.
- At-least-once: сообщение может прийти два раза. Обработчики нужно делать идемпотентными.
- Exactly-once: сложно между системами. Часто имитируют ключами идемпотентности и хранилищем.

Производители должны задать схему. Версионируйте полезную нагрузку. Потребители должны игнорировать неизвестные поля, когда можете. Те же правила совместимости, что у HTTP API.

Потребители должны обрабатывать ядовитые сообщения (сообщения, которые всегда падают). Используйте очередь повторов и очередь мёртвых писем. Логируйте id полезной нагрузки, не секрет.

Не обрабатывайте сообщение неограниченным штормом горутин. Используйте лимит воркеров (тема 19). Передавайте контекст. Фиксируйте или подтверждайте только после успеха побочного эффекта либо используйте шаблон outbox, когда нужно вместе писать в базу и сообщение.

Выбирайте брокер вместе с командой эксплуатации. Программная часть часто меньше. Диск, отставание и группы потребителей — большая часть.

2. Добавьте флаг возможности и внутрипроцессное событие, которое второй пакет потребляет в ограниченном воркере. Покажите путь ядовитого сообщения.
3. Запустите сервис от не-root в контейнере с секретом из окружения. Подтвердите, что логи опускают секрет.

#### Сложные практические задания

1. Напишите архитектурный обзор модуля: политика совместимости, пробелы наблюдаемости, карта таймаутов, заметки об угрозах (внедрение и секреты), граф пакетов и выбор очереди.
2. Добавьте span OpenTelemetry и автоматический выключатель на одном исходящем вызове. Докажите быстрый отказ, когда выключатель открыт, и полную трассу, когда вызов работает.

# 14. Другие модели и масштаб

## Описание

Эта тема — обзор моделей данных, которые не являются реляционной табличной моделью, и того, как делить работу между складами и узлами. Вы изучаете склады ключ-значение, документные, широких столбцов, графовые и поисковые, полиглот-персистентность, CAP практическими словами, шардирование, итоговую согласованность, саги, outbox, идемпотентные записи и OLTP против OLAP.

Используйте один термин для каждого понятия. Модель данных — способ, которым продукт организует значения и запросы. Система учёта — склад, который побеждает, когда копии не согласны. Шард — подмножество данных на одном узле. Завершите эту тему после того, как умеете моделировать таблицы и ключи. Реляционная модель нужна как сравнение.

Путь нейтрален к вендорам. Имена продуктов — примеры категории. Не выбирайте продукт только по популярности.

## Склады ключ-значение, документные, широких столбцов, графовые и поисковые

Склад **ключ-значение** сопоставляет ключ значению. Основная операция — get и set по ключу. Склад не разбирает значение как первоклассную модель запроса.

```text
SET session:42 --> { user_id: 7, expiry: ... }
GET session:42
DEL session:42
```

Используйте склад ключ-значение, когда всегда знаете ключ, нужна низкая задержка и значение — кэш, сессия, блокировка или флаг. Не используйте его как единственный склад заказов с многими формами запросов. Вы бы сканировали ключи или строили вторичные индексы руками. Ключам нужна схема имён. Столкновение перезаписывает значение. Долговечность отличается. Некоторые конфигурации держат данные только в памяти. Читайте настройку персистентности, прежде чем хранить то, что нельзя перестроить.

**Документный** склад держит документ, часто JSON, как единицу данных. Один документ может вкладывать массивы и объекты. Документы в одной коллекции могут отличаться полями (гибкая схема).

```text
{
  "order_id": 1001,
  "customer": { "name": "Ada", "city": "Kyiv" },
  "lines": [
    { "sku": "A-10", "qty": 2 }
  ]
}
```

Используйте документный склад, когда единица чтения и записи — весь документ, форма часто меняется и вы загружаете один агрегат по id. Целостность часто в приложении. Дублирование обычно. Вы копируете имя клиента в документ заказа. Обновление имени клиента не меняет старые заказы, пока не напишете эту работу. Не храните безгранично растущие массивы в одном документе. У документов есть пределы размера.

Склад **широких столбцов** организует данные по ключу строки и гибкому набору столбцов, часто сгруппированных в семейства столбцов. Запросы, которые совпадают с одним ключом строки, эффективны. Запросы, которые сканируют много ключей, могут быть дорогими.

```text
Row key: user#42
  family profile: name=Ada, city=Kyiv
  family events:  2026-09-13T10:00=login
```

Используйте склад широких столбцов, когда пишете большой объём событий или метрик и читаете по известному ключу строки или диапазону ключей. Проект первичного ключа — схема. Если позже нужен другой путь доступа, добавляете другую таблицу и пишете дважды. Не выбирайте эту модель для маленького магазина с многими отчётами с тяжёлыми соединениями.

**Графовая** база хранит узлы и рёбра. Запрос ходит по путям: соседи, кратчайший путь или шаблон типов.

```text
(Ada:Person)-[:WORKS_AT]->(Acme:Company)
(Ada:Person)-[:KNOWS]->(Grace:Person)
```

Используйте графовую базу, когда вопрос — связь: друзья друзей, кто может достичь этого ресурса, рекомендация вдоль пути. Реляционная база может хранить рёбра как таблицу связи. Глубокие пути становятся рекурсивным SQL. Не моделируйте простой счёт один-ко-многим как граф только чтобы следовать тренду. Храните деньги в системе учёта. Суперузел (узел с миллионами рёбер) — горячая точка.

**Поисковый** движок индексирует токены и поля, чтобы ранжировать текст. Пользователи вводят слова. Движок возвращает документы по релевантности, фильтрам и фасетам.

Используйте поисковый движок, когда пользователи ищут текст, когда нужно нечёткое совпадение или когда нужна релевантность. Не используйте поисковый индекс как единственную копию заказа. Поисковые индексы часто итогово согласованы с системой учёта. Записи идут сначала в систему учёта. Затем обновляете индекс. Контроль доступа должен применяться к попаданиям. Поиск, который игнорирует гранты строк, может утечь документы.

```text
Relational   : tables, rows, SQL
Document     : JSON documents
Key-value    : get / set by key
Wide-column  : row key plus columns
Graph        : nodes and edges
Search       : inverted index, ranked hits
```

## Полиглот-персистентность

Полиглот-персистентность значит, что одно приложение намеренно использует больше одной модели данных. Пример: реляционные заказы, сессии ключ-значение, поиск каталога, граф для рекомендаций.

У каждого склада есть работа. Один склад — система учёта для каждого факта. Другие склады производные.

```text
Order placed --> relational DBMS (record)
             --> search index (catalog availability text)
             --> cache invalidate (session cart)
```

Польза: каждый запрос использует подходящую модель. Цена: больше операций, больше режимов сбоя, больше работы согласованности. Нужно определить порядок записи и задание ремонта.

Правила:

1. Назовите систему учёта для каждого факта.
2. Не пишите цену в трёх складах как три равных без правила синхронизации.
3. Начинайте с одного склада. Добавляйте второй склад, когда есть измеренная потребность (задержка поиска, объём сессий).
4. Держите транзакции в складе учёта. Используйте outbox или задание повтора для производных складов (позже раздел).

Не добавляйте склад потому что пост в блоге его хвалил. Не запускайте пять продуктов для учебного проекта.

Одна реляционная СУБД может покрыть большую часть маленькой системы. Полиглот — архитектурный выбор под нагрузкой или под особый запрос, не значок.

## CAP практическими словами

CAP — способ говорить о разделе (сетевом расколе) в распределённом складе.

- **C (consistency)** здесь значит, что все клиенты видят одну последнюю запись (линеаризуемость, неформальными словами: одна актуальная копия).
- **A (availability)** значит, что каждый запрос к неисправному узлу получает ответ (не ошибку «я не могу решить»).
- **P (partition tolerance)** значит, что система продолжается, пока сеть роняет сообщения между узлами.

На одном узле вы не выбираете CAP. Когда сеть между узлами отказывает, продукт должен выбрать: отказать в некоторых записях или чтениях (держать один ответ) или продолжать обслуживать и принять, что копии расходятся.

```text
Partition: site A cannot talk to site B
  Option 1: A stops writes so B cannot miss them  (prefer one copy)
  Option 2: A and B both accept writes            (prefer availability, diverge)
```

Практические слова:

- Реляционный primary, который отказывает в записях, когда не может достичь sync replica, предпочитает одну копию.
- Мульти-primary, который принимает записи на обеих сторонах раскола, предпочитает доступность. Позже сливаете.
- «Мы AP» или «мы CP» как слоган прячет настоящую настройку (размер кворума, повтор, переключение клиента).

CAP не говорит, что выбрасываете долговечность или что SQL устарел. Он обычно не применяется к одному файлу SQLite на одном диске.

Когда читаете страницу вендора, спрашивайте: что происходит, когда две площадки не могут говорить? Кто принимает записи? Как клиенты находят узел? Что чините после раскола?

Не используйте CAP, чтобы закончить разговор о проекте. Используйте его, чтобы начать историю раздела.

## Шардирование и итоговая согласованность

Шардирование (горизонтальное секционирование) делит строки набора данных по ключу шарда. Каждый шард держит непересекающееся подмножество ключей. Маршрутизатор или приложение шлёт запрос на шард, который владеет ключом.

```text
shard key = customer_id
customers 1..999    --> shard A
customers 1000..1999 --> shard B
```

Используйте шардирование, когда один primary не может держать данные или скорость записи. Шардирование — операционная и проектная цена. Не шардируйте маленькую базу.

Хороший ключ шарда появляется почти в каждом запросе, размазывает записи (нет одного горячего ключа) и держит связанные строки, которые соединяете, на одном шарде, когда можете.

Плохой ключ шарда создаёт горячий шард (все новые заказы идут в «сегодня», если шардируете только по дате) или заставляет межшардовые соединения. Межшардовые запросы должны расходиться веером. Они медленнее и труднее изолировать. Транзакции, которые касаются двух шардов, — распределённые транзакции или саги приложения.

Не шардируйте «для высокой доступности». Репликация даёт копии. Шардирование даёт ёмкость. Часто нужны оба.

Диапазонные шарды просты и могут разбалансироваться. Хеш-шарды размазывают лучше и делают диапазонные сканирования труднее. Решардинг (перенос ключей на новые узлы) — запланированный проект.

Итоговая согласованность значит, что копии могут отличаться какое-то время. Если записи останавливаются, копии сходятся к одним значениям (по правилам продукта). Читатели могут видеть устаревшие данные во время задержки.

```text
Write on node A at t=0
Read on node B at t=50ms  -->  old value
Read on node B at t=2s    -->  new value (if replication caught up)
```

Эта модель появляется в асинхронных replica, поисковых индексах после записи, кэшах с TTL и шагах саги, которые ещё не закончились.

Используйте итоговую согласованность, когда бизнес может принять короткое устаревшее чтение. Пример: счётчик просмотров, результат поиска, рекомендация. Не используйте её как единственную историю для банковского баланса, если нет точного правила конфликта и журнала.

Дайте пользователям правду, которую они понимают: «Ваше изменение сохранено. Поиск может занять минуту.» Тихое устаревшее чтение выглядит как потерянная запись.

**Читать свои записи** — более сильная потребность. После сохранения читайте primary или ждите версию.

Не говорите «итоговая согласованность», чтобы значить «мы не знаем». Напишите бюджет задержки и ремонт, если сходимость падает (застрявшая replica).

## Саги, outbox и идемпотентные записи

Сага — последовательность локальных транзакций. У каждого шага есть компенсирующее действие, которое отменяет бизнес-эффект, если позже шаг падает.

```text
1. Reserve inventory   (compensate: release)
2. Charge payment      (compensate: refund)
3. Create shipment     (compensate: cancel shipment)
```

Сага не является изоляцией ACID между шагами. Другие читатели могут увидеть зарезервированный товар до окончания списания. Вы проектируете поля статуса (`reserved`, `paid`, `failed`).

Сага **оркестрации** имеет процесс-координатор, который вызывает каждый шаг. Сага **хореографии** даёт каждому сервису реагировать на события. Оркестрацию легче видеть. Хореография избегает одного начальника и труднее отлаживать.

Шаблон **outbox** пишет бизнес-строку и строку «событие для отправки» в одной локальной транзакции. Издатель читает outbox и шлёт событие на шину или в другой склад. Затем помечает строку outbox как отправленную.

```text
BEGIN
  UPDATE orders SET status = 'paid'
  INSERT INTO outbox (event) VALUES ('OrderPaid')
COMMIT
-- publisher sends OrderPaid; at-least-once
```

Без outbox можно зафиксировать заказ и упасть до отправки события. Другой сервис никогда не услышит. Двойная запись без транзакции — частый баг.

Идемпотентная запись может выполниться больше одного раза и оставить то же конечное состояние, что один успешный запуск. Сети повторяют. Саги повторяют. Потребители outbox повторяют. Без идемпотентности повтор списывает карту дважды.

```text
POST /payments { idempotency_key: "ord-1001-pay" }
-- first call: charges
-- retry: returns the same payment id, no second charge
```

Методы:

1. Клиентский ключ идемпотентности, сохранённый с результатом.
2. Натуральный уникальный ключ (`order_id` уникален на `payments`).
3. Конечный автомат: `pending` в `paid` только один раз.
4. Upsert с номером версии.

Доставка at-least-once (outbox, шина сообщений) требует идемпотентных потребителей. Exactly-once — сочетание at-least-once плюс идемпотентность.

`UPDATE balances SET n = n + 10` не идемпотентен. Два повтора добавляют 20. Компенсации должны быть безопасны для повтора. Возврат, который выполняется дважды, — баг денег, если возврат не идемпотентен.

Не используйте сагу, чтобы спрятать отсутствующее локальное ограничение. Не полагайтесь на «пользователь не кликнет дважды». Повтор по таймауту достаточен, чтобы применить дважды.

Распределённая транзакция (двухфазная фиксация) между продуктами дорога: лишние круговые пути, блокировки до конца координатора, период блокировки, если координатор падает. Многие команды избегают 2PC между продуктами. Они используют одну локальную транзакцию в одной системе учёта, затем распространяют сагой и outbox.

## OLTP против OLAP, хранилища, ETL/ELT и CDC

OLTP значит операционную обработку транзакций. Нагрузка — много маленьких чтений и записей. Каждая транзакция касается немногих строк. Пользователь ждёт. Примеры: оформить заказ, зарегистрировать гостя, провести платёж.

OLAP значит операционную аналитическую обработку. Нагрузка — меньше запросов, которые читают много строк. Запрос агрегирует. Пользователь — аналитик или отчёт. Примеры: продажи по месяцам, воронка конверсии, старение запаса.

```text
OLTP:  UPDATE one order, COMMIT, 10 ms
OLAP:  SUM sales for two years, 30 s, scan many pages
```

Форма схемы отличается. OLTP благоприятствует нормализованным таблицам и текущему состоянию. OLAP благоприятствует широким таблицам фактов, измерениям и истории, которая не меняется (или меняется контролируемо).

Если запускаете тяжёлый OLAP на primary OLTP, вы загрязняете буферный кэш, держите блокировки или потребляете I/O и замедляете оформление. Используйте replica, хранилище или ночной пакет.

Операционная база (система учёта) держит текущее бизнес-состояние. Она принимает записи от приложений. Ограничения и транзакции защищают это состояние.

Хранилище данных держит копию данных для анализа. Это не место, где клиент завершает оформление. Загрузки приходят пакетами или как поток. Пользователи запускают отчёты и модели.

```text
Apps --> operational DBMS --> (ETL/ELT/CDC) --> warehouse --> reports
```

Replica операционной базы не является хранилищем. У replica та же схема и та же раскладка строк. Хранилище преобразует, ведёт историю и обслуживает другие инструменты.

Не давайте аналитикам `SELECT` на продакшен-операционных таблицах как единственную архитектуру. Вы утекаете персональные данные, нагружаете primary и не можете перестроить историю. Одно направление истины: операционная — учёт. Хранилище производное.

ETL значит extract, transform, load. Вы извлекаете из источника, преобразуете в конвейере, загружаете в цель.

ELT значит extract, load, transform. Вы извлекаете, загружаете сырые данные в цель, преобразуете внутри цели SQL или движком хранилища.

```text
ETL:  source --> transform (job) --> warehouse
ELT:  source --> raw load --> transform (SQL in warehouse)
```

ETL подходит, когда нужно уменьшить данные до выхода из источника или спрятать столбцы до посадки. ELT подходит, когда хранилище может обрабатывать большой SQL и вы хотите держать сырую копию.

Обоим нужны расписание или триггер, идемпотентные загрузки или водяной знак (загрузка с метки времени T), повтор при сбое и контракт данных. Не преобразуйте в разовых блокнотах как единственный продакшен-путь. Не запускайте полный extract каждый час, если есть инкрементальный водяной знак. Проверки качества принадлежат конвейеру: числа строк, доли null, уникальные ключи. Часовые пояса и типы денег должны пережить конвейер.

CDC (захват изменений данных) читает изменения из операционной базы (обычно WAL или поток изменений) и публикует эти изменения потребителям: хранилище, поиск, кэш, другой сервис.

```text
Primary WAL --> CDC reader --> events --> consumers
```

Польза CDC: почти реальное время производных складов, меньше нагрузки чем полные extract, естественный журнал событий. Цена CDC: порядок, смена схемы и потребность в идемпотентных потребителях. CDC не является резервом. CDC не заменяет проверенный дамп.

Не проектируйте таблицу OLTP сначала для отчёта из 50 столбцов. Не проектируйте звёздную схему для оформления за 5 мс.

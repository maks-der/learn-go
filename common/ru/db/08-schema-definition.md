# 8. Определение схемы

## Описание

Эта тема показывает, как создавать таблицы, менять таблицы и удалять таблицы. Вы изучаете обычные типы данных на высоком уровне, ограничения таблиц, индексы как объекты схемы и соглашения об именах.

Используйте один термин для каждого понятия. Оператор определения схемы меняет объекты, не значения строк. `CREATE`, `ALTER` и `DROP` — язык определения данных (`DDL`). Завершите эту тему до глубокого изучения транзакций. `DDL` и транзакции взаимодействуют способами, специфичными для продукта.

Практикуйтесь на одноразовой базе. Не удаляйте таблицу, которую используют другие люди.

## `CREATE TABLE`, типы данных (высокий уровень)

`CREATE TABLE` определяет базовую таблицу. Вы называете таблицу. Вы называете каждый столбец. Вы даёте каждому столбцу тип. Вы добавляете ограничения.

```sql
CREATE TABLE products (
    product_id INTEGER PRIMARY KEY,
    sku VARCHAR(32) NOT NULL UNIQUE,
    name VARCHAR(200) NOT NULL,
    price DECIMAL(10, 2) NOT NULL,
    active BOOLEAN NOT NULL,
    created_at TIMESTAMP NOT NULL
);
```

Обычные семейства типов (имена отличаются по продукту):

| Семейство | Типичное имя в стиле стандарта | Применение |
| --- | --- | --- |
| Целое | `INTEGER` | Счётчики, id, количества |
| Десятичное | `DECIMAL(p, s)` | Деньги и точные дроби |
| Плавающее | `DOUBLE PRECISION` | Научные меры, не деньги |
| Текст | `VARCHAR(n)`, `CHAR(n)` | Строки; предпочитайте `VARCHAR` |
| Дата | `DATE` | Календарный день |
| Время | `TIMESTAMP` | День плюс время |
| Булево | `BOOLEAN` | Истина или ложь |

Используйте `DECIMAL` (или точный числовой тип продукта) для денег. Не используйте двоичный плавающий тип для валюты. Появляются ошибки округления.

`VARCHAR(n)` имеет максимальную длину. Выберите длину, которая подходит домену. `VARCHAR(2)` хватает для многих кодов стран. `VARCHAR(200)` подходит многим именам. У некоторых продуктов есть неограниченные текстовые типы. Используйте их, когда длина действительно без границы.

`TIMESTAMP` может включать или не включать часовой пояс в зависимости от имени типа. Более поздняя тема покрывает часовые пояса. Для этого пути храните метки времени в одном согласованном правиле и документируйте его.

`BOOLEAN` есть не в каждом продукте. Некоторые продукты используют `0`/`1` или `'t'`/`'f'`. Проверьте руководство.

Не изобретайте тип на продукт на этом пути, когда существует тип в стиле стандарта. Пишите `INTEGER` и `DECIMAL`. Подстраивайтесь под продукт при реализации.

`CREATE TABLE` падает, когда имя уже существует. Используйте новое имя или удалите старую таблицу только если это безопасно.

## `ALTER TABLE`

`ALTER TABLE` меняет существующую таблицу. Вы добавляете столбец, удаляете столбец, меняете тип или добавляете ограничение. Точные предложения отличаются по вендору. Изучайте идеи, затем читайте синтаксис продукта.

Добавить столбец:

```sql
ALTER TABLE customers
    ADD email_verified BOOLEAN NOT NULL DEFAULT FALSE;
```

Новому столбцу `NOT NULL` нужно значение по умолчанию, если строки уже есть. СУБД должна заполнить новый столбец для каждой старой строки.

Удалить столбец:

```sql
ALTER TABLE customers
    DROP COLUMN email_verified;
```

Удаление столбца уничтожает эти данные. Другие объекты (представления, индексы) могут блокировать удаление.

Переименовать столбец или таблицу (синтаксис варьируется):

```sql
ALTER TABLE customers
    RENAME COLUMN name TO full_name;
```

Добавить ограничение после того, как таблица существует:

```sql
ALTER TABLE products
    ADD CONSTRAINT chk_products_price CHECK (price >= 0);
```

Добавление падает, если текущая строка ломает проверку. Сначала почистите данные или исправьте правило.

Меняйте тип, когда существующие значения чисто преобразуются. Смена с `VARCHAR(200)` на `VARCHAR(50)` падает, если значение длиннее 50.

Не используйте `ALTER TABLE` как ежедневный инструмент правки данных. Используйте `UPDATE` для значений. Используйте `ALTER` для структуры.

Некоторые продукты не могут изменить столбец за один шаг. Они добавляют новый столбец, копируют данные, удаляют старый столбец и переименовывают. Планируйте этот путь для больших таблиц.

`DDL` может заблокировать таблицу. Долгое изменение может блокировать писателей. Выполняйте большие изменения в окне обслуживания в продакшене. Этому пути нужны только маленькие учебные таблицы.

## `DROP TABLE` и каскадные удаления (осторожно)

`DROP TABLE` удаляет объект таблицы и её данные. Имени нет. Индексы на этой таблице нет. Действие — не пустая таблица. Чтобы сохранить таблицу и удалить строки, используйте `DELETE` или `TRUNCATE` (тема 5).

```sql
DROP TABLE scratch_items;
```

Если другие таблицы ссылаются на таблицу внешним ключом, СУБД по умолчанию отвергает удаление. Этот отказ — правило безопасности.

Некоторые продукты позволяют:

```sql
DROP TABLE customers CASCADE;
```

`CASCADE` удаляет зависимые объекты или удаляет внешние ключи, которые указывают на таблицу. Точный список отличается по вендору. `CASCADE` может убрать больше, чем ожидаете. Представления и дочерние ограничения могут исчезнуть.

**Каскадные удаления** — другая идея. Это действие внешнего ключа при `DELETE` строки, не `DROP TABLE`:

```sql
CONSTRAINT fk_orders_customers
    FOREIGN KEY (customer_id) REFERENCES customers (customer_id)
    ON DELETE CASCADE
```

Когда удаляете клиента, СУБД удаляет заказы, которые указывают на этого клиента. Это правило сильное и опасное. Удаление одного родителя может убрать большое дерево детей.

Предпочитайте `ON DELETE RESTRICT` или отсутствие каскада (обычное значение по умолчанию: отвергнуть удаление), пока учитесь. Добавляйте `ON DELETE CASCADE` только когда ребёнок не может существовать без родителя и вы намерены это стирание.

Не путайте:

- `DROP TABLE ... CASCADE` — удалить объекты
- `ON DELETE CASCADE` — удалить дочерние строки, когда удалена родительская строка

Не выполняйте `DROP TABLE` в общей базе без списка зависимостей. Сначала запросите метаданные или используйте GUI, чтобы перечислить внешние ключи и представления.

У некоторых продуктов есть `DROP TABLE IF EXISTS`. Эта форма избегает ошибки, когда таблицы уже нет. Используйте её в скриптах, которые перезапускаете.

## Ограничения: `NOT NULL`, `UNIQUE`, `CHECK`, `DEFAULT`

Ограничения — правила на таблице. Тема 3 разместила их по видам целостности. Этот раздел показывает формы SQL.

**`NOT NULL`.** Столбец должен иметь значение в каждой строке.

**`UNIQUE`.** Никакие две строки не делят одно значение (для `NULL` продукты отличаются: многие допускают несколько `NULL` в уникальном столбце). Уникальное ограничение может покрывать больше одного столбца.

**`CHECK`.** Выражение должно быть истинным или неизвестным для каждой строки. `CHECK (price >= 0)` отвергает отрицательные цены. Цена `NULL` делает проверку неизвестной, поэтому допускающая `NULL` цена всё ещё может быть `NULL`, если не добавить также `NOT NULL`.

**`DEFAULT`.** Когда вставка опускает столбец, СУБД хранит это значение. Значение по умолчанию — не ограничение в том же смысле, но оно принадлежит определению столбца.

```sql
CREATE TABLE products (
    product_id INTEGER PRIMARY KEY,
    sku VARCHAR(32) NOT NULL UNIQUE,
    name VARCHAR(200) NOT NULL,
    price DECIMAL(10, 2) NOT NULL DEFAULT 0,
    active BOOLEAN NOT NULL DEFAULT TRUE,
    CONSTRAINT chk_products_price CHECK (price >= 0)
);
```

`PRIMARY KEY` подразумевает `UNIQUE` и `NOT NULL`. Не нужно писать эти два снова на тех же столбцах.

Называйте ограничения (`chk_products_price`). Имя появляется в сообщениях об ошибках. Безымянные ограничения получают сгенерированное имя, которое трудно читать.

Можно прикрепить `UNIQUE`, `CHECK` и внешние ключи как ограничения таблицы. Можно прикрепить `NOT NULL` и `DEFAULT` как атрибуты столбца.

Не используйте `CHECK` для правил, которым нужна другая таблица. Используйте внешний ключ. Некоторые продукты позволяют подзапросы в `CHECK`. Эта возможность не переносима.

Не полагайтесь на `DEFAULT`, чтобы скрыть отсутствующее бизнес-значение. Если приложение должно слать `active`, требуйте его в приложении, даже если у столбца есть значение по умолчанию.

## Индексы как объект схемы (подробности в разделе 11)

Индекс — объект схемы, который ускоряет поиск. Это не вторая таблица бизнес-данных. СУБД поддерживает индекс, когда вы пишете строки.

Вы создаёте индекс через `CREATE INDEX`. Уникальное ограничение или первичный ключ также создаёт индекс в большинстве продуктов.

```sql
CREATE INDEX idx_orders_customer_id
    ON orders (customer_id);
```

```sql
CREATE UNIQUE INDEX idx_customers_email
    ON customers (email);
```

Уникальный индекс обеспечивает уникальность и поддерживает быстрый поиск по email. Ограничение `UNIQUE` — логическое правило. Индекс — физический помощник. Тема 3 сделала это разделение. Тема 11 объясняет B-деревья, составные индексы и когда индекс вредит записи.

Называйте индексы с ясным префиксом (`idx_`). Включайте таблицу и столбцы, когда длина имени позволяет.

Не добавляйте индекс на каждый столбец. Каждый индекс стоит места и времени записи. Добавляйте индекс, когда фильтр запроса или ключ соединения его нуждается, или когда уникальное правило его нуждается.

`DROP INDEX` удаляет индекс. Он не удаляет строки таблицы. Имя и синтаксис отличаются (`DROP INDEX` против удаления ограничения через `ALTER TABLE`), когда индекс поддерживает ограничение.

Перечисляйте индексы в клиенте или в представлениях метаданных. Подтвердите, что не создали дубликат индекса на тех же столбцах.

Считайте индексы частью схемы. Проверяйте их в том же процессе изменений, что и таблицы. Не создавайте случайные индексы в продакшене без причины запроса.

## Соглашения об именах

Соглашение об именах — правило команды для имён объектов. СУБД принимает много имён. Читателям нужен один стиль.

Рекомендуемые привычки для этого пути:

- Используйте строчные буквы, цифры и `_`.
- Используйте стиль таблиц в единственном или множественном числе. Выберите один. Этот путь часто использует множественные имена таблиц (`customers`) и речь о сущности в единственном числе (`customer`).
- Называйте первичные ключи `table_id` или `id`. Выберите одно. `customer_id` ясно в соединениях.
- Называйте внешние ключи по ссылочному ключу (`customer_id` в `orders`).
- Называйте индексы `idx_table_columns`.
- Называйте уникальные ограничения `uq_table_columns`.
- Называйте проверки `chk_table_rule`.
- Называйте внешние ключи `fk_table_ref`.

Примеры:

```text
customers.customer_id
orders.customer_id
idx_orders_customer_id
fk_orders_customers
chk_products_price
```

Не используйте пробелы в именах. Не используйте зарезервированные слова (`order`, `user`, `table`) как сырые имена. Если нужно, заключайте имя в кавычки. Имена в кавычках чувствительны к регистру на многих продуктах. Избегайте необходимости кавычек.

Не смешивайте `camelCase` и `snake_case` в одной схеме. Читатели SQL ожидают `snake_case` во многих экосистемах.

Держите имена на английском, если язык команды для кода — английский. Держите имена стабильными. Переименование ломает программы.

Не кодируйте тип в имени (`name_varchar`). Тип живёт в каталоге. Не префиксируйте каждую таблицу именем схемы (`sales_sales_orders`). Схема уже даёт таблице пространство имён.

Документируйте соглашение на короткой странице. Следуйте ему в каждом операторе `CREATE`.

### Вопросы

#### Теоретические вопросы

1. Опишите путь от `CREATE TABLE` к позднему `ALTER` и безопасному `DROP`.
2. Как `NOT NULL`, `UNIQUE`, `CHECK` и `DEFAULT` работают вместе на одном столбце?

#### Простые практические задания

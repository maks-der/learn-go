# 14. Распределённая координация

## Описание

Приложения используют Redis как общее место для блокировок, лимитов, id запросов, сессий и флагов. Эта тема покрывает эти шаблоны и разницу между Pub/Sub и потоками.

Сначала завершите тему 3 (строковые блокировки), тему 8 (Lua) и тему 12 (клиенты). Считайте каждый шаблон дизайном приложения плюс команды Redis, а не продуктом консенсуса.

Используйте один термин для каждого понятия. Блокировка — ключ, который может держать только один работник. Ограничение частоты — потолок событий в окне времени. Ключ идемпотентности — сохранённый id запроса, который делает второе применение пустой операцией. Сессия — состояние на пользователя с TTL. Флаг функции — сохранённый переключатель. Pub/Sub — рассылка fire-and-forget. Поток — журнал с id.

## Распределённая блокировка (`SET NX EX`) и спор Redlock

Тема 3 ввела простую блокировку:

```text
SET lock:resource holder-id NX EX 30
```

`OK` значит этот работник держит блокировку. Null-ответ значит её держит другой работник. TTL освобождает ключ, если работник умер.

Снятие должно удалять только вашу блокировку. Скрипт Lua (тема 8) делает `GET`, затем `DEL`, если значение равно `holder-id`. Двухшаговый `GET` плюс `DEL` с клиента может снять блокировку другого работника после истечения.

Пределы блокировок одного экземпляра:

- Пауза Redis, вытеснение или долгий GC в работнике могут истечь блокировку, пока работник ещё работает.
- Второй работник затем захватывает блокировку. Два работника выполняют критическую секцию.
- Один экземпляр Redis — не система консенсуса на нескольких узлах. Переключение может потерять блокировку, которая не была сохранена.

Redlock — алгоритм, который использует несколько независимых экземпляров Redis. Документация Redis его описывала. Мартин Клеппманн и другие опубликовали критику. Спор покрывает часы, паузы, fencing и безопасен ли Redlock для работы, критичной к корректности.

Этот справочник не разрешает спор. Для обучения:

- Используйте один экземпляр, уникальный id держателя, TTL и атомарное снятие.
- Для работы, критичной к корректности (деньги, уникальные побочные эффекты), добавьте fencing-токен (монотонное число из `INCR`), который проверяет ресурс, или используйте систему, спроектированную для консенсуса.
- Не считайте `SET NX EX` полной распределённой транзакцией базы.

Не блокируйте, когда одна команда Redis уже делает обновление безопасным (`INCR`, обновление Lua данных только Redis).

## Ограничение частоты (фиксированное окно, скользящее окно, token bucket)

Ограничение частоты отклоняет или задерживает события, когда клиент превышает бюджет.

Фиксированное окно:

```text
INCR rl:user:42:202609131857
EXPIRE rl:user:42:202609131857 60
```

Используйте текущую минуту (или секунду) в ключе. Если счёт выше N, отклоняйте. `EXPIRE` на первом увеличении (Lua может задать срок только когда значение `1`).

Лимит сбрасывается на краю окна. Пользователь может отправить N событий в конце одной минуты и N в начале следующей (2N за две секунды).

Скользящее окно: храните метки событий в упорядоченном множестве. `ZREMRANGEBYSCORE` сбрасывает старых членов. `ZCARD` — счёт. `ZADD` нового события, если ниже лимита. Тема 6 покрыла команды. Память растёт с событиями в окне.

Token bucket: ключ хранит токены (или время последней дозаправки плюс токены). Каждый запрос берёт один токен. Токены дозаправляются со временем до потолка. Скрипт Lua обновляет ключ атомарно. Всплески разрешены до размера корзины.

Выбирайте:

- Фиксированное окно — просто, дёшево, всплеск на границах
- Скользящее окно — глаже, больше CPU и памяти
- Token bucket — управление всплеском со стабильной дозаправкой

Cluster: держите все ключи одного лимита на одном слоте (`{user:42}`).

Не ограничивайте частоту только в процессе приложения. Многие процессы делят один бюджет Redis.

## Ключи идемпотентности

Клиент может отправить один запрос дважды (повтор, двойной щелчок, таймаут). Ключ идемпотентности заставляет второе применение вернуть первый результат (или зарезервированную ошибку) без второго побочного эффекта.

Шаблон:

```text
SET idem:pay:req-9f3a 1 NX EX 86400
```

Если ответ `OK`, это первый запрос. Сделайте работу. Затем сделайте `SET` сохранённого результата (или хеша) на том же ключе или соседнем ключе.

Если ответ null, ключ есть. Верните сохранённый результат. Не списывайте снова.

Используйте TTL достаточно длинный для повторов (часы для платежей часты). Документируйте TTL.

Сама работа всё ещё должна быть безопасной, если процесс умрёт после `SET NX` и до завершения побочного эффекта. Некоторые дизайны хранят `pending`, затем `done` плюс результат. Согласователь заканчивает ключи `pending`.

Redis — координатор. Запись банка или SQL всё ещё нуждается в своей идемпотентности, когда можете её использовать.

Не используйте короткий TTL для id платежа, который клиент может повторить через 10 минут.

Cluster: `{pay:req-9f3a}` и на ключе блокировки, и на ключе результата, если используете два ключа.

## Хранилище сессий

Сессия — данные, которые принадлежат браузеру или устройству после входа. Redis — частое хранилище сессий: низкая задержка, TTL и общее хранилище для многих процессов приложения.

Типичная раскладка:

```text
HSET sess:a1b2 user 42 role staff
EXPIRE sess:a1b2 1800
```

Или одна строка JSON: `SET sess:a1b2 '{"user":42}' EX 1800`.

Приложение задаёт cookie с id сессии (случайное значение). Cookie — не id пользователя. Redis держит отображение.

Скользящая сессия: на каждом запросе снова `EXPIRE` (или `SET` с новым TTL). Абсолютная сессия: держите поле `created` и отказывайте после макс. возраста даже если `EXPIRE` скользит.

Выход: `DEL` ключа сессии.

Не храните пароли в сессии. Храните id пользователя и небольшой набор утверждений. Подписывайте или шифруйте cookie, если id должен быть неугадываемым; ключу Redis всё ещё нужен длинный случайный id.

Многие процессы делят один Redis. В этом смысл. Локальная карта сессий процесса падает, когда балансировщик меняет процесс.

Персистентность: сессии могут быть кэшем. Потеря выходит всех. Если это неприемлемо, включите персистентность или примите риск (тема 9, тема 21).

## Флаги функций

Флаг функции — сохранённый переключатель. Приложение читает флаг и выбирает путь кода. Redis может хранить флаги для быстрой центральной смены без деплоя.

```text
HSET flags checkout_v2 1 search_v3 0
HGET flags checkout_v2
```

Или один ключ на флаг: `SET flag:checkout_v2 1`.

Хеш держит все флаги в одном `HGETALL` (только маленький хеш). Многим флагам с большими переопределениями на пользователя нужна другая раскладка (`flag:checkout_v2:user:42`).

Кэшируйте флаги в процессе на несколько секунд, если иначе каждый запрос делал бы `HGET`. Затем примите короткую задержку после смены.

Флаги — не граница безопасности. Пользователь, который может писать Redis, может включать флаги. Защищайте Redis (тема 17). Используйте ACL, чтобы пользователь приложения не мог `FLUSHALL`.

Не оставляйте мёртвые флаги навсегда. Назовите владельца и дату истечения в каталоге.

Сложный таргетинг (процентный rollout, списки пользователей) может использовать множества, хеши или скрипт Lua. Начните с глобального булева.

## Pub/Sub (`PUBLISH`, `SUBSCRIBE`) против потоков

Pub/Sub:

```text
SUBSCRIBE news
PUBLISH news hello
```

Redis доставляет `hello` текущим подписчикам. Если ни один подписчик не подключён, сообщение пропало. Нет журнала, нет `ACK` и нет группы потребителей.

`PSUBSCRIBE news*` совпадает с шаблонами. `UNSUBSCRIBE` покидает канал.

Соединение в режиме подписки не выполняет обычные команды. Используйте выделенное соединение (тема 12).

Потоки (введение темы 7, полностью тема 15):

- У записей есть id
- Потребитель может читать позже
- Группы и `XACK` отслеживают работу
- `XTRIM` / `MAXLEN` ограничивают память

Используйте Pub/Sub для живых сигналов, когда потеря приемлема (подсказки инвалидации кэша, «перезагрузить флаги», присутствие). Используйте потоки, когда работник должен обработать каждое событие хотя бы раз и нужен список отложенных.

Pub/Sub в Cluster использует шину кластера для fan-out. Доставка всё ещё at-most-once для каждого подписчика.

Не используйте Pub/Sub как долговечную очередь задач.

## Обзор темы

Эти вопросы не повторяют вопросы из разделов выше. Они охватывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Какие шаблоны этой темы критичны к корректности и какой лишний инструмент (fence, долговечный журнал, ограничение SQL) им нужен кроме Redis?
2. Чем ограничение частоты, ключ идемпотентности и блокировка отличаются по времени жизни ключа и по смыслу `NX`?
3. Когда выбирать Pub/Sub вместо потока для одного имени события?
4. Чем сессии и флаги функций отличаются по политике TTL и по тому, кто может писать ключ?
5. Почему «Redis жив» недостаточно, чтобы назвать блокировку безопасной после переключения?

#### Простые практические задания

1. Напишите шпаргалку: блокировка `SET`, ограничение частоты `INCR`, идемпотентность `SET NX`, сессия `HSET`, флаг `HGET`, `PUBLISH`.
2. Нарисуйте один запрос пользователя, который проверяет флаг, лимит частоты и ключ сессии.
3. Напишите пять лабораторных имён ключей с префиксами `lock:`, `rl:`, `idem:`, `sess:`, `flag:`.
4. Перечислите команды, которые должны использовать Lua для атомарного чтения-затем-записи в этой теме.

#### Средние практические задания

1. Соберите крошечный API: создание сессии, лимит фиксированного окна и ворота флага. Запишите ключи Redis после одного успеха и одного отказа.
2. Напишите страницу решения: блокировка против обновления только Lua против уникального ограничения SQL.
3. Задокументируйте повтор + идемпотентность + ограничение частоты вместе. Запишите порядок проверок.

#### Сложные практические задания

1. Реализуйте блокировку + fencing + идемпотентность для макетного вызова «создать заказ». Напишите тесты двойной отправки и истечения блокировки во время работы.
2. Напишите промышленную заметку: когда эта команда разрешает Redlock, когда запрещает и что использует вместо для платежей.

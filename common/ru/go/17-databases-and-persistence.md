# 17. Базы данных и постоянное хранение

## Описание

Эта тема показывает, как программы на Go хранят данные. Стандартный пакет `database/sql` — это интерфейс. Драйвер реализует низкоуровневые вызовы. Вы пишете SQL, управляете транзакциями и передаёте `context.Context` в запросы.

Для каждого понятия используйте один термин. Драйвер говорит с одним продуктом базы данных. Пул (`sql.DB`) держит соединения. Транзакция группирует операторы так, что они фиксируются или откатываются вместе. ORM генерирует или отображает SQL за вас. Не храните секреты в исходных файлах. Не склеивайте пользовательский ввод в SQL. Используйте параметры.

## Интерфейс `database/sql`

Пакет `database/sql` не содержит клиент PostgreSQL или MySQL. Он определяет типы, которые реализуют драйверы. Приложение импортирует драйвер ради побочного эффекта, затем использует `sql.DB`.

```go
import (
    "database/sql"
    _ "github.com/jackc/pgx/v5/stdlib"
)

db, err := sql.Open("pgx", os.Getenv("DATABASE_URL"))
if err != nil {
    return err
}
defer db.Close()

if err := db.PingContext(ctx); err != nil {
    return err
}
```

Пустой импорт регистрирует драйвер. `sql.Open` проверяет имя драйвера и конфигурацию. Он не всегда открывает настоящее сетевое соединение. `Ping` или `PingContext` доказывают, что соединение работает.

`sql.DB` безопасен для конкурентного использования. Не открывайте новый `sql.DB` на каждый запрос. Откройте один пул при старте процесса. Закройте его при остановке процесса.

Обычные методы:

- `Exec` / `ExecContext` — INSERT, UPDATE, DELETE, DDL
- `Query` / `QueryContext` — много строк
- `QueryRow` / `QueryRowContext` — одна строка
- `Prepare` / `PrepareContext` — повторно используемый оператор
- `Begin` / `BeginTx` — транзакция

Сканируйте строки в переменные:

```go
rows, err := db.QueryContext(ctx, `SELECT id, name FROM items WHERE qty > $1`, min)
if err != nil {
    return err
}
defer rows.Close()

for rows.Next() {
    var id int
    var name string
    if err := rows.Scan(&id, &name); err != nil {
        return err
    }
}
if err := rows.Err(); err != nil {
    return err
}
```

Всегда вызывайте `Close` у `Rows`. Всегда проверяйте `rows.Err()` после цикла. `QueryRow` возвращает `sql.ErrNoRows`, когда строки нет. Проверяйте эту ошибку через `errors.Is`.

Столбцы NULL нуждаются в обнуляемых типах: `sql.NullString`, `sql.NullInt64`, `sql.NullTime` или указатель (`*string`). Обычная `string` не может хранить NULL.

Плейсхолдеры зависят от драйвера. PostgreSQL использует `$1`, `$2`. MySQL и SQLite используют `?`. Не меняйте стиль плейсхолдеров без взгляда в документацию драйвера.

`Result` из `Exec` может сообщить `RowsAffected` и `LastInsertId`. `LastInsertId` не переносим. PostgreSQL предпочитает `INSERT ... RETURNING id` и `QueryRow`.

Не игнорируйте ошибки `Scan`, `Close` или `Commit`. Не держите `Rows` открытыми, пока выполняете другой запрос на том же соединении, если это единственное соединение. Закройте или используйте транзакцию.

## Драйверы (например `pgx`, `lib/pq`, SQLite)

Драйвер переводит вызовы `database/sql` в протокол одной базы данных. Драйвер выбирают, когда выбирают базу данных.

**PostgreSQL**

- `github.com/jackc/pgx/v5` — текущий клиент. Используйте `pgx/v5/stdlib`, когда нужен `database/sql`. Используйте `pgxpool` и нативный API `pgx`, когда нужны возможности PostgreSQL и меньше слоёв.
- `github.com/lib/pq` — более старый драйвер `database/sql`. Он в режиме сопровождения. Не начинайте новый проект на `lib/pq`.

Нативный `pgx` даёт COPY, LISTEN/NOTIFY и лучший контроль типов. `database/sql` даёт один API для нескольких баз данных. Многие команды используют `pgx` через `stdlib`, чтобы `sqlx` или инструменты миграций всё ещё работали.

**SQLite**

- `github.com/mattn/go-sqlite3` использует cgo и библиотеку SQLite на C. Он быстрый и полный. Ему нужен компилятор C.
- `modernc.org/sqlite` — порт на чистом Go. Он избегает cgo. Сборка и кросс-компиляция проще. Измеряйте, если нужна последняя доля скорости.

SQLite — один файл. Это хороший выбор для тестов, локальных инструментов и малых приложений. Это слабый выбор для многих писателей на многих хостах. Используйте серверную базу, когда много процессов должны писать сразу.

**MySQL и другие**

Драйверы есть для MySQL, SQL Server и других. API `database/sql` остаётся тем же. Типы, плейсхолдеры и возможности всё равно различаются.

Имена регистрации:

- pgx stdlib: `sql.Open("pgx", dsn)`
- lib/pq: `sql.Open("postgres", dsn)`
- mattn sqlite: `sql.Open("sqlite3", path)`

Читайте README драйвера про формат DSN. URL PostgreSQL выглядят как `postgres://user:pass@host:5432/dbname?sslmode=require`. DSN SQLite выглядят как путь к файлу плюс параметры.

Держите версию драйвера в `go.mod`. Запускайте `go test` после мажорного обновления драйвера. Мажорные обновления могут менять типы по умолчанию (часовые пояса, bytea, UUID).

Не импортируйте два драйвера только чтобы «иметь варианты» в продакшене. Один продукт, один драйвер, один формат DSN.

## Подготовленные операторы и транзакции

Подготовленный оператор разбирает SQL один раз на сервере (или в драйвере), затем выполняется с новыми параметрами. Параметры остаются вне текста SQL. Это правильный способ передавать пользовательские значения.

```go
stmt, err := db.PrepareContext(ctx, `SELECT name FROM items WHERE id = $1`)
if err != nil {
    return err
}
defer stmt.Close()

var name string
err = stmt.QueryRowContext(ctx, id).Scan(&name)
```

`database/sql` может также готовить операторы внутри `Query` в зависимости от драйвера и базы. Явный `Prepare` помогает, когда один и тот же SQL запускают много раз в цикле. Закрывайте оператор.

Транзакция группирует операторы. Все операторы фиксируются или все откатываются.

```go
tx, err := db.BeginTx(ctx, &sql.TxOptions{Isolation: sql.LevelSerializable})
if err != nil {
    return err
}
defer tx.Rollback() // no-op after a successful Commit

if _, err := tx.ExecContext(ctx, `UPDATE accounts SET bal = bal - $1 WHERE id = $2`, amount, fromID); err != nil {
    return err
}
if _, err := tx.ExecContext(ctx, `UPDATE accounts SET bal = bal + $1 WHERE id = $2`, amount, toID); err != nil {
    return err
}
return tx.Commit()
```

`defer tx.Rollback()` — безопасный шаблон. После `Commit` `Rollback` возвращает `sql.ErrTxDone`. Эту ошибку в defer можно игнорировать.

Правила:

- внутри транзакции используйте дескриптор `tx`, а не `db`
- `Stmt` из `db.Prepare` не привязан к вашей транзакции, пока не используете `tx.Stmt` или `tx.Prepare`
- проверяйте каждую ошибку до `Commit`
- выбирайте уровень изоляции намеренно; значение по умолчанию зависит от базы
- держите транзакции короткими; не ждите клик пользователя внутри открытой транзакции

`sql.LevelReadCommitted` и `sql.LevelSerializable` — обычные выборы. Serializable снижает некоторые гонки и может увеличить число повторов. Читайте документацию базы. Go только передаёт запрос изоляции драйверу.

Точки сохранения есть в некоторых базах. `database/sql` не даёт переносимого API точек сохранения. Используйте дополнительный SQL, если они нужны и вы принимаете привязку к поставщику.

Не используйте формат строк, чтобы вставлять значения. Кавычка в имени тогда становится SQL-инъекцией.

## Запросы с учётом контекста

Каждый долгий вызов базы должен принимать `context.Context`. Контекст несёт срок и сигнал отмены. Когда клиент отключается, вы отменяете запрос. Драйвер тогда может остановить работу на сервере, если протокол это позволяет.

Используйте методы `*Context`:

- `PingContext`
- `ExecContext`
- `QueryContext`
- `QueryRowContext`
- `PrepareContext`
- `BeginTx` (первый аргумент — контекст)

```go
ctx, cancel := context.WithTimeout(r.Context(), 3*time.Second)
defer cancel()

row := db.QueryRowContext(ctx, `SELECT name FROM items WHERE id = $1`, id)
```

В HTTP-обработчике начинайте с `r.Context()`. Этот контекст отменяется, когда клиент уходит. Добавьте тайм-аут, если у контекста запроса нет срока.

`QueryRowContext` всё равно возвращает `*sql.Row`. `Scan` — вызов, который ждёт. Если контекст завершён, `Scan` возвращает ошибку контекста (или обёртку драйвера). Используйте `errors.Is(err, context.DeadlineExceeded)` или `errors.Is(err, context.Canceled)`.

`BeginTx` использует контекст для запроса begin и может привязать отмену к транзакции в зависимости от драйвера и версии Go. Если контекст отменён, транзакция не должна продолжаться. Не используйте `tx` повторно после отмены.

Не храните контекст запроса в фоновом работнике. Работник переживает запрос. Выведите новый контекст с тайм-аутом для заданий.

Не передавайте `context.Background()` в обработчике, когда есть `r.Context()`. Background никогда не отменяется от клиента.

`sql.Conn` из `db.Conn(ctx)` — зарезервированное соединение. Закройте его. Используйте его, когда нужно состояние сессии (`SET LOCAL`, временные таблицы). Предпочитайте обычное использование пула, когда состояние сессии не нужно.

## Пул соединений

`sql.DB` — пул. Когда вы вызываете `Query`, пул берёт соединение, выполняет работу и возвращает соединение. В обычном коде сокетами не управляют.

Настраивайте пул так:

```go
db.SetMaxOpenConns(10)
db.SetMaxIdleConns(5)
db.SetConnMaxLifetime(30 * time.Minute)
db.SetConnMaxIdleTime(5 * time.Minute)
```

Значения:

- `MaxOpenConns` — максимум соединений в использовании сразу (0 значит без предела; не используйте 0 в продакшене)
- `MaxIdleConns` — соединения, которые держат открытыми в простое
- `ConnMaxLifetime` — максимальный возраст; полезно, когда прокси закрывает старые соединения
- `ConnMaxIdleTime` — максимальное время простоя, после которого пул закрывает соединение

Если `MaxOpenConns` слишком мал, горутины ждут свободное соединение. Если слишком велик, база отклоняет лишние сессии или замедляется. Сопоставляйте предел с `max_connections` базы и с числом реплик приложения. Пять реплик по 20 открытых соединений — 100 сессий.

`Ping` при старте заполняет хотя бы одно соединение. Всплеск трафика затем растит пул до `MaxOpenConns`.

Проверки здоровья: `PingContext` достаточно для простой проверки живости. Не запускайте тяжёлый запрос на каждый зонд. Некоторые платформы зондируют слишком часто и опустошают пул простоя.

`Stats()` возвращает `sql.DBStats`: открытые соединения, в использовании, в простое, число ожиданий. Логируйте эти значения, когда отлаживаете исчерпание пула.

Нативный `pgxpool` — другой пул. Не оборачивайте `pgxpool` в `database/sql` и одновременно не открывайте второй `sql.DB` к тому же приложению без плана. Один пул на процесс — простое правило.

Не копируйте `sql.DB` по значению так, будто думаете, что дублируете пул. Указатель `sql.DB` — дескриптор. Передавайте `*sql.DB`.

Закрывайте пул при остановке, чтобы процесс чисто сбрасывал сокеты. Запросы в полёте всё равно нуждаются в политике остановки (остановить новую работу, подождать, затем закрыть).

## SQL и ORM (`sqlx`, `ent`, `gorm`) — компромиссы

SQL пишут сами через `database/sql`. Можно добавить тонкий помощник. Можно использовать полный ORM. Каждый шаг скрывает больше SQL и добавляет больше скрытого поведения.

**`database/sql`**

Вы пишете SQL. Вы сканируете столбцы. Вы контролируете каждый запрос. Цена — шаблонный код и аккуратный порядок `Scan`.

**`sqlx` (`github.com/jmoiron/sqlx`)**

`sqlx` расширяет `database/sql`. `Get`, `Select` и `StructScan` заполняют структуры. Именованные запросы используют `:name`. SQL вы всё равно пишете. `sqlx` — тонкий слой. Команды, которым нравится SQL, часто останавливаются здесь.

**`ent`**

`ent` — каркас генерации кода. Схему определяют на Go. Генерируют типизированный клиент. Запросы — код на Go. Инструмент может выпускать миграции. Подходит сильно, когда граф сущностей — продукт. Цена — шаг генерации и кривая обучения.

**`gorm`**

`gorm` — полный ORM. Модели — структуры. Доступны связи, хуки и колбэки. В начале можно писать меньше SQL. Цена — скрытые запросы, загрузки N+1 и неожиданные формы `UPDATE`. SQL, который выпускает GORM, всё равно нужно читать.

Компромиссы:

| Подход | Контроль SQL | Шаблонный код | Неожиданные запросы | Хорошее применение |
| --- | --- | --- | --- | --- |
| `database/sql` | высокий | высокий | низкий | простые хранилища, горячие пути |
| `sqlx` | высокий | средний | низкий | большинство сервисов, которые используют SQL |
| `ent` | средний | низкий после генерации | средний | типизированная область, много связей |
| `gorm` | низкий, пока не принуждаете SQL | низкий | высокий при небрежности | прототипы, CRUD с осторожностью |

Правила:

- сначала выучите `database/sql`
- не выбирайте GORM только чтобы избежать SQL; SQL всё равно отлаживают в продакшене
- используйте `sqlx`, когда сканирование в структуру — единственная боль
- используйте `ent`, когда принимаете генерацию и хотите помощь запросов на этапе компиляции
- измеряйте N+1: цикл `Get` по id — ошибка на каждом слое
- оставляйте сырой SQL для отчётов и обновлений, которые ORM выражает плохо

ORM не снимают транзакции, контексты и пулы. Их всё равно задают. Миграции всё равно пишут (или ревьюят сгенерированные).

## Миграции

Миграция — версионированное изменение схемы. У каждой миграции есть идентификатор и скрипт вверх. У многих инструментов есть и скрипт вниз. Инструмент записывает применённые версии в таблицу.

Используют инструмент вроде:

- `github.com/golang-migrate/migrate`
- `github.com/pressly/goose`
- Atlas (`ariga.io/atlas`)

Рабочий процесс один:

1. Напишите новый файл миграции (SQL или сгенерированный SQL).
2. Примените его к разработке.
3. Запустите тесты.
4. Примените те же файлы к продакшену по порядку.
5. Не редактируйте миграцию, которую продакшен уже применил. Добавьте новую миграцию.

Примеры имён:

```text
0001_init.up.sql
0001_init.down.sql
0002_items_qty.up.sql
0002_items_qty.down.sql
```

Скрипты вверх должны быть безопасны для однократного запуска. Скрипты вниз — для разработки и аварийного отката. Некоторые команды никогда не запускают вниз в продакшене. Они добавляют прямую миграцию, которая исправляет проблему. Такая политика допустима, если её записывают.

Расширение и сжатие — безопасный шаблон для живых систем:

- добавьте новый столбец (обнуляемый или со значением по умолчанию)
- выпустите код, который пишет и в старое, и в новое
- заполните данные
- выпустите код, который читает новый столбец
- удалите старый столбец в более поздней миграции

Не удаляйте столбец в том же выпуске, который его ещё читает.

Запускайте миграции из CI или из контролируемого задания. Не давайте каждой реплике запускать миграции при старте без блокировки. Две реплики могут гоняться. `migrate` и `goose` могут использовать блокировку базы. Читайте документацию инструмента.

Держите миграции в репозитории. Ревьюйте их как код. Тестируйте на одноразовой базе. SQLite в тестах недостаточно, если используете возможности PostgreSQL. Используйте тот же продукт в интеграционных тестах.

Не смешивайте вручную правленную схему продакшена с версиями, которыми управляет инструмент. Таблица версий тогда лжёт.

## Redis / кэши (необязательно)

Кэш хранит данные, которые дорого загружать или вычислять. Redis — удалённое хранилище в памяти. Обычные клиенты Go включают `github.com/redis/go-redis/v9`. Стандартная библиотека не включает клиент Redis.

Используйте кэш, когда:

- много чтений попадают в одну строку или один JSON
- данные могут быть слегка устаревшими (задаёте TTL)
- база данных — источник истины

Не используйте Redis как единственную копию важных данных, пока не проектируете это (и не принимаете пределы устойчивости). Перезапуск или сброс не должны терять денежные записи.

Шаблон cache-aside:

1. Прочитайте кэш.
2. При промахе прочитайте базу.
3. Запишите кэш с TTL.
4. Верните значение.

```go
func (s *Store) GetItem(ctx context.Context, id string) (Item, error) {
    key := "item:" + id
    if b, err := s.rdb.Get(ctx, key).Bytes(); err == nil {
        var it Item
        if err := json.Unmarshal(b, &it); err == nil {
            return it, nil
        }
    }
    it, err := s.dbGet(ctx, id)
    if err != nil {
        return Item{}, err
    }
    if b, err := json.Marshal(it); err == nil {
        _ = s.rdb.Set(ctx, key, b, 5*time.Minute).Err()
    }
    return it, nil
}
```

При записи удалите или обновите ключ. Устаревший кэш — обычная ошибка. Короткий TTL ограничивает ущерб.

Другие применения Redis: лимиты частоты, блокировки, блобы сессий, pub/sub. У каждого применения есть режимы отказа. Блокировка должна истекать. Лимит частоты не должен блокировать проверки здоровья. Pub/sub — не устойчивая очередь.

`sync.Map` или охраняемая `map` — кэш внутри процесса. Он не разделяется между репликами. Redis разделяется между репликами. Выбирайте меньший инструмент, который работает.

Всегда передавайте `context.Context` в вызовы Redis. Задавайте тайм-ауты. Redis не должен вешать обработчик без срока.

Этот раздел необязателен. Сначала завершите SQL. Добавляйте кэш, когда измерение показывает горячий ключ.

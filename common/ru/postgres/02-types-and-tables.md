# 2. Типы и таблицы

## Описание

Эта тема показывает частые типы данных и как создавать таблицы в PostgreSQL 16 и PostgreSQL 17. Вы узнаёте целые, точные числовые значения, числа с плавающей точкой, текст, boolean, дату и время, `uuid` и `bytea`. Также узнаёте `NULL`, `CREATE TABLE`, столбцы identity, ограничения, значения по умолчанию и наследование таблиц.

Сначала завершите тему 1. Нужно подключаться через `psql` и создавать базу. Завершите эту тему до написания соединений и прикладного SQL.

Используйте один термин для каждого понятия. Тип — имя, которое PostgreSQL даёт набору значений. Таблица — именованный набор строк. Ограничение — правило, которому должна удовлетворять строка. Столбец identity — столбец, который PostgreSQL заполняет из последовательности. Наследование копирует определения столбцов из родительской таблицы. Для денег предпочитайте `numeric`. Для моментов времени предпочитайте `timestamptz`. Для строк предпочитайте `text`. Для новых дизайнов предпочитайте композицию (внешние ключи), а не наследование.

## Целые, `numeric` и типы с плавающей точкой

В PostgreSQL три двоичных целых типа:

| Тип | Псевдонимы | Размер | Диапазон |
| --- | --- | --- | --- |
| `smallint` | `int2` | 2 байта | -32768 до 32767 |
| `integer` | `int`, `int4` | 4 байта | около -2.1e9 до 2.1e9 |
| `bigint` | `int8` | 8 байт | около -9e18 до 9e18 |

`integer` — обычный выбор для ключей и счётчиков, которые умещаются в 32 бита. Используйте `bigint` для высоконагруженных identity-ключей и больших счётчиков. Используйте `smallint` только когда набор мал и замкнут и вам важна экономия места.

Переполнение вызывает ошибку:

```sql
SELECT 32767::smallint + 1::smallint;
```

Целые литералы пишите без кавычек: `42`. Заквотированный `'42'` — неизвестный тип или текст, пока не будет приведения.

Типы serial (`smallserial`, `serial`, `bigserial`) — не настоящие типы. Они создают последовательность и значение по умолчанию. Для новых таблиц предпочитайте столбцы identity.

Целое деление усекает к нулю:

```sql
SELECT 5 / 2;      -- 2 (integer)
SELECT 5::numeric / 2;
```

`numeric` и `decimal` в PostgreSQL — один тип. Они хранят точные значения по основанию 10. Задаёте точность и масштаб:

```sql
amount numeric(12, 2)
```

Используйте `numeric` для денег и для значений, которые не должны терять цифры. Не используйте `real` или `double precision` для денег. Эти типы — двоичная плавающая точка. Они приблизительные.

```sql
SELECT 0.1::numeric + 0.2::numeric;
SELECT 0.1::float8 + 0.2::float8;
```

`real` (`float4`) — 4 байта. `double precision` (`float8`) — 8 байт. Используйте их для научных измерений и для значений, где небольшая ошибка допустима.

Используйте `bigint` для `id`, когда таблица может вырасти больше двух миллиардов строк. Позже менять `integer` на `bigint` — тяжёлая перезапись.

## Текст, `boolean`, дата/время, `uuid`, `bytea`

Для строк предпочитайте `text`. `varchar(n)` — это `text` с проверкой длины. `char(n)` дополняет пробелами. Не используйте `char(n)` для новой работы.

```sql
SELECT pg_typeof('hello');
SELECT 'hello'::varchar(3);
```

Строковые литералы используют одинарные кавычки. Dollar-quoting — тема 3.

`boolean` хранит `true`, `false` или `NULL`. На вход принимает `t`/`f`, `true`/`false`, `yes`/`no`, `1`/`0`. В SQL предпочитайте `true` и `false`.

```sql
SELECT true IS TRUE;
SELECT NOT false;
```

Типы даты и времени:

| Тип | Смысл |
| --- | --- |
| `date` | календарная дата |
| `time` | время суток без часового пояса |
| `timetz` | время суток с часовым поясом (для новой работы не используйте) |
| `timestamp` | дата и время без часового пояса |
| `timestamptz` | дата и время с часовым поясом (хранится в UTC) |
| `interval` | длительность |

Для моментов предпочитайте `timestamptz`. Для одного календарного дня предпочитайте `date`. Для длительностей предпочитайте `interval`.

```sql
SELECT now();
SELECT DATE '2026-09-13';
SELECT TIMESTAMPTZ '2026-09-13 12:00:00+00';
SELECT INTERVAL '1 day 2 hours';
```

`uuid` хранит 128-битный идентификатор. Значения генерирует `gen_random_uuid()` (встроен с PostgreSQL 13):

```sql
SELECT gen_random_uuid();
```

`bytea` хранит сырые байты. Используйте для небольших двоичных значений. Не кладите большие файлы в `bytea` без плана по размеру. Для больших блобов предпочитайте объектное хранилище.

```sql
SELECT E'\\xDEADBEEF'::bytea;
```

`json` и `jsonb` — тема 4. Массивы — тема 4. Этот раздел — скалярные типы, которые большинству таблиц нужны сначала.

## `NULL` и трёхзначная логика

`NULL` значит «неизвестно» или «отсутствует». Это не строка `'null'`. Это не `0`. Это не пустая строка.

SQL использует трёхзначную логику: `true`, `false` и `unknown`. Любое сравнение с `NULL` даёт `unknown`, не `true`.

```sql
SELECT 1 = NULL;          -- NULL
SELECT NULL = NULL;       -- NULL
SELECT NULL IS NULL;      -- true
SELECT NULL IS NOT NULL;  -- false
```

`WHERE` оставляет строки, где условие — `true`. Предложение `WHERE col = NULL` не оставляет ни одной строки. Пишите `WHERE col IS NULL`.

`AND` и `OR` с `NULL`:

```sql
SELECT true AND NULL;     -- NULL
SELECT false AND NULL;    -- false
SELECT true OR NULL;      -- true
SELECT false OR NULL;     -- NULL
```

Списки `IN` и `NOT IN`, которые содержат `NULL`, — частая ловушка. `x NOT IN (1, NULL)` никогда не бывает `true`.

Ограничения `CHECK` считают `unknown` успехом. `CHECK (qty > 0)` допускает `qty` `NULL`, если нет ещё и `NOT NULL`.

Уникальные ограничения в PostgreSQL допускают несколько `NULL` в одностолбцовом уникальном индексе (каждый `NULL` для уникальности различен). Уникальное ограничение на нескольких столбцах считает `NULL` в этом столбце различным. Знайте правило, прежде чем моделировать «необязательный уникальный email».

Агрегатные функции игнорируют входы `NULL`, кроме `COUNT(*)`. `COUNT(col)` пропускает `NULL`. `SUM` без ненулевых значений — `NULL`.

Используйте `COALESCE`, когда нужна подстановка (тема 4). Используйте `NOT NULL`, когда значение должно существовать.

## `CREATE TABLE` и `GENERATED ALWAYS AS IDENTITY`

`CREATE TABLE` задаёт имя таблицы, столбцы и ограничения таблицы.

```sql
CREATE TABLE customers (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email      text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);
```

Порядок столбцов — тот, который использует `SELECT *`. В прикладном SQL называйте столбцы явно.

Полезные предложения:

- `IF NOT EXISTS` — не падать, если таблица уже есть
- `TEMPORARY` / `TEMP` — таблица сессии; удаляется в конце сессии (или транзакции)
- `UNLOGGED` — без WAL; быстрее; не устойчива к сбою; не реплицируется
- `INHERITS` — см. раздел про наследование
- `PARTITION BY` — тема 10

```sql
CREATE TEMP TABLE scratch (id int);
CREATE UNLOGGED TABLE cache_keys (k text PRIMARY KEY, v text);
```

`TEMP` — для черновых данных сессии. `UNLOGGED` — только когда данные можно потерять.

`CREATE TABLE ... AS SELECT` строит таблицу из запроса. Ограничения не копирует.

Столбец identity использует последовательность. PostgreSQL владеет последовательностью и привязывает её к столбцу.

```sql
CREATE TABLE orders (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    note text
);

INSERT INTO orders (note) VALUES ('first') RETURNING id;
```

Два режима:

- `GENERATED ALWAYS AS IDENTITY` — отвергает значение от пользователя, если нет `OVERRIDING SYSTEM VALUE`
- `GENERATED BY DEFAULT AS IDENTITY` — использует последовательность, когда клиент столбец опускает

Для новых ключей предпочитайте `ALWAYS`. Для таблиц, которые могут расти, предпочитайте identity на `bigint`.

`serial` всё ещё работает. Это default плюс последовательность. Последовательность проще случайно отвязать. Для новых таблиц используйте identity.

`ALTER TABLE` позже добавляет столбцы и ограничения. Некоторые формы `ALTER TABLE` переписывают таблицу. Тестируйте на копии.

`DROP TABLE name;` удаляет таблицу. `DROP TABLE name CASCADE;` также удаляет зависимые объекты. Используйте `CASCADE` только когда именно это и хотите.

Именуйте таблицы в единственном или множественном числе — как решит команда. Используйте одну форму. Используйте `snake_case`.

## Первичный ключ, unique, check и внешние ключи

**Первичный ключ** однозначно идентифицирует строку. Он `NOT NULL` и уникален. У таблицы может быть один первичный ключ. Первичный ключ может использовать больше одного столбца (составной).

Ограничение **unique** запрещает дубликаты в перечисленных столбцах. Оно может допускать `NULL` так, как описано выше.

Ограничение **check** — булево выражение, которому должна удовлетворять каждая строка (или оставить `unknown`).

**Внешний ключ** говорит, что значение должно совпасть с уникальным ключом (обычно первичным) в другой таблице или быть `NULL`, если столбец допускает `NULL`.

```sql
CREATE TABLE customers (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email text NOT NULL UNIQUE
);

CREATE TABLE orders (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL REFERENCES customers (id),
    total       numeric(12, 2) NOT NULL CHECK (total >= 0)
);
```

Форма на уровне таблицы нужна для многостолбцовых ключей:

```sql
PRIMARY KEY (id, created_on),
FOREIGN KEY (customer_id) REFERENCES customers (id)
```

Действия внешнего ключа:

- `NO ACTION` / `RESTRICT` — отвергнуть удаление или обновление родителя, пока есть дети
- `CASCADE` — удалить или обновить детей
- `SET NULL` — поставить в дочернем столбце `NULL`
- `SET DEFAULT` — поставить в дочернем столбце его default

Пишите `ON DELETE` и `ON UPDATE` при создании ключа. По умолчанию — `NO ACTION`.

PostgreSQL создаёт индекс для первичных ключей и уникальных ограничений. Индекс на столбце внешнего ключа автоматически не создаёт. Добавьте этот индекс, когда соединяете или удаляете родителей (тема 5).

`NOT NULL` — ограничение. Ставьте его на каждый столбец, у которого должно быть значение.

Не используйте натуральный ключ как единственный ключ, когда бизнес-значение может меняться. Не опускайте внешний ключ и «проверяйте только в приложении», если база может это обеспечить.

## Значения по умолчанию и `now()`

Default заполняет столбец, когда `INSERT` этот столбец опускает.

```sql
CREATE TABLE events (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    created_at timestamptz NOT NULL DEFAULT now(),
    source     text        NOT NULL DEFAULT 'web'
);
```

`now()` — время начала транзакции как `timestamptz`. Все вызовы `now()` в одной транзакции возвращают одно значение. `clock_timestamp()` возвращает настенные часы на момент вызова. `statement_timestamp()` возвращает начало текущего оператора.

```sql
BEGIN;
SELECT now();
SELECT pg_sleep(2);
SELECT now(), clock_timestamp();
COMMIT;
```

Используйте `now()` (или `CURRENT_TIMESTAMP`, SQL-имя той же идеи) для «когда эта строка создана в этой транзакции». Используйте `clock_timestamp()` только когда нужно реальное прошедшее время внутри одной транзакции.

Выражение default выполняется в момент вставки. Это не триггер. Сгенерированный столбец — другое (тема 9).

`DEFAULT` может вызывать функцию: `gen_random_uuid()`, `now()` или пользовательскую функцию. Функция должна быть разрешена роли, которая вставляет.

`INSERT ... DEFAULT VALUES` вставляет строку только из default. `UPDATE ... SET col = DEFAULT` восстанавливает выражение default.

Не храните `now()` только в приложении, если база должна владеть временем создания. Двое часов приложения могут расходиться. Не используйте `timestamp` `DEFAULT now()`, когда нужен часовой пояс.

## Наследование таблиц (знать, что есть; предпочитать композицию)

Наследование таблиц копирует столбцы из родительской таблицы в дочернюю.

```sql
CREATE TABLE vehicles (
    id    bigint GENERATED ALWAYS AS IDENTITY,
    vin   text NOT NULL
);

CREATE TABLE cars (
    doors int NOT NULL
) INHERITS (vehicles);
```

У `cars` есть `id`, `vin` и `doors`. `INSERT` в `cars` также делает строку видимой в `SELECT` из `vehicles`, если не использовать `ONLY`:

```sql
SELECT * FROM vehicles;
SELECT * FROM ONLY vehicles;
```

Наследование выглядит полезным для моделей «is-a». У него жёсткие пределы:

- Уникальные ограничения и первичные ключи родителя не покрывают детей как один глобальный уникальный набор так, как ожидают новички.
- Внешние ключи на родителя не видят дочерние строки как родительские.
- Индексы не покрывают всю иерархию как один индекс.
- Декларативное секционирование (тема 10) — поддерживаемый способ разрезать большую таблицу.

Предпочитайте композицию. Общие столбцы кладите в одну таблицу. Другие таблицы указывайте на неё внешним ключом. Пример: `vehicles` как одна таблица со столбцом `kind`, или `cars.vehicle_id REFERENCES vehicles (id)`.

Знайте, что `INHERITS` существует, чтобы читать старые схемы и документацию. Не начинайте новый дизайн с наследования. Не смешивайте наследование с декларативным секционированием на одной таблице.

PostgreSQL 16 и 17 всё ещё поддерживают наследование. Новые возможности и инструменты нацелены на секционированные таблицы, а не на деревья наследования.

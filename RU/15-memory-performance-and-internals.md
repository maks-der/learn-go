# 15. Память, производительность и внутреннее устройство

## Описание

Эта тема объясняет, как Go хранит значения, как сборщик мусора освобождает память и как компилятор решает, где живёт значение. Вы пишете более быстрые программы, когда понимаете срезы, карты, строки, аллокацию и выравнивание. Вы также узнаёте пределы `unsafe` и пределы оптимизаций компилятора.

Для каждого понятия используйте один термин. Аллокация — это резервирование памяти. Анализ побега — проход компилятора, который выбирает стек или кучу. Сборщик мусора (`GC`) освобождает объекты кучи, до которых программа больше не может добраться. Не считайте микробенчмарки доказательством без `testing.B` и ясной гипотезы.

## Стек и куча; анализ побега

У каждой горутины есть стек. Стек хранит локальные переменные, которые не убегают. Аллокация на стеке дешёвая. Среда выполнения растит и сжимает стек, когда горутине нужно больше места.

Куча хранит объекты, которые живут после возврата из функции, или те, которые компилятор не может оставить на стеке. Сборщик мусора управляет кучей. Аллокация в куче дороже аллокации на стеке. Объекты кучи добавляют работу `GC`.

Анализ побега — проход компилятора, который решает место. Компилятор не следует простому правилу «`new` значит куча». Значение, созданное как `&T{}`, может остаться на стеке, если указатель никто не удерживает. Локальная переменная может уйти в кучу, если вы возвращаете её адрес.

Обычные причины, по которым значение убегает в кучу:

- вы возвращаете указатель на значение
- вы кладёте значение в значение интерфейса (интерфейсу может понадобиться объект в куче)
- вы отправляете значение в канал, который переживает функцию
- вы сохраняете указатель в структуре или срезе, которые уже живут в куче
- вы замыкаете переменную в горутине, которая работает после возврата из функции

Смотрите анализ побега так:

```text
go build -gcflags=-m
```

Добавьте `-m` дважды для большей детализации: `-gcflags="-m -m"`. Компилятор печатает строки вроде `moved to heap` и `escapes to heap`. Читайте эти строки как подсказки. Это не стабильный публичный API. Формулировки могут меняться между версиями Go.

```go
func makeInt() *int {
    x := 42
    return &x // x escapes
}

func sum(a, b int) int {
    return a + b // a and b stay on the stack
}
```

Не принуждайте аллокацию в куче без причины. Не прячьте указатели от компилятора. Пишите ясный код. Сначала профилируйте. Затем меняйте аллокацию только когда профиль показывает цену.

Большой локальный массив тоже может быть дорог на стеке. Очень большой кадр стека может вызвать рост стека. Для больших буферов используйте `make([]byte, n)` и примите срез в куче или повторно используйте буфер.

Стек не разделяется между горутинами. Не берите адрес локальной переменной и не передавайте этот указатель другой горутине, пока время жизни не ясно. Значение может сдвинуться при росте стека. Среда выполнения обновляет указатели, о которых знают `GC` и компилятор. Не прячьте указатели от среды выполнения (см. `unsafe`).

## Сборщик мусора (обзор: конкурентный, трёхцветный)

Go использует конкурентный сборщик мусора. `GC` большую часть работы выполняет одновременно с вашими горутинами. `GC` всё же использует короткие паузы stop-the-world (`STW`) для некоторых фаз. На текущих версиях Go эти паузы малы. Нельзя опираться на конкретную длину паузы.

Сборщик использует алгоритм трёхцветной пометки. У каждого объекта есть цвет в цикле пометки:

- белый: ещё не доказано, что достижим
- серый: достижим, но `GC` ещё не просмотрел все указатели внутри него
- чёрный: достижим, и `GC` просмотрел его указатели

`GC` начинает с корней. Корни включают глобальные переменные, стеки и регистры. `GC` помечает достижимые объекты. В конце цикла белые объекты — мусор. Затем `GC` подметает неиспользуемую память и возвращает её аллокатору.

Поскольку программа меняет кучу во время конкурентной пометки, среда выполнения использует барьер записи. Барьер записи фиксирует обновления указателей, чтобы `GC` не пропустил объект. Вы сами барьер записи не вызываете. Его вставляет компилятор.

`GC` в Go — не поколенческий сборщик в классическом смысле young/old. Это неперемещающий конкурентный mark-sweep сборщик. Адреса объектов из-за `GC` не меняются. Указатель можно передать в C через cgo на время, пока вы его закрепляете или держите достижимым. Всё равно считайте cgo отдельной темой.

Пейсер `GC` решает, когда начать цикл. Среда выполнения смотрит на размер кучи и скорость аллокации. Мягкую цель можно задать через `GOGC` (по умолчанию 100). `GOGC=100` значит, что куча может вырасти примерно до двойного живого размера после цикла, прежде чем начнётся следующий цикл. `GOGC=off` отключает `GC`. Не отключайте `GC` в продакшене.

`GOMEMLIMIT` (Go 1.19 и новее) задаёт мягкий предел памяти. Среда выполнения старается держать суммарную память около этого предела. Используйте его, когда процесс должен оставаться внутри лимита контейнера. Не используйте его вместо корректной программы.

`runtime.GC()` запускает цикл сборки мусора и ждёт его завершения. Используйте его в тестах или бенчмарках, когда нужно известное состояние. Не вызывайте его на частом пути запроса.

`runtime.ReadMemStats` и `testing.B` сообщают об аллокациях. Профили `pprof` показывают объекты кучи. Измеряйте, прежде чем настраивать `GC`.

## Внутреннее устройство `slice`, `map` и `string`

Срез — дескриптор с тремя полями: указатель на массив, длина и ёмкость. Дескриптор — малое значение. Копия среза копирует дескриптор. Копия разделяет тот же backing-массив.

```go
s := make([]int, 2, 4) // pointer, len=2, cap=4
t := s                 // same array, same len, same cap
t[0] = 9               // s[0] is also 9
```

`append` может писать в неиспользованную ёмкость. Если ёмкость заполнена, `append` выделяет новый массив, копирует элементы и возвращает новый дескриптор. Старый массив остаётся живым, если на него ещё указывает какой-либо срез.

Строка — дескриптор с двумя полями: указатель на байты и длина. У строки нет ёмкости. Байты неизменяемы. Две строки могут разделять backing-массив. Подстрока `s[a:b]` может разделять байты с `s`.

Карта — хеш-таблица. С Go 1.24 среда выполнения реализует карты через Swiss tables. Языковые операции те же: `make`, вставка, поиск, удаление. Заголовок, который вы копируете, — значение, похожее на указатель. Копия значения карты разделяет ту же таблицу. Нильвая карта разрешает чтение и возвращает нулевое значение. Запись в нильвую карту вызывает panic.

Порядок итерации по карте случайный. Не опирайтесь на последовательность ключей. Семя хеша и раскладка таблицы могут меняться между версиями.

```text
slice:  [ ptr | len | cap ] --> array elements
string: [ ptr | len ]       --> immutable bytes
map:    pointer --> hash table (Swiss tables in Go 1.24 and later)
```

`len` и `cap` у среза — `O(1)`. `len` у карты — `O(1)`. Поиск в карте в среднем `O(1)`. Худший случай зависит от ключей и реализации хеша. Не считайте карту упорядоченным списком.

Срез структур хранит структуры в одном массиве. Срез указателей хранит указатели. Срез указателей может быть меньше, когда структуры велики, но добавляет объекты в куче и сканирование указателей для `GC`.

Очищайте срез или карту встроенной `clear` (Go 1.21 и новее). `clear(s)` обнуляет элементы среза `s` и сохраняет длину. `clear(m)` удаляет все ключи карты `m`.

## Неизменяемость строк и преобразования `[]byte`

Строка не может изменить свои байты. Оператор вроде `s[0] = 'A'` не компилируется. Неизменяемость позволяет среде выполнения разделять backing-массивы между строками. Она также делает безопасным копирование строк как дескрипторов.

Преобразование между `string` и `[]byte` копирует байты в безопасной поддерживаемой форме:

```go
b := []byte("hello") // copy of the bytes
s := string(b)       // copy of the bytes
```

Копия стоит времени и памяти. В горячем цикле повторные преобразования аллоцируют. Предпочитайте `[]byte` для буферов, которые вы меняете. Предпочитайте `string` для ключей, текстовых API и значений, которые вы не меняете.

`strings.Builder` собирает строку растущим буфером. `Builder.String` может разделять буфер. Не используйте builder после вызова `String`, если вы ещё пишете в builder. Читайте документацию `strings.Builder` для текущих правил.

`bytes.Buffer` — писатель, который хранит байты. Используйте его, когда нужен `io.Writer`. Используйте `strings.Builder`, когда собираете только строку.

Пакет `unsafe` даёт преобразования `unsafe.String` и `unsafe.Slice` без копии. Эти преобразования допустимы только если вы соблюдаете правила неизменяемости. Если вы преобразуете `[]byte` в `string` без копии, срез после этого менять нельзя. Поздняя запись меняет строку на месте и ломает модель памяти языка. Не используйте эти преобразования, пока не можете сформулировать правила времени жизни. Предпочитайте обычное преобразование.

Range по строке даёт руны (кодовые точки Unicode) и индексы байтов. Индексация строки даёт байт. Преобразование строки в `[]rune` копирует кодовые точки. Выбирайте форму, которая соответствует задаче.

```go
s := "Gö"
fmt.Println(len(s))      // bytes
fmt.Println(len([]rune(s))) // runes
```

Не храните секреты в строках, если их нужно стереть. Байты строки перезаписать нельзя. Используйте `[]byte` и перезапишите срез, когда секрет нужно очистить.

## Код с учётом аллокаций (`sync.Pool`, заранее заданный размер среза)

Код с учётом аллокаций снижает аллокации в куче на горячих путях. Сначала всё равно пишите ясный код. Аллокацию меняйте после того, как профиль или бенчмарк показал цену.

Задавайте размер среза заранее, когда знаете длину или хорошую ёмкость:

```go
out := make([]T, 0, len(in))
for _, v := range in {
    if keep(v) {
        out = append(out, v)
    }
}
```

`make([]T, 0, n)` избегает многих аллокаций роста. `make([]T, n)` правилен, когда вы задаёте каждый индекс. Не угадывайте огромную ёмкость, которую никогда не используете. Большой неиспользуемый `cap` держит живым большой массив.

Повторно используйте буферы. Функция, которая кодирует JSON или читает файл, может принять `[]byte` и вернуть срезанный префикс:

```go
func appendJSON(buf []byte, v any) ([]byte, error) {
    // encode into buf, grow if needed, return the new slice
    return buf, nil
}
```

`sync.Pool` хранит временные объекты для повторного использования. Пул может выбросить объекты в любой момент, в том числе во время `GC`. `Get` может вернуть новый объект. Объект нужно сбросить перед повторным использованием.

```go
var bufPool = sync.Pool{
    New: func() any {
        b := make([]byte, 0, 1024)
        return &b
    },
}

func withBuf(fn func(buf *[]byte)) {
    p := bufPool.Get().(*[]byte)
    *p = (*p)[:0]
    defer bufPool.Put(p)
    fn(p)
}
```

Правила для `sync.Pool`:

- используйте его для короткоживущих объектов с высокой текучестью
- не используйте его как кэш важных данных
- сбрасывайте каждый объект, который получаете
- кладите тот же тип, который получаете
- не считайте, что объект останется в пуле

Другие советы по аллокациям:

- предпочитайте `strconv.AppendInt` и помощники `append` пакета `bytes` формату, который выделяет новую строку
- избегайте `+` для строк в цикле
- передавайте указатель на большую структуру, когда функции копия не нужна
- не храните указатели только чтобы избежать копии, когда структура мала; объект в куче и сканирование `GC` могут стоить дороже
- используйте `slices.Grow` или `slices.Clip`, когда эти помощники подходят задаче

Измеряйте так:

```text
go test -bench=. -benchmem
```

Не добавляйте `sync.Pool` только потому, что статья его упомянула. Добавляйте его, когда `benchmem` и профили показывают аллокацию одной и той же формы объекта на частом пути.

## Пакет `unsafe` (знать опасности)

Пакет `unsafe` позволяет сломать систему типов. Компилятор и `GC` предполагают, что вы соблюдаете задокументированные правила. Если вы их ломаете, программа может упасть, испортить память или неверно скомпилироваться после обновления Go.

`unsafe.Pointer` — тип указателя, который можно преобразовывать в другие типы указателей и обратно. Преобразование допустимо только в случаях, которые перечисляет документация. Обычные законные шаблоны:

- преобразовать `*T` в `unsafe.Pointer` и обратно в `*T`
- преобразовать `unsafe.Pointer` в `uintptr` для арифметики, затем сразу обратно в `unsafe.Pointer` в том же выражении
- использовать `unsafe.Sizeof`, `unsafe.Alignof` и `unsafe.Offsetof` для фактов о раскладке
- использовать `unsafe.String`, `unsafe.StringData`, `unsafe.Slice` и `unsafe.SliceData` с их задокументированными предусловиями

```go
n := unsafe.Sizeof(int32(0)) // 4 on current ports
```

Не храните `uintptr` и не используйте его позже как указатель. `GC` не считает `uintptr` указателем. Объект могут собрать. Целое тогда не удерживает объект живым. Не прячьте указатель в целом.

Не используйте `unsafe`, чтобы читать неэкспортируемые поля другого пакета. Раскладка может измениться. Инструмент `go vet` сообщает о некоторых плохих шаблонах `unsafe`. `vet` ловит не каждую ошибку.

`unsafe` не делает Go системным языком с ручным `free`. Сборщик мусора остаётся. Объекты всё равно нужно держать достижимыми, пока вы используете указатели на них.

Допустимые причины читать код с `unsafe`:

- вы изучаете стандартную библиотеку
- вы пишете пакет, который должен стыковаться с C ABI, и принимаете цену
- вы используете хорошо проверенный помощник, например помощники указателей `sync/atomic`, которые внутри оборачивают unsafe

Недопустимые причины:

- вы хотите, чтобы программа работала быстрее без профиля
- вы хотите избежать копии, которую язык уже делает дешёвой
- вы хотите изменить строку

Для этого справочника нужный навык — узнавать опасность, а не изобретать новые преобразования `unsafe`. Если задание просит использовать `unsafe`, оставайтесь внутри задокументированных преобразований.

## Выравнивание и заполнение структур

ЦП и ABI требуют выравнивания. Тип размера 8 часто нуждается в адресе, кратном 8. Компилятор вставляет байты заполнения, чтобы каждое поле начиналось со правильного смещения.

```go
type Bad struct {
    A bool  // 1 byte
    // 7 bytes padding on a typical 64-bit port
    B int64 // 8 bytes
}

type Good struct {
    B int64
    A bool
    // 7 bytes padding at the end so that the struct size is a multiple of 8
}
```

У `Good` всё ещё есть заполнение в конце. Размер структуры кратен выравниванию структуры. Тогда массив `Good` сохраняет выравнивание каждого элемента.

Порядок полей меняет заполнение. Ставьте поля от большего выравнивания к меньшему, когда важен размер. Не переставляйте экспортируемые поля структуры, которую кодируете двоичным форматом, зависящим от раскладки. Не переставляйте поля только ради стиля, когда профиль памяти этого не просит.

`unsafe.Alignof(v)` — выравнивание `v`. `unsafe.Offsetof(s.Field)` — смещение поля. `unsafe.Sizeof(v)` — размер включая заполнение.

Атомарные операции и некоторые обращения к оборудованию требуют выровненных адресов. Типы `sync/atomic` вроде `atomic.Int64` берут выравнивание на себя. Если вы встраиваете `int64` и используете `atomic.AddInt64` на поле, поле должно быть выровнено по 64 битам. На 32-битных портах это реальный риск. Предпочитайте `atomic.Int64`.

`bool` занимает один байт. Указатель занимает 4 или 8 байт в зависимости от архитектуры. Строка — два слова размера указателя. Срез — три слова размера указателя. Эти размеры объясняют, почему структура из многих малых полей плюс один указатель может тратить место при плохом порядке полей.

Пустые структуры `struct{}` имеют размер ноль. Поле типа `struct{}` может разделять адрес со следующим полем. Это полезно в множестве `map[K]struct{}`. Не добавляйте поле нулевого размера в середину структуры, пока не знаете эффект на раскладку.

## Оптимизации компилятора, на которые можно опираться (и те, на которые нельзя)

Компилятор Go применяет оптимизации. Некоторые достаточно стабильны: можно писать код в обычном стиле и ждать хороший результат. Другие меняются между версиями. Не пишите тёмный код, чтобы принудить оптимизацию.

Оптимизации, на которые обычно можно опираться:

- **подстановка малых функций** — короткая функция часто встраивается в вызывающий код; держите функции малыми и простыми
- **анализ побега** — значения, которые не убегают, остаются на стеке
- **устранение проверки границ в простых циклах** — цикл вида `for i := 0; i < len(s); i++` с `s[i]` часто теряет повторные проверки границ
- **удаление мёртвого кода** — код, недостижимый после свёртки констант, может исчезнуть
- **свёртка констант** — `2 * 3` становится `6` на этапе компиляции
- **девиртуализация в ограниченных случаях** — конкретный тип, лежащий в интерфейсе так, что компилятор это видит, может стать прямым вызовом

Пишите обычные ясные циклы. Не разворачивайте циклы вручную, пока бенчмарк не докажет выигрыш. Компилятор и ЦП уже обрабатывают многие простые циклы.

Оптимизации, на которые опираться нельзя:

- конкретная функция всегда встраивается (комментарий, вызов интерфейса или большое тело могут запретить подстановку)
- конкретная аллокация всегда остаётся на стеке
- порядок итерации карты или момент роста карты
- момент цикла `GC`
- заданный коэффициент роста `append` (политика роста может измениться)
- точный выбор инструкций или использование регистров
- тот же текст `gcflags=-m` после обновления
- что `sync.Pool` сохранит объект через `GC`
- монотонные детали `time.Now` для безопасности (для секретов используйте `crypto/rand`)

ABI и битовые шаблоны указателей — не контракт уровня пользователя. Не разбирайте свой стек. Не опирайтесь на размер `int`, кроме как через сам `int` (`int` не меньше 32 бит; на 64-битных портах это 64 бита).

Режимы сборки меняют результат. `-race` добавляет лишнюю память и более медленный код. `-gcflags=all=-l` отключает подстановку. Отладочная сборка с дополнительными проверками — не продакшен-двоичный файл. Бенчмаркьте с теми же флагами, которые отправляете в продакшен.

Можно читать заметки о подстановке и побеге:

```text
go build -gcflags="-m"
```

Можно дизассемблировать:

```text
go build -o app .
go tool objdump -s SomeFunc app
```

Используйте `objdump`, чтобы учиться, а не чтобы привязать исходник к одной последовательности инструкций.

Практическое правило: пишите ясную версию. Измеряйте. Меняйте алгоритм (меньше работы, меньше аллокаций, лучшая раскладка данных). Не превращайте алгоритм в нечитаемую форму ради причуды компилятора.

## Обзор темы

Эти вопросы не повторяют вопросы из разделов выше. Они охватывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Опишите жизнь локальной переменной от аллокации до повторного использования её памяти. Охватите стек, кучу, анализ побега и цвета `GC`.
2. Чем различаются дескрипторы среза, строки и карты и что копирует присваивание в каждом случае?
3. Когда преобразуют между `string` и `[]byte`, а когда оставляют один тип на весь конвейер?
4. Какие правила не дают `sync.Pool` и `unsafe` стать тихими ошибками продакшена?
5. Коллега переставляет поля структуры, добавляет `unsafe` и ставит `GOGC=off` ради скорости. Какие факты вы используете, чтобы отклонить каждое изменение?

#### Простые практические задания

1. Создайте модуль `example.com/memx`. Добавьте демонстрацию роста среза, демонстрацию преобразования строк и демонстрацию заполнения структуры. Запустите `go test` и `go build -gcflags=-m`.
2. Напишите одностраничную шпаргалку: причины побега, цвета трёхцветной схемы, поля заголовка среза, `clear`, `GOGC`, сброс `sync.Pool` и один запрет `unsafe`.
3. Запустите `go test -bench=. -benchmem` на функции, которая собирает строку через `+`, и на функции с `strings.Builder`. Сохраните вывод.
4. Нарисуйте трёхцветные состояния трёх объектов во время цикла пометки. Подпишите один корень.

#### Практические задания среднего уровня

1. Напишите программу, которая утекает, добавляя указатели в глобальный срез. Затем напишите версию, которая обрабатывает элементы и отбрасывает их. Сравните `HeapAlloc` после `runtime.GC()`.
2. Минимизируйте заполнение в структуре с `uint8`, `uint64`, `uint16` и `uint32`. Напечатайте `Sizeof` для двух порядков полей.
3. Задокументируйте изменение производительности в десяти шагах: измерить, выдвинуть гипотезу, изменить одно, измерить снова. Примените шаги к одной функции.

#### Сложные практические задания

1. Постройте небольшой путь кодирования JSON, который повторно использует буфер из пула и заранее задаёт размер среза. Сравните с `json.Marshal` в бенчмарке. Укажите, когда лишний код не стоит того.
2. Прочитайте текущее руководство по `GC` Go и документацию пакета `unsafe`. Напишите одностраничную политику для команды: разрешённые измерения, разрешённые пулы, запрещённые шаблоны `unsafe` и обязательное ревью смены раскладки структур в экспортируемых двоичных форматах.

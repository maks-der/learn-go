# 5. Другие типы данных

## Описание

У Redis больше типов, чем строки, хеши, списки, множества и упорядоченные множества. Эта тема вводит битовые карты, HyperLogLog, потоки, геопространственные индексы и модули Redis Stack (JSON, Search, TimeSeries). Цель — верная первая картина, а не полный гид по эксплуатации.

Завершите эту тему до изучения конвейеров, транзакций и Lua.

Используйте один термин для каждого понятия. Битовая карта — строка, которую вы адресуете смещением бита. HyperLogLog — приблизительный счётчик уникальных элементов. Поток — журнал только для добавления записей. Геоключ хранит позиции. Модуль добавляет команды, которых нет в базовом Redis.

## Битовые карты

Битовая карта — строка, которую Redis считает массивом битов. Бит `0` — первый бит первого байта. Можно задать миллионы битов. Redis растит строку до наивысшего смещения, которое вы пишете.

`SETBIT key offset value` задаёт бит `offset` в `0` или `1`. Ответ — старый бит.

`GETBIT key offset` возвращает `0` или `1`. Отсутствующий ключ ведёт себя как все нули.

`BITCOUNT key` возвращает число битов, которые равны `1`. Можно передать диапазон байтов.

`BITOP` выполняет `AND`, `OR`, `XOR` или `NOT` по битовым картам и пишет ключ назначения. `BITPOS` находит первый бит, который равен `0` или `1`.

```text
SETBIT lab:bits 0 1
SETBIT lab:bits 7 1
GETBIT lab:bits 7
BITCOUNT lab:bits
```

Типичное применение: один бит на id пользователя для «был активен сегодня». Ключ `active:2026-09-13`, смещение = id пользователя. `BITCOUNT` — дневной активный счёт. Это работает, когда id плотные и не огромные. Разреженное 64-битное пространство id — плохая битовая карта (строка была бы огромной).

Битовые карты — не новый тип в `TYPE`. `TYPE` возвращает `string`. Команды битовой карты падают на хеше или списке (`WRONGTYPE`).

`SETBIT` на огромном смещении выделяет ОЗУ до этого смещения. Не тестируйте смещение `2^32` на маленькой машине.

`GETRANGE` и `SETRANGE` тоже работают, потому что значение — строка. Для битовой логики предпочитайте битовые команды.

## HyperLogLog

HyperLogLog (HLL) оценивает число уникальных значений, которые вы добавили. Он не хранит значения. Память мала (около 12 KB на ключ в Redis). Ошибка обычно около 1 процента (стандартная ошибка HLL; Redis документирует точную границу).

`PFADD key element [element ...]` добавляет элементы. Ответ — `1`, если оценка изменилась, иначе `0`.

`PFCOUNT key [key ...]` возвращает оценку. Несколько ключей дают оценку объединения.

`PFMERGE dest src [src ...]` пишет слитый HLL в `dest`.

```text
PFADD lab:uv user:1 user:2 user:1
PFCOUNT lab:uv
```

Счёт не точный. `PFADD` одного элемента дважды не растит истинный уникальный счёт. Оценка всё равно может чуть сдвинуться в крайних случаях. Не используйте HLL для биллинга, которому нужно точное целое.

Используйте HLL для уникальных посетителей, уникальных поисковых запросов и других больших кардинальностей, где множество не поместится.

`TYPE` ключа HLL — `string`. Кодировка особая. Не делайте `GET` и не разбирайте его. Не делайте `SET` поверх ключа HLL, если хотите сохранить эскиз.

HLL не говорит, какие пользователи были уникальными. Если нужны id, используйте множество или битовую карту (когда id помещаются).

## Потоки (`XADD`, `XREAD`) — введение

Поток — журнал только для добавления. У каждой записи есть id и одна или несколько пар поле–значение.

`XADD key * field value [field value ...]` добавляет запись. `*` просит Redis создать id. Id выглядит как `timestamp-sequence`. Можно передать явный id, когда нужно.

```text
XADD lab:s * type signup user 42
XLEN lab:s
XRANGE lab:s - +
```

`XREAD COUNT 10 STREAMS lab:s 0-0` читает от id. Используйте `$`, чтобы читать только новые записи после текущего конца. `XREAD BLOCK 5000 STREAMS lab:s $` ждёт новую запись.

`XREAD` — чтение с веером. Каждый клиент отслеживает свой id. Redis не записывает, что клиент обработал запись.

Группа потребителей отслеживает последний доставленный id и ожидающие записи на потребителя. Команды (обзор):

- `XGROUP CREATE lab:s group1 0 MKSTREAM`
- `XREADGROUP GROUP group1 consumerA COUNT 1 STREAMS lab:s >`
- `XACK lab:s group1 <id>`

`>` значит «новые сообщения для группы». Ожидающие записи, которые потребитель не подтвердил, остаются в PEL (список ожидающих записей). Другой потребитель может сделать `XCLAIM`. Тема 10 покрывает полную модель.

Используйте поток, когда нужны журнал, много потребителей и повтор. Используйте Pub/Sub, когда нужна широковещательная рассылка fire-and-forget и вы принимаете потерянные сообщения. Используйте очередь-список, когда достаточно простого конкурирующего pop.

`XTRIM` или `MAXLEN` на `XADD` ограничивают поток. Неограниченные потоки заполняют память.

## Геопространственные команды

Геоключ хранит членов с долготой и широтой. Redis хранит их в упорядоченном множестве. Счёт — geohash. `TYPE` может показать `zset`. Используйте геокоманды, а не сырой `ZADD`, если не знаете кодировку.

`GEOADD key longitude latitude member` добавляет или обновляет точку. Долгота первая. Диапазон — допустимые координаты Земли. Неверная координата возвращает ошибку.

```text
GEOADD lab:geo 13.405 52.52 berlin
GEOADD lab:geo -0.1276 51.5074 london
```

`GEOSEARCH` (Redis 6.2+) находит членов рядом с точкой или внутри прямоугольника. Вы задаёте радиус, единицу (`m`, `km`, `mi`, `ft`) и необязательные `ASC` / `DESC` и `COUNT`.

```text
GEOSEARCH lab:geo FROMLONLAT 13.4 52.5 BYRADIUS 300 km ASC
```

Старые команды `GEORADIUS` и `GEORADIUSBYMEMBER` всё ещё существуют. Новый код использует `GEOSEARCH` и `GEOSEARCHSTORE`.

`GEODIST` возвращает расстояние между двумя членами. `GEOPOS` возвращает координаты. Помощники `GEOENCODE` / `GEODECODE` есть на некоторых версиях.

Гео — двумерный индекс на модели сферы. Это не полный ГИС. Нет полигонов страны, проекций или маршрутизации по дорогам. Точности хватает для «магазины рядом с пользователем», не для съёмки земли.

Очень большие радиусы и огромные множества дороги. Используйте `COUNT`, чтобы ограничить результаты.

Если нужны запросы по имени города, храните хеш для метаданных и держите геоключ только для расстояния.

## Модули Redis Stack (обзор)

Базовый Redis не включает тип документа JSON, полнотекстовый индекс или компактный тип временных рядов. Redis Stack и модули Redis добавляют эти возможности.

RedisJSON (`JSON.SET`, `JSON.GET`, `JSON.ARRAPPEND`) хранит JSON и обновляет пути. Можно сменить `$.user.city` без полного `GET` / `SET` строки. Используйте, когда документы большие, а обновления частичные.

RediSearch (`FT.CREATE`, `FT.SEARCH`) индексирует хеши или JSON. Можно запрашивать текст, числа и теги. Это поисковый движок рядом с Redis, не SQL. Нужно определить схему. Нужно поддерживать индекс.

RedisTimeSeries (`TS.ADD`, `TS.RANGE`, `TS.CREATERULE`) хранит выборки с метками времени. Есть агрегация (avg, min, max) и даунсэмплинг. Используйте для метрик. Не храните метрики как одного члена упорядоченного множества на выборку в большом масштабе без плана.

RedisBloom и связанные фильтры добавляют фильтры Блума, фильтры Кукушки и эскизы Count-Min. Они отвечают «возможно в множестве» с меньшей памятью, чем множество.

Модули загружаются в сервер. Команды появляются в `COMMAND`. Клиент должен поддерживать дополнительные команды. Cluster и персистентность должны совпадать с правилами модуля. Стоимость эксплуатации растёт (версии, ОЗУ, резервная копия данных модуля).

Используйте модуль, когда модуль совпадает с шаблоном доступа и ваша платформа его поставляет (Redis Stack, Redis Cloud или управляемый модуль). Не загружайте случайные модули на промышленный базовый Redis без разбора.

Темы 1–11 можно завершить базовым Redis. Используйте образ Docker `redis/redis-stack`, когда практикуете этот обзор. Тема 12 покрывает выбор модуля и промышленное использование.

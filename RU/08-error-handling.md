# 8. Обработка ошибок

## Описание

Go считает ошибку обычным значением. Функция возвращает `error`, когда операция может завершиться неудачей. Вызывающий код проверяет значение и выбирает следующий шаг. Эта тема показывает интерфейс `error`, создание и оборачивание ошибок, а также просмотр цепочки ошибок. Тема также показывает, когда уместен `panic` и когда уместен помощник `Must*`.

Сначала завершите тему 5. Тема 5 вводит `panic` и `recover`. Эта тема даёт правила для рабочего кода. Используйте один термин для каждой идеи. Используйте `error` для значения, которое реализует интерфейс `error`. Используйте `panic` только для сбоя, после которого программа не должна продолжаться.

## Интерфейс `error`

Предопределённый интерфейс `error` имеет один метод:

```go
type error interface {
    Error() string
}
```

Любой тип с методом `Error() string` является `error`. Метод возвращает сообщение для человека и для журнала. Не разбирайте эту строку в логике программы. Проверяйте типизированное значение или цепочку. См. следующие разделы.

Нулевое значение интерфейса `error` равно `nil`. Значение `nil` означает успех. Ненулевое значение означает сбой. Проверяйте ошибку сразу после возврата функции:

```go
n, err := w.Write(p)
if err != nil {
    return err
}
```

По соглашению `error` — последний результат. Типичная сигнатура: `func Open(name string) (*File, error)`. Когда `err != nil`, не используйте остальные результаты, если пакет не описывает особый случай.

Значение интерфейса равно `nil` только тогда, когда не заданы и тип, и данные. Функция, которая возвращает `error`, должна вернуть `nil`-интерфейс, а не нулевой указатель внутри интерфейса. Эта ошибка встречается часто:

```go
var p *MyError = nil
return p // the error is not nil
```

Возвращайте `nil` напрямую. Не возвращайте нулевой указатель как `error`.

## `errors.New`, `fmt.Errorf`, `%w`

Пакет `errors` создаёт простую ошибку:

```go
err := errors.New("not found")
```

`errors.New` сохраняет строку. Строка позже не меняется. Используйте `errors.New` для фиксированного сообщения без дополнительных данных.

`fmt.Errorf` форматирует сообщение как `fmt.Sprintf` и возвращает `error`:

```go
err := fmt.Errorf("user %d not found", id)
```

Глагол `%w` оборачивает другую ошибку. Новая ошибка хранит исходную ошибку в цепочке:

```go
err := fmt.Errorf("load config: %w", fileErr)
```

Используйте `%w`, когда вызывающий код всё ещё должен найти исходную ошибку через `errors.Is` или `errors.As`. Используйте `%v` или `%s`, когда нужна только текстовая форма и цепочку сохранять не нужно. Строка формата должна использовать `%w` только с операндом типа `error`.

Начиная с Go 1.20 можно обернуть несколько ошибок в одном вызове:

```go
err := fmt.Errorf("copy %s to %s: %w; %w", src, dst, errRead, errWrite)
```

`errors.Join` тоже объединяет ошибки. `errors.Join` возвращает `nil`, когда каждый вход равен `nil`. Используйте `errors.Join`, когда два или более независимых шага завершились неудачей и нужно сообщить обо всех.

Не оборачивайте одну и ту же ошибку много раз без причины. Каждая обёртка добавляет кадр контекста. Держите сообщение коротким. Не начинайте сообщение с заглавной буквы. Не ставьте точку в конце сообщения. Таков стиль стандартной библиотеки.

## `errors.Is`, `errors.As`, `errors.Unwrap`

После оборачивания ошибок `==` не находит внутреннее значение. Утверждение типа для внешней ошибки не находит внутренний тип. Используйте функции пакета `errors`.

`errors.Is(err, target)` обходит цепочку. Функция возвращает true, когда значение в цепочке совпадает с `target`. Совпадение использует `==` или метод `Is(error) bool` у типа в цепочке. Используйте `errors.Is` для сентинел-ошибок:

```go
if errors.Is(err, os.ErrNotExist) {
    // the file is missing
}
```

`errors.As(err, &target)` обходит цепочку. Функция находит первое значение, которое совпадает с типом `target`. `target` должен быть ненулевым указателем на тип, который реализует `error`, или указателем на интерфейс. При успехе `errors.As` записывает значение в `target` и возвращает true:

```go
var pe *os.PathError
if errors.As(err, &pe) {
    fmt.Println(pe.Path)
}
```

`errors.Unwrap(err)` возвращает следующую одну ошибку в цепочке. Функция возвращает `nil`, когда следующей ошибки нет. `errors.Unwrap` не обходит объединение многих ошибок. `errors.Is` и `errors.As` такое объединение обходят.

Не пишите `err == os.ErrNotExist` после обёртки. Не пишите `err.(*os.PathError)` после обёртки. Используйте `errors.Is` и `errors.As`.

Когда `err` равен `nil`, `errors.Is(err, target)` истинно только тогда, когда `target` тоже равен `nil`.

## Сентинел-ошибки и свои типы ошибок

Сентинел-ошибка — это переменная уровня пакета, которую вызывающий код сравнивает через `errors.Is`:

```go
var ErrNotFound = errors.New("not found")
```

Стандартная библиотека использует сентинелы. Примеры: `io.EOF`, `os.ErrNotExist`, `sql.ErrNoRows`. Сентинел уместен, когда сбой — один известный случай и вызывающему коду не нужны дополнительные поля.

Свой тип ошибки — это структура (или другой именованный тип) с методом `Error() string`. Добавьте поля для данных, которые вызывающий код должен прочитать:

```go
type QueryError struct {
    Query string
    Err   error
}

func (e *QueryError) Error() string {
    return e.Query + ": " + e.Err.Error()
}
```

Добавьте `func (e *QueryError) Unwrap() error { return e.Err }`, когда тип оборачивает другую ошибку. Тогда `errors.Is` и `errors.As` проходят через этот тип.

Используйте сентинел, когда случай стабилен и нет дополнительных данных. Используйте свой тип, когда вызывающий код должен прочитать путь, код состояния или другое поле. Не экспортируйте большой набор сентинелов, которые никогда не появляются в коде вызывающей стороны. Не используйте свой тип, когда достаточно сентинела.

Сравнивайте сентинелы через `errors.Is`, а не через `==`, когда возможна любая обёртка. Обнаруживайте свои типы через `errors.As`, а не через утверждение типа, когда возможна любая обёртка.

## Оборачивание контекста в ошибки

Ошибка нижнего уровня часто не содержит данных, которые нужны человеку. Сообщения «no such file» недостаточно. Сообщения «open /etc/app.yaml: no such file» достаточно. Добавляйте контекст на том слое, где есть данные.

Оборачивайте в точке, где вызываете другую функцию:

```go
f, err := os.Open(path)
if err != nil {
    return fmt.Errorf("open config %s: %w", path, err)
}
```

Каждый пакет добавляет факт, который ему известен. Пакет `config` добавляет роль файла. Обработчик `http` добавляет путь запроса. Не добавляйте один и тот же факт дважды.

Используйте `%w`, когда верхний вызывающий код должен проверить причину. Не используйте `%w`, когда причину нужно скрыть. Пример: публичный API не должен раскрывать внутреннюю ошибку базы данных. Тогда верните новую ошибку без `%w` или верните свой сентинел.

Помещайте в сообщение операцию и имена. Не помещайте в сообщение секреты. Не помещайте в сообщение большие данные. Держите одну короткую строку.

Не оборачивайте на каждой строке внутри одной функции, когда нового факта нет. Оборачивайте один раз на границе: граница пакета, граница процесса или граница, видимая пользователю.

`fmt.Errorf` с `%w` не записывает трассировку стека. Стандартная библиотека не печатает стек для обёрнутой ошибки. Используйте `errors.Is`, `errors.As` и `errors.Unwrap`, чтобы просмотреть цепочку.

## Когда уместен `panic` (действительно невосстановимый сбой)

`error` нужен для сбоя, который вызывающий код может обработать. `panic` останавливает текущую горутину (`goroutine`). Если никто не вызывает `recover`, процесс печатает стек и завершается.

Используйте `panic` только тогда, когда программа не может безопасно продолжаться. Типичные случаи:

- Инвариант программиста ложен. Пример: в `switch` нет ветки, которую система типов не может исключить, и вы считаете это ошибкой в коде.
- Инициализация не может завершиться, и полезной программы не остаётся. Пример: в двоичном файле нет обязательного встроенного ресурса.
- Вы достигли состояния, которое означает порчу памяти или невозможный контракт.

Не используйте `panic` для ожидаемых сбоев. Отсутствующие файлы, неверный ввод пользователя, сетевые таймауты и случаи HTTP 4xx — это ошибки. Вызывающий код должен получить `error`.

Не используйте `panic` как второй путь возврата в библиотеке. Библиотечный код, который паникует на обычном вводе, заставляет каждого вызывающего использовать `recover`. Такой дизайн трудно тестировать и трудно сочетать.

`recover` уместен на определённой границе. HTTP-сервер в стандартной библиотеке перехватывает `panic` в обработчике, чтобы один запрос не останавливал процесс. Не разбрасывайте `recover` по каждой функции. Тема 5 показывает синтаксис. Эта тема даёт правило: перехватывайте на границе и записывайте `panic` в журнал.

Разыменование нулевого указателя, индекс вне диапазона и отправка в закрытый канал тоже вызывают `panic`. Эти паники — ошибки в коде. Исправьте код. Не скрывайте их широким `recover`, если вы не на границе процесса.

## Помощники `Must*` (например `template.Must`)

Помощник `Must*` вызывает функцию, которая возвращает `(T, error)`, и паникует, когда ошибка не равна `nil`. Помощник возвращает только `T`. Примеры в стандартной библиотеке:

- `template.Must` в `html/template` и `text/template`
- `regexp.MustCompile`

Используйте `Must*`, когда вход — фиксированный литерал или встроенный файл, а сбой означает, что двоичный файл неверен. Вызывайте `Must*` из `init` или из переменной уровня пакета:

```go
var namePat = regexp.MustCompile(`^[a-z]+$`)
```

```go
var page = template.Must(template.New("p").Parse("<h1>{{.Title}}</h1>"))
```

Не используйте `Must*` для данных от пользователя, из сети или из файла, которого может не быть. В этих случаях функция должна вернуть `error`.

Вы можете написать свой помощник:

```go
func must[T any](v T, err error) T {
    if err != nil {
        panic(err)
    }
    return v
}
```

Держите этот помощник в тестовом коде или на старте программы. Не экспортируйте общий `Must` из библиотеки, которая обрабатывает данные запроса.

`regexp.Compile` возвращает ошибку. `regexp.MustCompile` паникует. Используйте `Compile`, когда шаблон не является константой.

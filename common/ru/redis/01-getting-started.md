# 1. Начало работы

## Описание

Redis — хранилище данных в памяти. Программы используют Redis как кэш, как брокер сообщений и как хранилище ключей в ОЗУ. Эта тема показывает, что такое Redis, как Redis сравнивают с двумя частыми альтернативами и как запустить экземпляр. Вы также изучаете `redis-cli`, модель ключ–значение, однопоточное выполнение команд и имена ключей.

Завершите эту тему до изучения строк, TTL и других типов.

Используйте один термин для каждого понятия. Экземпляр — один работающий процесс Redis. Клиент — программа, которая отправляет команды этому экземпляру. Команда — один запрос с именем и аргументами. Ключ — строковое имя. Значение — данные, которые Redis хранит для этого ключа. Тип — вид значения.

## Что такое Redis (кэш, брокер и хранилище в памяти)

Redis хранит данные в ОЗУ. Клиент отправляет команду. Redis применяет команду к ключам в памяти. Затем Redis отправляет ответ. Путь короткий. Задержка часто меньше одной миллисекунды в локальной сети.

Redis — хранилище данных. Вы пишете ключ. Вы читаете этот ключ. Redis также поддерживает больше, чем простое строковое значение. Позже темы покрывают хеши, списки, множества, упорядоченные множества, потоки и другие типы.

Коллективы используют Redis в трёх частых ролях:

- Кэш. Приложение записывает результат, который дорого считать. Следующее чтение идёт в Redis. TTL может удалить ключ через время.
- Брокер. Приложение публикует сообщения или пишет записи потока. Другие процессы читают эти сообщения.
- Хранилище в памяти. Приложение хранит состояние в Redis и считает Redis источником истины. Тогда важны персистентность и репликация.

Redis не заменяет любую базу. Redis не заменяет реляционный движок для сложных соединений и ограничений на много строк. Redis не является полной платформой сообщений с долгой историей по сравнению с журналом вроде Apache Kafka.

Redis быстр, потому что данные живут в памяти и потому что выполнение команд идёт в одном основном потоке. Запись на диск необязательна. Можно запустить Redis без файлов на диске. Можно включить снимки или файл только для добавления. Тема 7 покрывает эти режимы.

Типичная промышленная схема: один или несколько экземпляров Redis, клиентская библиотека в приложении и явная политика имён ключей и TTL. Типичная учебная схема: один экземпляр на вашей машине и `redis-cli`.

## Redis против Memcached против кэш-таблицы SQL

Memcached — кэш в памяти. Memcached хранит ключи и значения. У Memcached небольшой набор команд. Memcached не даёт типы Redis вроде списков, множеств и упорядоченных множеств. Memcached не даёт персистентность в стиле Redis, репликацию или потоки.

Кэш-таблица SQL — таблица в реляционной базе. Приложение пишет строки кэша в эту таблицу. Тот же движок хранит кэш и долговечные данные. SQL даёт транзакции, ограничения и средства запросов. Строка кэша в SQL медленнее ключа Redis для простого чтения. Кэш также использует тот же диск и те же блокировки, что и другие таблицы.

Выбирайте Redis, когда нужны низкая задержка, богатые типы и отдельный кэш или хранилище сессий. Выбирайте Memcached, когда нужен простой кэш и команда уже эксплуатирует Memcached. Выбирайте кэш-таблицу SQL, когда кэш должен соединяться с другими таблицами, когда нельзя добавить новый сервис или когда кэш должен жить в той же транзакции, что и долговечная запись.

Redis и Memcached оба вытесняют ключи при заполнении памяти, если вы настроили вытеснение. Таблица SQL растёт, пока диск не заполнится, если приложение не удаляет строки.

Redis может сохранять данные. Memcached — кэш. Перезапуск процесса Memcached теряет кэш. Перезапуск процесса Redis может загрузить данные, если включена персистентность.

Не считайте эти три варианта одним продуктом. Измерьте путь чтения. Измерьте стоимость эксплуатации. Используйте одно основное хранилище для долговечных бизнес-записей, если только вы специально не проектируете Redis как это хранилище.

## Установка Redis или Docker

Вы можете запустить Redis на своей машине, в контейнере или в хостинговом сервисе.

В Linux установите пакет Redis из дистрибутива или скачайте официальную сборку. После установки запустите процесс `redis-server`. Порт по умолчанию — `6379`.

В Windows проект Redis не поставляет полноценный нативный сервер Windows для текущих версий. Используйте Docker Desktop, Windows Subsystem for Linux (WSL) или хостинговый сервис Redis.

Docker — частый учебный путь. Скачайте официальный образ. Запустите контейнер, который публикует порт `6379`:

```text
docker run --name redis-learn -p 6379:6379 redis
```

Контейнер запускает `redis-server`. Остановите контейнер, когда сессия закончится. Запустите тот же контейнер снова, чтобы сохранить данные, если контейнер ещё есть и вы не удалили том.

Хостинговый сервис Redis даёт хост, порт и пароль. Вы подключаетесь через `redis-cli` или клиентскую библиотеку по сети. Используйте TLS, если сервис требует TLS.

Redis Stack — дистрибутив, который добавляет модули вроде JSON и Search. Используйте Redis Stack, когда более поздняя тема нужна этим модулям. Используйте обычный Redis для тем 1–11, если задание не называет модуль.

После старта экземпляра убедитесь, что клиент может подключиться. Следующий раздел использует `redis-cli` для этой проверки.

Не открывайте учебный экземпляр в публичный интернет. Привяжите к `127.0.0.1` на локальной машине. Задайте пароль любому экземпляру, который не только на localhost.

## `redis-cli`, `PING`, `INFO`

`redis-cli` — официальный клиент командной строки. Инструмент отправляет команды Redis и печатает ответы. Используйте `redis-cli` для обучения, проверок здоровья и разовых операций.

Запустите интерактивную сессию к хосту и порту по умолчанию:

```text
redis-cli
```

Приглашение показывает хост и номер логической БД, например `127.0.0.1:6379>`. Введите команду. Нажмите Enter. Прочитайте ответ.

Подключитесь к другому хосту или порту:

```text
redis-cli -h 127.0.0.1 -p 6379
```

Отправьте одну команду без интерактивной сессии:

```text
redis-cli PING
```

Если экземпляр требует пароль, передайте `-a` или используйте `AUTH` после подключения. Предпочитайте переменную окружения или запрос пароля, а не пароль в истории оболочки. Хостинговые сервисы часто требуют имя пользователя и пароль. Используйте `--user` и `--pass` или `AUTH`, как показывает документация сервиса.

`PING` проверяет соединение. Redis отвечает `PONG`, когда экземпляр принимает команду. Можно отправить сообщение. `PING hello` повторяет `hello`. Клиентские библиотеки также используют `PING` как проверку здоровья.

`INFO` возвращает текстовые разделы об экземпляре. Запустите `INFO` для полного отчёта. Запустите `INFO server`, `INFO memory`, `INFO clients`, `INFO replication` или `INFO keyspace` для одного раздела.

Полезные строки для новичков:

- `redis_version` — версия сервера
- `used_memory_human` — используемая память
- `connected_clients` — открытые клиентские соединения
- `db0` в `INFO keyspace` — число ключей и число сроков для логической БД 0

Вывод не JSON. Разбирайте его как строки `key:value`.

`SELECT` меняет логическую БД для текущего соединения. По умолчанию БД `0`. Ключи в БД `0` не видны в БД `1`. Современные приложения используют одну логическую БД, обычно БД `0`. Они разделяют данные префиксами ключей, а не через `SELECT`. Redis Cluster не поддерживает `SELECT`. Не проектируйте новую систему, которая зависит от многих логических БД.

`redis-cli` печатает типы ответов в читаемом виде. Простая строка, целое, bulk-строка, массив и ошибка выглядят по-разному. Ошибка начинается с сообщения сервера.

Выйдите из интерактивной сессии через `QUIT` или `exit`, либо закройте терминал.

Не запускайте `KEYS *` на промышленном экземпляре. Эта команда может заблокировать сервер на большом пространстве ключей. Этот путь обучения использует `KEYS` только на локальном пустом экземпляре. Тема 9 вводит `SCAN`.

Основная документация — [https://redis.io/docs/](https://redis.io/docs/). Справочник команд — [https://redis.io/commands/](https://redis.io/commands/). Когда страница и этот справочник расходятся по новому флагу, доверяйте странице команды для вашей версии Redis. Проверьте `INFO server` на `redis_version`.

## Модель ключ–значение: ключи — строки; у значений есть тип

Redis хранит пары. У каждой пары один ключ и одно значение. Клиент называет ключ в команде. Redis находит значение для этого ключа. В базовой модели нет SQL-клаузы `FROM` и нет имени коллекции документов.

Ключ Redis — бинарно-безопасная строка. Обычно используют текст UTF-8. Есть максимальный размер ключа (512 MB). Не используйте большие ключи. Правило — короткие стабильные имена.

Отсутствующий ключ — не ошибка для большинства команд чтения. `GET` отсутствующего ключа возвращает null. Команды записи создают ключ, если его нет, если команда не говорит иное.

Один ключ держит одно значение. У этого значения один тип. Нельзя одновременно хранить хеш и строку под одним ключом. Можно удалить ключ и создать его снова с новым типом.

Основные типы на этом пути обучения:

- строка
- хеш
- список
- множество
- упорядоченное множество
- поток
- битовая карта (строка как биты)
- HyperLogLog (строка как эскиз)
- геоданные (упорядоченное множество со счетами)

`TYPE key` возвращает имя типа или `none`, если ключа нет.

Команды принадлежат типам. `HGET` работает с хешем. `HGET` на строковом ключе возвращает ошибку `WRONGTYPE`. `GET` работает со строкой. `GET` на хеше возвращает `WRONGTYPE`.

Некоторые команды работают с любым ключом: `DEL`, `EXISTS`, `EXPIRE`, `TTL`, `TYPE`, `RENAME`. Эти команды не читают внутреннюю структуру.

Redis в базовой модели не ищет по значению. Вы не говорите «найди все ключи, чья строка равна `alice`». Вы проектируете ключи так, чтобы приложение уже знало имя, либо сознательно ведёте вторичные индексы.

Ключи живут в одном пространстве ключей на логическую БД. Экземпляр может держать миллионы ключей, если хватает памяти. У каждого ключа небольшой расход ОЗУ. Много крошечных ключей стоит больше памяти, чем одна более крупная структура.

Выбирайте тип по шаблону доступа. Строка подходит для блоба или счётчика. Хеш подходит для небольшого объекта с полями. Список подходит для очереди или журнала недавних элементов. Множество подходит для уникального членства. Упорядоченное множество подходит для рейтинга и диапазонов.

## Однопоточное выполнение команд (обзор)

Redis выполняет команды в одном основном потоке. Экземпляр берёт одну команду, выполняет её до конца, затем берёт следующую. Две команды `INCR` на одном ключе не чередуются. Блокировка для одной команды не нужна.

Эта модель упрощает многие операции. `INCR` атомарна. `LPUSH` атомарна. Скрипт Lua или Redis Function, который выполняется на сервере, тоже атомарны относительно других команд.

Цена тоже ясна. Медленная команда блокирует остальные. `KEYS *` на большом пространстве ключей, `LRANGE` огромного списка или тяжёлый `SORT` могут застопорить экземпляр. Держите команды маленькими. Делите большую работу.

Начиная с Redis 6, необязательные потоки ввода-вывода могут читать и писать сокеты. Эти потоки не выполняют логику команд. Основной поток по-прежнему выполняет команды. Не думайте, что Redis — многоядерный движок команд, потому что есть потоки ввода-вывода.

Конвейеры отправляют много команд за один сетевой круг. Сервер всё равно выполняет эти команды по одной. Конвейеры сокращают ожидание сети. Они не выполняют команды параллельно на многих ядрах. Тема 6 покрывает конвейеры.

Для одного экземпляра масштабирование выполнения команд по CPU означает больше шардов (Cluster) или больше экземпляров, а не больше потоков на том же пространстве ключей. Вертикальная скорость по-прежнему идёт от быстрых команд и достаточного ОЗУ.

## Соглашения об именах ключей

У Redis одно плоское пространство ключей на логическую БД. Папок нет. Папки имитируют соглашением в строке ключа.

Частый шаблон использует `:` как разделитель:

```text
user:42:profile
user:42:cart
session:abc123
cache:product:1001
```

Некоторые команды используют `#` или `/`. Выберите один разделитель и держите его. Символ не имеет особого смысла для Redis, кроме хеш-тегов Cluster, которые используют `{` и `}`. Тема 8 покрывает хеш-теги.

Хорошее имя стабильно, уникально и читаемо. Включайте тип объекта, id и роль поля, когда на объект нужно больше одного ключа. Не кладите секреты в имена ключей. Имена ключей видны в `MONITOR`, в журналах и в инструментах поддержки.

Используйте префикс продукта или арендатора на общем экземпляре:

```text
shopA:user:42
shopB:user:42
```

Эти ключи не сталкиваются. Они всё равно делят память и `maxmemory`. Изоляция нескольких арендаторов на одном экземпляре — соглашение, а не граница безопасности. Тема 12 покрывает политику арендаторов.

Документируйте схему. Напишите каталог ключей на одну страницу. Избегайте случайных имён вроде `data` или `tmp`. Для временных ключей включите назначение и уникальный суффикс и задайте TTL.

Предпочитайте буквы, цифры, `:`, `-` и `.`. Ключ может содержать пробелы, но пробелы усложняют работу в CLI. Ключ вроде `user:42:profile` ясен. Ключ, который держит полный JSON-документ в имени, неверен.

`SCAN` с шаблоном `MATCH` может перечислить ключи по префиксу на лабораторном экземпляре. Не используйте `KEYS user:*` в продакшене.

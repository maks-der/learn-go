# 2. Основные идеи

## Описание

Redis — хранилище ключ-значение с типизированными значениями. Эта тема объясняет модель данных, модель выполнения и модель памяти. Вы также изучаете TTL, вытеснение и соглашения об именах ключей.

Завершите эту тему до изучения команд строк и других типов.

Используйте один термин для каждого понятия. Ключ — строковое имя. Значение — данные, которые Redis хранит для этого ключа. Тип — вид значения (строка, хеш, список и другие). TTL — оставшееся время жизни ключа. Вытеснение — удаление ключей, когда память заполнена.

---

## Модель ключ-значение

Redis хранит пары. У каждой пары один ключ и одно значение. Клиент называет ключ в команде. Redis находит значение для этого ключа. В базовой модели нет SQL-предложения `FROM` и нет имени коллекции документов.

Отсутствующий ключ — не ошибка для большинства команд чтения. `GET` отсутствующего ключа возвращает null-ответ. Команды записи создают ключ, если его нет, если команда не говорит иное.

Один ключ держит одно значение. У этого значения один тип. Нельзя хранить хеш и строку под одним ключом одновременно. Можно удалить ключ и создать его снова с новым типом.

Redis не ищет по значению в базовой модели. Вы не говорите «найди все ключи, чья строка равна `alice`». Вы проектируете ключи так, чтобы приложение уже знало имя, либо специально держите вторичные индексы (множества, упорядоченные множества или модуль поиска).

Ключи живут в одном пространстве ключей на логическую БД. Экземпляр может держать миллионы ключей, если хватает памяти. У каждого ключа небольшой оверхед в ОЗУ. Много крошечных ключей стоят больше памяти, чем одна более крупная структура.

Модель ключ-значение проста. Приложение владеет схемой имён и путями доступа. Redis хранит и достаёт. Redis не заменяет вашу предметную модель. Вы отображаете предметную область на ключи.

## Ключи — строки; у значений есть тип

Ключ Redis — двоично-безопасная строка. Обычно вы используете текст UTF-8. Ключ может содержать пробелы, но пробелы усложняют работу в CLI. Предпочитайте буквы, цифры, `:`, `-` и `.`.

Есть максимальный размер ключа (512 МБ). Не используйте большие ключи. Правило — короткие стабильные имена. Ключ вроде `user:42:profile` ясен. Ключ, который держит полный JSON-документ в имени, неверен.

У значения есть тип. Основные типы на этом пути обучения:

- string
- hash
- list
- set
- sorted set
- stream
- bitmap (строка как биты)
- HyperLogLog (строка как эскиз)
- geospatial (упорядоченное множество со счётами)

`TYPE key` возвращает имя типа или `none`, когда ключа нет.

Команды принадлежат типам. `HGET` работает с хешем. `HGET` на строковом ключе возвращает ошибку `WRONGTYPE`. `GET` работает со строкой. `GET` на хеше возвращает `WRONGTYPE`.

Некоторые команды работают с любым ключом: `DEL`, `EXISTS`, `EXPIRE`, `TTL`, `TYPE`, `RENAME`. Эти команды не читают внутреннюю структуру.

Выбирайте тип по шаблону доступа. Строка подходит для блоба или счётчика. Хеш подходит для небольшого объекта с полями. Список подходит для очереди или журнала недавних элементов. Множество подходит для уникального членства. Упорядоченное множество подходит для рейтинга и диапазонов.

Не храните каждый объект как JSON в строке, когда нужны обновления полей. Хеш или модуль JSON может обновить одно поле без полной перезаписи. Позже темы показывают эти типы.

## Однопоточное выполнение команд (на высоком уровне; потоки ввода-вывода есть)

Redis выполняет команды в одном основном потоке. Экземпляр берёт одну команду, выполняет её до конца, затем берёт следующую. Две команды `INCR` на одном ключе не перемешиваются. Блокировка для одной команды не нужна.

Эта модель делает многие операции простыми. `INCR` атомарна. `LPUSH` атомарна. Скрипт Lua или Redis Function, который выполняется на сервере, тоже атомарны относительно других команд.

Цена тоже ясна. Медленная команда блокирует другие команды. `KEYS *` на большом пространстве ключей, `LRANGE` огромного списка или тяжёлый `SORT` могут остановить экземпляр. Держите команды маленькими. Дробите большую работу.

С Redis 6 необязательные потоки ввода-вывода могут читать и писать сокеты. Эти потоки не выполняют логику команд. Основной поток по-прежнему выполняет команды. Не думайте, что Redis — многоядерный движок команд, потому что есть потоки ввода-вывода.

Конвейеры отправляют много команд за один сетевой круг. Сервер всё равно выполняет эти команды по одной. Конвейеры сокращают ожидание в сети. Они не выполняют команды параллельно на многих ядрах.

Для одного экземпляра горизонтальное масштабирование CPU выполнения команд значит больше шардов (Cluster) или больше экземпляров, а не больше потоков на том же пространстве ключей. Вертикальная скорость по-прежнему идёт от быстрых команд и достаточного ОЗУ.

## Сначала память; персистентность необязательна

Redis читает и пишет ОЗУ сначала. Успешный `SET` меняет память. Клиент получает `OK`. Диска нет на этом пути, если вы не настроили ожидание долговечной записи (это ожидание не значение по умолчанию для каждой схемы).

Персистентность необязательна. Можно запустить Redis без RDB и без AOF. Остановка процесса тогда теряет все ключи. Этот режим допустим для чистого кэша.

Когда данные нужны после перезапуска, включите персистентность. Redis может писать снимки (RDB). Redis может добавлять каждое изменение в файл (AOF). Можно совместить оба. Тема 9 покрывает режимы и окно потери.

Память — предел ёмкости. Размер экземпляра — размер ключей, значений и оверхеда. Размер диска важен только когда персистентность включена.

Считайте Redis прежде всего памятью в дизайне приложения. Не предполагайте, что каждый `OK` уже на диске. Если Redis — база записи, вы должны выбрать режим персистентности и проверить перезапуск. Если Redis — кэш, вы должны принять потерю и восстановить из источника истины.

`INFO persistence` показывает, активны ли RDB или AOF и когда закончилось последнее сохранение.

## TTL и вытеснение

TTL — время жизни. К ключу можно прикрепить срок. Когда TTL достигает нуля, Redis удаляет ключ. Команды вроде `EXPIRE` и `SET ... EX` задают срок. Тема 4 покрывает полный набор команд.

Ключ без срока живёт, пока вы его не удалите или пока вытеснение его не уберёт. `TTL key` возвращает оставшиеся секунды, `-1` если ключ есть и срока нет, или `-2` если ключа нет.

Вытеснение отличается от TTL. Вытеснение работает, когда экземпляр достигает `maxmemory` и записьм нужна память. Redis тогда удаляет ключи по политике (`allkeys-lru`, `volatile-lru`, `noeviction` и другие). Тема 4 покрывает политики.

TTL — таймер на ключ. Вытеснение — механизм давления памяти. Кэш часто использует оба: TTL, чтобы данные не устаревали навсегда, и политику вытеснения, чтобы Redis мог сбрасывать ключи, когда ОЗУ заполнено.

Не путайте «срок ключа истёк» с «Redis вытеснил ключ». В `INFO stats` есть `expired_keys` и `evicted_keys`. Эти счётчики не одно и то же.

Активное истечение — фоновый цикл. Redis не ждёт чтения, чтобы удалить каждый истёкший ключ. Redis также проверяет срок при доступе. Число ключей может упасть без клиентского `DEL`.

## Пространства имён ключей соглашениями `:` или `#`

У Redis одно плоское пространство ключей на логическую БД. Папок нет. Вы имитируете папки соглашением в строке ключа.

Частый шаблон использует `:` как разделитель:

```text
user:42:profile
user:42:cart
session:abc123
cache:product:1001
```

Некоторые коллективы используют `#` или `/`. Выберите один разделитель и держите его. Символ не имеет особого смысла для Redis, кроме хеш-тегов Cluster, которые используют `{` и `}`. Тема 11 покрывает хеш-теги.

Хорошее имя стабильно, уникально и читаемо. Включите тип объекта, id и роль поля, когда нужно больше одного ключа на объект. Не кладите секреты в имена ключей. Имена ключей появляются в `MONITOR`, в журналах и в инструментах поддержки.

Используйте префикс продукта или арендатора в общем экземпляре:

```text
shopA:user:42
shopB:user:42
```

Эти ключи не сталкиваются. Они всё равно делят память и `maxmemory`. Изоляция многих арендаторов на одном экземпляре — соглашение, а не граница безопасности.

Документируйте схему. Напишите каталог ключей на одну страницу. Избегайте случайных имён вроде `data` или `tmp`. Для временных ключей включите назначение и уникальный суффикс и задайте TTL.

`SCAN` с шаблоном `MATCH` может перечислить ключи по префиксу на лабораторном экземпляре. Не используйте `KEYS user:*` в промышленной среде.

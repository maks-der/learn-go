# 21. Укрепление продакшена

## Описание

Эта тема показывает, как запускать PostgreSQL 16 и PostgreSQL 17 в продакшене. Вы узнаёте роль приложения с наименьшими привилегиями, сетевые правила для порта `5432`, инструменты миграций, смены схемы expand-contract, мониторинг и runbook для failover и полного диска.

Сначала завершите тему 20. Вы знаете слоты, реплики и тяжёлый SQL. Это последняя операционная тема перед экосистемой.

Используйте один термин для каждого понятия. Наименьшие привилегии значат, что у роли только права, которые нужны программе. Миграция — версионированная смена схемы. Expand-contract — совместимая смена мелкими шагами. Runbook — письменная процедура, которой следует дежурный. Этот справочник рассчитан на PostgreSQL 16 и PostgreSQL 17.

## Роль приложения с наименьшими привилегиями

Тема 12 представила роли и `GRANT`. В продакшене это умолчание, а не дополнение.

Роль приложения (`shop_app`):

- имеет `LOGIN`
- имеет `CONNECT` на базе приложения
- имеет `USAGE` на схеме приложения
- имеет DML на таблицах приложения (`SELECT`, `INSERT`, `UPDATE`, `DELETE` по необходимости)
- имеет `USAGE` последовательностей для вставок identity
- имеет `EXECUTE` только на функциях, которые приложение должно вызывать
- не имеет `SUPERUSER`, `BYPASSRLS`, `CREATEDB`, `CREATEROLE` или `REPLICATION`
- не владеет таблицами, если ими владеет роль мигратора

Роль мигратора выполняет DDL. CI использует секрет мигратора. Приложение этот секрет никогда не видит.

```sql
CREATE ROLE shop_migrator LOGIN PASSWORD 'migrator-secret';
CREATE ROLE shop_app LOGIN PASSWORD 'app-secret';

GRANT CONNECT ON DATABASE shop TO shop_migrator, shop_app;
GRANT USAGE, CREATE ON SCHEMA shop TO shop_migrator;
GRANT USAGE ON SCHEMA shop TO shop_app;
-- table grants and default privileges: topic 12
```

Row-level security остаётся включённым, если вы мультиарендные. Роль приложения не должна обходить RLS.

Облачные админ-роли — не роли приложения. Человек может использовать админ-роль с бастиона. Пул соединений использует только `shop_app`.

Не отлаживайте продакшен-аварию, выдавая `SUPERUSER` роли `shop_app`. Не используйте один пароль для мигратора и приложения. Не оставляйте у `PUBLIC` `CREATE` на `public`, если используете эту схему (PostgreSQL 15+ уже отозвал; не выдавайте обратно).

## Сеть: не открывайте `5432` миру

PostgreSQL по умолчанию слушает TCP-порт `5432`. Если порт достижим из публичного интернета, его сканируют атакующие. SSL не делает публичный `5432` хорошей идеей (тема 12). Сильного пароля недостаточно.

Безопасный шаблон:

- `listen_addresses` привязывает только нужные интерфейсы
- файрвол или security group разрешает `5432` только из подсети приложения, PgBouncer или бастиона
- `pg_hba.conf` совпадает с этими источниками и требует `scram-sha-256` (и `hostssl`, когда используете TLS)
- клиенты используют `sslmode=verify-full`, когда контролируете сертификаты
- администраторы используют VPN, бастион или частную ссылку поставщика, а не открытое правило `0.0.0.0/0`

Тема 2 сказала не сочетать `listen_addresses = '*'` с `trust`. Продакшен также запрещает `trust` и `password` (открытый текст). Используйте `scram-sha-256`.

Docker `-p 5432:5432` на ноутбуке — лабораторная привычка. На облачной VM опубликованный `5432` на `0.0.0.0` — инцидент.

Управляемые сервисы всё равно нуждаются в сетевом правиле. «Public IP disabled» или «authorized networks» — та же идея.

Не ставьте PostgreSQL в публичный интернет «на тест выходных» на хосте с настоящими данными. Не используйте `trust` ни для одной удалённой строки. Не отключайте файрвол потому что драйвер не подключился; исправьте `pg_hba` и security group.

Официально `pg_hba`: [https://www.postgresql.org/docs/17/auth-pg-hba-conf.html](https://www.postgresql.org/docs/17/auth-pg-hba-conf.html).

## Миграции (Flyway, golang-migrate, Sqitch)

Миграция — версионированная смена SQL (или кода), которую применяют по порядку. Схема продакшена не должна быть «тем, что кто-то запустил в `psql`».

Частые инструменты:

- **Flyway** — файлы версий вроде `V3__add_orders.sql`; ведёт `flyway_schema_history`
- **golang-migrate** — `0003_add_orders.up.sql` и файл down; часто в сервисах Go
- **Sqitch** — планы с именами и зависимостями; силён для ревью

Всем трём нужны:

- одна таблица истории
- роль мигратора (предыдущий раздел)
- шаг CI, который применяет ожидающие файлы
- правило: файл, который дошёл до продакшена, не меняют

```text
-- 0004_items_qty.up.sql
ALTER TABLE shop.items ADD COLUMN qty int NOT NULL DEFAULT 0;
```

Миграции down в некоторых командах необязательны. Если держите их, тестируйте. Down, который удаляет столбец, уничтожает данные.

Не смешивайте Flyway и golang-migrate на одной базе. Не редактируйте `V3__add_orders.sql` после того, как продакшен применил его. Не запускайте DDL как `shop_app`.

Расширения темы 13 (`CREATE EXTENSION`) принадлежат миграции, которую запускает суперпользователь или разрешённый админ, а не старту приложения на каждый запрос.

## Blue/green или смены схемы expand-contract

Блокировка, которая переписывает большую таблицу, может остановить приложение. PostgreSQL 16 и 17 всё ещё переписывают некоторые формы `ALTER TABLE`. Смотрите текущую страницу `ALTER TABLE`: одни смены — только обновление каталога; другие сканируют таблицу; третьи переписывают.

**Expand-contract** (расширить, мигрировать, сжать):

1. Expand: добавить новый столбец или таблицу, которые старое приложение игнорирует (`NULL` или умолчание, которое не переписывает, если так говорит документация)
2. Двойная запись или backfill: приложение или задание заполняет новый объект
3. Переключить чтения на новый объект
4. Contract: удалить старый столбец или таблицу в более позднем релизе

Пример: переименовать `name` в `title` без долгой перезаписи:

1. Добавить `title text`
2. Выкатить приложение, которое пишет оба
3. Backfill `title` из `name`
4. Выкатить приложение, которое читает `title`
5. Удалить `name`

**Blue/green** для схемы может значить две схемы или две базы. Мигрируете зелёную копию, переключаете пул на green, держите blue для отката. Это тяжелее. Подходит большой перезаписи. Синхронизация данных всё равно нужна.

`CREATE INDEX CONCURRENTLY` (тема 8) — шаг expand. `DROP INDEX CONCURRENTLY` — шаг contract. `DETACH PARTITION` (тема 15) может сбросить старые данные без огромного `DELETE`.

Не запускайте `ALTER TABLE ... ALTER COLUMN type` на таблице 200 ГБ в рабочие часы без плана перезаписи. Не добавляйте `NOT NULL` без умолчания или предварительного backfill. Не выкатывайте приложение, которому нужен столбец, который миграция ещё не применила.

Официально `ALTER TABLE`: [https://www.postgresql.org/docs/17/sql-altertable.html](https://www.postgresql.org/docs/17/sql-altertable.html).

## Мониторинг: соединения, отставание репликации, раздутие, wraparound

Продакшену нужны измерения, а не ощущения. Тема 18 показала представления. Этот раздел — минимальный набор.

**Соединения**

```sql
SELECT count(*) FROM pg_stat_activity;
SHOW max_connections;
SELECT usename, state, count(*)
FROM pg_stat_activity
GROUP BY 1, 2;
```

Алерт, когда использованные соединения остаются высокими, когда много сессий `idle in transaction`, или когда приложение не может подключиться.

**Отставание репликации** (тема 16 и тема 19)

```sql
SELECT client_addr, state, replay_lsn, sent_lsn
FROM pg_stat_replication;
```

На реплике используйте функцию времени отставания, если есть воспроизведение. Алерт, когда отставание превышает SLA отчёта.

**Раздутие** (тема 11)

```sql
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 20;
```

Алерт по доле мёртвых кортежей и по росту размера, который число строк не объясняет.

**Wraparound** (тема 11)

```sql
SELECT datname, age(datfrozenxid)
FROM pg_database
ORDER BY 2 DESC;
```

Алерт задолго до предела wraparound. Autovacuum должен успевать. Неудачная заморозка — чрезвычайная ситуация.

Также следите: свободный диск (тема 18), WAL, удерживаемый слотом репликации, выбросы `pg_stat_statements`, всплески checkpoint, журналы ошибок.

Не алертите на каждый `n_dead_tup > 0`. Не игнорируйте wraparound потому что «autovacuum включён». Не собирайте текст SQL, который содержит секреты.

## Runbook для failover и полного диска

Runbook — процедура, которой может следовать уставший человек. Тема 16 покрыла promote и инструменты HA. Тема 18 покрыла полный диск. Продакшен хранит runbook рядом с пейджером.

**Runbook failover** (физическая реплика, обзор):

1. Подтвердите, что первичный лежит или небезопасен (больше одной проверки).
2. Оградите старый первичный (остановить записи: остановить VM, отозвать security group, ограждение поставщика). Не пропускайте этот шаг.
3. Повысьте одну реплику (`pg_promote` или Patroni или failover поставщика).
4. Направьте пул или DNS на новый первичный.
5. Проверьте записи (`INSERT` в проверочную таблицу) и отставание реплики, если есть новый стендбай.
6. Откройте инцидент: окно потери данных, кто повысил, когда восстанавливаете новую реплику.

**Runbook полного диска** (обзор):

1. Подтвердите, какой том полон (`PGDATA`, `pg_wal`, журналы).
2. Если сервер принимает соединение, выполните запросы слотов и archiver (тема 18).
3. Освободите место, не удаляя `pg_wal` наугад.
4. Исправьте причину (архив, слот, журналы, раздутие).
5. Подтвердите, что записи возобновились и WAL перерабатывается.
6. Если файлы уничтожены, восстановите из резервной копии (тема 16) и прекратите гадать.

Каждому runbook нужны: владелец, дата последней проверки, ссылки на дашборды, шаги консоли поставщика и строка отката или «остановиться и эскалировать».

Не держите единственную копию runbook на первичном хосте. Не повышайте две реплики. Не практикуйте failover только на бумаге.

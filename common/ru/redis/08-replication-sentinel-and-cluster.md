# 8. Репликация, Sentinel и Cluster

## Описание

Redis может копировать данные с основного экземпляра на реплики. Redis также может делить ключи между многими основными. Эта тема покрывает асинхронное отставание, Redis Sentinel, аварийное переключение, хеш-слоты Cluster, хеш-теги, пределы многоключевых команд и что должен делать клиент в режиме cluster.

Сначала завершите более ранние темы. Cluster — не Sentinel. Cluster шардирует данные. Sentinel переключает один основной.

Используйте один термин для каждого понятия. Основной принимает записи. Реплика копирует основной и может обслуживать чтения. Отставание — задержка между записью на основном и той же записью на реплике. Sentinel — набор процессов, которые следят за Redis и могут повысить реплику. Слот — целое от `0` до `16383`. Хеш-тег — часть `{...}` ключа, которую Redis использует, чтобы посчитать слот. Перенаправление — ответ `MOVED` или `ASK`, который говорит клиенту другой узел.

## Асинхронные реплики и отставание

`REPLICAOF host port` делает текущий экземпляр репликой этого основного. Реплика подключается, выполняет синхронизацию и затем применяет поток записей.

```text
REPLICAOF 127.0.0.1 6379
```

`REPLICAOF NO ONE` останавливает репликацию. Экземпляр становится автономным основным с данными, которые у него уже есть.

Старые документы и команды использовали `SLAVEOF`. Текущий Redis принимает `REPLICAOF`. Используйте `REPLICAOF` в новой работе. `INFO replication` всё ещё показывает поля вроде `role:master` и `role:slave` на многих версиях.

Первая синхронизация часто отправляет снимок (RDB) плюс журнал команд. Реплика загружает снимок и затем догоняет. Большой набор делает первую синхронизацию тяжёлой (CPU, диск, сеть).

По умолчанию реплика только для чтения (`replica-read-only yes`). Записи на реплике падают. Это то, что нужно. Не пишите на реплику.

Реплика может персистировать на диск. Персистентность на реплике независима от основного. Реплика сама по себе не резервная копия, пока вы не скопируете файлы с хоста.

Репликация Redis асинхронна в обычной схеме. Основной отправляет `OK` клиенту, когда запись в памяти основного (и после правил персистентности основного). Основной по умолчанию не ждёт реплику.

Реплика получает запись позже. Задержка — отставание. Отставание растёт, когда реплика медленная, сеть медленная или реплика занята загрузкой снимка.

`WAIT numreplicas timeout` на основном может ждать, пока хотя бы `numreplicas` реплик подтвердят запись, или пока не кончится таймаут. `WAIT` повышает шанс, что реплика имеет запись. `WAIT` — не полный синхронный коммит при отказах. Читайте страницу `WAIT` про пределы (и `WAITAOF` на Redis 7.2+).

Если основной умрёт, реплика, которую вы повысите, может пропустить последние записи. Это цена асинхронной репликации. Приложение должно принять эту потерю или использовать `WAIT` и всё равно принять крайние случаи.

Не предполагайте, что чтение на реплике видит запись, которую тот же пользователь только что отправил основному. Это устаревшее чтение. Устаревшие чтения приемлемы для некоторых дашбордов. Они неприемлемы для «прочитать свою запись».

`INFO replication` на основном перечисляет подключённые реплики. На реплике показывает хост основного, статус связи и поля смещения.

Персистентность на диске на основном и репликация на реплику — два пути. Можно потерять запись при аварии основного, даже если реплика получила бы её мгновением позже.

Следите за отставанием реплики. Убирайте реплику из пула чтения, когда отставание превышает бюджет (например 1 секунда).

## Sentinel и аварийное переключение

Redis Sentinel — отдельный процесс (или несколько процессов). Sentinel — не Cluster. Sentinel не шардирует ключи. Sentinel следит за именованным основным и его репликами.

Типичная лаборатория использует три процесса Sentinel. Они голосуют. Большинство должно согласиться, что основной лежит. Один Sentinel затем начинает переключение: выбрать реплику, повысить её, перенастроить другие реплики и обновить имя основного.

Клиенты спрашивают Sentinel текущий адрес основного (`SENTINEL get-master-addr-by-name mymaster`). После переключения этот адрес меняется. Клиенты должны поддерживать Sentinel или использовать прокси, который это делает.

Sentinel не делает репликацию синхронной. Переключение может сбросить последние асинхронные записи.

Вы настраиваете `sentinel monitor <name> <host> <port> <quorum>`. Кворум — число Sentinel, которые должны согласиться. Три Sentinel и кворум 2 — частая учебная схема.

Не запускайте один Sentinel и не называйте это высокой доступностью. Один Sentinel — один наблюдатель.

`INFO` на Redis недостаточно, чтобы увидеть Sentinel. Используйте `redis-cli -p 26379 SENTINEL masters` (порт Sentinel по умолчанию — `26379`).

Повышение превращает реплику в основной. После повышения этот экземпляр принимает записи. Другие реплики должны копировать с нового основного.

Ручное повышение (лаборатория, без Sentinel):

1. Подтвердите, что реплика настолько свежая, насколько можете проверить (`INFO replication`)
2. `REPLICAOF NO ONE` на выбранной реплике
3. Направьте приложения на новый основной
4. `REPLICAOF new-primary` на других репликах
5. Держите старый основной выключенным или пересоберите его как реплику, чтобы избежать двух писателей

Если старый основной возвращается как основной, у вас два писателя (раздвоение мозга). Данные расходятся. Sentinel старается избежать этого, перенастраивая старый основной как реплику.

`replica-priority 0` значит «никогда не повышать эту реплику». Используйте это для реплики, которая только резервная копия или в далёком регионе.

Повышение не воспроизводит потерянные асинхронные записи с мёртвого основного, если эти записи никогда не достигли реплики. Клиенты, которые писали и получили `OK`, всё ещё могут потерять эти ключи.

После повышения клиенты, которые закэшировали старый IP, должны обновиться (Sentinel, DNS или прокси).

Проверьте повышение в лаборатории. Замерьте простой. Замерьте потерю данных счётчиком записей.

Раздвоение мозга возможно, если сети делятся плохим образом. Читайте официальную документацию Sentinel до продакшена.

## Хеш-слоты Cluster и хеш-теги

Redis Cluster делит ключи между многими основными экземплярами. Redis Cluster делит пространство ключей на 16384 слота. Каждый ключ отображается в один слот. Redis считает `CRC16(key) mod 16384` (с правилами хеш-тегов). Результат — слот.

Каждый основной владеет набором слотов. Вместе основные владеют всеми 16384 слотами. Если у слота нет владельца, кластер нездоров для этого слота.

Запись ключа идёт на основной, который владеет слотом ключа. Другие основные не хранят этот ключ. Это шардирование. Память и CPU масштабируются наружу. Один ключ всё равно живёт на одном основном. Огромный ключ не делится.

```text
CLUSTER KEYSLOT user:42
CLUSTER SLOTS
CLUSTER NODES
```

`CLUSTER KEYSLOT` работает на узле кластера и показывает слот для ключа.

Шина кластера (второй порт, часто `16379`, когда клиентский порт — `6379`) несёт gossip и сообщения переключения между узлами. Клиенты используют клиентский порт.

Логических БД в Cluster нет. `SELECT` недоступен. Используйте префиксы ключей.

Кластеру нужно несколько основных (три — частый минимум для продакшена). У каждого основного могут быть реплики для переключения внутри кластера. Это переключение — не Sentinel. Узлы кластера голосуют.

`INFO cluster` и `CLUSTER INFO` показывают `cluster_state`. `ok` значит слоты покрыты. `fail` значит кластер не готов.

Если ключ содержит подстроку `{...}`, Redis использует только символы между первой `{` и соответствующей `}`, чтобы посчитать слот. Эта подстрока — хеш-тег.

```text
{user:42}:profile
{user:42}:cart
{user:42}:orders
```

Эти три ключа отображаются в один слот. Они могут жить на одном основном. Многоключевые команды, которые требуют один слот, могут выполняться на них.

Правила:

- Первая `{` начинает тег
- Первая `}` после этого заканчивает тег
- Если `{}` пуст, Redis игнорирует тег и хеширует полный ключ
- Если `{` нет, Redis хеширует полный ключ

Хеш-теги — сознательный инструмент горячей точки. Если все ключи используют `{global}`, один слот и один основной берут весь трафик. Это побеждает шардирование.

Используйте хеш-теги, когда транзакция, скрипт Lua или `MGET` должны трогать несколько ключей. Не тегируйте всё.

Lua, безопасный для Cluster, должен обращаться только к ключам в `KEYS[]`, и эти ключи должны делить слот (на практике один тег).

Решардирование перемещает слоты с одного основного на другой. Вы делаете это, чтобы добавить основной, убрать основной или сбалансировать память и CPU. Во время миграции слот может быть в переходном состоянии. Клиенты могут получить перенаправления `ASK`. `ASK` значит «попробуй тот узел один раз для этого ключа». `MOVED` значит «обнови карту слотов; тот узел владеет слотом».

Решардирование не делит один большой ключ. Если один ключ слишком большой, нужно менять модель данных.

Удаление основного требует сначала увести его слоты. Не убивайте основной, который всё ещё владеет слотами.

## Многоключевые команды через слоты

Многие команды принимают больше одного ключа: `MGET`, `MSET`, `DEL key1 key2`, `SUNION`, `SINTER`, `RENAME`, `ZUNIONSTORE`, `BITOP` и Lua с несколькими `KEYS`.

В Cluster все ключи в одной команде должны хешироваться в один слот. Если нет, Redis возвращает ошибку вроде `CROSSSLOT Keys in request don't hash to the same slot`.

```text
MGET {u:1}:name {u:1}:city
MGET u:1:name u:2:name
```

Первый `MGET` может работать (один тег). Второй падает, если слоты отличаются.

`RENAME` требует источник и назначение в одном слоте. Чтобы переименовать через слоты, приложение делает `GET`, `SET` нового ключа и `DEL` старого. Этот путь не атомарный.

Транзакции (`MULTI`/`EXEC`) и `WATCH` тоже требуют все ключи на одном узле и правила слотов. Нельзя охватить два основных в одной транзакции Redis.

Конвейеры могут включать команды для разных слотов только если клиент делит конвейер по узлу. Наивный конвейер к одному узлу падает или перенаправляет.

Одноключевые команды (`GET`, `HGET`, `INCR`) всегда целят один слот. Это простой случай. Клиент следует `MOVED` к верному узлу.

Когда проектируете схему, кладите ключи, которые нужно читать вместе, под один хеш-тег, или избегайте многоключевых команд и делайте несколько одноключевых вызовов.

`SCAN` — на узел. Полное сканирование кластера должно запрашивать каждый основной.

## Поддержка клиента для режима cluster

Клиент, осведомлённый о кластере:

- Подключается хотя бы к одному узлу
- Загружает карту слотов (`CLUSTER SLOTS`)
- Отправляет каждую команду на узел, который владеет слотом
- Следует `MOVED` и обновляет карту
- Следует `ASK` с `ASKING`, когда слот мигрирует
- Делит конвейеры и многоключевые команды по слоту, когда библиотека умеет

Клиент, не осведомлённый о кластере, говорит с одним узлом как с автономным Redis. Этот узел возвращает `MOVED` для ключей, которыми не владеет. Неосведомлённый клиент считает `MOVED` ошибкой. Не используйте клиент только для автономного режима против Cluster.

`redis-cli -c` включает режим cluster. CLI тогда следует перенаправлениям.

```text
redis-cli -c -h 127.0.0.1 -p 7000
```

Пулы соединений должны хранить карту слотов и соединение на узел (или подмножество). После переключения или решардирования карта меняется. Хорошие клиенты обновляются на `MOVED`.

Таймауты и повторы требуют осторожности. Повтор записи после сетевой ошибки может дважды применить `INCR`. Используйте идемпотентные записи или примите риск.

Библиотеки: многие официальные и популярные клиенты имеют опцию cluster (клиент cluster или флаг). Читайте ту страницу. Не задавайте только список хостов для Sentinel, когда сервер — Cluster. Sentinel и Cluster — разные топологии.

Вывод `CLUSTER SLOTS` включает адреса узлов и диапазоны слотов. Межсетевые экраны должны позволять клиенту достичь каждого основного (и реплик, если читаете с реплик). Один VIP, который прячет все узлы, не работает, если это не умный прокси.

Проверьте клиент в лаборатории с `MOVED` (перезапуск узла, решардирование одного слота) до продакшена.

`READONLY` — команда Cluster для чтений с реплики. Чтения с реплики могут быть устаревшими, как чтения с реплики Sentinel.

# 7. Конвейер агрегации

## Описание

Агрегация обрабатывает документы в **конвейере**. Каждая **стадия** меняет поток. Эта тема показывает `$match`, `$project`, `$group`, `$sort`, `$limit`, `$lookup`, `$unwind`, `$addFields`, `$set` и `$facet`. Также сравниваете агрегацию со многими маленькими find и изучаете лимиты памяти. Сначала завершите запросы и моделирование.

Используйте один термин для каждого понятия. **Конвейер** — массив стадий. **Стадия** — объект с одним оператором. `$match` фильтрует. `$group` объединяет документы. `$lookup` читает другую коллекцию. Не используйте агрегацию, когда хватает одного `find`.

---

## Идея конвейера: `$match`, `$project`, `$group`, `$sort`, `$limit`

Конвейер запускают через `aggregate`:

```javascript
db.orders.aggregate([
  { $match: { status: "paid" } },
  { $project: { userId: 1, total: 1, _id: 0 } },
  { $group: { _id: "$userId", spent: { $sum: "$total" } } },
  { $sort: { spent: -1 } },
  { $limit: 10 }
])
```

Порядок важен. `$match` сначала уменьшает число документов. Ставьте `$match` как можно раньше. `$match` может использовать индексы, когда он в начале.

`$project` формирует поля. `1` оставляет поле. Выражение вычисляет поле. Поздние стадии видят только спроецированные поля.

`$group` требует `_id`. `_id` — ключ группы. `null` группирует весь поток в один документ. Накопители включают `$sum`, `$avg`, `$min`, `$max`, `$push` и `$first`.

`$sort` и `$limit` работают как в `find`. `$sort` плюс `$limit` можно оптимизировать до сортировки top-k.

Поток — документы. После `$group` каждый документ — результат группы. Имена полей меняются. В поздних стадиях используйте новые имена.

Пишите конвейеры списком. Именуйте каждую стадию комментарием в заметках. Проверяйте по одной стадии.

## `$lookup` (похоже на соединение)

`$lookup` читает документы из другой коллекции. Это обычная стадия, похожая на соединение.

Простая форма (равенство):

```javascript
{
  $lookup: {
    from: "users",
    localField: "userId",
    foreignField: "_id",
    as: "user"
  }
}
```

Поле результата `user` — **массив**. Совпадение один-к-одному всё равно массив из одного документа. Пустой массив значит, что совпадения нет.

Unwind или `$arrayElemAt`, если нужен один объект.

Более общая форма использует `pipeline` внутри `$lookup` (коррелированный подзапрос). Можно `$match` и `$project` чужие документы.

`$lookup` может быть дорогим. Это не повод игнорировать встраивание. Если каждое чтение нуждается в lookup, лучше встраивание или снимок.

Проиндексируйте `foreignField` на другой коллекции. Без индекса каждый lookup может сканировать.

`$lookup` не заменяет реляционный движок соединений для разовой аналитики. Используйте его для известных путей доступа.

Коллекции должны быть в одной базе для простой формы (читайте текущее руководство про исключения).

## `$unwind`

`$unwind` разворачивает массив. Каждый элемент становится отдельным документом.

```javascript
{ $unwind: "$lines" }
```

Документ `{ _id: 1, lines: [ "a", "b" ] }` становится двумя документами. У каждого `lines: "a"` или `lines: "b"`.

Опции:

- `preserveNullAndEmptyArrays: true` — оставить документы с отсутствующим или пустым массивом
- `includeArrayIndex` — сохранить индекс в поле

`$unwind` умножает число документов. Массив из 1000 элементов делает 1000 документов из одного родителя. Ставьте `$match` до `$unwind`, когда можете. Разворачивайте только нужные массивы.

Частый шаблон: `$unwind`, затем `$group` для агрегации элементов массива, или `$unwind`, затем `$lookup` на каждой строке.

Не делайте `$unwind` огромного неограниченного массива. Измените модель.

После `$unwind` поле `lines` больше не массив (если элемент сам не массив). Поздние стадии должны использовать новую форму.

## `$addFields`, `$set`

`$addFields` добавляет или заменяет поля. Остальные поля остаются.

```javascript
{ $addFields: { totalWithTax: { $multiply: [ "$total", 1.25 ] } } }
```

`$set` в агрегации — псевдоним `$addFields`. Это не тот же объект, что оператор обновления `$set` в `updateOne`, но идея похожа: задать поля.

Используйте `$addFields`, когда нужно вычисленное поле и ещё нужны старые поля. Используйте `$project`, когда нужна строгая форма вывода и вы отбрасываете поля.

Можно перезаписать поле:

```javascript
{ $set: { name: { $toLower: "$name" } } }
```

Выражения используют операторы агрегации: `$concat`, `$ifNull`, `$cond`, `$dateToString` и многие другие. Первый аргумент многих выражений — путь поля с `$`.

`$addFields` не фильтрует. Не группирует. Только вычисляет.

Не вычисляйте на клиенте, если конвейер уже стримит данные и формула проста. Не кладите тяжёлую уникальную бизнес-логику только в конвейер, если та же формула должна жить на двух языках.

## `$facet`

`$facet` запускает несколько конвейеров на **тех же** входных документах. Каждый подконвейер даёт массив в результате.

```javascript
{
  $facet: {
    byStatus: [
      { $group: { _id: "$status", n: { $sum: 1 } } }
    ],
    top: [
      { $sort: { total: -1 } },
      { $limit: 3 }
    ]
  }
}
```

Выход стадии — один документ (или один на входящую группу, но обычное использование — после общего `$match`). Каждый ключ facet держит массив результатов этого подконвейера.

Используйте `$facet` для панели: счета, топ-списки и выборка за один обмен.

Цена: сервер держит входы и выходы facet. Большие facet используют память. Каждый facet независим. `$limit` в одном facet не ограничивает другой.

Не используйте `$facet`, чтобы заменить два дешёвых find, если команда не может читать конвейер. Ясность важна.

Подконвейеры `$facet` не могут использовать `$out` или `$merge` по старым правилам. Читайте текущий список ограничений.

## Агрегация и много маленьких find

Данные можно загрузить многими вызовами `find` в приложении. Данные можно загрузить одним конвейером.

Предпочитайте **find**, когда:

- Нужны документы как они хранятся
- Есть фильтр, сортировка и проекция
- Листаете список
- Логику проще тестировать в приложении

Предпочитайте **агрегацию**, когда:

- Группируете, суммируете или меняете форму
- Нужно развернуть и снова сгруппировать
- Нужен похожий на соединение `$lookup` за одну поездку
- Считаете отчёт

Много маленьких find — проблема, когда:

- Запускаете find на каждый документ в цикле (N+1)
- Тянете большие документы и затем фильтруете в памяти
- Реализуете group-by на клиенте на огромном массиве

Агрегация — проблема, когда:

- Конвейер — второй язык программирования, который может менять только один человек
- Прячете бизнес-правила в конвейере, который приложение тоже реализует
- Делаете `$lookup` графов, которые должны быть сменой модели

Хороший выбор по умолчанию: find для чтений OLTP, агрегация для отчётов и вычисленных представлений. Если отчёт идёт на каждый клик пользователя, храните вычисленное поле (следующий шаблон темы).

## Лимиты памяти и `allowDiskUse`

У стадии конвейера есть лимит памяти. Во многих версиях лимит — **100 мегабайт** ОЗУ на стадию, пока не разрешите диск.

```javascript
db.orders.aggregate(pipeline, { allowDiskUse: true })
```

`$group`, `$sort` и большие потоки `$facet` или `$unwind` могут упереться в лимит. Ошибка упоминает память или `allowDiskUse`.

`allowDiskUse` позволяет стадии сбрасывать во временные файлы. Запрос может завершиться. Он может быть гораздо медленнее. Сброс на диск — не бесплатное исправление.

Лучшие исправления:

- `$match` раньше
- Проецировать меньше полей
- Избегать `$unwind` огромных массивов
- Индекс, чтобы `$sort` не был огромной сортировкой в памяти
- Изменить модель
- Предвычислить

У Atlas и `mongod` есть и другие лимиты (время, размер документа). Лимит документа 16 MB во многих случаях всё равно применяется к документам в потоке. Очень широкие массивы `$push` могут упереться в размер документа.

Не ставьте `allowDiskUse: true` на каждый запрос OLTP. Используйте для отчётов.

`explain` в некоторых версиях может показать использование диска. Тестируйте с размером данных, похожим на продакшен.

1. Прочитайте о памяти агрегации и лимитах 64-бит в вашей версии. Запишите любой лишний лимит Atlas, который найдёте.
2. Спроектируйте отчёт, который не может использовать `allowDiskUse` на пути запроса. Напишите ночной план `$merge`.

## Обзор темы

Эти вопросы не повторяют вопросы из разделов выше. Они охватывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Опишите путь одного документа заказа через `$match`, `$unwind`, `$group` и `$sort`.
2. Как `$lookup` и `$facet` каждый объединяют работу, которую можно сделать больше чем одним запросом?
3. Когда `$addFields` и `$project` приводят к позднему `$match`, который не может использовать индекс?
4. Как лимиты памяти меняют выбор между aggregate, find и хранимым вычисленным полем?
5. Коллега пишет конвейер из 20 стадий для страницы входа. Какими фактами вы его отвергнете?

#### Простые практические задания

1. Напишите один конвейер, который совпадает, группирует, сортирует и ограничивает. Запустите. Запишите результат.
2. Напишите шпаргалку: имена стадий этой темы, по одной строке, плюс `allowDiskUse`.
3. Сделайте `$lookup`, затем `$unwind` массива `as`. Запишите форму поля после unwind.
4. Выполните `explain` на одном конвейере. Сохраните вывод.

#### Средние практические задания

1. Соберите конвейер панели с `$facet` (счета и топ N) после `$match`.
2. Замените цикл N+1 find одной агрегацией. Напишите оба. Сравните времена.
3. Вызовите или опишите ошибку памяти, затем исправьте через `$match` или `allowDiskUse`. Запишите, какое исправление выбрали и почему.

#### Сложные практические задания

1. Напишите конвейер из пяти стадий с `$lookup`, `$unwind` и `$group`. Добавьте индексы, которые нужны `$match` и lookup. Докажите через `explain`.
2. Прочитайте `$merge` или `$out`. Напишите задачу, которая хранит коллекцию дневной сводки. Включите конвейер и уникальный ключ сводки.

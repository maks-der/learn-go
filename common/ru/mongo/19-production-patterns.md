# 19. Производственные практики

## Описание

Эта тема показывает привычки, которые держат приложение MongoDB безопасным в продакшене. Вы меняете схемы через **expand-contract**. Запускаете **дозаполнения**. Делаете записи **идемпотентными**. Выбираете раскладку **мультиарендности**. Смотрите соединения, отставание репликации, ошибки страниц и медленные операции. Сначала завершите моделирование, драйверы, индексы, репликацию и производительность.

Используйте один термин для каждого понятия. **Expand-contract** — смена схемы, которая добавляет новую форму, переносит данные, затем убирает старую форму. **Дозаполнение** — задача, которая пишет отсутствующие или новые поля на существующих документах. **Идемпотентная** запись даёт тот же результат, когда запускаете её снова. **Наблюдаемость** — практика измерять систему, чтобы видеть проблему.

Эти практики — работа приложения и эксплуатации вместе. Хорошая модель всё равно падает, если выкат нельзя откатить.

## Смены схемы expand-contract

MongoDB не требует миграцию таблицы для нового поля. Приложению всё равно нужен план. Старые процессы и новые процессы могут работать одновременно во время выката.

**Expand-contract** (также называют expand-migrate-contract):

1. **Expand.** Добавить новое поле или новую коллекцию. Выкатить код, который пишет и старую форму, и новую, или пишет новое поле и всё ещё читает старое.
2. **Migrate.** Дозаполнить старые документы (следующий раздел). Подтвердить, что читатели могут использовать новое поле.
3. **Contract.** Выкатить код, который читает только новое поле. Затем перестать писать старое поле. Убрать старое поле позже, если нужно место.

Пример: переименовать `n` в `quantity`.

- Версия A пишет только `n`
- Версия B пишет `n` и `quantity`
- Дозаполнение копирует `n` в `quantity`, где отсутствует
- Версия C читает `quantity` и пишет только `quantity`
- Поздняя задача делает `$unset` `n`

Не выкатывайте читателя, которому нужен `quantity`, до конца дозаполнения, если у читателя нет запасного пути.

Не удаляйте поле в том же релизе, который впервые пишет новое поле.

Поле **версии схемы** (`schemaVersion: 2`) помогает приложению выбрать путь декодирования. Для катящихся выкатов всё равно нужен expand-contract.

Валидация (JSON Schema) тоже должна сначала расшириться. Строгая схема, которая требует новое поле, отклонит старые документы. Поднимайте `validationLevel` осторожно. Используйте `moderate` или более слабое правило во время переноса, если должны.

## Дозаполнения

**Дозаполнение** — пакетная задача, которая обновляет существующие документы. Используете её после расширения схемы, после бага или после добавления вычисленного поля.

Безопасные привычки дозаполнения:

- Работать **пакетами** (`find` с диапазоном по `_id`, затем `bulkWrite`)
- Использовать фильтр, который выбирает только документы, которым ещё нужно изменение
- Делать задачу **идемпотентной** (следующий раздел)
- Ограничивать скорость, чтобы не заполнить кэш WiredTiger или oplog скачком
- Логировать прогресс (последний `_id`, счёт, ошибки)
- Предпочитать secondary для **чтения** скана, если принимаете отставание, но **писать** на primary
- Запускать на replica set, чтобы можно было прервать и повторить

Идея примера:

```javascript
db.orders.updateMany(
  { quantity: { $exists: false }, n: { $exists: true } },
  [ { $set: { quantity: "$n" } } ]
)
```

Один `updateMany` на десятках миллионов документов может быть слишком велик. Предпочитайте зацикленные пакеты с паузой.

Не дозаполняйте на пути веб-запроса.

Не начинайте дозаполнение в пятницу без выключателя остановки.

Не держите мультидокументную транзакцию через огромное дозаполнение.

Если добавили индекс, который нужно дозаполнению, создайте индекс сначала. Если дозаполнение делает индекс бесполезным, удалите старый индекс в фазе contract.

У Atlas есть онлайн-инструменты, и скрипт всё равно можно запустить с воркера. Измеряйте отставание репликации во время задачи.

## Идемпотентные записи

**Идемпотентная** запись оставляет то же хранимое состояние, когда отправляете её один раз или много раз с тем же намерением.

Повторы случаются. Драйверы повторяют некоторые записи. Пользователи дважды кликают. Очереди доставляют снова. Потребители change stream воспроизводят. Без идемпотентности получаете дубликаты заказов или двойной `$inc`.

Инструменты:

- **Естественный ключ** и **уникальный индекс**. `insertOne` `{ _id: orderId }` или `{ idempotencyKey }` падает во второй раз. Считайте дубликат ключа успехом, если документ тот же.
- **`upsert`** с фильтром, который есть идентичность сущности.
- **`$set`** абсолютного значения вместо `$inc`, когда можете отправить итоговое число.
- **Compare-and-set** (`updateOne` с полем версии), когда два писателя гоняются.
- Для `$inc` включите **набор дедупликации** (ограниченный) id запросов или храните один документ журнала на запрос.

Пример:

```javascript
db.orders.updateOne(
  { _id: "ord_123" },
  { $setOnInsert: { total: 10, createdAt: new Date() } },
  { upsert: true }
)
```

Второй вызов не создаёт второй заказ.

Не генерируйте новый ObjectId на клиенте для каждого повтора того же действия пользователя. Отправляйте id, который клиент создал один раз.

Не делайте `$inc` баланса на каждый повтор того же платежа.

Идемпотентность — не только для денег. Флагам отправки email и обработчикам webhook она тоже нужна.

Сочетайте это с write concern majority для платежей, чтобы повтор после таймаута не скрыл зафиксированную запись. Читайте заметки драйвера о повторе и `retryWrites`.

## Мультиарендность: база vs коллекция vs `tenantId`

**Мультиарендность** значит, что одно приложение обслуживает многих клиентов (тенантов). Данные нужно изолировать.

Три частые раскладки:

**База на тенанта.** `tenant_acme`, `tenant_globex`. Сильная изоляция. Свои индексы и резервные копии на тенанта. Многие базы могут давить на метаданные и соединения. Лучше для немногих больших тенантов или строгой изоляции.

**Коллекция на тенанта.** `orders_acme`. Изоляция слабее, чем база. Число коллекций может взорваться. Редко лучший выбор по умолчанию.

**Поле `tenantId`** на общих коллекциях. `{ tenantId: "acme", ... }`. Один набор индексов. Каждый запрос **должен** включать `tenantId`. Уникальный индекс — `{ tenantId: 1, orderId: 1 }`, не один `{ orderId: 1 }`, если id могут столкнуться. Это обычный выбор по умолчанию для многих малых тенантов.

Правила для `tenantId`:

- Приложение задаёт `tenantId` из сессии, не только из тела клиента
- Индексы начинаются с `tenantId` или включают его
- Если шардируете, `tenantId` часто префикс ключа шарда (следите за горячими тенантами)
- Шифрование и RBAC могут добавить слой (пользователь на тенанта труден в большом масштабе; часто фильтр обеспечивает приложение)

Не смешивайте раскладки без письменного плана.

Не доверяйте `tenantId` из тела JSON без проверки на сервере.

Огромному тенанту позже может понадобиться своя база или шард (выброс). Expand-contract применяется к переносу одного тенанта.

Atlas и `maxIncomingConnections` всё равно применяются. Тысяча баз может навредить. Измеряйте.

## Наблюдаемость: соединения, отставание репликации, ошибки страниц, медленные операции

**Наблюдаемость** значит, что здоровье видно метриками, логами и трассами. Для MongoDB смотрите хотя бы эти сигналы.

**Соединения.** Каждый клиент использует пул. Слишком много экземпляров приложения × большие пулы исчерпывают `maxIncomingConnections`. Метрики: текущие соединения, доступные, процент использования. Исправление: меньшие пулы, меньше простаивающих клиентов, не создавать `MongoClient` на запрос.

**Отставание репликации.** Secondary позади primary. Метрики: разрыв optime, отставание репликации Atlas. Причины: медленный диск, сеть, огромные записи, дозаполнение. Эффекты: устаревшие чтения, задержанные резервные копии, риск окна oplog. Сигнализируйте, когда отставание остаётся высоким.

**Ошибки страниц / давление кэша.** Рабочий набор не помещается. На некоторых ОС видите ошибки страниц. На всех установках видите задержку, IOPS диска и вытеснение кэша WiredTiger. Исправление: ОЗУ, меньшие документы, меньше индексов, архив или шард.

**Медленные операции.** Профайлер, медленный лог, Atlas Query Insights. Ищите `COLLSCAN`, огромные сортировки и долгие записи. Чините через `explain` и индексы (тема 14).

Также смотрите:

- Свободное место на диске
- CPU
- Окно oplog
- Прогресс построения индекса
- Очереди билетов (билеты чтения/записи WiredTiger) на занятых серверах

Кладите панели в Atlas или в свой стек метрик (сбор `serverStatus`). Будите человека по отставанию и насыщению соединений, не только по CPU.

Не сигнализируйте об одном медленном запросе в лаборатории. Сигнализируйте об устойчивом изменении от базовой линии.

Логи не должны содержать пароли. Редактируйте.

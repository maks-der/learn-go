# 8. Индексы

## Описание

Эта тема показывает индексы в PostgreSQL 16 и PostgreSQL 17. Вы узнаёте B-tree по умолчанию и когда используют Hash, GiST, GIN и BRIN. Также узнаёте частичные индексы, индексы по выражению, уникальные и составные индексы, `CREATE INDEX CONCURRENTLY` и `REINDEX`.

Сначала завершите тему 7. Нужно знать операторы, которые поддерживают индексы. Завершите эту тему до чтения планов запросов.

Используйте один термин для каждого понятия. Индекс — вторичная структура, которая помогает серверу находить строки. Куча — таблица. Сканирование может использовать индекс или читать кучу по порядку (последовательное сканирование). Индекс не копирует полную строку, пока не добавите дополнительные столбцы (`INCLUDE`, тема 19).

## B-tree (по умолчанию)

`CREATE INDEX` без `USING` строит B-tree.

```sql
CREATE INDEX items_name_idx ON items (name);
CREATE INDEX items_qty_idx ON items (qty);
```

B-tree поддерживает операторы сравнения: `=`, `<`, `<=`, `>`, `>=`. Поддерживает `ORDER BY` по тому же столбцу и направлению. Поддерживает `BETWEEN`. Поддерживает `LIKE 'abc%'` (префикс). Сам по себе не поддерживает `LIKE '%abc'`.

B-tree — правильный индекс для:

- первичных ключей и уникальных ключей (PostgreSQL их уже создаёт)
- столбцов внешних ключей
- обычных фильтров равенства и диапазона
- ключей сортировки, которые совпадают с запросом

```sql
SELECT * FROM items WHERE id = 10;
SELECT * FROM items WHERE qty >= 100 ORDER BY qty;
SELECT * FROM items WHERE name LIKE 'na%';
```

Планировщик использует индекс только когда оценивает, что индекс дешевле последовательного сканирования. Фильтр, который совпадает с большинством строк, часто использует последовательное сканирование. Этот выбор может быть верным.

Индексы B-tree — сбалансированные деревья. Поиск логарифмический по числу строк. Обновления должны поддерживать индекс. Каждый лишний индекс замедляет `INSERT`, `UPDATE` и `DELETE`.

Именуйте индексы ясным шаблоном: `tablename_column_idx`. Уникальные индексы часто используют `tablename_column_key`.

`\d items` перечисляет индексы. `pg_indexes` перечисляет определения.

Не создавайте второй B-tree на том же столбце, что первичный ключ. Не индексируйте столбец, если нет запроса, которому этот индекс нужен.

## Hash, GiST, GIN, BRIN (когда какой класс)

Класс выбираете через `USING`:

```sql
CREATE INDEX ... ON table USING btree (col);  -- default
CREATE INDEX ... ON table USING hash (col);
CREATE INDEX ... ON table USING gist (col);
CREATE INDEX ... ON table USING gin (col);
CREATE INDEX ... ON table USING brin (col);
```

**Hash** поддерживает только равенство (`=`). Индексы Hash в текущем PostgreSQL пишутся в WAL. B-tree тоже поддерживает `=` и ещё неравенство и `ORDER BY`. Предпочитайте B-tree, пока нет измеренной причины использовать hash.

**GiST** (Generalized Search Tree) поддерживает много классов операторов: геометрические типы, диапазонные типы, полнотекст (`tsvector` с GiST), `pg_trgm` и ограничения исключения. Используйте GiST, когда документация типа говорит GiST. Ограничения исключения на диапазонах используют GiST (тема 5).

**GIN** (Generalized Inverted Index) — для значений, которые содержат много элементов: `jsonb`, массивы, `tsvector` и `pg_trgm`. Индекс GIN сопоставляет элементы указателям строк. Используйте GIN для `jsonb @>`, массива `@>` и полнотекста `@@`.

```sql
CREATE INDEX events_payload_gin ON events USING gin (payload);
CREATE INDEX packs_tags_gin ON packs USING gin (tags);
CREATE INDEX posts_tsv_gin ON posts USING gin (tsv);
```

**BRIN** (Block Range Index) хранит сводки по диапазонам страниц. BRIN маленький. Помогает, когда столбец коррелирует с физическим порядком (временной ряд, который дописывают в таблицу). Используйте BRIN на большом `timestamptz`, который вставляете в порядке времени. Не используйте BRIN на случайном `uuid`.

```sql
CREATE INDEX readings_ts_brin ON readings USING brin (read_at);
```

Выбирайте класс по типу и оператору, не по привычке. Если нужны только `=` и `<` на целом, используйте B-tree.

## Частичные индексы

Частичный индекс использует предложение `WHERE`. Индекс хранит только строки, которые совпадают с предикатом.

```sql
CREATE INDEX orders_open_idx
ON orders (created_at)
WHERE status = 'open';
```

Планировщик может использовать этот индекс, когда `WHERE` запроса подразумевает предикат:

```sql
SELECT * FROM orders
WHERE status = 'open' AND created_at > DATE '2026-01-01';
```

Запрос, который опускает `status = 'open'`, не использует `orders_open_idx`.

Используйте частичный индекс, когда:

- горячее маленькое подмножество (`status = 'open'`, `deleted_at IS NULL`)
- нужно правило уникальности на подмножестве (`UNIQUE (email) WHERE deleted_at IS NULL`)

```sql
CREATE UNIQUE INDEX users_active_email_key
ON users (email)
WHERE deleted_at IS NULL;
```

Это допускает много строк с одним email, если они удалены, и один email среди активных строк.

Частичные индексы меньше полных. Они снижают стоимость записи для строк, которые не совпадают с предикатом.

Держите предикат простым. Используйте неизменяемые выражения. Запрос должен использовать совместимое условие. `WHERE status IN ('open')` часто совпадает с `status = 'open'`. Обёртка-функция может скрыть совпадение.

## Индексы по выражению

Индекс по выражению хранит результат выражения, не сырой столбец.

```sql
CREATE INDEX users_email_lower_idx ON users (lower(email));
```

Планировщик может использовать этот индекс, когда запрос использует то же выражение:

```sql
SELECT * FROM users WHERE lower(email) = 'a@example.com';
```

`WHERE email = 'A@example.com'` не использует `lower(email)`, пока вы тоже не напишете `lower(email)`.

Частые выражения:

- `lower(email)` для равенства без учёта регистра
- `(payload->>'type')` для поля JSON
- `date_trunc('day', created_at)` для дневных корзин
- `(f(col))`, когда `f` помечена `IMMUTABLE`

Выражение должно быть помечено immutable для `CREATE INDEX`. `now()` не immutable. Индексировать `now()` нельзя.

```sql
CREATE INDEX events_type_idx ON events ((payload->>'type'));
```

Вокруг выражения, которое не столбец, нужны скобки.

Уникальный индекс по выражению обеспечивает уникальность выражения:

```sql
CREATE UNIQUE INDEX users_email_lower_key ON users (lower(email));
```

Индексы по выражению добавляют стоимость записи. Сервер вычисляет выражение на каждой записи.

Предпочитайте хранимый генерируемый столбец плюс простой индекс, когда выражение длинное и вы его также `SELECT` (тема 13).

## Уникальные и составные индексы

**Уникальный индекс** запрещает дубликаты ключей. Ограничения `PRIMARY KEY` и `UNIQUE` создают уникальные индексы. Можно также написать:

```sql
CREATE UNIQUE INDEX items_sku_key ON items (sku);
```

Предпочитайте ограничение `UNIQUE`, когда правило — правило данных. Имя ограничения появляется в ошибках. Уникальный индекс — реализация.

**Составной** (многостолбцовый) индекс хранит больше одного столбца:

```sql
CREATE INDEX orders_cust_created_idx
ON orders (customer_id, created_at);
```

Правило большого пальца (B-tree):

- Равенство по левым столбцам, затем диапазон по следующему, хорошо совпадает.
- `WHERE customer_id = 1 AND created_at > '2026-01-01'` может использовать `(customer_id, created_at)`.
- Одно `WHERE created_at > '2026-01-01'` часто не может хорошо использовать этот индекс.

Порядок столбцов важен. Сначала столбцы равенства. Столбец диапазона после.

Составной уникальный индекс обеспечивает уникальность пары:

```sql
CREATE UNIQUE INDEX lines_order_sku_key
ON order_lines (order_id, sku);
```

`INCLUDE` добавляет неключевые столбцы в B-tree для сканирований только по индексу (тема 19). Знайте слово. Используйте, когда измерили стоимость выборки из кучи.

Не дублируйте индекс ограничения вторым самодельным уникальным индексом на тех же столбцах.

Два одностолбцовых индекса — не то же самое, что один составной. Планировщик может комбинировать индексы bitmap-сканированием (тема 9). Составной индекс всё равно лучше для шаблона ведущее равенство плюс диапазон.

## `CREATE INDEX CONCURRENTLY`

`CREATE INDEX` берёт блокировку, которая блокирует записи в таблицу на время построения. На занятой таблице эта блокировка — проблема.

`CREATE INDEX CONCURRENTLY` строит индекс без долгой блокировки записи. Чтения и записи продолжаются. Построение сканирует таблицу дважды. Его нельзя запускать внутри блока транзакции.

```sql
CREATE INDEX CONCURRENTLY items_name_idx ON items (name);
```

Правила:

- Нельзя класть `CONCURRENTLY` в `BEGIN ... COMMIT`.
- Построение может упасть. Неудачный конкурентный индекс недействителен. `\d` показывает `INVALID`.
- Удалите недействительный индекс через `DROP INDEX CONCURRENTLY` и попробуйте снова.
- Конкурентное построение занимает больше времени и ресурсов, чем обычное.

```sql
DROP INDEX CONCURRENTLY IF EXISTS items_name_idx;
```

`CREATE UNIQUE INDEX CONCURRENTLY` тоже есть. Проверки уникальности идут во время построения. Конкурентные записи не должны нарушать уникальность.

Используйте `CONCURRENTLY` в продакшене на больших живых таблицах. Используйте обычный `CREATE INDEX` в пустых базах, миграциях, которые уже блокируют, и сессиях, которые допускают паузу записи.

`REINDEX CONCURRENTLY` — соответствующая команда перестроения (следующий раздел).

В PostgreSQL 16 и 17 конкурентное создание индекса — стандартный операционный инструмент. Тестируйте на копии. Следите за нагрузкой.

## `REINDEX`

Индексы могут раздуваться или портиться. `REINDEX` перестраивает индекс из таблицы.

```sql
REINDEX INDEX items_name_idx;
REINDEX TABLE items;
REINDEX SCHEMA public;
REINDEX DATABASE current_database();
```

`REINDEX TABLE` перестраивает все индексы таблицы, включая индекс первичного ключа.

Обычный `REINDEX` блокирует записи. `REINDEX INDEX CONCURRENTLY` и `REINDEX TABLE CONCURRENTLY` перестраивают без долгой блокировки записи. Конкурентный reindex нельзя запускать в транзакции. Некоторые системные каталоги он обрабатывает не во всех формах. Читайте документацию для формы, которую используете.

```sql
REINDEX INDEX CONCURRENTLY items_name_idx;
```

Когда переиндексировать:

- измерили раздутие индекса (тема 11)
- сменили `fillfactor` или параметры хранения
- документация или процесс поддержки говорит перестроить после порчи
- конкурентное создание оставило недействительный индекс (удалить и создать снова; reindex — другой путь)

`REINDEX` — не еженедельная привычка для каждой таблицы. Autovacuum и HOT-обновления (тема 19) держат многие B-tree здоровыми. Сначала измеряйте.

`VACUUM FULL` тоже переписывает таблицу и её индексы. Эта команда тяжелее. Тема 11 её разбирает.

PostgreSQL 17 улучшил часть внутренностей vacuum и reindex. SQL, который вы пишете, тот же.

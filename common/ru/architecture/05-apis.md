# 5. API

## Описание

API (интерфейс прикладного программирования) — контракт, который клиент может вызвать. Эта тема покрывает REST с HTTP и JSON, RPC с gRPC, GraphQL, версионирование, обратную совместимость, постраничную выдачу, ошибки, ключи идемпотентности и разницу между публичными и внутренними API.

API — архитектура. Смена контракта дорога для каждого клиента. Считайте API продуктом. Пишите контракт. Тестируйте контракт.

Завершите темы 1–4 до этой темы. Сочетайте с `net.topics.md`, если HTTP новый. Используйте защитный дизайн. Не используйте эту тему, чтобы планировать злоупотребление другими системами.

Используйте один термин для каждого понятия. REST — не «любой JSON поверх HTTP». RPC — стиль вызова. GraphQL — язык запросов и среда выполнения. Эти инструменты решают разные задачи.

## REST / HTTP JSON

REST (Representational State Transfer) — стиль для HTTP API. Практический REST API использует ресурсы, методы HTTP и представления (часто JSON).

Ресурс — существительное, которое API открывает (`/books/42`, `/loans`). `GET` читает. `POST` создаёт или начинает действие. `PUT` заменяет. `PATCH` обновляет часть. `DELETE` удаляет. Используйте методы по смыслу. Не используйте `GET` для изменения.

JSON — текстовый формат структурированных данных. Держите имена полей стабильными. Используйте типы, которые JSON может выразить (объект, массив, строка, число, логическое, null). Датам нужен заявленный формат (часто ISO 8601).

Практический чек-лист REST:

- Используйте существительные в путях для ресурсов.
- Используйте коды статуса HTTP с ясным смыслом (`200`, `201`, `204`, `400`, `401`, `403`, `404`, `409`, `429`, `500`).
- Используйте `Content-Type: application/json`, когда тело — JSON.
- Держите аутентификацию вне URL (используйте заголовки).
- Держите API без состояния на экземпляре (тема 2).

REST — не религия. Действие `POST /loans/42/return` может быть яснее общего `PATCH`. Документируйте правило.

Гипермедиа (ссылки в ответах) необязательна. Многие команды поставляют JSON ресурса без полного дизайна гипермедиа. Этот выбор приемлем, если контракт задокументирован.

Проверяйте вход. Ограничивайте размеры. Ставьте тайм-ауты (тема 2). Журналируйте идентификатор запроса.

## RPC (gRPC) и GraphQL (когда каждый помогает)

RPC (удалённый вызов процедуры) — стиль, где клиент вызывает именованную процедуру на сервере. Клиент выглядит как локальная функция. Сеть скрыта за заглушкой.

gRPC — частая система RPC. Она использует HTTP/2 и Protocol Buffers (protobuf) для типов. Вы пишете файл `.proto`. Инструменты генерируют код клиента и сервера.

gRPC подходит для внутренних вызовов сервис-сервис, когда обе стороны могут делить схему и когда нужны строгие типы и потоки. gRPC труднее для простого браузерного клиента. Браузеры часто используют gRPC-Web или JSON HTTP API вместо этого.

Выгоды gRPC:

- Сгенерированные типы снижают часть дрейфа контракта.
- Двоичное кодирование может быть эффективным.
- Потоки — идея первого класса.

Цены gRPC:

- Инфраструктура браузера и кэша проще с JSON HTTP.
- Человеческая отладка двоичных полезных нагрузок нуждается в инструментах.
- Правила версий всё равно нужны. Сгенерированный код не снимает работу совместимости.

Считайте файл `.proto` контрактом. Ревьюйте его как API. Не меняйте номера полей небрежно. У protobuf есть правила кодирования, которые зависят от этих номеров.

GraphQL — язык запросов и среда выполнения. Клиент просит граф полей в одном запросе. Сервер разрешает эти поля. GraphQL помогает, когда многим клиентам нужны разные формы одного графа и когда один ресурс HTTP JSON заставил бы много круговых поездок.

Цены GraphQL:

- Наивный резолвер может создать нагрузку N+1 на хранилище.
- Авторизация должна идти на поле или на тип, не только на URL.
- Кэширование труднее, чем кэширование ресурса `GET`.
- Публичная конечная точка GraphQL может открыть большую поверхность.

RPC — не «быстрее, поэтому всегда используйте». GraphQL — не «современно, поэтому всегда используйте». Измеряйте. Небольшому монолиту не нужен gRPC внутри процесса. Используйте вызов функции. Одностраничное студенческое приложение, которое читает три ресурса, может использовать REST.

Типичный раздел: JSON HTTP (стиль REST) для публичных или браузерных клиентов. gRPC только если появляется второй внутренний сервис и обе команды могут эксплуатировать protobuf. GraphQL когда у BFF или публичного графа есть доказанная проблема полезной нагрузки (тема 13).

## Версионирование и обратная совместимость

Версионирование — практика менять контракт без тихого разрыва старых клиентов. Обратная совместимость значит, что старый клиент всё ещё работает после развёртывания нового сервера (или наоборот, в заявленном окне).

Правила, которые держат JSON HTTP API совместимым:

- Добавляйте поле. Не удаляйте поле, которое клиенты ещё читают.
- Не меняйте смысл поля.
- Не меняйте тип (строка на объект) без нового имени поля или новой версии.
- Считайте неизвестные поля в запросе политикой проверки, которую вы пишете (отклонить или игнорировать). Пишите правило.

Окно совместимости — время, когда работают и старые, и новые клиенты. Мобильные клиенты требуют длинное окно. Внутренние клиенты в одном репозитории могут использовать короткое окно, если вы поставляете их вместе.

Версия в URL (`/v1/books`) или в заголовке. Версии в URL легко видеть. Версии в заголовке держат пути короткими. Выберите одно правило и держите его.

Ломающее изменение нуждается в новой версии или новом поле. Документируйте дату заката старой версии. Не держите вечные версии без владельца.

У protobuf и gRPC свои правила. Новые необязательные поля могут быть совместимы. Повторное использование номера поля опасно. Зарезервированные номера существуют не зря.

Совместимость — не только типы. Коды ошибок, токены постраничной выдачи и порядок сортировки по умолчанию — часть контракта. Смена сортировки по умолчанию — разрыв для клиента, который не отправил сортировку.

Тема 12 покрывает расширить-сжать для схемы и для API. Та же идея: добавить, мигрировать клиентов, затем удалить.

## Постраничная выдача, ошибки, ключи идемпотентности

Постраничная выдача делит большой список на страницы. Клиент не должен запрашивать неограниченный список. Ограничьте размер страницы. Укажите максимум.

Два частых стиля:

- Смещение и лимит: просто. Нестабильно, если строки вставляются во время обхода.
- Курсор (токен следующей страницы): стабильнее для живого списка. Токен непрозрачен для клиента.

Пишите размер страницы по умолчанию. Пишите сортировку. Отсутствующая сортировка делает страницы бессмысленными. Возвращайте токен следующей или URL следующей. Не заставляйте клиента угадывать.

Ошибки — часть контракта. Полезное тело ошибки включает:

- Код ошибки приложения, который остаётся стабильным
- Короткое сообщение для операторов (без секретов)
- Идентификатор запроса (тема 11)
- Необязательные ошибки полей для проверки

Используйте статус HTTP для класса отказа. Используйте тело для детали. Не возвращайте `200` со скрытым флагом ошибки как единственным сигналом.

Ключи идемпотентности защищают небезопасные записи (тема 2). Клиент отправляет ключ на `POST`, который создаёт платёж или выдачу. Сервер хранит ключ и результат. Повтор с тем же ключом не создаёт второй побочный эффект.

Правила для ключей:

- Клиент генерирует ключ для одного намерения.
- Сервер ограничивает размер ключа и время жизни.
- Второй запрос с тем же ключом и другим телом — конфликт (`409`).
- API чтения не нуждаются в ключе.

Фильтр и сортировка тоже контракт. Документируйте разрешённые поля. Отклоняйте неизвестные ключи сортировки. Ограничивайте сложность фильтра, чтобы клиент не мог заставить полное сканирование как отказ в обслуживании. Оставайтесь в защите.

## Публичные против внутренних API

Публичный API имеет клиентов, которых вы не поставляете в том же выпуске. Браузеры, мобильные приложения, партнёры и другие организации — публичные клиенты. Окно совместимости длинное. Документация — продукт. Аутентификация, лимиты частоты и стабильная модель ошибок обязательны.

Внутренний API имеет клиентов, которыми владеет одна организация. Окно может быть короче, если вы поставляете клиентов вместе. Вы всё равно пишете контракт. Вы всё равно версионируете ломающие изменения. «Внутренний» — не лицензия на тихий разрыв.

Различия, которые важны:

- Публичные API скрывают внутренние имена и формы таблиц.
- Публичные API открывают меньше данных (наименьшие привилегии, тема 10).
- Внутренние API могут использовать gRPC, если обе стороны его эксплуатируют.
- Публичные API обычно остаются на HTTP JSON для браузеров и партнёров.
- Лимиты частоты и контроль злоупотреблений строже на публичных поверхностях. Оставайтесь в защите.

Модульный монолит может открыть один публичный HTTP API и держать внутренние пакеты как вызовы функций. Это не два API. Не добавляйте сеть внутри процесса ради моды.

Когда у вас две единицы развёртывания, внутренний контракт всё равно API (тема 9). Относитесь к нему с тайм-аутами, идемпотентностью и совместимостью.

Не ставьте операции администратора на ту же публичную поверхность без более строгой идентичности и отдельного аудита (тема 10). Скрытый путь — не контроль безопасности.

Пишите, кто может вызывать API. Пишите класс данных каждого поля. Публичное поле каталога — не то же, что персональный идентификатор.

#### Простые практические задания

# 7. Обмен сообщениями

## Описание

Обмен сообщениями — связь через сообщения, которые брокер или журнал хранит и доставляет. Эта тема покрывает команды, события и запросы; брокеры против журналов событий; исходящий и входящий ящик; проблему двойной записи; порядок, дубликаты и ядовитые сообщения.

Обмен сообщениями — не значение по умолчанию. Вызов функции в модульном монолите проще (тема 3). Добавляйте сообщение, когда нужен разрыв по времени, буфер всплеска или граница между владельцами (темы 4 и 6). Детали журнала событий сочетайте с `kafka.topics.md`.

Завершите темы 1–6 до этой темы. Используйте тайм-ауты и идемпотентность из темы 2. Оставайтесь в защите. Не используйте брокеры, чтобы скрыть отсутствующую границу модуля.

Используйте один термин для каждого понятия. Команда — просьба. Событие — факт. Запрос — чтение. Очередь брокера и журнал событий — не один инструмент.

## Команды против событий против запросов

Команда просит систему сделать работу. Имя в повелительном наклонении: `PlaceOrder`, `CapturePayment`. Команда может провалиться. Отправитель часто хочет результат (принято или отвергнуто).

Событие утверждает, что что-то произошло. Имя в прошедшем времени: `OrderPlaced`, `PaymentCaptured`. Событие — факт. Подписчики реагируют. Производитель факта не ждёт всех подписчиков.

Запрос просит данные и не меняет источник истины. `GetOrder` — запрос. Запросы обычно остаются на HTTP или RPC (тема 5). Запрос на основе сообщений возможен, но часто медленнее и труднее отлаживать. Предпочитайте API запрос-ответ для запросов.

Не смешивайте три в одном имени. `UpdateOrder`, которое также значит «заказ обновлён», путает отправителей. Отправьте команду. После успеха опубликуйте событие.

Кто отвечает:

- Обработчик команды проверяет и меняет агрегат (тема 4).
- Подписчик события не должен быть обязателен для фиксации команды, если только вы не используете одну транзакцию с исходящим ящиком (позже в разделе).
- Обработчик запроса читает одобренную модель (тема 6).

Тип сообщения должен включать имя, версию и идентификатор корреляции. Идентификатор корреляции соединяет журналы между процессами (тема 11).

Публикация/подписка (pub/sub) подходит событиям. Издатель отправляет сообщение в тему. Подписчики получают копию. Издатель не называет каждого подписчика. У команды обычно один владелец. Очередь с одной группой потребителей яснее для «сделай эту работу».

Издатель не должен ждать успеха подписчика внутри того же запроса пользователя, если только продукт не шина запрос-ответ. Это ожидание воссоздаёт жёсткую связанность.

## Брокер против журнала событий

Брокер сообщений (например очереди в стиле RabbitMQ) доставляет сообщение потребителям. После подтверждения потребителя брокер может удалить сообщение из очереди (зависит от продукта). Фокус — работа, которую нужно сделать. Конкурирующие потребители делят очередь. Одно сообщение обрабатывает один рабочий в группе.

Журнал событий (например Apache Kafka) добавляет записи в долговечный упорядоченный журнал. Потребители держат смещение. Они могут воспроизвести. Фокус — история фактов. См. `kafka.topics.md`.

Используйте очередь брокера, когда:

- У вас есть задание (отправить почту, сделать миниатюру).
- Нужны конкурирующие рабочие.
- Не нужна долгая воспроизведение всех фактов.

Используйте журнал событий, когда:

- Многим независимым потребителям нужны те же факты.
- Нужны воспроизведение и более долгое хранение.
- Вы принимаете большую стоимость эксплуатации.

Журнал — не база для произвольных запросов. Очередь — не полная история аудита, если вы удаляете сообщения.

Не запускайте оба продукта в первый день. Маленькая команда может начать с управляемой очереди для одного задания. Добавляйте журнал, когда есть несколько подписчиков и нужда в воспроизведении.

Оба инструмента — дополнительные домены отказа. Вы должны спроектировать, что происходит, когда брокер или журнал недоступен (тема 8).

Свойства доставки зависят от продукта:

- Не более одного раза: подписчик может пропустить сообщение.
- Не менее одного раза: подписчик может видеть дубликаты. Этот случай частый.
- Ровно один раз: редко как сквозная бизнес-гарантия. Вы всё равно проектируете идемпотентные обработчики.

## Исходящий ящик, входящий ящик и двойная запись

Двойная запись — две записи в два хранилища, которые нельзя зафиксировать как одну транзакцию. Пример: записать строку заказа в базу, затем опубликовать `OrderPlaced` в брокер. Если процесс останавливается между двумя записями, система неверна. Либо событие отсутствует, либо событие есть без строки.

Шаблон транзакционного исходящего ящика хранит бизнес-строку и строку исходящего ящика в одной транзакции базы. Реле читает исходящий ящик и публикует в брокер. Запись факта и запись «пожалуйста, опубликуй» остаются вместе.

Входящий ящик (или хранилище обработанных сообщений) записывает идентификаторы сообщений, которые потребитель уже обработал. При дублирующей доставке потребитель пропускает побочный эффект. Это идемпотентность для сообщений (тема 2).

Правила:

- Не делайте двойную запись и не надейтесь.
- Используйте исходящий ящик, когда источник истины и брокер — разные продукты.
- Используйте входящий ящик или другое хранилище идемпотентности на потребителе.
- Реле должно быть перезапускаемым. Строка исходящего ящика остаётся, пока публикация не преуспеет.
- Ограничивайте рост исходящего ящика. Застрявшее реле — инцидент эксплуатации.

В модульном монолите событие в процессе всё ещё может использовать исходящий ящик, если более поздний подписчик работает в другом процессе. Если все подписчики работают в той же транзакции, что и запись, брокер не нужен. Предпочитайте этот простой путь, когда можете.

Исходящий ящик не делает подписчиков транзакционными с писателем. Подписчики всё равно видят факт позже (тема 4). Исходящий ящик только предотвращает отсутствующую или лишнюю публикацию относительно записи источника.

## Порядок, дубликаты и ядовитые сообщения

Порядок — правило, которое говорит, какое сообщение потребитель видит первым. Многие брокеры не дают глобальный порядок всех сообщений. Журнал событий может дать порядок внутри раздела или ключа. Если два факта должны остаться в порядке, вы должны положить их на один упорядоченный поток (тот же ключ, тот же раздел или та же очередь с одним потребителем).

Не предполагайте глобальный порядок по всем темам. Проектируйте потребителя так, чтобы пара вне порядка была безопасна, или кладите пару на один поток.

Дубликаты нормальны при доставке не менее одного раза. Потребитель может увидеть то же сообщение дважды после сбоя или тайм-аута. Обработчики должны быть идемпотентны. Используйте входящий ящик, уникальный бизнес-ключ или сохранённый ключ идемпотентности.

Ядовитое сообщение — сообщение, которое падает каждый раз. Примеры: неверный JSON, отсутствующее обязательное поле или правило, которое всегда отвергает. Бесконечный повтор ядовитого сообщения блокирует очередь или тратит рабочих.

Правила для ядовитых сообщений:

- Ограничьте число повторов.
- После границы переместите сообщение в хранилище мёртвых писем.
- Оповестите оператора (тема 11).
- Не отбрасывайте бизнес-факт без записи.
- Исправьте производителя или обработчик. Затем воспроизведите из хранилища мёртвых писем, если факт всё ещё действителен.

Ошибка проверки часто не стоит повтора. Тайм-аут зависимости может стоить повтора с отступлением (тема 8).

Пишите ключ порядка в контракте. Пример: все события для одного `orderId` остаются в одном разделе. События разных заказов могут чередоваться.

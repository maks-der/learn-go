# 9. Репликация и устойчивость

## Описание

Репликация копирует каждую партицию на больше чем один брокер. Устойчивость — шанс, что зафиксированная запись останется после падения брокера. Kafka использует лидера, фолловеров и набор in-sync replica (ISR).

Эта тема покрывает ISR, `min.insync.replicas`, unclean leader election, лаг репликации и контроллер KRaft. Завершите эту тему после тем 2 и 4. Предпочитайте KRaft для всех новых кластеров. Не используйте ZooKeeper для новой работы. Этот раздел упоминает ZooKeeper только как старую историю.

Используйте один термин для каждого понятия. Реплика — копия партиции. ISR — набор реплик, которые актуальны. Контроллер — компонент, который управляет метаданными кластера и лидерами партиций. В новой Kafka контроллер — кворум KRaft.

## ISR (in-sync replicas)

Набор in-sync replica (ISR) — набор реплик, которые догнали лидера. Лидер всегда в ISR. Фолловер остаётся в ISR, когда получает новые записи в пределах настроенного лага.

Когда фолловер слишком медленный или останавливается, лидер удаляет его из ISR. Реплика всё ещё назначена, но не in-sync. Вывод `describe` показывает реплики и ISR как два списка.

Для `acks=all` лидер ждёт текущий ISR (и `min.insync.replicas`). Produce, который удовлетворяет этому ожиданию, устойчив на этих in-sync брокерах.

Фолловер, который догнал, может снова войти в ISR. Лаг репликации (следующий раздел) объясняет задержку.

ISR — на партицию. У партиции 0 и партиции 1 отдельные списки ISR.

Не считайте «фактор репликации 3» как «три in-sync копии всегда». ISR может сжаться до 1, если два фолловера отстанут. Тогда `acks=all` ждёт только одного брокера, если `min.insync.replicas` не блокирует запись.

## `min.insync.replicas`

`min.insync.replicas` — минимальный размер ISR, который лидер требует для успешного produce, когда продюсер использует `acks=all`. Если ISR меньше этого значения, лидер отклоняет produce.

Пример: фактор репликации 3, `min.insync.replicas=2`. Кластер может потерять одну реплику и всё ещё принимать устойчивые записи. Если две реплики недоступны, записи с `acks=all` падают. Этот сбой лучше тихой записи на один диск, когда вы требовали две копии.

`min.insync.replicas=1` с `acks=all` гарантирует только одну in-sync копию. Эта копия — лидер. Данные всё ещё можно потерять, если этот брокер умрёт до того, как фолловеры догонят.

Задайте это значение в значении брокера по умолчанию и переопределите на важных топиках. Настройка `acks` продюсера не заменяет эту проверку брокера.

Обычная продакшен-пара — фактор репликации 3 и `min.insync.replicas=2`. Учебный кластер из одного брокера должен использовать `min.insync.replicas=1` и фактор репликации 1.

## Unclean leader election (опасность)

Unclean leader election означает, что Kafka может избрать лидера, которого нет в ISR. Эта реплика отстаёт. Записи, которые существовали только на старом лидере, могут исчезнуть из журнала. Консьюмеры могут увидеть откат. Новые читатели эти записи никогда не увидят.

Безопасный выбор по умолчанию — отказать в unclean election. Если ни один участник ISR не жив, партиция остаётся офлайн, пока не вернётся in-sync реплика. Записи останавливаются. Этот простой лучше тихой потери данных для важных данных.

Имя конфигурации — `unclean.leader.election.enable`. Задайте `false` для важных кластеров. Рассматривайте `true` только когда доступность устаревших данных важнее корректности и бизнес принимает потерю. Задокументируйте этот выбор.

Unclean election — не инструмент ремонта. Не включайте его, чтобы «топик заработал» во время сбоя без письменного решения.

KRaft не меняет эту опасность. Контроллер всё ещё может избрать лидера вне ISR, если вы это разрешите.

## Лаг репликации

Лаг репликации — насколько фолловер отстаёт от лидера. Лаг можно выразить как офсеты (конец журнала лидера минус конец журнала фолловера) или как время.

Лаг растёт, когда фолловер медленный: диск, сеть, CPU или длинная пауза сборки мусора. Лаг также растёт, когда лидер принимает большой всплеск produce.

Высокий лаг вызывает сжатие ISR. Затем взаимодействуют устойчивость и `min.insync.replicas`. Высокий лаг также задерживает момент, когда фолловер — безопасный кандидат в лидеры.

Консьюмеры, которые читают у лидера, не ждут всех фолловеров. Они ждут high watermark (зафиксированные данные). Тема 20 покрывает high watermark против log end offset. Для этой темы: запись безопасна для `acks=all`, когда она есть у ISR.

Мониторьте недореплицированные партиции и метрики fetch фолловера. Постоянный лаг на одном брокере — проблема железа или конфигурации.

Не чините лаг включением unclean election.

## Контроллер (KRaft против старого ZooKeeper)

Контроллер управляет метаданными кластера: топики, назначения партиций, выборы лидеров и членство брокеров.

**KRaft (используйте это).** Kafka хранит метаданные в журнале Raft на узлах контроллеров. Вы форматируете хранилище с идентификатором кластера. Вы запускаете один или несколько контроллеров. Продакшен-кластер использует нечётное число выделенных контроллеров (например 3). Кластер на ноутбуке может использовать совмещённые процессы брокер+контроллер.

KRaft не использует ZooKeeper. Новые версии Kafka не запускают ZooKeeper. Kafka 4.0 и позже убирают ZooKeeper. Учите только KRaft.

**Старый ZooKeeper (не используйте для новой работы).** Старые кластеры хранили часть метаданных в ZooKeeper. Учебники того времени сначала запускают процесс ZooKeeper. Игнорируйте эти шаги, когда строите новый кластер. Если поддерживаете старый кластер, следуйте официальному руководству миграции на KRaft. Не проектируйте новые системы на ZooKeeper.

Контроллер — не то же самое, что лидер партиции. Лидер партиции обрабатывает produce и fetch для одной партиции. Контроллер назначает этого лидера.

Когда активный контроллер падает, кворум KRaft избирает нового контроллера. Операции метаданных кратко паузятся. Данные партиций на брокерах остаются.

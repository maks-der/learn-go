# 13. Промышленное использование

## Описание

Эта тема показывает привычки и инструменты, которые держат приложение MongoDB безопасным в промышленности. Вы открываете change streams и храните resume-токены. Изучаете Atlas Search, коллекции временных рядов и GridFS. Меняете схемы через expand-contract, запускаете дозаполнения и делаете записи идемпотентными. Выбираете мультитенантную раскладку. Избегаете частых антипаттернов.

Сначала завершите моделирование, драйверы, индексы, репликацию и производительность.

Используйте один термин для каждого понятия. **Change stream** — официальный курсор событий изменений. **Resume-токен** позволяет продолжить после разрыва. **Expand-contract** — смена схемы, которая добавляет новую форму, переносит данные, затем убирает старую форму. **Идемпотентная** запись даёт тот же результат, когда запускаете её снова. **Антипаттерн** — дизайн, который выглядит удобно, а потом ломается.

Эти шаблоны — работа приложения и эксплуатации вместе. Хорошая модель всё равно падает, если выкладку нельзя откатить.

## Change streams и resume-токены

Change stream — долгоживущий курсор. Сервер шлёт новое событие, когда совпавшая запись фиксируется. Change streams нужен replica set или шардированный кластер. Одиночного `mongod` недостаточно.

Открыть поток на коллекции в `mongosh`:

```javascript
const cs = db.orders.watch()
cs.tryNext()
```

Драйверы используют `watch` или эквивалентный помощник. Можно смотреть:

- Одну коллекцию
- Одну базу
- Всё развёртывание (с нужным API и привилегиями)

Типичное событие включает:

- `_id` — resume-токен
- `operationType` — `insert`, `update`, `replace`, `delete` и другие
- `fullDocument` — документ после изменения, когда вы его запрашиваете
- `documentKey` — `_id` и поля ключа шарда
- `updateDescription` — поля, которые изменились, для некоторых обновлений
- `clusterTime` — когда изменение произошло в кластере

По умолчанию событие обновления может опустить полный документ. Откройте поток с `fullDocument: "updateLookup"`, когда нужен документ после обновления. Этот lookup имеет цену и может гоняться. Читайте текущие опции.

Поток следует oplog. Если слушатель недоступен дольше окна oplog, поток нельзя возобновить. Нужна полная повторная синхронизация нижестоящей системы.

Фильтруйте в `watch` конвейером агрегации (`$match` по `operationType` или по полям). Не тяните каждое событие, если нужны только вставки.

Не считайте change stream очередью с бесконечным хранением. Это не Kafka. Хранение — окно oplog, пока не добавите другое хранилище.

Не запускайте воркер change stream, который делает медленную работу внутри цикла приёма без противодавления. Можно выпасть из oplog.

**Resume-токен** — `_id` события изменения. Его передают в `watch`, чтобы следующий курсор продолжился после этого события.

```javascript
const token = event._id
const cs2 = db.orders.watch([], { resumeAfter: token })
```

Родственные опции (имена зависят от версии):

- `resumeAfter` — продолжить после этого токена
- `startAfter` — начать после invalidate в некоторых случаях
- `startAtOperationTime` — начать с метки времени кластера

Сохраняйте токен только после того, как закончили нижестоящую работу для этого события. Если сохранить токен сначала и затем упасть, можно пропустить событие. Если токен никогда не сохранять, события воспроизводятся. Предпочитайте доставку **at-least-once** и делайте потребителя **идемпотентным**.

Токены непрозрачны. Не собирайте их вручную. Не храните случайный ObjectId как токен.

Если токен вне oplog, `watch` падает. Нужно снять снимок исходной коллекции и затем начать новый поток с известного времени.

После `invalidate` (drop, rename, drop database) многие курсоры умирают. Может понадобиться `startAfter` или новая полная синхронизация.

Команды используют change streams для **CDC** (change data capture) в поиск или хранилище. Типичный поток:

1. Снять начальный снимок коллекции.
2. Записать cluster time или токен.
3. Применить снимок к приёмнику.
4. Начать change stream с этого времени или токена.
5. Применять события по порядку на документ. Делать каждое применение идемпотентным.

Не читайте хвост `local.oplog.rs` в приложении. Используйте официальный API change stream.

## Atlas Search, временные ряды и GridFS

**Atlas Search** — поисковый движок, который Atlas строит на **Apache Lucene**. Создаёте поисковый индекс на коллекции. Запрашиваете этапом агрегации `$search` (и родственными этапами вроде `$searchMeta`).

Atlas Search — не то же самое, что текстовый индекс MongoDB (`$text`). Текстовый индекс — возможность сервера с ограниченным скорингом и поддержкой языков. Atlas Search сильнее для релевантности полного текста, нечёткого совпадения, автодополнения, фасетов и анализаторов.

Задаёте отображения. Динамические отображения индексируют многие поля. Статические отображения именуют поля и анализатор. Статические отображения легче контролировать.

Типичный конвейер:

```javascript
db.articles.aggregate([
  {
    $search: {
      index: "default",
      text: { query: "replica set", path: "body" }
    }
  },
  { $limit: 20 },
  { $project: { title: 1, score: { $meta: "searchScore" } } }
])
```

Поиск в конечном счёте согласован с коллекцией. Запись не всегда в индексе в ту же миллисекунду. Community Server не включает Atlas Search.

Не создавайте поисковый индекс на каждое поле «на всякий случай». Не используйте `$search` как первую идею для `{ _id: id }`. Используйте `find`.

**Коллекция временных рядов** хранит документы, у которых есть **поле времени** и обычно **поле метаданных**. MongoDB группирует документы в **корзины** на диске. Раскладка корзин экономит место и может ускорить некоторые диапазонные сканирования по времени.

```javascript
db.createCollection("readings", {
  timeseries: {
    timeField: "ts",
    metaField: "sensorId",
    granularity: "seconds"
  }
})
```

Каждое измерение в API всё равно документ. Вставляете одно показание на событие. Корзинами вручную не управляете.

Хорошее применение: датчики, метрики, потоки кликов или событий с ясной меткой времени.

Плохое применение: документы, которые часто обновляют на месте, сильно реляционные операционные данные, данные без настоящего поля времени.

Коллекцию временных рядов нельзя считать обычной коллекцией для каждой команды. Некоторые шаблоны обновления и удаления ограничены. Прочитайте страницу ограничений до миграции горячей коллекции.

Не храните огромный неограниченный массив показаний внутри одного документа датчика.

Лимит размера документа — 16 МБ. **GridFS** хранит больший файл как много **чанков** плюс один документ метаданных **файла**.

Коллекции по умолчанию:

- `fs.files` — имя файла, длина, тип содержимого, дата загрузки
- `fs.chunks` — `{ files_id, n, data }`, где `data` — двоичный чанк

Размер чанка по умолчанию на многих версиях — 255 КБ. Драйверы реализуют загрузку и скачивание. В обычном коде приложения чанки вручную не собирают.

Используйте GridFS, когда файл нужно держать в MongoDB и файл больше 16 МБ, или нужен потоковый API.

Не используйте GridFS, когда доступно объектное хранилище (S3 или аналог) и файл велик или файлов много. Не используйте GridFS для нескольких килобайт. Храните поле BinData или URL.

GridFS нужны индексы, которые создаёт драйвер (уникальный `files_id` + `n` на чанках). Не удаляйте их.

Размер резервной копии растёт с каждым файлом. Дамп GridFS тяжёлый.

Выберите инструмент, который соответствует задаче. Не используйте GridFS для JSON 1 КБ. Не используйте Atlas Search для одного равенства по `_id`.

## Изменения expand-contract, дозаполнения и идемпотентные записи

MongoDB не требует миграцию таблицы для нового поля. Приложению всё равно нужен план. Старые и новые процессы могут работать одновременно во время выкладки.

**Expand-contract** (также expand-migrate-contract):

1. **Expand.** Добавить новое поле или новую коллекцию. Выложить код, который пишет и старую форму, и новую, или пишет новое поле и всё ещё читает старое.
2. **Migrate.** Дозаполнить старые документы. Подтвердить, что читатели могут использовать новое поле.
3. **Contract.** Выложить код, который читает только новое поле. Затем перестать писать старое поле. Позже убрать старое поле, если нужно место.

Пример: переименовать `n` в `quantity`.

- Версия A пишет только `n`
- Версия B пишет `n` и `quantity`
- Дозаполнение копирует `n` в `quantity`, где отсутствует
- Версия C читает `quantity` и пишет только `quantity`
- Позднее задание делает `$unset` `n`

Не выкладывайте читателя, которому нужен `quantity`, до конца дозаполнения, если у читателя нет запасного пути.

Не удаляйте поле в том же релизе, который впервые пишет новое поле.

**Поле версии схемы** (`schemaVersion: 2`) помогает приложению выбрать путь декодирования. Для катящихся выкладок expand-contract всё равно нужен.

Валидация (JSON Schema) тоже должна сначала расшириться. Строгая схема, которая требует новое поле, отклонит старые документы. Используйте `moderate` или более слабое правило во время переноса, если нужно.

**Дозаполнение** — пакетное задание, которое обновляет существующие документы. Его используют после расширения схемы, после бага или после добавления вычисленного поля.

Безопасные привычки дозаполнения:

- Работайте **пакетами** (`find` с диапазоном по `_id`, затем `bulkWrite`)
- Используйте фильтр, который выбирает только документы, которым ещё нужно изменение
- Делайте задание **идемпотентным**
- Ограничивайте скорость, чтобы не заполнить кэш WiredTiger или oplog всплеском
- Логируйте прогресс (последний `_id`, счёт, ошибки)
- Предпочитайте secondary для **чтения** сканирования, если принимаете отставание, но **пишите** на primary

Идея примера:

```javascript
db.orders.updateMany(
  { quantity: { $exists: false }, n: { $exists: true } },
  [ { $set: { quantity: "$n" } } ]
)
```

Один `updateMany` на десятках миллионов документов может быть слишком велик. Предпочитайте циклы пакетов с паузой.

Не дозаполняйте на пути веб-запроса. Не держите мультидокументную транзакцию через огромное дозаполнение.

**Идемпотентная** запись оставляет то же хранимое состояние, когда отправляете её один раз или много раз с тем же намерением.

Повторы случаются. Драйверы повторяют некоторые записи. Пользователи дважды кликают. Очереди доставляют снова. Потребители change stream воспроизводят. Без идемпотентности получаете дубликаты заказов или двойной `$inc`.

Инструменты:

- **Натуральный ключ** и **уникальный индекс**. `insertOne` `{ _id: orderId }` падает во второй раз. Считайте дубликат ключа успехом, если документ тот же.
- **`upsert`** с фильтром, который есть тождество сущности.
- **`$set`** абсолютного значения вместо `$inc`, когда можете послать итоговое число.
- **Compare-and-set** (`updateOne` с полем версии), когда два писателя гоняются.
- Для `$inc` включите **множество дедупликации** (ограниченное) id запросов или храните один документ журнала на запрос.

Пример:

```javascript
db.orders.updateOne(
  { _id: "ord_123" },
  { $setOnInsert: { total: 10, createdAt: new Date() } },
  { upsert: true }
)
```

Второй вызов не создаёт второй заказ.

Не генерируйте новый ObjectId в клиенте на каждый повтор того же действия пользователя. Шлите id, который клиент создал один раз.

Не делайте `$inc` баланса на каждый повтор того же платежа.

## Мультитенантная раскладка

**Мультитенантность** значит, что одно приложение обслуживает многих клиентов (арендаторов). Данные нужно изолировать.

Три частые раскладки:

**База на арендатора.** `tenant_acme`, `tenant_globex`. Сильная изоляция. Свои индексы и копии на арендатора. Много баз могут давить на метаданные и соединения. Лучше для немногих крупных арендаторов или строгой изоляции.

**Коллекция на арендатора.** `orders_acme`. Изоляция слабее, чем база. Число коллекций может взорваться. Редко лучший выбор по умолчанию.

**Поле `tenantId`** на общих коллекциях. `{ tenantId: "acme", ... }`. Один набор индексов. Каждый запрос **должен** включать `tenantId`. Уникальный индекс — `{ tenantId: 1, orderId: 1 }`, не один `{ orderId: 1 }`, если id могут столкнуться. Это обычный выбор по умолчанию для многих мелких арендаторов.

Правила для `tenantId`:

- Приложение задаёт `tenantId` из сессии, не только из тела клиента
- Индексы начинаются с `tenantId` или включают его
- Если шардируете, `tenantId` часто префикс ключа шарда (следите за горячими арендаторами)
- Шифрование и RBAC могут добавить слой (пользователь на арендатора труден в большом масштабе; часто фильтр обеспечивает приложение)

Не смешивайте раскладки без письменного плана.

Не доверяйте `tenantId` из тела JSON без проверки на сервере.

Огромному арендатору позже может понадобиться своя база или шард (выброс). Expand-contract применяется к переносу одного арендатора.

Atlas и `maxIncomingConnections` всё равно действуют. Тысяча баз может навредить. Измерьте.

## Антипаттерны: неограниченные массивы, огромные документы, ключи шарда низкой кардинальности, использование в форме SQL

**Антипаттерн** — дизайн, который выглядит удобно, а потом ломается. Если антипаттерн уже используете, меняйте модель. Сначала не добавляйте больше железа.

**Неограниченный массив** — поле, которое получает `push` на каждое событие без потолка. Примеры: все комментарии вирусного поста, все просмотры страниц, все строки лога, все платежи в одном документе клиента.

Проблемы:

- Каждое обновление переписывает больший документ
- Документ подходит к 16 МБ, затем записи падают
- Индексы массива становятся большими (мультиключевые)
- Каждый читатель загружает весь массив, даже когда нужны последние пять элементов
- Одновременные `$push` и другие обновления спорят за один документ

Правило моделирования остаётся: данные, к которым обращаетесь вместе, могут жить вместе **если массив остаётся ограниченным**.

Ограниченные шаблоны:

- Держать последние N элементов (`$slice` на `$push`)
- Хранить детей во второй коллекции с id родителя
- Использовать шаблон корзины или коллекцию временных рядов для событий
- Использовать шаблон выброса для одного популярного родителя

«Маленький» массив, который растёт на 1 элемент в день, через несколько лет станет большим. Запишите потолок в дизайне.

Не делайте `$push` события просмотра в документ пользователя на каждый клик.

**Лимит размера документа BSON — 16 МБ**. Документ «всего» 10 МБ уже проблема. Он использует кэш, полосу и время блокировки этого документа.

Причины огромных документов: неограниченные массивы, встроенные файлы, огромные строки (дампы HTML, изображения base64), вложенные копии тех же связанных данных.

Профилактика: храните двоичные данные вне документа, ссылайтесь на большие связанные графы, используйте шаблон подмножества, проверяйте максимальную длину в приложении.

Не храните PDF как поле BinData 14 МБ, потому что «это меньше 16 МБ». Если вы близко к лимиту — уже поздно. Разделяйте до ошибки в промышленности.

**Ключ шарда низкой кардинальности** имеет мало различных значений. Примеры: `country` с тремя значениями, `status` с четырьмя значениями, `isActive` с двумя значениями.

Эффекты:

- Чанки нельзя разделить дальше различных значений
- Эти чанки становятся **jumbo**
- Все документы с `status: "open"` живут на одном шарде
- Этот шард **горячий**
- Балансировщик вас не спасёт

Хеширование булева значения не создаёт кардинальность. Всё равно два хеша.

Составной ключ `{ status: 1, orderId: 1 }` может добавить кардинальность **если** `orderId` различен. Префикс `status` всё равно группирует открытые вместе.

Не шардируйте по полю, потому что «оно есть в каждом запросе», если у поля пять значений.

Если уже шардировали по плохому ключу, используйте refine или reshard. Это проект.

**Подмена SQL «как есть»** — идея, что оставляете таблицы, нормализуете каждую сущность, соединяете на каждое чтение и только меняете базу.

MongoDB не запускает SQL как основной язык. `$lookup` — не полный планировщик соединений SQL для каждого разового отчёта. Нет декларативных внешних ключей как главного инструмента целостности. Транзакции есть, но они не запись по умолчанию.

Если сопоставить каждую таблицу коллекции один-к-одному, часто получаете много кругов или много этапов `$lookup`, медленные отчёты, которые SQL делал лучше, схему, которая никогда не использует встраивание, и ключи шарда, которые не совпадают с доступом.

MongoDB подходит, когда проектируете **документы под доступ**. Встраивайте то, что читаете вместе. Ссылайтесь на то, чем делите и обновляете независимо. Используйте хранилище или реляционную базу для тяжёлой разовой аналитики, если это нагрузка.

Мигрировать из SQL можно. Нужно **перепроектировать**. Недостаточно только мигрировать типы.

Не реализуйте эмулятор SQL на MongoDB для всего приложения.

Не запрещайте встраивание, потому что «нормализация всегда права». Не встраивайте всё, потому что «соединения запрещены». Обе крайности — антипаттерны.

Родственный антипаттерн — оборачивать **каждую** запись в мультидокументную транзакцию. Записи одного документа уже атомарны. Используйте транзакцию, когда два документа должны меняться вместе и их нельзя смоделировать как один документ.

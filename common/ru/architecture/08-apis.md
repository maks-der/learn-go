# 8. API

## Описание

API (application programming interface) — это контракт, который клиент может вызвать. Эта тема разбирает REST с HTTP и JSON, RPC с gRPC, GraphQL, версионирование, обратную совместимость, пагинацию, фильтрацию, ошибки, ключи идемпотентности и разницу между публичными и внутренними API.

API — это архитектура. Смена контракта дорога для каждого клиента. Считайте API продуктом. Пишите контракт. Тестируйте контракт.

Завершите темы 1–7 до этой темы. Сочетайте с `net.topics.md`, если HTTP новый. Используйте защитное проектирование. Не используйте эту тему, чтобы планировать злоупотребление другими системами.

Используйте один термин для каждого понятия. REST — это не «любой JSON поверх HTTP». RPC — стиль вызова. GraphQL — язык запросов и среда выполнения. Эти инструменты решают разные задачи.

## REST / HTTP JSON

REST (Representational State Transfer) — стиль для HTTP API. Практический REST API использует ресурсы, HTTP-методы и представления (часто JSON).

Ресурс — это существительное, которое API открывает (`/books/42`, `/loans`). `GET` читает. `POST` создаёт или начинает действие. `PUT` заменяет. `PATCH` обновляет часть. `DELETE` удаляет. Используйте методы по их смыслу. Не используйте `GET` для изменения.

JSON — текстовый формат структурированных данных. Держите имена полей стабильными. Используйте типы, которые JSON может выразить (object, array, string, number, boolean, null). Датам нужен заявленный формат (ISO 8601 обычен).

Практический чеклист REST:

- Используйте существительные в путях для ресурсов.
- Используйте коды статуса HTTP с ясным смыслом (`200`, `201`, `204`, `400`, `401`, `403`, `404`, `409`, `429`, `500`).
- Используйте `Content-Type: application/json`, когда тело — JSON.
- Держите аутентификацию вне URL (используйте заголовки).
- Держите API stateless на экземпляре (тема 4).

REST — не религия. Действие `POST /loans/42/return` может быть яснее общего `PATCH`. Документируйте правило.

Hypermedia (ссылки в ответах) необязательна. Многие команды поставляют JSON ресурса без полного hypermedia-проекта. Этот выбор приемлем, если контракт задокументирован.

Проверяйте ввод. Ограничивайте размеры. Задавайте таймауты (тема 4). Пишите идентификатор запроса в журнал.

## RPC (gRPC)

RPC (remote procedure call) — стиль, где клиент вызывает именованную процедуру на сервере. Клиент выглядит как локальная функция. Сеть скрыта за заглушкой.

gRPC — обычная система RPC. Она использует HTTP/2 и Protocol Buffers (protobuf) для типов. Вы пишете файл `.proto`. Инструменты генерируют код клиента и сервера.

gRPC подходит для внутренних вызовов сервис-сервис, когда обе стороны могут разделять схему и когда нужны строгие типы и потоковая передача. gRPC труднее для простого клиента браузера. Браузеры часто используют gRPC-Web или JSON HTTP API вместо этого.

Выгоды:

- Сгенерированные типы снижают часть дрейфа контракта.
- Двоичное кодирование может быть эффективным.
- Потоковая передача — идея первого класса.

Цены:

- Инфраструктура браузера и кэша проще с JSON HTTP.
- Человеческая отладка двоичных полезных нагрузок требует инструментов.
- Правила версий всё равно нужны. Сгенерированный код не снимает работу совместимости.

RPC — не «быстрее, поэтому всегда используйте». Измеряйте. Маленькому монолиту не нужен gRPC внутри процесса. Используйте вызов функции.

Считайте файл `.proto` контрактом. Рецензируйте его как API. Не меняйте номера полей бездумно. У protobuf есть правила кодирования, которые зависят от этих номеров.

## GraphQL (когда помогает, когда вредит)

GraphQL — язык запросов и среда выполнения для API. Клиент отправляет запрос, который называет нужные поля. Сервер возвращает JSON, который соответствует форме запроса. Один endpoint обычен (`POST /graphql`).

GraphQL помогает, когда многим клиентам нужны разные срезы большого графа (mobile хочет мало полей, консоль администратора хочет много полей). Он может снизить число round trip, которое потребовал бы фиксированный набор ресурсов REST.

GraphQL вредит, когда:

- Команда маленькая и нескольких ресурсов REST достаточно.
- Запросы становятся дорогими, потому что клиенты просят глубокие графы (чтения N+1).
- Кэширование на HTTP проще с ресурсами `GET`, чем с одним запросом `POST`.
- Авторизация чувствительна к полям и её легко пропустить.
- Загрузка файлов и простые CDN кэша неудобны.

Схема GraphQL всё равно контракт. Переименование поля — ломающее изменение. Вы всё равно версионируете или объявляете поля устаревшими.

Не используйте GraphQL как модный фасад одной таблицы. Если клиенту всегда нужны те же пять полей, REST проще.

Защищайте сервер. Ограничивайте глубину и стоимость запроса. Аутентифицируйте. Не открывайте внутренние колонки, которые клиент не должен видеть.

## Версионирование

Версионирование — это метод, которым вы публикуете больше одного контракта одновременно или развиваете контракт контролируемым способом.

Обычные методы:

- Версия в пути: `/v1/books` и `/v2/books`.
- Версия в заголовке: `Accept: application/vnd.myapp.v1+json`.
- Аддитивная эволюция без номера для маленького внутреннего API.

Версии в пути легко видеть в журналах и в прокси. Версии в заголовке держат URL стабильными. Выберите один метод. Документируйте его. Не смешивайте оба без причины.

Версия — не папка, которую вы копируете вечно. У `v2` должна быть причина: ломающее изменение, которого нельзя избежать. Аддитивным полям не всегда нужен `v2`.

Держите `v1`, пока клиенты не переедут. Задайте дату заката. Измеряйте, какие клиенты всё ещё вызывают `v1`. Тема 2: наблюдаемость.

Внутренние API могут развиваться быстрее, если одна команда владеет всеми клиентами. Публичные API не могут. Следующие разделы разбирают совместимость и публичные против внутренних API.

Пишите тесты совместимости. Храните примеры запросов и ответов. Проигрывайте их в непрерывной интеграции.

## Обратная совместимость

Совместимое изменение позволяет старым клиентам продолжать работать. Ломающее изменение заставляет клиентов меняться.

Совместимые примеры:

- Добавить необязательное поле.
- Добавить endpoint.
- Добавить значение enum только если старые клиенты игнорируют неизвестные значения (укажите правило).
- Ослабить ограничение (принять более длинное имя, если вы всё равно его храните).

Ломающие примеры:

- Удалить или переименовать поле.
- Изменить тип или смысл поля.
- Превратить успех в ошибку для того же запроса.
- Переиспользовать имя поля для нового смысла.
- Изменить формат идентичности (`42` против UUID) без периода отображения.

Правила, которые держат версию стабильной:

- Не удаляйте и не переименовывайте поля.
- Не меняйте типы полей.
- Добавляйте новые поля как необязательные.
- Добавляйте новые endpoint вместо смены смысла старого endpoint.

Правило неизвестных полей: сервер игнорирует неизвестные поля от клиентов, если вы хотите, чтобы более старый сервер принимал более нового клиента. Клиент игнорирует неизвестные поля от серверов, если вы хотите, чтобы старый клиент принимал новый сервер. Запишите правило. Библиотеки JSON различаются.

Семантическое изменение — тихий разрыв. Поле `status` всё ещё существует, но «open» теперь означает другое бизнес-состояние. Это изменение ломающее, даже если JSON разбирается.

## Пагинация, фильтрация, ошибки

Пагинация делит большой список на страницы. Без пагинации endpoint списка может вернуть слишком много данных. Задержка и память растут. Доступность может упасть.

Обычные стили:

- Offset и limit: `?offset=40&limit=20`. Просто. Нестабильно, если строки вставляются во время обхода.
- Cursor: `?cursor=abc&limit=20`. Стабильнее для бесконечной прокрутки. Труднее прыгнуть на страницу 10.

Всегда ограничивайте `limit`. Клиент не должен запрашивать миллион строк. Возвращайте next cursor или next offset. Документируйте пустые страницы.

Фильтрация ограничивает набор (`?status=open`). Сортировка должна использовать allow-list полей. Не передавайте сырой SQL. Это дефект.

Ошибкам нужна стабильная форма. Пример полей: `code`, `message`, `request_id`. Не утекайте внутренности (трассировки стека, SQL или пути на диске) публичному клиенту.

Используйте правильный класс статуса:

- 4xx: клиент может исправить запрос (или не может иметь доступ).
- 5xx: сервер или зависимость отказали.

Не используйте `200` со скрытым полем ошибки как единственный сигнал, если можете использовать код статуса. Некоторые проекты GraphQL используют `200` с массивом `errors`. Документируйте это исключение.

Пределы частоты используют `429`. Ошибки проверки используют `400` или `422`, если вы принимаете это соглашение. Будьте последовательны.

## Ключи идемпотентности для записей

Ключ идемпотентности — это сгенерированный клиентом идентификатор для одной задуманной записи. Клиент отправляет ключ в заголовке (обычное имя — `Idempotency-Key`). Сервер хранит ключ и исход. Повтор с тем же ключом не применяет запись снова.

Используйте ключи на платежах, переводах и других записях, которые не должны дублироваться. Тема 4 определила идемпотентность. Этот раздел применяет её к HTTP API.

Правила клиента:

- Генерируйте новый ключ для нового намерения.
- Переиспользуйте ключ только для повтора того же намерения.
- Держите ключ на окно таймаута и повтора.

Правила сервера:

- Храните ключ, отпечаток запроса (или хеш полного тела), статус и ответ.
- Если ключ существует и тело совпадает, верните сохранённый ответ.
- Если ключ существует и тело отличается, отвергните запрос (`409` или `422`).
- Истекайте старые ключи.

`GET` не нужен ключ. `PUT` полного ресурса может быть естественно идемпотентным. `POST`, который создаёт новый платёж, обычно нужен ключ.

Документируйте заголовок, время жизни ключа и ошибку, когда тело не совпадает.

Ключи не заменяют аутентификацию. Ключ — не секрет, который доказывает идентичность. Считайте ключи уникальными идентификаторами. Всё равно аутентифицируйте.

## Публичные и внутренние API

Публичный API имеет клиентов, которых вы не контролируете: сторонние разработчики, неизвестные приложения или заказчики. Внутренний API имеет клиентов, которыми владеет ваша организация.

Публичным API нужна более медленная скорость изменений, опубликованная политика, более сильная совместимость и более ясные ошибки. Нельзя обновить всех клиентов в один день. Даты заката должны быть длинными. Документация — часть продукта.

Внутренние API могут двигаться быстрее, если один конвейер разворачивает всех клиентов или если вы принимаете согласованный выпуск. Контракт всё равно нужен. Можно пропустить часть церемонии (нет публичного портала разработчика), но нельзя пропускать таймауты, auth и журналы.

Безопасность различается. Публичный API на границе низкого доверия. Пределы частоты, более сильная аутентификация и менее подробные ошибки нормальны. Внутренний API всё равно аутентифицирует. «Внутри сети» недостаточно (тема 2).

Не открывайте внутренний admin API в публичном интернете. Используйте отдельный вход, отдельную идентичность и least privilege.

Некоторые команды используют те же обработчики с разными шлюзами. Этот проект приемлем, если авторизация не только «шлюз так сказал» без проверок в сервисе.

Пишите аудиторию в документе API: public, partner или internal. Политика версий следует аудитории.

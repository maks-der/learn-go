# 3. Реляционная модель

## Описание

Реляционная модель — теория за таблицами, ключами и ограничениями. Эта тема сопоставляет формальные слова с таблицами, которые вы уже знаете. Вы также изучаете каталоги, представления и разницу между логической схемой и физическим хранением.

Используйте один термин для каждого понятия. Отношение — таблица с уникальными строками. Кортеж — строка. Атрибут — столбец. Ограничение — правило, которое обеспечивает СУБД. Завершите эту тему до написания SQL-запросов.

Держите модель нейтральной к вендорам. Детали хранения отличаются по продукту. Логические идеи остаются теми же.

## Отношения, кортежи и атрибуты (простыми словами)

Отношение — множество кортежей, которые делят одни и те же атрибуты. На практике вы называете отношение таблицей. Идея множества важна: настоящее отношение не содержит двух одинаковых кортежей. Таблица SQL может допускать дубликаты строк, если вы не задали ключ. Всегда задавайте ключ, чтобы таблица вела себя как отношение.

Кортеж — одна строка. Он держит одно значение для каждого атрибута. Порядок кортежей не имеет смысла в модели. Вы добавляете порядок только когда запрашиваете с `ORDER BY`.

Атрибут — именованный столбец с доменом. Домен — множество допустимых значений. Пример: атрибут `qty` имеет домен «положительное целое». Имя `qty` уникально внутри отношения.

Пример. Отношение `products`:

- атрибуты: `product_id`, `name`, `price`
- один кортеж: `(10, 'Notebook', 4.50)`

Реляционная модель не использует вложенную таблицу внутри ячейки как первоклассную идею. Каждое значение атрибута атомарно в базовой модели. Тема 10 покрывает первую нормальную форму.

Имена SQL отличаются от имён теории. Изучайте оба:

| Теория | Практика SQL |
| --- | --- |
| Отношение | Таблица |
| Кортеж | Строка |
| Атрибут | Столбец |
| Домен | Тип данных плюс дополнительные правила |
| Степень | Число столбцов |
| Кардинальность | Число строк |

Не полагайтесь на порядок строк на диске. Запрос без `ORDER BY` может вернуть любой порядок. Модель считает отношение множеством.

## Схемы и каталоги

Схема — именованная группа объектов. Объекты включают таблицы, представления и ограничения. Схема держит имена организованными. Две схемы могут каждая иметь таблицу с именем `users`. Полное имя — `schema_name.users`.

Каталог — база или более высокий контейнер, в зависимости от продукта. В стандарте SQL каталог содержит схемы. Во многих продуктах вы подключаетесь к базе, и эта база содержит схемы. Изучите трёхуровневое имя, когда продукт его использует: `catalog.schema.table`.

Примеры имён:

```text
learn.public.customers
shop.sales.orders
```

`learn` — база. `public` или `sales` — схема. `customers` и `orders` — таблицы.

Слово *схема* также значит проект: список таблиц и столбцов. Этот смысл — логическая схема. Именованный объект схемы — пространство имён. Говорите «объект схемы», когда имеете в виду пространство имён. Говорите «логическая схема», когда имеете в виду проект.

Создавайте схему для предметной области, когда база растёт. Пример: `sales`, `hr`, `inventory`. Не кладите каждый эксперимент в системную схему, если продукт даёт схему по умолчанию для пользователей.

Каталог также хранит метаданные: имена таблиц, типы столбцов, ключи. Вы запрашиваете метаданные через информационные представления. Имена представлений отличаются по вендору. Идея одна. СУБД описывает базу в таблицах.

Не угадывайте имена объектов. Перечисляйте схемы и таблицы из клиента или из представлений метаданных.

## Ограничения целостности (домен, сущность, ссылка)

Ограничение целостности — правило, которому должно удовлетворять каждое сохранённое изменение. СУБД отвергает изменение, которое ломает ограничение. Ограничения не пускают плохие данные.

**Доменное ограничение.** Значение должно принадлежать домену атрибута. Типы обеспечивают часть этого правила: целочисленный столбец отвергает `'abc'`. Дополнительные правила сужают домен: `price >= 0`, `email` соответствует шаблону, `status` — один из списка. `NOT NULL` — доменное правило: значение должно присутствовать.

**Ограничение сущности.** Каждый кортеж должен быть идентифицируем. Первичный ключ реализует это правило. Никакие две строки не делят ключ. Ключ не `NULL`. Целостность сущности — формальное имя этого правила.

**Ссылочное ограничение.** Значение внешнего ключа должно совпадать с существующим ключом или быть `NULL`, когда проект допускает `NULL`. Ссылочная целостность — формальное имя. Тема 2 показала ту же идею на таблицах.

Пример:

```sql
CREATE TABLE products (
    product_id INTEGER PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    price DECIMAL(10, 2) NOT NULL,
    CONSTRAINT chk_products_price CHECK (price >= 0)
);

CREATE TABLE order_lines (
    order_id INTEGER NOT NULL,
    product_id INTEGER NOT NULL,
    qty INTEGER NOT NULL,
    PRIMARY KEY (order_id, product_id),
    CONSTRAINT chk_ol_qty CHECK (qty > 0),
    CONSTRAINT fk_ol_products FOREIGN KEY (product_id) REFERENCES products (product_id)
);
```

`CHECK (price >= 0)` — доменное ограничение. `PRIMARY KEY` — ограничение сущности. `FOREIGN KEY` — ссылочное ограничение.

Не полагайтесь только на приложение для этих правил. Второй клиент может пропустить проверки приложения. Кладите правила в базу.

## Кандидатные ключи, суперключи, составные ключи

Суперключ — набор атрибутов, который уникально идентифицирует кортеж. Набор может содержать лишние атрибуты, которые не нужны для уникальности.

Кандидатный ключ — минимальный суперключ. Нельзя убрать атрибут и сохранить уникальность. У таблицы может быть больше одного кандидатного ключа.

Первичный ключ — кандидатный ключ, который вы выбираете как главный идентификатор. Другие кандидатные ключи становятся уникальными ограничениями.

Составной ключ — ключ с более чем одним атрибутом. Составной ключ может быть кандидатным или первичным.

Пример. `employees`:

- `employee_id` уникален (суррогат)
- `national_id` уникален в этой стране
- `email` уникален в компании

Каждый из них может быть кандидатным ключом. `employee_id` плюс `email` — суперключ, но он не минимален. Пара не кандидатный ключ.

Пример. `order_lines`:

- `(order_id, line_no)` — составной кандидатный ключ
- `(order_id, product_id)` тоже может быть кандидатным ключом, если один товар появляется один раз на заказ

```sql
CREATE TABLE employees (
    employee_id INTEGER PRIMARY KEY,
    national_id VARCHAR(32) NOT NULL UNIQUE,
    email VARCHAR(255) NOT NULL UNIQUE,
    name VARCHAR(100) NOT NULL
);
```

Не добавляйте столбцы в ключ без причины. Более широкий ключ труднее использовать как внешний ключ. Предпочитайте минимальный кандидатный ключ как первичный.

## Представления и базовые таблицы

Базовая таблица — сохранённая таблица. Строки живут в файлах базы. `CREATE TABLE` определяет базовую таблицу. Вставки пишут в эту таблицу.

Представление — именованный запрос. `CREATE VIEW` сохраняет текст запроса, а не вторую копию строк (в базовом случае). Когда вы выбираете из представления, СУБД выполняет запрос.

```sql
CREATE VIEW open_orders AS
SELECT order_id, customer_id, ordered_at
FROM orders
WHERE shipped_at IS NULL;
```

```sql
SELECT order_id
FROM open_orders
WHERE customer_id = 15;
```

Представления дают стабильное имя частому запросу. Представления скрывают столбцы, которые роль не должна видеть. Представления могут соединять таблицы, чтобы пользователь отчёта читал один объект.

Представление по умолчанию не кэш. Каждый выбор может снова читать базовые таблицы. Некоторые продукты предлагают материализованные представления, которые хранят снимок. Эта возможность дополнительная. Считайте обычное представление сохранённым `SELECT`.

Некоторые простые представления можно обновлять. Многие представления только для чтения, потому что запрос — соединение или агрегат. Не предполагайте, что `INSERT` в представление работает. Проверьте продукт. Предпочитайте запись в базовые таблицы.

Не используйте представление как замену отсутствующей таблицы в модели. Если сущности нужно хранение, создайте базовую таблицу. Используйте представление, чтобы показывать или ограничивать данные.

## Логическая схема и физическое хранение (высокий уровень)

Логическая схема — проект, который видят пользователи и программы: таблицы, столбцы, ключи, представления и ограничения. Вы меняете логическую схему через `CREATE`, `ALTER` и `DROP`.

Физическое хранение — как СУБД размещает байты на диске: файлы, страницы, индексы и куча или кластерная раскладка. Продукт выбирает многие из этих деталей. Вы настраиваете некоторые из них позже (тема 11 и более поздние операционные темы).

Реляционная модель позволяет работать на логическом уровне. Вы пишете `SELECT` против таблиц. Вы не читаете страницы руками. СУБД отображает логическую строку на физические страницы.

Пример. Два продукта хранят одну и ту же таблицу `customers` в разных раскладках файлов. Ваш SQL остаётся тем же. План запроса может отличаться. Логическая схема переносима. Физический план не полностью переносим.

Индексы — физические помощники, которые вы объявляете. Они не меняют смысл таблицы. Уникальный индекс может поддерживать логическое уникальное ограничение. Ограничение логическое. Индекс физический.

Не проектируйте таблицы вокруг слуха про порядок на диске. Проектируйте ключи и ограничения ради смысла. Добавляйте индексы для путей доступа после того, как знаете запросы.

Не путайте табличное пространство или файловую группу с пространством имён схемы. Схема — группа имён. Табличное пространство — место хранения. Продукты используют разные слова.

### Вопросы

#### Теоретические вопросы

1. Сопоставьте полный магазин (`customers`, `orders`, `order_lines`) с отношением, кортежем, атрибутом и тремя видами целостности.
2. Как кандидатные ключи и первичный ключ появляются в `CREATE TABLE` для `employees`?
3. Когда добавляете представление и когда добавляете базовую таблицу?
4. Что остаётся тем же между вендорами на логическом уровне и что может меняться в хранении?
5. Коллега говорит: «схема — это папка на диске». Какие два смысла вы разделяете в ответе?

#### Простые практические задания

1. Напишите шпаргалку: отношение, кортеж, объект схемы, каталог, представление, виды ограничений, суперключ, кандидатный ключ.
2. Создайте две таблицы с первичными ключами, одним внешним ключом и одним `CHECK`. Вставьте один допустимый набор строк.
3. Создайте представление, которое скрывает один столбец таблицы. Выберите из представления.
4. Напишите полное имя объекта одной таблицы в вашей СУБД (база и схема, если они есть).

#### Средние практические задания

1. Реализуйте `products` и `order_lines` из этой темы. Вызовите один доменный сбой, один сбой сущности и один ссылочный сбой.
2. Добавьте второй уникальный столбец как кандидатный ключ. Покажите, что дубликат в этом столбце падает.
3. Задокументируйте команду метаданных, которая перечисляет ограничения одной таблицы. Вставьте вывод в заметки.

#### Сложные практические задания

1. Спроектируйте логическую схему библиотеки на одну страницу: схемы, таблицы, ключи, два представления. Опустите физические имена файлов.
2. Сравните представления и базовые таблицы для роли безопасности, которая может читать заказы, но не должна читать столбцы оплаты. Напишите представление и идею выдачи прав словами.

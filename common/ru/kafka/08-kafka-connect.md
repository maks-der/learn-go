# 8. Kafka Connect

## Описание

Kafka Connect — фреймворк, который двигает данные между Kafka и другими системами. Source-коннектор пишет записи в Kafka. Sink-коннектор читает записи из Kafka и пишет их в другую систему.

Эта тема показывает source- и sink-коннекторы, задачи, конвертеры, single message transforms (SMT), очереди недоставленных и частые коннекторы (JDBC, S3, Debezium). Завершите эту тему после тем 4, 5 и 7. Воркеры Connect говорят с кластером Kafka. Используйте KRaft для этого кластера. Не добавляйте ZooKeeper для новой работы.

Используйте один термин для каждого понятия. Коннектор — плагин, который определяет, как движутся данные. Задача — единица работы, которую воркер запускает для коннектора. Конвертер превращает байты в данные Connect и обратно. SMT меняет одну запись в воркере. Очередь недоставленных — топик, который хранит записи, которые упали.

## Source- и sink-коннекторы

**Source-коннектор** читает внешнюю систему и производит записи в топики Kafka. Примеры: таблица базы, каталог файлов, API сообщений.

**Sink-коннектор** потребляет топики Kafka и пишет во внешнюю систему. Примеры: объектное хранилище, индекс поиска, хранилище.

Connect работает как один или несколько **воркеров**. Режим standalone использует один процесс и локальный файл для офсетов. Режим distributed использует группу воркеров. Режим distributed хранит конфигурацию коннекторов, офсеты и статус в топиках Kafka. Эти топики — внутренние топики Connect. Не используйте их как прикладные топики.

Вы отправляете конфигурацию коннектора (JSON через REST API или файл в режиме standalone). Конфигурация называет класс коннектора, топики или таблицы и конвертеры. Воркеры запускают коннектор.

Connect не замена каждому своему продюсеру или консьюмеру. Используйте Connect, когда есть поддерживаемый коннектор и вы хотите старт, стоп и масштаб в одном месте.

Кластер Kafka может быть KRaft. Connect не нужен ZooKeeper. Воркеры используют `bootstrap.servers`. Инструменты admin кластера используют `--bootstrap-server`.

Типичные свойства воркера:

```text
bootstrap.servers=localhost:9092
group.id=connect-cluster
key.converter=...
value.converter=...
config.storage.topic=connect-configs
offset.storage.topic=connect-offsets
status.storage.topic=connect-status
```

Создайте эти внутренние топики с фактором репликации, который кластер может поддержать. На одноброкерном учебном кластере используйте фактор репликации 1.

## Задачи, конвертеры и SMT

Коннектор может запустить одну или несколько **задач**. Задача — единица процесса, которая копирует срез работы. Для source задачи могут делить таблицы или диапазоны запросов. Для sink задачи могут делить партиции топика.

`tasks.max` в конфигурации коннектора — верхний предел. Коннектор может запустить меньше задач. Одна задача не может быть больше работы, которую коннектор может разделить. Пример: sink не может полезно использовать больше задач, чем число назначенных партиций.

**Конвертер** сериализует и десериализует ключи и значения записей на границе Connect. Частые конвертеры:

- `StringConverter` для простого текста
- `JsonConverter` для JSON
- конвертеры Avro, Protobuf или JSON Schema, которые говорят с Schema Registry (тема 7)

Конвертер на выходе source должен совпадать с тем, чего ждут консьюмеры. Конвертер на входе sink должен совпадать с тем, что на топике. Несовпадение даёт ошибки или мусорные поля.

У Connect есть конвертер ключа и конвертер значения. Могут быть конвертеры заголовков. Задавайте их в значениях воркера по умолчанию и переопределяйте на коннектор, когда нужно.

**Single message transform (SMT)** — функция, которую воркер применяет к одной записи. SMT работает в Connect, не в вашем приложении.

Типичные действия SMT: переименовать или убрать поле, сменить имя топика (маршрут), вставить статическое поле, замаскировать значение, сплющить вложенную структуру.

Вы цепочкуете SMT в конфигурации коннектора. Порядок в списке — порядок выполнения. Поздний SMT видит выход раннего SMT.

SMT не заменяют обработку потоков. SMT должен оставаться простым. У него нет окна и нет join между записями. Для агрегаций используйте Kafka Streams, ksqlDB или Flink (тема 9).

Не путайте конвертер с SMT. Конвертер меняет кодировку. SMT меняет содержимое записи или маршрутизацию после того, как конвертер произвёл данные Connect.

Не кладите секреты в статические поля SMT. Не используйте SMT как единственный механизм контроля доступа. Тема 10 покрывает ACL.

Пример ключей конфигурации (имена могут отличаться по версии):

```text
transforms=MaskCard
transforms.MaskCard.type=...
transforms.MaskCard.fields=card_number
```

## Очереди недоставленных

**Очередь недоставленных (DLQ)** в Connect — топик Kafka, который принимает записи, которые коннектор не может обработать. Типичные причины: ошибка конвертера, ошибка SMT или отказ внешней системы.

Без DLQ ядовитая запись может заблокировать задачу sink. Задача повторяет и не движется вперёд. С DLQ воркер может написать неудачную запись (и заголовки ошибки) в топик DLQ и продолжить.

Включайте DLQ только когда коннектор и ваша версия это поддерживают. Имена конфигурации включают `errors.tolerance` и имя топика DLQ. Прочитайте текущую страницу обработки ошибок Connect для точных ключей.

DLQ — обычный топик Kafka. Задайте ретеншн. Задайте фактор репликации, который соответствует нуждам устойчивости на KRaft. Читайте DLQ отдельным процессом. Исправьте запись или отображение. Не игнорируйте растущий DLQ.

DLQ — не очередь повторов с расписанием. Повторы Connect — отдельная настройка. Не считайте объём DLQ успехом.

Source-коннекторы тоже могут падать. Некоторые source пишут ошибки только в логи. Читайте документацию коннектора.

Тема 3 описывает ядовитые сообщения на пути продюсера. Тема 11 описывает ядовитые сообщения в приложениях. DLQ Connect — эксплуатационный инструмент на пути Connect.

## JDBC, S3 и Debezium (CDC)

**JDBC source** читает таблицы или запросы через JDBC и пишет строки в Kafka. Вы выбираете incrementing-режим, timestamp-режим или bulk-режим. Incrementing-режиму нужен растущий id. Timestamp-режиму нужна надёжная колонка метки времени. Bulk-режим копирует полный результат на каждый poll. Не используйте bulk-режим по умолчанию для больших таблиц.

**JDBC sink** пишет записи Kafka в таблицы. Нужно отобразить поля на колонки. Конфигурация первичного ключа контролирует upsert против insert.

**S3 sink** пишет записи в объектное хранилище (Amazon S3 или совместимый с S3 API). Коннектор группирует записи в файлы. Вы задаёте формат (JSON, Avro, Parquet) и размер или интервал flush. Объектное хранилище — не шина сообщений. Читатели S3 видят файлы, не живую группу консьюмеров.

**Debezium** — проект CDC (захват изменений данных). Коннектор Debezium читает журнал транзакций базы (WAL, binlog или эквивалент) и пишет события изменений в Kafka. CDC не то же самое, что poll JDBC. CDC может захватить удаления и порядок фиксаций. Нужно задать права базы и политику снимка. Коннекторы Debezium часто работают на Kafka Connect.

CDC — хороший издатель для шаблона outbox (тема 11). Приложение пишет строку outbox в той же транзакции базы. Debezium читает журнал и производит в Kafka.

Устанавливайте плагины коннекторов в путь плагинов Connect. Фиксируйте версии плагинов. Читайте лицензию коннектора. Некоторые коннекторы не часть Apache Kafka.

Всем этим коннекторам нужен работающий кластер Kafka KRaft (или другой кластер API Kafka, который вы принимаете). Они не запускают ZooKeeper.

# 1. Начало работы

## Описание

MongoDB — документоориентированная база данных. Такая база хранит данные как документы, а не как строки в таблицах. Эта тема показывает, что такое MongoDB, когда подходит документная модель, как установить MongoDB и как пользоваться `mongosh`. Вы также изучаете базы данных, коллекции, документы, типы BSON и лимит размера документа.

Сначала изучите общие идеи баз (`db.topics.md`). Затем завершите эту тему. Завершите эту тему до того, как писать запросы.

Используйте один термин для каждого понятия. **База данных** содержит коллекции. **Коллекция** содержит документы. **Документ** — один объект BSON с полями. Не называйте коллекцию таблицей. Не называйте документ строкой.

## Что такое MongoDB и когда подходят документы

MongoDB — система управления документоориентированной базой данных. Процесс сервера — `mongod`. Клиенты отправляют команды в `mongod`. Atlas — облачный сервис MongoDB. Одна и та же документная модель работает на локальном сервере и в Atlas.

Документ — набор пар поле–значение. Значениями бывают строки, числа, даты, массивы и вложенные документы. Документы в одной коллекции не обязаны иметь одинаковые поля. У приложения всё равно есть схема. База не навязывает одну схему, пока вы не добавите валидацию.

MongoDB хранит документы в BSON. BSON — двоичный формат. Запросы вы пишете в синтаксисе, похожем на JSON. Сервер хранит и возвращает BSON.

MongoDB не является реляционной базой. Она не использует SQL как основной язык. Ей не нужны соединения для каждой связи. Связи всё равно можно моделировать. Связанные данные встраивают или хранят как ссылку.

MongoDB — не только хранилище ключ–значение. У документа может быть много полей. Эти поля можно запрашивать. Эти поля можно индексировать.

Типичные применения:

- Операционные данные веб- и мобильных приложений
- Контент с вложенной формой
- События и каталоги
- Сервисы, которые уже обмениваются JSON

Документная модель подходит, когда приложение читает и пишет вложенный объект как одну единицу. Пример: заказ со строками. Заказ и строки — один документ. Одно чтение возвращает весь заказ.

Документная модель также подходит, когда форма данных часто меняется. Новые поля не требуют миграции таблицы на каждое изменение. Имена полей всё равно планируют. Типы всё равно планируют.

Реляционная модель лучше, когда многие сущности делят данные и эти данные нужно держать в одном месте. Пример: имя товара, которое многие заказы должны показывать как актуальное. Реляционный внешний ключ и соединение держат одну строку товара.

Реляционная модель также лучше, когда нужны много разовых соединений, строгие ограничения на несколько строк или тяжёлая отчётность по многим таблицам.

Используйте документы, когда:

- Данные, к которым обращаются вместе, имеют ясное вложение
- Документ остаётся ниже лимита размера
- Массивы остаются ограниченными
- Схемой владеет приложение

Используйте реляционную модель, когда:

- В центре модели связи многие-ко-многим
- Основной контроль — декларативная ссылочная целостность
- Аналитики запускают много новых запросов с соединениями
- Запись по умолчанию — транзакции на много независимых строк

Можно использовать оба. Многие системы хранят операционные документы в MongoDB, а отчёты — в реляционной базе или хранилище.

## Установка Community, Atlas или Docker

MongoDB можно запустить тремя частыми способами.

**MongoDB Community Server.** Скачайте установщик со страницы загрузок MongoDB. Выберите операционную систему. Установите сервер. Запустите службу `mongod`. Community Server бесплатен. Хост, диск и обновления ведёте вы.

**Atlas.** Atlas — официальный облачный сервис. Создайте проект и кластер. Бесплатного уровня достаточно для учёбы. Сервер ведёт Atlas. Подключаетесь по строке соединения. Нужно задать пользователя базы и список IP-доступа.

**Docker.** Docker запускает `mongod` в контейнере. Типичная учебная команда использует официальный образ `mongo` и публикует порт `27017`. Данные в контейнере пропадут, если не смонтировать том. Используйте том, если данные должны остаться.

Для этого пути выберите один способ и держитесь его. Не смешивайте три среды без пометки, какую используете.

После запуска сервера установите `mongosh`, если установщик его не добавил. `mongosh` — официальная оболочка.

Порт по умолчанию — `27017`. Не открывайте этот порт в публичный интернет на учебной машине без аутентификации.

## `mongosh`

`mongosh` — оболочка MongoDB. Это клиент командной строки. Им запускают команды, смотрят данные и проверяют запросы. Старая оболочка `mongo` — не текущий инструмент. Используйте `mongosh`.

Подключение к локальному серверу:

```text
mongosh
```

Подключение по URI:

```text
mongosh "mongodb://localhost:27017"
```

Подключение к Atlas — по URI, который показывает Atlas. В URI есть имя пользователя. Оболочка спрашивает пароль, либо учётные данные кладут в URI. Не коммитьте URI с паролем.

После подключения вы в среде JavaScript. Базу выбирают командой `use`:

```text
use learn
```

`db` — текущая база. `db.help()` показывает частые помощники. `show dbs` перечисляет базы. `show collections` перечисляет коллекции текущей базы.

Простая вставка и поиск:

```javascript
db.notes.insertOne({ title: "hello", n: 1 })
db.notes.find()
```

`mongosh` печатает документы как расширенный JSON. Результаты можно присвоить переменным. Можно писать небольшие скрипты. Для ежедневной учёбы вводите команды по одной.

Выход — `exit` или `Ctrl+C`, как описано в документации оболочки.

Веб-руководство — источник истины для опций и лимитов. Используйте руководство, которое соответствует вашей основной версии. Не доверяйте случайным фрагментам блогов правилам write concern или транзакций.

## Базы данных, коллекции и документы

**Развёртывание** MongoDB содержит одну или несколько баз данных. **База данных** содержит коллекции и представления. **Коллекция** содержит документы. **Документ** — единица, которую вставляют, обновляют и ищут.

Имена:

- Имена баз — строки. Не используйте зарезервированные имена вроде `admin`, `local` и `config` для данных приложения.
- Имена коллекций — строки. Используйте ясное существительное во множественном числе, например `orders`.
- Имена полей — строки. Не начинайте имена полей приложения с `$`. Не используйте `.` в имени поля.

MongoDB создаёт базу, когда вы впервые сохраняете в ней данные. MongoDB создаёт коллекцию, когда вы впервые вставляете документ, если только не создаёте коллекцию специально.

У каждого документа есть поле `_id`. Если `_id` опустить, MongoDB добавит ObjectId. `_id` уникален в коллекции.

Коллекция — не таблица. Нет фиксированного списка столбцов. Два документа могут выглядеть по-разному. Эта гибкость — не повод хранить случайные формы без плана.

Команды в `mongosh` используют `db.collectionName.method()`. Пример: `db.orders.insertOne({ ... })`.

Удалить коллекцию — `db.orders.drop()`. Удалить базу — `db.dropDatabase()`. Эти команды удаляют данные. Не запускайте их на общем кластере без осторожности.

## JSON против BSON, типы полей, `_id` и лимит 16 МБ

JSON — текстовый формат для объектов, массивов, строк, чисел, булевых значений и null. Люди читают JSON. Многие API отправляют JSON.

BSON — двоичное кодирование. MongoDB использует BSON на диске и в сети. BSON включает байт типа и длину для каждого значения. Сервер не разбирает текст JSON для каждого хранимого документа.

У BSON есть типы, которых нет в JSON. Примеры: ObjectId, Date, Binary, Decimal128, Timestamp, Regular Expression. `mongosh` печатает эти типы как расширенный JSON. Расширенный JSON использует обёртки вроде `{ "$oid": "..." }` и `{ "$date": "..." }`.

Число JSON — не полное соответствие числам BSON. В BSON есть 32-битные целые, 64-битные целые и 64-битные числа с плавающей точкой. Драйверы сопоставляют числа языка типам BSON. Для десятичных денег нужен `Decimal128`, а не двоичный float.

Не редактируйте сырой BSON вручную. Используйте оболочку, драйвер или инструмент.

Частые типы полей BSON:

- **String.** Текст UTF-8. Строки — для имён, кодов и токенов.
- **Number.** Целое или double. В `mongosh` используйте `NumberInt`, `NumberLong` или обычное число. Для точных десятичных — `NumberDecimal`.
- **Bool.** `true` или `false`.
- **Date.** Дата и время UTC. В `mongosh` используйте `ISODate("2026-01-15T12:00:00Z")`. Не храните даты как локальные строки, если их нужно сортировать как время.
- **ObjectId.** Идентификатор на 12 байт.
- **Array.** Упорядоченный список значений. По возможности держите в массиве один тип.
- **Встроенный документ.** Вложенный объект. Пример: `address: { city: "Oslo", zip: "0001" }`.
- **Null.** Отсутствующее значение. Null — не то же самое, что отсутствующее поле.
- **Binary.** Сырые байты. Binary — для небольших блобов. Не используйте binary для больших файлов.

Тип важен для запросов и индексов. Число `1` и строка `"1"` не равны. Выберите тип для каждого поля и держите его.

У каждого документа есть `_id`. `_id` уникален в коллекции. MongoDB создаёт индекс по `_id`. Этот индекс нельзя удалить.

Если `_id` опустить при вставке, драйвер или сервер добавит ObjectId. Можно задать `_id` другого типа. Значение должно быть уникальным. Значение должно быть стабильным.

ObjectId — 12 байт: метка времени в секундах, случайное значение и счётчик. Часть с меткой времени позволяет грубо сортировать по времени вставки. Не считайте ObjectId строгими часами для всех узлов.

`_id` на практике неизменяем. `_id` не меняют через `$set`. Чтобы использовать новый `_id`, вставляют новый документ и удаляют старый. Держите `_id` маленьким.

Один документ MongoDB имеет максимальный размер 16 мегабайт. Лимит включает накладные расходы BSON. Лимит защищает сервер и клиент. Документ, который растёт без границы, упрётся в лимит.

Не храните большие файлы как один документ. Для больших файлов используйте GridFS или объектное хранилище. `Object.bsonsize(doc)` в `mongosh` возвращает размер BSON в байтах для документа в памяти.

Лимит 16 МБ — не лимит коллекции. Коллекция может держать много документов. Курсор возвращает пакеты.

## «Без схемы» не значит «без схемы вовсе»

MongoDB не требует схему при создании коллекции. Можно вставить `{ a: 1 }` и `{ b: "x" }` в одну коллекцию. Это поведение — **хранение без схемы**.

У приложения схема всё равно есть. Приложение ожидает имена полей. Приложение ожидает типы. Приложение ожидает массивы или вложенные документы известной формы. Если форма меняется без плана, запросы ломаются. Индексы тратят место. Валидация потом падает.

**Полностью без схемы** значило бы, что формой никто не владеет. Так рабочая система не живёт. Схемой кто-то владеет: приложение, файл схемы или валидатор на коллекции.

Хорошая практика:

- Запишите форму документа для каждой коллекции.
- Используйте стабильные имена полей.
- Используйте один тип на поле.
- Добавьте поле `schemaVersion`, когда форма должна измениться (позже в пути).
- Добавьте валидацию JSON Schema, когда коллекция достаточно стабильна (позже в пути).

Гибкая схема — инструмент. Она помогает при изменениях. Это не повод пропускать проектирование.

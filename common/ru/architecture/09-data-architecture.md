# 9. Архитектура данных

## Описание

Архитектура данных — это набор решений о том, где живут данные, кто ими владеет и как другие части их читают. Эта тема разбирает одну базу на сервис против общей базы, антипаттерн integration database, CQRS, кэширование, поисковые индексы против источника истины и владение данными.

Решения о данных дорого менять (тема 1). Неверное разделение таблиц создаёт скрытое зацепление (тема 3). Сочетайте эту тему с `db.topics.md`. Для деталей кэша сочетайте с `redis.topics.md`.

Завершите темы 1–8 до этой темы. Начинайте с одной базы в модульном монолите (тема 5). Дробите хранилища только когда владение или мера требует этого.

Используйте один термин для каждого понятия. Источник истины — это хранилище, которое побеждает, когда копии не согласны. Кэш — не источник истины. Поисковый индекс — не источник истины, если вы не спроектировали его так (редко).

## Одна база на сервис против общей базы

Общая база — это одна база, которую читает и пишет больше одной единицы развёртывания (или больше одного модуля без владельца). Правило «одна база на сервис» говорит, что каждый развёртываемый сервис владеет своим хранилищем данных. Другие сервисы используют API или события, не таблицы.

В модульном монолите одна база — значение по умолчанию. Модули всё равно могут владеть таблицами. Владение — логическое правило. Физический раскол приходит позже.

Когда больше одного сервиса пишут те же таблицы:

- Нельзя сменить колонку без выпуска нескольких сервисов.
- Инварианты растекаются по кодовым базам.
- Транзакции скрывают отсутствующий API.
- Команды блокируют друг друга.

Когда у каждого сервиса своё хранилище:

- Можно менять схему внутри владельца.
- Вы теряете лёгкие транзакции между сущностями.
- Нужны API, события или слой композиции для соединений.
- Стоимость эксплуатации растёт (тема 2: стоимость).

Не копируйте слоган «одна база на сервис» в монолит из трёх человек. У вас уже одна единица развёртывания. Сначала используйте владение таблицами.

Общая реплика только для чтения той же принадлежащей базы — не то же самое, что общая integration database. Реплики — инструмент масштаба. У них всё равно один владелец.

Запишите владельца каждого хранилища в ADR. Если два сервиса «делят на короткое время», запишите конечную дату. Короткие времена становятся годами.

## Антипаттерн integration database

Integration database — это база, которая существует, чтобы многие программы интегрировались, читая и записывая те же таблицы. База становится контрактом. Этот справочник считает такой проект антипаттерном для интеграции приложений.

Почему это вредит:

- Схема не может развиваться. Каждая программа — клиент каждой колонки.
- У инвариантов нет единого владельца.
- «Быстрое» SQL-соединение в отчёте привязывает вас к внутренностям.
- Безопасность становится «у кого пароль базы».
- Нельзя протестировать одну программу без полной схемы и полного смысла данных.

Предпочтительные стили интеграции (позже в пути, тема 13): API, обмен сообщениями или передача файлов с задокументированным форматом. У этих стилей явные контракты.

Хранилище данных или аналитическая реплика могут быть допустимой копией для отчётов. Это всё равно копия. Владелец источника истины остаётся операционной системой. Отчёты не должны писать обратно в операционные таблицы без определённого процесса.

Если вы унаследовали integration database, не добавляйте пятого писателя. Добавьте API перед владельцем. Перемещайте писателей по одному. Запишите список паролей и сократите его.

Здесь часто появляются правовые и аудиторские ограничения. Многие писатели затрудняют сказать, кто изменил персональную запись.

## CQRS (когда чтения и записи расходятся)

CQRS (Command Query Responsibility Segregation) означает, что модель, которую вы используете для изменения данных, не та же модель, которую вы используете для чтения данных. Команды (записи) идут на одну сторону. Запросы (чтения) идут на другую сторону.

Лёгкая форма обычна и достаточна: писать в нормализованные таблицы, читать из представления SQL, таблицы, заточенной под запрос, или кэша. Модель записи остаётся строгой. Модель чтения удобна.

Сильная форма использует другое хранилище для чтений (поисковый индекс, документ, куб). Проектор обновляет хранилище чтения, когда происходят записи. Согласованность становится eventual (тема 7).

Используйте CQRS, когда:

- Формы чтения и формы записи сильно различаются.
- Нагрузка чтения намного выше нагрузки записи.
- Одна модель заставляет болезненные соединения на каждой странице.

Не используйте полный CQRS, когда нескольких SQL-запросов достаточно. Второе хранилище — второй домен отказа. Нужно обрабатывать отставание, перестройки и двойные ошибки.

Командам всё равно нужны проверка и инварианты. CQRS — не причина пропускать модель записи. Запросы не должны тайно писать.

Назовите отставание. «Панель администратора может отставать на 2 секунды» — требование. «Итог оформления может отставать на 2 секунды» часто неприемлемо.

## Слои кэша (`redis.topics.md`)

Кэш — это хранилище копий, которые можно перестроить из источника истины. Цель — ниже задержка или ниже нагрузка на основное хранилище. См. `redis.topics.md` про Redis как кэш.

Кэш необязателен. Система всё равно должна работать (возможно медленнее), если кэш пуст или лежит, если вы явно не спроектировали деградированный режим.

Обычные слои:

- Кэш клиента (браузер).
- CDN для публичных файлов.
- Кэш памяти приложения (локальный для процесса).
- Общий кэш (Redis или похожий).
- Буферный кэш базы (у базы он уже есть).

Инвалидация — трудная часть. После записи копии могут быть устаревшими. Стратегии включают time-to-live (TTL), удаление при записи и ключи версий. Каждая стратегия может провалиться. TTL прост и допускает устаревание. Удаление при записи может промахнуться по имени ключа.

Не кэшируйте данные, которые должны быть точными в момент чтения, если TTL не ноль или вы не инвалидируете правильно. Денежные балансы и решения авторизации требуют заботы.

Локальные кэши процесса не разделяют удаления. Два экземпляра могут не соглашаться до конца TTL. Общий кэш снижает эту проблему и добавляет сетевой hop.

Запишите, что вы кэшируете, формат ключа, TTL и поведение устаревания. Измеряйте долю попаданий. Кэш с низкой долей попаданий всё равно добавляет сложность.

Не используйте кэш как единственное хранилище записи. Этот проект теряет данные, когда кэш вытесняет ключ.

## Поисковый индекс против источника истины

Поисковый индекс — это структура, оптимизированная для текстового поиска и фасетных запросов. Elasticsearch и похожие продукты — индексы. Реляционная таблица с функцией полнотекстового поиска всё равно источник истины, если она владелец. Отдельный поисковый продукт обычно производная копия.

Источник истины принимает записи и держит авторитетную запись. Поисковый индекс получает проекцию. Поиск может отставать. Поиск может уронить документ. Ранжирование поиска может пропустить строку, которая есть в источнике.

Правила пользователя:

- Создание, обновление и удаление идут в источник истины.
- Поисковые запросы могут идти в индекс.
- Открытие по id после щелчка должно уметь загрузить из источника, если индекс неверен.

Не пишите только в индекс. Перестройка изобрела бы данные, которые вы никогда не хранили.

Переиндексация — обязательная операция. Нужно заполнить индекс из источника после ошибки или смены отображения. Если нельзя перестроить, индекс стал случайным источником истины.

Согласованность eventual. Запишите отставание, которое поиск может иметь. Для магазина новый товар, который появляется в поиске через 10 секунд, может быть приемлем. Распроданный товар, который остаётся «покупаемым» в поиске, — бизнес-риск. Сочетайте попадания поиска с проверкой запаса в источнике в момент покупки.

## Владение данными

Владение данными означает, что один модуль или один сервис отвечает за набор данных. Этот владелец — единственный писатель (кроме контролируемых миграций). Другие части читают через API владельца, события или одобренную копию.

Владение включает:

- Права смены схемы
- Инварианты
- Срок хранения и удаление (закон)
- Правила доступа
- Восстановление резервной копии этих данных

Без владения у вас integration database или грязь (тема 5). С владением вы можете развиваться.

Общие справочные данные (коды стран) могут иметь маленького владельца или статический пакет. Не позволяйте каждому сервису изобретать таблицу стран.

У копий должен быть статус: источник, кэш, поиск, склад. У каждой копии есть правило обновления. У каждой копии есть запрет тихих записей.

Владение также факт заинтересованных сторон (тема 1). Владелец принимает качество этих данных. Команда отчётов, которая не владеет заказами, не должна «чинить» строки заказов на месте.

В монолите запишите владельца в модуле и в комментарии таблицы или в заголовке файла схемы. В системе из нескольких сервисов запишите владельца в ADR и в API.

Удаление и приватность следуют владельцу. Если вы копируете персональные данные в три хранилища, владелец должен знать все копии. Поиск и кэш — копии.

# 11. Vacuum, раздутие и обслуживание

## Описание

Эта тема показывает, зачем PostgreSQL 16 и PostgreSQL 17 нужен vacuum. Вы узнаёте мёртвые кортежи, autovacuum, ручной `VACUUM`, `VACUUM FULL`, `ANALYZE`, wraparound id транзакций и раздутие.

Сначала завершите тему 10. Нужно знать MVCC и снимки. Завершите эту тему до изучения ролей и безопасности.

Используйте один термин для каждого понятия. Мёртвый кортеж — версия строки, которая ни одному снимку не нужна. Vacuum удаляет мёртвые кортежи и обновляет карту видимости. Раздутие — лишнее место, которое остаётся после тяжёлых обновлений или удалений. Wraparound — риск, когда 32-битные id транзакций повторно используют старые номера. Autovacuum — фоновый процесс, который запускает vacuum и analyze.

## Почему UPDATE/DELETE оставляют мёртвые кортежи

MVCC не перезаписывает строку на месте для обычного `UPDATE`. Сервер пишет новый кортеж. Старый кортеж помечает мёртвым для будущих снимков. `DELETE` помечает кортеж мёртвым. Место не возвращается операционной системе. Оно остаётся в файле таблицы, пока vacuum не пометит его повторно используемым.

```sql
UPDATE items SET qty = qty + 1 WHERE id = 1;
DELETE FROM items WHERE id = 2;
```

Каждый из этих операторов может создать мёртвые кортежи. Долгая транзакция, которая всё ещё видит старый снимок, задерживает vacuum. Vacuum не может удалить кортеж, который какому-то снимку ещё нужен.

Посмотреть числа мёртвых кортежей:

```sql
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
WHERE relname = 'items';
```

`n_dead_tup` — оценка. Выполните `ANALYZE` или подождите активности, чтобы счётчики обновились.

Обновления heap-only tuple (HOT) могут избежать новой записи индекса, когда индексированные столбцы не меняются и новый кортеж умещается на той же странице. Тема 19 разбирает HOT. Знайте, что одни обновления стоят меньше других.

`INSERT` не создаёт мёртвый кортеж. Откаченный `INSERT` оставляет кортеж, который vacuum должен почистить.

Мёртвые кортежи также есть в индексах. Vacuum чистит указатели индекса на мёртвые кортежи кучи.

Не запускайте `UPDATE` каждой строки каждую минуту без плана vacuum. Не держите `BEGIN` открытым часами на занятой базе.

## Autovacuum

Autovacuum по умолчанию включён. Процесс-launcher запускает рабочие процессы. Рабочие выполняют `VACUUM` и `ANALYZE` на таблицах, которые проходят порог.

Важные настройки (обзор):

- `autovacuum` — вкл/выкл (оставьте вкл.)
- `autovacuum_naptime` — как часто launcher смотрит на таблицы
- `autovacuum_vacuum_threshold` и `autovacuum_vacuum_scale_factor` — когда делать vacuum
- `autovacuum_analyze_threshold` и `autovacuum_analyze_scale_factor` — когда делать analyze
- `autovacuum_vacuum_insert_threshold` и insert scale factor — vacuum после многих вставок (карта видимости)
- `autovacuum_freeze_max_age` — защита от wraparound (поздний раздел)

Триггер vacuum примерно:

```text
threshold + scale_factor * reltuples
```

Большой таблице нужно больше мёртвых кортежей, прежде чем autovacuum стартует. Занятая маленькая таблица очищается раньше.

Можно задать параметры хранения на одну таблицу:

```sql
ALTER TABLE items SET (autovacuum_vacuum_scale_factor = 0.05);
```

Посмотреть рабочих:

```sql
SELECT * FROM pg_stat_activity
WHERE backend_type = 'autovacuum worker';
```

`pg_stat_progress_vacuum` показывает идущий vacuum.

Не выключайте autovacuum. Если выключили для массовой загрузки, включите снова и сами выполните `VACUUM ANALYZE`.

Autovacuum может быть занят после большого `UPDATE`. Это нормально. Если autovacuum никогда не успевает, слишком много обновлений, слишком мало рабочих или долгий снимок.

PostgreSQL 16 и 17 улучшили память vacuum и смежные внутренности. Пороги настраиваете так же.

## Ручной `VACUUM` и `VACUUM FULL` (последний переписывает таблицу)

`VACUUM` удаляет мёртвые кортежи и делает место повторно используемым внутри файла. В обычном случае он не возвращает место на диске операционной системе. Может работать параллельно с чтениями и записями. Берёт скромную блокировку.

```sql
VACUUM items;
VACUUM (VERBOSE) items;
VACUUM (ANALYZE) items;
VACUUM;
```

`VACUUM` без имени таблицы обрабатывает базу. Это могут суперпользователи и некоторые роли. Владельцы таблиц могут `VACUUM` свои таблицы.

`VACUUM (ANALYZE)` также обновляет статистику. Эта пара обычна после массовой загрузки.

`VACUUM FULL` переписывает таблицу в новый файл. Он возвращает место операционной системе. Строит новые индексы. Берёт блокировку `ACCESS EXCLUSIVE`. Никакая сессия не может читать или писать таблицу во время переписи. Нужно дополнительное место на диске для новой копии.

```sql
VACUUM FULL items;
```

Используйте обычный `VACUUM` для нормального обслуживания. Используйте `VACUUM FULL` только когда измерили большое пустое место и можете заблокировать таблицу (или используете инструмент, который переписывает с меньшей блокировкой, например `pg_repack`, которого нет в ядре).

Опции в текущих версиях:

- `VACUUM (INDEX_CLEANUP ON)` — очистка индексов по умолчанию
- `VACUUM (TRUNCATE ON)` — попытаться обрезать пустые страницы в конце файла
- `VACUUM (PARALLEL n)` — параллельный vacuum индексов одной таблицы (обычный vacuum)

`VACUUM FULL` также называют `CLUSTER` без индекса, когда нужна только перепись. Когда цель — сжать, предпочитайте явное имя `VACUUM FULL`.

Не планируйте `VACUUM FULL` каждую ночь на больших продакшен-таблицах. Не запускайте `VACUUM FULL` вместо исправления долгой транзакции, которая блокирует autovacuum.

## `ANALYZE`

`ANALYZE` сэмплирует таблицу и хранит статистику для планировщика (тема 9). Autovacuum запускает analyze по отдельному порогу от vacuum.

```sql
ANALYZE items;
ANALYZE items (name, qty);
ANALYZE;
```

Можно анализировать конкретные столбцы. Это полезно, когда одному столбцу нужна более высокая цель статистики.

После большого `INSERT`, `COPY` или `DELETE` выполните `ANALYZE` (или `VACUUM ANALYZE`) до того, как доверять `EXPLAIN`. Тогда `reltuples` в `pg_class` ближе к новому размеру.

`ANALYZE` не удаляет мёртвые кортежи. `VACUUM ANALYZE` делает и то и другое.

Analyze, связанный с freeze, — не то же самое, что статистика планировщика. Не пропускайте `ANALYZE` планировщика только потому, что запускали vacuum.

Посмотреть времена последнего analyze:

```sql
SELECT relname, last_analyze, last_autoanalyze, n_mod_since_analyze
FROM pg_stat_user_tables;
```

`n_mod_since_analyze` показывает, сколько изменилось с последнего analyze.

Не запускайте `ANALYZE` в тесном цикле. Он сэмплирует I/O. После массовой загрузки одного раза хватает, пока данные снова не изменятся.

## Wraparound id транзакций (нужно знать риск)

PostgreSQL помечает версии строк 32-битным id транзакции (xid). В круговом пространстве доступно около двух миллиардов xid. Если кластер назначает xid и никогда не замораживает старые строки, старые xid могут стать «в будущем». Тогда видимость ломается. PostgreSQL останавливает новые транзакции, чтобы защитить данные:

```text
ERROR:  database is not accepting commands to avoid wraparound data loss
```

**Freeze** заменяет старые xid на кортежах маркером заморозки. Эту работу делает vacuum freeze. Autovacuum всегда запускает freeze vacuum, когда возраст таблицы приближается к `autovacuum_freeze_max_age` (по умолчанию 200 миллионов). Этот аварийный vacuum может быть агрессивным. Он не необязателен.

Смотреть возраст:

```sql
SELECT datname, age(datfrozenxid), datfrozenxid
FROM pg_database
ORDER BY age(datfrozenxid) DESC;

SELECT c.relname, age(c.relfrozenxid)
FROM pg_class AS c
JOIN pg_namespace AS n ON n.oid = c.relnamespace
WHERE n.nspname = 'public'
  AND c.relkind = 'r'
ORDER BY age(c.relfrozenxid) DESC;
```

`age(datfrozenxid)` должен оставаться далеко ниже двух миллиардов. Многие команды алертят на нескольких сотнях миллионов.

Причины риска wraparound:

- autovacuum выключен
- очень долгая транзакция или забытая подготовленная транзакция
- слот или реплика, которая держит снимок (логические слоты, устаревшие реплики)
- столько трафика обновлений, что freeze никогда не заканчивается

Исправления: включить autovacuum, завершить долгие транзакции, vacuum freeze старых таблиц, добавить мощность.

```sql
VACUUM (FREEZE, VERBOSE) items;
```

Не замораживайте вручную каждый день. Следите за возрастом. Держите autovacuum здоровым.

Функции `xid8` (64 бита) из темы 10 не убирают 32-битный wraparound из кучи. Freeze всё равно важен в PostgreSQL 16 и 17.

Этот риск настоящий. Относитесь к алертам wraparound как к срочным.

## Раздутие таблиц и индексов

Раздутие — неиспользуемое место внутри файла таблицы или индекса. Его вызывают мёртвые кортежи, оборванные цепочки HOT и разбиения индекса. Файл остаётся большим. Запросы читают больше страниц. Доля попаданий в кэш может упасть.

Обычный `VACUUM` делает место повторно используемым. Он не всегда сжимает файл. Новые вставки могут переиспользовать место. Если число строк таблицы сжалось, а на диске она огромная, у вас раздутие.

Проверить размеры:

```sql
SELECT
    relname,
    pg_size_pretty(pg_relation_size(oid)) AS heap,
    pg_size_pretty(pg_indexes_size(oid)) AS indexes
FROM pg_class
WHERE relname = 'items';
```

`pgstattuple` и `pgstatindex` (расширение `pgstattuple`) оценивают свободное место. Многие сайты используют запросы из вики PostgreSQL (оценки раздутия из `pg_class` и `reltuples`). Оценки могут быть неверны. Когда нужно знать точно, измеряйте расширением.

Снизить раздутие таблицы:

- autovacuum, который успевает
- меньше ненужных `UPDATE` (обновлять только изменённые столбцы; избегать заданий «тронуть всё»)
- `VACUUM FULL` или `CLUSTER`, когда можно заблокировать
- `pg_repack` или похожие инструменты, когда блокировать нельзя (внешние)

Снизить раздутие индекса:

- `REINDEX INDEX CONCURRENTLY` (тема 8)
- удалить неиспользуемые индексы
- предпочитать HOT-дружественные обновления (не менять индексированные столбцы)

Fillfactor ниже 100 оставляет место на каждой странице для HOT-обновлений. Более низкий fillfactor может снизить раздутие на горячих столбцах обновления. Он использует больше диска. Задавайте с измерением.

```sql
ALTER TABLE items SET (fillfactor = 80);
```

Не гонитесь за нулевым раздутием. Часть свободного места полезна. Гонитесь за раздутием, которое измерили (размер против числа строк, кэш, I/O).

PostgreSQL 17 снизил часть накладных расходов vacuum. Раздутие всё равно появляется, если обновляете больше, чем vacuum успевает чистить.

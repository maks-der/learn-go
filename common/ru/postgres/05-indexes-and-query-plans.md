# 5. Индексы и планы запросов

## Описание

Эта тема показывает индексы и планы запросов в PostgreSQL 16 и PostgreSQL 17. Вы узнаёте B-tree, Hash, GiST, GIN и BRIN. Узнаёте частичные, выражений, уникальные и составные индексы. Также узнаёте `CREATE INDEX CONCURRENTLY`, `REINDEX`, `EXPLAIN`, методы соединений, `ANALYZE` и `pg_stat_statements`.

Сначала завершите тему 4. Вы знаете операторы, которые поддерживают индексы. Завершите эту тему до изучения транзакций и vacuum.

Используйте один термин для каждого понятия. Индекс — вторичная структура, которая помогает серверу находить строки. Куча — таблица. Планировщик выбирает план. Исполнитель выполняет план. Сканирование читает таблицу или индекс. Метод соединения объединяет два источника строк. Статистика — оценки, которые хранит `ANALYZE`.

## B-tree, Hash, GiST, GIN, BRIN

`CREATE INDEX` без `USING` строит B-дерево.

```sql
CREATE INDEX items_name_idx ON items (name);
CREATE INDEX items_qty_idx ON items (qty);
```

B-дерево поддерживает операторы сравнения: `=`, `<`, `<=`, `>`, `>=`. Поддерживает `ORDER BY` по тому же столбцу и направлению. Поддерживает `BETWEEN`. Поддерживает `LIKE 'abc%'` (префикс). Само по себе не поддерживает `LIKE '%abc'`.

B-дерево — правильный индекс для первичных ключей, уникальных ключей, столбцов внешних ключей, равенства, диапазонов и ключей сортировки, которые совпадают с запросом.

Другой класс выбираете через `USING`:

| Класс | Типичное применение |
| --- | --- |
| **B-tree** | по умолчанию; равенство и диапазон |
| **Hash** | только равенство (`=`); редко; без порядка |
| **GiST** | диапазоны, геометрия, часть полнотекста и триграмм |
| **GIN** | массивы, `jsonb`, полнотекст `tsvector` |
| **BRIN** | очень большие таблицы с физической корреляцией (добавление по времени) |

```sql
CREATE INDEX items_id_hash ON items USING HASH (id);
CREATE INDEX events_payload_gin ON events USING GIN (payload);
CREATE INDEX readings_created_brin ON readings USING BRIN (created_at);
```

Hash-индексы в текущих версиях пишутся в WAL. Они всё ещё не поддерживают `ORDER BY` или диапазоны. Предпочитайте B-дерево, пока не измерите выигрыш.

GiST — сбалансированное дерево для типов, у которых нет простого скалярного порядка. PostGIS (тема 14) использует GiST. `tstzrange` и похожие типы диапазонов часто используют GiST.

GIN — инвертированный индекс. Хорош, когда одна строка содержит много ключей (элементы массива, ключи JSON, лексемы). GIN большой. Записи медленнее.

BRIN хранит сводки min/max на диапазон страниц. Он маленький. Помогает, когда строки с общим ключом лежат рядом на диске (вставка по времени). Не работает, когда значения на диске случайны.

Планировщик использует индекс только когда оценивает, что индекс дешевле последовательного сканирования. Фильтр, который совпадает с большинством строк, часто использует последовательное сканирование. Этот выбор может быть верным.

Каждый лишний индекс замедляет `INSERT`, `UPDATE` и `DELETE`. Не создавайте второе B-дерево на том же столбце, что первичный ключ. Именуйте индексы по ясному шаблону: `tablename_column_idx`.

## Частичные, выражений, уникальные и составные индексы

**Частичный** индекс покрывает подмножество строк:

```sql
CREATE INDEX orders_open_idx ON orders (id)
    WHERE status = 'open';
```

Планировщик может использовать его только когда `WHERE` запроса влечёт предикат. Частичные индексы остаются маленькими.

Индекс **выражения** хранит вычисленное значение:

```sql
CREATE INDEX users_email_lower_idx ON users (lower(email));
```

Запрос должен использовать то же выражение: `WHERE lower(email) = 'a@b.com'`. Тема 4 использовала `(payload ->> 'type')` как индекс выражения.

**Уникальный** индекс запрещает дубликаты. `CREATE UNIQUE INDEX` и ограничение `UNIQUE` оба строят уникальный индекс. Уникальный индекс может быть частичным:

```sql
CREATE UNIQUE INDEX users_one_active_email
    ON users (email)
    WHERE deleted_at IS NULL;
```

**Составной** (многостолбцовый) индекс имеет список столбцов:

```sql
CREATE INDEX orders_cust_created_idx
    ON orders (customer_id, created_at);
```

Составные B-деревья — левый префикс. Запрос, который фильтрует `customer_id`, может использовать этот индекс. Запрос, который фильтрует только `created_at`, обычно использует его плохо.

Порядок столбцов важен. Сначала столбцы равенства. Затем столбцы диапазона или сортировки.

Неключевые столбцы можно добавить через `INCLUDE` (покрывающий индекс). Тема 13 разбирает `INCLUDE` с пагинацией. Знайте, что столбцы `INCLUDE` не часть ключа поиска.

```sql
CREATE INDEX orders_cust_inc
    ON orders (customer_id) INCLUDE (created_at, total);
```

Не стройте пять пересекающихся составных индексов «на всякий случай». Не делайте уникальный индекс на столбце, который должен допускать дубликаты. Не забывайте, что функции в запросах должны совпадать с индексами выражений.

## `CREATE INDEX CONCURRENTLY` и `REINDEX`

`CREATE INDEX` на живой таблице берёт сильную блокировку, которая блокирует записи. `CREATE INDEX CONCURRENTLY` строит индекс без долгой блокировки записи. Ждёт старые транзакции. Сканирует таблицу дважды.

```sql
CREATE INDEX CONCURRENTLY items_name_idx ON items (name);
```

Правила:

- `CONCURRENTLY` нельзя запускать внутри блока транзакции.
- Построение может упасть и оставить **недействительный** индекс. `\d` или `pg_index.indisvalid` его показывает.
- Удалите недействительный индекс и попробуйте снова: `DROP INDEX CONCURRENTLY items_name_idx;`
- `CONCURRENTLY` медленнее обычного построения.

`CREATE UNIQUE INDEX CONCURRENTLY` допустим. Нарушения уникальности роняют построение.

`REINDEX` перестраивает индекс. Используйте после раздутия или порчи. `REINDEX INDEX name` перестраивает один индекс. `REINDEX TABLE name` перестраивает все индексы этой таблицы.

```sql
REINDEX INDEX CONCURRENTLY items_name_idx;
REINDEX TABLE CONCURRENTLY items;
```

`REINDEX CONCURRENTLY` есть в текущих версиях. Правила транзакций похожи. Нельзя запускать в блоке транзакции.

В PostgreSQL 16 и 17 у `REINDEX` есть опции вроде `TABLESPACE`. У системных каталогов дополнительные пределы. Не делайте `REINDEX` системных каталогов наобум на общем хосте.

Неудачный concurrent reindex может оставить временный индекс. Прочитайте документацию и `pg_index`, прежде чем удалять объекты.

Не используйте `CONCURRENTLY` на пустой учебной таблице только чтобы набрать слово. Используйте, когда записи должны продолжаться. Не игнорируйте недействительный индекс. Планировщик его не использует.

## `EXPLAIN` и `EXPLAIN ANALYZE`

`EXPLAIN` печатает план. Запрос не выполняет (кроме некоторых форм, которые всё же готовят работу). `EXPLAIN ANALYZE` выполняет запрос и печатает фактические времена и числа строк.

```sql
EXPLAIN
SELECT * FROM items WHERE name = 'nail';

EXPLAIN ANALYZE
SELECT * FROM items WHERE name = 'nail';
```

Полезные опции:

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT * FROM items WHERE qty > 10;
```

Частые опции в PostgreSQL 16 и 17:

- `ANALYZE` — выполнить запрос
- `BUFFERS` — показать общие и прочитанные буферы
- `WAL` — показать записи WAL (полезно на записях)
- `SETTINGS` — показать настройки планировщика, которые отличаются от default
- `VERBOSE` — дополнительные детали
- `COSTS` — показать стоимости (по умолчанию вкл.)
- `TIMING` — таймер на узел (по умолчанию вкл. с `ANALYZE`)
- `SUMMARY` — сводка общего времени

`EXPLAIN ANALYZE` на `INSERT`, `UPDATE` или `DELETE` **выполняет** изменение. Когда нужен только план, используйте транзакцию и `ROLLBACK`:

```sql
BEGIN;
EXPLAIN ANALYZE UPDATE items SET qty = qty + 1;
ROLLBACK;
```

Читайте текстовый план сверху. Первый узел — корень. Отступ показывает детей. PostgreSQL сначала выполняет детей.

Два числа на каждом узле: оценочная стоимость (`cost=startup..total`) и оценочные строки (`rows=`). После `ANALYZE` также видны `actual time` и `actual rows`. Большой разрыв между оценочными и фактическими строками значит плохую статистику или плохую оценку предиката.

Не настраивайте запрос только по числам стоимости. Используйте фактическое время из `ANALYZE`. Не запускайте `EXPLAIN ANALYZE` на тяжёлой записи в продакшене без плана.

`EXPLAIN` не включает сетевое время до клиента. Не включает циклы приложения.

## Seq scan, index scan, nested loop, hash join, merge join

**Последовательное сканирование** читает кучу с начала до конца. Дёшево на строку, когда нужны большинство строк. Дорого, когда нужна одна строка из большой таблицы.

**Сканирование индекса** идёт по индексу и достаёт кортежи кучи. **Index-only scan** может использовать карту видимости и пропускать кучу, когда все нужные столбцы в индексе (и видимость позволяет). **Bitmap index scan** плюс **bitmap heap scan** эффективны, когда совпадает много строк.

```sql
EXPLAIN SELECT * FROM items WHERE id = 1;
EXPLAIN SELECT * FROM items WHERE qty > 0;
```

Методы соединений:

| Метод | Идея |
| --- | --- |
| **Nested loop** | Для каждой внешней строки найти внутренние. Хорош для малых внешних наборов и индексированных внутренних поисков. |
| **Hash join** | Построить хеш-таблицу на одной стороне. Зондировать другой. Хорош для более крупных соединений по равенству. |
| **Merge join** | Отсортировать обе стороны (или сканировать упорядоченные индексы) и слить. Хорош для отсортированного равенства или части диапазонов. |

Планировщик выбирает метод по стоимостям и статистике. Для учёбы методы можно форсировать:

```sql
SET enable_hashjoin = off;
SET enable_mergejoin = off;
```

После теста сбросьте. Не оставляйте эти настройки в продакшене.

`work_mem` ограничивает память на шаг сортировки или хеша (тема 13). Малый `work_mem` может сбрасывать на диск. `EXPLAIN ANALYZE` показывает `Sort Method` и пакеты хеша.

Соединение, которое в `EXPLAIN` выглядит как nested loop, — не цикл программирования, который вы пишете. Это алгоритм исполнителя.

Не добавляйте индекс на каждое последовательное сканирование, которое видите. Измеряйте селективность. Не отключайте последовательное сканирование глобально.

## `ANALYZE` и `pg_stat_statements`

`ANALYZE` собирает статистику: числа строк, самые частые значения, гистограммы и доли NULL. Планировщик читает `pg_statistic` (через представления вроде `pg_stats`).

```sql
ANALYZE items;
ANALYZE;
```

`ANALYZE` без имени таблицы анализирует все таблицы базы, которые вам можно читать. Autovacuum тоже запускает analyze (тема 7). После массовой загрузки выполните `ANALYZE` сами. Не ждите, если сразу сделаете `EXPLAIN`.

```sql
SELECT attname, n_distinct, most_common_vals
FROM pg_stats
WHERE tablename = 'items';
```

Плохая статистика даёт плохие оценки строк. Плохие оценки дают неверные методы соединений и неверные типы сканирования.

`pg_stat_statements` записывает отпечаток SQL и суммарное время. Это расширение (тема 9). Включите его в `postgresql.conf`:

```text
shared_preload_libraries = 'pg_stat_statements'
```

Затем в базе:

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT query, calls, total_exec_time, mean_exec_time, rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```

PostgreSQL 16 и 17 используют `total_exec_time` и связанные столбцы exec. В старых текстах было `total_time`.

`pg_stat_statements` нормализует литералы. Много похожих запросов становятся одной строкой. Это не замена `EXPLAIN` на одном вызове. Это говорит, какие операторы жгут время в продакшене.

`pg_stat_user_indexes` показывает сканирования индексов. `idx_scan = 0` через неделю может значить неиспользуемый индекс.

Не запускайте `ANALYZE` в тесном цикле. Не включайте `pg_stat_statements` без `shared_preload_libraries`. Не считайте верхний запрос «сломанным» без `EXPLAIN ANALYZE`.

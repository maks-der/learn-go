# 7. Персистентность

## Описание

Redis может писать данные на диск, чтобы перезапуск мог загрузить ключи. Персистентность необязательна. Эта тема покрывает снимки RDB, файл только для добавления (AOF), режимы `appendfsync`, гибрид RDB+AOF, окна потери данных и `BGSAVE` против `SAVE`.

Завершите эту тему до изучения репликации. Реплики не заменяют план резервного копирования.

Используйте один термин для каждого понятия. Снимок — файл RDB на момент времени. AOF — журнал команд записи (или эффектов). `fsync` — вызов ОС, который толкает данные файла на долговечное хранилище. Окно потери — время записей, которые можно потерять при аварии. Не считайте «персистентность включена» как «каждый `OK` на диске».

---

## Снимки RDB

RDB — компактный двоичный снимок набора данных. Redis пишет файл (часто `dump.rdb`). При старте Redis загружает этот файл в ОЗУ. Ключи, которых не было в снимке, не возвращаются.

Можно запустить снимок через `BGSAVE` или `SAVE`. Можно также задать правила сохранения в `redis.conf`:

```text
save 900 1
save 300 10
save 60 10000
```

Эти правила значат: сохранить после 900 секунд, если изменился хотя бы 1 ключ, после 300 секунд, если изменились 10 ключей, и после 60 секунд, если изменились 10 000 ключей. `save ""` отключает автоматический RDB.

RDB хорош для резервных копий и для быстрого перезапуска больших наборов. Файл меньше многословного журнала команд. Вы копируете `dump.rdb` в хранилище резервных копий.

RDB — не журнал на каждую команду. Записи после последнего снимка отсутствуют, если процесс умрёт. Окно потери — «время с последнего успешного снимка» плюс любой снимок, который не закончился.

Снимок — полная копия набора данных на момент. Большие наборы занимают время и дополнительную ОЗУ во время `BGSAVE` (copy-on-write). Тема 11 покрывает стоимость fork. Здесь знайте, что `BGSAVE` не бесплатен.

`INFO persistence` показывает `rdb_last_save_time`, `rdb_changes_since_last_save` и статус последнего сохранения.

Не правьте файл RDB вручную. Используйте Redis или официальные инструменты, чтобы проверить файл.

## AOF и `appendfsync`

AOF записывает записи, чтобы Redis мог воспроизвести их при старте. Файл растёт с каждой записью (пока не будет перезаписи). Имя по умолчанию часто `appendonly.aof` (Redis 7 может использовать каталог частей AOF).

Включите AOF:

```text
appendonly yes
```

`CONFIG SET appendonly yes` может включить AOF на работающем лабораторном экземпляре. Подтвердите на вашей версии. Для реального сервиса предпочитайте `redis.conf` плюс перезапуск.

При старте Redis воспроизводит AOF (и может загрузить преамбулу RDB в гибридном режиме). Набор данных совпадает с журналом, кроме хвоста, который не был `fsync`.

Перезапись AOF строит более короткий файл, который даёт тот же набор данных. Redis может переписать в фоне (`BGREWRITEAOF`). Автоматическая перезапись использует `auto-aof-rewrite-percentage` и `auto-aof-rewrite-min-size`.

AOF больше и медленнее загружается, чем компактный RDB для тех же данных, если не использовать гибридный режим. AOF может потерять меньше записей, чем RDB, если вы часто делаете `fsync`.

`INFO persistence` показывает `aof_enabled`, `aof_last_write_status` и поля перезаписи.

Повреждённый AOF может заблокировать старт. Инструменты Redis могут починить хвост (`redis-check-aof`). Не запускайте ремонт на единственной копии. Сначала скопируйте файл.

AOF — не журнал запросов для людей. Не разбирайте его как систему аудита, если не строите это сознательно.

`appendfsync` контролирует, когда Redis просит ОС сбросить данные AOF на диск.

- `always` — `fsync` после каждой записи. Окно потери — около одной команды. Это самый медленный режим. Задержка каждой записи включает диск.
- `everysec` — `fsync` примерно раз в секунду. Можно потерять около одной секунды записей при аварии. Это частый режим по умолчанию. Это баланс безопасности и скорости.
- `no` — Redis не делает `fsync` по расписанию. ОС сбрасывает, когда хочет. Окно потери может быть длиннее. Это самый быстрый режим и наименее безопасный.

```text
appendfsync everysec
```

`always` не делает Redis полной заменой дисковой базы. Железо и ОС всё ещё могут потерять данные при отключении питания, если диск врёт про сброс. Используйте ИБП и честные диски, когда данные важны.

`everysec` может застопорить записи, если `fsync` занимает много времени (`appendfsync` и `no-appendfsync-on-rewrite` взаимодействуют во время перезаписи). Читайте документацию, если видите скачки задержки во время перезаписи.

Проверьте работающее значение через `CONFIG GET appendfsync`.

Приложение всё равно получает `OK` после того, как Redis применил запись в памяти. `OK` — не обещание, что `everysec` или `no` уже сбросили диск. Только `always` ждёт `fsync` на этой записи (с пределами выше).

Для кэша AOF можно оставить выключенным. Для хранилища записи выберите `everysec` или `always` и проверьте убийство процесса.

## Гибрид RDB+AOF

Можно включить и RDB, и AOF. Redis 7 использует AOF, который может начинаться с преамбулы RDB. Перезапись даёт двоичный снимок плюс хвост команд. Старт загружает преамбулу, затем воспроизводит хвост. Время загрузки лучше, чем у огромного AOF только из команд.

Старые схемы использовали RDB для резервных копий и AOF для долговечности, с обоими файлами на диске. Поймите вашу версию:

- `appendonly yes` плюс правила `save`
- Redis 7 `aof-use-rdb-preamble` (часто да по умолчанию)

Гибридный режим всё ещё имеет окно потери `appendfsync` на хвосте AOF. Преамбула RDB — снимок более раннего момента. Хвост — остальное.

Выгоды:

- Более быстрый перезапуск, чем длинное воспроизведение AOF
- Лучшая долговечность, чем только RDB (с `everysec` или `always`)
- Одна история восстановления: включите AOF, держите резервные копии RDB как дополнительные копии

Цены:

- Больше диска
- Больше ввода-вывода
- Больше эксплуатационных частей для мониторинга (`INFO persistence`)

Реплика может персистировать даже когда основной персистирует. Персистентность и репликация — разное. Реплика с AOF не заменяет резервные копии основного, если нужны копии на момент времени вне хоста.

Когда включаете AOF впервые, Redis может создать файл из текущего набора данных (перезапись). Планируйте место на диске до включения AOF на большом экземпляре.

## `BGSAVE` против `SAVE`

`SAVE` пишет файл RDB в основном потоке. Redis не выполняет другие команды, пока `SAVE` не закончится. Клиенты ждут. На большом наборе `SAVE` может застопорить экземпляр на секунды или минуты. Не используйте `SAVE` в продакшене.

`BGSAVE` делает fork дочернего процесса. Потомок пишет файл RDB. Родитель продолжает обслуживать команды. Операционная система использует copy-on-write (COW). Если много ключей меняется во время сохранения, RSS может вырасти почти до двух копий набора. Оставьте свободную ОЗУ для этого пика.

```text
BGSAVE
```

`LASTSAVE` возвращает время Unix последнего успешного снимка.

`INFO persistence` показывает `rdb_bgsave_in_progress`. Не запускайте другой `BGSAVE`, если один уже идёт, если не знаете, что сервер это позволяет (обычно отказывает).

`SHUTDOWN` может выполнить сохранение. `BGREWRITEAOF` — аналог фоновой перезаписи AOF (тоже fork).

Используйте `BGSAVE` для резервных копий по запросу. Планируйте автоматические правила `save` или внешнюю резервную копию, которая копирует файл после завершения `BGSAVE`.

Если `BGSAVE` падает (ошибка `fork`, диск полон), исправьте причину. Redis можно настроить останавливать записи, когда последний `BGSAVE` упал (`stop-writes-on-bgsave-error`). Этот флаг защищает от тихого состояния «нет снимков». Он также может заблокировать кэш. Знайте настройку.

## Перезапуск и ожидания потери данных

Напишите ясный контракт для каждой среды.

Экземпляр кэша:

- Персистентность может быть выключена
- Перезапуск теряет все ключи
- Приложение восстанавливает из источника истины
- Потеря ожидаема

Долговечный экземпляр:

- AOF включён, `appendfsync everysec` или `always`
- RDB или гибрид для более быстрой загрузки и резервных копий
- Убийство процесса может потерять до примерно одной секунды (`everysec`) или редкую потерю на уровне диска (`always`)
- Отказ диска хоста теряет данные, если нет резервных копий вне хоста и/или реплик

Проверьте контракт. Не угадывайте.

Тесты:

1. `SET` ключа-маркера
2. `BGSAVE` или дождитесь fsync AOF
3. Перезапустите Redis чисто (`SHUTDOWN` или остановка Docker)
4. `GET` маркера
5. Повторите с жёстким убийством после вспышки записей

`SHUTDOWN` может записать финальный RDB или AOF в зависимости от конфигурации (`SHUTDOWN NOSAVE` не пишет). Читайте страницу `SHUTDOWN`. Авария или `kill -9` пропускает изящное сохранение.

Реплики, которые не повысили, не помогают, если вы уничтожаете единственную копию и реплики нет. Резервные копии — файлы, которые вы скопировали прочь.

Документируйте время восстановления (загрузка RDB/AOF) для вашего размера. Набор 20 GB не мгновенный.

Клиенты должны обрабатывать ошибки соединения во время перезапуска. Приложение должно повторять с потолком.

5. Как доказать контракт перезапуска тестами?

#### Простые практические задания

1. Экспортируйте `INFO persistence` в файл. Отметьте поля RDB, поля AOF и поля последней ошибки.
2. Напишите шпаргалку: правила `save`, `appendonly`, `appendfsync`, `BGSAVE`, `SAVE`, `BGREWRITEAOF`, `SHUTDOWN`.
3. Нарисуйте шкалу времени: запись, `OK`, fsync (или снимок), авария, перезапуск, `GET`.
4. Напишите три лабораторных правила: нет `SAVE` в продакшене, копировать файлы до ремонта, проверять kill -9.

#### Средние практические задания

1. Настройте одноразовый экземпляр с гибридной персистентностью и `everysec`. Запустите тест из 1000 записей и тест перезапуска. Запишите результаты.
2. Опишите пути диска и команды копирования резервной копии для Docker Redis.
3. Напишите политику персистентности на одну страницу для кэш-Redis и долговечного Redis.

#### Сложные практические задания

1. Восстановите тот же RDB на второй версии Redis (или прочитайте заметки о совместимости). Запишите, загрузился ли файл и риск перекоса версий.
2. Замерьте время старта и пиковый RSS для `BGSAVE` на наборе класса 1 GB, если можете его построить. Запишите заметки про железо. Если не можете, напишите план размерности вместо этого.

# 21. Промышленные шаблоны

## Описание

Промышленный Redis — набор политик, а не только работающий процесс. Эта тема покрывает отдельные экземпляры для кэша и долговечных данных, бюджеты ключей и TTL, префиксы многих арендаторов, разрыв цепи, когда Redis недоступен, и как прогревать или делать двойную запись кэша.

Сначала завершите темы 9, 12, 13 и 17. Те темы дают персистентность, клиенты, шаблоны кэша и безопасность. Эта тема их сочетает.

Используйте один термин для каждого понятия. Кэш Redis — экземпляр, который можно потерять. Долговечный Redis — экземпляр, который является источником истины или хранилищем, которое нужно восстановить. Бюджет ключей — предел числа или байт. Префикс арендатора — строка в начале ключа. Разрыв цепи останавливает вызовы к Redis после ошибок. Прогрев заполняет кэш до или во время трафика. Двойная запись обновляет два хранилища в одном дизайне.

## Отделяйте кэш Redis от долговечного Redis

Один экземпляр, который и огромный кэш, и единственная копия задач или сессий, создаёт конфликт.

Кэш хочет:

- Вытеснение (`allkeys-lru` или похожее)
- Короткие TTL
- Необязательную персистентность или никакой
- Терпимость к сбросу и перезапуску

Долговечное хранилище хочет:

- `noeviction` или осторожные только `volatile-*`
- Проверенную персистентность (тема 9)
- Репликацию и резервную копию (тема 10, тема 19)
- Нет `FLUSHALL` как шага деплоя

Если оба живут в одном процессе, давка кэша или политика `maxmemory` могут вытеснить долговечные ключи. `FLUSHALL` стирает оба. Остановка `KEYS` бьёт оба.

Шаблон: два экземпляра (или две базы вендора). Разные хосты, разный `maxmemory`, разные ACL, разные резервные копии. Приложение использует два клиента.

Поток, который нельзя сбрасывать (тема 15), принадлежит долговечному экземпляру или Kafka. Кэш страницы товара принадлежит экземпляру кэша.

Стоимость: два пула, две панели, два обновления. Эта стоимость ниже одного смешанного инцидента.

Не используйте логический `SELECT`, чтобы делить кэш и долговечные данные (тема 1, тема 11 Cluster).

Называйте экземпляры в конфигурации: `REDIS_CACHE_URL` и `REDIS_DURABLE_URL`. Не используйте один URL для обеих ролей.

## Бюджеты ключей и TTL как политика

Бюджет ключей — записанный предел: максимум ключей на префикс, максимум байт на ключ, TTL по умолчанию, джиттер и владелец.

Без политики каждая возможность добавляет ключи навсегда. Redis растёт до вытеснения или OOM.

Строки политики выглядят так:

```text
prefix     role      ttl     jitter   max bytes   owner
cache:p:   cache     300s    0-60s    16KB        shop
sess:      session   1800s   0        4KB         iam
neg:       negative  30s     0-5s     16B         shop
```

Бюджеты используют тему 13 (TTL, джиттер, негативное) и тему 16 (большие ключи). Ops оповещают, когда `INFO keyspace` или оценка `SCAN` превышает бюджет.

`maxmemory` — жёсткая остановка. Политика — социальная остановка. Сначала бьёте политику.

Долговечным ключам всё ещё нужен бюджет. Утечка ключей блокировок без TTL заполняет экземпляр `noeviction`, пока записи не упадут.

Каждому новому префиксу нужен обзор: TTL да/нет, кто удаляет, что происходит при деплое.

Не изобретайте префикс в pull request без строки каталога.

Измеряйте: образцы `MEMORY USAGE`, `--bigkeys` на реплике, число ключей на префикс из темпированного `SCAN` в задании, не `KEYS`.

## Префиксы ключей многих арендаторов

Несколько арендаторов (клиенты, магазины, команды) могут делить один Redis. Вы префиксируете ключи:

```text
t:acme:cache:product:1
t:globex:cache:product:1
```

Префикс избегает столкновений. Арендаторы всё ещё делят:

- ОЗУ и `maxmemory`
- CPU в основном потоке
- `connected_clients`
- `FLUSHALL` (если кто-то может запустить)
- Сеть и диск

Префикс — не граница безопасности (тема 2, тема 17). Клиент, который может `GET t:acme:*`, всё ещё может `GET t:globex:...`, если ACL не ограничивают шаблоны ключей.

ACL могут ограничить пользователя арендатора до `~t:acme:*`. Это настоящий контроль. Пользователь приложения, который обслуживает всех арендаторов, не должен иметь эту изоляцию, если не используете пользователей Redis на арендатора (редко) или экземпляры на арендатора (сильнее).

Шумный сосед: один арендатор может заполнить память или запустить большой `HGETALL`. Бюджеты на префикс арендатора, ограничения частоты (тема 14) и отдельные экземпляры для крупных арендаторов чинят это.

Хеш-теги Cluster: `{t:acme}` может приколоть одного арендатора к диапазону слотов, если так проектируете. Это также может сделать один слот горячей точкой. Предпочитайте теги для ключей, которые должны жить вместе, не для всех ключей арендатора, если не измерили.

Не кладите id арендатора только в значение и не используйте один ключ для всех арендаторов.

## Разрыв цепи, когда Redis недоступен (приложение должно работать, если Redis — кэш)

Если Redis — кэш, отказ Redis не должен ронять продукт. Приложение читает источник истины и пропускает кэш.

Разрыв цепи:

- Считает ошибки или таймауты к Redis
- Открывается после порога
- Быстро отказывает (не ждёт долгий таймаут на каждый запрос)
- Полуоткрывается, чтобы попробовать зонд (`PING` или один `GET`)
- Закрывается, когда Redis здоров

Таймауты темы 12 важны. Таймаут 5 секунд без разрыва может исчерпать пул потоков приложения.

Если Redis долговечный (сессии, которые нельзя восстановить, поток задач), разрыв не изобретает данные. Приложение возвращает ошибку или деградированный режим, который вы спроектировали. Это другое продуктовое решение. Не притворяйтесь, что долговечное хранилище необязательно.

Cache-aside (тема 13) подходит разрыву: считайте ошибки Redis промахами.

Журналы: когда разрыв открывается, журналируйте раз в интервал, не раз на запрос.

Метрики: состояние разрыва, доля ошибок Redis, нагрузка SQL (SQL вырастет, когда кэш выключен).

Не повторяйте вечно внутри окна разрыва (тема 12).

Проверка: остановите Redis в лаборатории и подтвердите, что HTTP API всё ещё обслуживает маршруты, необязательные для кэша.

## Двойная запись и прогрев

Прогрев заполняет ключи кэша до того, как они горячие. Двойная запись держит два хранилища в синхроне во время миграции или заполнения кэша.

Прогрев:

- Задание читает источник истины и делает `SET` ключей кэша (с TTL и джиттером)
- Прогреваете после сброса, до запуска или после нового региона
- Темпируйте задание так, чтобы Redis и SQL выжили (конвейеры с границами, тема 16)

Двойная запись:

- Приложение пишет SQL и Redis в одном запросе (write-through, тема 13)
- Или пишет два кластера Redis во время миграции
- Обработка отказа: если Redis падает, решите, падает ли запрос (долговечный) или продолжается (кэш)

Двойная запись может разойтись. Нужно задание ремонта (читать SQL, `SET` Redis) и TTL, чтобы расхождение умерло.

Не делайте двойную запись двух долговечных систем без истории идемпотентности (тема 14) и ясного источника истины.

Холодный старт: пустой кэш после перезапуска вызывает давку (тема 13). Прогрейте топ-N ключей, или используйте single-flight, или примите нагрузку SQL.

Деплой: предпочитайте версионированные ключи (`cache:p:1001:v2`) и прогревайте `v2` до переключения. Затем удалите `v1` позже. Не делайте `FLUSHALL`, чтобы «обновить кэш».

Ремонт чтения: при промахе заполните Redis. Это cache-aside. Прогрев — пакетная версия.

# 10. TLS

## Описание

TLS защищает поток байтов между двумя программами. Эта тема показывает конфиденциальность, целостность и подлинность. Вы узнаете сертификаты и PKI. Вы узнаете рукопожатие на высоком уровне. Вы узнаете частые отказы. Вы узнаете SSH как отдельный безопасный канал.

Завершите эту тему после DNS и предварительного обзора HTTPS.

Используйте один термин для каждого понятия. Конфиденциальность значит, что наблюдатель не может прочитать полезную нагрузку. Целостность значит, что смена обнаруживается. Подлинность значит, что вы говорите с задуманным соседом. Сертификат связывает открытый ключ с именем. PKI — набор УЦ и политик, которые делают эту связь пригодной. Не говорите «безопасно», не называя, какое из трёх свойств имеете в виду. Не считайте SSH тем же, что TLS.

Практикуйтесь с `curl -v` и видом сертификата в браузере. Захватывайте записи TLS. Вы видите версии и сообщения рукопожатия. Вы не видите пути HTTP в обычной сессии HTTPS.

## Конфиденциальность, целостность, подлинность

Конфиденциальность скрывает полезную нагрузку от наблюдателя пути. TLS шифрует байты приложения после рукопожатия. Адреса и порты остаются видны. Имя Server Name Indication (SNI) часто всё ещё видно в старом TLS. TLS 1.3 может шифровать больше рукопожатия. Шифрование — не невидимость соединения.

Целостность позволяет приёмнику обнаружить смену записей. Промежуточное устройство, которое переворачивает биты, должно вызвать отказ, а не тихую неверную страницу. TLS использует MAC или AEAD для этой задачи. Математика не нужна. Нужно свойство.

Подлинность связывает сессию с личностью соседа. Для HTTPS личность — имя DNS на сертификате. Шифрования без проверки имени недостаточно. Атакующий на пути может завершить TLS другим сертификатом, если клиент не проверяет.

Три слова работают вместе. Конфиденциальность без подлинности может скрыть данные от третьей стороны и всё равно отдать данные неверному соседу. Подлинность без целостности — не полный канал. Целостность без конфиденциальности всё равно может утечь секреты.

Не считайте VPN заменой TLS к публичному API, пока не спроектировали эту модель доверия. SSH использует те же три идеи с другим протоколом и другой моделью личности.

## Сертификаты и PKI

Сертификат связывает открытый ключ с именем и иногда с другими именами. Удостоверяющий центр (УЦ) подписывает эту связь. У клиента есть хранилище доверенных корневых сертификатов УЦ. Операционная система и браузер поставляют эти корни.

PKI — public key infrastructure. PKI — набор УЦ, сертификатов, данных отзыва и политик, которые делают связь пригодной. Публичный УЦ для этой темы вы не запускаете. Нужно знать цепочку доверия: сертификат сервера, необязательные промежуточные и корень, которому клиент уже доверяет.

Клиент проверяет:

- имя в URL совпадает с именем на сертификате
- текущее время внутри интервала действия
- цепочка ведёт к доверенному корню
- подпись на каждом звене действительна
- статус отзыва, когда клиент реализует эту проверку

Самоподписанный сертификат подписан своим ключом. Браузер ему не доверяет, пока не добавите исключение или не установите локальный УЦ вроде mkcert. Используйте самоподписанный или mkcert только на машинах, которыми владеете.

Клиентский сертификат необязателен. Некоторые API используют взаимный TLS. Этой теме нужно только: обычный веб-случай подлинности сервера.

Не отправляйте закрытый ключ в чат или в репозиторий. Не отключайте проверку, чтобы «заработало» на пути настоящего пользователя. Не считайте значок замка на фишинговом имени безопасностью. Замок говорит только, что TLS к этому имени удался.

## Рукопожатие (высокий уровень)

Рукопожатие TLS согласует версию TLS, набор шифров и ключи. В обычном веб-случае оно подлинности сервера сертификатом. Затем обе стороны шифруют данные приложения.

Учебная последовательность в стиле TLS 1.2:

1. Client Hello: версия, случайное, предложенные шифры, SNI
2. Server Hello: выбранные версия и шифр
3. Сертификат сервера
4. Сообщения обмена ключами
5. Переход к зашифрованным записям
6. Данные приложения (HTTP)

TLS 1.3 совмещает шаги и шифрует больше рукопожатия. Всё равно нужны Client Hello, выбор сервера, сертификат и ключи. Каждое расширение не нужно.

ALPN (Application-Layer Protocol Negotiation) позволяет клиенту предложить `http/1.1` и `h2`. Сервер выбирает. Тема 11 использует ALPN.

Рукопожатие нуждается в лишних круговых поездках на новом соединении. Возобновление сессии может укоротить позднее рукопожатие. TCP всё равно сначала нужно своё рукопожатие в классическом HTTPS.

Не путайте тройное рукопожатие TCP с рукопожатием TLS. Оба происходят для HTTPS на TCP. Не ждите прочитать HTTP в захвате до конца рукопожатия.

Отказ в рукопожатии обрывает до HTTP. `curl` печатает ошибку TLS. Тема 13 отлаживает частые отказы.

## Частые отказы

У частых отказов TLS есть имена. Учите симптом и обычную причину.

Несовпадение имени: хост URL не на сертификате. Неверный Host или сырой IP против сертификата только с именем отказывают.

Истёкший или ещё не действительный сертификат: часы неверны или оператор забыл продлить. NTP (тема 12) важен. Ноутбук с мёртвыми часами отказывает везде.

Недоверенный издатель: самоподписанный сертификат, отсутствующий промежуточный или корпоративный УЦ осмотра, которого нет у клиента.

Отозванный сертификат: клиент проверил и отказал. Не все клиенты проверяют одинаково.

Несовпадение протокола или шифра: старый клиент, старый сервер или промежуточное устройство, которое блокирует TLS 1.3.

Перехват: прокси предъявляет свой сертификат. Клиент должен доверять этому корпоративному УЦ. В неизвестной сети это предупреждение.

Проверка имени хоста выключена: программа использовала `-k` или `InsecureSkipVerify`. Сессия может шифровать к неверному соседу.

Не чините путь настоящего пользователя выключенной проверкой. Не игнорируйте истёкший сертификат, потому что «в браузере работает», если браузер показал клик-сквозь. Не вините DNS в несовпадении имени, пока не прочитаете имена сертификата.

`curl -v` и текст ошибки браузера — первые инструменты. Захват показывает, уходит ли Client Hello и возвращается ли предупреждение.

## SSH как безопасный канал

SSH — протокол, который даёт безопасный канал. Люди используют его для удалённой оболочки, копирования файлов (`scp`, SFTP) и туннелей. SSH — не TLS и не HTTP.

SSH подлинности сервера ключом хоста. Клиент хранит отпечаток ключа хоста в `known_hosts`. Сменившийся ключ — предупреждение. Клиент подлинности пользователя паролем или, лучше, парой открытого ключа.

SSH даёт конфиденциальность, целостность и подлинность сессии. Модель личности — ключи и учётные записи пользователей, не публичное хранилище УЦ в обычной настройке OpenSSH. Некоторые площадки используют сертификаты для SSH. Здесь это необязательно.

Обычный порт — 22. Провод — не HTTP. Захват показывает SSH, не TLS Client Hello.

Используйте SSH на пути, которым можно пользоваться. Используйте ключ с парольной фразой. Не переиспользуйте пароль с сайта. Не отключайте проверки ключа хоста, чтобы скрыть лабораторное предупреждение на настоящем jump-хосте.

TLS остаётся верным выбором для публичных API HTTPS. SSH остаётся верным выбором для оболочек администратора. VPN (тема 14) — третий дизайн.

Не выставляйте SSH во весь Internet без лишних контролей (только ключи, списки разрешения). Этот справочник не даёт шагов атаки.

# 8. Транспорт: UDP

## Описание

UDP — транспортный протокол, который отправляет датаграммы. UDP не строит соединение. UDP не повторяет передачу. Эта тема показывает порты, датаграммы, контрольные суммы, отсутствие надёжности и порядка и когда UDP — верный выбор.

Используйте один термин для каждого понятия. Датаграмма — одно сообщение UDP. Порт выбирает сокет на хосте. Завершите эту тему до изучения TCP.

UDP прост. Приложение должно обрабатывать потери, задержку и дубликаты датаграмм, когда эти события важны.

## Номера портов

Порт UDP — 16-битное число. В заголовке UDP есть исходный порт и порт назначения. Порт назначения выбирает принимающий сокет. Исходный порт говорит приёмнику, куда отправить ответ.

Пара IP-адресов, UDP и два порта — 4-tuple, который идентифицирует поток UDP во многих межсетевых экранах и ящиках NAT. (TCP использует 5-tuple с той же идеей плюс поле протокола уже установлено в TCP.)

Общеизвестные порты — низкие номера. DNS часто использует UDP-порт 53. DHCP использует 67 и 68. Многие игры и голосовые инструменты используют высокие порты, которые документирует поставщик.

Клиент часто использует эфемерный исходный порт. Сервер привязывает известный порт назначения. Сервер также может привязать порт 0 и дать ОС выбрать порт. Тогда клиент должен узнать этот порт другим способом.

Порты — на протокол. Порт TCP 53 и порт UDP 53 — разные сокеты. Процесс может слушать оба. Не говорите «порт 53» без TCP или UDP, когда разница важна.

Правило межсетевого экрана должно называть UDP, когда служба UDP. Разрешение TCP не пропускает UDP.

## Датаграмма без соединения

UDP без соединения. Перед первой датаграммой нет рукопожатия. Отправитель пишет датаграмму. Сеть пытается доставить эту датаграмму. Приёмник может получить её, получить дубликат или не получить ничего.

Каждый `send` — одна датаграмма. Каждый `recv` возвращает не больше одной датаграммы (когда используете API датаграмм). ОС не склеивает два сообщения UDP в один поток.

Поле длины UDP покрывает заголовок UDP и полезную нагрузку. Максимальная нагрузка ограничена MTU IP минус заголовки IP и UDP, если отправитель не разрешает фрагментацию IP. Большие датаграммы UDP могут фрагментироваться. Фрагментация хрупкая. Многие приложения держат нагрузку UDP маленькой.

Нет состояния «listen» UDP как у TCP listen. Привязанный сокет UDP может принимать датаграммы от любого узла, если программа не соединяет сокет UDP (фильтр узла по умолчанию). `connect` на UDP не создаёт сетевое рукопожатие. Он только задаёт удалённый адрес по умолчанию в ядре.

Не ждите «сброса соединения» как обязательную функцию UDP. ICMP port unreachable может прийти, если удалённый порт закрыт. Многие хосты его не отправляют. Многие межсетевые экраны его отбрасывают.

Не считайте успешный `send` доставкой. Вызов только ставит датаграмму в очередь.

## Контрольная сумма

В заголовке UDP есть поле контрольной суммы. Контрольная сумма покрывает заголовок UDP, полезную нагрузку и псевдозаголовок с IP-адресами. Приёмник отбрасывает датаграмму с плохой контрольной суммой.

IPv4 разрешает контрольную сумму UDP ноль как «нет контрольной суммы» по старым правилам. Не полагайтесь на это. IPv6 требует контрольную сумму UDP. Современные стеки считают контрольную сумму.

Контрольная сумма — не криптографический хеш. Middlebox или переворот бита всё ещё могут дать коллизию в теории. Контрольная сумма ловит только обычные ошибки. Приложениям, которым нужна подлинность, используют TLS, DTLS или MAC приложения.

Железо может выгружать контрольную сумму. Захват на хосте-отправителе может показать ноль или неверную контрольную сумму, пока NIC не заполнит поле. Не отлаживайте «плохую контрольную сумму» на захвате отправителя без осторожности.

UDP-Lite существует для частичных контрольных сумм на медиа. Этот справочник не требует UDP-Lite.

Не отключайте контрольные суммы UDP ради трюка «скорости» в общей сети. Не считайте хорошую контрольную сумму доказательством, что отправитель доверенный.

## Нет надёжности, нет порядка

UDP не повторяет передачу. Если датаграмма потеряна, UDP не отправляет её снова. Приложение или уровень выше UDP должны повторить, если повтор нужен.

UDP не нумерует датаграммы. Сеть может переставить пакеты. Приёмник может получить сообщение 2 до сообщения 1. Приложение должно терпеть перестановку или добавить номера последовательности.

UDP не задаёт темп отправителю. Быстрый отправитель может переполнить медленного приёмника или тонкий канал. Это не «управление потоком» в смысле TCP. Некоторые приложения добавляют свои окна.

UDP сам не избегает перегрузки. Плохой отправитель UDP может заполнить канал. QUIC и многие медиастеки добавляют управление перегрузкой в приложении или в библиотеке. У сырого UDP нет такого состояния.

Дубликаты могут появиться. Повтор приложения может встретить позднюю исходную датаграмму. Приложение должно игнорировать дубликаты, если они ломают логику.

Не используйте сырой UDP для копирования файла, если не напишете протокол. Не вините UDP, когда забыли обработать потери.

## Когда UDP — верный выбор (DNS, игры, QUIC, медиа)

Выбирайте UDP, когда одна независимая сообщение — естественная единица. Запросы DNS — короткие датаграммы запрос-ответ. Второй запрос — новая датаграмма. Таймаут и повтор сидят в резолвере.

Выбирайте UDP, когда поздние данные бесполезны. Игры и медиа часто предпочитают новый образец поздней повторной передаче. Поздний пакет может быть хуже потери.

Выбирайте UDP, когда хотите построить свой транспорт. QUIC использует UDP, чтобы работать в пространстве пользователя и меняться без TCP ядра. HTTP/3 использует QUIC. Вы изучите это позже. Этой теме нужно только: QUIC — не «ненадёжный HTTP». QUIC добавляет свою надёжность и TLS.

Выбирайте UDP для некоторых туннелей и для DHCP. Протоколы простые и локальные или короткие.

Выбирайте TCP, когда нужен надёжный поток байтов и вы не хотите писать эту логику. Передача файлов, почта и многие API используют TCP (или QUIC).

Не выбирайте UDP только потому, что он «быстрее». Потерянная датаграмма UDP может заставить пользователя ждать повтора приложения. Измеряйте.

Не кладите большой файл на сырой UDP в производстве.

# 12. Сеть со стороны ОС

## Описание

Ядро реализует сокеты, TCP и UDP, маршрутизацию и фильтры пакетов. Эта тема — взгляд операционной системы на этот стек. Вы изучаете API сокетов, как ядро относится к TCP и UDP, пространства имён сети и знакомство с iptables и nftables. Полный путь протоколов живёт в `net.topics.md`. Эта тема его не заменяет.

Завершите эту тему после безопасности и изоляции. Завершите эту тему до наблюдаемости (тема 13). Вы уже знаете дескрипторы файлов, `epoll`, сокеты Unix и пространства имён.

Используйте один термин для каждого понятия. Сокет — конечная точка, которую процесс открывает через `socket`. TCP — надёжный протокол потока байтов, который реализует ядро. UDP — протокол дейтаграмм, который реализует ядро. Пространство имён сети — копия вида сетевого стека (интерфейсы, маршруты, таблицы фильтров). Фильтр пакетов — код ядра, который принимает, отбрасывает или меняет пакеты по правилам. Не смешивайте сокет Unix с интернет-сокетом. Не смешивайте iptables с API сокетов.

## API сокетов

Процесс говорит с сетью через API сокетов. Основные вызовы — POSIX и есть в Linux, BSD и macOS. У Windows похожая модель с другими именами.

Типичный путь потокового сервера:

1. `socket(AF_INET, SOCK_STREAM, 0)` или `AF_INET6`
2. `bind` на адрес и порт
3. `listen`
4. `accept`, чтобы получить новый соединённый дескриптор
5. `read` / `write` или `recv` / `send`
6. `close`

Типичный путь потокового клиента: `socket`, необязательный `bind`, `connect`, затем ввод-вывод, затем `close`.

UDP использует `SOCK_DGRAM`. Нет `listen` или `accept`. `sendto` и `recvfrom` включают адреса.

Сокет — дескриптор файла в Unix. `epoll` может на нём ждать (тема 8). `fork` его наследует. `SCM_RIGHTS` может его передать (тема 9).

Структуры адресов (`sockaddr_in`, `sockaddr_in6`) несут IP и порт. `getaddrinfo` превращает имя и строку службы в эти структуры. Предпочитайте `getaddrinfo` старому `gethostbyname`.

`SO_REUSEADDR` и (в Linux) `SO_REUSEPORT` меняют правила bind. Читайте страницу man, прежде чем копировать флаги.

Ошибки в `errno`. TCP `read` 0 значит, что партнёр закрыл. `EAGAIN` значит неблокирующий и не готов.

Этот раздел — интерфейс ОС. Форматы пакетов, маршрутизация и детали DNS принадлежат `net.topics.md`.

## TCP/UDP в ядре

Ядро владеет конечными автоматами TCP и UDP. Ваш процесс не шлёт сырые сегменты, если использует API сокетов. Ядро строит заголовки, считает контрольные суммы (или выгружает их) и ставит пакеты в очередь на устройство.

TCP в ядре:

- таблица соединений с ключом локальный и удалённый адрес и порт
- номера последовательности, подтверждения, таймеры повторной передачи
- буфер отправки и буфер приёма (`SO_SNDBUF`, `SO_RCVBUF`)
- управление перегрузкой (алгоритм — модуль ядра или выбор sysctl)
- `TIME_WAIT` после активного закрытия

`write` на сокете TCP копирует байты в буфер отправки (или блокируется). Ядро сегментирует позже. `read` копирует из буфера приёма. Правила блокировки темы 8 применяются.

UDP в ядре:

- нет состояния соединения в смысле TCP (соединённые сокеты UDP всё равно только кэшируют партнёра)
- дейтаграммы; `recv` — одна дейтаграмма (усечение возможно)
- нет повторной передачи
- контрольные суммы; ядро или NIC могут отбросить плохой пакет

Таблица маршрутизации ядра выбирает выходной интерфейс. Таблица соседей (ARP или NDP) находит следующий MAC. Драйверы и DMA (тема 8) шлют кадр. Входящие пакеты идут обратным путём: драйвер, IP, TCP/UDP, очередь сокета, разбудить процесс.

`netstat` и `ss` показывают сокеты и некоторые состояния TCP. `/proc/net/tcp` и `/proc/net/udp` — старые текстовые таблицы.

Вы не реализуете TCP в этой теме. Вы изучаете, что состояние живёт в ядре и что `ss` его показывает. `net.topics.md` покрывает рукопожатие, окно и перегрузку в деталях протокола.

## Пространства имён сети

Пространство имён сети — пространство имён Linux (тема 10) для сетевого стека. У каждого пространства имён свои:

- сетевые интерфейсы (кроме того, что физические устройства сидят в одном пространстве имён за раз)
- адреса IPv4 и IPv6
- таблица маршрутизации
- таблицы iptables или nftables
- сокеты (порт прослушивания в пространстве имён A — не порт в пространстве имён B)

Начальное пространство имён — пространство имён хоста. `ip netns` создаёт именованное пространство имён. Среда контейнера по умолчанию создаёт пространство имён сети на контейнер.

Пара `veth` — частая связь: один конец в пространстве имён контейнера, один конец на хосте или в пространстве имён моста. Хост делает NAT или маршрутизирует наружу. Тема 10 назвала пространство имён. Этот раздел называет копию стека.

`ip netns exec <name> ss -l` показывает сокеты внутри этого пространства имён. `nsenter -n` — другой способ войти.

Цикл `lo` есть в каждом пространстве имён. Вы должны его поднять (`ip link set lo up`), иначе `127.0.0.1` внутри не работает.

Пространства имён сети изолируют виды. Они сами по себе не заменяют политику межсетевого экрана. Контейнер с `--network host` делит пространство имён хоста. Этот режим — более слабая изоляция.

Не удаляйте интерфейсы хоста в лаборатории на общей машине. Используйте ВМ.

## iptables / nftables (знакомство)

Фильтры пакетов Linux сидят в каркасе netfilter ядра. Администраторы пишут правила, которые сопоставляют пакеты, затем принимают, отбрасывают, отвергают или меняют их (NAT).

`iptables` — старый пользовательский инструмент и старые имена таблиц (`filter`, `nat`, `mangle`). Многие скрипты всё ещё его используют. `iptables` может быть фронтендом над nftables в текущих дистрибутивах.

`nftables` — текущий каркас. Пользовательский инструмент — `nft`. Один набор правил может заменить несколько таблиц iptables. Синтаксис другой. Понятия остаются: хуки (вход, выход, пересылка), совпадения и вердикты.

Правила знакомства для этого пути:

- Фильтры работают в ядре. Процессный `connect` может упасть, потому что правило отбрасывает пакет. `errno` может быть таймаутом, не «iptables сказал нет» в API сокетов.
- Контейнерные и облачные системы добавляют много правил. Не сбрасывайте таблицы на общем хосте (`iptables -F`).
- `ss` показывает сокеты. `iptables -L` или `nft list ruleset` показывают фильтры (нужны права).
- NAT (исходный NAT, пересылка порта) — работа таблицы фильтров, не API сокетов. `net.topics.md` покрывает NAT в пути протокола.

Вы не пишете здесь промышленный межсетевой экран. Вы изучаете, что у ОС есть фильтр пакетов и что это не API сокетов.

`nft` и `iptables` нуждаются в `CAP_NET_ADMIN` или root. Наименьшие привилегии (тема 11) применяются.

## Полный путь протокола в `net.topics.md`

Эта тема ОС останавливается на интерфейсе ядра. Учебный путь сети в `net.topics.md` покрывает историю протокола по порядку:

- слои и инкапсуляция
- Ethernet, MAC, ARP
- адреса IPv4 и IPv6
- маршрутизация, ICMP, NAT
- поведение UDP и TCP (рукопожатие, окно, перегрузка)
- HTTP и TLS
- DNS и больше

Используйте эту тему ОС, когда пишете `socket` и когда отлаживаете `ss`, пространства имён и фильтры. Используйте `net.topics.md`, когда спрашиваете, зачем нужна контрольная сумма, как трёхстороннее рукопожатие выглядит на проводе или как маршрутизируется префикс.

Спаривайте пути:

- API сокетов ОС + глава TCP сети
- пространства имён сети ОС + адресация и маршрутизация сети
- знакомство с iptables ОС + NAT и промежуточные устройства сети
- `strace` ОС на `connect` + захват пакетов сети

Не ждите, что этот файл научит CIDR или TLS. Не ждите, что `net.topics.md` научит `task_struct` или таблицы страниц.

Лаборатория, которой нужны оба: напишите клиент TCP (эта тема), захватите рукопожатие через `tcpdump` (`net.topics.md`).

1. Объедините `epoll` (тема 8) и TCP (эта тема) в маленьком эхо для нескольких клиентов. Напишите проект цикла событий из шести строк.
2. В ВМ поместите сервер в пространство имён сети и соединитесь с хоста через veth. Запишите адреса. Оставшиеся вопросы протокола укажите на `net.topics.md`.

# 18. Безопасность

## Описание

Эта тема показывает, как контролировать, кто подключается, что они могут делать и как защищать данные в пути и в покое. Вы изучаете аутентификацию, авторизацию, наименьшие привилегии, секреты, TLS, шифрование в покое, инъекцию, широкие выдачи прав и открытые порты администрирования.

Используйте один термин для каждого понятия. Аутентификация доказывает личность. Авторизация выдаёт права этой личности. Секрет — пароль, токен или ключ, который нельзя публиковать. Завершите эту тему после того, как умеете подключаться драйвером и писать параметризованный SQL. Безопасность — свойство всего пути, не одного поля пароля.

Этот путь нейтрален к вендорам. Имена привилегий отличаются. Правила — нет.

## Аутентификация и авторизация

Аутентификация отвечает «кто эта сессия?» СУБД проверяет имя пользователя и учётные данные (пароль, сертификат, токен или внешний каталог). Неудачная аутентификация не начинает сессию.

Авторизация отвечает «что может делать эта сессия?» СУБД проверяет привилегии: подключиться, читать таблицу, писать таблицу, создавать объекты, управлять ролями.

```text
Connect request --> authenticate --> session identity
SQL statement   --> authorize    --> allow or reject
```

Верный пароль без привилегии `SELECT` всё равно валит `SELECT`. `GRANT` без успешного входа никогда не применяется.

Типичные личности:

- человек-администратор
- пользователь приложения
- репортёр только для чтения
- пользователь миграции (смена схемы)

Не делите одного пользователя на все эти работы. Нельзя отозвать утекший пароль приложения, не заблокировав также администратора. Нельзя аудировать, кто изменил строку, если каждая программа использует `postgres` или `sa`.

Методы аутентификации отличаются: пароль, peer/socket, LDAP, сертификат. Используйте сильный метод на сетях, которым не полностью доверяете. Аутентификация `trust` (любой подключающийся принят) только для закрытой лаборатории.

Не путайте вход в операционную систему со входом в СУБД. Они могут отображаться, но это не одна проверка, если вы не настроили это отображение.

Журналируйте неудачи аутентификации. Много неудач с одного хоста могут быть атакой или плохой строкой подключения.

## Роли наименьших привилегий

Наименьшие привилегии значат, что у роли только права, которые ей нужны. Пользователь приложения может `SELECT`, `INSERT`, `UPDATE` и `DELETE` на таблицах, которые использует приложение. Он не может `DROP TABLE` в продакшене. Он не может читать `pg_authid` или другие каталоги паролей, если можете это предотвратить.

Роль — именованный набор привилегий. Пользователи — роли, которые могут войти (модель продукта отличается). Вы выдаёте роль пользователю. Вы меняете роль один раз. Все члены получают изменение.

```sql
-- Shape only; verbs and names differ by product
GRANT SELECT, INSERT, UPDATE, DELETE ON orders TO app_shop;
REVOKE DELETE ON invoices FROM app_shop;
```

Начинайте с нуля. Выдавайте то, что нужно программе. Не выдавайте `SUPERUSER`, `DBA` или `sysadmin` приложению.

Владельцы объектов и значения по умолчанию `PUBLIC` важны. Некоторые продукты выдают широкие права `PUBLIC`. Отзывайте эти права на чувствительных объектах. Читайте ACL по умолчанию.

Миграциям нужен более сильный пользователь. Выполняйте миграции как этот пользователь. Приложение не использует этого пользователя во время выполнения.

Роли только для чтения не должны писать. Реплике отчёта всё ещё нужен пользователь, который не может `DELETE`.

Не выдавайте `SELECT` на все таблицы, если приложению нужны только пять таблиц. Не используйте одну роль записи для инструмента стажёра и для платежей.

Просматривайте выдачи, когда добавляете таблицу. Новая таблица может унаследовать слишком широкие значения по умолчанию. Выдавайте явно.

## Секреты для строк подключения

Строка подключения часто содержит пароль. Этот пароль — секрет. Секрет в репозитории Git, журнале чата или образе контейнера — утечка.

Правила:

1. Храните секреты в переменной окружения, менеджере секретов или файле с жёсткими правами. Не храните их в исходниках.
2. Используйте другой пароль в разработке, тесте и продакшене.
3. Ротируйте утекший пароль. Ротируйте по расписанию, если политика требует.
4. Не печатайте строку подключения в журналах. Драйверы могут журналировать URI. Выключите это или редактируйте.
5. Предпочитайте URI без пароля плюс отдельное поле пароля, которое процесс читает при старте.

```text
# Environment (example names)
DATABASE_HOST=127.0.0.1
DATABASE_USER=app_shop
DATABASE_PASSWORD=...   # from a secret store, not from the repo
```

Сертификаты и токены API тоже секреты. Считайте клиентский ключ TLS как пароль.

Файлы `.env` помогают локальной работе. Не коммитьте `.env`. Добавьте `.env` в файл игнорирования. Закоммиченный `.env.example` содержит только заполнители.

Метаданные облака и переменные CI утекают, если выдаёте широкую роль конвейеру. Используйте короткоживущие учётные данные, когда платформа их предлагает.

Если секрет утёк, смените его. Утечка в старом коммите остаётся в истории Git. Ротируйте. Считайте репозиторий публичным с этого момента.

Не шлите продакшен-строки подключения по почте. Не кладите их в тело тикета.

## Шифрование в пути (TLS)

TLS шифрует сетевые байты между клиентом и СУБД. Наблюдатель в сети не может прочитать текст SQL или строки. TLS также аутентифицирует сервер, когда клиент проверяет сертификат.

Без TLS на недоверенной сети захват пакетов может показать пароли и персональные данные. «Порт в частной VLAN» снижает риск. Он не шифрует. Операторы и неверно направленный пакет всё ещё могут видеть открытый текст.

```text
Client --TLS--> DBMS
         ^
   verify server certificate
```

Режимы (имена отличаются):

- disable: нет TLS
- allow/prefer: может использовать TLS, может откатиться к открытому тексту
- require: TLS, но клиент может пропустить полные проверки сертификата
- verify-ca / verify-full: TLS плюс проверки сертификата (имя хоста)

Используйте verify-full (или эквивалент продукта) в продакшене. Режим `require` без проверок имени всё ещё может принять другой сервер.

Установите сертификат на СУБД, который принимает хранилище доверия клиента. Самоподписанным сертификатам нужен явный CA в клиенте. Не ставьте «пропустить проверку» в продакшене, чтобы заглушить ошибку.

TLS не заменяет аутентификацию. TLS не заменяет выдачи. TLS не шифрует файлы данных на диске.

Внутренние сети всё ещё выигрывают от TLS. Многие инциденты начинаются внутри сети.

Не открывайте порт СУБД в публичный интернет даже с TLS. TLS не файрвол.

## Шифрование в покое (высокий уровень)

Шифрование в покое защищает файлы данных и резервы, когда кто-то получает диск или файл резерва. Байты на томе — шифротекст без ключа.

Слои (можно использовать больше одного):

| Слой | Что шифрует | Кто держит ключ |
| --- | --- | --- |
| Полный диск или том | Весь том | ОС или облачный KMS |
| Табличное пространство или TDE | Файлы базы | СУБД плюс KMS |
| Шифрование резерва | Файлы дампа или снимка | Инструмент резерва плюс KMS |
| Шифрование поля приложения | Выбранные столбцы | Приложение |

Шифрование тома — обычный первый шаг в облачной ВМ. Если злоумышленник получает работающий сервер и смонтированный том, ОС уже расшифровала диск. Шифрование тома помогает, когда диск отсоединён или украден.

Прозрачное шифрование данных (`TDE`) или эквивалент шифрует файлы, которые пишет СУБД. СУБД расшифровывает страницы для сессии, которой разрешено читать. Злоумышленнику только с файлами всё ещё нужен ключ.

Шифрование столбца в приложении скрывает значения от СУБД и от многих администраторов. Вы теряете обычный `WHERE` и индексы по открытому тексту, если не проектируете ищущее шифрование. Используйте его для немногих высокочувствительных полей.

Ключи — секреты. Ключ на том же диске, что данные, — слабый проект. Используйте службу управления ключами. Ротируйте ключи по процедуре продукта.

Шифрование в покое не скрывает данные от подключённого пользователя приложения. Выдачи и аутентификация всё ещё применяются.

Не считайте «у нас шифрование диска» полной политикой резерва. Шифруйте и резервы. Храните ключ вдали от файлов резерва.

## Инъекция, слишком широкие выдачи, открытые порты администрирования

Три обычных сбоя появляются вместе в инцидентах.

**Инъекция.** Приложение строит SQL из недоверенного текста. Злоумышленник выполняет SQL как пользователь приложения. Параметризованные операторы предотвращают инъекцию значений. Наименьшие привилегии ограничивают ущерб, если инъекция всё ещё происходит. Пользователь приложения без `DROP` не может удалить таблицы через инъекцию.

**Слишком широкие выдачи.** `GRANT ALL` или суперпользователь приложения превращает любую ошибку в полный контроль. Утекший пароль становится полным дампом. Просматривайте выдачи. Отзывайте неиспользуемые права.

**Открытые порты администрирования.** Адрес прослушивания СУБД — `0.0.0.0` на публичном IP. Сканеры находят порт. Они пробуют пароли. Они пробуют старые ошибки. Привязывайте к localhost или к частной сети. Используйте файрвол. Используйте VPN или бастион для инструментов администрирования. Не публикуйте `5432`, `3306` или порты UI администрирования вендора в интернет.

```text
Public internet --x--> DBMS port
Admin --> VPN / bastion --> DBMS
App   --> private net   --> DBMS
```

Также закрывайте неиспользуемые расширения и неиспользуемые языки, если продукт позволяет. Убирайте образцовых пользователей и пароли по умолчанию.

Защита слоями:

1. Нет публичного порта СУБД
2. TLS с проверкой

4. Наименьшие привилегии
5. Параметризованный SQL
6. Шифрование в покое для дисков и резервов

Не полагайтесь на один слой. Не тестируйте инъекцию на системах, которыми не владеете.

### Вопросы

#### Теоретические вопросы

1. Как наименьшие привилегии снижают эффект SQL-инъекции?
2. Почему `GRANT ALL` приложению — находка высокой серьёзности?
3. Почему порт СУБД не должен слушать на публичном адресе?
4. Какой путь должен использовать инструмент администрирования вместо публичного порта?
5. Почему нужно больше одного из шести слоёв?

#### Простые практические задания

1. Напишите шесть слоёв как чеклист.
2. Найдите настройку адреса прослушивания в вашей СУБД. Напишите учебное значение (`localhost`) и запрещённое значение для ноутбука в кафе Wi-Fi.
3. Перечислите порты по умолчанию для двух продуктов СУБД. Пометьте их как «не публиковать».
4. Напишите один `REVOKE`, который применили бы после ошибки `GRANT ALL` (на одноразовой базе).

#### Средние практические задания

1. Подтвердите, что учебная СУБД недоступна с другой машины. Если доступна, привяжите к localhost или добавьте правило файрвола, которое понимаете.
2. Сочетайте параметризованный запрос с пользователем, который не может `DROP`. Напишите, как попытка инъекции не смогла бы удалить таблицу.
3. Найдите публичное предупреждение про открытый порт базы. Напишите пять предложений своими словами. Не копируйте предупреждение.

#### Сложные практические задания

1. Напишите руководство по ужесточению на одну страницу для маленького продакшен-магазина: привязка, файрвол, TLS, роли, секреты, шифрование резерва.
2. Просмотрите файл compose или группу безопасности облака. Перечислите каждый открытый порт. Закройте или обоснуйте каждый. Запишите изменение в одноразовой среде.

## Обзор темы

Эти вопросы не повторяют вопросы разделов выше. Они покрывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Как аутентификация, авторизация и TLS падают независимо на одной строке подключения?
2. Когда утечка секрета становится полным нарушением данных только потому, что выдачи были слишком широки?
3. Как шифрование в пути и шифрование в покое покрывают разных злоумышленников?
4. Какие контроли останавливают инъекцию и какие контроли только ограничивают радиус взрыва?
5. Коллега кладёт URI администратора в приложение, открывает порт 5432 на `0.0.0.0` и отключает TLS в «частной» облачной подсети. Какие факты вы используете в ответе?

#### Простые практические задания

1. Напишите шпаргалку: authn против authz, наименьшие привилегии, секреты, TLS, в покое, три обычных сбоя.
2. Создайте пользователя не-администратора. Подключитесь. Выполните `SELECT 1`. Покажите, что `DROP DATABASE` падает.
3. Отредактируйте образцовый URI для README. Оставьте хост и имя базы. Уберите пароль.
4. Напишите адрес прослушивания и режим TLS учебного экземпляра.

#### Средние практические задания

1. Постройте мини-пользователя приложения: пароль из окружения, выдачи только на двух таблицах, TLS если доступен, параметризованный SQL.
2. Напишите таблицу угроз: украденный диск ноутбука, захват пакетов, утекший пароль Git, SQL-инъекция. Сопоставьте по одному контролю.
3. Выполните обзор привилегий на базе `learn`. Произведите список выдач и план отзыва.

#### Сложные практические задания

1. Напишите обзор безопасности маленького проекта против этой темы. Разложите находки по серьёзности. Исправьте те, которыми владеете.
2. Спроектируйте продакшен-контроли для схемы платежей: роли, секреты, TLS verify-full, зашифрованные резервы, нет публичного порта. Нарисуйте сеть.

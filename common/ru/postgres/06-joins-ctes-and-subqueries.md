# 6. Соединения, CTE и подзапросы

## Описание

Эта тема показывает, как объединять строки в PostgreSQL 16 и PostgreSQL 17. Вы узнаёте внутренние, внешние и декартовы соединения. Узнаёте `WITH` (общие табличные выражения), рекурсивные запросы, `LATERAL` и `DISTINCT ON`.

Сначала завершите тему 5. Нужны таблицы с внешними ключами. Завершите эту тему до изучения функций и индексов.

Используйте один термин для каждого понятия. Соединение объединяет строки из двух таблиц. CTE — именованный подзапрос в предложении `WITH`. Рекурсивный CTE может читать свой собственный вывод. Боковое соединение позволяет правой стороне использовать столбцы левой. `DISTINCT ON` оставляет первую строку каждой группы в текущем порядке сортировки.

## Внутренние / внешние / декартовы соединения

**Внутреннее соединение** возвращает строки, которые совпадают с условием соединения.

```sql
SELECT c.email, o.id AS order_id
FROM customers AS c
INNER JOIN orders AS o ON o.customer_id = c.id;
```

`JOIN` без слова — внутреннее соединение. Когда учите, пишите `INNER JOIN`.

**Левое внешнее соединение** возвращает каждую строку левой таблицы. Когда совпадения нет, правые столбцы — `NULL`.

```sql
SELECT c.email, o.id AS order_id
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id;
```

**Правое внешнее соединение** возвращает каждую строку правой таблицы. **Полное внешнее соединение** возвращает каждую строку с обеих сторон.

```sql
SELECT *
FROM customers AS c
FULL JOIN orders AS o ON o.customer_id = c.id;
```

**Декартово соединение** — декартово произведение. Каждая левая строка сочетается с каждой правой. Предложения `ON` нет.

```sql
SELECT *
FROM sizes
CROSS JOIN colors;
```

Используйте декартово соединение только когда нужны все пары (пример: размер × цвет).

`USING (customer_id)` — короткая форма, когда у обоих столбцов одно имя. `NATURAL JOIN` сопоставляет все одноимённые столбцы. Не используйте `NATURAL JOIN`. Новый столбец может сменить соединение.

Фильтр в `ON` против `WHERE` для внешних соединений:

- `ON` решает совпадения
- `WHERE` по правому столбцу после `LEFT JOIN` может убрать несовпавшие левые строки и превратить соединение во внутреннее

```sql
-- keeps customers without orders
SELECT c.email, o.id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.id > 10;

-- removes customers with no matching order
SELECT c.email, o.id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id > 10;
```

Всегда пишите псевдонимы. Всегда пишите условие соединения. Не соединяйте без `ON`, если не имеете в виду `CROSS JOIN`.

## `WITH` (общие табличные выражения)

CTE именует запрос. Основной запрос читает это имя как таблицу.

```sql
WITH recent AS (
    SELECT id, customer_id, created_at
    FROM orders
    WHERE created_at >= DATE '2026-01-01'
)
SELECT c.email, r.id
FROM recent AS r
JOIN customers AS c ON c.id = r.customer_id;
```

Можно перечислить больше одного CTE. Разделяйте запятыми.

```sql
WITH
active_customers AS (
    SELECT id, email FROM customers WHERE email IS NOT NULL
),
order_counts AS (
    SELECT customer_id, count(*) AS n
    FROM orders
    GROUP BY customer_id
)
SELECT a.email, o.n
FROM active_customers AS a
JOIN order_counts AS o ON o.customer_id = a.id;
```

CTE может быть `INSERT`, `UPDATE` или `DELETE` с `RETURNING` (модифицирующий данные CTE):

```sql
WITH moved AS (
    DELETE FROM scratch
    WHERE done
    RETURNING *
)
INSERT INTO scratch_archive
SELECT * FROM moved;
```

В PostgreSQL 12 и новее планировщик может встраивать многие `SELECT` CTE. CTE не всегда забор оптимизации. Используйте `WITH cte AS MATERIALIZED (...)`, чтобы принудить материализацию. Используйте `NOT MATERIALIZED`, чтобы принудить встраивание.

Пишите CTE, когда запрос так проще читать. Пишите подзапрос, когда запрос короткий. Не вкладывайте пять CTE, которые нигде не переиспользуете.

Имя CTE скрывает настоящую таблицу с тем же именем внутри оператора. Используйте ясные имена.

## `WITH RECURSIVE` для деревьев

У рекурсивного CTE есть якорная часть и рекурсивная часть. Части стоят в `UNION` (или `UNION ALL`).

```sql
CREATE TABLE org (
    id        int PRIMARY KEY,
    parent_id int REFERENCES org (id),
    name      text NOT NULL
);

INSERT INTO org VALUES
    (1, NULL, 'HQ'),
    (2, 1, 'Engineering'),
    (3, 1, 'Sales'),
    (4, 2, 'Platform');

WITH RECURSIVE tree AS (
    SELECT id, parent_id, name, 1 AS depth
    FROM org
    WHERE parent_id IS NULL
    UNION ALL
    SELECT o.id, o.parent_id, o.name, t.depth + 1
    FROM org AS o
    JOIN tree AS t ON o.parent_id = t.id
)
SELECT * FROM tree
ORDER BY depth, id;
```

Якорь выбирает корни. Рекурсивная часть соединяет базовую таблицу с CTE. PostgreSQL повторяет рекурсивную часть, пока она не вернёт ни одной строки.

Используйте `UNION ALL`, когда дубликаты отбрасывать не нужно. Используйте `UNION`, когда дубликаты нужно отбросить. Циклы требуют дополнительной осторожности. Держите массив пути и останавливайтесь, когда `id` уже в пути:

```sql
WITH RECURSIVE tree AS (
    SELECT id, parent_id, name, ARRAY[id] AS path
    FROM org
    WHERE id = 1
    UNION ALL
    SELECT o.id, o.parent_id, o.name, t.path || o.id
    FROM org AS o
    JOIN tree AS t ON o.parent_id = t.id
    WHERE o.id <> ALL (t.path)
)
SELECT * FROM tree;
```

В текущем PostgreSQL есть предложения `SEARCH` и `CYCLE` (обнаружение циклов по стандарту SQL). Их можно использовать вместо массива пути, собранного вручную. См. официальную документацию `WITH`.

Не рекурсируйте без условия остановки. Цикл без защиты может работать, пока сервер не упрётся в лимит стека, таймаут оператора или отмену.

Рекурсивные CTE также генерируют числовые ряды. Для простых диапазонов предпочитайте `generate_series`.

## Боковые соединения (`LEFT JOIN LATERAL`)

Обычное соединение не может использовать столбец левой строки внутри подзапроса правой стороны в списке `FROM`. `LATERAL` это позволяет.

```sql
SELECT c.id, c.email, last_order.id, last_order.created_at
FROM customers AS c
LEFT JOIN LATERAL (
    SELECT o.id, o.created_at
    FROM orders AS o
    WHERE o.customer_id = c.id
    ORDER BY o.created_at DESC
    LIMIT 1
) AS last_order ON true;
```

Для каждого клиента подзапрос читает этот `c.id` и возвращает последний заказ. `LEFT JOIN LATERAL` оставляет клиентов без заказа. Столбцы `last_order` для этих клиентов — `NULL`.

`ON true` обычно, когда боковой подзапрос уже фильтрует. Для `LEFT JOIN` предложение условия соединения всё равно нужно.

`CROSS JOIN LATERAL` — внутренняя форма. Она отбрасывает левые строки, когда подзапрос не возвращает строку.

```sql
SELECT c.email, s.n
FROM customers AS c
CROSS JOIN LATERAL (
    SELECT count(*) AS n
    FROM orders o
    WHERE o.customer_id = c.id
) AS s;
```

Функции, возвращающие множество, в `FROM` неявно боковые:

```sql
SELECT u.id, u.tag
FROM users AS u
CROSS JOIN LATERAL unnest(u.tags) AS tag;
```

Можно писать `FROM users u, unnest(u.tags) AS tag`. Форма с запятой — неявное декартово соединение. Для ясности предпочитайте `JOIN LATERAL`.

Используйте `LATERAL` для «top N на группу» с `LIMIT`. Оконные функции — другой метод (тема 20). `DISTINCT ON` — третий метод (следующий раздел).

Боковой подзапрос, который запускает тяжёлый запрос на каждую левую строку, может быть медленным. Смотрите `EXPLAIN`. Соединение плюс оконная функция на больших наборах может быть быстрее.

## Distinct on (`DISTINCT ON`) — специфика PostgreSQL

`DISTINCT ON (expr [, ...])` оставляет первую строку каждого различного значения выражений. «Первая» следует `ORDER BY`.

```sql
SELECT DISTINCT ON (customer_id)
    customer_id, id, created_at
FROM orders
ORDER BY customer_id, created_at DESC;
```

Это возвращает одну строку на `customer_id`: с последним `created_at`. `ORDER BY` должен начинаться с тех же выражений, что `DISTINCT ON`, в том же порядке. Затем добавляете дополнительные ключи сортировки (`created_at DESC`).

Правила:

- `DISTINCT ON` — расширение PostgreSQL. Его нет в стандарте SQL.
- `DISTINCT` без `ON` отбрасывает полные дубликаты строк. Это другое.
- Без подходящего `ORDER BY` выбранная строка не определена.
- `SELECT DISTINCT ON (a) b` может вернуть любой `b` для этого `a`, если `ORDER BY` не фиксирует `b`.

Перепишите через оконную функцию, когда нужен стандартный SQL:

```sql
SELECT customer_id, id, created_at
FROM (
    SELECT
        customer_id, id, created_at,
        row_number() OVER (
            PARTITION BY customer_id
            ORDER BY created_at DESC
        ) AS rn
    FROM orders
) AS s
WHERE rn = 1;
```

Используйте `DISTINCT ON` для коротких ясных запросов PostgreSQL. Используйте оконную форму, когда тот же SQL должен работать на другом продукте.

`DISTINCT ON` может использовать индекс, который совпадает с `ORDER BY`. Тема 9 показывает, как читать план.

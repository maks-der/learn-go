# 2. Документы и BSON

## Описание

MongoDB хранит каждый документ как BSON. BSON — Binary JSON. Эта тема показывает, чем JSON отличается от BSON, какой размер может иметь документ, какие типы полей использовать и как работает `_id`. Завершите эту тему до того, как писать команды CRUD.

Используйте один термин для каждого понятия. **JSON** — текстовый формат. **BSON** — формат хранения. **Поле** — имя и значение в документе. **ObjectId** — тип `_id` по умолчанию. Хранение без схемы не значит, что у приложения нет схемы.

---

## JSON и BSON

JSON — текстовый формат для объектов, массивов, строк, чисел, булевых значений и null. Люди читают JSON. Многие API отправляют JSON.

BSON — двоичная кодировка. MongoDB использует BSON на диске и по сети. BSON включает байт типа и длину для каждого значения. Сервер не разбирает текст JSON для каждого хранимого документа.

У BSON есть типы, которых нет в JSON. Примеры: ObjectId, Date, Binary, Decimal128, Timestamp, Regular Expression. `mongosh` печатает эти типы как extended JSON. Extended JSON использует обёртки вроде `{ "$oid": "..." }` и `{ "$date": "..." }`.

Число JSON не полностью совпадает с числами BSON. В BSON есть 32-битные целые, 64-битные целые и 64-битные числа с плавающей точкой. В JSON один синтаксис числа. Драйверы сопоставляют числа языка типам BSON. Для десятичных денежных сумм нужен `Decimal128`, а не двоичный float.

BSON не заменяет JSON в каждом API. Приложение по-прежнему может отправлять JSON клиентам. Драйвер преобразует объекты языка, JSON и BSON.

Не редактируйте сырой BSON вручную. Используйте оболочку, драйвер или инструмент.

## Лимит размера документа (16 MB)

Один документ MongoDB имеет максимальный размер 16 мегабайт. Это жёсткий лимит одного документа. Лимит включает накладные расходы BSON, а не только текст, который вы набираете.

Лимит защищает сервер и клиент. Очень большой документ дорого читать, писать и кэшировать. Документ, который растёт без границы, упрётся в лимит.

Не храните большие файлы как один документ. Для больших файлов используйте GridFS или объектное хранилище. Не кладите неограниченный поток событий в один массив одного документа.

Если документ близок к лимиту, измените модель. Разделите данные. Используйте ссылки. Для временных рядов используйте шаблон bucket. Эти решения — в следующих темах.

`Object.bsonsize(doc)` в `mongosh` возвращает размер BSON в байтах для документа в памяти. Используйте это при проверке роста.

Лимит 16 MB — не лимит коллекции. Коллекция может хранить много документов. Лимит 16 MB — не лимит набора результатов. Курсор возвращает пакеты.

## Типы полей: string, number, bool, date, objectId, array, embedded document, null, binary

Частые типы полей BSON:

- **String.** Текст UTF-8. Строки — для имён, кодов и токенов.
- **Number.** Целое или double. В `mongosh` используйте `NumberInt`, `NumberLong` или обычное число. Для точных десятичных — `NumberDecimal`.
- **Bool.** `true` или `false`.
- **Date.** Дата-время UTC. В `mongosh` используйте `ISODate("2026-01-15T12:00:00Z")`. Не храните даты как локальные строки, если нужно сортировать их как время.
- **ObjectId.** Идентификатор на 12 байт. См. следующий раздел.
- **Array.** Упорядоченный список значений. Типы значений могут быть разными. По возможности держите в массиве один тип.
- **Embedded document.** Вложенный объект. Пример: `address: { city: "Oslo", zip: "0001" }`.
- **Null.** Отсутствующее значение. Null — не то же самое, что отсутствующее поле. Запрос на null может совпасть с обоими, если не написать более строгий запрос.
- **Binary.** Сырые байты. Binary — для небольших блобов. Не используйте binary для больших файлов.

Есть и другие типы: Regular Expression, JavaScript, Timestamp, MinKey, MaxKey. В документах приложения они встречаются реже.

Тип важен для запросов и индексов. Число `1` и строка `"1"` не равны. Date и строка ISO-даты — разные типы.

Выберите тип для каждого поля и держите его. Валидация — в следующих темах.

## `_id` и ObjectId

У каждого документа есть `_id`. `_id` уникален в коллекции. MongoDB создаёт индекс по `_id`. Этот индекс нельзя удалить.

Если при вставке `_id` опустить, драйвер или сервер добавит ObjectId. Можно задать `_id` другого типа. Команды часто используют ObjectId, строку UUID или естественный ключ. Значение должно быть уникальным. Значение должно быть стабильным.

ObjectId — 12 байт:

- Метка времени в секундах
- Случайное значение
- Счётчик

Часть с меткой времени позволяет грубо сортировать по времени вставки. Не считайте ObjectId строгими часами для всех узлов. Часы могут расходиться.

`mongosh` показывает ObjectId как `ObjectId("...")`. Шестнадцатеричная строка — 24 символа.

На практике `_id` неизменяем. `_id` не меняют через `$set`. Чтобы использовать новый `_id`, вставляют новый документ и удаляют старый.

Не используйте большой вложенный документ как `_id`. Держите `_id` маленьким. Индекс `_id` хранит ключ.

## Schema-less не значит schema-free (у приложения всё равно есть схема)

MongoDB не требует схему при создании коллекции. Можно вставить `{ a: 1 }` и `{ b: "x" }` в одну коллекцию. Это поведение — **хранение без схемы** (schema-less storage).

У приложения всё равно есть схема. Приложение ждёт имена полей. Приложение ждёт типы. Приложение ждёт массивы или вложенные документы известной формы. Если форма меняется без плана, запросы ломаются. Индексы тратят место. Валидация позже падает.

**Schema-free** значило бы, что формой никто не владеет. Так рабочая система не живёт. Схемой кто-то владеет: приложение, файл схемы или валидатор на коллекции.

Хорошая практика:

- Опишите форму документа для каждой коллекции.
- Используйте стабильные имена полей.
- Используйте один тип на поле.
- Добавьте поле `schemaVersion`, когда форма должна измениться (следующая тема).
- Добавьте валидацию JSON Schema, когда коллекция достаточно стабильна (следующая тема).

Гибкая схема — инструмент. Она помогает при изменении. Это не повод пропускать проектирование.

# 6. Транзакции и MVCC

## Описание

Эта тема показывает транзакции и конкурентный доступ в PostgreSQL 16 и PostgreSQL 17. Вы узнаёте, почему читатели не блокируют писателей, уровни изоляции, блокировки строк, консультативные блокировки, взаимные блокировки и снимки.

Сначала завершите тему 5. Вы умеете читать планы. Завершите эту тему до изучения vacuum.

Используйте один термин для каждого понятия. Транзакция — группа операторов, которые фиксируются или откатываются вместе. Изоляция — насколько одна транзакция видит другую. Снимок — набор транзакций, которые видны. Блокировка ждёт или падает, когда другая сессия держит конфликтующую блокировку. MVCC значит Multi-Version Concurrency Control. Уровень изоляции по умолчанию — read committed.

## Читатели не блокируют писателей

PostgreSQL хранит больше одной версии строки. `UPDATE` пишет новый кортеж и помечает старый как мёртвый. `DELETE` помечает кортеж как мёртвый. `SELECT` использует снимок. `SELECT` читает версию, видимую этому снимку. Он не ждёт писателя, который меняет другую версию.

Начать и закончить транзакцию:

```sql
BEGIN;
UPDATE items SET qty = qty + 1 WHERE id = 1;
COMMIT;
-- или ROLLBACK;
```

Один оператор вне `BEGIN` всё равно транзакция. Он фиксируется, когда успешен.

Правила, которые новичок должен помнить:

- Обычный `SELECT` не берёт блокировку строки.
- Обычный `SELECT` не ждёт `UPDATE` или `DELETE` той же строки.
- `UPDATE` ждёт другой `UPDATE` (или `SELECT FOR UPDATE`) той же строки.
- Мёртвые кортежи остаются до `VACUUM` (тема 7).

У каждого кортежа есть скрытые системные столбцы. Часть можно выбрать:

```sql
SELECT xmin, xmax, ctid, * FROM items WHERE id = 1;
```

`xmin` — id вставляющей транзакции (отображение 32-битного xid). `ctid` — физическое расположение `(page, offset)`. После `UPDATE` `ctid` меняется. Логический `id` остаётся тем же.

Потому что читатели не блокируют писателей, PostgreSQL может обслуживать много чтений во время записей. Писатели всё ещё конфликтуют с писателями на той же строке.

`INSERT` нового ключа не ждёт `SELECT`. Уникальные индексы всё равно заставляют двух вставляющих один ключ сериализоваться.

MVCC — не то же самое, что «без блокировок». DDL берёт более сильные блокировки. `SELECT FOR UPDATE` берёт блокировки строк. Внешние ключи берут блокировки.

Не используйте `SELECT` как блокировку. Если нужно остановить другого писателя, используйте `SELECT ... FOR UPDATE` или `UPDATE`. Не держите `BEGIN` открытым часами на занятой базе.

## Уровни изоляции; по умолчанию read committed

SQL определяет уровни изоляции. PostgreSQL реализует:

| Уровень | Поведение PostgreSQL |
| --- | --- |
| `READ UNCOMMITTED` | То же, что `READ COMMITTED`. Грязных чтений нет. |
| `READ COMMITTED` | По умолчанию. Каждый оператор видит строки, зафиксированные до начала этого оператора. |
| `REPEATABLE READ` | Снимок с первого оператора. Поздние операторы той же транзакции видят тот же снимок. |
| `SERIALIZABLE` | Повторяемое чтение плюс проверки, которые предотвращают больше аномалий. Транзакция может упасть с ошибкой сериализации. |

Задать уровень:

```sql
BEGIN TRANSACTION ISOLATION LEVEL READ COMMITTED;
-- операторы
COMMIT;

BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

`default_transaction_isolation` — `read committed`, если не сменить.

Факты **read committed**:

- Оператор 1 может видеть версию строки V1. После того как другая сессия зафиксирует обновление, оператор 2 в той же транзакции может видеть V2.
- Неповторяемые чтения возможны. Фантомные строки возможны.
- `UPDATE` находит последнюю зафиксированную версию и ждёт при необходимости. Затем заново оценивает `WHERE` на этой версии.

Большинство транзакционных приложений используют read committed. Это правильный default. Незафиксированные данные другой транзакции читать нельзя. Грязного чтения нет.

**Repeatable read** берёт снимок на первом запросе. Все поздние операторы `SELECT` видят этот снимок. Если вы `UPDATE` строку, которую другая транзакция зафиксировала после вашего снимка, PostgreSQL может поднять `could not serialize access due to concurrent update`. Откатываете и повторяете.

Repeatable read в PostgreSQL использует изоляцию снимков. Часть аномалий write-skew всё ещё возможна.

**Serializable** использует Serializable Snapshot Isolation (SSI). Если появляется опасный шаблон, одна транзакция падает с ошибкой сериализации (`SQLSTATE 40001`). Приложение должно повторить. Все сессии, которым нужна гарантия, должны использовать `SERIALIZABLE`.

```sql
SHOW transaction_isolation;
```

Используйте repeatable read для согласованных отчётов из многих операторов. Используйте serializable, когда бизнес-правило не может принять write skew и вы напишете цикл повтора. Используйте read committed для большей части транзакционной работы.

Не поднимайте глобальный default до `serializable` без плана повторов. Не считайте, что `READ UNCOMMITTED` даёт грязные чтения. Не даёт. Не игнорируйте ошибки сериализации.

## `SELECT ... FOR UPDATE` и консультативные блокировки

`SELECT ... FOR UPDATE` блокирует выбранные строки. Другая сессия, которая хочет `UPDATE`, `DELETE` или `SELECT FOR UPDATE` этих строк, ждёт (или падает с `NOWAIT`).

```sql
BEGIN;
SELECT * FROM items WHERE id = 1 FOR UPDATE;
-- другие операторы
COMMIT;
```

Силы блокировок (самая сильная последняя среди этих четырёх):

- `FOR KEY SHARE` — разрешает обновления, которые не меняют ключ; используют внешние ключи
- `FOR SHARE` — разделяемая блокировка; блокирует `FOR UPDATE`
- `FOR NO KEY UPDATE` — как update, но не блокирует `KEY SHARE`
- `FOR UPDATE` — блокирует другие исключительные блокировки строк и обновления

Опции:

- `NOWAIT` — ошибка вместо ожидания
- `SKIP LOCKED` — пропустить уже заблокированные строки (очереди работ)
- `OF table` — блокировать строки одной таблицы в соединении

```sql
SELECT id FROM jobs
WHERE status = 'new'
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT 1;
```

Блокировка длится до конца транзакции. `COMMIT` или `ROLLBACK` её снимает. `FOR UPDATE` не блокирует всю таблицу.

Используйте блокировки строк, когда читаете значение и затем пишете решение (проверка баланса, захват задания). Не держите транзакцию открытой, пока ждёте пользователя в браузере.

Консультативные блокировки — блокировки, которые определяет приложение. PostgreSQL не привязывает их к строке таблицы. Передаёте целочисленные ключи.

Блокировки уровня сессии остаются, пока не снимете или сессия не закончится:

```sql
SELECT pg_advisory_lock(42);
-- работа
SELECT pg_advisory_unlock(42);
```

Блокировки уровня транзакции остаются до `COMMIT` или `ROLLBACK`:

```sql
BEGIN;
SELECT pg_advisory_xact_lock(42);
COMMIT;
```

`pg_try_advisory_lock` возвращает `false` вместо ожидания. Двухаргументные формы используют пару ключей `int4`.

Применения консультативных блокировок: одиночный cron-задание, ресурс, у которого ещё нет строки, работа, которая охватывает больше одной таблицы.

Смотреть блокировки:

```sql
SELECT * FROM pg_locks;
SELECT * FROM pg_stat_activity WHERE wait_event_type = 'Lock';
```

Не используйте консультативные блокировки вместо уникального ограничения. Не используйте их вместо `FOR UPDATE`, когда строка есть. У сессионных консультативных блокировок должно быть парное снятие на каждом пути.

## Взаимные блокировки

Взаимная блокировка случается, когда сессия A ждёт сессию B, а сессия B ждёт сессию A. PostgreSQL обнаруживает цикл. Он прерывает одну транзакцию:

```text
ERROR:  deadlock detected
```

Другая транзакция продолжается. Прерванная сессия должна повторить. `SQLSTATE` — `40P01`.

Типичная причина: две транзакции обновляют те же две строки в противоположном порядке.

```text
Session A: UPDATE t SET ... WHERE id = 1;
Session B: UPDATE t SET ... WHERE id = 2;
Session A: UPDATE t SET ... WHERE id = 2;  -- ждёт
Session B: UPDATE t SET ... WHERE id = 1;  -- взаимная блокировка
```

Предотвращение:

- Всегда обновляйте строки в одном порядке (пример: по `id`)
- Держите транзакции короткими
- Не держите блокировки, пока ждёте сеть

PostgreSQL пишет строку деталей, которая показывает два процесса. `log_lock_waits` и `deadlock_timeout` управляют журналом ожиданий. `deadlock_timeout` — как долго длится ожидание, прежде чем сервер проверит взаимную блокировку (по умолчанию `1s`).

```sql
SHOW deadlock_timeout;
SHOW log_lock_waits;
```

Журнал сервера (или `stderr` в Docker) содержит отчёт о взаимной блокировке. `psql` показывает ошибку клиенту, который проиграл.

Взаимная блокировка — не падение сервера. Это обычная ошибка при конкурентном доступе. Приложение повторяет.

Не поднимайте `deadlock_timeout`, чтобы спрятать баг порядка блокировок. Исправьте порядок.

## Снимки (осведомлённость)

Снимок говорит, какие id транзакций видны. В обычном SQL снимок вручную не задаёте. Его задают уровни изоляции.

Старые функции используют префикс `txid_`. В текущем PostgreSQL также есть функции `xid8`:

```sql
SELECT pg_current_xact_id();
SELECT pg_current_xact_id_if_assigned();
SELECT pg_current_snapshot();
SELECT pg_snapshot_xmin(pg_current_snapshot());
SELECT pg_snapshot_xmax(pg_current_snapshot());
```

Старые псевдонимы всё ещё есть (`txid_current()`, `txid_current_snapshot()`). В новой работе на PostgreSQL 16 и 17 предпочитайте имена `pg_current_*`.

`pg_current_xact_id()` назначает id транзакции, если у транзакции его ещё нет. Транзакция только для чтения может избежать xid, пока не пишет. Используйте `pg_current_xact_id_if_assigned()`, когда назначать нельзя.

У снимка есть `xmin`, `xmax` и список xid в процессе. Правила видимости используют эти значения. Полные правила не нужны, чтобы писать прикладной SQL. Нужно знать:

- Vacuum и wraparound используют xid (тема 7)
- `xmin` на кортеже — вставляющий xid
- Repeatable read и serializable замораживают видимость на одном снимке

```sql
SELECT xmin, xmax FROM items;
```

Долгая транзакция держит старый снимок. Vacuum не может удалить кортежи, которые этому снимку ещё нужны. Этот факт связывает тему с раздутием (тема 7).

Не используйте xid как прикладные ключи. Xid заворачиваются. Не сравнивайте xid как целые в коде приложения.

Этот раздел — осведомлённость. Xid снова встретите, когда изучите freeze и wraparound.

### Вопросы

#### Теоретические вопросы

1. Как MVCC, снимок и блокировка строки отвечают на три разных вопроса?
2. Почему read committed хватает для большинства прикладных записей?
3. Когда выбираете `FOR UPDATE SKIP LOCKED` вместо консультативной блокировки?
4. Чем повтор взаимной блокировки отличается от повтора сбоя сериализации?
5. Почему долгий снимок вредит позднему vacuum даже без взаимной блокировки?

#### Простые практические задания

1. Выполните один скрипт: `BEGIN`, `SELECT` с `xmin`/`ctid`, `UPDATE`, снова `SELECT`, `COMMIT`. Сохраните оба значения `ctid`.
2. Напишите шпаргалку: MVCC, четыре уровня изоляции, `FOR UPDATE`, консультативная блокировка, взаимная блокировка, снимок.
3. `SHOW` `transaction_isolation` и `deadlock_timeout`.
4. Нарисуйте двух писателей на одной строке и читателя на той же строке. Пометьте, кто ждёт.

#### Средние практические задания

1. Двумя сессиями покажите: читатель не ждёт, писатель ждёт, затем взаимная блокировка на двух id. Сохраните сообщения клиента.
2. Захватите задание через `FOR UPDATE SKIP LOCKED` и защитите cron через `pg_advisory_xact_lock` в тех же учебных заметках.
3. Сравните один и тот же отчётный запрос в read committed и repeatable read, пока вторая сессия пишет. Запишите два набора результатов.

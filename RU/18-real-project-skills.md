# 18. Навыки реального проекта

## Описание

Настоящая программа на Go — это больше, чем одна функция `main`. Нужно организовать пакеты, загрузить конфигурацию, писать логи, остановить процесс безопасно и отдать бинарный файл. Эта тема показывает обычные навыки проекта, которые команды используют после основ языка.

Команда Go не задаёт одно официальное дерево папок для приложений. Команды всё равно делят общие шаблоны. Используйте эти шаблоны, когда они помогают. Не копируйте большую раскладку для маленького инструмента.

## Структура проекта (`cmd/`, `internal/`, `pkg/`)

Официальные заметки о раскладке модуля: [https://go.dev/doc/modules/layout](https://go.dev/doc/modules/layout). Этот документ — руководство. Это не обязательный стандарт.

Типичный модуль приложения выглядит так:

- `go.mod` в корне модуля
- `cmd/appname/` для `package main`, который вы собираете и запускаете
- `internal/` для пакетов, которые другие модули не должны импортировать
- необязательный `pkg/` для пакетов, которые другие модули могут импортировать
- `api/`, `migrations/` или `docs/` для файлов, которые не являются пакетами Go

`cmd/` хранит команды. Каждый подкаталог — одна программа. Пример: `cmd/api` и `cmd/worker`. Имя каталога часто становится именем бинарного файла.

`internal/` — правило компилятора. Пакет вне родителя `internal` не может импортировать пакет из этого дерева `internal`. Используйте `internal/` для доступа к базе, конфигурации и другого закрытого кода.

`pkg/` — только соглашение. Компилятор не считает `pkg/` особым. Одни команды кладут в `pkg/` публичный библиотечный код. Другие кладут публичные пакеты в корень модуля. Оба варианта допустимы.

Держите первую версию модуля маленькой. Один пакет `main` в корне достаточен для крошечного инструмента. Добавьте `cmd/`, когда появятся две команды. Добавьте `internal/`, когда нужен закрытый пакет. Не создавайте пустые слои вроде `models/`, `utils/` и `helpers/` без ясной работы для каждого пакета.

Называйте пакеты по тому, что они дают. Имя пакета — последний элемент пути импорта. Предпочитайте `store`, а не `storepkg`. Предпочитайте `httpapi`, а не `helpers`.

## Конфигурация: переменные окружения, файлы и twelve-factor

Конфигурация — данные, которые меняются между окружениями. Примеры: адрес прослушивания, URL базы данных и уровень логов. Конфигурация — не код приложения. Не зашивайте значения, зависящие от окружения, в исходные файлы.

Метод Twelve-Factor App хранит конфигурацию в окружении. Читайте метод: [https://12factor.net/config](https://12factor.net/config). Переменные окружения работают в локальных оболочках, контейнерах и многих платформах размещения.

В Go читайте переменную окружения через `os.Getenv` или `os.LookupEnv`. `LookupEnv` сообщает, задана ли переменная. Разбирайте числа через `strconv`. Разбирайте длительности через `time.ParseDuration`. Проверяйте значения при старте. Останавливайте процесс, если обязательное значение отсутствует или неверно.

Файлы конфигурации тоже обычны. Файлы JSON, TOML и YAML могут хранить структурированные настройки. Загружайте файл при старте. Файл полезен для значений по умолчанию, которые не являются секретами. Не храните секреты в файле, который вы коммитите в git.

Простой порядок такой:

1. Задайте значения по умолчанию в коде.
2. Наложите значения из файла, если задан путь к файлу.
3. Наложите значения из переменных окружения.
4. Проверьте итоговую структуру.

Держите одну структуру конфигурации. Передавайте её в конструкторы. Не читайте `os.Getenv` из многих пакетов после старта. Поздние чтения усложняют тесты и аудит.

Падайте при старте, если конфигурация неверна. Процесс, который стартует с плохим URL базы и падает на первом запросе, сложнее эксплуатировать, чем процесс, который сразу завершается.

## Структурированные логи с `slog`

Пакет `log/slog` — структурированный логгер стандартной библиотеки (Go 1.21 и новее). Структурированная запись лога содержит сообщение и атрибуты ключ-значение. Машина может разобрать эти атрибуты. Текстовая строка со свободными словами сложнее для поиска.

Создайте обработчик и логгер:

```text
logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))
logger.Info("server start", "addr", addr)
```

`slog.NewJSONHandler` пишет JSON. Используйте JSON в продакшене. `slog.NewTextHandler` пишет текст ключ-значение. Текст легче читать на ноутбуке.

Уровни: `Debug`, `Info`, `Warn` и `Error`. Задайте минимальный уровень в `slog.HandlerOptions`. Не пишите `Info` для событий в каждом тесном цикле. Не логируйте секреты. Не логируйте токены доступа и пароли.

`slog.SetDefault` ставит логгер на весь процесс. Тогда `slog.Info` использует этот логгер. Лучше передавать `*slog.Logger` в свои типы. Поле в структуре легко тестировать.

Добавляйте стабильные ключи. Примеры: `request_id`, `method`, `path`, `duration_ms`, `err`. Используйте одни и те же имена ключей в каждом обработчике. `logger.With("request_id", id)` возвращает логгер, который включает этот атрибут в каждую запись.

`slog.LogValuer` позволяет типу управлять тем, как он выглядит в логе. Используйте его, чтобы скрыть секретный тип. `slog.Group` вкладывает атрибуты под один ключ.

Пишите логи в стандартный вывод или стандартную ошибку. Процесс, который запускает бинарный файл, собирает эти потоки. Не открывайте свой файл лога из приложения, если нет особой нужды.

## Корректное завершение

Корректное завершение значит: процесс перестаёт принимать новую работу и затем доделывает текущую работу перед выходом. Противоположность — жёсткая остановка. Жёсткая остановка может оборвать HTTP-ответ или оставить открытой транзакцию базы.

Операционные системы шлют сигналы. Интерактивные терминалы шлют `SIGINT` по Ctrl+C. Хосты контейнеров шлют `SIGTERM`. Используйте `signal.NotifyContext` (Go 1.16 и новее) или `signal.Notify`, чтобы получать эти сигналы.

`http.Server.Shutdown` останавливает слушатель и ждёт активные соединения. Передайте контекст с таймаутом. Если таймаут истекает, `Shutdown` возвращает ошибку. Затем можно вызвать `Server.Close` для жёсткой остановки.

Типичная последовательность:

1. Запустите `ListenAndServe` в горутине.
2. Дождитесь сигнала.
3. Вызовите `Shutdown` с таймаутом из конфигурации.
4. Остановите фоновые воркеры отменой `context`.
5. Закройте пул базы данных.
6. Выйдите с ненулевым кодом, если завершение не удалось.

`ListenAndServe` возвращает `http.ErrServerClosed` после чистого `Shutdown`. Считайте это значение успехом. Другие ошибки считайте сбоями старта или остановки.

Осушайте пулы воркеров через `sync.WaitGroup`. Отменяйте корневой контекст, чтобы исходящие HTTP-клиенты и запросы к базе остановились. Задайте таймауты на эти операции. Не ждите вечно.

Не вызывайте `os.Exit` из горутины, которая пропускает `defer`. `os.Exit` пропускает отложенную очистку. Вернитесь из `main` после закрытия ресурсов.

## Внедрение зависимостей без фреймворков

Внедрение зависимостей значит: тип получает значения, которые ему нужны. Тип не создаёт каждую зависимость сам. В Go обычный способ — функция-конструктор.

```text
func NewServer(store Store, log *slog.Logger) *Server
```

`main` (или маленький пакет `cmd`) создаёт конкретную базу, логгер и HTTP-сервер. Это корень композиции. Нижние пакеты принимают интерфейсы или маленькие структуры.

Определяйте интерфейсы в пакете, который их использует, когда интерфейс маленький. Интерфейса хранилища с `Get` и `Save` достаточно для HTTP-обработчика. Не создавайте интерфейс заранее для каждой структуры.

Фреймворки вроде `wire`, `fx` и `dig` генерируют или разрешают графы конструкторов. Они необязательны. Команде с маленьким сервисом они часто не нужны. Длинный список конструкторов в `main` ясен и его легко отлаживать.

Плюсы внедрения через конструктор:

- Тесты передают поддельный `Store`.
- Список зависимостей виден в сигнатуре функции.
- Граф виден без контейнера.

Не прячьте обязательные зависимости в переменных уровня пакета. Глобальные клиенты заставляют тесты делить состояние. Если нужно значение по умолчанию, дайте `NewServer` плюс маленький `main`, который собирает продакшен-значения.

Передавайте `context.Context` первым аргументом методов, которые делают I/O. Не храните контекст запроса в долгоживущей структуре сервера.

## Консольные приложения (`flag`, Cobra по желанию)

Консольное приложение читает аргументы и флаги, затем выполняет одну работу. Пакет стандартной библиотеки — `flag`.

`flag.String`, `flag.Int` и `flag.Bool` задают флаги. Вызовите `flag.Parse` до чтения значений. `flag.Args` возвращает оставшиеся аргументы после флагов.

```text
out := flag.String("o", "out.txt", "output file")
flag.Parse()
```

`flag` печатает справку, когда пользователь передаёт `-h`. Пишите ясную строку использования. Задайте `flag.Usage`, если текста по умолчанию недостаточно.

`os.Args` — сырой срез аргументов. `os.Args[0]` — имя программы. Предпочитайте `flag` ручному разбору, когда нужны типизированные флаги.

Один модуль может держать несколько команд под `cmd/`. У каждой команды свой `package main`. Такая раскладка избегает большого набора флагов в одном бинарном файле.

Cobra (`github.com/spf13/cobra`) — сторонняя библиотека для вложенных подкоманд, постоянных флагов и сгенерированной справки. Используйте Cobra, когда много подкоманд и длинное дерево справки. Сначала выучите `flag`. Не добавляйте Cobra в инструмент с двумя флагами.

Коды выхода важны. Выходите с `0` при успехе. Выходите с ненулевым кодом при ошибках использования и ошибках выполнения. `flag` по умолчанию вызывает `os.Exit(2)` при ошибках разбора.

## REST и JSON-сервисы

HTTP-сервис в стиле REST открывает ресурсы через URL и методы HTTP. JSON — обычный формат тела. Пакеты стандартной библиотеки — `net/http` и `encoding/json`.

Go 1.22 и новее расширяют `http.ServeMux`. Можно зарегистрировать метод и шаблон пути:

```text
mux.HandleFunc("GET /items/{id}", getItem)
```

`r.PathValue("id")` возвращает сегмент пути. Используйте эти шаблоны до стороннего маршрутизатора.

Декодируйте JSON через `json.NewDecoder(r.Body)`. Кодируйте JSON через `json.NewEncoder(w)`. Задайте `Content-Type` равным `application/json`. Задайте код статуса до записи тела. `Encode` пишет тело.

Лимиты защищают сервер. Оберните `r.Body` в `http.MaxBytesReader`. Используйте `Decoder.DisallowUnknownFields`, когда API должен отклонять неизвестные ключи. Проверяйте ошибки `Decode`. Отличайте неверный JSON от допустимого пустого объекта.

Держите обработчики тонкими. Разберите запрос. Вызовите метод сервиса с `r.Context()`. Запишите ответ. Вернитесь после записи ошибки. Не продолжайте обработчик после записи тела 4xx или 5xx.

Используйте `GET` для чтений, которые не меняют состояние. Используйте `POST`, `PUT`, `PATCH` и `DELETE` с ясными правилами. Документируйте коды статуса: `200`, `201`, `204`, `400`, `401`, `404`, `409` и `500` обычны.

`httptest.NewRecorder` и `httptest.NewRequest` тестируют обработчики без сокета прослушивания. Проверяйте тело JSON и код статуса.

## Основы аутентификации (JWT и сессии)

Аутентификация отвечает на вопрос: кто этот клиент? Авторизация отвечает на вопрос: что этому клиенту можно делать? Держите эти слова отдельно.

Сессия — состояние на стороне сервера. Сервер создаёт запись сессии после успешного входа. Браузер хранит идентификатор сессии в cookie. Поздние запросы шлют cookie. Сервер ищет сессию.

Флаги cookie важны. Используйте `HttpOnly`, чтобы скрипт не мог прочитать cookie. Используйте `Secure`, чтобы cookie уходила только по HTTPS. Задайте `SameSite`, чтобы снизить злоупотребление межсайтовыми запросами. Задайте путь и срок действия.

JSON Web Token (JWT) — компактный подписанный токен. Обычная форма имеет три части: заголовок, утверждения и подпись. Части — строки Base64-URL, разделённые точками. Подпись позволяет серверу заметить изменение утверждений.

В утверждениях JWT часто есть `sub` (субъект), `exp` (срок), `nbf` (не раньше), `iss` (издатель) и `aud` (аудитория). Проверяйте все эти поля. Отклоняйте просроченный токен. JWT по умолчанию не шифруется. Любой держатель может прочитать утверждения. Не кладите пароль в JWT.

Сессиям нужны хранилище и путь отзыва. JWT access-токены часто без состояния. Отзыв сложнее, если нет чёрного списка или короткого срока плюс refresh-токен. Короткий срок снижает риск при утечке токена.

Транспорт в продакшене должен быть HTTPS. Шлите токены в заголовке `Authorization` как `Bearer` для API или используйте cookie для браузеров. Не кладите токены в строки запроса. Строки запроса попадают в логи.

Хранение паролей — отдельная тема. Храните хеш пароля медленной хеш-функцией из поддерживаемой библиотеки. Никогда не храните пароль открытым текстом. Никогда не логируйте пароль.

Этот раздел концептуальный. Не изобретайте свою криптографию. Используйте поддерживаемые библиотеки и письменную модель угроз.

## Образы Docker для бинарного файла Go

Образ контейнера упаковывает бинарный файл и файлы, которые ему нужны. Go может дать статический бинарный файл. Статическому бинарному файлу не нужна `libc` в образе. Задайте `CGO_ENABLED=0`, когда собираете для образа scratch.

Многостадийный Dockerfile собирает в образе Go и копирует только бинарный файл в маленький образ выполнения:

```text
FROM golang:1.22-bookworm AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/app ./cmd/app

FROM scratch
COPY --from=build /out/app /app
ENTRYPOINT ["/app"]
```

`scratch` пуст. Нет оболочки. Нет файла сертификатов УЦ, если вы его не скопируете. HTTPS-клиентам нужны сертификаты УЦ. Образы Distroless вроде `gcr.io/distroless/static` включают сертификаты и пользователя не-root. В образах Distroless по-прежнему нет менеджера пакетов и оболочки.

Не запускайте процесс от root. Задайте `USER` пользователя не-root в финальном образе. Статические образы Distroless дают такого пользователя для этой цели.

Добавьте файл `.dockerignore`. Исключите `.git`, testdata и локальные бинарные файлы. Меньший контекст сборки ускоряет сборку.

Передавайте конфигурацию переменными окружения во время выполнения. Не запекайте продакшен-секреты в образ. Фиксируйте версии базовых образов. Пересобирайте, когда нужны обновления безопасности образа сборки.

Бинарный файл, который вы копируете, должен совпадать с ОС и архитектурой контейнера. Бинарный файл Windows не запустится в образе Linux. См. следующий раздел про `GOOS` и `GOARCH`.

## Кросс-компиляция с `GOOS` и `GOARCH`

Go по умолчанию кросс-компилирует, когда `CGO_ENABLED=0`. Задайте `GOOS` для целевой операционной системы. Задайте `GOARCH` для целевой архитектуры.

```text
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -o app-linux-amd64 ./cmd/app
```

Обычные пары:

- `windows` / `amd64`
- `linux` / `amd64`
- `linux` / `arm64`
- `darwin` / `arm64`
- `darwin` / `amd64`

Перечислите все пары командой `go tool dist list`. Покажите текущую пару командой `go env GOOS GOARCH`.

Инструмент `go` добавляет `.exe` к имени вывода, когда `GOOS=windows` и вы не задали `-o`. Задайте `-o`, когда собираете несколько целей в одном скрипте.

Cgo меняет картину. Cgo нужен компилятор C для цели. Кросс-компиляция с Cgo сложнее. Предпочитайте чистые сборки Go для релизных бинарных файлов, когда можете. Теги сборки `netgo` и `osusergo` запрашивают чистый резолвер Go и поиск пользователя на некоторых платформах.

Вам не нужно запускать чужой бинарный файл на своей машине, чтобы его получить. Вы всё равно должны тестировать бинарный файл на целевой ОС или в контейнере, который совпадает с целью.

`GOARM` выбирает версию ARM для 32-битного ARM. `GOAMD64` выбирает уровень микроархитектуры `amd64` (Go 1.18 и новее). Задавайте эти переменные только когда нужна особая цель.

Не смешивайте `GOOS` из окружения с забытым старым значением. Скрипты должны задавать `GOOS` и `GOARCH` в той же команде, что запускает `go build`.

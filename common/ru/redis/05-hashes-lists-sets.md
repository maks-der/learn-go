# 5. Хеши, списки, множества

## Описание

У Redis есть три частых коллекционных типа кроме строк. Хеш хранит пары поле-значение под одним ключом. Список хранит упорядоченную последовательность строк. Множество хранит уникальные строки без порядка. Эта тема показывает основные команды и когда выбирать каждый тип.

Завершите эту тему до изучения упорядоченных множеств.

Используйте один термин для каждого понятия. Поле — имя внутри хеша. Элемент — строка в списке. Член — строка в множестве. Не используйте `GET` на этих ключах. Используйте команды этого типа.

## Хеши: `HSET`, `HGET`, `HGETALL`, `HINCRBY`, `HDEL`

Хеш — карта внутри одного ключа. Используйте хеш для объекта с несколькими полями (профиль, настройки, корзины ограничения частоты).

`HSET key field value` пишет одно поле. Можно передать много пар поле-значение в одном `HSET`. Ответ — число полей, которые Redis добавил (не число, которые Redis только обновил). У старых серверов был `HMSET`. Новый код использует `HSET`.

`HGET key field` читает одно поле. Отсутствующее поле возвращает null. Отсутствующий ключ возвращает null.

`HMGET key field [field ...]` читает много полей одной командой. Массив может содержать null.

`HGETALL key` возвращает все поля и значения как плоский массив. На большом хеше `HGETALL` дорог и блокирует. Предпочитайте `HSCAN` для больших хешей.

`HINCRBY key field integer` добавляет целое к полю. Поле должно держать целое или отсутствовать. `HINCRBYFLOAT` добавляет float.

`HDEL key field [field ...]` удаляет поля. `HEXISTS` проверяет одно поле. `HKEYS` и `HVALS` возвращают все имена или все значения. `HLEN` возвращает число полей.

```text
HSET user:42 name Ada city London
HGET user:42 name
HINCRBY user:42 logins 1
HDEL user:42 city
```

Хеш — не второй экземпляр Redis. Вы всё равно адресуете хеш одним ключом. Нельзя истечь одно поле базовой командой в старом Redis. Redis 7.4+ добавляет срок на уровне поля в хешах в некоторых сборках. Проверьте версию. До тех пор истекайте весь ключ или делите поля на ключи.

Не используйте хеш с безграничными полями (одно поле на событие навсегда). Память растёт. Используйте поток, список с `LTRIM` или много ключей с TTL.

## Списки: `LPUSH`, `RPUSH`, `LPOP`, `RPOP`, `LRANGE`, `LTRIM`

Список — последовательность строк. Левый конец и правый конец оба пригодны. Redis не использует числовой индекс как основной API записи. Вы толкаете и снимаете с концов.

`LPUSH key element [element ...]` вставляет слева (голова). `RPUSH` вставляет справа (хвост). Ответ — длина после вставки.

`LPOP key` удаляет и возвращает левый элемент. `RPOP` использует правый. Отсутствующий ключ или пустой список возвращает null. Можно передать счёт в версиях, которые поддерживают `LPOP key N`.

`LRANGE key start stop` возвращает элементы в этом диапазоне индексов. Индексы с нуля. `0` — самый левый элемент после текущих вставок. `-1` — последний элемент. Индекс stop включительный.

```text
RPUSH lab:list a b c
LRANGE lab:list 0 -1
LRANGE lab:list 0 1
```

`LTRIM key start stop` оставляет только этот диапазон и удаляет остальное. Используйте `LTRIM`, чтобы ограничить список (последние 100 элементов).

`LLEN` возвращает длину. `LINDEX` читает один индекс. `LSET` пишет один индекс.

Список может расти без границы. Безграничный список может заполнить память. Всегда планируйте потолок (`LTRIM`) или потребителя, который снимает.

`LRANGE 0 -1` огромного списка блокирует и копирует большой полезный груз. Не делайте этого в промышленной среде.

Блокирующие варианты `BLPOP` и `BRPOP` ждут элемент. Они полезны для очередей. Следующий раздел покрывает шаблон очереди.

## Списки как очереди

Очередь — список плюс правило: один конец принимает работу, другой отдаёт работу.

Очередь FIFO (первый вошёл, первый вышел) использует `LPUSH` для постановки и `RPOP` для снятия, или `RPUSH` и `LPOP`. Выберите одну пару и держите её.

```text
LPUSH jobs {"id":1}
RPOP jobs
```

Стек LIFO использует вставку и снятие с одного конца (`LPUSH` и `LPOP`).

`BLPOP` и `BRPOP` блокируют клиент, пока элемент не появится или не кончится таймаут. Работник может ждать без занятого цикла.

```text
BRPOP jobs 5
```

Ответ — имя ключа и элемент, или null по таймауту. Один работник может ждать на нескольких списках: `BRPOP high normal 5`. Redis снимает первый список, в котором есть данные, в порядке аргументов.

Много работников могут снимать с одного списка. Каждая задача идёт одному работнику. Это конкурирующие потребители. Redis не отслеживает «в работе» на простом списке. Если работник снял задачу и умер, задача пропала.

Надёжные очереди нуждаются в большей структуре: список обработки, таймаут и повтор. Redis Streams (тема 7 и более поздние темы потоков) дают группы потребителей и подтверждения. Используйте Streams, когда нужна эта модель. Используйте список, когда потерянная задача приемлема или когда одного работника достаточно.

Не делайте `LRANGE` очереди на горячем пути работника. Снимайте.

`RPOPLPUSH` или `LMOVE` (новее) могут атомарно перенести элемент в список обработки. Это лучший шаблон надёжности на списках, чем одно снятие.

## Множества: `SADD`, `SREM`, `SMEMBERS`, `SISMEMBER`, `SINTER`, `SUNION`

Множество — коллекция уникальных членов. Порядок не определён. Повторный `SADD` не добавляет вторую копию.

`SADD key member [member ...]` добавляет членов. Ответ — число членов, которые были новыми.

`SREM key member [member ...]` удаляет членов.

`SISMEMBER key member` возвращает `1` или `0`. `SMISMEMBER` проверяет многих членов в версиях, которые это поддерживают.

`SMEMBERS key` возвращает всех членов. На большом множестве `SMEMBERS` дорог. Используйте `SSCAN` для больших множеств.

`SCARD` возвращает размер.

`SINTER key [key ...]` возвращает пересечение. `SUNION` возвращает объединение. `SDIFF` возвращает членов в первом множестве и не в следующих. `SINTERSTORE`, `SUNIONSTORE` и `SDIFFSTORE` пишут результат в ключ назначения.

```text
SADD lab:tags:1 redis cache
SADD lab:tags:2 cache linux
SINTER lab:tags:1 lab:tags:2
```

Множества хороши для тегов, уникальных посетителей (когда множество не огромное) и индексов отношений (`user:42:roles`). Они плохое хранилище уникальных посетителей в интернет-масштабе. Используйте HyperLogLog (тема 7), когда нужна приблизительная численность, а не точные id.

Член множества — строка. Нельзя хранить вложенное множество. Можно хранить id и держать объекты в хешах.

Не используйте множество как безграничный журнал событий. Используйте список с `LTRIM` или поток.

## Когда использовать каждый тип

Выбирайте тип по шаблону доступа, а не по предметному слову «объект».

Используйте строку, когда есть один блоб, счётчик или блокировка. Используйте `GET` / `SET` / `INCR`.

Используйте хеш, когда есть один id и много маленьких полей, которые вы читаете или обновляете по одному. Профиль пользователя — обычный пример. Можно сделать `HINCRBY` одного поля. Можно сделать `HGET` одного поля без полного объекта.

Используйте список, когда важны порядок и концы: очереди, стеки и ленты «последние N». Вы толкаете, снимаете и обрезаете. Случайные проверки членства не нужны.

Используйте множество, когда важны уникальность и членство: теги, роли, уникальные id. Нужны `SISMEMBER`, пересечение или объединение. Счёты не нужны (это упорядоченное множество).

Примеры:

- Блоб сессии → строка с TTL
- Профиль пользователя → хеш
- Очередь задач → список (или поток)
- Последние 50 уведомлений → список плюс `LTRIM`
- Теги поста → множество
- Все id постов с тегом `redis` → множество (вторичный индекс)

Можно сочетать типы. Хеш поста `post:9` плюс множество `tag:redis:posts`, которое содержит `9`, — нормальный дизайн.

Если нужен ранг или числовой счёт, используйте упорядоченное множество (тема 6). Если нужен журнал только для добавления с id, используйте поток (тема 7).

Переносите неверный тип только миграцией: прочитайте, запишите новый ключ, удалите старый. Redis не превращает хеш в список на месте.

# 4. Типы данных

## Описание

Эта тема показывает распространённые типы данных в PostgreSQL 16 и PostgreSQL 17. Вы узнаёте целые, точные числовые значения, приблизительные float, текст, boolean, дату и время, `uuid`, JSON, `bytea`, массивы и `NULL`.

Сначала завершите тему 3. Нужно уметь создать таблицу и выполнить `SELECT`. Завершите эту тему до проектирования ограничений.

Используйте один термин для каждого понятия. Тип — имя, которое PostgreSQL даёт множеству значений. Размер хранения — размер на диске для значения этого типа, без заголовков кортежа. Предпочитайте наименьшее целое, которое покрывает ваш диапазон. Для денег предпочитайте `numeric`. Для мгновений предпочитайте `timestamptz`. Для строк предпочитайте `text`. Для JSON, который ищете, предпочитайте `jsonb`.

## Целые: `smallint`, `int`, `bigint`

В PostgreSQL три двоичных целочисленных типа:

| Тип | Псевдонимы | Размер | Диапазон |
| --- | --- | --- | --- |
| `smallint` | `int2` | 2 байта | -32768 до 32767 |
| `integer` | `int`, `int4` | 4 байта | около -2.1e9 до 2.1e9 |
| `bigint` | `int8` | 8 байт | около -9e18 до 9e18 |

`integer` — обычный выбор для ключей и счётчиков, которые умещаются в 32 бита. Используйте `bigint` для высоконагруженных identity-ключей и больших счётчиков. Используйте `smallint` только когда набор маленький и закрытый и важен размер.

Переполнение даёт ошибку:

```sql
SELECT 32767::smallint + 1::smallint;
```

Целочисленные литералы пишите без кавычек: `42`. Заключённое в кавычки `'42'` — unknown или text до приведения.

Типы serial (`smallserial`, `serial`, `bigserial`) — не настоящие типы. Они создают последовательность и значение по умолчанию. Для новых таблиц предпочитайте столбцы identity (тема 5).

Целочисленное деление усекает к нулю:

```sql
SELECT 5 / 2;      -- 2 (integer)
SELECT 5::numeric / 2;
```

Используйте `bigint` для `id`, когда таблица может вырасти за два миллиарда строк. Позже менять `integer` на `bigint` — тяжёлая перепись.

## `numeric` / `decimal` для денег и точных значений

`numeric` и `decimal` в PostgreSQL — один тип. Они хранят точные значения по основанию 10. Задаёте точность и масштаб:

```sql
amount numeric(12, 2)
```

Точность `12` — общее число цифр. Масштаб `2` — число цифр после десятичной точки. `numeric` без точности хранит значения переменного размера. Неограниченный `numeric` для части работы медленнее ограниченного.

Используйте `numeric` для денег, юридических количеств и любого значения, которое не должно терять цифры. Не используйте `real` или `double precision` для денег.

```sql
SELECT 0.1::numeric + 0.2::numeric;
SELECT 0.1::numeric + 0.2::numeric = 0.3::numeric;
```

Арифметика `numeric` точна для значений, которые умещаются. Деление может дать много цифр. Используйте `round`:

```sql
SELECT round(1::numeric / 3, 4);
```

Тип `money` существует. Он зависит от локали. Предпочитайте `numeric` плюс столбец кода валюты.

Не сравнивайте `numeric` и float без явного плана. Приводите float к `numeric` или наоборот только когда принимаете округление.

Хранение растёт с числом цифр. Очень большая точность не бесплатна.

## `real` / `double precision` (приблизительные)

`real` — 4-байтовое IEEE-число с плавающей точкой (`float4`). `double precision` — 8-байтовое IEEE-число с плавающей точкой (`float8`). Эти типы приблизительные. У многих десятичных дробей нет точной двоичной формы.

```sql
SELECT 0.1::double precision + 0.2::double precision;
SELECT 0.1::float8 + 0.2::float8 = 0.3::float8;
```

Второй запрос часто ложен. Не используйте float для денег или для точного равенства десятичных значений.

Используйте float для научных измерений, части статистики и значений, где скорость важнее точных десятичных цифр.

У `real` около 6 десятичных цифр точности. У `double precision` около 15. Когда нужен float, предпочитайте `double precision`.

Особые значения: `Infinity`, `-Infinity` и `NaN`.

```sql
SELECT 'Infinity'::float8;
SELECT 'NaN'::float8;
```

Сравнения `NaN` особые. `NaN = NaN` ложно. Используйте «`x = x` ложно» как проверку NaN или осторожно шаблоны `x IS DISTINCT FROM`. В PostgreSQL `NaN` в некоторых контекстах сортируется больше остальных значений. Читайте документацию, когда сортируете float.

Не смешивайте `numeric` и float в денежном столбце. Не храните float и не ждите, что напечатанная десятичная дробь совпадёт с исходным текстом.

## Текст: `text`, `varchar`, `char`

Текстовые типы PostgreSQL:

- `text` — строка любой длины (ограничена размером строки)
- `varchar(n)` / `character varying(n)` — строка до `n` символов
- `varchar` без `n` — то же поведение, что `text`
- `char(n)` / `character(n)` — дополняется пробелами до `n` символов

Предпочитайте `text` или `varchar(n)`, когда лимит длины нужен как ограничение. Предпочитайте `text` плюс `CHECK (char_length(col) <= n)`, когда хотите ясное правило. `varchar(n)` отклоняет более длинную строку на вводе.

`char(n)` дополняет пробелами. Это дополнение удивляет сравнения и конкатенацию. Не используйте `char(n)` для новых прикладных столбцов.

```sql
CREATE TABLE labels (
    a text,
    b varchar(10),
    c char(10)
);

INSERT INTO labels VALUES ('hi', 'hi', 'hi');
SELECT a, b, c, length(a), length(b), length(c);
```

`length` для `char(n)` считает дополненное значение. `text` и `varchar` не дополняют.

PostgreSQL хранит короткие строки внутри строки. Длинные строки могут использовать TOAST. TOAST вручную не выбирают.

Для коротких строк нет выигрыша в производительности у `varchar(10)` против `text`. Старый миф из других баз здесь не работает.

Используйте `text` для имён, комментариев и токенов. Используйте `varchar(n)`, когда стандарт или форма имеют жёсткую длину.

## `boolean`

`boolean` хранит `true`, `false` или `NULL`. Ввод принимает несколько текстов:

```sql
SELECT true, false;
SELECT 't'::boolean, 'f'::boolean;
SELECT 'yes'::boolean, 'no'::boolean;
SELECT 'on'::boolean, 'off'::boolean;
SELECT '1'::boolean, '0'::boolean;
```

В SQL предпочитайте токены `true` и `false`. `psql` по умолчанию печатает `t` и `f`.

Не используйте `integer` 0 и 1 как булев столбец. Используйте `boolean`.

`WHERE flag` значит `WHERE flag = true`. Флаг `NULL` — неизвестно. Строка не проходит. Раздел про `NULL` разбирает трёхзначную логику.

```sql
CREATE TABLE flags (
    id integer PRIMARY KEY,
    active boolean NOT NULL DEFAULT true
);
```

`NOT` инвертирует `true` и `false`. `NOT NULL` всё равно `NULL`.

Некоторые драйверы сопоставляют `boolean` с нативным bool. Проверяйте драйвер при чтении значений.

## Дата/время: `date`, `time`, `timestamp`, `timestamptz`

Частые типы:

- `date` — календарная дата, без времени суток
- `time` / `time without time zone` — время суток
- `timetz` / `time with time zone` — избегать для новой работы
- `timestamp` / `timestamp without time zone` — дата и время, без зоны
- `timestamptz` / `timestamp with time zone` — мгновение; хранится в UTC

Предпочитайте `date`, когда нужен только день. Предпочитайте `timestamptz`, когда нужно мгновение (created_at, время события). Предпочитайте `timestamp`, когда нужно локальное дата-время без зоны (настенные часы в одном здании). Не смешивайте два типа timestamp без правила.

```sql
SELECT DATE '2026-09-13';
SELECT TIMESTAMP '2026-09-13 15:30:00';
SELECT TIMESTAMPTZ '2026-09-13 15:30:00+02';
SHOW TimeZone;
```

PostgreSQL хранит `timestamptz` как UTC. Отображение использует `TimeZone` сессии.

```sql
SET TimeZone TO 'UTC';
SELECT TIMESTAMPTZ '2026-09-13 15:30:00+02';
SET TimeZone TO 'Europe/Kyiv';
SELECT TIMESTAMPTZ '2026-09-13 15:30:00+02';
```

`now()` — время старта текущей транзакции. `CURRENT_TIMESTAMP` то же, что `now()`. `clock_timestamp()` меняется внутри транзакции. Тема 5 разбирает значения по умолчанию.

`interval` — длительность:

```sql
SELECT DATE '2026-09-13' + INTERVAL '7 days';
SELECT now() - INTERVAL '1 hour';
```

Не храните целые Unix epoch, когда работает `timestamptz`. Не используйте `timetz`.

## `uuid`, `json` / `jsonb`, `bytea`

`uuid` хранит 128-битный идентификатор. Текстовая форма: `a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11`. Генерируйте значения через `gen_random_uuid()` (в ядре с PostgreSQL 13):

```sql
SELECT gen_random_uuid();
CREATE TABLE events (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    payload jsonb NOT NULL
);
```

`json` хранит текст JSON. Сохраняет пробелы и порядок ключей. Принимает дубликаты ключей. `jsonb` хранит разобранную двоичную форму. Отбрасывает незначимые пробелы. Не хранит дубликаты ключей (побеждает последний ключ). `jsonb` поддерживает индексы и операторы включения. Предпочитайте `jsonb` для столбцов, которые ищете. Предпочитайте `json` только когда нужно сохранить точный входной текст.

```sql
SELECT '{"a":1}'::json;
SELECT '{"a":1}'::jsonb;
SELECT '{"a":1}'::jsonb @> '{"a":1}';
```

Тема 7 разбирает JSON-операторы. Тема 14 разбирает JSON глубже.

`bytea` хранит сырые байты. Ввод может быть в hex-формате:

```sql
SELECT '\xDEADBEEF'::bytea;
```

Используйте `bytea` для небольших двоичных значений. Большие файлы часто лучше в объектном хранилище. Очень большой `bytea` использует TOAST и память у клиента.

Не храните JSON как неограниченный `text`, если нужна проверка. `json` и `jsonb` отклоняют невалидный JSON на вводе.

## Массивы

Массив — упорядоченный список значений одного типа элемента. Тип пишут как `integer[]` или `text[]`.

```sql
CREATE TABLE packs (
    id integer PRIMARY KEY,
    tags text[],
    nums integer[]
);

INSERT INTO packs VALUES (1, ARRAY['red', 'blue'], ARRAY[1, 2, 3]);
INSERT INTO packs VALUES (2, '{green,blue}', '{4,5}');
```

Индексы начинаются с 1:

```sql
SELECT nums[1], nums[2] FROM packs WHERE id = 1;
```

Полезные операторы и функции:

- `=` — равные массивы
- `@>` — левый содержит правый
- `<@` — левый содержится в правом
- `&&` — пересечение
- `unnest(arr)` — одна строка на элемент
- `array_length(arr, 1)` — длина первого измерения
- `cardinality(arr)` — всего элементов

```sql
SELECT * FROM packs WHERE tags @> ARRAY['blue'];
SELECT unnest(tags) FROM packs WHERE id = 1;
```

Массивы могут быть многомерными. Большинство приложений используют одно измерение.

Элементы `NULL` допустимы. Само значение массива тоже может быть `NULL`.

Не заменяйте массивом дочернюю таблицу, когда нужны ключи, ограничения и соединения. Используйте массивы для маленьких множеств (теги, дни недели). Тема 14 глубже разбирает `unnest`.

Индекс GIN может ускорить включение на массивах (тема 8).

## `NULL` и трёхзначная логика

`NULL` значит неизвестно или отсутствует. Это не число 0. Это не пустая строка. Трёхзначная логика использует `true`, `false` и `unknown`.

```sql
SELECT 1 = 1;          -- true
SELECT 1 = 2;          -- false
SELECT 1 = NULL;       -- NULL (unknown)
SELECT NULL = NULL;    -- NULL (unknown)
```

`WHERE` оставляет строки, где условие `true`. `WHERE col = NULL` никогда не оставляет строку. Используйте `IS NULL` и `IS NOT NULL`:

```sql
SELECT * FROM items WHERE qty IS NULL;
SELECT * FROM items WHERE qty IS NOT NULL;
```

`IS DISTINCT FROM` считает два значения `NULL` не различными:

```sql
SELECT NULL IS DISTINCT FROM NULL;     -- false
SELECT 1 IS DISTINCT FROM NULL;        -- true
```

`AND` и `OR` с `NULL`:

- `true AND NULL` это `NULL`
- `false AND NULL` это `false`
- `true OR NULL` это `true`
- `false OR NULL` это `NULL`

`NOT NULL` это `NULL`.

Агрегаты вроде `SUM` и `AVG` пропускают входы `NULL`. `COUNT(col)` пропускает `NULL`. `COUNT(*)` считает строки.

Ограничение уникальности в PostgreSQL допускает много значений `NULL` (в этом правиле NULL отличен от NULL), если не использовать `UNIQUE NULLS NOT DISTINCT` (PostgreSQL 15 и новее).

Всегда решайте `NULL` или `NOT NULL` для каждого столбца. Предпочитайте `NOT NULL`, когда значение должно существовать.

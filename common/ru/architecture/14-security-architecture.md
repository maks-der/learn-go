# 14. Архитектура безопасности

## Описание

Архитектура безопасности — это набор границ доверия, правил идентичности, правил доступа и правил обращения с секретами, которые структура должна поддерживать. Эта тема разбирает границы доверия, аутентификацию против авторизации, роли OAuth 2.0 и OpenID Connect, секреты и ключи, least privilege, простое моделирование угроз STRIDE и риск цепочки поставок от зависимостей.

Эта тема защитная. Используйте её, чтобы снижать случайности и злоупотребления. Не используйте её, чтобы планировать атаки или обходить контроли. Следуйте закону и правилам вашей школы или работодателя. Завершите темы 1–13 до этой темы. Тема 2 определяет безопасность как атрибут качества. Эта тема показывает структуру, которая поддерживает это качество.

Используйте один термин для каждого понятия. Аутентификация — не авторизация. Клиент — не resource server. Секрет — не публичный идентификатор. STRIDE — чеклист обзора. Это не продукт.

## Границы доверия

Граница доверия — это линия, где уровень доверия меняется. Данные и вызовы, которые пересекают линию, нуждаются в дополнительных проверках. Тема 2 ввела идею. Этот раздел ставит её на структуру.

Типичные зоны:

- Публичный интернет и браузеры
- Край (балансировщик или API gateway, тема 12)
- Процессы приложения
- Хранилища данных
- Пути оператора и администратора
- Сторонние API

Запрос из «внутренней» сети не автоматически доверен. Внутренние сети сканируют. Случается неверная конфигурация. Аутентифицируйте principals. Авторизуйте действия. Шифруйте в пути через враждебные или общие сети.

Нарисуйте границу на диаграмме контейнеров C4. Пометьте каждую стрелку, которая пересекает линию. Для каждой стрелки напишите:

- Какая идентичность путешествует
- Какая классификация данных путешествует (публичные, внутренние, персональные)
- Что происходит, если вызывающий поддельный или повторён

У монолита всё равно есть границы доверия: браузер к процессу, процесс к базе, процесс к поставщику почты. Микросервисы добавляют больше линий. Больше линий означает больше политики и больше шанса пропущенной проверки (тема 12).

Не изобретайте «безопасную зону», которая пропускает аутентификацию, потому что есть межсетевой экран. Межсетевой экран — один контроль. Идентичность — другой контроль.

Интерфейсам администратора нужна более строгая граница. Используйте отдельное имя хоста, более сильную идентичность и более короткую сессию. Журналируйте действия администратора.

## Аутентификация против авторизации

Аутентификация отвечает «кто этот principal?». Авторизация отвечает «что этот principal может делать?». Тема 2 использует ту же пару. Смешение двух слов вызывает дефекты.

Principal — пользователь, служебная учётная запись или машинная идентичность. Аутентификация связывает запрос с principal через учётные данные или токен. Сессии и токены — доказательство более ранней аутентификации.

Авторизация использует роли, разрешения или политики. «Пользователь вошёл» недостаточно. Студент, который аутентифицирован, не должен писать оценки.

Пишите авторизацию рядом с владельцем данных. Сервис, который владеет записью оценки, должен проверить права преподавателя. Шлюз может отвергнуть отсутствующий токен. Шлюз не должен быть единственным местом, которое знает «этот преподаватель может менять этот курс», если другие пути могут достичь сервиса (тема 12).

Падайте закрыто. Если идентичность отсутствует или хранилище политик лежит, запретите чувствительное действие. Запишите отказ. Не падайте открыто на путях администратора.

Идентичность — не отображаемое имя. Используйте стабильные идентификаторы. Не кладите пароли в журналы (следующие разделы).

Публичные страницы могут пропускать аутентификацию. Им всё равно нужны другие контроли: пределы частоты, пределы размера и проверка.

## OAuth2 / OIDC (роли client, IdP, resource server)

OAuth 2.0 — рамка делегированной авторизации. Пользователь может разрешить клиенту доступ к resource server, не делясь паролем с этим клиентом. OpenID Connect (OIDC) — слой идентичности поверх OAuth 2.0. OIDC добавляет ID token, который указывает, кто аутентифицировался.

Изучите роли. Не начинайте с имени продукта.

- Resource owner: пользователь или организация, которая владеет данными.
- Client: приложение, которое запрашивает доступ.
- Authorization server (поставщик идентичности, IdP): аутентифицирует пользователя и выдаёт токены.
- Resource server: API, который держит данные и проверяет access token.

Клиент часто не resource server. Одностраничное приложение — клиент. Ваш API — resource server. Кампусная система входа может быть IdP.

OIDC — то, как многие команды реализуют «войти кампусной учётной записью». ID token — для идентичности. Access token — для доступа к API. Не считайте их одним токеном.

Обязанности архитектуры:

- Выберите один IdP. Не изобретайте хранилище паролей, если у организации уже есть одно.
- Регистрируйте клиентов. Используйте правильный тип клиента для среды (публичный браузер против конфиденциального сервера).
- Проверяйте токены на resource server. Проверяйте issuer, audience, expiry и подпись ключами IdP.
- Держите scopes маленькими. Scope — не полная модель авторизации. Ваш API всё равно проверяет права на уровне объекта.

Не кладите долгоживущие секреты в публичный мобильный двоичный файл или в исходный бандл фронтенда. Тема 20 отмечает пределы клиента.

Этот раздел — карта ролей. Это не поваренная книга типов grant. Читайте документацию IdP вашей школы или поставщика, когда реализуете. Оставайтесь на одобренных потоках. Не проектируйте свой формат токена без причины.

## Секреты и управление ключами

Секрет — значение, которое даёт доступ: пароль, токен API, закрытый ключ или учётные данные базы. Публичный идентификатор — не секрет. Ключ — секрет, который использует криптографическая функция. Этот справочник группирует пароли, токены и ключи как секреты, если предложение не называет тип ключа.

Правила:

- Не храните секреты в системе контроля версий.
- Не кладите секреты в образы, тикеты или чат.
- Не пишите секреты в журналы.
- Внедряйте секреты во время выполнения из хранилища секретов, которое контролирует эксплуатация.
- Ротируйте секреты. Запишите, кто может их читать.
- Используйте разные секреты на среду.

Хранилище секретов — сервис или функция платформы, которая держит значения и выдаёт их идентифицированным нагрузкам. Облачные платформы и операторы предоставляют эти хранилища. Приложение читает значение при старте или через sidecar. Приложение не пишет значение в файл конфигурации в репозитории.

Управление ключами включает генерацию, хранение, ротацию и уничтожение ключей. Предпочитайте службу ключей платформы для шифрования диска и для подписи, если команда не может провести церемонию ключей.

Сертификаты истекают. Истёкший сертификат TLS — инцидент доступности (тема 2). Календарите истечение. Автоматизируйте продление, когда платформа позволяет.

Привычка инцидента: если секрет был в журнале или репозитории, ротируйте его. Не только удаляйте строку.

Этот материал защитный. Не используйте его, чтобы извлекать секреты из систем, которыми вы не владеете.

## Least privilege в сетях и данных

Least privilege — правило: давайте каждому principal только права, которые нужны работе. Правило применяется к людям, процессам, токенам и сетевым путям. Тема 2 сформулировала идею. Этот раздел применяет её к структуре.

На данных:

- Задача отчёта, которая только читает, должна использовать роль базы только для чтения.
- Веб-процесс не должен использовать роль, которая может удалять таблицы.
- Персональные данные остаются в хранилище владельца. Другие сервисы получают минимум полей (тема 9).
- Действия администратора используют отдельную роль и отдельный след аудита.

В сетях:

- Worker, который говорит только с брокером, не нужен публичный вход.
- Базы принимают соединения из сети приложения, не из публичного интернета.
- Порты управления остаются вне публичного края.
- Вызовы east-west используют идентичность, не только частный IP.

Слишком много привилегий прячется в «одна учётная запись администратора для всех сред» и в «API использует суперпользователя базы». Эти короткие пути проваливают аудит и увеличивают инцидент.

Начинайте с запрета. Добавляйте путь, когда функция нуждается в нём. Записывайте путь на диаграмме.

Least privilege может увеличить труд. Новой функции нужна новая выдача. Этот труд дешевле широких учётных данных, которые могут уничтожить данные.

Не путайте least privilege со сложной mesh, которую команда не может обслуживать. Несколько ясных сетевых правил плюс сильные роли данных бьют диаграмму, которую никто не может изменить.

## Моделирование угроз (STRIDE, простое)

Моделирование угроз — структурированный обзор того, как система может отказать в терминах безопасности. Вы делаете его, чтобы добавить контроли. Вы не делаете его, чтобы писать рецепты атак.

STRIDE — простая мнемоника:

- Spoofing: principal притворяется другим principal.
- Tampering: данные или код меняются без права.
- Repudiation: актор может отрицать действие, потому что журнал слаб.
- Information disclosure: данные достигают человека или процесса, который не должен их видеть.
- Denial of service: система не может делать полезную работу.
- Elevation of privilege: principal получает права, которые проект не выдавал.

Как провести короткий обзор:

1. Нарисуйте диаграмму потока данных с границами доверия.
2. Для каждого процесса и хранилища спросите шесть имён STRIDE.
3. Напишите один реалистичный отказ на имя, которое применяется.
4. Напишите один защитный контроль на отказ.
5. Назначьте владельца и тест.

Держите сессию короткой. Два часа на одну функцию лучше модели на 40 страниц, которую никто не читает.

Контроли нарочно скучные: аутентификация, проверки целостности, журналы аудита, шифрование в пути и в покое, пределы частоты и least privilege. Тема 2 просила проверяемые требования безопасности. Модель должна производить эти требования.

Не включайте шаги эксплуатации, полезные нагрузки или инструкции обхода в заметки. Назовите отказ и контроль.

Закон и случаи злоупотребления принадлежат тому же обзору: хранение, согласие и правила детских данных, если они применяются. Пригласите заинтересованную сторону, которая владеет этим ограничением (тема 1).

## Цепочка поставок (зависимости)

Программная цепочка поставок — это набор исходников, сборок, зависимостей, образов и издателей, которые производят то, что вы запускаете. Дефект или враждебное изменение в зависимости становится вашим дефектом.

Обязанности архитектуры:

- Записывайте зависимости (lock-файлы).
- Предпочитайте пакеты, которые команда может обновлять.
- Ограничьте установку из неизвестных источников.
- Фиксируйте версии в производственных сборках.
- Сканируйте известные опубликованные уязвимости инструментом, который команда может запускать в CI (тема 18).
- Отделяйте сборку от выполнения. Не компилируйте ненадёжный код на производственном хосте.

Транзитивные зависимости умножают поверхность. Одна прямая библиотека может тянуть много других. Просматривайте lock-файл, когда добавляете прямую зависимость.

«Маленький помощник», который экономит 20 строк, может добавить большое дерево. Тема 2 считает стоимость и сопровождаемость качествами. Зависимость — решение сопровождаемости и безопасности. Напишите ADR для необычных или высокорисковых пакетов.

Образы и базовые слои — зависимости. Пересобирайте по расписанию. Не запускайте образ с известным критическим дефектом в базовом слое, если ремонт есть.

Люди — часть цепи. Один человек, который может выложить в продакшен без обзора, — риск цепочки поставок. Используйте обзоры и конвейеры с подписью, когда организация требует их.

Этот раздел защитный. Используйте его, чтобы снижать случайное раскрытие. Не используйте его, чтобы проектировать вредоносные пакеты.

# 13. Производительность и безопасность

## Описание

Эта тема показывает, как найти медленную базу и как защитить, кто подключается и что может делать. Вы изучаете измерение, кардинальность, горячие строки, пагинацию, кэширование, аутентификацию, авторизацию, секреты, TLS, шифрование на диске, инъекцию и открытые порты админки.

Используйте один термин для каждого понятия. Метрика — число, которое собираете со временем. Аутентификация доказывает личность. Авторизация даёт права этой личности. Завершите эту тему после того, как умеете читать план запроса и подключаться драйвером.

Не меняйте настройку, пока нет базовой линии. Измерьте, смените одно, измерьте снова. Безопасность — свойство всего пути, не одного поля пароля.

## Сначала измерьте: журнал медленных запросов и метрики

Журнал медленных запросов записывает операторы, которые превышают порог времени. Вы задаёте порог. Журнал даёт текст SQL, длительность и иногда план. Начинайте здесь, когда пользователи говорят «медленно», а вы не знаете какой оператор.

Метрики — временные ряды: подключения, CPU, дисковый I/O, доля попаданий кэша, ожидания блокировок, лаг репликации, скорость транзакций. Метрики показывают форму проблемы (упор в CPU, I/O, блокировки, подключения). Они не всегда называют SQL.

```text
User report --> metrics (which resource) --> slow log or traces (which SQL) --> plan --> change
```

Базовая линия — измерение до изменения. Записывайте: текст запроса, длительность, план, числа строк и время суток. Без базовой линии нельзя знать, помогло ли изменение.

Типичные первые вопросы:

1. Насыщен ли хост (CPU, диск, память)?
2. Медленен один оператор или многие операторы ждут?
3. Ожидание на I/O, на блокировке или на последовательном сканировании?

Не включайте очень низкий порог журнала медленных запросов на занятой продакшен-системе без плана. Журнал может заполнить диск. Используйте выборку, более высокий порог или хранилище операторов продукта.

Не настраивайте по фольклору («увеличьте shared buffers и будет быстро»). Соотносите метрику с оператором.

Метрики приложения важны. Время API 200 мс при 5 мс в СУБД — не проблема базы. Измеряйте обе стороны.

## Кардинальность, горячие строки и пагинация

Кардинальность — число различных значений в столбце (или в группе столбцов). Высокая кардинальность значит много различных значений. Пример: уникальный столбец email имеет кардинальность, равную числу строк. Булев столбец имеет кардинальность 2.

Оптимизатор использует статистику, чтобы оценить, сколько строк вернёт фильтр. Если статистика устарела, оценка неверна. Неверная оценка может выбрать вложенный цикл, который должен быть hash join, или сканирование, которое должно быть поиском. После большой загрузки обновляйте статистику (команда продукта: `ANALYZE` или эквивалент).

Не создавайте индекс на булевом, который истинен для 99 процентов строк, и не ждите, что поиск поможет этим запросам. Низкая селективность благоприятствует сканированию.

Не путайте кардинальность с размером таблицы. Таблица из 10 миллионов строк может иметь столбец кардинальности 10.

Горячая строка — строка, которую многие транзакции пытаются менять одновременно. Пример: одна строка счётчика «осталось билетов» или один родительский заказ, который блокирует каждое обновление строки.

Конкуренция блокировок — время ожидания на блокировках. Сессии встают в очередь. Пропускная способность падает. CPU может выглядеть простаивающим, пока сессии ждут.

```text
Session A: UPDATE counters SET n = n - 1 WHERE id = 1;  -- holds row lock
Session B: same row  -->  wait
```

Изоляция и блокировки строк верны. Проект неверен, если одна строка — глобальное узкое место.

Смягчения (выбирайте после измерения):

1. Разделите счётчик на много строк и суммируйте их.
2. Используйте атомарное приращение, которое документирует продукт, если оно сокращает время транзакции.
3. Вынесите горячий факт из транзакционной таблицы (очередь, кэш с позже сверкой), когда бизнес допускает короткую задержку.
4. Укоротите транзакцию. Не держите блокировку горячей строки, пока вызываете сетевой сервис.

Не поднимайте изоляцию до serializable как первое исправление горячей строки. Не добавляйте больше серверов приложения, которые все обновляют одну строку. Вы добавляете больше ждущих.

Пагинация возвращает страницу строк. Есть два обычных метода.

**Пагинация OFFSET.** Вы запрашиваете `LIMIT n OFFSET k`. СУБД всё ещё проходит или сортирует k + n строк, затем отбрасывает k. Большое k дорого.

```sql
SELECT order_id, ordered_at
FROM orders
ORDER BY ordered_at DESC, order_id DESC
LIMIT 20 OFFSET 40;
```

**Пагинация keyset** (метод поиска). Вы просите строки после последнего ключа предыдущей страницы. Запрос использует диапазон по ключу сортировки. Цена остаётся около одной страницы.

```sql
SELECT order_id, ordered_at
FROM orders
WHERE (ordered_at, order_id) < (:last_at, :last_id)
ORDER BY ordered_at DESC, order_id DESC
LIMIT 20;
```

Keyset нужен уникальный ключ сортировки (добавьте первичный ключ, чтобы разорвать ничьи). OFFSET может прыгнуть на страницу 500 (за цену). OFFSET также дрейфует: новая вставка сверху может сдвинуть строки между страницами.

Не используйте `OFFSET` для глубоких страниц на больших таблицах. Не используйте `SELECT *` на широкой таблице для страницы списка. Общий подсчёт (`SELECT COUNT(*)`) — отдельная цена. Не запускайте полный подсчёт на каждой странице, если UI может показать «ещё» без итога.

Индекс, который совпадает с `ORDER BY` (и предикатом keyset), держит страницу дешёвой. Читайте план.

## Кэш перед базой

Кэш хранит результаты запросов или объекты в быстром складе (память, продукт ключ-значение). Приложение сначала читает кэш. При промахе читает СУБД и заполняет кэш.

Кэш помогает, когда:

- одно чтение частое
- результат может быть старше нескольких секунд или минут
- СУБД — узкое место

```text
Read:  cache hit --> return
       cache miss --> DBMS --> fill cache --> return
Write: DBMS commit --> invalidate or update cache keys
```

Инвалидация — трудная часть. Если обновляете строку и оставляете старый ключ кэша, пользователи видят устаревшие данные. Если инвалидируете слишком много ключей, кэш бесполезен и СУБД видит шторм промахов (thundering herd).

Ключи кэша должны включать каждый вход, который меняет результат (пользователь, страница, локаль). Ключ, который опускает пользователя, может утечь данные между пользователями. Эта утечка — баг безопасности.

Не кэшируйте путь записи, который должен оставаться согласованным с ограничениями, если всё равно не фиксируете в СУБД. Кэш не является системой учёта.

Не добавляйте кэш, чтобы спрятать запрос N+1 или отсутствующий индекс. Сначала исправьте запрос. Измерьте. Затем кэшируйте, если чтение всё ещё горячее.

Короткий TTL (время жизни) ограничивает устаревание без идеальной инвалидации. TTL — компромисс, не полный проект.

Буферный кэш СУБД — не этот кэш. Буферный кэш держит страницы. Кэш приложения держит результаты.

## Аутентификация против авторизации и наименьшие права

Аутентификация отвечает «кто эта сессия?» СУБД проверяет имя пользователя и учётные данные (пароль, сертификат, токен или внешний каталог). Неудачная аутентификация не начинает сессию.

Авторизация отвечает «что эта сессия может делать?» СУБД проверяет привилегии: подключиться, читать таблицу, писать таблицу, создавать объекты, управлять ролями.

```text
Connect request --> authenticate --> session identity
SQL statement   --> authorize    --> allow or reject
```

Верный пароль без привилегии `SELECT` всё равно роняет `SELECT`. `GRANT` без успешного входа никогда не применяется.

Типичные личности: человек-админ, пользователь приложения, репортёр только для чтения, пользователь миграций (смена схемы).

Не делите одного пользователя на все эти работы. Нельзя отозвать утёкший пароль приложения, не заблокировав также админа. Нельзя аудировать, кто сменил строку, если каждая программа использует `postgres` или `sa`.

Наименьшие права значат, что у роли только права, которые ей нужны. Пользователь приложения может `SELECT`, `INSERT`, `UPDATE` и `DELETE` на таблицах, которые использует приложение. Он не может `DROP TABLE` в продакшене.

```sql
-- Shape only; verbs and names differ by product
GRANT SELECT, INSERT, UPDATE, DELETE ON orders TO app_shop;
REVOKE DELETE ON invoices FROM app_shop;
```

Начинайте с нуля. Давайте то, что нужно программе. Не давайте `SUPERUSER`, `DBA` или `sysadmin` приложению.

Миграциям нужен более сильный пользователь. Запускайте миграции как этот пользователь. Приложение не использует этого пользователя во время выполнения.

Роли только для чтения не должны писать. Replica отчётов всё равно нужен пользователь, который не может `DELETE`.

Владельцы объектов и умолчания `PUBLIC` важны. Некоторые продукты дают широкие права `PUBLIC`. Отзывайте эти права на чувствительных объектах.

Не давайте `SELECT` на всех таблицах, если приложению нужны только пять таблиц. Просматривайте гранты, когда добавляете таблицу. Новая таблица может унаследовать слишком широкие умолчания. Давайте явно.

Аутентификация `trust` (принимается любой соединитель) только для закрытой лаборатории. Журналируйте неудачи аутентификации. Много неудач с одного хоста могут быть атакой или плохой строкой подключения.

## Секреты, TLS и шифрование на диске

Строка подключения часто содержит пароль. Этот пароль — секрет. Секрет в репозитории Git, журнале чата или образе контейнера — утечка.

Правила:

1. Храните секреты в переменной окружения, менеджере секретов или файле с жёсткими правами. Не храните их в исходниках.
2. Используйте другой пароль в разработке, тесте и продакшене.
3. Ротируйте утёкший пароль. Ротируйте по расписанию, если политика требует.
4. Не печатайте строку подключения в журналах. Драйверы могут журналировать URI. Выключите это или редактируйте.
5. Предпочитайте URI без пароля плюс отдельное поле пароля, которое процесс читает при старте.

```text
# Environment (example names)
DATABASE_HOST=127.0.0.1
DATABASE_USER=app_shop
DATABASE_PASSWORD=...   # from a secret store, not from the repo
```

Файлы `.env` помогают локальной работе. Не коммитьте `.env`. Закоммиченный `.env.example` содержит только заполнители.

Если секрет утёк, смените его. Утечка в старом коммите остаётся в истории Git. Ротируйте. С этого момента считайте репозиторий публичным.

TLS шифрует сетевые байты между клиентом и СУБД. Наблюдатель в сети не может прочитать текст SQL или строки. TLS также аутентифицирует сервер, когда клиент проверяет сертификат.

Без TLS в недоверенной сети захват пакетов может показать пароли и персональные данные. «Порт в частной VLAN» снижает риск. Это не шифрует.

Режимы (имена отличаются): disable, allow/prefer, require, verify-ca / verify-full. В продакшене используйте verify-full (или эквивалент продукта). Режим `require` без проверки имени всё ещё может принять другой сервер.

Не ставьте «пропустить проверку» в продакшене, чтобы заглушить ошибку. TLS не заменяет аутентификацию. TLS не заменяет гранты. TLS не шифрует файлы данных на диске. Не открывайте порт СУБД в публичный интернет даже с TLS. TLS не является файрволом.

Шифрование на диске защищает файлы данных и резервы, когда кто-то получает диск или файл резерва. Байты на томе — шифротекст без ключа.

Слои (можно использовать больше одного):

| Слой | Что шифрует | Кто держит ключ |
| --- | --- | --- |
| Весь диск или том | Весь том | ОС или облачный KMS |
| Табличное пространство или TDE | Файлы базы | СУБД плюс KMS |
| Шифрование резерва | Файлы дампа или снимка | Инструмент резерва плюс KMS |
| Шифрование поля в приложении | Выбранные столбцы | Приложение |

Шифрование тома помогает, когда диск отсоединён или украден. Если злоумышленник получает работающий сервер и смонтированный том, ОС уже расшифровала диск.

Прозрачное шифрование данных (TDE) или эквивалент шифрует файлы, которые пишет СУБД. Злоумышленнику только с файлами всё равно нужен ключ.

Шифрование столбца в приложении прячет значения от СУБД и от многих админов. Вы теряете обычный `WHERE` и индексы по открытому тексту, если не проектируете searchable encryption.

Ключи — секреты. Ключ на том же диске, что данные, — слабый проект. Используйте службу управления ключами.

Шифрование на диске не прячет данные от подключённого пользователя приложения. Гранты и аутентификация всё ещё применяются. Шифруйте и резервы. Храните ключ вдали от файлов резерва.

## Инъекция и открытые порты админки

Три частых сбоя появляются вместе в инцидентах.

**Инъекция.** Приложение строит SQL из недоверенного текста. Злоумышленник выполняет SQL как пользователь приложения. Параметризованные операторы предотвращают инъекцию значений. Наименьшие права ограничивают ущерб, если инъекция всё же случается. Пользователь приложения без `DROP` не может удалить таблицы через инъекцию.

**Слишком широкие гранты.** `GRANT ALL` или суперпользователь приложения превращает любой баг в полный контроль. Утёкший пароль становится полным дампом. Просматривайте гранты. Отзывайте неиспользуемые права.

**Открытые порты админки.** Адрес прослушивания СУБД — `0.0.0.0` на публичном IP. Сканеры находят порт. Они пробуют пароли. Они пробуют старые баги. Привязывайте к localhost или к частной сети. Используйте файрвол. Используйте VPN или бастион для инструментов админки. Не публикуйте `5432`, `3306` или порты UI админки вендора в интернет.

```text
Public internet --x--> DBMS port
Admin --> VPN / bastion --> DBMS
App   --> private net   --> DBMS
```

Также закрывайте неиспользуемые расширения и неиспользуемые языки, если продукт позволяет. Удаляйте образцовых пользователей и пароли по умолчанию.

Защита слоями:

1. Нет публичного порта СУБД
2. TLS с проверкой
3. Сильные уникальные пароли или сертификаты
4. Наименьшие права
5. Параметризованный SQL
6. Шифрование на диске для дисков и резервов

Не полагайтесь на один слой. Не тестируйте инъекцию на системах, которыми не владеете.

### Вопросы

#### Теоретические вопросы

1. Как журнал медленных запросов, статистика и план работают вместе до добавления индекса или кэша?
2. Когда причина — горячая строка, а когда глубокий `OFFSET` медленной страницы?

4. Как шифрование в пути и шифрование на диске покрывают разных злоумышленников и какие контроли останавливают инъекцию, а какие только ограничивают радиус взрыва?
5. Коллега поднимает буферы, добавляет кэш, кладёт URI админки в приложение и открывает порт 5432 на `0.0.0.0` без базовой линии. Какие факты вы используете в ответе?

#### Простые практические задания

1. Напишите шпаргалку: измерение, кардинальность, горячие строки, keyset, кэш, authn против authz, секреты, TLS, на диске, шесть слоёв.
2. Включите или найдите журнал медленных запросов. Скопируйте одну строку в заметки (очистите секреты). Создайте пользователя не-админа. Подключитесь. Выполните `SELECT 1`. Покажите, что `DROP DATABASE` падает.
3. Напишите один запрос keyset и один запрос OFFSET для одного списка. Отредактируйте образец URI для README. Оставьте хост и имя базы. Уберите пароль.
4. Напишите адрес прослушивания и режим TLS учебного экземпляра.

#### Средние практические задания

1. Постройте черновую нагрузку: большая таблица, устаревшая статистика, затем `ANALYZE`, затем страница keyset. Запишите планы и времена. Получите ожидание блокировки двумя сессиями. Напишите, чем метрики отличаются.

3. Напишите шаблон тикета настройки: базовая линия, гипотеза, одно изменение, результат. Запустите обзор привилегий на базе `learn`. Получите список грантов и план отзыва.

#### Сложные практические задания

1. Настройте один реальный медленный оператор (или сделанный медленным): измерение, статистика, индекс или перепись, исправление пагинации. Напишите до/после. Напишите обзор безопасности маленького проекта против этой темы. Разложите находки по серьёзности. Исправьте те, которыми владеете.

# 5. Консьюмеры

## Описание

Консьюмер — клиент, который читает записи из партиций топика. Обычный путь — группа, подписка и цикл poll. Консьюмер фиксирует офсеты, чтобы продолжить после перезапуска.

Эта тема покрывает API консьюмера, subscribe против assign, цикл poll, режимы фиксации, риски `enable.auto.commit`, тайм-ауты poll и сессии, типы ребаланса и seek. Завершите эту тему после темы 4. Тема 6 подробнее покрывает группы консьюмеров. Тема 7 покрывает семантику доставки.

Используйте один термин для каждого понятия. Poll — вызов, который получает записи и ведёт консьюмера. Фиксация сохраняет офсет для группы и партиции. Subscribe позволяет группе назначать партиции. Assign задаёт партиции в клиенте. Используйте кластеры KRaft. Консьюмер говорит с брокерами, не с ZooKeeper.

## API консьюмера

API консьюмера — клиентский интерфейс, который читает записи. В Java тип — `KafkaConsumer`. В других языках есть тип консьюмера с той же идеей: настроить, subscribe или assign, poll, commit, close.

Типичная последовательность:

1. Соберите конфигурацию. Задайте `bootstrap.servers`. Задайте `group.id` для пути группы. Задайте десериализаторы для ключа и значения.
2. Создайте консьюмера.
3. Подпишитесь на имена топиков или назначьте объекты партиций.
4. Цикл: вызывайте `poll` с тайм-аутом. Обрабатывайте записи. Фиксируйте, когда требует политика.
5. Вызовите `close`, когда процесс заканчивается. `close` может вызвать выход из группы и ребаланс.

`group.id` идентифицирует группу консьюмеров. Два процесса с одним `group.id` делят партиции. Новый `group.id` читает независимо.

`auto.offset.reset` применяется, когда у группы нет зафиксированного офсета для партиции. `earliest` начинает с самой старой сохранённой записи. `latest` начинает с конца журнала. `none` падает, если офсета нет.

Не делите один объект консьюмера между потоками, если клиент не документирует такое использование. Обычный Java-консьюмер не потокобезопасен.

## Subscribe против assign

`subscribe` регистрирует имена топиков (или шаблон). Координатор группы и assignor выбирают партиции. Когда участники входят или выходят, Kafka переназначает партиции. Это обычный прикладной путь.

`assign` задаёт явный список партиций топика на консьюмере. Консьюмер не входит в ребаланс группы для этого назначения. Список ваш. Если запустить два процесса, которые назначают одну партицию, оба читают те же записи. Автоматического деления нет.

Используйте `subscribe`, когда работники должны делить топик. Используйте `assign` для инструментов, задач воспроизведения и тестов, которые должны закрепить партицию.

Не вызывайте `subscribe` и `assign` конфликтующим образом на одном консьюмере. Выберите один режим.

Подписка в некоторых клиентах может использовать шаблон топика. Используйте узкий шаблон. Широкий шаблон может подписаться на топики, которые вы не хотите.

## Цикл poll

Цикл poll — сердце консьюмера. Каждый вызов `poll`:

- входит в группу и делает heartbeat, как требует клиент
- получает записи из назначенных партиций
- возвращает пакет записей вашему коду

Вы должны вызывать `poll` достаточно часто. Если нет, группа может считать участника мёртвым. Следующие разделы покрывают таймеры.

Обрабатывайте записи, которые вернул `poll`, до следующего вызова `poll`. Не запускайте безграничную работу в других потоках и затем делайте poll без границы. Если обработка медленная, можно превысить `max.poll.interval.ms`.

`max.poll.records` ограничивает, сколько записей возвращает один `poll`. Меньшее значение укорачивает каждый срез обработки. Большее значение повышает пропускную способность и риск длинного среза.

Не блокируйтесь навсегда внутри цикла. Ограничивайте внешние вызовы. Тема 19 пути повторяет это правило как backpressure.

Пустой poll нормален. Тайм-аут на `poll` — максимальное ожидание записей, не ошибка.

## Автофиксация против ручной фиксации

Фиксация пишет офсет группы для партиции в Kafka (топик `__consumer_offsets`). После перезапуска консьюмер продолжает с зафиксированной позиции.

**Автофиксация.** Клиент фиксирует по таймеру, когда `enable.auto.commit` истинно. Таймер — `auto.commit.interval.ms`. Клиент фиксирует офсеты, которые консьюмер вернул из `poll`, а не офсеты, которые ваша бизнес-логика закончила, если вы не заканчиваете работу до следующей точки фиксации.

**Ручная фиксация.** Ваш код вызывает `commitSync` или `commitAsync` (имена Java) после завершения работы. Синхронная фиксация ждёт брокера. Асинхронная фиксация не ждёт. Комбинируйте их с ясной политикой.

Ручная фиксация даёт контроль. Можно фиксировать после записи в базу данных. Можно фиксировать каждую запись или каждый пакет.

Обработка at-least-once — обычный результат: если упасть после работы и до фиксации, обработаете снова. Тема 7 покрывает этот случай.

Не смешивайте политики в одной команде без письменного правила.

## Ловушки `enable.auto.commit`

`enable.auto.commit=true` удобно. Это также легко сделать неправильно.

Ловушка 1: вы обрабатываете запись после того, как клиент её уже зафиксировал. Падение тогда пропускает запись. Это at-most-once. Это происходит, когда вы ещё работаете с записями, пока срабатывает таймер автофиксации, или когда передаёте записи другому потоку.

Ловушка 2: вы падаете после обработки, но до следующей автофиксации. Вы обрабатываете снова. Это at-least-once. Появляются дубликаты.

Ловушка 3: вы думаете, что автофиксация означает «фиксировать, когда я закончил свою функцию». Это не так. Это означает «фиксировать по таймеру клиента и циклу poll».

Ловушка 4: ребаланс может произойти, пока автофиксация и обработка перекрываются. Можно зафиксировать или пропустить неожиданным образом, если другие потоки держат записи.

Для обучения выключите автофиксацию. Фиксируйте в своём коде после завершения работы. Если оставляете автофиксацию включённой, заканчивайте всю работу по записям poll до следующего вызова `poll` и не передавайте записи другим потокам.

## `max.poll.interval.ms` и тайм-аут сессии

У консьюмера два важных таймера.

`session.timeout.ms` (вместе с интервалом heartbeat) контролирует живость процесса в группе. Если heartbeat останавливаются, координатор удаляет участника. Heartbeat могут идти в фоновом потоке в текущих Java-клиентах.

`max.poll.interval.ms` контролирует, сколько группа разрешает между двумя вызовами `poll`. Если обработка занимает больше этого интервала, координатор удаляет участника, даже если heartbeat ещё идут. Партиция назначается другому участнику. Ваш старый участник затем может фиксировать или обрабатывать записи, которыми больше не владеет. Это серьёзный баг.

Задайте `max.poll.interval.ms` выше вашего худшего времени обработки одного пакета poll. Или уменьшите `max.poll.records`, чтобы каждый пакет был меньше.

`heartbeat.interval.ms` должен быть ниже `session.timeout.ms`. Официальные документы дают отношение. Не задавайте случайные значения.

Эти таймеры — не то же самое, что `delivery.timeout.ms` у продюсера.

## Ребаланс: eager против cooperative

Ребаланс — изменение назначения партиций в группе. Участники входят, выходят или падают. Assignor вычисляет новое назначение.

**Eager-ребаланс** (старый протокол по умолчанию). Все участники сначала отзывают все партиции. Потребление останавливается. Затем участники получают новое назначение. Это пауза stop-the-world. Тема 6 покрывает взгляд группы на эту паузу.

**Cooperative-ребаланс** (инкрементальный). Участники отзывают только партиции, которые должны отдать. Остальные оставляют. Потребление продолжается на партициях, которые не двигаются.

Используйте cooperative sticky assignor для новых приложений, когда клиент его поддерживает. Пример имени Java: `CooperativeStickyAssignor`. Задайте `partition.assignment.strategy` соответственно.

Во время ребаланса фиксируйте офсеты партиций, которые отзываете. У текущих клиентов есть callback отзыва. Фиксируйте в callback отзыва, когда используете ручную фиксацию.

Не берите длинную блокировку в callback ребаланса. Можно превысить таймеры и вызвать ещё один ребаланс.

## Seek, начало, конец

Seek перемещает позицию консьюмера в партиции. Следующий `poll` читает с этого офсета.

- Seek к офсету. Нужно назначить партицию (или подождать, пока её назначат). Некоторые клиенты требуют poll до seek.
- Seek к началу. Следующее чтение — самый ранний сохранённый офсет.
- Seek к концу. Следующее чтение — конец журнала. Вы пропускаете существующие записи.

Seek не всегда фиксирует. Если сделать seek и затем упасть до фиксации, группа может перезапуститься на старом зафиксированном офсете. Если хотите, чтобы seek пережил перезапуск, фиксируйте после seek (или используйте инструмент сброса admin).

Инструмент consumer-groups может сбросить офсеты для простаивающей группы. Используйте этот инструмент для эксплуатации. Используйте seek в работающем консьюмере для воспроизведения в процессе.

Не делайте seek на партиции, которой не владеете в группе subscribe. Назначение может измениться.

`--from-beginning` у консольного консьюмера — seek к началу для этого старта, часто с новой группой.

# 13. Конфигурация и настройка

## Описание

Эта тема показывает конфигурацию и частые шаблоны настройки в PostgreSQL 16 и PostgreSQL 17. Вы узнаёте настройки памяти, checkpoint, журнал медленных операторов, представления активности и блокировок, keyset-пагинацию, покрывающие индексы, `max_connections` и реплики чтения.

Сначала завершите тему 12. Вы умеете именовать сессии через `application_name`. Завершите эту тему до укрепления продакшена.

Используйте один термин для каждого понятия. Настройка — имя, которое используют `SHOW` и `postgresql.conf`. `shared_buffers` — кэш страниц сервера внутри PostgreSQL. `work_mem` — память на один шаг сортировки или хеша. Checkpoint — сброс грязных страниц и позиция WAL. Keyset-пагинация — поиск по последнему виденному ключу сортировки. Покрывающий индекс включает дополнительные столбцы, чтобы index-only scan мог избежать кучи. Этот справочник рассчитан на PostgreSQL 16 и PostgreSQL 17.

## `shared_buffers`, `work_mem`, `effective_cache_size`

PostgreSQL использует несколько настроек памяти. Это не одна ручка «процент ОЗУ».

**`shared_buffers`** — общий кэш страниц таблиц и индексов. Частый старт — около 25 процентов ОЗУ машины на выделенном хосте, с верхней границей, которую измеряете. Кэш операционной системы всё ещё держит страницы. Не задавайте `shared_buffers` почти на всю ОЗУ.

**`work_mem`** — предел на одну операцию сортировки или хеша в одном шаге запроса. Запрос может использовать несколько шагов. Многие сессии могут сортировать одновременно. Хост с `max_connections = 200` и `work_mem = 100MB` может запросить больше ОЗУ, чем есть у машины. Начинайте низко (например `8MB` или `16MB`). Поднимайте для известного тяжёлого запроса в этой сессии: `SET work_mem = '64MB';`.

**`maintenance_work_mem`** — для `VACUUM`, `CREATE INDEX` и `ALTER TABLE`. Одна команда обслуживания использует этот бюджет. Можно задать выше `work_mem`, потому что мало заданий обслуживания идут сразу.

**`effective_cache_size`** — подсказка планировщику. Это не выделение. Задавайте примерно ОЗУ, которую ждёте для кэша ОС плюс `shared_buffers` (часто 50–75 процентов ОЗУ на выделенном хосте). Неверное значение ОЗУ не выделяет. Может сменить, выберет ли планировщик индекс.

```sql
SHOW shared_buffers;
SHOW work_mem;
SHOW maintenance_work_mem;
SHOW effective_cache_size;
```

Не копируйте блог, который задаёт `shared_buffers = 80%` и `work_mem = 1GB` на общем ноутбуке. Не поднимайте `work_mem` глобально, чтобы починить один отчёт. Не считайте `effective_cache_size` резервом памяти.

Официально: [https://www.postgresql.org/docs/17/runtime-config-resource.html](https://www.postgresql.org/docs/17/runtime-config-resource.html).

## Checkpoint и `max_wal_size`

Checkpoint сбрасывает грязные буферы и записывает позицию. Восстановление начинается с последнего checkpoint и затем проигрывает WAL. Слишком частые checkpoint дают лишние записи. Слишком долгие checkpoint растят WAL и удлиняют восстановление после сбоя.

**`max_wal_size`** — цель роста WAL между checkpoint. Когда WAL растёт к этому размеру, сервер начинает checkpoint. **`min_wal_size`** — пол для переработанных файлов WAL.

**`checkpoint_timeout`** — лимит времени между checkpoint (часто по умолчанию 5 минут). Сервер делает checkpoint по более раннему из лимита времени и триггера размера WAL.

```sql
SHOW max_wal_size;
SHOW min_wal_size;
SHOW checkpoint_timeout;
SELECT * FROM pg_stat_bgwriter;
```

`pg_stat_bgwriter` и в PostgreSQL 17 связанные представления I/O помогают видеть активность checkpoint. В PostgreSQL 16 также есть `pg_stat_io` для статистики I/O. Используйте представления, которые поставляет ваша мажорная версия.

`CHECKPOINT` запускает checkpoint сейчас. Используйте в лаборатории. Не запускайте в цикле на продакшене.

Реплика и `archive_command` должны успевать. Большой `max_wal_size` может быть нормален, если диски быстрые и время восстановления приемлемо.

Не задавайте крошечный `max_wal_size`, чтобы «быть в безопасности». Увеличиваете усиление записи. Не игнорируйте всплески checkpoint после массового `COPY`.

Официально: [https://www.postgresql.org/docs/17/wal-configuration.html](https://www.postgresql.org/docs/17/wal-configuration.html).

## Журнал медленных операторов

PostgreSQL может писать строку журнала на каждый оператор, который выполняется не меньше N миллисекунд.

```sql
SHOW log_min_duration_statement;
SET log_min_duration_statement = 200;
```

`0` журналирует каждый оператор. `-1` выключает возможность (частый default). Глобальный `0` на занятом сервере заполняет диск и стоит I/O.

Связанные настройки (обзор):

- `logging_collector` — захватывать журналы в файлы
- `log_directory` и `log_filename` — куда идут файлы
- `log_line_prefix` — добавить время, пользователя, `application_name`, pid
- `log_checkpoints` — журналировать старт и стоп checkpoint
- `log_lock_waits` — журналировать ожидания дольше `deadlock_timeout`
- `log_connections` / `log_disconnections` — полезно в лаборатории; шумно в продакшене

`SET` в сессии хватает, чтобы учиться. `ALTER SYSTEM` плюс `SELECT pg_reload_conf();` меняет работающий сервер, когда настройка перечитываемая.

Читайте журналы, чтобы найти медленный SQL. Затем используйте `EXPLAIN ANALYZE` (тема 5) и `pg_stat_statements`. Не гадайте.

Не оставляйте `log_min_duration_statement = 0` на продакшене. Не журналируйте пароли. Клиентские операторы `SET` могут появиться в журналах; держите секреты вне текста SQL.

Официально: [https://www.postgresql.org/docs/17/runtime-config-logging.html](https://www.postgresql.org/docs/17/runtime-config-logging.html).

## `pg_stat_activity` и блокировки

**`pg_stat_activity`** показывает одну строку на backend. Полезные столбцы: `pid`, `usename`, `application_name`, `client_addr`, `state`, `wait_event_type`, `wait_event`, `query`, `xact_start`, `query_start`.

```sql
SELECT pid, usename, application_name, state, wait_event, left(query, 80)
FROM pg_stat_activity
WHERE datname = current_database()
  AND pid <> pg_backend_pid();
```

Значения `state` включают `active` и `idle in transaction`. Долгий `idle in transaction` блокирует vacuum (тема 7).

**Блокировки:** `pg_locks`, соединённый с `pg_stat_activity`, показывает, кто ждёт. `log_lock_waits` пишет строку журнала. `pg_blocking_pids(pid)` перечисляет блокирующих.

```sql
SELECT * FROM pg_blocking_pids(12345);
```

**`pg_stat_statements`** агрегирует время на нормализованный запрос. Нужны `shared_preload_libraries` и `CREATE EXTENSION` (темы 5 и 9).

```sql
SELECT calls, round(total_exec_time::numeric, 1) AS total_ms, left(query, 80)
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

`pg_cancel_backend(pid)` просит запрос остановиться. `pg_terminate_backend(pid)` завершает сессию. Сначала предпочитайте cancel.

Не запускайте `SELECT * FROM pg_stat_activity` в тесном цикле в приложении. Не выдавайте эти представления всему миру, если они раскрывают текст SQL с секретами.

Официально: [https://www.postgresql.org/docs/17/monitoring-stats.html](https://www.postgresql.org/docs/17/monitoring-stats.html).

## Keyset-пагинация и покрывающие индексы (`INCLUDE`)

`LIMIT` плюс `OFFSET` каждый раз пропускает строки. Страница 100 с `OFFSET 1000` всё равно читает и отбрасывает 1000 строк. Эта цена растёт с номером страницы.

Keyset-пагинация (также метод seek) фильтрует по последней строке, которую клиент уже видел:

```sql
SELECT id, created_at, title
FROM shop.posts
WHERE (created_at, id) < ('2026-09-01 12:00:00+00', 8400)
ORDER BY created_at DESC, id DESC
LIMIT 21;
```

Клиент использует последние `created_at` и `id` предыдущей страницы. Нужен уникальный развязывающий ключ (`id`). Без него две строки с одной меткой времени могут быть пропущены или повторены.

Подходящее B-дерево:

```sql
CREATE INDEX posts_created_id_idx ON shop.posts (created_at DESC, id DESC);
```

`EXPLAIN` должен показать сканирование индекса, которое останавливается после `LIMIT`, а не полную сортировку таблицы.

**Покрывающий** индекс добавляет неключевые столбцы через `INCLUDE`. Планировщик может использовать index-only scan, когда запросу нужны только ключевые столбцы плюс включённые, и карта видимости позволяет.

```sql
CREATE INDEX posts_created_id_inc
    ON shop.posts (created_at DESC, id DESC)
    INCLUDE (title);
```

Столбцы `INCLUDE` не часть порядка поиска. Они всё ещё считаются индексированными столбцами для HOT-обновлений (тема 7). Не `INCLUDE` столбцы, которые обновляете на каждый запрос.

`OFFSET` приемлем для маленьких админских страниц. Это неверный default для бесконечной прокрутки большой таблицы.

Не пагинируйте только по неуникальному столбцу. Не добавляйте пять пересекающихся покрывающих индексов. Не используйте `LIMIT` / `OFFSET`, чтобы спрятать отсутствующий индекс.

## `max_connections` и реплики чтения

`max_connections` — потолок backend сервера. Каждый backend использует память (`work_mem` на шаг плюс оверхед на backend). Операционная система тратит больше времени на переключения контекста, когда сотни backend активны.

Thrashing здесь значит: слишком много backend, слишком мало ОЗУ, тяжёлый swap или вытеснение кэша, и каждый запрос медленнее, чем у меньшего пула.

Шаблон:

1. задайте `max_connections` числом, которое хост может выполнить (часто 100–200 на среднем хосте, не 2000)
2. поставьте впереди PgBouncer или пул драйвера (тема 12)
3. размерьте пул на несколько десятков серверных подключений для OLTP
4. используйте отдельный маленький пул для админки и миграций

```sql
SHOW max_connections;
SELECT count(*) FROM pg_stat_activity;
```

Облачные экземпляры часто задают `max_connections` по классу ОЗУ. Не поднимайте default, чтобы «убрать ошибки слишком многих подключений» без пула. Эта ошибка — сигнал пулить, а не размножать backend.

**Реплика чтения** — hot stand-by (тема 11). Туда отправляете отчётные `SELECT`. Записи остаются на primary.

Правила чтений с реплики:

- терпеть лаг
- терпеть отмену запроса (конфликты `hot_standby`)
- не отправлять записи
- дать реплике свой `max_connections` и пул
- использовать `application_name`, чтобы видеть отчётный трафик

Не задавайте `max_connections` 1000 на хосте 4 ГБ. Не открывайте сессию на каждый HTTP-запрос. Не считайте реплику вторым primary.

1. Посчитайте худший случай ОЗУ: `max_connections * work_mem` плюс `shared_buffers`. Напишите, выдержит ли хост.
2. Спланируйте размеры пулов: API 40, отчёты 10, админка 5, `max_connections` 80. Объясните запас.
3. Из `pg_stat_activity` сгруппируйте по `application_name` и `state`. Напишите, кто держит простаивающие сессии.

#### Сложные практические задания

1. Напишите правило маршрутизации: какие запросы идут на primary, какие на реплику. Включите SLA лага.
2. Прочитайте `max_connections` и зарезервированные подключения (`superuser_reserved_connections`) в документации 17. Напишите, почему оставляете запас для админки.

## Обзор темы

Эти вопросы не повторяют вопросы разделов выше. Они покрывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Как `shared_buffers`, `work_mem` и `max_connections` образуют один бюджет ОЗУ?
2. Когда меняете `max_wal_size` вместо добавления индекса?
3. На какие разные вопросы отвечают журналы медленных запросов и `pg_stat_activity`?
4. Почему keyset-пагинация и `INCLUDE` относятся к одной теме настройки?
5. Коллега поднимает `max_connections`, чтобы починить таймауты, и направляет отчёты на реплику без проверки лага. Какие факты используете в ответе?

#### Простые практические задания

1. `SHOW` `shared_buffers`, `work_mem`, `max_wal_size`, `log_min_duration_statement` и `max_connections`. Сохраните пять значений.
2. Напишите шпаргалку: ручки памяти, checkpoint, журнал медленных, активность, keyset, `INCLUDE`, реплика.
3. Выполните один `EXPLAIN ANALYZE` на постраничном запросе. Запишите тип сканирования.
4. Выберите `count(*)` из `pg_stat_activity`.

#### Средние практические задания

1. Настройте один учебный запрос: `ANALYZE`, один индекс (возможно `INCLUDE`), keyset вместо `OFFSET`. Докажите через `EXPLAIN ANALYZE`.
2. Вызовите ожидание блокировки. Найдите его в `pg_stat_activity` и `pg_blocking_pids`. Зажурналируйте, если `log_lock_waits` включён.
3. Нарисуйте схему пула и реплики с `application_name` на каждом пути.

#### Сложные практические задания

1. Напишите порядок настройки на одну страницу: измерить (`pg_stat_statements`, журналы), план (`EXPLAIN`), индекс, память, checkpoint, пул, реплика. Дайте по одному примеру на каждом шаге.
2. Сопоставьте эту тему с официальными главами ресурсов, WAL, журналирования и мониторинга. Добавьте одно представление 16-или-17, которое тема назвала только мимоходом.

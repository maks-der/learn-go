# 12. Контекст

## Описание

`context.Context` несёт крайний срок, сигнал отмены и необязательные значения запроса через границы API. Передавайте контекст первым параметром функции. Вызываемый код останавливает работу, когда контекст завершён.

Эта тема учит, зачем существует контекст и как использовать стандартные конструкторы. Завершите тему 11 до этой темы. Нужно знать `goroutine`, `channel` и `select`.

Для каждого понятия используйте одно слово. Контекст — не мешок необязательных параметров. Функция отмены не необязательна. Нужно вызвать отмену, когда создаёте производный контекст.

---

## Зачем существует `context.Context`

Сервер обрабатывает много запросов одновременно. Каждый запрос запускает работу: запрос к базе данных, HTTP-вызов, воркер. Клиент может отключиться. Крайний срок может истечь. Процесс может завершаться. Работа должна остановиться. Если работа не останавливается, вы утекаете `goroutine`, держите соединения и тратите CPU.

`context.Context` — стандартный тип для этого сигнала. Интерфейс находится в пакете `context`:

```go
type Context interface {
    Deadline() (deadline time.Time, ok bool)
    Done() <-chan struct{}
    Err() error
    Value(key any) any
}
```

`Done` закрывается, когда работа должна остановиться. `Err` объясняет почему. `Deadline` сообщает время, если крайний срок есть. `Value` возвращает значение в рамках запроса.

До `context` пакеты изобретали свои каналы отмены и тайм-ауты. Эти типы не сочетались. Функция, которая вызывает две библиотеки, не имела общего типа отмены. Стандартный тип `Context` это решает. Начиная с Go 1.7, `net/http` использует контекст на запросе. Остальная стандартная библиотека последовала.

Контекст образует дерево. Начинаете от корня. Порождаете детей через `WithCancel`, `WithTimeout`, `WithDeadline` или `WithValue`. Когда родитель завершён, дети завершены. Отмена ребёнка не отменяет родителя.

Не используйте контекст как общий объект конфигурации. Не храните контекст в долгоживущем поле структуры, если структура — не та работа, которую контролирует контекст (редкий случай). Передавайте контекст вниз по цепочке вызовов.

## `context.Background`, `TODO`

`context.Background` возвращает пустой корневой контекст. Этот контекст никогда не отменяется. У него нет крайнего срока. У него нет значений. Используйте `Background` на вершине функции `main`, в `init`, когда нужно, и в тестах, когда начинаете дерево.

```go
ctx := context.Background()
```

`context.TODO` тоже возвращает пустой контекст. Используйте `TODO`, когда не знаете, какой контекст передать. `TODO` — метка для поздней работы. Замените `TODO` настоящим контекстом, когда цепочка вызовов ясна.

```go
ctx := context.TODO()
```

`Background` и `TODO` не отменяются, когда запрос заканчивается. Если передадите их в обработчик сервера вместо `r.Context()`, обработчик не остановится, когда клиент отключится.

Не создавайте новый `Background` в каждом помощнике. Порождайте от контекста, который передал вызывающий. Не используйте `TODO` в открытом API, у которого уже есть запрос или родительский контекст.

В тестах `Background` обычен для модульного теста, которому не нужен крайний срок. Предпочитайте `WithTimeout` в тестах, которые могут зависнуть.

Две функции возвращают контекст, который реализует интерфейс `Context`. Их не закрывают. Для них не вызывают функцию отмены. Порождайте детей, когда нужна отмена или крайний срок.

## `WithCancel`, `WithTimeout`, `WithDeadline`

Эти функции порождают дочерний контекст от родителя. Каждая функция возвращает новый контекст и функцию отмены.

```go
ctx, cancel := context.WithCancel(parent)
defer cancel()

ctx, cancel := context.WithTimeout(parent, 2*time.Second)
defer cancel()

ctx, cancel := context.WithDeadline(parent, time.Now().Add(5*time.Second))
defer cancel()
```

Нужно вызвать `cancel`. Функция отмены освобождает ресурсы, которые держит ребёнок (таймер, узел в дереве). `defer cancel()` — обычная форма. Второй вызов `cancel` безопасен. Он ничего не делает.

`WithCancel` завершён, когда вызываете `cancel` или когда родитель завершён.

`WithTimeout` завершён, когда длительность заканчивается, когда вызываете `cancel` или когда родитель завершён. `WithTimeout` — это `WithDeadline` с `time.Now().Add(timeout)` как крайним сроком.

`WithDeadline` завершён, когда часы достигают крайнего срока, когда вызываете `cancel` или когда родитель завершён.

После завершения ребёнка `ctx.Err()` равен `context.Canceled` или `context.DeadlineExceeded`. Если родитель завершён первым, ребёнок сообщает ошибку родителя.

Начиная с Go 1.21:

- `WithCancelCause` записывает причину. `context.Cause(ctx)` возвращает эту ошибку.
- `WithTimeoutCause` и `WithDeadlineCause` существуют для той же цели.
- `WithoutCancel(parent)` возвращает ребёнка, который не отменяется, когда отменяется родитель. У ребёнка нет крайнего срока и `Done` равен `nil`. Значения родителя остаются. Прочитайте `go doc context.WithoutCancel` перед использованием этой функции.
- `AfterFunc(ctx, f)` запускает `f` в новой `goroutine` после завершения `ctx`.

Не игнорируйте функцию отмены. Не ждите только тайм-аут и не пропускайте `cancel` после успеха. Таймер может остаться до конца длительности, если никогда не отменяете.

## `WithValue` (и почему избегать его для необязательных параметров)

`WithValue` возвращает дочерний контекст, который хранит один ключ и одно значение.

```go
type traceIDKey struct{}

ctx := context.WithValue(parent, traceIDKey{}, "abc123")
id, ok := ctx.Value(traceIDKey{}).(string)
```

Поиск идёт от ребёнка к родителю. Ребёнок может перекрыть ключ. `Value` возвращает `nil`, когда ключа нет.

Используйте `WithValue` только для данных в рамках запроса, которые не входят в сигнатуру функции. Типичные значения — идентификатор трассировки, идентификатор запроса или личность пользователя для журнала и диагностики.

Не используйте `WithValue` для необязательных параметров. Не кладите в контекст дескриптор базы данных, журнал, который функция обязана иметь, или структуру конфигурации. Эти значения принадлежат параметрам или структуре, которую передаёте явно. Скрытые параметры делают функцию трудной для тестов и трудной для чтения.

Тип ключа должен быть сравнимым. Используйте неэкспортированный тип структуры как ключ. Строковый ключ может столкнуться с другим пакетом, который использует ту же строку.

```go
// good key
type ctxKey struct{}

// collision risk
ctx = context.WithValue(ctx, "user", u)
```

`WithValue` не меняет отмену или крайний срок. Ребёнок завершён, когда родитель завершён.

Не храните большой объект в каждом производном контексте, если можно этого избежать. Каждый `WithValue` добавляет узел в дерево.

## Продвижение контекста через API

Первый параметр функции, которая может блокироваться, делать ввод-вывод или запускать работу, — `ctx context.Context`. Имя — `ctx`. Тип — интерфейс, не указатель.

```go
func FetchUser(ctx context.Context, id string) (User, error) {
    return db.QueryUser(ctx, id)
}
```

Передавайте тот же `ctx` каждому вызываемому коду, который делает работу для этого запроса. Порождайте ребёнка, когда вызываемому коду нужен более короткий тайм-аут или локальная отмена.

```go
func FetchUser(ctx context.Context, id string) (User, error) {
    ctx, cancel := context.WithTimeout(ctx, 300*time.Millisecond)
    defer cancel()
    return db.QueryUser(ctx, id)
}
```

Не храните `ctx` в структуре, которая переживает запрос. Типичный сервер не хранит контекст в структуре сервиса. Каждый метод получает `ctx` от обработчика.

Исключение — воркер, который запускаете с контекстом и который выходит, когда контекст завершён. Воркер держит контекст на своё время жизни, не на время жизни процесса.

Не запускайте `goroutine` с контекстом запроса и затем не возвращайтесь из обработчика, пока эта `goroutine` всё ещё использует контекст. Сервер отменяет контекст запроса, когда обработчик возвращает управление. `goroutine` видит `Canceled`. Если работа должна продолжаться после ответа, породите новый контекст от `Background` или от контекста завершения сервера, скопируйте нужные значения и задайте новый тайм-аут. `context.WithoutCancel` (Go 1.21) может отсоединиться от отмены родителя. Всё равно нужно задать крайний срок и всё равно нужно избегать утечек.

Возвращайте `ctx.Err()`, когда останавливаетесь, потому что контекст завершён. Не скрывайте эту ошибку без причины. Вызывающему нужно знать, что работа отменена.

Оставляйте параметр контекста даже когда текущее тело его не использует. Следующий вызов ввода-вывода будет в нём нуждаться. Линтер может требовать, чтобы первый параметр был контекстом.

## Ожидание `ctx.Done()`

`ctx.Done()` возвращает `channel`. `channel` закрывается, когда контекст завершён. Приём из `Done` в этот момент успешен. Не отправляйте в `Done`. Только принимайте.

Обычное ожидание — `select`:

```go
select {
case <-ctx.Done():
    return ctx.Err()
case v := <-results:
    return handle(v)
}
```

Проверяйте `ctx.Err()` после закрытия `Done`. `Err` равен `nil`, пока контекст не завершён. После завершения контекста `Err` не равен `nil`.

Цикл опроса может проверять `Err` без `select`:

```go
for {
    if err := ctx.Err(); err != nil {
        return err
    }
    if done := step(); done {
        return nil
    }
}
```

Опрос без ожидания сжигает CPU. Предпочитайте `select` на `Done` и на рабочем `channel`.

`Done` может вернуть `nil` для контекста, который никогда не отменяется (`Background`). Приём из `nil` `channel` блокируется навсегда. Это верно для `Background`: работа не отменяется.

Не закрывайте `Done` сами. Пакет `context` владеет этим `channel`.

Совмещайте `Done` с вводом-выводом, который не принимает контекст. Запустите ввод-вывод. Ждите в `select` на `Done` и на `channel` результата. Если побеждает `Done`, бросьте или отмените ввод-вывод так, как позволяет библиотека. Если у библиотеки нет отмены, можно утечь `goroutine`. Предпочитайте API, которые принимают контекст.

Начиная с Go 1.21, `context.AfterFunc` может выполнить очистку, когда `Done` закрывается. В основном потоке по-прежнему можно использовать `select`.

## HTTP и отмена контекста

Входящие HTTP-запросы несут контекст. `r.Context()` завершён, когда клиент отключается, когда обработчик возвращает управление или когда сервер достигает настроенного тайм-аута.

```go
func handler(w http.ResponseWriter, r *http.Request) {
    ctx := r.Context()
    row, err := store.Load(ctx, r.PathValue("id"))
    if err != nil {
        if errors.Is(err, context.Canceled) {
            return
        }
        http.Error(w, "unavailable", http.StatusServiceUnavailable)
        return
    }
    // write row
}
```

Начиная с Go 1.22, шаблоны `ServeMux` могут включать метод и подстановки пути. `r.PathValue` читает подстановку. Это изменение маршрутизации. Правила контекста те же.

Исходящие HTTP-вызовы должны использовать контекст:

```go
req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
if err != nil {
    return err
}
resp, err := client.Do(req)
```

Не используйте `http.NewRequest` и затем не игнорируйте отмену. `NewRequestWithContext` — текущий API. `Request.WithContext` существует для копии запроса.

У `http.Client` также есть `Timeout`. Этот тайм-аут покрывает весь вызов. Крайний срок контекста и тайм-аут клиента могут действовать оба. Предпочитайте один ясный крайний срок. Контекст входящего запроса — обычный родитель для исходящих вызовов. Порождайте более короткий тайм-аут, когда нижестоящий должен отказать первым.

Тайм-ауты сервера:

- `ReadTimeout` и `WriteTimeout` на `http.Server`
- `http.TimeoutHandler` для крайнего срока обработчика
- `Server.Shutdown(ctx)` для корректного завершения

`Shutdown` останавливает новые соединения. Он ждёт обработчиков. `ctx` у `Shutdown` задаёт предел этого ожидания. Обработчики по-прежнему видят контекст своего запроса.

Зарегистрируйте сигнал в `main`. Отмените корневой контекст на `SIGINT` или `SIGTERM`. Передайте этот контекст в `Shutdown`. Тема 18 разбирает корректное завершение в полном сервисе.

Тестируйте отмену через `httptest` (тема 13). Закройте соединение клиента или отмените контекст запроса и проверьте, что обработчик возвращает управление.

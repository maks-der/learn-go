# 11. Протоколы приложения: HTTP

## Описание

HTTP — протокол приложения для сообщений запроса и ответа. Эта тема показывает URL, методы, коды состояния, заголовки, тела, keep-alive HTTP/1.1, заголовок Host, cookie, превью TLS для HTTPS, `curl -v` и прокси.

Используйте один термин для каждого понятия. Запрос — сообщение клиента. Ответ — сообщение сервера. Завершите эту тему после TCP и сокетов. Поздние темы покрывают HTTP/2, HTTP/3 и TLS глубже.

Практикуйтесь с `curl -v` и браузером. Захватывайте HTTP на порту 80, когда сайт ещё это разрешает. HTTPS скрывает байты HTTP. Вы всё равно видите TCP и TLS.

## URL, метод, статус, заголовки, тело

URL называет ресурс. Обычная форма — `scheme://host:port/path?query#fragment`. Схема — `http` или `https`. Хост — имя или IP-адрес. Порт по умолчанию — 80 для HTTP и 443 для HTTPS. Путь — ресурс на сервере. Запрос — строка параметров. Фрагмент остаётся в клиенте. Клиент не отправляет фрагмент серверу.

Метод — глагол запроса. Обычные методы: `GET` (читать), `POST` (отправить тело), `PUT` (сохранить), `DELETE` (удалить), `HEAD` (только заголовки), `OPTIONS` (разрешённые методы). Используйте `GET` для безопасных чтений. Используйте `POST`, когда у запроса есть побочный эффект, который кэш не должен повторять как GET.

Код состояния — трёхзначное число в ответе. 1xx — информационный. 2xx — успех (`200` OK). 3xx — перенаправление (`301`, `302`, `304`). 4xx — ошибка клиента (`400`, `403`, `404`). 5xx — ошибка сервера (`500`, `502`, `503`). Сначала читайте класс, затем точный код.

Заголовки — строки имя-значение. Заголовки запроса включают `Host`, `User-Agent`, `Accept` и `Content-Type`, когда есть тело. Заголовки ответа включают `Content-Type`, `Content-Length` или `Transfer-Encoding`, `Location` при перенаправлениях и `Set-Cookie`.

Тело необязательно. У `GET` часто нет тела. У `POST` часто есть тело. Тело — байты. `Content-Type` называет формат (`text/html`, `application/json`).

Текст HTTP/1.1 начинается со строки запроса или строки статуса, затем заголовки, затем пустая строка, затем тело. Не забывайте пустую строку.

## Keep-alive HTTP/1.1

HTTP/1.0 часто закрывал соединение TCP после одного ответа. HTTP/1.1 использует постоянные соединения по умолчанию. Клиент и сервер могут отправлять больше запросов и ответов на том же соединении TCP. Это keep-alive.

Keep-alive избегает нового рукопожатия и нового slow start для каждого изображения или скрипта. Клиент всё равно должен разобрать каждый ответ. HTTP/1.1 на одном соединении последовательный: клиент обычно ждёт ответа до следующего запроса (если не использует pipelining, который редок и хрупок). Многие браузеры открывают несколько соединений TCP к одному хосту.

Заголовок `Connection: close` просит закрыть после этого ответа. Сервер тоже может закрыть. Клиент должен обработать закрытие и повторить или открыть новое соединение по политике.

Таймауты простоя закрывают тихое соединение keep-alive. У прокси может быть более короткое время простоя, чем у клиента. Следующему запросу тогда нужна новая сессия TCP.

Не считайте, что один `curl` без `-v` показывает keep-alive. Смотрите заголовки и захват пакетов. Не конвейеризуйте запросы, если не знаете, что сервер это поддерживает.

HTTP/2 мультиплексирует много потоков на одном соединении. Это поздняя тема. Keep-alive HTTP/1.1 всё ещё один запрос за раз на соединение в обычном случае.

## Заголовок Host и виртуальные хосты

Заголовок Host обязателен в HTTP/1.1. Он несёт имя хоста (и порт, если порт не по умолчанию). Пример: `Host: example.com`. Пример: `Host: localhost:8080`.

Один IP-адрес может обслуживать много сайтов. Сервер читает заголовок Host и выбирает файлы сайта или конфигурацию виртуального хоста. Это виртуальный хост. Без Host сервер не может отличить `a.example` от `b.example` на одном сокете.

У TLS есть Server Name Indication (SNI) в рукопожатии. SNI называет хост до начала HTTP. Сервер может выбрать сертификат. Виртуальным хостам HTTPS нужны SNI, затем всё равно Host в HTTP. Поздняя тема TLS идёт глубже.

Неверный Host может вернуть сайт по умолчанию или `400`. Некоторые серверы отвергают отсутствующий Host. `curl` ставит Host из URL. Сырой клиент TCP, который пишете, должен отправить Host.

Не кладите схему в Host. Не используйте IP как Host, когда нужен виртуальный хост по имени, если это имя не сам IP намеренно.

DNS сопоставляет имя с адресом. Host говорит приложению, какое имя спросил пользователь. Оба нужны для размещения по имени.

## Cookie

Cookie — маленький кусок состояния, который сервер просит клиента сохранить. Заголовок ответа `Set-Cookie` отправляет cookie. Клиент позже отправляет заголовки запроса `Cookie` на подходящих запросах.

У cookie есть имя, значение и атрибуты: `Domain`, `Path`, `Expires` или `Max-Age`, `Secure`, `HttpOnly`, `SameSite`. `Secure` значит отправлять только по HTTPS. `HttpOnly` значит, что скрипт страницы не должен читать cookie. `SameSite` ограничивает межсайтовые отправки.

Cookie — не секретное хранилище. Кто может прочитать заголовок cookie, может выдать себя за сессию, если cookie — id сессии. Используйте HTTPS. Используйте `Secure` и строгий `SameSite`, когда можете.

Клиент хранит cookie по профилю браузера. `curl` не держит cookie, если не используете `-c` и `-b` или `--cookie-jar`.

Не кладите пароли в cookie. Не используйте огромный cookie как базу данных. Не игнорируйте `SameSite`, когда отлаживаете отсутствующий cookie на межсайтовом запросе.

Cookie — не единственный метод сессии. Есть также заголовки Authorization и сессии на сервере. Этот раздел — механизм cookie HTTP.

## Превью HTTPS (TLS)

HTTPS — HTTP поверх TLS. TLS даёт конфиденциальность, целостность и подлинность сервера (и необязательно клиента). Браузер проверяет сертификат. Сертификат связывает открытый ключ с именем. Поздняя тема покрывает PKI.

Клиент начинает рукопожатие TLS после TCP. Затем клиент отправляет HTTP по защищённому каналу. Захват пакетов показывает TCP и записи TLS. Он не показывает путь URL HTTP, если вы не расшифруете ключом, которым владеете, или не используете локальный прокси, которым управляете.

Схема URL `https` значит порт 443 по умолчанию и требование TLS. Смешанная страница, которая загружает изображения HTTP на сайте HTTPS, — ошибка безопасности в браузере.

Обычные сбои: истёкший сертификат, несовпадение имени, недоверенный издатель и перехватчик в публичном Wi-Fi. Клиент должен остановиться. Не кликайте предупреждение на реальном сайте.

`curl -v` печатает субъекта сертификата и версию TLS. Используйте этот вывод, чтобы учиться. `curl -k` пропускает проверку. Не используйте `-k` в производстве.

Не называйте HTTPS «зашифрованным HTTP» и затем забывайте подлинность. Шифрования без проверки имени недостаточно.

## `curl -v`

`curl` — клиент HTTP командной строки. `-v` (подробный) печатает заголовки запроса, заголовки ответа и детали соединения. Используйте `-v` как учебный инструмент. Используйте `-sS`, когда хотите тихое тело плюс ошибки.

Полезные параметры:

- `-I` или `--head` только заголовки (`HEAD`)
- `-X` задать метод
- `-H` добавить заголовок
- `-d` отправить тело
- `-L` следовать перенаправлениям
- `-o` записать тело в файл
- `-4` и `-6` принудительно выбрать семейство
- `--http1.1` избежать HTTP/2 в клиенте

Читайте подробные строки. `*` — сведения о соединении. `>` — запрос. `<` — ответ. Это разделение тренирует глаз.

`curl` может говорить HTTP/2. Подробный вывод показывает версию. Захват HTTP/2 двоичный. Эта тема всё равно использует текст HTTP/1.1 как учебную форму.

Не вставляйте подробный вывод, в котором есть `Authorization` или cookie реального аккаунта. Не используйте `curl` для атаки хоста. Используйте сайты, которыми владеете, или публичные примеры.

`curl -v` также полезен для ошибок TLS. Сообщение часто называет проверку, которая упала.

## Прокси и обратные прокси

Прямой прокси сидит рядом с клиентом. Клиент отправляет запрос прокси. Прокси открывает соединение к серверу-источнику. Предприятия используют прямые прокси для политики и кэша. Клиент должен быть настроен (`HTTP_PROXY`, настройки браузера). Для HTTPS клиент использует `CONNECT`, чтобы открыть туннель. Прокси видит имя и порт. Нагрузка TLS остаётся непрозрачной, если прокси не перехватывает.

Обратный прокси сидит рядом с серверами. Клиент думает, что говорит с источником. Обратный прокси пересылает внутреннему приложению. TLS может завершаться на обратном прокси. Балансировщики нагрузки и CDN часто действуют как обратные прокси. `Host` и `X-Forwarded-For` (или `Forwarded`) говорят приложению исходного клиента и имя. Доверяйте этим заголовкам только от своего прокси.

Прокси может понимать HTTP (уровень 7) или только пропускать TCP (уровень 4). Эта тема использует случай с пониманием HTTP.

Не выставляйте открытый прямой прокси в Internet. Не доверяйте `X-Forwarded-For` из публичного Internet.

Обратный прокси может добавить keep-alive к клиенту и новый пул соединений к приложению. Таймауты на прокси — обычный источник `502` и `504`.

SOCKS — другое семейство прокси. Браузеры и некоторые инструменты используют SOCKS. Идея всё равно «клиент говорит со средним хопом».

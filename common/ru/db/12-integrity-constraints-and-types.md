# 12. Целостность, ограничения и типы

## Описание

Эта тема показывает, как держать сохранённые значения корректными. Вы изучаете доменные типы, ошибки денег и плавающей точки, часовые пояса, каскадные внешние ключи, мягкое удаление против жёсткого удаления и аудиторские столбцы.

Используйте один термин для каждого понятия. Домен — множество допустимых значений для столбца. Ограничение — правило, которое СУБД проверяет при записи. Тип — имя СУБД для домена. Завершите эту тему после того, как умеете создавать таблицы, ключи и правила `CHECK`. Типы и ограничения — правила, которым эти таблицы должны подчиняться.

Этот путь нейтрален к вендорам. Имена типов отличаются по продукту. Идеи — нет.

## Доменные типы: целые, десятичные, текст, даты, булевы

Доменный тип ограничивает, что столбец может хранить. СУБД отвергает значение, которое не совпадает с типом. Типы — первое правило целостности.

**Целое.** Целое — целое число. Используйте целое для счётчиков, идентификаторов, которые являются числами, и количеств, у которых не может быть дроби. Пример: `quantity` на строке заказа. Не используйте целое для денег.

**Десятичное.** Десятичное хранит число с фиксированной шкалой. Шкала — число цифр после десятичной точки. Точность — общее число цифр. Пример: `NUMERIC(12, 2)` может хранить значения вроде `1999.50` с двумя дробными цифрами. Используйте десятичное, когда дробь должна быть точной.

**Текст.** Текст хранит символы. Используйте ограниченный тип, когда продукт даёт один (`VARCHAR(n)`). Используйте неограниченный тип только когда у длины нет полезного предела. Храните коды в стабильном алфавите. Не храните дату или число как текст, если нужно сортировать или считать по этому значению.

**Дата и время.** Тип даты хранит календарный день. Тип метки времени хранит день и время часов. Тип времени хранит время часов без дня. Используйте эти типы для значений времени. Не храните дату как текст, если нужно сравнивать даты.

**Булево.** Булево хранит истину или ложь. Некоторые продукты также допускают неизвестное (`NULL`). Используйте булево для факта да/нет. Пример: `is_active`. Не используйте целые `0` и `1`, если у продукта нет булева типа.

Выбирайте самый узкий тип, который подходит домену. Узкий тип использует меньше места. Узкий тип также отвергает больше плохих записей.

```sql
CREATE TABLE products (
    product_id   INTEGER PRIMARY KEY,
    sku          VARCHAR(32) NOT NULL,
    name         VARCHAR(200) NOT NULL,
    unit_price   NUMERIC(12, 2) NOT NULL,
    in_stock     BOOLEAN NOT NULL,
    released_on  DATE
);
```

`NULL` не тип. `NULL` значит, что значение отсутствует. Тип плюс `NOT NULL` сильнее, чем тип один.

Не смешивайте единицы в одном столбце. Пример: не храните килограммы и граммы в одном числовом столбце без столбца единицы. Тип не видит единицу.

## Деньги и ловушки плавающей точки

Деньги — счёт единицы валюты. Счёт должен быть точным. Плавающий тип (`REAL`, `FLOAT`, `DOUBLE PRECISION`) — двоичное приближение. У многих десятичных дробей нет точной двоичной формы. Пример: `0.1` плюс `0.2` может не пройти проверку равенства в плавающей точке.

Не храните деньги в плавающем столбце. Используйте десятичный тип с фиксированной шкалой или храните целое число наименьших единиц (центов). Оба метода держат точные суммы.

```sql
-- Prefer a decimal with a known scale
unit_price NUMERIC(12, 2) NOT NULL

-- Or an integer count of cents
unit_price_cents INTEGER NOT NULL
```

Выберите один метод для всей схемы. Не смешивайте доллары как float и центы как целое в одной базе без письменного правила.

Округление — бизнес-правило. Двухдесятичные деньги часто используют банковское округление или округление половины вверх. Десятичный тип СУБД хранит цифры. Ваше приложение или задокументированная функция SQL должна применять правило округления на одном и том же шаге каждый раз.

Валюта — не только число. Цена `10.00` неполна, если не знаете валюту. Используйте столбец кода валюты (`USD`, `EUR`), когда существует больше одной валюты. Не складывайте суммы в разных валютах.

Налоги и скидки создают больше точек округления. Считайте из одного источника истины (цена единицы и количество). Храните итог строки, который выставили. Не пересчитывайте исторический счёт из живых налоговых таблиц, если продукт этого не требует.

Плавающие типы остаются полезны для измерений и научных значений. Они неверный тип для журналов учёта.

## Часовые пояса и UTC

Метка времени без часового пояса — локальное показание часов. СУБД не знает пояс. Метка времени с часовым поясом (или мгновение, хранимое в UTC) называет одну точку на шкале времени.

UTC — стандартная шкала времени. Многие системы хранят мгновения в UTC. Приложение преобразует в локальный пояс только когда показывает значение человеку.

Используйте одно правило для всех мгновений:

1. Получите время от клиента с явным поясом или как UTC.
2. Преобразуйте значение в UTC.
3. Храните UTC.
4. Преобразуйте в пояс пользователя только на слое представления.

Календарная дата (`DATE`) не имеет времени часов и пояса. День рождения — дата. Начало встречи — мгновение. Не храните начало встречи только как дату.

«Местное гражданское время» — другая потребность. Пример: магазин, который открывается в 09:00 в каждом городе. Это значение — время плюс имя пояса, не одно мгновение UTC, пока не выберете день.

```sql
-- Instant: prefer UTC in the column or a timestamptz type
created_at TIMESTAMP NOT NULL  -- store UTC; document the rule

-- Civil date: no zone
birth_date DATE NOT NULL
```

Не дописывайте аббревиатуру пояса вроде `EST` как свободный текст. Аббревиатуры сталкиваются. Используйте имя пояса IANA (`America/New_York`), когда нужно хранить пояс.

Переход на летнее время меняет смещение. Сохранённое мгновение UTC не двигается. Сохранённое локальное время без пояса может стать неоднозначным в часе перекрытия.

Не сравнивайте метки времени, которые смешивают UTC и неизвестный локальный пояс. Сначала преобразуйте.

## Каскадные внешние ключи: `ON DELETE` / `ON UPDATE`

Внешний ключ говорит, что дочернее значение должно совпадать с родительским ключом. СУБД также может определить, что происходит, когда родительская строка меняется.

`ON DELETE` задаёт действие, когда удаляете родительскую строку.

| Действие | Эффект на дочерние строки |
| --- | --- |
| `NO ACTION` / `RESTRICT` | Удаление родителя падает, пока дети существуют |
| `CASCADE` | СУБД удаляет совпадающие дочерние строки |
| `SET NULL` | СУБД ставит внешний ключ в `NULL` (столбец должен допускать `NULL`) |
| `SET DEFAULT` | СУБД ставит внешний ключ в значение по умолчанию |

`ON UPDATE` задаёт действие, когда меняется значение родительского ключа. Применяются те же имена действий. Суррогатные ключи редко меняются. Натуральные ключи меняются чаще. Предпочитайте стабильные ключи, чтобы `ON UPDATE` оставался редким.

```sql
CREATE TABLE orders (
    order_id     INTEGER PRIMARY KEY,
    customer_id  INTEGER NOT NULL,
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id) REFERENCES customers (customer_id)
        ON DELETE RESTRICT
        ON UPDATE CASCADE
);
```

`CASCADE` при удалении удобен и опасен. Удаление одного клиента может убрать все заказы и, если те таблицы тоже каскадируют, все строки заказов. Используйте `RESTRICT` (или `NO ACTION`), когда история должна остаться. Используйте `CASCADE` для принадлежащих частей, которые не имеют смысла без родителя. Пример: строки заказа принадлежат заказу.

`SET NULL` значит «этот ребёнок остаётся, но у него нет родителя». Это действие подходит необязательным связям. Оно не подходит обязательному клиенту на заказе.

Не используйте каскад как замену запланированной процедуре удаления. Знайте полный граф детей до включения `CASCADE`.

Действия по умолчанию отличаются по продукту. Читайте руководство продукта. Пишите действие в операторе `CREATE TABLE`, чтобы схема была явной.

## Мягкое удаление и жёсткое удаление

Жёсткое удаление убирает строку. После `COMMIT` строки нет в таблице. Связанные строки следуют действиям внешнего ключа.

Мягкое удаление оставляет строку и помечает её как удалённую. Типичные метки:

- булево `is_deleted`
- метка времени `deleted_at`, которая `NULL` для живых строк

```sql
ALTER TABLE customers
    ADD COLUMN deleted_at TIMESTAMP;

-- Soft delete
UPDATE customers
SET deleted_at = CURRENT_TIMESTAMP  -- store UTC; see the time-zone section
WHERE customer_id = 42;

-- Live rows
SELECT *
FROM customers
WHERE deleted_at IS NULL;
```

Используйте жёсткое удаление, когда у строки нет юридической или бизнес-ценности после удаления и когда дочерняя история не должна остаться.

Используйте мягкое удаление, когда нужно скрыть строку от обычных запросов, но сохранить её для аудита, отмены или истории уникального ключа.

У мягкого удаления есть цены. Каждый запрос, который значит «живые строки», должен фильтровать метку. Уникальные ключи всё ещё видят удалённую строку, если не спроектируете частичный уникальный индекс или не измените ключ. Внешние ключи всё ещё видят строку. «Удалённый» клиент может всё ещё блокировать нового клиента с тем же email.

Не смешивайте два метода на одной таблице без письменного правила. Не используйте мягкое удаление как резерв. Резерв — копия базы. Мягко удалённая строка всё ещё в живой базе.

Восстановление после жёсткого удаления нуждается в резерве или журнале аудита. Восстановление после мягкого удаления — `UPDATE`, который очищает метку.

## Аудиторские столбцы (`created_at`, `updated_at`)

Аудиторские столбцы записывают, когда строка была создана и когда строка последний раз менялась. Это факты о строке, не времена бизнес-событий.

Типичные столбцы:

| Столбец | Смысл | Кто пишет |
| --- | --- | --- |
| `created_at` | Мгновение первой вставки | Значение по умолчанию СУБД или приложение, один раз |
| `updated_at` | Мгновение последнего обновления | Триггер СУБД или приложение, на каждом обновлении |
| `created_by` | Пользователь или служба, которая вставила строку | Приложение (необязательно) |
| `updated_by` | Пользователь или служба, которая последний раз обновила строку | Приложение (необязательно) |

```sql
CREATE TABLE products (
    product_id  INTEGER PRIMARY KEY,
    name        VARCHAR(200) NOT NULL,
    created_at  TIMESTAMP NOT NULL,
    updated_at  TIMESTAMP NOT NULL
);
```

Храните эти мгновения в UTC. Ставьте `created_at` при вставке. Не меняйте `created_at` при обновлении. Ставьте `updated_at` при вставке (тот же, что `created_at`) и на каждом позднем обновлении.

Значение по умолчанию «сейчас» на столбце помогает `created_at`. Триггер или код приложения должен поддерживать `updated_at`. Одно значение по умолчанию не меняется на `UPDATE`.

Аудиторские столбцы — не полный журнал аудита. Полный журнал аудита хранит старые значения и оператор или образ строки. `updated_at` хранит только время последней записи.

Не используйте `updated_at` как бизнес «статус изменился в», если это не единственные часы статуса, которые нужны. У заказа есть `placed_at`, `shipped_at` и `cancelled_at` как бизнес-времена. У этих столбцов есть смысл. `updated_at` только говорит, что какой-то столбец изменился.

Не доверяйте часам клиента как единственному источнику, если пользователи могут поставить свои часы. Предпочитайте `CURRENT_TIMESTAMP` (или эквивалент вендора) в СУБД.

# 21. Продвинутые темы

## Описание

Продвинутые темы — идеи, которые вы должны узнавать и которые не должны принимать как значение по умолчанию. Эта тема разбирает event sourcing, CRDT на уровне осведомлённости, multi-region active-active, data mesh и lakehouse на уровне осведомлённости, платформенную инженерию и внутренние платформы разработчика, и формальные методы с TLA+ как необязательный инструмент для жёстких протоколов.

Эти идеи дороги. Они решают редкие задачи. Завершите темы 1–20 до этой темы. Вам нужны модульный монолит, ясное владение данными и честная эксплуатация до того, как добавить любой пункт здесь. Сочетайте идеи событий с темой 10. Сочетайте идеи регионов с темами 15 и 19.

Используйте один термин для каждого понятия. Event sourcing — не «мы используем события». CRDT — не общее слияние для каждой формы. Active-active — не multi-AZ. Data mesh — не озеро. Платформа — не логотип кластера. TLA+ — язык спецификации. Вы редко реализуете Raft сами (тема 11).

## Event sourcing (дорого; редкое значение по умолчанию)

Event sourcing хранит источник истины как последовательность событий. Вы перестраиваете состояние переигровкой. Текущий баланс — проекция. Журнал событий — источник истины (тема 9).

Это не то же самое, что «публиковать события после записи строки». Этот шаблон — интеграция, ведомая событиями (тема 10). Event sourcing меняет модель записи.

Цены:

- Нужно версионировать события вечно
- Нужно проектировать правила upcast
- Удаление и исправление PII становятся трудными (закон, тема 1)
- Проекции отстают. UX должен говорить правду (тема 20)
- Стоимость переигровки и хранения растёт
- Людям нужно обучение

Когда может подойти:

- Жёсткий аудит каждого изменения — продукт
- У вас уже есть команда, которая обслуживает журнал событий
- Вы можете сформулировать правила удаления и исправления

Когда не подходит:

- Обычное CRUD-приложение кампуса
- Молодой продукт с меняющимся языком (тема 7)
- Команда из двух человек

CQRS часто появляется с event sourcing (тема 9). CQRS без event sourcing достаточно для многих расколов чтения/записи.

Не начинайте побочный проект на event sourcing, чтобы выглядеть продвинуто. Начинайте со строки и outbox.

Если изучаете, читайте аккуратный источник и напишите ADR, который называет правовое ограничение. Не копируйте слоганы поставщиков.

## CRDT (осведомлённость)

CRDT (conflict-free replicated data type) — структура данных, которую реплики могут обновлять без блокировки. Слияние определено так, что реплики сходятся. Нужно использовать типы, у которых есть эта математика слияния.

CRDT помогают некоторым совместным редакторам и некоторым краевым репликам. Они не сливают произвольные бизнес-объекты. Банковский баланс — не случайная задача CRDT. Деньгам обычно нужен один писатель или аккуратно спроектированный тип и аудит.

Правила осведомлённости:

- Вы можете назвать CRDT, когда статья или продукт заявляет автоматическое слияние
- Вы спрашиваете: какой тип? какие операции? какой видимый пользователю конфликт?
- Вы не добавляете библиотеку CRDT, чтобы «решить офлайн» для корзины магазина без доказательства

Тема 20 сказала, что большинство кампусных приложений используют победу сервера плюс запрос. Это правило остаётся. CRDT — альтернатива для малого набора типов (множества, счётчики, некоторый текст).

Стоимость включает память, сложность и команду, которая может объяснить слияние службе поддержки.

Не изобретайте CRDT. Используйте просмотренную библиотеку, если появляется настоящая нужда продукта. Напишите ADR.

Этот раздел — осведомлённость. Реализовывать тип не нужно.

## Multi-region active-active

Active-active multi-region означает, что больше одного региона принимает записи одновременно. Пользователи могут работать в двух географиях без ожидания failover.

Это не multi-AZ в одном регионе (тема 19). Это не DR active-passive (тема 15).

Жёсткие задачи:

- Задержка между регионами (тема 11)
- Конфликт, если два региона пишут один ключ
- Привязка сессии и идентичности
- Правовое расположение (некоторые данные не должны покидать регион)
- Стоимость тестов и стоимость людей
- Компромиссы CAP практическими словами (тема 11)

Большинство продуктов, которым нужен второй регион, используют active-passive: один регион пишет, другой — резерв. RPO и RTO достаточно (тема 15).

Active-active может подойти продукту с естественным разделом (tenant или регион как владелец записи) и редким глобальным ключом. Глобальный уникальный каталог ISBN с записями на двух континентах — исследовательский проект, если у вас ещё нет платформенной команды.

Не продавайте «active-active» на слайде, если у вас одна primary база в одном регионе. Это заявление ложно.

Если нужно, вам также понадобится тема 16 на высоком уровне дисциплины и правило конфликта, которое продукт принимает.

Консенсус через регионы медленный. Вы редко реализуете его (тема 11). Вы настраиваете продукт, который уже решил подмножество.

## Data mesh / lakehouse (осведомлённость)

Data mesh — организационная и архитектурная идея: доменные команды владеют аналитическими продуктами данных, с поддержкой платформы и общими правилами. Lakehouse — технический стиль, который хранит большие аналитические данные в файлах плюс форматах таблиц и обслуживает запросы вроде склада.

Это термины осведомлённости. Они появляются на слайдах. Они не значение по умолчанию для операционного API каталога.

Правила осведомлённости:

- Операционный источник истины остаётся у владельца (тема 9)
- Аналитические копии могут отставать. Это eventual consistency (тема 7)
- Mesh без владельцев — болото данных
- Lakehouse без правил доступа — утечка (тема 14)
- Mesh не нужен, чтобы экспортировать ночной файл (тема 13)

Маленькая команда использует реплику или экспорт файлов для отчётов. Этого достаточно.

Если организация принимает mesh, ваша работа как архитектора приложения — опубликовать ясный продукт данных: схема, владелец, SLO свежести и класс приватности. Вы не перестраиваете магазин как mesh.

Не переименовывайте общую базу отчётов в mesh. Тема 9 всё равно называет это риском интеграции, если писатели множатся.

Прочитайте один публичный обзор позже. Напишите термины своими словами. Не копируйте длинные отрывки.

## Платформенная инженерия и внутренние платформы разработчика

Платформенная инженерия — работа по строительству внутреннего продукта, которым другие разработчики пользуются, чтобы поставлять. Внутренняя платформа разработчика (IDP) — этот продукт: шаблоны, конвейеры, золотые пути и вымощенная инфраструктура.

Платформа — не Kubernetes сама по себе (тема 19). Платформа — мнениетый путь: «вот как эта компания разворачивает сервис с журналами, идентичностью и базой».

Цели:

- Снизить изобретение каждой команды заново
- Закодировать темы 14–18 как значения по умолчанию
- Держать золотой путь меньше полного облачного каталога

Цены:

- Платформенной команде нужны люди
- Плохая платформа становится воротами, которые никто не может изменить
- Универсальные шаблоны могут бороться с настоящим ограничением

Продуктовая команда из двух человек — не платформенная команда. Они всё равно могут держать маленький золотой путь: один конвейер, один PaaS, одна управляемая база. Это платформенная работа в крошечном масштабе.

Не ждите IDP, чтобы начать модульный монолит. Не стройте IDP, чтобы оправдать микросервисы (тема 12). Выделению всё равно нужна граница.

Если вы присоединяетесь к компании с платформой, сначала изучите золотой путь. Исключению нужны ADR и ограничение времени.

Измеряйте платформу как продукт: время до первого развёртывания и время до новой среды. Это SLI платформы (тема 15).

## Формальные методы (TLA+) — необязательно, высокая ценность для жёстких протоколов

Формальные методы используют математику, чтобы специфицировать и проверять проекты. TLA+ — язык и набор инструментов для этой работы. Вы пишете спецификацию состояний и разрешённых шагов. Проверяльщик модели ищет сломанный инвариант.

Высокая ценность появляется, когда протокол маленький, а ошибки дороги: консенсус, служба блокировок, тонкий failover. Тема 11 сказала, что вы редко реализуете Raft. Если проектируете новый протокол, TLA+ может окупиться.

Эта работа необязательна. Большинству функций приложения она не нужна. Тестов, типов и обзоров достаточно.

Как использовать, если выбираете:

1. Специфицируйте протокол, не весь магазин
2. Назовите инварианты (нет split brain, нет двойного списания)
3. Держите модель крошечной
4. Пусть проверяльщик найдёт контрпример
5. Исправьте спецификацию. Затем напишите код, который соответствует спецификации

Не специфицируйте приложение на 200 страниц. Модель не закончит. Не считайте зелёную модель полной реализацией.

Можно позже прочитать публичный пример TLA+. TLA+ не нужен, чтобы закончить этот путь.

Если поставщик заявляет, что протокол «доказан», спросите, что было специфицировано. Заявление может быть маркетингом.

Сочетайте с тестами хаоса и failover (тема 15). Спецификация не заменяет учение восстановления.

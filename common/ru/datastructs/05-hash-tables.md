# 5. Хеш-таблицы

## Описание

Хеш-таблица отображает ключ в значение в среднем за константное время. Эта тема объясняет хеш-функции, коллизии, метод цепочек, открытую адресацию, коэффициент заполнения, resize, правила ключей и стоимость худшего случая.

Завершите эту тему после массивов и списков. Вы будете использовать хеш-таблицу как множество и как отображение в следующей теме.

Используйте один термин для каждого понятия. **Ключ** — имя для поиска. **Хеш-функция** отображает ключ в целое. **Корзина** — слот в массиве таблицы. **Коллизия** происходит, когда два ключа отображаются в одну корзину. **Коэффициент заполнения** — n, делённое на число корзин. Ключ **хешируемый**, когда вы можете вычислить хеш из него. Ключ **стабильный**, когда его хеш и равенство не меняются, пока ключ живёт в таблице.

## Хеш-функция и коллизии

**Хеш-функция** h отображает ключ в целое. Таблица использует `index = h(key) mod m`, когда в таблице m корзин. Некоторые таблицы используют битовую маску, когда m — степень 2.

Хеш-функция должна быть **детерминированной**. Один и тот же ключ должен давать один и тот же хеш, пока ключ живёт в таблице.

Хеш-функция должна использовать полный ключ (или определённую часть ключа). Если вы хешируете только первую букву строки, многие ключи сталкиваются.

```text
h("cat")  →  81321
index     →  81321 mod m
```

Хеш языка часто не криптографический хеш. Не используйте хеш таблицы как хеш пароля. Хеш таблицы — для распределения в памяти.

Хороший хеш быстрый. Медленный хеш может доминировать в стоимости поиска.

Хороший хеш **равномерный**. Каждая корзина должна получать примерно одно число ключей для типичного входа. Равномерный не значит случайный в смысле безопасности. Это значит, что индексы размазаны.

**Коллизия** происходит, когда два разных ключа получают один индекс корзины. Коллизии нормальны. Нельзя предотвратить все коллизии, когда ключей много. Нужно хранить больше одного ключа в корзине или зондировать другую корзину.

Целочисленные ключи могут использовать функцию смешивания, чтобы соседние целые не все попадали в соседние корзины. Строковые ключи смешивают символы. Этой теме нужна идея: отобразить ключ в целое, затем в корзину.

## Метод цепочек и открытая адресация

**Метод цепочек** хранит небольшую коллекцию в каждой корзине. Обычная коллекция — связный список записей. Каждая запись держит ключ, значение и указатель next.

Чтобы найти ключ, вы хешируете в корзину, затем идёте по цепочке, пока не найдёте равный ключ или не достигнете конца.

```text
m = 4
bucket 0:  (cat → 1) → (dog → 2)
bucket 1:  empty
bucket 2:  (eel → 3)
bucket 3:  empty
```

Вставка добавляет запись в цепочку. Удаление убирает запись из цепочки.

Если хеш равномерный, средняя длина цепочки — коэффициент заполнения. Поиск тогда в среднем Θ(1 + α), где α есть n/m.

**Открытая адресация** хранит записи в самом массиве таблицы. Цепочки нет. Когда корзина занята, вы **зондируете** другую корзину.

**Линейное зондирование** пробует index, index+1, index+2, ... и заворачивается модулем m.

```text
h(key) mod 5 = 2
cells:  [ ] [ ] [A] [B] [ ]
insert C that also hashes to 2
C goes to the first empty cell after 2
```

Поиск следует той же последовательности зондов, пока не найдёт ключ или пустую ячейку.

Удаление в открытой адресации — не простая очистка. Очищенная ячейка может остановить поздний зонд. Многие таблицы хранят **надгробие** (метку удалённого). Поиск пропускает надгробия. Вставка может переиспользовать надгробие.

Открытой адресации нужен коэффициент заполнения ниже 1. В таблице должны быть пустые ячейки. Цепочки могут вырасти за m записей, потому что цепочки сидят вне массива.

**Кластеризация** — пробег полных ячеек при линейном зондировании. Длинные кластеры замедляют поиск и вставку. Есть другие методы зонда (квадратичное зондирование, двойное хеширование). Этой теме нужна идея: вторая формула выбирает следующую ячейку.

## Коэффициент заполнения и resize

**Коэффициент заполнения** α есть n / m. n — число ключей. m — число корзин (или ячеек в открытой адресации).

Когда α мал, многие корзины пусты. Поиск быстрый. Память тратится впустую.

Когда α велик, цепочки длинные или зонды длинные. Поиск медленный.

Таблица делает **resize**, когда α проходит **порог**. Частый порог — около 0.75 для открытой адресации. Цепочки могут использовать похожий порог или больший.

Resize выделяет новый массив с большим m. Частый новый размер — около 2m. Затем вы **перехешируете**: вставляете каждый старый ключ в новую таблицу. Вы не копируете цепочки как есть. Новый модуль меняет индексы.

```text
old m = 4, n = 3, α = 0.75
resize to m = 8
rehash each key with mod 8
```

Перехеширование n ключей есть Θ(n). Эта стоимость похожа на рост динамического массива. Если вы удваиваете m, амортизированная стоимость вставки может остаться Θ(1) при хорошем хеше.

Не делайте resize при каждой вставке. Не выбирайте новое m, которое слишком мало. α остался бы большим.

Некоторые таблицы сжимаются, когда n становится малым. Сжатие тоже перехеширует. Сжатие необязательно.

m часто степень 2, чтобы индекс мог использовать маску. Некоторые таблицы выбирают простое m. Точное правило — деталь реализации. Идея остаётся: m должен расти, когда растёт n.

## Ключи должны быть хешируемыми и стабильными

Ключ должен быть **хешируемым**. Нужно вычислить целочисленный хеш из ключа. Нужно также проверять **равенство**. Поиск использует равенство, а не только хеш. Два ключа могут столкнуться. Только равные ключи — одна запись.

Ключ должен быть **стабильным**, пока живёт в таблице. Стабильность значит:

- хеш ключа не меняется
- равенство с другими ключами не меняется

Если вы кладёте изменяемый объект в таблицу и затем меняете поле, которое использует хеш, ключ сидит в старой корзине. Поиск использует новый хеш. Поиск смотрит в неверную корзину. Запись потеряна.

```text
bad:
  insert object {name: "Ann"}
  change name to "Bob"
  find "Bob" → wrong bucket
  find "Ann" → equality can also fail
```

Безопасные ключи: целые, неизменяемые строки, кортежи неизменяемых значений. Небезопасные ключи: список или запись, которую вы меняете после вставки.

Два равных ключа должны иметь один хеш. Это правило — **контракт хеш-равенства**. Если равные ключи имеют разные хеши, поиск может промахнуться.

Два неравных ключа могут иметь один хеш. Это событие — коллизия. Оно разрешено.

Не используйте меняющийся счётчик или текущее время как часть хранимого ключа.

Некоторые языки запрещают нехешируемые типы как ключи. Некоторые языки не запрещают. Правило всё равно ваше: хешируемый и стабильный.

## Среднее O(1) против деградации худшего случая

Хорошая хеш-таблица даёт **среднее Θ(1)** поиска, вставки и удаления. Среднее предполагает равномерный хеш и ограниченный коэффициент заполнения.

**Худший случай** может быть Θ(n). Все ключи могут попасть в одну корзину. Цепочки тогда обходят n записей. Открытая адресация тоже может зондировать много ячеек, если таблица полна коллизий или надгробий.

```text
average:  hash spreads keys, α is bounded, few probes
worst:    all keys in one chain, find scans n entries
```

У деградации больше одной причины:

- плохая хеш-функция
- слишком большой коэффициент заполнения
- много надгробий
- атакующий, который подбирает сталкивающиеся ключи (в некоторых старых таблицах)

Resize и лучший хеш снижают первые две причины. Периодическая перестройка может очистить надгробия.

Среднее Θ(1) — не гарантия для одной операции. Один поиск всё ещё может просмотреть длинную цепочку.

Если нужна строгая оценка худшего случая, сбалансированное дерево-отображение может дать Θ(log n) для каждого вызова. Тема 6 и тема 9 покрывают этот выбор.

Не говорите «хеш-таблица есть O(1)» без слов «среднее» и допущений.

Некоторые таблицы переключают длинную цепочку в дерево. Этот гибрид улучшает худшую цепочку. Это дополнительный дизайн. Базовая модель остаётся: среднее константное, худшее линейное, пока вы не добавите больше структуры.

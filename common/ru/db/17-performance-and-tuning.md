# 17. Производительность и настройка

## Описание

Эта тема показывает, как найти медленную базу и как менять правильную часть. Вы изучаете измерение, журналы медленных запросов, метрики, кардинальность, статистику, горячие строки, конкуренцию блокировок, пагинацию, кэширование и штормы подключений.

Используйте один термин для каждого понятия. Метрика — число, которое собираете со временем. Кардинальность — число различных значений. Настройка — изменение, которое можете измерить. Завершите эту тему после того, как умеете читать план запроса и использовать индексы. Планы и индексы — обычные первые инструменты.

Не меняйте настройку до того, как есть базовая линия. Измерьте, смените одно, измерьте снова.

## Сначала измеряйте: журнал медленных запросов, метрики

Журнал медленных запросов записывает операторы, которые превышают порог времени. Вы задаёте порог. Журнал даёт текст SQL, длительность и иногда план. Начинайте здесь, когда пользователи говорят «медленно», а вы не знаете, какой оператор.

Метрики — временные ряды: подключения, CPU, ввод-вывод диска, доля попаданий кэша, ожидания блокировок, отставание репликации, скорость транзакций. Метрики показывают форму проблемы (ограничение CPU, ввода-вывода, блокировок, подключений). Они не всегда называют SQL.

```text
User report --> metrics (which resource) --> slow log or traces (which SQL) --> plan --> change
```

Базовая линия — измерение до изменения. Записывайте: текст запроса, длительность, план, числа строк и время суток. Без базовой линии нельзя знать, помогло ли изменение.

Типичные первые вопросы:

1. Насыщен ли хост (CPU, диск, память)?
2. Медленен один оператор или многие операторы ждут?
3. Ожидание на вводе-выводе, на блокировке или на последовательном сканировании?

Не включайте очень низкий порог журнала медленных запросов на занятой продакшен-системе без плана. Журнал может заполнить диск. Используйте образец, более высокий порог или специфичное для продукта хранилище операторов.

Не настраивайте по фольклору («увеличь shared buffers и будет быстро»). Соотносите метрику с оператором.

Метрики приложения важны. Время API 200 мс с 5 мс в СУБД — не проблема базы. Измеряйте обе стороны.

## Кардинальность и статистика

Кардинальность — число различных значений в столбце (или в группе столбцов). Высокая кардинальность значит много различных значений. Пример: уникальный столбец email имеет кардинальность, равную числу строк. Булев столбец имеет кардинальность 2.

Оптимизатор использует статистику, чтобы оценить, сколько строк вернёт фильтр. Статистика — образцы или сводки: числа различных, гистограммы, самые частые значения, доля null. Оптимизатор выбирает план из этих оценок.

```sql
-- High selectivity (few rows) if customer_id is unique in this filter
WHERE customer_id = 42

-- Low selectivity if status has two values and most rows are 'active'
WHERE status = 'active'
```

Если статистика устарела, оценка неверна. Неверная оценка может выбрать вложенный цикл, который должен быть хеш-соединением, или сканирование, которое должно быть поиском. После большой загрузки обновляйте статистику (команда продукта: `ANALYZE` или эквивалент).

Кардинальность результата соединения не произведение размеров таблиц, если ключи совпадают. Оптимизатор использует статистику соединения или допущения. Плохие оценки соединения — обычная причина плохого плана.

Не создавайте индекс на булевом, которое истинно для 99 процентов строк, и не ожидайте, что поиск поможет этим запросам. Низкая селективность благоприятствует сканированию.

Не путайте кардинальность с размером таблицы. Таблица из 10 миллионов строк может иметь столбец кардинальности 10.

Читайте оценку и фактическое число строк в плане, который показывает оба. Большой разрыв значит устаревшую или слабую статистику или корреляцию, которую модель статистики пропускает.

## Горячие строки и конкуренция блокировок

Горячая строка — строка, которую многие транзакции пытаются изменить одновременно. Пример: одна строка счётчика «осталось билетов» или один родительский заказ, который блокирует каждое обновление строки.

Конкуренция блокировок — время ожидания на блокировках. Сессии становятся в очередь. Пропускная способность падает. CPU может выглядеть простаивающим, пока сессии ждут.

```text
Session A: UPDATE counters SET n = n - 1 WHERE id = 1;  -- holds row lock
Session B: same row  -->  wait
Session C: same row  -->  wait
```

Изоляция и блокировки строк корректны. Проект неверен, если одна строка — глобальное узкое место.

Смягчения (выбирайте после измерения):

1. Разделите счётчик на много строк и суммируйте их.
2. Используйте атомарное приращение, которое документирует продукт, если оно снижает время транзакции.
3. Вынесите горячий факт из транзакционной таблицы (очередь, кэш с поздней сверкой), когда бизнес допускает короткую задержку.
4. Укоротите транзакцию. Не держите блокировку горячей строки, пока вызываете сетевой сервис.

Не поднимайте изоляцию до serializable как первое исправление горячей строки. Более сильная изоляция может увеличить ожидания.

Не добавляйте больше серверов приложения, которые все обновляют одну строку. Вы добавляете больше ожидающих.

Читайте метрики ожидания блокировок и блокирующую сессию. Медленный запрос, который держит блокировку, часто причина, не ожидающий, которого увидели первым.

Взаимные блокировки могут появиться, когда две горячие строки обновляются в противоположном порядке. Используйте стабильный порядок блокировок. Повторяйте при взаимной блокировке (более ранняя тема).

## Пагинация (`OFFSET` против keyset)

Пагинация возвращает страницу строк. Есть два обычных метода.

**Пагинация `OFFSET`.** Вы запрашиваете `LIMIT n OFFSET k`. СУБД всё равно проходит или сортирует k + n строк, затем отбрасывает k. Большое k дорого. Пример: страница 1000 с размером страницы 20 использует `OFFSET 19980`.

```sql
SELECT order_id, ordered_at
FROM orders
ORDER BY ordered_at DESC, order_id DESC
LIMIT 20 OFFSET 40;
```

**Пагинация keyset** (метод поиска). Вы просите строки после последнего ключа предыдущей страницы. Запрос использует диапазон по ключу сортировки. Цена остаётся около одной страницы.

```sql
SELECT order_id, ordered_at
FROM orders
WHERE (ordered_at, order_id) < (:last_at, :last_id)
ORDER BY ordered_at DESC, order_id DESC
LIMIT 20;
```

Keyset нужен уникальный ключ сортировки (добавьте первичный ключ, чтобы разорвать ничьи). Keyset не прыгает на страницу 500 без лишней работы. `OFFSET` может прыгать (за цену).

`OFFSET` также дрейфует: новая вставка сверху может сдвинуть строки между страницами. Keyset стабилен для «следующая страница», если используете последний увиденный ключ.

Не используйте `OFFSET` для глубоких страниц на больших таблицах. Не используйте `SELECT *` на широкой таблице для страницы списка.

Индекс, который совпадает с `ORDER BY` (и предикатом keyset), держит страницу дешёвой. Читайте план.

Общий подсчёт (`SELECT COUNT(*)`) — отдельная цена. Не выполняйте полный подсчёт на каждой странице, если UI может показать «ещё» без итога.

## Кэширование перед базой

Кэш хранит результаты запросов или объекты в быстром складе (память, продукт ключ-значение). Приложение сначала читает кэш. При промахе оно читает СУБД и заполняет кэш.

Кэширование помогает, когда:

- одно и то же чтение частое
- результат может быть на несколько секунд или минут старше
- СУБД — узкое место

```text
Read:  cache hit --> return
       cache miss --> DBMS --> fill cache --> return
Write: DBMS commit --> invalidate or update cache keys
```

Инвалидация — трудная часть. Если обновляете строку и оставляете старый ключ кэша, пользователи видят устаревшие данные. Если инвалидируете слишком много ключей, кэш бесполезен и СУБД видит шторм промахов (thundering herd).

Ключи кэша должны включать каждый ввод, который меняет результат (пользователь, страница, локаль). Ключ, который опускает пользователя, может утечь данные между пользователями. Эта утечка — ошибка безопасности.

Не кэшируйте путь записи, который должен оставаться согласованным с ограничениями, если всё ещё не фиксируете в СУБД. Кэш не система учёта.

Не добавляйте кэш, чтобы скрыть запрос N+1 или отсутствующий индекс. Сначала исправьте запрос. Измерьте. Затем кэшируйте, если чтение всё ещё горячее.

Короткий TTL (время жизни) ограничивает устаревание без идеальной инвалидации. TTL — компромисс, не полный проект.

Буферный кэш СУБД не этот кэш. Буферный кэш держит страницы. Кэш приложения держит результаты.

## Штормы подключений

Шторм подключений — внезапное большое число новых сессий СУБД. Причины:

- перезапуск приложения многих экземпляров сразу
- слишком большой размер пула умножить на число экземпляров
- циклы повтора без паузы после тайм-аута
- проверки здоровья, которые открывают полное подключение каждый раз
- шторм промахов кэша, который открывает работу на каждом потоке приложения

Каждое подключение использует память и процесс или поток на СУБД (модель продукта отличается). Слишком много подключений замедляет каждую сессию. Новые подключения падают. Простой выглядит как «база упала». Триггер был клиенты.

```text
100 app instances * 50 pool = 5000 sessions  -->  server stalls
```

Смягчения:

1. Ограничьте размер пула из бюджета, не из «числа потоков».
2. Используйте пулер перед СУБД, если экосистема продукта его имеет.
3. Перезапускайте экземпляры пакетами.
4. Повторяйте с дрожанием и пределом.
5. Падайте быстро в приложении, когда пул пуст.

Не поднимайте `max_connections` как первое исправление. Более высокий предел без бюджета пула повторяет шторм по более высокой цене памяти.

Не прячьте медленный запрос за большим числом подключений. Вы добавляете ожидающих.

Измеряйте: число подключений, скорость создания подключений, ожидание слота пула и память СУБД.

Шторм может последовать за failover. Все клиенты переподключаются вместе. Тестируйте переподключение с пределом.

### Вопросы

#### Теоретические вопросы

1. Что такое шторм подключений?
2. Как размер пула и число экземпляров умножаются?
3. Почему повторы без паузы могут создать шторм?
4. Почему более высокий `max_connections` — слабое первое исправление?
5. Почему failover может начать шторм?

#### Простые практические задания

1. Посчитайте наихудшие сессии: экземпляры умножить на макс. пул. Напишите произведение.
2. Перечислите пять причин из этого раздела.
3. Напишите правило повтора: три попытки, растущая задержка, случайное дрожание (опишите, не изобретайте библиотеку).
4. Найдите `max_connections` (или эквивалент) в вашей СУБД.

#### Средние практические задания

1. Поставьте крошечный `max_connections` на одноразовом экземпляре. Откройте больше клиентов, чем предел. Запишите ошибку.
2. Напишите бюджет пула: память СУБД, байты на подключение (из документов или догадка, помеченная как догадка), макс. экземпляров.
3. Спроектируйте скользящий перезапуск четырёх экземпляров приложения так, чтобы скорость создания подключений оставалась ограниченной.

#### Сложные практические задания

1. Напишите политику подключений на одну страницу: формула пула, пулер, перезапуск, повтор и оповещения о скорости подключений.
2. Симулируйте волну переподключений (скрипт многих коротких подключений) на одноразовом экземпляре. Запишите, когда сервер деградирует. Затем добавьте предел в скрипт.

## Обзор темы

Эти вопросы не повторяют вопросы разделов выше. Они покрывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Как журнал медленных запросов, статистика и план работают вместе до того, как добавите индекс или кэш?
2. Когда причина — горячая строка и когда причина — глубокий `OFFSET` медленной страницы?
3. Как кэш и шторм подключений могут сделать друг друга хуже?
4. Какие измерения говорят исправить SQL и какие говорят исправить пул клиента?
5. Коллега поднимает буферы, добавляет кэш и удваивает `max_connections` без базовой линии. Какие факты вы используете в ответе?

#### Простые практические задания

1. Напишите шпаргалку: измерение, кардинальность, горячие строки, keyset, кэш, штормы.
2. Включите или найдите журнал медленных запросов. Скопируйте одну строку в заметки (очистите секреты).
3. Напишите один запрос keyset и один запрос OFFSET для одного списка.
4. Посчитайте наихудшее число подключений вашего приложения.

#### Средние практические задания

1. Постройте черновую нагрузку: большая таблица, устаревшая статистика, затем `ANALYZE`, затем страница keyset. Запишите планы и времена.
2. Произведите ожидание блокировки двумя сессиями. Произведите медленный OFFSET. Напишите, как метрики отличаются.
3. Напишите шаблон тикета настройки: базовая линия, гипотеза, одно изменение, результат.

#### Сложные практические задания

1. Настройте один настоящий медленный оператор (или намеренно замедлённый): измерение, статистика, индекс или перепись, исправление пагинации. Напишите до/после.
2. Напишите операционный обзор: дашборды, которые нужны (отставание, блокировки, подключения, медленные операторы), и первое действие для каждого оповещения.

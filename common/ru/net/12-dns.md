# 12. DNS

## Описание

DNS сопоставляет имя с данными. Обычный случай — имя с IP-адресом. Эта тема показывает резолверы, типы записей, TTL, `dig` и `nslookup`, split horizon и DNS поверх HTTPS или TLS.

Используйте один термин для каждого понятия. Имя — доменное имя, например `example.com`. Резолвер — программа, которая задаёт вопросы DNS. Авторитетный сервер отвечает из зоны, которую размещает. Завершите эту тему после HTTP. Вы уже используете имена в URL.

Практикуйтесь с `dig` или `nslookup`. Захватывайте UDP-порт 53, когда запрос открытый текст. Зашифрованный DNS скрывает запрос от пути. Вы всё равно видите адрес резолвера.

## Имя в адрес

У программы часто есть имя, не IP-адрес. Хост должен найти адрес, прежде чем сможет отправлять пакеты IP этому узлу. DNS — обычная карта из имени в адрес.

У операционной системы есть stub-резолвер. Stub отправляет запрос рекурсивному резолверу. Рекурсивный резолвер часто домашний маршрутизатор, резолвер провайдера или публичный резолвер. Ответ приходит как один или несколько IP-адресов.

У имени может быть адрес IPv4 (A), адрес IPv6 (AAAA), оба или ни одного. Двойной стек использует оба, когда оба есть. Позднее соединение использует один адрес. Happy Eyeballs может пробовать оба семейства.

Карта — не только «имя в адрес». Почта использует MX. Службы используют SRV. Текст использует TXT. Этот раздел начинается с поиска адреса, потому что браузеры и `curl` делают это первыми.

Не считайте имя хостом. Одно имя может указывать на много адресов. Один адрес может обслуживать много имён. Не кэшируйте адрес в долгоживущей программе без плана TTL. Следующий раздел о TTL объясняет почему.

Локальный файл вроде `hosts` может переопределить DNS для одного имени. Используйте этот файл только на машине, которой владеете, и только для теста.

## Рекурсивный против авторитетного резолвера

Рекурсивный резолвер принимает запрос от stub. Он находит ответ. Он может использовать свой кэш. Если в кэше нет действительных данных, он спрашивает другие серверы. Он начинает с подсказки корня, затем сервер TLD, затем авторитетный сервер зоны. Затем возвращает ответ stub.

Авторитетный сервер отвечает из данных зоны, которые туда положил администратор или реестр. Ему не нужно рекурсировать для имён в этой зоне. Сервер может быть авторитетным для одних зон и рекурсивным для других запросов. Многие публичные резолверы рекурсируют и не авторитетны для `example.com`.

Цепочка полномочий использует записи NS. Родительская зона перечисляет серверы имён потомка. Вы следуете NS от корня к зоне. Этот справочник не требует запускать корневой сервер. Нужно знать, что рекурсия обходит это дерево.

Рекурсивный резолвер — кэш и обходчик. Авторитетный сервер — источник для зоны. Не смешивайте два слова.

Stub не обходит дерево в обычной настройке ОС. Stub спрашивает один настроенный резолвер. Дерево можно обойти самому через `dig +trace`, когда инструмент это поддерживает.

Не открывайте рекурсивный резолвер в публичный Internet на хосте, который не задуман как публичная служба. Открытый резолвер могут злоупотреблять. Не меняйте рабочий DNS без плана отката.

## Типы записей: A, AAAA, CNAME, MX, NS, TXT, SRV

DNS хранит ресурсные записи. У каждой записи есть тип, имя, класс (обычно IN), TTL и данные.

A сопоставляет имя с адресом IPv4. AAAA сопоставляет имя с адресом IPv6. Клиент, который хочет IPv4, спрашивает A. Клиент, который хочет IPv6, спрашивает AAAA.

CNAME сопоставляет имя с другим именем. Затем резолвер ищет эту цель. Не кладите другие типы записей на то же имя владельца, что CNAME, по обычным правилам зоны. CNAME — псевдоним, не адрес.

MX сопоставляет домен с именем почтового обменника и номером предпочтения. Затем почтовая система ищет A или AAAA для этого обменника. Меньшее значение предпочтения пробуют первым.

NS сопоставляет зону с именем сервера имён. Родитель и потомок оба публикуют данные NS. Клеевые записи A или AAAA у родителя помогают, когда имя NS внутри зоны потомка.

TXT держит текст. Операторы используют TXT для SPF, проверки домена и других строк. Читайте формат, прежде чем доверять значению TXT.

SRV сопоставляет службу с хостом, портом и приоритетом. Имя часто выглядит как `_service._proto.example.com`. Некоторые системы используют SRV. Многие веб-клиенты нет.

Не выдумывайте тип записи. Используйте тип, который документирует протокол. Не считайте CNAME перенаправлением на HTTP. Перенаправления HTTP — другой уровень.

## TTL

TTL — время жизни записи DNS в кэше. Значение в секундах. Рекурсивный резолвер не должен отдавать кэшированную запись после конца TTL. Stub и приложения тоже могут кэшировать.

Длинный TTL снижает запросы к авторитетным серверам. Короткий TTL позволяет быстрее сменить адрес. После смены записи некоторые кэши всё ещё держат старые данные, пока их TTL не кончится. Планируйте смены с учётом старого TTL.

TTL 0 значит «не кэшировать» в обычном чтении. Некоторые кэши всё равно держат данные короткое дополнительное время. Не рассчитывайте на мгновенную глобальную смену.

Отрицательные ответы (нет такого имени или нет записей этого типа) тоже имеют время кэша. Это время приходит из SOA зоны, не из отсутствующего TTL A. Неверное имя может «прилипнуть» как NXDOMAIN на минуты.

Не ставьте TTL в одну секунду на занятом публичном имени без ёмкости для нагрузки запросов. Не игнорируйте TTL в долгоживущем клиенте. Обновляйте имя или используйте API резолвера, который чтит TTL.

Приложения иногда игнорируют TTL и кэшируют на жизнь процесса. Это поведение вызывает «работает после перезапуска».

## `dig` / `nslookup`

`dig` — инструмент запросов DNS, обычный в Unix и доступный для Windows. `nslookup` доступен в Windows и во многих системах Unix. Оба отправляют запросы и печатают ответы. Предпочитайте `dig`, когда он есть. Вывод яснее для типа записи и TTL.

Полезные формы `dig`:

- `dig example.com A`
- `dig example.com AAAA`
- `dig example.com MX`
- `dig @8.8.8.8 example.com A` (спросить конкретный резолвер)
- `dig +short example.com A` (короткий вывод)
- `dig +trace example.com` (обход от корня, когда политика позволяет)

Полезные формы `nslookup`:

- `nslookup example.com`
- `nslookup -type=MX example.com`
- `nslookup example.com 1.1.1.1` (сервер как последний аргумент на многих системах)

Читайте раздел ответа, не только первую строку. Читайте статус: NOERROR, NXDOMAIN, SERVFAIL, REFUSED. Читайте флаги: `rd` — рекурсия желательна. `ra` — рекурсия доступна.

Не используйте эти инструменты, чтобы затопить сервер имён. Не запрашивайте частный корпоративный сервер из сети без разрешения. Используйте публичные имена и резолверы, которыми можно пользоваться.

`Resolve-DnsName` — командлет Windows PowerShell. Он может показать типы записей в таблице. Используйте его, если предпочитаете PowerShell.

## Split horizon

Split horizon (или split view) значит, что одно имя может вернуть разные ответы разным клиентам. Ответ зависит от исходной сети, вида на сервере или другого резолвера.

Обычный случай: `app.example.com` возвращает частный адрес офисным хостам и публичный адрес Internet. Пользователи VPN могут видеть внутренний вид, когда используют офисный резолвер.

Split horizon — не CNAME. Имя то же. Данные различаются по зрителю. Два человека могут оба быть «правы» и всё равно не согласиться.

Устранение неполадок должно записывать, какой резолвер вы спросили и из какой сети. `dig @office-resolver` и `dig @public-resolver` могут не согласиться. Это несогласие часто проект, не неисправность.

Не публикуйте внутреннее имя в публичной зоне случайно. Не считайте, что ноутбук в домашнем Wi-Fi видит офисный вид. Не используйте split horizon как единственный контроль доступа. Утёкший внутренний адрес всё равно секрет, который нужно защищать.

Geo-DNS — родственная идея: разные публичные адреса по региону клиента. Цель — задержка или закон, не частная LAN.

## DNS поверх HTTPS / TLS (осведомлённость)

Классический DNS между stub и рекурсивным резолвером часто открытый текст UDP (или TCP) на порту 53. Наблюдатель пути может прочитать имя запроса. Злоумышленник пути может попытаться сменить ответ, если ничего больше не защищает сессию.

DNS over TLS (DoT) оборачивает DNS в TLS, часто на порту 853. DNS over HTTPS (DoH) отправляет DNS в HTTPS, часто на URL резолвера. Оба скрывают запрос и ответ от пути между stub и этим резолвером.

Вы всё равно доверяете резолверу. Резолвер видит имена. DoH и DoT не скрывают имена от оператора резолвера. Они также не заменяют HTTPS для веб-сайта. Они защищают только шаг DNS.

Браузер может использовать DoH и игнорировать резолвер ОС. Тогда `dig` и браузер могут не согласиться. Это несогласие — обычный сюрприз отладки.

Не считайте, что DoH значит «анонимный DNS». Не отключайте весь локальный журнал DNS в компании без политики. Предприятия могут использовать свои конечные точки DoH или DoT.

Этот раздел — осведомлённость. Вам не нужно реализовывать клиент DoH. Нужно назвать проблему (запросы открытым текстом) и идею (TLS к резолверу).

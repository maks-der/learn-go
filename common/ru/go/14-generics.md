# 14. Обобщения

## Описание

Обобщения позволяют писать функции и типы, которые работают с несколькими типами. Вы объявляете параметры типа. Компилятор подставляет конкретный тип, когда вы вызываете функцию или конкретизируете тип. Компилятор по-прежнему проверяет типы на этапе компиляции.

Эта тема показывает параметры типа, ограничения, вывод типов и решения по проектированию. Используйте обобщения, когда один алгоритм подходит многим типам и нужна безопасность типов. Не используйте обобщения, чтобы спрятать простой код за сложным API.

Для каждого понятия используйте один термин. Параметр типа — это имя в квадратных скобках. Ограничение — это интерфейс, который ограничивает аргумент типа. Конкретизация — это шаг, который связывает аргумент типа с параметром типа.

## Параметры типа у функций и типов

Обобщённая функция объявляет параметры типа после имени функции. За каждым параметром типа следует ограничение. Список параметров функции затем использует эти имена как типы.

```go
func First[T any](items []T) (T, bool) {
    if len(items) == 0 {
        var zero T
        return zero, false
    }
    return items[0], true
}
```

`T` — параметр типа. `any` — ограничение. Вызывающий код может написать `First[int](nums)` или опереться на вывод типа из `nums`. Тип результата — `T`. Когда срез пуст, функция возвращает нулевое значение `T`.

Обобщённый тип объявляет параметры типа после имени типа:

```go
type Pair[A any, B any] struct {
    First  A
    Second B
}

type Stack[T any] struct {
    items []T
}

func (s *Stack[T]) Push(v T) {
    s.items = append(s.items, v)
}

func (s *Stack[T]) Pop() (T, bool) {
    var zero T
    if len(s.items) == 0 {
        return zero, false
    }
    i := len(s.items) - 1
    v := s.items[i]
    s.items = s.items[:i]
    return v, true
}
```

Методы обобщённого типа могут использовать параметры типа этого типа. Методы не должны объявлять новые параметры типа. Это правило действует и в текущем Go. Если операции нужен второй параметр типа, напишите функцию, а не метод.

```go
// Allowed: a function with its own type parameters.
func Convert[T any, U any](s Stack[T], f func(T) U) Stack[U] {
    out := Stack[U]{}
    for _, v := range s.items {
        out.Push(f(v))
    }
    return out
}
```

Обобщённый тип конкретизируют списком аргументов типа:

```go
var p Pair[string, int]
s := Stack[int]{}
```

В Go 1.24 и новее разрешены обобщённые псевдонимы типов. У псевдонима могут быть параметры типа, как у определённого типа:

```go
type Handler[T any] = func(context.Context, T) error
```

Используйте определённый тип, когда на этом имени нужны методы. Используйте псевдоним, когда нужно только короткое имя для уже существующего типа.

Стандартная библиотека использует параметры типа в `slices`, `maps` и `cmp` (Go 1.21 и новее). Предпочитайте эти пакеты, прежде чем писать свои обобщённые помощники для обычной работы со срезами и картами.

## Ограничения и `comparable`

Ограничение — это интерфейс. Аргумент типа должен удовлетворять этому интерфейсу. Компилятор использует ограничение, чтобы решить, какие операции допустимы для значений параметра типа.

Встроенное ограничение `comparable` называет каждый тип, который поддерживает `==` и `!=`. `comparable` нужен, когда вы сравниваете значения или используете тип как ключ карты.

```go
func Contains[T comparable](items []T, want T) bool {
    for _, v := range items {
        if v == want {
            return true
        }
    }
    return false
}

type Set[T comparable] map[T]struct{}
```

Ограничение-множество типов перечисляет типы. Между типами ставьте `|`. Используйте `~`, чтобы включить каждый тип, чей базовый тип совпадает с названным типом.

```go
type Signed interface {
    ~int | ~int8 | ~int16 | ~int32 | ~int64
}

func Abs[T Signed](v T) T {
    if v < 0 {
        return -v
    }
    return v
}
```

`Abs` может принять `int` и определённый тип, чей базовый тип — `int`:

```go
type Count int
```

Без `~` определённый тип с тем же базовым типом ограничению не удовлетворяет.

Ограничение может включать методы и множество типов в одном интерфейсе:

```go
type StringID interface {
    ~string
    ID() string
}
```

Аргумент типа должен иметь базовый тип `string` и метод `ID() string`.

`cmp.Ordered` в пакете `cmp` — стандартное ограничение для типов с операциями `<`, `<=`, `>` и `>=`. Используйте `cmp.Ordered` для обобщённых помощников min, max и сортировки. Пакет `slices` его использует.

```go
import "cmp"

func Min[T cmp.Ordered](a, b T) T {
    if a < b {
        return a
    }
    return b
}
```

В Go 1.21 также добавили встроенные `min` и `max` для упорядоченных значений одного типа. Используйте встроенные функции в простых случаях. Пишите обобщённую функцию, когда нужен повторно используемый помощник с дополнительной логикой.

Текущий Go проверяет операции по множеству типов ограничения. Множество типов должно поддерживать каждую операцию, которую использует тело функции. Если функция использует `<`, ограничение должно быть упорядоченным. Если функция использует `==`, ограничение должно быть `comparable` или множеством сравниваемых типов.

Интерфейсы, которые не стоят ограничением в списке параметров типа, остаются обычными интерфейсами. Обычные интерфейсы по-прежнему используют для полиморфизма во время выполнения. Не путайте ограничение (множество типов на этапе компиляции) со значением интерфейсного типа (множество методов во время выполнения).

## `any` и пользовательские ограничения

`any` — псевдоним для `interface{}`. Как ограничение `any` разрешает любой тип. Функция может копировать значения `T`, класть их в срезы и передавать в другие функции, которые принимают `T`. Функция не должна сравнивать значения `T`. Функция не должна складывать значения `T`. Функция не должна вызывать метод у `T`, если этого метода нет в ограничении.

```go
func Clone[T any](items []T) []T {
    out := make([]T, len(items))
    copy(out, items)
    return out
}
```

`Clone` только копирует элементы. `any` — правильное ограничение.

Пользовательское ограничение документирует нужные операции. Предпочитайте самое узкое ограничение, при котором тело функции законно.

```go
type Closer interface {
    Close() error
}

func CloseAll[T Closer](items []T) error {
    for _, item := range items {
        if err := item.Close(); err != nil {
            return err
        }
    }
    return nil
}
```

Здесь обычный параметр интерфейса `[]Closer` тоже работает. Обобщённая форма сохраняет конкретный тип каждого элемента. Вы не упаковываете каждое значение в интерфейс, если срез уже хранит конкретный тип.

Используйте `any`, когда:

- функция только хранит, копирует или перемещает значения
- вызывающий код задаёт поведение аргументом-функцией (`func(T)`)

Используйте пользовательское ограничение, когда:

- функция сравнивает, упорядочивает или хеширует значения
- функция вызывает методы у `T`
- функция использует операторы вроде `+` или `<`

Не используйте `any` и затем не приводите `T` к `any` (интерфейсу) для type switch как обычный приём. Такая смесь теряет пользу параметра типа. Если нужен type switch по неизвестному значению, обычный параметр `any` яснее.

Пустой интерфейс как значение и `any` как ограничение — разные роли. Значение типа `any` несёт динамический тип во время выполнения. Параметр типа с ограничением `any` после конкретизации — один конкретный тип на этапе компиляции.

## Вывод типов

Компилятор может вывести аргументы типа из типов обычных аргументов. Список аргументов типа в вызове функции часто можно опустить.

```go
n := First([]int{1, 2, 3})
// same as First[int]([]int{1, 2, 3})
```

Вывод использует типы аргументов и присваивание результата, когда эти типы известны. Вывод не угадывает тип из ничего.

```go
func Empty[T any]() []T {
    return nil
}

// _ = Empty()    // compile error: cannot infer T
_ = Empty[int]()  // explicit type argument
```

Функция, которая возвращает только `T` и не принимает значение типа `T`, обычно требует явный аргумент типа.

Когда параметров типа больше одного, вывод использует каждый аргумент:

```go
func Transform[T, U any](in []T, f func(T) U) []U {
    out := make([]U, len(in))
    for i, v := range in {
        out[i] = f(v)
    }
    return out
}

strs := Transform([]int{1, 2}, strconv.Itoa)
```

Компилятор выводит `T` как `int` из среза. Компилятор выводит `U` как `string` из `strconv.Itoa`.

Вывод для обобщённых типов слабее, чем вывод для обобщённых функций. Аргументы типа нужно писать, когда вы называете обобщённый тип:

```go
s := Stack[int]{}
// Stack{} is not enough
```

Составной литерал обобщённого типа нуждается в конкретизированном типе. Вспомогательная функция может это скрыть:

```go
func NewStack[T any]() *Stack[T] {
    return &Stack[T]{}
}

s := NewStack[int]() // still explicit, because no argument has type T
```

Неэкспортируемые и экспортируемые параметры типа подчиняются одним правилам вывода. Вывод — процесс этапа компиляции. В двоичном файле нет отдельного шага вывода во время выполнения.

Если вывод не удался, компилятор сообщает, что не может вывести аргумент типа. Укажите список аргументов типа. Не меняйте алгоритм только ради принудительного вывода.

В Go 1.21 и новее улучшили вывод для некоторых типов функций и случаев ограничений. Пишите явные аргументы типа, когда вызов трудно читать. Ясность важнее короткого вызова.

## Обобщённые структуры данных и интерфейсы

Обобщённая структура данных хранит элементы типа `T`. Компилятор проверяет каждую вставку и каждое чтение. `Stack[int]` не может хранить `string`. В месте использования нет утверждения типа.

Структура на интерфейсах хранит интерфейсный тип. `Stack` из `any` хранит любой тип. Вызывающий код должен утверждать тип на выходе. Ошибка проявляется во время выполнения.

```go
// Generic: type-safe at compile time.
type List[T any] struct {
    items []T
}

// Interface: flexible, runtime checks.
type AnyList struct {
    items []any
}
```

Используйте обобщённую структуру, когда:

- коллекция однородна (один тип элементов)
- нужны проверки на этапе компиляции
- важно избегать упаковки в интерфейс для малых типов

Используйте интерфейс, когда:

- одна коллекция должна одновременно хранить много разных типов
- тип элемента уже интерфейс с методами (`io.Reader`, `error`)
- множество типов открыто, и вы выбираете ветку через type switch

Множество методов интерфейса описывает поведение. Параметр типа описывает тип-заполнитель. Не заменяйте каждый интерфейс параметром типа. Параметр `io.Reader` — правильный API для «читать байты». Обобщённый тип `Reader[T]` — неверная модель для этой задачи.

Обобщённые структуры и интерфейсы могут работать вместе. Структура обобщённая. Операции над элементами используют ограничение-интерфейс или аргумент-функцию:

```go
type Heap[T any] struct {
    items []T
    less  func(a, b T) bool
}
```

Этой куче не нужно, чтобы `T` реализовывал интерфейс. Вызывающий код передаёт `less`. Такой дизайн оставляет `T` без ограничения и всё равно задаёт порядок.

Стандартная библиотека предпочитает функции в `slices` и `maps` множеству обобщённых типов контейнеров. Go не поставляет обобщённый список или дерево в стандартной библиотеке. Напишите небольшую структуру в своём модуле, когда она нужна. Не импортируйте большую библиотеку контейнеров ради короткого стека.

Упаковка в интерфейс означает, что компилятор хранит значение в интерфейсе. Значение интерфейса держит тип и указатель (или малое значение напрямую). Конкретизация обобщения сохраняет конкретную раскладку `T`. Для элементов `int` срез `[]int` дешевле, чем `[]any`.

## Когда обобщения не нужны

Обобщения добавляют имена, ограничения и ошибки конкретизации. Используйте их, когда они убирают дублирование и не скрывают программу.

Не используйте обобщения, когда есть только один конкретный тип. Напишите `func Sum(items []int) int`. Позже второй тип — причина пересмотреть дизайн. Возможный будущий тип — не причина.

Не используйте обобщения, когда интерфейс уже называет поведение. `io.Reader`, `error` и `fmt.Stringer` — стабильные API. Обобщённая обёртка вокруг них не помогает вызывающему коду.

Не используйте обобщения, чтобы строить каркас, который программе не нужен. Обобщённый контейнер внедрения зависимостей обычно труднее читать, чем несколько конструкторов.

Не используйте обобщения, чтобы избежать коротких ясных функций. Две короткие функции с ясными именами лучше одной обобщённой функции со слабым ограничением и колбэком, который никто не понимает.

Не смешивайте обобщения с рефлексией как стиль по умолчанию. Рефлексия (`reflect`) решает открытые динамические случаи. Обобщения решают закрытые случаи этапа компиляции. Если вы уже используете `reflect`, чтобы обходить неизвестные структуры, параметр типа эту работу не снимает.

Не экспортируйте обобщённый API, который раскрывает ваши типы реализации. Держите публичную поверхность маленькой. Предпочитайте конкретный тип на границе пакета, когда пакет всегда использует один тип.

Хорошие применения обобщений:

- контейнеры (`Set[T]`, `Stack[T]`)
- помощники для срезов и карт, которых нет в стандартной библиотеке
- числовые помощники с `cmp.Ordered` или ограничением числа
- небольшие адаптеры, которые сохраняют конкретный тип

Проверьте этот список, прежде чем добавлять параметр типа:

1. Нужны ли сегодня хотя бы два реальных типа одному и тому же коду?
2. Есть ли уже стандартная функция в `slices`, `maps` или `cmp`?
3. Описывает ли поведение уже существующий интерфейс?
4. Может ли аргумент-функция (`func(T)`) заменить сложное ограничение?
5. Прочитает ли новичок сигнатуру за один проход?

Если ответ — нет, пропуск, интерфейс, колбэк или перепись, не добавляйте обобщения.

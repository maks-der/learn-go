# 13. Шаблоны кэширования

## Описание

Кэш хранит результат, чтобы более позднее чтение избежало медленного пути. Эта тема покрывает, как приложение читает и пишет этот кэш, как много клиентов могут промахнуться сразу, и как дизайн TTL снижает давки.

Сначала завершите тему 4 (срок и вытеснение) и тему 12 (клиенты). Эта тема предполагает, что Redis — кэш, а не единственный источник истины, если задание не говорит иное.

Используйте один термин для каждого понятия. Источник истины — долговечное хранилище (часто база SQL или документов). Попадание — чтение, которое находит пригодное значение в Redis. Промах — чтение, которое не находит. Давка — много промахов одного ключа в одно время. Негативное кэширование хранит маркер «нет». Джиттер — случайный дополнительный TTL.

## Cache-aside

Cache-aside (ленивая загрузка) кладёт логику кэша в приложение:

1. Приложение делает `GET` ключа кэша.
2. При попадании приложение использует значение.
3. При промахе приложение читает источник истины.
4. Приложение делает `SET` ключа кэша (часто с TTL).
5. Приложение возвращает значение.

```text
GET cache:product:1001
# miss
# ... read SQL ...
SET cache:product:1001 <bytes> EX 300
```

Приложение владеет политикой. Redis не вызывает базу. Redis не знает SQL.

При записи в источник истины приложение обновляет или удаляет ключ кэша. Два частых выбора:

- Удалить (`DEL`) ключ кэша. Следующее чтение перезагружает. Это просто.
- Записать новое значение в кэш. Следующее чтение попадает. Нужно то же кодирование, что и путь чтения.

Удаление может гоняться: процесс A читает SQL (старое), процесс B пишет SQL и удаляет кэш, процесс A затем делает `SET` старого значения. Короткие TTL ограничивают окно устаревания. Некоторые коллективы используют поле версии или шаг сравнения.

Если Redis недоступен, приложение должно читать источник истины и пропускать кэш (разрыв цепи, тема 21). Cache-aside делает этот путь естественным: промах и ошибка Redis оба могут упасть на SQL.

Не считайте попадание в кэш доказательством, что источник истины всё ещё имеет эту строку. Кэш может быть устаревшим до TTL или инвалидации.

## Read-through / write-through (на уровне приложения)

Read-through и write-through переносят шаги загрузки и сохранения в модуль кэша, который приложение вызывает так, будто это база.

Read-through: приложение спрашивает модуль ключ. Модуль делает `GET` Redis. При промахе модуль читает источник истины, делает `SET` Redis и возвращает значение. Обработчик не содержит ветку промаха.

Write-through: приложение пишет через модуль. Модуль пишет источник истины и пишет Redis в одном запросе приложения (два хранилища, один вызов). Запрос пользователя ждёт оба.

В Redis вы всё равно реализуете это в приложении или в библиотеке. Redis сам не загружает SQL. Некоторые продукты добавляют прокси или модуль. Этот справочник считает шаблон уровнем приложения.

Read-through скрывает путь промаха. Это может быть чище. Это также может скрыть стоимость: «простой get» может запустить медленный запрос.

Write-through держит Redis и источник истины ближе в момент записи. Запрос медленнее, чем запись, которая касается только SQL. Если Redis падает, нужно решить: провалить запрос или писать SQL и принять промах кэша позже.

Не путайте write-through с базой только Redis. Источник истины остаётся долговечным хранилищем, если не проектируете иначе.

Cache-aside и read-through могут хранить те же байты. Разница в том, кто владеет функциями промаха и записи.

## Write-behind

Write-behind (write-back) сначала пишет Redis (или только Redis в запросе). Фоновый работник пишет источник истины позже.

Запрос пользователя быстрый. Долговечное хранилище отстаёт. Если Redis теряет ключ до запуска работника (вытеснение, перезапуск без персистентности, ошибка), долговечное хранилище никогда не видит запись.

Используйте write-behind только когда принимаете этот риск, или когда Redis персистентен и есть очередь повтора (потоки, тема 15), которую потребляет работник.

Типичная форма:

1. Приложение пишет кэш или запись потока.
2. Приложение возвращает успех пользователю (если продукт это позволяет).
3. Работник читает очередь и пишет SQL.
4. Работник подтверждает запись.

Это ближе к шаблону брокера, чем к простому кэшу.

Не используйте write-behind для денег или юридических записей, если нет долговечного журнала вне изменчивого кэша.

Cache-aside плюс `DEL` проще, когда источник истины должен побеждать каждый раз.

## Давка / thundering herd

Давка (thundering herd) случается, когда много клиентов промахиваются по одному ключу сразу. Каждый клиент загружает источник истины. База получает всплеск. Кэш затем получает всплеск `SET`.

Типичные причины:

- Ключ истекает (`TTL` достигает 0), пока трафик высок
- Вытеснение убирает горячий ключ
- Деплой сбрасывает кэш
- Процесс стартует с пустым кэшем (холодный старт)

Эффекты: высокая нагрузка SQL, высокий CPU Redis, более медленные запросы пользователей.

Смягчения (следующие разделы добавляют ещё):

- Single-flight: только один загрузчик на ключ; другие вызывающие ждут этого загрузчика
- Блокировка (`SET NX EX`) вокруг загрузки (тема 14)
- Мягкий TTL плюс раннее обновление (следующий раздел)
- Джиттер TTL, чтобы много ключей не истекали в одну секунду
- Прогрев кэша до деплоя (тема 21)
- Негативное кэширование, чтобы отсутствующая строка не била SQL на каждый запрос

Давка — задача координации. Redis может держать блокировку или флаг «загрузка». Приложение должно её использовать.

Не сбрасывайте все ключи при деплое, если набор большой и горячий. Предпочитайте версионированные ключи или постепенный прогрев.

## Вероятностное раннее истечение

Фиксированный TTL истекает каждую копию горячего ключа в один момент. Вероятностное раннее истечение обновляет ключ до этого момента с вероятностью, которая растёт, когда оставшийся TTL сжимается.

Идея:

- Храните логическое время истечения со значением (или используйте `PTTL`)
- На каждом попадании считайте вероятность из оставшегося времени и стоимости перезагрузки
- Иногда перезагружайте из источника истины и снова делайте `SET`, хотя ключ ещё есть

Один клиент обновляет рано. Другие клиенты всё ещё попадают. Ключ не достигает нуля, пока все клиенты ждут SQL.

Это алгоритм приложения. Redis не считает вероятность. Статьи и библиотеки описывают варианты (xfetch, perishable cache).

Вам всё ещё нужен TTL. Раннее обновление — дополнительно. Если никто не читает ключ, он истекает. Это нормально для холодного ключа.

Цена: некоторые лишние чтения SQL на горячем ключе. Эта цена обычно меньше давки.

Не обновляйте рано на каждом попадании. Это убирает выгоду кэша.

Сочетайте с блокировкой или single-flight, чтобы два ранних обновления не били SQL оба.

## Негативное кэширование

Промах может значить «в источнике истины нет строки». Если ничего не хранить, каждый запрос плохого id бьёт SQL.

Негативное кэширование хранит маркер на короткий TTL:

```text
SET cache:product:9999:neg 1 EX 30
```

Или вы храните пустой объект JSON с полем типа `{ "missing": true }`. Приложение должно отличать «нет» от «товар с пустым именем».

Используйте короткий TTL. Негативная запись, которая живёт слишком долго, скрывает строку, которую вы только что вставили.

При успешном создании в SQL удалите негативный ключ. Иначе следующее чтение всё ещё может показать «нет».

Злоупотребление: атакующие могут запрашивать много случайных id. Негативное кэширование защищает SQL. Оно также пишет много ключей. Используйте TTL, бюджет префикса (тема 21) и ограничения частоты (тема 14).

Не кэшируйте негативно ошибки вроде «SQL недоступен». Этот маркер скрыл бы восстановление. Кэшируйте «не найдено», не «нельзя говорить с SQL».

## Джиттер TTL

Джиттер TTL добавляет случайное дополнительное время жизни каждому ключу. Если 10 000 ключей товаров все получают `EX 300`, они могут истечь в одну секунду после массовой загрузки. Следующая секунда — давка.

```text
# conceptual: 300 seconds plus a random 0–60
SET cache:product:1001 <bytes> EX 347
```

Каждый ключ истекает в разное время. Перезагрузки растекаются по минуте.

Джиттер — не блокировка. Джиттер не помогает одному горячему ключу, который делят все клиенты. Джиттер помогает многим ключам, которые делят один TTL и одно время загрузки.

Выберите диапазон джиттера из базового TTL. TTL 300 секунд плюс 0–30 секунд частый. Джиттер больше базового TTL делает истечение трудным для рассуждения.

Документируйте политику: `ttl = base + random(0, jitter)`. Используйте часы, достаточно хорошие для секунд. Не используйте крошечный джиттер (0–1 секунда) на огромной массовой загрузке.

Вытеснение всё ещё может убрать много ключей сразу, если память заполнена. Джиттер не заменяет планирование `maxmemory` (тема 4).

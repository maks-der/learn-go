# 6. Методы и интерфейсы

## Описание

Метод — функция с получателем. Получатель связывает метод с типом. Вы вызываете метод на значении или на указателе этого типа.

Интерфейс — набор сигнатур методов. Тип удовлетворяет интерфейсу, когда у типа есть эти методы. Вы не пишете ключевое слово implements. Соответствие неявное.

Эта тема показывает value-получатели, pointer-получатели и неявное соответствие. Она показывает `any`, type assertion и type switch. Она показывает частые интерфейсы стандартной библиотеки.

Используйте методы, чтобы дать типу поведение. Используйте интерфейсы, чтобы описать поведение, которое могут предоставить многие типы. Принимайте интерфейсы в параметрах. Возвращайте конкретные структуры из конструкторов, когда можете.

## Value-получатели против pointer-получателей

В объявлении метода получатель стоит в скобках перед именем.

```go
type Point struct {
	X int
	Y int
}

func (p Point) Sum() int {
	return p.X + p.Y
}

func (p *Point) Scale(k int) {
	p.X *= k
	p.Y *= k
}
```

Получатель `(p Point)` — value-получатель. Метод получает копию структуры. Изменение `p` не меняет значение вызывающего кода.

Получатель `(p *Point)` — pointer-получатель. Метод получает указатель. Изменение `p.X` меняет хранилище вызывающего кода.

Метод с value-получателем можно вызвать на значении или на указателе. Метод с pointer-получателем можно вызвать на указателе. Его также можно вызвать на адресуемом значении. Компилятор берёт адрес. Значение адресуемо, когда это переменная. Временное значение не адресуемо. `Point{1, 2}.Scale(2)` не компилируется.

Набор методов `T` — набор методов с получателем `T`. Набор методов `*T` — набор методов с получателем `T` или `*T`. Интерфейсы используют наборы методов.

Используйте pointer-получатель, когда метод должен изменить получатель. Используйте pointer-получатель, когда структура большая. Используйте pointer-получатель, когда некоторые методы типа уже используют pointer-получатель. Держите один стиль для типа.

Используйте value-получатель, когда тип — маленькое неизменяемое значение. Именованный тип карты может использовать value-получатель. Запись в карту через value-получатель видна вызывающему коду. Заголовок — копия. Таблица — нет.

Метод с pointer-получателем может получить `nil`. Проверяйте `nil`, когда это состояние допустимо. Конструктор, который возвращает `*T`, хорошо сочетается с pointer-методами.

## Неявное соответствие интерфейсу

Тип интерфейса перечисляет методы. Тип удовлетворяет интерфейсу, когда набор методов этого типа содержит каждый перечисленный метод. Связь не объявляют.

```go
type Speaker interface {
	Speak() string
}

type Dog struct {
	Name string
}

func (d Dog) Speak() string {
	return d.Name
}

func say(s Speaker) {
	fmt.Println(s.Speak())
}
```

`Dog` удовлетворяет `Speaker`. `say(Dog{Name: "Rex"})` допустим. Дополнительное ключевое слово не нужно. Имена и сигнатуры методов должны совпадать. Лишние методы на `Dog` допустимы.

Если у `Speak` pointer-получатель, `Dog` не удовлетворяет `Speaker`. `*Dog` удовлетворяет `Speaker`. Присвойте `&Dog{}` переменной `Speaker`.

Значение интерфейса имеет две части: динамический тип и динамическое значение. Нулевое значение интерфейса — `nil`. Обе части не заданы.

Типизированный указатель nil в интерфейсе — не интерфейс `nil`. `var d *Dog; var s Speaker = d` делает `s == nil` ложным. Эта ошибка появляется в возвратах ошибок. Проверяйте конкретный указатель до сохранения его в интерфейс.

Держите интерфейсы маленькими. Один или два метода — хороший размер. Именуйте интерфейсы глаголом или с `-er`, когда у них один метод. Примеры: `Speaker`, `Reader`, `error`.

Интерфейсы можно встраивать в интерфейс. Новый интерфейс включает все методы. `io.ReadWriter` требует `Read` и `Write`. Тип, у которого уже есть оба метода, удовлетворяет `ReadWriter`. Не собирайте большие интерфейсы.

## `any`, type assertion и type switch

Пустой интерфейс не имеет методов. Ему удовлетворяет каждый тип. Предопределённое имя `any` — псевдоним `interface{}`. В новом коде используйте `any`.

```go
var x any
x = 3
x = "hi"
x = Point{X: 1}
```

Нельзя вызывать методы на `x` без type assertion. Предпочитайте настоящий интерфейс, когда знаете методы. `any` скрывает тип. Не используйте `any`, чтобы избежать проектирования.

Значение `any` равное `nil` — интерфейс `nil`. После `x = (*int)(nil)` выражение `x == nil` ложно.

Type assertion читает динамический тип значения интерфейса.

```go
var s Speaker = Dog{Name: "Rex"}
d := s.(Dog)
```

`s.(Dog)` успешен, когда динамический тип — `Dog`. Assertion паникует, когда тип не совпадает. Форма comma-ok не паникует.

```go
d, ok := s.(Dog)
if !ok {
	fmt.Println("not a Dog")
}
```

Type switch выбирает ветку по динамическому типу. `v` имеет тип совпавшей ветки.

```go
switch v := s.(type) {
case Dog:
	fmt.Println(v.Name)
case *Dog:
	fmt.Println(v.Name)
default:
	fmt.Println("other")
}
```

Не используйте type switch как первое проектное решение. Предпочитайте методы на интерфейсе. Используйте type switch на границе. Assertion к типу указателя не совпадает с типом значения. `*Dog` — не `Dog`. Assertion на интерфейсе `nil` паникует в форме с одним значением. Форма comma-ok возвращает `ok == false`.

## Частые интерфейсы: `error`, `fmt.Stringer`, `io.Reader`, `io.Writer`

Интерфейс `error` имеет один метод.

```go
type error interface {
	Error() string
}
```

`error` предопределён. Функции возвращают `error` как последний результат. Ошибка `nil` означает успех. Любой тип с `Error() string` может быть ошибкой. В обычном коде используйте `errors.New` и `fmt.Errorf`. Тема 7 подробно покрывает обработку ошибок.

`fmt.Stringer` имеет один метод.

```go
type Stringer interface {
	String() string
}
```

`fmt` вызывает `String` для глаголов вроде `%s` и `%v`. Реализуйте `String` для ясной формы печати. Не паникуйте в `String`.

`io.Reader` имеет один метод.

```go
type Reader interface {
	Read(p []byte) (n int, err error)
}
```

`Read` заполняет `p` байтами. Возвращает число и ошибку. `io.EOF` помечает конец. Многие типы — читатели: файлы, буферы, тела HTTP.

`io.Writer` имеет один метод.

```go
type Writer interface {
	Write(p []byte) (n int, err error)
}
```

`Write` пишет байты из `p`. `fmt.Fprint` пишет в любой `io.Writer`. `os.Stdout` — писатель. `bytes.Buffer` — читатель и писатель.

```go
var buf bytes.Buffer
fmt.Fprint(&buf, "hello")
```

Эти четыре интерфейса маленькие. Им можно удовлетворить одним методом каждый. Можно тестировать через `bytes.Buffer` и `strings.NewReader`. Не пишите `Read` или `Write`, если не обеспечиваете задокументированный смысл. Неверные правила `io.EOF` ломают вызывающий код.

## Принимайте интерфейсы, возвращайте структуры

Это правило проектирования. Параметры функций принимают типы интерфейсов. Конструкторы и помощники возвращают конкретные типы структур.

```go
type Store struct {
	path string
}

func NewStore(path string) *Store {
	return &Store{path: path}
}

func Save(w io.Writer, data []byte) error {
	_, err := w.Write(data)
	return err
}
```

`NewStore` возвращает `*Store`. Вызывающий код видит все методы `Store`. Можно добавить методы позже без нового интерфейса.

`Save` принимает `io.Writer`. Вызывающий код передаёт файл, буфер или тестовый писатель. `Save` не зависит от `*os.File`.

Если `NewStore` возвращал интерфейс, вызывающий код не мог бы вызывать лишние методы. Тестам нужен был бы более широкий интерфейс. Новые методы ломали бы интерфейс или оставались скрытыми.

Возвращайте интерфейс, когда нужно скрыть тип. Примеры: вы возвращаете один из нескольких типов, или конкретный тип должен остаться неэкспортируемым и маленьким. Эти случаи — исключение.

Принимайте конкретный тип, когда функции нужен именно этот тип и другой тип не имеет смысла. Не изобретайте интерфейс для одной реализации в том же пакете без нужды тестов.

Параметр типа `any` — плохая замена маленькому интерфейсу. Назовите методы, которые вам нужны.

Это правило работает с неявным соответствием. Вам не нужно менять конкретный тип, чтобы добавить `io.Writer` в список параметров. Нужны только методы.

2. Спроектируйте получатели методов и интерфейсы для типа `Cache` с `Get` и `Set`. Пишите только сигнатуры.

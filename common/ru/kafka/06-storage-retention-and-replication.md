# 6. Хранение, ретеншн и репликация

## Описание

Kafka хранит каждую партицию как журнал на диске. Журнал — последовательность файлов сегментов. Правила ретеншна удаляют старые данные. Компакция оставляет последнее значение на ключ. Репликация копирует каждую партицию на больше чем один брокер.

Эта тема показывает сегменты журнала, ретеншн по времени и по размеру, компакцию, томбстоуны, ISR, `min.insync.replicas`, unclean leader election и контроллер KRaft. Завершите эту тему после тем 2 и 3. Предпочитайте KRaft для всех новых кластеров. Не запускайте новые кластеры на ZooKeeper.

Используйте один термин для каждого понятия. Сегмент — один файл (плюс индексные файлы) в журнале партиции. Ретеншн — правило, которое удаляет старые записи. Компакция — правило, которое оставляет последнюю запись на ключ. Томбстоун — запись со значением null. Реплика — копия партиции. ISR — набор реплик, которые актуальны. Контроллер — компонент, который управляет метаданными кластера и лидерами партиций. В новой Kafka контроллер — кворум KRaft.

## Сегменты журнала

Журнал партиции — не один бесконечный файл. Kafka делит журнал на **сегменты**. Активный сегмент принимает новые добавления. Когда активный сегмент достигает предела размера или времени, Kafka закрывает его и начинает новый активный сегмент.

У каждого сегмента есть базовый офсет. Имя файла использует этот офсет. Kafka также пишет индексные файлы. Индекс офсетов отображает офсет на позицию в файле `.log`. Индекс времени отображает метку времени на офсет. Эти файлы не правят вручную.

Ретеншн и компакция работают на закрытых сегментах. Активный сегмент не кандидат на удаление тем же способом. Очень длинные активные сегменты задерживают очистку. Конфигурация вроде `log.segment.bytes` и `log.roll.ms` контролирует, когда начинается новый сегмент.

Маленькие сегменты создают много файлов. Большие сегменты задерживают удаление и делают восстановление тяжелее. Используйте значения по умолчанию, пока нет измеренной причины.

`log.dirs` (или `log.dir`) — конфигурация брокера, которая называет каталоги журналов партиций. Можно задать больше одного каталога. Kafka назначает партиции каталогам. Это не менеджер RAID. Используйте правильную дисковую установку под каталогами.

Не удаляйте файлы сегментов в файловой системе, чтобы «освободить диск». Используйте ретеншн или удалите топик через admin API. Ручное удаление портит партицию.

У метаданных KRaft свой каталог хранения в конфигурации контроллера. Не путайте журнал метаданных с `log.dirs` для партиций топиков. Обоим нужен диск. Форматируйте оба при создании кластера (официальная команда format).

## Ретеншн по времени и по размеру

Политика очистки по умолчанию — `delete`. Kafka удаляет старые записи из закрытых сегментов, когда срабатывает предел ретеншна.

**Время.** `retention.ms` (или `log.retention.hours` на уровне брокера) — максимальный возраст записи. Когда предел времени истекает, Kafka может удалить сегмент.

**Размер.** `retention.bytes` — максимальный размер журнала партиции. Когда журнал больше, Kafka удаляет самые старые сегменты.

Если задать оба предела, Kafka может удалять, когда срабатывает любой. Проверьте точное правило в документах вашей версии.

Ретеншн — на партицию, не на топик как один blob. Горячая партиция первой упирается в предел размера.

`retention.ms=-1` и выключенный предел размера могут хранить данные вечно. Диск заполнится. Используйте бесконечный ретеншн только когда есть план диска.

Консьюмеры с зафиксированным офсетом, который теперь удалён, имеют проблему. Применяется `auto.offset.reset` (тема 4). Можно потерять логическую позицию. Мониторьте лаг и диск.

Копии умножают диск. Фактор репликации 3 хранит примерно втрое данных. Включайте реплики в планы диска.

Полный диск — серьёзный сбой. Брокер может остановить запись. Мониторьте диск. Ретеншн — главный инструмент освобождения места. Не заполняйте диск до 100%.

## Компакция и томбстоуны

**Компакция** оставляет последнюю запись для каждого ключа в партиции. Более старые записи с тем же ключом можно удалить. Записи с разными ключами остаются.

Используйте компакцию для changelog: текущее состояние сущности — последнее значение для этого ключа. Примеры: профиль пользователя, статус счёта, состояние таблицы потока.

Компакции нужны ключи. Ключи null не компактируются как changelog сущности. Используйте стабильный ключ.

Компакция не мгновенна. Поток cleaner читает закрытые сегменты и пишет компактированные сегменты. Последнее значение может существовать больше одного раза, пока cleaner не отработает.

Компакция не делает топик базой данных. Нельзя запрашивать по ключу через протокол Kafka, как запрашиваете SQL. Консьюмер всё равно читает журнал.

Задайте `cleanup.policy=compact` на топике. Не предполагайте, что значение брокера по умолчанию — compact. Обычное значение по умолчанию — `delete`.

Топик может использовать обе политики: `cleanup.policy=compact,delete`. Kafka компактирует ключи и также удаляет записи старше времени ретеншна. Используйте compact+delete, когда нужен changelog, который не растёт вечно. Старые ключи, которые никто не обновляет, всё равно оставляют запись в топике только compact.

**Томбстоун** — запись с ключом и значением null. На компактируемом топике томбстоун значит «этот ключ удалён». Cleaner может убрать более ранние значения этого ключа. После времени ретеншна томбстоуна сам томбстоун может исчезнуть.

Продюсеры отправляют томбстоун, когда сущность исчезла. Пример: пользователь удалён. Консьюмеры, которые строят таблицу, убирают ключ из таблицы, когда видят значение null.

Если только перестать отправлять обновления, компакция оставляет последнее ненулевое значение. Ключ остаётся. Нужно отправить томбстоун, чтобы удалить ключ из compact changelog.

Значение null на топике только `delete` — просто запись со значением null. У неё нет того же смысла очистки, что у compact-томбстоуна.

`delete.retention.ms` контролирует, сколько томбстоуны остаются (официальное имя). Читателям нужно это окно, чтобы увидеть удаление.

## ISR, `min.insync.replicas`, unclean leader election

**Набор синхронных реплик (ISR)** — набор реплик, которые догнали лидера. Лидер всегда в ISR. Фолловер остаётся в ISR, когда получает новые записи в пределах настроенного лага.

Когда фолловер слишком медленный или останавливается, лидер убирает его из ISR. Реплика всё ещё назначена, но не синхронна. Вывод `describe` показывает реплики и ISR как два списка.

Для `acks=all` лидер ждёт текущий ISR (и `min.insync.replicas`). Отправка, которая удовлетворяет это ожидание, устойчива на этих синхронных брокерах.

Не считайте «фактор репликации 3» как «три синхронные копии всегда». ISR может сжаться до 1, если два фолловера отстанут.

`min.insync.replicas` — минимальный размер ISR, который лидер требует для успешной отправки, когда продюсер использует `acks=all`. Если ISR меньше этого значения, лидер отклоняет отправку.

Пример: фактор репликации 3, `min.insync.replicas=2`. Кластер может потерять одну реплику и всё равно принимать устойчивые записи. Если две реплики вне, записи с `acks=all` падают. Этот сбой лучше тихой записи на один диск, когда вы требовали две копии.

Частая продакшен-пара — фактор репликации 3 и `min.insync.replicas=2`. Одноброкерный учебный кластер должен использовать `min.insync.replicas=1` и фактор репликации 1.

**Лаг репликации** — насколько фолловер отстаёт от лидера. Высокий лаг вызывает сжатие ISR. Не чините лаг включением unclean election.

**Unclean leader election** значит, что Kafka может выбрать лидера, которого нет в ISR. Эта реплика отстаёт. Записи, которые существовали только на старом лидере, могут исчезнуть из журнала. Консьюмеры могут увидеть откат.

Безопасное значение по умолчанию — отказывать в unclean election. Если ни один участник ISR не жив, партиция остаётся офлайн, пока не вернётся синхронная реплика. Этот простой лучше тихой потери данных для важных данных.

Имя конфигурации — `unclean.leader.election.enable`. Задайте `false` для важных кластеров. KRaft не меняет эту опасность. Контроллер всё ещё может выбрать лидера вне ISR, если вы это разрешите.

Когда ISR меньше списка реплик, партиция **недореплицирована**. Тема 10 покрывает эксплуатацию этого алерта.

## Контроллер KRaft (не запускайте новые кластеры на ZooKeeper)

**Контроллер** управляет метаданными кластера: топиками, назначениями партиций, выборами лидеров и членством брокеров.

**KRaft (используйте это).** Kafka хранит метаданные в журнале Raft на узлах контроллеров. Вы форматируете хранилище идентификатором кластера. Запускаете один или несколько контроллеров. Продакшен-кластер использует нечётное число выделенных контроллеров (например 3). Кластер на ноутбуке может использовать совмещённые процессы брокер+контроллер.

KRaft не использует ZooKeeper. Новые версии Kafka не запускают ZooKeeper. Kafka 4.0 и позже убирают ZooKeeper. Учите только KRaft.

**Старый ZooKeeper (не используйте для новой работы).** Старые кластеры хранили часть метаданных в ZooKeeper. Учебники того времени сначала запускают процесс ZooKeeper. Игнорируйте эти шаги, когда строите новый кластер. Если поддерживаете старый кластер, следуйте официальному руководству миграции на KRaft. Не проектируйте новые системы на ZooKeeper.

Контроллер — не то же самое, что лидер партиции. Лидер партиции обрабатывает produce и fetch для одной партиции. Контроллер назначает этого лидера.

Когда активный контроллер падает, кворум KRaft выбирает нового контроллера. Операции метаданных кратко паузятся. Данные партиций на брокерах остаются.

KRaft не заменяет журналы партиций. Данные партиций по-прежнему живут в `log.dirs`. KRaft не заменяет ISR или репликацию.

Инструменты admin используют `--bootstrap-server`. Не используйте старые флаги ZooKeeper на новых кластерах.

#### Сложные практические задания

1. Запустите кластер KRaft из трёх контроллеров (или задокументируйте файл Compose). Остановите активного контроллера. Подтвердите, что отправка в топик всё ещё работает после того, как новый контроллер активен.
2. Напишите лист установки «новый кластер» на одну страницу, который никогда не упоминает команду старта ZooKeeper, кроме сноски «не делайте этого».

## Повторение темы

Эти вопросы не повторяют вопросы разделов выше. Они покрывают всю тему.

### Вопросы

#### Теоретические вопросы

1. Опишите жизнь записи от добавления в активный сегмент до удаления или компакции.
2. Как сворачивание сегмента, ретеншн и поток cleaner зависят друг от друга?
3. Опишите устойчивую отправку: лидер, ISR, `min.insync.replicas`, `acks=all`.
4. Почему unclean leader election — функция потери данных, а не высокой доступности?
5. Какие две системы хранения есть в кластере KRaft (метаданные против журналов партиций)?

#### Простые практические задания

1. Создайте `store.review` с коротким ретеншном по времени. Отправьте пять записей. Опишите конфигурацию топика. Выделите политику очистки и ключи ретеншна.
2. Напишите шпаргалку на одну страницу: сегмент, ретеншн, compact, томбстоун, ISR, min ISR, unclean election, контроллер KRaft.
3. Опишите реплицируемый топик. Выделите лидера, реплики, ISR и min ISR, если показано.
4. Нарисуйте compact+delete на оси времени для одного неиспользуемого ключа и одного горячего ключа.

#### Средние практические задания

1. Напишите скрипт, который создаёт компактируемый топик, отправляет ключи, отправляет томбстоун и читает с начала.
2. Создайте топик с RF 3 и min ISR 2 на трёхброкерном кластере, если он есть. Пишите. Остановите один брокер. Пишите снова. Опишите ISR после каждого шага.
3. Сопоставьте каждый подраздел с одним официальным ключом конфигурации.

#### Сложные практические задания

1. Соберите маленькую программу «таблица из компактируемого топика». Перезапустите её. Подтвердите, что она перестраивается из журнала. Затем отправьте томбстоун и подтвердите, что ключ исчез.
2. Напишите продакшен-стандарт хранения: значения по умолчанию для потоков событий против changelog, формула диска с репликами, unclean election выключен, только KRaft и запрет ручного удаления файлов.

# 8. Хеш-таблицы

## Описание

Хеш-таблица отображает ключ в значение за среднее константное время. Эта тема объясняет хеш-функции, коллизии, цепочки, открытую адресацию, коэффициент заполнения, правила ключей и стоимость худшего случая. Завершите эту тему после массивов и списков. Вы используете хеш-таблицу как множество и как отображение в следующей теме.

Используйте один термин для каждого понятия. **Ключ** — имя для поиска. **Хеш-функция** отображает ключ в целое. **Корзина** — слот в массиве таблицы. **Коллизия** происходит, когда два ключа отображаются в одну корзину. **Коэффициент заполнения** — n, делённое на число корзин.

---

## Хеш-функция

**Хеш-функция** h отображает ключ в целое. Таблица использует `index = h(key) mod m`, когда в таблице m корзин. Некоторые таблицы используют битовую маску, когда m — степень 2.

Хеш-функция должна быть **детерминированной**. Один и тот же ключ должен давать один и тот же хеш, пока ключ живёт в таблице.

Хеш-функция должна использовать полный ключ (или определённую часть ключа). Если вы хешируете только первую букву строки, многие ключи сталкиваются.

```text
h("cat")  →  81321
index     →  81321 mod m
```

```go
// Go: you do not call the map hash; the runtime hashes the key
m := map[string]int{"cat": 1}
```

```python
# Python: hash(obj) for a hashable object
h = hash("cat")
```

Языковой хеш часто не криптографический хеш. Не используйте хеш таблицы как хеш пароля. Хеш таблицы — для распределения в памяти.

Хороший хеш быстрый. Медленный хеш может доминировать в стоимости поиска.

Целые ключи могут использовать функцию смешивания, чтобы близкие целые не все попадали в близкие корзины. Строковые ключи смешивают символы. Точное смешивание — более поздняя инженерная тема. Эта тема требует идею: отобразить ключ в целое, затем в корзину.

## Равномерность и коллизии

**Равномерность** означает, что ключи распределяются по корзинам. Каждая корзина получает около n / m ключей, если хеш равномерный.

**Коллизия** происходит, когда два разных ключа дают один и тот же индекс корзины. Коллизии нормальны. Вы должны разрешать коллизии. Вы не можете предполагать, что h идеальна для всех ключей.

```text
m = 4
h(alice) mod 4 = 1
h(bob)   mod 4 = 1   ← collision
```

Если хеш не равномерный, некоторые корзины получают длинные цепочки. Поиск становится медленным.

**Противник** может выбрать ключи, которые сталкиваются, если хеш предсказуем и таблица открыта для недоверенных ключей. Некоторые языки рандомизируют семя на процесс. Это семя усложняет атаки коллизиями.

Два разных ключа могут иметь одно и то же целое хеша до mod. Это событие тоже коллизия. Таблица всё равно сравнивает ключи на равенство. Хеш только выбирает корзину.

Равенство и хеш должны согласовываться. Если два ключа равны, у них должен быть один и тот же хеш. Если два ключа не равны, у них обычно должны быть разные хеши. Они всё ещё могут столкнуться.

## Раздельное связывание

**Раздельное связывание (separate chaining)** хранит список в каждой корзине. Когда два ключа сталкиваются, оба ключа сидят в одном списке.

Поиск хеширует ключ, выбирает корзину, затем обходит список. Обход сравнивает ключи.

Вставка хеширует ключ, находит корзину, затем добавляет узел, если ключ новый. Если ключ существует, вы обновляете значение.

Удаление находит ключ в списке корзины и удаляет узел.

```text
buckets
  0:  → ("ab", 1)
  1:  → ("cd", 2) → ("xy", 3)
  2:  empty
  3:  → ("zz", 4)
```

Если хеш равномерный и m около n, каждый список короткий. Средний поиск — Θ(1). Если все ключи попадают в одну корзину, поиск — Θ(n).

Корзина может использовать динамический массив вместо связного списка. Корзина-массив имеет лучшую локальность. Некоторые языки переключают длинную корзину на дерево. Это переключение — продвинутый дизайн.

Цепочки хорошо растут. Вы можете иметь n > m. Списки становятся длиннее. Вы всё равно меняете размер, чтобы держать коэффициент заполнения малым.

## Открытая адресация: линейное / квадратичное пробирование, Robin Hood (ознакомление)

**Открытая адресация** хранит каждый ключ в массиве таблицы. Списка узлов нет. Когда происходит коллизия, таблица пробует другой слот.

**Линейное пробирование** пробует index, index+1, index+2, ... и заворачивается. Линейное пробирование простое. Ключи образуют кластеры. Кластеры растут и замедляют пробу.

**Квадратичное пробирование** пробует смещения 1², 2², 3², ... (плюс базовый индекс). Квадратичное пробирование уменьшает часть кластеризации. Вы должны выбрать m и формулу так, чтобы посещать пустые слоты.

**Хеширование Robin Hood** — тема ознакомления. В Robin Hood ключ, который прошёл далеко, может вытеснить ключ, который прошёл коротко. Цель — более равномерные длины проб. Вам не нужно реализовывать Robin Hood в этой теме.

```text
linear probe, m = 8, start = 3
  try 3, 4, 5, 6, ... until empty or key found
```

Удаление труднее, чем в цепочках. Удалённый слот не может быть просто пустым, если цепочка проб должна продолжаться. Таблицы используют **надгробие (tombstone)** (метка удаления) или перехешируют кластер.

Открытая адресация нуждается в большем числе пустых слотов, чем цепочки. Высокий коэффициент заполнения даёт длинные пробы. Меняйте размер раньше, чем вы могли бы в цепочках.

Вы не должны хранить больше m ключей в простой открытой таблице. Ёмкость — m. Коэффициент заполнения должен оставаться ниже 1.

## Коэффициент заполнения и изменение размера

**Коэффициент заполнения** α — n / m. n — число ключей. m — число корзин (или слотов).

Когда α растёт, коллизии растут. Средний поиск становится медленнее. Таблица **меняет размер**: выделяет большее m и **перехеширует** все ключи.

```text
if n / m > max_alpha:
    new_m = next_size(m)   // often about 2 * m
    new_table = array of new_m buckets
    for each key in the old table:
        insert key into new_table
```

Типичный max_alpha для цепочек — около 0.75 до 1.0. Типичный max_alpha для открытой адресации ниже, например 0.5 до 0.7.

Изменение размера — Θ(n). Изменение размера редко, если m растёт геометрически. Амортизированная вставка может остаться Θ(1) в среднем.

Языковое отображение меняет размер за вас. Вы всё равно выбираете начальный размер, если знаете n. Go `make(map[K]V, n)` — подсказка. Python `dict` растёт сам.

После изменения размера индексы меняются. Вы не должны хранить индекс корзины как долгоживущий указатель в таблицу. Храните ключ.

## Ключи должны быть хешируемыми и стабильными

Ключ должен быть **хешируемым**. Язык может вычислить h(key). Ключ также должен поддерживать равенство.

Ключ должен быть **стабильным**, пока сидит в таблице. Если вы меняете поле, которое использует хеш, ключ в неверной корзине. Поиск падает. Таблица испорчена.

```text
bad idea
  put object in map
  change object.id
  look up by the new id  →  miss
```

Используйте неизменяемые ключи, когда можете. Строки и числа безопасны. Изменяемый список — плохой ключ. Python не позволяет список как ключ dict. Кортеж чисел разрешён.

В Go ключи map должны быть сравнимыми. Срезы, map и функции не сравнимы. Структуры сравнимы, если все поля сравнимы. Не мутируйте поле структуры, которое использовали как ключ.

Если два объекта сравниваются как равные, у них должен быть один и тот же хеш. Если вы пишете своё равенство, вы должны написать согласованный хеш.

Ключ-float может быть проблемой. NaN не равен NaN по обычным правилам IEEE. Избегайте ключей-float.

## Средняя O(1) против деградации худшего случая

Хеш-таблица даёт **среднюю Θ(1)** find, insert и delete. Эта оценка нуждается в равномерном хеше, ограниченном коэффициенте заполнения и простом смешивании ключа.

**Худший случай** find — Θ(n). Все ключи могут попасть в одну цепочку. Открытая адресация также может деградировать до длинной пробы многих слотов.

Деградация случается, когда:

- хеш константный или очень слабый
- противник выбирает сталкивающиеся ключи
- вы никогда не меняете размер
- почти каждый слот полон (открытая адресация)

```text
average (good hash, bounded α):  Θ(1)
worst case:                      Θ(n)
```

Сбалансированное дерево-отображение — Θ(log n) в худшем случае. Если нужна оценка худшего случая, используйте дерево. Если нужна скорость на типичных данных, используйте хеш-таблицу.

Некоторые хеш-таблицы откатываются к дереву в длинной корзине. Этот дизайн улучшает худший случай до Θ(log n) для этой корзины. Вы можете считать этот дизайн ознакомлением.

Не пишите «O(1)» без «средняя», когда описываете хеш-таблицу. Пишите «средняя Θ(1), худшая Θ(n)», если реализация не даёт более сильный худший случай.

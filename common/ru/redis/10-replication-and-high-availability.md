# 10. Репликация и высокая доступность

## Описание

Redis может копировать данные с экземпляра primary на одну или несколько реплик. Эта тема покрывает `REPLICAOF`, асинхронный лаг, Redis Sentinel, повышение и устаревшие чтения с реплик.

Завершите эту тему до изучения Cluster. Cluster — система шардирования. Sentinel — система переключения при отказе для одного master (primary) и его реплик.

Используйте один термин для каждого понятия. Primary принимает записи. Реплика копирует primary и может обслуживать чтения. Лаг — задержка между записью на primary и той же записью на реплике. Sentinel — набор процессов, которые следят за Redis и могут повысить реплику. Повышение — превращение реплики в primary.

---

## Replica-of / `REPLICAOF`

`REPLICAOF host port` делает текущий экземпляр репликой этого primary. Реплика подключается, выполняет синхронизацию и затем применяет поток записей.

```text
REPLICAOF 127.0.0.1 6379
```

`REPLICAOF NO ONE` останавливает репликацию. Экземпляр становится автономным primary с данными, которые уже есть.

Старые документы и команды использовали `SLAVEOF`. Текущий Redis принимает `REPLICAOF`. Используйте `REPLICAOF` в новой работе. `INFO replication` всё ещё показывает поля вроде `role:master` и `role:slave` во многих версиях. Читайте имена полей, которые печатает ваша версия.

Первая синхронизация часто отправляет снимок (RDB) плюс журнал команд. Реплика загружает снимок и затем догоняет. Большой набор делает первую синхронизацию тяжёлой (CPU, диск, сеть).

По умолчанию реплика только для чтения (`replica-read-only yes`). Записи на реплике падают. Это то, что нужно. Не пишите на реплику.

Реплика может сохранять на диск. Персистентность на реплике независима от primary. Реплика — не резервная копия сама по себе, пока не скопируете файлы с хоста.

Топология этой темы: один primary, одна или несколько реплик. Не цепляйте много реплик, если не знаете лишний лаг. Redis также поддерживает реплику-реплики в некоторых схемах. Предпочитайте простое дерево для обучения.

`INFO replication` на primary перечисляет подключённые реплики. На реплике показывает хост primary, статус связи и поля смещения.

Аутентификация: реплика должна использовать пароль или пользователя, который требует primary (`masteruser` / `masterauth` в конфигурации). У TLS есть дополнительные настройки.

## Асинхронная репликация и лаг

Репликация Redis асинхронна в обычной схеме. Primary отправляет `OK` клиенту, когда запись в памяти primary (и после правил персистентности primary). Primary по умолчанию не ждёт реплику.

Реплика получает запись позже. Задержка — лаг. Лаг растёт, когда реплика медленная, сеть медленная или реплика занята загрузкой снимка.

`WAIT numreplicas timeout` на primary может ждать, пока хотя бы `numreplicas` реплик подтвердят запись, или пока не кончится таймаут. `WAIT` повышает шанс, что реплика имеет запись. `WAIT` — не полный синхронный коммит через отказы. Читайте страницу `WAIT` про пределы (и `WAITAOF` в Redis 7.2+).

Поля `INFO replication` вроде `master_repl_offset` и `slave_repl_offset` реплики (имена варьируются) помогают видеть расхождение. Sentinel и инструменты мониторинга тоже отслеживают лаг.

Если primary умрёт, реплика, которую вы повысите, может пропустить последние записи. Это цена асинхронной репликации. Приложение должно принять эту потерю или использовать `WAIT` и всё равно принять крайние случаи.

Не предполагайте, что чтение на реплике видит запись, которую тот же пользователь только что отправил на primary. Это устаревшее чтение (следующий раздел).

Персистентность на диске на primary и репликация на реплику — два пути. Можно потерять запись при сбое primary даже если реплика получила бы её мгновение спустя. Можно также сохранить на primary и всё ещё иметь отстающую реплику.

Держите реплику в том же регионе для низкого лага, если чтения должны быть достаточно свежими. Измеряйте лаг под нагрузкой.

## Redis Sentinel (мониторинг + переключение при отказе)

Redis Sentinel — отдельный процесс (или несколько процессов). Sentinel — не Cluster. Sentinel не шардирует ключи. Sentinel следит за именованным primary и его репликами.

Типичная лаборатория использует три процесса Sentinel. Они голосуют. Большинство должно согласиться, что primary недоступен. Один Sentinel затем начинает переключение: выбрать реплику, повысить её, перенастроить другие реплики и обновить имя primary.

Клиенты спрашивают Sentinel текущий адрес primary (`SENTINEL get-master-addr-by-name mymaster`). После переключения этот адрес меняется. Клиенты должны поддерживать Sentinel или использовать прокси, который это делает.

Sentinel мониторит:

- отвечает ли primary
- состояние реплики
- некоторую конфигурацию

Sentinel не делает репликацию синхронной. Переключение может сбросить последние асинхронные записи.

Вы настраиваете `sentinel monitor <name> <host> <port> <quorum>`. Кворум — число Sentinel, которые должны согласиться. Три Sentinel и кворум 2 — частая учебная схема.

Sentinel нужны достижимые сетевые пути к Redis и к другим Sentinel. Разделение мозга возможно, если сети разделяются плохо. Читайте официальную документацию Sentinel до промышленной среды.

Не запускайте один Sentinel и не называйте это высокой доступностью. Один Sentinel — один наблюдатель.

`INFO` на Redis недостаточно, чтобы видеть Sentinel. Используйте `redis-cli -p 26379 SENTINEL masters` (порт Sentinel по умолчанию — `26379`).

## Повышение реплики

Повышение превращает реплику в primary. После повышения этот экземпляр принимает записи. Другие реплики должны копировать с нового primary.

Ручное повышение (лаборатория, без Sentinel):

1. Подтвердите, что реплика настолько свежая, насколько можете проверить (`INFO replication`)
2. `REPLICAOF NO ONE` на выбранной реплике
3. Направьте приложения на новый primary
4. `REPLICAOF new-primary` на других репликах
5. Держите старый primary выключенным или пересоберите его как реплику, чтобы избежать двух писателей

Если старый primary возвращается как primary, у вас два писателя (разделение мозга). Данные расходятся. Sentinel пытается избежать этого, перенастраивая старый primary как реплику. Ручные операции должны быть осторожны.

Повышение Sentinel выбирает реплику по правилам (приоритет, смещение, run id). `replica-priority 0` значит «никогда не повышать эту реплику». Используйте это для реплики, которая только резервная копия или в далёком регионе.

Повышение не воспроизводит потерянные асинхронные записи с мёртвого primary, если эти записи никогда не достигли реплики. Клиенты, которые писали и получили `OK`, всё ещё могут потерять эти ключи.

После повышения репликам старого primary нужна новая топология. Клиенты, которые закэшировали старый IP, должны обновить (Sentinel, DNS или прокси).

Проверяйте повышение в лаборатории. Измеряйте простой (время, когда записи падают). Измеряйте потерю данных счётчиком записей.

Не повышайте реплику, которая далеко отстала, потому что «это единственная, которая жива», без решения. Можно потерять большой суффикс записей.

## Чтение с реплик (устаревшие данные)

Можно отправлять команды чтения на реплику. Реплика отвечает из своей копии. Эта копия может отставать от primary. Приложение может видеть старые значения.

Это устаревшее чтение. Устаревшие чтения приемлемы для некоторых панелей, таблиц лидеров и заполнений кэша. Они неприемлемы для «прочитать свою запись» (пользователь сохраняет профиль, а следующая страница всё ещё показывает старый город).

Шаблоны:

- Все чтения и записи на primary — просто, нет устаревших чтений реплики
- Записи на primary, чтения на реплики — масштабировать трафик чтения, принять устаревание
- Читать свою запись с primary, другие чтения с реплик — смешанный

Клиент должен знать, какое соединение — primary. После переключения старый primary может стать репликой. Запись на старый адрес должна упасть, если узел теперь только для чтения. Чтение отстающей реплики всё ещё может быть устаревшим.

`WAIT` после записи может снизить шанс, что чтение реплики устарело, если затем читаете эту реплику. Это не чинит каждую гонку.

У реплик может быть разный лаг. Не балансируйте чтения и не предполагайте, что все реплики имеют те же данные в тот же момент.

Мониторьте лаг реплик. Убирайте реплику из пула чтения, когда лаг превышает бюджет (например 1 секунда).

`READONLY` — команда Cluster для реплик. На топологиях Sentinel обычное управление — `replica-read-only`. Не путайте два.

# 18. Поиск и смежные инструменты

## Описание

Эта тема показывает инструменты MongoDB, которые сидят рядом с обычными коллекциями. **Atlas Search** использует Lucene для полнотекстового поиска. **Коллекции временных рядов** хранят измерения, у которых есть время. **GridFS** хранит файлы, которые превышают лимит размера документа. MongoDB может действовать как **кэш**, но **Redis** обычно лучший кэш. Сначала завершите запросы, индексы и агрегацию.

Используйте один термин для каждого понятия. **Поисковый индекс** — индекс Lucene, который ведёт Atlas. **Коллекция временных рядов** — тип коллекции, который кладёт измерения в корзины. **GridFS** — соглашение драйвера, которое использует коллекции `files` и `chunks`. **Кэш** — быстрое хранилище данных, которыми уже владеет другая система.

Выберите инструмент, который соответствует задаче. Не используйте GridFS для JSON на 1 KB. Не используйте Atlas Search для одного равенства по `_id`.

## Atlas Search (Lucene)

**Atlas Search** — поисковый движок, который Atlas строит на **Apache Lucene**. Вы создаёте поисковый индекс на коллекции. Запрашиваете стадией агрегации `$search` (и родственными стадиями вроде `$searchMeta`).

Atlas Search — не то же самое, что текстовый индекс MongoDB (`$text`). Текстовый индекс — возможность сервера с ограниченным скорингом и поддержкой языков. Atlas Search сильнее для:

- Полнотекстовой релевантности
- Нечёткого совпадения
- Автодополнения
- Фасетов (с возможностями фасетов Search)
- Анализаторов (как текст делится на токены)

Вы задаёте отображения. Динамические отображения индексируют многие поля. Статические отображения именуют поля и анализатор. Статические отображения проще контролировать.

Типичный конвейер:

```javascript
db.articles.aggregate([
  {
    $search: {
      index: "default",
      text: { query: "replica set", path: "body" }
    }
  },
  { $limit: 20 },
  { $project: { title: 1, score: { $meta: "searchScore" } } }
])
```

Поиск конечно согласован с коллекцией. Запись не всегда в индексе в ту же миллисекунду. Проектируйте UI на короткую задержку или обновляйте после известного ожидания в инструментах администратора.

Atlas Search работает на Atlas. Community Server не включает Atlas Search. Альтернативы на самоуправляемых стеках — внешний поисковый движок плюс CDC (тема 15).

Не создавайте поисковый индекс на каждом поле «на всякий случай». Индексы стоят памяти и времени построения.

Не используйте `$search` как первую идею для `{ _id: id }`. Используйте `find`.

Читайте документацию Atlas Search своей версии Atlas. Операторы меняются.

## Коллекции временных рядов

**Коллекция временных рядов** хранит документы, у которых есть **поле времени** и обычно **поле мета**. MongoDB группирует документы в **корзины** на диске. Раскладка корзин экономит место и может ускорить некоторые диапазонные сканы по времени.

Создание:

```javascript
db.createCollection("readings", {
  timeseries: {
    timeField: "ts",
    metaField: "sensorId",
    granularity: "seconds"
  }
})
```

Каждое измерение в API всё равно документ. Вставляете одно показание на событие. Корзинами вручную не управляете.

Хорошее соответствие:

- Датчики
- Метрики
- Потоки кликов или событий с ясной меткой времени
- Данные, которые часто запрашивают по диапазону времени и по устройству или хосту

Плохое соответствие:

- Документы, которые часто обновляете на месте
- Сильно реляционные операционные данные
- Данные без настоящего поля времени

Вторичные индексы разрешены с лимитами, зависящими от версии. Часто индексируют поле мета и поле времени.

TTL на коллекциях временных рядов может удалять старые корзины. Читайте текущую страницу TTL для временных рядов.

Нельзя считать коллекцию временных рядов обычной коллекцией для каждой команды. Некоторые шаблоны update и delete ограничены. Читайте страницу ограничений до миграции горячей коллекции.

Не храните огромный неограниченный массив показаний внутри одного документа датчика. Это антипаттерн из моделирования. Используйте коллекцию временных рядов или шаблон bucket, который контролируете.

## GridFS (большие файлы)

Лимит размера документа — 16 MB. **GridFS** хранит больший файл как много **чанков** плюс один документ метаданных **file**.

Коллекции по умолчанию:

- `fs.files` — имя файла, длина, тип содержимого, дата загрузки
- `fs.chunks` — `{ files_id, n, data }`, где `data` — двоичный чанк

Размер чанка по умолчанию — 255 KB во многих версиях. Драйверы реализуют загрузку и скачивание. В обычном коде приложения чанки вручную не собираете.

```javascript
// driver APIs differ; mongosh may use a GridFSBucket helper
```

Используйте GridFS, когда:

- Файл нужно держать в MongoDB (простые операции, один домен резервной копии)
- Файл больше 16 MB или нужен потоковый API
- Принимаете резервную копию базы и цену двоичных данных

Не используйте GridFS, когда:

- Доступно объектное хранилище (S3 или аналог) и файлов много или они велики
- Нужен только URL к CDN
- Файл — несколько килобайт (храните поле BinData или URL)

Файлы GridFS — не обычные документы для `find` всего файла. Метаданные запрашиваете в `fs.files`. Чанки стримите через драйвер.

Индексы: GridFS нужны индексы, которые создаёт драйвер (`files_id` + `n` уникальный на чанках). Не удаляйте их.

Размер резервной копии растёт с каждым файлом. Дамп GridFS тяжёлый. Снимки включают двоичные данные.

У Atlas нет особого «продукта GridFS». Это всё ещё коллекции. Лимит 16 MB всё равно применяется к каждому документу чанка, что нормально при 255 KB.

## MongoDB как кэш (обычно Redis лучше)

**Кэш** держит копии данных для быстрых чтений. Источник истины часто другое хранилище (или та же коллекция MongoDB).

MongoDB может быстро обслуживать горячие документы, когда они помещаются в ОЗУ. Это база с тёплым кэшем, не специализированный продукт кэша.

**Redis** (или похожее хранилище в памяти) обычно лучше как кэш, потому что:

- TTL и политики вытеснения — первоклассные
- Задержка обычно ниже для маленьких ключей
- Можно вытеснять без истории контрольных точек WiredTiger
- Многие шаблоны кэша (блокировки, счётчики, блобы сессий) уже документированы для Redis

Когда MongoDB достаточно без кэша:

- Рабочий набор помещается в ОЗУ
- Find по `_id` или покрытый запрос уже выдерживает SLA
- Не хотите вторую систему

Когда кэш перед MongoDB помогает:

- Горячий ключ, который иначе бил бы по одному документу
- Вычисленная агрегация, которая дорога и может быть устаревшей на секунды
- Данные сессии, которые не хотите в основном рабочем наборе

Если всё же используете MongoDB как коллекцию кэша:

- Задайте TTL-индекс по `expiresAt`
- Держите документы маленькими
- Примите, что TTL не мгновенен до секунды
- Не считайте это единственной копией данных, которые нельзя восстановить

Не добавляйте Redis «потому что все так делают». Измеряйте. Не используйте MongoDB как кэш «чтобы избежать Redis», если затем плохо реализуете вытеснение.

Не храните сессии в огромном документе MongoDB, который растёт без TTL.
